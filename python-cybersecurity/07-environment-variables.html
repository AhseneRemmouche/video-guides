Environment variables and their security importance

Reading configuration and secrets from the environment instead of hard-coding them.

▶ Watch this part (00:39:14)

Security tools constantly need secrets: an API key for a threat-intelligence feed, a token for a chat bot, a database password. The wrong place to keep those is inside your code. This step shows the right place: an environment variable, read at runtime with the os module so the secret never lives in the file you commit.

What the presenter explains

Every running program is handed a small set of named values by the operating system when it starts. These are environment variables. They hold things like your user name, your home folder, and anything you choose to put there. The course introduces them (at 39:30) as "configuration that lives outside the code", and then makes the security point (at 39:14): a key you type into a script gets copied everywhere the script goes, including into git history, screenshots, and pasted snippets. A key read from the environment does not.

In Python you reach these values through os.environ, which behaves like a dictionary of strings. The presenter is careful to use os.environ.get(name) rather than os.environ[name] (at 40:05): the .get form returns None or a default you choose when the variable is missing, instead of crashing the whole tool with a KeyError.

Do this

  1. Create os/04_env_and_path.py in your project (the same file is reused in Step 09 for the PATH half).
  2. In your terminal, set a throwaway secret so you can see it being read. On Windows PowerShell: $env:MY_TOOL_API_KEY = "demo-123". On Linux or macOS: export MY_TOOL_API_KEY=demo-123.
  3. Run the script in that same terminal window: python os/04_env_and_path.py. Setting the variable in one window does not affect other windows, so the variable and the run must share a terminal.
  4. Read the first lines of output: your user name, your home folder, and the API key. Open a fresh terminal without setting the variable and run again to see the safe default appear instead.

The full file

This is our own, runnable version of what the video demonstrates. The top half (lines 10–20) is the environment-variable lesson for this step; the PATH half (lines 22–31) is explained in Step 09.

"""Environment variables and the system PATH.

Environment variables hold configuration the operating system and other programs
read at runtime: the current user name, the home folder, and - importantly for
security - secrets like API keys that should NEVER be hard-coded in source.

The PATH variable is the list of folders the OS searches when you type a command
like `python` or `nmap`. Reading it tells an analyst which tools are installed.
"""
import os

# Read a single variable. os.environ.get returns None (not a crash) if it is unset,
# and lets you supply a default. This is how tools read secrets safely.
print("User:", os.environ.get("USERNAME") or os.environ.get("USER"))
print("Home:", os.environ.get("HOME") or os.environ.get("USERPROFILE"))

# The right way to read a secret: from the environment, with a clear fallback,
# so the key is never written in the code or committed to git.
api_key = os.environ.get("MY_TOOL_API_KEY", "<not set>")
print("API key loaded from environment:", api_key)

# PATH is one long string of folders joined by a separator that differs per OS:
#   ';' on Windows, ':' on Linux/macOS.  os.pathsep is that separator.
raw_path = os.environ.get("PATH", "")
folders = raw_path.split(os.pathsep)
print(f"\nPATH has {len(folders)} folders. First five:")
for folder in folders[:5]:
    print("  ", folder)

# Sort them alphabetically - a small example of processing system data.
print("\nAlphabetically first folder on PATH:", sorted(folders)[0] if folders else "none")

New to environment variables? What they are and why they matter

An environment variable is a named piece of text the operating system keeps for each running program. Think of it as a note the system pins to your program when it starts. Programs read these notes to learn things they should not hard-code: where the user's home folder is, what language to display, or where to find a secret. They are set in the terminal, in your shell profile, or by a tool that launches your program, and they disappear when you close that terminal unless you make them permanent.

Why hard-coding a secret is dangerous

If you write api_key = "sk-live-abc123" in a file, that string travels with the file forever. It lands in your git history even after you delete the line, it appears in error logs and stack traces, and it shows up in any screenshot or snippet you share while asking for help. Attackers scan public code for exactly these patterns. Reading the key from the environment keeps the secret out of the file entirely, which is why it is a core cybersecurity habit.

Where should the secret actually live?

For quick work, set the variable in your terminal session as shown above. For a project, a common pattern is a .env file that you list in .gitignore so it is never committed, loaded into the environment when the tool starts. The key point stays the same: the value lives outside the tracked source, and the code only ever reads it by name.

What you should see. With no secret set, the first lines of output look like this (your user and home folder will differ): 
User: you
Home: C:\Users\you
API key loaded from environment: <not set>
The <not set> is the default from line 19, proving the variable was missing and the tool did not crash. Set MY_TOOL_API_KEY first and that last line shows your value instead.
Common mistakes.
  • Setting the variable in one terminal and running the script in another. The value only exists in the window where you set it; run both in the same window.
  • Using os.environ["MY_TOOL_API_KEY"] with square brackets. If the variable is unset this raises KeyError and stops the tool. Prefer .get with a default.
  • Expecting the variable to survive after you close the terminal. A plain export or $env: lasts only for that session; make it permanent in your shell profile or a .env file if you need it again.
  • Printing a real secret to the screen or into a log. Fine for this demo value, dangerous for a live key.
Recap
  • Environment variables are per-program values the operating system supplies at runtime.
  • Read them with os.environ.get(name, default) so a missing value gives a safe default, not a crash.
  • Keep secrets like API keys in the environment, never hard-coded, so they stay out of git, logs and screenshots.
  • Set a variable and run the script in the same terminal; the value is scoped to that session.
