Imported DLLs and functions as behaviour clues

Reading the import table to predict what a binary will do, and flagging suspicious APIs.

▶ Watch this part (03:18:18)

A program has to announce the external functions it borrows from Windows. That announcement, the import table, is a preview of behaviour: before running anything, you can read which system functions a file intends to call and make an educated guess about what it does. This step reads the import table with pefile and flags functions that malware commonly abuses.

Still a benign file. We read the same trustworthy sample_app.exe as the previous step. The value of a clean file here is the contrast: you see what an ordinary program's imports look like, so an unusual list in a real sample stands out.

What this step does

The presenter moves from a file's shape to its intentions (at 3:18:18). Our script, 16_imports.py, lists every DLL the file imports, shows a few function names from each, and checks every imported function against a small watch-list of APIs that are frequently seen in malicious code. It prints a clear note when none of them are present.

New to the import table? What it is

Windows programs rarely do everything themselves. To open a file, allocate memory or talk to the network, they call functions that live in system libraries (DLLs) such as KERNEL32.dll. So that Windows can wire those calls up when the program loads, the program lists the functions it needs, grouped by the DLL that provides them. That list is the import table, and because it is declared in the file, you can read it statically.

What is a DLL?

A DLL (Dynamic-Link Library) is a file of reusable functions that many programs share. KERNEL32.dll provides core operating-system calls (files, memory, processes); SHLWAPI.dll provides small path- and string-handling helpers. Importing from these two is completely ordinary.

Why imports are such a strong clue

Some functions are almost a signature of a technique. A file importing CreateRemoteThread together with VirtualAllocEx and WriteProcessMemory is very likely injecting code into another process. One importing URLDownloadToFileA is probably fetching a payload from the internet; one importing CryptEncrypt might be ransomware. None of these functions is malicious on its own, plenty of good software uses them, but seeing several of them in an unfamiliar file is a strong reason to look harder. A backdoor, for instance, often imports functions for running shell commands and opening network connections.

Run the import reader

  1. From code/malware/, run python 16_imports.py sample_app.exe.
  2. Read the DLL list and the "Suspicious APIs present" summary at the bottom.
  3. With no argument it defaults to your own Python interpreter, another safe file to inspect.
"""Reading the import table: which Windows functions a binary plans to call.

A program declares the external functions it needs in its import table (grouped by
the DLL that provides them). That list is a behaviour preview: a program importing
CreateRemoteThread + VirtualAllocEx is probably doing code injection; one importing
URLDownloadToFile is probably fetching a payload. We flag known-suspicious APIs.

Usage:  python 16_imports.py <path-to-exe-or-dll>
"""
import sys
import pefile

# API name -> what it is often used for by malware (also used legitimately!).
SUSPICIOUS = {
    "VirtualAlloc": "allocate executable memory",
    "VirtualAllocEx": "allocate memory in ANOTHER process (injection)",
    "CreateRemoteThread": "run code in another process (injection)",
    "WriteProcessMemory": "write into another process (injection)",
    "WinExec": "launch a program",
    "ShellExecuteA": "launch a program/URL",
    "URLDownloadToFileA": "download a file from the internet",
    "RegSetValueExA": "write to the registry (persistence)",
    "CryptEncrypt": "encrypt data (ransomware)",
    "InternetOpenA": "open an internet connection",
}


def analyze(path: str):
    pe = pefile.PE(path)
    pe.parse_data_directories()               # needed to populate imports

    flagged = []
    if not hasattr(pe, "DIRECTORY_ENTRY_IMPORT"):
        print("No import table found.")
        pe.close()
        return

    print(f"Imported DLLs and a sample of their functions for {path}:\n")
    for entry in pe.DIRECTORY_ENTRY_IMPORT:
        dll = entry.dll.decode("latin-1")
        funcs = [imp.name.decode("latin-1") for imp in entry.imports if imp.name]
        print(f"  {dll}  ({len(funcs)} functions)")
        print("    e.g.", ", ".join(funcs[:6]) or "(ordinals only)")
        for fn in funcs:
            if fn in SUSPICIOUS:
                flagged.append((dll, fn))

    print("\nSuspicious APIs present:")
    if not flagged:
        print("  none from our watch-list (this looks like an ordinary program).")
    for dll, fn in flagged:
        print(f"  [!] {fn} ({dll}) - {SUSPICIOUS[fn]}")
    pe.close()


if __name__ == "__main__":
    target = sys.argv[1] if len(sys.argv) > 1 else sys.executable
    analyze(target)

What does "flagging an API" prove?

On its own, nothing, and that is important. A flag means "this function is worth your attention", not "this file is malware". Web browsers download files; installers write to the registry; backup tools encrypt data. The watch-list narrows thousands of imports down to the handful a human should think about, in the context of everything else the file shows. It is triage, not a verdict.

  SHLWAPI.dll  (3 functions)

  none from our watch-list (this looks like an ordinary program).
Two DLLs, KERNEL32.dll (83 functions) and SHLWAPI.dll (3), and no watch-list hits. That is exactly what a normal utility looks like, which is why it is a useful baseline.
Common mistakes.
  • Skipping pe.parse_data_directories(). Without it the import table is never populated, and the script sees no imports at all.
  • Reading imports as guilt. Zero watch-list hits is reassuring but not a clean bill of health; one or two hits is a prompt to investigate, not a conviction.
  • Expecting names for every import. Some functions are imported by ordinal (a number) with no name; the if imp.name check simply skips those.
  • A file packed to hide its real code can show a tiny, misleading import table. Combine this with the entropy reading from the previous step.
Recap
  • The import table lists the Windows functions a file plans to call, grouped by DLL.
  • pe.parse_data_directories() must run before the imports are readable.
  • Our benign file imports only KERNEL32.dll and SHLWAPI.dll, with no watch-list APIs.
  • Suspicious APIs are a prompt for a human to look closer, never a verdict by themselves.
