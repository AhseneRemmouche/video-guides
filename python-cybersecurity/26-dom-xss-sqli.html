Detecting XSS and SQLi with a headless browser (authorized)

Confirming that injected input becomes live DOM, and watching for database errors, on your lab target.

▶ Watch this part (05:35:03)

The final chapters of the course (5:35:03) use a real browser to confirm XSS and watch for SQL injection. Step 13 detected these with requests by reading raw HTML; here we go one level deeper. A browser does not just receive HTML — it builds a live DOM and runs scripts. That lets us confirm whether injected input actually becomes a working element, which is stronger evidence than a text match.

Authorized testing only. This runs against the local lab (lab_server.py on 127.0.0.1). It confirms findings and gives fixes; it does not exploit anything or target third parties. See Rules of engagement.

Why confirm in the DOM, not just the text

With requests, "my marker appeared in the response" is a strong hint of reflected XSS, but the input might sit somewhere the browser treats as plain text. The decisive question is: did the browser turn my input into a real element? If we send <b id=...> and the browser then reports a live element with that id, the HTML was injected, not escaped — a reflected-XSS sink, confirmed. We still use a harmless <b> tag, never a script.

The confirmation script

It uses a marker built from an MD5 hash so the id is unique and cannot clash with text already on the page. Then it asks the browser whether an element with that id exists (XSS) and whether a database error reached the rendered page (SQLi).

"""Authorized testing: confirming reflected XSS and SQL errors in a real browser.

requests shows the raw HTML; a browser shows what actually renders and runs. For
XSS, the question is not just "did my text come back?" but "did it become a live
DOM element?". Playwright lets us check the rendered DOM. For SQL injection we
watch the page/response for the tell-tale database error. Lab target only.
Start lab_server.py first.
"""
import hashlib
from playwright.sync_api import sync_playwright

BASE = "http://127.0.0.1:8099"

# A unique marker derived from a hash, so we can be sure any match is ours and not
# some coincidental text already on the page.
MARKER = "x" + hashlib.md5(b"guide-marker").hexdigest()[:10]


def test_reflected_xss(page):
    # Put the marker inside a tag so, IF unescaped, it becomes a real <b> element.
    payload = f"<b id={MARKER}>hi</b>"
    page.goto(f"{BASE}/search?q={payload}")
    # Did a real element with our id appear in the DOM? That means the HTML was
    # injected, not escaped - a confirmed reflected-XSS sink.
    injected = page.locator(f"#{MARKER}").count() > 0
    print("Reflected XSS on /search:",
          "CONFIRMED - our tag became a live DOM node" if injected
          else "not reflected as HTML (safe)")


def test_sql_error(page):
    page.goto(f"{BASE}/product?id=10'")
    body = page.locator("body").inner_text()
    leaked = "SQL" in body
    print("SQL error on /product:",
          "CONFIRMED - database error leaked to the page" if leaked
          else "no error leaked")


if __name__ == "__main__":
    with sync_playwright() as p:
        browser = p.chromium.launch(headless=True)
        page = browser.new_page()
        test_reflected_xss(page)
        test_sql_error(page)
        browser.close()
    print("\nConfirmed findings go in a report with remediation advice"
          " (output-encode user input; use parameterised SQL queries).")

What is the DOM, exactly?

When a browser loads a page it parses the HTML into a tree of objects called the Document Object Model. Scripts and tools query that tree ("is there an element with id X?"). Checking the DOM tells you what the page actually became, not just what bytes arrived — which is why it confirms XSS more reliably than a text search.

What you should see. Against the lab, both checks confirm, and the script ends with the remediation reminder: 
Reflected XSS on /search: CONFIRMED - our tag became a live DOM node

Common mistakes. Forgetting to start the lab, or forgetting playwright install chromium (Step 22). Reading "CONFIRMED" as permission to do more — confirmation is where testing stops and reporting begins. Using a real <script> payload instead of the harmless <b> marker: unnecessary and reckless, even on your own lab.

Closing the loop: the fixes

Both findings have well-known remedies. For XSS, output-encode every piece of user input before placing it in a page (and add a Content-Security-Policy as defence in depth). For SQL injection, use parameterised queries everywhere and never show raw database errors to users. A confirmed finding plus a clear fix is the deliverable that makes you useful to a team — and it is where this guide ends.

Recap
  • A real browser confirms XSS by showing whether input became a live DOM element.
  • A hash-based marker guarantees any match is yours.
  • The same run watches for a leaked SQL error on the rendered page.
  • Finish every finding with its fix: output encoding and a CSP for XSS, parameterised queries for SQLi.
