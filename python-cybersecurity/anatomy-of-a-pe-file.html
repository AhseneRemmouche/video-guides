Anatomy of a Windows PE file

What is inside an .exe: the MZ/PE headers, sections, the import table and strings - what pefile reads.

Module 3 reads Windows programs without running them. To make sense of what the tools report, it helps to know what is actually inside an executable. This primer is a tour of the PE (Portable Executable) format: the headers at the front, the sections that follow, the idea of entropy, the import table, and the readable strings scattered through it. It is lighter than a step; read it once and the hands-on steps will click.

What a PE file is

Every Windows .exe and .dll is stored in the PE format: a fixed, documented layout that tells Windows how to load and run the file. Because the layout is predictable, a library like pefile can read each part reliably. For a defender that is a gift: static analysis means reading all of this structure without ever executing the file, so you can learn a great deal in complete safety.

Why does an .exe still start with "MZ"?

The first two bytes of every PE are the letters MZ, the initials of a Microsoft engineer from the MS-DOS era, followed by the famous "This program cannot be run in DOS mode" message. It is a historical stub kept for compatibility. In practice it is a quick signature: if a file starts with MZ, a tool treats it as a Windows executable.

The headers: what the file says about itself

The PE and optional headers hold the facts you record first about any sample: the machine (which processor it targets, such as x64), the build timestamp (when the linker made it, a clue that can be forged), the entry point (where code would begin if run), and the image base (its preferred load address). None of this requires running the file; it is all written down in the headers.

Sections: where code and data live

After the headers come the sections, each a named region with its own job. You will meet the same handful again and again:

SectionWhat it holds
.textThe executable code, the program's instructions.
.rdataRead-only data: constants, string literals, and import/export information.
.dataVariables the program can read and change while running.
.rsrcResources such as icons, menus and version information.
.relocRelocation fix-ups used if the file loads at a different address.

Each section header records how big the region is in memory (virtual size) and on disk (raw size). When those two numbers disagree sharply, or when a section has an odd name, it is worth a closer look.

Entropy and packing

Entropy measures how random a chunk of bytes looks, from 0 (very regular) to 8 (indistinguishable from random). Ordinary code and text sit in the middle, roughly 4 to 6.5. Compressed or encrypted data sits near 8. Malware authors often pack their code, compressing or encrypting it so that scanners and analysts cannot read it directly; the packed code only unpacks in memory when the program runs. The tell-tale sign in static analysis is a code section with entropy close to 8, which is why the PE step prints an entropy column.

The import table: borrowed behaviour

Programs lean on the operating system for real work, calling functions that live in system libraries (DLLs) such as KERNEL32.dll. To let Windows wire those calls up, the PE lists the functions it needs, grouped by DLL. That list, the import table, is a behaviour preview you can read without running anything: a file importing download, process-injection or encryption functions is announcing what it can do. A benign utility, by contrast, imports a short, unremarkable set.

Strings: text hidden in the bytes

Finally, compiled files are full of readable text: URLs, file paths, error messages, registry keys. Pulling these strings out is often the single fastest way to grasp a sample's purpose, and the ones that look like URLs, IP addresses or crypto wallets become indicators you can search for elsewhere. Headers, sections, entropy, imports and strings together give you a rounded picture of a file, all gathered safely, without ever letting it run.

Recap
  • A PE file is headers that describe the program followed by sections that contain it.
  • The headers give machine type, build time, entry point and image base; sections such as .text and .rsrc hold code, data and resources.
  • Entropy near 8 in a code section hints at packing; the import table previews behaviour; strings reveal purpose and indicators.
  • All of this is readable statically, without running the file, which is why it is safe to learn.
