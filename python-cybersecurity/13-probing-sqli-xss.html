Probing inputs for SQLi and XSS (authorized testing)

Sending harmless marker values to detect reflected XSS and SQL-error signals on a target you own.

▶ Watch this part (01:36:19)

At 1:36:19 the course uses query parameters to look for two of the most common web flaws: cross-site scripting (XSS) and SQL injection. This step does the same, but it stays on the right side of the line: it only detects the signal that a flaw might exist, on a target we own, and never exploits anything.

Authorized testing only. Everything here runs against the local practice lab (lab_server.py on 127.0.0.1) that you start yourself. Sending these probes to a system you do not own or have written permission to test is illegal. Re-read Rules of engagement if you are unsure.

The idea: send a harmless marker, then read the response

You do not need a live exploit to find these flaws. You send a small, recognisable, harmless value through an input and look at what comes back:

  • Reflected XSS signal: if your exact marker appears unescaped in the HTML response, the app put your input straight into the page — the browser could be tricked into treating input as code.
  • SQL injection signal: if adding a single quote (') to a value makes the app return a database error, your input is probably being pasted into a query unsafely.

Finding the signal is enough to report a finding. You never need to actually run a script in someone's browser or read their database to prove a problem exists.

The probe script

Our lab's /search endpoint reflects the q parameter unescaped, and /search?...&safe=1 escapes it, so we can show the contrast. The /product endpoint returns a fake database error when id contains a quote. The script checks both.

"""Authorized testing only: probing an input for reflected XSS and SQL-error signs.

ONLY run this against a system you own or are explicitly authorized to test. Here
that is our local lab_server.py. The technique: send a harmless marker through a
parameter and look at the response.
  - If the exact marker comes back unescaped, the input is reflected -> possible XSS.
  - If a single quote makes the app return a database error, the input may be
    concatenated into SQL unsafely -> possible SQL injection.
We are only DETECTING the signal, not exploiting anything.
"""
import requests

BASE = "http://127.0.0.1:8099"

# A unique, obviously-harmless marker. If it returns verbatim inside HTML, the
# value was not escaped. We do not inject scripts; we inject a recognisable string.
XSS_MARKER = "zzxsstest123<b>"


def check_reflection():
    resp = requests.get(BASE + "/search", params={"q": XSS_MARKER})
    reflected_raw = XSS_MARKER in resp.text
    # Compare against the safe endpoint, which escapes the same input.
    safe = requests.get(BASE + "/search", params={"q": XSS_MARKER, "safe": "1"})
    reflected_safe = XSS_MARKER in safe.text
    print("Reflection test on /search?q=")
    print("  unsafe endpoint reflects marker verbatim:", reflected_raw, "-> XSS risk" if reflected_raw else "")
    print("  safe endpoint reflects marker verbatim:  ", reflected_safe, "(escaped -> not vulnerable)")


def check_sql_error():
    normal = requests.get(BASE + "/product", params={"id": "10"})
    probe = requests.get(BASE + "/product", params={"id": "10'"})
    print("\nSQL-error test on /product?id=")
    print("  id=10   -> status", normal.status_code)
    print("  id=10'  -> status", probe.status_code,
          "(500 + SQL error string -> injection risk)" if probe.status_code == 500 else "")
    if "SQL" in probe.text:
        print("  server leaked:", probe.text.strip())


if __name__ == "__main__":
    check_reflection()
    check_sql_error()
    print("\nThese are DETECTION signals, not exploits. Report findings; do not weaponise them.")

Why is reflected input dangerous? (XSS in one minute)

A browser decides what is text and what is code by looking at HTML tags. If an app drops your input into a page without output encoding, an attacker can submit input that becomes a tag — including a <script> — and the victim's browser will run it in the context of that site. The fix is to encode <, >, & and quotes so they display as characters instead of acting as markup.

Why does a single quote matter for SQL?

If code builds a query by gluing strings together — "SELECT * FROM products WHERE id = '" + user_input + "'" — then a quote in the input closes the string early and the rest is read as SQL. That is SQL injection. The fix is a parameterised query, where values are sent separately from the query text and can never change its structure.

What you should see. Against the lab, the unsafe endpoint reflects the marker and the quote triggers a 500:

  unsafe endpoint reflects marker verbatim: True -> XSS risk
  safe endpoint reflects marker verbatim:   False (escaped -> not vulnerable)

SQL-error test on /product?id=
  id=10   -> status 200
  id=10'  -> status 500 (500 + SQL error string -> injection risk)
  server leaked: <h1>SQL error near "'": syntax error</h1>
Common mistakes. Forgetting to start lab_server.py first (every request then raises a connection error). Treating a reflected marker as "I hacked it" — it is a signal to investigate and report, not a finished exploit. And never, ever running these probes against a site you found in the wild.

From finding to fix

A good report does not stop at "it is vulnerable". It names the input, shows the harmless proof, and gives the remediation: output-encode user input before putting it in a page (XSS), and use parameterised queries for every database call (SQLi). That is the difference between an attacker and a security professional.

Recap
  • A harmless marker reveals reflected XSS; a single quote reveals likely SQL injection.
  • Detecting the signal is enough to report — you never need a working exploit.
  • We only test our own lab, and we always include the fix in the finding.
  • Fixes: output encoding for XSS, parameterised queries for SQL injection.
