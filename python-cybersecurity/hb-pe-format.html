The PE format, in more depth

Headers, sections, imports/exports, entropy and packing explained.

Module 3 opens Windows executables and reads them without running them. To make sense of what pefile prints, you need a mental model of the file format it is parsing. This chapter is that model: the layout of a PE file from its ancient DOS stub to its modern headers, what sections hold, how the import table betrays behaviour, and what entropy, timestamps and packing can tell an analyst.

Why this matters for your project. Reading a file's structure is the heart of static analysis - learning about a program without executing it, which is safe to do on your own machine. Every number the triage classifier in step 21 uses comes from the fields described here.

What "PE" means

PE stands for Portable Executable, the format Windows uses for .exe and .dll files. It is a container with a strict layout: a series of headers that describe the file, followed by the sections that hold the actual code and data. Because the layout is predictable, a library like pefile can walk it field by field and hand you structured information.

The DOS (MZ) header

Every PE file still begins with a tiny MS-DOS header, a relic kept for backward compatibility. Its first two bytes are the letters MZ (the initials of a DOS architect), which is the classic "magic number" that identifies the file type. It is followed by a small DOS stub program whose only job, if you somehow ran the file under DOS, is to print "This program cannot be run in DOS mode". Tucked inside this header is a pointer (e_lfanew) to where the real PE header begins.

import pefile
pe = pefile.PE("sample_app.exe")
print(pe.DOS_HEADER.e_magic)   # the MZ signature
print(pe.DOS_HEADER.e_lfanew)  # offset to the PE header
New to "magic numbers"? What they are and why they matter

A magic number is a fixed sequence of bytes at a known position that identifies a file's type regardless of its name. MZ marks a DOS/PE file; PK marks a ZIP; %PDF marks a PDF. Analysts trust magic bytes over file extensions, because a .jpg can easily be a renamed executable - the bytes do not lie.

The PE header

Follow e_lfanew and you reach the signature PE\0\0, then the headers that actually matter. They split into the file header (how many sections, which machine, a timestamp) and the optional header (which, despite the name, is always present and holds the entry point and image base). The key fields pefile exposes:

FieldWhat it tells you
MachineTarget CPU - e.g. x64 (64-bit) or x86 (32-bit)
TimeDateStampClaimed build time of the file
NumberOfSectionsHow many sections follow
AddressOfEntryPointWhere execution would start, as an offset
ImageBasePreferred address to load the file at in memory

On the benign sample used in step 18, these read as machine x64 (64-bit), build timestamp 2022-08-06T06:41:05+00:00, and 6 sections - the exact numbers you will see printed when you run it.

Entry point and image base

The entry point is the offset of the first instruction Windows would run. The image base is the address the file would like to be loaded at; the entry point is given relative to it. You read these fields statically, but together they are where a dynamic analyst would set their first breakpoint. For our purposes they are just two more fields that help describe - and later fingerprint - a sample.

Sections

After the headers come the sections - named blocks that hold the file's real contents, each with permissions (readable, writable, executable). Common ones carry conventional names:

SectionUsually holds
.textExecutable code - the program's instructions
.rdataRead-only data, including imports/exports info
.dataWritable global variables
.rsrcResources - icons, menus, version info
.relocRelocation fixups if loaded away from ImageBase

The benign sample has the tidy set .text .rdata .data .pdata .rsrc .reloc - exactly what you would expect from a normally compiled program. Odd or non-standard section names, a section that is both writable and executable, or a .text that holds almost no readable code, are the kinds of anomalies that make an analyst look closer.

Imports and exports

A program rarely does everything itself; it borrows functions from the operating system's libraries - the DLLs. The import table lists which DLLs a file needs and which functions it pulls from each. This is one of the most revealing things in static analysis, because the imports hint at what the program can do before it does anything at all. Exports are the reverse: functions a DLL offers to others.

On the clean sample, pefile shows imports from just KERNEL32.dll (83 functions) and SHLWAPI.dll (3 functions), with no suspicious APIs - a deliberately dull contrast to real malware. Step 19 builds a small watch-list: imports around networking, process injection, or cryptography are not proof of malice, but they tell you where to look.

Imports are clues, not verdicts. Plenty of legitimate software uses networking or encryption. A suspicious import raises a question; it does not answer it. The classifier in step 21 always ends with "a human analyst should confirm" for exactly this reason.

Entropy and packing

Entropy is a measure of randomness, scored roughly 0 to 8 per section. Ordinary code and text sit in a middle range; data that is compressed or encrypted looks almost perfectly random and pushes toward 8. Packing is when a program is compressed or encrypted and wrapped in a small stub that unpacks it in memory at runtime - a legitimate technique for shrinking files that malware also loves, because it hides code from static analysis.

The benign sample's .text scores about 6.39 - comfortably in the normal range, consistent with ordinary unpacked code. A packed sample would show one or more sections near 8, few readable strings, and a tiny import table (because the real imports are hidden until unpacking). High entropy alone is not proof of malware, but combined with other signals it is a strong hint.

Timestamps

The TimeDateStamp claims when the file was built. It is useful context - our sample reports 2022-08-06T06:41:05+00:00 - but treat it with suspicion: it is trivially faked, sometimes zeroed, and occasionally set to absurd past or future dates on purpose. Use it as one weak signal among many, never as fact.

Common misconceptions. "A suspicious import means it is malware" - no, it means look closer. "High entropy proves packing" - compressed resources raise entropy too. "The timestamp shows when it was made" - only if nobody forged it. "Static analysis is risky" - reading a file never runs it; that is the whole point.
Recap
  • A PE file is headers (DOS/MZ, then PE) followed by sections; pefile reads this layout without running the file.
  • The DOS header's MZ magic bytes identify the type; a pointer leads to the real PE header.
  • The PE header holds machine, timestamp, section count, entry point and image base.
  • Sections like .text, .data and .rsrc carry code and data with their own permissions.
  • The import table lists borrowed DLL functions - a powerful, early clue to behaviour, but not a verdict.
  • High section entropy suggests packing; timestamps are useful but easily faked.
Learn more. Official references only: Microsoft's PE Format specification and the pefile project. The format is stable, but confirm field names against current docs.
