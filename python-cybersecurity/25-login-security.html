Login security: the brute-force threat and its defences

Detecting a missing account-lockout on a system you own, and the defences that stop guessing attacks.

▶ Watch this part (05:19:14)

At 5:19:14 the course automates a login panel to try many passwords — a brute-force attack. A working password guesser is a weapon, so this step does not build one. Instead it does the two things a defender actually needs: detect that a login has no protection against guessing, and build the defence that stops it.

No password guessing here. The script never tries to find the real password. It sends a few deliberately wrong logins to our own lab to show that nothing locks the account, then demonstrates the fix. Pointing a real guesser at a login you do not own is a crime — see Rules of engagement.

Why brute force works — and what stops it

Brute force is simple: try password after password until one works. It succeeds only when two things are true — users pick weak passwords, and the login lets an attacker make unlimited fast attempts. You cannot force every user to choose a strong password, so the defender's job is to remove the second condition. A login that locks or slows down after a few failures makes guessing hopelessly slow, even against weak passwords.

Part A — detect the missing lockout

Our lab's login accepts attempt after attempt with no limit — a realistic weakness. The script proves it by sending five obviously-wrong passwords and watching the status code. It uses Playwright to drive the real login form, the same way Steps 22–24 did.

Part B — build the defence

Then it shows how a secure login behaves, with a small RateLimiter that records failures per account and refuses further attempts once a threshold is passed. This is the server-side logic the lab is missing.

"""Login security: demonstrating the brute-force WEAKNESS and its DEFENCE.

A brute-force attack tries many passwords against a login until one works. This
script does NOT do that. Instead it does two defender-focused things against our
own lab:

  Part A - detect the weakness: send a few DELIBERATELY WRONG logins and show the
           server never locks the account or slows down. That absence of a limit
           is the finding you report.
  Part B - show the fix: a small RateLimiter that locks an account after N failed
           attempts, which is what a secure login must do.

There is no password list here and nothing that targets a real system. Only run
the probe against systems you are authorized to test. Start lab_server.py first.
"""
import time
from playwright.sync_api import sync_playwright

BASE = "http://127.0.0.1:8099"


def probe_lockout(attempts: int = 5):
    """Send a few obviously-wrong logins to our OWN lab and watch the responses."""
    print(f"Part A - sending {attempts} wrong logins to the lab to test for a lockout:\n")
    results = []
    with sync_playwright() as p:
        browser = p.chromium.launch(headless=True)
        page = browser.new_page()
        for i in range(1, attempts + 1):
            page.goto(BASE + "/login")
            page.fill("input[name=username]", "admin")
            page.fill("input[name=password]", f"definitely-wrong-{i}")   # never the real one
            # Submit and capture the server's response status for this attempt.
            with page.expect_response("**/login") as resp_info:
                page.click("input[type=submit]")
            status = resp_info.value.status
            results.append(status)
            print(f"   attempt {i}: HTTP {status}")
        browser.close()

    locked = any(s == 429 for s in results)      # 429 = Too Many Requests
    print("\nFinding:",
          "server locked us out (good)" if locked
          else "server accepted attempt after attempt with no lockout or delay (WEAKNESS).")


class RateLimiter:
    """Part B - how a secure login SHOULD behave: lock after too many failures."""

    def __init__(self, max_failures: int = 3, cooldown_seconds: int = 300):
        self.max_failures = max_failures
        self.cooldown = cooldown_seconds
        self.failures: dict[str, list[float]] = {}

    def record_failure(self, account: str):
        self.failures.setdefault(account, []).append(time.time())

    def is_locked(self, account: str) -> bool:
        recent = [t for t in self.failures.get(account, []) if time.time() - t < self.cooldown]
        self.failures[account] = recent
        return len(recent) >= self.max_failures


def demo_defence():
    print("\nPart B - the same attempts against a login that enforces a limit:\n")
    guard = RateLimiter(max_failures=3)
    for i in range(1, 6):
        if guard.is_locked("admin"):
            print(f"   attempt {i}: BLOCKED - account temporarily locked")
            continue
        guard.record_failure("admin")            # pretend this attempt failed
        print(f"   attempt {i}: allowed, failure recorded")
    print("\nDefences that stop brute force: account lockout, rate limiting,"
          " CAPTCHAs, and multi-factor authentication.")


if __name__ == "__main__":
    probe_lockout()
    demo_defence()

New to status code 429?

429 "Too Many Requests" is the HTTP way a server says "slow down — you have made too many requests in too little time." Seeing it during repeated logins is a sign the server enforces a limit. Never seeing it, no matter how many failures, means it does not.

Why count failures per account and use a cooldown?

Locking forever would let an attacker lock out real users on purpose (a denial-of-service). A cooldown — lock for a few minutes after N failures — stops guessing while letting a legitimate user back in shortly after. Tracking per account (and often per IP) keeps one attacker from affecting everyone.

Common mistakes. Forgetting to start lab_server.py (Part A cannot connect). Thinking Part A "broke in" — it did not; every attempt was rejected, which is the point. And raising the attempt count to turn this into a real guesser: do not. That crosses the line this guide refuses to cross.

The full defence checklist

  • Account lockout / rate limiting after a few failures — the single biggest win.
  • MFA — even a correct password is not enough on its own.
  • CAPTCHA or proof-of-work after suspicious activity, to stop scripts.
  • Strong-password policy and breached-password checks, so guesses are less likely to land.
  • Monitoring and alerting on bursts of failed logins — the same 401 pattern Part A produced.
Recap
  • Brute force only works when a login allows unlimited fast attempts.
  • We detected the missing lockout with a few deliberately-wrong logins — never a guesser.
  • A small per-account rate limiter is the core defence; MFA, CAPTCHAs and monitoring back it up.
  • Report the weakness with the fix, and never run a real brute-forcer outside your own lab.
