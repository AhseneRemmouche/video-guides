Fingerprinting a server and finding known CVEs

Reading response headers to guess the tech stack, then looking it up in the NVD database.

▶ Watch this part (02:00:10)

A server often tells you what it is running without being asked. In this step we read two response headers to guess the technology behind our lab, then take that guess to the National Vulnerability Database (NVD) to ask a simple question: are there published vulnerabilities for this version? Both halves are everyday blue-team work — knowing your own software's exposure is the first step to patching it.

Authorized testing only. Reading headers and looking up CVEs for a system is reconnaissance. Do it only against software you own or are explicitly authorized to test — here, the local practice lab on 127.0.0.1. See Rules of engagement.

What this step does

Two short scripts, run against the lab you started in the previous step:

  • Fingerprint the server. We send a few requests, print each status code with a plain-English meaning, then read the Server and X-Powered-By headers to see what the lab admits to running.
  • Look up known CVEs. We take a product and version and query the NVD JSON API for matching CVE records, printing each id with its CVSS severity.
New to fingerprinting? What it is and why it matters

Fingerprinting means working out what software a server runs by looking at clues it leaks — response headers, error-page wording, default files, timing. A defender fingerprints their own estate to build an inventory: you cannot patch what you do not know you are running. An attacker fingerprints to find a version with a known weakness. The technique is identical; only the authorization differs.

Concepts the presenter explains

The course frames this as the natural next move after you can send a request: once a tool can read a response, it can read the metadata of that response too. A status code is the server's one-number summary of what happened, and a handful of headers often name the web server and application framework outright. The presenter then connects that to vulnerability research — a product plus a version string is exactly what a CVE database is indexed by.

Before you run

  1. Open a terminal in the code/requests/ folder and start the lab in it: python lab_server.py. Leave it running.
  2. Open a second terminal in the same folder for the scripts below.

Part 1 — Fingerprinting the server

This is the same file you met when learning status codes; here we focus on its fingerprint() function, which reads the two giveaway headers.

"""HTTP status codes and simple server fingerprinting.

Status codes are the server's one-number summary of what happened. Fingerprinting
means reading response headers to guess the technology behind a site - useful for
an analyst mapping an authorized target. Start lab_server.py first.
"""
import requests

BASE = "http://127.0.0.1:8099"

# A short map so a tool can print human-friendly meanings.
MEANING = {
    200: "OK - the request succeeded",
    401: "Unauthorized - credentials needed or wrong",
    403: "Forbidden - the server refuses, even with credentials",
    404: "Not Found - no such resource",
    500: "Server Error - the app crashed handling the request",
}


def describe(path):
    resp = requests.get(BASE + path)
    code = resp.status_code
    print(f"{path:12} -> {code}  {MEANING.get(code, 'other')}")
    return resp


def fingerprint(resp):
    print("\nTechnology clues from headers:")
    for header in ("Server", "X-Powered-By"):
        value = resp.headers.get(header)
        if value:
            print(f"  {header}: {value}")


if __name__ == "__main__":
    describe("/")             # 200
    describe("/admin")        # 200 (a 'secret' path that exists)
    describe("/missing")      # 404
    home = describe("/product?id=1'")  # 500 from the fake SQL error
    fingerprint(home)

Why read headers instead of just the body?

The body is the page a human sees; the headers are the envelope around it — metadata the browser and server exchange. Headers carry the status, content type, cookies, caching rules and, often, the server's own name and version. For an analyst they are a compact, machine-readable summary, which is why fingerprinting starts there rather than scraping the HTML.

Part 2 — From a version to known vulnerabilities

Suppose the fingerprint told us the target runs Apache 2.4.49. The next question is whether that version has published flaws. We ask the NVD, the U.S. government's free catalogue of known vulnerabilities, through its JSON API.

New to CVEs and the NVD? What they are

A CVE (Common Vulnerabilities and Exposures) is a unique id for one publicly known security flaw, like CVE-2021-41773. The NVD (National Vulnerability Database) is a public database that enriches every CVE with a description and a severity score, and offers a free API to search them. Defenders use it to check whether the software they run has known holes that need patching.

What does the severity (CVSS) mean?

CVSS (Common Vulnerability Scoring System) turns how bad a flaw is into a number from 0.0 to 10.0, with a word band: Low, Medium, High, Critical. It helps you triage — patch the Criticals first. The score reflects how easy the flaw is to exploit and how much damage it allows, not how likely you personally are to be attacked.

"""Looking up known vulnerabilities (CVEs) for a product version.

Once fingerprinting tells you a target runs, say, "Apache 2.4.49", the next
question is: are there published vulnerabilities for that version? The U.S.
National Vulnerability Database (NVD) has a free JSON API for exactly this.

This builds the request the way the NVD API expects, then prints each CVE id and
its severity. To keep the lesson reproducible offline, if the live request fails
it falls back to a bundled sample response (sample_nvd.json) captured earlier.
"""
import json
import os
import requests

NVD_API = "https://services.nvd.nist.gov/rest/json/cves/2.0"
SAMPLE = os.path.join(os.path.dirname(__file__), "sample_nvd.json")


def fetch(keyword: str) -> dict:
    try:
        # keywordSearch finds CVEs mentioning the term; resultsPerPage caps the list.
        resp = requests.get(
            NVD_API,
            params={"keywordSearch": keyword, "resultsPerPage": 5},
            timeout=10,
        )
        resp.raise_for_status()
        return resp.json()
    except Exception as exc:                       # no network / rate limited
        print(f"[live request unavailable: {exc}] using bundled sample\n")
        with open(SAMPLE, encoding="utf-8") as f:
            return json.load(f)


def summarise(data: dict):
    vulns = data.get("vulnerabilities", [])
    print(f"{len(vulns)} CVE record(s):\n")
    for item in vulns:
        cve = item["cve"]
        cid = cve["id"]
        desc = cve["descriptions"][0]["value"][:90]
        # Severity lives under metrics; the key differs by CVSS version.
        sev = "unknown"
        metrics = cve.get("metrics", {})
        for key in ("cvssMetricV31", "cvssMetricV30", "cvssMetricV2"):
            if metrics.get(key):
                sev = metrics[key][0]["cvssData"]["baseSeverity"] if key != "cvssMetricV2" \
                    else metrics[key][0].get("baseSeverity", "unknown")
                break
        print(f"  {cid}  [{sev}]  {desc}...")


if __name__ == "__main__":
    data = fetch("Apache 2.4.49")
    summarise(data)

The long error is the point of the try/except. Here the TLS handshake to NVD could not be verified — on this network a security appliance intercepts HTTPS and presents a certificate Python does not recognise (unable to get local issuer certificate). Rather than crash, the script printed the reason and loaded the bundled sample, so you still get the two CVEs: CVE-2021-41773 rated HIGH and CVE-2021-42013 rated CRITICAL.

Why did the live request fail? TLS interception explained

Many corporate and some home networks run a device that sits in the middle of every HTTPS connection to inspect it. It decrypts your traffic and re-encrypts it with its own certificate. Browsers are configured to trust that certificate, but a fresh Python install is not — so requests correctly refuses to trust the connection and raises CERTIFICATE_VERIFY_FAILED. This is Python being safe, not broken. On an unfiltered network the same script would reach NVD and print the live results. We do not disable certificate verification to force it through — turning off TLS checks is exactly the habit that gets people compromised.

Common mistakes
  • Forgetting to start the lab. Part 1 talks to lab_server.py; if it is not running you get a ConnectionError. The CVE script in Part 2 does not need the lab.
  • "Fixing" the TLS error by turning off verification. Passing verify=False would silence the warning and defeat the whole point of HTTPS. Leave verification on; the fallback already keeps the lesson working.
  • Trusting a version string blindly. Servers can be told to lie in their Server header, and a version may be patched without the number changing. A CVE hit is a lead to confirm, not proof the box is vulnerable.
  • Hammering the NVD API. The public endpoint is rate-limited. Add delays and request an API key if you query it for real; our lesson makes a single call.
Recap
  • A status code plus the Server and X-Powered-By headers often reveal what a server runs — the lab admits to LabServer/1.0 and DemoApp/0.1.
  • A product and version string is the key into the NVD, which returns CVE ids and CVSS severities.
  • Our live NVD call failed TLS verification behind an intercepting proxy, so the script honestly reported it and fell back to the bundled sample.
  • The sample yields CVE-2021-41773 (HIGH) and CVE-2021-42013 (CRITICAL) — the classic Apache 2.4.49 path-traversal pair.
  • Never disable certificate verification to force a request through; fix the trust store instead.
