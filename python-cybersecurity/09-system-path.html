Reading and ordering the system PATH

Splitting the PATH variable to see which tools and folders the OS can reach.

▶ Watch this part (00:53:06)

When you type python or nmap in a terminal, the operating system does not search your whole disk for it. It looks only in a fixed list of folders called the PATH. Reading and ordering that list is a small but useful skill: for an analyst it reveals which tools are installed, and it is a clean example of processing system data with the os module.

What the presenter explains

PATH is a single long string of folder names glued together by a separator (at 53:30). The separator is not the same on every system: Windows joins folders with a semicolon ; while Linux and macOS use a colon :. Hard-coding either one would break your tool on the other platform. The os module hands you the correct separator as os.pathsep, so splitting the string the same way works everywhere (at 55:20). This is the heart of writing cross-platform code: ask the os module for system-specific details instead of guessing them.

Once PATH is a list of folders, it is ordinary Python data. The presenter counts the folders, prints the first few, and sorts them alphabetically (at 57:00) to show that system information becomes easy to work with the moment you split it correctly.

This step reuses the file from Step 07, os/04_env_and_path.py; here we focus on its PATH section (lines 22–31). Rather than repeat the whole file, these are the lines that matter:

raw_path = os.environ.get("PATH", "")
folders = raw_path.split(os.pathsep)
print(f"\nPATH has {len(folders)} folders. First five:")
for folder in folders[:5]:
    print("  ", folder)

print("\nAlphabetically first folder on PATH:", sorted(folders)[0] if folders else "none")

New to the PATH? What it is and why it matters

The PATH is the list of folders the operating system searches, in order, when you type a command name without a full path. If python.exe lives in a folder on PATH, typing python finds it; if not, you get a "command not found" error. The order matters: the first matching folder wins, which is why two versions of a tool can shadow each other. Understanding PATH explains a huge share of "it works on my machine" problems.

What is os.pathsep, and how is it different from os.sep?

os.pathsep is the character that separates entries in the PATH list: a semicolon on Windows, a colon on Unix. Do not confuse it with os.sep, which separates parts of a single path (a backslash on Windows, a forward slash on Unix). One joins folders into a list; the other joins names into a folder path. Both exist so your code can adapt to the system without you writing the character yourself.

Why the order of PATH matters for security

Because the first matching folder wins, a writable folder placed early on PATH is a classic attack surface: drop a fake python or git there and it runs instead of the real one. Defenders audit PATH for world-writable or unexpected folders near the front. Reading PATH in code, as this step does, is the first move in that kind of check.

Common mistakes.
  • Splitting on a literal ";" or ":". It works on one platform and silently returns the whole string as a single entry on the other. Use os.pathsep.
  • Confusing os.pathsep (between PATH entries) with os.sep (between parts of one path). They are different characters for different jobs.
  • Assuming sorted(folders)[0] is the folder the OS checks first. It is the alphabetically first one; the real search order is the unsorted list.
  • Calling sorted(folders)[0] without the empty-list guard. On an empty PATH that raises IndexError.
Recap
  • PATH is one string of folders joined by os.pathsep, which is ; on Windows and : on Unix.
  • Split on os.pathsep so the same code is cross-platform; never hard-code the separator.
  • Once split, PATH is a normal list you can count, slice and sort.
  • Search order (the unsorted list) is what the OS uses; the first matching folder wins, which has real security consequences.
