Browser automation with Playwright

Why some sites need a real browser, and how Playwright drives one from Python.

▶ Watch this part (04:24:02)

So far we have read websites with the requests library. That is fast and perfect for plain pages, but it only ever sees the raw HTML the server first sends. Many modern sites build most of their content after that, using JavaScript running inside a browser. To test those sites you need a tool that drives a real browser. In this step we meet Playwright, install its browser, and write our first script that opens a page and reads it.

Start the lab first. Every example in this module talks to the local practice lab you met in Step 11. Open one terminal and run python lab_server.py so it is listening on 127.0.0.1:8099, then run the Playwright scripts in a second terminal. If the lab is not running, Playwright will open a browser but the page will fail to load.

Why a plain request is sometimes not enough

When you call requests.get(url) you get back exactly the bytes the server sent in its first response — usually an HTML document. The presenter explains (at 4:26:40) that on an old-fashioned website that document already contains everything: the text, the links, the forms. But a single-page application (SPA) sends a nearly empty HTML shell plus a pile of JavaScript, and the browser then runs that JavaScript to build the real page. The pieces the user finally sees live in the Document Object Model (DOM), the in-memory tree of elements the browser assembles. requests never runs JavaScript, so for those sites it sees the empty shell and misses the content.

A real browser does run the JavaScript, so it ends up with the finished DOM. Playwright (at 4:28:10) is a library that lets your Python code control a real browser — Chromium, Firefox or WebKit — the same way a person would: open a page, wait for it to finish, read text, click buttons, fill forms. For security testing this matters because the attack surface you want to map (links, login forms, hidden inputs) often only exists after the scripts run.

New to the DOM? What it is and why it matters

The DOM (Document Object Model) is the live tree of elements a browser builds from an HTML page. Each tag — <h1>, <a>, <form> — becomes a node with text, attributes and children. JavaScript can add, change or remove nodes after the page loads, which is exactly how an SPA fills an empty shell. When we "read the page" with Playwright we are reading this finished tree, not the original HTML text.

New to SPAs? What a single-page application is

A single-page application loads one small HTML page and then uses JavaScript to swap the content in and out as you click around, without fetching a brand-new page each time. Gmail and most dashboards work this way. The upside is a smooth, app-like feel. The side effect for us is that the interesting content is not in the first response — you have to let the browser run the scripts to see it.

Install Playwright and its browser

Installing Playwright happens in two parts, and beginners often forget the second one. First you install the Python package with pip. Then you tell Playwright to download the actual browser binary it will drive — that is a separate download, because the browser is large and lives outside your Python packages. The presenter runs both commands (at 4:30:15).

  1. Make sure the lab is not needed for this command and install the package: 
    pip install playwright
  2. Download the Chromium browser Playwright will control. We only need Chromium for this guide: 
    python -m playwright install chromium
    This fetches a private copy of Chromium (it does not touch the Chrome you browse with). Run it once per machine.
  3. In a separate terminal, start the practice lab so there is something to open: 
    python lab_server.py
  4. Save the script below as 20_open_browser.py and run it in yet another terminal: 
    python 20_open_browser.py
New to headless mode? What "headless" means

A headless browser is a real browser running with no visible window. It loads pages, runs JavaScript and builds the DOM exactly like the normal browser, but nothing is drawn on screen. That makes it fast and lets it run on a server with no display. Pass headless=True when you just want the data; pass headless=False while you are learning and want to watch the browser do its thing.

The first script

This is our own, runnable version of what the video demonstrates. It launches a headless Chromium, opens the lab home page, reads the title and the first heading, and saves a screenshot as proof of what the browser saw.

"""First Playwright script: drive a real browser from Python.

Some sites build their pages with JavaScript, so requests only sees an empty
shell. Playwright controls a real browser (Chromium, Firefox or WebKit), so it
sees the page exactly as a user would, after scripts run. This opens the lab
site, reads the title, and saves a screenshot.

Setup once:  python -m playwright install chromium
Start lab_server.py first, then run this.
"""
from playwright.sync_api import sync_playwright

BASE = "http://127.0.0.1:8099"

with sync_playwright() as p:
    # headless=True means no visible window (fast, good for automation/servers).
    browser = p.chromium.launch(headless=True)
    page = browser.new_page()

    page.goto(BASE + "/")                     # navigate and wait for load
    print("Page title:", page.title())
    print("Current URL:", page.url)

    # Read rendered text the way a user sees it (after any JavaScript ran).
    heading = page.locator("h1").inner_text()
    print("Heading on page:", heading)

    page.screenshot(path="lab_home.png")      # proof of what the browser saw
    print("Saved screenshot: lab_home.png")

    browser.close()                           # always close to free the process

New to locators and selectors? The short version

A selector is a short pattern that describes which elements you mean — "h1" means "every level-one heading", "a" means "every link", "input[type=password]" means "password inputs". A locator is Playwright's object that represents the elements matching a selector. The locator does not grab the elements immediately; it waits and re-checks when you act on it, which makes scripts reliable on pages that load slowly. We use both heavily in the next two steps.

What you should see

What you should see. With the lab running, the script prints four lines:

The title Practice Lab Home comes from the page's <title> tag, and Lab home is the rendered <h1>. A new file lab_home.png appears next to your script.
Common mistakes.
  • Forgot playwright install. If you only ran pip install playwright, launching the browser fails with an error about a missing executable. Run python -m playwright install chromium once to fix it.
  • Forgot to start the lab. If lab_server.py is not running, page.goto cannot connect and you get a connection error. Start the lab in its own terminal first.
  • Never calling browser.close(). Leaving it out (or putting it outside the with block incorrectly) leaves headless Chromium processes running. The with sync_playwright() block plus close() keeps things tidy.
  • Expecting a window to pop up. With headless=True there is no window on purpose. Set headless=False if you want to watch.
Recap
  • The requests library only sees the first HTML response; it never runs JavaScript, so it misses content built by an SPA.
  • Playwright drives a real browser, so it reads the finished DOM — the page as a user sees it.
  • Install in two parts: pip install playwright, then python -m playwright install chromium.
  • headless=True runs the browser with no window; the script shape is launch → new_page → goto → read → close.
  • Always run the lab in one terminal and the script in another.
