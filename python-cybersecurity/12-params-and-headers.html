Query parameters and request headers

How parameters carry user input and how headers describe (or disguise) the client.

▶ Watch this part (01:15:53)

A bare GET to the home page is only the start. Real requests carry two more things an analyst cares about: query parameters (the values after ? in a URL, where user input enters an app) and request headers (metadata that says who you are and what you accept). This step sends both to the lab and watches what comes back.

Authorization first. This script sends requests to the practice lab on 127.0.0.1 — your own machine. Sending crafted parameters or spoofed headers to a system you do not own is not practice, it is an intrusion. Keep to the lab and the Rules of engagement.

Why parameters and headers matter

The presenter explains that most of what a web app does is driven by input, and almost all of that input arrives as query parameters or form fields (at 1:24:10). Parameters are the attacker's front door: a search box, a product id, a page number — each is a value the server trusts you to send, and each is a place where a careless app can be tricked. Learning to send them precisely is the groundwork for every input test later in the module.

Headers are the other half. Every request carries headers the server reads and that a defender's logs record (at 1:29:45). The User-Agent says which client you claim to be; Accept says which formats you want back. Because you control them, you can look like a normal browser — or, from the blue-team side, you learn that a suspicious User-Agent in the logs is a signal worth watching.

New to query parameters? What they are

A query parameter is a name=value pair tacked onto a URL after a ?. Several are joined with &, as in ?q=shoes&page=2. The server reads them to decide what to return — a search term, a product id, a sort order. Because the value comes from whoever typed the URL, parameters are the main channel for user input, which is exactly why security testing focuses on them.

New to URL encoding? Why spaces become +

URLs cannot contain raw spaces or many punctuation characters, so they are "percent-encoded": a space becomes + (or %20), an ampersand becomes %26, and so on. If you build URLs by hand you have to do this yourself and it is easy to get wrong. The big convenience of requests is that when you pass parameters as a dict it encodes them correctly for you — which is why the final URL below shows hello+world.

Sending it from Python

The script does two things: a GET with query parameters, then a GET with custom headers. Start the lab first, then run it.

  1. Make sure lab_server.py is running in Terminal 1 (see Step 11).
  2. In Terminal 2, from code/requests/, run python 09_params_headers.py.
  3. Read the final URL it built and the reflected body, then the status it got with custom headers.
"""Query parameters and request headers.

Parameters are the values after '?' in a URL (?q=hello). Headers are metadata
sent with every request (who you are, what you accept). Both matter in security:
parameters are where user input enters an app, and headers can reveal or disguise
the client. Start lab_server.py first.
"""
import requests

BASE = "http://127.0.0.1:8099"

# Pass parameters as a dict; requests URL-encodes them for you and builds
# http://127.0.0.1:8099/search?q=hello+world
params = {"q": "hello world"}
resp = requests.get(BASE + "/search", params=params)
print("Final URL requested:", resp.url)
print("Reflected body:", resp.text)

# Custom headers also go in as a dict. A realistic User-Agent, an Accept header,
# and a custom marker header. The server (and a defender's logs) see all of these.
headers = {
    "User-Agent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64)",
    "Accept": "text/html",
    "X-Scan-Session": "lab-demo-01",
}
resp2 = requests.get(BASE + "/", headers=headers)
print("\nStatus with custom headers:", resp2.status_code)
# Echo back what we sent, to make the point that headers are just data we control.
print("User-Agent we sent:", headers["User-Agent"])

New to request headers? What they carry

Alongside the method and path, every HTTP request sends a list of headers: short Name: value lines. Common ones are Host, User-Agent, Accept, Cookie and Content-Type. They are metadata — they describe the request rather than being the content itself. In requests you add your own by passing a dict to headers=, and they are merged with the sensible defaults the library already sends.

New to the User-Agent? Why it is both useful and unreliable

The User-Agent header is a string naming the browser and operating system making the request, such as Mozilla/5.0 (Windows NT 10.0; Win64; x64). Servers use it to tailor pages and defenders use it to spot odd clients. But as this script shows, you can set it to anything, so it is a hint, never proof. Scanners often announce themselves in it; thoughtful ones (and attackers) set a browser-like value to blend in.

What you should see. With the lab running, 09_params_headers.py prints:

The space in hello world became hello+world in the URL — requests encoded it for you. The body shows the lab reflecting your value straight back. The second request returns 200 with the headers you chose.
Common mistakes.
  • Building the query string by hand. Writing BASE + "/search?q=hello world" sends a raw space and may break. Pass a dict to params= and let requests encode it.
  • Confusing params= with headers=. Parameters go in the URL; headers travel beside it. Swapping them sends your data to the wrong place.
  • Expecting the User-Agent to be trusted. It is client-controlled. Never use it alone for a security decision.
  • Lab not running. As in Step 11, a missing server gives a ConnectionError. Start lab_server.py first.
Recap
  • Query parameters are the name=value pairs after ? — the main channel for user input, and the focus of input testing.
  • Pass them as a dict to params= and requests encodes and builds the URL for you; resp.url shows the result.
  • Request headers are metadata you control; add them with headers=.
  • The User-Agent and other headers appear in server logs — evidence for defenders, a footprint for testers — and prove only what the client claims.
