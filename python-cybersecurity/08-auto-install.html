Auto-installing missing libraries at runtime

Making a shared script install its own dependencies with pip through sys.executable.

▶ Watch this part (00:45:17)

Security scripts are often shared as a single file you hand to a teammate or drop onto a lab machine. If that machine is missing a library the script needs, the normal result is an ugly crash. This step shows a friendlier pattern: try to import the library, and if it is not there, install it automatically with pip and carry on.

What the presenter explains

When Python cannot find a library you import, it raises ImportError and stops. The presenter frames this (at 45:40) as a usability problem: a one-file tool should not fail just because a dependency is missing. The fix is to wrap the import in a try/except block. If the import succeeds, nothing special happens. If it raises ImportError, the script installs the package and imports it again (at 48:00).

The subtle and important part (at 51:00) is which Python does the installing. A machine often has several Python installations side by side, each with its own set of packages. If you run pip blindly you might install into the wrong one, and the import would still fail. The code calls sys.executable, which is the full path to the exact Python running this script, and asks that Python to run its own pip. The package then lands in the same place the script will look for it.

Do this

  1. Create os/05_auto_install.py in your project.
  2. Decide which package to guarantee. Our example uses requests; change the argument to ensure(...) for a different library.
  3. Run it in your terminal: python os/05_auto_install.py. If the package is already present you see one line of output and no install.
  4. To watch the install path trigger, run it inside a fresh virtual environment where the package is absent, and you will see the install message before the version line.

The full file

This is our own, runnable version of the pattern the video demonstrates.

"""Auto-installing a missing library at runtime.

Security tools are often shared as a single script. If the user does not have a
dependency installed, the tool should install it instead of crashing with
ImportError. The clean way is to try the import, and on failure call pip through
sys.executable (the exact Python running the script) so the package lands in the
right environment.

This example targets 'requests'. If it is already installed nothing happens.
"""
import importlib
import subprocess
import sys


def ensure(package: str, import_name: str | None = None):
    """Import `package`, installing it with pip first if it is missing."""
    name = import_name or package
    try:
        return importlib.import_module(name)
    except ImportError:
        print(f"[*] {package} not found - installing it now...")
        # sys.executable is the full path to THIS Python, so pip installs into the
        # same environment the script runs in (not some other Python on the system).
        subprocess.check_call([sys.executable, "-m", "pip", "install", package])
        return importlib.import_module(name)


if __name__ == "__main__":
    requests = ensure("requests")
    print("requests is ready, version:", requests.__version__)

New to try / except? What it is and why it matters

Python runs the code inside a try: block normally. If a line in there raises an error, Python jumps to a matching except: block instead of crashing. You name the error type you expect, here ImportError, so you only catch that one situation and let everything else fail loudly. It is the standard way to handle a problem you can recover from, like a missing dependency.

What is pip, and what does "-m pip" mean?

pip is Python's package installer. It downloads libraries from the Python Package Index and puts them where your Python can import them. Writing python -m pip instead of just pip tells a specific Python to run its own copy of pip. That matters because the bare pip command can point at a different Python than the one running your script. Using -m with sys.executable removes all doubt.

Why run pip through subprocess at all?

pip is itself a program, not a function you call from your code. subprocess is how Python launches another program and waits for it to finish. check_call runs the command, blocks until it ends, and raises an exception if the program reports failure, so your script can trust that a successful return really means the package installed.

What you should see. Because requests was already installed when we ran it, there was no install step and the output was a single line: 
requests is ready, version: 2.34.2
If the library had been missing, you would first see [*] requests not found - installing it now... followed by pip's progress, and only then the version line.
Common mistakes.
  • Catching a broad except Exception instead of ImportError. That hides real bugs inside the library and makes debugging painful.
  • Calling bare pip install from inside the code. It can install into a different Python than the one running, so the import still fails. Always go through sys.executable.
  • Assuming the pip name equals the import name. Some libraries differ (pip beautifulsoup4 imports as bs4); that is exactly what the import_name argument is for.
  • Relying on auto-install on a machine with no internet or no permission to install. For shared tools, document the dependencies and prefer a proper requirements file; treat auto-install as a convenience, not a guarantee.
Recap
  • Wrap a risky import in try/except ImportError so a missing library can be handled instead of crashing.
  • importlib.import_module imports by name at runtime, letting one helper serve any package.
  • Run pip through subprocess.check_call with sys.executable so the install lands in the Python that is actually running.
  • Auto-install is a convenience for single-file tools; for projects, prefer a documented requirements file.
