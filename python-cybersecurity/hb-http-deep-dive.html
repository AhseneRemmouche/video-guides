HTTP, in more depth

Methods, cookies, sessions, TLS and how browsers and tools differ.

Module 2 of this guide speaks HTTP from Python, and Module 4 drives a real browser that speaks it too. The quick primer gave you the vocabulary; this chapter goes deeper. We will look closely at request methods, the full shape of a request and a response, how cookies and sessions keep you logged in, what TLS adds to make HTTPS, and why a real browser sees a page so differently from a simple tool.

Why this matters for your project. Every web tool you build - input probes, status readers, header audits, Playwright crawlers - is just sending requests and reading responses. The better you understand the protocol, the more signal you can pull from what comes back, and the fewer false conclusions you draw.

HTTP is a conversation of requests and responses

HTTP is a text-based protocol with a simple rhythm: a client sends a request, the server sends back one response, and the exchange is over. There is no long-lived connection in the basic model - each request stands alone. That statelessness is why cookies exist, as we will see.

Methods: the verb of a request

Every request carries a method - a verb saying what you want to do. A handful cover almost everything:

MethodIntentChanges server state?
GETFetch a resource (a page, an image, JSON)No - should be safe to repeat
POSTSubmit data (a login form, a new record)Yes - creates or acts
PUT / PATCHReplace or update an existing resourceYes
DELETERemove a resourceYes
HEADLike GET but headers only, no bodyNo

GET and POST are the two you use constantly. In step 12 you send a GET with query parameters; the lab's login in step 25 is a POST. The distinction matters for testing: a safe GET can be retried freely, while blindly repeating a POST might submit the same action many times.

The full shape of a request and response

A request is a start line (method, path, version), a block of headers, a blank line, and an optional body. A response mirrors it: a status line (version, status code, reason), headers, a blank line, and the body. Seeing the raw text once makes the structure stick.

GET /search?q=hello HTTP/1.1
Host: 127.0.0.1:8099
User-Agent: python-requests/2.34.2
Accept: */*
(blank line - no body for a simple GET)
HTTP/1.1 200 OK
Server: LabServer/1.0
X-Powered-By: DemoApp/0.1
Content-Type: text/html; charset=utf-8

<html>...the page body...</html>

Those two Server and X-Powered-By headers are exactly what the fingerprint tool in step 15 reads to guess the technology stack, and the absence of security headers is what the audit in step 16 scores.

New to headers? What they are and why they matter

Headers are Name: value lines that carry metadata about the request or response - who the client is, what content type the body is, how long it is, caching rules, cookies, and security policies. The body is the actual content; the headers are the label on the parcel. Many security findings come entirely from reading headers, without ever touching the body.

Cookies and sessions: remembering you

Because HTTP forgets you after each response, servers need a way to recognise returning clients. The answer is the cookie. On your first visit the server sends a Set-Cookie header with a unique session id; your client stores it and sends it back on every later request via a Cookie header. The server looks that id up in its own session store to know who you are and whether you are logged in.

In Python, the requests library makes this easy with a Session object, which stores cookies for you across calls:

import requests

s = requests.Session()                 # keeps cookies between requests
s.post("http://127.0.0.1:8099/login",
       data={"username": "admin", "password": "correcthorse"})
# the session cookie is now stored and sent automatically:
r = s.get("http://127.0.0.1:8099/admin")
print(r.status_code)
Why session security is a big deal. Because a session cookie is the proof of who you are, flaws that leak it are serious. That is one reason XSS (which can read cookies from the page) is dangerous, and why real cookies are marked HttpOnly and Secure. The lab in step 13 shows the XSS signal that would make such theft possible.

TLS and HTTPS: the same protocol, wrapped

Plain HTTP travels as readable text, so anyone between you and the server can read or change it. HTTPS is simply HTTP sent through a TLS tunnel. TLS does three jobs: it encrypts the traffic so eavesdroppers see only noise, it checks integrity so tampering is detected, and it proves the server's identity with a certificate.

New to certificates? What they are and why they matter

A TLS certificate is a signed document stating "this public key belongs to this domain", vouched for by a Certificate Authority your system already trusts. Your client checks that the certificate is valid, unexpired, and issued for the domain you asked for. If any check fails you get a warning - which, outside a lab, usually means something is wrong (misconfiguration, interception, or a fake site).

Why a browser differs from a simple tool

A call with requests fetches one response - the raw HTML - and stops. A real browser does far more: it parses that HTML, downloads every linked script, stylesheet and image, and then runs the JavaScript, which can rewrite the page entirely. For a single-page app the first response may be almost empty, with the real content built by script afterward.

Browsers also send a rich User-Agent and dozens of headers, handle redirects and cookies automatically, and expose a live DOM you can query. That is exactly why step 22 switches to Playwright: to test a JavaScript-heavy app you have to see what the browser sees, not just the first response.

Common misconceptions. "The page is empty, so there is nothing there" - it may be built by script. "HTTPS means the site is safe" - it means the connection is encrypted and the identity checked, not that the application is secure. "GET and POST are interchangeable" - only GET is meant to be safe to repeat. "A 200 means success" - it means the request was handled, not that your logic worked.
Recap
  • HTTP is a stateless request-response conversation; each request gets one response.
  • The method (GET, POST, ...) is the verb; GET fetches, POST submits and changes state.
  • Requests and responses share a shape: start/status line, headers, blank line, optional body.
  • Cookies carry a session id so a stateless protocol can remember a logged-in user - protect them.
  • HTTPS is HTTP inside a TLS tunnel that encrypts, checks integrity, and proves identity with a certificate.
  • Browsers run JavaScript and build the DOM; simple tools only fetch, so JS-heavy pages need Playwright.
