Content discovery and auditing security headers

Finding sensitive paths with a wordlist and scoring a site's defensive HTTP headers.

▶ Watch this part (02:08:26)

Two more pieces of web reconnaissance, both run against our own lab. First, content discovery: asking a server whether a list of likely paths exists, to find pages that are reachable but never linked. Second, a security-header audit: checking whether the site sends the defensive headers browsers rely on. One finds things that should be hidden; the other finds protections that are missing.

Authorized testing only. Content discovery sends many requests probing for files the owner may not want found. Against a system you do not own or have explicit written permission to test, that is an attack, not research — and often a crime. In this step the only target is the local lab on 127.0.0.1. Read Rules of engagement before running anything here.

What this step does

  • Content discovery. We take a tiny wordlist of common path names, request each one, and report the paths that do not return 404 — the ones that quietly exist.
  • Header audit. We read one response's headers and score it against five protective headers every modern site should send. Our lab deliberately sends none, so it scores a clean zero.

Part 1 — Content discovery with a wordlist

Servers often host paths nobody links to: an /admin panel, a forgotten /backup.zip, a committed /.env file full of secrets. You will never find them by clicking links. A discovery scan asks the server about each candidate directly and watches the status code.

New to content discovery and wordlists? What they are

Content discovery is the practice of finding reachable URLs that are not linked anywhere, by guessing their names. A wordlist is just a list of likely names (admin, login, backup.zip, …) to try. Real tools like ffuf or dirb use lists with tens of thousands of entries; we use seven so the lesson stays readable. A path that answers with anything other than 404 Not Found is worth a closer look.

"""Authorized testing only: content discovery with a small wordlist.

Web apps often leave sensitive paths reachable (/admin, /.env, backups). A
discovery scan asks the server for each candidate path and notes which ones do
NOT return 404. Run this only against systems you are authorized to test; here
that is the local lab. Be gentle: a real scan should rate-limit and respect
robots.txt and the engagement scope. Start lab_server.py first.
"""
import requests

BASE = "http://127.0.0.1:8099"

# In real tools this comes from a file; a tiny inline list keeps the lesson clear.
WORDLIST = ["admin", "login", "backup.zip", ".env", "robots.txt", "secret", "config.php"]


def discover():
    found = []
    for word in WORDLIST:
        url = f"{BASE}/{word}"
        resp = requests.get(url)
        marker = "FOUND" if resp.status_code != 404 else "----"
        print(f"  [{marker}] {resp.status_code}  /{word}")
        if resp.status_code != 404:
            found.append(url)
    return found


if __name__ == "__main__":
    print("Content discovery against the lab target:")
    hits = discover()
    print(f"\n{len(hits)} interesting path(s) found:")
    for h in hits:
        print("  ", h)

Part 2 — Auditing security headers

Modern browsers enforce a set of defensive behaviours only when the server asks for them, through HTTP response headers. If the headers are missing, the protections are simply off. Checking for them is one of the quickest, highest-value audits you can run, and missing headers are an easy, well-understood finding to report.

New to security headers? What they do

A security header is a response header that tells the browser to switch on a defence. The five we check: Strict-Transport-Security (HSTS) forces HTTPS; Content-Security-Policy (CSP) restricts where scripts may load from, blunting XSS; X-Frame-Options stops the page being framed (anti-clickjacking); X-Content-Type-Options stops MIME-type sniffing; Referrer-Policy limits how much URL detail leaks when you navigate away. None of them change the page a user sees — they are pure defence.

"""Auditing a site's security headers.

Browsers enforce a set of defensive HTTP headers when a site sends them. Missing
headers are a common, easy-to-report finding. This reads the headers of a response
and reports which protections are present or absent. Start lab_server.py first
(it deliberately sets none of them, so you see a failing report).
"""
import requests

BASE = "http://127.0.0.1:8099"

# header name -> why it matters
CHECKS = {
    "Strict-Transport-Security": "forces HTTPS, blocks downgrade attacks",
    "Content-Security-Policy": "limits where scripts can load from (anti-XSS)",
    "X-Frame-Options": "stops the page being framed (anti-clickjacking)",
    "X-Content-Type-Options": "stops MIME-type sniffing",
    "Referrer-Policy": "controls how much URL info leaks on navigation",
}


def audit(url):
    resp = requests.get(url)
    present, missing = [], []
    for header, reason in CHECKS.items():
        if header in resp.headers:
            present.append(header)
        else:
            missing.append((header, reason))

    print(f"Security-header audit for {url}\n")
    print("Present:")
    print("  (none)" if not present else "")
    for h in present:
        print(f"  [ok]  {h}: {resp.headers[h]}")
    print("\nMissing:")
    for h, reason in missing:
        print(f"  [!]   {h} - {reason}")
    score = len(present)
    print(f"\nScore: {score}/{len(CHECKS)} protective headers set.")


if __name__ == "__main__":
    audit(BASE + "/")

Common mistakes
  • Lab not running. Both scripts need lab_server.py up in another terminal; without it you get a ConnectionError.
  • Running discovery anywhere but your own lab. Pointing BASE at a site you do not own turns a lesson into an attack. Keep it on 127.0.0.1.
  • Treating only 200 as a hit. A 401 or 403 means the path exists but is protected — still a finding. That is why the code tests for "not 404".
  • Reading the header check as "secure". Present headers earn the point, but a weak Content-Security-Policy can still be bypassable. The audit flags absence, not quality.
Recap
  • Content discovery guesses path names from a wordlist and reports anything that is not a 404.
  • Against the lab it finds five hidden paths: /admin, /login, /backup.zip, /.env and /robots.txt.
  • The header audit checks five defensive headers and scores the lab 0/5 — a realistic unhardened baseline.
  • Each missing header is both the finding and the fix: send it to switch the defence on.
  • Both techniques are reconnaissance — legal on your own lab, an attack anywhere else. See Rules of engagement.
