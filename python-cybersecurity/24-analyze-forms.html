Analyzing forms and input fields automatically

Finding every form on a page and describing its fields to spot logins and inputs.

▶ Watch this part (05:08:03)

Forms are where user input enters an application, so they are the first thing a tester inspects. A form tells you what the app accepts, where that input is sent, and whether the page handles something sensitive like a password. In this step we let Playwright find every form on the lab's login page and describe its fields automatically, then decide whether it looks like a login form.

Start the lab first. As before, run python lab_server.py in one terminal so 127.0.0.1:8099 is listening, then run this script in another.

Why forms are worth mapping

The presenter explains (at 4:46:05) that every form is a doorway into the application: whatever you type is packaged up and sent to the server, which then trusts it unless the developer was careful. For a defender, listing the forms and their fields answers useful questions quickly — where does input go (the form's action), how is it sent (GET or POST), and which fields are sensitive? Doing this by hand is slow and easy to get wrong, so we let the browser read the structure for us.

A form is an HTML <form> element wrapping one or more <input> fields. Each input has useful attributes: a name (the key sent to the server), a type (text, password, submit, and so on), and sometimes a placeholder (the greyed-out hint text). Our script reads those attributes straight from the rendered DOM and prints them in a tidy summary.

New to HTML forms? The parts that matter

A <form> groups input fields and defines where they go when submitted. Its action is the URL that receives the data; its method is usually GET (data in the URL) or POST (data in the request body). Inside it, each <input> collects one value. A field with type="password" hides what you type — and its presence is a strong hint that the form is a login.

New to GET vs POST? Which one a form uses

Both are HTTP methods. A GET form puts its values in the URL's query string — fine for searches, bad for secrets, because URLs get logged. A POST form puts values in the request body, which is the right choice for a login. Seeing POST -> /login tells you both where credentials go and that the form sends them in the body.

Run it

  1. Keep the lab running in its own terminal: 
    python lab_server.py
  2. Save the script below as 22_analyze_forms.py.
  3. Run it in a second terminal: 
    python 22_analyze_forms.py
"""Find every form on a page and describe its input fields.

Forms are where user input enters an app, so they are what a tester inspects
first: what does each field accept, where does the form submit, and is it a login?
This visits the lab login page and prints a structured description of its form.
Start lab_server.py first.
"""
from playwright.sync_api import sync_playwright

BASE = "http://127.0.0.1:8099"

with sync_playwright() as p:
    browser = p.chromium.launch(headless=True)
    page = browser.new_page()
    page.goto(BASE + "/login")

    forms = page.locator("form")
    count = forms.count()
    print(f"Found {count} form(s) on /login\n")

    for i in range(count):
        form = forms.nth(i)
        # The action is where the form posts; the method is GET or POST.
        action = form.get_attribute("action")
        method = (form.get_attribute("method") or "get").upper()
        print(f"Form #{i + 1}: {method} -> {action}")

        inputs = form.locator("input")
        for j in range(inputs.count()):
            field = inputs.nth(j)
            print("   field:",
                  "name=", field.get_attribute("name"),
                  "| type=", field.get_attribute("type"),
                  "| placeholder=", field.get_attribute("placeholder"))

        # A simple heuristic: a password field means this is a login form.
        if form.locator("input[type=password]").count():
            print("   -> looks like a LOGIN form (has a password field)")

    browser.close()

New to chained locators? Searching inside one element

You can build a locator from another locator: form.locator("input") means "every input within this form", not every input on the page. This scoping matters when a page has several forms — it keeps each form's fields together. nth(i) then picks one match by its position, counting from zero.

What you should see

What you should see. With the lab running, the script finds one form, reports where it posts, lists its three fields, and flags it as a login: 
Found 1 form(s) on /login

Form #1: POST -> /login
   field: name= username | type= text | placeholder= user
   field: name= password | type= password | placeholder= pass
   field: name= None | type= submit | placeholder= None
   -> looks like a LOGIN form (has a password field)
Note the submit button shows name= None and placeholder= None — it has neither attribute, which is perfectly normal. The password field is what triggers the login flag.
Common mistakes.
  • Forgot to start the lab. Without lab_server.py running, page.goto(BASE + "/login") cannot connect. Start it first.
  • Forgot playwright install. No Chromium binary means the launch fails. Run python -m playwright install chromium once per machine.
  • Expecting values instead of None. get_attribute returns None when an attribute is absent. That is expected for the submit button; do not treat it as an error.
  • Searching the whole page for inputs. Using page.locator("input") instead of form.locator("input") would mix fields from different forms. Scope the search to each form.
Recap
  • Forms are the main entry point for user input, so mapping them is an early testing step.
  • page.locator("form") plus nth(i) lets you walk each form one at a time.
  • For each field, get_attribute reads its name, type and placeholder; a missing attribute reads as None.
  • Chaining form.locator("input") scopes the search to one form.
  • A password input is a simple, reliable signal that a form is a login — a hint for a human to confirm.
