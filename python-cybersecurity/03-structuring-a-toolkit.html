Structuring a professional security toolkit

Splitting logic from exploits and laying out folders so a growing tool stays maintainable.

▶ Watch this part (00:05:58)

Before writing more tools, it is worth pausing on how a security project is laid out. A tool thrown into one giant file works for a demo and becomes a nightmare the moment it grows. This step is about the thinking the course spends time on (at 05:58): separating shared logic from the individual checks, giving output its own place, and keeping the whole thing tidy enough to trust. No new library here — just structure.

Authorization still applies. A well-organised toolkit is still only ever pointed at systems you own or are allowed to test. Read the Rules of engagement before running any check you build into this structure.

Why structure matters

As the presenter explains while sketching the project (at 06:20), a serious tool has three different kinds of code that should not be mixed:

  • Shared logic — code every part relies on, such as the thing that sends web requests, or the logger. Written once, used everywhere.
  • Individual checks — one small file per task: a security-header audit, a status check, content discovery. Each can be read, tested and fixed on its own.
  • Output — reports and logs the tool produces, kept well away from the source code so results never get confused with the program.

Keeping these apart is called separation of concerns. It is the difference between a project you can still understand in three months and one you quietly abandon.

The layout this guide uses

From here on, tools follow one simple layout. You can build it by hand, or generate it with the one-click scaffolder (06_project_scaffolder.py) that you will meet in Step 10 — it creates exactly this tree and never overwrites your work.

How to build it

  1. Create the project root folder, for example my_scanner, with os.makedirs(..., exist_ok=True).
  2. Inside it, create core/, modules/ and reports/.
  3. Put an __init__.py in core/ and modules/ so Python treats them as packages.
  4. Add starter files such as core/http_client.py and modules/security_headers.py, empty for now.
  5. Write a short README.md at the root saying what the tool is.
  6. Drop a .gitkeep in reports/ so the empty folder is preserved.
What is "separation of concerns"?

It is the habit of giving each part of a program one clear job. The request-sending code should not also know how to format a report; a single check should not also contain the logger. When each piece does one thing, you can change or fix it without breaking the others — and you can reuse it. It is one of the oldest and most useful ideas in software.

What is __init__.py, and what makes a "package"?

A module is a single .py file. A package is a folder of modules that you can import as a group. Putting an __init__.py file (even an empty one) inside a folder marks it as a package, so import core.http_client works. Without it, Python may not find your code when you import across folders.

Why keep offensive checks out of the shared library?

In a defensive toolkit the shared core/ code (the HTTP client, the logger) should stay neutral and reusable. Anything that actively probes a target lives in its own file under modules/, clearly named, so it is obvious what each check does and so nothing dangerous hides inside a utility everyone imports. It also makes an authorization review easy: a reviewer reads the modules/ folder and sees exactly what the tool can do.

Three purpose-built folders, a README at the root, and an empty reports/ ready for output. The exact listing order of files within a folder may differ, since the operating system decides it.
Common mistakes.
  • One giant file. Putting logic, checks and output in a single script makes it unreadable fast and impossible to reuse.
  • Forgetting __init__.py. Imports across folders fail with ModuleNotFoundError when a folder is not marked as a package.
  • Committing output. Saving generated reports into your source folders clutters the project; keep them in reports/ and leave that out of version control (apart from .gitkeep).
  • Circular dependencies. If core/ starts importing a specific check, the one-way flow breaks. Shared code must not depend on an individual module.
Recap
  • A professional toolkit separates shared logic (core/), individual checks (modules/) and output (reports/).
  • This separation of concerns keeps each piece small, testable and reusable as the project grows.
  • __init__.py marks a folder as an importable package; .gitkeep preserves an empty output folder.
  • Dependencies flow one way: checks import core and write to reports; core never depends on a single check.
  • Step 10's scaffolder builds this exact layout automatically and safely.
