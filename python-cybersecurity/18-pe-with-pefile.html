Inspecting a Windows PE file with pefile

Opening an executable and reading its machine type, build time and sections without running it.

▶ Watch this part (02:42:02)

Every Windows .exe and .dll follows the same layout, the PE (Portable Executable) format. Before running anything, an analyst reads that layout: which processor the file targets, when it was built, and how it is divided into sections. This step uses the pefile library to read all of that from a program, without ever executing it.

We analyse a benign file. The demos here read our own copy of a normal Windows program, a small pip launcher we renamed sample_app.exe. It is a trustworthy program; we just never run it. Everything you learn applies identically to a suspicious file, which is the whole point of static analysis.

What this step does

The presenter introduces pefile (at 2:42:02) as the tool that turns the raw bytes of an executable into something readable. Our script, 15_pe_basics.py, opens a file, prints its machine type, build timestamp, entry point and image base, then lists every section with its sizes and entropy. These are the first facts you record about any sample.

If you want the full tour of what lives inside a PE first, read the primer Anatomy of a Windows PE file. This step is the hands-on version of that picture.

New to the PE format? What it is

PE stands for Portable Executable. It is the container format Windows uses for programs (.exe) and libraries (.dll). A PE begins with headers that describe the file (the CPU it needs, when it was built, where execution starts) and continues with sections that hold the actual code, data and resources. Because the format is fixed and documented, a library like pefile can read every field reliably.

What is a section?

A section is a named region inside a PE with its own purpose and permissions. Common ones are .text (the executable code), .rdata (read-only data such as strings and import names), .data (variables the program can change), .rsrc (resources like icons) and .reloc (relocation fixups). Each section header records how big the region is both on disk and in memory, which is useful when those two numbers disagree.

Install pefile and run the script

  1. Install the library once: pip install pefile. We ran pefile 2024.8.26.
  2. Point the script at a program you trust. From code/malware/, run python 15_pe_basics.py sample_app.exe.
  3. With no argument the script falls back to sys.executable, your own Python interpreter, which is also a safe PE to read.
"""Reading a Windows PE file's structure with pefile.

Every Windows .exe and .dll is in the PE (Portable Executable) format. Before
running anything (static analysis), an analyst reads its header: which CPU it
targets, when it was built, and how it is divided into sections. pefile parses
all of that for us.

Usage:  python 15_pe_basics.py <path-to-any-exe-or-dll>
Point it at a program you trust (e.g. a copy of python.exe). We never execute it.
"""
import datetime
import sys
import pefile

# Maps the numeric machine code in the header to a human name.
MACHINE = {0x14c: "x86 (32-bit)", 0x8664: "x64 (64-bit)", 0x1c0: "ARM", 0xaa64: "ARM64"}


def analyze(path: str):
    pe = pefile.PE(path, fast_load=True)       # parse headers without loading everything

    machine = pe.FILE_HEADER.Machine
    print("File:", path)
    print("Machine:", MACHINE.get(machine, hex(machine)))

    # TimeDateStamp is when the linker built the file (seconds since 1970, UTC).
    # It is a strong clue, though attackers can forge it.
    ts = pe.FILE_HEADER.TimeDateStamp
    built = datetime.datetime.fromtimestamp(ts, datetime.timezone.utc)
    print("Build timestamp:", built.isoformat(), f"(raw {ts})")

    print("Entry point (RVA):", hex(pe.OPTIONAL_HEADER.AddressOfEntryPoint))
    print("Image base:", hex(pe.OPTIONAL_HEADER.ImageBase))
    print(f"Number of sections: {pe.FILE_HEADER.NumberOfSections}\n")

    # Each section is a region (code, data, resources). High entropy ~7.5-8.0 in a
    # code section often means it is packed or encrypted - a red flag.
    print(f"{'Section':10}{'VirtSize':>10}{'RawSize':>10}{'Entropy':>10}")
    for s in pe.sections:
        name = s.Name.rstrip(b"\x00").decode("latin-1")
        print(f"{name:10}{s.Misc_VirtualSize:>10}{s.SizeOfRawData:>10}{s.get_entropy():>10.2f}")

    pe.close()


if __name__ == "__main__":
    target = sys.argv[1] if len(sys.argv) > 1 else sys.executable
    analyze(target)

What is entropy, and why do analysts care?

Entropy is a measure of how unpredictable a chunk of bytes is, on a scale from 0 to 8. Ordinary code and text sit around 4 to 6.5. Compressed or encrypted data sits near 8, because it looks random. So an unusually high-entropy code section is a hint that the real code has been packed (compressed or encrypted) to hide it, which is common in malware. Our benign .text section measures about 6.39, which is normal.

Common mistakes.
  • ModuleNotFoundError: No module named 'pefile' means the library is not installed. Run pip install pefile in the same environment you run the script from.
  • Passing a file that is not a PE (a text file, a .png) makes pefile raise PEFormatError. That is expected; point it at a real .exe or .dll.
  • Trusting the build timestamp blindly. It is a useful clue but attackers can set it to any value, so treat an oddly old or future date as suspicious rather than authoritative.
  • Forgetting that fast_load=True skips the import table. That is fine here; the next step re-parses the directories to read imports.
Recap
  • Windows programs are PE files: headers plus named sections.
  • pefile.PE(path) reads those fields without running anything.
  • Our benign sample is x64, built 2022-08-06, with 6 sections and normal entropy.
  • High entropy in a code section hints at packing; a build timestamp is a clue, not proof.
