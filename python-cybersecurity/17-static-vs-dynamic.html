Malware analysis: static versus dynamic

What malware analysis is, and the difference between reading a file and running it safely.

▶ Watch this part (02:38:46)

This step opens Module 3, the blue-team half of the course. Here you learn what malware analysis actually is, the difference between reading a suspicious file and running it, and the safety rules that keep you out of trouble. We also build a harmless practice sample so the rest of the module has something safe to look at.

Never download real malware to practise. Real samples can infect your machine, your network and other people the moment you touch them. Everything in this module uses either a file we generate ourselves that contains no runnable code, or a benign Windows program you already trust. You never need a real sample to learn these skills.

What this step does

Module 2 pointed requests at web servers. Module 3 turns the lens onto a single file sitting on disk: a suspicious .exe, a strange attachment, something a user reported. The question a defender asks is simple: what is this, and is it dangerous? The presenter introduces the module (at 2:38:46) by splitting the answer into two families of technique, static and dynamic. This page explains both, explains why we lean on static analysis for learning, and prepares a safe file to study.

The two ways to analyse a file

Static analysis means examining a file without running it: reading its structure, the text hidden inside it, the list of system functions it wants to call. It is safe, fast, and it is where this module spends almost all of its time. Dynamic analysis means the opposite: you actually execute the sample and watch what it does to files, the registry and the network. Dynamic analysis reveals behaviour that static analysis can miss, but running unknown code is dangerous, so it is only ever done inside a locked-down sandbox.

New to malware analysis? What it is and why it matters

Malware analysis is the work of taking a suspicious program and figuring out what it is, what it does and how to detect it elsewhere. Defenders do it to write detection rules, to understand an incident, and to decide how badly a machine was affected. You do not need to be a programmer to start: the first and most valuable questions are answered just by reading the file, which is exactly what static analysis is.

Why run anything in a sandbox?

A sandbox is an isolated, disposable environment, usually a virtual machine with no access to your real files or network, built so that running a sample there cannot escape and harm anything real. Afterwards you throw the environment away. Because this guide is for beginners and because static analysis answers so much on its own, we do not run any samples here. We build the static skills first; dynamic analysis in a proper sandbox is a later topic.

Why we use static analysis for learning

Static analysis is the right place to start for three reasons. It is safe: you cannot be infected by a file you only read. It is fast: you get useful answers in seconds, with no environment to set up. And it is repeatable: the same file always gives the same reading, so you can compare samples and share findings. A practical first-pass habit is to record the file's hash (for example its MD5) so you can refer to the exact file later, then read its structure, imports and strings in turn, as the next four steps do.

A safe sample to practise on

To study a file we need a file. Instead of a real sample, we write one ourselves. make_sample.py writes suspect.bin: a plain binary file that contains the kinds of text a stealer or ransomware would carry (a fake command-and-control URL, a ransom note, Windows function names) but no executable code whatsoever. It cannot run and cannot harm anything. It is just bytes in a file, like a note that mentions scary words.

How can a file look malicious but be harmless?

A program is only dangerous if something runs it. Our sample is never run; the analysis tools only read it. The scary parts are strings (plain text embedded in the bytes) chosen to look like a real threat so the detection tools in this module have realistic patterns to find. Removing the ability to run the file removes all the danger while keeping everything we want to learn from.

Build the sample

  1. Open a terminal in the module's code folder, code/malware/.
  2. Run python make_sample.py.
  3. Confirm a new file, suspect.bin, appears next to the script. The next four steps analyse this file.
"""Create a HARMLESS practice sample so the analysis examples have something to read.

Real malware is dangerous to download and handle. For learning, analysts use safe
stand-ins. This writes a plain binary file that contains the kinds of *strings* a
stealer or ransomware would contain (a fake command-and-control URL, a ransom note,
Windows API names) but NO executable code at all. It cannot run and cannot harm
anything - it is just bytes in a file, like a note that mentions scary words.

Output: suspect.bin  (analyzed by the strings, YARA and classifier examples)
"""
import os

INDICATOR_BLOB = (
    b"\x4d\x5a\x90\x00"                        # 'MZ' + padding, so file-type tools see a PE-like header
    + b"This program cannot be run in DOS mode.\r\n"
    + b"\x00" * 32
    # Strings a STEALER would carry:
    + b"\\Google\\Chrome\\User Data\\Default\\Login Data\0"
    + b"api.telegram.org/bot<token>/sendDocument\0"
    + b"password\0cookies\0credit_card\0"
    # Strings RANSOMWARE would carry:
    + b"All your files have been encrypted!\0"
    + b"Send 0.05 BTC to 1A1zP1eP5QGefi2DMPTfTL5SLmv7DivfNa\0"
    + b".locked\0vssadmin delete shadows\0"
    # Strings a BACKDOOR would carry:
    + b"cmd.exe /c\0"
    + b"185.220.101.1\0"                       # a plain IPv4 literal
    + b"http://malicious-c2-example.onion/gate.php\0"
    # Windows API names (also visible in a real import table):
    + b"VirtualAlloc\0CreateRemoteThread\0WinExec\0RegSetValueExA\0URLDownloadToFileA\0"
    + b"\x00" * 64
)


def main():
    out = os.path.join(os.path.dirname(__file__), "suspect.bin")
    with open(out, "wb") as f:
        f.write(INDICATOR_BLOB)
    print(f"Wrote harmless practice sample: {out} ({len(INDICATOR_BLOB)} bytes)")
    print("It contains scary-looking STRINGS but no runnable code. Safe to analyze.")


if __name__ == "__main__":
    main()

Common mistakes.
  • Downloading a real sample "just to try it". Do not. The generated suspect.bin is all this module needs.
  • Double-clicking a suspicious file to "see what it does". That is unsandboxed dynamic analysis and can infect you instantly.
  • Running make_sample.py from the wrong folder, then wondering where suspect.bin went. It is always written next to the script, so run the next steps from code/malware/ too.
  • Treating strings as proof. Scary text is a clue, not a conviction; a real file can carry decoy strings, and a benign file can mention scary words.
Recap
  • Static analysis reads a file without running it; dynamic analysis runs it and must happen inside a sandbox.
  • This module is static and safe, so you never need to download real malware.
  • make_sample.py writes suspect.bin: realistic malicious-looking strings, but no runnable code, 517 bytes.
  • Always read an unknown file first; recording its hash and reading structure, imports and strings answers most triage questions.
