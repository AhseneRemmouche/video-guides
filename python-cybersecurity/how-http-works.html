How HTTP works in five minutes

Requests, responses, methods, status codes and headers - the vocabulary the requests and Playwright modules assume.

Almost everything in Modules 2 and 4 — sending requests, reading status codes, auditing headers, driving a browser — rests on one simple exchange called HTTP. In five minutes this page gives you the vocabulary the rest of the guide assumes: what a request and a response are, the two methods you will use most, how a URL is put together, what the status-code families mean, and what headers are for.

The whole idea: request and response

HTTP (HyperText Transfer Protocol) is the language a browser or a script uses to talk to a web server. It works in strict turns. Your side sends a request — "please give me this page" — and the server sends back exactly one response — "here it is", or "that does not exist". The server never speaks first. Every page you load and every API call you make is one of these round trips, and often many of them.

A raw request is just text. A GET for the login page looks roughly like this:

GET /login HTTP/1.1
Host: 127.0.0.1:8099
User-Agent: python-requests/2.34.2

And the response is text too — a status line, some headers, a blank line, then the body:

HTTP/1.1 200 OK
Server: LabServer/1.0
Content-Type: text/html

<html><title>Practice Lab Home</title> ... </html>

Methods: GET and POST

Every request names a method — a verb saying what you want to do. There are several, but two cover almost everything you will meet in this guide:

  • GET asks to read something. Loading a page, fetching an image, calling a read-only API — all GETs. A GET should not change anything on the server, and any data it carries rides in the URL.
  • POST asks to send something — submitting a login form, uploading a file, creating a record. Its data travels in the request body, not the URL, so it does not show up in the address bar or server logs the same way.

Anatomy of a URL

A URL (web address) packs several parts into one string. Reading them apart is a core skill, because an analyst spends a lot of time changing one part and watching how the response changes. Take this address:

http://127.0.0.1:8099/search?q=hi&safe=1

The scheme says how to talk — http:// in plain text, or HTTPS encrypted. The host and port say which machine and which door (web servers usually listen on 80 for HTTP and 443 for HTTPS; our lab uses 8099). The path picks the page, and the query string after the ? carries extra named inputs.

Status codes: the server's one-number answer

Every response opens with a three-digit status code that summarises what happened. You do not need to memorise all of them — just the family, which is the first digit.

  • 2xx — success. 200 OK is the one you want: the request worked and the body is the answer.
  • 3xx — redirection. "What you asked for lives at a different URL." Browsers follow these automatically; a login often redirects you afterwards.
  • 4xx — client error. Something about your request was wrong: 404 Not Found (no such page), 401 Unauthorized (log in first), 403 Forbidden (not allowed even if logged in).
  • 5xx — server error. Your request was fine but the server broke handling it. 500 is the generic crash — and, as the lab shows, a 500 provoked by odd input can leak clues about what went wrong.

Headers: the envelope around the body

The body of a response is the content you came for — the HTML, the JSON, the image. The headers are the labelled envelope around it: metadata that both sides read but a human usually does not see. Headers carry the content type, cookies, caching rules, and — important for security work — the server's own name and its defensive settings.

This split is why so much of Module 2 reads headers rather than page text. The Server header can name the software; the missing Content-Security-Policy header is a finding; a Set-Cookie header starts a session. When you audit a site, you spend as much time in the envelope as in the letter.

Recap
  • HTTP is a turn-based exchange: the client sends one request, the server sends one response.
  • GET reads and puts its data in the URL; POST sends and puts its data in the body.
  • A URL splits into scheme, host, port, path and a query string of name=value parameters — the inputs testers probe.
  • Status codes group by first digit: 2xx success, 3xx redirect, 4xx your error, 5xx server error.
  • Headers are the metadata envelope around the body — where fingerprinting and header audits do their work.
