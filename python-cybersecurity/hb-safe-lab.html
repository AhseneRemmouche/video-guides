Building a safe practice lab

How to practise legally: local targets, deliberately vulnerable apps, and isolation.

The single rule of this guide is that you only ever test systems you own or have written permission to test. A practice lab is how you give yourself endless targets while staying firmly on the right side of that line. This chapter explains how to build one safely: local targets on localhost, deliberately vulnerable apps made for learning, and the isolation that keeps experiments from touching anything real.

The one rule, again. A lab exists so you never need to point a tool at someone else's system. If you ever feel the urge to "just try it on a real site", stop - that is the moment this chapter is here to prevent. Re-read the Rules of engagement before any testing.

What a practice lab is

A practice lab is a set of targets, running on hardware you control, that you are completely free to attack, break and rebuild. Because you own every machine involved, every scan, probe and login attempt is authorized by definition. A lab can be as small as a single Python server on your laptop, or as large as several virtual machines on a private network.

The simplest lab: localhost

The address 127.0.0.1 - also written localhost - means "this same computer". When your tool connects to 127.0.0.1, the traffic never leaves the machine; it is your computer talking to itself. That is why this guide ships a tiny server, lab_server.py, bound to 127.0.0.1:8099. You start it in one terminal and run the examples against it in another.

New to localhost? What it is and why it matters

localhost (IP address 127.0.0.1) is a loopback address: packets sent to it are routed straight back to the same host and never touch your network card or the internet. Running a target on localhost is the safest possible lab - there is no way to accidentally hit someone else's machine, because the traffic physically cannot leave.

Our lab server is deliberately insecure in controlled ways, so the tools have something to find. It reflects a query parameter without escaping it (an XSS signal), returns a fake database error when a single quote is injected (a SQL injection signal), hides a few "secret" paths for content discovery, and sends no security headers at all. You meet it first in step 11 and again in step 22.

# one terminal: start the target
python lab_server.py        # serves 127.0.0.1:8099

# another terminal: point a tool at it - this is authorized
python 10_input_probe.py    # probes your own lab

Deliberately vulnerable apps

When you outgrow a one-file server, use applications that were built to be attacked. These are maintained by security educators precisely so learners have realistic, legal targets. Two well-known examples, named here as illustrations at the time of writing:

TargetWhat it isGood for practising
OWASP Juice ShopA modern JavaScript single-page shop, full of planted flawsWeb app testing, SPA behaviour, Playwright exercises
DVWA (Damn Vulnerable Web Application)A classic PHP app with adjustable difficulty levelsInjection, authentication and vulnerability basics

Both are commonly run as local containers or on a lab virtual machine, so they stay off the public internet. Always install them following their own current documentation, and keep them on an isolated network. Check their official sites for up-to-date instructions, as setup steps change.

Not a target list. Vulnerable apps are for your lab. Finding one running on someone else's server does not make it fair game; it is still their system. The permission comes from you installing and owning the copy, not from the app being "designed to be hacked".

Isolation with virtual machines

A virtual machine (VM) is a whole computer simulated in software - its own operating system running in a window on your real one, using tools such as VirtualBox or VMware. VMs are the backbone of a serious lab for two reasons: they contain anything that goes wrong, and they let you network several targets together without exposing your real machine.

Snapshots: an undo button for a whole machine

A snapshot freezes a VM's exact state - disk and memory - at a moment in time. If a tool corrupts the target, or a real malware sample does something nasty, you roll the VM back to the snapshot and it is pristine again in seconds. The habit is simple: take a clean snapshot before each session, and restore it afterwards.

The malware corner of the lab

Module 3 of this guide reads suspicious files statically - with pefile and YARA - which means it never runs them, so it is safe on your normal machine. The sample used, suspect.bin, is a harmless file we built that only looks scary (it contains alarming indicators but no runnable code). If you ever graduate to dynamic analysis - actually executing a sample to watch its behaviour - that belongs in an isolated VM with snapshots and no network, never on your host. See step 17 for the distinction.

Handling real malware safely. Keep live samples in a dedicated, offline VM; never open them on your host "just to look"; disable shared folders and clipboard; and restore the snapshot afterwards. If in doubt, stay static - reading a file cannot execute it.

Never test others - a checklist

Everything above exists so the answer to "is this allowed?" is always yes. Before you run a tool, confirm all of these:

  1. The target is on 127.0.0.1, your own VM, or an app you installed yourself.
  2. No traffic can reach a machine you do not own (check the VM is on a host-only network).
  3. You are not relying on "it is only a test" or "I will not change anything" as permission.
  4. For a real engagement, you have written scope naming the exact systems - see the law and disclosure chapter.
Recap
  • A practice lab gives you unlimited, fully authorized targets on hardware you own.
  • The simplest lab is a localhost server like lab_server.py on 127.0.0.1 - traffic never leaves your machine.
  • Deliberately vulnerable apps (OWASP Juice Shop, DVWA) are realistic targets you install and own.
  • Virtual machines isolate experiments; snapshots let you roll back instantly when something breaks.
  • Read malware statically on your host; run it only inside an offline, snapshotted VM.
  • If any item on the checklist is not a clear yes, do not test.
