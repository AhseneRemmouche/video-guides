Python set-up for security work

Installing Python, virtual environments, and why tools run inside a venv.

Before you can run any of the tools in this guide, you need a working Python set-up that you understand and trust. This chapter is background reading: it explains how to install Python, what a virtual environment is and why security folk live inside one, how pip fetches libraries, and how to run a script from a terminal. Get this foundation right once and every later step just works.

Why this matters for your project. Every module in this guide - the os examples, requests, pefile and yara, and Playwright - is a Python program that pulls in outside libraries. If those libraries are installed in a tidy, isolated place, your tools stay reproducible and you can throw them away without touching the rest of your system. That isolation is itself a small security habit.

Installing Python

Python is the language the whole course is written in. You want a recent version from the official source, python.org (on Windows you can also use the Microsoft Store build). This guide was written and tested on Python 3.14.5, but the examples are standard and run on Python 3.10 and newer.

Check what you already have

Open a terminal and ask Python for its version. The command differs slightly by platform, which is your first taste of why we write cross-platform code later on.

# macOS / Linux
python3 --version

# Windows (the launcher)
py --version

If you see something like Python 3.14.5 printed to standard output, you are ready. If the command is not found, install Python first and, on Windows, tick "Add Python to PATH" in the installer so the PATH knows where to find it.

New to the terminal? What it is and why it matters

A terminal (also called a shell, console, or command prompt) is a text window where you type commands instead of clicking. Security tools are almost always run this way: it is fast, scriptable, and shows you exactly what happened. On Windows the common shells are PowerShell and Command Prompt; on macOS and Linux it is usually bash or zsh. Every command in this guide is typed at such a prompt.

What a virtual environment is

By default, when you install a library it goes into one shared, system-wide location. That sounds convenient until two projects need two different versions of the same library, or until a tool you were only testing leaves clutter behind. A virtual environment (venv) solves this: it is a private folder that holds its own copy of Python and its own set of installed libraries, used by one project only.

Creating and activating one

The venv module ships with Python, so there is nothing extra to install. You create the environment once per project, then "activate" it in each terminal session so that python and pip point at the private copy.

# create a venv called .venv inside your project folder
python -m venv .venv

# activate it - macOS / Linux
source .venv/bin/activate

# activate it - Windows (PowerShell)
.venv\Scripts\Activate.ps1

Once active, most shells show the name (.venv) at the start of the prompt. That little label is your reminder that anything you install now lands inside the project, not on the whole system. To leave, type deactivate.

What you should see. After activating, python --version still prints your Python version, but pip list shows a nearly empty list - just pip and a couple of defaults. That empty list is the point: you start clean and add only what the project needs.

Installing libraries with pip

pip is Python's package installer. It downloads libraries from the Python Package Index (PyPI) and places them inside whichever environment is active. With your venv activated, installing the tools this guide uses looks like this:

pip install requests pefile yara-python playwright

# Playwright also needs a browser binary:
python -m playwright install chromium

These are the exact libraries behind the later modules: requests for HTTP (step 11), pefile and yara-python for malware triage (step 18 onward), and playwright for browser automation (step 22). The guide was tested with requests 2.34.2, pefile 2024.8.26 and yara-python 4.5.4; pinning versions keeps results repeatable.

New to pip? What it is and why it matters

Think of pip as an app store for Python code. A single pip install name fetches a library and everything it depends on. Because it installs into the active environment, running it inside a venv keeps those packages scoped to one project. Running it with no venv active installs system-wide, which is exactly what you are trying to avoid.

Writing down your dependencies

A professional habit is to record exactly what a project needs so someone else (or future you) can rebuild it. The convention is a plain text file, requirements.txt, listing one package and version per line.

requests==2.34.2
pefile==2024.8.26
yara-python==4.5.4
playwright==1.48.0

Anyone can then recreate the environment with pip install -r requirements.txt. The course itself shows a neat trick for this - a script that installs its own missing libraries at runtime using sys.executable - which you build in step 08.

Running your scripts

A Python program is just a text file ending in .py. You run it by naming it after the python command. Many of this guide's examples come in pairs: one terminal runs the practice lab server, a second terminal runs the tool that talks to it.

# terminal 1: start the local practice lab
python lab_server.py

# terminal 2 (venv active): run a tool against it
python 08_requests_intro.py

Keeping tools isolated and safe

Isolation is not only about avoiding version clashes - it is a defensive mindset. Security tooling often means running or inspecting code you do not fully trust. A few habits keep that contained:

  • One venv per project. Never install a security tool into your base system Python.
  • Read before you run. Especially with code from the internet, skim it before executing. The safe practice lab chapter takes this further with virtual machines and snapshots.
  • Keep secrets out of code. Read tokens and passwords from environment variables, never hard-code them - the habit you learn in step 07.
  • Analyse malware only in a sandbox. The malware module reads files statically (without running them); if you ever need to run a sample, do it in a disposable virtual machine, not your host.
Common mistakes. Forgetting to activate the venv (so pip install pollutes the system); running pip as administrator "to make the error go away" (it rarely helps and spreads the mess); and editing a script in one folder while running an older copy from another. When something behaves oddly, check your current working directory and whether the venv prompt is showing.
Recap
  • Install a recent Python (3.10+); this guide used 3.14.5.
  • A virtual environment gives each project its own private libraries - create with python -m venv .venv and activate it before installing anything.
  • pip installs into the active environment; record versions in requirements.txt for reproducibility.
  • Run scripts with python file.py; the lab examples use two terminals, one for the server and one for the tool.
  • Isolation - venvs, sandboxes, secrets in the environment - is a security habit, not just tidiness.
