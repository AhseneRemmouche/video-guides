Week 4 · Day 3 — Tools, Conditional Edges and Memory

Add tools with a ToolNode and conditional edges, trace with LangSmith, and keep memory between turns with SQLite checkpointing. Python and TypeScript.

Companion to Ed Donner's course · uv setup · Python (+ TypeScript/React where it fits) · code from the course repo

This is the day LangGraph starts to pay off. We add three things to our chatbot graph: tools (so the model can act on the world), a conditional edge (so the graph can branch and loop), and checkpointing (so the graph finally remembers between turns). Along the way we switch on LangSmith so we can watch every call happen. The lab (2_lab2.ipynb) gives the model two tools: a Google search through Serper and a push notification to your phone. The TypeScript tabs build the same two tools with LangGraph.js.

The big three today. Conditional edges, tool nodes, and checkpointing. Each is a small amount of code that LangGraph handles elegantly — the ideas matter more than the typing.

Tools touch the code in two places

Whenever an agent uses tools there are always two jobs. First, before calling the model, you describe the tools to it so it knows what it can ask for. Second, after the model replies, you check whether it asked for a tool and, if so, run it. LangGraph gives you a one-liner for each.

New to this? What bind_tools does

A model cannot run your Python functions; it can only ask for them by name. For it to ask, it must first be told each tool's name, description and inputs, formatted as JSON. bind_tools builds that JSON for every tool and attaches it to the model, giving you a new "model with tools". Whenever you invoke that version, the tool descriptions ride along automatically. It is the same JSON we wrote by hand in week 1, now generated for us.

Conditional edges: the graph's "if"

A plain edge always goes to the same next node. A conditional edge runs a small function that looks at the state and decides which node is next. Here the decision is "did the model ask for a tool?". LangGraph ships a ready-made decider called tools_condition that answers exactly that question.

Two subtle wiring details matter. The edge from chatbot is conditional, so after each reply the graph either jumps to the tools node or finishes. But the edge from tools back to chatbot is a plain edge: once a tool runs, its output must always return to the model. Forget that return edge and the agent breaks in confusing ways. LangGraph automatically adds an END for the "no tool" branch.

LangSmith: watch it happen

Before running, the instructor turns on LangSmith. You create a free account, generate an API key, paste a few variables into your .env, and reload. From then on every graph run shows up in a dashboard with its inputs, outputs, latency, token counts, and — eye-opening for beginners worried about cost — the price of each call, often a tiny fraction of a cent. When a tool-using run misbehaves, LangSmith is where you see each step: the search, the push notification, the tool results, the final answer.

New to this? Why a tracing dashboard helps

An agent makes many hidden calls: it may search, read a page, call another tool, then answer. When something goes wrong you cannot see any of that from the final reply alone. LangSmith records the whole chain so you can open a run and read exactly what the model was sent, what it asked for, what each tool returned, and where it failed. It is the single most useful debugging tool for agent work, and the free tier is generous.

Memory at last: checkpointing and thread_id

Recall from day 2 that each invoke is a full run of the graph — a superstep — and state does not survive between supersteps on its own. Checkpointing fixes that: after every superstep LangGraph saves a snapshot of the state, and the next superstep restores it. You switch it on by compiling with a checkpointer, and you tell LangGraph which conversation a run belongs to with a thread_id.

New to this? MemorySaver vs SQLite

MemorySaver stores checkpoints in RAM. It is great for a demo but forgets everything when the program stops. Swap it for SqliteSaver and the exact same memory is written to a database file on disk, so a conversation survives a restart. The remarkable thing is how little changes: the only difference is which checkpointer object you pass to compile(). The graph, nodes and edges stay identical.

Video 8 · Super-steps and checkpointing, explained

8. Day 3 - LangGraph Advanced Tutorial Super Steps & Checkpointing Explained.mp4 · 5:47

Slides, no notebook. Ed recaps the five steps that define a graph before invoke runs it, and lists today's plan: LangSmith for watching runs, ready-made and custom tools, and memory. Then the key idea of the day: a super-step is one complete invocation of the graph. Every user message starts a new super-step, and nodes that run in parallel belong to the same super-step. The reducers combine state within a super-step, but nothing carries over to the next one unless you use checkpointing, which freezes a record of the state after each super-step.

// Video 9 in TypeScript: an online search tool and a homemade push tool. Run: npx tsx lab2_tools.ts
import "dotenv/config";
import { z } from "zod";
import { tool } from "@langchain/core/tools";

// LangSmith tracing needs no code: put LANGSMITH_TRACING=true, LANGSMITH_API_KEY, LANGSMITH_PROJECT in .env

// An off-the-shelf search, written as a tool around Serper's API (SERPER_API_KEY in .env)
const search = tool(
  async ({ query }) => {
    const res = await fetch("https://google.serper.dev/search", {
      method: "POST",
      headers: { "X-API-KEY": process.env.SERPER_API_KEY ?? "", "Content-Type": "application/json" },
      body: JSON.stringify({ q: query }),
    });
    const data = (await res.json()) as { organic?: { title: string; snippet: string }[] };
    return (data.organic ?? []).map((r) => `${r.title}: ${r.snippet}`).join("\n");
  },
  {
    name: "search",
    description: "Useful for when you need more information from an online search",
    schema: z.object({ query: z.string() }),
  },
);

const toolPush = tool(
  async ({ text }) => {
    await fetch("https://api.pushover.net/1/messages.json", {
      method: "POST",
      body: new URLSearchParams({
        token: process.env.PUSHOVER_TOKEN ?? "",
        user: process.env.PUSHOVER_USER ?? "",
        message: text,
      }),
    });
    return "success";
  },
  {
    name: "send_push_notification",
    description: "useful for when you want to send a push notification",
    schema: z.object({ text: z.string() }),
  },
);


// Try the tools "the LangChain way": every tool has invoke
console.log(await search.invoke({ query: "What is the capital of France?" }));
console.log(await toolPush.invoke({ text: "Hello, me" }));

// Bring them together
export const tools = [search, toolPush];

import { createInterface } from "node:readline/promises";
import { stdin as input, stdout as output } from "node:process";
import { z } from "zod";
import { tool } from "@langchain/core/tools";
import { ChatOpenAI } from "@langchain/openai";
import { StateGraph, MessagesAnnotation, START, END } from "@langchain/langgraph";
import { ToolNode, toolsCondition } from "@langchain/langgraph/prebuilt";

// The same two tools as Video 9
const search = tool(
  async ({ query }) => {
    const res = await fetch("https://google.serper.dev/search", {
      method: "POST",
      headers: { "X-API-KEY": process.env.SERPER_API_KEY ?? "", "Content-Type": "application/json" },
      body: JSON.stringify({ q: query }),
    });
    const data = (await res.json()) as { organic?: { title: string; snippet: string }[] };
    return (data.organic ?? []).map((r) => `${r.title}: ${r.snippet}`).join("\n");
  },
  {
    name: "search",
    description: "Useful for when you need more information from an online search",
    schema: z.object({ query: z.string() }),
  },
);

const toolPush = tool(
  async ({ text }) => {
    await fetch("https://api.pushover.net/1/messages.json", {
      method: "POST",
      body: new URLSearchParams({
        token: process.env.PUSHOVER_TOKEN ?? "",
        user: process.env.PUSHOVER_USER ?? "",
        message: text,
      }),
    });
    return "success";
  },
  {
    name: "send_push_notification",
    description: "useful for when you want to send a push notification",
    schema: z.object({ text: z.string() }),
  },
);

const tools = [search, toolPush];

// Step 1 + 2: MessagesAnnotation is the ready-made State with one messages field and the addMessages reducer
// Step 3: the model, told about the tools (request side), and the chatbot node
const llm = new ChatOpenAI({ model: "gpt-6-luna", reasoning: { effort: "none" } });
const llmWithTools = llm.bindTools(tools);

async function chatbot(state: typeof MessagesAnnotation.State) {
  return { messages: [await llmWithTools.invoke(state.messages)] };
}

// Steps 3-5: the tools node (response side), the conditional edge, the loop back, compile
const graph = new StateGraph(MessagesAnnotation)
  .addNode("chatbot", chatbot)
  .addNode("tools", new ToolNode(tools))
  .addConditionalEdges("chatbot", toolsCondition, ["tools", END])
  .addEdge("tools", "chatbot")
  .addEdge(START, "chatbot")
  .compile();
console.log((await graph.getGraphAsync()).drawMermaid());

// Each message is still a fresh invoke: no memory yet
async function chat(userInput: string): Promise<string> {
  const result = await graph.invoke({ messages: [{ role: "user", content: userInput }] });
  return String(result.messages[result.messages.length - 1].content);
}

const rl = createInterface({ input, output });
for (;;) {
  const userInput = await rl.question("You (empty line to quit): ");
  if (!userInput.trim()) break;
  console.log("Bot:", await chat(userInput));
}
rl.close();

  .addEdge(START, "chatbot")
  .compile({ checkpointer: memory });
console.log((await graph.getGraphAsync()).drawMermaid());

// The thread_id picks which conversation's memory to use (try "2", then back to "1")
const config = { configurable: { thread_id: "1" } };

async function chat(userInput: string): Promise<string> {
  const result = await graph.invoke({ messages: [{ role: "user", content: userInput }] }, config);
  return String(result.messages[result.messages.length - 1].content);
}

import "dotenv/config";
import { createInterface } from "node:readline/promises";
import { stdin as input, stdout as output } from "node:process";
import { z } from "zod";
import { tool } from "@langchain/core/tools";
import { ChatOpenAI } from "@langchain/openai";
import { StateGraph, MessagesAnnotation, START, END } from "@langchain/langgraph";
import { ToolNode, toolsCondition } from "@langchain/langgraph/prebuilt";
import { SqliteSaver } from "@langchain/langgraph-checkpoint-sqlite";

// The same two tools as Video 9
const search = tool(
  async ({ query }) => {
    const res = await fetch("https://google.serper.dev/search", {
      method: "POST",
      headers: { "X-API-KEY": process.env.SERPER_API_KEY ?? "", "Content-Type": "application/json" },
      body: JSON.stringify({ q: query }),
    });
    const data = (await res.json()) as { organic?: { title: string; snippet: string }[] };
    return (data.organic ?? []).map((r) => `${r.title}: ${r.snippet}`).join("\n");
  },
  {
    name: "search",
    description: "Useful for when you need more information from an online search",
    schema: z.object({ query: z.string() }),
  },
);

const toolPush = tool(
  async ({ text }) => {
    await fetch("https://api.pushover.net/1/messages.json", {
      method: "POST",
      body: new URLSearchParams({
        token: process.env.PUSHOVER_TOKEN ?? "",
        user: process.env.PUSHOVER_USER ?? "",
        message: text,
      }),
    });
    return "success";
  },
  {
    name: "send_push_notification",
    description: "useful for when you want to send a push notification",
    schema: z.object({ text: z.string() }),
  },
);

const tools = [search, toolPush];

// The only real change: a checkpointer that writes to a database file on disk
const sqlMemory = SqliteSaver.fromConnString("memory.db");

// Step 1 + 2: MessagesAnnotation is the ready-made State with one messages field and the addMessages reducer
// Step 3: the model, told about the tools (request side), and the chatbot node
const llm = new ChatOpenAI({ model: "gpt-6-luna", reasoning: { effort: "none" } });
const llmWithTools = llm.bindTools(tools);

async function chatbot(state: typeof MessagesAnnotation.State) {
  return { messages: [await llmWithTools.invoke(state.messages)] };
}

// Steps 3-5: the tools node (response side), the conditional edge, the loop back, compile
const graph = new StateGraph(MessagesAnnotation)
  .addNode("chatbot", chatbot)
  .addNode("tools", new ToolNode(tools))
  .addConditionalEdges("chatbot", toolsCondition, ["tools", END])
  .addEdge("tools", "chatbot")
  .addEdge(START, "chatbot")
  .compile({ checkpointer: sqlMemory });

  return String(result.messages[result.messages.length - 1].content);
}

What you should see. Ask the bot to "send me a push notification with the current USD to GBP exchange rate" and it will search, find the rate, and push it to your phone — two tool calls in one turn. Tell it your name, ask again later, and with the checkpointer on it remembers. Open LangSmith and the whole chain is laid out: the search, the push, the final reply. With the SQLite checkpointer, the memory even survives a kernel restart.
Common mistakes.
  • No return edge from tools. Without add_edge("tools", "chatbot") the tool results never reach the model and the run stalls or answers nonsense.
  • Forgetting the config. Memory only works if you pass the same thread_id on every invoke. Leave it out and each turn starts fresh.
  • Expecting MemorySaver to persist. It lives in RAM and clears when the program stops. Use SqliteSaver for memory that survives a restart.
  • Importing Tool from langchain.agents. That worked in the video; LangChain 1.0 removed it. Import it from langchain_core.tools.
  • No module named 'langgraph.checkpoint.sqlite'. The SQLite checkpointer is a separate package: uv add langgraph-checkpoint-sqlite.
Recap
  • Tools appear twice: bind_tools describes them to the model, and a ToolNode runs the one the model asks for.
  • A conditional edge with tools_condition routes the graph to the tools node on a tool call, or to END otherwise; the tools node always loops back to the chatbot.
  • LangSmith records every run — inputs, outputs, latency, tokens, cost — and is the main way to debug agent behaviour.
  • Checkpointing saves a snapshot after each superstep so the graph remembers; compile with a checkpointer to switch it on.
  • The thread_id selects which conversation's memory to use, keeping separate chats isolated.
  • MemorySaver keeps memory in RAM; SqliteSaver writes it to disk, changing only one line.
  • Any function becomes a tool with LangChain's Tool wrapper (name, function, description); LangChain's community package adds ready-made ones like Serper search.
