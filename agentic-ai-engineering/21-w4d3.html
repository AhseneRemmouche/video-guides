Week 4 · Day 3 — Tools, Conditional Edges and Memory

Add tools with a ToolNode and conditional edges, trace with LangSmith, and keep memory between turns with SQLite checkpointing. Python and TypeScript.

Companion to Ed Donner's course · uv setup · Python (+ TypeScript/React where it fits) · code from the course repo

This is the day LangGraph starts to pay off. We add three things to our chatbot graph: tools (so the model can act on the world), a conditional edge (so the graph can branch and loop), and checkpointing (so the graph finally remembers between turns). Along the way we switch on LangSmith so we can watch every call happen. The Python lab wires its tools to Playwright, a real browser the agent can drive; the TypeScript port uses two safe local tools so it runs anywhere.

The big three today. Conditional edges, tool nodes, and checkpointing. Each is a small amount of code that LangGraph handles elegantly — the ideas matter more than the typing.

Tools touch the code in two places

Whenever an agent uses tools there are always two jobs. First, before calling the model, you describe the tools to it so it knows what it can ask for. Second, after the model replies, you check whether it asked for a tool and, if so, run it. LangGraph gives you a one-liner for each.

New to this? What bind_tools does

A model cannot run your Python functions; it can only ask for them by name. For it to ask, it must first be told each tool's name, description and inputs, formatted as JSON. bind_tools builds that JSON for every tool and attaches it to the model, giving you a new "model with tools". Whenever you invoke that version, the tool descriptions ride along automatically. It is the same JSON we wrote by hand in week 1, now generated for us.

Conditional edges: the graph's "if"

A plain edge always goes to the same next node. A conditional edge runs a small function that looks at the state and decides which node is next. Here the decision is "did the model ask for a tool?". LangGraph ships a ready-made decider called tools_condition that answers exactly that question.

Two subtle wiring details matter. The edge from chatbot is conditional, so after each reply the graph either jumps to the tools node or finishes. But the edge from tools back to chatbot is a plain edge: once a tool runs, its output must always return to the model. Forget that return edge and the agent breaks in confusing ways. LangGraph automatically adds an END for the "no tool" branch.

LangSmith: watch it happen

Before running, the instructor turns on LangSmith. You create a free account, generate an API key, paste a few variables into your .env, and reload. From then on every graph run shows up in a dashboard with its inputs, outputs, latency, token counts, and — eye-opening for beginners worried about cost — the price of each call, often a tiny fraction of a cent. When a tool-using run misbehaves, LangSmith is where you see each step: the search, the navigation, the tool results, the final answer.

New to this? Why a tracing dashboard helps

An agent makes many hidden calls: it may search, read a page, call another tool, then answer. When something goes wrong you cannot see any of that from the final reply alone. LangSmith records the whole chain so you can open a run and read exactly what the model was sent, what it asked for, what each tool returned, and where it failed. It is the single most useful debugging tool for agent work, and the free tier is generous.

Memory at last: checkpointing and thread_id

Recall from day 2 that each invoke is a full run of the graph — a superstep — and state does not survive between supersteps on its own. Checkpointing fixes that: after every superstep LangGraph saves a snapshot of the state, and the next superstep restores it. You switch it on by compiling with a checkpointer, and you tell LangGraph which conversation a run belongs to with a thread_id.

New to this? MemorySaver vs SQLite

MemorySaver stores checkpoints in RAM. It is great for a demo but forgets everything when the program stops. Swap it for SqliteSaver and the exact same memory is written to a database file on disk, so a conversation survives a restart. The remarkable thing is how little changes: the only difference is which checkpointer object you pass to compile(). The graph, nodes and edges stay identical.

Playwright: a browser as a tool

The Python lab hands the agent Playwright, Microsoft's browser-automation tool. LangChain's Playwright toolkit turns a real Chromium browser into a set of tools — navigate to a page, extract text, click, read links — that the agent can call. We only skim it today; day 4 builds a full browsing agent on it.

Here is the complete lab in both languages. Python drives Playwright and uses MemorySaver; the TypeScript port swaps in two safe local tools (a calculator and a fake price lookup) so it needs no browser and no key, and it demonstrates thread isolation.

// Week 4 - Day 3: tools + conditional edges + memory (LangGraph.js port of 3_lab3.py).
//
// Three new ideas:
//   * bindTools      - tell the LLM which tools exist so it can ask to call one.
//   * ToolNode + toolsCondition - a prebuilt node that runs whatever tool the LLM
//     asked for, and a prebuilt router that sends the graph to "tools" when there is
//     a tool call, or to END when there is not.
//   * a checkpointer (MemorySaver) + a thread_id - so the graph REMEMBERS the
//     conversation between separate invoke() calls. Same thread_id = same memory.
//
// The course uses Playwright browser tools; here we use two safe local tools (a
// calculator and a fake price lookup) so the file needs no browser and no API key.
import { StateGraph, MessagesAnnotation, START, MemorySaver } from "@langchain/langgraph";
import { ToolNode, toolsCondition } from "@langchain/langgraph/prebuilt";
import { tool } from "@langchain/core/tools";
import { z } from "zod";
import { makeLlm } from "./model.js";

// --- Tools -----------------------------------------------------------------
// tool() wraps a function with a name, description and a zod schema for its input.
// The description is how the model decides when to call the tool.
const calculator = tool(
  async ({ expression }) => {
    if (!/^[0-9+\-*/(). ]+$/.test(expression)) {
      return "Error: only numbers and + - * / ( ) are allowed.";
    }
    try {
      // Function(...) evaluates the arithmetic; the regex above restricts the input.
      const value = Function(`"use strict"; return (${expression});`)();
      return String(value);
    } catch (err) {
      return `Error: ${String(err)}`;
    }
  },
  {
    name: "calculator",
    description: "Evaluate a basic arithmetic expression, e.g. '23 * 19' or '(2+3)/4'.",
    schema: z.object({ expression: z.string().describe("the arithmetic to evaluate") }),
  },
);

const getPrice = tool(
  async ({ symbol }) => {
    const prices: Record<string, number> = { AAPL: 231.4, MSFT: 418.2, GOOG: 165.7, NVDA: 142.9 };
    const price = prices[symbol.toUpperCase()];
    return price === undefined
      ? `No price on file for ${symbol}. Known: ${Object.keys(prices).join(", ")}.`
      : `${symbol.toUpperCase()} is trading at $${price.toFixed(2)}.`;
  },
  {
    name: "get_price",
    description: "Return the current price for a stock ticker symbol (FAKE demo data).",
    schema: z.object({ symbol: z.string().describe("a ticker symbol like AAPL") }),
  },
);

const tools = [calculator, getPrice];

// The LLM, told about the tools so it can request them.
const llmWithTools = makeLlm().bindTools(tools);

async function chatbot(state: typeof MessagesAnnotation.State) {
  return { messages: [await llmWithTools.invoke(state.messages)] };
}

// Build the graph: chatbot <-> tools loop. toolsCondition routes chatbot -> tools when
// the last message has tool calls, otherwise chatbot -> END. After tools run, go back
// to the chatbot so it can use the results.
const graph = new StateGraph(MessagesAnnotation)
  .addNode("chatbot", chatbot)
  .addNode("tools", new ToolNode(tools))
  .addEdge(START, "chatbot")
  .addConditionalEdges("chatbot", toolsCondition)
  .addEdge("tools", "chatbot")
  // The checkpointer persists state per thread_id, so the graph remembers turns.
  .compile({ checkpointer: new MemorySaver() });

/** Send one message on a given conversation thread and return the reply text. */
export async function send(userInput: string, threadId: string): Promise<string> {
  const result = await graph.invoke(
    { messages: [{ role: "user", content: userInput }] },
    { configurable: { thread_id: threadId } },
  );
  return String(result.messages.at(-1)?.content ?? "");
}

async function main() {
  console.log(await graph.getGraphAsync().then((g) => g.drawMermaid()));

  const thread = "demo-thread-1";

  // Turn 1: give a fact AND ask for a tool.
  const q1 = "My name is Ada. Please use the calculator to compute 23 * 19.";
  console.log(`\n[thread=${thread}] User: ${q1}`);
  console.log(`Assistant: ${await send(q1, thread)}`);

  // Turn 2: SAME thread_id. If memory works, the model recalls the name from turn 1.
  const q2 = "What is my name, and what was the multiplication result you gave me?";
  console.log(`\n[thread=${thread}] User: ${q2}`);
  console.log(`Assistant: ${await send(q2, thread)}`);

  // Turn 3: a different thread has no memory of Ada - proves isolation.
  const q3 = "What is my name?";
  console.log(`\n[thread=demo-thread-2] User: ${q3}`);
  console.log(`Assistant: ${await send(q3, "demo-thread-2")}`);
}

main().catch((err) => {
  console.error(err);
  process.exitCode = 1;
});

What you should see. Ask the Python bot to "send me a push notification with the current USD to GBP exchange rate" and it will browse, find the rate, and push it to your phone — two tool calls in one turn. Tell it your name, ask again later, and with the checkpointer on it remembers. Open LangSmith and the whole chain is laid out: the search, the navigation, the push, the final reply.
Common mistakes.
  • No return edge from tools. Without add_edge("tools", "chatbot") the tool results never reach the model and the run stalls or answers nonsense.
  • Forgetting the config. Memory only works if you pass the same thread_id on every invoke. Leave it out and each turn starts fresh.
  • Expecting MemorySaver to persist. It lives in RAM and clears when the program stops. Use SqliteSaver for memory that survives a restart.
  • Mixing sync and async. Playwright tools are async, so the chat callback must use ainvoke, not invoke.
  • Browser does not launch. Run playwright install once first, and keep nest_asyncio.apply() in the notebook.
Recap
  • Tools appear twice: bind_tools describes them to the model, and a ToolNode runs the one the model asks for.
  • A conditional edge with tools_condition routes the graph to the tools node on a tool call, or to END otherwise; the tools node always loops back to the chatbot.
  • LangSmith records every run — inputs, outputs, latency, tokens, cost — and is the main way to debug agent behaviour.
  • Checkpointing saves a snapshot after each superstep so the graph remembers; compile with a checkpointer to switch it on.
  • The thread_id selects which conversation's memory to use, keeping separate chats isolated.
  • MemorySaver keeps memory in RAM; SqliteSaver writes it to disk, changing only one line.
  • Playwright turns a real browser into tools the agent can drive — the foundation for day 4's browsing agent.
