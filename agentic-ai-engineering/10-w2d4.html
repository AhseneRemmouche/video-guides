Week 2 · Day 4 — Deep Research, a Multi-Agent Team

A team that researches the web: a planner designs searches, search agents run them in parallel, and a writer composes a report. Hosted web-search tool and a typed plan. Python and TypeScript.

Companion to Ed Donner's course · uv setup · Python (+ TypeScript/React where it fits) · code from the course repo

Day 4 is the week's first big project: Deep Research, an agentic workflow that takes a topic, searches the web, and writes a report. This is the pattern the big labs ship as a "deep research" button, and it is built here from a small team of agents you already know how to make. Three familiar ideas carry the whole thing: agents, structured outputs, and running work in parallel with asyncio. The one new piece is a hosted tool.

The team has four members. A planner turns your query into a short list of searches. A search agent runs each search on the web. A writer folds the findings into a long report. An email agent sends it. The notebook builds these step by step; the real project wraps the same steps in a ResearchManager class. We look at the notebook first, then the project shape.

The web search is paid and hosted — we did not run it live. OpenAI's WebSearchTool runs on OpenAI's servers and costs about 2.5 cents per call at the settings used here (and sometimes more, since one call can trigger several searches). Ten searches can add up to a few dollars. This guide shows the search exactly as in the course but did not call it live; our runnable checks used a local model with no web access. Start with a small number of searches and watch your spend.

The deep research team

The hosted WebSearchTool

Until now every tool was a Python function you wrote. A hosted tool is different: OpenAI runs it on their servers. There are three — web search, file search, and a computer tool — and this project uses web search. You give the search agent a WebSearchTool and the SDK handles the actual searching remotely. The agent's job is just to summarise what comes back.

New to this? What tool_choice="required" does

The search agent is created with model_settings=ModelSettings(tool_choice="required"). Normally a model decides for itself whether to use a tool. "Required" removes that choice: the agent must call its tool. Since the whole point of this agent is to run a web search, you do not want it to answer from memory and skip the search, so you force the tool call. search_context_size="low" keeps each search small and cheap.

The planner and structured outputs

The planner's job is to turn one query into a handful of good searches. It uses a structured output so the result is data, not prose. Two Pydantic models describe the shape: a WebSearchItem has a reason and a query, and a WebSearchPlan holds a list of those items. Setting the planner's output type to WebSearchPlan guarantees you get back a tidy list you can loop over.

New to this? Why ask for a reason as well as a query

Two reasons. First, the reason is passed to the search agent as context, so it searches with purpose. Second, asking the model to write the reason before the query nudges it to think — a light version of "chain of thought". Because the model predicts the next most-likely words, having just written a rationale makes the query it writes next more coherent with that rationale. You tend to get better queries as a side effect, with no extra code. The Field(description=...) text is sent to the model too, so it knows what each field is for.

Running the searches in parallel

Searches do not depend on each other, so there is no reason to run them one at a time. Each search mostly waits on the network, which is exactly what async/await and asyncio are good at. The lab creates one task per search and then awaits them all together, so three searches take about as long as the slowest one, not the sum of all three.

The research manager

The ResearchManager is the conductor. It holds the four steps as methods and runs them in order inside one trace, reporting progress as it goes. The Python version is an async generator that yields status strings — "Searches planned…", "writing report…" — and finally the report, which is exactly what a streaming UI needs (that UI arrives on Day 5). One difference from the lab: the manager uses asyncio.as_completed so it can print "2/5 completed" as each search lands, and wraps each search in a try/except so one failed search does not sink the whole run.

from agents import Runner, trace, gen_trace_id
from search_agent import search_agent
from planner_agent import planner_agent, WebSearchItem, WebSearchPlan
from writer_agent import writer_agent, ReportData
from email_agent import email_agent
import asyncio

class ResearchManager:

    async def run(self, query: str):
        """ Run the deep research process, yielding the status updates and the final report"""
        trace_id = gen_trace_id()
        with trace("Research trace", trace_id=trace_id):
            print(f"View trace: https://platform.openai.com/traces/trace?trace_id={trace_id}")
            yield f"View trace: https://platform.openai.com/traces/trace?trace_id={trace_id}"
            print("Starting research...")
            search_plan = await self.plan_searches(query)
            yield "Searches planned, starting to search..."     
            search_results = await self.perform_searches(search_plan)
            yield "Searches complete, writing report..."
            report = await self.write_report(query, search_results)
            yield "Report written, sending email..."
            await self.send_email(report)
            yield "Email sent, research complete"
            yield report.markdown_report
        

    async def plan_searches(self, query: str) -> WebSearchPlan:
        """ Plan the searches to perform for the query """
        print("Planning searches...")
        result = await Runner.run(
            planner_agent,
            f"Query: {query}",
        )
        print(f"Will perform {len(result.final_output.searches)} searches")
        return result.final_output_as(WebSearchPlan)

    async def perform_searches(self, search_plan: WebSearchPlan) -> list[str]:
        """ Perform the searches to perform for the query """
        print("Searching...")
        num_completed = 0
        tasks = [asyncio.create_task(self.search(item)) for item in search_plan.searches]
        results = []
        for task in asyncio.as_completed(tasks):
            result = await task
            if result is not None:
                results.append(result)
            num_completed += 1
            print(f"Searching... {num_completed}/{len(tasks)} completed")
        print("Finished searching")
        return results

    async def search(self, item: WebSearchItem) -> str | None:
        """ Perform a search for the query """
        input = f"Search term: {item.query}\nReason for searching: {item.reason}"
        try:
            result = await Runner.run(
                search_agent,
                input,
            )
            return str(result.final_output)
        except Exception:
            return None

    async def write_report(self, query: str, search_results: list[str]) -> ReportData:
        """ Write the report for the query """
        print("Thinking about report...")
        input = f"Original query: {query}\nSummarized search results: {search_results}"
        result = await Runner.run(
            writer_agent,
            input,
        )

        print("Finished writing report")
        return result.final_output_as(ReportData)
    
    async def send_email(self, report: ReportData) -> None:
        print("Writing email...")
        result = await Runner.run(
            email_agent,
            report.markdown_report,
        )
        print("Email sent")
        return report
// ResearchManager (TypeScript port of 2_openai/deep_research/research_manager.py).
// It orchestrates the four agents: plan -> search (in parallel) -> write -> email.
//
// The Python version is an async generator that yields status strings. Here run() is an async generator too,
// so a console runner or the HTTP API can watch progress; the final value yielded is the markdown report.
import { run, withTrace, getGlobalTraceProvider } from "@openai/agents";
import { plannerAgent, type WebSearchItem, type WebSearchPlan } from "./planner.js";
import { searchAgent } from "./search.js";
import { writerAgent, type ReportData } from "./writer.js";
import { emailAgent } from "./email.js";
import { LOCAL } from "../setup.js";

export class ResearchManager {
  /** The full report from the most recent run (set once writeReport completes). */
  report: ReportData | undefined;

  /** Run the deep research process, yielding status updates and finally the markdown report. */
  async *run(query: string): AsyncGenerator<string> {
    const traceId = getGlobalTraceProvider().generateTraceId();
    const updates: string[] = [];
    this.report = undefined;
    // A local captured by the closure below. Because it is assigned inside a closure, TypeScript keeps it at
    // its declared type at the use site (unlike a class property, which it would narrow to never here).
    let report: ReportData | undefined;

    const work = withTrace(
      "Research trace",
      async () => {
        if (!LOCAL) updates.push(`View trace: https://platform.openai.com/traces/trace?trace_id=${traceId}`);
        console.log("Starting research...");
        const plan = await this.planSearches(query);
        updates.push("Searches planned, starting to search...");
        const results = await this.performSearches(plan);
        updates.push("Searches complete, writing report...");
        report = await this.writeReport(query, results);
        this.report = report;
        updates.push("Report written, sending email...");
        await this.sendEmail(report);
        updates.push("Email sent, research complete");
      },
      { traceId },
    );

    // Drain status updates as they are recorded, while the workflow runs.
    let done = false;
    void work.finally(() => {
      done = true;
    });
    let sent = 0;
    while (!done || sent < updates.length) {
      if (sent < updates.length) {
        yield updates[sent++]!;
      } else {
        await new Promise((r) => setTimeout(r, 100));
      }
    }
    await work; // rethrow if the workflow failed
    if (report) yield report.markdown_report;
  }

  /** Plan the searches to perform for the query. */
  async planSearches(query: string): Promise<WebSearchPlan> {
    console.log("Planning searches...");
    const result = await run(plannerAgent, `Query: ${query}`);
    const plan = result.finalOutput!;
    console.log(`Will perform ${plan.searches.length} searches`);
    return plan;
  }

  /** Perform the planned searches in parallel; report progress as each one completes. */
  async performSearches(plan: WebSearchPlan): Promise<string[]> {
    console.log("Searching...");
    let numCompleted = 0;
    const tasks = plan.searches.map((item) =>
      this.search(item).then((r) => {
        numCompleted += 1;
        console.log(`Searching... ${numCompleted}/${plan.searches.length} completed`);
        return r;
      }),
    );
    const results = (await Promise.all(tasks)).filter((r): r is string => r !== null);
    console.log("Finished searching");
    return results;
  }

  /** Perform one search; a failed search returns null instead of killing the whole run. */
  async search(item: WebSearchItem): Promise<string | null> {
    const input = `Search term: ${item.query}\nReason for searching: ${item.reason}`;
    try {
      const result = await run(searchAgent, input);
      return String(result.finalOutput);
    } catch {
      return null;
    }
  }

  async writeReport(query: string, searchResults: string[]): Promise<ReportData> {
    console.log("Thinking about report...");
    const input = `Original query: ${query}\nSummarized search results: ${JSON.stringify(searchResults)}`;
    const result = await run(writerAgent, input);
    console.log("Finished writing report");
    return result.finalOutput!;
  }

  async sendEmail(report: ReportData): Promise<ReportData> {
    console.log("Writing email...");
    await run(emailAgent, report.markdown_report);
    console.log("Email sent");
    return report;
  }
}

How the manager orchestrates the team

What you should see. The planner prints a plan of three (lab) or five (project) searches, each with a reason and a query. The searches run in parallel — in the trace the search agents appear side by side, not one after another — then the writer produces a long markdown report and the email agent sends it, ending with "Hooray!". In the OpenAI traces dashboard the whole run appears as one tree named "Research trace".
Common mistakes.
  • Surprise cost. Each hosted web search costs roughly 2.5 cents, and a single call can run several searches. Raising HOW_MANY_SEARCHES multiplies the bill. Start at 3 and watch the dashboard.
  • Forgetting tool_choice="required". Without it the search agent may answer from memory and never search, giving stale, made-up results.
  • Reading a structured field off free text. result.final_output.searches only works because the planner has an output_type. Without it the output is a string and the attribute access fails.
  • Running searches in a plain loop. Awaiting each search one at a time works but is slow. The parallel version (asyncio.gather / Promise.all) is the whole reason the project feels fast.
  • SendGrid not set up. The email step needs a verified sender and SENDGRID_API_KEY in .env; change the hard-coded addresses to your own.
Recap
  • Deep Research is a team of four agents: a planner, a web-searcher, a writer, and an emailer, run in order by a manager.
  • The WebSearchTool is a hosted tool — it runs on OpenAI's servers and is billed per call, so it was shown but not run live here.
  • The planner uses a structured output: output_type=WebSearchPlan returns a typed list of searches, each with a query and a reason.
  • Asking for a reason as well as a query gives the searcher context and nudges the model toward better queries.
  • Searches are independent and network-bound, so they run in parallel with asyncio.gather (lab) or asyncio.as_completed (project) — Promise.all in TypeScript.
  • The writer returns a ReportData (summary, markdown report, follow-up questions); the manager turns the notebook's loose steps into a reusable class with progress and error handling.
Honesty note. The hosted web search and the SendGrid email are paid or hosted services, shown exactly as in the course but not run live for this guide. The agent wiring, structured outputs and parallel orchestration were verified locally against Ollama (free, with no web access), and the TypeScript port type-checks and builds with vite. Small local models call tools less reliably than the cloud models, so where a search or handoff was narrated rather than truly invoked, that is a limit of the tiny model, not of the code.
