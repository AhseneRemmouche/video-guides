Week 2 · Day 2 — Tools, Handoffs and Agents as Tools

Build a sales team of agents: give them tools (including sending email), run several in parallel with asyncio, use agents as tools, and hand off between them. Python and TypeScript.

Companion to Ed Donner's course · uv setup · Python (+ TypeScript/React where it fits) · code from the course repo

Day two is our first real Agents SDK project: an automated Sales Development Rep (SDR) that writes cold sales emails for a made-up company called ComplAI. We build it in three layers, each one a little more "agentic" than the last. First a plain workflow where our own Python runs several agents. Then we give an agent a real tool (a function that sends email). Finally we let agents collaborate with each other in two different ways — agents as tools and handoffs — and we learn the crucial difference between them.

The star of the day is how little code each layer takes. The boilerplate JSON we wrote by hand in week one to describe a tool is now a single decorator. The instructor builds it up cell by cell in Cursor, and so will we.

About SendGrid (a paid/hosted service). The emails are sent through SendGrid, a Twilio company for sending transactional email. It has a free tier that the instructor uses, but it is an external hosted service: you create an account, make an API key, add SENDGRID_API_KEY to your .env, and verify a single sender email so SendGrid is allowed to send as you. We did not call SendGrid live for this guide. The code is shown exactly as in the course; our local verification swapped the real send for a safe stand-in.

The three layers we build

Layer 1: a workflow of agents

We create three sales agents with the same job but different personalities — professional, humorous, and busy/concise — by giving each a different instructions (its system prompt). Then we ask all three to write an email at the same time using asyncio's gather. There is nothing autonomous here yet: our Python decides the order. This is a workflow.

New to this? What asyncio.gather does

await asyncio.gather(a(), b(), c()) starts three coroutines and lets the event loop overlap them: while one waits on the network, another runs. You get back a list of their results in the order you passed them. Because each Runner.run(...) spends almost all its time waiting for the model, running three together finishes in roughly the time of one instead of three. Day one introduced this; here we finally use it.

The lab then adds a fourth agent, a sales_picker, that reads the three drafts and returns the one it likes best. That is the familiar "ask many, then pick" shape from week one, now written with agents.

Layer 2: giving an agent a tool

A tool is a function the model is allowed to call. In week one we described each tool with a big block of JSON by hand. The SDK does that for us: put @function_tool above a normal function and the SDK reads the function's name, its docstring, and its type hints to build the JSON schema automatically.

New to this? What a "decorator" is

A decorator is the @something line written directly above a function. It wraps the function in extra behaviour without you changing the function's body. Here @function_tool takes your ordinary send_email function and hands back a tool object: it keeps your code but adds the machine-readable description the model needs to call it. The docstring becomes the tool's description, so a clear docstring is worth writing.

Layer 3a: agents as tools

Here is the twist: a whole agent can itself become a tool. Call agent.as_tool(...) and you get a tool that, when called, runs that agent and returns its answer. So our three sales agents become three tools, and we hand them to a new Sales Manager agent. The manager does not write emails itself; it calls its sales-agent tools to produce drafts, picks the best, and then calls the send_email tool. Now an agent — not our Python — is choosing what to run and when.

Layer 3b: handoffs

A handoff looks similar but behaves differently. You give an agent a list of handoffs=[...] — other agents it can delegate to. We build an Email Manager agent (it owns its own subject-writer and HTML-converter tools, plus a send-email tool) and give it to the Sales Manager as a handoff. When the Sales Manager has chosen the winning draft, it hands off to the Email Manager, which formats and sends the email. Control passes across and does not come back.

New to this? The handoff_description

An agent that might be handed off to carries a short handoff_description, for example "Convert an email to HTML and send it". It is like a tool description but for a whole agent: it tells other agents what this agent is for, so a manager knows when delegating to it makes sense. The Email Manager sets one; the Sales Manager reads it when deciding to hand off.

Agents-as-tools vs handoffs — the key distinction

This is the idea to take away from the day. Both let one agent collaborate with another. The difference is what happens to control: with a tool, control comes back (request, response, carry on); with a handoff, control passes across (you delegate the rest of the job and step out).

// Week 2 Day 2 - tools, agents-as-tools and a handoff (TypeScript port of 2_openai/2_lab2.py)
// Three ideas, in order:
//   1. a function tool made with tool({ name, description, parameters: z.object(), execute })
//   2. agents wrapped as tools with agent.asTool(...), driven by a Sales Manager
//   3. a handoff: the manager passes the winning email to an Email Manager that formats and sends it
import { Agent, run, tool, withTrace } from "@openai/agents";
import { z } from "zod";
import { MODEL, sendEmail } from "./setup.js";

// Three sales agents with different styles.
const instructions1 =
  "You are a sales agent working for ComplAI, a company that provides a SaaS tool for ensuring SOC2 " +
  "compliance and preparing for audits, powered by AI. You write professional, serious cold emails.";
const instructions2 =
  "You are a humorous, engaging sales agent working for ComplAI, a company that provides a SaaS tool " +
  "for ensuring SOC2 compliance and preparing for audits, powered by AI. You write witty, engaging cold " +
  "emails that are likely to get a response.";
const instructions3 =
  "You are a busy sales agent working for ComplAI, a company that provides a SaaS tool for ensuring SOC2 " +
  "compliance and preparing for audits, powered by AI. You write concise, to the point cold emails.";

const salesAgent1 = new Agent({ name: "Professional Sales Agent", instructions: instructions1, model: MODEL });
const salesAgent2 = new Agent({ name: "Engaging Sales Agent", instructions: instructions2, model: MODEL });
const salesAgent3 = new Agent({ name: "Busy Sales Agent", instructions: instructions3, model: MODEL });

// ---------- 1. A function tool ----------
// Python wraps a function with @function_tool and reads its docstring + type hints.
// TypeScript has no runtime types, so tool() takes a zod schema that describes the parameters.
const sendEmailTool = tool({
  name: "send_email",
  description: "Send out an email with the given body to all sales prospects",
  parameters: z.object({ body: z.string() }),
  execute: async ({ body }) => sendEmail("Sales email", body),
});

// ---------- 2. Agents as tools ----------
// Calling the tool runs the agent and returns its final output as the tool result.
const description = "Write a cold sales email";
const tool1 = salesAgent1.asTool({ toolName: "sales_agent1", toolDescription: description });
const tool2 = salesAgent2.asTool({ toolName: "sales_agent2", toolDescription: description });
const tool3 = salesAgent3.asTool({ toolName: "sales_agent3", toolDescription: description });

// An Email Manager that formats and sends email. It owns two agent-tools and one function tool,
// and advertises a handoffDescription so other agents know when to hand off to it.
const subjectWriter = new Agent({
  name: "Email subject writer",
  instructions:
    "You can write a subject for a cold sales email. You are given a message and you need to write a " +
    "subject for an email that is likely to get a response.",
  model: MODEL,
});
const subjectTool = subjectWriter.asTool({
  toolName: "subject_writer",
  toolDescription: "Write a subject for a cold sales email",
});

const htmlConverter = new Agent({
  name: "HTML email body converter",
  instructions:
    "You can convert a text email body to an HTML email body. You are given a text email body which might " +
    "have some markdown and you need to convert it to an HTML email body with simple, clear, compelling layout.",
  model: MODEL,
});
const htmlTool = htmlConverter.asTool({
  toolName: "html_converter",
  toolDescription: "Convert a text email body to an HTML email body",
});

const sendHtmlEmail = tool({
  name: "send_html_email",
  description: "Send out an email with the given subject and HTML body to all sales prospects",
  parameters: z.object({ subject: z.string(), html_body: z.string() }),
  execute: async ({ subject, html_body }) => sendEmail(subject, html_body, "text/html"),
});

const emailerAgent = new Agent({
  name: "Email Manager",
  instructions:
    "You are an email formatter and sender. You receive the body of an email to be sent. You first use the " +
    "subject_writer tool to write a subject for the email, then use the html_converter tool to convert the " +
    "body to HTML. Finally, you use the send_html_email tool to send the email with the subject and HTML body.",
  tools: [subjectTool, htmlTool, sendHtmlEmail],
  model: MODEL,
  handoffDescription: "Convert an email to HTML and send it",
});

// ---------- 3. The Sales Manager: tools + a handoff ----------
// It uses the three sales_agent tools to draft, picks the best, then hands off to the Email Manager.
const salesManagerInstructions = `You are a Sales Manager at ComplAI. Your goal is to find the single best cold sales email using the sales_agent tools.

Follow these steps carefully:
1. Generate Drafts: Use all three sales_agent tools to generate three different email drafts. Do not proceed until all three drafts are ready.
2. Evaluate and Select: Review the drafts and choose the single best email using your judgment of which one is most effective.
3. Handoff for Sending: Pass ONLY the winning email draft to the 'Email Manager' agent. The Email Manager will take care of formatting and sending.

Crucial Rules:
- You must use the sales agent tools to generate the drafts - do not write them yourself.
- You must hand off exactly ONE email to the Email Manager - never more than one.`;

const salesManager = new Agent({
  name: "Sales Manager",
  instructions: salesManagerInstructions,
  tools: [tool1, tool2, tool3],
  handoffs: [emailerAgent],
  model: MODEL,
});

// A standalone demo of the plain function tool (not used by the manager, but shown here).
void sendEmailTool;

await withTrace("Automated SDR", async () => {
  const result = await run(salesManager, "Send out a cold sales email addressed to Dear CEO from Alice");
  console.log("Last agent:", result.lastAgent?.name);
  console.log("Final output:", result.finalOutput);
});

});		Layer 2 in TypeScript. tool({...}) takes the name and description you would otherwise read from a docstring, a Zod parameters schema in place of type hints, and an execute function that runs when the tool is called. This is the manual equivalent of @function_tool.

Why TypeScript needs Zod. Python reads a tool's parameters from type hints at runtime, but TypeScript types are erased before the code runs. Zod schemas (z.object({ ... })) give the SDK the same information at runtime, which is why every tool({...}) here carries a parameters schema.

Watching it run in the trace

What you should see. The run prints one short sales email (the concise "Busy" style often wins), beginning "Dear CEO" and signed "Alice" as asked. If your SendGrid keys and verified sender are set, an email arrives in your inbox — check Spam if not. In https://platform.openai.com/traces the "Automated SDR" trace shows the three sales-agent tool calls, the handoff, and then the Email Manager calling its subject, HTML and send tools. The instructor's run used nine tools in about a minute.
Common mistakes.
  • No email arrives. Check Spam first. Then check SENDGRID_API_KEY and that your verified sender address is set in the SendGrid dashboard — SendGrid only sends from a verified address.
  • SSL certificate errors. On some machines SendGrid raises SSL: CERTIFICATE_VERIFY_FAILED. The lab's fix is to upgrade certifi and point SSL_CERT_FILE at it.
  • Addresses still set to the instructor's. Change both the from (your verified sender) and the to (your own inbox) before running, so you are not emailing someone else.
  • Expecting control to return after a handoff. It does not. If you need the first agent to keep going afterwards, use an agent-as-tool, not a handoff.
  • Small local models skip tools. Tiny models sometimes describe calling a tool instead of calling it. On a capable cloud model the manager reliably uses its tools and the handoff.
Recap
  • We built an automated SDR in three layers: a parallel workflow, an agent with a tool, and agents collaborating.
  • asyncio.gather runs several agents at once and returns their outputs as an ordered list.
  • @function_tool (Python) and tool({...}) with a Zod schema (TypeScript) turn a function into a tool — no hand-written JSON.
  • agent.as_tool(...) wraps a whole agent as a tool; a Sales Manager uses three such tools to draft and pick.
  • handoffs=[...] lets an agent delegate to another, advertised by its handoff_description.
  • The key distinction: with a tool, control returns to the caller; with a handoff, control passes across and does not come back.
  • Giving the manager tools and a handoff is the line that turns a fixed workflow into an autonomous agent.
Honesty note. The agents call OpenAI's paid API, and SendGrid is a separate hosted service; neither was run live for this guide.
