Week 1 · Day 2 — Workflow Design Patterns

The difference between a workflow and an agent, and the five everyday patterns (chaining, routing, parallelisation, orchestrator-workers, evaluator-optimiser) for building reliable LLM systems.

Companion to Ed Donner's course · uv setup · Python (+ TypeScript/React where it fits) · code from the course repo

Day two is the one rare theory day in the whole six-week course. There is no lab to run and no code to type. Instead, Ed Donner steps back and answers two questions that everything else on the course builds on: what do we actually mean by an agent, and what are the common shapes that agent-style software tends to take? By the end you will be able to tell the difference between a workflow (where you, the developer, wire up a fixed sequence of steps) and an agent (where the model itself decides what happens next), and you will know the five everyday design patterns from Anthropic's post Building Effective Agents. Take this day slowly; the ideas here reappear in every later week.

New to this? What "agent" and "agentic AI" even mean

The word agent has been hyped so much that people use it to mean many different things. Ed quotes a crisp definition from Hugging Face's smolagents project: "AI agents are programs where LLM outputs control the workflow." In plain words, one output from the model gets to decide what happens next and in what order.

More loosely, people call something agentic AI when it shows any of five hallmarks: it makes several model calls; the model can use tools; there is an environment where several models pass information to each other; there is a planner that coordinates the work; or, the one most people point to, the system has some autonomy — it is allowed to choose how a task gets done.

New to this? What a "design pattern" is

A design pattern is just a reusable shape for solving a common problem — a recipe that has worked many times, named so people can talk about it. The five patterns on this page are not libraries or code; they are arrangements of model calls and plain code that you can recognise and reuse. Anthropic named and drew them so the whole industry could share a vocabulary.

New to this? What the "autonomy spectrum" means

Autonomy here just means how much freedom the model has to decide what happens next. At one end, plain code runs fixed steps and the model has none. In the middle, a workflow fixes the overall path but may let the model make small choices inside it. At the other end, an agent lets the model choose its own plan. Rather than two tidy boxes, picture a slider: the further right you go, the more the model is in charge — more powerful, but harder to predict.

Agentic systems: workflows and agents

Ed leans on Anthropic's Building Effective Agents because it is so clearly written. Anthropic uses agentic system as an umbrella term and splits it into two kinds. Workflows are systems where models and tools are orchestrated through predefined paths — you decide the steps in advance. Agents are systems where models dynamically direct their own processes and tools, keeping control over how the task gets done. The honest takeaway is that the line between them is a little blurred: many things people call "agents" are really workflows with a dash of autonomy. But the split is still a useful way to think.

The five workflow design patterns

Anthropic identifies five workflow patterns you meet again and again when building agentic systems. In the diagrams a shaded box is a call to a large language model, and an outlined box is ordinary code that you wrote (it is optional). Here they are at a glance.

PatternWhat it isWhen to use it
Prompt chaining A fixed line of model calls: the output of one call (optionally checked by your code) feeds the next. Each call handles one well-defined subtask. When a job splits cleanly into ordered steps and you want to frame each prompt precisely and keep the whole thing on guardrails.
Routing An input arrives and one model classifies it, then sends it to the specialist model best suited to handle it. When you have distinct categories of request and separate, specialised handlers — separation of concerns.
Parallelisation Your code splits a task into pieces, runs several model calls at the same time, then your code stitches the answers back together. When subtasks are independent and can run concurrently, or when you run the same task several times and combine the results (for example, take an average).
Orchestrator-workers Like parallelisation, but a model does the splitting and the combining instead of fixed code, so it can decide how to divide the work. When a complex task cannot be carved up in advance and you want the model to choose how many workers to use and what each one does.
Evaluator-optimiser One model generates a solution; a second model checks it and either accepts it or sends it back with a reason, forming a feedback loop. When quality, accuracy and robustness matter and you want a second pass to catch and fix weak answers before they reach the output.

1. Prompt chaining

The simplest pattern. Prompt chaining runs a series of model calls one after another, decomposing the job into a fixed set of subtasks. Between calls you can add a little code to check or shape the result before passing it on. Ed points out this is almost exactly what day one did: first ask the model to pick a business sector, then given that sector ask for a pain point, then ask for a solution. Because each prompt is framed tightly, every step does its narrow job well, and the whole process stays on rails.

2. Routing

In routing, an input comes in and one model acts as a classifier: it decides which of several specialist models is best equipped to handle this particular request, then hands it over. Think of specialists that are each good at a different kind of task; the router's whole job is to pick the right expert. There is real decision-making here, but it still follows a fixed overall shape.

3. Parallelisation

At first glance parallelisation looks like routing, but the orchestration here is done by code, not a model. Your code (say, some Python) takes a task, breaks it into pieces, and fires several model calls at the same time. More code then collects the answers and stitches them together. The pieces do not have to be different: you could send the same task three times and have the aggregator take an average. Most often, though, it is several independent subtasks running concurrently to save time.

4. Orchestrator-workers

This looks almost identical to parallelisation, and that is the point of the contrast. The one subtle change: the splitting and the combining are now done by a model, not fixed code. In orchestrator-workers, an orchestrator model breaks a complex task into smaller steps, worker models carry out each step, and a model synthesises the results into the final answer. Because the orchestrator decides how to divide the work — and even how many workers to use — this is far more dynamic, and (as Ed notes) it is a bit artificial to call it a pure workflow at all.

5. Evaluator-optimiser

This is the one Ed says he uses most; he often just calls them validation agents. In evaluator-optimiser, a generator model produces a solution and a second model plays evaluator, armed with extra context to check the work rather than create it. If it accepts, the answer goes to the output. If it rejects, it gives a reason, and that reason goes back to the generator, which tries again. That feedback loop is a powerful way to raise accuracy and build more confidence in the final answer — never a full guarantee with models, but a higher one.

Agents: no fixed path

With agents the process is open-ended. There is no set series of steps; instead a human makes a request to a model, the model takes actions on an environment (the outside world it can touch), gets information back, and repeats — choosing for itself when to stop. There are no sub-patterns here because the agent pattern is itself a kind of meta-design: the model gets to choose its own plan for solving the problem. That flexibility lets agents take on much bigger problems, but it is less predictable.

That power comes with real drawbacks. You do not know in advance what order the tasks will run in, or even which tasks will happen; you cannot be sure of the output quality; you do not know how long it will take; and the cost is unpredictable, since more model calls mean a bigger bill. Ed flags two mitigations the course returns to again and again: monitoring (visibility into what the models are doing, such as OpenAI's traces and LangSmith) and guardrails (software protections that keep models inside the boundaries you set — the OpenAI Agents SDK describes them as making models "behave safely, consistently and within the boundaries that you wish").

A spectrum of autonomy

It helps to see all of this as a spectrum rather than two separate boxes. On the left, plain code with no model in charge. In the middle, workflows: the path is predefined, though a model may still get some discretion inside it. On the right, agents: the model directs its own process. The patterns above sit at different points — prompt chaining gives a little autonomy, orchestrator-workers rather more — which is exactly why Ed says the line between workflow and agent is blurred.

How to pick a pattern

Start from the problem, not the pattern. If the job is a clean sequence of steps, reach for prompt chaining. If different kinds of request need different handlers, use routing. If independent pieces can run at once, use parallelisation. If the task is too complex to carve up in advance, let a model orchestrate with orchestrator-workers. If quality really matters, wrap your generator in an evaluator-optimiser loop. Only move all the way to a full agent when the problem genuinely needs the model to plot its own path.

Do not reach for a full agent too soon

Agents are exciting, but the open-ended loop brings uncertainty: unpredictable order of steps, unpredictable quality, unpredictable time, and unpredictable cost. A simple workflow — a fixed chain or an evaluator loop — is often more reliable, cheaper and easier to reason about. Use the least autonomy that solves the problem, and add monitoring and guardrails before you add freedom.

Recap
  • An agentic system splits into two kinds: workflows (you wire a predefined path) and agents (the model directs its own process). The line between them is blurred.
  • Hugging Face's crisp definition: agents are programs where the model's outputs control the workflow; the common thread people point to is autonomy.
  • The five workflow patterns from Anthropic's Building Effective Agents: prompt chaining, routing, parallelisation, orchestrator-workers, and evaluator-optimiser.
  • Parallelisation and orchestrator-workers share a shape; the difference is whether code or a model does the splitting and combining.
  • Agents are more powerful but less predictable in path, quality, time and cost; monitoring and guardrails are the key mitigations.
  • Think of a spectrum of autonomy, and use the least autonomy that gets the job done.
