Week 6 · Day 1 — MCP: the USB-C of Agentic AI

What the Model Context Protocol is: hosts, clients and servers. Use existing MCP servers from the OpenAI Agents SDK, including node-based ones, and wire several into one agent.

Companion to Ed Donner's course · uv setup · Python (+ TypeScript/React where it fits) · code from the course repo

Welcome to the finale week. For five weeks we have built agents with the OpenAI Agents SDK, CrewAI, LangGraph and AutoGen. This week is about something different: MCP, the Model Context Protocol from Anthropic. The instructor is careful to say it is not another framework. It is a protocol — an agreed way for the agent you build to plug in tools, data and prompts that other people wrote, without you having to understand how each one works inside.

Anthropic calls MCP "the USB-C of agentic AI". A USB-C port does not care what you plug into it; any device that speaks the standard just works. MCP is the same idea for agents: a tool someone published once can be used by thousands of agents, because they all speak the same protocol. Today we learn the three words you need — host, client, server — and then we point the OpenAI Agents SDK at real MCP servers and watch an agent browse the web and write a file on its own.

This is a lab, not a project yet. The code lives in 1_lab1.py (the exported notebook). The goal is to feel how MCP servers attach to an agent. The big capstone — a trading floor of autonomous agents — is built later this week on exactly these pieces.
Windows note from the instructor. MCP has a known problem running natively on Windows, and the reliable fix is to install WSL (Windows Subsystem for Linux) and run your editor against that Linux environment. Mac and Linux users do not need this. The setup is the same as the course's first-time environment setup, just repeated inside WSL.

What MCP is, and what it is not

The instructor spends real time clearing up confusion, because the name misleads people. So, plainly:

New to this? What MCP actually is (and is not)
  • It is not an agent framework. It does not build agents or replace the Agents SDK.
  • It is not the tools themselves. Anthropic wrote a few reference servers, but MCP is the standard, not a toolbox.
  • It is not a new way to make your own tools. Turning your own Python function into a tool is already easy — one function-tool decorator. MCP does not help with that and, for your own tools, is extra work you do not need.
  • It is a protocol for sharing and reusing tools. Someone builds a useful tool once, wraps it as an MCP server, and now any agent anywhere can plug it in and immediately know what it does and what arguments it takes. That frictionless connect-and-go is the whole point.

Mostly it is about tools. MCP can also share resources (read-only context, a bit like a RAG source) and prompt templates, but tools are where the excitement is.

Host, client, server — the three core words

There are exactly three concepts, and keeping them straight makes the rest of the week easy.

New to this? Host vs client vs server
  • The MCP host is the whole application that runs your agent. It could be Claude Desktop, or it could be the code you write with the OpenAI Agents SDK. The host is the thing in charge.
  • An MCP client is a small piece of software, like a plug-in, that lives inside the host. Each client connects one-to-one with exactly one server.
  • An MCP server is the separate program that actually provides the tools, context and prompts. It runs outside the host as its own process.

So: one host, holding several clients, each client wired to one server. When the Agents SDK uses three MCP servers, it quietly runs three clients for you.

The big misconception. The word "server" makes people picture a remote machine. In practice you download an MCP server from a public place and run it locally — just like a pip install or npm install. It runs on your box, outside the host. Remote (also called "hosted" or "managed") MCP servers exist but are rare.

Two transports: stdio and SSE

New to this? How a client talks to a server

There are two "transport" mechanisms in the spec. The common one is stdio (standard input/output): the client spawns a new process on your machine and talks to it over its input and output streams. This is what local servers use and what we use all week. The other is SSE (server-sent events) over HTTPS, which you must use when connecting to a remote hosted server. Local servers can use either, but almost always use stdio.

Meet the fetch server

The fetch MCP server fetches a web page. Behind the scenes it launches a headless browser (Chrome without a visible window, driven by Microsoft's Playwright) and returns the page as markdown. It is a reference server published by Anthropic. You run it with uvx, which installs and runs a Python package in one step.

The lab: using MCP servers from the Agents SDK

Here is the full first lab. It connects to three servers one at a time to list their tools, then builds an agent that uses two of them together.

In TypeScript: MCP is language-neutral — the protocol does not care what language anyone used. There is an official TypeScript MCP SDK, and the TS Agents SDK (@openai/agents) can attach MCP servers too. But this week stays in Python because the capstone (FastMCP servers, the Account class, the trading floor) is Python-only, so the day pages show single Python blocks. The small React side is a demo UI on the build page, not a port of this code.

# The imports

from dotenv import load_dotenv
from agents import Agent, Runner, trace
from agents.mcp import MCPServerStdio
import os

load_dotenv(override=True)

fetch_params = {"command": "uvx", "args": ["mcp-server-fetch"]}

async with MCPServerStdio(params=fetch_params, client_session_timeout_seconds=60) as server:
    fetch_tools = await server.list_tools()

fetch_tools


playwright_params = {"command": "npx","args": [ "@playwright/mcp@latest"]}

async with MCPServerStdio(params=playwright_params, client_session_timeout_seconds=60) as server:
    playwright_tools = await server.list_tools()

playwright_tools



sandbox_path = os.path.abspath(os.path.join(os.getcwd(), "sandbox"))
files_params = {"command": "npx", "args": ["-y", "@modelcontextprotocol/server-filesystem", sandbox_path]}

async with MCPServerStdio(params=files_params,client_session_timeout_seconds=60) as server:
    file_tools = await server.list_tools()

file_tools

instructions = """
You browse the internet to accomplish your instructions.
You are highly capable at browsing the internet independently to accomplish your task, 
including accepting all cookies and clicking 'not now' as
appropriate to get to the content you need. If one website isn't fruitful, try another. 
Be persistent until you have solved your assignment,
trying different options and sites as needed.
"""


async with MCPServerStdio(params=files_params, client_session_timeout_seconds=60) as mcp_server_files:
    async with MCPServerStdio(params=playwright_params, client_session_timeout_seconds=60) as mcp_server_browser:
        agent = Agent(
            name="investigator", 
            instructions=instructions, 
            model="gpt-4.1-mini",
            mcp_servers=[mcp_server_files, mcp_server_browser]
            )
        with trace("investigate"):
            result = await Runner.run(agent, "Find a great recipe for Banoffee Pie, then summarize it in markdown to banoffee.md")
            print(result.final_output)

Node-based servers and running several at once

Notice the two command styles. Python servers launch with uvx; JavaScript servers launch with npx and need a recent Node installed. Both end up as a local process the client talks to over stdio. Adding another capability to your agent is as easy as finding a server and dropping it into the mcp_servers list.

Marketplaces and security

The "aha" moment is an MCP marketplace — a website listing servers you can plug in. The instructor shows several (mcp.so, Glama, Smithery) with thousands of servers across categories like research, browser automation, memory and developer tools. Glama even rates servers for security, licensing and quality.

Security: treat a server like any code you install. Running an MCP server runs someone else's code on your machine — exactly as risky as a pip install or npm install. Do the usual due diligence: prefer publishers like Anthropic or Microsoft; check the GitHub stars, the activity and the reviews; read the marketplace's security grade. The extra worry is non-technical end users adding servers to tools like Claude Desktop without knowing how to vet them. Some servers can also be run inside a Docker container for more isolation.
Honesty note. The web-browsing and recipe run are shown as in the course and use real network calls. For this guide the pattern was verified locally: an agent built with the Agents SDK pointed at a local MCP server over stdio, with the model served by Ollama, so no paid key is needed to see an agent discover and call MCP tools. The marketplaces and the browser demo were not re-run for the guide.
Recap
  • MCP is a protocol for sharing tools, context and prompts — "the USB-C of agentic AI". It is not a framework and not the tools themselves.
  • Three words: the host runs your agent, a client lives inside it, and each client connects to one server that provides the tools.
  • Servers almost always run locally as a spawned process over stdio; remote (SSE) servers exist but are rare.
  • In the Agents SDK you describe a server with a params dictionary, open it with MCPServerStdio, call list_tools(), and attach it by passing mcp_servers=[...] to an Agent.
  • Python servers launch with uvx; JavaScript servers launch with npx and need Node.
  • Thousands of servers live in marketplaces — and each one is code you run on your box, so vet it like any dependency.
