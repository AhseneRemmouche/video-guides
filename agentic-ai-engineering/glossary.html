Glossary

Every technical term in this guide, explained for beginners.

Core concepts

Agent
A program built around a large language model that is given a goal and some freedom to decide its own next steps, instead of following a fixed script. In this course an agent usually runs a loop: it reads the situation, calls the model, maybe uses a tool, looks at the result, and repeats until the task is done.
Agentic AI
The style of building software where the language model is in the driver's seat: it plans, chooses actions, and uses tools to reach a goal, rather than just answering a single question. This whole course is about engineering such systems, starting from plain API calls in Week 1 up to a multi-agent trading floor.
Workflow
A system where the steps the language model takes are decided by you in code, following a fixed path. A workflow is more predictable than a full agent because you, not the model, control the order of the steps. Week 1 begins with a simple "plan then act" workflow before moving on to true agents.
LLM
Short for large language model. See large-language-model below. Throughout the course "the LLM" means the model you send messages to and get text (or tool calls) back from.
Large language model
A very large AI model, trained on huge amounts of text, that predicts and generates language. You give it a list of messages and it returns the next message. Examples used in this course include GPT-4o-mini, Claude, Gemini, DeepSeek and models run locally with Ollama.
OpenAI API
The web service from OpenAI that lets your code send messages to models like GPT-4o-mini and get responses back. You call it over the internet using an API key, usually through the official openai client library. In this course the same client style is reused for many other providers too.
API key
A secret string that identifies and bills your account when your code calls a provider's API. You keep it out of your code, usually in a .env file, and never share it publicly. Each provider (OpenAI, Anthropic, Google, DeepSeek, Groq) has its own key.
Endpoint
The web address (URL) your code sends requests to when it calls an API. For the OpenAI API this is OpenAI's own servers; for other providers you point the same client at a different endpoint using its base_url setting.
OpenAI-compatible
A provider whose API accepts the exact same request shape as OpenAI's. Because of this, you can talk to it using the same openai client and just change the base_url (and the API key). The course uses this trick to reach Gemini, DeepSeek, Groq and Ollama through one familiar client.
Client library
A ready-made package you install so your code can call an API without building the raw web requests by hand. In this course the Python openai package and the JavaScript openai package are the main client libraries.
Message
One turn in a conversation with the model, written as an object with a role (such as system, user or assistant) and content (the text). You send the model a list of these messages and it replies with a new assistant message.
System prompt
The first message, with role system, that sets the model's overall behaviour and personality before the conversation starts. In Week 1 the system prompt is what tells the chatbot to "act like you" and to use the tools correctly.
User prompt
A message with role user, holding the question or instruction coming from the person (or your code) that the model should respond to. The user prompt is the request; the system prompt is the standing rules.
Streaming
Receiving the model's answer piece by piece as it is generated, instead of waiting for the whole reply at once. Streaming makes a chat feel responsive because words appear as they are produced.
Structured output
Asking the model to reply in a strict, machine-readable shape (such as specific JSON fields) rather than free text, so your code can use the answer directly. In this course structured outputs are often defined with a Pydantic model so the fields are validated.
Pydantic
A popular Python library for describing the exact shape of data with classes, then checking that real data matches. The course uses Pydantic models to define structured outputs and tool arguments, so the model's replies come back as clean, validated objects.
Tool
A function your code offers to the model so the model can ask for it to be run, for example to look something up or record a detail. You describe each tool to the model with a JSON schema (its name, purpose and arguments); the model then chooses when to call it.
Function calling
The feature where the model, instead of answering in plain text, replies with a request to run one of the tools you gave it, along with the arguments to use. Your code runs the real function and sends the result back. This is how the Week 1 career agent records questions it cannot answer.
Tool call
A single request from the model to run one specific tool, naming the tool and the argument values it wants. Your code carries out the tool call, then feeds the result back into the conversation so the model can continue.
Resource
A piece of data or context you make available to a model or agent to work with, such as a document, a bio, or a PDF the chatbot reads. Later in the course (Week 6, MCP) "resources" also has a more specific meaning as data a server exposes to an agent.
Inference
The act of running the model to get an answer, that is, turning your input messages into generated output. Each API call you make is one inference; it costs time and, for paid providers, money.
Temperature
A setting between about 0 and 2 that controls how random the model's wording is. A low temperature makes answers steady and focused; a higher one makes them more varied and creative. It is one reason the same prompt can give different replies.
Token
The small chunk of text (roughly a few characters or part of a word) that models read and generate in. Usage and pricing are measured in tokens, and every model has a limit on how many tokens it can handle at once.
Markdown
A simple way to write formatted text using plain characters, for example # for a heading, * for a bullet, and **text** for bold. Models often reply in Markdown, and chat UIs like Gradio can render it as formatted text.

Patterns & providers

Workflow pattern
A reusable way of arranging the steps of an LLM system. This course teaches five of them, taken from Anthropic's article "Building Effective Agents": chaining, routing, parallelisation, orchestrator-workers and evaluator-optimiser. Day 2 of Week 1 explains all five.
Chaining (prompt chaining)
A workflow pattern where you break a task into ordered steps and feed the output of one model call into the next. Each call does one smaller job, which makes the whole task more reliable than trying to do everything in one prompt.
Routing
A workflow pattern where a first model call classifies the request and decides which specialised prompt, model or path should handle it next. It is like a receptionist sending each question to the right desk.
Parallelisation
A workflow pattern where you run several model calls at the same time, either to split a task into independent parts or to get multiple opinions, then combine the results. It saves time and can improve quality.
Orchestrator-workers
A workflow pattern where one "orchestrator" model breaks a task into subtasks and hands each to a "worker" model call, then gathers their outputs. Unlike simple parallelisation, the orchestrator decides the subtasks dynamically based on the input.
Evaluator-optimiser
A workflow pattern where one model produces an answer and a second model evaluates it and gives feedback, looping until the answer is good enough. In Week 1 a model acting as a judge to rank other models' answers is an example of this evaluate-then-improve idea.
Claude
Anthropic's family of large language models. In this course Claude is reached through Anthropic's API and, in Week 1, compared against other providers; the pinned repo uses the id claude-3-7-sonnet-latest.
Gemini
Google's family of large language models. The course calls Gemini through its OpenAI-compatible endpoint using the same openai client with a different base_url; the pinned repo uses gemini-2.0-flash.
DeepSeek
A provider of large language models with an OpenAI-compatible API. In Week 1 it is one of the several models asked the same question; the pinned repo uses the id deepseek-chat.
Groq
A service that runs open models very fast on special hardware and exposes an OpenAI-compatible API. The course reaches it with the same client and a different base_url; the pinned repo uses llama-3.3-70b-versatile.
Ollama
A tool that downloads and runs open language models on your own computer, offering an OpenAI-compatible endpoint so no API key or payment is needed. The course's Python projects are verified locally against Ollama; the pinned repo uses the model llama3.2.
Multi-LLM
Using more than one language model together, for example asking several providers the same question and having another model compare the answers. Week 1 Day 3 builds exactly this, all through one OpenAI-style client.

Tools & setup

uv
A fast, modern tool for managing Python versions, virtual environments and packages. This course sets everything up with uv: you run uv sync to install the project's dependencies and uv run to launch scripts and notebooks. It replaces the older Anaconda/conda approach.
Python
The main programming language of the course. It is widely used for AI work and reads almost like plain English, which makes it friendly for beginners. The labs are written in Python first, with TypeScript versions alongside in Week 1.
Jupyter
A system for running Python in interactive documents called notebooks, where you can run small pieces of code and see results immediately. The course runs the labs in Jupyter, either inside Cursor/VS Code or by launching uv run jupyter lab.
Notebook
A document made of cells that can hold either code or notes, where each code cell can be run on its own and its output appears right below it. Notebooks (files ending in .ipynb) are ideal for learning because you experiment step by step.
Kernel
The background process that actually runs your notebook's code. You must pick the right kernel, the project's .venv environment created by uv, so the notebook uses the packages the course installed.
Environment variable
A named value stored outside your code, in the operating system or in a .env file, that your program reads at run time. The course keeps secrets like API keys in environment variables so they stay out of the source code.
dotenv / .env file
A plain text file named .env that holds your secrets as NAME=value lines, loaded into your program by a "dotenv" helper. The course stores keys such as OPENAI_API_KEY and ANTHROPIC_API_KEY here and keeps the file out of version control.
Terminal
The text window where you type commands to your computer, such as git clone or uv run. On Windows this is PowerShell or a similar shell; the course runs its setup and scripts from the terminal.
Gradio
A Python library that turns your code into a simple web interface with just a few lines, so you can share a model or chatbot in the browser. Week 1 Day 4 uses Gradio to give the "acts like you" chatbot a chat window.
Hugging Face Spaces
A free hosting service from Hugging Face where you can publish a small app (such as a Gradio chatbot) so other people can use it from a web link. The course mentions it as a way to deploy your Week 1 app.
Push notification
A short alert sent to your phone or device. In Week 1 the career agent uses the Pushover service to send a push notification whenever someone it is chatting with leaves their contact details or asks a question it cannot answer.
JSON
A simple, widely used text format for data, made of names and values inside braces, for example {"name": "Ed", "answered": true}. APIs send and receive JSON, and the course uses it for tool arguments and structured outputs.
JSON schema
A description, itself written in JSON, of what a piece of JSON data should look like: which fields exist, their types and which are required. The course describes each tool to the model with a JSON schema so the model knows how to call it correctly.

TypeScript & React

TypeScript
A version of JavaScript that adds type labels so mistakes are caught before the code runs. Week 1 provides a TypeScript version of every lab beside the Python one, using the JavaScript openai SDK.
Node.js
The runtime that lets JavaScript and TypeScript run outside a browser, for example on your own machine or a server. The course's TypeScript labs and the Hono API run on Node.
npm
Node's package manager: the command-line tool that installs JavaScript/TypeScript libraries and runs project scripts. It is the TypeScript side's rough equivalent of uv for Python.
React
A popular JavaScript/TypeScript library for building user interfaces out of reusable pieces called components. In Week 1 a small React app provides the career-chat web UI on the TypeScript side.
JSX
The syntax used in React that lets you write HTML-like tags directly inside JavaScript code to describe what the UI should look like. When it appears in a TypeScript file it is called TSX.
Component
A self-contained, reusable building block of a React interface, such as a chat box or a button, defined as a function that returns some UI. You combine components to build a whole page.
Vite
A fast build-and-development tool for modern web apps. The course's TypeScript React projects are built and checked with Vite; "vite build" is used to verify the front end compiles.
Hono
A small, fast web framework for building APIs in JavaScript/TypeScript on Node. In Week 1 the TypeScript career-chat app is served by a Hono API that the React front end talks to.
TSX
A TypeScript file that also contains JSX, the HTML-like UI syntax; the file extension is .tsx. React components written in TypeScript live in TSX files.
REST API
A common style of web API where the front end makes HTTP requests (such as sending a chat message) to addresses on a server and gets data back, usually as JSON. The Week 1 React app reaches its Hono back end through a REST API.

Week 1 extras

Agent loop
The repeating cycle at the heart of an agent: call the model, see whether it wants to use a tool, run that tool and feed the result back, then call the model again, continuing until the model gives a final answer. Week 1's career agent runs this loop so it can use its tools before replying.
Digital twin
The course's name for a chatbot built to represent a real person, answering as if it were them based on their bio and background. Week 1 builds a "digital twin" career agent that talks to visitors on your behalf.
Gradio ChatInterface
A ready-made Gradio component, gr.ChatInterface, that gives you a full chat window (message history, input box and send button) by wrapping a single function that takes a message and returns a reply. Week 1 uses it to put a chat UI around the chatbot with almost no extra code.
Non-determinism
The fact that a language model can give different answers to the exact same prompt on different runs. This is normal and expected; settings like temperature affect how much it varies, and it is why agent behaviour is tested, not assumed to be fixed.
Handoff
Passing control of a task from one agent to another that is better suited to the next part of the job. The idea is introduced in Week 1 and becomes central later (especially the OpenAI Agents SDK in Week 2), where one agent can hand off a conversation to a specialist agent.

Week 2 · the OpenAI Agents SDK

OpenAI Agents SDK
A small Python framework (installed as the openai-agents package and imported as agents) that handles the agent loop for you. Instead of writing the call-the-model, run-a-tool, call-again cycle by hand, you describe an Agent with a name, instructions and model, and the SDK runs it, manages tools and handoffs, and records traces. Week 2 is built almost entirely on this SDK.
Runner
The part of the Agents SDK that actually runs an agent. You call Runner.run(agent, input) to execute the agent loop and get a result back, then read result.final_output for the agent's answer; Runner.run_streamed(...) streams the reply as it is produced. Runner.run is asynchronous, so you use it with await.
Trace
A record of everything an agent run did: each model call, tool call and handoff, grouped together so you can inspect it. In the SDK you wrap a run in with trace("some name"): and then view the whole run on OpenAI's traces dashboard, which makes debugging multi-agent systems much easier. Traces are one of the main things the SDK adds over raw API calls.
asyncio
Python's built-in library for writing asynchronous code, where the program can start a slow task (like a network call) and do other work while it waits, instead of blocking. Week 2 uses it to run several agents at the same time, for example asyncio.gather(...) to launch three sales agents in parallel and wait for all of them. The Agents SDK is built on asyncio, which is why its runs are awaited.
async / await
Two Python keywords for asynchronous code. async def marks a function that can pause partway through, and await is how you call such a function and wait for its result without blocking everything else. Because Runner.run is asynchronous, the Week 2 labs write await Runner.run(...).
@function_tool
A decorator from the Agents SDK that turns an ordinary Python function into a tool the agent can call. You write a normal function with a docstring and type hints, add @function_tool above it, and the SDK automatically builds the JSON schema and handles the tool call. In Week 2 it is used to wrap the email-sending function.
Agent as a tool
A way to let one agent use another agent as if it were a single tool, by calling agent.as_tool(tool_name=..., tool_description=...). The calling agent stays in control and simply gets the inner agent's output back, unlike a handoff where control is passed away. Week 2's sales manager uses three sales agents as tools to generate draft emails.
output_type
A setting on an Agent that makes it return structured output instead of plain text. You pass a Pydantic model as output_type=, and the SDK makes the agent fill in that model's fields, so result.final_output comes back as a validated object. Week 2's planner agent uses output_type=WebSearchPlan to return a tidy list of searches.
Guardrail
A check that runs alongside an agent to catch unwanted input or output, added with the @input_guardrail or @output_guardrail decorators. A guardrail is itself usually a small agent that inspects the message and returns a GuardrailFunctionOutput. In Week 2 an input guardrail checks whether the user's request contains someone's personal name before the sales manager is allowed to run.
Tripwire
The signal a guardrail raises when its check fails. The guardrail returns GuardrailFunctionOutput(..., tripwire_triggered=True), and when that happens the SDK stops the run and raises an exception instead of letting the agent continue. It is the mechanism that actually blocks a request a guardrail objects to.
WebSearchTool
A ready-made, hosted tool provided by the Agents SDK that lets an agent search the web, added by putting WebSearchTool() in an agent's tools list. It is run on OpenAI's side rather than being a function you write, and it is a paid, hosted feature. Week 2's Deep Research project uses it so the search agent can look things up online.
SendGrid
An email-delivery service, used in Week 2 to actually send emails from an agent. The labs call it through the sendgrid Python package with a SENDGRID_API_KEY, wrapped in a @function_tool so an agent can send a message. It is a paid, third-party service with its own account and verified sender.
@openai/agents
The official TypeScript/JavaScript port of the OpenAI Agents SDK, installed as the @openai/agents npm package. It mirrors the Python SDK's ideas (agents, a runner, tools, handoffs, guardrails and tracing) so the Week 2 labs can be written in TypeScript as well as Python. The guide's TypeScript track uses it for the bilingual versions of every Week 2 lab.

Week 3 · CrewAI

CrewAI
A Python framework for building teams of agents that work together on a job. You describe each agent and each task in simple configuration files, then group them into a "crew" that runs them. CrewAI is Python-only (there is no JavaScript port), so Week 3's labs are shown as single Python and YAML blocks rather than side-by-side TypeScript.
Crew
A team of agents plus the tasks they carry out, created in CrewAI as a Crew(agents=..., tasks=..., process=...) object. You start it running by calling kickoff(), and the crew works through its tasks according to its chosen process. Week 3's stock-picker crew has a finder, a researcher and a picker agent working as one crew.
Role, goal, backstory
The three short pieces of text that define a CrewAI agent: its role (the job title it plays), its goal (what it is trying to achieve) and its backstory (background that shapes how it behaves). They are usually written in the agents.yaml file and act like a tailored system prompt for each agent.
Task (CrewAI)
One unit of work you give a CrewAI crew, described by a description of what to do and an expected_output saying what the result should look like. Each task is normally assigned to an agent, and tasks are listed in the tasks.yaml file. The output of one task can be fed to a later task as context.
expected_output
The field on a CrewAI task that tells the agent, in plain words, what shape and content its answer should have, for example "a bullet-point list of three companies". It guides the model toward a useful, consistent result. It can be paired with output_pydantic to turn that result into a validated object.
Process.sequential
The simplest way a CrewAI crew can run its tasks: one after another, in the order you listed them, passing work forward. You set it with process=Process.sequential when creating the crew. Week 3's first (debate) crew uses this straightforward, predictable flow.
Process.hierarchical
A way for a CrewAI crew to run where a manager agent is put in charge: it decides which agent handles each task and in what order, rather than the tasks simply running top to bottom. You set it with process=Process.hierarchical and supply a manager_agent. The stock-picker crew uses this so a manager can delegate and coordinate.
Manager agent
In a hierarchical crew, the extra agent that coordinates the others: it plans the work, delegates tasks to the right agents and gathers their results. You pass it as manager_agent= and usually give it allow_delegation=True. It is not tied to a single task; its job is to run the team.
LiteLLM
A library that CrewAI uses under the hood to talk to many different model providers through one common interface. Because of it, you can name a model as provider/model (for example openai/gpt-4o-mini or ollama/llama3.2) and point different agents at different models. It is why a CrewAI agent can run against a local Ollama model with only a config change.
YAML
A plain-text format for writing configuration that is easy for people to read, using indentation and name: value lines instead of braces. CrewAI keeps its agent definitions in config/agents.yaml and its task definitions in config/tasks.yaml, so you can change behaviour without editing Python code.
Serper (SerperDevTool)
A paid web-search service that CrewAI can use through its ready-made SerperDevTool(), letting an agent look things up on the internet. It needs an API key and so is not run live in this guide. Week 3's financial-researcher and stock-picker crews give their research agents this tool.
output_pydantic
A setting on a CrewAI task that makes the agent return its answer as a validated Pydantic object instead of free text. You pass a model class, such as output_pydantic=TrendingCompanyList, and the task's result comes back with those exact fields filled in. Week 3 uses it so a research task returns a tidy list of companies your code can read directly.
Crew memory
CrewAI's optional ability to let a crew remember things, turned on with memory=True. It comes in kinds: short-term memory for the current run, long-term memory saved to a SQLite database across sessions, and entity memory that tracks key facts about people or companies. The stock-picker crew wires up all three so agents can build on what they learned before.
RAG storage
The vector-based store CrewAI uses for short-term and entity memory, created as RAGStorage(...). It turns remembered text into embeddings (with an embedding model such as text-embedding-3-small) so the crew can later retrieve the most relevant pieces. "RAG" stands for retrieval-augmented generation, the pattern of fetching relevant stored text to feed back to the model.
Code execution
A CrewAI feature that lets an agent actually write and run code, enabled with allow_code_execution=True. For safety it can run that code inside a Docker container using code_execution_mode="safe", so it is sandboxed away from your machine. Week 3's coder and engineering-team crews use it to produce and test real Python.

Week 4 · LangGraph

LangGraph
A framework that models an agent as a graph: a set of steps (nodes) wired together by connections (edges) that pass around a shared state. Instead of a single loop, you draw out the flow of the agent, which makes complex, looping or branching behaviour easier to reason about. Week 4 builds chatbots and the Sidekick app on LangGraph, and it has a real JavaScript port so the week is fully bilingual.
StateGraph
The builder object you create in LangGraph to assemble your graph, written as StateGraph(State). You add nodes and edges to it, then call compile() to turn it into a runnable graph you can invoke. It is the central piece every Week 4 lab starts from.
Node
One step in a LangGraph graph: a function that receives the current state and returns an update to it, for example a node that calls the model or one that runs tools. You register it with graph_builder.add_node("name", fn). Nodes are the "work" of the graph; edges decide which node runs next.
Edge
A connection in a LangGraph graph that says, after this node, go to that node. You add one with add_edge("from", "to"), and the special markers START and END mark where the graph begins and finishes. Plain edges always lead to the same next node.
Conditional edge
An edge whose destination is decided at run time by a small routing function, added with add_conditional_edges(...). It is how a LangGraph graph branches: for example, go to the tools node if the model asked for a tool, otherwise go to the evaluator or to END. The Sidekick uses conditional edges to loop between its worker, tools and evaluator.
Reducer
A rule that tells LangGraph how to combine an update with the value already in the state, rather than overwriting it. You attach one with Annotated[list, add_messages], which means "add these messages to the list" instead of replacing it. Reducers are what let the message history grow correctly as the graph runs.
add_messages
The built-in LangGraph reducer for a list of chat messages: when a node returns new messages, add_messages appends them to the existing conversation instead of discarding it. It is used in the state definition as messages: Annotated[list, add_messages]. This is the usual way a LangGraph chatbot keeps its history.
ToolNode
A ready-made LangGraph node that runs whatever tools the model asked for and feeds the results back into the state, created as ToolNode(tools=...). It saves you from writing the run-the-tool step by hand. It is usually paired with tools_condition, a helper that routes to the tool node only when the last model message contains a tool call.
Checkpointing
LangGraph's way of saving the state of a graph after each step so a conversation can continue later or survive a restart. You give the compiled graph a "checkpointer" (compile(checkpointer=...)), and together with a thread id it lets the graph remember earlier turns. It is how a LangGraph chatbot gains memory between messages.
MemorySaver
The simplest LangGraph checkpointer, which keeps saved state in memory for the life of the program, created as MemorySaver() and passed to compile(checkpointer=memory). It is perfect for labs and demos; for storage that outlasts a restart you would swap in a SQLite-backed checkpointer instead. Week 4's chatbot and Sidekick both use it.
thread_id
A label that tells a checkpointed LangGraph graph which conversation it is continuing, passed in the config as {"configurable": {"thread_id": "..."}}. Messages sharing a thread id build on the same saved history; a new id starts a fresh conversation. The Sidekick gives each user session its own thread id so people's chats stay separate.
LangSmith
A tracing and debugging service from the makers of LangGraph that records each run of your graph so you can inspect every model call and tool call. You switch it on with environment variables (such as LANGSMITH_API_KEY) and then view runs on its dashboard. It plays the same role for LangGraph that the traces dashboard does for the OpenAI Agents SDK.
Playwright
A browser-automation tool that can open web pages, click and read their contents under program control. In Week 4 it gives the Sidekick real browsing tools through LangChain's Playwright toolkit, so the agent can navigate to a site and extract its text. It runs an actual browser, optionally in visible ("headful") mode.
Worker / evaluator loop
The pattern behind the Sidekick: one agent (the worker) attempts the task, and a second agent (the evaluator) judges whether the result meets the stated success criteria and gives feedback. If the criteria are not met and no user input is needed, the graph loops back so the worker tries again. It is the evaluator-optimiser idea built as a LangGraph with conditional edges.
LangGraph.js
The official JavaScript/TypeScript port of LangGraph, installed as the @langchain/langgraph npm package. It mirrors the Python version's ideas (state, nodes, edges, conditional edges, checkpointing) so Week 4's labs and the Sidekick can be written in TypeScript too. It is why Week 4 is presented as fully bilingual.

Week 5 · AutoGen

AutoGen
A framework, originally from Microsoft, for building agents that solve problems by talking to each other. Week 5 uses its Python packages in two layers: a high-level conversational layer (AgentChat) and a lower-level message-passing layer (AutoGen Core). It is Python-primary here, so the labs are shown as single Python blocks with a short note about TypeScript.
AgentChat
AutoGen's high-level, beginner-friendly layer (the autogen_agentchat package) for quickly creating conversational agents and having them chat. You make an assistant agent, give it a model and tools, and call it with a message. Week 5 starts here before dropping down to the lower-level Core layer.
AutoGen Core
AutoGen's lower-level layer (the autogen_core package) that handles agents as independent units which send and receive messages through a runtime. It gives you fine control over how messages are routed and who handles what, at the cost of more setup. Week 5's rock-paper-scissors example is built on Core.
AssistantAgent
The main AgentChat agent class, created as AssistantAgent(name, model_client, system_message, tools). It wraps a model so you can send it messages with on_messages(...) and get a reply, optionally using tools you provide. In Week 5's Core examples it is often used as the "brain" that a routed agent delegates to.
Model client
The object in AutoGen that connects an agent to a particular language model, such as OpenAIChatCompletionClient(model="gpt-4o-mini") or OllamaChatCompletionClient(model="llama3.2"). You hand it to an agent so the agent knows which model to call. Swapping the client is how Week 5 runs the same agent against OpenAI or a local Ollama model.
TextMessage
The plain-text message type AgentChat agents exchange, created as TextMessage(content, source) where source says who sent it. You pass a list of these to an agent's on_messages(...) method. It is AutoGen's basic unit of conversation.
MultiModalMessage
An AgentChat message that can carry more than just text, for example an image alongside words, using MultiModalMessage together with autogen_core.Image. It lets an agent reason about pictures as well as text. Week 5 Day 2 uses it to show AutoGen handling multimodal input.
RoutedAgent
The base class in AutoGen Core you subclass to build your own agent, as in class MyAgent(RoutedAgent). It automatically delivers each incoming message to the right handler method based on the message's type. It is the standard starting point for a Core agent.
@message_handler
A decorator in AutoGen Core that marks a method on a routed agent as the one to run for a given message type. When a message of that type arrives, Core calls the decorated method with the message and a context. It is how you define what an agent actually does when it receives something.
Agent runtime
The engine in AutoGen Core that holds your agents, delivers messages between them and manages their lifecycle. The simplest one is SingleThreadedAgentRuntime(), which you start, register agents with, send messages through, then stop and close. Agents never call each other directly; they go through the runtime.
gRPC
A fast, standard way for programs in different processes or on different machines to call each other over a network. AutoGen uses it to let agents run separately and still exchange messages through a shared host. In Week 5 it is the plumbing behind the distributed runtime and the "world" capstone.
Distributed agents
Agents that run in separate processes (or on separate machines) rather than all inside one program, coordinated by AutoGen's GrpcWorkerAgentRuntime connecting to a GrpcWorkerAgentRuntimeHost over gRPC. This lets a system scale out and keep agents independent. Week 5 Day 4 shows agents talking across processes this way.
CancellationToken
A small object AutoGen passes along when an agent is working so the operation can be cancelled cleanly if needed. You see it as the second argument to on_messages([...], ctx.cancellation_token), usually taken from the message context. It is AutoGen's standard way to signal "stop this work".

Week 6 · MCP

MCP (Model Context Protocol)
An open standard for connecting agents to tools and data through a common interface, described in the course as "the USB-C of agentic AI". Instead of writing custom glue for every integration, an agent speaks MCP to any server that offers tools or resources. Week 6 both uses existing MCP servers and builds new ones in Python.
MCP host
The application the user interacts with that wants to use MCP-provided tools, such as an agent app or an AI chat client. The host runs one or more MCP clients to reach servers. In Week 6 the host is the Agents SDK program that launches and talks to MCP servers.
MCP client
The part inside a host that opens and manages a connection to a single MCP server, asking it for its tools and passing the agent's requests through. There is typically one client per server. The host uses its clients to gather tools from several servers at once.
MCP server
A program that exposes tools and resources over MCP for clients to use, for example a web-fetch server, a memory server or the course's own accounts server. A server can be a small Node command run with npx or your own Python program. Week 6's labs connect to ready-made servers and then build custom ones.
stdio transport
One way an MCP client and server talk: the server runs as a local subprocess and they exchange messages over its standard input and output streams. It suits servers running on the same machine, and is chosen with mcp.run(transport='stdio'). It contrasts with network-based transports used for remote servers.
FastMCP
The convenient Python helper for writing your own MCP server, created as FastMCP("name"). You decorate ordinary functions with @mcp.tool() and @mcp.resource(...) and it handles the MCP details for you. Week 6's accounts server is built with FastMCP in only a few lines.
MCP tool
A function an MCP server offers that an agent can call to do something, such as buy_shares or get_balance on the accounts server. In FastMCP you create one by putting @mcp.tool() above a function, and its docstring and type hints describe it to the agent. It is the MCP version of the tools seen earlier in the course.
MCP resource
A piece of read-only data an MCP server makes available at an address, rather than an action to run, declared with @mcp.resource("some://uri/{name}"). An agent reads a resource to get context, for example an account's current report or strategy. It is the "data" counterpart to an MCP tool's "action".
MCPServerStdio
The Agents SDK class used to launch and connect to an MCP server over the stdio transport, created with the command and arguments as its parameters. You pass the connected servers to an agent as mcp_servers=[...], and the agent can then use all their tools. Week 6 uses it to wire the fetch, memory, market and accounts servers into trader agents.
Trading floor
Week 6's capstone system: four autonomous Trader agents, each pairing a research agent with a trading agent and using MCP servers for accounts, market data and search. They manage their own portfolios and are run repeatedly by a scheduler. It brings together everything in the course into one running multi-agent application.
Polygon
A market-data provider the trading floor can call for stock prices and related data, reached through an MCP market server. It needs an API key and is paid, so it is not run live in this guide. It is one of the real-world data sources the trader agents rely on.
Brave Search
A web-search service used in Week 6, reached through an MCP server, that lets trader and research agents look things up online. Like Polygon, it is keyed and paid, so it is shown as in the course rather than run live. It is one of several MCP servers the trading floor connects to at once.
Scheduler
The part of the trading floor (trading_floor.py) that runs the trader agents over and over on a timer, for example every few minutes, so they keep researching and trading on their own. It is what turns a one-off agent run into a system that operates continuously. Settings in the .env file control how often it runs.
