Week 2 · Day 3 — Structured Outputs and Guardrails

Day 3 takes the Sales Development team we built on Day 2 and stretches it in three directions, each one a useful feature of the OpenAI Agents SDK. First, we drive the agents with models that are not from OpenAI — Google's Gemini, DeepSeek, and a large Llama served by Groq — without changing how an agent is written. The three new ideas at a glance

Using other models through the SDK

On Day 1 you passed a model to an agent as a plain string, like model="gpt-4o-mini". When the model is a string, the SDK assumes you mean OpenAI and calls OpenAI for you. To use a different provider you pass a small model object instead. Building that object takes two steps, and it leans on the same OpenAI-compatible trick from Week 1: most providers accept OpenAI-shaped requests, so one client library can reach them all by changing the endpoint address and the key.

  1. Create an AsyncOpenAI client pointed at the provider's base_url with that provider's API key.
  2. Wrap that client in an OpenAIChatCompletionsModel, giving it the model name (for example gemini-2.0-flash).
  3. Pass that model object to an Agent as model=.... Everything else about the agent is unchanged.
New to this? Why AsyncOpenAI and not plain OpenAI

The Agents SDK runs everything asynchronously so many calls can be in flight at once (see Day 1's primer on asyncio). To match that, it wants an async client: AsyncOpenAI is the same OpenAI client you met in Week 1, but its methods are awaited rather than run one at a time. You do not call it directly here; you hand it to the model object, and the SDK awaits it for you when an agent runs.

New to this? What OpenAIChatCompletionsModel is for

An Agent needs to know which model to call and how to reach it. For OpenAI's own models a name is enough. For anyone else, OpenAIChatCompletionsModel is a small adapter that bundles the model name together with the client that knows the right address and key. It uses the older "chat completions" style of request, which is exactly the shape Gemini, DeepSeek and Groq accept. That is why this one object is all you need to plug a third-party model into an agent.

Claude is missing on purpose. At the time of the course, Anthropic did not offer an OpenAI-compatible endpoint, so you cannot drop Claude in the same way. The instructor notes two workarounds he does not use here: a router service such as OpenRouter that exposes an OpenAI-compatible endpoint for Claude, or reaching Anthropic through MCP (covered in the final week). For this lab the three non-OpenAI models all have compatible endpoints, which is what keeps the code so short.

Structured outputs: an agent that returns an object

By default an agent replies with a string of text. Often you want something a program can rely on — named fields with known types. You get that by defining a Pydantic model (a class that describes the shape of the data) and setting it as the agent's output type. Tell the agent output_type=YourModel and its final output is an instance of that class, not free text.

New to this? How a model "returns an object"

It sounds magical, but underneath it is plain JSON. The SDK turns your Pydantic model into a JSON schema and tells the model "your answer must match this shape". The model replies with JSON, and the SDK loads that JSON back into an instance of your class. If a field is missing or the wrong type, loading fails loudly rather than handing you bad data. So the type label is doing real work, not just documentation.

Guardrails: checks at the edges

A guardrail is a test that runs automatically around your agents. The clever part of the SDK is that a guardrail can itself be an agent, so you can use an LLM to judge whether an input or output is acceptable — not just simple Python rules. You attach them in only two places: an input_guardrail runs on what goes into the first agent, and an output_guardrail runs on what comes out of the last one. You cannot sprinkle them in the middle of a workflow.

New to this? What a "tripwire" is

A guardrail function always returns a GuardrailFunctionOutput with two things: some output_info (data kept for the trace, useful for debugging) and a boolean called tripwire_triggered. Think of tripwire like a trip-wire on a path: set it to True and the SDK stops the whole run by raising an exception. Set it to False and work continues as normal. The guardrail's job is simply to decide which.

Why guardrails matter

In the lab the dangerous message is hard-coded, so you can see with your own eyes that it contains a name. The point is what happens in a real product: the prompt would come from your users, not from you. A guardrail is where you stop unwanted content — a customer's personal name, a phone number, other personal information — from flowing into automated emails. Because the check sits at the input, nothing downstream runs until it passes, so you never pay for or send a bad result.

    is_name_in_message: bool

async def guardrail_against_name(ctx, agent, message):

// Week 2 Day 3 - structured output + an input guardrail (TypeScript port of 2_openai/3_lab3.py)
// Python: a Pydantic BaseModel as output_type, and an @input_guardrail function.
// TypeScript: a zod schema as outputType, and an InputGuardrail object with an execute function.
import {
  Agent,
  InputGuardrailTripwireTriggered,
  run,
  tool,
  withTrace,
} from "@openai/agents";
import type { InputGuardrail } from "@openai/agents";
import { z } from "zod";
import { MODEL, sendEmail } from "./setup.js";

// A small sales/email setup reused from day 2, so the guardrail has something to protect.
const salesAgent = new Agent({
  name: "Sales Agent",
  instructions:
    "You are a sales agent working for ComplAI, a company that provides a SaaS tool for ensuring SOC2 " +
    "compliance and preparing for audits, powered by AI. You write concise, professional cold emails.",
  model: MODEL,
});
const salesTool = salesAgent.asTool({ toolName: "sales_agent", toolDescription: "Write a cold sales email" });

const sendHtmlEmail = tool({
  name: "send_html_email",
  description: "Send out an email with the given subject and HTML body to all sales prospects",
  parameters: z.object({ subject: z.string(), html_body: z.string() }),
  execute: async ({ subject, html_body }) => sendEmail(subject, html_body, "text/html"),
});

const emailerAgent = new Agent({
  name: "Email Manager",
  instructions:
    "You are an email formatter and sender. You receive the body of an email, write a subject, convert it to " +
    "clean HTML, and send it with the send_html_email tool.",
  tools: [sendHtmlEmail],
  model: MODEL,
  handoffDescription: "Convert an email to HTML and send it",
});

const salesManagerInstructions = `You are a Sales Manager at ComplAI. Use the sales_agent tool to draft a cold
sales email, then hand off exactly ONE email to the 'Email Manager' agent for formatting and sending.`;

// ---------- Structured output: a zod schema as outputType ----------
// The guardrail agent's final output is typed as NameCheckOutput instead of a free-form string.
const NameCheckOutput = z.object({
  is_name_in_message: z.boolean(),
  name: z.string(),
});

const guardrailAgent = new Agent({
  name: "Name check",
  instructions: "Check if the user is including someone's personal name in what they want you to do.",
  outputType: NameCheckOutput,
  model: MODEL,
});

// ---------- Input guardrail ----------
// Python: @input_guardrail async def guardrail_against_name(ctx, agent, message) -> GuardrailFunctionOutput
// TypeScript: an InputGuardrail with a name and an execute returning { outputInfo, tripwireTriggered }.
const guardrailAgainstName: InputGuardrail = {
  name: "guardrail_against_name",
  execute: async ({ input, context }) => {
    const text = typeof input === "string" ? input : JSON.stringify(input);
    const result = await run(guardrailAgent, text, { context: context?.context });
    const found = result.finalOutput;
    return {
      outputInfo: { found_name: found },
      tripwireTriggered: found?.is_name_in_message ?? false,
    };
  },
};

const carefulSalesManager = new Agent({
  name: "Sales Manager",
  instructions: salesManagerInstructions,
  tools: [salesTool],
  handoffs: [emailerAgent],
  model: MODEL,
  inputGuardrails: [guardrailAgainstName],
});

// A message containing a personal name trips the guardrail before any work is done.
await withTrace("Protected Automated SDR (name present)", async () => {
  try {
    await run(carefulSalesManager, "Send out a cold sales email addressed to Dear CEO from Alice");
    console.log("No tripwire (the guardrail did not spot a name)");
  } catch (e) {
    if (e instanceof InputGuardrailTripwireTriggered) {
      console.log("Guardrail tripwire triggered:", JSON.stringify(e.result.output.outputInfo));
    } else {
      throw e;
    }
  }
});

// A message with no personal name passes the guardrail and runs normally.
await withTrace("Protected Automated SDR (no name)", async () => {
  const result = await run(
    carefulSalesManager,
    "Send out a cold sales email addressed to Dear CEO from Head of Business Development",
  );
  console.log("Passed the guardrail. Last agent:", result.lastAgent?.name);
});

    const result = await run(guardrailAgent, text, { context: context?.context });
    return { outputInfo: { found_name: found }, tripwireTriggered: found?.is_name_in_message ?? false };
  },
};		The guardrail as a plain object with a name and an execute function. It runs the guardrail agent on the input and returns { outputInfo, tripwireTriggered } — the same two pieces as Python's GuardrailFunctionOutput. The ?? false falls back to "no trip" if the result is somehow empty, which TypeScript insists you handle.

How the guardrail decides

What you should see. The first protected run (message "from Alice") stops with an exception whose text mentions the input guardrail tripwire — that is success, not a bug. Open the trace and the "Name check" guardrail shows is_name_in_message true and name "Alice". The second run (no name) finishes normally and an email is produced. In the dashboard you can also see the three sales agents running in parallel, each on a different provider.
Common mistakes.
  • Passing a string where you meant a model object. model="gemini-2.0-flash" tells the SDK to call OpenAI with that name, which fails. For other providers pass the OpenAIChatCompletionsModel object, not the bare name.
  • Wrong base URL or missing key. Each client needs that provider's address and its own key. A key in the wrong client, or a missing optional key, causes an authentication error on that agent only.
  • Thinking the tripwire is a crash. A triggered guardrail raises an exception on purpose. In TypeScript catch InputGuardrailTripwireTriggered; in Python wrap the run if you want to handle it gracefully.
  • Expecting guardrails in the middle. They only attach to the first agent's input or the last agent's output. There is no way to check between inner steps.
  • Autonomous loops. The instructor's first run looped many times because the manager was told it "can use the tools multiple times". Agents are non-deterministic; watch the trace and the cost, and keep instructions tight.
Recap
  • A plain string model means "call OpenAI"; to use another provider, build an AsyncOpenAI client, wrap it in an OpenAIChatCompletionsModel, and pass that object to the agent.
  • Gemini, DeepSeek and Groq all expose OpenAI-compatible endpoints, so the only change per provider is the base URL and the key. Claude has no such endpoint at the time of the course.
  • Setting output_type to a Pydantic model (a zod schema in TypeScript) makes an agent return a typed object instead of free text — a structured output your code can trust.
  • Guardrails are automatic checks at the input of the first agent or the output of the last. A guardrail can itself be an agent, so an LLM can judge the content.
  • A guardrail returns GuardrailFunctionOutput; set tripwire_triggered to True to stop the run with an exception, False to let it continue.
  • Guardrails matter because real inputs come from users — they are where you keep names and other personal information out of automated output.
Honesty note. The Gemini, DeepSeek and Groq calls, and SendGrid email, are shown exactly as in the course and need each provider's own key to run; they were not re-run live for this guide. The SDK wiring, structured outputs and guardrails were verified locally against Ollama (free), and the TypeScript port type-checks and builds with vite. Small local models call tools less reliably than the cloud models, so some runs narrate a handoff rather than invoke it — that is a limit of the tiny model, not of the code.
