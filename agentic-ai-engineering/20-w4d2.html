The chatbot graph

The shape could not be simpler. One node, called chatbot, sits between START and END. Each time you send a message the graph runs start to finish, the node asks the model, and the reply comes back.

New to this? What ChatOpenAI is

ChatOpenAI comes from LangChain, LangGraph's sibling library. It is a thin wrapper around an LLM: you give it a model name, call .invoke(messages), and get a reply object back. LangGraph does not force you to use it — a node can call any model any way you like — but most community examples use ChatOpenAI because it is convenient and plays nicely with LangGraph's message objects. Point it at a local model by setting its base_url, exactly as we did with Ollama in earlier weeks.

The reducer in action

This is where add_messages earns its keep. When the node returns a reply, the reducer does not replace the message list — it appends to it. That is how a conversation accumulates within a single run.

What invoke returns, and why there is no memory yet

Every call to graph.invoke(...) is one complete run of the graph — the instructor calls this a superstep. State is managed within a superstep, but each new message starts a fresh superstep with a fresh, empty history. So this graph forgets your name the moment you send a second message. Memory between supersteps needs checkpointing, which day 3 explains in full.

New to this? HumanMessage and AIMessage

When you print what invoke returns you will not see plain strings; you will see objects called HumanMessage and AIMessage. These are LangChain's tidy wrappers around a message's role and content. The add_messages reducer does this packaging for you: hand it a dict with a role and content, and it stores the right message object. To read the text you take the last message and ask for its .content.

Video 4 · State in depth: immutable state and reducers

4. Day 2 - LangGraph Deep Dive Managing State in Graph-Based Agent Workflows.mp4 · 5:47

Slides, no notebook yet. Ed recaps Day 1 (an agent workflow is a graph; state is the current snapshot; nodes do the work and edges choose what runs next; five steps build the graph before you invoke it) and then goes deeper on the state, in two ideas.

The state is immutable. Once a state object exists you never change it. A node receives the old state and returns a new state object. The slide shows an artificial node whose state has one field, count: it reads the old count, adds one, and builds a fresh State instead of writing to old_state. (The slide writes the parameter as State: old_state; in real Python the name comes first, old_state: State, as you will see in the lab.)

def my_counting_node(State: old_state) -> State:
    count = old_state.count
    count += 1
    new_state = State(count=count)
    return new_state

Each field can have a reducer. When a node returns a new state, LangGraph calls that field's reducer to combine the new value with the existing state. Why not just let the node do it itself? Because LangGraph may run several nodes at the same time; with a reducer, their results are combined behind the scenes and no node overwrites another node's progress. Video 5 uses a ready-made reducer for message lists.

New to this? "Immutable" state

Immutable means "never changed after it is created". A node never edits the state it was handed: it reads the old state, builds a brand-new state object, and returns that. If several nodes running at once all edited one shared object they would clobber each other; returning fresh states and letting the reducer combine them means nothing gets lost. Think of each node as taking a photo and handing back a new photo, never scribbling on the original.

function shout(text: string): string {
  console.log(text.toUpperCase());
  return text.toUpperCase();
}
shout("hello");

// Step 1: Define the State object.
// One field, messages. Its reducer is addMessages (Python's add_messages): new messages are
// appended to the list instead of replacing it. The type says "stored as BaseMessage[],
// updated with anything message-like".
export const State = Annotation.Root({
  messages: Annotation<BaseMessage[], Messages>({
    reducer: addMessages,
    default: () => [],
  }),

// Step 2: Start the Graph Builder with this State (the definition, not a filled-in state)

// Video 6 in TypeScript: the silly graph, start to finish. Run: npx tsx lab1_silly.ts
import { createInterface } from "node:readline/promises";
import { stdin as input, stdout as output } from "node:process";
import { Annotation, StateGraph, START, END, addMessages, type Messages } from "@langchain/langgraph";
import type { BaseMessage } from "@langchain/core/messages";

const nouns = ["Cabbages", "Unicorns", "Toasters", "Penguins", "Bananas", "Zombies", "Rainbows", "Eels", "Pickles", "Muffins"];
const adjectives = ["outrageous", "smelly", "pedantic", "existential", "moody", "sparkly", "untrustworthy", "sarcastic", "squishy", "haunted"];
const choice = (items: string[]) => items[Math.floor(Math.random() * items.length)];

// Steps 1 and 2 (Video 5): the State and the builder
const State = Annotation.Root({
  messages: Annotation<BaseMessage[], Messages>({ reducer: addMessages, default: () => [] }),
});
const graphBuilder = new StateGraph(State);

// Step 3: Create a Node. It ignores the old state and returns a new one with one message.
function ourFirstNode(_oldState: typeof State.State) {
  const reply = `${choice(nouns)} are ${choice(adjectives)}`;
  return { messages: [{ role: "assistant", content: reply }] };
}

// Steps 3-5: add the node, the two edges, then compile
const graph = graphBuilder
  .addNode("first_node", ourFirstNode)
  .addEdge(START, "first_node")
  .addEdge("first_node", END)
  .compile();

// The notebook draws a picture; here we print the same graph as Mermaid text
console.log((await graph.getGraphAsync()).drawMermaid());

// That's it! Showtime! A terminal chat instead of the Gradio window
async function chat(userInput: string): Promise<string> {
  const result = await graph.invoke({ messages: [{ role: "user", content: userInput }] });
  console.log(result); // HumanMessage and AIMessage objects, packaged by the reducer
  return String(result.messages[result.messages.length - 1].content);
}

const rl = createInterface({ input, output });
for (;;) {
  const userInput = await rl.question("You (empty line to quit): ");
  if (!userInput.trim()) break;
  console.log("Bot:", await chat(userInput));
}
rl.close();

import "dotenv/config";
import { createInterface } from "node:readline/promises";
import { stdin as input, stdout as output } from "node:process";
import { Annotation, StateGraph, START, END, addMessages, type Messages } from "@langchain/langgraph";
import type { BaseMessage } from "@langchain/core/messages";
import { ChatOpenAI } from "@langchain/openai";

// Step 1: Define the State object
const State = Annotation.Root({
  messages: Annotation<BaseMessage[], Messages>({ reducer: addMessages, default: () => [] }),
});

// Step 2: Start the Graph Builder with this State
const graphBuilder = new StateGraph(State);

// Step 3: Create a Node (reads OPENAI_API_KEY from .env)
const llm = new ChatOpenAI({ model: "gpt-6-luna", reasoning: { effort: "none" } });

async function chatbotNode(oldState: typeof State.State) {
  const response = await llm.invoke(oldState.messages);
  return { messages: [response] };
}

// Steps 3-5: add the node, the edges, compile
const graph = graphBuilder
  .addNode("chatbot", chatbotNode)
  .addEdge(START, "chatbot")
  .addEdge("chatbot", END)
  .compile();
console.log((await graph.getGraphAsync()).drawMermaid());

// Each message is a fresh invoke: no memory yet (Day 3 adds checkpointing)
async function chat(userInput: string): Promise<string> {
  const result = await graph.invoke({ messages: [{ role: "user", content: userInput }] });
  console.log(result);
  return String(result.messages[result.messages.length - 1].content);
}

const rl = createInterface({ input, output });
for (;;) {
  const userInput = await rl.question("You (empty line to quit): ");
  if (!userInput.trim()) break;
  console.log("Bot:", await chat(userInput));
}
rl.close();

The real chatbot answers normally but has no memory: tell it your name, ask for it again, and it says it does not know.
Common mistakes.
  • Expecting memory from the first graph. Without a checkpointer every invoke starts empty. Forgetting is correct behaviour here.
  • Returning the wrong state shape. With a TypedDict State a node returns a plain dict like {"messages": […]}; with a Pydantic State it returns a State(…). Mixing them up is a common error.
  • Reading the reply as a string. invoke returns message objects, not strings. Take the last one and read its .content.
  • Passing a State object to the builder. StateGraph(State) takes the class, not State(messages=...).
  • Running the video's Gradio line on Gradio 6. gr.ChatInterface(chat, type="messages") now fails with an unexpected-argument error; drop type="messages" (see the Runs today tabs).
Recap
  • A chatbot graph is one node (chatbot) between START and END; the node calls ChatOpenAI and returns the reply.
  • The add_messages reducer appends each turn to the message list instead of replacing it.
  • The State can be a Pydantic model or a TypedDict; the node returns a matching shape.
  • Every invoke is one superstep. State lives inside a superstep, so without a checkpointer there is no memory between turns.
  • invoke returns HumanMessage/AIMessage objects; read .content for the text.
  • A node does not need an LLM: the silly graph proves nodes are just functions; the chatbot graph has the same shape with a model inside.
