Week 4 · Day 2 — State, Nodes and Edges: a Chatbot Graph

The chatbot graph

The shape could not be simpler. One node, called chatbot, sits between START and END. Each time you send a message the graph runs start to finish, the node asks the model, and the reply comes back.

New to this? What ChatOpenAI is

ChatOpenAI comes from LangChain, LangGraph's sibling library. It is a thin wrapper around an LLM: you give it a model name, call .invoke(messages), and get a reply object back. LangGraph does not force you to use it — a node can call any model any way you like — but most community examples use ChatOpenAI because it is convenient and plays nicely with LangGraph's message objects. Point it at a local model by setting its base_url, exactly as we did with Ollama in earlier weeks.

The reducer in action

This is where add_messages earns its keep. When the node returns a reply, the reducer does not replace the message list — it appends to it. That is how a conversation accumulates within a single run.

What invoke returns, and why there is no memory yet

Every call to graph.invoke(...) is one complete run of the graph — the instructor calls this a superstep. State is managed within a superstep, but each new message starts a fresh superstep with a fresh, empty history. So this graph forgets your name the moment you send a second message. Memory between supersteps needs checkpointing, which the Python file previews below and day 3 explains in full.

New to this? HumanMessage and AIMessage

When you print what invoke returns you will not see plain strings; you will see objects called HumanMessage and AIMessage. These are LangChain's tidy wrappers around a message's role and content. The add_messages reducer does this packaging for you: hand it a dict with a role and content, and it stores the right message object. To read the text you take the last message and ask for its .content.

// Week 4 - Day 2: a chatbot as a StateGraph (LangGraph.js port of 2_lab2.py).
//
// Same five steps as day 1, but now the single node calls a real LLM. The State's
// `messages` channel uses the add_messages reducer (via MessagesAnnotation), so each
// turn is appended to the running conversation that the node sees.
import { StateGraph, MessagesAnnotation, START, END } from "@langchain/langgraph";
import { makeLlm } from "./model.js";

// The model that powers the one node (pointed at Ollama by model.ts).
const llm = makeLlm();

// Step 3: the chatbot node. It asks the LLM using every message so far and returns
// the reply; the reducer appends it to state.messages.
async function chatbot(state: typeof MessagesAnnotation.State) {
  const response = await llm.invoke(state.messages);
  return { messages: [response] };
}

// Steps 1,2,4,5: State (MessagesAnnotation) -> add node -> wire edges -> compile.
const graph = new StateGraph(MessagesAnnotation)
  .addNode("chatbot", chatbot)
  .addEdge(START, "chatbot")
  .addEdge("chatbot", END)
  .compile();

/** Send one user message through the graph and return the assistant's reply text. */
export async function chatOnce(userInput: string): Promise<string> {
  const result = await graph.invoke({
    messages: [{ role: "user", content: userInput }],
  });
  return String(result.messages.at(-1)?.content ?? "");
}

async function main() {
  console.log(await graph.getGraphAsync().then((g) => g.drawMermaid()));

  // This graph has no checkpointer, so each call is independent - no memory between
  // turns. Memory is added in day 3.
  for (const prompt of [
    "In one sentence, what is LangGraph?",
    "Name one benefit of modelling an agent as a graph. One sentence.",
  ]) {
    console.log(`\nUser: ${prompt}`);
    console.log(`Assistant: ${await chatOnce(prompt)}`);
  }
}

main().catch((err) => {
  console.error(err);
  process.exitCode = 1;
});

The graph the Python file previews

So you know where day 3 is heading, here is the richer graph the Python notebook sketches: the chatbot can now loop through a tools node before answering.

What you should see. The plain chatbot answers normally but has no memory: tell it your name, ask for it again, and it says it does not know. Once the Python notebook compiles with a checkpointer and passes a thread_id, the same question gets the right answer — proof that memory comes from checkpointing, not from Gradio.
Common mistakes.
  • Expecting memory from the first graph. Without a checkpointer every invoke starts empty. Forgetting is correct behaviour here.
  • Returning the wrong state shape. With a TypedDict State a node returns a plain dict like {"messages": […]}; with a Pydantic State it returns a State(…). Mixing them up is a common error.
  • Reading the reply as a string. invoke returns message objects, not strings. Take the last one and read its .content.
  • Dropping the tools→chatbot edge. In the preview graph, if you forget the edge back from tools to the chatbot, tool results never reach the model and the run misbehaves.
Recap
  • A chatbot graph is one node (chatbot) between START and END; the node calls ChatOpenAI and returns the reply.
  • The add_messages reducer appends each turn to the message list instead of replacing it.
  • The State can be a Pydantic model or a TypedDict; the node returns a matching shape.
  • Every invoke is one superstep. State lives inside a superstep, so without a checkpointer there is no memory between turns.
  • invoke returns HumanMessage/AIMessage objects; read .content for the text.
  • The Python notebook previews tools, conditional edges and checkpointing — all explained in full on day 3.
