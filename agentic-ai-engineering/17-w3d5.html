Week 3 · Day 5 — The Engineering Team

The capstone crew: an engineering lead, a backend and a frontend engineer and a tester collaborate to turn requirements into working software.

Companion to Ed Donner's course · uv setup · Python (+ TypeScript/React where it fits) · code from the course repo

This is the capstone of crew week. We take the single coder agent from day four and grow it into a whole engineering team: an engineering lead who designs, a backend engineer who writes and runs the code, a frontend engineer who builds a Gradio UI, and a test engineer who writes and runs unit tests. Given a plain-English set of requirements, the crew turns them into working software — a complete backend module, a user interface, and tests — with no new CrewAI concepts, just more of what you already know.

Nothing new to learn — just more agents. Every idea here appeared earlier this week: role/goal/backstory, tasks with expected_output, context to pass work forward, different models per agent, and allow_code_execution in a Docker sandbox. The lesson of day five is how far those pieces go when you put four specialists together.

New to this? Agents as system prompts, tasks as user prompts

A useful way to picture a crew: each agent (its role, goal and backstory) behaves like a system prompt — the stable identity of the worker. Each task (its description) behaves like a user prompt — the specific request. The context you attach to a task is extra material folded into that request. Seeing it this way makes it clear why the same agent can handle several different tasks.

# CrewAI's built-in code execution (allow_code_execution) is gone, so the agent gets
# four small tools instead: list, read and write files in a sandbox folder, and run a
# Python file there inside a throwaway Docker container.
from crewai.tools import tool
from pathlib import Path
import subprocess


SANDBOX_DIR = Path(__file__).parents[3] / "sandbox"
SANDBOX_DIR.mkdir(parents=True, exist_ok=True)

@tool("List Sandbox Files")
def list_sandbox_files() -> str:
    """
    List the filenames currently in the sandbox directory.

    Returns:
        A newline-separated list of filenames, or a message if the
        sandbox is empty.
    """
    names = sorted(p.name for p in SANDBOX_DIR.iterdir())
    return "\n".join(names) if names else "The sandbox is empty."


@tool("Read Sandbox File")
def read_sandbox_file(filename: str) -> str:
    """
    Read and return the text contents of a file in the sandbox directory.

    Args:
        filename: The name of the file to read (e.g. "solution.py").
    Returns:
        The file's contents, or a message if the file does not exist.
    """
    path = SANDBOX_DIR / filename
    if not path.is_file():
        return f"No such file in the sandbox: {filename}"
    return path.read_text()


@tool("Write Sandbox File")
def write_sandbox_file(filename: str, content: str) -> str:
    """
    Write text to a file in the sandbox directory, replacing any existing
    file with the same name.

    Args:
        filename: The name of the file to write (e.g. "solution.py").
        content: The text content to write.
    Returns:
        A confirmation message.
    """
    path = SANDBOX_DIR / filename
    path.write_text(content)
    return f"Wrote {len(content)} characters to {filename}."


@tool("Run Sandbox Python File")
def run_sandbox_python(filename: str) -> str:
    """
    Execute a Python file from the sandbox directory inside an ephemeral
    Docker container, with the sandbox mounted as the working directory,
    and return whatever the script printed to stdout.

    Args:
        filename: The name of the Python file to run (e.g. "solution.py").
    Returns:
        The text printed to stdout by the executed script.
    """
    result = subprocess.run(
        [
            "docker", "run", "--rm",
            "-v", f"{SANDBOX_DIR}:/workspace",
            "-w", "/workspace",
            "python:3.13-slim",
            "python", filename,
        ],
        capture_output=True,
        text=True,
        timeout=60,
    )
    return result.stdout

sandbox_tools = [list_sandbox_files, read_sandbox_file, write_sandbox_file, run_sandbox_python]

Slides, then the CrewAI docs. Easy extension: "your team is hiring", so add a real test engineer who writes and runs a test plan, a business analyst who fleshes out requirements, a richer UI. The real challenge: the team only ever builds one fixed module. Let the lead describe several modules with structured outputs, then create a Task per module at run time, using a task callback (a function CrewAI calls when a task finishes) to spawn the next tasks. Ed first says callbacks live on the agent, then corrects himself: they are on the task. He scrolls through the Tasks page of the docs: tasks in code instead of YAML, guardrails (like the OpenAI Agents SDK's, but allowed on any task), output_pydantic/output_json, tools on tasks, context, asynchronous execution, and the callback mechanism below.

Honesty note. This crew calls paid OpenAI and Anthropic APIs (and uses a Docker sandbox for code execution), and was not re-run live for this guide. The files, the UI and the instructor's reactions are reported as shown in the course. The companion project was verified locally against Ollama where feasible; a large model is needed for a result as complete as the instructor's.
In TypeScript. There is no CrewAI for TypeScript, so this multi-agent build has no direct port. The generated program itself is Python (a module, a Gradio UI, and unit tests), which is Python-only too. In the Node world you would coordinate four model calls by hand and run the generated code in your own sandbox — exactly the plumbing CrewAI's agents, tasks, context and allow_code_execution remove.
Take it further. The instructor suggests two extensions. The easy one: add more agents (a real test engineer who writes and runs a test plan, a business analyst who fleshes out requirements). The hard one, the week's real challenge: use structured outputs so the lead describes multiple modules, then create Task objects dynamically at run time (using a task callback that spawns the next task) so the team can build a whole multi-module system rather than one fixed module.
Recap
  • The engineering_team crew turns plain-English requirements into working software: a design, a backend module, a Gradio UI, and unit tests.
  • Four agents, one task each, chained with context so each works from the right upstream result; the crew runs sequentially.
  • The backend and test engineers use allow_code_execution=True in a safe Docker sandbox; the lead and frontend only write. Different agents use different models (gpt-4o, Claude 3.7 Sonnet and DeepSeek in the video). Current CrewAI has removed that built-in execution; the "runs today" crew uses Docker sandbox tools instead.
  • Template placeholders ({requirements}, {module_name}, {class_name}) are set in main.py and used everywhere in the YAML, even in output file names.
  • No new CrewAI concepts — day five shows how far agents, tasks, context, per-agent models and code execution reach when combined.
