Week 4 · Day 1 — LangGraph: Agents as Graphs

Why LangGraph models an agent as a graph, and how Framework, Studio and Platform fit together. The core pieces: state, nodes, edges and the graph you compile and run - in Python and TypeScript.

Companion to Ed Donner's course · uv setup · Python (+ TypeScript/React where it fits) · code from the course repo

Welcome to week four. We are changing frameworks again, this time to LangGraph, which asks you to think about an agent in a brand-new way: as a graph. Instead of writing one long function that calls an LLM, loops, calls a tool, and loops again, you describe your work as a set of boxes (nodes) joined by arrows (edges), hand that description to LangGraph, and let it run the whole thing for you. Day 1 is all theory: three videos of slides with the four core ideas and the five steps. The first code, a deliberately silly graph, comes on Day 2.

Because LangGraph has a real JavaScript port called LangGraph.js, this whole week is bilingual. From Day 2 on, every lab is shown in Python (the language in the course video) and in TypeScript, with a Code in: switch to pick one.

This is a short, concept-heavy day. The instructor spends day one on vocabulary and draws the rest out over the week. We do the same: get the words right first, then the code on the following days feels easy.

Lesson by lesson

One section per video, in the order you watch them. Day 1 is three videos of slides, so there is no code on this page; the first lab (1_lab1.ipynb, a deliberately silly graph and then a chatbot graph) starts on Day 2.

Video 1 · LangGraph explained: graph-based architecture for robust agents

1. Day 1 - LangGraph Explained Graph-Based Architecture for Robust AI Agents.mp4 · 10:12

Slides. Ed opens LangGraph week (a shorter week, he says, because so much carries over from the OpenAI Agents SDK and CrewAI) and first clears up the "Lang" confusion with snapshots of the LangChain website. He admits a love-hate relationship with LangChain: a lot of power in very little code (a RAG pipeline in a few lines), but by signing up for its abstractions you see less of the actual prompts, and since most LLM APIs now look like OpenAI's and memory is "just the JSON blob of the conversation", you can often do those things yourself. LangGraph, in his words, is a separate product from the same company, independent of LangChain, built for stability, resiliency and repeatability when many agent steps are interconnected: workflows as graphs, with human-in-the-loop, memory and "time travel" (checkpoints you can step back to).

Three products with similar names

Before any code, the instructor clears up a common confusion. LangChain the company makes three different things, and their names all start with "Lang".

LangChain is the oldest: a big toolbox for anything that calls an LLM, including chaining calls together, prompt templates, memory, and retrieval. LangGraph is newer and independent. It is built for the thing people worry about with agents — running complex, looping, multi-step work in a way that is stable, repeatable, and can be paused, resumed, and rewound. LangSmith is a separate monitoring service that shows you what happened inside a run. You can use LangSmith with either of the other two.

New to this? Why "a graph"?

In computer science a graph is just boxes joined by arrows — think of a flowchart. LangGraph asks you to draw your agent as a flowchart: each box is a step (ask the model, run a tool, check an answer) and each arrow says what happens next. Drawing it this way lets LangGraph add safety nets at every box, run boxes in parallel when it can, and save a snapshot after each run so it can resume if something fails. The name says it all: Language models organised as a graph.

Video 3 · LangGraph theory: the core terms and the five steps

3. Day 1 - LangGraph Theory Core Components for Building Advanced Agent Systems.mp4 · 9:52

Slides, built up line by line under the title "Prepare for terminology": agent workflows are represented as graphs; state is the current snapshot of the application; nodes are Python functions that receive the state, do something and return an updated state; edges are Python functions that decide which node runs next, and can be conditional or fixed. "Nodes do the work. Edges choose what to do next." Then the five steps that lay out a graph before it runs. Ed mentions that the State class has something called a reducer and leaves it for tomorrow (Day 2, Video 4).

The four core ideas

These four words carry the whole week. The instructor repeats them on purpose; so will we.

  • State is a single object that holds the current situation of the whole application — for us, mostly the list of chat messages so far. It is information, not a function.
  • A node is a Python (or TypeScript) function. It receives the state, does something — maybe call an LLM, maybe write a file — and returns an update to the state.
  • An edge is the connection between nodes: it decides which node runs next. The special markers START and END are where the graph begins and finishes. An edge can be plain ("always go here next") or conditional ("go here only if…") — we meet conditional edges on day 3.
  • The compiled graph is what you get after you finish describing nodes and edges and call compile(). It is the runnable object you then invoke.

The five steps to build and run a graph

The step that trips people up is that building a graph is itself code that runs. When your program starts it first describes the whole workflow (steps 1–5), and only afterwards do you invoke it to make the agent actually do its job. It is a little like writing a recipe and then cooking it, both in the same program.

Ed repeats the key point three times on purpose: running a LangGraph application has two phases. First your code lays out the graph (the five steps); then you invoke it and the agents run. Tomorrow's lab writes code for all five steps and calls it.

What you should take away. There is nothing to run today. You should be able to say which of LangChain, LangGraph and LangSmith we build with, explain state, node and edge in one sentence each, and list the five steps in order, knowing that they all happen before invoke runs the graph.
Common mistakes.
  • Thinking LangGraph needs LangChain. They are separate products. The labs borrow LangChain's ChatOpenAI because it is convenient, but a node can call any model any way.
  • Thinking you need the paid Platform. The website pushes LangGraph Platform; the course only uses the free framework.
  • Mixing up the two phases. The five steps describe the graph; nothing runs until you invoke the compiled graph.
  • Confusing nodes and edges. Nodes do the work; edges only decide what runs next.
Recap
  • LangChain, LangGraph and LangSmith are three products; we build with LangGraph the framework and watch runs in LangSmith later.
  • Four ideas: State (shared data), nodes (functions that do work), edges (what runs next), and the compiled graph you invoke.
  • Anthropic's "Building effective agents" post argues for starting with plain LLM APIs; LangGraph is the opposite school, and Week 6's MCP is Anthropic's own answer.
  • Five steps build the graph (define State, start builder, add nodes, add edges, compile); then invoke runs it.
  • The State class has a reducer; Day 2 explains it, then builds the first graph.
