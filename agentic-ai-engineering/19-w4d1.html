Week 4 · Day 1 — LangGraph: Agents as Graphs

Why LangGraph models an agent as a graph, and how Framework, Studio and Platform fit together. The core pieces: state, nodes, edges and the graph you compile and run - in Python and TypeScript.

Companion to Ed Donner's course · uv setup · Python (+ TypeScript/React where it fits) · code from the course repo

Welcome to week four. We are changing frameworks again, this time to LangGraph, which asks you to think about an agent in a brand-new way: as a graph. Instead of writing one long function that calls an LLM, loops, calls a tool, and loops again, you describe your work as a set of boxes (nodes) joined by arrows (edges), hand that description to LangGraph, and let it run the whole thing for you. Day 1 is almost all theory. We learn the four core ideas and the five steps, then build one deliberately silly graph so the machinery is concrete before we do anything clever.

Because LangGraph has a real JavaScript port called LangGraph.js, this whole week is bilingual. Every lab is shown in Python (the language in the course video) and in TypeScript. Use the Code in: switch to pick one; the walkthrough follows your choice.

This is a short, concept-heavy day. The instructor spends day one on vocabulary and draws the rest out over the week. We do the same: get the words right first, then the code on the following days feels easy.

Three products with similar names

Before any code, the instructor clears up a common confusion. LangChain the company makes three different things, and their names all start with "Lang".

LangChain is the oldest: a big toolbox for anything that calls an LLM, including chaining calls together, prompt templates, memory, and retrieval. LangGraph is newer and independent. It is built for the thing people worry about with agents — running complex, looping, multi-step work in a way that is stable, repeatable, and can be paused, resumed, and rewound. LangSmith is a separate monitoring service that shows you what happened inside a run. You can use LangSmith with either of the other two.

New to this? Why "a graph"?

In computer science a graph is just boxes joined by arrows — think of a flowchart. LangGraph asks you to draw your agent as a flowchart: each box is a step (ask the model, run a tool, check an answer) and each arrow says what happens next. Drawing it this way lets LangGraph add safety nets at every box, run boxes in parallel when it can, and save a snapshot after each run so it can resume if something fails. The name says it all: Language models organised as a graph.

LangGraph is itself three things

One more layer of naming. "LangGraph" can mean any of three offerings. We only use the first.

The four core ideas

These four words carry the whole week. The instructor repeats them on purpose; so will we.

  • State is a single object that holds the current situation of the whole application — for us, mostly the list of chat messages so far. It is information, not a function.
  • A node is a Python (or TypeScript) function. It receives the state, does something — maybe call an LLM, maybe write a file — and returns an update to the state.
  • An edge is the connection between nodes: it decides which node runs next. The special markers START and END are where the graph begins and finishes. An edge can be plain ("always go here next") or conditional ("go here only if…") — we meet conditional edges on day 3.
  • The compiled graph is what you get after you finish describing nodes and edges and call compile(). It is the runnable object you then invoke.
New to this? "Immutable" state

LangGraph treats the state as immutable: a node never edits the state it was handed. It reads the old state, builds a brand-new state object, and returns that. Why bother? Because a graph may run several nodes at the same time, and if they all edited one shared object they would clobber each other. By returning fresh states and letting LangGraph combine them (with a reducer, below), nothing gets lost. Think of each node as taking a photo and handing back a new photo, never scribbling on the original.

The reducer and add_messages

There is one more piece of vocabulary: the reducer. When you describe a field of your state, you can attach a small function that tells LangGraph how to combine the new value a node returns with the value already in the state. For our message list we use a ready-made reducer called add_messages, which simply appends new messages onto the running list instead of replacing it. That is how the conversation grows turn by turn. We will see it work on day 2; for now, just know the word.

The five steps to build and run a graph

The step that trips people up is that building a graph is itself code that runs. When your program starts it first describes the whole workflow (steps 1–5), and only afterwards do you invoke it to make the agent actually do its job. It is a little like writing a recipe and then cooking it, both in the same program.

The first tiny graph

To make all this concrete the lab builds the silliest possible graph: one node that ignores its input and replies with a random sentence like "Penguins are sparkly". It has nothing to do with AI, and that is the point — it proves a node is just a function, and lets us see the five steps with no LLM in the way. The file then builds a second, slightly more sensible graph whose one node calls a real model with ChatOpenAI; that chatbot is what day 2 expands.

Here is the complete lab in both languages. Python is the course version; the TypeScript port keeps just the silly first graph using LangGraph.js. Both print the graph's shape and then run it.

from langchain_openai import ChatOpenAI

import random

adjectives = ["outrageous", "smelly", "pedantic", "existential", "moody", "sparkly", "untrustworthy", "sarcastic", "squishy", "haunted"]

shout("hello")

    messages: Annotated[list, add_messages]


graph_builder = StateGraph(State)

def our_first_node(old_state: State) -> State:

    reply = f"{random.choice(nouns)} are {random.choice(adjectives)}"
    messages = [{"role": "assistant", "content": reply}]

    new_state = State(messages=messages)

    return new_state

graph_builder.add_node("first_node", our_first_node)

// Week 4 - Day 1: a first tiny StateGraph (LangGraph.js port of 1_lab1.py).
//
// LangGraph models an agent as a GRAPH. Four ideas:
//   * State  - a shared, typed object that flows through the graph.
//   * Node   - a function that reads the state and returns an update to it.
//   * Edge   - what runs next (START -> node -> END).
//   * compile+invoke - turn the builder into a runnable graph and call it.
//
// This graph is deliberately silly (like the course's lab 1): one node appends a
// random "<Noun> are <adjective>" message. The point is only to see the five steps.
import { StateGraph, MessagesAnnotation, START, END } from "@langchain/langgraph";
import { AIMessage } from "@langchain/core/messages";

const nouns = ["Cabbages", "Unicorns", "Toasters", "Penguins", "Bananas", "Rainbows"];
const adjectives = ["outrageous", "smelly", "pedantic", "sparkly", "sarcastic", "haunted"];

const pick = <T>(xs: T[]): T => xs[Math.floor(Math.random() * xs.length)];

// Step 1 + 2: use the built-in MessagesAnnotation for the State. It defines a single
// `messages` channel whose reducer APPENDS new messages (the add_messages behaviour).
// Step 3: the node. It returns { messages: [...] }, which is appended to the state.
function firstNode(_state: typeof MessagesAnnotation.State) {
  const reply = `${pick(nouns)} are ${pick(adjectives)}`;
  return { messages: [new AIMessage(reply)] };
}

// Step 4 + 5: wire START -> first_node -> END, then compile into a runnable graph.
const graph = new StateGraph(MessagesAnnotation)
  .addNode("first_node", firstNode)
  .addEdge(START, "first_node")
  .addEdge("first_node", END)
  .compile();

// Run it from the command line: `npm run day1`.
async function main() {
  // Print the graph's shape as Mermaid text (the course draws it as a PNG).
  console.log(await graph.getGraphAsync().then((g) => g.drawMermaid()));

  const result = await graph.invoke({ messages: [] });
  // The last message is whatever the node appended.
  console.log("Reply:", result.messages.at(-1)?.content);
}

// Only run when executed directly (so the file can also be imported by tests/the API).
main().catch((err) => {
  console.error(err);
  process.exitCode = 1;
});

What you should see. The silly graph prints a random sentence like "Muffins are haunted" for any input. The picture shows START → first_node → END. The second graph answers like a real chatbot — but ask "what's my name?" after telling it, and it will not know, because there is no memory yet.
Common mistakes.
  • Passing a State instance to the builder. StateGraph(State) takes the class, not an object you created. Passing an instance fails.
  • Editing the old state. Do not change old_state inside a node; build and return a new one. Mutating it leads to confusing bugs once nodes run in parallel.
  • Forgetting load_dotenv. The second graph calls OpenAI; with no OPENAI_API_KEY loaded it fails. Crew loaded it for you, LangGraph does not.
  • Expecting memory. This graph has none. Forgetting your name between turns is expected today.
Recap
  • LangChain, LangGraph and LangSmith are three products; we build with LangGraph the framework and watch runs in LangSmith later.
  • Four ideas: State (shared data), nodes (functions that do work), edges (what runs next), and the compiled graph you invoke.
  • State is immutable: a node reads the old state and returns a new one, never editing it.
  • A field can carry a reducer; add_messages appends new messages to the running list.
  • Five steps build the graph (define State, start builder, add nodes, add edges, compile); then invoke runs it.
  • The first graph is deliberately silly to show a node is just a function; the chatbot version has no memory yet.
Honesty note. The chatbot graph calls OpenAI and needs your OPENAI_API_KEY to run; it was not re-run live for this guide. The graph wiring (State, node, edges, compile, invoke) was verified locally against Ollama, and the TypeScript port type-checks and builds with vite.
