Week 3 · Day 1 — CrewAI: Agents, Tasks and a Debate

Meet CrewAI: agents have a role, goal and backstory; tasks describe the work; a process runs them. Build a debate crew where different LLMs argue a motion and a judge decides.

Companion to Ed Donner's course · uv setup · Python (+ TypeScript/React where it fits) · code from the course repo

Welcome to week three and a brand new framework. Last week everything ran on the OpenAI Agents SDK. This week we put that to one side and meet CrewAI, a Python framework for building teams of agents that work together. The ideas are close enough that your week-two knowledge carries over, but the words are new and CrewAI is a little more opinionated about how you describe each agent. Day one is a gentle tour of the core pieces, ending with a working project: a debate crew where one agent argues both sides of a motion and a second agent judges the winner.

CrewAI is Python only. Unlike weeks one and two, there is no official JavaScript or TypeScript port of CrewAI, so every code block this week is a single Python or YAML file rather than a side-by-side language switch. Where a TypeScript developer would want to know "how would I do this in my world?", a short In TypeScript note answers it honestly. The small React demo you will see later in the week is just a user interface; it is not CrewAI running in TypeScript.

What "CrewAI" actually means

The instructor is careful to point out that the word "crew" is used for three different products. Knowing which is which saves confusion later.

New to this? The three things called "Crew"
  • CrewAI Enterprise — a paid platform for deploying, running and monitoring agents through dashboards. This is how the company makes money. We do not use it.
  • CrewAI UI Studio — a low-code / no-code tool for piecing agents together by clicking rather than coding. We do not use it either.
  • The CrewAI framework — the open-source Python library for "orchestrating high-performing AI agents". This is the one we write code against all week.

The framework itself comes in two flavours. Crews are teams of agents that solve a problem autonomously — good for creative, exploratory work. Flows are fixed, step-by-step workflows with decision points — good when you need a predictable, auditable path. Because this course is about agents choosing their own path, we focus entirely on crews.

The three building blocks

CrewAI has three core concepts. They map loosely onto what you already know, with one genuinely new idea (the task).

New to this? What an agent is in CrewAI

An agent is the smallest autonomous unit of work. It wraps an LLM and is described by three fields: a role (what it is), a goal (what it is trying to achieve) and a backstory (context that primes how it behaves). It can also be given tools and memory. This is more prescriptive than the OpenAI Agents SDK, where you just wrote a single instruction. Forcing you to fill in a role, goal and backstory nudges you toward good prompting habits. The trade-off is less direct control: CrewAI builds the real system prompt from those fields behind the scenes, so it is a little harder to see exactly what the model receives.

New to this? What a task is

A task is a specific assignment. It has a description (what to do), an expected_output (what a good answer looks like), and it is given to exactly one agent. The OpenAI Agents SDK had no direct equivalent — this is the new idea to learn this week. One agent can carry out several tasks, which is why CrewAI keeps tasks as separate objects rather than folding them into the agent.

New to this? What a crew is, and its two process modes

A crew is a team: a list of agents, a list of tasks, and a process mode that decides how the tasks run. There are two modes:

  • Process.sequential — run each task in order, top to bottom. Simple and predictable. The debate crew uses this.
  • Process.hierarchical — a manager agent (an LLM) decides which agent does which task. More autonomous, less predictable. We meet it on day three.

Naming any model with LiteLLM

CrewAI talks to models through a small library called LiteLLM. Its one job is to let you name any model as a plain string in the form provider/model. There is no client to configure and no base URL to remember for the common providers — you just write the string.

A CrewAI project is a folder, not a notebook

Weeks one and two lived in Jupyter notebooks. CrewAI is different: it scaffolds a whole project directory for each crew. You create one with a command, and it generates the folders, the config files and the Python modules for you. This is more scaffolding than we are used to, so it is worth seeing the shape of it before we build.

New to this? Why YAML files?

YAML is a simple, human-friendly text format for configuration. CrewAI uses two YAML files — agents.yaml and tasks.yaml — to hold the wordy parts of your agents and tasks (their roles, goals, backstories, descriptions). Keeping that text in YAML separates your prompts from your Python code, so you can edit the wording without touching logic. Indentation matters in YAML: a stray tab or wrong indent breaks the file, and the error you get can be hard to read. Keep the spacing exactly as shown.

Build the debate crew

The project is a debate. One debater agent argues for the motion and (separately) against it; a judge agent reads both arguments and decides the winner. The motion is a template value filled in at run time.

  1. Open a terminal and change into the week-three folder (3_crew).
  2. Create the project: crewai create crew debate. When prompted, choose OpenAI and gpt-4o-mini, then press Enter to skip key setup (you already have a .env).
  3. Open src/debate/config/agents.yaml and describe the two agents.
  4. Open src/debate/config/tasks.yaml and describe the three tasks.
  5. Edit src/debate/crew.py to wire the agents, tasks and crew together.
  6. Edit src/debate/main.py to set the motion and run it.
  7. Run it from inside the debate folder: crewai run.
You cannot name a task the same as an agent. The crew would have two things called, say, judge, and they clash. That is why the deciding task is called decide, not judge. Keep agent names and task names distinct.

The agents

Two agents, written entirely in YAML. Notice the {motion} placeholder: it is a template slot filled at run time from main.py. Notice too that each agent names a different model with the LiteLLM provider/model string.

debater:
  role: >
    A compelling debater
  goal: >
    Present a clear argument either in favor of or against the motion. The motion is: {motion}
  backstory: >
    You're an experienced debator with a knack for giving concise but convincing arguments.
    The motion is: {motion}
  llm: openai/gpt-4o-mini

judge:
  role: >
    Decide the winner of the debate based on the arguments presented
  goal: >
    Given arguments for and against this motion: {motion}, decide which side is more convincing,
    based purely on the arguments presented.
  backstory: >
    You are a fair judge with a reputation for weighing up arguments without factoring in
    your own views, and making a decision based purely on the merits of the argument.
    The motion is: {motion}
  llm: anthropic/claude-3-7-sonnet-latest

The tasks

Three tasks. The debater agent handles two of them (propose, then oppose); the judge handles the third (decide). Each task says where to save its output.

propose:
  description: >
    You are proposing the motion: {motion}.
    Come up with a clear argument in favor of the motion.
    Be very convincing.
  expected_output: >
    Your clear argument in favor of the motion, in a concise manner.
  agent: debater
  output_file: output/propose.md

oppose:
  description: >
    You are in opposition to the motion: {motion}.
    Come up with a clear argument against the motion.
    Be very convincing.
  expected_output: >
    Your clear argument against the motion, in a concise manner.
  agent: debater
  output_file: output/oppose.md
decide:
  description: >
    Review the arguments presented by the debaters and decide which side is more convincing.
  expected_output: >
    Your decision on which side is more convincing, and why.
  agent: judge
  output_file: output/decide.md

The crew module

This is where the pieces come together in Python. It is short because the wordy parts live in YAML. The magic is in the decorators.

from crewai import Agent, Crew, Process, Task
from crewai.project import CrewBase, agent, crew, task


@CrewBase
class Debate():
    """Debate crew"""


    agents_config = 'config/agents.yaml'
    tasks_config = 'config/tasks.yaml'

    @agent
    def debater(self) -> Agent:
        return Agent(
            config=self.agents_config['debater'],
            verbose=True
        )

    @agent
    def judge(self) -> Agent:
        return Agent(
            config=self.agents_config['judge'],
            verbose=True
        )

    @task
    def propose(self) -> Task:
        return Task(
            config=self.tasks_config['propose'],
        )

    @task
    def oppose(self) -> Task:
        return Task(
            config=self.tasks_config['oppose'],
        )

    @task
    def decide(self) -> Task:
        return Task(
            config=self.tasks_config['decide'],
        )


    @crew
    def crew(self) -> Crew:
        """Creates the Debate crew"""

        return Crew(
            agents=self.agents, # Automatically created by the @agent decorator
            tasks=self.tasks, # Automatically created by the @task decorator
            process=Process.sequential,
            verbose=True,
        )
New to this? What the @CrewBase, @agent, @task and @crew decorators do

A decorator is a label written above a function with an @ that quietly adds behaviour to it. CrewAI uses four:

  • @CrewBase wraps the whole class and manages the crew machinery.
  • @agent marks a method that returns an Agent. CrewAI collects every such method into a ready-made list called self.agents.
  • @task marks a method that returns a Task, collected into self.tasks.
  • @crew marks the method that builds and returns the finished Crew.

That is why, at the bottom, you can just write agents=self.agents and tasks=self.tasks without listing them by hand — the decorators already filled those lists.

The runner

Finally main.py sets the template value and kicks the crew off.

#!/usr/bin/env python
import sys
import warnings

from datetime import datetime

from debate.crew import Debate

warnings.filterwarnings("ignore", category=SyntaxWarning, module="pysbd")

# This main file is intended to be a way for you to run your
# crew locally, so refrain from adding unnecessary logic into this file.
# Replace with inputs you want to test with, it will automatically
# interpolate any tasks and agents information

def run():
    """
    Run the crew.
    """
    inputs = {
        'motion': 'There needs to be strict laws to regulate LLMs',
    }
    
    try:
        result = Debate().crew().kickoff(inputs=inputs)
        print(result.raw)
    except Exception as e:
        raise Exception(f"An error occurred while running the crew: {e}")

What you should see. After crewai run, the terminal prints each agent's work as it happens (because verbose=True). The debater produces a "for" argument, then an "against" argument, then Claude (the judge) weighs them and prints a decision. In the instructor's run the judge found the arguments in favour of regulating LLMs more convincing. A new output/ folder appears with propose.md, oppose.md and decide.md. Your exact wording will differ each time — LLMs are non-deterministic.
Common mistakes.
  • Running from the wrong folder. crewai run must be run from inside the debate project folder, not the week folder above it.
  • Name clashes. A task named the same as an agent causes a conflict. Keep them distinct.
  • Broken YAML indentation. A stray tab or wrong indent breaks the config and the error is cryptic. Match the spacing exactly.
  • Missing keys. The debater needs an OpenAI key and the judge needs an Anthropic key in your .env. Point both agents at one provider if you only have one key.
In TypeScript. There is no CrewAI for TypeScript, so there is nothing to port here. If you work in Node, the closest idea is to hand-write the same three steps — call a model for the "for" argument, call it again for the "against" argument, then call a model to judge — using the OpenAI SDK you met in week one. You would lose the YAML config, the decorators and the automatic task ordering; those conveniences are exactly what CrewAI gives you, and they only exist in Python.
Recap
  • CrewAI has three building blocks: the agent (role, goal, backstory, an LLM), the task (description, expected_output, assigned to one agent), and the crew (the team plus a process mode).
  • A crew runs either sequentially (tasks in order) or hierarchically (a manager agent decides). The debate crew is sequential.
  • LiteLLM lets you name any model as provider/model, so one agent can use OpenAI and another Anthropic with a one-line change.
  • A CrewAI project is a scaffolded folder. You edit two YAML files (agents, tasks), crew.py and main.py, then run crewai run.
  • The @CrewBase, @agent, @task and @crew decorators wire everything together and auto-fill self.agents and self.tasks.
  • {motion} placeholders are filled from the inputs dictionary passed to kickoff().
Honesty note. This crew calls paid OpenAI and Anthropic APIs and was not re-run live for this guide; the code and the instructor's result are shown as in the course. You can run the whole thing for free by pointing both agents at a local Ollama model (ollama/llama3.2) instead, which is how the companion project was verified locally.
