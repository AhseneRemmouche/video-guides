Week 5 · Day 4 — Distributed Agents

AutoGen Core's distributed runtime: run agents across processes that talk over a gRPC host. The architecture and a cross-process example.

Companion to Ed Donner's course · uv setup · Python (+ TypeScript/React where it fits) · code from the course repo

Day 4 takes AutoGen Core from one machine to many. The standalone runtime you met yesterday ran everything in a single process. Today's distributed runtime lets agents live in different processes — in principle on different computers, even written in different languages — and still message each other as if they were in the same file. The instructor keeps it high-level and honest: this layer is powerful but still experimental.

Experimental, straight from Microsoft. Microsoft labels the distributed runtime experimental and warns its APIs may change. It is an architecture and a glimpse of the future, not a production system. Treat this day as a flavour, exactly as the course does.

Two pieces: a host and workers

The distributed runtime splits into two components. The host (GrpcWorkerAgentRuntimeHost) is the meeting point: it accepts connections from workers, knows which agents each one has, and manages delivering direct messages between them. The worker (GrpcWorkerAgentRuntime) is what you treat like yesterday's runtime — you register agents with it and it runs their code. One host can serve many workers.

New to this? What gRPC is

gRPC is a way for one program to call a function in another program, even across a network or a different language. Think of it like a REST HTTP call, but instead of hitting a URL you call a function directly and get its return value back. It is used widely wherever programs need to talk across process boundaries. Here it is the wiring the host uses to carry messages between workers — but you never write gRPC yourself; AutoGen hides it.

The example: should we use AutoGen?

Rather than a toy game, Day 4 poses a small business decision: should a project adopt AutoGen? Two research agents go to work — player1 gathers the pros, player2 gathers the cons — each using a web-search tool borrowed from LangChain. A Judge agent messages both, collects their findings, and makes a recommendation based only on their research. The structure mirrors yesterday's referee, which is the point: the agent code barely changed.

One worker or three — same code

The lab runs the same agents in two layouts, chosen by a flag ALL_IN_ONE_WORKER. When True, all three agents register with a single worker. When False, three separate workers each host one agent, all connected to the same host. Nothing in the agent classes changes — only how many workers you start and where you register each agent. That is the headline: your code does not know, or care, how it is distributed.

instruction1 = "To help with a decision on whether to use AutoGen in a new AI Agent project, \
please research and briefly respond with reasons in favor of choosing AutoGen; the pros of AutoGen."

instruction2 = "To help with a decision on whether to use AutoGen in a new AI Agent project, \
please research and briefly respond with reasons against choosing AutoGen; the cons of Autogen."

judge = "You must make a decision on whether to use AutoGen for a project. \
Your research team has come up with the following reasons for and against. \
Based purely on the research from your team, please respond with your decision and brief rationale."

class Player1Agent(RoutedAgent):
    def __init__(self, name: str) -> None:
        super().__init__(name)
        model_client = OpenAIChatCompletionClient(model="gpt-4o-mini")
        self._delegate = AssistantAgent(name, model_client=model_client, tools=[autogen_serper], reflect_on_tool_use=True)

    @message_handler
    async def handle_my_message_type(self, message: Message, ctx: MessageContext) -> Message:
        text_message = TextMessage(content=message.content, source="user")
        response = await self._delegate.on_messages([text_message], ctx.cancellation_token)
        return Message(content=response.chat_message.content)
    
class Player2Agent(RoutedAgent):
    def __init__(self, name: str) -> None:
        super().__init__(name)
        model_client = OpenAIChatCompletionClient(model="gpt-4o-mini")
        self._delegate = AssistantAgent(name, model_client=model_client, tools=[autogen_serper], reflect_on_tool_use=True)

    @message_handler
    async def handle_my_message_type(self, message: Message, ctx: MessageContext) -> Message:
        text_message = TextMessage(content=message.content, source="user")
        response = await self._delegate.on_messages([text_message], ctx.cancellation_token)
        return Message(content=response.chat_message.content)
    
class Judge(RoutedAgent):
    def __init__(self, name: str) -> None:
        super().__init__(name)
        model_client = OpenAIChatCompletionClient(model="gpt-4o-mini")
        self._delegate = AssistantAgent(name, model_client=model_client)
        
    @message_handler
    async def handle_my_message_type(self, message: Message, ctx: MessageContext) -> Message:
        message1 = Message(content=instruction1)
        message2 = Message(content=instruction2)
        inner_1 = AgentId("player1", "default")
        inner_2 = AgentId("player2", "default")
        response1 = await self.send_message(message1, inner_1)
        response2 = await self.send_message(message2, inner_2)
        result = f"## Pros of AutoGen:\n{response1.content}\n\n## Cons of AutoGen:\n{response2.content}\n\n"
        judgement = f"{judge}\n{result}Respond with your decision and brief explanation"
        message = TextMessage(content=judgement, source="user")
        response = await self._delegate.on_messages([message], ctx.cancellation_token)
        return Message(content=result + "\n\n## Decision:\n\n" + response.chat_message.content)


from autogen_ext.runtimes.grpc import GrpcWorkerAgentRuntime

if ALL_IN_ONE_WORKER:

    worker = GrpcWorkerAgentRuntime(host_address="localhost:50051")
    await worker.start()

    await Player1Agent.register(worker, "player1", lambda: Player1Agent("player1"))
    await Player2Agent.register(worker, "player2", lambda: Player2Agent("player2"))
    await Judge.register(worker, "judge", lambda: Judge("judge"))

    agent_id = AgentId("judge", "default")

else:

    worker1 = GrpcWorkerAgentRuntime(host_address="localhost:50051")
    await worker1.start()
    await Player1Agent.register(worker1, "player1", lambda: Player1Agent("player1"))

    worker2 = GrpcWorkerAgentRuntime(host_address="localhost:50051")
    await worker2.start()
    await Player2Agent.register(worker2, "player2", lambda: Player2Agent("player2"))

    worker = GrpcWorkerAgentRuntime(host_address="localhost:50051")
    await worker.start()
    await Judge.register(worker, "judge", lambda: Judge("judge"))
    agent_id = AgentId("judge", "default")




response = await worker.send_message(Message(content="Go!"), agent_id)

display(Markdown(response.content))

await worker.stop()
if not ALL_IN_ONE_WORKER:
    await worker1.stop()
    await worker2.stop()

await host.stop()

What you should see. After "Go!" the two researchers search the web and return reasons for and against; the judge prints a Markdown document with "Pros of AutoGen", "Cons of AutoGen" and a "Decision" section. In the instructor's runs — in both layouts — the recommendation was to proceed with AutoGen. You may see harmless warnings about threads or gRPC during start-up; they did not stop the run.
Common mistakes.
  • No host running. Start the GrpcWorkerAgentRuntimeHost before any worker, or the workers have nothing to connect to.
  • Port already in use. If 50051 is taken (an earlier run you did not stop), the host fails to start. Stop the old one or pick another port.
  • Not awaiting worker start. GrpcWorkerAgentRuntime must be started with await worker.start(); the host uses a plain host.start(). Mixing these up is a common slip.
  • Forgetting the Serper key. The research agents search the web; without SERPER_API_KEY they cannot gather pros and cons.
  • Leaving runtimes running. Stop all workers and the host at the end, especially in the three-worker layout, or the next run clashes on the port.

In TypeScript

The distributed runtime, the gRPC host and worker, and the whole Core API are Python (with a separate .NET implementation). There is no JavaScript version, so none of this appears in the Week 5 React demo, which is only a chat-style UI. If you want distributed agents, you write them in Python.

Recap
  • The distributed runtime has two parts: a host (GrpcWorkerAgentRuntimeHost) that connects workers and routes messages, and workers (GrpcWorkerAgentRuntime) that register and run agents.
  • gRPC carries calls across process (and machine, and language) boundaries, so a remote send_message looks exactly like a local one.
  • The example has two research agents (pros and cons, with web search) and a judge that decides — the same referee pattern as Day 3.
  • The ALL_IN_ONE_WORKER flag runs the same agents in one worker or across three; the agent classes never change.
  • Local versus distributed is a deployment choice. Your RoutedAgent code plugs into either runtime unchanged.
  • Microsoft calls the distributed runtime experimental; treat it as an exciting preview, not production.
Honesty note. The distributed gRPC runtime is shown exactly as in the course and was not re-run live for this guide: it calls gpt-4o-mini, reaches the Serper web API, and is labelled experimental by Microsoft. What we verified locally against Ollama is the AgentChat conversational examples and a single-machine Core message-passing example. The distributed pieces here are presented faithfully but not independently reproduced.
