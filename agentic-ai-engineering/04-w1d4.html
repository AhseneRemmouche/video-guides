Week 1 · Day 4 — Tools, Resources and Structured Outputs

Give a model tools and resources, get structured (typed) output, put a Gradio chat UI on it, and build a multi-LLM pipeline where one model evaluates another.

Companion to Ed Donner's course · uv setup · Python (+ TypeScript/React where it fits) · code from the course repo

Day 4 is where the week stops feeling like an exercise and starts feeling like a product. We build a small web chatbot that answers as you: it reads a short profile about a real person, drops that profile into the model's instructions, and wraps the whole thing in a chat window anyone can type into. Along the way the instructor explains two different ways to make a model smarter — giving it information (resources) and giving it the power to act (tools) — and shows a clean trick for getting reliable, machine-readable answers back from a model (structured outputs).

This is the groundwork for Day 5. Tomorrow the same chatbot grows real tools and a phone alert and becomes the deployable “career agent” or digital twin. Today we lay the foundation: a profile, a persona, a chat UI, and a quality check.

What the instructor covers first

Before touching the lab, the instructor walks through three ideas. It is worth slowing down on each one, because the rest of the course keeps returning to them.

The framework landscape

There are many agentic AI frameworks, and they sit at different levels of complexity. At the simplest level is no framework at all — you just call the model APIs directly, exactly as we have done so far. Anthropic's “Building Effective Agents” post argues this is often the best choice: the APIs are simple, and you get to see everything that happens. Next up are lightweight frameworks (OpenAI Agents SDK, CrewAI), and above them the heavier ones (LangGraph, AutoGen) that trade a steeper learning curve for more power. Week 1 deliberately uses no framework so you understand the internals. The later weeks tour the others.

Resources: more context in the prompt

A resource is nothing fancier than extra information you paste into the prompt so the model can answer better. If you were building an airline support bot, you might paste in the ticket prices; the model then refers to them while replying. The clever version of this — fetching only the relevant context for each question — is a whole field called RAG (retrieval-augmented generation). Today's lab uses the plain version: we read a person's profile and paste all of it into the instructions.

New to “context”? What it means here

A language model has no memory of you and no access to your files. The only thing it knows for a given reply is the text you send it in that request. “Giving it context” literally means including the facts in that text. If a fact is not in the prompt, the model can only guess. So reading a PDF and pasting its words into the prompt is how the model comes to “know” about the person.

Tools: the power to act

A tool is when you give a model the ability to do something — run a database query, send a message, switch on a light. It sounds magical, but the instructor is careful to demystify it: under the hood you simply tell the model, in the prompt, which actions exist and ask it to reply in JSON saying which one it wants. Your code reads that reply, runs the action if asked, and calls the model a second time with the result. “At the end of the day it's JSON and if-statements.” Note the honest twist: today's lab does not actually use a tool yet — tools arrive on Day 5. Today we use resources instead, which sets everything up.

Resources today, tools tomorrow. The instructor spends time explaining tools, then says plainly: “we're not going to do a tool today.” Keep the mental model of tools (JSON plus an if-statement) parked — Day 5 turns it into working code.

The lab: a chatbot that acts like you

The lab lives in the repo at 1_foundations/3_lab3.py (the fourth notebook in the me-powered series). The plan is short:

  1. Put a profile in a folder called me: a linkedin.pdf (a PDF export of a LinkedIn profile or a résumé) and a summary.txt (a couple of sentences about the person, plus a fun fact).
  2. Read both files into text.
  3. Build a system prompt that tells the model to act as that person, with the profile pasted in as context.
  4. Write a small chat function and hand it to Gradio to get an instant web chat UI.
  5. Then make it smarter: add a second model that evaluates each reply, and rerun the reply if it fails — using structured outputs and a Pydantic schema.
Download your own LinkedIn PDF. In LinkedIn, open your profile, click the More (…) menu and choose Save to PDF. Drop the file in me/linkedin.pdf and write two or three sentences about yourself in me/summary.txt. The chatbot will then answer as you.

Reading a PDF for context

New to PDFs in code? Why we need a reader library

A PDF is not plain text — it stores positioned glyphs, fonts and layout, so you cannot just open() it and read sentences. A reader library walks the file and pulls the words back out for you. The lab uses pypdf, a popular pure-Python PDF reader. You install libraries like this from PyPI (the Python Package Index at pypi.org). The instructor's tip: if you ever need to learn a library quickly, ask ChatGPT or Claude for a short guide.

System prompt as a persona

New to system vs user prompts? The difference

Until now the lab sent a single user message. A chat request can actually carry two kinds of instruction. The system prompt sets the overall job, tone and rules — here, “you are acting as this person, be professional, say so if you don't know.” The user prompt is the actual question a visitor types. Separating them keeps the persona stable no matter what the visitor asks. The profile text is pasted into the system prompt, so the persona and the facts travel together.

A chat UI with Gradio

New to Gradio? What it does

Gradio is a Python library that builds a web user interface from a plain function — no HTML, CSS or front-end code required. For a chatbot you use ChatInterface: you give it a function that takes the new message and the history of the conversation and returns the next reply, and Gradio renders a full chat window, runs a small local web server, and calls your function every time the visitor sends a message.

Structured outputs and Pydantic

New to structured outputs? Why not just read the text

Normally a model replies with free-form text, which is awkward for code to act on. A structured output forces the reply into a shape you define — here an object with a boolean is_acceptable and a string feedback. You describe that shape with a Pydantic class (in Python) or a Zod schema (in TypeScript), pass it to the API, and the library parses the model's JSON back into that object for you. The instructor points out this is the close cousin of tool calling: both are really “make the model answer in JSON that matches a schema.”

// Day 3 (Lab 3) - the evaluator-optimizer pattern (structured outputs).
// TS port of 3_lab3.py. One model answers "as the person"; a second model
// evaluates that answer against a strict schema (is_acceptable + feedback).
// If it fails, we rerun the answer with the feedback folded into the prompt.
import "dotenv/config";
import OpenAI from "openai";
import { z } from "zod";
import { zodResponseFormat } from "openai/helpers/zod";

if (!process.env.OPENAI_API_KEY) {
  console.log("OPENAI_API_KEY not set - add it to your .env (see .env.example).");
  process.exit(0);
}

const openai = new OpenAI();

// The evaluator talks through the same client, just pointed at Gemini if a
// GOOGLE_API_KEY is present; otherwise it falls back to OpenAI.
const evaluatorClient = process.env.GOOGLE_API_KEY
  ? new OpenAI({
      apiKey: process.env.GOOGLE_API_KEY,
      baseURL: "https://generativelanguage.googleapis.com/v1beta/openai/",
    })
  : openai;
const evaluatorModel = process.env.GOOGLE_API_KEY ? "gemini-2.0-flash" : "gpt-4o-mini";

const name = "Ed Donner";

// Short stand-in for the summary.txt + linkedin.pdf the notebook loads.
const summary =
  "Ed Donner is a technologist and entrepreneur. He co-founded the AI startup Nebula.io, " +
  "building LLMs that help people discover their potential, and previously founded and sold " +
  "the AI startup untapt. He loves teaching people to build with LLMs and agents.";

const systemPrompt =
  `You are acting as ${name}. You are answering questions on ${name}'s website, ` +
  `particularly questions related to ${name}'s career, background, skills and experience. ` +
  `Your responsibility is to represent ${name} for interactions on the website as faithfully as possible. ` +
  `You are given a summary of ${name}'s background which you can use to answer questions. ` +
  "Be professional and engaging, as if talking to a potential client or future employer. " +
  "If you don't know the answer, say so." +
  `\n\n## Summary:\n${summary}\n\n` +
  `With this context, please chat with the user, always staying in character as ${name}.`;

// The structured-output schema. The evaluator MUST return exactly this shape.
const Evaluation = z.object({
  is_acceptable: z.boolean(),
  feedback: z.string(),
});
type Evaluation = z.infer<typeof Evaluation>;

const evaluatorSystemPrompt =
  `You are an evaluator that decides whether a response to a question is acceptable. ` +
  `You are provided with a conversation between a User and an Agent. Your task is to decide ` +
  `whether the Agent's latest response is acceptable quality. The Agent is playing the role of ` +
  `${name} and is representing ${name} on their website. The Agent has been instructed to be ` +
  `professional and engaging. The Agent has been given this context:\n\n## Summary:\n${summary}\n\n` +
  "With this context, please evaluate the latest response, replying with whether the response " +
  "is acceptable and your feedback.";

function evaluatorUserPrompt(reply: string, message: string, history: string): string {
  return (
    `Here's the conversation between the User and the Agent:\n\n${history}\n\n` +
    `Here's the latest message from the User:\n\n${message}\n\n` +
    `Here's the latest response from the Agent:\n\n${reply}\n\n` +
    "Please evaluate the response, replying with whether it is acceptable and your feedback."
  );
}

async function evaluate(reply: string, message: string, history: string): Promise<Evaluation> {
  const response = await evaluatorClient.chat.completions.parse({
    model: evaluatorModel,
    messages: [
      { role: "system", content: evaluatorSystemPrompt },
      { role: "user", content: evaluatorUserPrompt(reply, message, history) },
    ],
    response_format: zodResponseFormat(Evaluation, "evaluation"),
  });
  return response.choices[0]?.message.parsed ?? { is_acceptable: true, feedback: "" };
}

async function rerun(reply: string, message: string, feedback: string): Promise<string> {
  const updatedSystemPrompt =
    systemPrompt +
    "\n\n## Previous answer rejected\nYou just tried to reply, but the quality control rejected your reply\n" +
    `## Your attempted answer:\n${reply}\n\n` +
    `## Reason for rejection:\n${feedback}\n\n`;
  const response = await openai.chat.completions.create({
    model: "gpt-4o-mini",
    messages: [
      { role: "system", content: updatedSystemPrompt },
      { role: "user", content: message },
    ],
  });
  return response.choices[0]?.message.content ?? "";
}

async function chat(message: string): Promise<string> {
  const response = await openai.chat.completions.create({
    model: "gpt-4o-mini",
    messages: [
      { role: "system", content: systemPrompt },
      { role: "user", content: message },
    ],
  });
  let reply = response.choices[0]?.message.content ?? "";

  const evaluation = await evaluate(reply, message, "");
  if (evaluation.is_acceptable) {
    console.log("Passed evaluation - returning reply");
  } else {
    console.log("Failed evaluation - retrying");
    console.log(evaluation.feedback);
    reply = await rerun(reply, message, evaluation.feedback);
  }
  return reply;
}

async function main() {
  const message = "Do you hold a patent?";
  console.log("User:", message, "\n");
  console.log("Reply:\n", await chat(message));
}

main().catch((err) => {
  console.error(err);
  process.exit(1);
});

TypeScript note. The persona, evaluator and rerun logic port one to one; the two things that do not are the PDF reader (pypdf has no direct Node twin, so the profile is an inlined string) and the Gradio chat UI (the Node file prints to the console; the real browser chat is the React app you meet on Day 5). Structured outputs swap Pydantic for Zod + zodResponseFormat.
What you should see. Running the first launch() opens a local web page (a URL like http://127.0.0.1:7860) with a chat box. Ask “What is your greatest accomplishment?” and you get a confident, first-person answer drawn from the profile — the bot talks as the person. After adding the evaluator, the terminal prints Passed evaluation - returning reply for good answers, and Failed evaluation - retrying when the deliberately-broken Pig Latin reply is caught and rewritten.
Common mistakes.
  • Gradio not installed. import gradio as gr fails with ModuleNotFoundError: No module named 'gradio'. Make sure your environment is synced (uv sync) and that the notebook is using the project's .venv kernel.
  • Profile too long. A huge PDF can slow things down or hit the model's context limit. If replies get truncated or error, trim summary.txt or keep only the useful pages of the PDF before pasting the text in.
  • Wrong folder. PdfReader("me/linkedin.pdf") is relative; if the me folder is not beside where you run the code you get a FileNotFoundError.
  • History errors with some providers. As the notebook warns, providers like Groq may reject the extra fields Gradio adds to history; cleaning it with a list comprehension at the top of chat() fixes it. OpenAI does not mind.
Recap
  • A resource is just extra context pasted into the prompt; a tool is the power to act. Today used resources; Day 5 adds tools.
  • We read a profile (linkedin.pdf via pypdf, plus summary.txt) and built a system prompt that makes the model answer as that person.
  • Gradio ChatInterface turns one chat function into a full web chat UI, served from your own Python process.
  • Structured outputs with a Pydantic (or Zod) schema let a second model return a clean is_acceptable + feedback object, which drives an evaluator-optimiser loop that reruns weak replies.
  • The TypeScript port keeps the same logic but inlines the profile and prints to the console; there is no pypdf or Gradio in Node.
