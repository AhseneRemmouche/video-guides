By the end you will have made your very first call to an LLM, seen the messages format that every chat model expects, and chained two calls together into a tiny “plan, then act” workflow — your first taste of agentic AI.

From here on “we are rolling up our sleeves and coding agents ourselves.”

New to this? What “agentic AI” even means

An LLM (large language model) is a program that predicts text: you give it some words, it gives you likely next words back. On its own it does one thing — answer once. Agentic AI is what you get when your own code wraps an LLM in a bigger process: you make several calls, feed one answer into the next, let the model make small choices, and maybe give it tools to act in the world. Today we take the very first step of that idea — two calls where the first call’s output becomes the second call’s input. The instructor calls this “a baby step towards agentic AI”, and that is exactly right.

Setting up your environment with uv

The course uses uv to build its Python environment, and Cursor (an editor built on VS Code) as the place to run everything. uv is a fast, modern tool that installs the right version of Python and all the project’s packages into a private folder called .venv, so the project never clashes with anything else on your machine. The instructor is emphatic that this is not Anaconda/conda — it is simpler and much faster (he mentions environments that took an hour in Anaconda build in two or three minutes with uv).

New to uv? What it is and why the course uses it

When you write Python you almost always use packages other people wrote (here, the OpenAI client). Those packages have versions, and different projects need different versions, so you keep each project’s packages in an isolated environment. uv is the tool that creates that isolated environment and fills it with exactly the versions this project pins. You run uv sync once and it reads the project’s pyproject.toml, uv.lock and .python-version files, downloads the right Python, and builds a .venv folder. After that you run scripts with uv run python ... and they automatically use that environment.

Here is the Day 1 setup, the same five steps the instructor walks through (there is a separate PC video and a Mac/Linux video; the steps are the same).

  1. Install uv. On Windows, open PowerShell and run the install command from Astral (uv’s maker). On Mac or Linux, use the shell installer. Then close and reopen the terminal so uv is on your path, and check it with uv --version. 
    powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
    curl -LsSf https://astral.sh/uv/install.sh | sh
  2. Clone the course repo. Move into a projects folder in your home directory, then clone Ed Donner’s agents repository. The folder it creates (agents) is your project root — the place every later command runs from. 
    git clone https://github.com/ed-donner/agents.git
cd agents
  3. Build the environment. From inside the agents folder run uv sync. uv installs a dedicated Python 3.12 and every package the project needs, creating the .venv folder. This takes a few minutes the first time. 
    uv sync
  4. Open the project in Cursor / VS Code and pick the kernel. Open the agents folder, install the Python and Jupyter extensions if you do not have them, then open 1_foundations/1_lab1.ipynb. Click Select Kernel at the top right and choose the .venv (Python 3.12.x) option. This tells the notebook to run inside the environment uv just built; picking the wrong kernel is the single most common Day 1 mistake.
  5. Add your API keys in a .env file. Right-click in the project root, create a new file named exactly .env (starts with a dot), and add your key. The name must be exact and there are no quotes or spaces around the value. 
    OPENAI_API_KEY=sk-proj-...your-real-key...

    If you do not want to pay for OpenAI, the course also works with DeepSeek, Google Gemini (free tier), or Ollama running models locally for free. Add whichever key you use (e.g. DEEPSEEK_API_KEY=...); Ollama needs no key at all.

New to API keys and .env files?

An API key is a long secret string that proves to a service (here, the OpenAI API) that a request is really from your paid account. You must never paste it into your source code or commit it to Git, because anyone who sees it can spend your money. The usual solution is a dotenv file: a plain file called .env that holds lines like NAME=value. A small library reads that file and loads each line as an environment variable — a value your program can read from its surroundings rather than from its own text. The .env file stays on your machine and is ignored by Git.

Common mistakes
  • Wrong kernel. If the notebook runs on some other Python instead of .venv, imports like from openai import OpenAI fail with an ImportError even though the setup worked. Re-open the lab and click Select Kernel → .venv (Python 3.12.x).
  • Missing or mistyped key. load_dotenv returning False almost always means you forgot to save the .env file, or it is not in the project root, or the file is not named exactly .env. The variable name must be exactly OPENAI_API_KEY — not OPENAI_KEY or OPEN_API_KEY.
  • Mangled key. Do not paste the key through a word processor; some apps silently turn hyphens into “nicer” long dashes and the key stops working. Paste it straight into .env.

// Day 1 (Lab 1) - your first LLM call, then a two-step plan -> act workflow.
// TS port of 1_lab1.py. Load the key, confirm it, make a simple call, then
// chain two calls: the model proposes a hard question (plan) and answers it (act).
import "dotenv/config";
import OpenAI from "openai";

const apiKey = process.env.OPENAI_API_KEY;

// The equivalent of the notebook's "does the key exist?" sanity check.
if (!apiKey) {
  console.log("OPENAI_API_KEY not set - add it to your .env (see .env.example).");
  process.exit(0);
}
console.log(`OpenAI API Key exists and begins ${apiKey.slice(0, 8)}`);

// new OpenAI() reads OPENAI_API_KEY from the environment automatically.
const openai = new OpenAI();

async function main() {
  // A first, trivial call - "the hello world" of LLM engineering.
  const first = await openai.chat.completions.create({
    model: "gpt-4.1-nano",
    messages: [{ role: "user", content: "What is 2+2?" }],
  });
  console.log("\n2+2 =", first.choices[0]?.message.content);

  // --- Step 1: PLAN -----------------------------------------------------------
  // Ask a stronger model to invent a hard IQ-style question for us.
  const planPrompt =
    "Please propose a hard, challenging question to assess someone's IQ. " +
    "Respond only with the question.";
  const planResponse = await openai.chat.completions.create({
    model: "gpt-4.1-mini",
    messages: [{ role: "user", content: planPrompt }],
  });
  const question = planResponse.choices[0]?.message.content ?? "";
  console.log("\nProposed question:\n", question);

  // --- Step 2: ACT ------------------------------------------------------------
  // Feed that question straight back in as the next prompt - this hand-off of
  // one call's output into the next is the core of a chained workflow.
  const actResponse = await openai.chat.completions.create({
    model: "gpt-4.1-mini",
    messages: [{ role: "user", content: question }],
  });
  const answer = actResponse.choices[0]?.message.content ?? "";
  console.log("\nAnswer:\n", answer);
}

main().catch((err) => {
  console.error(err);
  process.exit(1);
});

The file ends with an exercise scaffold (around line 92 onward) where response = is deliberately left blank for you to complete: ask the model to pick a business area, then a pain point, then an agentic solution — three chained calls, the same pattern applied to something commercial.

In TypeScript the key handling is slightly different. Instead of a load_dotenv() call you write import "dotenv/config"; at the very top — importing that module is the act of loading .env, so it must come before you read any variable. You then read the key straight off process.env, Node’s object of environment variables. Everything else mirrors the Python almost exactly, except the API calls are awaited inside an async function because network calls in Node are asynchronous.

The messages format and prompt roles

Every chat model takes the same shape of input: a list of messages, where each message has a role and some content. OpenAI invented this format and it is now used almost everywhere. Today’s lab only ever sends one user prompt at a time, but two more roles matter and you will meet them on the next days.

New to roles? System vs user vs assistant

A system prompt (role system) sets the model’s standing instructions — who it is and how it should behave. A user message (role user) is what the person asks right now. An assistant message (role assistant) is what the model replied; when you keep a conversation going you append its replies back into the list so it remembers the context. In Lab 1 there is no system message at all — just a single user message each time — which is why the model answers with no special persona.

Plan, then act: your first workflow

The interesting part of Lab 1 is not one call — it is two calls wired together. Call one asks the model to invent a hard question (the plan). Call two feeds that exact question back in and asks the model to answer it (the act). The link between them is a single line that copies the first reply into the next request. The instructor calls this “orchestrating multiple calls to LLMs to solve a bigger problem” — a workflow pattern known as chaining.

Where the code actually runs

A point the instructor stresses: creating the client with OpenAI() does not put a giant model on your laptop. The client library is tiny. Your machine builds a messages list and sends it over HTTPS to OpenAI’s endpoint; the heavy work — inference, trillions of calculations — happens on OpenAI’s servers, and only the text reply comes back.

LLMs are non-deterministic

Run the lab twice and you get different questions and different answers, even though the prompt never changed. That is not a bug — it is non-determinism, a defining property of LLMs. The model picks each next token from a set of likely options with some randomness, so the same input can lead to different output. This is why you cannot test agentic code by checking for one exact string, and why the same workflow can feel creative one run and flat the next.

Recap
  • You set up the project with uv: install uv, git clone the repo, uv sync, select the .venv kernel, and put your key in a .env file.
  • A single LLM call is three parts: a client (OpenAI()), a messages list of {role, content}, and chat.completions.create(...); you read the reply from choices[0].message.content.
  • Messages carry roles — system, user, assistant. Lab 1 uses only a user message; system prompts come later.
  • Chaining two calls (plan a question, then act on it) is your first workflow and the first baby step toward agentic AI.
  • LLMs are non-deterministic: the same prompt can give different answers, so never test for one exact string.
  • The model runs in the cloud; the client library on your machine just sends and receives text.
