Week 3 · Day 4 — Running and Quantizing Open-Source Models

Load a model with AutoModelForCausalLM, shrink it with 4-bit quantization (bitsandbytes), generate text and stream the output, and watch the memory footprint.

So far this week you have used the high-level pipeline API and then the tokenizer. Today you drop down one more level to the model itself: you load a real transformer from the Hugging Face hub, run it to generate text, and watch the words stream out token by token. Along the way you meet the single most useful trick for running big open-source models on a small graphics card: 4-bit quantization.

The star of the lab is the lower-level model class AutoModelForCausalLM. It is the general class for loading any autoregressive (causal) large language model — a model that reads the tokens so far and predicts the next one. The instructor runs three models (Llama 3.1, Microsoft's Phi-3, and Google's Gemma 2) and leaves two more (Qwen2 and Mistral) as exercises. The same few lines of code load and run all of them.

What quantization is and why it matters

A model's weights are the billions of numbers learned during training. Normally each weight is a 32-bit floating-point number — four bytes each. An 8-billion-parameter model at full precision would therefore want roughly 32 GB of memory just to sit in the GPU, which is more than most affordable cards have. Quantization reduces the precision of those numbers so the model takes far less memory, loads faster, and runs faster.

The surprising part, and the instructor flags it as surprising, is how little accuracy you lose. Going from 32-bit down to 8-bit, and even all the way down to 4 bits (half a byte), hurts quality only a little — a trade worth making because it lets a big model fit on a small GPU. This same technique returns later in the course inside QLoRA (the "Q" stands for quantization) when you fine-tune.

New to "quantization"? What it is and why it matters

Think of a weight as a very precise decimal, like 0.4718265. Quantization rounds it to something coarser, like 0.47, so it needs fewer bits to store. Do that to every weight and the whole model shrinks dramatically. The rounding adds a small error to each number, but across billions of weights those errors mostly wash out, so the model still answers well. The payoff is concrete: a model that would not fit in your GPU at full precision suddenly does.

The tools: bitsandbytes, the model class, and the streamer

New to "bitsandbytes" and "nf4"?

bitsandbytes is a library that works hand in hand with Hugging Face transformers to do the quantization for you. You describe the quantization you want in a BitsAndBytesConfig object and pass it when you load the model. The key options: load_in_4bit=True (use 4 bits), bnb_4bit_quant_type="nf4" (the normalized-float 4-bit format, which is more accurate than plain 4-bit), bnb_4bit_use_double_quant=True (quantize the quantization constants too, saving a little more memory), and bnb_4bit_compute_dtype=torch.bfloat16 (do the math in a fast 16-bit float). You can also set load_in_8bit=True instead, to try 8 bits.

New to "AutoModelForCausalLM"?

It is the general class for creating any causal (also called autoregressive) LLM — one that takes the tokens so far and predicts the next token. You build one with AutoModelForCausalLM.from_pretrained(name, ...), exactly mirroring how AutoTokenizer.from_pretrained(name) builds the matching tokenizer. The first time you load a model, it downloads the weights from the hub into a cache on the machine (on Colab, a temporary disk that is wiped when the session disconnects) and loads them into GPU memory. Under the hood the model is a stack of PyTorch layers: an embedding layer, attention and MLP blocks, an activation function, layer norms, and a final linear head. Printing the model shows that architecture.

New to "TextStreamer" and the memory footprint?

TextStreamer prints each token as the model produces it, so you watch the answer appear instead of waiting for the whole thing. It needs the tokenizer, because tokens must be turned back into readable text as they arrive. You pass it to model.generate(..., streamer=streamer). Separately, model.get_memory_footprint() returns how many bytes the loaded model occupies; dividing by 1e9 gives gigabytes. For Llama 3.1 8B at 4-bit that is about 5.5 GB — a handy way to confirm quantization worked.

The code

This one file sets up the 4-bit config, loads Llama 3.1 and inspects it, then wraps the whole thing in a reusable function that also streams the output for Phi-3 and Gemma 2.

# Reconstructed to match the course's Google Colab notebook for this day.
# Standard HuggingFace code; runs on a GPU (e.g. Colab T4). Not executed here (no GPU).
#
# Week 3 - Day 4: the model class - loading a real transformer and running generate().
# Covers:
#   - quantization: load the weights at 4-bit precision (bitsandbytes) so a big model
#     fits a small GPU and loads/runs faster, with only a modest accuracy cost.
#   - AutoModelForCausalLM: the general class for an autoregressive (causal) LLM.
#   - model.generate: produce new tokens; TextStreamer streams them as they arrive.
#   - model.get_memory_footprint(): see how much GPU memory the model occupies.
#
# Colab setup (run once in a cell):
#   !pip install -q transformers accelerate bitsandbytes
#   from huggingface_hub import login
#   from google.colab import userdata
#   login(userdata.get("HF_TOKEN"), add_to_git_credential=True)
# Llama 3.1 is gated: accept Meta's terms on its model page first.

import gc

import torch
from transformers import (
    AutoModelForCausalLM,
    AutoTokenizer,
    BitsAndBytesConfig,
    TextStreamer,
)

# Current model ids on the HuggingFace hub.
LLAMA = "meta-llama/Meta-Llama-3.1-8B-Instruct"
PHI3 = "microsoft/Phi-3-mini-4k-instruct"
GEMMA2 = "google/gemma-2-2b-it"
QWEN2 = "Qwen/Qwen2-7B-Instruct"  # exercise: repeat the run with Qwen2

messages = [
    {"role": "system", "content": "You are a helpful assistant"},
    {"role": "user", "content": "Tell a light-hearted joke for a room of Data Scientists"},
]

# 4-bit quantization config. load_in_4bit halves-the-halving twice with double quant;
# nf4 is the normalized-float 4-bit type; bfloat16 is used for the compute dtype.
quant_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_use_double_quant=True,
    bnb_4bit_compute_dtype=torch.bfloat16,
    bnb_4bit_quant_type="nf4",
)


def load_llama_and_inspect():
    # Build the tokenizer, and set the pad token to the end-of-sentence token
    # (standard boilerplate that silences a warning).
    tokenizer = AutoTokenizer.from_pretrained(LLAMA)
    tokenizer.pad_token = tokenizer.eos_token
    inputs = tokenizer.apply_chat_template(
        messages, return_tensors="pt", add_generation_prompt=True
    ).to("cuda")

    # AutoModelForCausalLM.from_pretrained is to models what AutoTokenizer is to
    # tokenizers. device_map="auto" uses the GPU; quantization_config loads it at 4-bit.
    model = AutoModelForCausalLM.from_pretrained(
        LLAMA, device_map="auto", quantization_config=quant_config
    )

    # How much GPU memory the quantized model occupies (~5.5 GB for Llama 3.1 8B at 4-bit).
    print(f"Memory footprint: {model.get_memory_footprint() / 1e9:,.1f} GB")

    # Printing the model shows the actual PyTorch layers: embedding, attention and MLP
    # blocks, activation, layer norms, and the final linear head.
    print(model)

    # Generate up to 80 new tokens, then decode the single output sequence to text.
    outputs = model.generate(inputs, max_new_tokens=80)
    print(tokenizer.decode(outputs[0]))

    # Clean up so the next model has GPU memory to work with.
    del model, inputs, tokenizer, outputs
    gc.collect()
    torch.cuda.empty_cache()


def generate(model_name, messages):
    # Everything above, packaged into a reusable function that also streams output.
    tokenizer = AutoTokenizer.from_pretrained(model_name)
    tokenizer.pad_token = tokenizer.eos_token
    inputs = tokenizer.apply_chat_template(
        messages, return_tensors="pt", add_generation_prompt=True
    ).to("cuda")

    # TextStreamer prints tokens as the model produces them; it needs the tokenizer
    # to turn those tokens back into text.
    streamer = TextStreamer(tokenizer)

    model = AutoModelForCausalLM.from_pretrained(
        model_name, device_map="auto", quantization_config=quant_config
    )
    model.generate(inputs, max_new_tokens=80, streamer=streamer)

    del model, inputs, tokenizer, streamer
    gc.collect()
    torch.cuda.empty_cache()


def main():
    # Llama 3.1: load, inspect the architecture + memory footprint, generate.
    load_llama_and_inspect()

    # Phi-3 via the reusable streaming function.
    generate(PHI3, messages)

    # Gemma 2 does not support a system prompt, so pass the user message only.
    generate(GEMMA2, [{"role": "user", "content": messages[1]["content"]}])

    # Exercise: generate(QWEN2, messages)


if __name__ == "__main__":
    main()

What you should see. The footprint line prints roughly Memory footprint: 5.5 GB, then a long description of the model's PyTorch layers, then a short joke — for Llama 3.1, something like "Why did the logistic regression model go to therapy?". With the streaming function, Phi-3 and Gemma 2 print their answers word by word. (In the video Phi-3 declines to tell a joke and rambles instead — a fair reminder that small models vary.)
Common mistakes. Out of memory without quantization: loading an 8B model at full precision needs around 32 GB and will fail on a small GPU — always pass the quantization_config. Running out between models: if you skip the cleanup (del + gc.collect() + empty_cache()), the next load crashes; if it does, use Runtime → Restart session and rerun the imports. Gated model: Llama 3.1 requires you to accept Meta's licence on its model page and to be signed in with your Hugging Face token, or the download is refused. Wrong device: inputs must be on the same device as the model (.to("cuda")), or generate errors.

In TypeScript

This lab is Python-only, and honestly so. The 4-bit bitsandbytes quantization and the GPU-based AutoModelForCausalLM run only in Python on a CUDA GPU — there is no JavaScript equivalent of bitsandbytes.

In TypeScript you have two honest options. First, transformers.js (the @huggingface/transformers package) can run small open-source models directly in Node or the browser — for example a small text-generation model — using quantized ONNX weights rather than bitsandbytes. That is great for tiny models but will not load an 8-billion-parameter Llama on a laptop. Second, for anything that size you call a hosted inference API (such as Hugging Face's) from your TypeScript code and let the provider's GPUs do the work. So the pattern carries over — load, prompt, generate, stream — but the heavy 4-bit-on-your-own-GPU part stays in Python.

Recap
  • AutoModelForCausalLM.from_pretrained(name, ...) loads a real causal LLM, mirroring how AutoTokenizer loads its tokenizer.
  • Quantization lowers each weight's precision; a BitsAndBytesConfig with load_in_4bit, nf4, double-quant, and bfloat16 compute fits an 8B model into about 5.5 GB.
  • Run the model with model.generate(inputs, max_new_tokens=80); decode the output ids back to text, or pass a TextStreamer to see it word by word.
  • model.get_memory_footprint() confirms how much GPU memory the loaded model uses.
  • Clean up (del, gc.collect(), torch.cuda.empty_cache()) between models, and remember Llama 3.1 is gated and the whole lab needs a Colab GPU.
  • In TypeScript, transformers.js runs small models in Node/the browser, but big models and 4-bit bitsandbytes stay in Python or behind a hosted inference API.
