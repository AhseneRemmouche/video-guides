Week 6 · Day 5 — Fine-tuning with OpenAI

Prepare JSONL training data, launch a fine-tuning job with the OpenAI API, track training and validation loss with Weights & Biases, and evaluate the result - including when fine-tuning does not help.

Companion to Ed Donner's course · uv setup · Python + TypeScript/React · code verified against the repo

This is the day the whole week has been building towards. All of Week 6 you curated a huge dataset, built traditional machine-learning baselines, and measured how a plain frontier model does at guessing product prices. Today you finally do the thing the week promised: you take a frontier model from OpenAI and train it a little more on your own data. The instructor is candid up front that this session "may also disappoint" — and that honesty is the real lesson of the day.

In the world of big language models, fine-tuning is just another word for training. Nobody trains one of these models from scratch (that would cost hundreds of millions of dollars); instead you take a model that is already trained — a pre-trained model — and do a bit more training so it gets better at one specific task. That idea of building on an existing model is called transfer learning. OpenAI lets you do this through its fine-tuning API, and the whole job follows three steps.

The concepts the instructor introduces

A handful of ideas carry the day. Training data in messages format: fine-tuning needs examples, and OpenAI wants them as conversations — the same list-of-messages shape you already use for a normal chat call, but with the right answer included as the assistant's reply. JSONL: the file format OpenAI expects, which is subtly different from ordinary JSON. A fine-tuning job: you upload the files, kick off a job, and OpenAI trains the model on its own servers while you watch. Training and validation loss: the numbers that tell you whether training is going well, best viewed as live charts in Weights & Biases. And finally, the sober one: when fine-tuning a frontier model helps — and when it does not.

New to JSONL (the training-data format)? What it is and why it matters

Ordinary JSON wraps a collection in a list: [ {...}, {...}, {...} ] — one big object with commas between items and square brackets around the outside. JSONL ("JSON Lines") is different: it is a plain-text file where each line is its own complete JSON object, standing on its own with no surrounding list and no commas between lines. Reading the whole file as one JSON document would fail, because it is not one document — it is many, one per line.

For fine-tuning, every line is one training example. Each line has a single key, messages, whose value is the familiar list of role/content dictionaries — a complete little conversation the model should learn to produce. So the file is just "one example per line", and that is the format the upload step requires.

New to a fine-tuning job? What it is and why it matters

A fine-tuning job is a piece of work you hand to OpenAI. You do not train the model on your own computer — you upload your training file, call one API to create a job, and OpenAI runs the training on its servers. The job moves through stages: it validates your file, queues, then trains through your examples one step at a time, runs some safety checks, and finally produces a brand-new model with its own id. You get an email when it finishes. From then on you call that new model by its id exactly like any other model — the only thing that changes is the name you pass in.

New to training loss and validation loss? What they are and why they matter

Training loss is a single number that measures how wrong the model's answers are on the examples it is currently learning from. Lower is better, so during a good training run the number drifts down. Charts that point downward look alarming, but here down is exactly what you want.

Validation loss is the same measurement, but on a separate set of examples the model is not training on — a held-out check. Why bother? Because a model can get better and better at memorising its training examples while getting worse at anything new. That is overfitting, and watching only training loss hides it. If training loss keeps falling but validation loss starts rising, you are overfitting.

An epoch is one complete pass through all your training data. Today's run uses just one epoch: because every example is seen only once and never repeated, the data always stays "new", so the training-loss number is about as informative as the validation-loss number here.

New to Weights & Biases? What it is and why it matters

Weights & Biases (often written wandb) is a free-for-personal-use website that draws live charts of a training run. Reading loss numbers scrolling past in a log is painful; Weights & Biases turns them into the "wiggly lines" the instructor loves, so you can watch training happen and spot trends at a glance. It is completely optional. You create a free account, copy an API key from your settings, and paste that key into the Integrations section of the OpenAI dashboard (or pass it to the job). From then on, OpenAI streams the run's numbers to your Weights & Biases project automatically.

The full program

Here is the complete notebook code, from loading the data through the final evaluation. Read it once end to end, then use the line-by-line tables underneath to understand each key part.

# imports

import os
import re
import json
from dotenv import load_dotenv
from huggingface_hub import login
from openai import OpenAI
from pricer.items  import Item
from pricer.evaluator import evaluate

# environment

LITE_MODE = False

load_dotenv(override=True)
hf_token = os.environ['HF_TOKEN']
login(hf_token, add_to_git_credential=True)

username = "ed-donner"
dataset = f"{username}/items_lite" if LITE_MODE else f"{username}/items_full"

train, val, test = Item.from_hub(dataset)

print(f"Loaded {len(train):,} training items, {len(val):,} validation items, {len(test):,} test items")

openai = OpenAI()

# OpenAI recommends fine-tuning with populations of 50-100 examples
# But as our examples are very small, I'm suggesting we go with 100 examples (and 1 epoch)


fine_tune_train = train[:100]
fine_tune_validation = val[:50]

len(fine_tune_train)

def messages_for(item):
    message = f"Estimate the price of this product. Respond with the price, no explanation\n\n{item.summary}"
    return [
        {"role": "user", "content": message},
        {"role": "assistant", "content": f"${item.price:.2f}"}
    ]

messages_for(fine_tune_train[0])

# Convert the items into a list of json objects - a "jsonl" string
# Each row represents a message in the form:
# {"messages" : [{"role": "system", "content": "You estimate prices...


def make_jsonl(items):
    result = ""
    for item in items:
        messages = messages_for(item)
        messages_str = json.dumps(messages)
        result += '{"messages": ' + messages_str +'}\n'
    return result.strip()

print(make_jsonl(train[:3]))

# Convert the items into jsonl and write them to a file

def write_jsonl(items, filename):
    with open(filename, "w") as f:
        jsonl = make_jsonl(items)
        f.write(jsonl)

write_jsonl(fine_tune_train, "jsonl/fine_tune_train.jsonl")

write_jsonl(fine_tune_validation, "jsonl/fine_tune_validation.jsonl")

with open("jsonl/fine_tune_train.jsonl", "rb") as f:
    train_file = openai.files.create(file=f, purpose="fine-tune")

train_file

with open("jsonl/fine_tune_validation.jsonl", "rb") as f:
    validation_file = openai.files.create(file=f, purpose="fine-tune")

validation_file

openai.fine_tuning.jobs.create(
    training_file=train_file.id,
    validation_file=validation_file.id,
    model="gpt-4.1-nano-2025-04-14",
    seed=42,
    hyperparameters={"n_epochs": 1, "batch_size": 1},
    suffix="pricer"
)

openai.fine_tuning.jobs.list(limit=1)

job_id = openai.fine_tuning.jobs.list(limit=1).data[0].id

job_id

openai.fine_tuning.jobs.retrieve(job_id)

openai.fine_tuning.jobs.list_events(fine_tuning_job_id=job_id, limit=10).data

fine_tuned_model_name = openai.fine_tuning.jobs.retrieve(job_id).fine_tuned_model

fine_tuned_model_name

# The prompt

def test_messages_for(item):
    message = f"Estimate the price of this product. Respond with the price, no explanation\n\n{item.summary}"
    return [
        {"role": "user", "content": message},
    ]

# Try this out

test_messages_for(test[0])

# The inference function


def gpt_4__1_nano_fine_tuned(item):
    response = openai.chat.completions.create(
        model=fine_tuned_model_name,
        messages=test_messages_for(item),
        max_tokens=7
    )
    return response.choices[0].message.content

print(test[0].price)
print(gpt_4__1_nano_fine_tuned(test[0]))

evaluate(gpt_4__1_nano_fine_tuned, test)

What you should see

After jobs.create, list_events first shows a couple of events like "created fine-tuning job" and "validating training file". A few minutes later the same call shows training steps — "step 0", "step 1", … up to the last one — each with a training loss number. In Weights & Biases the same numbers appear as a live chart. A good run shows a sharp drop in the first few steps (the model quickly learns the obvious stuff, like the dollar sign and the decimal point), then a gentler downward trend with plenty of wiggle. After ten to fifteen minutes the status becomes "succeeded" and an email tells you the new model's name.

Common mistakes and pitfalls
  • Not enough data. A handful of examples teaches the model almost nothing. OpenAI suggests at least 50–100; more usually helps, especially if it is well curated.
  • Overfitting. Too many epochs on too little data makes the model memorise your examples and do worse on anything new. Watch validation loss, not just training loss, and this run deliberately uses a single epoch.
  • Forgetting binary mode. Opening the upload file with "r" instead of "rb" breaks the upload — OpenAI wants the raw bytes.
  • Expecting a frontier model to leap ahead. This is the big one. Fine-tuning a huge, already-excellent model on a task it already handles well may not beat the base model — and it can even do slightly worse. See the honest result below.

The honest result: it did not beat the base model

When the fine-tuned model was scored across the 250 test items, it came out slightly worse than the plain model. On the week's leaderboard (average dollar error, where lower is better), the instructor's numbers were: a constant guess 146, traditional machine learning 139, random forest 97, a human 127, plain gpt-4o-mini 80, plain gpt-4o 76 — and the fine-tuned model 91. Fine-tuning moved the needle in the wrong direction on the metric that mattered.

Why? A frontier model like the GPT-4 family already has trillions of parameters and has read an enormous slice of the world's text. It already understood the task and always returned a clean, parseable price. Handing it 100 — or even a few thousand — extra examples is unlikely to shift that deep world knowledge. There is even a risk called catastrophic forgetting, where extra training erodes some of what the model learned during pre-training. OpenAI's own guidance is blunt: get as much as you can from the prompt first, because for a frontier model good prompting usually takes you most of the way.

So when does fine-tuning a frontier model help?

OpenAI lists a handful of good reasons to fine-tune a frontier model — and notice they are all about things prompting struggles with, not about raw knowledge:

  • Style or tone — e.g. consistently sarcastic, or always on-brand.
  • Reliable formatting — producing a specific structure every single time.
  • Following a hard prompt the model keeps getting slightly wrong.
  • Handling edge cases — rare situations the base model fumbles.
  • A new skill that is genuinely hard to describe in words.

Our pricing task was none of these: the format was already perfect and the task was easy to state in a prompt. That is exactly why fine-tuning did not help here. Fine-tuning shines later in the course on open-source models, which start far smaller and have much more room to improve.

Video vs repo
  • Model name. The video fine-tunes gpt-4o-mini; the repo file shown here uses gpt-4.1-nano-2025-04-14. Both are small, cheap frontier models, and model ids get retired over time — treat it as a value to swap for whatever is current.

Recap
  • Fine-tuning means doing a little more training on an already pre-trained model (transfer learning); you never train a frontier model from scratch.
  • OpenAI's recipe is three steps: prepare data, run a job, evaluate — then tweak and repeat.
  • Training data goes in JSONL: one JSON object per line, each with a messages conversation whose assistant turn is the correct answer.
  • You upload the files with files.create(..., purpose="fine-tune") (binary mode), start the job with fine_tuning.jobs.create(...), and watch it with list_events.
  • Watch training loss and validation loss — ideally in Weights & Biases — and keep to one epoch here to avoid overfitting.
  • Calling the fine-tuned model is a normal chat call with one change: pass its model id.
  • Honest result: fine-tuning the frontier model did not beat the base model (91 vs 80), because prompting already solved the task well. Fine-tuning a frontier model helps most for tone, strict formatting, edge cases, and skills that are hard to put in a prompt.
  • The fine-tuning was not run here (it costs money and time); the React demo type-checks and builds but was not run live.
