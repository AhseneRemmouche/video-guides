Glossary

Every technical term in this guide, explained for beginners.

Models & providers

LLM (large language model)
A program trained on huge amounts of text that predicts the next piece of text, one token at a time. In this course it is the thing you send a prompt to and get an answer back from, such as GPT-4o or Llama.
Frontier model
One of the biggest, most capable models from a major lab, usually paid and reached over the internet through an API. GPT-4o, Claude, and Gemini are the frontier models used in this course.
Open-source model
A model whose weights are published so you can download and run it yourself, often for free and offline. Llama and DeepSeek are the open-source models used here, typically run through Ollama.
GPT
OpenAI's family of language models; the name is short for "Generative Pre-trained Transformer". The course calls OpenAI's models through the OpenAI API.
GPT-4o
A specific OpenAI model used in the videos, along with the cheaper gpt-4o-mini. Treat the model name as a value you can swap: labs retire models over time, so the current repo already uses a newer one and you may need to change the id to a model that still exists.
Reasoning model
A model that is built to "think" through steps before giving a final answer, which helps with harder problems but costs more and is slower. The course mentions OpenAI's o1-preview as an example on Day 3.
Claude
Anthropic's family of language models, such as Claude 3.5 Sonnet. The course highlights its careful, aligned style and its Artifacts feature, and uses an ANTHROPIC_API_KEY to call it.
Gemini
Google's family of language models. It is optional in Week 1; the video era used an id like gemini-2.0-flash and it is called with a GOOGLE_API_KEY.
Cohere
Another company that makes language models, mentioned on Day 3 when comparing providers. It is not required for the Week 1 labs.
Perplexity
An AI answer service that combines web search with a language model, so its replies cite live sources. It is shown on Day 3 as an example of search plus an LLM.
Ollama
A free tool that downloads and runs open-source models on your own computer. You install it from ollama.com; its server runs at http://localhost:11434 (visiting that address says "Ollama is running") and it also exposes an OpenAI-compatible endpoint at http://localhost:11434/v1.
Llama
Meta's family of open-source models. In this course you pull one with ollama pull llama3.2 (or llama3.2:1b on a small machine) and run it locally for free.
DeepSeek
Another family of open-source models. The repo optionally pulls a small distilled version, deepseek-r1:1.5b, through Ollama on Day 2.
Hugging Face
A popular website and community for sharing open-source models, datasets, and tools. It is referenced as the main hub where open models live.

API & code

OpenAI API
The internet service you send requests to in order to use OpenAI's models from your own code. You reach it with the openai Python library and an API key.
API key
A secret password-like string that proves a request is yours and lets the provider bill you. OpenAI keys start with sk-proj-; keep keys in your .env file and never commit them.
Endpoint
A web address that a service listens on for requests. For example, Ollama's OpenAI-compatible endpoint is http://localhost:11434/v1.
Client library
A package you install so your code can talk to a service without building the raw web requests by hand. Here it is the openai library, used as from openai import OpenAI.
Chat completions
The main way you call a chat model: you send a list of messages and get the model's reply. In code this is openai.chat.completions.create(model=..., messages=[...]), and the text comes back as response.choices[0].message.content.
OpenAI-compatible
Describes a different service that accepts the same request shape as OpenAI, so the same openai library works against it. You just point the client at its address, as in OpenAI(base_url="http://localhost:11434/v1", api_key="ollama") for Ollama.
Message
One entry in the conversation you send to the model, written as a small dictionary with a role and content. The whole chat is a list of these messages.
Role
The label on a message that says who is speaking: system sets the rules, user is you, and assistant is the model's own past replies.
System prompt
The system message that sets the model's job, tone, and rules before the conversation starts. In the Day 1 lab it tells the model to summarize a web page and to ignore navigation text.
User prompt
The user message that carries your actual question or request for this turn. In the summarizer it holds the page's title and text.
Response format
An option you add to a chat call to control the shape of the reply. Setting response_format={"type":"json_object"} asks the model to return valid JSON.
JSON mode
The result of asking for a JSON response format: the model is constrained to reply with well-formed JSON, which is easier for your code to parse. Day 5 uses it to get a clean list of links.
Streaming
Receiving the reply piece by piece as it is generated, instead of waiting for the whole thing. You turn it on with stream=True and read each part as chunk.choices[0].delta.content or "".
Inference
Running a trained model to get an answer, as opposed to training it. Every time you call the API and the model produces text, that is inference.
Temperature
A setting from about 0 to 2 that controls how random the model's wording is: low values give steady, predictable text and higher values give more varied, creative text.
Markdown
A simple text format where symbols like # and * mark headings and lists. Models often reply in Markdown, and the notebooks render it nicely with from IPython.display import Markdown, display.

How LLMs work

Token
The small chunk of text a model actually reads and writes, usually a word or part of a word including its leading space. As a rough guide one token is about four characters of English, and models are priced per million tokens.
Tokenizer
The tool that splits text into tokens and turns them into numbers the model can process, and back again. Different model families use different tokenizers.
tiktoken
OpenAI's tokenizer library, used in the Day 4 demo. You load the GPT-4o family rules with tiktoken.get_encoding("o200k_base"), then .encode(text) gives a list of token ids and .decode([id]) turns one back into text. For example "banoffee" splits into two tokens, ' ban' and 'offee'.
Context window
The maximum number of tokens a model can take in at once, counting both your input and its output. If a conversation grows past it, the oldest parts no longer fit.
Parameters
The internal numbers a model learned during training; their count (often billions) is a rough measure of a model's size and capability. "Parameters" and "weights" refer to the same numbers.
Weights
Another name for a model's learned parameters. Downloading an open-source model means downloading its weights so you can run it yourself.
Transformer
The model design introduced in Google's 2017 paper "Attention is All You Need" that made modern LLMs possible. The "T" in GPT stands for Transformer.
Neural network
A learning system loosely inspired by the brain, built from layers of simple units connected by weights. A transformer is a particular kind of large neural network.
Training
The one-time, expensive process of adjusting a model's weights by showing it enormous amounts of text until it predicts well. After training, using the model is called inference.
Stateless
Means the model remembers nothing between calls: every request starts fresh. The "memory" in a chat is really the whole conversation sent again each time, as the Day 4 memory demo shows.
Prompt
The text you give the model to act on. In chat calls it is split into the system prompt and the user prompt.
One-shot prompting
Giving the model a single worked example inside the prompt so it copies the pattern for your real request.
Multi-shot prompting
Giving the model several examples in the prompt so it learns the pattern more reliably before answering.

Tools & setup

Python
The programming language this course is written in. Week 1 uses Python 3.12.
Jupyter
A tool for running Python in a web browser, cell by cell, mixing code, output, and notes. The course runs notebooks in JupyterLab or inside the Cursor/VS Code editor.
Notebook
A document (a .ipynb file) made of cells you run one at a time, keeping results and notes together. Each Week 1 lab is a notebook.
Kernel
The background Python process that actually runs a notebook's cells. You must "Select the Kernel" and pick the course's Python (the project .venv) for each notebook.
uv
Astral's fast Python package and environment manager, and the only setup tool this course uses. uv sync reads pyproject.toml and uv.lock to create a .venv and install the exact pinned versions, and uv run <cmd> runs a command inside that environment. It replaces Anaconda/conda and pip/virtualenv here.
Environment variable
A named value that lives outside your code, in the operating system or in a .env file, so secrets are not written into your scripts. The API keys are read this way.
dotenv
A small library that loads the key=value lines from a .env file into environment variables. The code uses from dotenv import load_dotenv and then load_dotenv().
Terminal (command line)
A text window where you type commands instead of clicking, used to install packages, start Ollama, and launch Jupyter.
Web scraping
Fetching a web page with code and pulling out the parts you want, such as its text. The Day 1 lab scrapes a page so the model can summarize it.
BeautifulSoup
A Python library that parses HTML so you can read a page's title and text. The lab uses it as from bs4 import BeautifulSoup and strips out script, style, img, and input tags.
requests
A Python library for downloading web pages over HTTP. It fetches the raw HTML that BeautifulSoup then parses.
JSON
A simple, widely used text format for structured data, built from key-value objects and lists. The course uses it to pass a list of links in and out of the model on Day 5.
Summarization
Asking a model to boil longer text down to its key points. It is the goal of the Day 1 lab, which scrapes a web page and returns a short summary.

TypeScript & React

TypeScript
A version of JavaScript that adds type labels, so the editor and compiler can catch mistakes before the code runs. This guide shows each lab in Python and in TypeScript side by side.
Node.js
The program that runs JavaScript and TypeScript outside a web browser, such as on your own computer or a server. The TypeScript labs and the API server both run on Node.js.
npm
Node's package manager, the tool that downloads and installs JavaScript libraries listed in a project's package.json. It is the TypeScript side's counterpart to Python's installer.
React
A popular JavaScript library for building user interfaces out of reusable pieces. The guide includes a small React app that shows the Day 1 summarizer and Day 5 brochure in the browser.
JSX
The HTML-like syntax you write inside React code to describe what the screen should look like. A tag such as <button> written in a React file is JSX, which is turned into real page elements.
Component
A single reusable piece of a React interface, written as a function that returns some JSX. A page is built by combining components, each in charge of one part of the screen.
Vite
The build and development tool for the React app. It serves the app with instant reloads while you edit, and bundles it into optimized files for release with vite build.
Hono
A small, fast web framework used to write the API server that sits between the React app and the language model. The browser code calls this server instead of calling the model directly.
tsx
A command-line runner that executes a .ts TypeScript file directly, without a separate compile step. The TypeScript labs are run with it, as in tsx day1_summarize.ts.
REST API
A set of plain web addresses that a program calls over HTTP to get or send data. The React app talks to the Hono server through a small REST API rather than reaching the model itself.
node-html-parser
The TypeScript library that reads a web page's HTML and pulls out its title and text. It plays the same role on the TypeScript side that BeautifulSoup plays in the Python labs.
gpt-tokenizer
A pure-JavaScript tokenizer used in the TypeScript token demo, in place of Python's tiktoken. It uses the same o200k_base rules and produces the same token ids, which was verified against the Python output.

Week 2 — chatbots, tools, multimodal

anthropic
The company that makes Claude, and the name of its official Python SDK (from anthropic import Anthropic). Its API is shaped differently from OpenAI's: the system prompt is a top-level system= argument, you call client.messages.create, max_tokens is required, and the reply comes back as a list of content blocks rather than a single string.
Gradio
A Python library that turns a plain function into a shareable web page with just a few lines of code, so you can try your model in a browser without writing any front-end. Week 2 uses it to build quick user interfaces around the labs.
gr.Interface
The basic Gradio building block: you hand it a function plus a list of inputs and outputs, and it builds a simple form-style web page. It is the fastest way to wrap a single function in a UI.
gr.ChatInterface
The Gradio building block made for chatbots. You give it a function that takes a message and the past conversation, and it draws a full chat window with a message box and history for you.
Chatbot
A program that holds a back-and-forth conversation with a user, remembering what was said earlier in the chat. In Week 2 you build one by sending the model a system prompt plus the running list of messages each turn.
Conversation history
The list of past messages (user turns and the model's replies) that you resend with every new request. Because the model is stateless, this resent history is what gives a chatbot its "memory".
Tool
A function in your own code that you let the model use, described to it ahead of time so it knows what the function does and what inputs it needs. In the Day 4 lab the tool is get_ticket_price, which looks up the price of a flight to a city.
Function calling
The feature where the model, instead of answering directly, asks you to run one of your tools with specific arguments. You run the function, hand the result back, and the model uses it to finish its reply. It is how an LLM reaches real data and actions.
Tool call
One round trip of function calling: the model replies that it wants a tool run (with the arguments it chose), your code runs it and sends the result back as a new message, and the model then continues. The Day 4 loop keeps doing this until the model has a final answer.
JSON schema
A structured description, written as JSON, of a tool's name, what it does, and the inputs it accepts (their names, types, and which are required). You pass this schema so the model knows how to call the tool correctly.
Agent
An LLM that can take actions in the world through tools, rather than only producing text. The Day 5 lab combines a chat model with image and audio tools to make a simple multimodal agent.
Multimodal
Working with more than just text, such as images and audio as well. Week 2 ends by adding picture generation and speech so the assistant can both show and say things.
DALL-E
OpenAI's image-generation model, used in the video era as dall-e-3. You give it a text description and it returns a picture. (The current repo uses a newer image model, so treat the model id as a value you may need to update.)
Image generation
Creating a picture from a text description by calling an image model. In the Day 5 lab this is done with client.images.generate(...), which returns the generated image.
Text-to-speech (TTS)
Turning written text into spoken audio by calling a speech model. The Day 5 lab uses client.audio.speech.create(...) (the video era model tts-1) so the assistant can talk.
Adversarial conversation
A setup where two models talk to each other, often playing opposing roles so one pushes against the other. The Day 1 lab runs an adversarial chat between two different models to show how their styles differ.

Week 3 — open-source and HuggingFace

Hugging Face Hub
The website that hosts open-source models, datasets, and spaces (small demo apps), all in one place. Week 3 downloads its models and tokenizers from the Hub, using a Hugging Face token to reach gated ones such as the Llama models.
Google Colab
A free cloud service that runs Jupyter notebooks in your browser, including a free GPU so you can run bigger models than your own machine could. Week 3's code runs in Colab, and the Hugging Face token is stored there as a Colab secret.
GPU
The graphics chip that performs the many parallel calculations a model needs, which makes running and training models far faster than on an ordinary CPU. Week 3 uses a free Colab GPU such as an NVIDIA T4.
pipeline
The transformers library's one-line, high-level helper for a whole task: you name the task and a model and call it like a function. For example pipe = pipeline("sentiment-analysis") then pipe("I love this") handles tokenizing, running the model, and reading the result for you.
transformers library
Hugging Face's main Python library for loading and running open-source models and their tokenizers. It provides both the quick pipeline helper and the lower-level AutoTokenizer and AutoModel loaders used later in the week.
AutoTokenizer
A transformers loader that fetches the correct tokenizer for a model by name, so you do not have to know which tokenizer class it uses. You call AutoTokenizer.from_pretrained("meta-llama/Meta-Llama-3.1-8B-Instruct") to get the tokenizer that matches the model.
Chat template
The exact text layout a particular chat model expects a conversation to be formatted in, including its special markers for each turn. Instead of writing that format by hand, you pass your list of messages to the tokenizer's apply_chat_template(...), which builds the correct prompt string for that model.
AutoModel
A transformers loader that fetches the model's weights by name; for text generation you use the AutoModelForCausalLM variant. You call AutoModelForCausalLM.from_pretrained(...) to load a model you can then run on the GPU.
Quantization
Storing a model's weights using fewer bits each (for example 4-bit instead of the usual 16-bit) so the model needs much less memory and can fit on a smaller GPU. The trade-off is a small loss of precision in the answers.
bitsandbytes
The library that performs the quantization, letting transformers load a model in 4-bit or 8-bit. In Day 4 it is configured with a BitsAndBytesConfig and passed to from_pretrained so the large model fits in the free GPU's memory.
Whisper
OpenAI's open-source speech-to-text model, which turns spoken audio into written text. The Day 5 meeting-minutes lab uses Whisper to transcribe a recording before an LLM summarizes it.
transformers.js
The JavaScript port of the transformers library, published as @huggingface/transformers, that runs small models directly in Node or the browser with no Python. The TypeScript side of Week 3 uses it to run pipeline-style tasks client-side.
Dataset
A ready-made collection of data for training or evaluating models, shared on the Hugging Face Hub alongside the models. You can browse and download datasets the same way you download a model.
Inference API
Calling a model that Hugging Face already hosts for you over the internet (HTTP), instead of downloading its weights and running them yourself. It is the quick, hosted alternative to loading a model locally.
diffusers
Hugging Face's library for image-generation (diffusion) models, the picture-making counterpart to the text-focused transformers library. It loads and runs models that create images from a text prompt.

Week 4 — choosing models and code generation

Scaling law
A rule of thumb for how much a model improves as you add more parameters and more training data. The Chinchilla scaling law found that for a fixed compute budget, size and training-data amount should be balanced rather than just making the model bigger.
Benchmark
A standard test set of questions or tasks used to score and compare models on the same footing. Common benchmarks measure things like reasoning, math, or coding skill.
Leaderboard
A public ranking of models ordered by their scores on one or more benchmarks. Week 4 looks at the HuggingFace Open LLM Leaderboard and several others to shortlist models.
Chatbot Arena
The LMSYS website where people compare two anonymous models side by side and vote for the better answer. Because the models are hidden until after the vote, the ranking reflects blind human preference rather than a fixed test.
Elo rating
The chess-style scoring system the Chatbot Arena uses to rank models from head-to-head votes. A model's number goes up when it beats others and down when it loses, so stronger models settle at higher ratings.
Open-source vs closed
The trade-off between open-weight models you can download and run yourself and proprietary (closed) models you can only reach through a paid API. Open models give control, privacy, and lower cost; closed frontier models often lead on raw capability and ease of use.
Code generation
Having an LLM write or convert code for you rather than prose. The Week 4 project uses it to rewrite slow Python as fast C++.
Inference endpoint
A hosted model that you call over HTTP instead of downloading and running its weights yourself. Week 4 uses HuggingFace Inference Endpoints to run an open-source code model in the cloud.
CodeQwen
An open-source model specialised for writing code, used in Week 4 as the open alternative to the frontier models. It is called through a HuggingFace Inference Endpoint.
C++
A fast, compiled programming language the Week 4 optimizer targets. The project asks an LLM to translate slow Python into C++ so the same work runs far quicker.
Evaluation metric
How you decide whether a model is doing well. Week 4 splits these into model-centric metrics (like benchmark scores or speed) and business-centric metrics (like money saved or users helped).
Overfitting
When a model looks great on its test questions but does poorly on real, unseen inputs because it effectively memorised the test. High benchmark scores can hide this, so a leaderboard win does not always mean real-world quality.
Data leakage
When the answers to a benchmark accidentally end up in a model's training data, so it has effectively seen the test beforehand. This (also called contamination) inflates scores and makes a model look better than it really is.

Week 5 — RAG and LangChain

RAG (Retrieval-Augmented Generation)
A pattern where, instead of relying only on what a model already knows, you first fetch text relevant to the question, add it to the prompt, and then let the model generate the answer. It lets an LLM answer from your own documents and stay up to date.
Retrieval
The first step of RAG: finding the pieces of your documents that are most relevant to the user's question. It is what turns a plain LLM into one that can look things up.
Augmentation
The second step of RAG: taking the retrieved pieces of text and adding them into the prompt so the model can use them when it answers. The model then generates its reply from that enriched prompt.
Vector embedding
A piece of text turned into a list of numbers (a vector) that captures its meaning, so that texts with similar meanings end up with similar numbers. Embeddings are what make search by meaning possible.
Vector database
A store built to hold many vector embeddings and quickly find the ones closest to a query vector. Chroma and FAISS are two examples used in this course.
Chroma
An easy-to-use vector database that stores your embeddings and finds the closest matches at query time. It is one of the two vector stores shown on the Python side of Week 5.
FAISS
A fast vector-search library from Meta (Facebook AI Similarity Search) that can act as the vector store in a RAG pipeline. It is the alternative to Chroma compared in Week 5.
LangChain
A Python framework for building LLM applications by connecting steps such as loading documents, splitting them, embedding them, retrieving, and calling the model. Week 5 uses it to assemble the whole RAG pipeline.
LangChain.js
The JavaScript/TypeScript version of LangChain, used on the TypeScript side of this guide. It offers the same building blocks as the Python framework so you can build RAG in TypeScript.
Text splitter
A LangChain tool that breaks long documents into smaller pieces before they are embedded, since a whole document is usually too big to handle at once. Week 5 uses the RecursiveCharacterTextSplitter.
Chunk
One of the smaller pieces a document is split into. Each chunk is embedded and stored on its own, so retrieval can return just the relevant pieces rather than a whole document.
Chunk overlap
A small amount of text shared between one chunk and the next, so that a sentence or idea sitting on the boundary is not cut in half. The overlap helps keep each chunk understandable on its own.
Retriever
The component that takes a question, embeds it, and finds the most relevant chunks from the vector store to hand to the model. It is the part of the pipeline that actually does the retrieval step.
Cosine similarity
A common way to measure how close two vectors are by comparing the direction they point in rather than their length. A higher cosine similarity means two embeddings have more similar meaning.
t-SNE
A technique that projects high-dimensional vectors down to 2-D or 3-D so they can be drawn on a chart. Week 5 uses it to plot embeddings and see how related pieces of text cluster together.
Knowledge base
The collection of documents you want the model to be able to answer from. In RAG these documents are split, embedded, and stored so the retriever can search them.
Semantic search
Searching by meaning rather than by exact keywords, so a query finds relevant text even when it uses different words. It works by comparing vector embeddings instead of matching letters.
Conversation memory
Keeping track of earlier turns in a chat so that follow-up questions make sense and the conversation stays coherent. In the Week 5 RAG chain it lets the assistant remember what was already asked.

Week 6 — fine-tuning and ML baselines

Fine-tuning
Taking a model that is already trained and training it a bit more on your own examples so it specialises in your task. Week 6 fine-tunes a frontier model to estimate product prices.
Training data
The collection of examples a model learns from during training. Here each example pairs a product description with the price the model should learn to predict.
Dataset curation
The work of gathering, cleaning, and balancing your data before training, so the examples are high quality and not skewed. Day 1 scrubs the raw product data and builds a balanced set.
JSONL
JSON Lines: a text file with one JSON object per line, used for lists of examples. It is the format OpenAI's fine-tuning expects, so Day 5 writes the training examples out as JSONL.
Feature engineering
Turning raw data into numeric inputs (features) that a machine-learning model can actually use. For text, this often means converting the words into numbers before a model sees them.
Bag of words
A simple way to represent a piece of text as the counts of the words it contains, ignoring their order. It turns text into numbers that a basic model can learn from.
CountVectorizer
The scikit-learn tool that builds a bag-of-words representation: it scans the texts and produces a table of word counts. Day 3 uses CountVectorizer to prepare features for the baseline models.
Linear regression
A classic model that predicts a number by adding up weighted inputs, fitting a straight-line relationship. Day 3 uses it as one of the simple baselines for predicting price.
Random forest
A model that combines many decision trees and averages their answers, which usually predicts better than a single tree. It is one of the scikit-learn baselines in Day 3.
SVR (support vector regression)
A scikit-learn model that fits a regression using the support vector machine method. Day 3 tries it as another traditional baseline to beat.
Baseline model
A deliberately simple model whose score you treat as the bar to clear. If a fancy fine-tuned model cannot beat the baseline, it is not adding value.
Weights & Biases
An online tool for tracking training runs, recording settings and plotting metrics like loss over time. Day 5 connects the OpenAI fine-tuning job to it so you can watch the loss as training proceeds.
Training loss
A number that measures how wrong the model is on the training examples; training tries to push it down. On its own a falling training loss is not enough, because the model could just be memorising.
Validation loss
The same error measure but computed on held-out examples the model did not train on. It is the honest check: if training loss keeps dropping while validation loss rises, the model is overfitting.
Epoch
One full pass over the whole training dataset during training. Training usually runs for several epochs, and the loss is often reported once per epoch.
scikit-learn
Python's classic machine-learning library, offering ready-made models like linear regression, random forests, and SVR plus tools such as CountVectorizer. Day 3 uses it to build the traditional baselines.
pandas
Python's data-table library, which loads data into DataFrames (rows and columns) you can filter, clean, and summarise. Week 6 uses it to prepare and explore the product data.

Week 7 — QLoRA fine-tuning

LoRA (Low-Rank Adaptation)
A way to fine-tune a model cheaply: you freeze the original weights and train only a few small extra matrices that are added alongside them. Because those added matrices are tiny, training needs far less memory than retraining the whole model.
QLoRA
LoRA applied on top of a model that has been loaded in 4-bit quantized form. Quantizing the frozen base shrinks its memory use, so a very large model plus its small trainable adapters can fit on a single modest GPU.
PEFT
Hugging Face's Parameter-Efficient Fine-Tuning library. It provides the tools to add and train only a small set of extra parameters (such as LoRA adapters) instead of all of a model's weights.
Adapter
The small set of LoRA weights that are trained and added to the frozen base model. After training you save just this adapter, which is tiny compared with the full model.
Low-rank
The mathematical trick behind LoRA: a big weight change is approximated by multiplying two much smaller matrices. Keeping the "rank" small is what makes the trained adapters so compact.
TRL
Hugging Face's library for training and fine-tuning language models (its name is short for Transformer Reinforcement Learning). Week 7 uses it to run the supervised fine-tuning step.
SFTTrainer
TRL's supervised fine-tuning trainer. You hand it the base model, the training dataset, and the training settings, and it runs the fine-tuning loop for you.
Base model
The original pre-trained model before you fine-tune it. In Week 7 it is the open-source Llama model that the LoRA adapter is trained on top of.
Hyperparameter
A training setting you choose yourself before training starts, rather than a value the model learns. Examples include the learning rate, the number of epochs, and the batch size.
Learning rate
The hyperparameter that controls how big a step the training takes each time it adjusts the weights. Too high can make training unstable, while too low makes it learn very slowly.
Gradient accumulation
Adding up the gradients from several small mini-batches before updating the weights once, so training behaves as if it used one larger batch. It lets you train with a bigger effective batch size than would otherwise fit in GPU memory.
RMSLE
Root Mean Squared Log Error, a way of scoring how far predicted prices are from the real ones. Because it compares the logarithms of the values, it treats being off by a percentage similarly whether an item is cheap or expensive.

Week 8 — the autonomous agent system

Agentic AI
Systems where LLMs take actions and coordinate with each other to get work done, rather than only answering a single question. Week 8 builds one: several specialised agents that together hunt for good deals.
Structured output
Making a model return typed, schema-valid data (such as a specific object with named fields) instead of free-form text. This lets the rest of your code rely on the shape of what comes back.
Pydantic
The Python library used to define those typed schemas as classes, then validate that data matches them. The agent system uses it to describe the structured results each agent should produce.
Modal
A serverless platform for deploying code and models to the cloud so they run on demand. Week 8 deploys the fine-tuned pricer to Modal and calls it as a remote service.
Ensemble
Combining several models' predictions into one better answer. The pricing ensemble blends a frontier model, the fine-tuned model, and a RAG estimate to guess a price more reliably than any one alone.
Planning agent
The agent that coordinates the system: it decides what work to do and directs the other agents. It sits at the top of the deal-hunting workflow.
Scanner agent
The agent that finds candidate deals, for example by reading product feeds and picking out promising items. It passes what it finds on for pricing.
Messaging agent
The agent that sends alerts when a good deal is found, such as a push notification to your phone. It is the system's way of telling you something worth acting on.
Push notification
An alert sent straight to your phone or device, popping up without you having to check an app. The messaging agent uses one to flag a strong deal.
Serverless
Cloud compute that runs your code on demand without you managing any servers yourself; you just deploy the function and the platform runs it when called. Modal is the serverless platform used here.
Handoff
One agent passing its work to the next agent in the pipeline. Deals flow by handoff from the scanner to the pricing ensemble to the messaging agent.
Autonomous agent
An agent that runs on its own, making decisions without a human in the loop. The finished "Price is Right" system is autonomous: it scans, prices, and alerts by itself.
