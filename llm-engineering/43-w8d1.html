Week 8 · Day 1 — The Agent System and Structured Outputs

What an agentic system is, the architecture of the deal-hunting project, and structured outputs - making models return reliable, typed data your code can use.

Welcome to the final week. Everything you built over the last seven weeks now comes together into one ambitious project that Ed calls "The Price is Right". The goal: a program that sits in the background, watches the internet for deals, works out what each item is really worth, and sends you a push notification when it spots a genuine bargain. It runs on its own, with no human clicking buttons. That makes it an agentic AI system - several specialised pieces, some of them language models, working together toward a goal.

Second, the two ideas that make such a system trustworthy enough to run unattended: deploying a model as a reliable cloud service (with a platform called Modal), and getting a model to return structured output - clean, typed data your code can depend on - instead of a paragraph of free text you have to pick apart.

What is an agentic system?

Up to now you have mostly called a model once and read its answer. An agent is a step up: a component that is given a job and some tools, decides what to do, and does it - often by calling a model, sometimes by running plain Python. An agentic system is several such components working together. No single model does everything; instead each piece is small, specialised and good at one thing, and a coordinator passes work between them. Because the whole thing can keep running and act without you, it is an autonomous agent system.

New to agents? What makes something "agentic"

A plain script does exactly what you typed, in order. An agent is given a goal rather than a fixed recipe: "find the best deals", "estimate this price". It figures out the steps, usually by calling a language model to make judgements, and it can use tools (a web request, a database, another model). An agentic workflow chains several agents so the output of one becomes the input of the next. The payoff is that each agent stays simple and testable; the intelligence comes from how they are wired together. The risk is that if one agent hands over messy data, the next one chokes - which is exactly why the structured-output idea below matters so much.

Why reliability matters more for autonomous systems

When you are sitting at a notebook and a model returns something odd, you just read it and try again. An autonomous system has nobody watching. If the scanner agent returns a price as the words "about three hundred dollars" instead of the number 300, the next agent cannot compare it to anything and the whole chain breaks silently - or worse, pushes you a nonsense alert at 3am. Autonomy raises the bar: every handoff between agents has to be in a shape the receiving code can trust every single time. That is the real reason this week leans on deployed services and typed schemas rather than hand-parsing text.

Ed is explicit that there are really seven agents, not four. The ensemble agent is itself a small team: it calls three separate price-estimating agents and combines their guesses (that is what "ensemble" means - pooling several models). The diagram above hides those three to stay readable; you will meet them later in the week. Not every agent uses a language model - the scanner's RSS fetching and the messaging agent's HTTP call are ordinary Python. That mix is normal and healthy for an agentic system.

The plan for the week

The capstone is built one layer at a time. Here is where each day fits, so you can see why Day 1 is about deployment and reliable data rather than the finished app.

Deploying the first agent with Modal

Last week you fine-tuned a small, specialised pricing model. It only helps the system if other code can call it reliably. Modal (at modal.com - spelled "modal") is a serverless platform: you wrap a normal Python function, and Modal runs it on a cloud machine you describe in code (operating system, packages, GPU). You only pay for the seconds it actually runs. The clever part is how little changes: a function you would call locally becomes a cloud call by swapping .local() for .remote().

The notebook below walks through this in stages: a trivial hello function (to prove local vs remote), then a quantised Llama model on a GPU, then last week's fine-tuned pricer run as a temporary ("ephemeral") app, then deployed as a permanent service, and finally wrapped in the first real agent of the project - the Specialist Agent. Read it top to bottom; the line-by-line table underneath explains the parts that carry the new ideas.

Common mistakes.
  • Running .remote() before setting up Modal. The first time, you must run modal setup once (uncomment that line in the notebook); it opens a browser to authorise and stores your tokens for you.
  • Forgetting the Hugging Face token. The GPU examples read it from Modal secrets (set under HF_secret in the Modal dashboard). Without it, the model download fails on the cloud machine.
  • Expecting the first call to be fast. A cold service spends a couple of minutes downloading and loading the model. That is why pricer_service2 uses a class that keeps the model warm - the second call is quick.

Structured outputs: data your code can trust

The second foundation is the one that makes autonomy possible. When the scanner agent reads a web page full of deals, it must hand the next agent a list of deals, each with a clear numeric price. If the model replies with a chatty paragraph, your code has to guess where the price is - and guessing breaks. Structured output fixes this: you tell the model the exact shape you want, and it returns data in that shape, which your code can read directly.

New to structured output and JSON schema?

Normally a model returns a block of text. Structured output means you give the model a description of the exact fields you want - a JSON schema - and the model fills it in, returning JSON like {"price": 650, "url": "…"}. JSON is just a universal way to write nested data as text; a schema is the contract that says which keys must be present and what type each value is (a number, a string, a list). Because the reply matches the contract, your program can read each field by name instead of searching through prose. OpenAI supports this directly, so the model is strongly guided to obey the shape.

New to Pydantic and typed schemas?

Pydantic is a Python library for describing data as a class with typed fields, and it is the easiest way to express that schema. You write a class such as Deal with product_description: str, price: float and url: str, and Pydantic both generates the JSON schema for the model and checks the reply against it. If the model returns a price as text, or omits a field, Pydantic raises a clear error instead of letting bad data flow on. The OpenAI SDK ties the two together with chat.completions.parse(..., response_format=YourModel), which returns a ready-made Python object - typed, validated, done.

You will build this fully with the scanner agent later in the week, but here is the shape so the idea lands. First the schema, written as Pydantic classes (this mirrors the course's agents/deals.py; shown for illustration):

from pydantic import BaseModel

class Deal(BaseModel):
    product_description: str
    price: float
    url: str

class DealSelection(BaseModel):
    deals: list[Deal]

Then the model call that returns it, taken from this week's day-3 notebook (real code, real line numbers):

messages = [{"role": "system", "content": SYSTEM_PROMPT}, {"role": "user", "content": user_prompt}]

response = openai.chat.completions.parse(model=MODEL, messages=messages, response_format=DealSelection)
results = response.choices[0].message.parsed

for deal in results.deals:
    print(deal.product_description)
    print(deal.price)
    print(deal.url)

When structured output goes wrong. Two failure modes to watch for. First, the model not following the schema - returning almost-JSON with a comment, or a price as "around 650". Using .parse() with a Pydantic response_format (rather than hand-written JSON instructions) makes this rare and turns any remaining mismatch into a clear validation error you can catch. Second, brittle free-text parsing - the temptation to skip the schema and hunt for a number with string tricks. It works on your three test cases and fails the first time a deal is phrased "$299 off". In an autonomous system nobody is watching, so lean on the schema, not on parsing by hand.
What you should see. After deploying on Modal, calling agent.price("iPhone 10") returns a plain number (Ed's fine-tuned model priced his microphone at $133). After a structured-output call, results is a DealSelection object and results.deals is a list you can loop over, with deal.price already a number - no text parsing anywhere.
Recap
  • An agentic system is several specialised components - some language models, some plain Python - coordinated to pursue a goal on their own. This week's "Price is Right" uses seven such agents.
  • The high-level architecture: a Gradio UI, an agent framework with shared memory and logging, and a planning agent coordinating scanner, ensemble and messaging agents. Work flows as clean handoffs between them.
  • Modal is a serverless platform: wrap a Python function and run it in the cloud by swapping .local() for .remote(). Day 1 deploys last week's fine-tuned pricer and wraps it in the project's first agent, the Specialist Agent.
  • Structured output makes a model return typed data (via a Pydantic schema and chat.completions.parse) instead of free text, so each agent can trust the data it receives.
  • Reliability is the whole point: an autonomous system has nobody watching, so every handoff must have a known, fixed shape - deployed services and typed schemas rather than hand-parsed text.
