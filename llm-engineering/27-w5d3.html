Week 5 · Day 3 — Vector Stores and Visualizing Embeddings

Store embeddings in Chroma, then actually see them: project the high-dimensional vectors down to 2-D/3-D with t-SNE to watch similar documents cluster together.

Companion to Ed Donner's course · uv setup · Python + TypeScript/React · code verified against the repo

On Days 1 and 2 we turned our documents into chunks and then into vector embeddings — long lists of numbers that capture the meaning of each piece of text. Today we do two things with those numbers. First we store them in a vector database called Chroma, so they are saved on disk and ready to search. Then we visualize them: we flatten the high-dimensional vectors down to two or three dimensions with a technique called t-SNE and draw them as a coloured scatter plot. Seeing documents of the same kind land near each other is the moment embeddings stop feeling like magic and start feeling like meaning turned into geometry.

This is the session the instructor describes as “finally getting to play with vectors.” It is deliberately hands-on and visual — the whole point is to build intuition before we wire up a full question-answering pipeline on Day 4.

Honesty note. The code below is shown exactly as in the course notebook, normalised to the video’s models. It was not run live here (building the store calls the paid OpenAI embeddings API). The numbers quoted from the lesson — 123 chunks and 1,536 dimensions — are what the instructor sees on screen.

What a vector store is for

A vector is just a point in space. An embedding with 1,536 numbers is a point in 1,536-dimensional space, placed so that texts with similar meaning sit close together. A vector database is a store built to hold millions of these points and answer one question fast: which stored vectors are closest to this new one? That closeness search is what later powers semantic search and retrieval. Today we only build the store and look at it; the searching comes next.

New to vector databases and Chroma? What they are and why they matter

An ordinary database finds rows by exact matches: “give me the customer whose id is 42.” A vector database finds rows by nearness: “give me the chunks whose meaning is closest to this question.” It stores a vector next to each piece of text and can rank all of them by distance in milliseconds.

Chroma is a popular open-source vector database. The instructor notes that many regular databases (for example MongoDB) can now hold vectors too, but Chroma was built for this from the start and is very easy to use. In our project it saves everything to local files using SQLite, inside a folder we name vector_db. Deleting that folder resets the store.

New to dimensions and t-SNE? What “projecting down” means

We can picture points in 2-D (a sheet of paper) or 3-D (a room). We cannot picture 1,536-D at all. Dimensionality reduction is a family of techniques that squeeze many dimensions down to two or three while trying to keep the overall shape — points that were far apart stay far apart, points that were close stay close.

t-SNE (t-distributed Stochastic Neighbor Embedding) is the one used here. You tell it how many dimensions you want (n_components=2) and give it a random seed (random_state=42) so the picture is reproducible, then call fit_transform to get the reduced points. It is excellent for seeing clusters, but it is only a visualization — see the warning below.

Why visualize embeddings at all?

You never need a picture to run retrieval; the computer compares the full 1,536-D vectors directly. The picture is for you. When you watch chunks from the same folder gather into the same region — without ever telling the model which folder they came from — you understand, in one glance, that the embedding model really did capture meaning. That intuition makes every later design choice (chunk size, overlap, which store) easier to reason about.

The code

The whole lab fits in one file. It loads the knowledge base, chunks it, embeds each chunk, builds the Chroma store, then pulls every vector back out and plots it in 2-D and 3-D. The instructor’s big point: building the vector store is a single line of code — LangChain hides all the glue.

import os
import glob
import numpy as np
from dotenv import load_dotenv
from langchain_openai import OpenAIEmbeddings
from langchain_chroma import Chroma
from langchain_community.document_loaders import DirectoryLoader, TextLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from sklearn.manifold import TSNE
import plotly.graph_objects as go

MODEL = "gpt-4o-mini"
db_name = "vector_db"
load_dotenv(override=True)

# Load in everything in the knowledge base using LangChain's loaders

folders = glob.glob("knowledge-base/*")

documents = []
for folder in folders:
    doc_type = os.path.basename(folder)
    loader = DirectoryLoader(folder, glob="**/*.md", loader_cls=TextLoader, loader_kwargs={'encoding': 'utf-8'})
    folder_docs = loader.load()
    for doc in folder_docs:
        doc.metadata["doc_type"] = doc_type
        documents.append(doc)

# Divide into chunks using the RecursiveCharacterTextSplitter

text_splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200)
chunks = text_splitter.split_documents(documents)
print(f"Divided into {len(chunks)} chunks")

# Pick an embedding model that turns each chunk into a vector

embeddings = OpenAIEmbeddings(model="text-embedding-3-small")

# Delete the collection if it already exists, so we don't add vectors twice

if os.path.exists(db_name):
    Chroma(persist_directory=db_name, embedding_function=embeddings).delete_collection()

# Create the Chroma vector store from the chunks - one line does it all

vectorstore = Chroma.from_documents(documents=chunks, embedding=embeddings, persist_directory=db_name)
print(f"Vectorstore created with {vectorstore._collection.count()} documents")

# Let's investigate the vectors

collection = vectorstore._collection
count = collection.count()

sample_embedding = collection.get(limit=1, include=["embeddings"])["embeddings"][0]
dimensions = len(sample_embedding)
print(f"There are {count:,} vectors with {dimensions:,} dimensions in the vector store")

# Prework: pull every vector, its text and its metadata back out

result = collection.get(include=['embeddings', 'documents', 'metadatas'])
vectors = np.array(result['embeddings'])
documents = result['documents']
metadatas = result['metadatas']
doc_types = [metadata['doc_type'] for metadata in metadatas]
colors = [['blue', 'green', 'red', 'orange'][['products', 'employees', 'contracts', 'company'].index(t)] for t in doc_types]

# We humans find it easier to visualize things in 2D!
# Reduce the dimensionality of the vectors to 2D using t-SNE
# (t-distributed stochastic neighbor embedding)

tsne = TSNE(n_components=2, random_state=42)
reduced_vectors = tsne.fit_transform(vectors)

# Create the 2D scatter plot
fig = go.Figure(data=[go.Scatter(
    x=reduced_vectors[:, 0],
    y=reduced_vectors[:, 1],
    mode='markers',
    marker=dict(size=5, color=colors, opacity=0.8),
    text=[f"Type: {t}<br>Text: {d[:100]}..." for t, d in zip(doc_types, documents)],
    hoverinfo='text'
)])

fig.update_layout(title='2D Chroma Vector Store Visualization',
    scene=dict(xaxis_title='x', yaxis_title='y'),
    width=800,
    height=600,
    margin=dict(r=20, b=10, l=10, t=40)
)

fig.show()

# Let's try 3D!

tsne = TSNE(n_components=3, random_state=42)
reduced_vectors = tsne.fit_transform(vectors)

# Create the 3D scatter plot
fig = go.Figure(data=[go.Scatter3d(
    x=reduced_vectors[:, 0],
    y=reduced_vectors[:, 1],
    z=reduced_vectors[:, 2],
    mode='markers',
    marker=dict(size=5, color=colors, opacity=0.8),
    text=[f"Type: {t}<br>Text: {d[:100]}..." for t, d in zip(doc_types, documents)],
    hoverinfo='text'
)])

fig.update_layout(
    title='3D Chroma Vector Store Visualization',
    scene=dict(xaxis_title='x', yaxis_title='y', zaxis_title='z'),
    width=900,
    height=700,
    margin=dict(r=10, b=10, l=10, t=40)
)

fig.show()

What the plot shows

Each dot is one chunk. Its colour is its folder (its doc_type), and its position comes from t-SNE. The striking result: chunks from the same folder gather into the same region, even though we never told the embedding model which folder a chunk came from. The model placed them by meaning alone.

What you should see. In the terminal: Divided into 123 chunks, then Vectorstore created with 123 documents, then There are 123 vectors with 1,536 dimensions in the vector store. Then a browser tab opens with a scatter plot of 123 dots in four colours, with same-topic dots grouped into their own regions. Hovering a dot shows its type and the first 100 characters of that chunk. (These are the lesson’s numbers; we did not run it live.)
t-SNE is for your eyes, not for retrieval. The x and y axes carry no meaning — t-SNE only tries to keep near things near, so the layout, rotation and spacing can change with the random seed or settings. Never search or measure distances on the 2-D/3-D coordinates. Real retrieval always compares the full 1,536-dimensional vectors inside Chroma, which is what the next day builds. Also: if you re-run the build without the delete step (lines 41–42), you will get 246 vectors instead of 123.

In TypeScript

On Days 1 and 2 we saw ingest.ts, the LangChain.js data-prep script. That file already builds the equivalent of today’s vector store: after loading and splitting the documents it calls MemoryVectorStore.fromDocuments(docs, embeddings), which embeds every chunk and holds the vectors in memory. It is the same idea as Chroma.from_documents in Python — one call does the embedding and the storing — just with an in-memory store instead of Chroma’s on-disk SQLite files, so there are no native dependencies to install.

The visualization half of today has no direct browser equivalent here. Projecting vectors with t-SNE and drawing them with Plotly is a Python/matplotlib-style step that lives naturally in a Jupyter notebook; it is a one-off exploration to build intuition, not part of the running application. So there is no ingest.ts change to show for it — if you want to visualize the TypeScript store’s vectors, the practical route is to export them and plot them in Python exactly as above. The TypeScript project was type-checked and built; its embedding calls were not run live.

Video vs repo. The video builds the store with OpenAI embeddings (1,536 dimensions), which is what we show. The current repo offers a free local option too — a HuggingFace model (all-MiniLM-L6-v2) — and simply swaps the one embeddings = ... line; that model returns 384 dimensions instead of 1,536, so your printed dimension count will differ. The repo also uses model gpt-6-luna in place of the video’s gpt-4o-mini, though that only matters for the question-answering days, not for today’s embeddings.
Recap
  • A vector database like Chroma stores a vector next to each chunk and finds the nearest ones fast; Chroma.from_documents embeds and stores all 123 chunks in a single line.
  • collection.get(...) pulls the vectors, text and metadata back out; each vector here has 1,536 dimensions.
  • t-SNE projects those 1,536-D vectors down to 2-D (or 3-D) so Plotly can draw them; random_state=42 keeps the picture reproducible.
  • Colouring dots by folder shows same-topic chunks clustering on their own — proof the embeddings captured meaning, since the model never saw the folder labels.
  • The plot is for intuition only: its axes are meaningless and you must never retrieve from the 2-D coordinates — real search uses the full vectors, coming on Day 4.
  • In TypeScript, ingest.ts builds the store with MemoryVectorStore.fromDocuments; the t-SNE plot is a Python-only step.
