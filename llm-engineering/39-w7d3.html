The big idea of QLoRA is that you never touch the giant base model. You keep its billions of weights frozen (and squashed to 4-bit with quantization, which is the "Q"), and you train a tiny set of extra numbers bolted onto a few layers. Those extra numbers are the adapter. Training only the adapter is what makes it possible to fine-tune an 8-billion-parameter model on a single rented GPU.

Reconstructed, not run here. A real QLoRA run needs a GPU and hours (the instructor's full three-epoch run takes roughly a day on a top-end box). The code below is standard QLoRA / PEFT / TRL code reconstructed to match the Colab notebook; it was not executed on a GPU for this guide. The values (r=32, alpha=64, the target modules, the "Price is $" response template) are the ones the instructor uses on screen.

The LoRA configuration

LoRA ("Low-Rank Adaptation") is the trick that makes the adapter small. Instead of learning a full, dense change for a layer's big weight matrix, LoRA learns two much thinner matrices and multiplies them together. That product is the "delta" - the change - added on top of the frozen weight. Because the two matrices are thin, there are very few numbers to train.

New to r, alpha and target_modules? What the LoRA knobs mean A layer's weight is a big grid of numbers (a matrix). LoRA replaces the change to that grid with two thin matrices, A and B. r (the rank) is how thin they are - how many columns A has and rows B has. Small r = fewer numbers to train = cheaper and less likely to overfit; bigger r = more capacity. The instructor starts at r=32 because the dataset is large; r=8 is a fine, cheaper default. alpha is a scaling factor that controls how strongly the adapter's change counts when it is added to the frozen weight; the rule of thumb everyone uses is alpha = 2 × r, so r=32 pairs with alpha=64. target_modules is the list of layers to attach adapters to - here the four attention projections. Everything not in that list stays frozen.
New to the attention projections (q/k/v/o_proj)? Why those layers Inside every transformer block there is an attention step, and it uses four weight matrices nicknamed the query (q_proj), key (k_proj), value (v_proj) and output (o_proj) projections. These are where most of the model's "how do I relate these tokens" behaviour lives, so they are the standard, high-impact place to attach LoRA adapters. The base model is far too big to retrain whole; targeting these few projections gets most of the benefit for a tiny fraction of the cost.

The data collator: train only on the price

Each training example is one long piece of text: a product description followed by "Price is $" and then the actual price. If you trained normally, the model would spend most of its effort learning to re-write product descriptions - which you do not care about. You only want it to get good at the number after Price is $.

TRL's DataCollatorForCompletionOnlyLM does exactly this. You hand it a response template - the exact text "Price is $" - and it masks out (ignores for the loss) everything up to and including that template, so the model is scored only on the tokens it produces afterwards.

New to the data collator and completion-only loss? What masking does A collator is the helper that packs a batch of examples into the tensors the trainer feeds the model. The completion-only collator also builds a loss mask: a yes/no flag per token saying "count this token when measuring how wrong the model was". It sets the flag to "no" for every token up to and including the response template, and "yes" for the tokens after it. So the model still reads the whole description for context, but it is only graded - and only learns - on predicting the price. This focuses all the training signal on the one thing you want.

SFTTrainer: the object that runs the training

SFTTrainer (Supervised Fine-Tuning Trainer) comes from Hugging Face's TRL library. It is the engine that does the whole training loop for you: it feeds batches through the model, computes the loss, runs back-propagation, and steps the optimizer - over and over. You do not write that loop; you just hand the trainer the pieces and call one method.

New to SFTTrainer / TRL and task_type? What they are TRL (Transformer Reinforcement Learning) is a Hugging Face library of high-level trainers. Its SFTTrainer wraps the standard training loop so you only supply the model, the data, the LoRA config and the training settings. It knows how to apply a PEFT/LoRA config, so it freezes the base model and attaches the adapters for you. task_type="CAUSAL_LM" on the LoRA config tells PEFT what kind of model this is: a causal language model - one that predicts the next token left to right, which is exactly what Llama is and what "guess the price token" needs. Setting the wrong task type would wire the adapters up for the wrong kind of head.

The training loop (what one step does)

You never write this loop, but it helps to picture what the trainer repeats for every batch. This is also why the hyperparameters on the Day 4 page matter - they control the size and shape of these steps.

# Reconstructed to match the course's Google Colab notebook for this day.
# Standard QLoRA/PEFT code; runs on a GPU (e.g. Colab). Not executed here (no GPU).
#
# Week 7 - Day 3 / Day 4: the actual QLoRA training run.
# Freeze the 4-bit base model, attach LoRA adapters to the attention projections,
# and fine-tune only those adapters with TRL's SFTTrainer. A DataCollator for
# completion-only LM masks out the prompt so the model is trained only to predict
# the price token(s) after "Price is $". Progress is logged to Weights & Biases and
# checkpoints are pushed to the HuggingFace Hub.

import os
from datetime import datetime

import torch
import wandb
from google.colab import userdata
from huggingface_hub import login
from datasets import load_dataset
from transformers import AutoTokenizer, AutoModelForCausalLM, BitsAndBytesConfig
from peft import LoraConfig
from trl import SFTTrainer, SFTConfig, DataCollatorForCompletionOnlyLM


# ----------------------------------------------------------------------------
# Constants
# ----------------------------------------------------------------------------

BASE_MODEL = "meta-llama/Meta-Llama-3.1-8B"
PROJECT_NAME = "pricer"
HF_USER = "ed-donner"  # change to your own HuggingFace username

DATASET_NAME = f"{HF_USER}/pricer-data"
MAX_SEQUENCE_LENGTH = 182

# Unique, timestamped run name so every run is its own Hub repo / W&B run.
RUN_NAME = f"{datetime.now():%Y-%m-%d_%H.%M.%S}"
PROJECT_RUN_NAME = f"{PROJECT_NAME}-{RUN_NAME}"
HUB_MODEL_NAME = f"{HF_USER}/{PROJECT_RUN_NAME}"

# --- QLoRA hyperparameters ---
LORA_R = 32                 # adapter rank (start 8, double to 16, then 32)
LORA_ALPHA = 64             # scaling factor; rule of thumb alpha = 2 * r
TARGET_MODULES = ["q_proj", "v_proj", "k_proj", "o_proj"]  # the attention layers
LORA_DROPOUT = 0.1          # regularization: drop 10% of neurons each step
QUANT_4_BIT = True

# --- Training hyperparameters ---
EPOCHS = 3                  # instructor ran 3 (best checkpoint ~end of epoch 3);
                            # a single epoch already gives strong results and is far cheaper.
BATCH_SIZE = 16             # 16 fits an A100 (40GB); use 1 (or 2-4) on a T4.
GRADIENT_ACCUMULATION_STEPS = 1
LEARNING_RATE = 1e-4
LR_SCHEDULER_TYPE = "cosine"
WARMUP_RATIO = 0.03
OPTIMIZER = "paged_adamw_32bit"  # good convergence; memory-hungry. Swap for a
                                 # cheaper optimizer if you run out of memory.

# --- Admin / logging ---
STEPS = 50                  # log training loss to W&B every 50 steps
SAVE_STEPS = 5000           # push a checkpoint to the Hub every 5000 steps
LOG_TO_WANDB = True


# ----------------------------------------------------------------------------
# Log in to HuggingFace and Weights & Biases
# ----------------------------------------------------------------------------

hf_token = userdata.get("HF_TOKEN")
login(hf_token, add_to_git_credential=True)

if LOG_TO_WANDB:
    wandb_api_key = userdata.get("WANDB_API_KEY")
    os.environ["WANDB_API_KEY"] = wandb_api_key
    wandb.login()
    os.environ["WANDB_PROJECT"] = PROJECT_NAME
    os.environ["WANDB_LOG_MODEL"] = "checkpoint"
    os.environ["WANDB_WATCH"] = "gradients"


# ----------------------------------------------------------------------------
# Data
# ----------------------------------------------------------------------------

dataset = load_dataset(DATASET_NAME)
train = dataset["train"]
test = dataset["test"]

print(f"Training on {len(train):,} items; holding out {len(test):,} test items")
print("Example training text:\n")
print(train[0]["text"])


# ----------------------------------------------------------------------------
# Quantization config + tokenizer + frozen base model
# ----------------------------------------------------------------------------

if QUANT_4_BIT:
    quant_config = BitsAndBytesConfig(
        load_in_4bit=True,
        bnb_4bit_use_double_quant=True,
        bnb_4bit_compute_dtype=torch.bfloat16,
        bnb_4bit_quant_type="nf4",
    )
else:
    quant_config = BitsAndBytesConfig(
        load_in_8bit=True,
        bnb_8bit_compute_dtype=torch.bfloat16,
    )

tokenizer = AutoTokenizer.from_pretrained(BASE_MODEL, trust_remote_code=True)
tokenizer.pad_token = tokenizer.eos_token
tokenizer.padding_side = "right"

base_model = AutoModelForCausalLM.from_pretrained(
    BASE_MODEL,
    quantization_config=quant_config,
    device_map="auto",
)
base_model.generation_config.pad_token_id = tokenizer.pad_token_id
print(f"Memory footprint: {base_model.get_memory_footprint() / 1e6:,.1f} MB")


# ----------------------------------------------------------------------------
# Completion-only data collator
# ----------------------------------------------------------------------------
#
# We only want the model to learn the token(s) AFTER "Price is $" - not how to
# rewrite the product description. The collator masks everything up to and
# including the response template so the loss is computed only on the price.

response_template = "Price is $"
collator = DataCollatorForCompletionOnlyLM(response_template, tokenizer=tokenizer)


# ----------------------------------------------------------------------------
# LoRA config (the QLoRA adapters)
# ----------------------------------------------------------------------------

lora_config = LoraConfig(
    r=LORA_R,
    lora_alpha=LORA_ALPHA,
    target_modules=TARGET_MODULES,
    lora_dropout=LORA_DROPOUT,
    bias="none",
    task_type="CAUSAL_LM",
)


# ----------------------------------------------------------------------------
# SFT training config
# ----------------------------------------------------------------------------

train_config = SFTConfig(
    output_dir=PROJECT_RUN_NAME,
    num_train_epochs=EPOCHS,
    per_device_train_batch_size=BATCH_SIZE,
    gradient_accumulation_steps=GRADIENT_ACCUMULATION_STEPS,
    learning_rate=LEARNING_RATE,
    lr_scheduler_type=LR_SCHEDULER_TYPE,
    warmup_ratio=WARMUP_RATIO,
    optim=OPTIMIZER,
    max_grad_norm=0.3,
    weight_decay=0.001,
    max_seq_length=MAX_SEQUENCE_LENGTH,
    dataset_text_field="text",
    # logging
    logging_steps=STEPS,
    report_to="wandb" if LOG_TO_WANDB else "none",
    run_name=RUN_NAME,
    # saving / pushing to the Hub
    save_strategy="steps",
    save_steps=SAVE_STEPS,
    push_to_hub=True,
    hub_model_id=HUB_MODEL_NAME,
    hub_strategy="every_save",
    hub_private_repo=True,
    # misc
    save_total_limit=10,
    bf16=True,
    group_by_length=True,
    seed=42,
)


# ----------------------------------------------------------------------------
# Trainer
# ----------------------------------------------------------------------------

trainer = SFTTrainer(
    model=base_model,
    train_dataset=train,
    peft_config=lora_config,
    args=train_config,
    data_collator=collator,
    processing_class=tokenizer,  # older TRL versions use tokenizer=tokenizer
)


# ----------------------------------------------------------------------------
# Train, then push the final adapter to the Hub
# ----------------------------------------------------------------------------

if __name__ == "__main__":
    trainer.train()
    trainer.model.push_to_hub(PROJECT_RUN_NAME, private=True)
    print(f"Saved adapter to the Hub: {HUB_MODEL_NAME}")
    if LOG_TO_WANDB:
        wandb.finish()

What you should see. When trainer.train() starts, GPU memory climbs sharply (the instructor's A100 goes from about 6 GB to roughly 38 GB of its 40 GB with batch size 16). Then a progress bar appears and, every 50 steps, a training-loss number is printed and sent to Weights & Biases. The loss should trend downwards. The full three-epoch run shows an estimate of around a day on this hardware - you do not have to let it finish to see it working.
Common mistakes. Wrong target modules: if the names in target_modules do not match the model's real layer names, the adapters attach to the wrong layers (or none), and the loss barely moves - double-check them for your base model. Batch size vs GPU memory: per_device_train_batch_size=16 only fits a large (40 GB) GPU; on a smaller card (such as a Colab T4) it throws a CUDA out-of-memory error. Start at 1 and raise it only while memory has headroom. Powers of two (1, 2, 4, 8, 16) are the convention. Also remember alpha should track r (alpha = 2 × r) if you change the rank.
Video vs repo. The guide follows the video's Colab: base model meta-llama/Meta-Llama-3.1-8B, the Week 6 pricing dataset, and the "Price is $" response template. The current repo's re-recording uses a newer, smaller Llama and a different dataset/Item class (see the Day 2 note). Treat the model name and dataset id as values you swap; the QLoRA method - LoRA config, SFTTrainer, completion-only collator, trainer.train() - is the same either way. One real version note: newer TRL uses processing_class=tokenizer, older TRL uses tokenizer=tokenizer.
Recap
  • QLoRA freezes the 4-bit base model and trains only small LoRA adapters, so an 8B model fine-tunes on one GPU.
  • The LoRA config sets r=32 (rank), alpha=64 (scaling, = 2×r), target_modules=["q_proj","v_proj","k_proj","o_proj"] (the attention projections), lora_dropout=0.1 and task_type="CAUSAL_LM".
  • The DataCollatorForCompletionOnlyLM masks everything up to "Price is $", so the model is trained only to predict the price.
  • SFTTrainer (from TRL) takes the base model, the data, the LoRA config, the SFTConfig and the collator, then runs the whole loop when you call trainer.train().
  • The key SFTConfig settings here are epochs, per_device_train_batch_size (watch GPU memory), learning rate with a cosine schedule, and max_seq_length=182.
