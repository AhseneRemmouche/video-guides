Two kinds of metrics

A metric is just a number you agree to track so you can tell progress from wishful thinking. The instructor's key insight is that there are two different kinds of them, they answer different questions, and a good project uses both.

New to model-centric metrics? What they are and why they matter

Model-centric (also called technical) metrics measure the model's performance directly and immediately. Data scientists "live and breathe" these because you can optimize against them while training. Two the instructor explains:

  • Loss — a general word for "how badly the model did". Training is the job of making loss as small as possible. The common one for language models is cross-entropy loss: when the model predicts the next token, it really outputs a probability for every possible next token. You look up the probability it gave to the token that actually came next, then take minus the log of that probability. A perfect prediction (probability 1) gives a loss of 0; a confident wrong guess (probability near 0) gives a large loss. Lower is better.
  • Perplexity — simply e to the power of the cross-entropy loss. A perplexity of 1 means the model is completely confident and correct. A perplexity of 2 is like being right half the time; a perplexity of 4 is like a one-in-four guess. Think of it as "how many equally-likely options the model is effectively torn between". Lower is better.

Other model-centric numbers include raw accuracy/correctness, speed (latency) and token cost. They share one trait: they are fast to compute and point straight back at the model, so you can use them to tune it.

New to business-centric metrics? What they are and why they matter

Business-centric (also called outcome) metrics are the ones your business audience actually asked for. They are KPIs tied to a real result: return on investment, time or money saved, user satisfaction, or a direct comparison against a benchmark. For this week's project the business metric is beautifully simple: how many times faster is the generated C++ than the original Python, for the same answer?

Their strength is that they are tangible and concrete and speak to the goal: move them, and you have proven impact. Their weakness is that they are not directly tied to the model — the outcome also depends on your data, the environment, how the tool is used, and whether the original idea solves the problem at all. Many unknowns sit between "the model got better" and "the business number moved".

What makes a good metric?

A metric earns its place when it is: measurable (you can actually compute it, cheaply and repeatably); meaningful (moving it reflects something you genuinely care about); comparable (same definition every time, so today's number lines up with last week's); and hard to game (you cannot push the number up without really improving the thing). The reason you keep both families is that model-centric metrics are easy to measure but can drift away from what matters, while business-centric metrics are meaningful but slow and noisy. Decide what you will measure before you build — the instructor stresses that evaluation must be "thought up front" and established early.

The take-away. Use the two families in concert. Model-centric metrics let you tune and compare models quickly; business-centric metrics are what you show the business to prove the solution was worth it. For the optimizer you built, the headline business metric is the speedup: the instructor reports that in his experiment the fastest generated code ran many thousands of times faster than the Python original (a figure from the course video, not something measured in this guide).
Common trap: optimizing the wrong metric. A number that is easy to measure is not always the number that matters. If you only chase a model-centric score you can "win" on paper and still fail the business — faster code that returns a different answer is worthless, and a lower loss on a test set can simply mean the model memorised that set. Always pair the easy technical metric with the real outcome it is supposed to produce, and sanity-check that the outputs actually match before you celebrate a speed number.

How to pick metrics for a project

You do not invent metrics in a vacuum. Start from the outcome the business wants, work back to a technical metric you can optimize day to day, and keep a guardrail so you do not cheat the easy number.

Notice that this scoreboard is a business-centric metric: it compares the whole product's output (speed, for an identical answer), not the model's internal loss. That is exactly the pairing the page argues for — a concrete outcome number, with "same answer" as the correctness guardrail.

// Send slow Python to a frontier model and ask for a high-performance C++ rewrite,
// streaming the C++ back as it is generated.
//   - GPT-4o    via the openai client library
//   - Claude    via the native @anthropic-ai/sdk (claude-3-5-sonnet-20240620)
//
// The original lab also compiled + ran the C++ to compare speed against Python; that part
// is machine-specific (it shells out to clang++), so here we focus on the model-driven port,
// which is the reusable core the UI calls.
//
// Run with: npm run optimize    (needs the key for the chosen model; see .env.example)
import "dotenv/config";
import { pathToFileURL } from "node:url";
import OpenAI from "openai";
import Anthropic from "@anthropic-ai/sdk";

// Video-era model ids (the lab pins these for reproducible results).
export const GPT_MODEL = "gpt-4o";
export const CLAUDE_MODEL = "claude-3-5-sonnet-20240620";

// The UI dropdown picks one of these.
export type Model = "gpt-4o" | "claude";

// A representative compile command, handed to the model so it tunes the C++ for it.
// (The lab targets the fastest possible runtime with aggressive optimisation flags.)
const COMPILE_COMMAND =
  "clang++ -std=c++17 -O3 -march=native -DNDEBUG main.cpp -o main";

// Same instruction the Python lab uses: C++ only, identical output, fastest time.
export const SYSTEM_PROMPT =
  "Your task is to convert Python code into high performance C++ code. " +
  "Respond only with C++ code. Do not provide any explanation other than occasional comments. " +
  "The C++ response needs to produce an identical output in the fastest possible time.";

export function userPromptFor(python: string): string {
  return (
    "Port this Python code to C++ with the fastest possible implementation that produces " +
    "identical output in the least time. Pay attention to integer and floating-point types " +
    "to make sure the results match, and watch for overflow.\n" +
    "Your response will be written to a file called main.cpp and then compiled and executed; " +
    `the compilation command is:\n${COMPILE_COMMAND}\n` +
    "Respond only with C++ code. Do not wrap it in markdown fences.\n\n" +
    "Python code to port:\n\n" +
    "```python\n" +
    python +
    "\n```\n"
  );
}

// --- clients (built lazily so the module imports fine with no keys) ------------
function hasKeyFor(model: Model): boolean {
  return model === "gpt-4o" ? !!process.env.OPENAI_API_KEY : !!process.env.ANTHROPIC_API_KEY;
}

// A clear error the server turns into a 400 and the CLI prints.
export class MissingKeyError extends Error {
  constructor(public readonly model: Model) {
    super(
      model === "gpt-4o"
        ? "OPENAI_API_KEY is not set"
        : "ANTHROPIC_API_KEY is not set",
    );
    this.name = "MissingKeyError";
  }
}

// Strip stray markdown code fences the model may still emit, mirroring the Python
// `reply.replace('```cpp','').replace('```','')` cleanup.
export function stripCodeFences(text: string): string {
  return text.replace(/```(?:cpp|c\+\+)?/gi, "");
}

// --- the core: stream a C++ port of the given Python -------------------------
// Yields chunks of C++ as they arrive, mirroring the Gradio `yield` loop.
export async function* optimizePython(python: string, model: Model): AsyncGenerator<string> {
  if (!hasKeyFor(model)) throw new MissingKeyError(model);

  if (model === "gpt-4o") {
    const openai = new OpenAI(); // reads OPENAI_API_KEY
    const stream = await openai.chat.completions.create({
      model: GPT_MODEL,
      messages: [
        { role: "system", content: SYSTEM_PROMPT },
        { role: "user", content: userPromptFor(python) },
      ],
      stream: true,
    });
    for await (const chunk of stream) {
      const delta = chunk.choices[0]?.delta.content ?? "";
      if (delta) yield delta;
    }
  } else {
    const anthropic = new Anthropic(); // reads ANTHROPIC_API_KEY
    const stream = anthropic.messages.stream({
      model: CLAUDE_MODEL,
      max_tokens: 2000,
      system: SYSTEM_PROMPT,
      messages: [{ role: "user", content: userPromptFor(python) }],
    });
    for await (const event of stream) {
      if (
        event.type === "content_block_delta" &&
        event.delta.type === "text_delta"
      ) {
        yield event.delta.text;
      }
    }
  }
}

// Convenience: collect the whole (fence-stripped) C++ port.
export async function optimizePythonToString(python: string, model: Model): Promise<string> {
  let out = "";
  for await (const chunk of optimizePython(python, model)) out += chunk;
  return stripCodeFences(out);
}

async function main(): Promise<void> {
  const model = (process.argv[2] as Model) ?? "gpt-4o";
  if (model !== "gpt-4o" && model !== "claude") {
    console.log('Usage: npm run optimize -- [gpt-4o|claude]');
    return;
  }
  if (!hasKeyFor(model)) {
    console.log(
      `${new MissingKeyError(model).message} - this demo needs it. See .env.example.`,
    );
    return;
  }
  console.log(`Optimising the sample Python with ${model}...\n`);
  for await (const chunk of optimizePython(SAMPLE_PYTHON, model)) {
    process.stdout.write(chunk);
  }
  process.stdout.write("\n");
}

Recap
  • There are two families of evaluation metrics, and good projects use both.
  • Model-centric (technical) metrics — loss/cross-entropy, perplexity, accuracy, speed, token cost — measure the model directly and are what you optimize during training.
  • Cross-entropy loss is minus-log of the probability the model gave the true next token (0 is perfect); perplexity is e to that loss (1 is perfect).
  • Business-centric (outcome) metrics — ROI, time/money saved, speedup, user satisfaction — measure the whole product and prove real-world impact.
  • Pick metrics by starting from the business outcome, choosing a model-centric metric to tune on, and keeping a correctness guardrail so you do not optimize the wrong number.
