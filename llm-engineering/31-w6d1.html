Week 6 · Day 1 — From Inference to Training: Curating Data

The shift from using models to training them. Where training data comes from, and how to curate and scrub a dataset of product descriptions and prices.

Companion to Ed Donner's course · uv setup · Python + TypeScript/React · code verified against the repo

Week six is a turning point. For five weeks you have been doing what the instructor calls inference: taking a model that someone else already trained and finding clever ways to get more out of it (better prompts, multi-shot examples, tools, and last week's RAG). The model's internal numbers never changed. This week you start to change them. That is fine-tuning, and it is the first step into training models rather than only using them.

Training sounds glamorous, but it starts with the least glamorous part: the data. This first day is all about getting the data right - where it comes from, how to look at it, and how to clean and shape it into a tidy set of examples a model can learn from. The instructor is blunt that this matters more than any clever tuning later: improving the quality of the data that goes in has "by far the most profound impact" on the final model. So today there is no model call at all. We find a big pile of raw Amazon product data, study it, scrub it, and cut it down to a clean, balanced set of examples.

From inference to training

Everything in weeks one to five shared one idea: the model's weights (its billions of internal numbers) were fixed, and we worked around them. Multi-shot prompting, prompt chaining, tool calls and RAG all take a finished model and feed it better input at run time. Training is different. In training we reach inside and nudge those weights, very slightly, based on examples, so the model itself gets better at the task.

Training a frontier model from scratch is out of reach - the big labs spend well over $100 million doing it. The trick that makes this week possible is transfer learning: start from a model that is already trained on a huge amount of text, then keep training it a little more on your own, smaller, specialised dataset. The general knowledge carries over, and the extra training sharpens it for your specific job. That continued-training step is exactly what fine-tuning is.

New to this? Training vs inference, and what fine-tuning is

Inference is using a trained model: you give it an input and it predicts the next token, over and over, to produce an answer. Nothing about the model changes; the same input always costs the same and the model's "knowledge" is frozen.

Training is the opposite: you show the model many example inputs with the right answers, and an algorithm adjusts the model's weights so its predictions move closer to those answers. Do this across millions of examples and the model slowly gets better at the task.

Fine-tuning is training that starts from an already-trained model instead of from random numbers. You take a pre-trained model and continue training it on a focused dataset. It is far cheaper than training from scratch and is the normal way to specialise a general model for one job.

The project: a product pricer

The commercial problem for the next few weeks: imagine working at an online marketplace. Given a free-text description of a product (fridges, washing machines, electronics, car parts, tools and so on), predict how much it costs. It is easy to state and, crucially, easy to score: we know the real price, so we can simply measure how far off the model's guess was.

A data scientist might object that predicting a number is a job for a regression model, not a text generator. True - but it turns out frontier models are surprisingly good at it, especially when asked to answer with a number, and the clear, human-understandable scoring ("you said $100, it was really $120, so you were $20 out") makes it a perfect teaching project. Later days build traditional regression baselines and pit them against fine-tuned models.

Where training data comes from

Before any code, the instructor lists the usual places to find training data, roughly in order of preference:

  • Your own proprietary data - whatever your company already owns that fits the problem. This is the best source because it is specific to you and nobody else has it.
  • Kaggle - a long-standing hub of public datasets shared by the data-science community.
  • Hugging Face - a huge collection of community datasets, which is what this course uses.
  • Synthetic data - data generated by another model. Useful for seeding a smaller model, but it rarely makes sense to have a frontier model generate the data you then teach that same frontier model.
  • Specialist vendors (for example Scale) - companies you pay to build a curated dataset.

This project uses a public Hugging Face dataset: McAuley-Lab/Amazon-Reviews-2023, a scrape of Amazon going back years. Besides reviews it carries product metadata - titles, descriptions, features and prices - which is exactly what a pricer needs. It is enormous: almost 50 million items across many categories. We do not use all of it; we pluck out a handful of categories so training stays affordable.

What does "dataset curation" mean?

Dataset curation is the work of turning a raw pile of data into a clean, consistent, well-chosen set of examples for training. It includes dropping records that are broken or missing key fields, cleaning up messy text, removing duplicates, and deciding which records to keep so the set is not lopsided. It is not glamorous, but it is where most of the real quality gain comes from. The instructor describes six stages: investigate (understand the fields and their quality), parse (turn raw records into tidy objects), visualize (plot distributions), assess (judge quality and limits), curate (decide what to keep and how to balance it), and save (upload the finished set).

Why does data quality matter so much?

A model learns the patterns in whatever you show it, including the bad ones. If a quarter of your records are broken, the model wastes effort learning noise. If your text is full of junk the model has to spend tokens reading it, pushing the useful words out. And if the set is lopsided - say, mostly cheap items - the model learns to always guess "cheap". The instructor's point is practical: you can spend weeks tuning knobs for a tiny gain, or you can clean the data and get a much bigger gain for less effort. That is why today is spent entirely on the data.

Tokens in training data - why length matters

Models read text as tokens (word pieces), not characters. During training, every example must fit inside a fixed token budget, and the more tokens each example has, the more memory training needs and the more each example costs on a paid API. So part of curation is capping how long each example can be. In the video the instructor fixes a budget of about 180 tokens per item, measured with the Llama tokenizer, so that later - when the same data trains an open-source Llama model - every example already fits. That is why the cleaning step both trims junk and truncates long descriptions.

How one record becomes a training example

The heart of the cleaning lives in an Item class and a parse function. The instructor keeps them in their own module (not the notebook) so the logic can be reused and the notebook stays tidy, and urges you to read it yourself. In words, for each raw record it:

  • sets a constant BASE_MODEL to a Llama 3.1 8B variant, because its tokenizer is what measures the token budget;
  • runs scrub_details, which strips distracting boilerplate like "Batteries included" and "by Manufacturer" that would waste tokens;
  • runs scrub, which removes odd characters and collapses repeated spaces with a little regex - and, cleverly, deletes any word of eight-plus characters that contains a digit, because those are usually Amazon part numbers that explode into many useless tokens;
  • builds two prompts: a training prompt ("How much does this cost to the nearest dollar?" plus the description, ending with the real price) and a test prompt, identical but cut off just before the answer. The training prompt teaches; the test prompt asks.
What you should see. After loading Appliances, a count of roughly 94,000 records. After parse-and-filter, a much smaller set (the instructor saw about half kept) of clean Items whose .full text reads like a tidy product description with the part numbers removed and the length capped. After combining categories and de-duplicating, a large combined count, and after sampling, exactly 820,000 items with a noticeably flatter price and category spread than the raw data.
Common data mistakes.
  • Data leakage into the test set. If the same item (or a near-duplicate) appears in both training and test, the model "passes" the test by memorising, not by learning, and your score is a lie. That is exactly why the notebook de-duplicates before splitting, and why train, val and test are cut from disjoint slices.
  • Unbalanced data. The raw set is mostly cheap items and mostly a couple of categories. Train on it unchanged and the model learns to always guess "cheap Automotive part". The weighted sampling (favour pricier items, push down the biggest categories) is what prevents that.
  • Forgetting that price can be None or missing - always guard the float(...) conversion, as the max-price loop does, or the whole cell crashes on the first bad record.
Video vs repo. In the video the instructor keeps the cleaning in a single module, items.py, with an Item class whose parse method does the scrubbing and builds the prompts, and he curates only the Appliances category on Day 1 (combining categories and uploading come on Day 2). The current repo has refactored this: the logic is split into a pricer package - pricer/items.py (the Item class), pricer/parser.py (the parse function), and pricer/loaders.py (ItemLoader) - and this Day 1 notebook already goes all the way through combining eight categories, de-duplicating, weighted sampling and uploading a train/validation/test split. The cleaning idea is the same; only the file layout and how far the notebook runs differ. The repo also filters to a $1-$1000 price range inside parse, so some exact counts and the final price range differ from the numbers shown on screen.

How we will know it worked

The instructor closes Day 1 by naming the metrics. Model-centric metrics live in the data scientist's world: training loss and validation loss (which should fall as the model learns), and errors like RMSLE (which balances absolute and percentage mistakes) or mean squared error (which blows up on expensive items, so it is a poor fit here). Business-centric metrics are the ones a CEO cares about. The beauty of this project is one metric that is both: the average dollars off ("you said $100, it was $120, so $20 out"). It is simple, human, and tied straight to the model. A common companion rule counts a guess as a "hit" if it is within $40 or within 20% - and later days measure what percentage of guesses are hits.

Recap
  • Week six moves from inference (working around a fixed model) to training (changing the model). Fine-tuning is training that continues from an already-trained model.
  • The project is a product pricer: predict a price from a product description, chosen because it is easy to score in plain dollars.
  • Training data comes first from your own proprietary data, then public hubs (Kaggle, Hugging Face), synthetic data, or specialist vendors. This course uses the Hugging Face Amazon-Reviews-2023 metadata.
  • Curation runs six stages - investigate, parse, visualize, assess, curate, save - and the biggest quality gains come from the data, not from later tuning.
  • The notebook loads categories, parses each record into a clean Item (scrubbing junk and part numbers, trimming to a token budget), filters, de-duplicates, weight-samples to 820,000 to fix the skew, then splits into disjoint train/val/test sets and uploads them.
