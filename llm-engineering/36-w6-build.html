Week 6 · Project Build — The Product Pricer, Step by Step

Build the product pricer: curate data, train baselines and fine-tune a model in Python + uv, then wire the finished model to a small React demo UI (enter a description, get a price) in Node + TypeScript.

Build it yourself · Python + uv (training) and a React demo UI

The five day-pages explain Week 6 one idea at a time. This page is different: it is a hands-on build. You will put the whole week's project together, in order, so that at the end you have a model that reads a product description and estimates what the product costs - plus a small app to try it. This is the course's product pricer: you curate a large dataset of real products and prices, measure how well simple methods and off-the-shelf frontier models do, and then fine-tune a frontier model on your own examples so it learns to price items from their descriptions.

The training is a data-science job and stays in Python, managed with uv. The finished model is reached over the network with an API key, so the demo app that calls it can be written in anything. This week's demo is a small React page (built with Node and TypeScript) where you paste a description and read back a price. So the two tracks are not two versions of the same program, as in earlier weeks - they are two stages: Track A trains and produces a model id; Track B is a thin UI that uses that id.

  • Track A - Python + uv does the real work: curate and balance the dataset, build simple baseline models with scikit-learn, evaluate frontier models, then launch an OpenAI fine-tuning job. The full, explained code is on the Day 1 through Day 5 pages; here we only list what to type and what you should see. The training code was not run live in this guide - it needs a lot of data, money and time, so it is shown exactly as in the course.
  • Track B - React + Node + TypeScript is the demo UI. It is the real project in the week6-ts/ folder: a description box, an Estimate price button, and the price shown big. It calls your fine-tuned model through a tiny Hono API. It type-checks and the web app builds; the model call was not run live.

Build it step by step

Run it locally (Python + uv)

The runnable Week 6 project lives in the week6-py/ folder and runs fully locally against Ollama, with no paid API keys. Install Ollama first, then:

ollama pull llama3.2
cd week6-py
UV_NATIVE_TLS=1 uv sync
uv run python src/make_data.py
uv run python src/baselines.py
uv run python src/frontier_eval.py

The sklearn baselines train and score on a small synthetic dataset and the eval uses local Ollama; the real OpenAI fine-tuning finale (finetune_note.py) needs a paid key and is not run.

Do Track A first if you want your own model; it is the week's real project. Track B is short and can be built at any time, because it works with the base model until you paste in a fine-tuned id. The overview below shows the order.

Track A - Python + uv (train the pricer)

This track follows Days 1 to 5 of the week. Each step points to the day page that holds the full, line-by-line code; here you get the commands and the shape of the work. You build it inside a uv project (or the course repo you cloned in Week 1).

New to fine-tuning? What it is and why this week uses it Most of the course prompts a general model: you send instructions and examples in each request. Fine-tuning is different - you give a provider a file of input/output examples and it trains a private copy of the model on them, returning a new model id. From then on the model has your examples baked in, so your prompts can be shorter and the answers more consistent for your narrow task. Here the task is pricing: each example is a product description (the input) paired with its real price (the wanted output). It is not always worth it - a big part of the week is measuring whether it beat the simpler methods.
  1. Create the project Make a fresh folder and let uv manage it. uv is the fast Python package manager the course uses instead of Anaconda: 
    uv init llm-week6
cd llm-week6
    You can also work inside the course repo you cloned in Week 1; either way the commands below are the same.
  2. Add the libraries Add the data-science and API packages this week needs. uv add installs each one and records it in pyproject.toml: 
    uv add openai datasets pandas scikit-learn matplotlib python-dotenv wandb
    openai is the API client (for evaluation and for creating the fine-tuning job), datasets loads and pushes data to the Hugging Face Hub, pandas holds the data in tables, scikit-learn provides the baseline models, matplotlib draws the charts that compare results, python-dotenv loads your keys from .env, and wandb is Weights & Biases, which records the fine-tuning run so you can watch the training loss.
  3. Set your keys Create a .env file in the project root. You need an OpenAI key; the Hub and Weights & Biases tokens are only needed for the dataset push and the training dashboard: 
    OPENAI_API_KEY=sk-proj-...
HF_TOKEN=hf_...
WANDB_API_KEY=...
    .env is git-ignored; never commit it. This week calls paid APIs - evaluation and fine-tuning each cost a little real money (usually a few dollars for the small example runs the course uses).
  4. Curate and balance the dataset (Days 1-2) Load a large set of real products with prices, scrub the text (strip part numbers and noise, keep a concise description), and balance it so cheap and expensive items are both well represented - otherwise the model just learns to guess a middle price. Then push the cleaned splits (train / validation / test) to the Hugging Face Hub so every later step loads the exact same data. The full code is on the Day 1 and Day 2 pages.
  5. Build scikit-learn baselines (Day 3) Before any fine-tuning, build cheap "how hard is this?" models with scikit-learn: pull simple features (such as item weight and text length), turn the descriptions into word-count vectors with bag-of-words (CountVectorizer), and fit a LinearRegression, a support vector regressor (SVR) and a RandomForestRegressor. Record each one's average error in dollars. These are the bar the fine-tuned model has to beat. Full code on the Day 3 page.
  6. Evaluate frontier models (Day 4) Now ask off-the-shelf frontier models (for example gpt-4o-mini and Claude) to price the same test items with a short prompt, and measure their error the same way. This tells you how far a plain prompt gets you, and gives fine-tuning something concrete to improve on. Full code on the Day 4 page.
  7. Prepare JSONL and launch the fine-tuning job (Day 5) Turn a slice of the training items into JSONL - one line per example, each a chat exchange whose user message is the product and whose assistant reply is the price. Upload the train and validation files with openai.files.create(...), then start the job with openai.fine_tuning.jobs.create(...), pointing it at those files and connecting it to Weights & Biases so you can watch the loss fall. Full code on the Day 5 page.
  8. Note your fine-tuned model id When the job finishes, read the new model id with openai.fine_tuning.jobs.retrieve(job_id).fine_tuned_model. It looks like ft:gpt-4o-mini-2024-07-18:personal::XXXX. Evaluate it against your baselines and the frontier models from the earlier days - sometimes it wins, sometimes it does not. Either way, copy this id: it is what Track B's demo needs.
What you should see. The baseline step prints an average error in dollars for each simple model and draws a chart. The fine-tuning step prints a job id, and the Weights & Biases page shows the training and validation loss curves as the run progresses. When the job completes you get a fine-tuned model id you can call like any other model.
Common mistakes. Skipping the balance step leaves a dataset full of cheap items, so every model (including the fine-tuned one) learns to guess low. Fine-tuning on a messy dataset wastes money - clean and measure first. And do not expect fine-tuning to always win: if the baselines or the plain frontier prompt already do well, the course shows that it may not be worth it.
Video vs repo. The repo keeps moving ahead of the videos. The guide pins the video-era gpt-4o-mini as both the frontier model to evaluate and the base model to fine-tune; a newer repo may name a different model id. Treat the model name as a value you swap, since AI companies retire models. The dataset sizes and the number of fine-tuning examples in the course are kept small on purpose, to keep the spend tiny.

Track B - React + Node + TypeScript (the demo)

This track rebuilds the little web app in week6-ts/: a React page where you paste a product description and get an estimated price. A tiny Hono API calls the pricing model; the scripts run with tsx and the page is bundled by Vite. These are the real files, and the steps below match them exactly. The demo works with the base gpt-4o-mini out of the box; point it at your fine-tuned id once Track A gives you one.

  1. Scaffold the project You need Node (version 18 or newer); check with node --version. Create the React + TypeScript app with Vite, then set up the one package that holds the UI and the server together: 
    npm create vite@latest week6-ts -- --template react-ts
cd week6-ts
npm init -y
    This project keeps its Vite app under a web/ folder and adds server/ and src/ beside it, all in one package with "type": "module" in package.json.
  2. Add the runtime libraries Add the OpenAI client, the Hono web server and the env loader. npm add installs them and records them in package.json: 
    npm add openai hono @hono/node-server dotenv
    openai is the JavaScript SDK that calls the pricing model, hono plus @hono/node-server are the tiny web server, and dotenv loads your key from .env.
  3. Add the dev tool Add tsx so you can run a .ts file directly (React, Vite and TypeScript already came with the scaffold): 
    npm add -D tsx
    -D marks it as a development-only dependency.
  4. Create the inference core Create src/price.ts. It exports estimatePrice(description), which sends a short system prompt ("reply only with the price in dollars") plus the description to openai.chat.completions.create(...) and reads the reply. The model it calls comes from the environment: process.env.FINE_TUNED_MODEL, falling back to gpt-4o-mini when that is not set. It also exports a pure parsePrice(text) helper that strips currency symbols and thousands separators and returns the first number it finds (or NaN). The call is guarded, so importing the file is safe without a key.
  5. Create the Hono API Create server/index.ts. It builds a Hono app with one route, POST /api/price, that reads { description }, returns a 400 JSON error if the body or the OPENAI_API_KEY is missing, calls estimatePrice(...) and returns { price, model }. It also serves the built React app and listens on http://localhost:8788.
  6. Build the React form Create web/src/App.tsx: a textarea for the description, an Estimate price button, and fetch("/api/price", ...) to post the description. While the request runs the button shows "Estimating..."; when the price comes back it is shown big, formatted as US dollars. Errors are shown in a small red box.
  7. Point it at your model and run Add your fine-tuned id from Track A to .env (leave it out to use the base model): 
    OPENAI_API_KEY=sk-proj-...
FINE_TUNED_MODEL=ft:gpt-4o-mini-2024-07-18:personal::XXXX
    The commands are already wired in package.json. These are the real scripts in week6-ts/: 
    {
  "scripts": {
    "price": "tsx src/price.ts",
    "api": "tsx server/index.ts",
    "web": "vite --config web/vite.config.ts",
    "typecheck": "tsc --noEmit -p tsconfig.json",
    "build": "tsc --noEmit -p tsconfig.json && vite build --config web/vite.config.ts"
  }
}
    price prices one description from the command line, api starts the Hono server and web starts the Vite dev server. Run the app in two terminals - the API in the first: 
    npm run api
    and the web server in the second: 
    npm run web
    Then open http://localhost:5173. Vite proxies /api to the server on port 8788, so the browser can reach it. Paste a description and click Estimate price.
What you should see. npm run api prints LLM Engineering Week 6 API on http://localhost:8788. The page at http://localhost:5173 shows a description box pre-filled with a sample product and an Estimate price button. Click it and a dollar amount appears below. With no key set, you get a clear 400 error instead of a crash.
Common mistakes. Starting only npm run web but not npm run api makes every request fail - both must be running. Forgetting the .env file returns the 400 "OPENAI_API_KEY is not set" error. If you set FINE_TUNED_MODEL to an id that is still training (or a typo), the call fails - leave it unset to fall back to gpt-4o-mini while you test the UI.

What you built

You built this week's product pricer end to end. In Track A you did the real data-science work in Python with uv: you curated and balanced a dataset of products and prices and pushed it to the Hub, built scikit-learn baselines and evaluated frontier models so you had a bar to beat, then prepared JSONL and launched an OpenAI fine-tuning job, tracking the loss with Weights & Biases, and ended with a fine-tuned model id. In Track B you built the small React demo from week6-ts/ - a form that posts a description to a Hono API, which calls your model and returns a price - and pointed it at your model id through FINE_TUNED_MODEL.

Recap

  • Track A: uv add openai datasets pandas scikit-learn matplotlib python-dotenv wandb, set your keys, curate and balance the dataset and push it to the Hub (Days 1-2), build scikit-learn baselines (Day 3), evaluate frontier models (Day 4), prepare JSONL and launch the OpenAI fine-tuning job tracked with Weights & Biases (Day 5), then note the fine-tuned model id.
  • Track B matches the real week6-ts/: the Vite react-ts scaffold plus npm init, npm add openai hono @hono/node-server dotenv and npm add -D tsx, then src/price.ts (estimatePrice + parsePrice, model from FINE_TUNED_MODEL), server/index.ts (Hono POST /api/price) and web/src/App.tsx (the React form), run with npm run api + npm run web.
  • The full line-by-line code lives on the day pages, including Day 3 (the baselines) and Day 5 (the fine-tuning job and the demo screenshot).
  • Fine-tuning does not always win: the week measures simple and off-the-shelf methods first so you can tell whether it was worth it.
