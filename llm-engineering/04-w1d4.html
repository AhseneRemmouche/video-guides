From early AI to the transformer, then the ideas you use every day: parameters, tokens, the context window, API costs, and why a model has no memory.

A large language model (LLM) does one small thing over and over: given the text so far, it predicts the most likely next token (a word or word-piece). It then adds that token to the text and predicts again. That is all it does. Everything that feels like understanding is a by-product of doing this at enormous scale. The instructor calls that effect emergent intelligence: the model is imitating the patterns in its training data so well that it behaves as if it understands.

A very short history

The instructor walks through how we got here. Decades of early AI leaned on hand-written rules. Then machine learning let programs learn patterns from data instead. Deep learning stacked many layers into a neural network, which learns during training. The turning point came in 2017, when researchers at Google published the paper "Attention is All You Need" and introduced the transformer — the architecture behind almost every model in this course. One year later OpenAI released GPT-1 (the "T" stands for Transformer), and the line GPT-2 (2019), GPT-3 (2020), ChatGPT (late 2022) and GPT-4 (2023) followed.

New to transformers? What one is and why it matters

A transformer is a particular design of neural network. Its key idea is attention: when the model looks at a word, it can weigh how much every other word in the text matters to it, all at once. That lets it handle long passages and learn relationships that older designs missed. You do not have to build one in this course — you just call finished transformer models over an API. The important fact is that nearly every model you will use (GPT, Claude, Gemini, Llama) is a transformer.

Parameters (weights): how big a model is

Inside a model is a huge pile of numbers called parameters, also called weights. Think of them as tiny knobs that control how the model turns an input into a prediction. Training nudges these knobs, example after example, until the model predicts the next token well. The count of these knobs is the rough measure of a model's size.

The numbers the instructor quotes are staggering. An old linear-regression model might have 20 to 200 parameters. GPT-1 (2018) had about 117 million. GPT-2 had 1.5 billion, GPT-3 had 175 billion, and GPT-4 is reported at about 1.76 trillion. Today's frontier models are believed to reach around 10 trillion. Open-source models you can run yourself, such as Llama 3.1, come in 8B, 70B and 405B sizes.

Tokens: the units a model reads and writes

Models do not see letters or whole words. They see tokens: chunks of text that are often a whole common word but sometimes just a word-piece. A tokenizer is the tool that splits your text into these chunks and gives each one an id number. The instructor explains why this middle ground won: training character by character asks too much of the model (it must learn to build every word from letters), while giving every possible word its own token needs an impossibly large vocabulary that still cannot cover every name and rare word. Word-pieces sit in between: common words are one token, and rare words split into a few pieces that often carry meaning (for example "witchcraft" becomes "witch" + "craft").

A useful rule of thumb: on average one token is about four characters of English, or roughly three-quarters of a word, so 1,000 tokens is about 750 words. Code, math, and long numbers use many more tokens per character.

New to tokens? What they are and why they matter

When you send text to a model, the first thing that happens is tokenization: your text is cut into tokens and each becomes a number. The model only ever sees those numbers. This explains a famous weakness — ask a model "how many letter a's are in this sentence?" and it often fails, because by the time it reads the text the letters are already hidden inside tokens. It also explains billing: because the unit is the token, providers price their models per token, not per word.

See tokens for real: the tokenizer demo

Every model family ships its tokenizer as a small library that runs entirely on your machine — no API key, no cost, no network. Here is the complete demo file. We did run this one in both languages, and the two produced the identical token ids — a nice cross-check that both tokenizers really use the same rules. The real output is shown below the code.

In Python the tokenizer is tiktoken, OpenAI's own library. get_encoding("o200k_base") loads the GPT-4o family rules; encode turns text into ids and decode turns an id back into text.

TypeScript has no tiktoken, so the port uses gpt-tokenizer, a pure-JavaScript package that ships the same o200k_base vocabulary. You import encode and decode from gpt-tokenizer/encoding/o200k_base and run the file with tsx on Node. Same rules, same ids.

# Day 4 - Seeing tokens with tiktoken
# tiktoken is OpenAI's tokenizer. It turns text into the integer token ids a model
# actually reads, and back again. It runs locally - no API key and no cost.

import tiktoken

# o200k_base is the encoding used by the GPT-4o family of models.
encoding = tiktoken.get_encoding("o200k_base")

text = "Hi my name is Ed and I like banoffee pie"

# encode() -> the list of token ids the model sees
tokens = encoding.encode(text)
print(tokens)
print(f"{len(text)} characters became {len(tokens)} tokens")

# decode each id on its own to see where the word-pieces fall
for token_id in tokens:
    print(f"{token_id} = {encoding.decode([token_id])!r}")
// Day 4 - Seeing tokens with a tokenizer (TypeScript port of day4_tokens.py)
// The Python lab uses tiktoken's o200k_base encoding. gpt-tokenizer is the pure-JS
// equivalent: it ships the same o200k_base vocabulary and runs locally - no API key, no cost.
import { encode, decode } from "gpt-tokenizer/encoding/o200k_base";

const text = "Hi my name is Ed and I like banoffee pie";

// encode() -> the list of token ids the model sees
const tokens = encode(text);
console.log(tokens);
console.log(`${text.length} characters became ${tokens.length} tokens`);

// decode each id on its own to see where the word-pieces fall
for (const tokenId of tokens) {
  console.log(`${tokenId} = ${JSON.stringify(decode([tokenId]))}`);
}

The context window

The context window is the total number of tokens a model can look at in one go when it predicts the next token. Crucially, it counts both your input and the output the model generates. The instructor's examples: most GPT models allow about 128,000 tokens, Claude about 200,000, and Gemini 1.5 Flash a huge 1,000,000 (close to the whole works of Shakespeare, about 1.2 million tokens). Everything in a conversation — the system prompt, every message back and forth, and the new tokens being produced — has to fit inside this one budget.

New to the context window? What it is and why it matters

Think of the context window as the model's desk: it can only work with what fits on the desk at once. A short first question barely uses it. But a long conversation, or pasting in a big document, fills the desk fast. When a chat grows past the window, the oldest parts must be dropped, which is why a very long chat can seem to "forget" what you said at the start. Picking a model with a larger window, or trimming what you send, is a real engineering decision later in the course.

API cost

The chat website (ChatGPT) is usually a flat monthly subscription, but the OpenAI API you call from code is pay-per-use. The cost of one call depends on the model and on two counts: input tokens and output tokens. Prices are quoted per million tokens, and output tokens usually cost more than input tokens. In the video, Claude 3.5 Sonnet is about $3 per million input and $15 per million output, while the course workhorse gpt-4o-mini is about $0.15 per million input and $0.60 per million output. For the short questions in this course that is a tiny fraction of a cent per call; providers ask you to load about $5 of credit to start, which you will barely touch.

New to API pricing? How the cost is worked out

Take the input and output token counts for a call, divide each by one million, multiply by that model's input and output price, and add the two. Example (illustrative): a call with 2,000 input tokens and 500 output tokens on gpt-4o-mini costs about (2000 ÷ 1,000,000 × $0.15) + (500 ÷ 1,000,000 × $0.60) = $0.0003 + $0.0003 = $0.0006, well under a tenth of a cent. The cost only matters once a program makes many thousands of calls — then it adds up and you watch it on the provider's dashboard.

LLMs are stateless: the "illusion of memory"

This is the "aha" moment of Day 4. Every call to an LLM is stateless: the model keeps nothing from one call to the next. So how does ChatGPT seem to remember your earlier messages? It is a trick. Each time you send a message, the whole conversation so far — the system prompt, your earlier user prompts, and the model's own earlier replies (the assistant role) — is sent again as the input. The model then predicts the next tokens given all of it. The "memory" is really the replay. This is also why a longer chat costs more: you resend everything every time.

The demo below proves it with three chat completions calls. Call 1 tells the model a name. Call 2, sent on its own, asks for the name — and the model cannot answer, because it never saw call 1. Call 3 includes the earlier turns, and now the model answers correctly.

The TypeScript port is a line-for-line match of the Python. The only differences are JavaScript's: each call is awaited because it is asynchronous, the options are passed as one object ({ model, messages }), and import "dotenv/config" does the job of Python's load_dotenv() — loading your key from .env into the environment.

# Day 4 - The illusion of memory
# Every call to an LLM is stateless: it remembers nothing between calls. We create
# the feeling of memory by sending the whole conversation back every time.

from openai import OpenAI

openai = OpenAI()
MODEL = "gpt-4o-mini"

# First call: we tell it our name.
messages = [
    {"role": "system", "content": "You are a helpful assistant"},
    {"role": "user", "content": "Hi! I'm Ed!"},
]
response = openai.chat.completions.create(model=MODEL, messages=messages)
print(response.choices[0].message.content)

# Second call, on its own: it has no idea who we are - the first call is forgotten.
messages = [
    {"role": "system", "content": "You are a helpful assistant"},
    {"role": "user", "content": "What's my name?"},
]
response = openai.chat.completions.create(model=MODEL, messages=messages)
print(response.choices[0].message.content)

# Fix: replay the whole conversation, including the assistant's earlier reply.
messages = [
    {"role": "system", "content": "You are a helpful assistant"},
    {"role": "user", "content": "Hi! I'm Ed!"},
    {"role": "assistant", "content": "Hi Ed! How can I assist you today?"},
    {"role": "user", "content": "What's my name?"},
]
response = openai.chat.completions.create(model=MODEL, messages=messages)
print(response.choices[0].message.content)

What you should see

We did not run this file here — in either language — because it needs a paid API key; it is shown exactly as the course presents it. Following the course, the expected behaviour is:

  • Call 1 — a friendly greeting, something like "Hi Ed! How can I assist you today?"
  • Call 2 — the model cannot tell you your name. It replies that it does not know, because this call never saw that you are Ed.
  • Call 3 — now that the earlier turns are replayed, the model answers correctly: your name is Ed.

The exact wording will vary from run to run (and with the model), and the Python and TypeScript versions behave the same way. The pattern — fail, then succeed once the history is included — is the point.

Why do LLMs have no memory, and whose job is it to fake it?

The model is just a function: text in, next tokens out. It does not save anything on a server between your calls, and two calls from the same program are as unrelated as calls from two strangers. "Memory" in a chat product is built around the model by the application: it stores the conversation and resends it every time. As an AI engineer, giving the model the right context each call — and deciding what to keep when the conversation gets too long for the context window — becomes your job. This same idea reappears later as the "memory" of agentic systems in week 8.

Common mistakes
  • Thinking the model remembers you. It does not. If you want it to know something from an earlier turn, you must include that turn in the messages list you send this time.
  • Forgetting the assistant's own replies. When you replay a conversation, include the model's earlier answers under the assistant role, not just your own user messages — otherwise the model loses the thread of what it already said.
  • Forgetting that output counts too. The generated tokens count toward both the cost and the context window, not just your input. A long answer is a real part of the bill and the budget.
  • Reading prices per token instead of per million. "$3" is per million input tokens, not per token. Mixing these up makes the models look thousands of times more expensive than they are.
  • Expecting different tokens in each language. They are the same. tiktoken (Python) and gpt-tokenizer (TypeScript) both use o200k_base, so the ids match exactly — do not "fix" code because the numbers look identical.
Recap
  • Modern LLMs are transformers, from Google's 2017 "Attention is All You Need" paper; they work by predicting the next token over and over.
  • Parameters (weights) are the model's learned numbers; their count measures size, from GPT-1's 117 million to frontier models near 10 trillion.
  • Text is split into tokens (about 4 characters each). We saw a real split: our 40-character sentence became 11 tokens, and "banoffee" became ' ban' + 'offee' — with the same ids in Python (tiktoken) and TypeScript (gpt-tokenizer).
  • The context window is the total token budget for input and output together; a growing chat uses more of it.
  • API cost = input tokens × input price + output tokens × output price, both priced per million tokens.
  • LLMs are stateless: "memory" is the whole conversation replayed on every call, which is why call 3 in the demo answers when call 2 could not.
