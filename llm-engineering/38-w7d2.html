Week 7 · Day 2 — Evaluating the Base Model

Measure the open-source model before fine-tuning: an evaluation harness that runs it over the test set and scores its price predictions, as a starting point.

Companion to Ed Donner's course · uv setup · Python + TypeScript/React · code verified against the repo

Today is the day the project stops being about other people's models and starts being about ours. Week 7 is where we build a small, specialised open-source model and try to make it compete with the giants. But before we change a single weight, we have to answer one honest question: how good is the model right now, straight off the shelf, before any fine-tuning?

That is what Day 2 is about. We pick a base model, run it over our test set exactly as it comes, parse the price it predicts for each product, and score the average error in dollars. That one number is our starting line. If fine-tuning cannot beat it, fine-tuning is not helping. And if the base model is already far behind the frontier models, that is fine too, because our model is free to run and the whole point of the next few days is to close that gap.

New to this? Why measure a "base score" first

A base score is the result you get from the untouched model before you do any work on it. You measure it first for three reasons. It gives you a target to beat, so you can tell whether fine-tuning actually improved anything. It is cheap to get, so you learn early if the whole idea is hopeless. And it keeps you honest: it is easy to fool yourself into thinking a model is clever until you compare it against a dumb guess. In this project the "dumb guess" is a model that always answers the average training price, and the base open-source model is going to have to prove it can do better than that.

Choosing the base model

The instructor spends real time on this choice, because the base model is, in his words, like one giant hyperparameter: change it and everything downstream changes. A few decisions come up.

How big? More parameters usually means a better shot at the problem, and we are not short of data (the course has around 400,000 training examples). The real limit is memory: we want the model to fit on one affordable GPU box, which caps us at roughly a 7-to-8-billion-parameter model.

Base or instruct? Most chat models ship in two forms: the raw pre-trained "base" (sometimes called a foundation model) and an "instruct" variant that has been further trained to follow system and user prompts. For a single, fixed task like ours the instructor leans towards the base variant: we are going to train it for one job anyway, so we would rather it spend all of its capacity on that job than on learning chat manners. He mentions that he tried both and base did slightly better.

Which family? After touring the Hugging Face Open LLM Leaderboard he settles on Llama 3.1 8B. Several models score higher, but Llama has one convenient property for this task: its tokenizer turns every whole number from 0 to 999 into a single token. Qwen, Gemma and Phi-3 mostly use about one token per digit instead. Since we want the model to predict a price, it is much simpler if the whole price lands in one token the model has to get right.

New to tokens? Greedy decoding and the "top token"

When a model generates, it does not pick a word directly. It produces a probability for every possible next token, and then something chooses one. The simplest choice is "greedy decoding": always take the single highest-probability token. Because a three-digit price is one token in Llama, predicting the price well boils down to putting a high probability on the right number token. The code still asks for up to four new tokens, just in case the model adds a dollar sign or a stray character, but one token is really all we need.

The method: run the base model over the test set

The recipe is short and is the same idea the course has used before. Load the base model, wrap it in a small predict function, run that function over all 250 test prompts, and let a test harness add up how wrong it was.

  1. Load the model in 4-bit. The 8-billion-parameter Llama is loaded through Hugging Face with quantization turned on, so it fits in a free GPU. In the video this uses the AutoModel loader (the causal-LM variant) together with bitsandbytes for the 4-bit config, and AutoTokenizer for the matching tokenizer. The 4-bit model takes about 5.6 GB of memory.
  2. Write a predict function. It takes one test item, encodes the prompt with the tokenizer, pushes it to the GPU, calls the model's generate with up to four new tokens and a single returned sequence, then decodes the answer back to text.
  3. Parse the price. The generated text is messy, so a small helper plucks the number out of it (for example turning "Price is $1,800" into 1800).
  4. Score it. The Week 6 Tester harness runs the predict function over the 250 test points, colours each guess green or red by how close it is, and reports the average dollar error.
New to this? What a "test harness" is (the Tester recap)

A test harness is a small piece of code that runs your model over a fixed set of examples and reports how well it did, the same way for every model so comparisons are fair. The course's Tester class, first built in Week 6, takes a prediction function and the test data, loops over each item, compares the guess to the true price, prints each one in green (close) or red (far off), and at the end draws a chart and prints the average error. The Week 7 version is almost identical; the instructor notes one subtle change, that it reads a data point from the dataset rather than an Item object.

New to this? Parsing a number out of model text

The model does not hand back a tidy number; it hands back text such as "Price is $89.99" or "$1,800.00 for this item". Before we can score it we have to pull the number out. A small helper (the course calls it extract_price) scans the text, drops the dollar sign and commas, and returns the first number it finds as a plain value. If the model writes nothing number-like, it falls back to zero. This is a common, slightly boring step whenever a language model is used to produce a value your code needs to do maths on.

What you should see

In the video the base Llama 3.1, quantized to 4-bit, scores an average error of about $395. Re-running the exact same harness with 8-bit quantization instead gives about $301 — better, because 8 bits keep more information than 4, but still poor. For comparison, a model that just guesses the average training price is off by about $146, so the untouched base model is actually worse than guessing. That is the uncomfortable, motivating result: a tiny, heavily compressed model, with no training on our task, loses to a constant guess. The first test product (an OEM AC compressor that costs $374) is predicted at $1,800. Honesty note: these figures are read from the course video; this evaluation was not run here because it needs a GPU and a gated model.

Common gotchas
  • The model is gated. Llama is a gated model on Hugging Face: you must accept its licence on the model page and log in with a Hugging Face token before the download works. The code logs in with HF_TOKEN; without an accepted licence you get an access error, not the model.
  • It is slow on a CPU. Generating 250 times through an 8-billion-parameter model is painfully slow without a GPU. Run this in Google Colab on a GPU runtime, which is what the course does.
  • Do not read too much into one product. The first item being wildly wrong ($1,800 for a $374 part) is a bad omen, but the real verdict is the average over all 250 points, not any single guess.
Video vs repo — read this before the code

The code file below (week7/day2.py) is the current repository's version, and it is a newer re-recording of the course. It does not line up one-to-one with the video you just read about. The differences:

  • Model. The repo uses meta-llama/Llama-3.2-3B (3 billion parameters). The video uses Llama 3.1 8B. Treat the model id as a value you can swap.
  • Data. The repo loads a custom pricer.items.Item class and the ed-donner/items_full dataset, builds prompts, and pushes a new ed-donner/items_prompts_full dataset to the Hub. The video uses the Week 6 pricing dataset directly.
  • What the file actually does. This re-recorded day2.py is really the data-preparation step: load data, study the token lengths, decide a cutoff, turn each item into a prompt-and-completion pair, and upload the result. The base-model evaluation that this page teaches (load the model, model.predict, extract_price, the Tester and the ~$395 score) is what the video performs; it is described above in prose and diagrams rather than shown as code, because that evaluation code is not in the current repository file.
  • Frontier ids. The re-recording also refreshes the frontier model ids it compares against. Use whatever model still exists when you run it.

In short: learn the method (run the base model over the test set and get a starting error to beat) from the discussion above; read the file below to see how the re-recorded course prepares the data that the training in the next days will consume.

The repository code (day2.py)

Here is the current repository file exactly as it ships. It loads the data through the course's Item class, loads the Llama-3.2-3B tokenizer, looks at how many tokens each product description uses, picks a cutoff, turns every item into a prompt-and-completion pair, and pushes the prepared dataset back to the Hub.

import os
from dotenv import load_dotenv
from huggingface_hub import login
from pricer.items import Item
from tqdm.notebook import tqdm
from transformers import AutoTokenizer
import matplotlib.pyplot as plt


LITE_MODE = False

load_dotenv(override=True)
hf_token = os.environ['HF_TOKEN']
login(hf_token, add_to_git_credential=True)

username = "ed-donner"
dataset = f"{username}/items_lite" if LITE_MODE else f"{username}/items_full"

train, val, test = Item.from_hub(dataset)
items = train + val + test

print(f"Loaded {len(train):,} training items, {len(val):,} validation items, {len(test):,} test items")

BASE_MODEL = "meta-llama/Llama-3.2-3B"

tokenizer = AutoTokenizer.from_pretrained(BASE_MODEL)

token_counts = [item.count_tokens(tokenizer) for item in tqdm(items)]

plt.figure(figsize=(15, 6))
plt.title(f"Tokens in Summary: Avg {sum(token_counts)/len(token_counts):,.1f} and highest {max(token_counts):,}\n")
plt.xlabel('Number of tokens in summary')
plt.ylabel('Count')
plt.hist(token_counts, rwidth=0.7, color="skyblue", bins=range(0, 200, 10))
plt.show()

CUTOFF = 110
cut = len([count for count in token_counts if count > CUTOFF])
print(f"With this CUTOFF, we will truncate {cut:,} items which is {cut/len(items):.1%}")


print(train[0].summary)

for item in tqdm(train+val):
    item.make_prompts(tokenizer, CUTOFF, True)
for item in tqdm(test):
    item.make_prompts(tokenizer, CUTOFF, False)

print("PROMPT:")
print(test[0].prompt)
print("COMPLETION:")
print(test[0].completion)


prompt_token_counts = [item.count_prompt_tokens(tokenizer) for item in tqdm(items)]

plt.figure(figsize=(15, 6))
plt.title(f"Tokens: Avg {sum(prompt_token_counts)/len(prompt_token_counts):,.1f} and highest {max(prompt_token_counts):,}\n")
plt.xlabel('Number of tokens in prompt and the completion')
plt.ylabel('Count')
plt.hist(prompt_token_counts, rwidth=0.7, color="gold", bins=range(0, 200, 10))
plt.show()

username = "ed-donner"
dataset = f"{username}/items_prompts_lite" if LITE_MODE else f"{username}/items_prompts_full"

Item.push_prompts_to_hub(dataset, train, val, test)

Recap
  • Before any fine-tuning, measure the untouched base model so you have a starting score to beat; a model that cannot beat a constant guess has a lot to prove.
  • The method: load the base model, write a predict function, run it over the 250 test prompts, parse the price out of its text, and score the average dollar error with the Tester harness.
  • Llama 3.1 8B was chosen partly because its tokenizer maps a three-digit price to a single token, so predicting the price is predicting one next token well.
  • In the video the 4-bit base model scores about $395 average error ($301 at 8-bit) — worse than the $146 constant guess and far behind GPT-4o's $76. That gap is the week's challenge. (Not run here; it needs a GPU and a gated model.)
