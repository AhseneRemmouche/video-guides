Week 5 · Day 4 — The Full RAG Pipeline in LangChain

Put it together: a retriever finds the relevant chunks, the LLM answers from them, and conversation memory keeps the chat coherent - the complete RAG chain.

Companion to Ed Donner's course · uv setup · Python + TypeScript/React · code verified against the repo

Everything in Week 5 has been building to this page. You loaded the documents, split them into chunks, embedded them, and stored the vectors. Now you wire the last pieces together and get a working RAG pipeline: you type a question, a retriever pulls the most relevant chunks out of the vector store, those chunks are dropped into the prompt as context, the model answers using them, and conversation memory keeps a multi-turn chat coherent. The instructor calls it a knowledge worker for the fictional insurance company Insurellm, and he is right that it is "stupid easy" once the earlier pieces are in place.

On the Python side this is done with LangChain, which wraps the three moving parts into small objects and glues them together with one chain. On the TypeScript side we build the same flow by hand with LangChain.js, so you can see exactly what the chain does under the covers. The two versions do the same job; the code-tabs below let you read either one.

New to retrievers? What a retriever is and why we need one

A retriever is the component that takes a question and returns the handful of chunks most likely to answer it. It works by semantic search: it turns your question into the same kind of vector (a list of numbers that captures meaning) that the chunks were turned into, then finds the chunks whose vectors sit closest to the question's vector. Because it compares meaning, not letters, it can match "auto insurance" to a document that only ever says "car cover". In the Python code you do not build the retriever from scratch — you take the vector store you already created and call as_retriever() on it, and LangChain wraps it in the standard retriever interface.

New to the RAG chain? How retrieve, stuff, and answer fit together

RAG stands for Retrieval-Augmented Generation. "Retrieval" is the retriever finding chunks; "augmented" means those chunks are added to the prompt; "generation" is the model writing the answer. The key idea is that the model answers from text you handed it in the prompt, not only from what it learned during training. That is why it can talk accurately about your private documents and stay up to date: change the knowledge base and the answers change, with no retraining. If the answer is not in the retrieved chunks, a good system prompt tells the model to say it does not know rather than guess.

New to conversation memory? Why follow-up questions work

Conversation memory is how the assistant remembers earlier turns. Without it, "What did she do before?" is meaningless — the model has no idea who "she" is. Memory keeps the earlier messages and sends them along with the new question, so the model can resolve "she" to a person mentioned a moment ago. In the Python version LangChain's ConversationBufferMemory stores the turns for you and the chain replays them on every call. In the TypeScript version there is no memory object: the caller passes the earlier turns in as a history array, and we turn them into messages ourselves. Same effect, built two different ways.

New to returning sources? Why the answer carries its documents

A RAG answer is only trustworthy if you can check it. That is why the TypeScript version returns not just the text but a sources list — the filenames of the documents the chunks came from. The retriever stores each chunk's origin in its metadata.source, so after retrieving we collect those filenames, remove duplicates, and hand them back. The chat UI can then show "answered from: employees/avery.md", which lets a reader verify the claim and builds trust in the system.

Here is the complete code in both languages. Python uses the LangChain chain; TypeScript builds the same flow step by step. Use the switch to read whichever you prefer.

import os
import glob
from dotenv import load_dotenv
import gradio as gr

from langchain.document_loaders import DirectoryLoader, TextLoader
from langchain.text_splitter import CharacterTextSplitter
from langchain_openai import OpenAIEmbeddings, ChatOpenAI
from langchain_chroma import Chroma
from langchain.memory import ConversationBufferMemory
from langchain.chains import ConversationalRetrievalChain

MODEL = "gpt-4o-mini"
db_name = "vector_db"

load_dotenv(override=True)

# Load every Markdown file in the knowledge base, tagging each with its folder name.
folders = glob.glob("knowledge-base/*")
documents = []
for folder in folders:
    doc_type = os.path.basename(folder)
    loader = DirectoryLoader(folder, glob="**/*.md", loader_cls=TextLoader)
    folder_docs = loader.load()
    for doc in folder_docs:
        doc.metadata["doc_type"] = doc_type
        documents.append(doc)

# Split the documents into overlapping chunks (about 123 chunks here).
text_splitter = CharacterTextSplitter(chunk_size=1000, chunk_overlap=200)
chunks = text_splitter.split_documents(documents)
print(f"Total number of chunks: {len(chunks)}")

# Embed every chunk and store the vectors in Chroma (each vector has 1536 dimensions).
embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
if os.path.exists(db_name):
    Chroma(persist_directory=db_name, embedding_function=embeddings).delete_collection()
vectorstore = Chroma.from_documents(documents=chunks, embedding=embeddings, persist_directory=db_name)
print(f"Vectorstore created with {vectorstore._collection.count()} documents")

# The four lines that build the whole RAG pipeline.
llm = ChatOpenAI(temperature=0.7, model_name=MODEL)
memory = ConversationBufferMemory(memory_key="chat_history", return_messages=True)
retriever = vectorstore.as_retriever()
conversation_chain = ConversationalRetrievalChain.from_llm(llm=llm, retriever=retriever, memory=memory)

# Ask one question to prove it works end to end.
query = "Can you describe Insurellm in a few sentences"
result = conversation_chain.invoke({"question": query})
print(result["answer"])


# Wrap the same chain in a Gradio chat UI. We ignore Gradio's own `history`
# argument because the chain's memory already tracks the conversation.
def chat(message, history):
    result = conversation_chain.invoke({"question": message})
    return result["answer"]


gr.ChatInterface(chat, type="messages").launch()
// Day 4 / Day 5 - The RAG pipeline (TypeScript port of the knowledge-worker project)
//
// The Python course wired a retriever + an LLM + conversation history into a
// ConversationalRetrievalChain and served it with Gradio. Here we build the same
// pieces with LangChain.js and expose a single `answer(question, history)` function
// that the Hono server and the `npm run ask` CLI both reuse.
//
//   retriever (MemoryVectorStore.asRetriever) -> context -> ChatOpenAI (gpt-4o-mini) -> answer
//
// Key-guarded: it imports cleanly with no API key; answer() only needs one at call time.
import "dotenv/config";
import { pathToFileURL } from "node:url";
import { ChatOpenAI } from "@langchain/openai";
import { SystemMessage, HumanMessage, AIMessage, type BaseMessage } from "@langchain/core/messages";
import type { Document } from "@langchain/core/documents";
import type { MemoryVectorStore } from "langchain/vectorstores/memory";
import { buildVectorStore, hasOpenAIKey } from "./ingest.js";

export const MODEL = "gpt-4o-mini";
export const RETRIEVAL_K = 4;

export type ChatMessage = { role: "user" | "assistant"; content: string };
export type RagAnswer = { answer: string; sources: string[] };

const SYSTEM_PROMPT = `You are a knowledgeable, friendly assistant representing the company Insurellm.
You are chatting with a user about Insurellm, its employees and its products.
Answer only from the context extracts provided below. Be accurate, relevant and complete.
If the answer is not in the context, say you don't know.

Context:
{context}`;

// Build the store once and reuse it across calls (embedding every request would be wasteful).
let storePromise: Promise<MemoryVectorStore> | null = null;
function getStore(): Promise<MemoryVectorStore> {
  if (!storePromise) storePromise = buildVectorStore();
  return storePromise;
}

// Turn the stored {role, content} history into LangChain message objects.
function toHistoryMessages(history: ChatMessage[]): BaseMessage[] {
  return history.map((m) =>
    m.role === "assistant" ? new AIMessage(m.content) : new HumanMessage(m.content),
  );
}

// AIMessage.content can be a string or an array of content parts; normalise to a string.
function contentToString(content: BaseMessage["content"]): string {
  if (typeof content === "string") return content;
  return content
    .map((part) => (typeof part === "string" ? part : "text" in part ? part.text : ""))
    .join("");
}

// Retrieve the most relevant chunks for a question.
export async function retrieve(question: string, k: number = RETRIEVAL_K): Promise<Document[]> {
  const store = await getStore();
  const retriever = store.asRetriever(k);
  return retriever.invoke(question);
}

// The core RAG call: retrieve context, stuff it into the system prompt, ask the model.
export async function answer(question: string, history: ChatMessage[] = []): Promise<RagAnswer> {
  if (!hasOpenAIKey()) {
    throw new Error("OPENAI_API_KEY is not set - the RAG pipeline needs it. See .env.example.");
  }

  const docs = await retrieve(question);
  const context = docs
    .map((d) => `Extract from ${d.metadata.source ?? "unknown"}:\n${d.pageContent}`)
    .join("\n\n");

  const llm = new ChatOpenAI({ model: MODEL, temperature: 0.2 });
  const messages: BaseMessage[] = [
    new SystemMessage(SYSTEM_PROMPT.replace("{context}", context)),
    ...toHistoryMessages(history),
    new HumanMessage(question),
  ];

  const reply = await llm.invoke(messages);

  // De-duplicate the source filenames so the UI can show which docs were used.
  const sources = [...new Set(docs.map((d) => String(d.metadata.source ?? "unknown")))];
  return { answer: contentToString(reply.content), sources };
}

async function main(): Promise<void> {
  const question = process.argv.slice(2).join(" ") || "Who won the IIOTY award?";
  if (!hasOpenAIKey()) {
    console.log("OPENAI_API_KEY not set - this demo needs it. See .env.example.");
    console.log(`Would ask: "${question}"`);
    return;
  }
  console.log(`Q: ${question}`);
  const { answer: a, sources } = await answer(question);
  console.log(`\nA: ${a}`);
  console.log(`\nSources: ${sources.join(", ")}`);
}

// Only run the demo when executed directly (npm run ask), not when imported.
if (import.meta.url === pathToFileURL(process.argv[1] ?? "").href) {
  main().catch((err) => {
    console.error(err);
    process.exitCode = 1;
  });
}

The headline of the lesson is that the pipeline is built in four lines (lines 42–45): an LLM object, a memory object, a retriever, and the chain that ties them together. Everything above those lines is the document loading and embedding you already did on earlier days; everything below is using the chain.

ConversationalRetrievalChain vs doing it by hand. In Python the chain hides the work: you never see the question get embedded, the chunks get retrieved, or the prompt get built. That is the point of LangChain — four lines and you are done. The trade-off is that the mechanics are out of sight. The TypeScript version on the other tab does the same steps in the open, which is the best way to understand what the chain is actually doing.

The TypeScript port uses LangChain.js but does not use a ready-made chain. It builds the flow by hand in an answer(question, history) function: retrieve the chunks, stuff them into the system prompt, add the history, call ChatOpenAI, and return an object with the answer and its sources. Reading it is the clearest way to see what the Python chain does under the covers.

Memory vs passing history. Python hands memory to the chain and never thinks about it again — the chain stores each turn and replays it. TypeScript has no memory object: whoever calls answer(question, history) owns the history and passes it in each time, and toHistoryMessages converts it to messages. Both reach the same result; one hides the history, the other keeps it in your hands.
What you should see. After the four lines run, nothing dramatic happens — the chain is just built. The payoff is the next call: invoke({"question": query}) returns a dictionary, and result["answer"] holds a few sentences about Insurellm, pulled from the company documents. In the Gradio chat you can then ask a follow-up like "What did she do before?" and, because of memory, the assistant knows "she" is Avery and answers from her employee record. The TypeScript npm run ask "your question" prints the answer followed by the list of source files it used.
Common mistakes. Retrieving too few chunks (a small k) can miss the one passage that holds the answer, so the model says it does not know. Retrieving too many wastes context-window space, costs more, and can bury the useful chunk among irrelevant ones — start around k = 4 and adjust. The other classic slip is losing memory: if you rebuild or re-run the chain between turns (or forget to pass history in TypeScript), the assistant forgets everything and follow-up questions with "she" or "it" stop making sense. In Gradio, re-running the cell is how you deliberately clear the memory and start fresh.
Video vs repo. The video builds the pipeline with LangChain's ConversationalRetrievalChain and ConversationBufferMemory — the four-line version shown here, which is what you see on screen. The current repo has since refactored the same project: it splits retrieval, answering and evaluation into separate modules and adds extras such as query rewriting and re-ranking (you meet those on Day 5). The idea is identical; only the packaging changed. As always, treat the model name gpt-4o-mini as a value you may need to swap, since providers retire models over time.
Recap
  • A full RAG chain does four things per question: the retriever finds the nearest chunks, the chunks are stuffed into the prompt as context, the model answers from them, and memory keeps a multi-turn chat coherent.
  • In Python it is four lines: an llm, a memory, a retriever, and a ConversationalRetrievalChain.from_llm(...) that ties them together. You drive it with invoke({"question": q}) and read result["answer"].
  • In TypeScript the same flow is written by hand in answer(question, history): retrieve, build the context and messages, call ChatOpenAI, and return { answer, sources }.
  • Memory (Python) and the history argument (TypeScript) are two ways to the same end: letting follow-up questions refer back to earlier turns.
  • Tune k carefully — too few chunks miss the answer, too many waste the context window — and do not lose the memory between turns.
  • The API and embedding calls are shown exactly as in the course and were not run live here; the TypeScript project type-checks and builds.
