Week 5 · Day 4 — The Full RAG Pipeline in LangChain

Put it together: a retriever finds the relevant chunks, the LLM answers from them, and conversation memory keeps the chat coherent - the complete RAG chain.

Companion to Ed Donner's course · uv setup · Python + TypeScript/React · code verified against the repo

Everything in Week 5 has been building to this page. You loaded the documents, split them into chunks, embedded them, and stored the vectors. Now you wire the last pieces together and get a working RAG pipeline: you type a question, a retriever pulls the most relevant chunks out of the vector store, those chunks are dropped into the prompt as context, the model answers using them, and conversation memory keeps a multi-turn chat coherent. The instructor calls it a knowledge worker for the fictional insurance company Insurellm, and he is right that it is "stupid easy" once the earlier pieces are in place.

On the Python side this is done with LangChain, which wraps the three moving parts into small objects and glues them together with one chain. The TypeScript port uses the same three objects and the same chain from LangChain.js.

New to retrievers? What a retriever is and why we need one

A retriever is the component that takes a question and returns the handful of chunks most likely to answer it. It works by semantic search: it turns your question into the same kind of vector (a list of numbers that captures meaning) that the chunks were turned into, then finds the chunks whose vectors sit closest to the question's vector. Because it compares meaning, not letters, it can match "auto insurance" to a document that only ever says "car cover". In the Python code you do not build the retriever from scratch — you take the vector store you already created and call as_retriever() on it, and LangChain wraps it in the standard retriever interface.

New to the RAG chain? How retrieve, stuff, and answer fit together

RAG stands for Retrieval-Augmented Generation. "Retrieval" is the retriever finding chunks; "augmented" means those chunks are added to the prompt; "generation" is the model writing the answer. The key idea is that the model answers from text you handed it in the prompt, not only from what it learned during training. That is why it can talk accurately about your private documents and stay up to date: change the knowledge base and the answers change, with no retraining. If the answer is not in the retrieved chunks, a good system prompt tells the model to say it does not know rather than guess.

New to conversation memory? Why follow-up questions work

Conversation memory is how the assistant remembers earlier turns. Without it, "What did she do before?" is meaningless — the model has no idea who "she" is. Memory keeps the earlier messages and sends them along with the new question, so the model can resolve "she" to a person mentioned a moment ago. In the Python version LangChain's ConversationBufferMemory stores the turns for you and the chain replays them on every call. In the TypeScript port LangChain.js's BufferMemory does the same job.

New to returning sources? Why the answer carries its documents

A RAG answer is only trustworthy if you can check it. The chain in the video returns just the answer, but every retrieved chunk carries its origin in metadata["source"] (the file path the loader recorded), so a system can hand back the documents it used. Ed's current repository does exactly that: its chat window shows the retrieved context, with each chunk's source file, next to the answer, which lets a reader verify the claim.

import os
import glob
from dotenv import load_dotenv
import gradio as gr

# imports for langchain

from langchain.document_loaders import DirectoryLoader, TextLoader
from langchain.text_splitter import CharacterTextSplitter
from langchain.schema import Document
from langchain_openai import OpenAIEmbeddings, ChatOpenAI
from langchain_chroma import Chroma
import numpy as np
from sklearn.manifold import TSNE
import plotly.graph_objects as go
from langchain.memory import ConversationBufferMemory
from langchain.chains import ConversationalRetrievalChain

# price is a factor for our company, so we're going to use a low cost model

MODEL = "gpt-4o-mini"
db_name = "vector_db"

# Load environment variables in a file called .env

load_dotenv()
os.environ['OPENAI_API_KEY'] = os.getenv('OPENAI_API_KEY', 'your-key-if-not-using-env')

# Read in documents using LangChain's loaders
# Take everything in all the sub-folders of our knowledgebase

folders = glob.glob("knowledge-base/*")

documents = []
for folder in folders:
    doc_type = os.path.basename(folder)
    loader = DirectoryLoader(folder, glob="**/*.md", loader_cls=TextLoader)
    folder_docs = loader.load()
    for doc in folder_docs:
        doc.metadata["doc_type"] = doc_type
        documents.append(doc)

text_splitter = CharacterTextSplitter(chunk_size=1000, chunk_overlap=200)
chunks = text_splitter.split_documents(documents)

len(chunks)

doc_types = set(chunk.metadata['doc_type'] for chunk in chunks)
print(f"Document types found: {', '.join(doc_types)}")

# Put the chunks of data into a Vector Store that associates a Vector Embedding with each chunk
# Chroma is a popular open source Vector Database based on SQLLite

embeddings = OpenAIEmbeddings()

# Delete if already exists

if os.path.exists(db_name):
    Chroma(persist_directory=db_name, embedding_function=embeddings).delete_collection()

# Create vectorstore

vectorstore = Chroma.from_documents(documents=chunks, embedding=embeddings, persist_directory=db_name)
print(f"Vectorstore created with {vectorstore._collection.count()} documents")

# Get one vector and find how many dimensions it has

collection = vectorstore._collection
sample_embedding = collection.get(limit=1, include=["embeddings"])["embeddings"][0]
dimensions = len(sample_embedding)
print(f"The vectors have {dimensions:,} dimensions")

# create a new Chat with OpenAI
llm = ChatOpenAI(temperature=0.7, model_name=MODEL)

# set up the conversation memory for the chat
memory = ConversationBufferMemory(memory_key='chat_history', return_messages=True)

# the retriever is an abstraction over the VectorStore that will be used during RAG
retriever = vectorstore.as_retriever()

# putting it together: set up the conversation chain with the GPT 3.5 LLM, the vector store and memory
conversation_chain = ConversationalRetrievalChain.from_llm(llm=llm, retriever=retriever, memory=memory)

query = "Can you describe Insurellm in a few sentences"
result = conversation_chain.invoke({"question":query})
print(result["answer"])

# Wrapping that in a function

def chat(message, history):
    result = conversation_chain.invoke({"question": message})
    return result["answer"]

// Video 10 in TypeScript: the RAG pipeline - LLM, memory, retriever, chain (run: npx tsx day4_rag.ts)
import "dotenv/config";
import { readdirSync, statSync } from "node:fs";
import { basename, join } from "node:path";
import { createInterface } from "node:readline/promises";
import { DirectoryLoader } from "@langchain/classic/document_loaders/fs/directory";
import { TextLoader } from "@langchain/classic/document_loaders/fs/text";
import { MemoryVectorStore } from "@langchain/classic/vectorstores/memory";
import { BufferMemory } from "@langchain/classic/memory";
import { ConversationalRetrievalQAChain } from "@langchain/classic/chains";
import { CharacterTextSplitter } from "@langchain/textsplitters";
import { ChatOpenAI, OpenAIEmbeddings } from "@langchain/openai";
import type { Document } from "@langchain/core/documents";

const MODEL = "gpt-6-luna";

// Load, split and embed exactly as on Days 2 and 3
const folders = readdirSync("knowledge-base")
  .map((name) => join("knowledge-base", name))
  .filter((path) => statSync(path).isDirectory());

const documents: Document[] = [];
for (const folder of folders) {
  const loader = new DirectoryLoader(folder, { ".md": (path) => new TextLoader(path) });
  for (const doc of await loader.load()) {
    doc.metadata.doc_type = basename(folder);
    documents.push(doc);
  }
}
const chunks = await new CharacterTextSplitter({ chunkSize: 1000, chunkOverlap: 200 }).splitDocuments(documents);
const embeddings = new OpenAIEmbeddings({ model: "text-embedding-3-small" });
const vectorstore = await MemoryVectorStore.fromDocuments(chunks, embeddings); // in memory instead of Chroma
console.log(`Vectorstore created with ${vectorstore.memoryVectors.length} documents`);

// create a new Chat with OpenAI (no temperature: newer GPT models may not accept a custom one)
const llm = new ChatOpenAI({ model: MODEL, reasoning: { effort: "none" } });

// set up the conversation memory for the chat
const memory = new BufferMemory({ memoryKey: "chat_history", returnMessages: true });

// the retriever is an abstraction over the VectorStore that will be used during RAG
const retriever = vectorstore.asRetriever();

// putting it together: the conversation chain with the LLM, the retriever and the memory
const conversationChain = ConversationalRetrievalQAChain.fromLLM(llm, retriever, { memory });

const query = "Can you describe Insurellm in a few sentences";
const result = await conversationChain.invoke({ question: query });
console.log(result.text); // LangChain.js calls the answer "text" (Python: "answer")

// A terminal chat instead of Gradio; the chain's memory keeps the conversation
const rl = createInterface({ input: process.stdin, output: process.stdout });
while (true) {
  const message = await rl.question("You: ");
  if (!message.trim()) break;
  const reply = await conversationChain.invoke({ question: message });
  console.log(reply.text);
}
rl.close();

What you should see. After the four lines run, nothing dramatic happens: the chain is just built. The payoff is the next call: invoke({"question": query}) returns a dictionary, and result["answer"] holds a few sentences about Insurellm, pulled from the company documents. (lower case, first name only) gets "Before founding Insurellm, Avery Lancaster worked as a Senior Product Manager at Innovate Insurance Solutions…", straight from her HR record, something Day 1's keyword matcher could never find. The TypeScript port prints the store size and the first answer, then waits for your questions in the terminal.
Common mistakes. Retrieving too few chunks (a small k) can miss the one passage that holds the answer, so the model says it does not know. Retrieving too many wastes context-window space, costs more, and can bury the useful chunk among irrelevant ones — the default is k = 4; Day 5 shows what happens when that is too few. The other classic slip is losing memory: if you rebuild or re-run the chain between turns (or forget to pass history in TypeScript), the assistant forgets everything and follow-up questions with "she" or "it" stop making sense. In Gradio, re-running the cell is how you deliberately clear the memory and start fresh.

Recap
  • A full RAG chain does four things per question: the retriever finds the nearest chunks, the chunks are stuffed into the prompt as context, the model answers from them, and memory keeps a multi-turn chat coherent.
  • In Python it is four lines: an llm, a memory, a retriever, and a ConversationalRetrievalChain.from_llm(...) that ties them together. You drive it with invoke({"question": q}) and read result["answer"].
  • In TypeScript, LangChain.js has the same pieces: ChatOpenAI, BufferMemory, asRetriever() and ConversationalRetrievalQAChain.fromLLM, with the answer in result.text.
  • Memory is what lets follow-up questions refer back to earlier turns, which is why the Gradio chat function can ignore its history argument.
  • Tune k carefully — too few chunks miss the answer, too many waste the context window — and do not lose the memory between turns.
  • The API and embedding calls need a paid key and were not run live here; the "As in the video" code is shown exactly as recorded, and the "Runs today" and TypeScript code was checked against today's library versions.
