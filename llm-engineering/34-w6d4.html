Week 6 · Day 4 — How Well Do Frontier Models Price?

Test GPT-4o-mini and Claude on the pricing task out of the box, compare them with the baselines and with humans, and see where frontier models shine.

Companion to Ed Donner's course · uv setup · Python + TypeScript/React · code verified against the repo

For three days you built the slow, careful way to price a product: curate a dataset, engineer features, train a model on 400,000 examples. Today the instructor does something that feels almost like cheating. He takes the test data, hands each product description straight to a frontier model, and asks it to guess the price — no training at all. The question for the day is simple: how well do GPT‑4o and Claude price things out of the box, and can a model with zero task training beat the traditional machine‑learning models that studied hundreds of thousands of examples?

To answer that fairly you need a referee, so this session also introduces the course's test harness: a small reusable piece of code that runs any price‑predicting function over the same test set, scores each guess, colours it green / yellow / red by how far off it was, and prints one headline number plus a chart. The same harness scored the Day 3 baselines; now it scores a human, then the frontier models, so every result sits on the same scale. Everything here is a dress rehearsal for tomorrow, when we finally start fine‑tuning.

Numbers here are the course's, not reproduced. The pricing calls cost money and need paid API keys, so none of this was run live for the guide. Every dollar figure and hit rate below is quoted from what the instructor saw on screen. Treat the model ids the same way you treat any API value: companies retire models, so you may need to swap gpt-4o-mini for whatever is current when you run it.

The big idea: pricing with zero training

The traditional models from Day 3 learned a mapping from text to price by looking at 400,000 training examples. A frontier model is handed none of them. Instead you give it only the test item and lean entirely on the world knowledge already baked into its billions of parameters. The instructor frames it as finishing a sentence: show the model a product and nudge it toward completing “this product is worth $…”, and it will fill in the most plausible next token, which turns out to be a sensible price. That is what zero‑shot or out‑of‑the‑box use means: solving a task the model was never specifically trained for, using nothing but a good prompt.

New to zero-shot / out-of-the-box use? What it means

Zero‑shot means you ask the model to do a task without giving it any worked examples and without any extra training. You rely on the general knowledge it picked up during its original training. It is the opposite of what you did with the traditional models, which had to be trained on this specific pricing task before they could say anything useful.

Why would a general chat model be any good at pricing car parts and chandeliers? Because somewhere in its enormous training data it has seen countless prices, product listings and reviews, so it has a rough sense of what a tyre, a headlamp or a shower faucet costs. The instructor flags one honest caveat: because the training data was so vast, the model might have seen these exact products before (he calls this test‑data contamination). He saw no strong sign of it — the model almost never nails a price exactly — but it is worth keeping in mind.

The test harness: a fair referee for every model

Before comparing anything, the instructor reuses a piece of code he wrote earlier and clearly loves: a test harness. In the videos it is a class he calls Tester; he has since moved it into its own Python module so every notebook can import it. You call it with one thing — a function that takes an item and returns a predicted price — plus the test dataset. It then runs that function over the first chunk of test items, compares each prediction to the true price, and reports the results both as numbers and as a picture.

The picture is the clever part. Each prediction becomes a coloured dot: green when the guess is close, yellow when it is middling, and red when it is badly off. At a glance a wall of green means a model is doing well and a wall of red means it is not. Underneath, the harness prints the headline evaluation metric — the average error in dollars — and a hit rate, the share of guesses that landed in the green. In this guide's code the same harness is imported as a function called evaluate.

New to a test harness? Why write one

A test harness is a small, reusable program whose only job is to measure how well something else works. You write it once, then point it at every candidate solution so they are all judged by exactly the same yardstick. Here the yardstick is: “given these product descriptions, how close are your predicted prices to the real ones?”

The win is consistency and honesty. Because the human, the Day 3 baselines and the frontier models all go through the same harness over the same test items, their scores are directly comparable — nobody gets an easier test. The instructor strongly recommends building a harness like this for any real business problem, and scoring against as many business‑relevant metrics as you can.

How is the error measured?

The headline number is an average error in dollars: for each test item the harness takes the gap between the predicted price and the true price, and averages those gaps across all the items it scored. Lower is better, and because it is in plain dollars it is easy to reason about (“on average I am about $80 off”).

The colour of each dot and the hit rate come from how close a single guess was: a small enough gap is a green “hit”, a medium gap is yellow, and a large gap is red. The instructor does not spell out the exact thresholds on screen, so treat green / yellow / red as “close / so‑so / way off” rather than precise cut‑offs. One honest wrinkle: a single wildly wrong guess (Claude once predicted $4,999.99 for a $495.95 item) can drag the average up, even though it is only one dot out of hundreds.

A surprise baseline: a human

Before any frontier model, the instructor adds one more baseline he says nearly broke him: a human. He wrote out the first 250 test prompts to a CSV file, then sat and guessed every price by hand — wheels, refurbished computers, chandeliers and all — and read his guesses back in. A tiny human_pricer function looks up his guess for a given item, so the human can be scored by the same harness as everything else. The result: an average error of $127 with a 32% hit rate. Respectable, and better than guessing the average price every time ($146) and better than a bare linear‑regression baseline ($139), but comfortably beaten by the better Day 3 models.

The code

Here is the repo's week6/day4.py in full. It does three jobs in order: it scores the human baseline, it trains and scores one more traditional baseline (a small PyTorch neural network, carried over from the Day 3 line of work), and then it reaches the frontier — defining one tiny function per model and feeding each into the same evaluate harness. The file is long, so after the listing we walk through the parts that matter most: turning an item into a prompt, calling a model, and scoring it.

import os

from sklearn.model_selection import train_test_split

LITE_MODE = False

load_dotenv(override=True)
hf_token = os.environ['HF_TOKEN']
login(hf_token, add_to_git_credential=True)

username = "ed-donner"
dataset = f"{username}/items_lite" if LITE_MODE else f"{username}/items_full"

train, val, test = Item.from_hub(dataset)

print(f"Loaded {len(train):,} training items, {len(val):,} validation items, {len(test):,} test items")

# Write the test set to a CSV

with open('human_in.csv', 'w', encoding="utf-8") as csvfile:
    writer = csv.writer(csvfile)
    for t in test[:100]:
        writer.writerow([t.summary, 0])

# Read it back in

human_predictions = []
with open('human_out.csv', 'r', encoding="utf-8") as csvfile:
    reader = csv.reader(csvfile)
    for row in reader:
        human_predictions.append(float(row[1]))

def human_pricer(item):
    idx = test.index(item)
    return human_predictions[idx]

human = human_pricer(test[0])
actual = test[0].price
print(f"Human predicted {human} for an item that actually costs {actual}")


evaluate(human_pricer, test, size=100)

# Prepare our documents and prices

y = np.array([float(item.price) for item in train])
documents = [item.summary for item in train]

# Use the HashingVectorizer for a Bag of Words model
# Using binary=True with the CountVectorizer makes "one-hot vectors"

np.random.seed(42)
vectorizer = HashingVectorizer(n_features=5000, stop_words='english', binary=True)
X = vectorizer.fit_transform(documents)

# Define the neural network - here is Pytorch code to create a 8 layer neural network

class NeuralNetwork(nn.Module):
    def __init__(self, input_size):
        super(NeuralNetwork, self).__init__()
        self.layer1 = nn.Linear(input_size, 128)
        self.layer2 = nn.Linear(128, 64)
        self.layer3 = nn.Linear(64, 64)
        self.layer4 = nn.Linear(64, 64)
        self.layer5 = nn.Linear(64, 64)
        self.layer6 = nn.Linear(64, 64)
        self.layer7 = nn.Linear(64, 64)
        self.layer8 = nn.Linear(64, 1)
        self.relu = nn.ReLU()

    def forward(self, x):
        output1 = self.relu(self.layer1(x))
        output2 = self.relu(self.layer2(output1))
        output3 = self.relu(self.layer3(output2))
        output4 = self.relu(self.layer4(output3))
        output5 = self.relu(self.layer5(output4))
        output6 = self.relu(self.layer6(output5))
        output7 = self.relu(self.layer7(output6))
        output8 = self.layer8(output7)
        return output8

# Convert data to PyTorch tensors
X_train_tensor = torch.FloatTensor(X.toarray())
y_train_tensor = torch.FloatTensor(y).unsqueeze(1)

# Split the data into training and validation sets
X_train, X_val, y_train, y_val = train_test_split(X_train_tensor, y_train_tensor, test_size=0.01, random_state=42)

# Create the loader
train_dataset = TensorDataset(X_train, y_train)
train_loader = DataLoader(train_dataset, batch_size=64, shuffle=True)

# Initialize the model
input_size = X_train_tensor.shape[1]
model = NeuralNetwork(input_size)

trainable_params = sum(p.numel() for p in model.parameters() if p.requires_grad)

print(f"Number of trainable parameters: {trainable_params:,}")

# Define loss function and optimizer

loss_function = nn.MSELoss()
optimizer = optim.Adam(model.parameters(), lr=0.001)

# We will do 2 complete runs through the data

EPOCHS = 2

for epoch in range(EPOCHS):
    model.train()
    for batch_X, batch_y in tqdm(train_loader):
        optimizer.zero_grad()

        # The next 4 lines are the 4 stages of training: forward pass, loss calculation, backward pass, optimize
        
        outputs = model(batch_X)
        loss = loss_function(outputs, batch_y)
        loss.backward()
        optimizer.step()

    model.eval()
    with torch.no_grad():
        val_outputs = model(X_val)
        val_loss = loss_function(val_outputs, y_val)

    print(f'Epoch [{epoch+1}/{EPOCHS}], Train Loss: {loss.item():.3f}, Val Loss: {val_loss.item():.3f}')

def neural_network(item):
    model.eval()
    with torch.no_grad():
        vector = vectorizer.transform([item.summary])
        vector = torch.FloatTensor(vector.toarray())
        result = model(vector)[0].item()
    return max(0, result)

evaluate(neural_network, test)

Model-centric metrics, previewed

Everything today is scored with two model‑centric metrics: average dollar error and hit rate. They describe how good the model's numbers are, in isolation, on a held‑out test set. That is exactly what you want while comparing candidates and, from tomorrow, while watching a fine‑tune improve.

Keep in mind these are different from business metrics (did the pricing make the company money? did customers convert?). The instructor's advice is to track as many business‑relevant measures as you can, but during development a clean model‑centric score like “average error in dollars” is the fast, honest signal you iterate against.

Parsing a price out of free text. The prompt asks for “just the price”, but a model may still reply “The price is roughly $99.99 because…”. If you call float() on that whole string it throws ValueError. That is why the course extracts the first number from the reply (the video's get_price helper; in the repo this lives inside evaluate). Always assume a language model will add words you did not ask for, and parse defensively. A reply with no number at all should fall back to 0 rather than crashing the whole test run.

The headline is striking: GPT‑4o‑mini, with no training at all, beat the Random Forest that had studied 400,000 examples, and GPT‑4o edged ahead of it again. The instructor is careful not to oversell the gap between mini and full GPT‑4o — just a few dollars — because prices are genuinely volatile (sales, different stores) so some error is baked into the problem. Claude did well too but landed a touch behind, dragged partly by one wildly high guess. The lesson he draws: frontier models are so capable out of the box that they can crack problems that do not even look like text problems — a numeric regression — and still win.

What you should see. Each evaluate(…) call prints a stream of coloured dots, then a headline average error in dollars and a hit rate, then a chart. The human comes in around $127 error with a 32% hit rate; gpt-4o-mini around $80 with 52% green; gpt-4o a little better at about $76 and 58%; Claude a touch behind GPT‑4o‑mini. The GPT models give the same answer when re‑run (the video used a seed); Claude's will drift because it has no seed.
Watch the cost of a full test run. One pass of gpt-4o-mini over all 250 items is almost free — the instructor says it cost less than a fraction of a cent. gpt-4o is pricier: about $0.10–$0.20 per full run. Not bank‑breaking, but do not loop it a hundred times while debugging. Run it once to see the result, keep max_tokens small (you only need a short number back), and reuse the seed so repeat runs are reproducible rather than fresh paid calls you did not need.

Recap
  • Zero‑shot pricing: hand a frontier model only the test item and ask for a price — no training, just its world knowledge completing “this product is worth $…”.
  • The test harness (the video's Tester, the repo's evaluate) scores any predictor over the same test set, colours each guess green / yellow / red, and reports an average dollar error and a hit rate — so human, baselines and frontier models are all judged alike.
  • Each model is one tiny function that builds the prompt with messages_for, calls completion with a model= string, and returns the reply; the harness does the price extraction and comparison.
  • The results: GPT‑4o‑mini (~$80, zero‑shot) beat the Random Forest ($97) that trained on 400,000 examples; GPT‑4o was best (~$76); the human managed $127; Claude landed roughly level with Random Forest.
  • Be careful parsing a price from free text (parse defensively, fall back to 0) and watch the cost of running the whole test set; keep outputs short, reuse a seed, and do not loop paid runs needlessly.
