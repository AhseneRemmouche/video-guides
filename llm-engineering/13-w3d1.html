Week 3 · Day 1 — The HuggingFace Hub and Google Colab

Explore the HuggingFace Hub (models, datasets, spaces), set up a free Google Colab GPU notebook, and add your HuggingFace token as a Colab secret.

Welcome to Week 3. The first two weeks were about frontier models that live behind a company's API — you sent a prompt to OpenAI, Anthropic or Google and read the answer back. This week the models come to you: you download open-source models and run them yourself. To do that you need two new things, and this page sets them both up. The first is Hugging Face, the home of open-source AI. The second is Google Colab, a free cloud computer with a graphics card powerful enough to run those models. There is almost no code today — it is a setup and concepts day, so that from Day 2 onward you can focus on the models themselves.

What Hugging Face is

The instructor calls Hugging Face "ubiquitous" — it is used right across the open-source data-science community. A useful shorthand many people use is that it is the "GitHub of AI": just as GitHub is where the world keeps and shares code, Hugging Face is where the world keeps and shares AI models and data. In fact, under the covers the Hugging Face platform really is built on a pile of Git repositories, which is why downloading a model feels like pulling files from Git.

Hugging Face offers two big things. First, a platform (a website you log into at huggingface.co), which it calls the Hub. Second, a set of libraries — ready-made code you install and import — that do the heavy lifting of downloading and running those models. We meet the platform today and start using the libraries from Day 2.

New to this? What exactly is Hugging Face?

Hugging Face is a company and an online community for open-source artificial intelligence. "Open source" means the models and data are shared publicly for anyone to download, inspect and use, rather than hidden behind one company's paid service. Think of it as a giant public library of AI: hundreds of thousands of ready-trained models you can fetch and run, plus the data to train your own and a place to publish little demo apps. It lowers the "barrier to entry" so that you can get an AI model running with very little code of your own.

The Hub: models, datasets and spaces

When you sign in at huggingface.co, the main navigation starts with three tabs, and those three words are the whole platform in a nutshell: Models, Datasets and Spaces.

  1. Models — over 900,000 open-source models (the instructor notes the count had just passed from 800,000 to 900,000). Each does some task: chat, translation, turning text into an image, and much more. A model's name is usually the organisation followed by the model, like meta-llama/Meta-Llama-3.1-8B-Instruct. The word Instruct on the end means the model has been fine-tuned for chat-style, follow-my-instructions use. A model's page has a description, the languages it handles, code examples, and a Files and Versions tab that looks like a Git repository — because it is one.
  2. Datasets — over 200,000 datasets covering almost any problem you can think of. This is similar to Kaggle, a site focused on data, but far larger. Later in the course you will use a big dataset of Amazon product prices from here.
  3. Spaces — small apps that run on Hugging Face's own cloud hardware so anyone can try them in a browser. Many are built with Gradio (the UI framework from Week 2) or with Streamlit. A special kind of Space is a leaderboard: an app whose job is to score and rank different models against each other. Because the free hardware is shared, a popular Space can be too busy to run and you may need to try again.
Models vs datasets vs spaces — what is the difference?

A model is the trained AI itself: a file (really a bundle of files) full of numbers that, when run, can chat, translate or generate an image. A dataset is not AI at all — it is a collection of example data (text, prices, images), used to train a model or to test how well one works. A space is a running app: someone took a model, wrapped a small web interface around it, and published it so you can click and try it without writing any code. In short: a model is the engine, a dataset is the fuel, and a space is a finished little car you can take for a spin.

The Hugging Face libraries

The platform is only half the story. Hugging Face also gives you libraries — code you import — so you can use all of that from your own programs. The instructor highlights three you will meet first:

  • huggingface_hub — lets your code log in to Hugging Face and download or upload models and datasets from the Hub.
  • datasets — gives instant access to the data repositories on the Hub, so a single line of code pulls a dataset into your program.
  • transformers — the central library. It is the wrapper code around models that follow the "transformer" architecture. Underneath it uses PyTorch or TensorFlow to actually run the neural network. The important shift: when you call a function in transformers, you are no longer phoning a cloud API — you are running the model on your machine.

He also plants the names of three more advanced libraries you will meet later, so they feel familiar when they arrive: PEFT (parameter-efficient fine-tuning, used for a technique called LoRA), TRL (transformer reinforcement learning, which includes supervised fine-tuning, SFT), and accelerate (behind-the-scenes code that lets a model run efficiently across the hardware you have). You do not need to memorise these acronyms now.

Why we move to Google Colab this week

Running a model yourself is very different from calling an API. The model is a huge neural network of billions of numbers, and doing the maths to run it needs a GPU — a graphics chip that is very good at the parallel number-crunching neural networks rely on. Most laptops do not have a capable one. So this week we rent a computer that does, through Google Colab: a free service that runs a Jupyter notebook in the cloud on a Google machine that has a GPU attached.

What is a GPU, and why does AI need one?

A GPU (graphics processing unit) is a chip originally built to draw game graphics. Drawing graphics means doing the same simple maths on millions of pixels at once, and it turns out that running a neural network needs the same thing: huge amounts of parallel multiplication and addition on grids of numbers (matrices). A normal CPU does a few things very fast, one after another; a GPU does thousands of things at the same time. That is why training and running AI models is done on GPUs — and why you need a machine with one before an open-source model will run at any reasonable speed.

What is Google Colab?

Google Colab (short for Colaboratory) is a free Google service that runs a Jupyter notebook — the same kind of interactive code-and-text document you used in earlier weeks — on a computer in Google's cloud instead of on your own. The big wins: that cloud computer can have a GPU, and the notebook saves to your Google Drive and shares exactly like a Google Doc, so collaborating is effortless. There are paid competitors that do much the same thing; the instructor picks Colab because so many people use it and it is easy to share. There is a free tier that is enough for almost everything in this course, and a paid tier for faster, beefier machines.

Colab runtimes: picking your machine

In Colab you choose a runtime — the kind of machine behind your notebook. Through Runtime → Change runtime type you pick from roughly four options, cheapest first:

RuntimeWhat it isNotes from the course
CPUA normal box with no GPU.Fine for plain code; cannot run big models quickly.
T4 GPUA lower-end GPU, about 15 GB of GPU memory.Free tier (with usage limits), very cheap on the paid tier. Enough for everything in this course.
L4 GPUA higher-spec GPU.For heavier work; costs a little.
A100 GPUThe strongest option, about 40 GB of GPU memory.For fast, hefty training. Roughly $10 buys a day or two; sometimes oversubscribed, so you retry.

You can also ask for a "high-RAM" version, which adds system (CPU) memory — separate from the GPU memory, which is fixed by the box you pick. After choosing, you press Connect; Colab finds a machine and attaches it, which takes a moment. View resources then shows what you got — for a T4 the instructor sees about 13 GB of system RAM, a couple of hundred GB of disk, and a GPU with 15 GB of memory.

One warning about Colab disk. The local disk on a Colab box is ephemeral — it is wiped completely once you finish using the machine. Treat anything you save there as temporary. If you produce a model or data you want to keep, upload it to the Hugging Face Hub (that is one reason you need a token) or save it to your Google Drive.

The Hugging Face token, and why it is a Colab secret

To let your Colab notebook talk to the Hub — to download gated models or upload your own — it has to prove who you are. It does that with a Hugging Face token: a long secret string, like a password for your code. You create it once on the Hugging Face website, then store it in Colab so your notebooks can use it without the secret ever appearing in the code.

What is a Hugging Face token (and a "Colab secret")?

A token (also called an access token or API token) is a secret string that identifies you to a service, the way an API key does. Hugging Face uses one so it knows the download or upload is really you. You must never paste a secret like this straight into your code, because the code gets shared and anyone who sees it could use your account. A Colab secret solves that: Colab has a private vault (the key icon in the sidebar) where you store named secrets such as HF_TOKEN. Your notebook reads the value by name at run time, and — crucially — when you share the notebook, your code is shared but your secrets are not. Whoever opens it must add their own.

Set yourself up

Do this once now, so the next pages just work. There is no lab code today; these are account and dashboard steps.

  1. Create a free Hugging Face account. Go to huggingface.co and sign up with an email address and a password. It is free.
  2. Create an access token. Click your avatar → Settings → Access Tokens, then Create new token. Give it both read and write permissions (write lets you upload models and data later), and copy the token somewhere safe — you will paste it into Colab in a moment. Treat it like a password.
  3. Open Google Colab. Go to colab.research.google.com and sign in with a Google account (it will offer to create one if you do not have it). Choose File → New notebook in Drive to make a fresh notebook; it is saved in your Google Drive like any other Google file.
  4. Add your token as a secret. In the notebook's left sidebar, click the key icon to open Secrets, then Add new secret. Name it exactly HF_TOKEN, paste your token as the value, and turn on Notebook access so this notebook is allowed to read it.
  5. Pick a GPU runtime. Go to Runtime → Change runtime type and choose T4 GPU, then save.
  6. Connect. Press Connect (top right) and wait for it to attach a machine. Open the dropdown → View resources to confirm a GPU is present.
What you should see. After signing up, your Hugging Face Access Tokens page lists a new token. In Colab, the Secrets panel (key icon) shows a row named HF_TOKEN with Notebook access switched on. After choosing the T4 runtime and pressing Connect, the top-right shows a connected status, and View resources reports a GPU with around 15 GB of memory plus system RAM and disk. A cell that just prints a message (for example print("Hello Data Science World")) runs and shows its output — proof that you have a working Jupyter notebook in the cloud.
Common mistakes.
  • Forgetting to pick a GPU runtime. A new notebook defaults to CPU. If you skip Change runtime type → T4 GPU, this week's model code will be painfully slow or run out of memory. Always check View resources shows a GPU before running model code.
  • Token not added as a secret. If you paste the token into a code cell instead of the Secrets vault, you risk sharing it with the world, and if you forget it entirely the Hub download will fail with an authentication error. Store it once as HF_TOKEN and turn on Notebook access.
  • Name or permission wrong. The secret must be named exactly HF_TOKEN, and the token needs write permission if you plan to upload. A read-only token cannot push a model to the Hub.
  • Relying on Colab disk. The box's disk is wiped when the session ends — save anything you want to keep to the Hub or Google Drive.
