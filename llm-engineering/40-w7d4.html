Second, Weights & Biases: the same numbers drawn as live, zoomable charts, where the downward trend and the end-of-epoch dips become obvious. New to hyperparameters? What they are and why they matter

A hyperparameter is a setting you choose before training starts — as opposed to the model's weights, which training itself learns. Think of the oven: the recipe (your data) is fixed, but you still pick the temperature and the timer. Learning rate, number of epochs, batch size, which optimizer to use — these are all hyperparameters. There is no single right answer; you pick sensible starting values, watch the charts, and adjust. The instructor stresses that you do not need to spend a fortune experimenting: good results here cost "a matter of cents".

New to learning rate and the schedule? What they are and why they matter

The learning rate is how big a step the model takes each time it adjusts its weights. Too big and the model overshoots and the loss diverges (flies off instead of settling); too small and training crawls and may never get there. Here it is 1e-4 (0.0001).

A schedule changes the learning rate over the course of training instead of holding it fixed. This run uses two pieces together. Warmup (warmup_ratio=0.03): for the first 3% of steps the rate climbs from zero up to 1e-4, so the very first, most dramatic adjustments are gentle and the model does not overshoot while it is still far off. Cosine decay (lr_scheduler_type="cosine"): after the peak the rate curves smoothly back down toward zero, following the shape of a cosine wave, so late training takes smaller and smaller steps to settle precisely.

New to epochs, batch size and gradient accumulation? What they are and why they matter

An epoch is one full pass through all your training data. With 400,000 items, one epoch means the model has seen every item once. This run is set to three epochs — but the instructor's own experiment (below) shows a single epoch already gives strong results and costs far less.

Batch size is how many examples the model processes together before it updates its weights once. Bigger batches smooth out the noise and use the GPU better, but they eat memory. Here it is 16, which fills a 40 GB A100; on a small, cheap T4 you would drop to 1 or 2.

Gradient accumulation is a trick to fake a bigger batch when memory is tight: instead of updating after every batch, you add up (accumulate) the gradients from several small batches and update once. gradient_accumulation_steps=1 means no accumulation here (effective batch = 16). Set it to 4 and you would get the learning behaviour of batch 64 while only ever holding 16 examples in memory at a time.

New to Weights & Biases for a training run? What it is and why it matters

Weights & Biases (written wandb) is a free-for-personal-use website that draws live charts of a training run. The raw Colab log prints a loss number every step, but the numbers bounce around and it is hard to see whether things are improving. You add one setting — report_to="wandb" — and the trainer streams every number to your project, where you get a smooth, zoomable training-loss chart, a learning-rate chart, and GPU usage charts. The instructor also sets WANDB_WATCH="gradients" so you can inspect the gradients, and compares several runs on the same axes to prove a fresh run tracks an older one. You sign up at wandb.ai, copy your API key, and store it as a Colab secret.

New to saving an adapter? What it is and why it matters

Because this is QLoRA, you are not saving a whole new 8-billion-parameter model. You are saving only the small adapter — the thin set of low-rank matrices LoRA trained on top of the frozen base model. For rank 32 that works out to a single safetensors file of about 109 MB, plus a small adapter_config.json that records the rank, the target modules and the base-model name. To use the model later you load the original base model and apply this adapter on top. The training config pushes a fresh copy of the adapter to a HuggingFace Hub repo every save_steps (5000) steps, so each checkpoint is a Git commit you can download and test.

# Reconstructed to match the course's Google Colab notebook for this day.
# Standard QLoRA/PEFT code; runs on a GPU (e.g. Colab). Not executed here (no GPU).
#
# Week 7 - Day 3 / Day 4: the actual QLoRA training run.
# Freeze the 4-bit base model, attach LoRA adapters to the attention projections,
# and fine-tune only those adapters with TRL's SFTTrainer. A DataCollator for
# completion-only LM masks out the prompt so the model is trained only to predict
# the price token(s) after "Price is $". Progress is logged to Weights & Biases and
# checkpoints are pushed to the HuggingFace Hub.

import os
from datetime import datetime

import torch
import wandb
from google.colab import userdata
from huggingface_hub import login
from datasets import load_dataset
from transformers import AutoTokenizer, AutoModelForCausalLM, BitsAndBytesConfig
from peft import LoraConfig
from trl import SFTTrainer, SFTConfig, DataCollatorForCompletionOnlyLM


# ----------------------------------------------------------------------------
# Constants
# ----------------------------------------------------------------------------

BASE_MODEL = "meta-llama/Meta-Llama-3.1-8B"
PROJECT_NAME = "pricer"
HF_USER = "ed-donner"  # change to your own HuggingFace username

DATASET_NAME = f"{HF_USER}/pricer-data"
MAX_SEQUENCE_LENGTH = 182

# Unique, timestamped run name so every run is its own Hub repo / W&B run.
RUN_NAME = f"{datetime.now():%Y-%m-%d_%H.%M.%S}"
PROJECT_RUN_NAME = f"{PROJECT_NAME}-{RUN_NAME}"
HUB_MODEL_NAME = f"{HF_USER}/{PROJECT_RUN_NAME}"

# --- QLoRA hyperparameters ---
LORA_R = 32                 # adapter rank (start 8, double to 16, then 32)
LORA_ALPHA = 64             # scaling factor; rule of thumb alpha = 2 * r
TARGET_MODULES = ["q_proj", "v_proj", "k_proj", "o_proj"]  # the attention layers
LORA_DROPOUT = 0.1          # regularization: drop 10% of neurons each step
QUANT_4_BIT = True

# --- Training hyperparameters ---
EPOCHS = 3                  # instructor ran 3 (best checkpoint ~end of epoch 3);
                            # a single epoch already gives strong results and is far cheaper.
BATCH_SIZE = 16             # 16 fits an A100 (40GB); use 1 (or 2-4) on a T4.
GRADIENT_ACCUMULATION_STEPS = 1
LEARNING_RATE = 1e-4
LR_SCHEDULER_TYPE = "cosine"
WARMUP_RATIO = 0.03
OPTIMIZER = "paged_adamw_32bit"  # good convergence; memory-hungry. Swap for a
                                 # cheaper optimizer if you run out of memory.

# --- Admin / logging ---
STEPS = 50                  # log training loss to W&B every 50 steps
SAVE_STEPS = 5000           # push a checkpoint to the Hub every 5000 steps
LOG_TO_WANDB = True


# ----------------------------------------------------------------------------
# Log in to HuggingFace and Weights & Biases
# ----------------------------------------------------------------------------

hf_token = userdata.get("HF_TOKEN")
login(hf_token, add_to_git_credential=True)

if LOG_TO_WANDB:
    wandb_api_key = userdata.get("WANDB_API_KEY")
    os.environ["WANDB_API_KEY"] = wandb_api_key
    wandb.login()
    os.environ["WANDB_PROJECT"] = PROJECT_NAME
    os.environ["WANDB_LOG_MODEL"] = "checkpoint"
    os.environ["WANDB_WATCH"] = "gradients"


# ----------------------------------------------------------------------------
# Data
# ----------------------------------------------------------------------------

dataset = load_dataset(DATASET_NAME)
train = dataset["train"]
test = dataset["test"]

print(f"Training on {len(train):,} items; holding out {len(test):,} test items")
print("Example training text:\n")
print(train[0]["text"])


# ----------------------------------------------------------------------------
# Quantization config + tokenizer + frozen base model
# ----------------------------------------------------------------------------

if QUANT_4_BIT:
    quant_config = BitsAndBytesConfig(
        load_in_4bit=True,
        bnb_4bit_use_double_quant=True,
        bnb_4bit_compute_dtype=torch.bfloat16,
        bnb_4bit_quant_type="nf4",
    )
else:
    quant_config = BitsAndBytesConfig(
        load_in_8bit=True,
        bnb_8bit_compute_dtype=torch.bfloat16,
    )

tokenizer = AutoTokenizer.from_pretrained(BASE_MODEL, trust_remote_code=True)
tokenizer.pad_token = tokenizer.eos_token
tokenizer.padding_side = "right"

base_model = AutoModelForCausalLM.from_pretrained(
    BASE_MODEL,
    quantization_config=quant_config,
    device_map="auto",
)
base_model.generation_config.pad_token_id = tokenizer.pad_token_id
print(f"Memory footprint: {base_model.get_memory_footprint() / 1e6:,.1f} MB")


# ----------------------------------------------------------------------------
# Completion-only data collator
# ----------------------------------------------------------------------------
#
# We only want the model to learn the token(s) AFTER "Price is $" - not how to
# rewrite the product description. The collator masks everything up to and
# including the response template so the loss is computed only on the price.

response_template = "Price is $"
collator = DataCollatorForCompletionOnlyLM(response_template, tokenizer=tokenizer)


# ----------------------------------------------------------------------------
# LoRA config (the QLoRA adapters)
# ----------------------------------------------------------------------------

lora_config = LoraConfig(
    r=LORA_R,
    lora_alpha=LORA_ALPHA,
    target_modules=TARGET_MODULES,
    lora_dropout=LORA_DROPOUT,
    bias="none",
    task_type="CAUSAL_LM",
)


# ----------------------------------------------------------------------------
# SFT training config
# ----------------------------------------------------------------------------

train_config = SFTConfig(
    output_dir=PROJECT_RUN_NAME,
    num_train_epochs=EPOCHS,
    per_device_train_batch_size=BATCH_SIZE,
    gradient_accumulation_steps=GRADIENT_ACCUMULATION_STEPS,
    learning_rate=LEARNING_RATE,
    lr_scheduler_type=LR_SCHEDULER_TYPE,
    warmup_ratio=WARMUP_RATIO,
    optim=OPTIMIZER,
    max_grad_norm=0.3,
    weight_decay=0.001,
    max_seq_length=MAX_SEQUENCE_LENGTH,
    dataset_text_field="text",
    # logging
    logging_steps=STEPS,
    report_to="wandb" if LOG_TO_WANDB else "none",
    run_name=RUN_NAME,
    # saving / pushing to the Hub
    save_strategy="steps",
    save_steps=SAVE_STEPS,
    push_to_hub=True,
    hub_model_id=HUB_MODEL_NAME,
    hub_strategy="every_save",
    hub_private_repo=True,
    # misc
    save_total_limit=10,
    bf16=True,
    group_by_length=True,
    seed=42,
)


# ----------------------------------------------------------------------------
# Trainer
# ----------------------------------------------------------------------------

trainer = SFTTrainer(
    model=base_model,
    train_dataset=train,
    peft_config=lora_config,
    args=train_config,
    data_collator=collator,
    processing_class=tokenizer,  # older TRL versions use tokenizer=tokenizer
)


# ----------------------------------------------------------------------------
# Train, then push the final adapter to the Hub
# ----------------------------------------------------------------------------

if __name__ == "__main__":
    trainer.train()
    trainer.model.push_to_hub(PROJECT_RUN_NAME, private=True)
    print(f"Saved adapter to the Hub: {HUB_MODEL_NAME}")
    if LOG_TO_WANDB:
        wandb.finish()

What you should see

In the Colab log, a line per batch step with a training loss that starts high and bounces its way down. In Weights & Biases the same numbers become a chart: a bumpy line with a clear downward trend (apply the smoothing slider and the trend pops out). The learning-rate chart ramps up during warmup, then eases down a cosine curve. GPU-utilisation charts should show the GPU "nice and hot" — busy computing, not waiting on memory. And in the HuggingFace Hub your model repo gains a new commit roughly every 5000 steps, each holding a ~109 MB safetensors adapter and an adapter_config.json. You can load and test any of these checkpoints while training is still running.

Common mistakes and pitfalls
  • Learning rate too high. If learning rate is too large the loss diverges — it jumps around or shoots up instead of settling. If it is too small, training crawls. 1e-4 with warmup is a safe start.
  • Too many epochs = overfitting. The instructor watched the loss take a bigger dive at each epoch boundary: the model was memorising data it had already seen. When he tested later checkpoints they were worse, so there was no point past epoch 3. His rule of thumb: a loss much below 1.5 should make you suspicious. Often one epoch is enough.
  • Dead or exploding gradients. With WANDB_WATCH="gradients" on, watch that gradients never fall to zero (the model has stopped learning) or blow up (training is unstable).
  • Idle GPU. If GPU utilisation is low the GPU is shuffling memory, not computing — you are paying for time you are not using. Tune the hyperparameters to keep it busy.
