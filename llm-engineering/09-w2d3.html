Week 2 · Day 3 — Chatbots with History and Context

Build a conversational assistant that remembers the conversation, with a system prompt and multi-shot context to shape its answers.

Companion to Ed Donner's course · uv setup · Python + TypeScript/React · code verified against the repo

Today you build your first real chatbot: an assistant you can hold a back-and-forth conversation with, that remembers what was said earlier in the chat, that has a persona (a friendly clothes-store assistant), and that you can steer with examples. The surprise of the lesson is how little code it takes. In Python, Gradio hands you a ready-made chat window if you write one small function; in TypeScript we write the same function so a React app or a server can reuse it.

Everything today comes in two languages. Use the Python | TypeScript switch on the code card — or the Code in: switch at the top of the page — to flip between them; your choice is remembered as you read. The two versions do the same thing; only the syntax changes.

The big idea carries over from Day 4: an LLM is stateless and remembers nothing on its own. The sense of a continuous conversation is an illusion we build. Each turn, your code resends the whole conversation so far — the system prompt, every earlier exchange, and the new question — and the model predicts the next reply from all of it. This resent transcript is the conversation history.

This page explains the type="messages" version, because that is the code you will run.

New to conversation history? What it is and why we resend it

A chat model does not keep a memory between calls. So to make it look like it remembers, your program keeps the whole conversation in a list and sends that entire list on every turn. That list — the system prompt, each thing you said, and each thing the model replied — is the conversation history. When you ask "and a red one" after talking about ties, the model only knows what "one" means because the earlier turns are sitting right there in the list you just resent. The cost of this trick is that the list grows every turn, so a long chat sends more tokens (and costs a little more) each time. Managing that growth becomes your job as the engineer.

A conversation is a list of messages

You already know the shape of a chat request: a list of message dictionaries, each with a role and content. The roles take turns: a system message first to set the rules, then user, assistant, user, assistant, and so on. The chatbot's whole job is to keep appending to this list and resend it.

The callback Gradio wants: chat(message, history)

Gradio's chat UI does not want you to draw bubbles or track state. It wants one function with a fixed shape: it receives the new message the user just typed and the history of everything before it, and it returns (or streams) the reply. Gradio calls this function every turn, handing you a fresh copy of the history each time. Your function's one job is to turn that history into the messages list OpenAI expects, call the model, and give back the answer.

New to Gradio's ChatInterface? What it gives you for free

Gradio is a Python library that turns a function into a web UI with no front-end code. ChatInterface is its ready-made chat window: a scrolling transcript, a text box, and a send button, all wired up. You pass it your chat function as fn, add type="messages" so history arrives in the modern role/content shape, and call .launch(). That single line gives you the instant-message interface the instructor demos. In the TypeScript world there is no Gradio; instead a React app provides the window and a small server calls the same chat function, which is why the port keeps the function but drops the UI line.

The instructor builds the function up in stages. First a throwaway version that ignores its inputs and always returns "bananas", just to prove the wiring works. Then a version that echoes the message and history back so you can see their shape. Then the real one that calls OpenAI. We show the complete file below; those early "bananas" cells are included so you can see the progression, and the real work is in the final chat function.

// Day 3 - A chat function with history + a system prompt (TypeScript port of day3.py)
// Gradio's ChatInterface gave us `chat(message, history)` for free; here we write the
// equivalent as a plain function so the React UI (and the Hono server) can reuse it.
import "dotenv/config";
import { pathToFileURL } from "node:url";
import OpenAI from "openai";

export const MODEL = "gpt-4o-mini";

export const DEFAULT_SYSTEM_MESSAGE =
  "You are a helpful assistant in a clothes store. You should try to gently encourage the " +
  "customer to try items that are on sale. Hats are 60% off, and most other items are 50% off. " +
  "For example, if the customer says 'I'm looking to buy a hat', you could reply something like, " +
  "'Wonderful - we have lots of hats - including several that are part of our sales event.' " +
  "Encourage the customer to buy hats if they are unsure what to get.\n" +
  "If the customer asks for shoes, you should respond that shoes are not on sale today, but " +
  "remind the customer to look at hats!";

export type ChatMessage = { role: "user" | "assistant"; content: string };

// Build the messages array the API expects: system prompt + prior turns + the new message.
// Like the Python lab, we tweak the system prompt on the fly when 'belt' is mentioned.
export function buildMessages(
  message: string,
  history: ChatMessage[],
  system: string = DEFAULT_SYSTEM_MESSAGE,
): OpenAI.Chat.ChatCompletionMessageParam[] {
  let relevantSystem = system;
  if (message.toLowerCase().includes("belt")) {
    relevantSystem +=
      " The store does not sell belts; if you are asked for belts, be sure to point out other items on sale.";
  }
  return [
    { role: "system", content: relevantSystem },
    ...history.map((h) => ({ role: h.role, content: h.content })),
    { role: "user", content: message },
  ];
}

// Non-streaming version (returns the whole reply).
export async function chat(
  openai: OpenAI,
  message: string,
  history: ChatMessage[],
  system: string = DEFAULT_SYSTEM_MESSAGE,
): Promise<string> {
  const response = await openai.chat.completions.create({
    model: MODEL,
    messages: buildMessages(message, history, system),
  });
  return response.choices[0]?.message.content ?? "";
}

// Streaming version: yields the growing reply, mirroring the Gradio `yield response` loop.
export async function* chatStream(
  openai: OpenAI,
  message: string,
  history: ChatMessage[],
  system: string = DEFAULT_SYSTEM_MESSAGE,
): AsyncGenerator<string> {
  const stream = await openai.chat.completions.create({
    model: MODEL,
    messages: buildMessages(message, history, system),
    stream: true,
  });
  for await (const chunk of stream) {
    const delta = chunk.choices[0]?.delta.content ?? "";
    if (delta) yield delta;
  }
}

async function main(): Promise<void> {
  if (!process.env.OPENAI_API_KEY) {
    console.log("OPENAI_API_KEY not set - this demo needs it. See .env.example.");
    return;
  }
  const openai = new OpenAI();
  const history: ChatMessage[] = [];
  const reply = await chat(openai, "I'm looking to buy a hat", history);
  console.log("Assistant:", reply);
}

// Only run the demo when this file is executed directly, not when imported.
if (import.meta.url === pathToFileURL(process.argv[1] ?? "").href) {
  main().catch((err) => {
    console.error(err);
    process.exitCode = 1;
  });
}

Turning history into the messages OpenAI wants

This is the heart of the lesson. Gradio (or the React app) hands you the history; OpenAI wants a single messages list. The recipe is always the same: start with the system prompt, drop in every earlier turn from the history, then append the new user message at the end.

The video (an older recording) calls history a "list of lists". The code you run uses type="messages", so each history entry is already a {"role": ..., "content": ...} dictionary. Line 74 rebuilds those into clean dictionaries, and line 79 assembles the final list.

A system prompt sets the persona

With the wiring done, the instructor turns the plain "You are a helpful assistant" into a real character. The new system_message says the assistant works in a clothes store, should gently push items on sale, and lists the facts: hats are 60% off, most other items 50% off. It then gives an example reply for "I'm looking to buy a hat", so the model copies both the facts and the cheerful tone. Later a second line is appended: if the customer asks for shoes, say shoes are not on sale today but point them to hats.

New to the system prompt as a persona? How a few sentences set behaviour

The system prompt is the first message in the list and the model treats it as its standing instructions. It is where you set the job ("you work in a clothes store"), the tone ("gently encourage"), the facts the model should know ("hats are 60% off"), and the rules ("if you don't know, say so"). You do not fine-tune or retrain anything — you just write clear instructions in plain English. Because the model was trained on millions of instruction-following examples, it tends to obey. Change the system prompt and the whole personality changes, which is why the instructor keeps editing one global and relaunching.

Multi-shot prompting and context enrichment

Giving the model one worked example inside the prompt is one-shot prompting; giving it several is multi-shot prompting. Each example does double duty: it sets the style of a good answer and it slips in extra facts the model can reuse. The clothes-store prompt is really a small pile of examples and facts — "if the customer says this, you could say that" — which is why the replies come out both on-brand and well informed. The instructor stresses this is not training: the network is already trained. At inference time the model simply predicts tokens that fit what it has seen, so a prompt full of good examples makes a good reply more likely.

New to multi-shot prompting? One example vs several

Zero-shot means you just ask ("summarise this"). One-shot means you include a single worked example of the input-and-ideal-output before your real request. Multi-shot means you include several examples. More examples pin down the pattern more firmly — the format, the tone, and any facts the examples contain — so the model's next reply is more likely to match. It costs tokens (every example is resent in the prompt), and the examples can live in the system prompt or as a short made-up user/assistant exchange placed before the real conversation. Nothing is being trained; you are only giving the already-trained model better patterns to imitate.

The belt check is a first taste of context enrichment done per message: before building the list, the code looks at what the user said and, if it sees "belt", adds a fresh fact to the system prompt for that one turn. The instructor is honest that matching a bare substring is crude — it would also fire on "beltway" — and suggests a dictionary of store items and prices as a sturdier version. He frames it as a "baby version" of retrieval-augmented generation (RAG): find information relevant to the question and add it to the context before calling the model.

The instructor also notes a second way to do multi-shot prompting: instead of stuffing examples into the system prompt, you can prepend a fictional user/assistant exchange to the history — a conversation that never really happened — so the model sees how it "already" answered similar questions. Both approaches prime the model with style and facts; the suggested exercise is to try each and see which gives a better store assistant.

  • With the store persona, "I'd like to buy some shoes" brings a cheerful reply that mentions shoes are not on sale today but the hats are 60% off — the facts and tone came from the system prompt.
  • Ask for a belt and the assistant says the store does not carry belts, then points you at items on sale — the belt fact was added to the context just for that turn.

Exact wording varies from run to run and with the model.

Common mistakes
  • Forgetting to pass the history. If you build messages from only the system prompt and the new message and leave out history, the bot forgets everything instantly — "a red one" means nothing to it. The history must be in the list every single turn.
  • Wrong message format. Each entry must be a dictionary (object) with exactly role and content. Sending a raw string, a tuple, or a misspelled role like "users" makes the API reject the call. Line 74 rebuilds the history into clean {"role", "content"} dictionaries for this reason.
  • Dropping the system message, or putting it in the wrong place. The system prompt should be the first item in the list. If you forget it, the persona and rules disappear and you are back to a generic assistant.
  • Expecting the model to remember on its own. It does not. Each turn is a fresh, stateless call; the only memory is the list you resend.
  • Trusting a bare substring check. 'belt' in message.lower() also matches "beltway" and misses a user who writes "belts". It is fine as a demo, but a real lookup needs whole-word matching or a small dictionary.
Recap
  • A chatbot feels like it remembers, but the model is stateless — the conversation history is resent in full every turn.
  • In Python, Gradio's ChatInterface gives you a whole chat UI if you write one chat(message, history) function and add type="messages"; the TypeScript port keeps the function and lets a React app and server supply the UI.
  • The core recipe is one line: messages = [system] + history + [new user], sent to openai.chat.completions.create, optionally with stream=True to show the reply as it arrives.
  • A system prompt sets the persona, tone, facts, and rules; the clothes-store prompt turns the plain assistant into a sales-savvy helper.
  • Multi-shot prompting puts several examples in the prompt to steer style and supply facts, all at inference time, not by training.
  • Context enrichment adds a relevant fact to the prompt per turn (the "belt" check) — a baby version of RAG.
