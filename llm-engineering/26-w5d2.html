Week 5 · Day 2 — LangChain: Loaders, Splitters, Embeddings

Meet LangChain: load documents, split them into overlapping chunks with a text splitter, and turn them into OpenAI embeddings ready for a vector database (Chroma).

Companion to Ed Donner's course · uv setup · Python + TypeScript/React · code verified against the repo

On the previous day you built a tiny retrieval system by hand: read every document into a dictionary, look up the ones that mention a word, and paste them into the prompt. It worked, but it was crude. Today the instructor replaces that hand-rolled code with a real framework, LangChain, and does the first half of a proper Retrieval-Augmented Generation pipeline: load a folder of documents, split them into overlapping pieces, and get ready to turn those pieces into vectors and store them in a database.

This is the data-preparation side of RAG. It does not answer any questions yet. It takes a pile of files and turns them into clean, bite-sized, searchable pieces so that tomorrow we can look them up by meaning instead of by keyword. The instructor is careful to go slowly here, because the ideas introduced today — text splitters, chunks, overlap and embeddings — are the foundation everything else in the week rests on.

What LangChain is and why we switch to it

LangChain is a framework for building applications on top of large language models. The instructor gives its backstory: it appeared in late 2022, and its goal is to let people stitch together the common pieces of an LLM application — loading data, splitting it, embedding it, retrieving it, calling a model — in just a few lines of code. It also wraps the different model providers behind one interface, so you can write your code once and swap OpenAI for Claude without rewriting the calls.

New to LangChain? What a "framework" buys you here

Yesterday you wrote the retrieval logic yourself: open files, store text, search it, build the prompt. That is the "brute force" way, and the instructor is clear that there is nothing magical about RAG — you can roll your own. A framework like LangChain simply packages the parts everyone needs so you do not rewrite them each time. It gives you ready-made document loaders (read files into a standard object), text splitters (cut long text into pieces), embeddings wrappers (turn text into vectors) and vector store wrappers (save and search those vectors).

The instructor is also honest about the trade-off: as the model APIs have matured and become more alike, the need for a wrapper framework has shrunk compared with a year ago, and many people now build their own pipelines. But LangChain still gives you a big head start, so the course uses it.

The TypeScript twin uses LangChain.js, the JavaScript edition of the same framework. It has the same ideas — loaders, splitters, embeddings, a vector store — with camel-cased names and async methods.

Video vs repo. In the video the instructor imports CharacterTextSplitter and talks about OpenAI's embeddings. The current repo notebook that this page embeds uses the smarter RecursiveCharacterTextSplitter, and it defaults to a free local embedding model (HuggingFaceEmbeddings) with the OpenAI option left as a comment. The ideas are identical; only the exact class and model differ. We explain both below, and the TypeScript twin uses OpenAIEmbeddings with text-embedding-3-small as the video describes.

// Day 2 / Day 3 - Build the vector store (TypeScript port of the LangChain ingest step)
//
// The Python labs used LangChain's DirectoryLoader + CharacterTextSplitter +
// OpenAIEmbeddings + Chroma. Here we do the LangChain.js equivalent:
//   - read the sample docs under knowledge/  (a hand-rolled DirectoryLoader)
//   - split them with RecursiveCharacterTextSplitter
//   - embed with OpenAIEmbeddings (text-embedding-3-small)
//   - store the vectors in an in-memory MemoryVectorStore (no native deps, no Chroma server)
//
// Everything up to embedding works with no API key; only building the store needs one,
// so rag.ts / the server can import these helpers and stay key-guarded.
import "dotenv/config";
import { readdirSync, readFileSync, statSync } from "node:fs";
import { join, relative } from "node:path";
import { fileURLToPath, pathToFileURL } from "node:url";
import { Document } from "@langchain/core/documents";
import { OpenAIEmbeddings } from "@langchain/openai";
import { RecursiveCharacterTextSplitter } from "@langchain/textsplitters";
import { MemoryVectorStore } from "langchain/vectorstores/memory";

export const EMBEDDING_MODEL = "text-embedding-3-small";

// knowledge/ sits next to src/ at the project root.
const KNOWLEDGE_DIR = fileURLToPath(new URL("../knowledge", import.meta.url));

export function hasOpenAIKey(): boolean {
  return Boolean(process.env.OPENAI_API_KEY);
}

// Walk a folder and return every .md / .txt file path (recursively).
function listDocFiles(dir: string): string[] {
  const out: string[] = [];
  for (const entry of readdirSync(dir)) {
    const full = join(dir, entry);
    if (statSync(full).isDirectory()) {
      out.push(...listDocFiles(full));
    } else if (/\.(md|txt)$/i.test(entry)) {
      out.push(full);
    }
  }
  return out;
}

// A hand-rolled DirectoryLoader: one Document per file, tagged with its source
// path and a doc_type taken from the top-level folder (company / products / employees).
export function loadDocuments(): Document[] {
  const files = listDocFiles(KNOWLEDGE_DIR);
  return files.map((file) => {
    const rel = relative(KNOWLEDGE_DIR, file).replace(/\\/g, "/");
    const docType = rel.split("/")[0] ?? "general";
    return new Document({
      pageContent: readFileSync(file, "utf-8"),
      metadata: { source: rel, doc_type: docType },
    });
  });
}

// Split the documents into overlapping chunks, mirroring the Python chunk_size/overlap.
export async function splitDocuments(documents: Document[]): Promise<Document[]> {
  const splitter = new RecursiveCharacterTextSplitter({
    chunkSize: 1000,
    chunkOverlap: 200,
  });
  return splitter.splitDocuments(documents);
}

// Build the in-memory vector store. Requires OPENAI_API_KEY (embeddings call OpenAI).
export async function buildVectorStore(): Promise<MemoryVectorStore> {
  if (!hasOpenAIKey()) {
    throw new Error("OPENAI_API_KEY is not set - cannot create embeddings. See .env.example.");
  }
  const documents = loadDocuments();
  const chunks = await splitDocuments(documents);
  const embeddings = new OpenAIEmbeddings({ model: EMBEDDING_MODEL });
  return MemoryVectorStore.fromDocuments(chunks, embeddings);
}

async function main(): Promise<void> {
  const documents = loadDocuments();
  console.log(`Loaded ${documents.length} documents from knowledge/`);
  const chunks = await splitDocuments(documents);
  console.log(`Split into ${chunks.length} chunks`);

  if (!hasOpenAIKey()) {
    console.log("OPENAI_API_KEY not set - skipping embedding. Set it in .env to build the store.");
    return;
  }

  const store = await buildVectorStore();
  // MemoryVectorStore keeps vectors on `memoryVectors`; report how many we embedded.
  console.log(`Vector store built with ${store.memoryVectors.length} vectors (model: ${EMBEDDING_MODEL}).`);
}

// Only run when executed directly (npm run ingest), not when imported by rag.ts.
if (import.meta.url === pathToFileURL(process.argv[1] ?? "").href) {
  main().catch((err) => {
    console.error(err);
    process.exitCode = 1;
  });
}

Step 1 — loading a folder of documents

Yesterday's code read files into a dictionary by hand. A document loader does the same job but returns a Document object: a standard little container with the file's text in page_content and a metadata dictionary for extra facts about it. LangChain gives you two loaders here: TextLoader for a single text file, and DirectoryLoader to sweep an entire folder and run TextLoader on every file it finds.

New to "document loaders"? Why not just read the files?

You could read the files yourself — and yesterday you did. The point of a loader is that it hands back a consistent object no matter where the data came from. LangChain has loaders for text files, PDFs, web pages, Notion, databases and dozens more, and they all produce the same Document shape. That means the next stage (the splitter) and the stage after it (embeddings) never have to care whether the text started life as a .md file or a web page. Standardising early keeps the rest of the pipeline simple.

The loop also adds metadata. For each folder it records a doc_type — company, contracts, employees or products — on every document from that folder. Metadata rides along with the text through the whole pipeline, so later you can filter a search ("only look in contracts") or show the user where an answer came from.

Step 2 — splitting documents into chunks

A single document can be far too long to embed or to drop into a prompt. So we cut each one into chunks: pieces of roughly a fixed size. The text splitter takes two settings. The chunk_size is the rough target length in characters. The chunk_overlap is how much each chunk repeats from the end of the one before it.

Why chunk at all, and why the overlap?

Why chunk: embeddings work best on focused pieces of text, and when we later retrieve context for the model we want to send a few tight, relevant pieces — not a whole 20-page document that is mostly irrelevant. Small chunks also fit comfortably inside the prompt's context window.

Why overlap: if you cut a document into separate, non-overlapping blocks, an important sentence can land exactly on a boundary — half in one chunk, half in the next — and neither chunk then reads as clearly relevant to a query. Overlap means consecutive chunks share some text, so a key phrase is less likely to be stranded. The instructor describes it as making sure a critical word is not caught in only one chunk when a nearby, equally relevant chunk would otherwise be missed.

Why "recursive": the splitter does not cut blindly every 1000 characters. It tries to break at sensible boundaries — a blank line between sections, then a line break, then a space — so chunks end at natural seams instead of mid-word. That is why a chunk can come out a little larger than asked (the video shows one at 1088 characters): the splitter stretched it to avoid an ugly cut.

Getting chunk size and overlap wrong. If chunks are too big, each one mixes several topics, its embedding becomes a blurry average, and you waste context sending mostly-irrelevant text to the model. If chunks are too small, they lose the surrounding context that gives a sentence its meaning, and you end up with thousands of thin fragments. No overlap risks splitting a key fact across a boundary so neither chunk reads as relevant; too much overlap (say, an overlap near the chunk size) bloats the store with near-duplicate chunks and slows search. The course's 1000 / 200 is a sensible starting point — tune it to your documents.

Splitting the 31 documents produces 123 chunks in the video. Crucially, every chunk keeps the metadata of the document it came from, so each of the 123 chunks still carries its source and doc_type.

Step 3 — getting ready to embed and store

The chunks are now clean, bite-sized and tagged. The last stage of preparation is to turn each chunk into a vector embedding — a long list of numbers that captures the meaning of the text — and save those vectors in a vector database so we can search them by meaning later.

Embeddings, in one minute (recap from Day 1)

An embedding model reads a piece of text and returns a fixed-length list of numbers — a vector — positioned so that texts with similar meaning land near each other in that space. "Cancel my subscription" and "how do I end my plan" produce nearby vectors even though they share almost no words. That is the whole trick behind RAG: instead of matching keywords (yesterday's approach, which missed the CEO when she was mentioned by first name instead of surname), we match meaning. The course embeds with OpenAI's text-embedding-3-small; the repo also offers a free local model.

In Python, Chroma.from_documents(...) does the embed and store in one call: it runs every chunk through the embedding model and saves the resulting vectors to the vector_db folder on disk. In TypeScript, MemoryVectorStore.fromDocuments(...) does the same but keeps the vectors in memory. Either way, the output is the same: a searchable store of vectors, each still carrying its chunk's metadata.

What you should see. Running the Python notebook prints that the API key loaded, the total character and token counts of the knowledge base, Loaded 31 documents, then Divided into 123 chunks (possibly with a harmless warning about one 1088-character chunk). Common mistakes. Pointing the loader at the wrong folder (or running from the wrong directory) gives Loaded 0 documents — check the path. Forgetting the .env file means the embedding step fails with an authentication error, even though loading and splitting worked fine. Expecting the TypeScript MemoryVectorStore to still hold data on the next run: it does not — it rebuilds from scratch each time.

Recap
  • LangChain replaces yesterday's hand-written retrieval code with ready-made pieces: document loaders, text splitters, embeddings wrappers and vector stores. LangChain.js is the TypeScript twin.
  • Load: DirectoryLoader (using TextLoader) sweeps the knowledge-base/ folders into standard Document objects, and the loop tags each with a doc_type from its folder — 31 documents in the video.
  • Split: RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200) cuts the documents into overlapping chunks at sensible boundaries — 123 chunks — and every chunk keeps its parent's metadata.
  • Why chunk and overlap: small focused pieces embed and retrieve better; the shared overlap stops an important fact being stranded on a boundary. Too big, too small or wrong overlap all hurt retrieval.
  • Embed & store: OpenAIEmbeddings (text-embedding-3-small) turns each chunk into a vector; Python saves them in Chroma on disk, TypeScript keeps them in an in-memory MemoryVectorStore. Same idea, different durability.
