Week 8 · Day 2 — Deploying the Pricer and the Ensemble

Deploy the fine-tuned model to the cloud (Modal) as a service, then combine several pricing models - frontier, your fine-tuned model, and a RAG pricer - into one ensemble estimate.

Companion to Ed Donner's course · uv setup · Python + TypeScript/React · code verified against the repo

The instructor calls this the toughest day of the whole course, so take it slowly. Two big things happen. First, the fine-tuned open-source pricer you trained last week stops living only on your machine: you deploy it to the cloud with Modal so any Python code can call it like a normal function, while the real work runs on a cloud GPU. Second, you stop relying on a single model. You build an ensemble — several different pricing models whose guesses are combined into one estimate that is steadier than any of them alone.

The project behind all of this is "The Price is Right": an autonomous system that watches for online deals, estimates what each item is really worth, and sends a push notification when something looks like a bargain. The piece we assemble today is the price estimator. It will draw on three very different pricers at once: a RAG-based frontier pricer, your deployed fine-tuned specialist, and a machine-learning model built on vector embeddings.

Why deploy the model at all

Last week's fine-tuned model is just weights sitting on a GPU during a notebook session. The moment the notebook closes, it is gone, and nothing else can reach it. For a real system — an agent that runs on a schedule and prices hundreds of deals — you need the model to be always reachable. That means turning it into a service: code that lives in the cloud, waits for requests, runs the model on a GPU when asked, and returns an answer.

The clever part of Modal is that, from your side, calling that cloud service looks almost exactly like calling a local function. You write a small piece of ordinary Python; behind the scenes it reaches out to your model running on a GPU in the cloud, and you pay only for the seconds it actually runs.

New to Modal? What it is and why it matters

Modal is a cloud platform for running Python code — including code that needs a GPU — without you managing any servers. You describe, in Python, what your code needs (a GPU, certain libraries, your model file) and Modal builds that environment in the cloud and runs your function there on demand. There are other platforms that do similar things; the course uses Modal because it is simple and the code stays pure Python. The key idea for today: you deploy your fine-tuned pricer once, and from then on any program can call it remotely.

New to serverless? What "pay only for what you use" means

Serverless does not mean there is no server — it means you never rent, start, or shut down one. You hand the platform your code; it starts a machine when a request arrives, runs your code, and stops the machine when there is nothing to do. You are billed for the exact time your code ran, not for a GPU idling all month. The trade-off is the cold start: the first call after a quiet period has to wake a machine and load your model, so it is slow; later calls, while the machine is still warm, are fast.

New to "deploying a model as a service"? The shape of it

A service is code that runs continuously (or wakes on demand) and answers requests. To turn a model into a service you wrap it: load the weights once when the service starts, expose a function like price(description) that runs the model and returns a number, and give the whole thing a name so callers can find it. In this course that wrapper is a separate file, pricer_service.py, which you publish to Modal with a single modal deploy command. After that the service has a stable name (pricer-service) and a class (Pricer), and the notebook simply looks it up by those names and calls it.

How the service is deployed

The deployment itself lives in a separate file in the repo, pricer_service.py (it is not part of today's notebook, so it is described here rather than embedded). In that file you write a Modal class — roughly, a class decorated so Modal knows it needs a GPU and the model's libraries. A method runs once when the service starts to load the fine-tuned weights, and a method named price takes a product description and returns an estimate. You publish it from a terminal with:

modal deploy pricer_service.py

Modal builds the environment in the cloud, uploads the code, and registers the service under the name pricer-service with the class Pricer. From that point on it is callable from anywhere — including today's notebook — by looking it up with those two names. Your secrets (API keys, the Hugging Face token) are stored as Modal secrets in Modal's dashboard, never written into the code or the deployed file.

What an ensemble is, and why combine models

An ensemble is simply several models answering the same question, with their answers merged into one. The intuition is the one behind "the wisdom of the crowd": each model has its own blind spots, but the mistakes tend to point in different directions, so blending the guesses cancels some of the error out. Today's ensemble combines three very different estimators:

  1. Frontier + RAG A RAG pricer: it finds the five most similar products in a 400,000-item vector store and hands them to a frontier model as context, so the model prices with real examples in front of it.
  2. Specialist Your fine-tuned open-source model, now deployed on Modal — the one that beat the frontier models last week.
  3. Machine learning A model trained on the same vector embeddings (a classic machine-learning regressor on modern transformer vectors), giving a completely independent opinion.

The combiner then produces one number from the three. There are two common ways, and this is the key Video-vs-repo difference on this page (see the callout): the video learns a weighted blend with a linear regression, while the notebook file embedded below uses a simple fixed weighted average.

New to ensembles? Why three mediocre models can beat one good one

Imagine three friends guessing the price of a gadget. One always guesses a bit high, one tends to anchor on similar products, one reasons from raw specs. Any single guess can be well off, but their average is usually closer than most individuals, because their errors partly cancel. An ensemble does the same with models. It matters most when the models are different from each other — different training, different data, different method — because then they fail in different ways. Here the three pricers could hardly be more different, which is exactly what makes combining them worthwhile.

Inside the RAG pricer

The frontier pricer uses retrieval-augmented generation, built here by hand rather than with a framework. Each of the 400,000 training products is already stored in a Chroma vector database as an embedding. To price a new item, the code embeds the item, asks Chroma for the five nearest products, and writes those five (with their real prices) into the prompt as context. The frontier model then prices the item with concrete, similar examples in front of it — a strong hint that pushes its guess much closer than pricing blind.

The serverless request flow

When the ensemble asks the specialist for a price, that single line of Python triggers a round-trip to the cloud. It helps to picture the steps, because they explain both why the very first call is slow and why the rest are quick.

Not run here

Nothing on this page was executed on this machine. The code is the course's own, and running it needs a deployed Modal service, a populated 400,000-item Chroma vector store, a frontier-model API key, and the fine-tuned weights. Treat the code as a faithful copy of the lab to run yourself, not as output captured here. The prices in the diagrams are illustrative.

def vector(item):
    return encoder.encode(item.summary)

def find_similars(item):
    vec = vector(item)
    results = collection.query(query_embeddings=vec.astype(float).tolist(), n_results=5)
    documents = results['documents'][0][:]
    prices = [m['price'] for m in results['metadatas'][0][:]]
    return documents, prices

# We need to give some context to GPT-5.1 by selecting 5 products with similar descriptions

def make_context(similars, prices):
    message = "For context, here are some other items that might be similar to the item you need to estimate.\n\n"
    for similar, price in zip(similars, prices):
        message += f"Potentially related product:\n{similar}\nPrice is ${price:.2f}\n\n"
    return message

documents, prices = find_similars(test[0])
print(make_context(documents, prices))

def messages_for(item, similars, prices):
    message = f"Estimate the price of this product. Respond with the price, no explanation\n\n{item.summary}\n\n"
    message += make_context(similars, prices)
    return [{"role": "user", "content": message}]

documents, prices = find_similars(test[0])

# The function for gpt-5.1

def gpt_5__1_rag(item):
    documents, prices = find_similars(item)
    response = completion(model="gpt-5.1", messages=messages_for(item, documents, prices), seed=42)
    return response.choices[0].message.content

def get_price(reply):
    reply = reply.replace("$", "").replace(",", "")
    match = re.search(r"[-+]?\d*\.\d+|\d+", reply)
    return float(match.group()) if match else 0

In the notebook, the RAG pricer returns a price close to the true one on a test item, and evaluate draws a chart with many green points. The ensemble's first run is slow — a few minutes while Modal warms up the specialist — then a few seconds per item after that. Common mistakes and real costs
  • Cold starts feel like a hang. The first .remote call after a quiet period has to wake a machine and load the model — that can take minutes. It is not frozen; later calls are fast.
  • A running GPU service costs money. Serverless bills per second, but a service that never scales down, or one you set to stay warm, keeps a GPU running and billing. Check Modal's dashboard and tear down services you are not using.
  • Keep secrets out of the code. Never paste API keys or your Hugging Face token into pricer_service.py or the notebook. Store them as Modal secrets (and in your local .env), so they are never committed to git or baked into the deployed file.
  • Wrong service name. modal.Cls.from_name must use the exact app and class names from the deploy, or the lookup fails. A typo here is the most common error.
Video vs repo
  • The third pricer. The video builds a random forest (a traditional machine-learning model) on the embeddings. The repo file embedded here uses a deep neural network instead (DeepNeuralNetworkInference, NeuralNetworkAgent). The role is identical: a non-LLM opinion trained on the same vectors.
  • How the combiner is built. The video trains a linear regression over the model outputs — and even adds the minimum and maximum of the three as extra inputs — letting the data pick the weights. The embedded ensemble function uses a fixed weighted average (0.8 / 0.1 / 0.1). Same idea, simpler form; the production EnsembleAgent keeps the learned-weights approach.
  • Frontier model and SDK. The video calls gpt-4o-mini through the OpenAI client; this file calls gpt-5.1 through litellm. Model names are values you swap as providers retire them.
  • No LangChain. Both deliberately build the RAG pipeline by hand (embed, query Chroma, build the prompt) rather than using LangChain, so you can see exactly what happens under the hood.
Recap
  • A fine-tuned model is only useful to a real system if it is reachable; Modal turns it into a cloud service you call like a local function.
  • You deploy once with modal deploy pricer_service.py; the notebook then connects with modal.Cls.from_name("pricer-service", "Pricer") and calls pricer.price.remote(...) to run the model on a cloud GPU.
  • Serverless means you pay only for the seconds your code runs; the price is a cold start on the first call, after which calls are fast.
  • An ensemble combines three different pricers — a RAG frontier pricer, the deployed specialist, and a machine-learning model — into one steadier estimate.
  • The RAG pricer finds five similar products in a 400,000-item Chroma store and feeds them to the frontier model as context, built by hand without LangChain.
  • The combiner blends the three estimates: a fixed weighted average in this file, a learned linear regression in the video. The result is reliable rather than dramatically more accurate.
  • Keep keys in Modal secrets and your .env, watch for idle GPU costs, and remember this code was not run here — it needs the deployed service, the vector store, and keys.
