Week 8 · Day 4 — Agents That Collaborate

The agent framework: a planning agent coordinates a scanner agent (finds deals), the ensemble pricer, and a messaging agent - each doing one job and handing off to the next.

Companion to Ed Donner's course · uv setup · Python + TypeScript/React · code verified against the repo

This is the day everything from Week 8 clicks into place. Over the last three days you built the pieces of "The Price is Right": a scanner that reads deal feeds, an ensemble pricer that estimates what a product is really worth, and a way to send a push notification. Today you wire them into a single agentic system: a planning agent that runs the whole show by calling each worker in turn. Each agent does exactly one job and then hands its result to the next. That handoff pattern of small, specialised, collaborating agents is the big idea of the day.

The instructor is emphatic that none of this is magic. There are off-the-shelf agent frameworks (LangChain, Hugging Face agents, Gradio, and others), but he deliberately avoids them. By now you know how to call a model directly, so you can connect a few models and a little Python yourself and see exactly what information flows between the agents. The whole "framework" turns out to be a handful of plain classes that call one another.

What an agent system is, and the five hallmarks

In the video the instructor lists five hallmarks of agentic AI. A solution is agentic when it does some mix of these: it breaks a big task into smaller steps; it uses tools (function calling and structured outputs) so the model does more than chat; it has an environment the agents share (for example a common memory and a way to call each other); it often has a planning agent that decides what to do in what order; and, most distinctively, it has autonomy — some existence that runs behind the scenes rather than only while a human is chatting with it. No single one is required, but the more boxes you tick, the more clearly "agentic" the system is.

New to multi-agent systems? What they are and why they matter

A single agent is a program that uses a model to do a job. A multi-agent system is several such programs, each responsible for one narrow task, that cooperate to solve a problem none of them could do alone. Today's system has four workers: one finds candidate deals, one prices them, one picks the best, and one sends the alert. Splitting the work this way keeps each piece simple to write, test and reason about — the same reason we split ordinary code into small functions. The difference is that some of these "functions" are whole language models.

The four agents and their one job each

The planning agent is the coordinator. In this course it is not a model at all — it is a short piece of Python, because the workflow is simple and the order is fixed: scan, then price, then pick the best, then maybe alert. The instructor points out you could make the planner itself a model that decides the order (a nice challenge), but you do not have to; a planner can be plain code or even a JSON config.

The scanner agent (built on Day 3's work) reads RSS deal feeds, asks a frontier model to pull out a pithy description and a price for each item, and returns a short list of candidate deals. It is given the shared memory so it can skip anything already surfaced. The ensemble pricer agent estimates what each product is really worth by calling three underlying models (the fine-tuned specialist on Modal, a RAG frontier model, and a random-forest model) and blending their answers. The messaging agent is the simplest: given the best opportunity, it sends a push notification (via Pushover) so the deal lands on your phone.

New to specialised agents and handoff? What they are and why they matter

A specialised agent is one that does a single, well-defined job and nothing else. The scanner only finds deals; it does not price them. The pricer only estimates value; it does not decide whether to alert you. A handoff is the moment one agent finishes and passes its output to the next: the scanner hands a list of deals to the planner, which hands each description to the pricer, which hands a price back, and so on. Because each agent has a narrow contract (clear input, clear output), you can test, replace or upgrade any one of them without touching the others.

New to planning and orchestration? What they are and why they matter

Orchestration means arranging separate pieces so they run in the right order with the right data passed between them — like a conductor cueing each section of an orchestra. The planning agent is that conductor here. It knows which agent to call first, what to feed the next one, and when to stop. Keeping the orchestration in one place means the workers stay dumb and simple: they just do their job when asked. If you later want a different workflow, you change the planner, not the agents.

Autonomy: the one that really distinguishes an agent

The instructor singles out autonomy as the hallmark that most separates an agent from an ordinary chat app. The airline chatbot and the RAG Q&A from earlier weeks had memory, but they only existed while a human was typing into them. An autonomous agent has a presence beyond a single conversation: a process running behind the scenes, doing its job without a person prompting each step. Today's system is almost there — you still kick off a run by hand — and tomorrow (Day 5) you make it truly autonomous by having it run on a schedule with a Gradio dashboard on top.

New to autonomous operation? What it is and why it matters

An autonomous program runs on its own, triggered by a timer or an event rather than by a person clicking a button. A deal scanner that wakes up every few minutes, checks the feeds, and messages you only when it finds something good is autonomous: most of the time nothing happens and no human is involved. This is powerful but also where the warnings below come from — an unattended process that calls paid models needs guard-rails so it cannot spend money or loop forever without anyone watching.

The code

Below is the Day 4 notebook. It teaches the framework idea in two halves. The first half (most of the file) is a self-contained demo: it defines three tool functions — scan, estimate, notify — describes them to the model, and then lets a single model act as the planner, calling the tools in sequence until the job is done. This is the "planner as a model" version the instructor mentions. The second half (the last few lines) points at the real, Python-coded framework by creating an AutonomousPlanningAgent from the agents/ package and running its plan() method.

The three functions here are deliberately fake (they print and return hard-coded values) so you can watch the planning loop work without waiting for real feeds or Modal. The genuine agents live in standalone files in the repo, not in this notebook: deal_agent_framework.py (the DealAgentFramework class that sets up logging, loads the Chroma database and memory, and runs the planner), and the agents/ folder (agent.py — the tiny base class every agent extends to log in its own colour; scanner_agent.py, ensemble_agent.py, messaging_agent.py and the planning agents). Only this notebook is embedded below; the standalone files are what the finished system actually runs.

def handle_tool_call(message):
    """
    Actually call the tools associated with this message
    """
    results = []
    for tool_call in message.tool_calls:
        tool_name = tool_call.function.name
        arguments = json.loads(tool_call.function.arguments)
        tool = globals().get(tool_name)
        result = tool(**arguments) if tool else {}
        results.append({"role": "tool","content": json.dumps(result),"tool_call_id": tool_call.id})
    return results

Then just reply OK to indicate success.
"""

What you should see

When the real framework runs from the command line, the log fills with each agent announcing itself in its own colour: the agent framework initialises, the planning agent starts, the scanner becomes ready, then the ensemble's three models (the Modal specialist, the RAG frontier model, the random forest) load and report ready, the messenger is ready, and the framework prints that it is ready. Then a run kicks off: the scanner returns a handful of deals, the planner prices each one, picks the best, and — if the discount clears the threshold — sends a push notification to your phone with the deal and a tap-through link. In the video the instructor gets an alert about a refurbished laptop estimated near $925 and offered at $560.

Common mistakes and real risks of agent systems
  • Agents failing silently. If one agent returns nothing (the scanner finds no new deals, a model times out), the pipeline can quietly produce no alert. That is sometimes correct, but without good logging you cannot tell "nothing good today" from "something broke". This is exactly why every agent logs in its own colour.
  • The cost of many model calls. One run can call several models many times — the ensemble alone calls three models per deal, across several deals. Those paid calls add up fast. Keep an eye on how many calls a single run makes before you let it run often.
  • Runaway loops. A model-as-planner loop keeps calling tools until it decides to stop. A confused model could call tools over and over. The notify tool's "only call this one time" instruction and a sensible stop condition are the guard-rails; an autonomous, unattended version needs hard limits so it cannot loop (or spend) without end.
  • Hard-coded numbers. The instructor flags the hard-coded $50 threshold and the "top 5" count as things to turn into named, configurable values before you call this production code.

Recap
  • An agentic system breaks a task into steps, uses tools, shares an environment, often has a planner, and ideally runs autonomously.
  • Today's system has four specialised agents: a scanner (finds deals), an ensemble pricer (estimates value), a planner (coordinates and picks the best), and a messaging agent (sends the alert).
  • Each agent does one job and hands its output to the next; the planner runs them in a fixed order: scan, price, select, alert.
  • The planner can be plain Python (the video) or a model using function calling (the notebook demo); the embedded notebook shows both and then calls AutonomousPlanningAgent.plan().
  • Deal selection keeps only the single best opportunity and alerts only when the discount beats a threshold, so most runs correctly send nothing.
  • The real framework lives in standalone files (deal_agent_framework.py, agents/*); the notebook's tools are fake stand-ins so the loop can be shown cheaply.
  • Watch the risks: silent failures, the cost of many model calls, and runaway loops — logging, thresholds and stop conditions are the guard-rails. True autonomy comes on Day 5.
  • The system was not run live for this guide; it is shown as in the course.
