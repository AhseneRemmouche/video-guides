Week 8 · Day 3 — Structured Outputs and the Scanner Agent

Make the model return reliable typed data with structured outputs (Pydantic), then build the scanner agent that finds candidate deals and the messaging agent that sends alerts.

Companion to Ed Donner's course · uv setup · Python + TypeScript/React · code verified against the repo

So far this week you built pricing agents that take a clean product description and return a number. Today you build the piece that finds something worth pricing in the first place: a ScannerAgent that reads public deal feeds, hands the raw text to a frontier model, and gets back a tidy, typed list of the five best deals - product description, price, and link - ready to feed into the rest of the system. The new skill that makes this reliable is structured outputs: a way to tell the model "answer in exactly this shape" and have it obey.

The instructor frames Day 3 as a callback to Week 1. Back then you wrote a web summarizer - "the Reader's Digest of the internet". Today takes that same idea a few notches further: instead of summarizing one page, you scrape dozens of deal listings and ask the model to synthesize them into structured data you can act on. It is also a throwback in a second way - the messy, real-world text ("up to $350 off with trade-in") is exactly the kind of fuzzy input that only a language model can parse sensibly, which is the whole reason a model sits in the middle of this pipeline.

Where today's code sits in the project. The scanner is the front door of "The Price is Right". It produces candidate deals; the Day 2 pricing agents (the RAG retriever, the fine-tuned specialist, and the ensemble) then estimate what each item is really worth; and today's MessagingAgent sends you a phone alert when a deal looks like a genuine bargain. Day 4 wires all of these together under a planner.

The concepts the instructor explains

Two ideas carry the day. The first is structured outputs. You have already used JSON mode in earlier weeks - you ask the model, in words, to reply in JSON and describe the shape in the prompt. That works surprisingly often, but it is not a guarantee. On complicated objects the model can drift: a missing field, a wrong type, a stray sentence of explanation. Structured outputs fix that by letting you hand the model an actual Pydantic class as the required schema. The model is constrained to produce data that fits the class, and the SDK hands you back a real Python object, already validated - not a string you have to parse and pray over.

The second idea is the agent itself. The notebook first does the whole job inline - scrape, prompt, parse - so you can see every moving part. Then it shows the same logic packaged into a ScannerAgent class that lives in the project's agents/ folder. That is the shape of an agentic system: small, single-purpose components with a clear job, that a higher-level planner can call. The scanner's one job is "give me new, well-described, clearly-priced deals".

New to structured outputs? What they are and why they matter

A language model normally returns free text. "Structured outputs" is a feature of modern frontier models where you supply a schema - a precise description of the fields you want and their types - and the model is forced to answer in that exact shape. In this code the schema is a Pydantic class called DealSelection. Because the answer is guaranteed to fit, your program can use it directly (loop over results.deals, read deal.price) instead of writing fragile text-cleaning code. It is the difference between "please reply in JSON" (a polite request) and "you may only reply in this shape" (a contract).

New to Pydantic and BaseModel? A one-minute tour

Pydantic is a popular Python library for describing and validating data. You define a class that inherits from BaseModel and list its fields with their types, for example a price that must be a float. Pydantic then checks any data against that definition and can convert cleanly between the class and JSON. The course defines three such classes in agents/deals.py: a Deal (product_description, price, url), a DealSelection (just a list of Deal objects), and an Opportunity (a deal plus an estimated value and the resulting discount). Passing DealSelection to the model is how you say "I want a list of deals, each shaped like this".

The full notebook

Here is the complete Day 3 notebook code. It runs top to bottom: set up, scrape the feeds, build the prompts, call the model with a structured-output schema, print the results, then switch to the packaged ScannerAgent and finally test push notifications. len(deals)

deals[10].describe()

SYSTEM_PROMPT = """You identify and summarize the 5 most detailed deals from a list, by selecting deals that have the most detailed, high quality description and the most clear price.
Respond strictly in JSON with no explanation, using this format. You should provide the price as a number derived from the description. If the price of a deal isn't clear, do not include that deal in your response.
Most important is that you respond with the 5 deals that have the most detailed product description with price. It's not important to mention the terms of the deal; most important is a thorough description of the product.
Be careful with products that are described as "$XXX off" or "reduced by $XXX" - this isn't the actual price of the product. Only respond with products when you are highly confident about the price. 
"""

USER_PROMPT_PREFIX = """Respond with the most promising 5 deals from this list, selecting those which have the most detailed, high quality product description and a clear price that is greater than 0.
You should rephrase the description to be a summary of the product itself, not the terms of the deal.
Remember to respond with a short paragraph of text in the product_description field for each of the 5 items that you select.
Be careful with products that are described as "$XXX off" or "reduced by $XXX" - this isn't the actual price of the product. Only respond with products when you are highly confident about the price. 

Deals:

"""

USER_PROMPT_SUFFIX = "\n\nInclude exactly 5 deals, no more."

# this makes a suitable user prompt given scraped deals

def make_user_prompt(scraped):
    user_prompt = USER_PROMPT_PREFIX
    user_prompt += '\n\n'.join([scrape.describe() for scrape in scraped])
    user_prompt += USER_PROMPT_SUFFIX
    return user_prompt

# Let's create a user prompt for the deals we just scraped, and look at how it begins

user_prompt = make_user_prompt(deals)
print(user_prompt[:2000])
messages = [{"role": "system", "content": SYSTEM_PROMPT}, {"role": "user", "content": user_prompt}]

response = openai.chat.completions.parse(model=MODEL, messages=messages, response_format=DealSelection)
results = response.choices[0].message.parsed
results

for deal in results.deals:
    print(deal.product_description)
    print(deal.price)
    print(deal.url)
    print()

New to RSS feeds? What "fetching deals" actually means

An RSS feed is a machine-readable list a website publishes of its latest items - here, newly posted deals. The feedparser package reads a feed URL and returns the entries as plain dictionaries (title, summary, link). The course picks feeds in categories its pricing model knows well (electronics, computers, automotive, smart home). Because the feed summary alone is thin, ScrapedDeal also follows each link and scrapes the real page with BeautifulSoup, pausing briefly between requests so it does not hammer the server. That pause is simply good manners when scraping.

Structured outputs vs function calling - which should I use?

The instructor notes these are close cousins; both force the model's answer into a defined shape. The rule of thumb: if the model's output will be fed straight into application code as function arguments, prefer function calling (tools) - it is built for driving real functions with the right parameters. If you just want well-formed data for downstream use - like our list of deals - structured outputs is the cleaner fit. Both are far more reliable than describing the shape in words and hoping. You develop a feel for which performs better with practice.

From inline code to a packaged agent

The second half of the notebook takes everything above and uses it through a proper ScannerAgent class that lives in agents/scanner_agent.py. Same system and user prompts, same parse call - but wrapped as a reusable component with two extra touches: it can take a memory of URLs it has already seen and drop those, so you only get new deals; and it filters out anything whose price is not greater than zero before returning. If nothing new is found it returns None. That packaging is what lets a higher-level planner call the scanner on a schedule.

New to agents? What "an agent" means in this course

Here an agent is simply a small Python class with one clear responsibility and a method you call to do its job. The ScannerAgent finds deals; the MessagingAgent sends alerts; Day 2's agents estimate prices. None of them is "intelligent" on its own - the intelligence comes from the model calls inside. What makes the overall system agentic is that these independent pieces can be organized by a planner, keep a memory, and run without a human in the loop. Day 4 assembles them.

What you should see. After fetch finishes (a minute or two), len(deals) prints 50 (five feeds times ten). The parse call returns an object whose type is DealSelection, and results.deals holds exactly five Deal objects, each with a sensible product summary, a numeric price, and a working URL. The Pushover checks should print that each key "found and starts with" a letter, and the test pushes should arrive on your phone.
Common mistakes and the one the instructor hit live.
  • Reading .content instead of .parsed. With parse, the typed object is on .parsed. .content gives you a raw string and defeats the whole point.
  • Trusting the price blindly. On screen the model read "up to $350 off with trade-in" as a price of $350. The fix was to add explicit warnings about "$XXX off" to both prompts and tell the model to answer only when highly confident. Always spot-check the numbers a model extracts.
  • Missing Pushover keys. If the checks print "not found", add PUSHOVER_USER and PUSHOVER_TOKEN to .env, save, and re-run load_dotenv(override=True).
  • Stale results. Without the agent's memory of seen URLs you would get the same deals every run. The memory filter is what keeps each scan fresh.
