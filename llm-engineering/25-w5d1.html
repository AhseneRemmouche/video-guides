Week 5 · Day 1 — RAG Fundamentals and Vector Embeddings

What RAG is and why it helps, a do-it-yourself RAG with no libraries, and the key idea underneath it all - vector embeddings that place meaning in space.

Companion to Ed Donner's course · uv setup · Python + TypeScript/React · code verified against the repo

This week is about RAG — retrieval-augmented generation. It is a simple, powerful idea: before you ask a model a question, you first look through your own documents, pull out the few pieces that are relevant, and paste them into the prompt. The model then answers using that extra context instead of only what it memorised during training. Today's page covers three things, in the order the instructor teaches them: what RAG is and why it helps, a do-it-yourself RAG with no libraries at all (the Python Day 1 lab — brute-force keyword matching), and the key idea that makes the real thing work: vector embeddings.

The running example is a fictional insurance-tech company called Insurellm. We have a folder of its documents (company notes, products, employee records) and we want an AI knowledge worker that answers questions about them accurately. A plain model would guess or make things up; RAG lets it read the actual records first.

New to RAG? What it is and why it matters RAG stands for retrieval-augmented generation. A language model only knows what was in its training data, and it will confidently invent answers about anything else — your company, your documents, last week's events. RAG fixes this without retraining the model: you keep your documents in a store, and at question time you retrieve the relevant ones, augment the prompt with them, and let the model generate an answer grounded in that text. The model stays the same; you just feed it better context. This is how most "chat with your documents" and company-knowledge assistants are built.
Retrieval vs augmentation vs generation — the three words in the name The name spells out the pipeline. Retrieval is the lookup step: given the user's question, find the few documents most relevant to it. Augmentation is the stuffing step: take those documents and add them into the prompt you send the model (usually in the system message). Generation is the normal step you already know: the model reads the enriched prompt and writes an answer. RAG is just these three steps wired together. Everything hard about RAG is in the first step — finding the right documents — which is why vector embeddings matter.

The small idea: a DIY RAG with no libraries

The instructor calls this the "little idea" behind RAG, and it really is obvious once you see it: when a question comes in, look it up in a store of documents, and if something matches, paste that document into the prompt. No special library, no database — just a Python dictionary and a string match. It is brittle, but it shows there is no magic. Here is the whole flow before we read the code.

import os
import glob
from dotenv import load_dotenv

load_dotenv(override=True)

    print(f"OpenAI API Key exists and begins {openai_api_key[:8]}")

MODEL = "gpt-4o-mini"
openai = OpenAI()

knowledge = {}

filenames = glob.glob("knowledge-base/employees/*")

for filename in filenames:
    name = Path(filename).stem.split(' ')[-1]
    with open(filename, "r", encoding="utf-8") as f:
        knowledge[name.lower()] = f.read()

knowledge

knowledge["lancaster"]

filenames = glob.glob("knowledge-base/products/*")

for filename in filenames:
    name = Path(filename).stem
    with open(filename, "r", encoding="utf-8") as f:
        knowledge[name.lower()] = f.read()

knowledge.keys()

SYSTEM_PREFIX = """
You represent Insurellm, the Insurance Tech company.
You are an expert in answering questions about Insurellm; its employees and its products.
You are provided with additional context that might be relevant to the user's question.
Give brief, accurate answers. If you don't know the answer, say so.

Relevant context:
"""

def get_relevant_context_simple(message):
    text = ''.join(ch for ch in message if ch.isalpha() or ch.isspace())
    words = text.lower().split()
    relevant_context = []
    for word in words:
        if word in knowledge:
            relevant_context.append(knowledge[word])
    return relevant_context          

def get_relevant_context(message):
    text = ''.join(ch for ch in message if ch.isalpha() or ch.isspace())
    words = text.lower().split()
    return [knowledge[word] for word in words if word in knowledge]   

get_relevant_context("Who is lancaster?")

get_relevant_context("Who is Lancaster and what is carllm?")

def additional_context(message):
    relevant_context = get_relevant_context(message)
    if not relevant_context:
        result = "There is no additional context relevant to the user's question."
    else:
        result = "The following additional context might be relevant in answering the user's question:\n\n"
        result += "\n\n".join(relevant_context)
    return result

print(additional_context("Who is Alex Lancaster?"))

def chat(message, history):
    system_message = SYSTEM_PREFIX + additional_context(message)
    messages = [{"role": "system", "content": system_message}] + history + [{"role": "user", "content": message}]
    response = openai.chat.completions.create(model=MODEL, messages=messages)
    return response.choices[0].message.content

view = gr.ChatInterface(chat, type="messages").launch(inbrowser=True)
// Day 2 / Day 3 - Build the vector store (TypeScript port of the LangChain ingest step)
//
// The Python labs used LangChain's DirectoryLoader + CharacterTextSplitter +
// OpenAIEmbeddings + Chroma. Here we do the LangChain.js equivalent:
//   - read the sample docs under knowledge/  (a hand-rolled DirectoryLoader)
//   - split them with RecursiveCharacterTextSplitter
//   - embed with OpenAIEmbeddings (text-embedding-3-small)
//   - store the vectors in an in-memory MemoryVectorStore (no native deps, no Chroma server)
//
// Everything up to embedding works with no API key; only building the store needs one,
// so rag.ts / the server can import these helpers and stay key-guarded.
import "dotenv/config";
import { readdirSync, readFileSync, statSync } from "node:fs";
import { join, relative } from "node:path";
import { fileURLToPath, pathToFileURL } from "node:url";
import { Document } from "@langchain/core/documents";
import { OpenAIEmbeddings } from "@langchain/openai";
import { RecursiveCharacterTextSplitter } from "@langchain/textsplitters";
import { MemoryVectorStore } from "langchain/vectorstores/memory";

export const EMBEDDING_MODEL = "text-embedding-3-small";

// knowledge/ sits next to src/ at the project root.
const KNOWLEDGE_DIR = fileURLToPath(new URL("../knowledge", import.meta.url));

export function hasOpenAIKey(): boolean {
  return Boolean(process.env.OPENAI_API_KEY);
}

// Walk a folder and return every .md / .txt file path (recursively).
function listDocFiles(dir: string): string[] {
  const out: string[] = [];
  for (const entry of readdirSync(dir)) {
    const full = join(dir, entry);
    if (statSync(full).isDirectory()) {
      out.push(...listDocFiles(full));
    } else if (/\.(md|txt)$/i.test(entry)) {
      out.push(full);
    }
  }
  return out;
}

// A hand-rolled DirectoryLoader: one Document per file, tagged with its source
// path and a doc_type taken from the top-level folder (company / products / employees).
export function loadDocuments(): Document[] {
  const files = listDocFiles(KNOWLEDGE_DIR);
  return files.map((file) => {
    const rel = relative(KNOWLEDGE_DIR, file).replace(/\\/g, "/");
    const docType = rel.split("/")[0] ?? "general";
    return new Document({
      pageContent: readFileSync(file, "utf-8"),
      metadata: { source: rel, doc_type: docType },
    });
  });
}

// Split the documents into overlapping chunks, mirroring the Python chunk_size/overlap.
export async function splitDocuments(documents: Document[]): Promise<Document[]> {
  const splitter = new RecursiveCharacterTextSplitter({
    chunkSize: 1000,
    chunkOverlap: 200,
  });
  return splitter.splitDocuments(documents);
}

// Build the in-memory vector store. Requires OPENAI_API_KEY (embeddings call OpenAI).
export async function buildVectorStore(): Promise<MemoryVectorStore> {
  if (!hasOpenAIKey()) {
    throw new Error("OPENAI_API_KEY is not set - cannot create embeddings. See .env.example.");
  }
  const documents = loadDocuments();
  const chunks = await splitDocuments(documents);
  const embeddings = new OpenAIEmbeddings({ model: EMBEDDING_MODEL });
  return MemoryVectorStore.fromDocuments(chunks, embeddings);
}

async function main(): Promise<void> {
  const documents = loadDocuments();
  console.log(`Loaded ${documents.length} documents from knowledge/`);
  const chunks = await splitDocuments(documents);
  console.log(`Split into ${chunks.length} chunks`);

  if (!hasOpenAIKey()) {
    console.log("OPENAI_API_KEY not set - skipping embedding. Set it in .env to build the store.");
    return;
  }

  const store = await buildVectorStore();
  // MemoryVectorStore keeps vectors on `memoryVectors`; report how many we embedded.
  console.log(`Vector store built with ${store.memoryVectors.length} vectors (model: ${EMBEDDING_MODEL}).`);
}

// Only run when executed directly (npm run ingest), not when imported by rag.ts.
if (import.meta.url === pathToFileURL(process.argv[1] ?? "").href) {
  main().catch((err) => {
    console.error(err);
    process.exitCode = 1;
  });
}

The big idea: vector embeddings

The DIY matcher only finds a document when the question contains the exact key word. Ask "Who is Avery?" instead of "Lancaster", or misspell a name, and it finds nothing. The fix is to search by meaning instead of by exact letters, and the tool for that is the vector embedding.

New to vector embeddings? What they are A vector embedding turns a piece of text into a list of numbers — a point in space. A short string might become a list of around 1,500 numbers (the text-embedding-3-small model used this week produces 1,536). The numbers are chosen so that text with similar meaning lands at nearby points, even when the words are different. "Who is the CEO?" and "Avery Lancaster's role" would sit close together; "my cat is hungry" would sit far away. A model that does this is called an autoencoding model (it reads the whole input and emits one representation), as opposed to the autoregressive chat models that generate text one token at a time. The classic demo is vector math: king − man + woman lands near queen, which shows the numbers really do carry meaning.
New to cosine similarity? How "nearness" is measured To find nearby vectors you need a number for how close two of them are. The usual measure is cosine similarity: it looks at the angle between two vectors, not their length. Two vectors pointing the same way score 1 (very similar); at a right angle they score 0 (unrelated); pointing opposite they score −1. Using the angle rather than the straight-line distance means a long document and a short question can still count as a close match if they point the same way — they are "about the same thing". This is the comparison that powers semantic search.

Put it together and you get the full RAG pipeline: an encoding (embedding) model turns both the question and every document into vectors, you store the document vectors, and at question time you retrieve the documents whose vectors sit closest to the question's vector — then stuff them in the prompt exactly as the toy version did. Same three steps; a far smarter retrieval.

DIY vs the library way

What you should see. Running the Python notebook, the key check prints first, then the knowledge dictionary fills with surnames and product names as keys. Asking "Who is Avery Lancaster?" in the Gradio chat returns an accurate answer built from her real record; asking "What is carllm?" summarises the product document. Running the TypeScript ingest.ts with no key prints how many documents loaded and how many chunks they split into; with a key set it also reports how many vectors were embedded into the store.
Common mistakes and limits. The DIY matcher is deliberately brittle: "Avery" (first name), "lancaster" with a typo, or any synonym returns nothing, because it needs the exact key word. That is garbage-in from bad retrieval — if the lookup pulls the wrong document (or none), the model answers from thin air, and a confident wrong answer is worse than "I don't know". Embeddings fix the matching but are not free: every document and every question must be sent to the embedding API, which costs money and time, so you embed your documents once and reuse the store. Watch the model name too — the video uses gpt-4o-mini for chat and text-embedding-3-small for embeddings; both are values you may need to swap as providers retire models.

Recap
  • RAG = retrieve + augment + generate: find the documents relevant to a question, paste them into the prompt, and let the model answer from them. The model is unchanged; only its context improves.
  • The DIY RAG (Python day1.py) stores documents in a dictionary and retrieves by an exact word match against the question. It works, proves there is no magic, but is brittle — misspellings and synonyms find nothing.
  • Vector embeddings turn text into a long list of numbers (around 1,536 for text-embedding-3-small) so that similar meanings land at nearby points, letting you search by meaning instead of by exact letters.
  • Cosine similarity measures nearness by the angle between two vectors, which is how the retrieval step picks the closest documents (semantic search).
  • The TypeScript ingest.ts previews the library way: LangChain.js loads, splits and embeds documents into a vector store — the robust replacement for the dictionary match. Day 2 builds this same load/split/embed step in Python with LangChain.
