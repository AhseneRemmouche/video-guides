Week 5 · Day 1 — RAG Fundamentals and Vector Embeddings

What RAG is and why it helps, a do-it-yourself RAG with no libraries, and the key idea underneath it all - vector embeddings that place meaning in space.

Companion to Ed Donner's course · uv setup · Python + TypeScript/React · code verified against the repo

This week is about RAG — retrieval-augmented generation. It is a simple, powerful idea: before you ask a model a question, you first look through your own documents, pull out the few pieces that are relevant, and paste them into the prompt. The model then answers using that extra context instead of only what it memorised during training. Today's page covers three things, in the order the instructor teaches them: what RAG is and why it helps, a do-it-yourself RAG with no libraries at all (the Day 1 notebook: brute-force keyword matching), and the key idea that makes the real thing work: vector embeddings.

The running example is a fictional insurance-tech company called Insurellm. We have a folder of its documents (company notes, products, employee records) and we want an AI knowledge worker that answers questions about them accurately. A plain model would guess or make things up; RAG lets it read the actual records first.

New to RAG? What it is and why it matters RAG stands for retrieval-augmented generation. A language model only knows what was in its training data, and it will confidently invent answers about anything else — your company, your documents, last week's events. RAG fixes this without retraining the model: you keep your documents in a store, and at question time you retrieve the relevant ones, augment the prompt with them, and let the model generate an answer grounded in that text. The model stays the same; you just feed it better context. This is how most "chat with your documents" and company-knowledge assistants are built.
Retrieval vs augmentation vs generation — the three words in the name The name spells out the pipeline. Retrieval is the lookup step: given the user's question, find the few documents most relevant to it. Augmentation is the stuffing step: take those documents and add them into the prompt you send the model (usually in the system message). Generation is the normal step you already know: the model reads the enriched prompt and writes an answer. RAG is just these three steps wired together. Everything hard about RAG is in the first step — finding the right documents — which is why vector embeddings matter.

    for chunk in stream:
        response += chunk.choices[0].delta.content or ''
        yield response

// Video 2 in TypeScript: a DIY RAG with no libraries (run: npx tsx day1_diy_rag.ts)
import "dotenv/config";
import { readdirSync, readFileSync } from "node:fs";
import { basename, join } from "node:path";
import { createInterface } from "node:readline/promises";
import OpenAI from "openai";

// price is a factor for our company, so we're going to use a low cost model
const MODEL = "gpt-6-luna";
const openai = new OpenAI(); // reads OPENAI_API_KEY from .env

// The whole "knowledge base" is one object: key = a name, value = that document's text
const context: Record<string, string> = {};

// Employees: the key is the last word of the file name (the surname)
for (const file of readdirSync("knowledge-base/employees")) {
  const name = basename(file, ".md").split(" ").at(-1) ?? file;
  context[name] = readFileSync(join("knowledge-base/employees", file), "utf-8");
}

// Products: the key is the file name without ".md"
for (const file of readdirSync("knowledge-base/products")) {
  context[basename(file, ".md")] = readFileSync(join("knowledge-base/products", file), "utf-8");
}
console.log(Object.keys(context));

const systemMessage =
  "You are an expert in answering accurate questions about Insurellm, the Insurance Tech company. " +
  "Give brief, accurate answers. If you don't know the answer, say so. " +
  "Do not make anything up if you haven't been provided with relevant context.";

// Retrieval: every document whose key appears, exactly, in the message
function getRelevantContext(message: string): string[] {
  const relevantContext: string[] = [];
  for (const [title, details] of Object.entries(context)) {
    if (message.includes(title)) relevantContext.push(details);
  }
  return relevantContext;
}

// Augmentation: paste the matching documents under the question
function addContext(message: string): string {
  const relevantContext = getRelevantContext(message);
  if (relevantContext.length > 0) {
    message += "\n\nThe following additional context might be relevant in answering this question:\n\n";
    for (const relevant of relevantContext) message += relevant + "\n\n";
  }
  return message;
}

console.log(getRelevantContext("Who is Avery and what is carllm?").length); // 0: exact, case-sensitive match

// Generation: earlier turns + the augmented question, streamed back
const history: OpenAI.Chat.ChatCompletionMessageParam[] = [];

async function chat(message: string): Promise<string> {
  const messages: OpenAI.Chat.ChatCompletionMessageParam[] = [
    { role: "system", content: systemMessage },
    ...history,
    { role: "user", content: addContext(message) },
  ];
  const stream = await openai.chat.completions.create({
    model: MODEL,
    reasoning_effort: "none",
    messages,
    stream: true,
  });
  let response = "";
  for await (const chunk of stream) {
    const piece = chunk.choices[0]?.delta?.content ?? "";
    response += piece;
    process.stdout.write(piece);
  }
  process.stdout.write("\n");
  history.push({ role: "user", content: message }, { role: "assistant", content: response });
  return response;
}

// A terminal chat instead of Gradio: type a question, press Enter on an empty line to stop
const rl = createInterface({ input: process.stdin, output: process.stdout });
while (true) {
  const question = await rl.question("You: ");
  if (!question.trim()) break;
  await chat(question);
}
rl.close();

Video 3 · Understanding vector embeddings

3 -Day 1 - Understanding Vector Embeddings The Key to RAG and LLM Retrieval.mp4 · 9:30

Slides. The DIY matcher only finds a document when the question contains the exact key word, so Ed turns to the idea that makes real RAG work. Most models in the course are auto-regressive (predict the next token from the past ones); auto-encoding models instead read the whole input and produce one output, as in sentiment analysis, classification, or a vector embedding: a list of numbers (often hundreds or thousands) that places the text as a point in space, so that texts with similar meaning land close together. He recalls the famous example king − man + woman ≈ queen, names BERT and OpenAI's embeddings (the encoder used this week), and redraws the RAG diagram with two new boxes: an encoding LLM that turns the question into a vector, and a vector datastore that returns the stored texts whose vectors sit closest to it. Next time: LangChain.

New to vector embeddings? What they are A vector embedding turns a piece of text into a list of numbers — a point in space. A short string might become a list of around 1,500 numbers (the text-embedding-3-small model used this week produces 1,536). The numbers are chosen so that text with similar meaning lands at nearby points, even when the words are different. "Who is the CEO?" and "Avery Lancaster's role" would sit close together; "my cat is hungry" would sit far away. A model that does this is called an autoencoding model (it reads the whole input and emits one representation), as opposed to the autoregressive chat models that generate text one token at a time. The classic demo is vector math: king − man + woman lands near queen, which shows the numbers really do carry meaning.
New to cosine similarity? How "nearness" is measured To find nearby vectors you need a number for how close two of them are. The usual measure is cosine similarity: it looks at the angle between two vectors, not their length. Two vectors pointing the same way score 1 (very similar); at a right angle they score 0 (unrelated); pointing opposite they score −1. Using the angle rather than the straight-line distance means a long document and a short question can still count as a close match if they point the same way — they are "about the same thing". This is the comparison that powers semantic search.

Put it together and you get the full RAG pipeline: an encoding (embedding) model turns both the question and every document into vectors, you store the document vectors, and at question time you retrieve the documents whose vectors sit closest to the question's vector, then paste them into the prompt exactly as the toy version did. Same three steps; a far smarter retrieval.

What you should see. context.keys() lists surnames ('Lancaster', 'Tran', …) followed by product names ('Carllm', 'Homellm', …). get_relevant_context("Who is Avery and what is carllm?") returns an empty list [], while add_context("Who is Alex Lancaster?") wrongly pulls in Avery's record. In the Gradio chat, "Who is Avery Lancaster?" gets an accurate answer built from her HR record and "What is Carllm?" summarises the product, but in a fresh chat "Who is Avery?" gets "I don't have any information". The TypeScript port prints the keys and 0, then waits for your questions in the terminal.
Common mistakes and limits. The DIY matcher is deliberately brittle: "Avery" (first name), "lancaster" with a typo, or any synonym returns nothing, because it needs the exact key word. That is garbage-in from bad retrieval — if the lookup pulls the wrong document (or none), the model answers from thin air, and a confident wrong answer is worse than "I don't know". Embeddings fix the matching but are not free: every document and every question must be sent to the embedding API, which costs money and time, so you embed your documents once and reuse the store. Watch the model name too: the video's gpt-4o-mini has since been retired, which is why the "Runs today" tab uses gpt-6-luna. On Windows, the video's split('/') and open() without an encoding also go wrong; the "Runs today" tab fixes both.

Recap
  • RAG = retrieve + augment + generate: find the documents relevant to a question, paste them into the prompt, and let the model answer from them. The model is unchanged; only its context improves.
  • The DIY RAG (day1.ipynb) stores documents in a dictionary and retrieves by an exact match of a key inside the question. It works, proves there is no magic, but is brittle — misspellings and synonyms find nothing.
  • Vector embeddings turn text into a long list of numbers (around 1,536 for text-embedding-3-small) so that similar meanings land at nearby points, letting you search by meaning instead of by exact letters.
  • Cosine similarity measures nearness by the angle between two vectors, which is how the retrieval step picks the closest documents (semantic search).
  • Next comes the library way: Day 2 uses LangChain to load and split the documents, Day 3 embeds them into a vector store, and Day 4 retrieves by meaning instead of by exact letters.
