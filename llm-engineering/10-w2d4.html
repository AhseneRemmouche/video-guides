Week 2 · Day 4 — Tools: Giving the Model Function Calling

Build an AI airline assistant that can call your own functions - how you describe a tool, how the model asks to use it, and how you run it and return the result.

Companion to Ed Donner's course · uv setup · Python + TypeScript/React · code verified against the repo

So far the model could only ever answer with words. Today it gets a new power: it can ask your program to run real code for it. The instructor calls these tools, and the technique is OpenAI function calling. We build a customer support assistant for a fictional airline, "FlightAI", that can look up a ticket price with a get_ticket_price function. When a customer asks "how much is a ticket to London?", the model does not guess — it asks us to run that function, we hand back the real answer, and the model turns it into a courteous reply.

Everything today is shown in two languages. Use the Python | TypeScript switch on the code card — or the Code in: switch at the top of the page — to flip between them; your choice is remembered as you read. The two versions do the same thing; only the syntax changes.

This is the idea that turns a chatbot into something closer to an agent: a model that does not just talk, but reaches out to the world through code you control. It sounds spooky — we are "letting the model run code on our machine" — but under the covers it is a plain, repeatable loop of messages passed back and forth.

What a "tool" actually is

A tool is nothing more than a function you already wrote, plus a plain-English description of it that you hand to the model. The model never runs your function itself. Instead, when it decides your function would help, it replies with a tool call: a little message that says "please run get_ticket_price with destination_city = "London" and give me the result." Your code runs the real function, sends the result back, and the model carries on. The model stays a text predictor the whole time; the power to act lives entirely in your code.

New to tools / function calling? What it is and why it matters

An LLM on its own is sealed off from the world: it cannot look anything up, do reliable arithmetic, or change anything. Function calling pokes a hole in that wall. You describe some of your own functions to the model; it may then ask for one to be run and use the result in its answer. The four classic uses the instructor lists are: fetch extra data (look something up in a database), take an action (book a meeting, buy a ticket), do a calculation (models are famously bad at arithmetic, so hand them a calculator), and change the UI. The key mental model: the model only ever requests a call — your program decides whether and how to run it.

The JSON schema that describes the tool

To tell the model about a function, you write a JSON schema: a structured description giving the function's name, a human-readable description of when to use it, and its parameters (each with a type and its own description). OpenAI turns this schema into tokens and feeds it to the model alongside your messages, so the model learns what the function is for and what inputs it needs. The description fields are not decoration — they are the only thing the model reads to decide when and how to call the tool, so they must be clear.

New to JSON schema? What it is and why it matters

JSON schema is a small, standard way to describe the shape of data: what fields exist, what type each one is (string, number, object, array…), and which are required. Here it describes the arguments your function expects. The model uses the schema twice: to understand that destination_city is a required string, and to format its request so the argument comes back in exactly that shape. "additionalProperties": false tells it not to invent extra fields. You do not have to learn all of JSON schema — copy this little pattern and change the names and types for your own function.

The round trip: how a tool call actually flows

Here is the whole dance in order. You send the conversation and the tools. The model reads the question, decides it needs the price, and instead of answering it stops with a special finish reason of tool_calls. Your code notices that, runs the real function, and appends two new rows to the message list: first the model's own request (the assistant message that asked for the tool), then the result (a new tool message). You send the whole thing back, and now the model has the number it needed and writes the final answer.

New to the tool-call round trip? Why two API calls, not one

A single question can take two trips to the model. On the first trip the model says "I can't answer yet — run this tool." You run it, add the answer to the conversation, and make a second trip; now the model has what it needs and replies for real. Why not let the model just run the function? Because the model lives on OpenAI's servers and your function lives on your machine — the model can only ask. That gap is the safety of the design: nothing runs unless your code chooses to run it.

When does the model decide to call a tool?

You do not tell it to. You pass the tools on every call and let the model choose. If the question can be answered from what it already knows, it answers normally and the finish reason is stop. If it needs something a tool provides, it stops with tool_calls instead. Your code branches on that one value.

// Day 4 - Tools / OpenAI function-calling (TypeScript port of day4.py)
// An airline assistant (FlightAI) that can look up ticket prices. The model decides
// when it needs the tool, we run the real function, feed the result back, and let the
// model turn it into a courteous reply.
import "dotenv/config";
import { pathToFileURL } from "node:url";
import OpenAI from "openai";

export const MODEL = "gpt-4o-mini";

export const SYSTEM_MESSAGE =
  "You are a helpful assistant for an Airline called FlightAI. " +
  "Give short, courteous answers, no more than 1 sentence. " +
  "Always be accurate. If you don't know the answer, say so.";

// The "database" of ticket prices (a plain object stands in for the Python sqlite table).
const ticketPrices: Record<string, string> = {
  london: "$799",
  paris: "$899",
  tokyo: "$1400",
  berlin: "$499",
};

export function getTicketPrice(destinationCity: string): string {
  console.log(`Tool called for city ${destinationCity}`);
  const price = ticketPrices[destinationCity.toLowerCase()] ?? "Unknown ticket price";
  return `The price of a ticket to ${destinationCity} is ${price}`;
}

// The JSON schema that describes our function to the model.
export const priceFunction: OpenAI.Chat.ChatCompletionTool = {
  type: "function",
  function: {
    name: "get_ticket_price",
    description: "Get the price of a return ticket to the destination city.",
    parameters: {
      type: "object",
      properties: {
        destination_city: {
          type: "string",
          description: "The city that the customer wants to travel to",
        },
      },
      required: ["destination_city"],
      additionalProperties: false,
    },
  },
};

export const tools: OpenAI.Chat.ChatCompletionTool[] = [priceFunction];

// Run each tool call the model requested and build the matching `tool` messages.
export function handleToolCalls(
  message: OpenAI.Chat.ChatCompletionMessage,
): OpenAI.Chat.ChatCompletionToolMessageParam[] {
  const responses: OpenAI.Chat.ChatCompletionToolMessageParam[] = [];
  for (const toolCall of message.tool_calls ?? []) {
    if (toolCall.type === "function" && toolCall.function.name === "get_ticket_price") {
      const args = JSON.parse(toolCall.function.arguments) as { destination_city: string };
      const priceDetails = getTicketPrice(args.destination_city);
      responses.push({ role: "tool", content: priceDetails, tool_call_id: toolCall.id });
    }
  }
  return responses;
}

// The full tool-call loop: ask the model; while it wants tools, run them and ask again.
export async function chat(openai: OpenAI, message: string): Promise<string> {
  const messages: OpenAI.Chat.ChatCompletionMessageParam[] = [
    { role: "system", content: SYSTEM_MESSAGE },
    { role: "user", content: message },
  ];
  let response = await openai.chat.completions.create({ model: MODEL, messages, tools });

  while (response.choices[0]?.finish_reason === "tool_calls") {
    const responseMessage = response.choices[0].message;
    messages.push(responseMessage);
    messages.push(...handleToolCalls(responseMessage));
    response = await openai.chat.completions.create({ model: MODEL, messages, tools });
  }
  return response.choices[0]?.message.content ?? "";
}

async function main(): Promise<void> {
  // Offline-safe sanity check: the tool runs without any network call.
  console.log(getTicketPrice("London"));
  console.log("Tool schema:", JSON.stringify(priceFunction, null, 2));

  if (!process.env.OPENAI_API_KEY) {
    console.log("\nOPENAI_API_KEY not set - skipping the live tool-call loop. See .env.example.");
    return;
  }
  const openai = new OpenAI();
  const reply = await chat(openai, "How much is a ticket to Tokyo?");
  console.log("Assistant:", reply);
}

// Only run the demo when this file is executed directly, not when imported.
if (import.meta.url === pathToFileURL(process.argv[1] ?? "").href) {
  main().catch((err) => {
    console.error(err);
    process.exitCode = 1;
  });
}

The message list grows by two rows

The clearest way to see the trick is to watch the messages list. Before the round trip it ends with your question. After it, two rows have been added: the model's request to use the tool (an assistant message carrying tool_calls), and your answer to that request (a tool message). The model then reads the whole list and writes its final reply.

What makes this "agentic"

The while loop is the seed of an agent. On each pass the model can ask for tools, see the results, and decide what to do next — including asking for more tools — until it is ready to answer. The model is now steering a little loop in your program, choosing actions based on what it learns. That feedback loop, model to tool to model, is exactly what grows into the agents of later weeks.

New to agents? How a tool loop becomes one

An agent is a model placed inside a loop where it can take actions and react to their results, working toward a goal over several steps instead of one reply. Today's while loop is the smallest possible version: ask the model, run any tools it wants, feed the results back, repeat until it is done. Add more tools, memory, and planning and you have the agentic systems the course builds later. The important shift is that the model is no longer just answering — it is deciding what to do next.

Common mistakes
  • Schema and function out of step. The name in the schema must match the name your code checks (get_ticket_price), and the property names (destination_city) must match the keys you read with json.loads / JSON.parse. A mismatch means your if never fires, or the argument comes back None/undefined.
  • Forgetting to send the tool result back. You must append both the assistant's request and the tool result, then call the model again. Skip the second call and you return the model's request object instead of an answer; skip the result row and the model has nothing to work with.
  • Dropping the tool_call_id. The result message must carry the same tool_call_id as the request, or the API cannot match the result to the call and rejects the message.
  • Infinite tool loops. With the while version, if your tool always leaves the model wanting more (for example it returns an error every time), the loop never ends. Guard real loops with a maximum number of rounds.
  • Expecting the model to run your code. It cannot. It only asks; your program runs the function. Nothing happens unless your handle_tool_call(s) actually calls it.
Recap
  • A tool is one of your functions plus a plain-English description; OpenAI function calling lets the model ask for it to be run.
  • You describe a tool with a JSON schema (name, description, parameters) and pass it as tools=tools on the chat call.
  • The model never runs code. It replies with finish_reason == "tool_calls", a tool call asking you to run the function with given arguments.
  • Your code runs the real function and appends two rows — the assistant's request and a tool result (linked by tool_call_id) — then calls the model again so it can write the final answer.
  • In the lab, get_ticket_price("London") returns $799 (verified offline in the TypeScript port), and the airline assistant quotes real prices only through the tool.
  • Wrapping this in a while loop lets the model call tools repeatedly — the first small step toward an agent.
