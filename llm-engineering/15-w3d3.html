Week 3 · Day 3 — Tokenizers for Open-Source Models

AutoTokenizer for Llama 3.1, Phi-3, Qwen2 and Starcoder: encoding, decoding, special tokens and chat templates, and why each model tokenizes differently.

Companion to Ed Donner's course · uv setup · Python + TypeScript/React · code verified against the repo

On Day 2 you used Hugging Face pipelines — the easy, high-level way to run open-source models. Today the instructor rolls his sleeves up and drops one level down, to the two objects pipelines are built on: tokenizers and models. This page is all about the first one. A tokenizer translates between text (a string) and tokens (a list of numbers), and — for chat models — it also knows how to format a whole conversation into the exact prompt that model was trained on. This is the "aha" moment where the message lists you used with GPT and Claude in Week 1 finally make sense.

The key idea of the day: every open-source model has its own tokenizer. There is no single universal tokenizer, because the tokenizer is chosen when the model is trained, and you must use the same one at run time or you get garbage. We will look at four: Llama 3.1 (Meta), Phi-3 (Microsoft), Qwen2 (Alibaba Cloud) and Starcoder2 (a code model from ServiceNow, Hugging Face and NVIDIA).

Everything today comes in two languages. Use the Python | TypeScript switch on the code card — or the Code in: switch at the top of the page — to flip between them; your choice is remembered as you read. Python uses the transformers library; TypeScript uses transformers.js, which mirrors the same API in Node or the browser.

Encode and decode: text in, numbers out

A tokenizer is an object with two jobs. Encode goes from a string to a list of token ids. Decode goes back the other way, from ids to a string. That is almost all there is to it. Behind those two methods sits a vocabulary (the full table of text fragments and their id numbers) and, for chat models, a chat template. We will meet all three.

New to AutoTokenizer? What it is and why it matters

AutoTokenizer is a helper class from the transformers library. You do not ask for a specific tokenizer class by name; you call AutoTokenizer.from_pretrained("model/id") and it looks up that model on the Hugging Face hub and builds exactly the right tokenizer subclass for it, downloading the vocabulary and settings the first time. Because every model's tokenizer is different, this one line is how you always get the correct one: name the model, and the matching tokenizer comes back. The TypeScript library @huggingface/transformers offers the same AutoTokenizer.from_pretrained(...) call.

Here is the complete file. It defines four small functions — Llama encode/decode, the Llama chat template, a side-by-side comparison, and the Starcoder2 code tokenizer — and main() runs them in order.

# Reconstructed to match the course's Google Colab notebook for this day.
# Standard HuggingFace code; runs on a GPU (e.g. Colab T4). Not executed here (no GPU).
#
# Week 3 - Day 3: Tokenizers - the lower-level API.
# A tokenizer translates between text (a string) and tokens (a list of ints):
#   encode: text  -> tokens
#   decode: tokens -> text
# It carries a vocab (the fragment<->id mapping) and, for instruct models, a chat
# template that turns a list of {role, content} messages into the exact prompt string
# (with special tokens) that model was trained on. Every model has its own tokenizer;
# using the wrong one gives garbage.
#
# Colab setup (run once in a cell):
#   !pip install -q transformers
#   from huggingface_hub import login
#   from google.colab import userdata
#   login(userdata.get("HF_TOKEN"), add_to_git_credential=True)
# Llama 3.1 is gated: accept Meta's terms on its model page first (approval is quick).

from transformers import AutoTokenizer

# Current model ids on the HuggingFace hub.
LLAMA_MODEL = "meta-llama/Meta-Llama-3.1-8B-Instruct"
PHI3_MODEL = "microsoft/Phi-3-mini-4k-instruct"
QWEN2_MODEL = "Qwen/Qwen2-7B-Instruct"
STARCODER2_MODEL = "bigcode/starcoder2-3b"


def llama_encode_decode():
    # AutoTokenizer.from_pretrained picks the right tokenizer subclass for the model.
    tokenizer = AutoTokenizer.from_pretrained(LLAMA_MODEL, trust_remote_code=True)

    text = "I am excited to show Tokenizers in action to my LLM engineers"
    tokens = tokenizer.encode(text)
    print("Tokens:", tokens)
    print("Num characters:", len(text))
    print("Num tokens:", len(tokens))  # roughly 1 token per ~4 characters of English

    # decode turns tokens back into text; note the leading <|begin_of_text|> special token.
    print("Decoded:", tokenizer.decode(tokens))

    # batch_decode shows one string per token, so you can see where words were split.
    print("Per-token:", tokenizer.batch_decode(tokens))

    # The vocab is the full fragment<->id dictionary; added_vocab holds the special tokens.
    vocab = tokenizer.vocab
    print("Vocab size:", len(vocab))
    print("Special (added) tokens:", tokenizer.get_added_vocab())


def llama_chat_template():
    # The instruct variant knows how to format a chat. apply_chat_template takes the
    # familiar OpenAI-style list of dicts and produces the model's exact prompt.
    tokenizer = AutoTokenizer.from_pretrained(LLAMA_MODEL, trust_remote_code=True)

    messages = [
        {"role": "system", "content": "You are a helpful assistant"},
        {"role": "user", "content": "Tell a light-hearted joke for a room of Data Scientists"},
    ]
    # tokenize=False returns the text prompt so we can read the special-token structure;
    # add_generation_prompt=True tees up the assistant header so the model replies next.
    prompt = tokenizer.apply_chat_template(
        messages, tokenize=False, add_generation_prompt=True
    )
    print("Llama 3.1 chat prompt:\n", prompt)


def compare_tokenizers():
    # The same text tokenizes completely differently across models - different ids,
    # different special tokens, different chat-template structure.
    text = "I am excited to show Tokenizers in action to my LLM engineers"
    messages = [
        {"role": "system", "content": "You are a helpful assistant"},
        {"role": "user", "content": "Tell a light-hearted joke for a room of Data Scientists"},
    ]

    for name, model_id in [
        ("Llama 3.1", LLAMA_MODEL),
        ("Phi-3", PHI3_MODEL),
        ("Qwen2", QWEN2_MODEL),
    ]:
        tokenizer = AutoTokenizer.from_pretrained(model_id, trust_remote_code=True)
        print(f"\n=== {name} ===")
        print("Tokens:", tokenizer.encode(text))
        print(
            "Chat prompt:\n",
            tokenizer.apply_chat_template(
                messages, tokenize=False, add_generation_prompt=True
            ),
        )


def starcoder2_tokenizer():
    # Starcoder2 is built for code, so it tokenizes source more efficiently than an
    # English-focused tokenizer. Print each token next to the text it maps to.
    tokenizer = AutoTokenizer.from_pretrained(STARCODER2_MODEL, trust_remote_code=True)

    code = """
def hello_world(person):
    print("Hello", person)
"""
    tokens = tokenizer.encode(code)
    for token in tokens:
        print(token, "=", tokenizer.decode(token))


def main():
    llama_encode_decode()
    llama_chat_template()
    compare_tokenizers()
    starcoder2_tokenizer()


if __name__ == "__main__":
    main()
// Week 3 - Day 3: Tokenizers, the transformers.js way.
//
// The Python course uses `from transformers import AutoTokenizer`; transformers.js
// mirrors it: `AutoTokenizer.from_pretrained(id)`, then encode (text -> token ids) and
// decode (token ids -> text). Instruct models also carry a chat template, applied with
// tokenizer.apply_chat_template(messages).
//
// We use Xenova/* tokenizer repos (the transformers.js mirrors) so nothing is gated;
// the tokenizers for Llama 3.1, Phi-3, Qwen2 and Starcoder2 are all published there.
//
// Run with: npm run day3
// NOTE: the first run downloads each tokenizer's files from the HuggingFace hub.
import "dotenv/config";
import { pathToFileURL } from "node:url";
import { AutoTokenizer } from "@huggingface/transformers";

// transformers.js tokenizer mirrors of the course's models.
const LLAMA_MODEL = "Xenova/Meta-Llama-3.1-Tokenizer";
const PHI3_MODEL = "Xenova/Phi-3-mini-4k-instruct";
const QWEN2_MODEL = "Xenova/Qwen2-7B-Instruct-tokenizer";
const STARCODER2_MODEL = "Xenova/starcoder2-3b";

export async function encodeDecode() {
  const tokenizer = await AutoTokenizer.from_pretrained(LLAMA_MODEL);

  const text = "I am excited to show Tokenizers in action to my LLM engineers";
  const tokens = tokenizer.encode(text);
  console.log("Tokens:", tokens);
  console.log("Num characters:", text.length);
  console.log("Num tokens:", tokens.length); // ~1 token per 4 chars of English

  // decode turns token ids back into text.
  console.log("Decoded:", tokenizer.decode(tokens));

  // decode one id at a time to see where words were split.
  console.log(
    "Per-token:",
    tokens.map((id) => tokenizer.decode([id])),
  );
}

export async function chatTemplate() {
  // The instruct tokenizer knows how to format a chat into the model's exact prompt.
  const tokenizer = await AutoTokenizer.from_pretrained(LLAMA_MODEL);
  const messages = [
    { role: "system", content: "You are a helpful assistant" },
    { role: "user", content: "Tell a light-hearted joke for a room of Data Scientists" },
  ];
  const prompt = tokenizer.apply_chat_template(messages, {
    tokenize: false,
    add_generation_prompt: true,
  });
  console.log("Llama 3.1 chat prompt:\n", prompt);
}

export async function compareTokenizers() {
  // The same text tokenizes differently for each model.
  const text = "I am excited to show Tokenizers in action to my LLM engineers";
  for (const [name, id] of [
    ["Llama 3.1", LLAMA_MODEL],
    ["Phi-3", PHI3_MODEL],
    ["Qwen2", QWEN2_MODEL],
  ] as const) {
    const tokenizer = await AutoTokenizer.from_pretrained(id);
    console.log(`\n=== ${name} ===`);
    console.log("Tokens:", tokenizer.encode(text));
  }
}

export async function starcoder2Tokenizer() {
  // Starcoder2 is a code-focused tokenizer; it packs source more efficiently.
  const tokenizer = await AutoTokenizer.from_pretrained(STARCODER2_MODEL);
  const code = 'def hello_world(person):\n    print("Hello", person)\n';
  const tokens = tokenizer.encode(code);
  for (const id of tokens) {
    console.log(id, "=", JSON.stringify(tokenizer.decode([id])));
  }
}

async function main(): Promise<void> {
  await encodeDecode();
  await chatTemplate();
  await compareTokenizers();
  await starcoder2Tokenizer();
}

// Only run when invoked directly (so the file is safe to import for its helpers).
if (import.meta.url === pathToFileURL(process.argv[1] ?? "").href) {
  main().catch((err) => {
    console.error(err);
    process.exitCode = 1;
  });
}

Special tokens

When Llama decoded the sentence, a strange piece appeared at the front: <|begin_of_text|>. That whole thing maps to a single id (128000 for Llama 3.1). It is a special token: one token that stands for an instruction to the model rather than a piece of ordinary text, such as "this is the start of a prompt" or "this is where the assistant's turn begins".

New to special tokens? What they are and why they matter

A special token is a reserved entry in the vocabulary that carries meaning the model has learned, not letters to read aloud. There is nothing in the transformer architecture that forces a token to mean "start of text" — it works purely because of training: the model saw that token used that way in enough examples, so it learned what to expect. Llama 3.1 reserves tokens like <|begin_of_text|>, <|start_header_id|>, <|end_header_id|> and <|eot_id|> (end of turn). You can list them in Python with tokenizer.get_added_vocab(). To get the best results, you feed the model prompts that use the same special tokens it was trained on — which is exactly what the chat template does for you.

The chat template: where message lists come from

This is the moment the instructor has been building toward. In Week 1 you wrote conversations as a list of {"role": ..., "content": ...} dictionaries and handed them to GPT or Claude. But a model does not actually read a list of dictionaries — it reads one flat string of tokens. The thing that turns the list into that string is the chat template, and apply_chat_template runs it for you.

New to chat templates? What they do and why they matter

An instruct model (its name usually ends in "-Instruct") has been fine-tuned to expect conversations in one specific layout of special tokens. The chat template is a small formatting rule, shipped with the tokenizer, that knows that layout. apply_chat_template takes your role/content list and produces the exact prompt string, so you never have to hand-write the special tokens. This is why the message-list format from Week 1 works at all: hosted APIs run a chat template for you behind the scenes. With open-source models you can see and run it yourself.

Every model is different — see for yourself

Run the same sentence and the same conversation through several tokenizers and the results are not slightly different, they are completely different: different ids, different special tokens, and a different chat-template layout.

Why does every model have its own tokenizer?

The tokenizer is not a separate, swappable part — it is fixed when the model is trained. The model learns its numbers against one specific vocabulary and one specific set of special tokens. Feed it ids from a different tokenizer and the same numbers mean different fragments, so the input is gibberish to it. Teams also design tokenizers for their goals: Qwen2 covers Chinese as well as English, and Starcoder2 is tuned to tokenize source code efficiently. That is why the rule is simple and strict: use the exact tokenizer that model was trained with.

A tokenizer built for code

The last example runs a short Python snippet through Starcoder2's tokenizer. Because it was trained on code, it has single tokens for things like def and for the four-space indent, so it represents the same source in fewer tokens than an English tokenizer would. The instructor's suggested experiment: take a chunk of complicated code and confirm Starcoder2 tokenizes it more efficiently than a general model.

Common mistakes
  • Using the wrong tokenizer for a model. This is the big one. The ids from one tokenizer mean different fragments to another model, so the output is garbage. Always build the tokenizer from the same model id you will run.
  • Forgetting Llama is gated. meta-llama/Meta-Llama-3.1-8B-Instruct needs you to accept Meta's licence on its model page first and to be signed in with a Hugging Face token (added as the Colab secret HF_TOKEN). Approval is usually quick, but without it from_pretrained fails with a permission error. The public Xenova/* mirrors used by the TypeScript side are not gated.
  • Hand-writing special tokens. You do not need to type <|begin_of_text|> yourself — apply_chat_template inserts the right ones. Writing them by hand for the wrong model reintroduces the first mistake.
  • Expecting the same ids across models. They will not match, and that is correct. Do not "fix" code because Phi-3's numbers differ from Llama's.
  • Dropping add_generation_prompt. Leave it off and the prompt ends after your messages, with no assistant header, so the model has no clear cue that it is its turn to speak.

Recap
  • A tokenizer translates text to tokens (encode) and back (decode); batch_decode shows one piece per token.
  • AutoTokenizer.from_pretrained("model/id") fetches the correct tokenizer for any model; the TypeScript library @huggingface/transformers offers the same call.
  • Special tokens are single ids that signal things like start of text or the start of a role; a model learns their meaning through training.
  • A chat template (via apply_chat_template) turns a role/content message list into the one prompt string a model expects — the reason Week 1's message format works.
  • Every model has its own tokenizer: Llama 3.1, Phi-3, Qwen2 and Starcoder2 give different ids, different special tokens and different chat layouts; using the wrong one gives garbage.
  • Llama 3.1 is gated — accept its licence and sign in with a Hugging Face token first; the public Xenova/* mirrors are not gated.
