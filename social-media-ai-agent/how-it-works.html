How the Agent Team Works

One request from start to finish: the Master Agent, the team, the tools, the approval step and the publisher.

The step pages build Socialix one file at a time. This page puts the pieces together. We follow one real request from the moment the owner presses Send until a post appears on LinkedIn, and name the file and function responsible at every stage. Read it before step 12 to know where you are heading, and again after step 18 to check that everything fits.

Why this matters for your project. An agent team is many small parts: a page, two API routes, a background runner, five agents with their own tools, a database, an MCP server, and another app that publishes. When something goes wrong ("the Master Agent said it scheduled the post, but nothing happened"), you can only find the cause if you know which part does what, and in which order.

The request we follow

This is the request from our verified test run, typed to the Master Agent on the AI Agent page:

Research 2 trending topics about AI tools for small businesses this week, then write one LinkedIn post
and one X post about the best one, and schedule them for tomorrow at good times.

The result: the Research Agent searched the web and saved findings, the Creator Agent wrote a LinkedIn post and an X post, and the Scheduler Agent scheduled them for 2026-10-18 at 14:00 UTC (LinkedIn) and 18:00 UTC (X). Both waited for approval. Nothing was published until the owner pressed Approve.

Stage 1: the page sends the message

The AI Agent page (step 11) is a client component. When the owner presses Send it calls POST /api/agents/master/chat with the campaign id and the text. The route handler (src/app/api/agents/[agent]/chat/route.ts) checks three things: the owner is signed in (otherwise 401), the agent name is one of the five (otherwise 404), and the body has a campaign id and a message of 1 to 4,000 characters (otherwise 400). Then it calls startChat() and answers { ok: true } straight away.

"Straight away" is the important part. A full team run takes minutes. If the route waited for the answer, the browser request could time out, and the owner would stare at a frozen page. So the work continues in the background, and the page asks for news on its own schedule.

Stage 2: the background runner and polling

startChat() in src/lib/ai/runner.ts (step 14) does four things:

  1. It builds a key like campaignId:master and looks in a Set kept on globalThis. If the key is there, this agent is still busy, and it throws "This agent is still working on the last message." The route turns that into HTTP 409.
  2. It saves the owner's message in the agent_messages table and adds the key to the set.
  3. It starts an async function without awaiting it (void (async () => {...})()). That function loads the last 20 messages, runs the agent, and saves the reply (or an error message).
  4. In finally it removes the key, so the agent can take the next message even after an error.

Meanwhile the page polls GET /api/agents/state: every 5 seconds normally, every 1.5 seconds while the chosen agent is thinking. One response carries everything the page shows: each agent's status (running, done, failed, idle), whether the chosen agent is thinking, its messages, and the latest 30 tasks for the task board and the office picture.

New to background work in Next.js? What can go wrong with this approach

Our runner keeps working inside the same Node process that serves the pages. That is simple and fine for one owner on one machine, which is our case. It has limits: if the server stops (a restart, or low memory on the owner's PC), a run in progress is lost, and the "busy" set is empty again. The video uses Inngest, a job service that survives restarts and retries failed steps. Step 14 compares the two.

Stage 3: the agent loop

Every agent, Master or team member, runs in the same function, runAgent() (step 13). It is the classic agent loop built on Claude tool use:

  1. Send Claude the agent's system prompt (its role, the current date and time in UTC, and the campaign brief), the conversation, and the agent's tools.
  2. Save the call's token counts in the usage table.
  3. If Claude stopped with pause_turn, a server-side web search is still going: call again.
  4. If Claude asked for tools (tool_use blocks), run each one, and send the results back as tool_result blocks. A tool that throws becomes a result with is_error: true, so Claude can react instead of the whole run crashing.
  5. Otherwise Claude has answered: return its text.

The loop stops after 16 model calls at most, with "I stopped after too many steps. Please narrow the request." This protects against an agent that keeps calling tools forever, and against the bill that would come with it.

Stage 4: the Master Agent delegates

The Master Agent (claude-sonnet-5-5) has only two tools: assign_task and list_tasks. Its instructions tell it to break the request into tasks in a sensible order (research before writing, writing before scheduling), to do the work through the team, and to finish with a short summary.

When it calls assign_task with an agent, a title and instructions, the tool:

  1. inserts a row in agent_tasks with status running (the task board and the office light up on the next poll);
  2. runs the team member with runAgent(), giving it only the instructions as its first message;
  3. sets the task to done with the team member's answer, or failed with the error;
  4. returns that answer to the Master Agent as the tool result.

A team member never sees the Master's conversation. That is why the tool's description says "Include everything they need in the instructions (they do not see this conversation)", and why the Master passes the research results along when it asks the Creator to write.

Stage 6: approval

When the Scheduler finishes, the Master Agent replies with its summary and the run ends. The two posts sit in the posts table with status awaiting_approval. They appear on the Posts page (with the amber notice "Auto-publish is off"), on the Calendar (step 19) and on the Overview.

The owner reads each post and presses Approve. The button's server action checks the session and calls handOffPost(). Only now does anything leave Socialix. If auto-publish were on, the Scheduler's schedule_post tool would have called handOffPost() itself, without this human check.

Stage 7: MCP and the autopilot

handOffPost() calls the publish_post tool of our MCP server (mcp/social-publisher/server.ts), a separate Node process the app started once and talks to over stdio. The server refuses posts it cannot publish (YouTube, Instagram or TikTok without an image, a network that is not connected). Otherwise it inserts three rows in the autopilot's database, in one transaction, and returns a contentId. Socialix stores that id and marks the post queued.

Stage 8: the worker publishes

The autopilot's worker (npm run worker in the autopilot project) picks up jobs whose nextRunAt has passed, publishes them with the account's token (refreshing it when needed), retries up to three times, and writes an audit log. Socialix finds out on the next status sync: the "Refresh statuses" button, the Analytics page, or the Analytics Agent's post_overview tool all call get_post_status, and a PUBLISHED post becomes published with a link to the live post.

Common misconceptions.
  • "The Master Agent publishes posts." It cannot: its only tools are assign_task and list_tasks. The Scheduler only schedules. Publishing needs Approve and the autopilot's worker.
  • "Team members remember earlier chats." Each task starts a new conversation with only the Master's instructions. Shared knowledge lives in the database (research, drafts).
  • "Scheduled" means "will be published". In Socialix, scheduled means "has a time and waits for approval". Queued means "handed to the autopilot".
  • "Socialix holds the social tokens." It never sees them; they stay in the autopilot's database.
  • "If the page is closed, the work stops." The runner works on the server; closing the tab only stops the polling. Stopping the server does stop the run.
Recap
  • The page posts the message; the route starts the runner and answers at once; the page polls for the reply.
  • One loop, runAgent(), runs every agent: call Claude, run tools, repeat (at most 16 calls).
  • The Master delegates with assign_task; each team member works from instructions alone and writes its results to the database.
  • The Scheduler leaves posts in awaiting_approval; Approve hands them to our MCP server, which queues them in the autopilot; the worker publishes them at their time.
