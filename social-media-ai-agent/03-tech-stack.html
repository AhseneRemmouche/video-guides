Tech Stack

The video's stack (OpenAI, Blotato, InsForge, Inngest, E2B) next to ours (Claude, your autopilot, Postgres).

▶ Watch this part (00:07:11)

A "tech stack" is the list of tools and services an app is built from. In this chapter (07:11 to 10:25) the presenter names the main pieces of the video's stack. This page lists every piece the video uses across the course, puts our choice next to it, and explains why we swapped it. At the end you will read our package.json, the file that names every library our app installs.

What the video says

  • Building blocks (at 07:06). React and Next.js for the app, and Claude Code to write the code.
  • Blotato (at 07:06 to 07:54). An all-in-one social media automation service. The plan: connect your social accounts to Blotato; the agents generate captions, hashtags and images; Blotato's API publishes now or at a chosen date and time, and the app's calendar shows the scheduled posts.
  • CodeRabbit (at 07:54). CodeRabbit reviews the code with AI, catching bugs and security problems (covered in step 05).
  • ImageKit (at 08:16). ImageKit generates AI images, edits them from a text prompt, removes backgrounds and optimises them for fast delivery.
  • The rest of the chapter (08:40 to 10:16) promotes the channel's membership, where the source code is sold, and a sponsor.

Other services appear in other chapters: InsForge for login and the hosted database and Inngest for background jobs (both chosen during setup, at 11:50 and 12:15), the OpenAI Agents SDK for the agents (free daily OpenAI tokens are promised at 01:12), and an E2B cloud desktop for each agent (at 03:36).

Why each swap

Claude instead of OpenAI

The course title already says "Claude Code", and the owner of this guide has an Anthropic account. Our agents call Claude through the official Anthropic API. Claude's tool use does everything the OpenAI Agents SDK does for this app: we describe each tool with a JSON schema, Claude asks for a tool, our code runs it, and we send back the result (step 12). The bigger model (claude-sonnet-5-5) plans and writes; the smaller (claude-haiku-5-5) schedules and reports, which keeps costs down, the same idea as the video's "use Haiku for small tasks" (step 04).

The owner's autopilot instead of Blotato

The owner already runs a WordPress Social Autopilot: a separate app with its own database of connected social accounts, a publishing queue and a worker that publishes at the right time, refreshes access tokens, retries and keeps an audit log. Paying for Blotato would duplicate all that. So our app hands approved posts to the autopilot through a small MCP server we wrote (mcp/social-publisher/server.ts, step 18). Bonus: Socialix never sees a social media token.

New to MCP? What the Model Context Protocol is

MCP is a standard way for an app to offer tools to another program. An MCP server lists its tools (name, description, input schema) and runs them on request. The video uses Blotato's ready-made MCP server. We wrote our own with five tools: list_connections, publish_post, get_post_status, cancel_post and list_recent_posts. Our app starts it as a child process and talks to it over stdio (standard input and output), so no network port is needed.

Local Postgres instead of InsForge

InsForge gives the video a hosted database plus user sign-up. Our app has a single user, the owner, so a full sign-up system is not needed: one email and password in our settings file, and a signed session cookie (step 06). For data we use the Postgres server the autopilot already runs in Docker (container wsa-pg), with our own separate database on it. We still use Drizzle like the video.

An in-process runner instead of Inngest

A background job is work that continues after the web request that started it has answered. The video uses Inngest, a hosted job queue. Our agents run inside our own server: when you send a message, the server stores it, starts the agent without waiting, and answers at once. The page then asks the server for news every few seconds (polling). One app on one computer does not need a separate queue service. The trade-off: if you stop the server mid-task, that task stops too (step 14).

Web search instead of E2B

The video gives each agent a full remote desktop so it can open a browser and look things up. What our Research agent actually needs is search results, and Claude can search the web itself: we enable Anthropic's server tool web_search_20250305, limited to 5 searches per call. Anthropic runs the searches; no sandbox to pay for or watch (step 15).

No ImageKit, no CodeRabbit

Our app does not generate images; a post can carry the address of an image you host yourself (step 17). Instead of CodeRabbit we check the code with the TypeScript compiler, a production build and a browser test that clicks through the app (step 05).

Our package.json

Every Node.js project has a package.json at its root. It names the project, defines short commands ("scripts") and lists the libraries to install with their exact versions.

New to package.json? Dependencies, devDependencies and scripts

dependencies are libraries the app needs while running. devDependencies are only needed while developing or building (type definitions, the TypeScript compiler, the Tailwind compiler). scripts are named commands: pnpm dev runs whatever is written next to "dev". We use pnpm; the video uses npm. Both read the same file.

Our versions are written exactly ("16.4.2", not "^16.4.2"), so a fresh install gets the same versions the guide was tested with.

Video vs our app. The video's boilerplate installs a long list of packages (shadcn/ui components, Inngest, the OpenAI SDK, and more). Ours has ten runtime dependencies. There is no openai, inngest, e2b, imagekit or Blotato package, and no drizzle-kit: our tables are created by pnpm db:setup (step 06).
What you should see: after pnpm install (step 04), a node_modules folder and a pnpm-lock.yaml file appear, and pnpm list --depth 0 shows the versions above.
Common mistakes
  • Running npm install in a pnpm project. It ignores pnpm-lock.yaml and the onlyBuiltDependencies setting. Stay with pnpm.
  • Upgrading one of react/react-dom without the other. They must have the same version.
  • Adding the openai package to follow the video's agent code. Our agents use the Anthropic SDK only.
  • Using port 3000 for Socialix while the autopilot's dashboard is running. You get EADDRINUSE.
Recap
  • The video's stack: Next.js boilerplate, OpenAI Agents SDK, InsForge, Inngest, E2B, ImageKit, Blotato, CodeRabbit.
  • Ours: Next.js 16 by hand, Claude through the Anthropic SDK, local Postgres with Drizzle, an in-process runner, Claude's web search, and the owner's autopilot through our own MCP server.
  • Swaps reduce outside accounts from six to one (Anthropic) and keep social tokens out of our app.
  • package.json pins exact versions, defines our scripts, and runs the dev server on port 3100.
