Background Job Scheduler

Running agents in the background so the page stays responsive (Inngest in the video, an in-process runner here).

▶ Watch this part (01:26:04)

An AI agent can take a long time to answer. The Master Agent may call the Research Agent, which searches the web, then the Creator Agent, then the Scheduler Agent. That can take a minute or more. If the browser had to wait for all of that inside one web request, the page would freeze, and the request could time out. This step is about running that work in the background, so the page stays responsive and shows progress while the team works.

The video solves this with a hosted job service called Inngest and a check that runs every 15 minutes. Our app, Socialix, solves the "don't block the page" part with a small in-process background runner, and leaves the "publish at 14:00 tomorrow" part to the WordPress Social Autopilot's worker. This page explains both, and is honest about what our simpler approach cannot do.

What the video builds

At 01:26:11 the presenter introduces a background job: work that keeps running "even though you are not online or not using your PC". He shows a diagram called "Background Jobs Runner" (at 01:26:20) with eight boxes. The flow is:

  1. The user gives the Master Agent a task with a schedule, for example "Find trending AI tools every day at 8 AM and create a post for me".
  2. The Master Agent breaks it into sub-tasks, picks the right agent and saves the schedule (the time and the next run) in the database.
  3. A cron job runs every 15 minutes. It looks for tasks whose next run falls in the next 15 minutes and adds them to the Inngest queue.
  4. Inngest runs the agent workflow, handles retries and failures, and updates the task status.
  5. The agents save their results, and the user is notified.

New to background jobs? What they are and why they matter

A normal web request is short: the browser asks, the server answers, done. Many hosts stop a request after some seconds. Work that takes longer, or that must happen later (tomorrow at 8 AM), cannot live inside one request.

A background job is work the server does outside the request. The request only says "please do this" and returns at once. The job runs separately. Job systems like Inngest add useful extras: they keep the job in a queue that survives a restart, retry it when it fails, run it on a schedule, and show you each run in a dashboard.

New to cron? What "every 15 minutes" means

Cron is an old Unix tool for running something on a timetable. A cron expression has five fields: minute, hour, day of month, month, day of week. */15 * * * * means "every minute that is divisible by 15, every hour, every day": 00, 15, 30 and 45 past each hour. The video's cron does not run the agents itself; it only finds tasks that are due soon and hands them to Inngest.

What our app does instead

Socialix has no Inngest, no cron and no repeating tasks. It needs two smaller things:

  • Keep the page responsive while agents think. We start the agent run in the background inside the same Node.js server process, return from the request at once, and let the browser poll for progress.
  • Publish at the right time. We don't run a clock at all. When the owner approves a post, it is handed to the WordPress Social Autopilot's publish queue with its time, and the autopilot's worker publishes it when that time comes (step 18).

The chat route

This is the endpoint the AI Agent page calls when you press send. It is a Next.js route handler: a file named route.ts that exports a function per HTTP method.

import { NextResponse } from "next/server";
import { z } from "zod";
import { getSession } from "@/lib/auth";
import { AGENTS } from "@/lib/db/schema";
import { startChat } from "@/lib/ai/runner";

const Body = z.object({ campaignId: z.string().min(1), message: z.string().min(1).max(4000) });

/** POST a message to an agent. The reply is produced in the background; poll the messages route. */
export async function POST(req: Request, { params }: { params: Promise<{ agent: string }> }) {
  if (!(await getSession())) return NextResponse.json({ error: "Not signed in" }, { status: 401 });
  const { agent } = await params;
  if (!AGENTS.includes(agent as (typeof AGENTS)[number])) return NextResponse.json({ error: "Unknown agent" }, { status: 404 });
  const parsed = Body.safeParse(await req.json().catch(() => null));
  if (!parsed.success) return NextResponse.json({ error: "campaignId and message are required" }, { status: 400 });
  try {
    await startChat(parsed.data.campaignId, agent as (typeof AGENTS)[number], parsed.data.message.trim());
    return NextResponse.json({ ok: true });
  } catch (e) {
    return NextResponse.json({ error: e instanceof Error ? e.message : "Could not start" }, { status: 409 });
  }
}

The background runner

The runner lives in src/lib/ai/runner.ts. The top half is the agent loop from step 13 (runAgent). The bottom half, from line 85, is what this step is about.

import Anthropic from "@anthropic-ai/sdk";
import { asc, eq, and } from "drizzle-orm";
import { db, schema } from "@/lib/db";
import type { AgentRole } from "@/lib/db/schema";
import { config } from "@/lib/env";
import { TEAM, systemPrompt } from "./agents";
import { TOOLS, type ToolContext } from "./tools";

/**
 * The agent loop: send the conversation and the agent's tools to Claude, run any tools it asks for, send the
 * results back, and repeat until it answers. Web search is a server tool: Anthropic runs it, and a long
 * search may end a turn with "pause_turn", in which case we simply continue.
 */

const g = globalThis as unknown as { __anthropic?: Anthropic };
function anthropic(): Anthropic {
  g.__anthropic ??= new Anthropic({ apiKey: config.anthropicApiKey });
  return g.__anthropic;
}

const MAX_STEPS = 16;

async function recordUsage(agent: AgentRole, model: string, msg: Anthropic.Message) {
  const searches = msg.content.filter((b) => b.type === "server_tool_use" && b.name === "web_search").length;
  await db.insert(schema.usage).values({ agent, model, inputTokens: msg.usage.input_tokens, outputTokens: msg.usage.output_tokens, webSearches: searches });
}

async function campaignBrief(campaignId: string) {
  const c = await db.query.campaigns.findFirst({ where: eq(schema.campaigns.id, campaignId) });
  if (!c) throw new Error("Campaign not found");
  return c;
}

/** Run one agent on a list of messages and return its final text answer. */
export async function runAgent(role: AgentRole, campaignId: string, messages: Anthropic.MessageParam[]): Promise<string> {
  const info = TEAM[role];
  const model = info.model();
  const tools = TOOLS[role];
  const system = systemPrompt(role, await campaignBrief(campaignId));
  const ctx: ToolContext = {
    campaignId,
    runSubAgent: (agent, instructions) => runAgent(agent, campaignId, [{ role: "user", content: instructions }]),
  };

  const convo = [...messages];
  for (let step = 0; step < MAX_STEPS; step++) {
    const msg = await anthropic().messages.create({
      model,
      max_tokens: 4096,
      system,
      tools: tools.map((t) => t.definition),
      messages: convo,
    });
    await recordUsage(role, model, msg);
    convo.push({ role: "assistant", content: msg.content });

    if (msg.stop_reason === "pause_turn") continue; // a server tool (web search) is still working
    const calls = msg.content.filter((b): b is Anthropic.ToolUseBlock => b.type === "tool_use");
    if (msg.stop_reason !== "tool_use" || calls.length === 0) {
      return msg.content
        .filter((b): b is Anthropic.TextBlock => b.type === "text")
        .map((b) => b.text)
        .join("\n")
        .trim();
    }

    const results: Anthropic.ToolResultBlockParam[] = [];
    for (const call of calls) {
      const t = tools.find((x) => "name" in x.definition && x.definition.name === call.name);
      let content: string;
      let isError = false;
      try {
        content = t?.run ? await t.run(call.input, ctx) : `Unknown tool ${call.name}`;
      } catch (e) {
        content = `Tool failed: ${e instanceof Error ? e.message : "unknown error"}`;
        isError = true;
      }
      results.push({ type: "tool_result", tool_use_id: call.id, content, is_error: isError });
    }
    convo.push({ role: "user", content: results });
  }
  return "I stopped after too many steps. Please narrow the request.";
}

// ---------- Chat threads (what the dashboard calls) ----------

// "campaignId:agent" while a reply is being produced (kept on globalThis so hot reloads don't lose it)
const gr = globalThis as unknown as { __running?: Set<string> };
const running = (gr.__running ??= new Set<string>());

export function isRunning(campaignId: string, agent: AgentRole): boolean {
  return running.has(`${campaignId}:${agent}`);
}

/**
 * Save the owner's message and produce the agent's reply in the background. The dashboard polls the
 * messages and tasks while it works, like the video's live office.
 */
export async function startChat(campaignId: string, agent: AgentRole, text: string): Promise<void> {
  const key = `${campaignId}:${agent}`;
  if (running.has(key)) throw new Error("This agent is still working on the last message.");
  await db.insert(schema.agentMessages).values({ campaignId, agent, role: "user", content: text });
  running.add(key);

  void (async () => {
    try {
      const history = await db.query.agentMessages.findMany({
        where: and(eq(schema.agentMessages.campaignId, campaignId), eq(schema.agentMessages.agent, agent)),
        orderBy: asc(schema.agentMessages.createdAt),
      });
      const messages: Anthropic.MessageParam[] = history.slice(-20).map((m) => ({ role: m.role, content: m.content }));
      while (messages.length && messages[0]!.role !== "user") messages.shift();
      const reply = await runAgent(agent, campaignId, messages);
      await db.insert(schema.agentMessages).values({ campaignId, agent, role: "assistant", content: reply || "(no reply)" });
    } catch (e) {
      const message = e instanceof Anthropic.APIError ? `Claude API error ${e.status}: ${e.message}` : e instanceof Error ? e.message : "unknown error";
      await db.insert(schema.agentMessages).values({ campaignId, agent, role: "assistant", content: `Sorry, something went wrong: ${message}` });
    } finally {
      running.delete(key);
    }
  })();
}

New to "fire and forget" Promises? Why void (async () => ...)() works

An async function returns a Promise the moment you call it, and its body keeps running whenever it is not waiting. If you await the Promise, your code pauses until it finishes. If you don't, your code continues immediately and the work carries on in the same process.

That is all our "background job" is: a Promise nobody waits for. It works because a Next.js server started with pnpm start or pnpm dev is a long-running Node.js process that keeps running after the response is sent. On a serverless host (where each request gets a short-lived function) the work could be stopped as soon as the response goes out, which is one reason the video uses Inngest.

The polling side

The browser learns about progress by asking again and again. Step 11 explains the AI Agent page in full; the two pieces that matter here are:

  • src/app/dashboard/ai-agent/workspace.tsx line 46: setInterval(load, busy ? 1500 : 5000). It polls every 5 seconds normally, and every 1.5 seconds while an agent is busy, so replies show up quickly.
  • src/app/api/agents/state/route.ts lines 30 and 37 call isRunning(). Line 37 gives the chat its thinking flag; line 30 marks an agent "running" if it is producing a reply or has a task row with status running (sub-agents started by the Master Agent's assign_task).

What our approach cannot do (and Inngest can)

Our runner is a few lines of code and needs no extra service, which is why we chose it for a single-owner app. But it is not a job system. Be clear about the gaps:

  • No survival across restarts. The work lives only in the memory of the running Node.js process. If the server stops in the middle (you press Ctrl+C, Windows restarts, or the owner's PC runs low on memory), the reply is never written.
  • No automatic retries. If Claude's API fails, we save "Sorry, something went wrong: ..." and stop. You send the message again yourself.
  • No schedules or repeating tasks. You can't tell Socialix "every day at 8 AM". Agents only work when you send a message.

The time-based part that matters most, publishing a post at its scheduled time, is not done by our app at all. When you approve a post, Socialix inserts a PublishJob into the autopilot's database with nextRunAt set to the scheduled time in UTC. The autopilot's worker (npm run worker) picks it up at that time and publishes it, with its own token refresh, retries and audit log. So our app can be closed while posts still go out on time, as long as the autopilot's worker is running. Step 18 shows this hand-off.

Video vs our app. The video moves all agent work out of the web request into Inngest, with a 15-minute cron, repeating tasks, retries and concurrency limits, and needs the Inngest dev server running (npm run inngest:dev) or "nothing executes". Socialix runs agent work as a background Promise inside its own server (startChat in src/lib/ai/runner.ts), refuses a second message to a busy agent, and lets the page poll for progress. It has no scheduled or repeating agent tasks; scheduled publishing is done by the autopilot's worker. If you later need "every day at 8 AM" or runs that survive restarts, a job service like Inngest is the right tool.
What you should see
  • After you press send on the AI Agent page, your message appears straight away and the agent shows as thinking. The page stays usable: you can switch agents or tabs.
  • In the browser's developer tools (Network tab), the POST /api/agents/master/chat request finishes almost at once with {"ok":true}, followed by repeated GET /api/agents/state requests.
  • In our browser test, the Analytics Agent answered in about 4 seconds and the Creator saved an X draft in about 8 seconds. A full Master run with research, writing and scheduling takes longer.
  • If you send a second message to the same busy agent, a red note says "This agent is still working on the last message."
Common mistakes
  • Restarting the server mid-run. The work is lost. Also, a sub-task created by assign_task is stored with status running and is only set to done or failed when the run finishes, so after a crash it can stay "running" on the task board, and the state route keeps that agent marked as working. Send the request again; the old row is just a leftover.
  • EADDRINUSE :3100 when you start the app: a server is already running on that port. Use the one that's running, or stop it first.
  • Expecting agents to work while the app is closed. They don't. Only the autopilot's worker acts on its own, and only for posts already handed to it.
  • Deploying to a serverless host. The in-process runner assumes one long-running Node.js server. On serverless platforms the background Promise may be stopped when the response is sent.
Recap
  • The video uses Inngest: a 15-minute cron finds due tasks and Inngest runs them with retries, concurrency limits, repeating schedules and a run dashboard at localhost:8288.
  • Socialix's chat route calls startChat(), which saves your message, marks the agent busy in a Set on globalThis, starts runAgent() without awaiting it, and returns at once.
  • A second message to a busy agent is refused with 409; finally always frees the agent.
  • The page polls /api/agents/state every 5 s (1.5 s while busy); isRunning() feeds its thinking flag.
  • Our runner does not survive restarts, retry or run schedules. Timed publishing is done by the autopilot's worker from its PublishJob queue.
