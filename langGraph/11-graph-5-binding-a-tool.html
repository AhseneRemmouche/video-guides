Graph 5: Binding a Tool

@tool and bind_tools: the model asks for a tool, but nothing runs it yet.

▶ Watch this part (01:35:46)

Goal

"What makes the graphs and the agents really powerful? It's the tools" (95:46). In this step you write your first tool, a multiply function, and attach it to the model with bind_tools. Then you watch what the model does with it: for "hi" it just chats, and for "what is 2 * 10?" it replies with a request to run multiply with 2 and 10.

The important surprise: nothing runs the tool. The graph ends right after the model, so you get the model's request but never the answer 20. That gap is on purpose: the presenter stops here "so I can separate and you can understand better" (101:28), and step 12 closes it.

New to tools? How a model "uses" a function it can't run

The model runs on OpenAI's servers; your multiply function runs on your computer. The model can never execute your code. What happens instead:

  1. When you call the model, LangChain also sends a description of each bound tool: its name, what it does, and which inputs it takes.
  2. If the model decides a tool would help, it doesn't answer in words. It replies with a structured request, a tool call: "please run multiply with nb1=2, nb2=10".
  3. Your program must then run the function and send the result back to the model as a tool message, so the model can write the final answer.

This step covers points 1 and 2. Point 3 is the next step.

What the presenter explains

  • A tool is a decorated function (97:25): "an annotation that when put on a function it becomes a tool that … can be used by our model and by our agent." The annotation is @tool, the same one from the LangChain course.
  • Type hints and a docstring (98:16–98:44): multiply(nb1: int, nb2: int) -> int with the docstring "This tool is used for multiplying 2 numbers and returning the product".
  • Binding (98:44–99:31): model_llm.bind_tools([multiply]) creates "a new object with the model but this time the model binded … to the tools". You pass a list because a model can have many tools.
  • Binding offers, it doesn't force (102:19): "we are not forcing the LLM to use the tool, but we are giving the LLM the choice of using the tool if the LLM think this is the right thing to do."
  • A tool call isn't an answer (103:05–104:20): with a multiplication question, "we have a tool call right now … the name is multiply and I have the arguments, but I don't have the answer … the AI has chosen to use the tool."

The complete file

From the official repo. The video shows the same code (frame at 100:00).

from langgraph.graph import StateGraph, START, END, MessagesState
from langchain_openai import ChatOpenAI
from dotenv import load_dotenv
from langchain.tools import tool

load_dotenv()

model_llm = ChatOpenAI(model="gpt-4o")

@tool
def multiply(nb1: int, nb2: int) -> int:
    """This tool is used for multiplying 2 numbers and returning the product"""
    return nb1*nb2

model_llm_with_tool = model_llm.bind_tools([multiply])

# nodes
def chat_with_tool(state: MessagesState) -> MessagesState:
    return {"messages": [model_llm_with_tool.invoke(state["messages"])]}

builder = StateGraph(MessagesState)

builder.add_node("chat_with_tool", chat_with_tool)

builder.add_edge(START, "chat_with_tool")
builder.add_edge("chat_with_tool",END)

graph = builder.compile()

What @tool builds from your function

You can inspect the tool object directly. This runs instantly and costs nothing, because no model is involved. Verified in the locked environment:

from langchain.tools import tool

@tool
def multiply(nb1: int, nb2: int) -> int:
    """This tool is used for multiplying 2 numbers and returning the product"""
    return nb1*nb2

print(multiply.name)
print(multiply.description)
print(multiply.args)
print(multiply.invoke({"nb1": 2, "nb2": 10}))
print(type(multiply).__name__)

Note that a tool is invoked with a dictionary of its arguments, not with multiply(2, 10). That is exactly the shape the model will produce in its tool call.

This is JSON Schema: a standard way to describe data. bind_tools attaches it to every request the bound model sends.

New to decorators? What the @ line does

A line like @tool right above a def is a decorator. It's shorthand for "define the function, then pass it through tool and keep the result under the same name":

def multiply(nb1: int, nb2: int) -> int:
    """..."""
    return nb1*nb2
multiply = tool(multiply)   # what @tool does for you

That's why multiply afterwards has .name, .description, .args and .invoke: it's no longer a plain function.

Run it: "hi" vs "what is 2 * 10 ?"

Both runs below used a fake model standing in for gpt-4o. When tools are bound and the question contains two numbers, it asks for the tool, just as gpt-4o did in the video. Otherwise it replies with fixed text. Input is one human message each time.

RESULT messages: [('HumanMessage', 'hi'), ('AIMessage', 'Hi! How can I help you today?')]
RESULT messages: [('HumanMessage', 'what is 2 * 10 ?'), ('AIMessage', '')]

The second AIMessage has empty content: no words at all. The interesting part is in its tool_calls field. Printing every message of the result (same run, input "multiply 2 by 10"):

The last line is the answer to "is there any ToolMessage in the result?": False. The result is exactly two messages. Nothing ever ran multiply, so the number 20 appears nowhere.

What you see in Studio

In the video the presenter sends a greeting first, and the model just chats back. Then, on the same thread, "what is 2 * 10 ?" (frame at 103:50). Studio shows the AI message as a small table: the tool name multiply, an ID button, and the arguments nb1 2 and nb2 10. No sentence and no 20.

What you should see.
  • A greeting gets a normal text reply, and the run has two messages: yours and the AI's.
  • A multiplication question gets an AI message with a multiply tool call (nb1, nb2) and usually no text.
  • No tool message and no "20" anywhere. That's correct for this graph.
  • Studio keeps the earlier turn in the same thread (Turn 1, Turn 2), because the langgraph dev server saves each thread's state for you. A fresh thread (the + next to the thread ID) starts from an empty list. Plain graph.invoke in Python remembers nothing; that's what step 14 adds.
Common mistakes
  • Calling model_llm instead of model_llm_with_tool in the node: the model never hears about multiply and tries to do the maths itself.
  • Passing the tool without a list: bind_tools(multiply). Write bind_tools([multiply]).
  • Forgetting @tool: you'd be binding a plain function. Keep the decorator so name, description and args come from one obvious place.
  • No docstring: @tool refuses a function without a description. A vague one makes the model unsure when to use the tool.
  • Missing type hints: the model can't tell what kind of arguments to send.
  • Expecting the answer 20: this graph ends after the model. The tool call is the result here.
  • Calling the tool like a function (multiply(2, 10)) in a test: tools take a dictionary, multiply.invoke({"nb1": 2, "nb2": 10}).

Recap
  • @tool turns a function into a tool. The function name becomes the tool's name, the docstring its description and the type hints its argument schema. Check them with multiply.name, .description and .args.
  • model_llm.bind_tools([multiply]) returns a new model that sends the tool's JSON description with every request. The original model is unchanged.
  • Binding offers a tool and never forces it: "hi" gets text, "what is 2 * 10 ?" gets an AIMessage whose tool_calls holds name, args, id and type.
  • A tool call is a request, not a result. In graph 5 the run ends with Human + AI(tool_calls) and no ToolMessage, because no node runs the tool (verified).
  • Next: run the requested tool and send the result back (step 12).
