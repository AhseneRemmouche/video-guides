Memory That Survives a Restart

SqliteSaver, a chat loop, and why langgraph dev refuses your own checkpointer.

Extension · verified against LangGraph 1.2.11

Extension: not in the video. This step completes README exercise 7, "Replace MemorySaver with a persistent checkpointer". module1/11_graph_sqlite_memory.py was run against LangGraph 1.2.11 and langgraph-checkpoint-sqlite 3.1.1 with the offline fake model from step 15, in two separate Python processes one after the other: the first saved 4 messages, the second, started fresh, continued the same conversation to 8.

What that proves: the conversation really is stored on disk and reloaded by a new program. What it doesn't: what a real model answers. With your key the answers will be real, but the saving and loading work the same way.

Goal

At the end of the course the presenter makes a point worth repeating: in Studio the conversation is remembered, "however, if we are actually doing everything in the terminal, we will realize after every run, we are not actually keeping the memory" (132:02–132:28). Graph 9 fixes that with MemorySaver, but only while the program runs. MemorySaver keeps everything in the computer's RAM, and RAM is wiped when Python exits.

In this step you build a small chat program whose memory is a file on disk. Ask a question, quit, start the program again tomorrow with the same thread name, and the math teacher still knows what you talked about.

New to SQLite? A database in a single file

A database stores data in tables (rows and columns) and lets programs read and write it safely. Most databases (PostgreSQL, MySQL) run as a separate server you have to install. SQLite is different: the whole database is one ordinary file, and the code to read it ships with Python as the sqlite3 module. Nothing to install, nothing to start.

That makes it perfect for learning and for small local apps. For a web app with many users writing at the same time, you would switch to PostgreSQL (LangGraph has a langgraph-checkpoint-postgres package for that), but the graph code stays the same.

Install the SQLite checkpointer

  1. Add the package 
    uv add langgraph-checkpoint-sqlite

    uv add puts "langgraph-checkpoint-sqlite>=3.1.1" into pyproject.toml (line 13 of the file in step 15), updates uv.lock and installs it. It's the official package from the LangGraph team (MIT licence, source in the langchain-ai/langgraph repository under libs/checkpoint-sqlite). It isn't part of langgraph itself so that people who don't need SQLite don't have to install it.

  2. Create module1/11_graph_sqlite_memory.py

    New file in the module1 folder, with the code below. It doesn't copy the agent: it reuses the graph from 8_graph_agent.py (as fixed in step 15).

  3. Ignore the database file (recommended)

    The program creates checkpoints.sqlite holding your whole chat history. Add a line checkpoints.sqlite to .gitignore so it never ends up on GitHub.

import sqlite3
import sys

from langgraph.checkpoint.sqlite import SqliteSaver
from langchain.messages import HumanMessage

# reuse the agent we already built in 8_graph_agent.py (file names start with a digit,
# so we load the module by path instead of a normal import)
import importlib.util
from pathlib import Path

spec = importlib.util.spec_from_file_location("agent8", Path(__file__).with_name("8_graph_agent.py"))
agent8 = importlib.util.module_from_spec(spec)
spec.loader.exec_module(agent8)

# a real file on disk: the conversation survives when the program stops
connection = sqlite3.connect("checkpoints.sqlite", check_same_thread=False)
memory = SqliteSaver(connection)
graph = agent8.builder.compile(checkpointer=memory)

thread_id = sys.argv[1] if len(sys.argv) > 1 else "student-1"
config = {"configurable": {"thread_id": thread_id}}

print(f"Thread '{thread_id}'. Type a question, or q to quit.")
while True:
    question = input("You: ").strip()
    if question.lower() in {"q", "quit", "exit"}:
        break
    if not question:
        continue
    result = graph.invoke({"messages": [HumanMessage(content=question)]}, config)
    print("Teacher:", result["messages"][-1].content)

saved = graph.get_state(config).values.get("messages", [])
print(f"{len(saved)} messages saved for thread '{thread_id}' in checkpoints.sqlite")
connection.close()

New to module names? Why import 8_graph_agent is a SyntaxError

An import statement takes a Python identifier: letters, digits and underscores, and it can't start with a digit (the same rule as variable names). Python reads 8_graph_agent as a number that went wrong. Verified:

    import 8_graph_agent
            ^
SyntaxError: invalid decimal literal

from module1 import 8_graph_agent fails the same way. The course numbers its files so they sort in order, which is great for learning but means you need another way to load them:

  • importlib.import_module("module1.8_graph_agent") takes the name as a string, so the digit is fine. That's what the README's python -c commands use. But it only works when Python can find the module1 folder, i.e. when you run from the project root (from inside module1 we got ModuleNotFoundError: No module named 'module1').
  • importlib.util.spec_from_file_location(...) (lines 12–14) loads by file path, built from __file__, so it works from any folder. That's why this file uses it.

In your own projects, just give modules normal names like agent.py, and from agent import builder works.

New to threads? What check_same_thread=False means

Here "thread" means an operating-system thread: a separate line of execution inside one program. That's a different idea from a LangGraph conversation thread (the thread_id); the same word, two meanings.

By default Python's sqlite3 refuses to let a connection be used by any thread other than the one that created it, and raises an error if that happens. LangGraph runs graph steps in background worker threads, so the checkpointer does use the connection from another thread (verified: without the flag the first question fails with ProgrammingError). check_same_thread=False turns that safety check off. It's safe here because SqliteSaver guards the connection with its own lock; the package's own documentation uses exactly this line.

There's also a shorter form that opens and closes the connection for you:

with SqliteSaver.from_conn_string("checkpoints.sqlite") as memory:
    graph = agent8.builder.compile(checkpointer=memory)
    ...  # use the graph inside the with block

Run it twice

From the project root (with the virtual environment active, or put uv run in front):

python module1/11_graph_sqlite_memory.py student-1

Ask one question, then type q. Then run the same command again, a brand-new Python process, and ask a follow-up.

What you should see. Our two offline runs (fake model; the lines after You: are what we typed):

Thread 'student-1'. Type a question, or q to quit.
You: What is 12 multiplied by 7?
Teacher: (fake model) The answer is 84.
You: q
4 messages saved for thread 'student-1' in checkpoints.sqlite
Thread 'student-1'. Type a question, or q to quit.
You: Add 3 and 4
Teacher: (fake model) The answer is 7.
You: q
8 messages saved for thread 'student-1' in checkpoints.sqlite

Run 2 started with nothing in memory, yet ended with 8 messages: the 4 from run 1 were loaded from the file. A different thread is a separate conversation: python module1/11_graph_sqlite_memory.py student-2 with one question ended with 2 messages saved for thread 'student-2'. With a real key, try "My name is Sam" in run 1 and "What is my name?" in run 2.

What's inside the file

You don't need to open the database, but it helps to know what's there. We looked after the runs above: SqliteSaver created two tables, checkpoints and writes. The checkpoints table had 10 rows for student-1 and 3 for student-2. LangGraph saves a checkpoint after every step of the graph (input, model, tools, model…), not once per question. That's what makes "time travel" possible: graph.get_state_history(config) lists all of them, newest first. The handbook chapter Persistence, Memory & Time Travel goes further.

Why this isn't registered in langgraph dev

Two reasons, one technical and one practical:

  1. The server refuses a custom checkpointer. This is the same rule you met in step 15, fix 7: registering graph 9 made langgraph dev stop with "Heads up! Your graph ... includes a custom checkpointer ... With LangGraph API, persistence is handled automatically by the platform". A graph compiled with SqliteSaver is in the same situation.
  2. This file is a program, not just a graph. Importing it starts the chat loop and waits for input(), which a server can't answer.

And it isn't needed: in Studio the server already saves each thread (locally under .langgraph_api, which is why that folder is in .gitignore). So the rule of thumb is: plain Python, you choose the checkpointer; LangGraph server, it chooses for you.

Common mistakes

  • ModuleNotFoundError: No module named 'langgraph.checkpoint.sqlite': the package isn't installed. Run uv add langgraph-checkpoint-sqlite (the package name uses dashes, the import uses dots).
  • Running from a different folder each time. checkpoints.sqlite is created in the current folder. Run once from the project root and once from module1, and you get two separate files, so the "memory" seems lost. Always run from the project root.
  • Using a different thread name. student-1 and Student-1 are different threads. No argument means student-1.
  • Trying import 8_graph_agent. That's a SyntaxError; use the importlib lines as written.
  • Deleting check_same_thread=False. We tried: the very first question fails with sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread. LangGraph ran a step in a worker thread.
  • Committing the database. It contains every message you typed. Add it to .gitignore.
  • Forgetting config in invoke. With a checkpointer, LangGraph needs a thread ID to know where to save. Verified error: ValueError: Checkpointer requires one or more of the following 'configurable' keys: thread_id, checkpoint_ns, checkpoint_id.
Recap
  • MemorySaver lives in RAM and forgets everything when Python exits; SqliteSaver writes checkpoints to a file (README exercise 7).
  • Install the official langgraph-checkpoint-sqlite package, open sqlite3.connect("checkpoints.sqlite", check_same_thread=False), wrap it in SqliteSaver, and compile with it.
  • File names starting with a digit can't be imported with import; importlib.util.spec_from_file_location loads them by path.
  • A while True loop with input() makes a chat; the thread ID comes from sys.argv; get_state shows what's saved.
  • Verified: a second process on the same thread continued from 4 to 8 messages.
  • langgraph dev provides its own persistence and refuses custom checkpointers, so this file stays a terminal program.
