The React web app

Chat with the graph-9 agent in the browser: a live trace of every graph step, threads you can switch between, and the graph drawn as Mermaid text.

TypeScript · verified with LangGraph.js 1.5.0 and llama3.2

TypeScript only. Extension: not in the video. This page has no Python version. It takes the agent with memory from step 14 (graph 9, which builds on the agent loop of step 13) and puts it in a web page. The code is in the TypeScript project langgraph-acl-ts, in the folders server/ and web/.

What was checked: we ran the app in Chrome with MODEL_PROVIDER=ollama (llama3.2 on a laptop) and asked two questions on one thread, opened a new thread, and switched back. The answers and steps quoted on this page come from that run. What it doesn't prove: how OpenAI's gpt-4o would word the answers, or how fast it would stream.

Goal

So far every graph ran in the terminal. In this step you open the math teacher from graph 9 in a browser. You type a question and see the answer appear. Next to it, a "Graph steps" panel shows every node as it finishes: the model asking for a tool, the tool's result, the final answer. Each conversation is a thread; you can start a new one and switch back to an old one, and the server's checkpointer gives you its history back. You will read every file of the app.

It is the same idea as step 19 (stream the steps, draw the graph), but the output goes to a web page instead of the terminal.

The idea in brief

  • Two programs, two terminals. A Node.js server (server/index.ts) owns the graph, the tools, the model and the memory. A React app (web/) runs in the browser and only shows things.
  • The graph is graph 9, unchanged. The server imports graph and memory from module1/9-graph-agent-memory.ts. No new graph code is written for the web.
  • The server streams. POST /api/chat runs one turn with graph.stream(...) and sends what happens as Server-Sent Events: token (answer text), step (one finished node), done and error. Three small API endpoints read the memory and the graph's drawing.
  • The browser reacts. Each event changes a piece of React state, and React redraws the parts of the page that depend on it.
New to React? Components, state and why the page redraws itself

React is a library for building user interfaces out of components: functions that return a description of what the screen should look like, written in JSX (HTML-like tags inside TypeScript, in .tsx files). You never change the page by hand. Instead you keep the data that matters in state, created with the hook useState. Calling a state setter, such as setMessages(...), tells React "this data changed"; React calls your component again and updates only the parts of the page that differ. In this app every event from the server becomes one or two setter calls, and the chat and the "Graph steps" panel follow automatically. It is a bit like a LangGraph node: you never edit the state in place, you return an update.

New to Server-Sent Events? How a server streams to a browser

A normal HTTP request gets one reply and is finished. With Server-Sent Events (SSE), the server keeps the reply open and writes small text messages into it whenever it has something new. Each message has an event: line (its type) and a data: line (its content), and ends with a blank line. This is the web version of streaming from step 19: instead of printing each chunk, the server writes it into the open reply.

New to web servers? What an API endpoint and Hono are

A web server listens on a port (here 8787) and answers requests. An API endpoint is one address plus a method, like POST /api/chat, that runs a piece of your code and returns data instead of a web page. Hono is a small TypeScript framework for writing such servers: you create an app, register a function per endpoint with app.post(path, handler) or app.get(path, handler), and start it. The handler receives a context object c with the request (c.req) and helpers to build the response (c.json, c.text).

Run it

  1. Open a terminal in the TypeScript project folder. If you have not done it yet for the earlier steps, run pnpm install (it installs React, Vite and Hono too).
  2. Choose the model in .env. With an OpenAI key, keep MODEL_PROVIDER=openai and set OPENAI_API_KEY. Without one, set MODEL_PROVIDER=ollama, install Ollama and run ollama pull llama3.2 once; Ollama must be running while you use the app. This is the setup we used.
  3. Start the API server: pnpm api. It prints LangGraph agent API on http://localhost:8787. Leave this terminal open.
  4. Open a second terminal in the same folder and start the web app: pnpm web. Vite prints the address of the app.
  5. Open http://localhost:5173 in your browser. Click Add 3 and 4. (it fills the input box), then Send. When the answer is there, click Now multiply that by 10. and Send again: same thread, so the graph remembers the 7.
  6. To stop, press Ctrl+C in each terminal.

The server: server/index.ts

This is the whole back end: one file, four endpoints, and two helpers. describe turns a LangChain message into a small object the browser can show; relay runs one turn of the graph and forwards each step as an event.

// A small HTTP server for the web app. Run: pnpm api  (then pnpm web in a second terminal)
//   POST /api/chat          { threadId, message } -> a stream of events while the graph runs
//   GET  /api/threads       the thread ids the memory knows
//   GET  /api/threads/:id   the messages saved for one thread (read with graph.getState)
//   GET  /api/graph         the graph as Mermaid text
// Events are Server-Sent Events: "token" (answer text), "step" (one finished node), "done", "error".
import { serve } from "@hono/node-server";
import { AIMessage, HumanMessage, ToolMessage, type BaseMessage } from "langchain";
import { Hono } from "hono";
import { streamSSE, type SSEStreamingApi } from "hono/streaming";
// the agent with math tools and MemorySaver from graph 9
import { graph, memory } from "../module1/9-graph-agent-memory.js";

/** What one message added, in a shape the browser can show. */
function describe(message: BaseMessage) {
  if (AIMessage.isInstance(message) && message.tool_calls?.length) {
    return { kind: "tool_call", text: message.tool_calls.map((c) => `${c.name}(${JSON.stringify(c.args)})`).join(", ") };
  }
  if (ToolMessage.isInstance(message)) return { kind: "tool_result", text: `${message.name ?? "tool"} → ${message.text}` };
  if (AIMessage.isInstance(message)) return { kind: "answer", text: message.text };
  return { kind: "input", text: message.text };
}

/** Run one turn of the graph and forward each step to the browser as it happens. */
async function relay(sse: SSEStreamingApi, threadId: string, message: string) {
  const send = (event: string, data: unknown) => sse.writeSSE({ event, data: JSON.stringify(data) });
  try {
    const stream = await graph.stream(
      { messages: [new HumanMessage(message)] },
      { configurable: { thread_id: threadId }, streamMode: ["updates", "messages"] },
    );
    let step = 0;
    for await (const [mode, chunk] of stream) {
      if (mode === "messages") { // pieces of text while the model writes
        const [token, meta] = chunk;
        if (meta.langgraph_node === "chat_with_tools" && token.text) await send("token", token.text);
        continue;
      }
      // "updates": { nodeName: { messages: [what this node added] } }, once per finished node
      for (const [node, update] of Object.entries(chunk)) {
        const added = (update?.messages ?? []) as BaseMessage[];
        await send("step", { step: ++step, node, added: added.map(describe) });
      }
    }
    await send("done", {});
  } catch (error) {
    await send("error", (error as Error).message);
  }
}

const app = new Hono();

app.post("/api/chat", async (c) => {
  const { threadId, message } = await c.req.json<{ threadId: string; message: string }>();
  return streamSSE(c, (sse) => relay(sse, threadId, message));
});

app.get("/api/threads", async (c) => {
  const ids = new Set<string>();
  for await (const saved of memory.list({})) { // every checkpoint of every thread
    ids.add(saved.config.configurable!.thread_id);
  }
  return c.json([...ids]);
});

app.get("/api/threads/:id", async (c) => {
  const state = await graph.getState({ configurable: { thread_id: c.req.param("id") } });
  const messages = (state.values.messages ?? []) as BaseMessage[];
  return c.json(messages.map((m) => ({ type: m.type, ...describe(m) })));
});

app.get("/api/graph", async (c) => c.text((await graph.getGraphAsync()).drawMermaid()));

const port = Number(process.env.PORT ?? 8787);
serve({ fetch: app.fetch, port });
console.log(`LangGraph agent API on http://localhost:${port}`);

What travels over the wire for one question

Numbers sent as text, again. Look at step 1 above: llama3.2 sent "nb1":"3", text in quotes, not the number 3. Graph 9's tools use z.coerce.number(), so Zod turns "3" into 3 and the tool runs. With plain z.number() the tools node would have answered with a schema error instead (see the TypeScript notes in step 13).

The web app: web/src/sse.ts

The browser has a built-in reader for Server-Sent Events, EventSource, but it can only send GET requests without a body. /api/chat needs a JSON body, so this file sends a POST with fetch and reads the event stream itself. It also defines the types of the events, shared with App.tsx.

// POST a JSON body and read the Server-Sent Events that come back.
// (The browser's EventSource only does GET requests, so we read the stream ourselves.)
export type Added = { kind: "input" | "tool_call" | "tool_result" | "answer"; text: string };
export type Step = { step: number; node: string; added: Added[] };

export type GraphEvent =
  | { event: "token"; data: string }
  | { event: "step"; data: Step }
  | { event: "done"; data: Record<string, never> }
  | { event: "error"; data: string };

export async function postEvents(url: string, body: unknown, onEvent: (e: GraphEvent) => void) {
  const response = await fetch(url, {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify(body),
  });
  if (!response.ok || !response.body) throw new Error(`Server answered ${response.status}`);

  const reader = response.body.pipeThrough(new TextDecoderStream()).getReader();
  let buffer = "";
  for (;;) {
    const { value, done } = await reader.read();
    if (done) break;
    buffer += value;
    // Events are separated by a blank line; each has "event: ..." and "data: ..." lines.
    const blocks = buffer.split(/\r?\n\r?\n/);
    buffer = blocks.pop()!; // the last piece may be incomplete: keep it for the next read
    for (const block of blocks) {
      const event = block.match(/^event: (.*)$/m)?.[1];
      const data = block.match(/^data: (.*)$/m)?.[1];
      if (event && data !== undefined) onEvent({ event, data: JSON.parse(data) } as GraphEvent);
    }
  }
}

The web app: web/src/App.tsx

The whole user interface is one component. Read it in five parts: the state (lines 11–18), the start-up requests (21–24), the event handler handle (27–45), the actions (47–81: send a question, open a thread, start a new one), and the JSX that draws the page (83–143).

        setSteps((all) => [...all, e.data]);
        const answer = e.data.added.find((a) => a.kind === "answer");
        if (answer) updateLast((m) => ({ ...m, text: answer.text })); // the finished answer replaces the pieces
        break;
      }
      case "error":
        updateLast((m) => ({ ...m, text: `${m.text}\n[Error: ${e.data}]` }));
        break;
    }
  }

  async function send(event: FormEvent) {
    event.preventDefault();
    const text = input.trim();
    if (!text || busy) return;
    setInput("");
    setBusy(true);
    setSteps([]);
    setThreads((all) => (all.includes(threadId) ? all : [...all, threadId]));
    setMessages((all) => [...all, { role: "user", text }, { role: "assistant", text: "" }]);
    try {
      await postEvents("/api/chat", { threadId, message: text }, handle);
    } catch (error) {
      handle({ event: "error", data: (error as Error).message });
    } finally {
      setBusy(false);
    }
  }

  // Open an older thread: the server reads what its memory saved for it (graph.getState).
  async function openThread(id: string) {
    setThreadId(id);
    setSteps([]);
    const history: (Added & { type: string })[] = await (await fetch(`/api/threads/${encodeURIComponent(id)}`)).json();
    setSaved(history.length);
    setMessages(history
      .filter((m) => m.type === "human" || m.kind === "answer")
      .map((m) => ({ role: m.type === "human" ? "user" : "assistant", text: m.text })));
  }

  function newThread() {
    setThreadId(newThreadId());
    setMessages([]);
    setSteps([]);
    setSaved(null);
  }

  return (
    <div className="page">
      <header>
        <div>
          <p className="eyebrow">LangGraph.js · graph 9</p>
          <h1>Math teacher with memory</h1>
        </div>
        <button onClick={newThread} disabled={busy}>New thread</button>
      </header>

      <nav aria-label="Threads">
        <span className="muted">Threads:</span>
        {[...new Set([...threads, threadId])].map((id) => (
          <button key={id} className={`chip ${id === threadId ? "current" : ""}`} onClick={() => openThread(id)}
            disabled={busy} aria-current={id === threadId}>{id}</button>
        ))}
      </nav>

      <main>
        <section className="chat" aria-label="Conversation">
          {saved !== null && <p className="muted">Loaded {saved} saved messages for {threadId}.</p>}
          {messages.length === 0 && (
            <div className="empty">
              <p>Ask a math question. Try, one after the other:</p>
              {EXAMPLES.map((q) => (
                <button key={q} className="example" onClick={() => setInput(q)}>{q}</button>
              ))}
            </div>
          )}
          {messages.map((m, i) => (
            <article key={i} className={`bubble ${m.role}`}>
              <p>{m.text || (i === messages.length - 1 && busy ? "…" : "")}</p>
            </article>
          ))}
          <form onSubmit={send}>
            <input value={input} onChange={(e) => setInput(e.target.value)} placeholder="Type a question" disabled={busy} />
            <button disabled={busy || !input.trim()}>Send</button>
          </form>
        </section>

        <aside aria-label="Graph steps">
          <h2>Graph steps</h2>
          {steps.length === 0 && <p className="muted">Each node appears here as it finishes.</p>}
          <ol>
            {steps.map((s) => (
              <li key={s.step}>
                <code className="node">{s.node}</code>
                {s.added.map((a, i) => (
                  <div key={i} className={`added ${a.kind}`}><span>{LABELS[a.kind]}</span> {a.text}</div>
                ))}
              </li>
            ))}
          </ol>
          <details>
            <summary>The graph (Mermaid text)</summary>
            <pre>{mermaid}</pre>
          </details>
        </aside>
      </main>
    </div>
  );
}

const LABELS: Record<Added["kind"], string> = {

  tool_result: "tool result:",
  answer: "final answer:",

Threads, checkpoints and the memory

The browser does not store the conversation. It only remembers which thread is current. Everything else is in the server's MemorySaver, the same object as in step 14. When you click a chip, the browser asks the server, and the server asks the checkpointer.

What you should see

What you should see. This is the run we checked in Chrome with llama3.2. Your wording will differ, and a model can choose differently.

  • "Add 3 and 4." The steps panel shows 1 chat_with_tools, asks for a tool: addition({"nb2":"4","nb1":"3"}); 2 tools, tool result: addition → 7; 3 chat_with_tools, final answer. The chat says "The result of adding 3 and 4 is 7."
  • "Now multiply that by 10." on the same thread: multiply({"nb1":"7","nb2":"10"}), then 70, then "The result of multiplying 7 by 10 is 70." The model knew "that" meant 7: the memory works.
  • New thread adds a second chip and an empty chat. Clicking the first chip again reloads its questions and answers from the checkpointer, with the line "Loaded … saved messages for thread-…".
  • Open The graph (Mermaid text): you see graph 9's shape, including chat_with_tools -.-> tools; and chat_with_tools -.-> __end__;.

Memory is not honesty. In the terminal run of graph 9 (step 14), a brand-new thread was asked "What was my last result?" and llama3.2 answered "Your last result was 5, which was the result of the subtraction 10 - 5." That thread had no history; the model made it up (a hallucination). Try the same question on a new thread in the app. The checkpointer can only give the model what was saved; it cannot stop it from inventing.

Common problems.

  • Why pnpm api and not pnpm server? pnpm has a built-in command called server, and built-in commands win over scripts with the same name: pnpm server runs pnpm's own command and exits silently without starting anything. (pnpm run server would work.) Naming the script api avoids the clash.
  • Port already in use. If pnpm api fails with EADDRINUSE, another program (often a server you started earlier and forgot) uses port 8787. Stop it, or start with another port (PORT variable) and change the proxy target in web/vite.config.ts to match. If 5173 is busy, Vite picks the next free port and prints it; open that address.
  • Only pnpm web is running. The page loads, but no graph appears in the Mermaid block and every question ends with an [Error: …] line, because the proxy has nowhere to forward /api. Start pnpm api in the other terminal.
  • The model is not reachable. The server starts without calling the model, so problems show up at the first question, as [Error: …] at the end of the answer: Ollama not running (start it and check ollama list), or MODEL_PROVIDER=openai without OPENAI_API_KEY in .env. Restart pnpm api after editing .env.
  • The app forgot every thread. MemorySaver keeps threads in the server's memory. Restarting pnpm api erases them all: a reloaded page shows no chips, and an old chip still on screen loads 0 saved messages. For memory that survives restarts, use the SQLite checkpointer from step 17.
  • Answers vary. The same question can lead to a different tool, different wording, or no tool call at all (then the panel shows a single chat_with_tools step). With a small local model this is normal; the steps panel shows what really happened.

Try it yourself

  1. Check the memory. Ask "Add 3 and 4.", then click New thread and ask "Now multiply that by 10." What does the model do without the 7? Click the first chip and compare.
  2. Count the saved messages. After two questions on one thread, open another thread and come back. Does "Loaded … saved messages" match 4 per question with one tool call? Ask something that needs two tools ("Add 2 and 3, then multiply by 4") and predict the new count first.
  3. Watch the raw events. Open the browser's developer tools (F12), tab Network, send a question and click the chat request. You can see the token, step and done events arrive one by one.
  4. Keep threads across restarts. In server/index.ts, instead of importing graph 9, import builder from ../module1/8-graph-agent.js and compile it with SqliteSaver.fromConnString("checkpoints.sqlite"), as module1/11-graph-sqlite-memory.ts does (step 17). Export the saver as memory so /api/threads still works. Restart pnpm api: the chips come back.
  5. Add an event. Make the server send send("thread", threadId) at the start of relay, add the case to the GraphEvent type in sse.ts, and run pnpm typecheck. Then add a new kind to Added and see which line TypeScript points to.
Recap
  • The app is two programs: a Hono server that owns graph 9 (pnpm api, port 8787) and a React app served by Vite (pnpm web, port 5173), which forwards /api to the server.
  • The server runs graph.stream with the "updates" and "messages" modes and forwards each finished node as a step event, model text as token events, then done or error.
  • sse.ts reads those events from a POST response with fetch, because EventSource only does GET.
  • App.tsx keeps everything in useState; each event becomes a state change and React redraws the page.
  • The browser only knows the thread id. The history lives in MemorySaver: memory.list gives the thread ids, graph.getState gives one thread's messages, and a server restart forgets them all.
