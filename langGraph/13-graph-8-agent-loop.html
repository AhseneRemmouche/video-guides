Graph 8: The Agent Loop

Three math tools and an edge back to the model: a real agent.

▶ Watch this part (01:58:21)

Goal

Graph 6 ran the tool but stopped on a bare number. In this step you build the course's first real agent: a model with three math tools, a system message that gives it a role, and one changed edge, tools → chat_with_tools instead of tools → END. That single edge creates a loop: after the tools run, their results go back to the model, which can either ask for more tools or answer in plain words.

This loop (model, tools, model, tools… until the model answers) is the agent loop. The presenter calls it the ReAct architecture (130:02): the model reasons about what to do, acts by calling tools, sees the results, and repeats. Almost every tool-using agent you'll meet is a version of this graph.

What the presenter explains

At 118:21 the presenter says "I want the AI to tell me the full thing. And this is where we are going to start building our first agent." They create 8_graph_agent.py, adding: "I know I skipped seven, but I am calling it on purpose" (118:44). There is no file 7 in the repo either; nothing is missing, the number was simply skipped.

The file is written from scratch (119:08–125:48): the model, three tools (multiply, addition, subtraction) to show "how we're going to bind multiple tools" (119:37), a system message "you are a helpful math teacher" (122:09), and the same nodes and conditional edge as graph 6. The presenter first wires tools → END, just like graph 6, tries a few questions in Studio, and only then changes that one edge (130:48) to show the difference live. Both versions are below.

New to agents? What makes a graph an "agent"

In this course, an agent is a model that can decide for itself which tools to use, see the results, and decide again, until it's ready to answer. The presenter's description (130:26): "the agent will ask the tools for stuff and then the tool will bring back this information to the agent. So the agent will feel free to ask the tools again for other things or continue to proceed."

Compare with the earlier graphs: in graphs 0–6 you fixed the path in advance (at most one model call, at most one tool round). In graph 8 the model's replies decide how many rounds there are. That flexibility is the point, and also the risk: a loop needs a way to stop (see "Recursion limit" below).

The complete file

# check mural for explenation
from langgraph.graph import StateGraph, START, END, MessagesState
from langchain_openai import ChatOpenAI
from dotenv import load_dotenv
from langchain.tools import tool
from langgraph.prebuilt import ToolNode, tools_condition
from langchain.messages import SystemMessage
from typing import Literal


load_dotenv()

model_llm = ChatOpenAI(model="gpt-4o")

@tool
def multiply(nb1 : int, nb2: int) -> int:
    """this tool return the multiplication of 2 numbers"""
    return nb1*nb2

@tool
def addition(nb1 : int, nb2: int) -> int:
    """this tool return the sum of 2 numbers"""
    return nb1+nb2

@tool
def subtraction(nb1 : int, nb2: int) -> int:
    """this tool return the subtaction of 2 numbers"""
    return nb1-nb2

model_llm_with_tools = model_llm.bind_tools([multiply,addition,subtraction])

system_message = SystemMessage(content="you are a helpful Math teach")

# nodes
def chat_with_tools(state: MessagesState) -> MessagesState:
    return {"messages": [model_llm_with_tools.invoke(state["messages"] + [system_message])]}

builder = StateGraph(MessagesState)

builder.add_node("chat_with_tools", chat_with_tools)
builder.add_node("tools", ToolNode([multiply,addition,subtraction]))

builder.add_edge(START, "chat_with_tools")
builder.add_conditional_edges("chat_with_tools", tools_condition)
builder.add_edge("tools", "chat_with_tools")

graph = builder.compile()

New to joining lists with +? What line 36 really sends

In Python, [1, 2] + [3] makes a new list [1, 2, 3] and leaves both originals unchanged. Line 36 uses exactly that: state["messages"] + [system_message] builds a temporary list just for this model call. The state's own list is not modified, which is why the system message never shows up in the result.

Both sides must be lists. [system_message] is a one-item list; system_message alone is a single object, and list + object raises TypeError: can only concatenate list (not "SystemMessage") to list (verified). The order of the two sides decides where the system message lands: last here, first if you write [system_message] + state["messages"].

Run it: the agent loop for "What is 12 multiplied by 7?"

To run the repo file from the terminal, add these lines at the bottom:

result = graph.invoke({"messages": [HumanMessage(content="What is 12 multiplied by 7?")]})
for message in result["messages"]:

What you should see

  • Four messages for a one-tool question: Human, AI (tool call), Tool 84, AI (a sentence). The fourth one is new compared with graph 6.
  • With the real gpt-4o the last message is the model's own wording, something like "12 multiplied by 7 is 84." The exact text varies from run to run.
  • "hi" gives just two messages (Human, AI): no tool needed, so tools_condition goes straight to END (verified).
  • No system message in the result: it's sent to the model but never saved in the state.

The system message is sent last

Line 36 builds the list state["messages"] + [system_message], so the system message comes after the conversation. The test harness recorded what the model actually received (verified):

  • First call: [HumanMessage, SystemMessage]
  • Second call (after the tool ran): [HumanMessage, AIMessage, ToolMessage, SystemMessage]

It works: the model still reads the instruction, and the presenter's math-teacher greeting shows it. But the usual convention is to put the system message first, [system_message] + state["messages"], so the role is set before the conversation starts. That's what step 15 changes. The presenter also mentions (127:34) that you could instead send a system message as part of the input in Studio: "there's multiple way of doing it but we did it this way."

Several tools in one reply, and multi-step questions

At 129:14 the presenter asks one message with three calculations (the frame at 131:10 shows the input what is 10- 5, 20 * 3, 3 + 2). gpt-4o answers with one AI message containing three tool calls, and ToolNode runs all of them: Studio shows subtraction 5, multiply 60, addition 5. "We have three different tool calls that were executed" (129:38). Running ToolNode on exactly those three calls returns three ToolMessages, 5, 60 and 5, each with its own tool_call_id (verified).

With the first draft (tools → END) that's where it stopped: three numbers and no sentence. The presenter then made the one-line change to line 45 and ran "the same exact message in the new thread" (131:13). This time the results went back to the model, which "decided very good, I do not need to ask the tools anything again" and wrote the answer (131:39–132:02).

What about questions where one step needs the result of another, like "subtract 5 from 10, then multiply the result by 3"? The model can't request the multiplication yet, because it doesn't know the first result. Without the loop it would be stuck after the first round. With the loop, it can ask for subtraction(10, 5), read 5, then ask for multiply(5, 3) in a second round, and only then answer. That's the real power of the edge on line 45. (The video shows the three-independent-calculations case; how a real model splits a chained question into rounds is its own decision and can vary.)

Studio: why a new thread?

In Studio every run belongs to a thread, and the server remembers each thread's messages. Submitting again in the same thread appends your new message to everything already there, and the model sees the whole history, including the earlier unfinished tool results. Clicking New Thread (the + next to the thread ID) starts with an empty list, so the test is clean. That's why the presenter re-ran the question "in the new thread" after changing the edge (131:13). langgraph dev reloads the graph on save ("changes detected" in the log), so no restart was needed for that edit.

This server-side memory is also why Studio "remembers" while a plain graph.invoke does not; step 14 is about exactly that difference.

Recursion limit: what stops a loop that never ends?

A loop needs an exit. In graph 8 the only exit is the model answering without a tool call. If a model kept asking for tools forever, the graph would keep looping. LangGraph protects you with a recursion limit: a maximum number of steps (supersteps) per run. When it's reached, the run stops with an error instead of running (and paying for model calls) forever.

You set it per run in the config, the second argument of invoke:

result = graph.invoke(
    {"messages": [HumanMessage(content="What is 12 multiplied by 7?")]},
    {"recursion_limit": 10},
)

The 12 × 7 run uses three node steps (model, tools, model). Verified with the locked versions: with {"recursion_limit": 3} it already fails, with 4 it succeeds. The error:

langgraph.errors.GraphRecursionError: Recursion limit of 3 reached without hitting a stop condition. You can increase the limit by setting the `recursion_limit` config key.

In langgraph 1.2.11 the default limit is very high, 10007 (verified); older versions and many tutorials use 25. So for agents, setting your own limit (10 to 25 is plenty for this math agent) is a good habit. The video doesn't cover this; the handbook chapter Control Flow goes deeper.

Common mistakes

  • Leaving tools → END (the first draft). Tools run but you never get a sentence. The edge must go back to "chat_with_tools".
  • Edge back to the wrong name. The node is "chat_with_tools" (with an s); "chat_with_tool" from graph 6 gives ValueError: Found edge ending at unknown node `chat_with_tool` at compile time (verified).
  • A tool bound but missing from ToolNode (or the other way round). Keep lines 30 and 41 identical, or better, use one tools list (step 15).
  • state["messages"] + system_message without the brackets → TypeError: can only concatenate list (not "SystemMessage") to list (verified). Wrap it: [system_message].
  • Testing a changed graph in an old Studio thread. The earlier messages are still there and confuse the result. Use New Thread.
  • Vague tool docstrings. The model only knows what the docstring says. "the subtaction of 2 numbers" doesn't say which is subtracted from which.
  • No recursion limit on a real agent. Set {"recursion_limit": …} so a confused model can't loop for a long time.
