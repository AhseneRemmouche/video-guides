Running the requested tool: by hand first, then with LangGraph's prebuilt pieces.

Goal

At the end of step 11 the model could ask for the multiply tool, but nothing ever ran it: the graph went straight from the model to END, so the result was a human message and an AI message holding a tool call, and no answer. In this step you add the missing half. A new node runs the tool the model asked for, and a conditional edge decides, after every model reply, whether to go to that node or to stop.

You build it twice, the way the presenter explains it. First by hand (a node that calls the tool and a routing function that checks for tool calls), so you can see there is no magic. Then with LangGraph's two prebuilt pieces, ToolNode and tools_condition, which do the same job in two lines. You'll also meet the error the presenter spent four minutes chasing on camera, and see why the result of this graph still isn't a sentence.

What the presenter explains

At 104:42 the presenter copies graph 5 into a new file, 6_graph_tool_call.py: "we would like to have the full circle… he's requesting a tool call, let us run the tool call". They import two things from langgraph.prebuilt (105:35): ToolNode and tools_condition, and add a node: "I'm going to call it tool. Let's call it… we have to call it tools" (105:58).

The key explanation comes at 108:06. Remember the rule from step 8: nodes don't choose where the state goes next; nodes only modify the state. So the job is split in two:

  • The tool node modifies the state: it reads the last message, runs the requested tool with its arguments, and appends the result to the message list (108:32).
  • The conditional edge chooses the route: "does it go to the tools node or does it go to the end" (108:58).

Then (109:23–111:27) the presenter shows that they built both pieces by hand first, "so you can understand it easily", and kept that code in a docstring at the bottom of the repo file. That hand-written version is the best way to understand the prebuilt one, so it comes first below.

New to tool messages? How a tool result gets back into the conversation

You already know three message types: a human message (you), an AI message (the model), and a system message (instructions). The fourth is the ToolMessage: the result of running a tool.

When a model wants a tool, its AI message has empty text and a tool_calls list. Each tool call is a small dict: the tool's name, its args, and a unique id such as call_…. After you run the tool, you answer with a ToolMessage whose content is the result (as text) and whose tool_call_id is that same id. The id is how the model matches "this result" to "that request", which matters when it asked for several tools at once.

OpenAI is strict about this pairing: if a conversation sent to the model has a tool call with no matching tool message, the API rejects the request. That's why the tool node must always answer every call it runs, with the right id.

from typing import Literal

from langgraph.graph import StateGraph, START, END, MessagesState
from langchain_openai import ChatOpenAI
from dotenv import load_dotenv
from langchain.tools import tool
from langchain.messages import ToolMessage


load_dotenv()

model_llm = ChatOpenAI(model="gpt-4o")

@tool
def multiply(nb1: int, nb2: int) -> int:
    """This tool is used for multiplying 2 numbers and returning the product"""
    return nb1*nb2

model_llm_with_tool = model_llm.bind_tools([multiply])

# nodes
def chat_with_tool(state: MessagesState) -> MessagesState:
    return {"messages": [model_llm_with_tool.invoke(state["messages"])]}

# what ToolNode does for us, written by hand (kept in a docstring in the repo)
def tool_node(state: MessagesState) -> MessagesState:
    last_message = state["messages"][-1]
    tool_call = last_message.tool_calls[0]
    response = multiply.invoke(tool_call["args"])

    return {"messages": [ToolMessage(content=str(response),
                                      tool_call_id=tool_call["id"])]}


# what tools_condition does for us, written by hand
def should_continue(state: MessagesState) -> Literal["tool_node", "__end__"]:

    last_message = state["messages"][-1]

    # Did the LLM request a tool?
    if last_message.tool_calls:
        return "tool_node"

    return "__end__"


builder = StateGraph(MessagesState)

builder.add_node("chat_with_tool", chat_with_tool)
builder.add_node("tool_node", tool_node)

builder.add_edge(START, "chat_with_tool")
builder.add_conditional_edges("chat_with_tool", should_continue)
builder.add_edge("tool_node", END)

graph = builder.compile()
// Graph 6 without the prebuilt helpers: our own tool node and our own routing function.
import { END, MessagesAnnotation, START, StateGraph } from "@langchain/langgraph";
import { AIMessage, HumanMessage, ToolMessage, tool } from "langchain";
import { z } from "zod";
import { isMain } from "../src/is-main.js";
import { getModel } from "../src/model.js";
import { show } from "../src/show.js";

const modelLlm = getModel();

const multiply = tool(({ nb1, nb2 }) => nb1 * nb2, {
  name: "multiply",
  description: "This tool is used for multiplying 2 numbers and returning the product",
  // z.coerce.number() also accepts "4" (some models, like llama3.2, send numbers as text)
  schema: z.object({ nb1: z.coerce.number(), nb2: z.coerce.number() }),
});

const modelLlmWithTool = modelLlm.bindTools([multiply]);

// nodes
async function chatWithTool(state: typeof MessagesAnnotation.State) {
  return { messages: [await modelLlmWithTool.invoke(state.messages)] };
}

// what ToolNode does for us, written by hand
async function toolNode(state: typeof MessagesAnnotation.State) {
  const lastMessage = state.messages.at(-1) as AIMessage;
  const toolCall = lastMessage.tool_calls![0];
  const response = await multiply.invoke(toolCall.args as { nb1: number; nb2: number });

  return { messages: [new ToolMessage({ content: String(response), tool_call_id: toolCall.id! })] };
}

// what toolsCondition does for us, written by hand
function shouldContinue(state: typeof MessagesAnnotation.State): "tool_node" | typeof END {
  const lastMessage = state.messages.at(-1) as AIMessage;

  // Did the LLM request a tool?
  if (lastMessage.tool_calls?.length) {
    return "tool_node";
  }

  return END;
}

export const graph = new StateGraph(MessagesAnnotation)
  .addNode("chat_with_tool", chatWithTool)
  .addNode("tool_node", toolNode)
  .addEdge(START, "chat_with_tool")
  .addConditionalEdges("chat_with_tool", shouldContinue, ["tool_node", END])
  .addEdge("tool_node", END)
  .compile();

if (isMain(import.meta.url)) {
  const result = await graph.invoke({ messages: [new HumanMessage("What is 4 multiplied by 5?")] });
  result.messages.forEach((message) => console.log(show(message)));
}

New to routing functions? Nodes change state, edges choose the road

A routing function is a plain function that receives the state and returns the name of the node to run next (or END). You attach it with add_conditional_edges(from_node, router). You met one in step 8, where the route depended on the first word of a string. Here the route depends on whether the last message has tool calls.

A routing function must not change the state; it only reads it. And a node can't choose the next node; it only returns an update. Keeping those two jobs apart is what lets LangGraph draw the graph and show you each step in Studio.

Why the node must be called "tools"

tools_condition is a ready-made routing function, so it can't know what you called your tool node. It always returns the string "tools" (or END). LangGraph then looks for a node with that exact name. The presenter says it twice: "we have to call it tools" (105:58) and "I know that we need to call it tools" (114:56).

What happens if you name it something else, for example "my_tools"? compile() fails right away (verified):

ValueError: At 'chat_with_tool' node, 'tools_condition' branch found unknown target 'tools'

If you really want another name, give add_conditional_edges a third argument, a path map that translates the router's answers into your node names (verified to work):

builder.add_node("my_tools", ToolNode([multiply]))
builder.add_conditional_edges("chat_with_tool", tools_condition, {"tools": "my_tools", END: END})

Simpler: keep the name "tools", as the course does.

The error and the path map above are Python. In TypeScript, keep the node name "tools" and the target list ["tools", END] on line 30; we did not test other names there.

Why does add_edge with a function give "unknown node"?

add_edge(a, b) means "always go from node a to node b", and b must be a node name. Given the function tools_condition instead, LangGraph stores the edge anyway, and only when compile() checks every edge does it notice that no node is called <function tools_condition at 0x…> (that's how Python prints a function object). It's the same family of mistake as step 6, where a function was passed where a name belonged.

add_conditional_edges(a, router) is the only method that takes a function: it means "after a, call this function and go where it says".

In TypeScript the same rule holds for addEdge and addConditionalEdges. The difference is when you find out: the compile error TS2345 shows up in your editor as you type, before any run.

Look at the tool call above: {"nb1":"4","nb2":"5"}. llama3.2 sent the numbers as text, even though the schema asks for numbers. Our first version of the tool used the strict schema z.object({ nb1: z.number(), nb2: z.number() }). With it, the same graph gave this (real run):

What happened: Zod checked the arguments before multiply ran, rejected "4" and "5" ("expected number, received string"), and multiply never ran. Because ToolNode catches errors by default, the error became the tool message, with "Please fix your mistakes." added for the model. Python never hit this. Pydantic, which checks the arguments there, converts "4" to 4 by default. Zod does not convert unless you ask. The fix is one word on line 15: z.coerce.number(). Common mistakes

  • add_edge(…, tools_condition) → ValueError: Found edge ending at unknown node `<function tools_condition …>` (or GraphLoadError in langgraph dev). Use add_conditional_edges.
  • Naming the node anything but "tools" → ValueError: … 'tools_condition' branch found unknown target 'tools'. Rename it, or pass a path map.
  • Different tool lists in bind_tools([...]) and ToolNode([...]). The model may request a tool the node doesn't know. Keep one list and use it in both places (step 15 does this with a tools variable).
  • Returning the tool result as a plain string or an AIMessage in a hand-written tool node. It must be a ToolMessage with the request's tool_call_id, or OpenAI rejects the next call.
  • Forgetting the ToolMessage import when copying the docstring into real code → NameError: name 'ToolMessage' is not defined.
  • Not restarting after a load error. When startup failed, the server has exited ("Application startup failed. Exiting."). Fix the file, then run uv run langgraph dev again.
  • addEdge(…, toolsCondition) → compile error TS2345 in the editor, and at run time UnreachableNodeError: Node `tools` is not reachable. Use addConditionalEdges.
  • Strict z.number() in the tool schema with a model that sends "4": the tool message becomes "Received tool input did not match expected schema" (prebuilt ToolNode) or the run crashes with ToolInputParsingException (by-hand node). Use z.coerce.number().
  • Forgetting the target list ["tools", END] in addConditionalEdges: LangGraph.js cannot read your TypeScript types, so this list is how it learns where the router may go.

To see how each node's return value is appended to messages, and how the conditional edge is evaluated between steps, read How State Flows Through a Graph.

Recap
  • A tool request is useless until something runs it. Graph 6 adds a tool node and a conditional edge after the model.
  • By hand: tool_node reads the last message's tool call, runs the tool, and returns a ToolMessage(content=str(result), tool_call_id=…); should_continue returns "tool_node" or "__end__".
  • Prebuilt: ToolNode([multiply]) runs every tool call; tools_condition returns "tools" or END, so the node must be named "tools".
  • Routers go in add_conditional_edges. add_edge(…, tools_condition) gives "Found edge ending at unknown node", shown by langgraph dev as GraphLoadError.
  • With tools → END the result is Human, AI (tool call), Tool "20": the number, but no sentence. Step 13 sends the result back to the model.
  • In TypeScript: new ToolNode([multiply]) and toolsCondition with ["tools", END]. The addEdge mistake is a TS2345 compile error and, at run time, UnreachableNodeError. Use z.coerce.number(): llama3.2 sent "4", and strict z.number() turned the answer 20 into a schema error.
