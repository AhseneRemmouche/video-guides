Human-in-the-Loop & Interrupts

Pausing a graph with interrupt, approving or editing, and resuming with Command.

The agent from step 13 decides on its own which math tool to call, and calls it immediately. For a calculator that is fine. For a tool that sends an email, spends money, deletes a file or writes to a database, you usually want a person to look first. This chapter shows how a LangGraph graph can pause, show something to a human, wait (for seconds or for days), and then resume with the human's answer. You will learn the interrupt() function, the Command(resume=...) object, the approve / edit / reject patterns, the older "breakpoint" style (interrupt_before / interrupt_after), and the Interrupts button you can see at the top of LangGraph Studio in the video.

Why this matters for your project. The video does not cover this topic; the presenter ends after memory and says there is "a lot more to be learned" (at 136:17). Human-in-the-loop is the natural next step for graph 8: the same agent, but you approve each tool call. Everything here is built on the checkpoints from chapter 6, so read that first.

The idea: pausing is just saving

A Python function cannot normally "wait three days for a human". The process might restart, the server might scale down, the user might close the browser. LangGraph solves this with checkpoints. When a node asks for human input, LangGraph:

  1. Stops the node at the point where it called interrupt(...).
  2. Saves a checkpoint that records "this node is waiting, and here is the question".
  3. Returns from invoke with the question under a special key, __interrupt__.

Later (any time later, from any process that uses the same checkpointer) you call the graph again on the same thread with Command(resume=answer). LangGraph loads the checkpoint, runs the waiting node again, and this time interrupt(...) returns the answer instead of stopping.

A checkpointer is required. Verified with LangGraph 1.2.11: compiled without a checkpointer, the graph still stops at interrupt() and returns __interrupt__, but resuming fails with RuntimeError: Cannot use Command(resume=...) without checkpointer. There is nowhere to resume from. Under langgraph dev you do not add one yourself; the server provides it (chapter 6).

A complete example: review an email before sending

This graph writes a draft, asks a human to review it, and then either sends it, sends an edited version, or stops. It needs no model and no API key, so you can run it as is. It was run with all three answers; the outputs are shown after the code.

from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import interrupt, Command


class State(TypedDict):
    draft: str
    status: str


def write_draft(state: State):
    return {"draft": "Dear student, your answer 84 is correct."}


def human_review(state: State):
    decision = interrupt({"question": "Send this email?", "draft": state["draft"]})
    if decision["action"] == "approve":
        return Command(goto="send", update={"status": "approved"})
    if decision["action"] == "edit":
        return Command(goto="send", update={"draft": decision["draft"], "status": "edited"})
    return Command(goto=END, update={"status": "rejected"})


def send(state: State):
    print("SENDING:", state["draft"])
    return {}


builder = StateGraph(State)
builder.add_node("write_draft", write_draft)
builder.add_node("human_review", human_review, destinations=("send", END))
builder.add_node("send", send)
builder.add_edge(START, "write_draft")
builder.add_edge("write_draft", "human_review")
builder.add_edge("send", END)
graph = builder.compile(checkpointer=InMemorySaver())

config = {"configurable": {"thread_id": "review-1"}}
result = graph.invoke({"draft": "", "status": "new"}, config)
print(result["__interrupt__"][0].value)      # the question for the human
final = graph.invoke(Command(resume={"action": "approve"}), config)
print(final)

While paused, graph.get_state(config).next is ('human_review',), and the question is also available as graph.get_state(config).tasks[0].interrupts[0].value. That is how a web app can show "waiting for your approval" after a page reload.

The rule that surprises everyone: the node starts over

On resume, LangGraph does not continue from the middle of the Python function; it cannot, because the function's local variables are long gone. It runs the whole node again from the top, and when execution reaches the same interrupt() call, that call returns the resume value. A verified test: a node that appends to a list before calling interrupt ran its first line 2 times for one pause and one resume.

Approving tool calls in graph 8

Now the useful case. The agent from step 13 loops chat_with_tools → tools → chat_with_tools. Each time the model asks for a tool, we want a person to see the tool name and arguments first. There are two ways to do it. Both were verified on the fixed 8_graph_agent.py with the fake model from step 18, which asks for multiply(12, 7).

Way 1: a static breakpoint before the tools node

You can tell compile to pause before (or after) named nodes. No change to the graph code is needed:

graph = builder.compile(checkpointer=InMemorySaver(), interrupt_before=["tools"])
config = {"configurable": {"thread_id": "1"}}

graph.invoke({"messages": [HumanMessage(content="What is 12 multiplied by 7?")]}, config)
snapshot = graph.get_state(config)
print(snapshot.next)                                     # ('tools',)
print(snapshot.values["messages"][-1].tool_calls[0])     # name 'multiply', args {'nb1': 12, 'nb2': 7}

graph.invoke(None, config)     # approve: continue as planned -> ToolMessage "84", final answer

With a breakpoint you resume with invoke(None, config), not with a Command, because nothing is waiting for a value. To edit or reject you change the saved state first with update_state:

from langchain.messages import ToolMessage

last = graph.get_state(config).values["messages"][-1]

# edit: same message id, so add_messages REPLACES it instead of appending
edited = last.model_copy(update={"tool_calls": [{**last.tool_calls[0], "args": {"nb1": 12, "nb2": 8}}]})
graph.update_state(config, {"messages": [edited]})
graph.invoke(None, config)     # the tool now returns "96"

# reject (on another paused thread): answer the call yourself, as if you were the tools node
graph.update_state(config, {"messages": [ToolMessage(content="The user rejected this tool call.",
                                                     tool_call_id=last.tool_calls[0]["id"])]},
                   as_node="tools")
graph.invoke(None, config)     # the model sees the rejection and answers without the tool

The reject trick uses as_node="tools" so LangGraph follows the tools node's edge back to chat_with_tools (verified: next became ('chat_with_tools',)). Every tool call must get a matching ToolMessage; without one, the model provider rejects the next request.

Way 2: a review node that calls interrupt()

Breakpoints are handy for debugging. For approval steps in an application, interrupt() is usually the better fit, because the question, the answer and the routing live together in your code. Here a review node sits between the model and the tools:

from langgraph.graph import StateGraph, START, END, MessagesState
from langgraph.prebuilt import ToolNode, tools_condition
from langgraph.types import interrupt, Command
from langchain.messages import ToolMessage


def review(state: MessagesState):
    call = state["messages"][-1].tool_calls[0]
    answer = interrupt({"tool": call["name"], "args": call["args"]})
    if answer == "yes":
        return Command(goto="tools")
    return Command(goto="chat_with_tools",
                   update={"messages": [ToolMessage(content="Rejected by the user.",
                                                    tool_call_id=call["id"])]})


builder = StateGraph(MessagesState)
builder.add_node("chat_with_tools", chat_with_tools)          # from 8_graph_agent.py
builder.add_node("review", review, destinations=("tools", "chat_with_tools"))
builder.add_node("tools", ToolNode(tools))
builder.add_edge(START, "chat_with_tools")
builder.add_conditional_edges("chat_with_tools", tools_condition, {"tools": "review", END: END})
builder.add_edge("tools", "chat_with_tools")
graph = builder.compile(checkpointer=InMemorySaver())

Notice the third argument to add_conditional_edges: a path map. tools_condition still returns the string "tools" (it always does, see step 12), and the map sends that to review instead. Verified run: the first invoke returned {'tool': 'multiply', 'args': {'nb1': 12, 'nb2': 7}} as the question; resuming with "yes" produced Human, AI, Tool "84", AI; resuming with "no" produced the same four message types with the rejection as the tool result. (This simple version reviews only the first tool call in a message; a real one would loop over all of them.)

New to interrupt_after? When "after" is useful

interrupt_before=["two"] stops before node two runs, so you can change its input. interrupt_after=["one"] stops after node one ran, so you can check its output before anything else happens. Verified on a two-node counter graph (one adds 1, two multiplies by 10): with interrupt_before=["two"] the first invoke returned {'n': 2} with next == ('two',); after update_state(config, {"n": 5}) the resume returned {'n': 50}. With interrupt_after=["one"] the first invoke also stopped at {'n': 2}, and resuming gave {'n': 20}.

The Interrupts button in LangGraph Studio

In the video, every Studio screen shows two buttons above the graph drawing: Memory and Interrupts (for example at 42:25 with graph 0 and at 131:10 with graph 8). The presenter does not click them. According to the Studio docs, the Interrupts button sets breakpoints: you pick a node and whether to pause before or after it, submit your input, and the run stops there; you then click Continue in the thread log to resume. It is the visual version of interrupt_before / interrupt_after, and you do not need to change your code or add a checkpointer, because the langgraph dev server already persists threads.

If your graph calls interrupt() itself, Studio also stops there and shows the question in the thread, and you resume by sending a value. The exact UI changes between Studio versions, so follow the "How to use Studio" page linked below if the buttons look different for you.

Common mistakes
  • No checkpointer in plain Python: the graph pauses but cannot resume (RuntimeError: Cannot use Command(resume=...) without checkpointer).
  • Different thread id on resume: LangGraph looks in another notebook, finds nothing waiting, and starts fresh.
  • Resuming with a dictionary instead of Command: invoke({"action": "approve"}, config) is treated as new input, not as the answer.
  • Side effects before interrupt(): they run twice. Move them after the interrupt or into the next node.
  • Wrapping interrupt() in try/except Exception: the pause works by raising a special exception internally; a broad except swallows it. Verified: with try: interrupt(...) / except Exception: the graph never paused and the except branch ran instead. Keep interrupts outside broad try blocks.
  • Rejecting a tool call without a ToolMessage: the next model call fails because a tool call has no answer.
Recap
  • interrupt(value) pauses a node, saves a checkpoint and returns value to your code under __interrupt__.
  • Resume on the same thread with invoke(Command(resume=answer), config); interrupt then returns answer.
  • The node re-runs from the top on resume: keep side effects after the interrupt.
  • A checkpointer is required (the server provides one under langgraph dev).
  • Static breakpoints: compile(interrupt_before=[...]) / interrupt_after, resume with invoke(None, config), edit with update_state; Studio's Interrupts button does the same visually.
  • For graph 8, put a review step before tools and answer rejected calls with a ToolMessage.
