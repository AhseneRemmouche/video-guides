Designing State

TypedDict, Pydantic and dataclasses, reducers like add_messages and operator.add, and keeping state small.

What you will learn

The course changes its state several times. Graph 0 uses a bare string (StateGraph(str)). Graph 1 switches to a TypedDict with one key, graph_str. Graph 3 adds an optional graph_int. Graph 4 moves to MessagesState, whose list of messages grows instead of being replaced. This chapter explains the rules behind those choices so you can design state for your own graphs.

  • what a state schema is, and what LangGraph does with it;
  • three ways to declare it: TypedDict, Pydantic BaseModel and dataclass (all verified with LangGraph 1.2.11);
  • how node updates are merged: overwrite by default, or a reducer such as add_messages, operator.add or your own function;
  • separate input and output schemas, and private keys passed between two nodes;
  • what belongs in state and what doesn't.
Why this matters for your project. Most bugs in small graphs are state bugs: a key that gets overwritten when you wanted a history, a node that returns the whole state when it meant to change one field, a KeyError because a key was never set. The tool-calling graphs (steps 11–14) only work because messages appends; with a plain list key, every node would wipe the conversation.

What a state schema is

A schema is a description of the shape of your data: which keys exist and what type each one holds. You pass it to the builder: StateGraph(State). LangGraph reads it once and creates one storage slot (a channel, see chapter 1) per key. From then on, three rules apply to every run:

  1. Nodes read the whole state. Each node function receives the current state as its argument.
  2. Nodes return an update, not a new state. The return value is a dict with only the keys the node wants to change. Keys it doesn't mention keep their value. Returning None changes nothing (verified).
  3. LangGraph merges the update. For each key in the update, it either overwrites the old value (the default) or calls that key's reducer.

Graph 1 (step 7) shows rule 2 in its smallest form:

class State(TypedDict):
    graph_str:str

# node
def greeting(state: State) -> State:
    """function takes a dict and return a dict with greeting"""
    return {"graph_str": state["graph_str"]+" welcome to AI Career Lab!"}

The node reads state["graph_str"] and returns a dict with that one key. Because the key has no reducer, the returned value replaces the old one.

Three ways to declare state

Graph 0 shows that any type works as a schema: StateGraph(str) makes the whole state a single string. Real graphs need several named keys, and LangGraph accepts three common ways to declare them. We ran all three against LangGraph 1.2.11:

from dataclasses import dataclass
from pydantic import BaseModel
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class TDState(TypedDict):          # 1. TypedDict: the course's choice
    count: int

class PydState(BaseModel):         # 2. Pydantic model: checks types at run time
    count: int = 0

@dataclass
class DCState:                     # 3. dataclass: defaults, attribute access
    count: int = 0

def bump_dict(state: TDState) -> dict:
    return {"count": state["count"] + 1}       # TypedDict state is a dict

def bump_attr(state) -> dict:
    return {"count": state.count + 1}          # Pydantic / dataclass: attributes

for schema, node in [(TDState, bump_dict), (PydState, bump_attr), (DCState, bump_attr)]:
    builder = StateGraph(schema)
    builder.add_node("bump", node)
    builder.add_edge(START, "bump")
    builder.add_edge("bump", END)
    print(schema.__name__, builder.compile().invoke({"count": 1}))

All three print {'count': 2}. Notice two things. First, with Pydantic and dataclasses the node receives an object, so it reads state.count, not state["count"]. Second, whatever the schema, nodes still return a plain dict of updates and invoke still returns a dict.

New to TypedDict, Pydantic and dataclasses? A one-minute tour
  • TypedDict (from typing_extensions or typing): a normal dict plus type hints that your editor checks. Python itself doesn't check anything when the program runs.
  • Pydantic BaseModel: a class whose fields are validated when an object is created. Pass "three" for an int and you get a ValidationError. Pydantic is already installed with LangChain.
  • @dataclass (standard library): a class with an automatic __init__ and default values. No validation.

The difference shows up when the input is wrong. Send {"count": "three"}:

Optional keys: NotRequired

Graph 3 (step 9) declares graph_int:NotRequired[int]. That tells type checkers and LangGraph that callers don't have to provide it; node1 sets it later. You can see the effect with graph.get_input_jsonschema(): its required list contains graph_str but not graph_int (verified). That's the kind of schema LangGraph Studio uses for its Input form, where the presenter's graph 2 field shows as "Required". Inside a node, read keys that may be missing with state.get("graph_int", 0) instead of state["graph_int"], or a missing key raises KeyError.

How updates are merged: overwrite or reduce

By default a key is overwritten: the newest value wins. That's what you want for a title, a counter or a route name. For a history (messages, log lines, search results) you want the new value added to the old one. That's the job of a reducer: a function reducer(old_value, new_value) -> merged_value. You attach it to a key with Annotated[type, reducer].

import operator
from typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

def keep_last_3(old: list, new: list) -> list:      # a custom reducer
    return (old + new)[-3:]

class State(TypedDict):
    title: str                                   # no reducer: overwrite
    log: Annotated[list[str], operator.add]      # operator.add: append lists
    recent: Annotated[list[int], keep_last_3]    # custom: keep the last 3

def first(state: State) -> dict:
    return {"title": "draft", "log": ["first ran"], "recent": [1, 2]}

def second(state: State) -> dict:
    return {"title": "final", "log": ["second ran"], "recent": [3, 4]}

builder = StateGraph(State)
builder.add_node("first", first)
builder.add_node("second", second)
builder.add_edge(START, "first")
builder.add_edge("first", "second")
builder.add_edge("second", END)
graph = builder.compile()

print(graph.invoke({"title": "", "log": ["start"], "recent": [0]}))

Output: {'title': 'final', 'log': ['start', 'first ran', 'second ran'], 'recent': [2, 3, 4]}. Three keys, three behaviours: title was replaced twice, log kept everything, recent kept a rolling window.

add_messages: the reducer behind MessagesState

Chat graphs keep a list of messages. Graph 4 (step 10) uses the built-in MessagesState; the repo keeps its definition in a docstring, and our lesson file makes it runnable:

# state: what MessagesState looks like inside (the version kept in the repo's docstring)
class MessagesState(TypedDict):
    messages: Annotated[List[AnyMessage], add_messages]

add_messages is smarter than operator.add. It matches messages by their id:

from langchain.messages import AIMessage, HumanMessage, RemoveMessage
from langgraph.graph.message import add_messages

history = [HumanMessage("hi", id="1"), AIMessage("hello", id="2")]

print([m.content for m in add_messages(history, [AIMessage("more", id="3")])])    # new id: append
print([m.content for m in add_messages(history, [AIMessage("edited", id="2")])])  # same id: replace
print([m.content for m in add_messages(history, [RemoveMessage(id="1")])])        # remove by id

It prints ['hi', 'hello', 'more'], ['hi', 'edited'] and ['hello']. It also gives every message without an id a fresh one, and converts shortcuts like ("user", "hey") or a plain dict into proper message objects. That's why the chat nodes in the course can simply return {"messages": [model_llm.invoke(...)]}: the model's reply is appended to the conversation.

To add your own keys next to messages, subclass MessagesState:

from langchain.messages import AIMessage, HumanMessage
from langgraph.graph import StateGraph, START, END, MessagesState

class ChatState(MessagesState):     # messages (with add_messages) + one extra key
    turns: int

def reply(state: ChatState) -> dict:
    return {"messages": [AIMessage("hello!")], "turns": state.get("turns", 0) + 1}

builder = StateGraph(ChatState)
builder.add_node("reply", reply)
builder.add_edge(START, "reply")
builder.add_edge("reply", END)
graph = builder.compile()

result = graph.invoke({"messages": [HumanMessage("hi")]})
print([m.content for m in result["messages"]], result["turns"])   # ['hi', 'hello!'] 1
Reducers and parallel nodes. When two nodes run in the same superstep and write the same key, LangGraph needs a reducer to combine the two values. Without one it raises InvalidUpdateError: At key '...': Can receive only one value per step. Use an Annotated key to handle multiple values. (verified). Chapter 3 shows the parallel patterns that need this.

Input, output and private schemas

By default one schema is used for everything: what callers send, what nodes see, and what invoke returns. For bigger graphs you can split it. StateGraph takes optional input_schema and output_schema arguments (both present in 1.2.11):

from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class InputState(TypedDict):        # what callers may send
    question: str

class OutputState(TypedDict):       # what callers get back
    answer: str

class OverallState(TypedDict):      # everything the graph tracks
    question: str
    answer: str

class PrivateState(TypedDict):      # only passed between two nodes
    scratch: str

def think(state: InputState) -> PrivateState:
    return {"scratch": state["question"].upper()}

def reply(state: PrivateState) -> OutputState:
    return {"answer": state["scratch"] + "!"}

builder = StateGraph(OverallState, input_schema=InputState, output_schema=OutputState)
builder.add_node("think", think)
builder.add_node("reply", reply)
builder.add_edge(START, "think")
builder.add_edge("think", "reply")
builder.add_edge("reply", END)
graph = builder.compile()

print(graph.invoke({"question": "hi"}))   # {'answer': 'HI!'}

The caller sends a question and gets back only {'answer': 'HI!'}. The scratch key isn't in OverallState at all: LangGraph learns about it from the type hints on think and reply, so it works as a private hand-off between those two nodes and never appears in the result.

Keeping state small

State is copied, merged, and (with a checkpointer) saved after every superstep. The more you put in it, the slower and harder to debug your graph becomes. Some guidelines:

Put in stateKeep out of state
Data that changes during the run and that later nodes or routing functions need (messages, route, attempts)Things that never change: model objects, API clients, tool lists, config. Create them once at module level, like model_llm in the course
Small, serialisable values: strings, numbers, lists, dicts, messagesOpen files, database connections, locks: a checkpointer can't save them
IDs or short summaries of large dataWhole documents or images; store them elsewhere and keep a reference
Facts the model produced that you'll reuseValues you can recompute cheaply from other keys

The course already follows one of these rules. In graphs 8 and 9 the system message is a module-level constant added on each model call. It's never written to messages, so it doesn't pile up in the history every turn (FACTS finding 4; step 15 also moves it to the front).

Pitfalls
  • Returning a bare value instead of a dict: return "hello" in a TypedDict graph. Return {"graph_str": "hello"}. (Graph 0 is the exception: its whole state is a string.)
  • Returning a string for an append key: {"log": "ran"} with operator.add fails with TypeError: can only concatenate list (not "str") to list (verified). Return {"log": ["ran"]}.
  • Returning the whole state from a node. In a MessagesState graph it happens to look fine, because old messages keep their ids and are matched rather than duplicated (verified). With an operator.add key, the old entries are appended a second time.
  • Mutating the state in place (state["messages"].append(...)) and returning nothing. In a quick test the change even leaked through (verified), which makes it tempting. But it skips the reducer, doesn't show up as that node's update in streams or checkpoints, and breaks as soon as nodes run in parallel. Always return an update.
  • Reading an optional key with state["key"]. Use state.get("key", default).
Common misconceptions
  • "TypedDict checks my types." Only your editor does. At run time it's a plain dict.
  • "The node's return value becomes the new state." It's merged into the state, key by key.
  • "Reducers run when I read a key." They run when an update is written.
  • "MessagesState is special magic." It's a TypedDict with one key and the add_messages reducer. You can write the same class yourself, as the lesson file does.
Recap
  • A state schema declares the keys; LangGraph keeps one slot per key and merges each node's partial update.
  • TypedDict, Pydantic and dataclass schemas all work; Pydantic validates input, the others don't. Nodes always return dicts.
  • Default merge is overwrite. Annotated[list, operator.add] appends; add_messages appends, replaces by id and removes with RemoveMessage; any (old, new) -> merged function can be a reducer.
  • input_schema and output_schema define a public contract; keys only declared in node type hints stay private.
  • Keep state small and serialisable: put constants and clients at module level.
