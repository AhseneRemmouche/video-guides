Streaming, Debugging & LangGraph Studio

Stream modes, reading errors, LangSmith tracing and the Studio UI.

So far you have mostly called graph.invoke(...) and looked at the final result. That is fine while everything works. When something goes wrong, or when a user is waiting for a slow model, you want to see inside the run. This chapter covers the three ways to do that: streaming (getting results step by step, or token by token), reading error messages and tracebacks calmly, and the two visual tools from the video, LangSmith tracing and LangGraph Studio.

Why this matters for your project. In the video the presenter debugged mostly by running graphs in Studio and reading the terminal (for example the GraphLoadError at around 112:18). Step 19 added stream_mode="updates" and "values". Here you get the full picture: every stream mode that exists in LangGraph 1.2.11, the real errors this course produced and what each one means, and a tour of the Studio screen.

invoke vs stream

invoke runs the whole graph and gives you one thing at the end: the final state. stream runs the same graph but hands you pieces while it runs. You loop over it with for. Nothing else changes: same input, same config, same nodes.

The stream modes in LangGraph 1.2.11

The stream_mode argument chooses what each chunk contains. In the installed version, typing.get_args(langgraph.types.StreamMode) lists seven modes. All outputs below are real, from graph 2's shape (two nodes that each add a word) unless noted.

ModeEach chunk isReal exampleUse it for
"values"the full state after each step (input first){'graph_str': 'hi'}, {'graph_str': 'hi one'}, {'graph_str': 'hi one two'}showing the current state; this is what invoke uses internally
"updates"only what each node returned, keyed by node name{'node1': {'graph_str': 'hi one'}} then {'node2': {...}}progress ("tools finished"), logging; step 19's agent printout
"messages"a pair (message_chunk, metadata) for every token a chat model producesAIMessageChunk 'Rayleigh', ' ', 'scattering'... with metadata["langgraph_node"] == 'chat'typing-effect chat UIs

The two you will use most are "updates" and "messages". This is the agent loop from step 19, unchanged:

agent = load("8_graph_agent.py").graph
for chunk in agent.stream({"messages": [HumanMessage(content="What is 12 multiplied by 7?")]},
                          stream_mode="updates"):
    for node, update in chunk.items():
        last = update["messages"][-1]
        print(f"[{node}] {type(last).__name__}: {last.content or last.tool_calls}")

# [chat_with_tools] AIMessage: [tool call multiply 12, 7]
# [tools] ToolMessage: 84
# [chat_with_tools] AIMessage: ...

Token streaming with "messages"

A model can take several seconds to write an answer. With stream_mode="messages" your UI can show the words as they arrive. The surprising part: you do not have to change your node. Graph 4's node calls model.invoke(...), not model.stream(...), and LangGraph still captures the tokens. Verified with a fake model that streams word by word:

for chunk, metadata in graph.stream({"messages": [HumanMessage(content="why?")]},
                                    stream_mode="messages"):
    print(type(chunk).__name__, repr(chunk.content), metadata["langgraph_node"])

# AIMessageChunk 'Rayleigh' chat
# AIMessageChunk ' ' chat
# AIMessageChunk 'scattering' chat
# ...

Use metadata["langgraph_node"] to filter: in an agent you may only want tokens from chat_with_tools, not from some helper node that also calls a model. With the real ChatOpenAI the chunks are whatever pieces OpenAI sends, usually a word or part of a word.

Your own progress messages with "custom"

from langgraph.config import get_stream_writer


def node1(state: State):
    writer = get_stream_writer()
    writer({"progress": "node1 started"})
    return {"graph_str": state["graph_str"] + " one"}

for chunk in graph.stream({"graph_str": "hi"}, stream_mode="custom"):
    print(chunk)                    # {'progress': 'node1 started'}

Several modes at once

Pass a list and every chunk becomes a pair (mode, chunk). Verified output for stream_mode=["updates", "custom"]:

custom {'progress': 'node1 started'}
updates {'node1': {'graph_str': 'hi one'}}
updates {'node2': {'graph_str': 'hi one two'}}

If your graph contains subgraphs (chapter 10), add subgraphs=True to also receive their inner steps; each chunk then starts with a "namespace" tuple saying which subgraph it came from. LangGraph 1.2.11 also accepts version="v2", which turns every chunk into one dictionary shape, {'type': 'updates', 'ns': (), 'data': {...}}; check the streaming docs for whether it has become the default when you read this.

Reading errors without panic

A Python traceback is printed oldest call first, newest last. The most useful line is almost always the last one: the exception type and its message. Above it, look for the first line that points into your file (module1/...) rather than into site-packages (library code). LangGraph errors often end with a "For troubleshooting, visit:" link to a docs page about exactly that error.

The error that does not appear. If a node returns a key that is not in the state, for example {"grph_str": "x"} (typo) in a graph whose state has graph_str, LangGraph 1.2.11 raises nothing: the verified run simply returned the old state unchanged. When a value "does not update", check the spelling of the key first. Tests (step 18) catch this kind of silent bug.
New to debugging? A five-step routine that works for graphs
  1. Reproduce with the smallest input that fails. Write it down.
  2. Read the last line of the traceback, then find your own file in it.
  3. Watch the steps: run the same input with stream_mode="updates" and print each chunk. You will see which node produced the wrong value.
  4. Look at the shape: print(graph.get_graph().draw_mermaid()) (step 19) and paste it into mermaid.live. Missing or extra arrows are wiring bugs.
  5. Remove the model: replace it with a fake model (step 18). If the bug remains, it is in your graph; if it disappears, it is about the model's answers.

LangSmith tracing

A trace is a recording of one run: every node, every model call with its exact input messages and output, every tool call, how long each took and how many tokens were used. LangSmith is LangChain's hosted service that stores and displays traces. In the setup chapter the presenter created a LangSmith key and ran the quickstart in main.py to see the first trace (step 4).

Tracing needs no code changes. LangChain and LangGraph read environment variables, which the course keeps in .env:

LANGSMITH_API_KEY="lsv2_pt_..."     # never commit the real key
LANGSMITH_TRACING=true              # current docs name; the repo's LANGSMITH_TRACING_V2=true also works
LANGSMITH_PROJECT="LangGraph_ACL"   # traces are grouped by project

The repo's .env.example uses LANGSMITH_TRACING_V2=true. That was verified to work: the langsmith package accepts TRACING_V2 or TRACING with either the LANGSMITH_ or the older LANGCHAIN_ prefix. New projects should use the name in the current docs, LANGSMITH_TRACING. Remember that in plain Python the variables only exist after load_dotenv() ran, while langgraph dev loads .env itself ("env": ".env" in langgraph.json).

Privacy note. Traces contain the full text of prompts, user messages and tool results. Before tracing real user data, check what your organisation allows, and consider separate projects for development and production.

A tour of LangGraph Studio

Studio is a web page (served from smith.langchain.com/studio, so it needs a LangSmith account) that connects to the langgraph dev server running on your computer at http://127.0.0.1:2024. It reads the graphs listed in langgraph.json, draws them, and lets you run them. Here are the parts you see in the video:

PartWhat it does
Graph picker (Studio / 8_graph)switches between the graph ids from langgraph.json
Graph | ChatGraph mode shows the drawing and full state; Chat mode is a simpler chat window for messages graphs
ConnectedStudio can reach your local server. If it says otherwise, check that langgraph dev is still running
Input, View Raw, Submita form built from your state schema; View Raw switches to a JSON editor; Submit starts a run on the current thread
Thread, New Threadeach thread is one saved conversation (the server persists it); New Thread starts with an empty state, which the presenter does several times to get "a fresh memory" (around 81:28)

Deploystarts a deployment to LangSmith's hosted platform (chapter 9); needs an account plan that includes it

Two server behaviours make Studio pleasant to work with. First, langgraph dev hot-reloads: when you save a Python file, the log prints "changes detected" and Studio picks up the new code (visible in the video's terminal at 135:20). Second, errors in your graph files appear in the terminal, not in Studio. If a graph is missing from the picker, look at the terminal for a GraphLoadError.

Windows note: harmless UnicodeEncodeError lines. On Windows, the langgraph dev log may print UnicodeEncodeError messages because the console's default encoding cannot represent some characters in the log output. The server keeps working. To get a clean log, set Python's output encoding to UTF-8 before starting it. In PowerShell: $env:PYTHONIOENCODING="utf-8" then uv run langgraph dev.
Common misconceptions
  • "Streaming makes the graph faster." The total time is the same; the user just sees progress sooner.
  • "To stream tokens I must call model.stream in my node." Not with LangGraph: stream_mode="messages" captures tokens even from model.invoke.
  • "Studio runs my code in the cloud." Your code runs on your computer in langgraph dev; the Studio page is only the window onto it.
  • "No error means it worked." A misspelled state key is silently ignored. Check the state after each step.
  • "Tracing is on because I created a LangSmith key." You also need the tracing variable set, and in plain Python load_dotenv() must run first.
Recap
  • stream = invoke that hands you chunks. Modes in 1.2.11: values, updates, messages, custom, debug, tasks, checkpoints.
  • "updates" for progress, "messages" for token-by-token text, "custom" + get_stream_writer() for your own events; lists give (mode, chunk) pairs.
  • Read tracebacks bottom-up: message, your file, then library frames. Follow the "troubleshooting" link when there is one.
  • A misspelled state key raises no error; test and inspect state.
  • LangSmith tracing = API key + LANGSMITH_TRACING=true (the repo's LANGSMITH_TRACING_V2 also works) + optional project name.
  • Studio: graph picker, Graph/Chat, Input + Submit, threads, Memory, Interrupts, Interact/Trace; errors show in the terminal; on Windows set PYTHONIOENCODING=utf-8.
