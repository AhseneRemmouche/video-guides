Models Inside Graphs

Messages, prompts, tool binding, structured output and choosing a model per node.

What you will learn

Graphs 0–2 contain no AI at all. From graph 3 (step 9) on, a chat model appears inside a node, and by graph 8 the whole graph revolves around it. This chapter explains how models fit into a graph: what goes in and comes out, where the prompt belongs, how tools are attached, how to get answers you can route on reliably, and how to protect a node against slow or failing API calls.

  • a model call is just code inside a node;
  • the four message types, and the order the model should see them in;
  • bind_tools, tool_calls and how ToolNode answers them;
  • with_structured_output for routing decisions you can trust;
  • a different model per node;
  • retries and timeouts: on the model client, and on the node with RetryPolicy.
Why this matters for your project. Graph 3 routes on the model's free-text reply and crashes with ValueError when the model writes "Two" instead of "2" (FACTS finding 2). Graphs 8 and 9 put the system message last. Graph 5 asks for a tool that never runs. Each of these is a "model inside a graph" question, and this chapter gives the general rule behind each fix in step 15.

A model call is just code in a node

LangGraph has no special "LLM node". A node is a Python function; if that function calls a model, it's a model node. Graph 4 (step 10) is the cleanest example:

model_llm = ChatOpenAI(model="gpt-4o")

# nodes
def chat(state: MessagesState) -> MessagesState:
    return {"messages": [model_llm.invoke(state["messages"])]}

Three things to notice:

  1. The model object is created once, at module level, not inside the node. Creating it per call would work, but it's wasted effort, and the model isn't data that belongs in the state (chapter 2).
  2. Messages go in, one message comes out. model_llm.invoke(list_of_messages) returns a single AIMessage.
  3. The node returns an update, {"messages": [reply]}. The add_messages reducer appends the reply to the conversation.

The model name, gpt-4o in the course, is only an example at the time of writing. You can swap in any chat model LangChain supports; the graph doesn't care, as long as the node returns the same kind of update.

Messages: the model's input format

Chat models don't take one string; they take a list of messages, each with a role. LangChain has a class for each role, importable from langchain.messages (as in graphs 8 and 9):

ClassRoleWho creates itKey fields
SystemMessageInstructions: who the model is, rules to followYou, in codecontent
HumanMessageWhat the user saidThe caller (input to invoke, or Studio)content
AIMessageThe model's replyThe modelcontent, tool_calls
ToolMessageA tool's resultToolNode (or your own tool node)content, tool_call_id

Every message also gets an id, which add_messages uses to append or replace (chapter 2). The model behind it (an LLM) is stateless: it remembers nothing between calls. Every call must include the whole conversation it should know about. That's why graphs keep the history in messages, and why graph 9 needs a checkpointer to remember earlier turns.

Prompts as system messages, and why order matters

A prompt that sets the model's role is sent as a SystemMessage. The convention, followed by model providers and the LangChain docs, is to put it first, before the conversation. Graph 8 in the repo does it the other way around:

system_message = SystemMessage(content="you are a helpful Math teach")

# nodes
def chat_with_tools(state: MessagesState) -> MessagesState:
    return {"messages": [model_llm_with_tools.invoke(state["messages"] + [system_message])]}

It works, but the instruction arrives after the user's question, as the last thing the model reads. The fixed version from step 15 puts it first:

system_message = SystemMessage(content="You are a helpful math teacher. Use the tools for every calculation.")

# nodes
def chat_with_tools(state: MessagesState) -> MessagesState:
    # the system message goes first: it sets the role before the conversation starts
    return {"messages": [model_llm_with_tools.invoke([system_message] + state["messages"])]}

Here's the pattern as a small, complete graph you can run without an API key. GenericFakeChatModel from langchain_core replays the replies you give it, so the graph logic can be tested for free:

from langchain_core.language_models.fake_chat_models import GenericFakeChatModel
from langchain.messages import SystemMessage, HumanMessage, AIMessage
from langgraph.graph import StateGraph, START, END, MessagesState
from langgraph.types import RetryPolicy

# a fake model that always gives this reply: no API key needed
model = GenericFakeChatModel(messages=iter([AIMessage("Paris.")]))
system_message = SystemMessage("You are a concise geography tutor.")

def chat(state: MessagesState) -> dict:
    reply = model.invoke([system_message] + state["messages"])   # system first
    return {"messages": [reply]}

builder = StateGraph(MessagesState)
builder.add_node("chat", chat, retry_policy=RetryPolicy(max_attempts=3))
builder.add_edge(START, "chat")
builder.add_edge("chat", END)
graph = builder.compile()

result = graph.invoke({"messages": [HumanMessage("Capital of France?")]})
for m in result["messages"]:
    print(type(m).__name__, "|", m.content)

It prints HumanMessage | Capital of France? then AIMessage | Paris.: the system message was sent to the model but isn't in the result. To use a real model, replace the fake with ChatOpenAI(model="gpt-4o"). The retry_policy argument is explained at the end of this chapter. For a fuller fake model that also calls tools, see step 18.

Tools: bind_tools and tool_calls

A tool is a Python function the model may ask you to run. The @tool decorator (from langchain.tools) turns a function into a tool object with a name, a description (from the docstring) and an argument schema (from the type hints). bind_tools attaches those schemas to every request the model makes:

@tool
def multiply(nb1: int, nb2: int) -> int:
    """This tool is used for multiplying 2 numbers and returning the product"""
    return nb1*nb2

model_llm_with_tool = model_llm.bind_tools([multiply])

bind_tools returns a new model object; model_llm itself is unchanged. That's why the course keeps both names. When the bound model decides a tool would help, its AIMessage has empty (or short) content and a tool_calls list. With LangChain 1.3.18 a tool call looks like this (verified):

[{'name': 'multiply', 'args': {'nb1': 12, 'nb2': 7}, 'id': 'call_1', 'type': 'tool_call'}]

The model never runs the tool. It only asks. Something in your graph must run it and reply with a ToolMessage whose tool_call_id matches the request's id. In graph 5 (step 11) nothing does, so the run ends with the request unanswered. Graph 6 adds a ToolNode and the tools_condition router; graph 8 loops back so the model can use the result.

Structured output for routing

Graph 3 asks the model "choose between 1 or 3 or 2. reply only with a number", then does int(model_response.content). If the model replies "Two" or "2.", int() raises ValueError and the run crashes (verified). Free text is meant for humans; code needs a guaranteed shape.

with_structured_output(Schema) solves this. You describe the answer you want as a Pydantic class; the returned runnable gives you an instance of that class, already parsed and validated, instead of an AIMessage. That's ideal for a router node: the model decides, the node stores the decision, and an ordinary conditional edge reads it.

from typing import Literal
from pydantic import BaseModel, Field
from langchain_openai import ChatOpenAI
from langchain.messages import SystemMessage, HumanMessage, AIMessage
from langgraph.graph import StateGraph, START, END, MessagesState

class Route(BaseModel):
    """Where to send the user's message."""
    destination: Literal["math", "chitchat"] = Field(description="math for any calculation")

router_model = ChatOpenAI(model="gpt-4o", temperature=0).with_structured_output(Route)
answer_model = ChatOpenAI(model="gpt-4o")

class State(MessagesState):
    route: str

def classify(state: State) -> dict:
    decision = router_model.invoke(
        [SystemMessage("Classify the user's last message.")] + state["messages"])
    return {"route": decision.destination}          # a Route object, not text

def pick(state: State) -> Literal["math", "chitchat"]:
    return state["route"]

def math(state: State) -> dict:
    return {"messages": [answer_model.invoke(
        [SystemMessage("You are a careful math tutor.")] + state["messages"])]}

def chitchat(state: State) -> dict:
    return {"messages": [AIMessage("Happy to chat! Ask me a math question any time.")]}

builder = StateGraph(State)
builder.add_node("classify", classify)
builder.add_node("math", math)
builder.add_node("chitchat", chitchat)
builder.add_edge(START, "classify")
builder.add_conditional_edges("classify", pick)
builder.add_edge("math", END)
builder.add_edge("chitchat", END)
graph = builder.compile()

This needs an OpenAI key to run for real. We ran this exact file with a fake model substituted for ChatOpenAI: "what is 12 times 7?" was routed to math, "hi there!" to chitchat, and get_graph() shows classify with dashed edges to both. That proves the wiring and the Route object, not how a real model classifies.

New to structured output? What happens under the hood

with_structured_output turns your Pydantic class into a JSON schema and asks the provider to return data matching it, using the provider's native structured-output feature or tool calling, depending on the model and the method argument. LangChain then parses the reply into your class. If the model's answer doesn't match, parsing fails with an error rather than silently passing bad data on. Combined with a RetryPolicy on the node, an occasional bad answer can simply be retried.

A different model per node

Each node is independent code, so each can use a different model, or the same model with different settings. Common reasons:

  • Routing and grading are short, constrained tasks; a smaller, faster model with temperature=0 is often enough.
  • Writing the final answer may deserve a larger model.
  • Different providers for different jobs: LangChain's init_chat_model("provider:model-name") (in langchain.chat_models) creates a chat model from a string, so a node's model can come from configuration.
from langchain_openai import ChatOpenAI

router_model = ChatOpenAI(model="gpt-4o-mini", temperature=0)   # small and steady
writer_model = ChatOpenAI(model="gpt-4o", temperature=0.7)      # more capable, more varied

Model names here are examples at the time of writing; check your provider's current list. Bind tools only on the models that need them: in graph 8, only the chat node's model is bound.

Retries and timeouts

Model calls go over the network. They can be slow, hit a rate limit, or fail with a server error. You can protect a node at two levels.

On the model client

ChatOpenAI accepts timeout (seconds; stored as request_timeout) and max_retries (verified in langchain-openai 1.6.0): ChatOpenAI(model="gpt-4o", timeout=30, max_retries=2). These retry the HTTP request itself inside the OpenAI client.

On the node: RetryPolicy

add_node takes a retry_policy= argument with a RetryPolicy from langgraph.types. If the node raises, LangGraph waits and runs the whole node again. The defaults in 1.2.11 (printed from the class): max_attempts=3, initial_interval=0.5 seconds, backoff_factor=2.0 (each wait doubles), max_interval=128.0, jitter=True (adds a little randomness so many clients don't retry at the same moment).

Which errors are retried is decided by retry_on. The default function retries ConnectionError and HTTP 5xx errors, does not retry programming errors (ValueError, TypeError, KeyError and similar, which would just fail again), and retries most other exceptions. We tested a node that raised ConnectionError twice: with RetryPolicy(max_attempts=3) it succeeded on the third attempt; without a policy the first error ended the run.

from langgraph.types import RetryPolicy

builder.add_node(
    "chat_with_tools",
    chat_with_tools,
    retry_policy=RetryPolicy(max_attempts=4, initial_interval=1.0),
)

Node timeouts

LangGraph 1.2.11 also gives add_node a timeout= argument (seconds, a timedelta, or a TimeoutPolicy). It only works on async nodes (async def). On a normal function, compile() itself fails with ValueError: Node timeouts are only supported for async nodes because sync Python execution cannot be safely cancelled in-process. On an async node that runs too long, the run raises NodeTimeoutError (both verified). The course's nodes are all synchronous, so for them the client timeout is the practical choice.

Pitfalls
  • Creating the model inside the node on every call, or storing it in state. Create it once at module level.
  • Putting the system message last, or saving it into messages each turn, so it piles up in the history.
  • Calling the unbound model in a tool graph. Only the object returned by bind_tools knows about the tools.
  • Naming the tool node anything but "tools" while using tools_condition.
  • Parsing free text with int() or string checks to make a routing decision. Use structured output.
  • Retrying a node whose model call has side effects (sending an email) without making the action safe to repeat.
Common misconceptions
  • "The model remembers the conversation." It's stateless; the graph sends the history on every call.
  • "bind_tools runs the tools." It only describes them to the model. ToolNode runs them.
  • "Structured output means the model can't be wrong." The shape is guaranteed; the decision can still be a poor one.
  • "Retries fix everything." They help with network blips and server errors, not with wrong code or a bad prompt.
Recap
  • A model node is a normal function: messages in, one AIMessage out, returned as {"messages": [reply]}.
  • Four message types: System (instructions, first), Human, AI (may contain tool_calls), Tool (answers a call by tool_call_id).
  • bind_tools returns a new model that may request tools; your graph runs them with ToolNode and loops back.
  • with_structured_output(Schema) returns validated objects: the safe way to route on a model's decision.
  • Each node can use its own model and settings.
  • Protect model calls with client timeout/max_retries and node RetryPolicy; node timeout= needs async nodes.
