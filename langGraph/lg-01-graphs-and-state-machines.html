Graphs & State Machines

Where the graph idea comes from, directed graphs, cycles, and why workflows map onto them.

Graphs in computer science

In everyday English a "graph" is often a chart with axes. In computer science it means something else: a set of things and the connections between them. The things are called vertices or nodes. The connections are called edges. That's all a graph is.

The presenter's analogy (at 20:05) is Google Maps: cities are nodes and roads are edges. Graphs show up everywhere once you look: people and friendships in a social network, web pages and links, tasks and "must happen before" rules in a build tool, and in LangGraph, steps of work and what runs next.

New to graph vocabulary? The five words you will meet
  • Node (or vertex): one item. In LangGraph, one function that does work.
  • Edge: a connection between two nodes. In LangGraph, "after this node, run that one".
  • Path: a route that follows edges from one node to another, like START → node1 → node2 → END.
  • Cycle (or loop): a path that comes back to a node it already visited.
  • Entry / exit: where a run starts and stops. LangGraph names them START and END (START and END).

Directed graphs: edges with a direction

A road can be two-way. A friendship goes both ways too. Those are undirected edges. Other connections only go one way: a link from page A to page B doesn't create a link back. Those are directed edges, drawn as arrows. A graph whose edges are arrows is a directed graph.

LangGraph graphs are always directed. builder.add_edge("greeting", END) means "after greeting, go to END", and never the reverse. The arrow tells the engine which node to run next. If you want to go back, you add a second edge that points back, which is exactly what graph 8 does with builder.add_edge("tools", "chat_with_tools").

Cycles, DAGs and why loops matter

A directed graph with no cycles is called a DAG, a directed acyclic graph. Data pipelines, build systems and spreadsheet formulas are DAGs: work flows from the start to the end and never revisits a step. A DAG always finishes, because every path is finite.

A graph with a cycle can revisit a node. That's what an agent needs: call the model, run a tool, call the model again, maybe run another tool, and only then answer. Nobody knows ahead of time how many rounds it will take. LangGraph was built so that cycles are normal, not an error. The cost: a cyclic graph needs a stopping rule, or it could go around forever.

State machines

A state machine (or finite-state machine) is a very old idea from computer science and engineering. It has three parts:

  1. States: a fixed list of situations the system can be in, such as placed, paid, shipped.
  2. Events: things that happen, such as "payment received".
  3. Transitions: rules of the form "in state X, when event E happens, move to state Y".

The machine is always in exactly one state. Traffic lights, vending machines, login flows and order tracking are all state machines. Here is one in plain Python, no library at all:

# A tiny state machine in plain Python: an online order
transitions = {
    ("placed", "pay"): "paid",
    ("paid", "ship"): "shipped",
    ("shipped", "deliver"): "delivered",
    ("placed", "cancel"): "cancelled",
    ("paid", "cancel"): "cancelled",
}

state = "placed"
for event in ["pay", "ship", "deliver"]:
    state = transitions[(state, event)]
    print(event, "->", state)

It prints pay -> paid, ship -> shipped, deliver -> delivered. Asking for a transition that isn't in the table (say ("delivered", "pay")) raises a KeyError: the machine refuses moves it doesn't know. That's the appeal of state machines: every allowed move is written down.

How LangGraph uses the word "state"

Here's a point that confuses many beginners. In a classic state machine, "the state" is which box you are in (paid). In LangGraph, "the state" is the data that travels through the graph: the string in graph 0, the {"graph_str": ...} dict in graph 1, the list of messages in graph 4. Which box you are in is simply "which node is running". The presenter's analogy (step 5): the graph is the road network, and the state is a car driving along it, picking up and dropping cargo.

So a LangGraph graph is a state machine whose boxes do work, plus a bag of data that every box can read and update. The engine that runs it is described below.

Why agent workflows fit graphs

Before LangGraph, many LLM apps were built as chains: step A, then B, then C, a straight line. A chain is the simplest DAG. It works well until you need any of these, which real AI apps soon do:

  • Decisions: "if the user's message starts with hello, go to node 2" (graph 2), or "if the model asked for a tool, run it" (graph 6).
  • Loops: "keep calling the model and tools until the model answers" (graph 8), or "redraft until the reviewer approves".
  • Parallel work: search two sources at the same time, then combine.
  • Pauses and memory: save progress after every step so a run can be resumed, inspected, or continued later (graph 9 and chapter 6).

A graph handles all four with the same two building blocks. A decision is a conditional edge. A loop is an edge that points back. Parallel work is two edges leaving the same node. Pauses are possible because the engine stops between steps anyway. The presenter makes the same point at 55:25 about graph 2: "The edges do not touch the logic of the state. It guides the state." Nodes do the work; edges only decide where to go.

How LangGraph runs a graph: supersteps

When you call graph.invoke(...), LangGraph doesn't simply call your functions one after another in a Python loop. The compiled graph is an instance of a class called Pregel (we checked: CompiledStateGraph inherits from langgraph.pregel.main.Pregel in 1.2.11). The name comes from Pregel, a system Google described for processing very large graphs. It runs in rounds called supersteps, following a model known as Bulk Synchronous Parallel. The docstring of the class in the installed package says each step has three phases. In plain words:

  1. Plan. Decide which nodes run in this step. In the first step, that's the node(s) connected to START. Later, it's the nodes that edges point to from the nodes that just finished.
  2. Execute. Run all the chosen nodes, in parallel if there are several. Each node sees the state as it was at the start of the step; it can't see what the other nodes in the same step are writing.
  3. Update. Apply all the updates the nodes returned to the state. If two nodes wrote to the same key, the key's reducer decides how to combine them (chapter 2).

Repeat until no node is scheduled (the run reached END) or the step counter hits the recursion limit. Each round is one superstep. Internally the engine stores each state key in a channel, and nodes "subscribe" to channels. You don't need those words to use LangGraph, but they explain error messages you will see later.

You can watch the steps happen. This graph has a fork: after plan, two search nodes run, and write waits for both. The "debug" stream mode reports each task with its step number:

import operator
from typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    visited: Annotated[list[str], operator.add]

def make(name):
    def node(state: State) -> dict:
        return {"visited": [name]}
    return node

builder = StateGraph(State)
for name in ["plan", "search_web", "search_docs", "write"]:
    builder.add_node(name, make(name))
builder.add_edge(START, "plan")
builder.add_edge("plan", "search_web")      # fan-out: two edges leave "plan"
builder.add_edge("plan", "search_docs")
builder.add_edge(["search_web", "search_docs"], "write")  # fan-in: wait for both
builder.add_edge("write", END)
graph = builder.compile()

for event in graph.stream({"visited": []}, stream_mode="debug"):
    if event["type"] == "task":
        print("step", event["step"], "->", event["payload"]["name"])

Output with LangGraph 1.2.11:

step 1 -> plan
step 2 -> search_docs
step 2 -> search_web
step 3 -> write

Three consequences follow, and you will meet each one later:

  • Order inside a step is not something to rely on. Above, search_docs was listed before search_web. Nodes in the same step are independent; don't write code that assumes one runs first.
  • Two parallel writes to a plain key fail. If both searches returned {"result": ...} and result had no reducer, LangGraph raises InvalidUpdateError: At key 'result': Can receive only one value per step (verified, see chapter 3).
  • Steps are natural save points. A checkpointer saves the state after each superstep. That's how graph 9 remembers, and how a paused run can resume (chapter 6, chapter 7).

For the course graphs, most steps run a single node: graph 2 is node1 in step 1, then node2 or node3 in step 2. The How State Flows page traces those steps one by one.

What compile() does

StateGraph is a builder: a description you fill in with nodes and edges. It can't run. Compiling turns that description into something that can. You saw it at the end of every course file: graph = builder.compile().

from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    text: str

def shout(state: State) -> dict:
    return {"text": state["text"].upper()}

builder = StateGraph(State)          # 1. describe the graph
builder.add_node("shout", shout)
builder.add_edge(START, "shout")
builder.add_edge("shout", END)

graph = builder.compile()            # 2. check it and turn it into a runnable
print(type(graph).__name__)          # CompiledStateGraph
print(graph.invoke({"text": "hi"}))  # 3. run it: {'text': 'HI'}

compile() does three jobs:

  1. Checks the structure. Missing entry point: ValueError: Graph must have an entrypoint: add at least one edge from START to another node. An edge to a node that doesn't exist: ValueError: Found edge ending at unknown node `b`. Both verified. The second is the error the presenter hit with graph 6 (step 12), when tools_condition was passed to add_edge by mistake.
  2. Builds the runtime. It wires nodes to channels and returns a CompiledStateGraph, which is a Pregel object and a LangChain Runnable. That's why it has the same methods as a model: invoke, stream, batch, and their async versions.
  3. Attaches run-time options. compile() accepts keyword arguments such as checkpointer= (memory, graph 9), interrupt_before= / interrupt_after= (pause before or after a node), store=, cache= and name=. Graph 9 uses the first: builder.compile(checkpointer=memory).

One more useful method: graph.get_graph() returns the drawable shape. graph.get_graph().draw_mermaid() prints a Mermaid diagram you can paste into a viewer (step 19). LangGraph Studio draws the same picture with dashed arrows for conditional edges, as in the presenter's graph 2 at around 1:01:40.

Pitfalls
  • Calling builder.invoke(...). The builder has no invoke; compile first and call the result.
  • Forgetting add_edge(START, ...). compile() refuses a graph without an entry point.
  • Passing the function instead of its name to add_edge: add_edge(START, greeting). The course shows the resulting TypeError in step 6. Edges take node names (strings).
  • Building a loop with no exit. Every cycle needs a conditional edge that can reach END.
Common misconceptions
  • "State means the current node." In LangGraph, state is the shared data. The current node is just where the run is.
  • "Graphs are only for agents." Graphs 0–2 have no model at all. A graph is a way to organise any multi-step code.
  • "Nodes in a step run one after another." Nodes scheduled in the same superstep run in parallel and see the same starting state.
  • "Edges transform data." Edges only choose what runs next. Changes to the data happen in nodes.
Recap
  • A graph is nodes plus edges. LangGraph edges are directed: arrows that say what runs next.
  • A DAG has no cycles and always finishes. A cyclic graph (graph 8) can loop, so it needs a stopping rule.
  • A state machine lists states and allowed transitions. LangGraph keeps the "boxes and arrows" idea, but "state" means the shared data.
  • Graphs fit AI workflows because decisions, loops, parallel work and pauses are all just edges.
  • LangGraph runs in supersteps: plan which nodes run, execute them (in parallel), apply their updates. Repeat until END.
  • compile() checks the structure, builds a Pregel runnable and attaches options like a checkpointer.
