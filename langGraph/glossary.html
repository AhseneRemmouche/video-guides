Glossary

Every technical term in this guide, explained for beginners.

Every technical word used in this guide, explained in plain language. Pages link here the first time a term appears, so you can always come back. Terms are grouped by topic. Most entries say where the idea first shows up in the course and link to that step. Some also point to a handbook chapter that goes deeper.

Two maps to start with

Before the individual words, here is how they fit together. The first map shows where each piece of the project lives. The second shows how LangGraph's building blocks connect, from the state class you write to the finished graph you run.

Tools & the command line

Terminal (command line)
A text window where you type commands instead of clicking. In VS Code, open it with Ctrl+`. The presenter works on Windows in PowerShell. Lines in this guide such as uv sync or langgraph dev are typed there and run with Enter. First used in step 04.
VS Code (Visual Studio Code)
A free code editor from Microsoft, used by the presenter throughout the video. It has a file explorer on the left, editor tabs in the middle and a built-in terminal at the bottom. Its "PROBLEMS" panel shows mistakes before you run the code: in step 14 it underlines HumanMessage in red because graph 9 never imports it.
pip
Python's standard package installer. pip install X downloads package X from PyPI (the Python Package Index). The presenter checks it with pip --version during setup, but this project adds its packages with uv instead. See step 04.
uv
A fast Python project and package manager. In this course it creates the project (uv init), the virtual environment (uv venv --python 3.12), adds packages (uv add langchain langchain-openai langgraph dotenv "langgraph-cli[inmem]") and records exact versions in uv.lock. Someone who clones the repo runs uv sync to get the same packages. See step 04.
Virtual environment (.venv)
A private folder of Python packages for one project, so different projects don't fight over versions. uv creates it as .venv in the project folder. On Windows you switch it on with .venv\Scripts\activate; the prompt then shows the environment's name. If langgraph dev says "command not found", the environment is usually not active. See step 04.
Package
A bundle of someone else's code that you install and import, for example langgraph (graphs), langchain-openai (the OpenAI chat model) or python-dotenv (reads .env). Packages are downloaded from PyPI. See step 04.
Dependency
A package your project needs in order to run. This project's dependencies are listed in pyproject.toml. Packages your dependencies need in turn (for example langgraph-api, pulled in by langgraph-cli[inmem]) are installed automatically and pinned in the lockfile. See step 04 and step 15.
pyproject.toml
The project's settings file: its name, the Python version it needs and its dependencies. uv add writes to it for you. The repo's copy has a small typo, langgraph-cli[inemem,inmem], which causes the "does not have an extra" warnings the presenter sees around 17:16. It also lists colorama, which no file uses. Step 15 cleans this up.
Lockfile (uv.lock)
A file that records the exact version of every package that was installed, including indirect ones. With it, everyone who runs uv sync gets identical versions. This guide was verified against the repo's lockfile: langgraph 1.2.11, langchain 1.3.18, langchain-openai 1.6.0. See step 04.
.env file (environment variables)
A plain text file of NAME=value lines that holds secrets such as OPENAI_API_KEY. Code reads it with from dotenv import load_dotenv; load_dotenv(). langgraph dev reads it on its own because langgraph.json says "env": ".env". That's why graph 4 works in Studio but fails as a plain Python script: it never calls load_dotenv(). The repo ships a safe template, .env.example, with empty values. See step 04 and step 15.
API key
A long secret string that proves to a service (OpenAI, LangSmith, Tavily) that a request comes from your account, so it can bill you or log your traces. Treat it like a password: keep it in .env, never in code, never in a screenshot. LangSmith keys start with lsv2_pt_. Without an OpenAI key, creating ChatOpenAI fails with openai.OpenAIError: Missing credentials. See step 04.
.gitignore
A file listing paths Git should never track. The repo's copy lists .env (your keys) and .langgraph_api (the dev server's local data). It doesn't list __pycache__, so compiled .pyc files ended up in the repo. Step 15 adds the missing lines.
Git
A version-control tool: it records snapshots ("commits") of your files so you can go back and share them. The course repo, Mohamad-Hachem/LangGraph_ACL on GitHub, has two commits; this guide uses commit e42570d. See the home page.
JSON
A text format for data: objects in { } with "key": value pairs, lists in [ ], and strings always in double quotes. langgraph.json is written in JSON, and Studio's input panel expects JSON too. Typing {"Hel"} for graph 0 gives SyntaxError: Expected ':' after property name in JSON, because graph 0's state is a plain string, so the input must be a JSON string such as "Hello". See step 06.

Python

Python
The programming language of this whole course. The project uses Python 3.12 (pinned in .python-version); the presenter recommends 3.11 to 3.13. Check yours with python --version. See step 04.
import
The statement that brings code from a package or module into your file, for example from langgraph.graph import StateGraph, START, END. Use a name without importing it and Python stops with a NameError. That is exactly what happens in graph 9 with HumanMessage (step 14).
Module
One Python file seen from the outside. module1/2_graph_conditional_edge.py is a module. Its name starts with a digit, so you can't write import 2_graph_conditional_edge; that's why langgraph.json points at files by path ("./module1/2_graph_conditional_edge.py:graph") and the tests in step 18 load them with importlib. The folder module1 is just a folder of these files.
Function
A named, reusable block of code defined with def. It takes inputs (parameters) and gives back a result with return. In LangGraph every node is a function: def greeting(state): return state + "welcome to AI Career Lab!". See step 06.
Docstring
A string in triple quotes right under a def line that describes the function, such as """this tool return the multiplication of 2 numbers""". For normal functions it is just documentation. For a tool it matters a lot: @tool sends the docstring to the model as the tool's description, and the model uses it to decide when to call the tool. See step 11.
Type hint
A note about what type a value should be, written after a colon or arrow: def greeting(state: str) -> str. Python itself doesn't enforce hints, but LangGraph reads some of them: the class you pass to StateGraph(...) defines the state, and a Literal return hint on a routing function tells it which nodes can come next. See step 07.
Dictionary (dict)
Python's key-to-value container, written with braces: {"graph_str": "hello"}. You read a value with state["graph_str"]. From graph 1 on, the state is a dict, and nodes return a smaller dict containing only the keys they change. See step 07.
List
An ordered collection in square brackets: [multiply, addition, subtraction]. my_list[-1] is the last item, which is why answers are read with response["messages"][-1].content. Two lists join with +, as in state["messages"] + [system_message]. See step 10.
TypedDict
A way to describe the shape of a dictionary: which keys it has and what type each value is. class State(TypedDict): graph_str: str says the state has one key, graph_str, holding text. It is still an ordinary dict at run time. The course imports it from typing_extensions. See step 07; the handbook chapter Designing State compares it with Pydantic and dataclasses.
Literal
A type hint that lists the exact values allowed: Literal["node2", "node3"] means "one of these two strings". Graph 2's routing function uses it as its return type. LangGraph reads it to know where the conditional edge can lead, so the drawing in Studio shows both branches. Verified: without the hint, the drawn graph loses the branches. See step 08.
f-string
A string with an f in front that fills in values between braces: f"The result is {result}". The course's nodes glue text with + instead (state + "welcome to AI Career Lab!"), which is why graph 0's output has no space: hey am new!welcome to AI Career Lab!. Both ways work; f-strings are easier to read once there are several values.
Exception (error)
Python's way of saying "something went wrong, stop here". Each kind has a name: NameError (unknown name), TypeError (wrong kind of value), ValueError (right kind, bad value, such as int("Two")). You can catch one with try / except, which is how step 15 makes graph 3's number parsing safe.
Traceback
The block of text Python prints when an exception is not caught. Read it from the bottom: the last line names the error, and the lines above show the file and line number where it happened. In the video the most instructive one is the GraphLoadError from langgraph dev in step 12 ("Found edge ending at unknown node").

AI & models

LLM (large language model)
A model trained on huge amounts of text that predicts the next piece of text. You send it text, it sends text back. It has no memory between calls and can't run code or look things up by itself; that is what tools and graphs add. The course uses OpenAI's GPT-4o. See step 03.
Chat model
An LLM that takes a list of messages and returns one message. In code it is ChatOpenAI(model="gpt-4o") from langchain-openai, and you call it with model_llm.invoke(messages). Graph 3 is the first time a chat model sits inside a node. See step 09.
OpenAI
The company whose models answer in this course (GPT-4o in graphs 3 to 9; gpt-4.1 in the setup test main.py, models as named at the time of writing). You need an API key from its developer platform and a little prepaid credit. The presenter names their key "LangGraph_ACL". See step 04.
Token
The unit an LLM reads and writes: a word or a piece of a word. API usage is measured in tokens, so every message in the history costs something each time it is sent again. A long agent loop or a long memory thread sends more tokens per call.
Prompt
The text you give a model. In a chat model the prompt is the whole list of messages: the system message plus the conversation so far. In graph 3 the prompt asks the model to pick a number, and the graph routes on its answer. See step 09.
Message
One entry in a chat: a role plus content. LangChain has a class per role (the next four entries). A MessagesState graph keeps them in one list under the key "messages". See step 10.
SystemMessage
Standing instructions for the model, such as SystemMessage(content="you are a helpful Math teach") (the typo is in the repo). Graphs 8 and 9 add it on every model call but never store it in the state. They add it last; the usual convention is first, which step 15 switches to. See step 13.
HumanMessage
A message from the user: HumanMessage(content="Add 3 and 4."). In Studio, what you type in the input panel becomes a HumanMessage. Import it with from langchain.messages import HumanMessage; graph 9 forgets that import. See step 14.
AIMessage
A message from the model. Usually it holds text. When the model wants a tool, the AIMessage has empty text and a tool_calls list instead. See step 11.
ToolMessage
The result of running a tool, added to the messages so the model can read it. It carries a tool_call_id that matches the request it answers. In graph 6 the multiply tool's ToolMessage contains "20"; in graph 8's verified run it contains "84". See step 12.
Temperature
A model setting for randomness. Low values (like the temperature=0 in main.py) make answers more predictable; higher values make them more varied. Even so, an LLM is not a random number generator: in graph 3 the model kept answering "2" (around 81:05). See step 09.
Hallucination
When a model states something false with confidence, for example a wrong sum. Giving the model tools for exact work (the math tools in graph 8) reduces this: the number comes from your Python code, not from the model's guess. See step 13.
Prompt injection
An attack where text the model reads (a user message, a web page, a tool result) contains instructions such as "ignore your rules". The model can't reliably tell your instructions from someone else's text. Defences: give tools only the power they need, check tool arguments in code, and ask a human before risky actions. See the handbook chapter Testing, Deploying & Production.

LangGraph building blocks

LangChain
A Python library of building blocks for LLM apps: chat models (ChatOpenAI), messages, the @tool decorator and more. LangGraph is from the same company and uses these pieces inside its nodes. See step 03.
LangGraph
A library for building AI workflows as graphs: you describe the steps (nodes), the paths between them (edges) and the data they share (state), and LangGraph runs it, including loops and memory. This guide uses version 1.2.11. See step 03.
Graph
A set of nodes connected by edges. The presenter's analogy (from 20:05): a map where nodes are cities and edges are roads. In code, "the graph" is the object you get from builder.compile(), conventionally named graph. See step 05 and the handbook chapter Graphs & State Machines.
Node
One step of the graph: a Python function that receives the current state and returns an update. You register it with a name: builder.add_node("greeting", greeting). The name is what edges refer to. A node can also be a prebuilt object such as ToolNode. See step 06.
Edge
A fixed path from one node to the next: builder.add_edge("greeting", END). Both ends must be node names (strings). Passing the function instead (add_edge(START, greeting)) fails with TypeError: 'function' object is not iterable. See step 06.
Conditional edge
A path that is chosen at run time. builder.add_conditional_edges("node1", next_step) calls the routing function next_step after node1 and goes wherever it says. In the presenter's analogy: "if the car has cargo, go left". Using add_edge here by mistake gives "Found edge ending at unknown node". See step 08.
Routing function
The function behind a conditional edge. It reads the state and returns the name of the next node (or END); it doesn't change the state. Graph 2's next_step returns "node2" if the first word is exactly hello, otherwise "node3". tools_condition is a ready-made one. See step 08.
START and END
Two special nodes imported from langgraph.graph. START is where every run begins (add_edge(START, "greeting")) and END is where it stops. Studio draws them as __start__ and __end__. See step 06.
State
The data that travels through the graph, like the car in the presenter's road-trip analogy that picks up and drops cargo. Its shape is the class you pass to StateGraph: a plain str in graph 0, a TypedDict with graph_str in graphs 1 and 2, a list of messages from graph 4 on. Every node reads it and returns an update to it. See step 05 and How State Flows Through a Graph.
StateGraph
The builder class: builder = StateGraph(State). You add nodes and edges to it, then call compile(). It is not runnable itself; the compiled graph is. See step 06.
Reducer
The rule that merges a node's update into the state, one per state key. By default the new value simply overwrites the old one (that's why graph 1's node must re-include the old text). A key declared as Annotated[list, add_messages] uses the add_messages reducer instead and appends. See step 10 and the handbook chapter Designing State.
add_messages
LangGraph's reducer for message lists (from langgraph.graph.message import add_messages). It appends new messages to the existing list and gives each one an ID; a new message with the same ID as an old one replaces it instead. It also accepts a plain string or dict and turns it into a message. See step 10.
MessagesState
A ready-made state class with one key, messages: Annotated[list[AnyMessage], add_messages]. Graph 4 imports it, and its docstring shows the equivalent hand-written class. Every graph from 4 to 9 uses it. See step 10.
compile()
graph = builder.compile() checks the wiring (every edge points at a known node, there is a way in from START) and returns a runnable graph. You can pass a checkpointer here: builder.compile(checkpointer=memory). See step 06 and step 14.
invoke
Runs something once and returns the result. graph.invoke("hey am new!") runs graph 0 from START to END and returns the final state. model_llm.invoke(messages) calls the model once. With memory, add a config: graph.invoke(input, {"configurable": {"thread_id": "1"}}). See step 06.
stream
Like invoke, but hands you results step by step while the graph runs. stream_mode="updates" yields each node's update, such as {'node1': {...}}; stream_mode="values" yields the whole state after each step. See step 19.
Superstep
One "tick" of a graph run: the nodes that are due run, their updates are merged into the state, then the edges choose what runs in the next tick. In every course graph only one node runs per superstep, so a superstep is simply "one node ran". Graph 8 answering one math question takes three: model, tools, model. Checkpoints and the recursion limit are counted in supersteps. See How State Flows Through a Graph.
Recursion limit
A safety cap on the number of supersteps in one run, so a loop that never ends can't run forever. When it is hit you get GraphRecursionError: Recursion limit of N reached without hitting a stop condition. Set it per run with graph.invoke(input, {"recursion_limit": 10}). In langgraph 1.2.11 the default is very high (10007, verified); older versions and many tutorials use 25, so setting your own is a good habit for agents. See the handbook chapter Control Flow.
langgraph.json
The configuration file for langgraph dev. In this repo it has "dependencies": ["."] (install this project), a "graphs" map from a display name to path:variable (for example "0_graph": "./module1/0_graph_state_str.py:graph") and "env": ".env". Every new graph must be added here to appear in Studio. See step 06.
langgraph dev
A command from langgraph-cli[inmem] that starts a local server on http://127.0.0.1:2024, loads every graph in langgraph.json and opens Studio. It reloads when you save a file ("changes detected"). It provides its own memory, so it refuses a graph compiled with your own checkpointer (graph 9). On Windows, harmless UnicodeEncodeError lines can appear; set PYTHONIOENCODING=utf-8. See step 06 and step 17.
LangGraph Studio
A web page (at smith.langchain.com/studio, needs a free LangSmith account) that connects to your local langgraph dev server. On the left it draws the graph (__start__, your nodes, __end__) above an Input panel with a Submit button; on the right it shows each run as a thread, node by node. "New Thread" starts a fresh conversation. See step 06 and the handbook chapter Streaming, Debugging & LangGraph Studio.

Tools & agents

Tool
A Python function the model is allowed to ask for. The @tool decorator (from langchain.tools import tool) turns def multiply(nb1: int, nb2: int) -> int into a tool: its name, its type hints and its docstring become a description the model can read. The model never runs the tool itself; your graph does. See step 11.
bind_tools
model_llm.bind_tools([multiply, addition, subtraction]) returns a copy of the model that sends those tool descriptions with every call, so the model knows it may ask for them. It doesn't run anything. Graph 5 binds a tool but has no node to run it, so the run ends with an unanswered request. See step 11.
Tool call
The model's request to run a tool, stored in AIMessage.tool_calls: a name, arguments and an ID, for example {'name': 'multiply', 'args': {'nb1': 12, 'nb2': 7}, 'id': 'call_1'}. One AIMessage can hold several; in the video "what is 10- 5, 20 * 3, 3 + 2" produces three at once. See step 11.
ToolNode
A prebuilt node (from langgraph.prebuilt import ToolNode) that reads the tool calls in the last AIMessage, runs each matching tool and returns one ToolMessage per call. Register it under the name "tools". With handle_tool_errors=True, an exception inside a tool becomes an error message the model can read instead of crashing the run. See step 12 and step 16.
tools_condition
A prebuilt routing function. It looks at the last message: if it has tool calls it returns "tools", otherwise END. That's why the ToolNode must be named "tools" (the presenter: "I know that we need to call it tools", 114:56). Use it with add_conditional_edges, never add_edge. See step 12.
Agent
A model that can decide, on its own, to use tools and keep going until the task is done. In LangGraph it is just a graph: a model node, a tools node, and a loop between them. Graph 8 is the course's first real agent. See step 13 and the handbook chapter Agent Architectures.
Agent loop (ReAct)
Model, then tools, then model again, until the model answers without tool calls. In graph 8 the single edge builder.add_edge("tools", "chat_with_tools") is what turns graph 6 into a loop. The presenter calls this pattern ReAct (reason and act, around 130:02). See step 13 and How State Flows Through a Graph.

Memory, testing & what's next

Checkpointer
An object that saves a snapshot of the state after every superstep, filed under a thread ID. On the next invoke with the same thread, the graph starts from the saved state, so new messages are appended to the old ones. Pass it at compile time: builder.compile(checkpointer=memory). See step 14 and the handbook chapter Persistence, Memory & Time Travel.
MemorySaver (InMemorySaver)
A checkpointer that keeps snapshots in the computer's memory (RAM), from langgraph.checkpoint.memory. MemorySaver is another name for InMemorySaver (verified: same class). Everything is lost when the program ends. See step 14.
Thread ID
The name of one conversation in a checkpointer, passed as {"configurable": {"thread_id": "1"}}. The same ID continues the conversation; a new ID starts empty. Studio shows the ID of each thread at the top of the run panel. Invoking a graph that has a checkpointer without one fails with ValueError: Checkpointer requires one or more of the following 'configurable' keys: thread_id, .... See step 14.
Persistence
Keeping data after the program stops. MemorySaver is not persistent; a database-backed checkpointer such as SqliteSaver is. Under langgraph dev, the server handles persistence for you. See step 17.
SQLite (SqliteSaver)
SQLite is a small database stored in a single file, built into Python as sqlite3. The official package langgraph-checkpoint-sqlite provides SqliteSaver, which stores checkpoints in a file such as checkpoints.sqlite, so a conversation survives a restart. See step 17.
pytest
Python's most popular testing tool. You write functions whose names start with test_ containing assert lines, and uv run pytest -q runs them all and reports which fail. Step 18's suite has 13 tests, all passing. See step 18.
Fake model
A stand-in for ChatOpenAI that answers instantly with fixed text, or with a fixed tool call when tools are bound. It costs nothing and needs no key, so tests can check the graph's wiring, routing, tools and memory. It can't check what a real model would say. See step 18.
Mermaid
A text language for drawing diagrams. graph.get_graph().draw_mermaid() prints your graph in Mermaid; paste it into https://mermaid.live to see the picture. Solid arrows (-->) are fixed edges and dotted ones (-.->) are conditional. See step 19.
LangSmith
LangChain's web platform for watching and debugging LLM apps. It stores traces of your runs and hosts LangGraph Studio. The setup test (main.py) is LangSmith's own quickstart. See step 04.
Tracing
Recording every step of a run (each node, each model call, its inputs and outputs) so you can inspect it later in LangSmith. It is switched on by environment variables in .env. The repo's LANGSMITH_TRACING_V2=true works (verified); current docs use LANGSMITH_TRACING=true. See step 04.
Human-in-the-loop
Pausing a graph so a person can approve, edit or reject what happens next, for example before a tool sends an email. LangGraph does this with interrupt(...) and resumes with Command(resume=...) (both from langgraph.types); it needs a checkpointer. The Studio toolbar has an "Interrupts" button for it. Not covered in the video; see the handbook chapter Human-in-the-Loop & Interrupts.
Subgraph
A compiled graph used as a node inside another graph. It lets you build a big workflow from small tested pieces. Not covered in the video; see the handbook chapter Subgraphs, Multi-Agent Systems & Your Roadmap.
Multi-agent system
Several agents, each with its own prompt and tools, working together; for example a supervisor that hands a question to a "math agent" or a "research agent". In LangGraph each agent is a node or a subgraph. Not covered in the video; see the handbook chapter Subgraphs, Multi-Agent Systems & Your Roadmap.
