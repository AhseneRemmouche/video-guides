Graph 0: String State & LangGraph Studio

The smallest possible graph, running it in Python, langgraph.json, and LangGraph Studio.

▶ Watch this part (32:00)

Goal

Time for code. In step 5 you met nodes, edges and state on a whiteboard. Now you build the smallest real LangGraph graph there is: one node, two plain edges, and a state that is just a piece of text. You type something in, the node adds a greeting to it, and you get the longer text back.

It looks almost too simple, and that is the point. Every graph in this course (up to the agent with memory in step 14) is built with the same five moves you learn here: create a builder, add nodes, add edges, compile, invoke. In the second half of the page you also open LangGraph Studio, the visual tool the presenter uses for every graph from now on.

The idea behind the code

The presenter starts the file by writing four comments as a to-do list (33:24–33:48): State, nodes, edges, and "putting our graph together". You'll see the same four headings in every course file. For graph 0 they are filled in like this:

  • State: left empty on purpose. The state is a plain str, a type Python already has, so there is nothing to declare (34:14).
  • Nodes: one function, greeting. It takes the state and returns a new state (34:38).
  • Edges: also empty. Simple edges (always go from A to B) need no code of their own; you just connect names when you build the graph. Only conditional edges need a function, and those come in step 8 (35:48–36:11).
  • Putting it together: a StateGraph builder, add_node, add_edge, compile.
New to StateGraph? What "builder" and "compile" mean

StateGraph is LangGraph's main class (a state graph). You give it the type of the state you want to track, and it gives you an empty, editable graph: the builder. A builder is like a construction plan. You keep adding rooms (nodes) and corridors (edges) to it, but nobody can walk through it yet.

Compiling (builder.compile()) checks the plan (does every edge point at a node that exists? is there a way in from START?) and turns it into a runnable object. Only the compiled graph has .invoke(). That's why the course always ends with graph = builder.compile(): the variable graph is the thing you run, and the thing Studio loads.

New to START and END? The two built-in nodes

Every LangGraph graph has two special nodes you never write yourself (see START and END). START is where the input enters; END means "stop here and return the state". In Python they are just constants you import from langgraph.graph. Their real values are the strings "__start__" and "__end__", which is why Studio labels them __start__ and __end__.

Without an edge from START, LangGraph doesn't know which node to run first, and compile() refuses the graph. Without an edge into END, the graph never says it's finished.

Try the video's version: the mistake at 39:20

The first time the presenter ran the file, it crashed. In the edges they had written the function greeting (no quotes) instead of the node name "greeting". This is that version, lines 20–21:

# importing our lib
from langgraph.graph import StateGraph, START, END

# State

# nodes
def greeting(state: str) -> str:
    """this function greets people to ACL"""
    return state + "welcome to AI Career Lab!"

# edges

# langGraph putting our graph together
builder = StateGraph(str)

# add nodes to our graph
builder.add_node("greeting", greeting)

# add edges
builder.add_edge(START, greeting)
builder.add_edge(greeting, END)

graph = builder.compile()

print(graph.invoke("hey am new!"))

Running it stops before the graph is even built (verified):

Traceback (most recent call last):
  File "…\module1\0_graph_state_str.py", line 21, in <module>
    builder.add_edge(greeting, END)
  File "…\langgraph\graph\state.py", line 969, in add_edge
    for start in start_key:
                 ^^^^^^^^^
TypeError: 'function' object is not iterable

The presenter's diagnosis (39:20): "we named our node greeting… we are creating an edge between start and the function, but it doesn't know what this function is." The fix is to put the name in quotes on both lines.

Why does it say "not iterable", and why line 21, not line 20?

add_edge(start, end) accepts either one node name (a string) or a list of names as the start. When the start is not a string, LangGraph assumes it's a list and loops over it with for start in start_key. A function can't be looped over, so Python raises TypeError: 'function' object is not iterable. That's why line 21 (where the function is the start) crashes first.

Line 20 (add_edge(START, greeting)) has the function as the end, which isn't checked until compile(). If you only fix line 21, compile fails instead with ValueError: Found edge ending at unknown node `<function greeting at 0x…>` (verified). Both lines need quotes.

Read a traceback from the bottom up: the last line is the error, the frames above it show where. The frame in your file (line 21) is the one to fix; the frame inside langgraph is just where the problem was noticed.

See it in LangGraph Studio

A terminal shows only the final state. The presenter wants to see the state travel through the graph (40:03), so they switch to LangGraph Studio. Two pieces make that work: a configuration file, langgraph.json, that tells LangGraph where your graphs are, and the langgraph dev command, which starts a small local server that Studio talks to.

New to LangGraph Studio? What it is and where it runs

Studio is a web page, part of LangSmith, that draws your graph and lets you run it with a form instead of code. The page lives at smith.langchain.com/studio, so you need the free LangSmith account you created in step 4. But your graph does not run on LangSmith's servers: langgraph dev runs it on your own computer at http://127.0.0.1:2024 (127.0.0.1 means "this computer"), and the Studio page in your browser sends requests to that local address. The presenter: "all this is going locally" (41:36).

That's why the server must keep running in a terminal while you use Studio. Close the terminal and Studio shows it as disconnected.

Threads

Every run in Studio happens inside a thread (identified by a thread ID, shown at the top of the right pane). A thread is like one conversation: each Submit adds a new "turn" to it, and the server keeps the history (persistence is built into langgraph dev). New Thread starts a fresh, empty one. For graph 0 this barely matters; it becomes important in step 8 (a stale thread confuses the presenter at 62:01) and central in step 14 (memory).

Windows note: odd lines in the server log

On Windows the langgraph dev log may print UnicodeEncodeError lines. They come from the terminal not supporting some characters in the log (harmless; the server keeps working). To silence them, set the output encoding before starting the server in PowerShell:

$env:PYTHONIOENCODING = "utf-8"
uv run langgraph dev

Common mistakes

  • Function instead of name in an edge. add_edge(START, greeting) → TypeError or ValueError … unknown node. Use "greeting".
  • Running langgraph dev in the wrong folder. It looks for langgraph.json in the current folder. If you cd-ed into module1 for the terminal run, go back up with cd .. first.
  • langgraph.json inside module1. It belongs in the project root, next to pyproject.toml.
  • Wrong path or variable after the colon. ./module1/0_graph_state_str.py:graph must match the file name exactly and the variable must be called graph, or the server fails to load the graph.
  • Leaving the print(graph.invoke(...)) line active. The server imports the file, so the graph runs once on every (re)load and prints to the server log. Harmless here, but from step 9 on that would call the model, which costs tokens.
  • Input without quotes or with braces. A string state needs "…". See the table above.
  • "command not found: langgraph". Use uv run langgraph dev, or activate the virtual environment first.

For a slow-motion view of what happens to the state at each step (and why later graphs append instead of replace), read How State Flows Through a Graph.

Recap
  • Five moves build any graph: StateGraph(type), add_node(name, function), add_edge(from, to), compile(), invoke(input).
  • A node is a plain function: state in, new state out. With a str state, the returned string replaces the old one.
  • Edges connect node names (strings). Passing the function gives TypeError: 'function' object is not iterable.
  • "…" + "…" glues strings with no space, hence hey am new!welcome to AI Career Lab!.
  • langgraph.json maps a graph id to file.py:variable; uv run langgraph dev serves those graphs locally on port 2024 for Studio.
  • In Studio, a string state is typed as a JSON string in double quotes; runs live in threads, and New Thread starts a clean one.
