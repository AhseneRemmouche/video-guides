Control Flow: Edges, Routing, Loops & Parallelism

Conditional edges, Command, Send, parallel branches, loops and the recursion limit.

What you will learn

The course uses two kinds of edges: add_edge for "always go here next" and add_conditional_edges for "decide at run time". Graph 2 routes on the first word of a string, graph 3 routes on a number the model picked, and graphs 6–9 route with the prebuilt tools_condition. This chapter covers every way LangGraph lets you control what runs next, including the tools the course doesn't use: Command, Send, parallel branches and the recursion limit. Every snippet was run with LangGraph 1.2.11.

  • plain edges, fan-in edges and add_sequence;
  • conditional edges, path maps, and why Literal return hints change the drawing;
  • Command: update the state and choose the next node in one return value;
  • parallel branches (fan-out / fan-in) and map-reduce with Send;
  • loops, the recursion limit (default and how to set it) and GraphRecursionError.
Why this matters for your project. The agent in graph 8 (step 13) is nothing more than one conditional edge and one edge that points back. The bug the presenter hit in graph 6 (step 12), Found edge ending at unknown node, came from using the wrong one of these two methods. Once you know all the routing tools, you can build any workflow shape the later chapters describe.

Plain edges

An edge added with builder.add_edge("a", "b") means "every time a finishes, run b". Both ends are node names (strings), or the special START and END constants. Three useful variations:

  • Several edges out of one node make the targets run in parallel in the next superstep (see "Parallel branches" below).
  • A list as the start, builder.add_edge(["search_web", "search_docs"], "write"), means "run write once, after all of these have finished". That's a fan-in or join.
  • add_sequence adds several nodes and chains them in order, in one call. It exists in 1.2.11 (verified). Each node gets its function's name: builder.add_sequence([step_1, step_2]) creates nodes "step_1" and "step_2" with an edge between them. You still connect START and END yourself.
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    x: int

def step_1(state: State) -> dict:
    return {"x": state["x"] + 1}

def step_2(state: State) -> dict:
    return {"x": state["x"] * 10}

builder = StateGraph(State)
builder.add_sequence([step_1, step_2])     # nodes "step_1" -> "step_2"
builder.add_edge(START, "step_1")
builder.add_edge("step_2", END)
print(builder.compile().invoke({"x": 1}))  # {'x': 20}

Conditional edges

A conditional edge has a routing function instead of a fixed target. After the source node finishes, LangGraph calls the function with the current state; whatever it returns names the next node. Graph 2 (step 8):

# edges
def next_step(state: State) -> Literal["node2", "node3"]:
    """guide the state/graph to next node"""
    state_str = state["graph_str"]
    array_state_str = state_str.split(" ")

    if array_state_str[0] == "hello":
        return "node2"

    return "node3"

and later builder.add_conditional_edges("node1", next_step). The presenter's summary at 55:25: edges "guide the state", they don't do the logic. A routing function should only read the state and return a name. Any change to the data belongs in a node.

What a routing function may return

  • A node name: "node2".
  • END (or the string "__end__", which is what END contains): stop the run. Graph 3's next_step returns END when the model's number is neither 2 nor 3.
  • A list of names: all of them run in parallel in the next step (verified: returning ["a", "b"] ran both).
  • A list of Send objects: map-reduce, covered below.
  • A label that a path map translates into a node name.

Path maps

add_conditional_edges(source, path, path_map=None) takes an optional third argument. As a dict, it maps whatever the routing function returns to a node name. This keeps the routing function independent of your node names, and labels the arrows in drawings:

from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    score: int
    verdict: str

def grade(state: State) -> dict:
    return {}                                   # the score arrives in the input

def pass_or_fail(state: State) -> str:          # routing function: returns a label
    return "high" if state["score"] >= 50 else "low"

def passed(state: State) -> dict:
    return {"verdict": "pass"}

def failed(state: State) -> dict:
    return {"verdict": "fail"}

builder = StateGraph(State)
builder.add_node("grade", grade)
builder.add_node("passed", passed)
builder.add_node("failed", failed)
builder.add_edge(START, "grade")
builder.add_conditional_edges("grade", pass_or_fail, {"high": "passed", "low": "failed"})
builder.add_edge("passed", END)
builder.add_edge("failed", END)
graph = builder.compile()

print(graph.invoke({"score": 72}))   # {'score': 72, 'verdict': 'pass'}
print(graph.invoke({"score": 30}))   # {'score': 30, 'verdict': 'fail'}

A path map can also be a plain list of possible targets, like ["summarize"] in the Send example below. That doesn't translate anything; it just tells LangGraph where the edge may lead.

Why the course writes Literal[...]

LangGraph can't run your routing function at compile time to discover where it might go. It needs a hint to draw the graph: either a path map, or a return type such as -> Literal["node2", "node3"]. The presenter imports Literal for graph 2 at 51:20 for exactly this reason. Without either, the graph still runs correctly, but its picture is wrong. We checked with get_graph():

LangGraph Studio draws the same information. In the presenter's graph 2 (around 1:01:40), the two arrows out of node1 are dashed curves, the usual sign of a conditional edge, and the one actually taken is highlighted.

The graph 6 mistake, explained. builder.add_edge("chat_with_tool", tools_condition) passes a function where a node name is expected, so compile() complains: ValueError: Found edge ending at unknown node `<function tools_condition at 0x…>`. Routing functions go to add_conditional_edges. Also note that tools_condition returns the string "tools" (or END), so the tool node must be named exactly "tools", as the presenter says at 114:56.

Command: update and route in one step

Sometimes the node that does the work also knows best where to go next. Instead of writing a node and a separate routing function, the node can return a Command from langgraph.types. Its two main fields are update (a normal state update) and goto (the next node, a list of nodes, or Send objects):

import operator
from typing import Annotated, Literal
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import Command

class State(TypedDict):
    n: int
    log: Annotated[list[str], operator.add]

def decide(state: State) -> Command[Literal["even", "odd"]]:
    target = "even" if state["n"] % 2 == 0 else "odd"
    return Command(update={"log": ["decide"]}, goto=target)   # update AND route

def even(state: State) -> dict:
    return {"log": ["even"]}

def odd(state: State) -> dict:
    return {"log": ["odd"]}

builder = StateGraph(State)
builder.add_node("decide", decide)
builder.add_node("even", even)
builder.add_node("odd", odd)
builder.add_edge(START, "decide")          # no edges out of "decide": Command routes
builder.add_edge("even", END)
builder.add_edge("odd", END)
graph = builder.compile()

print(graph.invoke({"n": 3, "log": []}))   # {'n': 3, 'log': ['decide', 'odd']}

Parallel branches: fan-out and fan-in

When two edges leave the same node, both targets run in the same superstep, in parallel. A list-start edge joins them again:

Parallel nodes that write the same key need a reducer on that key. Without one, LangGraph refuses to pick a winner:

langgraph.errors.InvalidUpdateError: At key 'v': Can receive only one value per step.
Use an Annotated key to handle multiple values.

The fix is Annotated[list[str], operator.add] (or another reducer) on that key; see chapter 2. Parallel nodes writing different keys are fine without one.

Map-reduce with Send

Fixed edges are fine when you know the branches in advance. But what if the number of branches depends on the data, such as "summarise each of the N documents the user uploaded"? A routing function can return a list of Send objects. Each Send(node_name, payload) starts one run of that node with its own input, and all of them run in parallel. This is the map step. A normal edge then collects the results: the reduce step.

import operator
from typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import Send

class State(TypedDict):
    topics: list[str]
    summaries: Annotated[list[str], operator.add]   # parallel writes need a reducer
    report: str

class TopicState(TypedDict):        # what each parallel worker receives
    topic: str

def fan_out(state: State) -> list[Send]:
    return [Send("summarize", {"topic": t}) for t in state["topics"]]

def summarize(state: TopicState) -> dict:
    return {"summaries": [f"summary of {state['topic']}"]}   # a model call in real life

def combine(state: State) -> dict:
    return {"report": " | ".join(state["summaries"])}

builder = StateGraph(State)
builder.add_node("summarize", summarize)
builder.add_node("combine", combine)
builder.add_conditional_edges(START, fan_out, ["summarize"])
builder.add_edge("summarize", "combine")
builder.add_edge("combine", END)
graph = builder.compile()

result = graph.invoke({"topics": ["cats", "dogs", "owls"], "summaries": []})
print(result["report"])   # summary of cats | summary of dogs | summary of owls

Loops and the recursion limit

A loop is just an edge to a node that already ran. In graph 8, builder.add_edge("tools", "chat_with_tools") sends tool results back to the model, and tools_condition is the exit: when the model replies without tool calls, the conditional edge goes to END.

What if the exit never fires? A model could keep asking for tools, or a "rewrite until good" loop could never be satisfied. LangGraph protects you with the recursion limit: the maximum number of supersteps one run may take. When a run reaches it, LangGraph stops and raises GraphRecursionError (from langgraph.errors).

from typing import Literal
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.errors import GraphRecursionError

class State(TypedDict):
    count: int

def increment(state: State) -> dict:
    return {"count": state["count"] + 1}

def again(state: State) -> Literal["increment", "__end__"]:
    return "increment" if state["count"] < 1_000_000 else END   # practically never ends

builder = StateGraph(State)
builder.add_node("increment", increment)
builder.add_edge(START, "increment")
builder.add_conditional_edges("increment", again)
graph = builder.compile()

try:
    graph.invoke({"count": 0}, config={"recursion_limit": 5})
except GraphRecursionError as error:
    print("Stopped:", error)

Output (LangGraph 1.2.11):

Stopped: Recursion limit of 5 reached without hitting a stop condition. You can increase the limit by setting the `recursion_limit` config key.
For troubleshooting, visit: https://docs.langchain.com/oss/python/langgraph/errors/GRAPH_RECURSION_LIMIT

Many tutorials and older LangGraph versions say the default is 25. That number still exists in langchain_core as its own default, but it's not what a 1.2.11 graph uses. With a default of 10007, an endless loop calling a paid model could make thousands of calls before the safety net catches it. Set a limit that fits your graph.

Pitfalls
  • Using add_edge with a routing function (the graph 6 mistake). Routing functions go to add_conditional_edges.
  • Returning a name that isn't a node, such as "tool_node" when the node is called "tools". In 1.2.11 this doesn't raise an error: LangGraph logs wrote to unknown channel branch:to:tool_node, ignoring it and the run quietly stops after that node (verified). Watch the log, and test each route.
  • Leaving out the Literal hint or path map: the graph runs, but Studio and draw_mermaid() show the wrong shape.
  • Adding both a normal edge and a Command goto out of the same node: both fire, so two nodes run next.
  • Parallel branches writing one key without a reducer: InvalidUpdateError.
  • Relying on "25" as the safety net. In 1.2.11 the default is 10007; set your own limit.
Common misconceptions
  • "A conditional edge can change the state." Routing functions only read. Use a node, or Command(update=...).
  • "Parallel nodes run one after another." They run in the same superstep and see the same starting state.
  • "Send needs a special node." It targets any normal node; the node just receives the payload you sent instead of the full state.
  • "The recursion limit counts loops." It counts supersteps of the whole run, loop or not.
Recap
  • add_edge(a, b): always next. add_edge([a, b], c): join. add_sequence([f, g]): a chain in one call.
  • add_conditional_edges(source, router, path_map): the router reads the state and returns a node name, END, a list, or Sends. Give it a Literal hint or a path map so the graph draws correctly.
  • Command(update=..., goto=...) lets one node both update and route; annotate it with Command[Literal[...]].
  • Several edges out of a node run their targets in parallel; shared keys need a reducer. Send creates a run-time number of parallel branches (map-reduce).
  • Loops are edges back. Give each loop your own exit rule; the recursion limit (10007 by default in 1.2.11) raises GraphRecursionError as a last resort.
