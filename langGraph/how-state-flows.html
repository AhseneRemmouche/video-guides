How State Flows Through a Graph

Node updates, overwrite vs append (reducers), supersteps, routing, and what the checkpointer saves — traced step by step.

Every course file ends with graph = builder.compile(), and every run starts with graph.invoke(...). What happens in between? This page opens the box. It follows the state through five of the course's graphs (0, 2, 4, 8 and 9), one step at a time: what goes in, what each node gives back, how LangGraph merges that into the state, who decides which node runs next, why the agent loop stops, and what memory actually saves.

Read it alongside step 05 (the road-trip analogy) and the graph steps 06 to 14. Every output shown here was produced by running the repo's files against its locked versions (langgraph 1.2.11). Graphs 0 to 2 need no model. For graphs 8 and 9, a fake chat model stood in for GPT-4o, so the message types and counts are real, but the wording of the final answers is the fake model's.

The one rule: a node returns an update, not the state

In the presenter's analogy (from 20:05), the state is a car driving along roads (edges) between cities (nodes), picking up and dropping off cargo. In code, the car is a value that LangGraph keeps for you. A node is a plain Python function:

  1. LangGraph calls the node with the current state. The node can read anything in it.
  2. The node returns an update. For a dictionary state, that is a smaller dict containing only the keys it wants to change.
  3. LangGraph merges the update into the state. How it merges depends on the key's reducer: by default the new value overwrites the old one; for a messages list it appends.
  4. An edge decides which node runs next, either a fixed one or one picked by a routing function. When the next stop is END, the run is over and invoke returns the final state.

The node never "owns" the state and never calls the next node itself. It does its one job and hands back what changed. Keep these four steps in mind; every trace below is just them, repeated.

New to "returning an update"? Why not just change the state directly?

You could imagine a node writing state["graph_str"] = "...". LangGraph is designed the other way round: the node gives back a description of the change, and LangGraph applies it. That one design choice makes three things possible later in the course:

  • Different merge rules per key. A message list can grow while a counter is replaced, without the node having to know which.
  • Snapshots. Because LangGraph applies every change itself, it knows exactly what the state looked like after each step, so a checkpointer can save it (graph 9).
  • Streaming. graph.stream(..., stream_mode="updates") can show you each node's update as it happens (step 19).

Verified edge cases with a two-key state: a node that returns only {"b": "new"} leaves key a unchanged; a node that returns None changes nothing; a node that returns a plain string fails with InvalidUpdateError: Expected dict, got oops; and a key that isn't in the state (a typo) is silently ignored.

Trace 1: graph 0, where the state is a single string

Graph 0 (step 06) is the smallest possible graph. Its state type is str, so the whole state is one piece of text:

def greeting(state: str) -> str:
    return state + "welcome to AI Career Lab!"

builder = StateGraph(str)
builder.add_node("greeting", greeting)
builder.add_edge(START, "greeting")
builder.add_edge("greeting", END)
graph = builder.compile()

With a string state there are no keys, so the node's return value is the new state: it replaces the old string completely. That's why the node must include the old text (state + ...). Running graph.invoke("hey am new!") takes one node step:

What you should see. print(graph.invoke("hey am new!")) prints hey am new!welcome to AI Career Lab!. In Studio, type the input as a JSON string ("hey am new!" with the quotes), not as {"hey"}, which gives SyntaxError: Expected ':' after property name in JSON.

Overwrite versus append: reducers

From graph 1 on, the state is a TypedDict with named keys, and a node returns a dict with only the keys it changes. For each key, a reducer decides how the returned value is combined with the current one. There are two you meet in this course:

Key declared asReducerWhat an update doesUsed in
graph_str: strnone (the default)Overwrites: the new value replaces the old oneGraphs 1, 2, 3
messages: Annotated[list[AnyMessage], add_messages]add_messagesAppends: the new messages are added to the end of the listGraphs 4 to 9, via MessagesState
New to Annotated? How a reducer is attached to a key

Annotated[X, extra] (from Python's typing module) means "a value of type X, plus some extra information for whoever reads the hint". Python ignores the extra part; LangGraph reads it. So messages: Annotated[list[AnyMessage], add_messages] says: this key holds a list of messages, and when a node returns new messages, merge them with the function add_messages.

Graph 4's docstring shows this exact class, and MessagesState is the same thing ready-made. The presenter hovers over add_messages at about 89:04 to show that it "merges two lists". It does three things (verified):

  • it appends new messages to the end of the existing list;
  • it gives every message an id, and a new message with the same id as an existing one replaces it instead of being added;
  • it turns plain input into messages: {"messages": "hi"} becomes a HumanMessage.

Trace 2: graph 2 and the routing function

Graph 2 (step 08) adds a choice. After node1, the conditional edge calls next_step(state), which looks at the first word of graph_str:

def next_step(state: State) -> Literal["node2", "node3"]:
    state_str = state["graph_str"]
    array_state_str = state_str.split(" ")
    if array_state_str[0] == "hello":
        return "node2"
    return "node3"

builder.add_conditional_edges("node1", next_step)

A routing function is not a node. It reads the state, returns the name of the next node, and changes nothing. Its Literal return hint tells LangGraph which names are possible, which is how Studio knows to draw two dotted branches.

Here is what graph.stream({"graph_str": "hello "}, stream_mode="values") printed, one state per step (verified; the typo "Carrer" is in the repo):

With a single key and the overwrite reducer, the update and the full state look identical. That's a coincidence of this tiny state. With two keys, the update would contain only the key the node changed.

Supersteps: how LangGraph counts the run

LangGraph runs a graph in ticks called supersteps. In one superstep, every node that is due runs, their updates are merged, then the edges decide what is due next. In all of this course's graphs only one node is due at a time, so you can read "superstep" as "one node ran". LangGraph numbers them: step −1 receives your input, step 0 passes it through START, and steps 1, 2, 3… are your nodes. The routing function runs at the end of a step; it doesn't get a step of its own.

Why "superstep" and not just "step"?

LangGraph can run several nodes in the same tick, for example when one node has fixed edges to two others. Those nodes run side by side, and only after all of them finish are their updates merged and the next tick starts. "Superstep" is the name for that whole tick, however many nodes it contains. The course never branches into parallel nodes, but you meet a close cousin in graph 8: one tools superstep can run several tool calls and add several ToolMessages at once. The handbook chapter Control Flow covers parallel branches.

Trace 3: graph 4, a list of messages

Graph 4 (step 10) switches to MessagesState. The input is a dict with a list of messages, and the only node calls the model with that list:

def chat(state: MessagesState) -> MessagesState:
    return {"messages": [model_llm.invoke(state["messages"])]}

Notice the square brackets around model_llm.invoke(...). The model returns one AIMessage, and the node wraps it in a one-item list. add_messages then appends it after your HumanMessage.

Common mistake: returning the message without the list. If you forget the square brackets you hand add_messages a single message instead of a list. It happens to accept that, but every example in LangGraph's docs and in this course uses a list, and a list is what lets one node add several messages at once (as ToolNode does). Keep the brackets.

Trace 4: graph 8, the agent loop

Graph 8 (step 13) has two nodes and the most important edge in the course:

builder.add_node("chat_with_tools", chat_with_tools)
builder.add_node("tools", ToolNode([multiply,addition,subtraction]))

builder.add_edge(START, "chat_with_tools")
builder.add_conditional_edges("chat_with_tools", tools_condition)
builder.add_edge("tools", "chat_with_tools")

Graph 6 had tools → END, so the tool ran once and the model never saw the result. Graph 8 replaces that with tools → chat_with_tools: after the tools run, the model is called again with the results in its message list. That single edge turns a one-way pipeline into a loop, and the model into an agent.

Now follow the message list for the question "What is 12 multiplied by 7?". The run takes three node supersteps. stream_mode="updates" printed one update per step (verified; the fake model asks for multiply and then writes "The result is 84"):

Why the loop stops

Nothing in the graph counts laps. The loop ends because tools_condition looks at the newest message after every model call: if it contains tool_calls, go to "tools"; if it doesn't, go to END. So the loop stops when the model answers in plain text. It decides that by itself, when it judges that the tool results are enough. In the video's Studio run (around 129:38), "what is 10- 5, 20 * 3, 3 + 2" made the model ask for three tools in one AIMessage. The tools node ran all three in a single superstep (verified: one update holding three ToolMessages: 5, 60 and 5), and the model's next reply had no tool calls, so the run ended.

Where is the system message? Graph 8's node sends state["messages"] + [system_message] to the model, but returns only the model's reply. The system message is added to every model call and never stored in the state, so you won't see it in the result or in Studio's message list. (It is also placed last; step 15 moves it to the front, the usual convention.)

The recursion limit: the safety net

If a model kept asking for tools forever, the loop would never reach END. LangGraph guards against this with the recursion limit: the maximum number of supersteps one run may take. Exceed it and the run stops with GraphRecursionError: Recursion limit of N reached without hitting a stop condition. You set it per call:

graph.invoke({"messages": [HumanMessage(content="What is 12 multiplied by 7?")]},
             {"recursion_limit": 10})

Verified with the course graphs: the limit counts your node supersteps plus one. Graph 0 (one node step) needs at least 2, graph 2 (two node steps) needs 3, and graph 8 with one tool round (three node steps) fails at 3 and succeeds at 4. Each extra tool round adds two steps. In langgraph 1.2.11 the default limit is 10007 (read from the installed source), which is effectively "no limit" for a small project; older versions and many tutorials use 25. For a real agent, pass your own sensible limit.

Trace 5: graph 9, what the checkpointer saves

Without memory, every invoke starts from your input alone, so a follow-up question like "now multiply that by 10" has nothing to refer to. Graph 9 (step 14) compiles the same agent with a checkpointer:

memory = MemorySaver()
graph = builder.compile(checkpointer=memory)
config = {"configurable": {"thread_id": "1"}}
response = graph.invoke({"messages": messages}, config)

The repo's file stops with NameError: name 'HumanMessage' is not defined before it gets this far (it never imports HumanMessage), so the traces below use the fixed version from step 15, which has the same graph.

A checkpointer saves a snapshot of the state after every superstep, filed under the thread ID in the config. When you invoke again with the same thread ID, the graph loads the latest snapshot first, then merges your new input into it, using the same reducers as any node update.

Two consequences surprise beginners:

  • Memory follows the reducer. The messages "accumulate" only because add_messages appends. Compile graph 2 with a MemorySaver, invoke "hello " and then "hi " on the same thread, and the second run simply overwrites graph_str: the saved state ends as 'hi welcome to AI Carrer LabI am in Node 3' with no trace of "hello" (verified).
  • The config is required. Invoke a graph that has a checkpointer without a thread ID and you get ValueError: Checkpointer requires one or more of the following 'configurable' keys: thread_id, checkpoint_ns, checkpoint_id (verified).
And in Studio? Threads without a checkpointer

Studio remembered earlier messages long before graph 9, even for graph 8 which has no checkpointer. That's because the langgraph dev server adds its own persistence to every graph it serves: each conversation you start with "New Thread" gets a thread ID, which the presenter points out in the Studio panel at about 133:19. The server even refuses a graph that brings its own checkpointer: registering graph 9 in langgraph.json makes startup fail with ValueError: Heads up! Your graph 'graph' ... includes a custom checkpointer (verified). So graph 9 is for plain Python runs. Step 17 shows a checkpointer that survives a restart, SqliteSaver.

Common mistakes when reasoning about state

  • Returning only the new text from a plain key. With the overwrite reducer, return {"graph_str": " welcome"} throws the old text away. Include it: state["graph_str"] + " welcome".
  • Returning the whole message list from a messages node. return {"messages": state["messages"] + [reply]} works only because add_messages recognises the old messages by ID. Return just the new message: {"messages": [reply]}.
  • Misspelling a state key in an update. An unknown key is ignored without an error, so the state silently doesn't change (verified).
  • Passing a function to add_edge. Edges take node names. add_edge(START, greeting) fails with TypeError: 'function' object is not iterable.
  • Wiring a routing function with add_edge. add_edge("chat_with_tool", tools_condition) fails with "Found edge ending at unknown node". Routing functions go in add_conditional_edges.
  • Expecting memory without the same thread ID. Build the config once and reuse the variable; a new ID starts empty.
Recap
  • A node receives the state and returns an update; LangGraph merges it. A routing function returns a node name and changes nothing.
  • Each key has a reducer: plain keys are overwritten, messages (with add_messages) is appended to. A str state is replaced by whatever the node returns.
  • A run is a series of supersteps, one per node in this course: graph 0 has 1, graph 2 has 2, graph 8 with one tool round has 3.
  • The agent loop ends when the model replies without tool_calls; tools_condition then routes to END. The recursion limit (node steps + 1 needed) is the safety net.
  • A checkpointer saves a snapshot after every superstep, per thread_id, and the next invoke on that thread starts from the newest one. langgraph dev does this for you in Studio.
