Graph 1: TypedDict State

A state that is a dictionary with named, typed fields.

▶ Watch this part (43:55)

Goal

Graph 0's state was one bare string. Real applications need to carry several pieces of information through a graph: the user's question, the model's answer, a counter, a list of messages. So in this step the state becomes a dictionary with named fields, described by a TypedDict class.

The graph's shape doesn't change at all (still START → greeting → END). What changes is how the node reads the state and what it returns: instead of the whole new state, it returns a small dictionary of updates. That idea (nodes return updates, LangGraph applies them) is how every remaining graph in the course works, including the chat graphs in step 10.

New to TypedDict? A dictionary with a declared shape

A normal Python dict can hold any keys: {"graph_str": "hello"}, {"typo": 3}, anything. A TypedDict is a way to describe which keys a dict should have and what type each value is:

class State(TypedDict):
    graph_str: str

reads as "a State is a dict with a key graph_str whose value is a str". At run time a State is still a plain dict: you create it with {"graph_str": "hello"} and read it with state["graph_str"]. Python itself doesn't check it, but two things do read it: your editor (autocomplete, red underlines for wrong keys) and LangGraph, which uses the keys to know which "channels" the state has and to build Studio's input form.

Note the syntax: a class whose body is just name: type lines (type hints), no def __init__, no values.

typing_extensions or typing? Where TypedDict comes from

TypedDict exists in two places: the standard library's typing module, and the separate package typing_extensions, which carries newer typing features back to older Python versions. The course imports it from typing_extensions, the way LangGraph's own documentation does.

On Python 3.12 both work for this course: a quick check with from typing import TypedDict gave the identical result. You never installed typing_extensions yourself: it arrives as a dependency of LangGraph (version 4.16.0 in the lock file). In step 8 the presenter imports Literal from typing and TypedDict from typing_extensions in the same file; mixing them is fine.

The complete file

# importing the lib
from langgraph.graph import StateGraph, START, END
from typing_extensions import TypedDict

# State
class State(TypedDict):
    graph_str:str

# node
def greeting(state: State) -> State:
    """function takes a dict and return a dict with greeting"""
    return {"graph_str": state["graph_str"]+" welcome to AI Career Lab!"}

# edges

# putting our graph togther
builder = StateGraph(State)

builder.add_node("greeting", greeting)

builder.add_edge(START, "greeting")
builder.add_edge("greeting", END)

graph = builder.compile()

Nodes return updates, not the whole state

With a dict state, a node does not have to return every key, only the ones it wants to change. LangGraph takes the returned dict and applies it to the current state key by key: by default, the new value overwrites the old one. Keys the node doesn't mention keep their values. Graph 1 has only one key, so "update" and "whole state" look the same here, but the rule matters as soon as a state has more fields (from step 9 on).

Try it in Python

The course file has no print line, but you can run the graph from a small script or the Python prompt in the project folder. The input must now be a dict with the key graph_str:

import importlib
graph = importlib.import_module("module1.1_graph_state_dict").graph

print(graph.invoke({"graph_str": "hello"}))

(importlib is needed only because the file name starts with a digit, which a normal import line can't handle. Or simply add the print(...) line at the bottom of the file, run python module1/1_graph_state_dict.py, and remove the line again before using Studio.)

Output (verified):

{'graph_str': 'hello welcome to AI Career Lab!'}

What you should see

A dict, not a string: invoke returns the final state, and the state is now a dict. Inside it, the greeting is separated by a space this time. Python prints dicts with single quotes; that's just how it displays them.

Common mistakes

  • Invoking with a plain string. graph.invoke("hello") → InvalidUpdateError: Expected dict, got hello (verified). The input must be {"graph_str": "hello"}.
  • Wrong key name. graph.invoke({"text": "hello"}) runs the node with no graph_str, and line 12 fails with KeyError: 'graph_str' (verified). Keys are case-sensitive and must match line 7.
  • Returning a string from the node. return state["graph_str"] + "…" (without the {"graph_str": …} wrapper) → InvalidUpdateError: Expected dict, got … (verified).
  • Forgetting the comma in langgraph.json. Every graph line except the last needs a comma at the end; a missing one makes the JSON invalid and the server can't start.
  • Looking at the old graph in Studio. The picker at the top left still shows 0_graph; switch it to 1_graph.
Recap
  • A TypedDict class describes a dict state: class State(TypedDict): graph_str: str. At run time it's an ordinary dict.
  • TypedDict can come from typing_extensions (the course's choice) or typing; both work on Python 3.12.
  • Nodes read with state["key"] and return a dict of updates; returned keys overwrite, others are kept.
  • graph.invoke({"graph_str": "hello"}) returns {'graph_str': 'hello welcome to AI Career Lab!'}.
  • Register each new graph in langgraph.json as "id": "./path/file.py:graph"; Studio then shows a form field per state key.
