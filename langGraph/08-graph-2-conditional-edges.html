Graph 2: Conditional Edges

A routing function decides which node runs next.

▶ Watch this part (50:29)

Goal

So far every graph was a straight line: the state always took the same road. In this step the graph gets a fork. After the first node, a small function looks at the state and decides which node runs next: node2 if the text starts with "hello", node3 otherwise. That function is called a routing function, and the fork is a conditional edge.

This is the single most important mechanism in LangGraph. Here the decision is a simple string check, but in step 9 a model's answer decides the road, and in steps 12–13 the same mechanism decides "run a tool or stop", which is what makes an agent.

What the presenter explains

Two ideas carry this step, and the presenter repeats both:

  • Nodes do the work, edges decide the road. "We are not going to tell the state where to go. No, this is not the job of our nodes. Our nodes will simply take a state, apply some certain logic to it and then return a state" (53:27). And for the routing function: "The edges do not touch the logic of the state. It guides the state" (55:25).
  • The routing function returns the name of the next node. It "will check the state, ask the questions" and return "node2" or "node3" (54:39–55:02). The return type Literal["node2", "node3"] lists the possible answers.
New to routing functions? A function that returns a node name

A routing function looks like a node (it receives the state) but has a different job. A node returns an update for the state, like {"graph_str": "…"}. A routing function returns a name, like "node2", and must not change anything.

You attach it with builder.add_conditional_edges("node1", next_step), which means: "when node1 finishes, call next_step(state) and go to whichever node it names". It runs after node1, so it sees the state after node1's update. In the road-trip picture from step 5, it's the signpost at the junction: it doesn't touch the cargo, it just points left or right.

New to Literal? A type that lists the exact allowed values

str as a return type means "any string". Literal["node2", "node3"] (a Literal type, from the standard typing module) means "one of exactly these two strings". Python doesn't enforce it at run time: returning "node4" would not be stopped by Python (LangGraph would then complain that the node doesn't exist).

So why write it? Because LangGraph reads it. When you call add_conditional_edges without telling it the possible destinations, LangGraph looks at the routing function's return type. From Literal["node2", "node3"] it learns the two roads and can draw both dashed arrows before the graph has ever run. That's the picture Studio shows.

The complete file

from langgraph.graph import START, END, StateGraph
from typing_extensions import TypedDict
from typing import Literal

# state
class State(TypedDict):
    graph_str:str

# nodes
def node1(state: State)->State:
    """this node greet our user"""
    return {"graph_str": state["graph_str"] + "welcome to AI Carrer Lab"}

def node2(state: State)->State:
    """this node greet our user"""
    return {"graph_str": state["graph_str"] + "I am in Node 2"}
    

def node3(state: State)->State:
    """this node greet our user"""
    return {"graph_str": state["graph_str"] + "I am in Node 3"}

# edges
def next_step(state: State) -> Literal["node2", "node3"]:
    """guide the state/graph to next node"""
    state_str = state["graph_str"]
    array_state_str = state_str.split(" ")

    if array_state_str[0] == "hello":
        return "node2"

    return "node3"


# putting the groph together
builder = StateGraph(State)

builder.add_node("node1",node1)
builder.add_node("node2",node2)
builder.add_node("node3",node3)

builder.add_edge(START, "node1")
builder.add_conditional_edges("node1", next_step)
builder.add_edge("node2", END)
builder.add_edge("node3", END)

graph = builder.compile()

Functions vs names, again

Step 6 taught "edges take names, not functions". Line 43 looks like it breaks that rule, but it doesn't: the node ("node1") is still a name; the second argument is a different kind of thing, a routing function that LangGraph calls. Nodes are always referred to by name; routing functions are passed as functions.

How the decision is made

The routing function runs after node1, so it doesn't see your raw input: it sees your input with the greeting already glued on. For a normal sentence that changes nothing about the first word. Here is the decision for the presenter's first test, "hello I am new":

New to split and indexes? Turning a sentence into a list of words

"hello I am new".split(" ") returns ['hello', 'I', 'am', 'new'] (verified). Each space is a cut. Then words[0] is the first word, words[1] the second, and so on; words[-1] would be the last.

Splitting on " " keeps punctuation attached: "hello, I am new" gives 'hello,' as the first piece, which is not equal to 'hello'. And a one-word input has no space for node1's greeting to stop at: "hello" becomes "hellowelcome to AI Carrer Lab" after node1, whose first piece is 'hellowelcome'. Both go to node3 (verified).

Why start a new thread?

A Studio thread keeps every earlier turn. After a code change, an old thread mixes runs of the old code with runs of the new one, which is confusing to read. A fresh thread shows only runs of the current code. In this graph each Submit starts from the new input, so it's mostly about readability; with memory (step 14) old turns really do feed into new ones.

Common mistakes

  • Forgetting to register the graph. The file exists but Studio's picker has no 2_graph: add the line to langgraph.json (with the comma on the line before) and restart the server.
  • Router returns a name that doesn't exist. The strings in next_step must match the add_node names exactly ("node2", not "Node2" or "node_2").
  • Also adding add_edge("node1", …). Then node1 has a fixed edge and a conditional one, both targets run in the same step, and both try to set graph_str: InvalidUpdateError: At key 'graph_str': Can receive only one value per step. (verified). Use only add_conditional_edges out of node1.
  • Calling the router: add_conditional_edges("node1", next_step()). The parentheses call it immediately, without a state, and Python raises a TypeError about a missing argument. Pass next_step without parentheses.
  • Expecting "Hello" to match. The comparison is case-sensitive. To accept any case, compare array_state_str[0].lower() == "hello".
  • Copied node not edited. The 62:01 bug: route right, text wrong. Check each copied return line.
  • Stale results in Studio. After editing code, save, check the server log reloaded, and start a New Thread.

To see how the router fits into a run step by step (a node finishes, its update is applied, then the conditional edge is evaluated), read How State Flows Through a Graph.

Recap
  • Nodes change the state; routing functions only choose the next node by returning its name.
  • add_conditional_edges("node1", next_step) runs next_step after node1, on node1's updated state.
  • The return type Literal["node2", "node3"] tells LangGraph (and Studio's drawing) the possible destinations; without it the drawing shows only node1 → __end__.
  • split(" ")[0] is the first space-separated piece, compared exactly: "hello" → node2; "hi", "Hello", "hello," and a lone "hello" → node3.
  • Register each graph in langgraph.json; after changing code, save and use a New Thread so old runs don't confuse you.
