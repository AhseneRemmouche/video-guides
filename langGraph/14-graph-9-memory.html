Graph 9: Memory with a Checkpointer

MemorySaver and thread_id, so the agent remembers earlier turns.

▶ Watch this part (02:12:28)

Goal

The agent from step 13 forgets everything between runs. Each graph.invoke(...) starts from an empty message list, so if you ask "Add 3 and 4" and then "Now multiply that by 10", the second run has no idea what "that" is. In this last course step the presenter gives the graph a memory: a checkpointer that saves the state after every step, and a thread ID that says which conversation a run belongs to.

The graph's shape is exactly graph 8's. Only three things are added: MemorySaver(), compile(checkpointer=memory), and a config with a thread_id passed to invoke. Be warned before you start: the repo file crashes as written (one missing import), and it can't be loaded by langgraph dev. Both are explained below, with the fixes.

New to checkpointers? Saving the state after every step

A checkpointer is an object you hand to compile(). From then on, LangGraph saves a snapshot of the state (a checkpoint) after every step of every run, filed under the run's thread ID. When you call invoke again with the same thread ID, LangGraph first loads the latest snapshot for that thread, then applies your new input to it. For a MessagesState graph, "applies" means add_messages appends your new message to the saved ones, so the model sees the whole conversation.

MemorySaver is the simplest checkpointer: it keeps the snapshots in a Python dictionary in memory. Fast and needs no setup, but everything disappears when the program ends. (MemorySaver is just another name for InMemorySaver: MemorySaver is InMemorySaver is True in the locked version.) For memory that survives a restart you use a database-backed checkpointer such as SQLite; that's step 17.

New to threads? One ID per conversation

A thread is one conversation. Its thread ID is any string you choose: "1", "user-42", a random UUID (Studio uses those, like 01a058c0-c630-…). Runs with the same ID share a history; runs with different IDs are completely separate, even in the same program with the same graph.

You pass it through the config, the optional second argument of invoke. The shape is fixed: {"configurable": {"thread_id": "1"}}. "configurable" is LangGraph's bag for per-run settings; thread_id is the key the checkpointer looks for. Without a checkpointer the thread ID is simply ignored.

from langgraph.prebuilt import ToolNode, tools_condition
from langchain.messages import SystemMessage
from typing import Literal

load_dotenv()

model_llm = ChatOpenAI(model="gpt-4o")

@tool
def multiply(nb1 : int, nb2: int) -> int:
    """this tool return the multiplication of 2 numbers"""
    return nb1*nb2

@tool
def addition(nb1 : int, nb2: int) -> int:
    """this tool return the sum of 2 numbers"""
    return nb1+nb2

@tool
def subtraction(nb1 : int, nb2: int) -> int:
    """this tool return the subtaction of 2 numbers"""
    return nb1-nb2

model_llm_with_tools = model_llm.bind_tools([multiply,addition,subtraction])

system_message = SystemMessage(content="you are a helpful Math teach")

# nodes
def chat_with_tools(state: MessagesState) -> MessagesState:
    return {"messages": [model_llm_with_tools.invoke(state["messages"] + [system_message])]}

builder = StateGraph(MessagesState)

builder.add_node("chat_with_tools", chat_with_tools)
builder.add_node("tools", ToolNode([multiply,addition,subtraction]))

builder.add_edge(START, "chat_with_tools")
builder.add_conditional_edges("chat_with_tools", tools_condition)
builder.add_edge("tools", "chat_with_tools")

#graph = builder.compile()

memory = MemorySaver()
graph = builder.compile(checkpointer=memory)

# Specify a thread
config = {"configurable": {"thread_id": "1"}}

# Specify an input

# Run

What gets saved: one checkpoint per step

The checkpointer doesn't just save the final answer; it saves the state after every step. For thread "1" after the two turns above there are 10 checkpoints (verified with graph.get_state_history(config)): five per run, one for the input and one after each node.

Saving every step is what makes more advanced features possible later: inspecting a past state, resuming after a crash, or pausing for a human to approve a tool call. The handbook chapters Persistence, Memory & Time Travel and Human-in-the-Loop & Interrupts cover those.

Memory in Studio vs memory in your code

The presenter's point at 133:19 is that Studio "has already this built in". When you run graphs through langgraph dev, the server itself provides persistence: every Studio thread is saved by the server, which is why earlier turns stayed visible in steps 6–13 and why the presenter used New Thread to start clean. You don't add a checkpointer for that.

In fact, langgraph dev refuses a graph that brings its own checkpointer. Graph 9 is not in the repo's langgraph.json, and the README suggests registering it as an exercise. Doing so makes the server stop at startup (verified with langgraph-api 0.13.2; even with the import fixed):

ValueError: Heads up! Your graph 'graph' from './module1/9_graph_agent_memory.py' includes a custom checkpointer (type <class 'langgraph.checkpoint.memory.InMemorySaver'>). With LangGraph API, persistence is handled automatically by the platform, so providing a custom checkpointer (type <class 'langgraph.checkpoint.memory.InMemorySaver'>) here isn't necessary and will be ignored when deployed.
…
langgraph_api.utils.errors.GraphLoadError: Failed to load graph '9_graph' from ./module1/9_graph_agent_memory.py: Heads up! Your graph 'graph' …
… [error    ] Application startup failed. Exiting.

Note the message also names InMemorySaver, the real class behind MemorySaver. So graph 9 is a plain-Python example. For Studio, register graph 8 (which has no checkpointer) and let the server remember. Step 17 shows the same split with a SQLite saver.

What you should see

  • With the import fixed: the script prints one line, the AI's answer to "Add 3 and 4." (7, in whatever words the model chooses).
  • A second invoke with the same config: the result holds the earlier messages too (8 instead of 4 for the two math questions).
  • A different thread_id: a fresh conversation that knows nothing of thread "1".
  • Run the script again: it starts from zero. MemorySaver lives only as long as the program.

Common mistakes

  • Running the repo file unchanged → NameError: name 'HumanMessage' is not defined. Add the import.
  • Forgetting the config on a graph with a checkpointer → ValueError: Checkpointer requires one or more of the following 'configurable' keys: thread_id, checkpoint_ns, checkpoint_id (verified). Pass config to every invoke.
  • Misspelling the key, like {"configurable": {"threadid": "1"}} → KeyError: 'thread_id' (verified). It must be exactly thread_id.
  • Creating a new MemorySaver() per run (for example inside a function). Each new saver is empty, so nothing is remembered. Create it once and compile once.
  • Expecting memory after a restart. In-memory means in this process only. Use SQLite (step 17).
  • Registering graph 9 in langgraph.json → "custom checkpointer" error and the server won't start. Studio already remembers threads.
  • Module-level demo code. Lines 52–60 run on every import, calling the model. Put them under if __name__ == "__main__": (step 15).

For what the checkpointer stores between steps and how a new input is merged into a saved thread, read How State Flows Through a Graph.
