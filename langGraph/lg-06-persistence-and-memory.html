Persistence, Memory & Time Travel

Checkpointers, threads, get_state, state history, long-term memory stores.

In step 14 the presenter added two things to the agent: a MemorySaver() passed to compile(checkpointer=...), and a config with a thread_id. After that, the agent remembered earlier turns. In step 17 you swapped the memory for a SQLite file so the conversation survived a restart. This chapter explains what is really going on underneath: what a checkpointer saves and when, what a thread is, how to read the saved state back, how to go back in time and try a different path, how to remember facts across conversations with a store, and how to stop a long conversation from growing forever.

Why this matters for your project. Every feature in the next chapters is built on the same saved state. Human approval (chapter 7) pauses a graph and resumes it later, which only works because the state was saved. Studio's thread list (chapter 8) is a view of saved checkpoints. If you understand checkpoints, those features stop feeling like magic.

Persistence in one sentence

Persistence means "saving data so it is still there later". In LangGraph, persistence works like this: after every step of the graph, the checkpointer writes a snapshot of the whole state, called a checkpoint, under a thread id. The next time you run the graph with the same thread id, LangGraph loads the newest checkpoint first and continues from there.

A "step" here is a superstep: one round in which every node that is ready runs. In the simple straight-line graphs from the course, one superstep is simply one node.

To see this clearly, here is a tiny graph with no model at all. It has two nodes that each add a word to a string. Every snippet in this chapter marked verified was run against LangGraph 1.2.11 (the version locked in the repo), and the printed output shown is the real output.

from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver


class State(TypedDict):
    text: str


def add_hello(state: State) -> State:
    return {"text": state["text"] + " hello"}


def add_world(state: State) -> State:
    return {"text": state["text"] + " world"}


builder = StateGraph(State)
builder.add_node("add_hello", add_hello)
builder.add_node("add_world", add_world)
builder.add_edge(START, "add_hello")
builder.add_edge("add_hello", "add_world")
builder.add_edge("add_world", END)
graph = builder.compile(checkpointer=InMemorySaver())

config = {"configurable": {"thread_id": "demo"}}
print(graph.invoke({"text": "say:"}, config))
# {'text': 'say: hello world'}

The result looks exactly like a graph without a checkpointer. The difference is hidden: four checkpoints now exist for the thread "demo". The diagram shows them.

New to "snapshot"? What a checkpoint really is

Think of a video game save. When you save, the game writes down everything needed to continue: your position, your inventory, which level you are on. If the game crashes, you load the save and carry on. A checkpoint is the same idea for a graph. It stores the values of every state field, plus "which nodes should run next", plus some bookkeeping (a step number, an id, the id of the previous checkpoint). Because each checkpoint points to the one before it, the saves form a chain you can walk backwards. That chain is what makes "time travel" possible later in this chapter.

The checkpointers you can choose

A checkpointer is just "where the snapshots are written". The graph code stays the same; only the object you pass to compile changes. These are the options you will meet as a beginner:

The presenter's graph 9 uses the older name; the official docs now use InMemorySaver. Second, the SQLite version from step 17 only changes three lines:

import sqlite3
from langgraph.checkpoint.sqlite import SqliteSaver

connection = sqlite3.connect("checkpoints.sqlite", check_same_thread=False)
graph = agent8.builder.compile(checkpointer=SqliteSaver(connection))

That is a shortened excerpt of 11_graph_sqlite_memory.py. Run 1 saved four messages; a brand-new process on the same thread continued to eight. A context-manager form also exists and was checked to work: with SqliteSaver.from_conn_string("checkpoints.sqlite") as checkpointer: ....

For PostgreSQL, the package langgraph-checkpoint-postgres is published on PyPI by the LangGraph team (MIT licence, source in the langchain-ai/langgraph repository). Its own README shows this shape. It was not run for this guide because it needs a running Postgres server, so treat it as a sketch and check the current docs:

# uv add langgraph-checkpoint-postgres
from langgraph.checkpoint.postgres import PostgresSaver

DB_URI = "postgresql://user:password@localhost:5432/mydb"
with PostgresSaver.from_conn_string(DB_URI) as checkpointer:
    checkpointer.setup()          # creates the tables the first time
    graph = builder.compile(checkpointer=checkpointer)
    graph.invoke(inputs, {"configurable": {"thread_id": "user-42"}})
The langgraph dev trap. The repo README suggests registering 9_graph_agent_memory.py in langgraph.json. With langgraph-api 0.13.2 this makes the server fail at startup with ValueError: Heads up! Your graph 'graph' from './module1/9_graph_agent_memory.py' includes a custom checkpointer (type <class 'langgraph.checkpoint.memory.InMemorySaver'>). With LangGraph API, persistence is handled automatically by the platform ... followed by "Application startup failed". Keep graph 9 for plain-Python runs, and register graphs compiled without a checkpointer (like graph 8) for Studio.

Threads: one notebook per conversation

A thread is a named sequence of checkpoints. The name is the thread_id you put in the config. You can picture the checkpointer as a shelf of notebooks: each thread is one notebook, and each checkpoint is one page in it. Different thread ids never see each other's pages.

config = {"configurable": {"thread_id": "1"}}
graph.invoke({"messages": [HumanMessage(content="Add 3 and 4.")]}, config)
graph.invoke({"messages": [HumanMessage(content="Now multiply that by 10.")]}, config)   # remembers 7

other = {"configurable": {"thread_id": "2"}}
graph.invoke({"messages": [HumanMessage(content="What was my last result?")]}, other)  # empty memory

That is the demo from the fixed graph 9 (step 15). The step 18 test test_memory_keeps_threads_apart checks exactly this: after two turns thread "a" holds 4 messages, while a first turn on thread "b" returns only 2.

New to the config dictionary? Why {"configurable": {...}}

invoke and stream take an optional second argument called the config. It is a plain dictionary for "settings of this run" that are not part of the state. Inside it, the "configurable" key holds values that components look up by name: the checkpointer looks for thread_id (and optionally checkpoint_id to load an older page). Other top-level keys exist too, such as "recursion_limit" (chapter 3). If you compile with a checkpointer and forget the config, LangGraph 1.2.11 stops with ValueError: Checkpointer requires one or more of the following 'configurable' keys: thread_id, checkpoint_ns, checkpoint_id.

Rule of thumb for real apps. A thread id is only a label, not a password. Build it on the server from something you trust, such as the logged-in user's id plus a conversation number. Never let a browser send any thread id it likes, or one user could read another user's conversation.

Reading the saved state: get_state

Once a graph has a checkpointer you can ask "what does this thread look like right now?" without running anything. graph.get_state(config) returns a StateSnapshot object. Continuing the tiny graph from above:

snapshot = graph.get_state(config)
print(snapshot.values)            # {'text': 'say: hello world'}
print(snapshot.next)              # ()   empty: the graph finished
print(snapshot.metadata["step"])  # 2
print(snapshot.config["configurable"]["checkpoint_id"])   # a long id, different every run
FieldWhat it holdsWhen you use it
valuesthe state dictionary at that checkpointshow the conversation, count messages (step 17 prints how many were saved)
nexta tuple of node names that will run next; empty when finished"is this thread paused?" (see chapter 7)
configthe config that points to this exact checkpoint (includes checkpoint_id)replay or fork from here
metadatabookkeeping, including stepdebugging, ordering
tasksthe pending tasks, including any interrupts waiting for an answerhuman-in-the-loop

The step 17 chat loop ends with exactly this call: graph.get_state(config).values.get("messages", []) to print how many messages are stored for the thread.

History, replay and time travel

Because every checkpoint points to the previous one, you can list them all with graph.get_state_history(config). It yields snapshots newest first. Real output for the tiny graph:

for s in graph.get_state_history(config):
    print(s.metadata["step"], s.next, s.values)

# 2 () {'text': 'say: hello world'}
# 1 ('add_world',) {'text': 'say: hello'}
# 0 ('add_hello',) {'text': 'say:'}
# -1 ('__start__',) {}

"Time travel" is LangGraph's name for two things you can do with an old checkpoint:

  1. Replay. Pass an old checkpoint's config to invoke with None as the input. LangGraph loads that page and runs the nodes that were "next" from there. Useful to reproduce a bug: "run again from just before the tool call".
  2. Fork. First change the old state with update_state, which writes a new checkpoint branching off the old one, then continue from the config it returns. Useful for "what if the user had said something else?"
history = list(graph.get_state_history(config))
before_world = next(s for s in history if s.next == ("add_world",))

# replay: run add_world again from that bookmark
print(graph.invoke(None, before_world.config))
# {'text': 'say: hello world'}

# fork: change the past, then continue
fork_config = graph.update_state(before_world.config, {"text": "say: hi"})
print(graph.invoke(None, fork_config))
# {'text': 'say: hi world'}

One detail surprises people: after the replay and the fork above, the thread's history was 8 checkpoints long, not 4. Every run and every update_state adds pages; none are deleted. And get_state(config) (without a checkpoint_id) now returns the fork's result, because it is the newest page.

Changing state by hand: update_state

graph.update_state(config, values, as_node=None) writes a new checkpoint as if a node had returned values. Three things to know:

  • Reducers still apply. The update is merged exactly like a node's return value. For a plain field it overwrites; for messages in MessagesState the add_messages reducer appends, or replaces a message that has the same id.
  • as_node decides what runs next. LangGraph pretends the update came from that node, so the next step follows that node's outgoing edges. In the tiny graph, update_state(config, {"text": "edited"}, as_node="add_world") left next empty, because add_world leads to END.
  • It returns a config pointing at the new checkpoint, which you can pass to invoke(None, ...).

To delete messages from a MessagesState thread, send RemoveMessage objects; add_messages understands them. Verified on a thread with 6 messages:

from langchain.messages import RemoveMessage

messages = graph.get_state(config).values["messages"]      # 6 messages
graph.update_state(config, {"messages": [RemoveMessage(id=m.id) for m in messages[:2]]})
print([m.content for m in graph.get_state(config).values["messages"]])
# ['two', 'ok', 'three', 'ok']

Short-term vs long-term memory

Everything so far is short-term memory: it belongs to one thread. Start a new thread and it is gone. Often you also want long-term memory: facts about a user (their name, their level, what they prefer) that every future conversation can use. LangGraph keeps that in a separate object called a store.

A store organises items by a namespace (a tuple of strings, like a folder path) and a key (like a file name). The value is a dictionary. LangGraph 1.2.11 ships InMemoryStore for learning; like InMemorySaver it forgets everything when Python exits.

from langgraph.store.memory import InMemoryStore

store = InMemoryStore()
store.put(("users", "luca"), "profile", {"name": "Luca", "likes": "fractions"})

item = store.get(("users", "luca"), "profile")
print(item.value)          # {'name': 'Luca', 'likes': 'fractions'}
print([i.value for i in store.search(("users", "luca"))])   # every item in that namespace

To use the store inside nodes, pass it to compile(store=store). A node can then read it through the runtime. The runtime also carries a context: per-run data such as "which user is this", passed with invoke(..., context=...) and described by context_schema. This was run with two users:

from dataclasses import dataclass
from langgraph.graph import StateGraph, START, MessagesState
from langgraph.runtime import Runtime
from langgraph.checkpoint.memory import InMemorySaver
from langchain.messages import AIMessage, HumanMessage


@dataclass
class Context:
    user_id: str


def greet(state: MessagesState, runtime: Runtime[Context]):
    profile = runtime.store.get(("users", runtime.context.user_id), "profile")
    name = profile.value["name"] if profile else "stranger"
    return {"messages": [AIMessage(content=f"Hello {name}")]}


builder = StateGraph(MessagesState, context_schema=Context)
builder.add_node("greet", greet)
builder.add_edge(START, "greet")
graph = builder.compile(checkpointer=InMemorySaver(), store=store)

graph.invoke({"messages": [HumanMessage(content="hi")]},
             {"configurable": {"thread_id": "x"}}, context=Context(user_id="luca"))  # Hello Luca
graph.invoke({"messages": [HumanMessage(content="hi")]},
             {"configurable": {"thread_id": "y"}}, context=Context(user_id="ana"))   # Hello stranger

In a real agent, a node like greet would put the profile into the system message before calling the model, and a later node (or a tool) would call store.put when the user says something worth remembering. Deciding what to remember is the hard part, and is a design decision, not a library feature. Stores can also be configured for meaning-based (semantic) search; see "Memory" in the docs linked below if you need that.

New to "namespace"? Why the key is a tuple

A namespace groups related items so they do not collide, the way folders keep two files called notes.txt apart. ("users", "luca") and ("users", "ana") are two folders inside "users"; both can hold an item called "profile". Putting the user id in the namespace also makes it easy to delete everything about one user, which matters if someone asks you to remove their data.

When the history gets long

With MessagesState, every turn adds at least two messages, and an agent turn with tools adds four or more (Human, AI tool call, Tool, AI answer, as in step 13). The whole list is sent to the model on every call. Over time that means slower answers, higher cost (you pay per token) and finally an error when the list no longer fits in the model's context window. Three common fixes:

ApproachWhat changesTrade-off
Trim before calling the modelthe node sends only the last part of the history; the saved thread keeps everythingsimple; the model forgets old details
Delete old messagesRemoveMessage removes them from the saved statesmaller checkpoints; the data is gone from the latest state
Summarisea node asks the model to summarise old messages, stores the summary, deletes the originalskeeps the gist; costs an extra model call; summaries can lose facts

trim_messages from langchain_core.messages does the first one. This verified call keeps the last messages that fit a budget, and makes sure the kept part starts with a human message (a model is confused by a history that starts with a tool result). Here token_counter=len counts messages instead of tokens, which keeps the example simple; in a real app you would pass the model so it counts real tokens.

from langchain_core.messages import trim_messages

# messages = [Human 'one', AI 'ok', Human 'two', AI 'ok', Human 'three', AI 'ok']
trimmed = trim_messages(messages, strategy="last", token_counter=len,
                        max_tokens=3, start_on="human")
print([m.content for m in trimmed])    # ['three', 'ok']

Inside graph 8 you would apply it in chat_with_tools just before the model call, for example model_llm_with_tools.invoke([system_message] + trim_messages(state["messages"], ...)). Be careful with agents: never cut between an AI message that asked for a tool and the matching tool message, or the model provider will reject the request. Trimming on whole turns (start_on="human") avoids that.

Common misconceptions
  • "The model remembers the conversation." It does not. LangGraph loads the saved messages and sends them again on every call.
  • "MemorySaver saves to disk." It does not; it is RAM only. Use SqliteSaver or Postgres to survive a restart (step 17).
  • "I should add a checkpointer for Studio." No. langgraph dev refuses graphs that bring their own checkpointer; the server persists threads for you.
  • "Replay gives the same answer." Only for code without randomness. A model is called again and may answer differently.
  • "Time travel deletes the later history." It never deletes; forks are new branches.
  • "The store is filled automatically." Only the checkpointer is automatic. The store contains exactly what your code writes.
Recap
  • A checkpointer saves a checkpoint (state + "what runs next") after every superstep, under a thread_id.
  • InMemorySaver (= MemorySaver) is RAM only; SqliteSaver (langgraph-checkpoint-sqlite) and PostgresSaver (langgraph-checkpoint-postgres) persist. langgraph dev brings its own.
  • Pass {"configurable": {"thread_id": ...}} on every call; without it you get a ValueError.
  • get_state shows the latest snapshot (values, next, config, tasks); get_state_history lists all of them, newest first.
  • Replay = invoke(None, old_config); fork = update_state(old_config, ...) then invoke. Nothing is deleted.
  • A store (InMemoryStore, compile(store=...), runtime.store) holds long-term facts across threads.
  • Long histories: trim before the model call, remove with RemoveMessage, or summarise.
