Goal

The math teacher from step 13 can multiply, add and subtract. In this step you give it a fourth tool, division, in a new file module1/10_graph_division_tool.pymodule1/10-graph-division-tool.ts. Division is the first tool that can fail: you can't divide by zero. That makes it the perfect example for a question every agent builder runs into sooner or later: what happens when a tool throws an error?

You'll see that, by default, an error inside a tool crashes the whole graph run, and that one argument, handle_tool_errors=True, turns the error into a message the model can read and answer.

Here the two languages differ. In Python, by default, an error inside a tool crashes the whole graph run. In LangGraph.js, ToolNode has handleToolErrors set to true by default and catches any error a tool throws: the error becomes a message the model can read and answer. The file writes the option out so the choice is visible, and its demo shows what false does.

The README suggests adding the tool to 8_graph_agent.py. We use a new file so graph 8 stays exactly as in the video and you can compare the two side by side in Studio.

from langgraph.graph import StateGraph, START, MessagesState
from langchain_openai import ChatOpenAI
from dotenv import load_dotenv
from langchain.tools import tool
from langgraph.prebuilt import ToolNode, tools_condition
from langchain.messages import SystemMessage

load_dotenv()

model_llm = ChatOpenAI(model="gpt-4o")

@tool
def multiply(nb1: int, nb2: int) -> int:
    """Return the product of 2 numbers."""
    return nb1 * nb2

@tool
def addition(nb1: int, nb2: int) -> int:
    """Return the sum of 2 numbers."""
    return nb1 + nb2

@tool
def subtraction(nb1: int, nb2: int) -> int:
    """Return nb1 minus nb2."""
    return nb1 - nb2

@tool
def division(nb1: float, nb2: float) -> float:
    """Return nb1 divided by nb2. nb2 must not be 0."""
    if nb2 == 0:
        raise ValueError("Cannot divide by zero. Ask the user for a different divisor.")
    return nb1 / nb2

tools = [multiply, addition, subtraction, division]
model_llm_with_tools = model_llm.bind_tools(tools)

system_message = SystemMessage(content="You are a helpful math teacher. Use the tools for every calculation.")

def chat_with_tools(state: MessagesState) -> MessagesState:
    return {"messages": [model_llm_with_tools.invoke([system_message] + state["messages"])]}

builder = StateGraph(MessagesState)

builder.add_node("chat_with_tools", chat_with_tools)
# handle_tool_errors=True turns an exception inside a tool into a ToolMessage the model can read,
# instead of crashing the whole graph run
builder.add_node("tools", ToolNode(tools, handle_tool_errors=True))

builder.add_edge(START, "chat_with_tools")
builder.add_conditional_edges("chat_with_tools", tools_condition)
builder.add_edge("tools", "chat_with_tools")

graph = builder.compile()
import { END, MessagesAnnotation, START, StateGraph } from "@langchain/langgraph";
import { ToolNode, toolsCondition } from "@langchain/langgraph/prebuilt";
import { HumanMessage, SystemMessage, tool } from "langchain";
import { z } from "zod";
import { isMain } from "../src/is-main.js";
import { getModel } from "../src/model.js";
import { show } from "../src/show.js";

const modelLlm = getModel();

// z.coerce.number() also accepts "4" (some models, like llama3.2, send numbers as text)
const numbers = z.object({ nb1: z.coerce.number(), nb2: z.coerce.number() });

const multiply = tool(({ nb1, nb2 }) => nb1 * nb2, { name: "multiply", description: "Return the product of 2 numbers.", schema: numbers });
const addition = tool(({ nb1, nb2 }) => nb1 + nb2, { name: "addition", description: "Return the sum of 2 numbers.", schema: numbers });
const subtraction = tool(({ nb1, nb2 }) => nb1 - nb2, { name: "subtraction", description: "Return nb1 minus nb2.", schema: numbers });

const division = tool(
  ({ nb1, nb2 }) => {
    if (nb2 === 0) {
      // in JavaScript 5 / 0 is Infinity, not an error, so we throw one ourselves
      throw new Error("Cannot divide by zero. Ask the user for a different divisor.");
    }
    return nb1 / nb2;
  },
  { name: "division", description: "Return nb1 divided by nb2. nb2 must not be 0.", schema: numbers },
);

const tools = [multiply, addition, subtraction, division];
const modelLlmWithTools = modelLlm.bindTools(tools);

const systemMessage = new SystemMessage("You are a helpful math teacher. Use the tools for every calculation.");

async function chatWithTools(state: typeof MessagesAnnotation.State) {
  return { messages: [await modelLlmWithTools.invoke([systemMessage, ...state.messages])] };
}

/** Build the agent. handleToolErrors decides what happens when a tool throws. */
function buildGraph(handleToolErrors: boolean) {
  return new StateGraph(MessagesAnnotation)
    .addNode("chat_with_tools", chatWithTools)
    .addNode("tools", new ToolNode(tools, { handleToolErrors }))
    .addEdge(START, "chat_with_tools")
    .addConditionalEdges("chat_with_tools", toolsCondition, ["tools", END])
    .addEdge("tools", "chat_with_tools")
    .compile();
}

// true is already the LangGraph.js default (Python's default only catches bad arguments);
// we write it out so the choice is visible: the error becomes a ToolMessage the model can read
export const graph = buildGraph(true);

if (isMain(import.meta.url)) {
  const question = { messages: [new HumanMessage("Divide 5 by 0")] };

  console.log("1) handleToolErrors: true (the default)");
  const result = await graph.invoke(question);
  result.messages.forEach((message) => console.log("  ", show(message)));

  console.log("2) handleToolErrors: false");
  try {
    await buildGraph(false).invoke(question);
  } catch (error) {
    console.log("   the whole run crashed:", (error as Error).message);
  }
}

New to int and float? Why the division tool uses floats

Python has two main number types. An int is a whole number: 7, -3, 0. A float is a number with a decimal point: 3.5, 0.25, 7.0.

print(7 / 2)    # 3.5   "/" always gives a float
print(6 / 2)    # 3.0   even when it divides evenly
print(7 // 2)   # 3     "//" is floor division (drops the decimals)

For tools the type hint is more than a note: LangChain validates the model's arguments against it. With nb1: int, a call with 7.5 is rejected (verified: Input should be a valid integer, got a number with a fractional part). With nb1: float, both 7 and 7.5 are accepted. Division is the tool where decimals are normal, so it gets floats.

New to z.coerce.number()? Numbers that arrive as text

JavaScript has a single number type: 7 and 3.5 are both number, so z.number() accepts whole numbers and decimals alike. The question is what happens when the model sends "5", a string, instead of 5.

  • z.number() rejects it. Python's Pydantic would quietly convert "5" to 5; Zod does not convert by default.
  • z.coerce.number() first converts the value with Number(...), then checks it. "5" becomes 5. The JSON schema the model sees still says "type": "number".

This is not a theoretical case: llama3.2 sent division({"nb1":"5","nb2":"0"}) in our real run. See "Numbers sent as text" below for what happened before the fix.

When a tool fails: two kinds of errors

A ToolNode can meet two very different kinds of errors, and by default it treats them differently.

New to raise? How a function reports that something went wrong

raise SomeError("message") stops the function immediately and sends an exception up to whoever called it. If nobody catches it with try/except, the program stops and prints a traceback ending in the error type and your message.

ValueError is Python's standard error for "the type is right but the value isn't acceptable", which fits "0 is a number, but not a valid divisor".

def check_age(age: int) -> int:
    if age < 0:
        raise ValueError("age cannot be negative")
    return age

The ToolMessage text is built by LangGraph from a template, "Error: {error}\n Please fix your mistakes.", where {error} is repr() of your exception. That's why your error message should be written for the model to read. The fake model simply repeats the tool result; a real model reads "Cannot divide by zero. Ask the user for a different divisor." and typically answers along the lines of "You can't divide by zero. Which number would you like to divide 5 by instead?"

A ToolNode can meet two very different kinds of errors: bad arguments (the model sent values that don't fit the schema) and an error inside the tool (your own code threw). In LangGraph.js 1.5 the default catches both. This is a real difference from Python, whose default only catches bad arguments.

New to throw? How a function reports that something went wrong

throw new Error("message") stops the function immediately and sends the error up to whoever called it. If nobody catches it with try/catch, the program stops and prints the error with a stack trace (the list of function calls that led there).

Error is JavaScript's general error class. Its text is in error.message, which is what ToolNode puts in the ToolMessage.

Part 1: llama3.2 asks for division, the tool throws, ToolNode catches the error and returns it as a ToolMessage, and the model answers the user. The text is built from a template: "Error: " + error.message + "\n Please fix your mistakes.". That is why the line break appears in the middle of the tool line. Python's version shows the error class too (Error: ValueError('Cannot divide …')); JavaScript's shows only the message. Part 2: with false nothing catches the error, the whole invoke fails, and our catch prints the tool's message. The user would get no answer at all.

New to handle_tool_errors? All the values it accepts

The installed LangGraph documents these options for ToolNode(tools, handle_tool_errors=...):

  • True: catch every error and send the default template, Error: {repr(e)}\n Please fix your mistakes.
  • a string, e.g. "The tool failed, apologise to the user.": catch every error and send this text instead.
  • an exception type or a tuple of types, e.g. ValueError: catch only those, crash on the rest.
  • a function that takes the exception and returns a string: full control over the message.
  • False: never catch, not even bad arguments.

True is the simplest choice for learning. In a real app, catching only the errors you expect (handle_tool_errors=ValueError) keeps real bugs visible.

Numbers sent as text (real finding). Our first version used z.number(). llama3.2 sent division({"nb1":"5","nb2":"0"}), with the numbers in quotes, and Zod rejected the call before the tool ran. So the divide-by-zero check was never reached: the error the model got was about the schema, not about zero. The model still answered sensibly, but for the wrong reason. Is it safe to show error text to the model? The model sees whatever your exception message says. Write messages for it ("Cannot divide by zero. Ask the user for a different divisor.") and don't put secrets, file paths or stack traces in them. Anything the model reads can end up in its answer to the user.

Common mistakes

  • Adding the tool to only one place. If division is bound to the model but missing from the ToolNode, the model can ask for it and the ToolNode can't find it. Keep one tools list (line 29).
  • Removing the zero check because "JavaScript doesn't crash". Right, it doesn't: 5 / 0 is Infinity, and the model would report it as a result. Throw your own error.
  • Using z.number() with a small local model. Arguments sent as text are rejected before your tool runs (see "Numbers sent as text"). Use z.coerce.number().
  • Returning the error instead of throwing it, e.g. return "error". It "works", but the result looks like a normal success. Throwing marks the ToolMessage as an error (status: "error").
  • Setting handleToolErrors: false without your own try/catch: every tool error ends the run with no answer for the user.
  • Expecting the model to always call division. For "half of 10" a model might answer 5 directly. The system prompt asks for tools, but the model decides.

Recap
  • Graph 10 is graph 8 plus a division tool, in a new file registered as 10_graph (README exercise 5).
  • float type hints become "number" in the schema the model reads, so decimals are accepted; / returns a float.
  • The tool raises a ValueError with a message written for the model when nb2 is 0.
  • By default a ToolNode only handles bad arguments; an error inside a tool crashes the run (verified).
  • ToolNode(tools, handle_tool_errors=True) turns any tool error into a ToolMessage Error: ValueError(...), so the model can explain and the user still gets an answer (verified).
  • JavaScript has one number type and 5 / 0 is Infinity, so the tool throws its own error with a message written for the model.
  • In LangGraph.js, new ToolNode(tools) already has handleToolErrors: true and catches any error, bad arguments or thrown by the tool; false makes the whole run fail (both real runs).
  • llama3.2 sent the numbers as text; z.number() rejected them before the zero check ran. z.coerce.number() fixes it.
