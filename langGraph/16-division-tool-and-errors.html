Add a Division Tool & Handle Tool Errors

A fourth tool, dividing by zero, and handle_tool_errors so the model can recover.

Extension · verified against LangGraph 1.2.11

Extension: not in the video. This step completes README exercise 5, "Add a division tool". module1/10_graph_division_tool.py was run against LangGraph 1.2.11 with the offline harness from step 15 (a fake chat model that requests the division tool when the question says "divide" and has two numbers). Both error behaviours on this page, the crash and the recovered run, are real outputs from that run, and langgraph dev was started to confirm that 10_graph loads.

What that proves: the tool, its types, the wiring and the error handling work with these versions. What it doesn't: how a real model words its reply after an error. Try it with your own key.

Goal

The math teacher from step 13 can multiply, add and subtract. In this step you give it a fourth tool, division, in a new file module1/10_graph_division_tool.py. Division is the first tool that can fail: you can't divide by zero. That makes it the perfect example for a question every agent builder runs into sooner or later: what happens when a tool throws an error?

You'll see that, by default, an error inside a tool crashes the whole graph run, and that one argument, handle_tool_errors=True, turns the error into a message the model can read and answer.

The README suggests adding the tool to 8_graph_agent.py. We use a new file so graph 8 stays exactly as in the video and you can compare the two side by side in Studio.

Create the file

  1. Create module1/10_graph_division_tool.py

    In VS Code, right-click the module1 folder, choose New File, and name it 10_graph_division_tool.py. Paste the code below. (It was written from scratch so every line is explained, but it's graph 8 from step 15 plus a few lines.)

  2. Register it in langgraph.json

    Add "10_graph": "./module1/10_graph_division_tool.py:graph" as the last entry of "graphs", with a comma after the 8_graph line. The full file is in step 15, fix 7.

  3. Run it

    Either in Studio with uv run langgraph dev (pick 10_graph in the graph picker at the top), or from the terminal with the command in "Try it" below.

from langgraph.graph import StateGraph, START, MessagesState
from langchain_openai import ChatOpenAI
from dotenv import load_dotenv
from langchain.tools import tool
from langgraph.prebuilt import ToolNode, tools_condition
from langchain.messages import SystemMessage

load_dotenv()

model_llm = ChatOpenAI(model="gpt-4o")

@tool
def multiply(nb1: int, nb2: int) -> int:
    """Return the product of 2 numbers."""
    return nb1 * nb2

@tool
def addition(nb1: int, nb2: int) -> int:
    """Return the sum of 2 numbers."""
    return nb1 + nb2

@tool
def subtraction(nb1: int, nb2: int) -> int:
    """Return nb1 minus nb2."""
    return nb1 - nb2

@tool
def division(nb1: float, nb2: float) -> float:
    """Return nb1 divided by nb2. nb2 must not be 0."""
    if nb2 == 0:
        raise ValueError("Cannot divide by zero. Ask the user for a different divisor.")
    return nb1 / nb2

tools = [multiply, addition, subtraction, division]
model_llm_with_tools = model_llm.bind_tools(tools)

system_message = SystemMessage(content="You are a helpful math teacher. Use the tools for every calculation.")

def chat_with_tools(state: MessagesState) -> MessagesState:
    return {"messages": [model_llm_with_tools.invoke([system_message] + state["messages"])]}

builder = StateGraph(MessagesState)

builder.add_node("chat_with_tools", chat_with_tools)
# handle_tool_errors=True turns an exception inside a tool into a ToolMessage the model can read,
# instead of crashing the whole graph run
builder.add_node("tools", ToolNode(tools, handle_tool_errors=True))

builder.add_edge(START, "chat_with_tools")
builder.add_conditional_edges("chat_with_tools", tools_condition)
builder.add_edge("tools", "chat_with_tools")

graph = builder.compile()

New to int and float? Why the division tool uses floats

Python has two main number types. An int is a whole number: 7, -3, 0. A float is a number with a decimal point: 3.5, 0.25, 7.0.

print(7 / 2)    # 3.5   "/" always gives a float
print(6 / 2)    # 3.0   even when it divides evenly
print(7 // 2)   # 3     "//" is floor division (drops the decimals)

For tools the type hint is more than a note: LangChain validates the model's arguments against it. With nb1: int, a call with 7.5 is rejected (verified: Input should be a valid integer, got a number with a fractional part). With nb1: float, both 7 and 7.5 are accepted. Division is the tool where decimals are normal, so it gets floats.

When a tool fails: two kinds of errors

A ToolNode can meet two very different kinds of errors, and by default it treats them differently.

New to raise? How a function reports that something went wrong

raise SomeError("message") stops the function immediately and sends an exception up to whoever called it. If nobody catches it with try/except, the program stops and prints a traceback ending in the error type and your message.

ValueError is Python's standard error for "the type is right but the value isn't acceptable", which fits "0 is a number, but not a valid divisor".

def check_age(age: int) -> int:
    if age < 0:
        raise ValueError("age cannot be negative")
    return age

Behaviour 1: the default crashes (verified)

To see it, change line 47 to builder.add_node("tools", ToolNode(tools)) (no handle_tool_errors) and ask "Divide 5 by 0". The model correctly asks for division with 5 and 0, the tool raises, and the run stops:

builder.add_node("tools", ToolNode(tools))
Traceback (most recent call last):
  ...
ValueError: Cannot divide by zero. Ask the user for a different divisor.
During task with name 'tools' and id '7bd3e927-...'

The last line is LangGraph telling you which node was running when it failed: tools. The user gets no answer at all.

Bad arguments, on the other hand, are handled even by default. We sent the ToolNode a call with nb2="abc" and it returned this ToolMessage (with status="error") instead of crashing:

Error invoking tool 'division' with kwargs {'nb1': 5, 'nb2': 'abc'} with error:
 nb2: Input should be a valid number, unable to parse string as a number
 Please fix the error and try again.

Behaviour 2: handle_tool_errors=True recovers (verified)

With line 47 as in the file, the same question runs to the end. The messages in the final state are:

HumanMessage  'Divide 5 by 0'
AIMessage     ''   tool_calls: division(nb1=5, nb2=0)
ToolMessage   "Error: ValueError('Cannot divide by zero. Ask the user for a different divisor.')\n Please fix your mistakes."   status='error'
AIMessage     '(fake model) The answer is Error: ValueError(...) ...'

The ToolMessage text is built by LangGraph from a template, "Error: {error}\n Please fix your mistakes.", where {error} is repr() of your exception. That's why your error message should be written for the model to read. The fake model simply repeats the tool result; a real model reads "Cannot divide by zero. Ask the user for a different divisor." and typically answers along the lines of "You can't divide by zero. Which number would you like to divide 5 by instead?"

New to handle_tool_errors? All the values it accepts

The installed LangGraph documents these options for ToolNode(tools, handle_tool_errors=...):

  • True: catch every error and send the default template, Error: {repr(e)}\n Please fix your mistakes.
  • a string, e.g. "The tool failed, apologise to the user.": catch every error and send this text instead.
  • an exception type or a tuple of types, e.g. ValueError: catch only those, crash on the rest.
  • a function that takes the exception and returns a string: full control over the message.
  • False: never catch, not even bad arguments.

True is the simplest choice for learning. In a real app, catching only the errors you expect (handle_tool_errors=ValueError) keeps real bugs visible.

Is it safe to show error text to the model? The model sees whatever your exception message says. Write messages for it ("Cannot divide by zero. Ask the user for a different divisor.") and don't put secrets, file paths or stack traces in them. Anything the model reads can end up in its answer to the user.

  • Divide 5 by 0: the tool message contains the error text, and the model still answers.
  • What is (12 * 7) / 4?: a real model usually calls multiply first, then division with 84 and 4, so the loop runs twice.

Common mistakes

  • Adding the tool to only one place. If division is bound to the model but missing from the ToolNode, the model can ask for it and the ToolNode can't find it. Keep one tools list (line 34).
  • Forgetting the comma in langgraph.json after the 8_graph line. The server can't read the file and won't start.
  • Returning the error instead of raising it, e.g. return "error" from a function declared -> float. It "works", but the result looks like a normal success and the type hint lies. Raising plus handle_tool_errors marks the message as an error (status="error").
  • A wrong or placeholder key. With sk-... placeholders the run fails in chat_with_tools with Error code: 401 ... Incorrect API key provided (we saw this when checking the command above).
  • Expecting the model to always call division. For "half of 10" a model might answer 5 directly. The system prompt asks for tools, but the model decides.
Recap
  • Graph 10 is graph 8 plus a division tool, in a new file registered as 10_graph (README exercise 5).
  • float type hints become "number" in the schema the model reads, so decimals are accepted; / returns a float.
  • The tool raises a ValueError with a message written for the model when nb2 is 0.
  • By default a ToolNode only handles bad arguments; an error inside a tool crashes the run (verified).
  • ToolNode(tools, handle_tool_errors=True) turns any tool error into a ToolMessage Error: ValueError(...), so the model can explain and the user still gets an answer (verified).
