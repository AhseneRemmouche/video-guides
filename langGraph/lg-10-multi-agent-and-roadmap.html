Subgraphs, Multi-Agent Systems & Your Roadmap

Composing graphs, supervisor and handoff patterns, and what to learn next.

The course ends with one agent: graph 9, a math teacher with three tools and memory. Real applications often need more than one "brain": a researcher and a writer, a triage step that sends questions to the right specialist, a team of agents that hand work to each other. LangGraph builds these from a single idea you already know, a graph can be a node in another graph. This chapter shows how subgraphs work, the main multi-agent patterns, when not to use them, and then gives you a learning roadmap and practice projects that grow out of graphs 8 and 9.

Why this matters for your project. At the end of the video (136:17) the presenter says "we are just scratching the surface. There's a lot more to be done" and asks viewers to request a continuation. This chapter is a map of that "more": what to learn next, in which order, and small projects that practise each step using the code you already have.

Subgraphs: a graph inside a graph

A compiled graph is a CompiledStateGraph, and LangGraph lets you pass one to add_node exactly like a function. From the outside it behaves like one node: it receives the state, runs all its own nodes, and returns an update. Reasons to do this:

  • Organisation: build and test a "research team" graph on its own, then plug it into a bigger app.
  • Reuse: the same subgraph in several parent graphs.
  • Teams: different people own different subgraphs.
  • Multi-agent systems: each agent is its own graph (for example the ReAct loop from step 13).

Way 1: shared state keys, add the compiled graph directly

If the subgraph and the parent use the same state keys (here both use MessagesState), add the compiled subgraph as a node. Verified with LangGraph 1.2.11:

from langgraph.graph import StateGraph, START, MessagesState
from langgraph.checkpoint.memory import InMemorySaver
from langchain.messages import AIMessage, HumanMessage


def research(state: MessagesState):
    return {"messages": [AIMessage(content="research notes", name="researcher")]}

sub = StateGraph(MessagesState)
sub.add_node("research", research)
sub.add_edge(START, "research")
research_graph = sub.compile()                  # no checkpointer on the subgraph


def writer(state: MessagesState):
    notes = state["messages"][-1].content
    return {"messages": [AIMessage(content=f"article based on: {notes}", name="writer")]}

parent = StateGraph(MessagesState)
parent.add_node("research_team", research_graph)   # a compiled graph as a node
parent.add_node("writer", writer)
parent.add_edge(START, "research_team")
parent.add_edge("research_team", "writer")
graph = parent.compile(checkpointer=InMemorySaver())

out = graph.invoke({"messages": [HumanMessage(content="write about owls")]},
                   {"configurable": {"thread_id": "1"}})
print([(m.type, m.content) for m in out["messages"]])
# [('human', 'write about owls'), ('ai', 'research notes'), ('ai', 'article based on: research notes')]

Notice that only the parent gets a checkpointer; the subgraph uses the parent's automatically. To see inside the subgraph, draw with graph.get_graph(xray=True).draw_mermaid() (the Mermaid text then contains a subgraph research_team block), and stream with subgraphs=True. The verified stream printed three chunks: first ('research_team:<id>',) ['research'] from inside the subgraph, then () ['research_team'] and () ['writer'] from the parent. The tuple is the "namespace", the path to where the chunk came from.

Way 2: different state, call the subgraph from a function

If the subgraph has its own state shape, wrap it in a normal node function that translates in and out:

from typing_extensions import TypedDict


class NotesState(TypedDict):
    topic: str
    notes: str

def find_notes(state: NotesState):
    return {"notes": f"3 facts about {state['topic']}"}

nb = StateGraph(NotesState)
nb.add_node("find_notes", find_notes)
nb.add_edge(START, "find_notes")
notes_graph = nb.compile()


def call_notes(state: MessagesState):                  # parent node
    result = notes_graph.invoke({"topic": state["messages"][-1].content, "notes": ""})
    return {"messages": [AIMessage(content=result["notes"])]}
# with input "owls" the parent's last message becomes "3 facts about owls"

One more useful fact: LangChain's create_agent (chapter 5) also returns a CompiledStateGraph. Verified: an agent made with create_agent(model, tools=[multiply], name="math_expert") and a fake model, added with parent.add_node("math_expert", agent), produced Human, AI (tool call), Tool "84", AI inside the parent graph. Prebuilt agents and hand-built graphs mix freely.

Multi-agent systems

A multi-agent system is a graph where several nodes are agents, each with its own prompt and tools, and something decides who works next. Why bother, when one agent with all the tools might do?

Reason to splitReason not to
Each agent gets a short, focused prompt and a small tool list. Models choose tools more reliably from 3 tools than from 30.More model calls: someone has to decide who works next, and that is usually another call.
You can use a different model per agent (cheap for triage, strong for hard work).Harder to debug: the bug may be in a handoff, not in an agent.
Agents can be built and tested separately (subgraphs).Agents can pass work back and forth forever; you need limits.
Rule of thumb. Start with one agent (graph 8). Split only when you can name the problem a split solves: too many tools, prompts that contradict each other, or parts that need different models or permissions.

Pattern 1: a supervisor (or router) in the middle

One node decides which specialist runs, the specialist reports back, and the supervisor decides again or finishes. The decision can be plain code, as here, or a model call with structured output. This version routes with Command (chapter 3) and was verified:

from typing import Literal
from langgraph.graph import END
from langgraph.types import Command


def supervisor(state: MessagesState) -> Command[Literal["math_agent", "writer_agent", "__end__"]]:
    last = state["messages"][-1]
    if last.type == "human":
        goto = "math_agent" if any(ch.isdigit() for ch in last.content) else "writer_agent"
        return Command(goto=goto)
    return Command(goto=END)          # a specialist has answered: finish


def math_agent(state: MessagesState):       # in a real app: graph 8, added as a subgraph
    return {"messages": [AIMessage(content="84", name="math_agent")]}

def writer_agent(state: MessagesState):
    return {"messages": [AIMessage(content="a poem", name="writer_agent")]}

builder = StateGraph(MessagesState)
builder.add_node("supervisor", supervisor)
builder.add_node("math_agent", math_agent)
builder.add_node("writer_agent", writer_agent)
builder.add_edge(START, "supervisor")
builder.add_edge("math_agent", "supervisor")
builder.add_edge("writer_agent", "supervisor")
graph = builder.compile()
# "12 times 7?"   -> ['12 times 7?', '84']
# "a poem please" -> ['a poem please', 'a poem']

The return type hint Command[Literal[...]] tells LangGraph where the supervisor can go, so get_graph() draws dotted edges to both agents and to __end__ (verified in the Mermaid output).

Pattern 2: handoffs (agents pass control directly)

In a handoff design there is no central boss. The agent that is currently working decides to hand the conversation to another agent, usually by calling a "transfer to X" tool. Inside LangGraph, a handoff is a Command that jumps to another node. When the agent is a subgraph, it must jump in the parent graph, which is what graph=Command.PARENT means. Verified:

def triage(state: MessagesState):                     # a node inside the "support" subgraph
    return Command(goto="billing", graph=Command.PARENT,
                   update={"messages": [AIMessage(content="handing off to billing")]})

support = StateGraph(MessagesState)
support.add_node("triage", triage)
support.add_edge(START, "triage")

parent = StateGraph(MessagesState)
parent.add_node("support", support.compile(), destinations=("billing",))
parent.add_node("billing", lambda s: {"messages": [AIMessage(content="billing here")]})
parent.add_edge(START, "support")
# invoke with "refund" -> ['refund', 'handing off to billing', 'billing here']

Other patterns, and the names you will meet

The current LangChain multi-agent docs group the designs into five patterns: Subagents (a main agent calls other agents as if they were tools), Handoffs, Skills (one agent loads specialised prompts and knowledge on demand), Router (a classification step sends the input to one or more specialists, then combines the results) and Custom workflow (your own LangGraph graph mixing all of the above). Older tutorials use the words "supervisor" (close to Subagents/Router) and "swarm" (agents handing off to each other, close to Handoffs). Two add-on packages from the LangGraph team with those names exist on PyPI at the time of writing, langgraph-supervisor and langgraph-swarm (both MIT-licensed, source under github.com/langchain-ai). They were not used or tested for this guide; check the docs to see whether they are still the recommended route before adopting them. For running several specialists in parallel and collecting their results, use Send (chapter 3).

Pitfalls with multi-agent graphs
  • Ping-pong loops: two agents keep handing work back. Set a recursion_limit on every call (the 1.2.11 default is very high, see chapter 9) and count handoffs in state.
  • Everyone sees everything: with a shared messages list, every agent reads every other agent's tool chatter. Give agents private state (Way 2) or pass summaries.
  • Names matter: setting name= on messages (as above) helps both you and the models tell agents apart.
  • A checkpointer on a subgraph is usually a mistake; give it to the parent only (and to none of them under langgraph dev).

Your learning roadmap

You now know the core of LangGraph: state, nodes, edges, routing, models, tools, the agent loop and memory. This video ends by saying it only scratches the surface and asking viewers whether they want a continuation (136:17); it does not name the next topics. The same channel's earlier LangChain crash course listed its later topics as MCP, context and state, multi-agent systems, middleware and human-in-the-loop. Two of those are covered in this handbook already (chapters 7 and 10). Here is a suggested order, with what each stage adds:

Stage 2 in one paragraph each

MCP (Model Context Protocol). An open protocol that lets tools live in separate "MCP servers" which any compatible app can connect to, instead of being Python functions in your file. With the langchain-mcp-adapters package (published on PyPI by the LangChain team, MIT) MCP tools become ordinary LangChain tools, so they plug into bind_tools and ToolNode exactly like the course's multiply. Treat every MCP server as code you are choosing to trust: it can see the arguments your agent sends.

Context engineering. Deciding exactly what goes into each model call: which system prompt, which slice of history (chapter 6 trimming), which facts from the store, which tools. Most agent quality problems are context problems, not model problems. A good exercise: print the exact message list chat_with_tools sends (or read it in a LangSmith trace) and ask "does the model have what it needs, and nothing it does not?"

Multi-agent. This chapter. Practise by splitting graph 8 into a math agent and an "explain in words" agent behind a router.

New to "protocol"? What MCP standardises

A protocol is an agreed format for two programs to talk, like HTTP for browsers and web servers. MCP fixes how an AI application asks a tool server "what tools do you have?", reads their names, descriptions and argument schemas (the same information @tool creates from your docstring and type hints), and calls them. Because the format is shared, one MCP server can serve many different apps and frameworks.

Recap
  • A compiled graph can be a node: add it directly when keys are shared, or call it from a wrapper function when state differs. Only the parent gets a checkpointer.
  • See inside with get_graph(xray=True) and stream(..., subgraphs=True).
  • create_agent returns a compiled graph too, so prebuilt agents can be subgraphs.
  • Supervisor/router: a central node routes with Command. Handoffs: an agent jumps to another with Command(goto=..., graph=Command.PARENT).
  • Start with one agent; split only for a named reason; always cap loops.
  • Next topics: MCP, context engineering, multi-agent, human-in-the-loop, then production. Build a project at every stage.
