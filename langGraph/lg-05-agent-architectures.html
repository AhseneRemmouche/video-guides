Agent Architectures

The ReAct loop, create_agent vs a hand-built graph, routers, plan-and-execute and reflection.

What you will learn

Graph 8 (step 13) is the course's agent: a model, three math tools, and an edge back to the model. That shape has a name, the ReAct loop, and it's only one of several standard ways to arrange models, tools and decisions in a graph. This chapter names the common architectures, shows each as a small graph you can run, and explains when to build a graph by hand and when to use LangChain's ready-made create_agent.

  • the spectrum from fixed workflows to autonomous agents;
  • the ReAct loop, and graph 8 as a ReAct agent;
  • langchain.agents.create_agent: the same loop, prebuilt on LangGraph (its graph verified with get_graph());
  • routers, plan-and-execute, and reflection (evaluator) loops;
  • a decision guide: hand-built graph or create_agent.
Why this matters for your project. Once graph 8 works, the natural next questions are "should I just use create_agent?" and "how do I build something bigger than a calculator?". The answers are architectural choices, and every one of them is built from the pieces in chapters 2–4: state, conditional edges, loops, model nodes.

Workflows and agents: who decides the path?

The key question for any LLM application is who chooses what happens next. In a workflow, you do: the path is written in your edges, and models fill in content at fixed points. In an agent, the model does: it decides which tool to call, how many times, and when it's finished. Most real systems sit somewhere between the two.

The ReAct loop

ReAct stands for "Reasoning and Acting". The model alternates between thinking about the task and acting on it with a tool, then observes the result and decides again. In LangGraph it's two nodes and two edges, the agent loop:

  1. Model node: call the model (with tools bound) on the conversation so far.
  2. Conditional edge: if the reply has tool_calls, go to the tool node; otherwise go to END.
  3. Tool node: run every requested tool, append one ToolMessage per call.
  4. Edge back to the model node, which now sees the results.

Graph 8's wiring is exactly that:

builder = StateGraph(MessagesState)

builder.add_node("chat_with_tools", chat_with_tools)
builder.add_node("tools", ToolNode([multiply,addition,subtraction]))

builder.add_edge(START, "chat_with_tools")
builder.add_conditional_edges("chat_with_tools", tools_condition)
builder.add_edge("tools", "chat_with_tools")

graph = builder.compile()

The verified run for "12 times 7" produces four messages: Human, AI (tool call multiply(12, 7)), Tool "84", AI (final answer). A harder question ("(12 × 7) + 5") would typically go round the loop twice, because the addition needs the product first. Nobody wrote "call multiply, then addition"; the model chose it. That's the power and the risk of an agent: the number of loops is not under your control, which is why the recursion limit exists (chapter 3).

create_agent: the same loop, prebuilt

LangChain 1.x provides create_agent in langchain.agents. It builds a ReAct agent for you, and it's built on LangGraph: what it returns is a compiled LangGraph graph. You can check that without an API key, because building the agent doesn't call the model:

from langchain.agents import create_agent
from langchain.tools import tool

@tool
def multiply(nb1: int, nb2: int) -> int:
    """this tool return the multiplication of 2 numbers"""
    return nb1 * nb2

agent = create_agent(
    "openai:gpt-4o",                      # or a model object such as ChatOpenAI(...)
    tools=[multiply],
    system_prompt="You are a helpful math teacher.",
)
print(type(agent).__name__)               # CompiledStateGraph: a LangGraph graph
print(agent.get_graph().draw_mermaid())   # its nodes and edges
print(agent.config["recursion_limit"])    # 9999

We ran it with LangChain 1.3.18 and a placeholder OPENAI_API_KEY (creating the model needs one to be set, but nothing is sent). The important part of the Mermaid output:

__start__ --> model;
model -.-> __end__;
model -.-> tools;
tools -.-> model;

That's graph 8 with different node names: model instead of chat_with_tools, and a tools node. We also invoked it with the fake model from step 18 asking for multiply(12, 7): the result was the same four messages as graph 8 (Human, AI with tool call, Tool "84", AI "The result is 84").

create_agent also accepts what you'd otherwise wire by hand: checkpointer= (memory, like graph 9), response_format= (structured final answer), middleware= (hooks before/after the model, for summarising, guardrails, human approval), state_schema=, store=, and interrupt_before/interrupt_after. Whatever you add, the result is still a LangGraph graph, so you can use it as a node inside a bigger graph (chapter 10).

Router

A router makes one decision at the start and sends the input down one of several fixed paths. There's no loop. Graph 2 routes with an if, graph 3 with a number from the model, and chapter 4 builds a router with with_structured_output (classify → math or chitchat). Routers are cheap (one extra model call at most), easy to test (each branch is a fixed path), and a good fit for "triage" problems: support tickets, intent detection, picking a specialist.

Plan-and-execute

A ReAct agent decides one step at a time. For longer tasks it can lose track. Plan-and-execute separates the two jobs: a planner writes the whole list of steps first, an executor carries them out one by one, and a final node writes the answer. The plan lives in the state, so you can show it to a user, log it, or let a human approve it before anything runs (chapter 7).

Here's the skeleton with the model calls replaced by plain Python so it runs anywhere. In a real app, planner would call a model with structured output (a list of steps) and executor would call an agent with tools:

import operator
from typing import Annotated, Literal
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class PlanState(TypedDict):
    task: str
    plan: list[str]                                  # steps still to do
    results: Annotated[list[str], operator.add]      # finished work, appended
    answer: str

def planner(state: PlanState) -> dict:
    # in a real app: a model with structured output returns the list of steps
    return {"plan": ["find the price", "find the tax rate", "compute the total"]}

def executor(state: PlanState) -> dict:
    step, *rest = state["plan"]
    # in a real app: an agent (model + tools) carries out one step
    return {"plan": rest, "results": [f"done: {step}"]}

def more_steps(state: PlanState) -> Literal["executor", "finisher"]:
    return "executor" if state["plan"] else "finisher"

def finisher(state: PlanState) -> dict:
    return {"answer": f"{len(state['results'])} steps completed"}

builder = StateGraph(PlanState)
builder.add_node("planner", planner)
builder.add_node("executor", executor)
builder.add_node("finisher", finisher)
builder.add_edge(START, "planner")
builder.add_edge("planner", "executor")
builder.add_conditional_edges("executor", more_steps)
builder.add_edge("finisher", END)
graph = builder.compile()

print(graph.invoke({"task": "total price of a 20 euro book", "results": []}))

Output: {'task': ..., 'plan': [], 'results': ['done: find the price', 'done: find the tax rate', 'done: compute the total'], 'answer': '3 steps completed'}.

Line by line

Line(s)CodeWhat it does & why

9results: Annotated[..., operator.add]The finished work. Appended, so nothing is lost between loops.

Reflection and evaluator loops

A model's first draft is often not its best. A reflection (or evaluator-optimizer) loop adds a critic: one node writes, another grades or criticises, and a conditional edge either accepts the draft or sends it back with feedback. The critic can be the same model with a different prompt, a different model, or plain code (tests that must pass, a word limit, a JSON schema).

from typing import Literal
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class DraftState(TypedDict):
    topic: str
    draft: str
    feedback: str
    rounds: int

def writer(state: DraftState) -> dict:
    # real app: model writes or rewrites the draft using state["feedback"]
    version = state.get("rounds", 0) + 1
    return {"draft": f"{state['topic']} (version {version})", "rounds": version}

def critic(state: DraftState) -> dict:
    # real app: a second model call grades the draft (structured output)
    ok = state["rounds"] >= 2
    return {"feedback": "approved" if ok else "add an example"}

def good_enough(state: DraftState) -> Literal["writer", "__end__"]:
    if state["feedback"] == "approved" or state["rounds"] >= 3:   # hard cap
        return END
    return "writer"

builder = StateGraph(DraftState)
builder.add_node("writer", writer)
builder.add_node("critic", critic)
builder.add_edge(START, "writer")
builder.add_edge("writer", "critic")
builder.add_conditional_edges("critic", good_enough)
graph = builder.compile()

print(graph.invoke({"topic": "Why graphs?"}))

Output: {'topic': 'Why graphs?', 'draft': 'Why graphs? (version 2)', 'feedback': 'approved', 'rounds': 2}. The draft went round once, was approved on the second pass, and the graph ended.

Note the two exits in good_enough: "approved" is the normal one, rounds >= 3 is a hard cap. A real critic model may never be fully satisfied; without the cap, the loop would run until the recursion limit. Keep a counter in the state for every loop a model controls. The state.get("rounds", 0) on the first pass handles the key not existing yet, because the caller only sends topic.

Hand-built graph or create_agent?

Both produce the same kind of object, so this isn't a one-way door: you can start with create_agent and later replace it with your own graph, or put a create_agent agent inside a hand-built graph as one node.

SituationBetter fitWhy
A model that answers with the help of some tools, loop until donecreate_agentThat's exactly what it builds, with sensible defaults (the system prompt is placed first, which we checked in langchain/agents/factory.py; a structured final answer is one argument away).
The steps are known in advanceHand-built workflowFixed edges are cheaper, faster and easier to test than letting a model rediscover the path every time.
Routing, plan-and-execute, reflection, parallel branchesHand-built graphThese shapes need your own nodes, state keys and edges.
Learning how agents work (this course)Hand-builtGraph 8 shows every moving part; create_agent hides them.
An agent loop with extra behaviour around the model (summarise long histories, ask a human before a tool runs)create_agent + middlewareMiddleware adds hooks without rewriting the loop.
Several agents working togetherHand-built graph with agents as nodesThe outer graph decides who works when (chapter 10).
Pitfalls
  • Reaching for an agent when a fixed workflow would do: more model calls, more cost, less predictable results.
  • Model-controlled loops without a counter. Rely on your own cap first, the recursion limit second.
  • Giving an agent many similar tools with vague docstrings. The model chooses by name and description; make them distinct.
  • Forgetting that create_agent's nodes are called model and tools when you read streams or traces (not chat_with_tools).
  • Building plan-and-execute with a plan the executor can't change. Real plans often need a re-plan step when something fails.
Common misconceptions
  • "create_agent is separate from LangGraph." It returns a CompiledStateGraph; it's LangGraph underneath.
  • "An agent is smarter than a workflow." It's the same model with more freedom. Freedom helps on open-ended tasks and hurts on fixed ones.
  • "Reflection always improves the answer." A critic can be wrong too, and every round costs a model call. Measure before assuming.
  • "ReAct needs special prompts." With modern tool-calling models, the loop comes from the graph structure, not a prompt template.
Recap
  • Architectures differ in who decides the path: you (chain, router), a plan (plan-and-execute), a critic (reflection) or the model (ReAct agent).
  • ReAct = model node + tools node + conditional edge + edge back. Graph 8 is a ReAct agent.
  • create_agent builds the same loop on LangGraph: nodes model and tools, recursion_limit 9999, plus options such as checkpointer, response_format and middleware.
  • Routers make one decision; plan-and-execute keeps the plan in state; reflection loops need a counter-based exit.
  • Use create_agent for a single tool-using agent; hand-build anything with your own shape; combine them freely.
