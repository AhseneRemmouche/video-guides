A LangChain Agent over MCP

Build langchain_client.py: load the MCP tools into a LangChain agent you can chat with.

▶ Watch this part (64:30)

In step 10 you called your MCP tools by hand, one function at a time. In this step you hand the same tools to an LLM and let it decide which one to call. You build langchain_client.py: a small chat loop where you type a request in plain English, a LangChain agent picks the right MCP tool, runs it against your task database, and replies. The server does not change at all. Only the client gets smarter.

What this step adds

So far every client knew exactly which tool to run. A real assistant does not. You say "add a task to buy milk" and the assistant has to work out, on its own, that this means calling create_task. That decision is what an LLM is good at. We give the model a list of our MCP tools and a short system prompt, and it chooses and fills in the tool calls for us (demo at 74:00–77:00).

Concepts the presenter explains

  • Same tools, new driver (at 64:30). The MCP adapter fetches the exact same three tools (create_task, list_tasks, update_task_status) your FastMCP client used. The difference is who calls them: before it was your code, now it is the model.
  • An agent is a loop (at 70:00). An agent is the LLM plus the tools plus a loop. The model reads your message, may ask to run a tool, sees the tool's result, and then either runs another tool or writes the final answer. create_agent builds that loop for you.
  • Memory with a thread (at 72:00). A checkpointer saves the conversation so the agent remembers earlier turns. Each conversation is tagged with a thread id.
  • Tools are the boundary (at 77:00–77:34). The agent can only do what its tools allow. Ask it to change a task's description and it cannot, because there is no tool for that. This is the whole point of MCP: tools define exactly what a client may do.
New to a LangChain agent? What it is and why it matters

A plain LLM only produces text. An agent wraps the model with a set of tools and a loop so it can act, not just talk. When you ask a question, the model can reply with "please run tool X with these arguments". The agent runs the tool, feeds the result back to the model, and repeats until the model is done and writes a normal answer. LangChain is the library that gives us this agent; LangGraph provides the memory piece underneath.

Build the file

  1. Make sure your MCP server is still running from the earlier step. In one terminal: uv run python -m mcp_server.server. It must be listening on http://127.0.0.1:8000/mcp before the agent can fetch the tools.
  2. Create a new file at src/mcp_server/langchain_client.py next to client.py.
  3. Put your OpenAI key in .env as OPENAI_API_KEY=sk-.... The call to load_dotenv() reads it so the model can authenticate. See the primer on API keys below.
  4. Type the file below, then run it in a second terminal: uv run python -m mcp_server.langchain_client.

An API key is a secret that proves to OpenAI the request is yours, so they can run the model and bill the right account. Keep it out of your code and out of Git: it lives in the .env file (which .gitignore hides), and python-dotenv's load_dotenv() loads it at startup. The LangChain OpenAI model reads OPENAI_API_KEY from there automatically; you never pass the key in code.

The complete file

This is the whole client. It connects to the running server, turns the MCP tools into LangChain tools, builds the agent, and runs a chat loop until you type Q.

import asyncio
from uuid import uuid4

from dotenv import load_dotenv
from langchain.agents import create_agent
from langchain.mcp import MCPAdapter
from langchain.messages import HumanMessage
from langgraph.checkpoint.memory import InMemorySaver

load_dotenv()

mcp_adapter = MCPAdapter("http://127.0.0.1:8000/mcp")


async def main():
    async with mcp_adapter:
        tools = await mcp_adapter.list_tools()
        agent = create_agent(
            model="gpt-4o-mini",
            tools=tools,
            system_prompt="You are a helpful assistant for managing tasks",
            checkpointer=InMemorySaver(),
        )
        config = {"configurable": {"thread_id": str(uuid4())}}
        human_question = "can you help me?"
        while human_question != "Q":
            result = await agent.ainvoke(
                {"messages": [HumanMessage(content=human_question)]},
                config=config,
            )
            print("AI response:", result["messages"][-1].text)
            human_question = input("type your message ('Q' to quit): ")


if __name__ == "__main__":
    asyncio.run(main())

New to create_agent? What it is and why it matters

create_agent is a one-call helper in LangChain 1.x that assembles a working agent. You give it a model, a list of tools, an optional system prompt, and an optional checkpointer, and it returns an object you can ainvoke. Behind the scenes it builds the "think, maybe call a tool, look at the result, repeat" loop. You do not write that loop yourself.

New to a system prompt? What it is and why it matters

A system prompt is a short instruction that sits above the whole conversation and tells the model what role to play. It is not something the user types; you set it once when you build the agent. Here "You are a helpful assistant for managing tasks" nudges the model to treat requests as task operations and to reach for the task tools.

New to a checkpointer and memory? What it is and why it matters

By default an agent forgets everything the moment a turn ends. A checkpointer fixes that: it saves the message history after each turn and reloads it before the next one, filed under a thread id. InMemorySaver keeps that history in the program's memory, so it lasts while the program runs but is gone when you stop it. The thread id is how one conversation is kept separate from another; use the same id to continue a chat, a new id to start fresh.

New to tool calling? What it is and why it matters

Tool calling is how a model takes action. Instead of only writing text, the model can reply with a structured request: "call create_task with title 'buy milk'". The agent runs that function and hands the result back to the model, which then writes a normal answer. The model never touches your database directly; it only asks, and your MCP tools do the work. That is exactly why the tool list is a safety boundary.

Common mistakes
  • Server not running. The adapter fetches tools over HTTP. If the server is not listening on http://127.0.0.1:8000/mcp, list_tools() fails. Start the server first, in its own terminal.
  • Missing or wrong API key. No OPENAI_API_KEY in .env (or a typo) means the model call is rejected. Check the key and that load_dotenv() runs before the agent is used.
  • Forgetting await. agent.ainvoke(...) is async. Call it without await (or without asyncio.run at the bottom) and you get RuntimeWarning: coroutine '...' was never awaited and nothing happens.
  • Expecting a missing tool to work. Asking the agent to edit a description will not work — there is no such tool. That is correct behaviour, not a bug.
Video vs setup

The import from langchain.mcp import MCPAdapter uses a beta module built into LangChain, not the separate langchain-mcp-adapters package on PyPI (that package is currently broken against the 2.x MCP library). Your editor (Pylance) may underline langchain.mcp as unresolved and you may see a LangChainBetaWarning at runtime. Both are expected; the code runs. There is no public repo for this project, so the code here was transcribed from the video and then run locally to confirm it works.

Recap
  • The MCP adapter fetches the same three tools as before and hands them to an agent.
  • create_agent builds the model + tools + loop so the LLM chooses which tool to call.
  • A checkpointer plus a thread id give the conversation memory across turns.
  • The agent can only do what its tools allow — no description tool means no description edits. Tools are the boundary.
  • Run needs the server up and an OpenAI API key; the loop runs until you type Q.
