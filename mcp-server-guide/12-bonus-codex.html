Bonus: Use Your MCP from Codex

Register the server in mcp.json and use its tools from Codex — any MCP client can reuse it.

▶ Watch this part (77:04)

You have built an MCP server and called it from two of your own programs: a raw FastMCP client and a LangChain agent. This bonus step shows the real payoff. Without changing a single line of the server, you point a completely different tool at it — Codex, a coding assistant — and manage the same tasks from there. One server, many clients.

The big idea

MCP is a shared protocol. Once your server exposes its tools over an endpoint, any MCP-capable client can use them: your FastMCP script, your LangChain agent, Codex, a teammate's app, or an assistant you have not even heard of. You do not write a new integration for each one. You share the URL, and the client speaks MCP to it. The same data/tasks.db changes no matter who calls (demo at 79:00–83:00).

New to Codex? What it is and why it matters

Codex is an AI coding assistant that can connect to MCP servers. When you add your server to its settings, its model gets your three task tools in the same way the LangChain agent did. The point of this step is not Codex specifically — it is that any MCP client plugs in the same way. We use Codex only to prove it.

Concepts the presenter explains

  • The server is already a product (at 77:04). Nothing about the server changes. It is a running MCP endpoint; new clients just connect to it.
  • A config file points a client at the server (at 79:00). MCP clients read a small JSON file (here mcp.json) that lists which servers to connect to and how.
  • Streamable HTTP transport (at 80:00). Our server runs over HTTP, so we register it as an HTTP (streamable) MCP server, giving its URL. This is the same http://127.0.0.1:8000/mcp endpoint the other clients used.
  • Same data, different door (at 81:00–83:00). Chatting with Codex to add, list and update tasks changes the very same SQLite file the FastMCP client and the agent use.

Create the config file

Add an mcp.json file at the project root (next to pyproject.toml). It describes one MCP server: its name, that it speaks HTTP, and its URL.

  1. Create mcp.json at the root of the project.
  2. Paste the content below. The name "MCP Server ACL" matches the name you gave the server in server.py; the URL is the running endpoint.
  3. Keep the server running (uv run python -m mcp_server.server) so there is something to connect to.
{
  "mcpServers": {
    "MCP Server ACL": {
      "type": "http",
      "url": "http://127.0.0.1:8000/mcp"
    }
  }
}

Line by line

Line(s)CodeWhat it does & why
1, 8{ ... }The whole file is one JSON object. The outer braces open and close it.
2, 7"mcpServers": { ... }The key MCP clients look for: a map of every MCP server the client should connect to. You can list more than one; here there is just one.
3, 6"MCP Server ACL": { ... }The name of this server entry. It is a label for you; matching the server's own name keeps things clear. Everything inside describes how to reach it.
4"type": "http",Tells the client this server speaks over HTTP (streamable HTTP transport), not a local command. That matches how you started the server with transport="http".
5"url": "http://127.0.0.1:8000/mcp"The exact endpoint to connect to — the same URL the FastMCP client and the LangChain agent used. This is where the client sends MCP requests.
New to JSON? What it is and why it matters

JSON is a plain-text format for structured data, built from objects ({ } with "key": value pairs) and lists ([ ]). Many tools use it for config because it is easy for both people and programs to read. The commas, colons and quotes matter: a missing comma or quote makes the file invalid and the client will refuse to load it.

Add the server to Codex

Codex keeps its own settings for MCP servers. Exact menu names change between versions, so follow the shape rather than memorising labels.

  1. Open Codex's settings and find where MCP servers are configured. Codex can read a project's mcp.json, or you add the server through its settings UI — whichever your version offers.
  2. Add a new MCP server as a streamable HTTP server (the kind that connects to a URL, not the kind that launches a local command).
  3. Give it the name MCP Server ACL and the URL http://127.0.0.1:8000/mcp — the same values as in mcp.json.
  4. Save, then confirm Codex lists the three tools: create_task, list_tasks, update_task_status.
  5. Chat with Codex: ask it to list your tasks, add one, and update a status. Watch data/tasks.db change (demo at 81:00–83:00).

Common mistakes
  • Server not running. Codex can only connect to a live endpoint. Start the server first and leave it running in its own terminal.
  • Wrong transport type. Adding it as a local-command server instead of streamable HTTP will not connect. Use the HTTP/URL kind.
  • URL typo. It must be exactly http://127.0.0.1:8000/mcp, including the /mcp path and the port.
  • "connection closed by remote host". The same HTTP flakiness seen earlier (around 81:41 and 82:31) can appear here too. It is not fatal — try the request again. It is a quirk of the newest FastMCP build, not a bug in your task code.
Recap
  • The server does not change; new clients just connect to its endpoint.
  • mcp.json describes the server: its name, type: http, and URL.
  • Register it in Codex as a streamable HTTP MCP server and chat to manage tasks.
  • Every client — FastMCP, LangChain agent, Codex — shares the same tools and the same data/tasks.db.
  • The lesson: build the MCP server once, share the URL, and any MCP-capable client can use it.
