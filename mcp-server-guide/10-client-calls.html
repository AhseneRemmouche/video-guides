Calling Tools from the Client

Call every tool through MCP, and understand the async/await mistakes the video runs into.

▶ Watch this part (57:26)

In step 08 we called one tool from the client: create_task. The client file already contains two more functions, and in this step we finish them off: one that lists every task and one that updates a task's status. Both follow the exact same shape as before — open the connection, call a tool by name with an arguments dictionary, print and return result.data.

This step also fixes the one async mistake the presenter runs into on screen (at 61:55): forgetting to run an async function properly, which produces a "coroutine was never awaited" warning.

Note

We already embedded the whole client.py file on the previous step. Here we only show the two remaining functions as short excerpts, copied exactly from that same file. The line numbers in the tables match the full file.

List every task

This function asks the server's list_tasks tool for all tasks. That tool takes no arguments, so we pass an empty dictionary.

async def list_tasks_using_mcp():
    async with client:
        result = await client.call_tool("list_tasks", {})
        print(result.data)
    return result.data

Update a task's status

This function changes one task's status. It needs two pieces of information, so the arguments dictionary has two keys: which task (task_id) and the new status.

async def update_task_status_from_mcp(task_id: str):
    async with client:
        result = await client.call_tool(
            "update_task_status",
            {"task_id": task_id, "status": "in progress"},
        )
        print(result.data)
    return result.data

Why the arguments dictionary is different for each tool

Each tool on the server declares its own parameters. list_tasks takes none, so you send {}. update_task_status takes task_id and status, so you send both as keys. The rule is simple: the keys in the dictionary must match the tool's parameter names exactly. Get a name wrong, or miss a required one, and the server rejects the call.

The async mistake: "coroutine was never awaited"

Calling an async function the normal way — just name() — does not run it. It only builds a coroutine object and hands it back to you. Nothing happens until something drives that coroutine. At the top level, that "something" is asyncio.run(...). The presenter hits this exact mistake on screen (at 61:55).

Try the video's version: the call that does nothing

If you call the function directly, with no await and no asyncio.run(...):

list_tasks_using_mcp()

Python prints a warning like this and the task list is never fetched:

RuntimeWarning: coroutine 'list_tasks_using_mcp' was never awaited

The fix is to drive the coroutine with asyncio.run(...), exactly as the __main__ block does:

asyncio.run(list_tasks_using_mcp())
New to coroutines? Why a function call can "do nothing"

A normal function runs its body the moment you call it. An async function is different: calling it returns a coroutine — a paused piece of work — without running the body yet. It needs an event loop to run it. asyncio.run(something()) starts a loop, runs the coroutine to the end, and shuts the loop down. That is why every line in the __main__ block wraps its call in asyncio.run(...).

There is a whole page on this: see Async, await & asyncio.

Everything now goes through MCP

Notice what the client never does: it never imports database.py, and it never touches SQLite directly. Every function in this file reaches the data the same way — by calling a tool on the server over MCP. The server is the only program that talks to the database. This is the whole point of MCP: the client asks for an action by name, and the server decides how to carry it out.

Common mistakes
  • Forgetting asyncio.run(...) — the "coroutine was never awaited" warning above. The function looks like it ran, but nothing happened.
  • Wrong status value. update_task_status only accepts "in progress" or "completed". Any other value is rejected by the server.
  • A bad task_id. If the id does not exist, the tool returns an error dictionary rather than a task — that is expected, not a crash.
  • Importing the database in the client. Do not. The client's job is to call tools; the server owns the database.
  • Connection closed by remote host. As on the previous step, the HTTP transport can be flaky on the newest fastmcp build. Retry, or use an in-memory Client(mcp) for testing.
Recap
  • list_tasks_using_mcp() calls the list_tasks tool with an empty dictionary and prints the list of tasks.
  • update_task_status_from_mcp(task_id) calls update_task_status with task_id and a status of "in progress".
  • Calling an async function directly does nothing useful — it returns a coroutine and warns "never awaited". Drive it with asyncio.run(...).
  • Every client function reaches data through an MCP tool. The client has no database import; the server owns SQLite.
