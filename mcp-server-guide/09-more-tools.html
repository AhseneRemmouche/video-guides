More Tools: list_tasks & update_task_status

Add two more tools, use Literal to constrain status, and list the server's tools from the client.

▶ Watch this part (50:07)

In step 07 the server offered one tool, create_task. Now we add the two that complete the set: list_tasks, which returns every task, and update_task_status, which changes a task's status. Each is a thin MCP tool that wraps a database function. We also preview how a client asks the server what tools it has.

What this step adds

We stay in the same file, src/mcp_server/server.py, and add two more decorated functions below create_task. With all three tools in place, our MCP server can create, list, and update tasks — the full set of actions any client (including an AI agent) is allowed to perform. The presenter builds this part starting at 50:07.

These two tools follow the exact pattern you saw in step 07: a @mcp.tool(...) decorator with a name and a description, type hints that describe the inputs and output, a docstring, and one line that calls the matching database function.

Tool one: list_tasks

This tool takes no arguments and returns a list of every task. It simply calls get_all_tasks() from database.py, which returns a list of dictionaries (one per row).

@mcp.tool(
    name="list_tasks",
    description="this tool provides a list of all the tasks in our database",
)
def list_tasks() -> list[dict]:
    """this function returns all the tasks in our database"""
    return get_all_tasks()

Tool two: update_task_status

This tool takes a task's id and a new status, updates the row, and returns the updated task (or an error dictionary if the id does not exist). The interesting part is the type hint on status: it is a Literal, which pins the value to an exact list of allowed strings.

@mcp.tool(
    name="update_task_status",
    description="this tool will update the status of a task based on its id",
)
def update_task_status(
    task_id: str, status: Literal["in progress", "completed"]
) -> dict:
    """this function will update the status for a specific task based on its id"""
    return update_task_status_in_db(task_id, status)

Why Literal is used here

Around 52:22 the presenter points out why status is a Literal and not a plain str. When the input is a Literal["in progress", "completed"], those two strings are the only values allowed. FastMCP shares that constraint with every client, so an AI agent sees that status must be one of exactly two options and cannot invent a third like "done" or "finished". It is a guard rail: the tool's inputs stay valid, and the agent cannot pass junk that the database would store as a meaningless status.

Contrast this with create_task in step 07, where priority is a plain str with no constraint. The video is deliberately loose about status values across the project, so report what the code does rather than tidy it up: new tasks start as "to do" (from create_task), while this update tool only ever accepts "in progress" or "completed".

New to Literal? What it is and why it matters

Literal comes from Python's typing module. A normal hint like status: str says "any text." A hint like status: Literal["in progress", "completed"] says "only these exact strings." It turns a type into an allow-list. Editors and type checkers warn you if you use a value that is not on the list, and FastMCP passes the allow-list to clients so an agent knows the full set of valid choices up front. Use it whenever a value should be one of a small, fixed set.

New to async and await? What they are and why they matter

An async function can pause while it waits for something slow, like a network reply, without freezing the whole program. You call one with await, which means "run this and wait here for the result." The client code below uses await client.list_tools() because talking to a server over the network takes time. The tools in server.py themselves are ordinary (non-async) functions; it is the client that awaits the calls. Step 08 covers this side in full.

Previewing the server's tools from a client

Once the three tools are registered, how does a client find out they exist? It asks. A FastMCP client calls list_tools(), and the server replies with one object per tool. Each object has a .name you can print. This is the first thing step 10 does to confirm the connection works.

tools = await client.list_tools()
for tool in tools:
    print(tool.name)

With our server running, that loop prints the three tool names:

create_task
list_tasks
update_task_status

Seeing exactly those three names is proof that all three decorators registered correctly. If one is missing, you forgot its @mcp.tool(...) line or did not restart the server after editing.

What you should see. After adding both tools and restarting the server, a client's list_tools() returns three tools, and printing their names shows create_task, list_tasks, and update_task_status. Calling update_task_status with a real id and "completed" returns the updated task as a dictionary.

Common mistakes.

  • Passing an invalid status. Anything other than "in progress" or "completed" is outside the Literal allow-list; a type checker flags it, and a well-behaved client will not send it.
  • Using an id that does not exist. The database function returns {"error": "Task #... does not exist"} rather than raising; check for an error key in the result.
  • Not restarting the server. The running server holds the old code. After editing server.py, stop it with Ctrl+C and start it again, or the new tools will not appear.
  • Forgetting a decorator. A function without @mcp.tool(...) is invisible to clients, so list_tools() would show fewer than three names.
Recap
  • list_tasks() takes no inputs and returns get_all_tasks() — a list of task dictionaries.
  • update_task_status(task_id, status) forwards to update_task_status_in_db(...) and returns the updated task or an error dictionary.
  • status uses Literal["in progress", "completed"] so only those two values are allowed; it is an allow-list that stops an agent passing junk (52:22).
  • A client finds the tools by calling await client.list_tools() and reading each tool.name; all three should appear.
  • With create, list, and update in place, the server now exposes the full set of actions — step 10 drives them from a client.
