Understanding MCP

MCP as a USB-C port for AI apps: one standard way to connect agents to your tools and data.

▶ Watch this part (04:22)

Before we write any code, it helps to know what MCP actually is and why it exists. This page explains the idea in plain words, with pictures. It is still conceptual, so there is almost no code.

MCP is a USB-C port for AI applications

The presenter gives a neat picture (at 04:46): MCP is like a USB-C port for AI applications. Before USB-C, every device had its own plug, so you needed a different cable for each one. USB-C replaced that mess with one shape that fits everything. MCP does the same for AI: it is one standard way to connect an AI application to outside tools and data, instead of inventing a custom connection every time.

MCP stands for Model Context Protocol. A protocol is just an agreed set of rules for how two programs talk. Because the rules are shared, any program that follows them can talk to any other that does, without extra glue code.

New to the word "protocol"? What it means

A protocol is a set of rules two programs agree to follow so they understand each other. The web runs on one (HTTP); email runs on others. The rules cover things like how to ask a question and how an answer comes back. MCP is a protocol for AI applications and tools. You do not need to memorise its rules — a library handles them for you — but it helps to know that is what MCP is.

Why that matters: without MCP vs with MCP

Without a standard, connecting n apps to m systems means writing a custom integration for nearly every pair. Add one new system and you must touch every app again. With MCP, each system exposes one MCP server, and each app connects to it once. The work stops multiplying.

This is what MCP enables. An agent can reach your real tools and data, not just chat. And any MCP client — our own script, a LangChain agent, Codex — can reuse the same server with no changes. We will see all three use our one task server later in the guide.

New to "integration" and "API"? A quick primer

An integration is code that lets one program use another. An API (application programming interface) is the published list of calls a program accepts. Normally each service has a different API, so each integration is custom work. MCP's goal is to make tools look the same to every AI client, so you stop writing a fresh integration for each pairing.

The three roles in MCP

MCP has three parts. Keeping them straight makes the rest of the guide easy to follow (at 04:22).

  • The MCP server exposes the tools. It says "here are the things you can do" and runs them when asked. In our project this is server.py.
  • The MCP client connects to the server and calls a tool. It carries the request there and the result back.
  • The agent (the LLM) is the brain. Given a goal in plain English, it decides which tool to call and with what arguments. This step is often called tool calling.

A tool call, in code, is short. You name the tool and pass its arguments, and you get a result back. Here is the shape of it (the real calls come later):

result = await client.call_tool("create_task", {"title": "Buy milk"})
New to "agent" and "LLM"? How they differ

An LLM (large language model) is the model that turns text in into text out. An agent wraps an LLM so it can also act: it reads the goal, chooses a tool, calls it, reads the result, and continues until the job is done. The LLM is the thinker; the agent is the thinker plus the hands. In our project, LangChain builds the agent and MCP supplies the hands.

Key takeaway. MCP is one standard port between AI applications and the outside world. The server exposes tools, the client calls them, and the agent decides which to call. Build the server once, and every client reuses it.

Recap
  • MCP (Model Context Protocol) is a USB-C port for AI applications: one standard connection instead of many custom ones (at 04:46).
  • A protocol is a shared set of rules, so any MCP client can use any MCP server.
  • Without MCP the number of integrations multiplies; with MCP each side connects once.
  • Three roles: the server exposes tools, the client calls them, the agent (the LLM) decides which to call.
  • A client can list the tools, then call one; the server runs it and returns the result over the same connection.
