Database Functions: save, update, get all

Write save_task, update_task_status_in_db and get_all_tasks, returning dictionaries.

▶ Watch this part (16:33)

In the last step we created the database file and the tasks table. An empty table is not very useful on its own. This step adds the three functions that actually move data in and out of that table: one to save a new task, one to update a task's status, and one to read back every task. These three functions are the only way the rest of the project touches SQLite — later the MCP tools will call them, and nothing else will write SQL by hand.

All three live in the same file you started in step 04, src/mcp_server/database.py, right below init_db. We only show the new functions here as short excerpts; the complete file is on the previous page.

What the presenter builds (at 16:33)

The presenter writes the functions in the order a task travels through the app: first you save a task (an INSERT), then later you might change its status (an UPDATE), and at any point you want to list everything (a SELECT). Together that is three of the four CRUD operations — Create, Read, Update (this project never deletes a task).

1. Save a task

save_task takes one argument: a dictionary describing the task, and returns nothing (None). It opens a connection to the database, runs one INSERT, saves the change with commit, and closes the connection.

def save_task(task: dict) -> None:
    conn = sqlite3.connect(db_path)
    try:
        conn.execute(
            """
            INSERT INTO tasks(
                task_id, title, description, priority, status
            )
            VALUES (?, ?, ?, ?, ?)
            """,
            (
                task["task_id"],
                task["title"],
                task["description"],
                task["priority"],
                task["status"],
            ),
        )
        conn.commit()
    finally:
        conn.close()

The important idea here is the row of question marks. We do not paste the task's values straight into the SQL text. Instead we write ? for each value and pass the real values separately, as a tuple. SQLite fills the ? holes in safely. That is called a parameterised query.

New to parameterised queries? What they are and why they matter

A parameterised query is a SQL statement where the changing values are written as placeholders (? in SQLite) and the real values are passed in a separate list. The database engine keeps the SQL text and the values apart: a value can never be read as SQL, only as data.

Why this matters: the tempting alternative is to glue values into the text, like "... VALUES ('" + title + "')". If a title contains a quote or a snippet of SQL, it changes what the statement means — a bug at best, and the classic security hole called SQL injection at worst. Placeholders also handle quoting and types for you, so a title with an apostrophe just works. Rule of thumb: never build SQL by joining strings; always use ? and pass the values separately.

2. Update a task's status

update_task_status_in_db takes a task_id and a new status. It changes that one row, then reads the row back so the caller gets the updated task returned as a dictionary. If no row has that id, it returns a small error dictionary instead.

def update_task_status_in_db(task_id: str, status: str) -> dict:
    conn = sqlite3.connect(db_path)
    conn.row_factory = sqlite3.Row
    conn.execute(
        """
        UPDATE tasks
        Set status = ?
        WHERE task_id = ?
        """,
        (status, task_id),
    )
    conn.commit()
    record = conn.execute(
        """
        SELECT * FROM tasks
        where task_id = ?
        """,
        (task_id,),
    ).fetchone()
    conn.close()
    if record is None:
        return {"error": f"Task #{task_id} does not exist"}
    return dict(record)

Two SQL statements run here. The UPDATE changes the status; the SELECT fetches the whole updated row so we can hand it back. The one WHERE task_id = ? clause is what keeps us from changing every row — an UPDATE with no WHERE would touch the entire table.

New to sqlite3.Row and row factories? What they are

By default SQLite hands each row back as a tuple, so you read columns by position: row[0] is the first column. That is fragile — if the column order changes, your [0] now means something else.

A row factory is a setting on the connection that decides what shape each row comes back as. Setting conn.row_factory = sqlite3.Row makes every row a Row object: you can still index it by position, but you can also read columns by name (row["title"]), and you can convert the whole thing to a dictionary with dict(row). We set it once on the connection and every query on that connection uses it.

3. Get all tasks

get_all_tasks reads every row from the table and returns them as a list of dictionaries — exactly the shape the rest of the app wants to send back as JSON.

def get_all_tasks() -> list[dict]:
    conn = sqlite3.connect(db_path)
    conn.row_factory = sqlite3.Row
    cur = conn.cursor()
    try:
        cur.execute("Select * from tasks;")
        rows = cur.fetchall()
    finally:
        conn.close()
    return [dict(row) for row in rows]

New to dict vs tuple? Why we convert rows to dicts

A tuple is an ordered box of values with no labels: ("1", "a new task", "...", "low", "to do"). You read it by position. A dictionary labels each value with a key: {"task_id": "1", "title": "a new task", ...}. You read it by name.

We convert each row to a dictionary because names are clearer and safer than positions, and because dictionaries map directly to JSON, which is how the MCP tools send tasks back to a client. A client reading task["status"] does not care or need to know which column came first in the table.

Common mistakes
  • Passing values straight into the SQL text. Keep the ? placeholders and pass values as the second argument. Gluing strings is both a bug magnet and a security hole.
  • Forgetting conn.commit(). Without it, an INSERT or UPDATE never reaches the file; the next run shows no change.
  • Wrong tuple order. The values must line up with the ? marks. In the UPDATE it is (status, task_id), in that order.
  • A one-item tuple without the comma. (task_id) is just a string in parentheses; (task_id,) is a tuple. The SELECT needs the comma.
  • Missing a dictionary key. save_task reads five keys; a dict missing one raises KeyError.
Recap
  • Three functions give the app Create, Update and Read over the tasks table — no other code writes SQL.
  • save_task runs one INSERT with ? placeholders and a five-value tuple read from the task dict, then commits.
  • update_task_status_in_db runs an UPDATE, commits, reads the row back with sqlite3.Row, and returns it as a dict — or an error dict when the id is unknown.
  • get_all_tasks selects every row and returns a list of dicts via a list comprehension.
  • Parameterised queries, commit, and converting rows to dicts are the three habits to carry forward.
