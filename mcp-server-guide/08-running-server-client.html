Running the Server & a First Client

Run the HTTP server and write client.py: a FastMCP client that calls a tool over MCP.

▶ Watch this part (41:18)

So far we have built the database and a server that exposes three tools over MCP. But a server on its own does nothing until something talks to it. In this step we do two things: we start the server so it is listening for requests, and we write our very first client — a tiny Python program that connects to the server and asks it to run a tool. By the end you will create a task through MCP instead of calling the database directly.

This is the moment the project comes alive: two programs, running at the same time, talking to each other over HTTP.

What the presenter explains

A client and a server are two separate programs (at 41:18). The server waits and listens; the client starts the conversation by sending a request. Our server listens at the endpoint http://127.0.0.1:8000/mcp, so the client must send its requests to exactly that address.

Because they are two separate programs, they need two separate terminals (at 41:40). One terminal runs the server and stays busy forever (it never returns to the prompt while it is serving). The other terminal runs the client, which connects, does its work, prints a result, and exits.

The FastMCP client is built for asynchronous code (at 43:30). That is why every function is written with async def, why we open the connection with async with client:, and why we must await each tool call. We finish by handing the top-level function to asyncio.run(...), which actually runs it. We explain all of this below and in a dedicated page on Async, await & asyncio.

New to clients and servers? What they are and why there are two

A server is a program that starts up and then waits, listening at an address for requests. A client is a program that sends a request to that address and waits for the reply. Think of a restaurant: the kitchen (server) is always ready; a customer (client) places an order and gets a dish back. In this project the server is server.py and the first client is client.py. They are different programs, so they run in different terminals, and they talk over HTTP.

New to async with? What an async context manager does

A normal with block opens something, lets you use it, then cleans it up automatically when the block ends — even if an error happens. async with client: is the asynchronous version: it opens the connection to the server when the block starts and closes it when the block ends. Everything that talks to the server must sit inside this block. Outside the block the connection is closed, so a tool call there would fail.

Step 1 — Start the server

Open a terminal in the project folder and run the server with uv:

  1. Make sure you are in the project root (the folder that contains pyproject.toml).
  2. Run the server: 
    uv run python src/mcp_server/server.py
  3. Leave this terminal alone. It is now serving and will not return to the prompt.

Word by word: uv run runs a command inside the project's virtual environment (so it uses the exact package versions we installed); python is the interpreter; src/mcp_server/server.py is the file to run. Running server.py triggers its __main__ block, which calls mcp.run(transport="http", port=8000).

What you should see

FastMCP prints a banner (a box with the server name "MCP Server ACL" and its version) and a line telling you it is serving on http://127.0.0.1:8000/mcp. The terminal then appears to "hang" — that is correct. The server is running and waiting for clients. Do not press Ctrl+C; that would stop it.

Step 2 — Create the client file

  1. Create a new file at src/mcp_server/client.py.
  2. Import asyncio (from the Python standard library) and Client from fastmcp.
  3. Build one client pointed at the server's endpoint: client = Client("http://127.0.0.1:8000/mcp").
  4. Write an async function that opens async with client:, calls a tool with await client.call_tool(...), and prints result.data.
  5. In the __main__ block, run each function with asyncio.run(...).

Here is the whole file. We will embed it once, in full, and then explain the important lines.

import asyncio

from fastmcp import Client

client = Client("http://127.0.0.1:8000/mcp")


async def get_tools_from_server():
    async with client:
        tools = await client.list_tools()
        for tool in tools:
            print(tool.name)
    return tools


async def create_task_using_mcp():
    async with client:
        result = await client.call_tool(
            "create_task",
            {
                "title": "task2",
                "priority": "high",
                "description": "the is a test from our client",
            },
        )
        print(result.data)
    return result.data


async def list_tasks_using_mcp():
    async with client:
        result = await client.call_tool("list_tasks", {})
        print(result.data)
    return result.data


async def update_task_status_from_mcp(task_id: str):
    async with client:
        result = await client.call_tool(
            "update_task_status",
            {"task_id": task_id, "status": "in progress"},
        )
        print(result.data)
    return result.data


if __name__ == "__main__":
    asyncio.run(get_tools_from_server())
    asyncio.run(create_task_using_mcp())
    asyncio.run(list_tasks_using_mcp())

New to call_tool arguments? How the dictionary maps to the tool

On the server, create_task is defined with parameters title, priority and description. On the client you pass those as a dictionary: {"title": "task2", "priority": "high", "description": "…"}. FastMCP matches each key to the matching parameter. If you misspell a key or leave out a required one, the server rejects the call. This dictionary is sent to the server encoded as JSON under the hood.

Why result.data and not just result?

A tool reply carries more than the value itself (it can include text blocks, metadata and more). result.data picks out the plain Python value the tool actually returned — for create_task that is the new task dictionary. Printing result alone would show a bigger, noisier object.

Step 3 — Run the client in a second terminal

  1. Leave the server running in the first terminal.
  2. Open a second terminal in the same project folder.
  3. Run the client: 
    uv run python src/mcp_server/client.py
What you should see

In the client's terminal you should see the three tool names printed (create_task, list_tasks, update_task_status), then the new task printed as a dictionary (with a real UUID task_id and status "to do"), then the full list of tasks. The client then exits back to the prompt. Over in the server's terminal you may see log lines appear as it handles each request.

Common mistakes
  • Only one terminal. If you try to run the client in the same terminal as the server, there is nowhere for it to go — the server terminal is busy serving. Use two terminals: server in one, client in the other.
  • Server not running. If the client cannot connect at all, check that the first terminal still shows the server banner and has not been stopped.
  • Connection closed by remote host / peer unexpectedly closed connection. The HTTP transport can show these errors even when your code is correct. The presenter hits this on screen too (around 42:00). It is a flaky behaviour of the newest fastmcp build, not a bug in the task code. Retrying usually works. For testing without the network at all, you can build an in-memory client by passing the server object directly: Client(mcp) — that skips HTTP entirely.
  • Wrong address. The string in Client(...) must match the server's endpoint exactly, including /mcp at the end.
Recap
  • A server listens; a client connects. They are separate programs, so they need two terminals.
  • Start the server with uv run python src/mcp_server/server.py; it serves http://127.0.0.1:8000/mcp and stays busy.
  • client.py builds one Client(...) aimed at that endpoint, opens it with async with client:, and calls a tool with await client.call_tool(name, {args}).
  • result.data is the plain value the tool returned; asyncio.run(...) is what actually runs each async function.
  • If you see "connection closed by remote host", retry — it is a flaky fastmcp build, not your code. An in-memory Client(mcp) avoids the network for testing.
