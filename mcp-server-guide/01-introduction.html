New to MCP? What it is and why it matters

A large language model on its own can only produce text. It cannot read your files, call your database, or save anything. MCP is a small agreement — a protocol — that lets an AI application reach real tools in a standard way. You write the tools once; any MCP-aware application can then use them. Page 02 explains this in full. For now, think of MCP as the bridge between the model and your own code.

What we are going to build

The project is a small task manager exposed over MCP (at 00:00). It has five parts, and the guide builds them in order:

  • A SQLite database that stores tasks in a single file, data/tasks.db.
  • A FastMCP server (server.py) that exposes three tools: create_task, list_tasks and update_task_status.
  • A FastMCP client (client.py) that calls those tools directly, to prove the server works.
  • A LangChain agent that is given the same tools and decides for itself which one to call.
  • A bonus: wiring the same server into Codex, so a coding assistant can manage your tasks too.

Each task we store has a few fields: a task_id (a UUID), a title, a description, a priority (low, medium or high) and a status. We will look at these closely when we build the database.

New to clients and servers? What those words mean

A server is a program that waits for requests and answers them. A client is a program that sends the requests. Here, server.py is the server: it offers the three tools and waits. Each of client.py, the LangChain agent and Codex is a client: it connects and asks a tool to run. The same server can serve all of them at once, because they all speak MCP.

How the data flows

When a client asks to create a task, the request passes through the MCP tool into a plain Python function, which runs an SQL command against the file. The answer then returns the same way. Nothing talks to the database directly except database.py — the tools are the only door in.

New to databases and SQLite? A one-minute primer

A database stores data in a tidy, searchable way. SQLite is the simplest kind: the whole database is a single file on disk, with no separate program to install or run. Our tasks live in data/tasks.db. It is created automatically the first time the code runs, so there is nothing to set up by hand.

The final project layout

Here is the folder you will have at the end. The files you write by hand sit in src/mcp_server/. The rest are configuration and generated files.

Who this guide is for

This guide is written for people who are just starting out. You do not need to know MCP, LangChain, or SQLite in advance. You do need a little comfort with Python — running a script, editing a file — and a terminal. Every command, import and option is explained as it appears. Windows and PowerShell are used throughout, matching the video.

The code was not downloaded from a repository. There is no public repo for this video, so each file was transcribed from the screen in the video and then run locally to confirm it works before going into this guide. Where the video shows a mistake, we show it too, with the exact error and the fix.

How this guide is organised

The twelve steps move from an empty folder to a working server with three kinds of client. They fall into five phases.

The author's advice. The presenter's main tip is simple: do not just watch, and do not copy and paste. Type every line yourself. Typing it out is how the ideas stick. Give it about one hour a day, finish a step or two each time, and the whole project fits comfortably into a week.

Key takeaway. We are building one MCP server with three tools over a SQLite file, then pointing three different clients at it. The server is written once; every client reuses it. Keep the big architecture picture in mind — each later step fills in one box of it.
