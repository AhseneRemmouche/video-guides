Testing the Database

Run database.py directly, insert and update tasks, and fix the SQL errors the video hits.

▶ Watch this part (26:00)

We now have four database functions but we have never run them. Before wiring them into an MCP server, it is worth proving they work on their own. This step adds a small test block to the bottom of database.py and runs the file directly: it creates the database, saves a task, lists everything, and updates a status. The presenter also makes three small errors on screen and fixes them — we reproduce each one exactly, so you can recognise and fix it yourself.

A file that can also be run (at 26:00)

A Python file can be both imported by other code and run on its own. The trick is the if __name__ == "__main__": block at the bottom. When you run the file directly, the code inside runs; when another module imports database.py, it does not. That lets us keep a quick hand-test attached to the file without it firing every time the server imports these functions.

if __name__ == "__main__":
    init_db()
    save_task(
        {
            "task_id": "1",
            "title": "a new task",
            "description": "this is a new task",
            "priority": "low",
            "status": "to do",
        }
    )
    print("all tasks:", get_all_tasks())
    print("update:", update_task_status_in_db("1", "completed"))
    print("missing:", update_task_status_in_db("does-not-exist", "completed"))

New to if __name__ == "__main__":? What it is for

Every Python file has a built-in variable called __name__. When you run a file directly, Python sets its __name__ to the text "__main__". When that same file is imported by another file, __name__ is set to the module's name instead (here, "mcp_server.database").

So the line if __name__ == "__main__": means "only do this when I am the file being run, not when I am imported". It is the standard place to put a quick self-test or a command-line entry point, kept separate from the reusable functions above it.

Run it

We run the file with uv so it uses the project's virtual environment and dependencies. Open the terminal in VS Code at the project root and run the module file by path.

  1. Make sure you are in the project root (the folder with pyproject.toml). The prompt in the video reads PS D:\ACL\MCP_Server>.
  2. Run the database file directly: 
    uv run python src/mcp_server/database.py
  3. Read the three printed lines. Then run it again — the second run prints the same task once, because the id "1" already exists (see Common mistakes).

Look inside the database

New to primary keys and UNIQUE constraints? What they guarantee

In step 04 the table declared task_id TEXT PRIMARY KEY. A primary key is the column that uniquely identifies a row, and SQLite enforces that no two rows can share the same value in it. That guarantee is a UNIQUE constraint.

So inserting a second task with task_id "1" is refused with sqlite3.IntegrityError: UNIQUE constraint failed. That is the database protecting your data, not a bug. The finished app sidesteps it by generating a fresh UUID for every task, so ids never collide.

To actually see the row your code wrote, you can open data/tasks.db with a SQLite viewer. In VS Code the presenter uses the SQLite Viewer extension: install it from the Extensions panel, then click data/tasks.db in the file explorer. It opens a read-only grid showing the tasks table with your columns (task_id, title, description, priority, status) and one row. It is a nice way to confirm the write without writing a SELECT yourself. You do not need it for the project — the printed output already tells you the same thing.

Three errors the video hits — and the fixes

While typing these functions the presenter makes three small mistakes on screen. They are great to study because the error messages tell you exactly what to fix. Each block below shows the video's broken version, the exact message it produces, and the one-line fix.

New to reading Python errors? How to use them

When Python stops with an error it prints a traceback: a few lines ending in the error type and a short message, like TypeError: ... or IndentationError: .... Read it from the bottom up. The last line names the problem; the lines above it point at the file and line number where it happened.

Errors are not failures of yours to hide — they are the fastest guide to the fix. The three below each name their own fix: a syntax error means the SQL or Python text is malformed, an IndentationError means the spacing is off, and a TypeError means you called a function with the wrong kind or number of arguments.

Mistake 1: the missing VALUES keyword (at 29:00)

In the INSERT the presenter first forgets the VALUES word before the placeholders.

            INSERT INTO tasks(
                task_id, title, description, priority, status
            )
            (?, ?, ?, ?, ?)
Error 
sqlite3.OperationalError: near "(": syntax error

Fix: add the keyword — VALUES (?, ?, ?, ?, ?). SQLite could not parse the statement because a bare list of placeholders is not valid SQL after the column list.

Mistake 2: unexpected indentation (at 30:00)

The presenter indents the SQL statement itself in a way Python does not allow. Indentation inside the triple-quoted SQL string does not matter to SQLite, but the indentation of the Python statement does.

    try:
            conn.execute(
            """
            INSERT INTO tasks( ... )
            VALUES (?, ?, ?, ?, ?)
            """,
Error 
IndentationError: unexpected indent

Fix: line the statement up at one consistent level inside the try: block (four spaces in, not eight). Python uses indentation to group code, so an extra step-in with no reason is an error.

Mistake 3: passing a non-dict to save_task (at 31:30)

When calling the test, the presenter passes the task values loose instead of inside a dictionary. save_task expects one dict and reads it by key.

save_task(
    "1", "a new task", "this is a new task", "low", "to do"
)
Error 
TypeError: save_task() takes 1 positional argument but 5 were given

Fix: wrap the values in one dictionary with all five keys, exactly as in the test block above: save_task({"task_id": "1", "title": ..., "description": ..., "priority": ..., "status": ...}).

Common mistakes
  • Running from the wrong folder. Run uv run python src/mcp_server/database.py from the project root, the folder with pyproject.toml — not from inside src/.
  • Running it twice with the same id. The second run tries to insert task_id "1" again and SQLite raises sqlite3.IntegrityError: UNIQUE constraint failed: tasks.task_id, because task_id is the primary key. Delete data/tasks.db, or change the id, to run the save again cleanly. (The real app uses a fresh UUID per task, so this never happens there.)
  • Expecting a crash on a bad id. The last line uses a non-existent id on purpose; it should print an {"error": ...} dict, not raise.
  • No output at all. Check the code is inside the if __name__ == "__main__": block and that you ran the file directly rather than importing it.
Recap
  • The if __name__ == "__main__": block lets database.py run on its own without firing when it is imported.
  • uv run python src/mcp_server/database.py runs the file inside the project environment; it initialises the DB, saves a task, lists all tasks, and updates a status.
  • A SQLite viewer (the VS Code extension) shows the stored row, but the printed output already confirms the writes.
  • The three on-screen errors — missing VALUES, unexpected indentation, and passing loose arguments instead of a dict — each have a one-line fix the message points to.
  • Re-running with a fixed id trips the primary-key UNIQUE constraint; the real app avoids this with per-task UUIDs.
