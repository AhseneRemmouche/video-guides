Glossary

Every system-design term in this guide, explained for beginners.

This glossary explains every term used in the guide in plain language. It is grouped by topic so you can skim a whole area at once: the core ideas and the web, databases, scaling and reliability, APIs and protocols, networking, and authentication and security. Each page links the first time it uses a term straight to the matching entry here, so you can always jump back for a quick reminder.

Core and the web

System design
The practice of deciding how the parts of a software system fit together at a high level: which servers, databases and services exist, how they talk to each other, and the trade-offs behind each choice. It is the high-leverage skill tested in senior and staff engineering interviews.
Client
The program that starts a request and uses the response, such as a web browser or a mobile app. The client talks to a server across the network and shows the result to the person using it.
Server
A computer (or program) that waits for requests, does the work, and sends back a response. In a single-server setup one machine runs the web app, the database and the cache all at once.
DNS
The Domain Name System: the internet's address book. When a browser has a domain such as app.demo.com, it asks DNS to translate that name into the numeric IP address of the server.
IP address
The numeric address of a machine on a network, such as 93.184.216.34. DNS returns a server's IP address so the client knows where to send its request.
Domain
The human-friendly name people type to reach a service, such as app.demo.com. A domain is easy to remember; DNS turns it into the IP address a computer needs.
HTTP
HyperText Transfer Protocol: the request-and-response language of the web. A request carries a method, a resource URL, a version, a host and headers; a response carries a version, a status code, a content type and headers.
HTTPS
HTTP with TLS/SSL encryption added. It protects data in transit, checks that the data was not changed, and confirms the server's identity, so it should be used everywhere.
TLS
Transport Layer Security (the successor to SSL): the encryption layer that turns HTTP into HTTPS. It encrypts the traffic between client and server so others on the network cannot read or tamper with it.
API
Application Programming Interface: a contract between a client and a server that says which requests you can make and what responses to expect. It hides the implementation behind it and sets clear boundaries between services.
Endpoint
A single addressable operation of an API, such as GET /products/{id}. The set of endpoints and methods is the part of the API a client actually calls.
JSON
JavaScript Object Notation: a light text format for structured data, made of key-value pairs and lists. APIs often return JSON, for example {"id":1,"name":"Shoe","price":49}, which both servers and mobile apps can read easily.

Databases

Web tier
The part of a system that handles incoming requests and runs the application logic. Splitting it off from the data tier lets each layer be scaled on its own.
Data tier
The part of a system that stores and serves data, usually one or more databases. Separating it from the web tier means the application servers and the storage can grow independently.
RDBMS
A Relational Database Management System: software that stores data in tables of rows and columns and links tables together. PostgreSQL, MySQL, Oracle and SQLite are common examples.
SQL
Structured Query Language: the language used to read and write data in a relational database. SQL databases store structured data, support joins between tables and provide ACID transactions.
NoSQL
A family of non-relational databases built for flexibility and very large scale. The main types are document, wide-column, key-value and graph stores, each suited to different data shapes and access patterns.
ACID
Four guarantees that make transactions safe: Atomicity (all steps happen or none do), Consistency (the data stays valid), Isolation (concurrent transactions do not corrupt each other) and Durability (committed data survives a crash). A bank transfer is the classic example.
Transaction
A group of database operations treated as one unit that either fully succeeds or fully fails. Moving money between two accounts is one transaction: both the debit and the credit must happen together.
Table
A named collection of rows in a relational database, like a spreadsheet with a fixed set of columns. For example a customers table holds one row per customer.
Row
A single record in a table, holding one value for each column. One row in a products table describes one product.
Column
A named field that every row in a table shares, such as name or price. Each column has a type that limits what values it can hold.
Primary key
A column (or set of columns) whose value uniquely identifies each row in a table, such as an id. Other tables refer to a row by its primary key.
Join
A SQL operation that combines rows from two or more tables using a shared value, for example linking customers and products into orders. Joins are how relational databases answer questions that span tables.
Document store
A NoSQL database that stores each record as a flexible JSON-like document rather than a fixed row. MongoDB is a common example, and documents in the same collection need not share the same fields.
Key-value store
A NoSQL database that maps a key straight to a value, with no query language in between. Redis and Memcached keep data in RAM, which makes them the fastest option and a natural fit for caches.
Wide-column store
A NoSQL database that organises data into columns grouped into families, built for massive, write-heavy workloads. Cassandra and Cosmos DB are examples used at very large scale.
Graph database
A NoSQL database that stores data as nodes and the relationships between them, so connected data is fast to traverse. Neo4j and Amazon Neptune are used for things like recommendation engines.

Scaling and reliability

Latency
How long a single request takes to get a response, usually measured in milliseconds. Lower latency means a snappier system.
Throughput
How many requests a system can handle in a given time, for example requests per second. Higher throughput means the system copes with more traffic.
Vertical scaling
Scaling up: making one server more powerful by adding RAM, CPU or disk. It is simple, but it hits a hard resource ceiling and leaves no redundancy, so if that one server dies the app goes down.
Horizontal scaling
Scaling out: adding more servers and sharing the work between them. It gives better fault tolerance and scalability, but it needs a load balancer to spread requests across the servers.
Load balancer
A component that sits in front of several servers and spreads incoming traffic between them, routing around any server that has failed. It is what makes horizontal scaling work.
Round robin
A load-balancing strategy that sends each new request to the next server in rotation, one after another. It works well when all the servers have roughly equal capacity.
Least connections
A load-balancing strategy that sends each request to the server with the fewest active connections. It suits workloads where sessions last for varying lengths of time.
IP hash
A load-balancing strategy that hashes the client's IP address to pick a server, so the same client keeps reaching the same server. This helps when a server holds state for that client.
Weighted algorithm
A load-balancing strategy that gives each server a weight based on its capacity, such as RAM, so stronger servers receive a larger share of traffic. It is often combined with round robin or least connections.
Consistent hashing
A technique that places servers and requests on a hash ring so the same client maps to the same server, while adding or removing a server only reshuffles a small part of the traffic. It keeps routing stable as the pool of servers changes.
Health check
A periodic probe a load balancer sends to each server to see whether it is still responding. If a server fails its health check, the balancer stops routing traffic to it until it recovers.
Fault tolerance
A system's ability to keep working when one of its parts fails. Running several servers behind a load balancer is one way to add it.
Redundancy
Having spare copies of a component so that one failure does not stop the system, for example a standby load balancer ready to take over. When the failed part recovers, traffic can be shifted back to it.
Single point of failure
Any one component whose failure takes the whole system down, such as a single shared database or a single load balancer. Removing these points is a central goal of reliable design.
Self-healing
The ability of a system to detect a dead instance and automatically replace it with a fresh one, without a human stepping in. It keeps capacity steady after a failure.
Cache
A fast store, often held in RAM, that keeps copies of data or results so they can be returned without redoing slow work. Key-value stores such as Redis are commonly used as caches. (Caching is only mentioned in passing in this course, not taught in depth.)

APIs and protocols

REST
Representational State Transfer: an API style built around resources addressed by URLs and acted on with HTTP methods. REST is stateless and widely used for web and mobile back-ends.
GraphQL
A query language and API style, created at Facebook, that exposes a single endpoint where the client asks for exactly the fields it needs. It cuts round trips and over-fetching, which suits complex user interfaces.
gRPC
A high-performance remote-procedure-call framework that uses protocol buffers over HTTP/2 and supports streaming in both directions. It is a strong fit for internal, server-to-server communication between microservices.
Stateless
A design where the server keeps no memory of past requests, so each request must carry everything it needs. REST is stateless, which makes it easy to run many identical servers behind a load balancer.
Idempotent
An operation that gives the same result no matter how many times you repeat it. GET, PUT and DELETE are idempotent, while POST is not, because repeating it creates another record.
HTTP method
The verb in an HTTP request that says what to do with a resource: GET to read, POST to create, PUT or PATCH to update, and DELETE to remove. REST maps these verbs onto create-read-update-delete actions.
Status code
A three-digit number in an HTTP response that reports the outcome. The families are 2xx success, 3xx redirect, 4xx client error and 5xx server error, for example 200 OK, 201 Created, 404 Not Found.
Protocol buffers
A compact binary format from Google for encoding structured data, used by gRPC. Being binary and schema-defined makes messages small and fast to send compared with text formats.
WebSocket
A protocol that upgrades an HTTP connection into a persistent two-way channel, so the server can push data to the client without being asked. It replaces wasteful HTTP polling and suits chat and other real-time features.
AMQP
Advanced Message Queuing Protocol: a messaging protocol where a producer sends messages to a broker or queue and a consumer pulls them when it is free. It guarantees delivery and supports exchange types such as direct, fanout and topic.
Message queue
A buffer that holds messages between a producer and a consumer so the two do not have to work at the same speed. It smooths out spikes and lets work be processed when a consumer is ready.
Producer
The program that creates messages and sends them to a queue or broker. It does not wait for the consumer; it just hands the message off.
Consumer
The program that reads messages from a queue and processes them, pulling the next one when it has capacity. Separating producers from consumers lets each scale on its own.
Resource
A thing an API exposes, named with a plural noun in REST, such as /products. A collection is the whole set (/products) and an item is one member (/products/{id}).
Pagination
Returning a large result set in smaller pages instead of all at once, controlled by query parameters. Common styles are page-and-limit, offset-and-limit, and cursor based.
Offset
A pagination parameter that says how many records to skip before returning results, for example skip 20 then take 10. It is simple but can be slow or inconsistent on data that changes while you page through it.
Cursor
A pagination parameter that points at a specific position in the data, so the next page continues from there. It stays stable even when records are added or removed between requests.
Versioning
Giving an API a version marker, often in the path such as /api/v1, so you can change it later without breaking existing clients. Old clients keep using the old version while new ones move on.
Schema
A formal description of the shape of data or of an API, listing its types and fields. In GraphQL the schema is the contract that defines the types, queries, mutations and subscriptions a server supports.
Query
In GraphQL, a read operation that asks for data, similar to a GET in REST. The query names exactly the fields the client wants back.
Mutation
In GraphQL, a write operation that changes data, playing the role of POST, PUT, PATCH or DELETE in REST. Mutations usually take input types as their arguments.
Subscription
In GraphQL, an operation that streams real-time updates to the client as data changes, rather than returning once. It is how GraphQL supports live features.

Networking

TCP
Transmission Control Protocol: a reliable, connection-based transport that sets up a link with a three-way handshake, guarantees delivery, reorders packets and resends lost ones. Its extra overhead is worth it for payments, authentication, user data and email.
UDP
User Datagram Protocol: a fast, connectionless transport with no handshake and no delivery guarantee, so lost packets are simply skipped. The low overhead suits video calls, live streams and games, where being on time matters more than being complete.
Handshake
The exchange of messages that sets up a connection before data flows. TCP uses a three-way handshake (SYN, SYN-ACK, ACK) so both sides agree they are ready.
OSI model
A layered map of how network communication is organised, from physical signals up to the application. TCP and UDP sit at the transport layer, and protocols such as HTTP sit above them at the application layer.

Authentication and security

Authentication
Confirming who someone is, answering the question "who are you?". It always comes before authorization.
Authorization
Deciding what an already-identified user is allowed to do, answering "what can you do?". It happens after authentication.
Basic authentication
A scheme that sends the username and password, base64-encoded, in the Authorization header. The encoding is reversible, so it is only safe over HTTPS and is rarely used today.
Digest authentication
A scheme that sends an MD5 hash of the credentials instead of the raw password. It is slightly better than basic auth but is now considered outdated.
API key
A random string a client sends in a header such as Authorization or X-API-Key, which the server looks up to grant access and scopes. It carries no user identity, often has no built-in expiry, and is dangerous if it leaks.
Session
Server-side state that remembers a logged-in user between requests. The server stores it (in memory, Redis, SQL or a file) and gives the client a session cookie; this is stateful and harder to scale across many servers.
Cookie
A small piece of data the server asks the browser to store and send back on later requests, often used to carry a session identifier. Storing sensitive tokens in an HTTP-only cookie keeps JavaScript from reading them.
Bearer token
A token sent in the Authorization header where simply holding the token grants access, with no further proof of identity. Because anyone who holds it can use it, it must be kept secret and sent over HTTPS.
JWT
JSON Web Token: a signed token in three parts (header, payload, signature) that carries claims such as a user id, email, roles and an expiry. It is a token format, not a method; because the server can verify the signature locally it is stateless and scales well.
Access token
A short-lived token (often 15 minutes to an hour) that a client sends with each API call to prove it is allowed in. Keeping its lifetime short limits the damage if it leaks.
Refresh token
A longer-lived token (days or weeks) whose only job is to obtain new access tokens without making the user log in again. It should be stored in an HTTP-only cookie, never in localStorage.
OAuth 2
An authorization framework that lets a user grant an app limited, scoped access to their data on another service, such as read access to their Google Drive. The user consents, an authorization code is exchanged for an access token, and that token proves access, not identity.
OpenID Connect
An authentication layer built on top of OAuth 2 that returns an ID token (a JWT describing the user) alongside the access token. It powers "Sign in with Google/GitHub": the app verifies the signature, reads the identity and creates its own session.
SSO
Single sign-on: logging in once and then reaching many services without logging in again. It keeps a global session and issues an SSO cookie, using identity protocols such as SAML or OpenID Connect underneath.
SAML
Security Assertion Markup Language: an XML-based identity protocol used for single sign-on, common in enterprise and legacy systems such as Salesforce. It is one of the protocols that can sit under an SSO setup.
RBAC
Role-Based Access Control: you assign users roles such as admin, editor or viewer, and each role carries a set of permissions. It is the most common authorization model, used by GitHub, Stripe and many content systems.
ABAC
Attribute-Based Access Control: access is decided by policies over attributes of the user, the resource and the environment, for example "department = HR and resource = internal, then allow". It is very flexible but more complex and its rules can conflict.
ACL
Access-Control List: each resource carries its own list of which users may do what, such as a Google Drive document shared for read or edit. It is easy to reason about per resource but harder to manage at large scale.
Scope
A named permission attached to a token that limits what it can do, such as read-only access to one kind of data. OAuth 2 and API keys use scopes to grant only the access that is actually needed.
Rate limiting
Capping how many requests are allowed in a time window, per endpoint, per user or IP, and overall. It protects an API from abuse and from denial-of-service floods, where many bots each stay under the per-IP cap but are still stopped by the overall cap.
CORS
Cross-Origin Resource Sharing: browser rules that control which web origins may call an API. Configuring it so only your own front-end origin is allowed stops other sites' pages from calling your API in a user's browser.
SQL injection
An attack where hostile input is slipped into a database query, letting an attacker read or delete data they should not. It is prevented with parameterised queries or an ORM that keeps data separate from the query.
Firewall
A gatekeeper that inspects traffic and blocks suspicious requests, for example a web application firewall such as AWS WAF that drops odd methods or SQL keywords. It filters attacks before they reach the application.
VPN
Virtual Private Network: a private network boundary that keeps internal APIs reachable only from inside it, while public APIs stay open to everyone. It is a way to hide services that the outside world should never touch.
CSRF
Cross-Site Request Forgery: a malicious site tricks a logged-in user's browser into sending a request that rides on the user's existing cookie. It is countered with CSRF tokens checked alongside the session cookie.
XSS
Cross-Site Scripting: an attacker stores a script, for example in a comment, that then runs in other users' browsers. It is prevented by escaping and sanitising input both when it is stored and when it is shown.
