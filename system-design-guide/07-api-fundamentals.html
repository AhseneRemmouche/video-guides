API Fundamentals: REST, GraphQL & gRPC

What an API is, the three main styles, four design principles, and the API design life cycle.

Concept · explained from the video

Two servers can only work together if they agree, in advance, on how to talk. That agreement is an API. This page explains what an API really is, the three styles you will meet most often — REST, GraphQL and gRPC — the four principles that make an API pleasant to use, and the process of designing one from start to finish.

What an API is

API stands for application programming interface. The presenter defines it as a contract between a client (a browser or a mobile app) and a server (at 30:24). The contract says two things: what requests you are allowed to make, and what responses you can expect back (at 30:47).

"What requests you can make" means the list of endpoints and the methods you may use on each one. "What you can expect back" means the shape of the reply — for example a JSON object with an id, a name and a price.

An API is first of all an abstraction (at 31:11). It hides the implementation and exposes only the functionality. When you call an endpoint to save a user, you do not care how the server stores that user — which database, which code, which disk. You only care about the interface. The server can rewrite everything behind that endpoint and your code keeps working, as long as the contract does not change.

An API also sets service boundaries (at 31:34). Because the interface is clearly defined, you can split the work across separate servers: one server owns users, another owns posts, another owns payments. Each one talks to the others only through its API, so they can be built, deployed and scaled independently.

New to APIs? What a "contract" means here

Think of ordering at a counter. The menu is the contract: it lists what you can ask for (the dishes) and what you will get back (a described plate). You do not need to know how the kitchen works. If the kitchen buys a new oven, your order still works because the menu did not change. An API is that menu for software: a fixed list of requests and the replies they produce.

The three API styles

During design you will almost always pick one of three styles (at 32:21): REST, GraphQL and gRPC.

REST

REST (representational state transfer) is the most common style (at 32:21). It is resource-based: every thing in your system (a user, a post) is a resource with its own URL, and you act on it with the standard HTTP methods (at 32:44) — GET to read, POST to create, PUT or PATCH to update, DELETE to remove. REST is also stateless: each request carries everything the server needs, so no earlier request has to be remembered (at 32:44). It is the usual choice for web and mobile apps.

GraphQL

GraphQL is a query language that lets the client ask for exactly the fields it needs (at 33:07). It exposes a single endpoint for every operation, and the client describes the response shape in the request body. Its operations are query (read), mutation (write) and subscription (real-time) (at 33:30). Its big win is fewer round trips: data that would take three REST calls can come back in one (at 33:52), which makes it a good fit for complex screens.

gRPC

gRPC is a high-performance RPC framework that communicates with protocol buffers (at 34:38). Its methods are defined as RPCs in .proto files, and it supports streaming and two-way communication. It is the least common of the three for public apps, but excellent for microservices and internal server-to-server traffic, where it is faster than REST or GraphQL (at 35:00).

New to HTTP methods? GET, POST, PUT, PATCH, DELETE

An HTTP method (also called a verb) says what you want to do to a resource. GET reads it, POST creates a new one, PUT replaces one completely, PATCH changes part of it, and DELETE removes it. REST reuses these standard verbs instead of inventing its own, which is why a REST URL is a noun (the thing) and the method is the action.

New to "stateless"? Why each request stands alone

Stateless means the server keeps no memory of your previous requests. Every request must include all the context it needs — for example a token that says who you are. This makes scaling easy: any server in a pool can answer any request, because none of them rely on something an earlier request left behind.

REST vs GraphQL, side by side

The clearest way to feel the difference is a real request (at 35:00). In REST, related data lives at separate resource URLs, so fetching a user plus their posts plus their followers is three calls:

GET https://api.example.com/v1/users/123
GET https://api.example.com/v1/users/123/posts
GET https://api.example.com/v1/users/123/followers

Each REST response has a fixed structure. Ask for a user and you always get back the same shape, whether or not you needed every field:

{
  "id": 123,
  "name": "Ada Lovelace",
  "email": "ada@example.com",
  "createdAt": "2026-01-04"
}

In GraphQL there is one endpoint, and a single query names exactly the fields you want — across the user, the posts and the followers (at 36:36):

query {
  user(id: 123) {
    name
    posts { title content }
    followers { name }
  }
}

One round trip, and nothing comes back that you did not ask for. REST uses explicit versioning in the URL (the /v1/ above) and can lean on HTTP caching; GraphQL usually evolves its schema without version numbers and caches at the application level instead (at 37:22).

In an interview, say: "REST models the system as resources you act on with HTTP verbs; GraphQL gives one endpoint where the client declares the exact response shape, which cuts over-fetching and round trips; gRPC uses protocol buffers over HTTP/2 and shines for internal service-to-service calls." Naming the trade-off, not just the name, is what scores.

Four design principles

Whatever the style, a good API follows four principles (at 38:07). The presenter's rule of thumb: the best API is one you can use without reading the documentation (at 38:07).

  • Consistent — use the same naming, casing and patterns everywhere. Do not write one endpoint in camelCase and another in snake_case (at 38:51).
  • Simple — focus on the core use cases and an intuitive design, so a developer understands it quickly (at 39:15).
  • Secure — add authentication and authorization, validate every input, and apply rate limiting (at 39:38).
  • Performant — design for efficiency with caching, pagination for large lists, small payloads, and fewer round trips (at 40:02).
Common mistake: an endpoint that quietly does extra work. If GET /users/123 also updates a follower count, it has broken the contract — a read should only read. Surprising side effects are the fastest way to make an API that nobody can trust or use without the docs (at 38:29).

Protocol choice shapes the API

Each style rides on a protocol, and that choice fundamentally shapes what the API can do (at 40:47). HTTP's features — its methods and status codes — map neatly onto REST's create-read-update-delete operations, so REST (and GraphQL) run over HTTP. For live, two-way data such as chat you want WebSocket; for fast internal calls you reach for gRPC. Pick the protocol by its strengths and limits, not by habit (at 41:34). The design process and life cycle

Designing an API starts with the requirements (at 41:57): identify the core use cases and user stories, define what is in and out of scope, work out where performance will matter, and set the security constraints. There are three ways to approach the design (at 43:06):

  • Top-down — start from high-level requirements and workflows, then define endpoints. Common in interviews.
  • Bottom-up — start from existing data models and capabilities. Common inside a company that already has systems.
  • Contract-first — agree the request and response contract before any code. Close to top-down, and also common in interviews.

Building an API is far more than coding. Over its life it moves through five phases (at 43:53): design (agree requirements and outcomes), develop (build and test locally), deploy & monitor (ship to staging or production and watch it), maintain (keep it working — easier when you kept it simple), and finally deprecate & retire (for example when a v2 replaces v1).

In an interview, say: which approach you are using and why — "I'll go top-down from the requirements and design contract-first, so we agree the request and response shapes before writing code." It signals you treat the API as a design problem, not just code.
Recap
  • An API is a contract: the requests a client may make (endpoints and methods) and the responses it can expect.
  • It is an abstraction (hides implementation) and sets service boundaries (separate servers per concern).
  • REST = many resource URLs over HTTP verbs, stateless; GraphQL = one endpoint, ask for exact fields, fewer round trips; gRPC = protocol buffers over HTTP/2 for fast server-to-server calls.
  • Four principles: consistent, simple, secure, performant — aim for an API usable without the docs.
  • Protocol choice shapes the API; design top-down, bottom-up or contract-first; the life cycle runs design → develop → deploy/monitor → maintain → deprecate.
