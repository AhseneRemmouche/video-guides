Databases: SQL vs NoSQL

Relational vs non-relational databases, ACID transactions, the four NoSQL types, and when to use each.

Concept · explained from the video

One server that does everything is fine for a handful of users, but it soon runs out of room. The first big split is to put the application on one group of machines and the data on another. This lesson explains that split, then the two great families of databases — relational (SQL) and non-relational (NoSQL) — and how to choose between them.

Splitting the web tier from the data tier

As the user base grows, a single machine cannot keep up (at 06:13). The first move is to separate the web tier, which handles web and mobile traffic, from the data tier, which manages the database (at 06:36). Now each part can be scaled on its own: if the application code is busy, you grow the web tier; if queries are slow, you grow the data tier. The client still talks only to the server in the web tier, which in turn talks to the database.

Relational databases (SQL)

When you choose a database there are two main families (at 06:36). The first is the relational database, also called an RDBMS. Popular examples are PostgreSQL, MySQL, Oracle Database and SQLite. These databases are queried with SQL (Structured Query Language), and they store data in tables that look a lot like spreadsheets (at 07:23).

A table has columns, which are the fields or attributes, and rows, which are the individual records. For a customers table the columns might be id, name, age and email; one row could be the customer with id 123, name John, age 40 (at 07:23). The id column is the primary key — the value that uniquely identifies each row.

New to tables, rows and columns? What they are

Think of a spreadsheet. The top line of headings is the set of columns (what each piece of data means). Every line underneath is a row (one real thing — one customer, one order). A relational database is a collection of such tables, and a primary key is the one column whose value is never repeated, so you can always point at exactly one row.

Joining tables together

The first big advantage of SQL is the join: combining two or more tables into one result (at 08:08). Imagine a customers table and a products table. To record who bought what, you create an orders table that links them — it holds the customer id and the product id for each purchase. A join then stitches these back together so you can read, in one go, which customer ordered which product.

SELECT c.name, p.title
FROM orders o
JOIN customers c ON c.id = o.customer_id
JOIN products  p ON p.id = o.product_id;

Transactions and ACID

The second big advantage is strong consistency through transactions (at 08:31). A transaction is a sequence of one or more SQL operations treated as a single, all-or-nothing unit. Every SQL transaction follows the ACID rules. The classic example is a bank transfer: take money out of one account and put it into another.

  • Atomicity — the whole transfer succeeds, or the whole thing fails; money is never taken out without being put in.
  • Consistency — the database moves from one valid state to another valid state (at 09:17); the totals still add up.
  • Isolation — transactions running at the same time do not interfere with each other.
  • Durability — once it is done, the result survives even if the server crashes afterwards.
New to ACID? Why these four letters matter

ACID is a promise a relational database makes about transactions. Without it, a crash mid-transfer could leave money missing, two shoppers could buy the last item at once, or a confirmed order could vanish on restart. The four guarantees — Atomicity, Consistency, Isolation, Durability — are what let you trust the data even when things go wrong.

Non-relational databases (NoSQL)

The other family is NoSQL, suited to flexible, fast access to large volumes of unstructured or semi-structured data (at 06:59). NoSQL comes in four main types (at 09:40):

  • Document stores — a document store such as MongoDB keeps data in JSON-like documents, so one record can hold a rich, nested structure (at 09:40).
  • Wide-column stores — a wide-column store such as Cassandra (or Cosmos DB) uses rows with dynamic columns; it handles massive scale and heavy write loads (at 10:03).
  • Key-value stores — a key-value store such as Redis or Memcached keeps simple key-value pairs mostly in RAM, which makes reads and writes extremely fast (at 10:26).
  • Graph databases — a graph database such as Neo4j stores entities and their relationships; Amazon uses the Neptune graph database to make product recommendations (at 10:26).

Because of this flexibility, data that would need a join in SQL can often live in a single NoSQL record. In MongoDB you could store the customer, their orders and the products together as one document (at 11:12):

{
  "_id": "order_1001",
  "customer": { "id": 123, "name": "John" },
  "items": [
    { "product": "Desk lamp", "price": 39.99 },
    { "product": "Notebook",  "price": 4.50 }
  ]
}
New to NoSQL? How it differs from SQL

SQL spreads related data across several fixed tables and joins them on demand, which keeps data tidy and consistent. NoSQL relaxes that: records can have different shapes, and related data is often nested together so it can be read in one hit. You trade some of SQL's strict structure and guarantees for flexibility, very low latency and easier scaling to huge volumes.

When to use which

There is no single winner; it depends on your data and your needs (at 11:36). Choose SQL when data is well-structured with clear relationships (an e-commerce app tracking customers and orders), or when you need strong consistency and transactional integrity (a financial or banking system). Choose NoSQL when you need very low latency, when the data is unstructured or semi-structured and relationships are not crucial, or when you need flexible, scalable storage for massive volumes — for example a recommendation engine storing user activity.

In an interview, say

“SQL gives me joins and ACID transactions, so I would use PostgreSQL for the orders and payments. For the recommendation feed I would add a NoSQL store for low latency at scale.” Showing you can mix both, and naming the trade-off, scores better than defending one side.

Common mistake

Reaching for NoSQL by default “because it scales”. If your data has clear relationships and needs transactions — money, orders, inventory — a relational database is usually the safer, simpler choice. Pick the type for the data, not the hype.

Recap
  • Split the web tier (app traffic) from the data tier (database) so each scales on its own.
  • SQL / RDBMS (PostgreSQL, MySQL, Oracle, SQLite) stores data in tables of rows and columns, supports joins, and guarantees ACID transactions.
  • NoSQL has four main types: document (MongoDB), wide-column (Cassandra), key-value (Redis, Memcached) and graph (Neo4j, Neptune).
  • Choose SQL for structured, related data needing consistency; choose NoSQL for low latency, flexible shapes and massive scale.
