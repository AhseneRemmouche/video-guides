Single Points of Failure

What a single point of failure is, why it is dangerous, and how redundancy and self-healing remove it.

Concept · explained from the video

Adding more servers makes a system stronger — but only if no single piece can still take the whole thing down on its own. That weak piece is called a single point of failure. This page explains what one is, why it is dangerous, and three ways to stop your load balancer from becoming one.

What is a single point of failure?

A single point of failure (SPOF) is any one part of your system that, when it fails, brings the entire system down with it (at 26:10). Put simply: if this one component stops working, everything stops working.

The classic example is a shared database. Imagine clients connecting through a load balancer to several API servers, and all of those API servers reading and writing to a single database (at 26:32). The database is a single point of failure. The moment it goes down, every API server loses its data source, none of them can do their job, and your clients get no response — even though all the API servers are perfectly healthy.

Why a SPOF is dangerous

Having single points of failure creates vulnerabilities in three ways (at 26:55):

  • Reliability — a single failure can take the entire system down, which means an outage. For a business that can mean real losses: users cannot reach the platform, cannot get to the checkout page, cannot use the service at all.
  • Scalability — a system built around a SPOF struggles to grow, because every new component leans on that same fragile part and adds more risk to it.
  • Security — a SPOF is an obvious target. If the load balancer is the only way in, an attacker can aim a flood of traffic straight at it; knock it over and the whole system goes with it.

The database SPOF is handled in the databases section of the wider course. Here we focus on the other SPOF in our diagram: the load balancer itself. Right now there is only one, so if it goes down, no user can reach the APIs behind it (at 27:40). There are three common ways to fix this.

New to this? What "redundancy" means

Redundancy means keeping a spare. Instead of one of something, you run two or more that can do the same job, so if one dies another carries on. It is the opposite of a single point of failure: you deliberately duplicate the critical part so there is no single thing left to bring everything down.

Fix 1: Redundancy

The first strategy is to add redundancy — use more than one load balancer (at 28:03). With two load balancers, if the second one goes down, you redirect all of its traffic to the first one, and that one balances the load across the servers on its own. Meanwhile you keep monitoring the health of the failed load balancer, and when it comes back online you shift some of the traffic — for example 50% — back to it.

Fix 2: Health checks and monitoring of the load balancers

The second strategy is to run health checks and monitoring on the load balancers themselves (at 28:49). A load balancer already health-checks the servers behind it; we apply the same idea one level up and check the health of the load balancers continuously. Whenever one of them goes down, we know not to send any traffic to it until it is back online. This is what makes the redundancy above actually work — something has to notice a balancer has failed before traffic can be moved off it.

Common mistake

Adding a second load balancer and thinking the job is done. Redundancy without monitoring is not enough — if nothing is checking the balancers' health, the system has no way to know when to shift traffic over, or when to bring the recovered balancer back. The spare only helps if something is watching.

New to this? What "self-healing" means

A self-healing system fixes itself without a human stepping in. When it detects that a component has died, it automatically replaces it with a fresh copy. The replacement is just another instance of the same thing, so the system keeps running and users barely notice.

Fix 3: Self-healing

The third strategy is a self-healing system (at 29:14). Again we monitor the health of the load balancer, but this time, the moment we detect it has gone down, we automatically replace it with a new one — a fresh instance of the same load balancer. Because the replacement happens on its own, there is no interruption, and clients can connect to the new load balancer without ever knowing the old one failed.

In an interview, say this

When asked how you would make a system resilient, walk the interviewer through removing SPOFs: "I would add redundancy so no component is alone, health-check every layer including the load balancers, and make it self-healing so a dead instance is replaced automatically." Naming all three shows you understand that fault tolerance is designed in, not hoped for.

Recap
  • A single point of failure is any one component whose failure takes the whole system down — such as one shared database or a lone load balancer.
  • SPOFs are dangerous for reliability (outages and business loss), scalability (hard to grow) and security (one weak point to attack).
  • Fix the load-balancer SPOF with redundancy: run more than one and shift traffic over on failure, then back (e.g. 50%) on recovery.
  • Health-check and monitor the load balancers themselves, so failures are detected and traffic is only sent to healthy ones.
  • Add self-healing so a dead load balancer is automatically replaced by a fresh instance, with no interruption.
  • The database SPOF is covered in the databases section of the wider course.
