API Security

Seven techniques: rate limiting, CORS, injection defence, firewalls, VPNs, CSRF and XSS.

Concept · explained from the video

An API is a door into your system. Leave it unprotected and attackers can walk straight in and do what they like with your users' data (at 115:46). This closing lesson covers seven proven techniques for keeping those doors guarded (at 115:46). None of them is optional in a real production system; together they form a layered defence, where each technique stops a different kind of attack.

1. Rate limiting

Rate limiting caps how many requests a client may make in a given time (at 116:07). Say user A is allowed 100 requests per minute; the 101st is blocked until some time has passed (at 116:07). Without it, an attacker can flood your API with thousands of requests a minute, overwhelm the system, or brute-force your data (at 116:30). The presenter describes three levels that work together (at 116:30):

  • Per endpoint — a sensitive endpoint like /comments gets its own strict limit.
  • Per user or IP address — each caller gets a quota, so one abusive IP is blocked on its own.
  • Overall — a global cap that protects against DDoS attacks.

Why all three? An attacker can spin up many bots, each under the per-IP limit, so individually none is blocked — but their combined traffic is more than your system should handle (at 117:41). The overall cap catches that: when total traffic crosses the global number, you temporarily block everything until you find the cause (at 118:06). The numbers here are just examples (at 118:06).

What is a DDoS attack?

A distributed denial-of-service attack floods a system with so much traffic from so many sources (often a botnet of hijacked machines) that it cannot serve real users. Because the traffic comes from thousands of addresses, a per-IP limit alone will not stop it — each source stays just under the line. That is exactly why an overall, system-wide cap exists.

2. CORS

CORS — cross-origin resource sharing — controls which website origins may call your API from a browser (at 118:30). Without it, a malicious website could trick a user's browser into making requests on their behalf (at 118:30). If your API is only meant to serve your own front end at app.yourdomain.com, then only requests from that origin should be allowed; a request from app.anotherdomain.com should be refused (at 118:53).

3. SQL / NoSQL injection

Injection happens when user input is dropped straight into a database query (at 119:17). An attacker can craft input that changes the query's meaning, bypassing checks so they can read, modify or delete your data — whole tables at a time (at 119:17). The fix is to never build queries by sticking strings together: use parameterised queries or an ORM's safeguards, which keep user input as data and never let it become part of the query's logic (at 119:41).

// Vulnerable: input becomes part of the query
query("SELECT * FROM users WHERE name = '" + input + "'");
// attacker sends:  ' OR '1'='1   →  returns every row

// Safe: input is bound as a value, never as SQL
query("SELECT * FROM users WHERE name = ?", [input]);
What does "parameterised query" mean?

Instead of pasting the user's text into the query string, you leave a placeholder (a ? or a named parameter) and pass the value separately. The database treats that value strictly as data — a name to match, never a command to run. So even if someone types ' OR '1'='1, the database looks for a user literally called that, finds none, and nothing is bypassed.

4. Firewalls

A firewall acts as a gatekeeper, filtering malicious traffic out from normal traffic, and sits between the incoming requests and your API (at 119:41). A web application firewall such as AWS WAF can block requests that match known attack patterns — suspicious SQL keywords or strange HTTP methods — while letting legitimate requests through to your API (at 120:05).

5. VPN

Some APIs are private and should only be reachable from specific networks (at 120:27). A VPN — virtual private network — makes an API reachable only by someone who is also inside that network (at 120:27). A public-facing API accepts requests from anyone on the internet; an API inside the VPN rejects a request from the open web, but accepts one from a user who is on the same network (at 120:49). This is ideal for internal tools — for example an admin dashboard whose API is reachable only by employees connected to the company VPN (at 121:11).

6. CSRF

CSRF — cross-site request forgery — tricks a logged-in user's browser into making an unwanted request to an API (at 121:11). Suppose you are logged in to your bank, which authenticates you with a cookie. If the bank relies on the session cookie alone, a malicious site could ride that cookie and silently submit a hidden money-transfer request (at 121:35). The fix is a CSRF token used alongside the session cookie: the bank checks that the session cookie is present and that the CSRF token matches the one it issued; if it does not, the request is blocked, while genuine requests from you still go through (at 121:58).

Why can a cookie be "ridden" by another site?

Browsers attach a site's cookie to every request to that site automatically — even requests triggered by a different, malicious page you happen to have open. So the bank sees a request carrying your valid session cookie and thinks it is you. A CSRF token defeats this because the malicious site cannot read or guess the token value, so it cannot include a matching one.

7. XSS

XSS — cross-site scripting — lets an attacker inject a script into pages served to other users (at 122:23). Picture a comment section: a normal comment like "nice picture" is stored by your API and shown back harmlessly (at 122:23). But if an attacker submits a comment that contains a script, your API stores it, and later, when other users load the comments, their browsers execute that malicious JavaScript — it might steal their cookies or tamper with the page (at 122:46). The fix is to escape or sanitise input, both when storing it and when rendering it, so stored text is never treated as runnable code (at 123:10).

In an interview, say…

"API security is layered. I would rate-limit at endpoint, user and global levels, lock down CORS to my own origin, use parameterised queries against injection, put a WAF in front, keep internal APIs behind a VPN, add CSRF tokens next to session cookies, and escape all user input to stop XSS." Listing defences by the attack each one stops shows you understand why, not just what.

Common mistake

Treating CSRF and XSS as the same bug. CSRF abuses the browser's habit of sending your cookie, so the fix is a CSRF token the attacker cannot supply. XSS runs attacker code in other users' browsers, so the fix is escaping and sanitising input. Different attacks, different defences — and relying on one does nothing against the other.

Recap
  • Rate limiting caps requests per endpoint, per user/IP, and overall — the overall cap is what stops a DDoS swarm of bots.
  • CORS allows only your own front-end origin to call the API from a browser.
  • SQL/NoSQL injection is fixed with parameterised queries or an ORM, so input can never become query logic.
  • A firewall (such as AWS WAF) filters out suspicious requests before they reach your API.
  • A VPN keeps internal APIs reachable only from inside the private network.
  • CSRF rides a logged-in user's cookie; a matching CSRF token blocks the forgery.
  • XSS stores a script that runs in other users' browsers; escaping and sanitising input stops it.
