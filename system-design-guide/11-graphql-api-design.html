Designing GraphQL APIs

Why GraphQL exists, its schema and type system, queries, mutations, error handling and best practices.

Concept · explained from the video

In the last lesson we designed a tidy REST API. REST works well, but it has a recurring annoyance: a single screen often needs data from several endpoints, and each endpoint hands back a fixed shape that is either too much or too little. GraphQL was built to fix exactly that. In this lesson we cover why GraphQL exists, how its schema and type system work, how you read with queries and write with mutations, how errors are reported, and the best practices to follow (at 78:03).

Why GraphQL exists

GraphQL was created by Facebook to solve one specific pain: clients making multiple API calls and still not getting exactly the data they need (at 78:25). Imagine a Facebook page built on separate REST APIs — a user API, a post API, a comments API, a likes API. To render one page the client often has to call several of them, and sometimes still misses a field, forcing yet another request (at 78:25). Every extra round trip adds to the page's latency, because the page is not finished until all those requests come back (at 78:50).

Two problems hide in there. Over-fetching is when an endpoint returns more than the screen needs (every post field, including large images you will not show). Under-fetching is when one endpoint does not return enough, so you must call another. GraphQL removes both by letting the client describe the exact shape of the response.

One endpoint, client-chosen fields

With GraphQL there is a single endpoint. The client specifies the shape of the response, and that one endpoint handles all the data interactions (at 79:14). It is still an ordinary HTTP request — nothing exotic — but the body of the request says which fields you want. You might ask for user 123, and from that user only the name, plus their posts, and from each post only the title (no images), and from each post its comments (at 79:14). You get back a JSON response in exactly that shape, with no over-fetching (at 79:38).

query {
  user(id: "123") {
    name
    posts {
      title
      comments { text }
    }
  }
}
New to GraphQL? What it is in one minute

GraphQL is a query language for APIs. Instead of many URLs that each return a fixed block of data, you send a single request to one endpoint and describe the exact tree of fields you want. The server walks that tree and returns matching data in the same shape. Think of REST as ordering from a fixed menu of dishes, and GraphQL as telling the kitchen the precise plate you want assembled.

Over-fetching and under-fetching

Over-fetching means the response carries fields you did not need — wasted bytes and slower pages. Under-fetching means one response is not enough, so you make more calls. REST endpoints have a fixed shape, so both happen often. GraphQL lets the client pick fields, so it tends to avoid both at once.

The schema is the contract

A GraphQL schema is the contract between client and server (at 79:38). It has three main pieces. First, types: you define a type such as User and list its fields — id, name, posts, and so on. When a field is not a primitive (like posts), you point it at another type, such as an array of Post, which you define separately (at 80:01).

Second, queries to read data — the equivalent of GET in REST. You name the query, say what arguments it takes, and declare its return type, for example a user query that takes an id and returns a User (at 80:23). Third, mutations to change data — the equivalent of POST, PUT, PATCH and DELETE. Any time you write to the database, you call a mutation; a createUser mutation might accept a name and return the created User (at 80:47). GraphQL also offers subscriptions for real-time data, where the server pushes updates as they happen. A good schema mirrors your domain model and stays intuitive and flexible (at 81:09).

type User {
  id: ID!
  name: String!
  posts: [Post!]!
}

type Query {
  user(id: ID!): User
}

type Mutation {
  createUser(name: String!): User
}

Querying and mutating

Once the schema is defined, clients read with queries and write with mutations. A query uses the same user entry point from the schema and lists exactly the attributes it needs — name, posts, and from posts the title only — and the server returns precisely that (at 81:09). A mutation such as createPost sends the new data (a title and body) and then also states which fields to return once the post is created, for example its id and title (at 81:31). That is a neat property of GraphQL: even a write lets you choose the shape of what comes back.

mutation {
  createPost(title: "Hello", body: "First post") {
    id
    title
  }
}

Error handling: always 200

Error handling in GraphQL differs from REST (at 81:55). A REST API signals failure with the status code — 404, 400, 500 and so on. GraphQL instead returns 200 OK for almost every response, even when something went wrong (at 81:55). So the error information cannot live in the status line; it lives in an errors array in the response body (at 82:19).

That array lets the server report what failed while still returning whatever data it could gather — this is partial data. In the example below, user is null because it was not found, and the errors array explains why, carrying a code (404), a message ("not found"), and a path pointing at the user field in the schema (at 82:19). Because every response is 200, the code inside errors is how the client learns what kind of error this really was (at 82:40).

{
  "data": { "user": null },
  "errors": [
    {
      "message": "User not found",
      "code": 404,
      "path": ["user"]
    }
  ]
}
Why return 200 for an error?

A GraphQL request can touch many fields at once, and some may succeed while others fail. A single HTTP status code cannot describe a mixed result, so GraphQL keeps the transport layer simple (the request was delivered: 200) and moves the real outcome into the body. The trade-off is that clients must never assume "200 means success" — they have to check the errors array every time.

Best practices

The presenter closes with a short checklist (at 82:40). Keep schemas small and modular rather than one giant file. Avoid deeply nested queries: a user can contain posts, a post can contain comments, a comment can contain its author's posts, and so on without end. To stop that, teams set a query depth limit — how many layers deep a query may go, often around six or seven (at 83:03). Use meaningful names for types and fields, because both client and server read the same schema (at 83:27). And when writing data, use input types for mutations rather than long lists of loose arguments (at 83:27).

In an interview, say…

"GraphQL gives the client a single endpoint and lets it request exactly the fields it needs, which removes over-fetching and under-fetching. The schema is the contract: types describe the data, queries read, mutations write. Errors come back in an errors array with a 200 status, so partial data is possible."

Common mistake

Do not treat a 200 OK as proof the request succeeded. In GraphQL a failed field still returns 200, with the problem described in the errors array. Code that only checks the HTTP status will silently miss real errors.

Recap
  • GraphQL exists to stop multiple round trips and over/under-fetching; Facebook built it for that reason.
  • There is a single endpoint and the client chooses the exact fields it wants; it is still an HTTP request.
  • The schema is the contract: types define data, queries read (like GET), mutations write (like POST/PUT/DELETE), subscriptions push real-time updates.
  • Errors return as 200 with an errors array (code, message, path); partial data can come back alongside errors.
  • Best practices: small modular schema, limit query depth, meaningful names, input types for mutations.
