API Protocols: HTTP, WebSocket, AMQP & gRPC

The application-layer protocols behind APIs and when to choose each one.

Concept · explained from the video

The style you pick for an API rides on a protocol, and the wrong protocol causes bottlenecks and missing features (at 45:51). This page covers where protocols sit in the network stack, then the four you will meet most: HTTP and HTTPS, WebSocket, AMQP and gRPC — and how to choose between them.

Application layer vs transport layer

Protocols are stacked in layers (at 47:00). The ones we use to build APIs — HTTP, HTTPS, WebSocket, AMQP, gRPC — live at the application layer, right at the top. They define the message format, the request/response pattern, how connections are managed and how errors are handled.

Underneath sits the transport layer, with TCP and UDP, which actually move the bytes between machines. Below that are more layers again (network, data-link, physical), but when building APIs we mostly care about the application layer (at 47:24). The layering is part of the OSI model; the transport layer is covered on the next page.

New to "layers"? Why protocols stack

Each layer does one job and trusts the layer below to do its own. The application layer decides what a message means (a GET for a product). The transport layer decides how the message travels reliably across the wire. Because they are separated, HTTP does not have to know about cables, and the cables do not have to know about products. You can swap one layer without rewriting the others.

HTTP: the foundation of web APIs

HTTP (HyperText Transfer Protocol) is the most common protocol and the base of web APIs (at 47:24). It works in a request/response cycle (at 47:47). A request carries a method (such as GET), the resource URL, the HTTP version, the host (your server's domain) and usually authentication — for example a bearer token (at 48:10):

GET /api/products/123 HTTP/1.1
Host: api.example.com
Authorization: Bearer <token>
Accept: application/json

The response comes back in the same shape: the HTTP version, a status code (such as 200), the content type (often application/json) and any other headers, such as cache-control (at 48:34):

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: max-age=60

{ "id": 123, "name": "Keyboard", "price": 49.99 }

The methods are the familiar ones (at 49:19): GET reads, POST creates, PUT/PATCH updates, DELETE removes. Status codes come in families (at 49:19): 2xx success, 3xx redirect, 4xx the client made the error, 5xx the server made the error. Common headers include content-type, authorization, accept, cache-control and user-agent (at 49:43).

New to status-code families? Reading the first digit

The first digit tells you who to look at. 2xx means it worked (200 OK, 201 Created). 3xx means "go somewhere else" (a redirect). 4xx means your request was wrong — a bad URL, missing auth, not found (404). 5xx means the server broke while handling a valid request. If you see 4xx, fix the request; if you see 5xx, the problem is on the server.

HTTPS = HTTP + TLS/SSL

HTTPS is the same HTTP, wrapped in TLS/SSL encryption (at 50:07). That encryption protects your data in transit, adds data integrity, and authenticates the server before any data is handed over. It also brings SEO benefits. Plain HTTP exposes everything in transit, so the golden rule is simple: always use HTTPS (at 50:30).

Common mistake: shipping an API over plain HTTP "just for testing", then forgetting to switch. Without TLS, tokens and personal data travel in readable form and anyone on the network path can see or tamper with them. Use HTTPS from the very first request (at 50:30).

WebSocket: persistent two-way push

HTTP is great at request/response, but poor at live data (at 50:53). Imagine a chat built on HTTP: to find out if a new message arrived, the client keeps polling — asking again and again. Many of those replies are empty, which wastes bandwidth, server resources and adds latency (at 51:39).

WebSocket fixes this. The first request performs a handshake that upgrades the connection to a persistent, two-way channel (at 52:02). After that, the server can push data to the client the moment it has something — no repeated asking — and the client can still send whenever it needs to (at 52:25). That is what unlocks real-time data with minimal latency and far less wasted traffic, which is why chat and live feeds use it.

AMQP: producers, queues and consumers

AMQP (Advanced Message Queuing Protocol) is an enterprise messaging protocol for message queues with guaranteed delivery (at 53:33). Instead of talking directly, a producer (say a web service or payment system) publishes a message to a message broker, which holds it in a queue. A consumer (say a payment processor or notification service) pulls the message from the queue when it is free (at 53:56).

That decoupling is the point: when a new order is placed, the producer drops a message on the order queue and moves on; a busy consumer leaves the message in the queue and picks it up later when it has capacity (at 54:19). This is asynchronous — the two sides do not have to be ready at the same moment. AMQP's exchange types are direct (one-to-one), fanout (to everyone) and topic (by pattern) (at 54:42).

New to message queues? Why put a queue in the middle

Without a queue, the producer must wait for the consumer to be ready, and a slow or crashed consumer blocks or loses work. A queue is a buffer: the producer hands off and carries on, the message waits safely, and the consumer works through the backlog at its own pace. It is the difference between handing a parcel to a sorting office and standing at the recipient's door until they open.

gRPC: protocol buffers over HTTP/2

gRPC is a high-performance RPC framework from Google that works with protocol buffers and uses HTTP/2 for transport (at 54:42). Because it needs HTTP/2, both sides must support it — which is why it is used mostly between servers, with microservices calling each other, rather than browser-to-server (at 55:06). It has built-in streaming thanks to HTTP/2, and the compact protocol-buffer format makes it fast (at 55:28).

How to choose

Pick the protocol by the job (at 55:51). Start from the interaction pattern: a plain request/response defaults to HTTP; real-time chat needs WebSocket; many internal services talking to each other suit gRPC. Then weigh performance, client compatibility (most browsers do not support the newest HTTP, so gRPC is rare in the browser), payload size, security needs, and the developer experience — tooling and documentation you will live with (at 56:14).

In an interview, say: "I'd default to HTTPS request/response, move to WebSocket if the feature is real-time, use a message queue over AMQP for async work that must not be lost, and consider gRPC for internal service-to-service calls where latency matters." Leading with the interaction pattern shows you choose on requirements, not fashion.
Common mistake: reaching for gRPC between a browser and a server. Most browsers do not support the HTTP/2 features gRPC relies on, so it is a poor fit for client-facing APIs — keep it for server-to-server (at 56:14).
Recap
  • API protocols live at the application layer and ride on the transport layer (TCP/UDP) beneath them.
  • HTTP works in request (method, URL, version, host, auth) and response (version, status code, content-type, headers) pairs; status families are 2xx, 3xx, 4xx, 5xx.
  • HTTPS is HTTP plus TLS/SSL encryption — always use it.
  • WebSocket upgrades once via a handshake, then the server can push data two ways, replacing wasteful HTTP polling.
  • AMQP puts a broker and queue between a producer and a consumer for guaranteed, asynchronous delivery; gRPC uses protocol buffers over HTTP/2 for fast server-to-server calls.
  • Choose by interaction pattern, performance, client compatibility, payload size, security and developer experience.
