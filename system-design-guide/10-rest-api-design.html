Designing RESTful APIs

Resource modelling, URLs, filtering/sorting/pagination, HTTP methods, status codes and best practices.

Concept · explained from the video

RESTful APIs let different parts of a system talk to each other using the standard HTTP methods, and they are the most common way developers build and consume APIs today (at 63:04). This page shows how to design clean REST APIs by following proven best practices, so you avoid messy, inconsistent patterns that make an API hard to use and maintain. We will cover resource modelling and URL design, filtering, sorting and pagination, the HTTP methods behind CRUD, status codes, and the best practices that tie it all together (at 63:28).

Resources: model your domain as plural nouns

A resource is the core idea in REST (at 63:52). Start from your business domain — say products, orders and reviews — and turn each thing into a noun, in the plural: a product becomes /products, an order becomes /orders (at 63:52). You name the resource, not the action. So to read products you use GET /products, never /getProducts. The HTTP method already says what you are doing; the URL only names the thing (at 64:38).

A resource URL can point at a whole collection or a single item (at 64:15). /products returns the collection of products; /products/{id} returns one specific product. Resources can also be nested when one belongs to another: to get the reviews for a particular product you ask for /products/{id}/reviews (at 65:24).

GET /api/v1/products            # the whole collection
GET /api/v1/products/123        # a single item
GET /api/v1/products/123/reviews # reviews nested under product 123

Filtering, sorting and pagination with query parameters

In the real world you rarely want every row at once (at 65:46). You control what comes back using query parameters — everything after the ? in a URL (at 66:34). Filtering narrows the set: ?category=shoes&in_stock=true returns only in-stock shoes, so you do not waste bandwidth on items you will not show (at 65:46). Sorting orders the set: ?sort=price_asc asks the server to sort by price ascending. You sort in the back end because pulling a thousand unsorted rows to the front end just to order them is very inefficient (at 66:56).

GET /api/v1/products?category=shoes&in_stock=true   # filter
GET /api/v1/products?sort=price_asc                 # sort
GET /api/v1/products?page=3&limit=10                # paginate

Pagination returns the results one page at a time (at 67:41). You pass the page you want plus a limit — how many items per page — so one request returns, say, 10 items; clicking “next” fetches page 3, and so on. There are two other common styles (at 68:03). With offset + limit, the offset tells the API where to start counting and the limit how many to take. With a cursor, you pass an opaque pointer (a hash of the page) instead of a page number, and the API returns the items after it.

New to query parameters? What the part after “?” means

A query parameter is a key=value pair added to the end of a URL after a ?. Join several with &. They do not change which resource you ask for — /products is still products — they refine the request: which subset (filter), in what order (sort), and how many (pagination). They are ideal for optional, repeatable options.

New to pagination styles? page, offset and cursor

page + limit is the simplest: “give me page 3, 10 per page.” offset + limit says “skip the first N, then give me the next 10” — handy when you think in absolute positions. cursor passes a pointer to the last item you saw and asks for what comes after it; it stays stable even when rows are added or removed, so it suits large, fast-changing lists.

HTTP methods map to CRUD

Because REST rides on HTTP, it uses the standard HTTP methods for CRUD — Create, Read, Update, Delete (at 69:12). GET reads data (GET /products); it is safe (it changes nothing) and idempotent (calling it twice gives the same result) (at 69:58). POST creates a resource (POST /products); it changes server state and is not idempotent — post twice and you create two items (at 70:42). PUT replaces a whole resource, while PATCH updates it partially; both target one item, e.g. PUT /products/123 (at 71:06). DELETE removes the item at DELETE /products/123, with no request body (at 71:52).

A POST body typically carries the new resource as JSON:

POST /api/v1/products
{
  "name": "Running shoes",
  "price": 89.99,
  "category": "shoes",
  "in_stock": true
}
New to “safe” and “idempotent”? Why GET is special

Safe means the call does not change anything on the server — a GET only reads. Idempotent means making the same call many times leaves the server in the same state as making it once. GET, PUT and DELETE are idempotent (deleting item 123 twice still just leaves it gone); POST is not, because each call creates another new resource. This matters because clients and networks sometimes retry requests — and retrying a non-idempotent POST can create duplicates.

Status codes and error handling

Every response should carry the right status code so the client knows what happened (at 72:40). The 2xx family means success: 200 OK for a successful read, 201 Created after a POST creates a resource, 204 No Content when there is nothing to return (at 73:03). 3xx means redirection — the resource has moved (at 73:26). 4xx means the client got it wrong: 400 Bad Request for invalid input, 401 Unauthorized when the user is not authenticated, 404 Not Found when the resource does not exist (at 73:49). 5xx means the server failed through no fault of the client, e.g. 500 for an unexpected server error (at 74:36).

In an interview, say: “I use plural-noun resources, let the HTTP method carry the CRUD action, push filter/sort/paginate into query params, and return precise status codes — 201 on create, 404 on a missing item, 400 on bad input.”
Common mistake: putting the action in the URL (/getProducts, /deleteUser/5) or returning 200 OK for everything, including creates and errors. The method and status code exist to carry that meaning — duplicating it in the URL or flattening it to 200 makes the API confusing and hard to debug.

Best practices

Pulling it together (at 74:59): use plural nouns for resources (/products, not /product); use the correct HTTP method and URL for each action (delete a user with DELETE /users/{id}, never POST /users/{id} or a /delete path); support filtering, sorting and pagination together, not pagination alone; and add versioning with an /api/v1 prefix (at 76:08). Versioning lets you ship a v2 with new features while existing clients keep using v1, so a change does not break the people already depending on your endpoints (at 76:31).

Recap
  • Model the domain as plural-noun resources (/products), with collection (/products), item (/products/{id}) and nested (/products/{id}/reviews) URLs — nouns, never verbs.
  • Use query parameters for filtering (?category=&in_stock=true), sorting (?sort=price_asc) and pagination (?page=&limit=, or offset+limit, or cursor).
  • Map HTTP methods to CRUD: GET (read, safe + idempotent), POST (create), PUT (replace) / PATCH (partial), DELETE.
  • Return the right status code: 200/201/204, 3xx redirects, 400/401/404 client errors, 5xx server errors.
  • Best practices: plural nouns, correct methods + URLs, filter/sort/paginate, and /api/v1 versioning.
