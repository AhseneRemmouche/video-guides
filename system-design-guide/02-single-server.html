The Single-Server Setup

Start with one server: DNS, the HTTP request flow, and how web and mobile clients talk to it.

Concept · explained from the video

Designing a system for millions of users is hard, but every complex system starts simple. So we begin with the smallest possible setup — everything on one machine — and understand each core component before adding complexity (at 01:56). This single-server setup is the foundation the rest of the guide builds on.

Everything on one server

Imagine a small user base. In that case the whole application can run on one single server: the web application, the database, the cache and any other components all live together (at 02:20). The presenter chooses this on purpose — with one box and nothing else, you can see the core workings without distraction.

How a request reaches the server

Now follow one request from start to finish. Our users want to reach our website or our API. They might use a web browser or a mobile app — both are the client here (at 02:44). The server holds the files to serve to browsers and the API endpoints to serve to mobile apps, and it is hosted at some IP address (at 02:44).

The catch: users do not know that IP address. They know a domain instead, such as app.demo.com (at 03:08). So when they type the domain and press enter, the browser first contacts a DNS — the Domain Name System — whose job is to map domains to IP addresses. The DNS looks up app.demo.com, finds it points to our server's IP address, and sends that address back to the client (at 03:31).

Now the client knows where to send its request. It sends an HTTP request to that IP address asking for specific data. The server processes the request and sends back the requested data: an HTML page for a browser, or a JSON response for the app, depending on what was asked (at 03:31). This back-and-forth is one request and one response.

New to DNS? What it does and why it matters

People remember names like app.demo.com, but computers route traffic using numeric IP addresses. The Domain Name System (DNS) is the internet's address book: give it a domain and it returns the matching IP address. Without DNS you would have to memorise a string of numbers for every site you visit. It runs quietly before almost every request you make online.

What is an IP address?

An IP address is the numeric location of a machine on a network, a bit like a street address for a house. The DNS hands your browser the server's IP address so your request knows where to go. In this lesson the exact number does not matter; what matters is that the domain is a friendly label and the IP address is where the data actually lives.

What is HTTP, and what is a request and response?

HTTP (HyperText Transfer Protocol) is the agreed set of rules browsers and apps use to talk to servers. The conversation comes in pairs: the client sends a request (please give me this data), and the server sends back a response (here it is, or here is an error). Almost everything on the web is built from these request-and-response pairs.

Web and mobile: HTML versus JSON

Traffic usually comes from two sources: web applications and mobile applications (at 04:18). For web users, the server handles the business logic, data storage and presentation, and sends back HTML, CSS and JavaScript so the browser can draw the page (at 04:18). For mobile users, the conversation still happens over HTTP, but the app asks for data through API calls and the server replies with JSON — a lightweight format that is easy for a mobile device to read (at 04:42).

What is JSON?

JSON (JavaScript Object Notation) is a simple text format for structured data, written as names paired with values. It is small, human-readable and understood by almost every programming language, which is why mobile apps and APIs lean on it so heavily. When a server returns JSON, the app reads the fields it needs and lays them out on screen.

An example API call

Here is a concrete request the server might receive. The mobile app wants the details of one product, so it sends a GET request to our domain, to a path with that product's id (at 04:42):

GET /product/{id}

This is an endpoint whose job is to retrieve one product. The server replies with a JSON response holding that product's details — its id, name, description, price and any other metadata the client needs to show it on screen (at 05:05). A small illustrative example:

{
  "id": 42,
  "name": "Wireless headphones",
  "description": "Over-ear, noise cancelling",
  "price": 129.99
}

The app (or the browser) then uses this data to display the product (at 05:05).

Why one server is not enough for long

This setup is ideal for a small user base, but it may struggle under heavy traffic (at 05:28). As more users arrive, the single server has to handle every request, every database read and every cached value by itself. Eventually it runs out of capacity, and responses slow down or fail. That is the problem the rest of the course solves — starting by splitting the parts apart so each can grow on its own (at 06:13). Watching for the moment one server is no longer enough is exactly the instinct this guide is training.

In an interview, say…

"A request starts with a DNS lookup that turns the domain into an IP address. Then the client sends an HTTP request to that address, and the server returns HTML for a browser or JSON for an app." Walking the flow in order shows you understand the mechanics, not just the words.

Common misconception

DNS does not serve your web page or your data — it only hands back the server's IP address. The actual page or JSON comes from your server in a separate HTTP request afterwards. Mixing these two steps together is a common slip.

Recap
  • A single-server setup runs the web app, database and cache together — simple, and fine for a small user base.
  • A request begins with a DNS lookup that maps the domain to the server's IP address.
  • The client then sends an HTTP request; the server returns HTML for browsers or JSON for mobile apps.
  • Example: GET /product/{id} returns a JSON object with the product's id, name, description and price.
  • One server works until traffic grows; then it becomes the bottleneck, which is what later lessons fix.
