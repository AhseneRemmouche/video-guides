Authorization

What a user may do: role-based, attribute-based and access-control-list models, enforced with OAuth 2 and JWT.

Concept · explained from the video

The previous lesson answered the question "who are you?" with authentication. This lesson answers the next one: "what are you allowed to do?" That is authorization, and it is the step that happens straight after a user has logged in (at 104:58). Knowing who someone is does not tell you what they may touch; a logged-in user still needs rules that decide which resources and actions are open to them, and which are denied (at 105:21).

Authorization comes after authentication

Keep the two words apart. Authentication confirms identity — it decides whether to approve or deny a login request. Authorization runs afterwards, once the system already knows who the user is, and decides what that user can do inside the system (at 105:44). This is how an application controls security and privacy: the same identity can be granted one set of actions and refused another.

The presenter uses GitHub repositories as the everyday example (at 106:08). One user might have write access, so they can push code. Another might have read-only access, so they can view the repository but cannot push or open pull requests. An admin has full control and can even change settings or delete the repository. Same system, same login mechanism — very different permissions.

New to the difference? Authentication vs authorization in one line

Authentication is the bouncer checking your ID at the door — it decides whether you get in at all. Authorization is the wristband that says which rooms you may enter once you are inside. The first is about identity; the second is about permissions. You need both, and they run in that order.

Three models for managing permissions

Systems organise permissions using three common authorization models (at 105:44). Each has trade-offs, and real systems often combine more than one for a more secure setup (at 107:37).

RBAC — role-based access control

With RBAC, you do not grant permissions to people one by one. Instead you define roles, give each role a fixed set of permissions, and then assign users to roles (at 108:00). The presenter walks through three typical roles: an admin has full access — create, read, update, delete, and manage other users; an editor can create, read and update content but cannot delete or manage users; a viewer can only read (at 108:23). This is by far the most common model, and it is what you meet daily in GitHub, Stripe dashboards, content-management systems and team tools (at 108:45).

Why roles instead of per-user permissions?

Imagine setting five permissions individually for ten thousand users — fifty thousand decisions, and a nightmare to audit. With roles you decide the permissions once per role, then simply say "this person is an editor". New hire? Assign a role. Someone promoted? Swap their role. The permissions follow the role automatically, so the system stays easy to reason about even with millions of users.

ABAC — attribute-based access control

ABAC goes beyond roles. Instead of asking "what role does this user have?", it writes policies that combine attributes of the user, of the resource, and of the environment (at 109:09). A policy might say: allow access only when the user's department is HR and the resource is marked internal (at 109:33). User attributes could be department, age or clearance; resource attributes could be confidentiality, owner or classification; environment conditions could be time of day, location or device type (at 109:57). Because you combine several attributes to grant or deny each request, ABAC is more flexible than RBAC — but it needs careful policy management, is more complex, and policies can conflict with one another (at 110:20).

A small policy might read like this (illustrative):

policy "read-internal-hr"
  effect: allow
  action: read
  when:
    user.department   == "HR"
    resource.type     == "internal"
    environment.time  in  09:00..18:00

ACL — access-control list

The third model attaches the permission list to the resource itself (at 110:43). An ACL is kept per document or per file: user Alyssa has read access, Bob has read and write, a third user has none (at 110:43). You manage two things at once — which users may touch this specific resource, and what each of them may do (at 111:08). Google Drive is the classic example: you share one document with a colleague as read-only and another colleague with edit-and-comment rights (at 111:32). ACLs give fine-grained control over individual resources, but because they are so user-centric they are hard to scale to millions of users or objects unless managed carefully (at 111:08).

RBAC vs ABAC vs ACL — which lens does each use?

They answer the same question from different angles. RBAC groups permissions by role ("editors can update"). ABAC evaluates attributes at request time ("HR staff may read internal files during work hours"). ACL lists permissions on the resource ("this document is shared with Bob"). RBAC scales best, ABAC is most flexible, ACL is most precise — and large systems mix them.

How systems enforce these rules

Models decide what should be allowed; two technologies do the enforcing in practice (at 112:19).

OAuth 2 — delegated authorization

OAuth 2 is used when one service needs to act on a resource owned in another service, on your behalf (at 112:19). The presenter's example: you deploy an app to Vercel, which needs to read your GitHub repositories (at 112:43). You do not hand Vercel your GitHub username and password — that would give it unlimited control. Instead, GitHub issues a token that represents only the permissions you approved (at 112:43). You choose which repositories it can see and whether it may read, create, update or delete; GitHub then sends a token carrying exactly those permissions (at 113:06). The token proves what access was granted, not your identity, and OAuth 2 defines the flow for issuing and validating it safely (at 113:28).

JWT and bearer tokens carry the claims

Once a user is authenticated, most systems hand out a token — typically a JWT, or a bearer token — that carries the user's id, their roles (such as admin or editor), their scopes (what they are allowed to access), the expiry time, and the issuer (at 113:51). Every request the user makes carries this token to the backend, where the server checks that the token is valid and then applies the appropriate permission logic (at 114:14).

A JWT's claims payload looks something like this (illustrative):

{
  "sub":    "user_8821",
  "roles":  ["editor"],
  "scopes": ["repo:read", "repo:write"],
  "iss":    "auth.demo.com",
  "exp":    1764950400
}

Here is the key distinction the presenter stresses, and it is easy to confuse (at 114:38): the token carries the identity and claims; the authorization model — RBAC, ABAC or ACL — is what decides whether those claims are enough to allow the action. Tokens are the mechanism; models are the rules.

In an interview, say…

"Authentication proves identity; authorization decides permissions and runs after it. I would reach for RBAC by default because it scales, add ABAC where decisions depend on context, and use ACLs for per-resource sharing like documents. A JWT carries the claims, but the authorization model still decides what is allowed." Naming when to combine models is what senior interviewers listen for.

Common mistake

Do not treat a valid token as permission by itself. A token can be perfectly genuine and still not entitle the holder to the action — the server must check the claims against an authorization model every time. Confusing "the token is valid" with "the action is allowed" is how over-privileged access bugs creep in.

Recap
  • Authorization runs after authentication: it decides what an identified user can do.
  • RBAC assigns permissions to roles (admin / editor / viewer) — the most common model, used by GitHub and Stripe.
  • ABAC writes policies over user, resource and environment attributes — flexible but complex, and policies can conflict.
  • ACL keeps a per-resource permission list, like Google Drive sharing — precise but hard to scale.
  • OAuth 2 delegates a scoped token to a third party (Vercel reading your GitHub repos) instead of your password.
  • A JWT or bearer token carries id, roles, scopes, expiry and issuer; the authorization model, not the token, decides what is allowed. Real systems combine models.
