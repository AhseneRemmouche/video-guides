Authentication

Who the user is: basic, digest, API keys, sessions, bearer/JWT, access & refresh tokens, OAuth 2, OIDC and SSO.

Concept · explained from the video

Before a system can decide what you are allowed to do, it first has to know who you are. That is authentication: it verifies that the user or service trying to reach our system really is who they claim to be, whether they come through a browser, a mobile app, or as another service (at 83:27). This lesson is long because this is the topic engineers most often muddle. We will untangle it, then walk through every common method from the oldest to the modern standard (at 84:38).

Clear up the confusion first

Most of the confusion comes from treating four very different things as if they were all "login methods" (at 84:14). They are not:

  • JWT is a token format, not an authentication method — it is just a way to shape a token.
  • Bearer is a pattern (whoever holds the token gets access), not a specific method; people confuse it with JWT.
  • OAuth 2 is an authorization framework, not authentication — it is about access, not identity.
  • Single sign-on (SSO) is a user-experience pattern (log in once, use many services), not a method either.

Postman, the API tool, lists all of these together under one "Authorization" tab to keep its interface simple, which is one reason developers come to believe they are all the same kind of thing (at 89:42). Keep this slide in mind for the rest of the lesson.

Authentication comes before authorization

Authentication answers one simple question: who is the user trying to reach our system (at 85:01)? Picture your system as an API gateway in front of a service layer and a data store. Before anyone can call those services, they send a login request. If the identity checks out, we grant access; if not, we reject it with a 401 Unauthorized status (at 85:50). Only after that does authorization — what you are allowed to do — come into play, which is the next lesson's topic (at 86:13).

Authentication versus authorization

They sound alike but answer different questions. Authentication = "who are you?" (proving identity). Authorization = "what are you allowed to do?" (checking permissions). You must authenticate first; authorization only makes sense once the system knows who it is dealing with. This lesson is entirely about the first one.

Basic and digest authentication

The simplest method is basic authentication (at 86:35). You request a resource such as /users; the server replies 401 because you sent no credentials and prompts you to provide them (at 86:59). You retry the same request with an Authorization header containing the base64-encoded username:password. The server decodes and checks it, then returns 200 with the data or rejects it (at 87:22). The catch: base64 is not encryption, it is trivially reversible, so this is insecure unless wrapped in HTTPS — and even then it is rarely used in production outside internal tools, because the credentials travel on every request (at 87:46).

Digest authentication is slightly better: it sends an MD5 hash of the credentials instead of the base64 version, following the same 401-then-retry dance (at 88:10). It too is outdated and rarely used today, because better options exist (at 88:57).

Encoding is not encryption

Base64 turns bytes into a text-safe string so they survive being put in a header. Anyone can reverse it with a one-line command — there is no secret key involved. Encryption, by contrast, scrambles data so only someone with the key can read it. Basic auth only encodes, which is why it leaks your password to anyone who can see the request unless HTTPS encrypts the whole connection.

API keys

With API key authentication you generate a unique key for each client, and they send it with every request, in an Authorization header or an X-API-Key header (at 89:42). The server stores these keys in a database alongside a hash and their scopes, then looks the key up on each request; a valid key is authorized, a missing one gets 400 Bad Request, an invalid one gets 401 (at 90:29). This is what happens when you generate a key on a service's dashboard and attach it to your calls (at 90:29).

Two weaknesses matter. If the key leaks, anyone can act as you, and there is no built-in expiry unless you add it yourself (at 91:15). And unlike a JWT, an API key is just a random string with no information inside it — the server cannot tell who owns it or what they can do without a database lookup, so the key carries no identity (at 91:39).

Session-based authentication

The traditional web approach is session-based authentication (at 91:39). The user logs in with credentials, and the server creates a session in some session storage. That storage can be in memory (simple, but lost when the server restarts), a dedicated SQL database, or the file system (rare, and hard to scale). In production the usual choice is Redis, because it is fast and supports automatic expiry (at 92:25). The server returns a session id and sets a session cookie on the client (at 92:47). Every later request carries that cookie; the server looks the session up and, if it is valid, returns the user's data (at 93:11).

The downside is that this approach is stateful: the server must remember every session. That works well for traditional web apps but does not scale as easily for APIs or distributed systems, where many servers would each need to reach the same session store (at 93:11).

Token-based: bearer and JWT

Modern applications usually use tokens instead of sessions. The client sends a token with each request, in an Authorization header that names the type — Bearer — followed by the token (at 93:59). A bearer token simply means "whoever holds this token gets access": it is a pattern, not a specific method (at 93:59). The most common kind of bearer token is a JWT (JSON web token): a signed JSON object holding the user id or email, an expiry time, and other claims such as roles (at 94:23).

The big advantage is that a JWT is stateless (at 94:45). Before JWTs, a token was just a string the server had to look up in a database or cache every single time — stateful and slow (at 95:10). A JWT instead carries its own signed claims, so the server verifies the signature locally, with no database lookup. That reduces load and scales far better than sessions (at 95:31). A JWT has three parts joined by dots: a header, a payload of claims, and a signature (at 95:31).

Stateful versus stateless

A stateful system remembers something between requests — sessions, for instance, live on the server, so every server must reach the same store. A stateless system keeps no per-user memory: each request carries everything needed to verify it. JWTs are stateless because the claims and signature travel inside the token, which is what lets you add servers freely without sharing a session store.

Access tokens and refresh tokens

Modern systems issue two tokens at login (at 96:20). An access token is short-lived (15 minutes to an hour) and is sent on API calls. A refresh token is long-lived (days or weeks) and exists only to obtain new access tokens (at 96:45). When the access token expires you get a 401; the client then presents the refresh token, receives a fresh access token, and carries on without the user logging in again (at 97:34).

Storage matters here. The refresh token must never be kept in localStorage; it belongs in an HTTP-only cookie, which browser JavaScript cannot read, protecting it from cross-site scripting attacks on the client (at 97:09).

OAuth 2: access, not identity

OAuth 2 is one of the most misunderstood concepts. It is an authorization framework, not authentication: it answers "what can this app access on behalf of the user?" (at 97:58). Say you want to let an application read files from your Google Drive. You do not hand the app your password; instead Google redirects you to a consent screen listing the permissions requested. If you allow it, Google returns an authorization code to the app, which the app exchanges for an access token, and then uses that token to read your Drive files (at 98:44).

Here is the subtle part that trips people up: the access token proves the app is allowed to access certain resources, but it does not tell the app who you are (at 99:30). OAuth 2 grants access, not identity.

OpenID Connect: identity on top

OpenID Connect (OIDC) adds authentication on top of OAuth 2 (at 99:53). When you click "Sign in with Google", the provider redirects you to log in and consent, returns an authorization code, and the app exchanges it for tokens — but now you get back two: the OAuth 2 access token and an ID token (at 100:16). The ID token is a JWT containing your identity (email, username, user id). The app verifies its signature, extracts who you are, and creates its own session for you (at 100:39). This is the modern, secure, scalable pattern behind "Sign in with Google / GitHub / Microsoft" (at 101:01).

OAuth 2 versus OpenID Connect

They are a pair, not rivals. OAuth 2 handles authorization: can this app touch these resources on your behalf? OpenID Connect is a thin layer on top that adds authentication by returning an ID token — a JWT that states who you are. "Sign in with Google" uses OIDC; "let this app read my Google Drive" uses plain OAuth 2.

Single sign-on

Single sign-on (SSO) is a user-experience pattern, not an authentication method: log in once and access many services (at 101:25). Sign in to an identity provider such as Google once, and you reach Gmail, Drive, YouTube and Calendar without logging in again (at 101:50). Behind the scenes the provider stores a global session and returns an SSO cookie to your client; each service you open then checks that session rather than asking you to log in afresh (at 102:14).

SSO relies on identity protocols underneath. SAML (Security Assertion Markup Language) is XML-based and common in enterprise and legacy systems such as Salesforce; it returns a SAML assertion in XML to confirm your identity (at 102:37). OpenID Connect is the modern alternative, returning an ID token as a JWT (at 103:49). Both are secure and still widely used (at 104:12).

In an interview, say…

"Authentication proves identity and comes before authorization. Sessions are stateful and live on the server; JWTs are stateless and verified by signature, so they scale better. OAuth 2 grants access to resources, OpenID Connect adds identity with an ID token, and SSO is the log-in-once experience built on SAML or OIDC."

Common mistake

JWT is not an authentication method — it is a token format. Nor is bearer a method (it is a pattern), OAuth 2 is authorization not authentication, and SSO is a user-experience pattern. Mixing these up is the single most common error in this topic. Also: never store a refresh token in localStorage; use an HTTP-only cookie.

Recap
  • Authentication answers "who are you?" and comes before authorization; failure returns 401.
  • JWT is a format, bearer is a pattern, OAuth 2 is an authorization framework, SSO is a UX pattern — none is itself a method.
  • Basic auth base64-encodes credentials (reversible, HTTPS-only); digest uses MD5; both are outdated. API keys are random strings with scopes but carry no identity and can leak.
  • Session-based auth is stateful (server stores sessions, often in Redis); token-based auth with JWT is stateless and verified locally.
  • Access tokens are short-lived for API calls; refresh tokens are long-lived, renew them, and belong in HTTP-only cookies.
  • OAuth 2 grants resource access (not identity); OpenID Connect adds identity via a JWT ID token ("Sign in with Google"); SSO logs you in once across services using SAML or OIDC.
