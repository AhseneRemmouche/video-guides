Scaling: Vertical vs Horizontal

Scaling up vs scaling out, their trade-offs, and why horizontal scaling needs a load balancer.

Concept · explained from the video

Once the tiers are split, the next question is how to handle more traffic. There are two ways to grow: make one server bigger, or add more servers. This lesson explains both — vertical and horizontal scaling — why horizontal scaling suits high-traffic apps, and why it needs a new piece in the middle: the load balancer.

Two ways to scale

There are two primary approaches to scaling, and each handles growth differently (at 12:44). Vertical scaling makes a single server more powerful. Horizontal scaling adds more servers that share the work. We will look at each, then see why horizontal scaling is usually the better fit for high-traffic applications.

Vertical scaling (scale up)

Vertical scaling, also called “scale up”, means adding more resources to the server you already have — more RAM, more CPU, or anything else that helps it handle more traffic (at 12:44). It is simple, and it works well for low or moderate traffic because nothing about the architecture changes; the machine just gets stronger.

But it has two real limits (at 13:08). First, resource limits: there is a hard cap on how much you can add to one machine, and eventually you cannot upgrade any further. Second, no redundancy: there is still only one server, so if it goes down, the whole application goes down with it (at 13:32).

New to redundancy? Why one of anything is risky

Redundancy means having a spare so that no single failure stops everything. With one server there is no spare: a crash, a reboot or a hardware fault takes the whole app offline. Redundancy is the main reason teams add more servers even before they run out of raw power — it keeps the service up when one part dies.

Horizontal scaling (scale out)

Horizontal scaling, also called “scale out”, adds more servers to share the load instead of enlarging one (at 13:32). Rather than a single server, you might run three copies of the same server and spread requests across them. This suits large-scale applications for two reasons (at 13:56). It gives higher fault tolerance: if one server goes down, the others keep serving users while it recovers. And it gives better scalability: when you need more capacity, you simply add another server.

New to fault tolerance? What it buys you

Fault tolerance is a system's ability to keep working when one part fails. With several servers behind the scenes, one can crash and users never notice — the rest pick up its share. It is the practical payoff of redundancy: not just having a spare, but staying online while a failed part is repaired or replaced.

Distributing the traffic: the load balancer

Horizontal scaling raises a new question: with three servers, where should each request go (at 14:20)? When a mobile app sends a request, something must decide whether it goes to server one, two or three. That something sits in the middle and is called a load balancer (at 14:43).

The load balancer distributes traffic across the servers (at 15:06). For each new request it picks a server — for example the one with the least load — and forwards the request there. It also makes adding capacity easy: introduce a fourth server and the load balancer starts sending it traffic too.

The load balancer also handles fault tolerance (at 15:28). It keeps watch over the servers, and if one goes down — say server three — it simply stops sending traffic there and routes everything to the servers that are still up, until server three comes back.

Vertical vs horizontal at a glance

 Vertical (scale up)Horizontal (scale out)
What you changeAdd RAM / CPU to one serverAdd more servers to the pool
ComplexitySimple; nothing else changesNeeds a load balancer in front
LimitsHard resource cap on one machineAdd servers as needed
If a server diesWhole app goes down (no redundancy)Others keep serving (fault tolerant)
Best forLow / moderate trafficLarge-scale, high-traffic apps
In an interview, say

“I would start by scaling vertically because it is simple, then move to horizontal scaling behind a load balancer once I need redundancy and want to grow past one machine's limits.” Naming when you switch shows you understand the trade-off, not just the terms.

Common mistake

Adding more servers but forgetting the load balancer. Without it, clients have no single address to hit and traffic is not shared, so the extra servers do nothing. Horizontal scaling and the load balancer go together.

Recap
  • Vertical scaling (scale up) adds RAM/CPU to one server: simple, but it hits a hard resource cap and has no redundancy.
  • Horizontal scaling (scale out) adds more servers: higher fault tolerance and better scalability.
  • Horizontal scaling needs a load balancer to spread requests and to route around a failed server.
  • Start simple, then scale out behind a load balancer when you need to grow past one machine and survive failures.
