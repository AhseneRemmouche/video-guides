Load Balancing Strategies

Seven load-balancing algorithms, health checks, and software, hardware and cloud load balancers.

Concept · explained from the video

Once you scale out to many servers, something has to stand in front of them and decide which server handles each incoming request. That something is the load balancer. This page explains what a load balancer does, the seven strategies it can use to spread traffic, how it notices a dead server with health checks, and the three kinds of load balancer you will meet in real systems.

What a load balancer does

A load balancer sits between the clients and your pool of servers. Its job is to distribute the incoming traffic across those servers so that no single server bears too much load (at 16:36). It is the piece that makes horizontal scaling work: add more servers, and the load balancer shares the work among them. It also routes around trouble — if a server stops responding, the load balancer stops sending it requests.

The interesting question is how it chooses a server for each request. There is no single right answer; there are seven common strategies, and each one suits a different situation. We will look at each in turn.

New to this? What "a request" and "an active connection" mean

A request is one message from a client asking the server to do something (fetch a product, save a form). A connection is the open line between a client and a server while that work is happening. A server can hold many connections at once — one per user it is currently serving. Several strategies below decide where to send traffic by counting how many connections each server is juggling right now.

The seven load-balancing strategies

1. Round robin

Round robin is the simplest and most popular algorithm (at 16:58). Each server in the pool gets a request in a sequential, rotating order: request one goes to server one, request two to server two, request three to server three, and then it loops back to server one. It keeps cycling like that. Round robin works well when all the servers have similar specifications — same CPU, same memory — because it assumes every server can handle an equal share.

2. Least connections

The least connections algorithm directs each new request to the server with the fewest active connections right now (at 17:43). If server one has 10 open connections, server two has 9, and server three has 30, the next request goes to server two, because it is the least busy. This is useful when sessions have variable lengths — one user might stay for ten minutes while another leaves after one — so a simple rotation would leave some servers overloaded. Counting live connections keeps the load even.

3. Least response time

Least response time goes one step further and focuses on how fast each server answers (at 18:30). It prefers the server with the lowest response time and the fewest active connections. So it sends as much traffic as it can to the fastest server, but once that server fills up with connections it switches some traffic to the next most responsive server, and so on. This is effective when your goal is the quickest possible response and your servers have different capabilities.

4. IP hash

The IP hash algorithm chooses the server based on a hash of the client's IP address (at 19:15). When client one first connects, the load balancer hashes its IP address and lands on, say, server two. Every future request from that same client is hashed the same way, so it always goes back to server two. This is useful when a client needs to stay with the same server — for example when each server keeps some information about the clients connected to it.

New to this? What a "hash" is

A hash function turns any input (here, an IP address) into a fixed value in a predictable way. The same input always produces the same output. That property is exactly what makes IP hash — and consistent hashing below — able to send the same client to the same server every time, without storing a lookup table.

5. Weighted algorithms

Weighted algorithms are variants of the methods above — you can have weighted round robin or weighted least connections (at 20:25). Each server is assigned a weight based on its capacity and performance, such as how much RAM it has. If server one has 16 GB, server two 32 GB and server three 64 GB, the heavier (more powerful) servers are given a larger share of the traffic. The load balancer sends most requests to the strongest server and smaller portions to the weaker ones.

6. Geographic

Geographic algorithms are location-based: they direct each request to the server geographically closest to the user (at 21:10). Imagine a pool with one server in US East, one in US West, and one in Europe. A user in Europe is routed to the European server; a US user is checked by IP address and sent to US East or US West. This is useful for global services where reducing latency matters, because a nearer server means a faster reply.

7. Consistent hashing

Consistent hashing uses a hash function to place both the servers and the clients on a ring — a circle called the hash space (at 22:19). When a request arrives, the load balancer hashes the client's IP to a point on the ring, then hands the request to the nearest server going round the circle. Like IP hash, this keeps the same client on the same server. Its extra benefit is resilience: when a server is added or removed, only a small slice of clients is reassigned instead of reshuffling everyone.

In an interview, say this

Do not just name an algorithm — pair it with a reason. "Round robin for equally sized servers; least connections when request times vary; IP hash or consistent hashing when a client must stay on one server; weighted when servers differ in capacity; geographic to cut latency for a global audience." Showing the trade-off is what earns the marks.

Common mistake

Reaching for round robin by default. It only balances well when every server is the same size and every request takes a similar time. The moment sessions vary in length or servers differ in power, round robin can leave one server swamped while another sits idle — which is exactly what least connections or a weighted algorithm fixes.

Health checks: spotting a dead server

We said the load balancer stops sending traffic to a server that goes down — but how does it know a server is down in the first place? Through health checks (at 23:07). The load balancer continuously sends small health-check requests to every server and records which ones answer. If a server fails its health check, the load balancer marks it offline and stops routing requests there. When that server starts passing its health check again, the load balancer knows it is back online and resumes sending it traffic. This is what gives a balanced pool its fault tolerance.

Three kinds of load balancer

How do you actually run a load balancer? There are three families (at 23:54):

  • Software — a program you install on a server and configure. Nginx is the most common; it is also a web server, but it offers load-balancing too. You point it at the servers to balance, pick an algorithm, and set up health checks. HAProxy is another popular open-source option.
  • Hardware — a physical appliance built for the job. F5 is a widely used hardware load balancer known for high performance; Citrix also offers load-balancing hardware.
  • Cloud — a managed service you configure instead of running yourself. AWS Elastic Load Balancing, Azure Load Balancer and Google Cloud Load Balancing come with security, automatic scaling (adding servers to the pool as demand rises) and monitoring (their version of health checks) built in.
Recap
  • A load balancer spreads incoming traffic across a pool of servers and routes around failures.
  • Seven strategies: round robin (equal servers), least connections (variable sessions), least response time (fastest reply), IP hash (stick a client to one server), weighted (servers of different power), geographic (nearest region) and consistent hashing (sticky routing that survives server changes).
  • Health checks let the balancer detect offline servers and stop routing to them until they recover.
  • Load balancers come as software (Nginx, HAProxy), hardware (F5, Citrix) or cloud services (AWS ELB, Azure, GCP).
