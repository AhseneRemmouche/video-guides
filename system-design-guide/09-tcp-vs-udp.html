Transport Layer: TCP vs UDP

How data actually moves: reliable TCP vs fast UDP, the handshake, and which to pick.

Concept · explained from the video

Most developers build and call APIs every day, but rarely stop to think about what actually carries their requests across the internet (at 57:44). When your client sends a request to a server, the message is broken into small pieces and handed to a lower level of the network to deliver. That lower level is the transport layer, and it offers two very different ways to move data: TCP and UDP. This page explains both, so you can pick the right one for the kind of API you are designing.

In the OSI model the protocols we use to design APIs — HTTP, HTTPS, WebSocket, AMQP and gRPC — all live at the top, in the application layer (at 58:07). They do not deliver bytes themselves. They sit on top of the transport layer, which is where TCP and UDP do the real work of moving data from one machine to another. Both move data, but they make opposite trade-offs: TCP is reliable but slower, UDP is fast but makes no promises.

New to packets? What they are and why data is split up

When you send data over the internet it is almost never sent as one big lump. It is cut into many small pieces called packets, and each packet travels separately across the network before being reassembled at the other end (at 58:54). Large data — a file, a web page, a video frame — might be split into many chunks. The transport layer is responsible for how those packets are sent, and for what happens when one is lost or arrives in the wrong order.

TCP: reliable, connection-based delivery

TCP stands for Transmission Control Protocol (at 58:54). A good way to picture it is sending a parcel with a tracking number, a delivery receipt, and a required signature. When you send data, it is usually split into several chunks — say three — and TCP guarantees delivery of all of them. If a packet is lost on the way, TCP resends it. If packets arrive out of order, TCP puts them back in the right order before handing them to your application (at 59:17).

TCP is also connection-based. Before any data is sent, the client and server perform a three-way handshake to establish a connection (at 59:17). Only once that connection exists do they start exchanging data. All of this checking, resending and reordering adds overhead, which makes TCP slower — but it is accurate and reliable. That is why APIs that handle payments, authentication, user data and email always use TCP (at 60:03).

UDP: fast, connectionless delivery

UDP stands for User Datagram Protocol (at 60:03). It is fast and efficient, but the trade-off is that it does not guarantee that every packet arrives. If you send four packets and one is lost, UDP simply moves on — it will not resend it, and there is no delivery guarantee (at 60:03). There is also no handshake, no connection and no tracking. Because it skips all that work, UDP has less overhead and much faster transmission (at 60:26).

That sounds risky, but for some uses it is exactly right. In a video call, if someone's connection lags for a moment, you do not want the old, delayed audio resent to you — you are talking to them now (at 60:49). A dropped packet is fine; you move on to the next one. So UDP is the go-to for video calls, live streams and online games, where low latency matters far more than perfect delivery, and high throughput keeps the stream smooth (at 61:12).

In an interview, say: “TCP trades speed for reliability; UDP trades reliability for speed. I pick TCP when every byte must arrive — payments, auth, email — and UDP when fresh data matters more than complete data — live video, streaming, games.”
New to latency and throughput? Two ways to measure “fast”

Latency is the delay before data starts arriving — how long one message takes to make the trip. Throughput is how much data you can push through per second once it is flowing. A live video call needs low latency so the conversation feels instant; a large download cares more about high throughput. UDP's lack of handshakes and resends keeps latency low, which is why real-time media prefers it.

How to choose

The choice comes down to one question (at 62:19): do you need the connection to be safe and reliable, or do you need it to be fast and lightweight while tolerating some loss? If every piece of data must arrive, choose TCP — banking, email, payments. If speed matters most and the odd lost packet is acceptable, choose UDP — video streaming and gaming (at 62:41). Note that HTTP, the protocol behind REST APIs, runs on top of TCP — so most ordinary web APIs are reliable by default.

Common mistake: assuming “faster is always better” and reaching for UDP. For payments or login, a lost or reordered packet can corrupt data or drop a request silently — there is nothing to resend it. Only use UDP when losing the occasional packet genuinely does not matter.
Recap
  • TCP and UDP are transport-layer protocols; the API protocols (HTTP, WebSocket, gRPC) sit above them in the OSI model.
  • TCP is connection-based (three-way handshake: SYN, SYN-ACK, ACK), guarantees delivery, resends lost packets and reorders them — reliable but with more overhead.
  • UDP is connectionless, with no handshake, no delivery guarantee and no reordering — faster and lighter, but packets can be lost.
  • Choose TCP when every byte must arrive (payments, auth, user data, email); choose UDP when speed matters and some loss is fine (video calls, live streams, games).
