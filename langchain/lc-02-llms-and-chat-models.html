LLMs & Chat Models

Tokens, context windows, temperature, reasoning models, providers and cost.

What an LLM is, in one picture

A large language model is a very large neural network trained on huge amounts of text to do one thing: given some text, predict what comes next. Generation is a loop. The model reads everything so far, produces a probability for every possible next token, one token is picked, it is appended, and the loop repeats until the model produces a special "stop" token or hits a length limit.

Three consequences follow, and you will meet each in the project:

  • Output is produced piece by piece. That's why streaming is possible: you can show each token the moment it is picked instead of waiting for the whole answer.
  • Longer answers take longer. Every output token is one more turn of the loop. "Tell me a story" took noticeably longer than "what is the capital of Italy?" in the video (22:47).
  • The model only knows its input and its training. It has no memory between calls and no live connection to the world unless you give it one (messages for memory, tools for the world).

Tokens

Models don't read letters or whole words. They read tokens: chunks of text from a fixed vocabulary, often a common word, part of a word, a space plus a word, or punctuation. The exact split depends on the model's tokenizer. As a rough rule of thumb for English, one token is about four characters, or three quarters of a word. Other languages, code and unusual strings (like base64 image data) usually need more tokens per character.

You'll see tokens counted on every response. response.usage_metadata reports how many went in and came out (details below). The presenter points at these numbers when printing the full message at 27:56: "We have our tokens. We have who is our provider."

Training cutoff: what the model doesn't know

A model learns from data collected up to some date, its training cutoff. After training, its knowledge is frozen. It doesn't know today's news, today's date, prices that changed, or anything in your private files. Ask gpt-5-nano with no tools for the latest news and it says it can't pull real-time headlines (55:07, step 9). Give it a Tavily search tool and it can.

That's the main reason agents have tools. For the chef, the model already "knows" a lot of cooking, but a web search lets it ground the recipe in a real page. Each provider publishes the cutoff of each model in its documentation, so check there instead of asking the model, which may not know or may guess.

The context window

The context window is the maximum number of tokens a model can handle in one request, counting both the input you send and the output it writes. Everything the model "knows" about your conversation must fit in that window, on every call, because the model keeps nothing between calls.

Window sizes differ a lot between models and change with new releases, so check the provider's model page. A large window doesn't make big inputs free: you pay for every input token, and very long inputs are slower and can make the model miss details. Chapter 6 shows how to trim long conversations.

Sampling and temperature

At each step the model gives a probability for every possible next token. Sampling is how one token is chosen from those probabilities. Temperature reshapes them before the pick:

  • Low temperature (towards 0) sharpens the distribution: the most likely token almost always wins. Answers become more predictable and repeatable. Good for extraction, classification and code.
  • Higher temperature flattens it: less likely tokens get picked more often. Answers vary more between runs. Good for brainstorming and stories, but too high produces nonsense.

On OpenAI's API the range is 0 to 2. The presenter describes it as "from zero to one, from least creative to most creative" (20:47). That's a fair intuition, but the API accepts values above 1 too. Temperature 0 is not a hard guarantee of identical output either: it makes outputs much more consistent, not perfectly deterministic.

Why temperature=1.0 did nothing in the video

In step 4 the presenter sets temperature=1.0 and notices the answer isn't more creative (21:35). There are two reasons, both verified against the locked packages:

  1. 1.0 is already the default. Setting it changes nothing.
  2. gpt-5-nano doesn't accept other temperatures. The GPT-5 family are reasoning models that only accept the default. langchain-openai 1.3.4 knows this: for gpt-5* models it silently drops any temperature other than 1 (except gpt-5-chat* models, or when reasoning_effort="none"). So init_chat_model("gpt-5-nano", temperature=0) ends up with no temperature at all.
from langchain.chat_models import init_chat_model

init_chat_model("gpt-5-nano", temperature=0).temperature      # None  (dropped)
init_chat_model("gpt-5-nano", temperature=1.0).temperature    # 1.0   (the default anyway)
init_chat_model("gpt-4.1-mini", temperature=0).temperature    # 0.0   (kept: not a gpt-5 model)

To actually see temperature at work, use a model that supports it, such as gpt-4.1-mini at the time of writing. Ask for a short story three times at temperature=0 and three times at 1.2. The first three will be very similar; the last three will differ.

Reasoning models

A reasoning model is trained to "think" before it answers. It first generates internal reasoning tokens, working through the problem step by step, then writes the visible answer. OpenAI's gpt-5 family, including gpt-5-nano, works this way. What this means in practice:

  • Better at multi-step problems (planning, maths, deciding which tool to call), which suits agents.
  • Slower to the first visible token, because the reasoning happens first. When you stream, there's a pause before text appears.
  • Reasoning tokens count as output tokens, even though you don't see them. They show up in usage_metadata["output_token_details"]["reasoning"] when the provider reports them.
  • Fewer sampling knobs. As shown above, temperature is fixed. Instead, OpenAI reasoning models take a reasoning_effort setting (for example "low" or "high") that trades depth for speed. You can pass it through init_chat_model("gpt-5-nano", reasoning_effort="low"). Allowed values depend on the model, so check OpenAI's reasoning guide.

Providers and init_chat_model

A provider is a company or program that serves models through an API: OpenAI, Anthropic, Google, or Ollama running models on your own machine. Each API has its own request format. LangChain hides the differences behind one interface: every chat model class (ChatOpenAI, ChatAnthropic …) has the same invoke, stream, batch and bind_tools methods and returns the same message types.

init_chat_model is a factory that picks the right class for you. In the installed LangChain 1.3.12:

  • "gpt-5-nano" → the provider is inferred as openai from the gpt- prefix, and you get a ChatOpenAI.
  • "openai:gpt-5-nano" → explicit, the safer form. ext/models.py in step 19 uses it so you can switch with an environment variable.
  • Extra keyword arguments go to the provider class: temperature, max_tokens (cap on output length), timeout, max_retries, reasoning_effort…
  • create_agent(model="gpt-5-nano") (step 6) calls init_chat_model for you. Pass a model object instead when you need settings like these.

A model name in the wrong form can mislead the guessing. A name starting with gemini, for example, is currently guessed as Google Vertex AI (with a warning that this will change), not the Gemini Developer API. This is another reason to write the provider explicitly, as models.py does with "google_genai:…".

Cost tiers and latency

Hosted models are billed per token, with separate rates for input and output tokens. Output tokens (including hidden reasoning tokens) usually cost more than input tokens. Providers sell several tiers of the same family. In OpenAI's naming at the time of writing these are full, mini and nano models. Smaller tiers are cheaper and faster but less capable on hard tasks. The presenter picks gpt-5-nano, "a cheap model" (39:44), and adds $5 of credit to the OpenAI account in step 3, which is plenty for this course. Prices change often, so check the provider's pricing page and don't rely on numbers in tutorials.

Where the money and time go in an agent:

Cost driverWhyIn the chef project
Input tokens per callThe whole history is re-sent on every model call.The image and the Tavily results are sent again on the second call.
Number of model callsEach tool round trip is another call.One search means two model calls. Three searches mean four.
Output and reasoning tokensCharged at the output rate.A long recipe with steps, plus whatever reasoning the model does.
Tool calls themselvesThird-party APIs have their own limits.Each Tavily search uses credits (the free plan gives 1,000 a month).

Latency is how long the user waits. It has three main parts: network and queueing at the provider, time to first token (longer for reasoning models and long inputs), and generation time (longer for long outputs). For an agent, add the time of every tool call and every extra model call. Streaming doesn't make the total shorter, but the user sees progress right away, which feels much faster.

Chapter 9 covers spending limits and keeping costs under control.

invoke, stream and batch

Every chat model, and every agent, is a LangChain Runnable. All Runnables share the same set of methods (verified on langchain_core.runnables.Runnable):

MethodWhat you getUse it when
invoke(input)The complete result, once it's finished. For a model, one AIMessage.Scripts, background jobs, anything where you need the whole answer before continuing. Step 4, step 5.
stream(input)An iterator of pieces as they are generated (for a model, AIMessageChunks).Anything a person watches: chat UIs, terminals. Step 7 streams an agent with stream_mode="messages".
batch([input1, input2, …])A list of results, in the same order, run concurrently (in threads).Many independent requests, such as classifying 50 reviews. Faster than a loop of invoke.
ainvoke, astream, abatchThe same, as async versions.Async web servers (FastAPI and similar).
model = init_chat_model("openai:gpt-5-nano")

answer = model.invoke("What is the capital of Italy?")      # one AIMessage
print(answer.content)

for chunk in model.stream("Tell me a two-line story"):      # AIMessageChunk pieces
    print(chunk.text, end="", flush=True)

answers = model.batch(["Capital of Italy?", "Capital of Peru?"])   # list of AIMessage
print([a.content for a in answers])

What comes back: the AIMessage

model.invoke(...) returns an AIMessage, and the last item of an agent's response["messages"] is one too. Printing it whole, as the presenter does at 26:45, shows much more than the text. The fields you'll use (checked on langchain_core.messages.AIMessage):

msg = model.invoke("What is the capital of Italy?")

msg.content            # 'Rome.'
msg.text               # 'Rome.'  (always a plain string, even when content is a list of blocks)
msg.tool_calls         # []       (non-empty when the model asks for a tool)
msg.usage_metadata     # {'input_tokens': 13, 'output_tokens': 75, 'total_tokens': 88,
                       #  'output_token_details': {'reasoning': 64, ...}, ...}
msg.response_metadata  # {'model_name': 'gpt-5-nano-…', 'finish_reason': 'stop',
                       #  'model_provider': 'openai', 'token_usage': {...}, ...}

Two practical tips. First, prefer .text when you just want the words. content can be a list of content blocks for some providers and multimodal outputs, but .text is always a string. That's why step 18's streaming loop prints token.text. Second, log usage_metadata while you develop. It shows you exactly which prompts are expensive.

Common mistakes
  • ModuleNotFoundError: No module named 'langchain_openai': init_chat_model found the provider but its package isn't installed. Run uv add langchain-openai (18:59).
  • openai.OpenAIError: Missing credentials …: the key isn't in the environment. Call load_dotenv() before creating the model, and check the .env name and location (69:24).
  • Expecting temperature to change a gpt-5 model's style. It's dropped for those models; use a model that supports it.
  • Answer stops mid-sentence: check response_metadata["finish_reason"]. If it says "length", raise max_tokens or ask for a shorter answer. With reasoning models a low limit can be used up by reasoning before any text appears.
  • Asking the model for today's date or recent events and trusting the answer. It only knows its training data and your messages.
Common misconceptions
  • "The model remembers our chat." Each call is independent. Memory is your code re-sending the history (step 10).
  • "Temperature 0 means always identical output." It means much more consistent output, not a guarantee.
  • "Streaming is faster." It reaches the first word sooner, not the last.
  • "A bigger context window means I can paste everything." You pay for every token, every call, and quality can drop with very long inputs.
  • "LangChain is a model." It's a library that talks to models from many providers through one interface.
Recap
  • An LLM predicts the next token in a loop. Tokens are the unit of input, output, limits and billing.
  • Training cutoff: the model knows nothing after it. Tools such as web search fill the gap.
  • The context window holds input plus output for one call. The whole history is re-sent each time.
  • Temperature reshapes next-token probabilities. gpt-5* reasoning models only accept the default (1), and langchain-openai drops other values.
  • Reasoning models think first (hidden tokens, billed as output) and are tuned with reasoning_effort.
  • init_chat_model("provider:model", **settings) returns a provider class with a standard interface. Each provider needs its own package and key.
  • invoke = whole answer, stream = pieces as they come, batch = many inputs concurrently.
  • AIMessage: content/.text, tool_calls, usage_metadata, response_metadata, id.
