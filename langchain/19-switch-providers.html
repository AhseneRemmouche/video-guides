Switch Model Providers

Run the same chef on OpenAI, Anthropic, Google or a local Ollama model by changing one setting.

Extension · verified against LangChain 1.3.12

Extension, not in the video. models.py and main_any_model.py were run end-to-end against LangChain 1.3.12 with the offline test harness described in step 16 (fake chat model, canned Tavily result, no file picker). That checks the code paths, imports and the "provider:model" parsing with the installed packages. It did not call Anthropic, Google or Ollama: their integration packages aren't in the repo's lockfile. Model names on this page are examples at the time of writing. Always check the provider's current model list.

TypeScript version. The TypeScript project has two ways to switch models. src/models.ts reads MODEL_PROVIDER (openai or ollama) and is used by every lesson and chef file. chef/main-any-model.ts reads a "provider:model" string from CHEF_MODEL, like the Python file. Both passed pnpm test with a fake model, and main-any-model.ts was run for real with CHEF_MODEL=ollama:gemma4 (output below). Anthropic and Google were not called: their packages are not installed in the project.

Goal

The whole course uses one model, OpenAI's gpt-5-nano. But one of LangChain's main promises (step 2) is that the rest of your code doesn't care which provider runs the model. In this step you make that real: the chef reads the model name from a setting in .env, so you can switch between OpenAI, Anthropic, Google or a free local model with Ollama by changing one line, without touching the code.

Reasons you might switch: you already have credit with another provider, you want to compare answers, a model handles your language better, or you want to run everything on your own computer.

In TypeScript, chef/main-any-model.ts reads CHEF_MODEL itself and passes it to initChatModel (from "langchain"), which builds the matching class from the prefix: ChatOpenAI, ChatAnthropic, ChatGoogleGenerativeAI or ChatOllama.

New to model providers? Who actually runs the model

A chat model is trained and hosted by a company: OpenAI (GPT models), Anthropic (Claude models), Google (Gemini models) and others. Each company is a provider, with its own website, API, API key, billing and model names. Their APIs all do the same basic job (messages in, message out), but the details differ.

LangChain hides those details behind one interface. Each provider has an integration package (langchain-openai, langchain-anthropic…) with a class such as ChatOpenAI or ChatAnthropic. All these classes have the same methods (invoke, stream, tool binding), so create_agent can use any of them.

There's also a fourth option: run a model yourself. Ollama is a free program that downloads open models and runs them on your computer. No key, no bill, and your photos never leave your machine, but you need a reasonably powerful computer and local models are usually smaller.

The "provider:model" string

In the course you wrote init_chat_model("gpt-5-nano") and LangChain guessed the provider from the name: anything starting with gpt- is OpenAI. That guessing has limits. LangChain 1.3.12 maps names starting with claude to Anthropic, but names starting with gemini to google_vertexai (Google's enterprise cloud), not to the simpler google_genai API most beginners use, and a name like llama3.2 can't be guessed at all. The reliable way is to say the provider explicitly, before a colon:

LangChain.js's initChatModel also infers openai from the gpt-5 prefix, but it is async: await initChatModel("gpt-5-nano"). Write the prefix explicitly here too. Note the spelling for Google: google-genai: with a dash in JavaScript, google_genai: with an underscore in Python.

Found in the LangChain.js source: "openai:" turns on the Responses API. When you give createAgent the model as a string that starts with "openai:", for example createAgent({ model: "openai:gpt-5-nano" }), it also sets useResponsesApi: true, so requests go to OpenAI's newer Responses API. A bare "gpt-5-nano" uses Chat Completions. With the Responses API a message's .content can be a list of blocks instead of a string, which is one reason every file in the project prints .text: plain text in both cases. The lessons use the bare name (MODEL_ID in src/models.ts). chef/main-any-model.ts passes a model object built by initChatModel (line 18), not a string; whether that path also uses the Responses API was not checked (no OpenAI key).

Model names change often: new ones appear and old ones are retired. Treat these as examples at the time of writing and copy the current name from the provider's documentation. Keys come from each provider's own console, the same way you created your OpenAI key in step 3. Never paste keys into code or screenshots.

The TypeScript files check no Tavily key: without one, web_search answers "Web search is not configured…" and the model works from its own knowledge. All the real runs on these pages were made that way.

import os

from langchain.chat_models import init_chat_model

# "provider:model" strings. Set CHEF_MODEL in .env to switch without touching code.
# Examples (check each provider's current model list):
#   openai:gpt-5-nano              needs langchain-openai        + OPENAI_API_KEY
#   anthropic:claude-haiku-4-5     needs langchain-anthropic     + ANTHROPIC_API_KEY
#   google_genai:gemini-2.5-flash  needs langchain-google-genai  + GOOGLE_API_KEY
#   ollama:llama3.2                needs langchain-ollama        + Ollama running locally
DEFAULT_MODEL = "openai:gpt-5-nano"


def get_model():
    return init_chat_model(os.getenv("CHEF_MODEL", DEFAULT_MODEL))
// One place that decides which model every lesson and the chef use.
// MODEL_PROVIDER=openai (default, like the course) or MODEL_PROVIDER=ollama (free, runs on your computer).
import "dotenv/config";
import { ChatOllama } from "@langchain/ollama";
import { ChatOpenAI } from "@langchain/openai";

export const PROVIDER = process.env.MODEL_PROVIDER === "ollama" ? "ollama" : "openai";

export const OPENAI_MODEL = process.env.OPENAI_MODEL ?? "gpt-5-nano";
export const OLLAMA_MODEL = process.env.OLLAMA_MODEL ?? "llama3.2";
// llama3.2 cannot see images; gemma4 can (vision, tools and thinking).
export const OLLAMA_VISION_MODEL = process.env.OLLAMA_VISION_MODEL ?? "gemma4";

// The same model as a "provider:model" string, for initChatModel and createAgent({ model: "..." }).
export const MODEL_ID = PROVIDER === "openai" ? OPENAI_MODEL : `ollama:${OLLAMA_MODEL}`;

type ModelOptions = { temperature?: number };

function ollama(model: string, options: ModelOptions) {
  // numCtx keeps the context window small enough for an ordinary GPU, numPredict caps the answer length
  // (2048 tokens: room for a full recipe),
  // think: false turns off the hidden "thinking" of models such as gemma4 (much faster).
  return new ChatOllama({ model, temperature: 0, numCtx: 8192, numPredict: 2048, think: false, ...options });
}

/** The chat model for text. Pass { temperature } to change it (OpenAI documents only the default, 1, for gpt-5 models). */
export function getModel(options: ModelOptions = {}) {
  if (PROVIDER === "ollama") return ollama(OLLAMA_MODEL, options);
  return new ChatOpenAI({ model: OPENAI_MODEL, ...options });
}

/** The chat model for photos. On OpenAI it is the same model; on Ollama it must be a vision model. */
export function getVisionModel(options: ModelOptions = {}) {
  if (PROVIDER === "ollama") return ollama(OLLAMA_VISION_MODEL, options);
  return getModel(options);
}

New to os.getenv with a default? Settings vs secrets in .env

os.getenv("NAME", "fallback") looks up an environment variable. If it exists you get its value; if not you get "fallback" instead of None. That's the classic way to make a setting optional.

In TypeScript the same pattern is process.env.CHEF_MODEL ?? DEFAULT_MODEL: ?? uses the right side when the variable is not set.

Your .env file can hold both secrets (API keys) and ordinary settings like CHEF_MODEL. Putting the model name there means you can try another model without editing, committing or reviewing code, and two people on the same project can each use a different model. Since .env is in .gitignore, the setting stays on your machine.

Switching to a cloud provider (example: Anthropic)

  1. Install the integration package 
    uv add langchain-anthropic

    In TypeScript: pnpm add @langchain/anthropic. It is recorded in package.json and pnpm-lock.yaml, so teammates get it with pnpm install.

    This adds the package to pyproject.toml and uv.lock, so teammates get it with uv sync.

  2. Create a key

    Sign in to the provider's console, create an API key, and add billing or credit if the provider requires it. Copy the key once; most consoles won't show it again.

  3. Add two lines to .env 
    ANTHROPIC_API_KEY=your-anthropic-key-here
CHEF_MODEL=anthropic:claude-haiku-4-5

    Keep your existing OPENAI_API_KEY and TAVILY_API_KEY lines. Replace the placeholder with your real key, no quotes, no spaces around =.

Running a local model with Ollama

Ollama runs open models on your own computer. Nothing to pay and no key, but the model runs on your CPU or graphics card, so it's slower on an average laptop, and you need several gigabytes of free disk space per model.

  1. Install Ollama

    Download it from ollama.com for Windows, macOS or Linux, and install it. It runs in the background and listens on http://localhost:11434.

  2. Download a model 
    ollama pull llama3.2

    ollama is the command-line tool that came with the app; pull downloads a model by name, like git pull fetches code. This one takes a few minutes the first time.

    The TypeScript chef sends the photo, so it needs a vision model too: ollama pull gemma4. The text lessons use llama3.2.

  3. Install the integration and set the model 
    uv add langchain-ollama

    Then add CHEF_MODEL=ollama:llama3.2 to .env. No key line is needed.

    In TypeScript there is nothing to install: @langchain/ollama is already in package.json. Add CHEF_MODEL=ollama:gemma4 to .env for this file, or MODEL_PROVIDER=ollama for every file. No key line is needed.

  4. Read the next section before running the chef

    The chef needs two abilities that not every model has.

Not every model can run the chef

LangChain gives every model the same interface, but it can't give a model abilities it doesn't have. The chef needs two:

  • Tool calling: the model must be able to ask for web_search in the structured way described in step 8 (a tool call). Without it, the agent can't search; depending on the model you get an error or an answer that never searches.
  • Vision (image input): the model must accept the image block from photo_decoder.py. A text-only model can't see your photo at all, so it either rejects the message or answers without knowing the ingredients.

The big cloud providers' current general-purpose models generally support both, but check each model's page. For local models it varies a lot. llama3.2 is a good, small first download to test that Ollama and LangChain talk to each other, and it supports tool calling, but it's text-only, so it can't see your photo. For the full chef, pick a model whose page in Ollama's library lists both the tools and vision capabilities, and ollama pull that one instead.

Checked on the machine used for the TypeScript runs. ollama show llama3.2 lists the capabilities completion and tools, no vision. ollama show gemma4 lists completion, vision, audio, tools and thinking. That's why getVisionModel() in src/models.ts uses gemma4 on Ollama, and why the real chef runs on steps 16–19 use it. gemma4 "thinks" by default; src/models.ts turns that off with think: false, which its comment says is much faster.

New to local models? What changes when the model runs on your computer

A cloud model runs on the provider's servers; you send your messages over the internet and pay per token. A local model is a large file (often several gigabytes) that a program like Ollama loads into your computer's memory. Generating each answer is called inference, and with a local model your own processor does it.

  • Good: free to use, works offline (apart from the search tool here), and your data stays on your machine.
  • Trade-offs: needs disk space and memory, can be slow without a strong graphics card, and the models that fit on a laptop are smaller, so answers and tool use may be less reliable.

The code doesn't care: ChatOllama has the same methods as ChatOpenAI.

## 🔪 The Chef's Recipe: Creamy Lime Chicken Skillet

This dish marries the robust flavors of Asian cooking (soy sauce, chicken) with the creamy, bright elegance of Mediterranean cuisine (yogurt, lime, cheese).

**Prep Time:** 15 minutes
**Cook Time:** 30 minutes
**Serves:** 2-3

### 🥕 Ingredients List (The Palette)

*   **Chicken:** ~1 lb (cut into bite-sized pieces)
*   **Onions:** 1 large, diced
*   **Carrots:** 2-3 medium, sliced or diced
*   **Spinach:** 4-5 handfuls, roughly chopped
*   **Tomatoes:** 2-3 medium, diced
*   **Yogurt:** 1/2 cup (full-fat preferred)
*   **Milk:** 1/2 cup
*   **Butter:** 2 tbsp
*   **Eggs:** 3 large (for binding/topping)
*   **Soy Sauce:** 3-4 tbsp (or to taste)
*   **Cheese:** 1 cup (shredded, a versatile melting cheese like mozzarella or cheddar works best)
*   **Lime:** Juice and zest of 1 whole lime
*   **Lime:** (The remaining lime is for garnish/acidity boost)

***

### 🔥 Method: The Art of Assembly

**Phase 1: Building the Foundation (Searing)**
1.  In a large, deep skillet or frying pan, melt the **butter** over medium-high heat.
2.  Add the diced **chicken** and season lightly (salt and pepper, if allowed, but otherwise rely on the soy sauce). Sear the chicken until golden brown on all sides and nearly cooked through. Remove the chicken from the pan and set it aside, leaving the flavorful browned bits (fond) in the skillet.
3.  Reduce the heat to medium. Add the diced **onions** and **carrots** to the same skillet. Sauté for 5-7 minutes until they begin to soften.

**Phase 2: The Deep Flavor (Building the Sauce)**
1.  Push the vegetables to one side of the pan. Pour in the **yogurt** and **milk**, stirring to combine with the rendered chicken fat and vegetable juices.
2.  Stir in the **soy sauce**, the **lime juice**, and the **lime zest**. Bring the mixture to a gentle simmer.
3.  Add the diced **tomatoes** and the cooked **chicken** back into the pan.
4.  Allow the sauce to bubble gently, letting it thicken slightly (about 5 minutes).
5.  Finally, stir in the **spinach**. It will wilt almost instantly. Cook just until the spinach is tender, about 1-2 minutes.

**Phase 3: The Finale (Binding and Finishing)**
1.  Reduce the heat to low. Stir in the majority of the **cheese** until it is melted and the sauce is creamy.
2.  While the sauce finishes, lightly whisk the **eggs** in a small bowl. Pour the whisked eggs evenly over the top of the skillet, letting them cook like a delicate crust or a light custard (this is your egg "lid").
3.  Sprinkle the remaining **cheese** over the top of the egg layer.
4.  Cook gently for about 5-8 minutes, until the egg layer is set but still moist, and the cheese is perfectly melted and bubbly.
5.  Serve immediately, drizzling the rich sauce over the chicken and vegetables, and garnishing heavily with fresh **lime** wedges and a sprinkle of fresh herbs (if available, otherwise, a final squeeze of lime is perfect).

***

### 👨‍🍳 Chef's Notes

*   **Texture Control:** If you prefer a saucy dish, cook the eggs *separately* and serve them on the side as a soft scramble. If you want a rich, cohesive casserole effect, pour them directly on top as instructed.
*   **Acidity Balance:** The **lime** is the hero here. It cuts through the richness of the butter, creaminess of the yogurt, and depth of the soy sauce. Never skimp on the zest!
*   **Why it Works:** This dish perfectly balances the savory (soy sauce/chicken), the creamy (yogurt/milk/cheese), and the bright (lime/tomatoes). Every ingredient serves a vital, beautiful purpose.

Common mistakes

  • ImportError: Initializing ChatAnthropic requires the langchain-anthropic package. Please install it with `pip install langchain-anthropic`: the integration isn't installed. In a uv project, use uv add langchain-anthropic rather than pip install, so it's recorded in pyproject.toml.
  • A bare model name such as CHEF_MODEL=gemini-2.5-flash: LangChain 1.3.12 guesses google_vertexai, a different Google service with different setup. Always write the prefix.
  • A typo in the provider key, for example google: or googlegenai:: the prefix isn't recognised, so the whole string is treated as a model name and you get Unable to infer model provider. The valid keys include openai, anthropic, google_genai and ollama.
  • Quotes or spaces in .env: write CHEF_MODEL=ollama:llama3.2, not CHEF_MODEL = "ollama:llama3.2". python-dotenv tolerates some of this, but the plain form always works.
  • Ollama not running: a "connection refused" error mentioning localhost:11434. Start the Ollama app, or run ollama serve in another terminal.
  • Model not pulled: an error saying the model wasn't found. Run ollama pull <name> with exactly the name in CHEF_MODEL (after ollama:).
  • Expecting temperature to behave the same everywhere: providers and models differ (step 4 showed gpt-5-nano ignores it). This file doesn't set it, so each model uses its default.
  • No CHEF_MODEL and no OpenAI key: the file starts, then the first call fails with OpenAIError: Missing credentials…. Set CHEF_MODEL or add the key.
  • google_genai: with an underscore: that's the Python spelling. LangChain.js writes google-genai:.
  • A provider package that isn't installed: initChatModel can't load the integration. Install it with pnpm add, for example pnpm add @langchain/anthropic, so it is recorded in package.json.
  • Expecting temperature to be dropped, as in Python: @langchain/openai 1.6.2 sends the temperature you give it, even to gpt-5-nano. OpenAI documents only the default (1) for these models, so another value would likely be rejected (not tested: no key). src/models.ts only passes a temperature when you ask for one.

Recap
  • init_chat_model("provider:model") picks the integration from the prefix; always write the prefix rather than relying on name guessing.
  • models.py reads CHEF_MODEL from .env with a default, so switching models is a settings change, not a code change.
  • Each provider needs its integration package (uv add langchain-anthropic, langchain-google-genai, langchain-ollama) and, for cloud providers, its own key.
  • Ollama runs models locally: install it, ollama pull llama3.2, and use ollama:<name>.
  • The chef needs a model with tool calling and vision; check the provider's model page. Model names are examples at the time of writing.
  • In TypeScript, MODEL_PROVIDER in src/models.ts switches every file between OpenAI and Ollama (llama3.2 for text, gemma4 for photos); CHEF_MODEL with await initChatModel(…) takes any "provider:model" string.
