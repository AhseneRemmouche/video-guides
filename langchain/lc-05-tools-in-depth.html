Designing Good Tools

Schemas from type hints and docstrings, return values, errors, safety, and when models skip tools.

What you will learn

A tool is how an agent reaches beyond text: searching the web, reading a file, calling an API. In step 8 and step 9 the presenter creates two tools in a few lines each. This chapter is about making tools the model uses correctly: what the model actually sees, how to describe a tool, what to return, how to handle failures, and how to keep tools safe and cheap.

You will learn:

  • how @tool builds a schema from the function name, type hints and docstring, and how to inspect it;
  • how to write docstrings and arguments the model understands;
  • why small, focused tools beat do-everything tools;
  • what to return, and what happens to it (it becomes a ToolMessage);
  • what happens when a tool fails: bad arguments versus exceptions (verified behaviour);
  • side effects and safety;
  • why the model skipped print_document in step 8;
  • why Tavily results can blow up your token count, and how to trim them.
Why this matters for your project. The chef's only tool is web_search. Its docstring decides when the model searches, and its arguments decide what queries look like. Its return value is the biggest chunk of text in every chef run. Its error handling decides whether one network hiccup crashes the whole program. Step 16's improved tools.py applies most of this chapter in seven lines.

What the model actually sees

When an agent has tools, every model request carries a list of tool definitions next to the messages. A definition has three parts: a name, a description and a JSON Schema for the arguments. The model never sees your function's body. It chooses tools and writes arguments based only on those three parts.

The @tool decorator builds them from your function:

Tool partComes fromAttribute on the tool object
nameThe function nameweb_search.name
descriptionThe docstringweb_search.description
argument schemaThe parameters and their type hints (and default values)web_search.args (and web_search.args_schema, a Pydantic model)

You can inspect all of this without calling any model. Here is the repo's tool, inspected with the locked versions (output shown as comments):

from tools import web_search

web_search.name             # 'web_search'
web_search.description      # 'tool to search the web for information'
web_search.args             # {'query': {'title': 'Query', 'type': 'string'}}

convert_to_openai_tool(web_search)
# {'type': 'function',
#  'function': {'name': 'web_search',
#               'description': 'tool to search the web for information',
#               'parameters': {'properties': {'query': {'type': 'string'}},
#                              'required': ['query'], 'type': 'object'}}}

You can override the defaults when the function name isn't a good tool name, or you want the description somewhere other than the docstring: @tool("search_recipes", description="Find recipes online.") (verified). The tool definitions are sent on every model call and count as input tokens, so ten tools with long descriptions cost something on every turn.

Writing descriptions and arguments the model understands

Think of the description as instructions for a new colleague who can't see your code. It should say what the tool does, when to use it (and when not), and what good input looks like. Compare the three docstrings in this project:

DocstringWhereAssessment
"use this tool to generate the propre document for your student"step 8Says what, vaguely. Doesn't say what a "document" is or why the model can't just write one itself. The model skipped it (see below).
"tool to search the web for information"repo tools.pyGeneric: true of any search tool. Gives no hint about the chef's use or the kind of query.
"Search the web for recipes and cooking information. Use short, specific queries."ext/tools.py (step 16)Says what it's for and how to call it well. The logs in the video show queries like "garlic fried…" (100:24), and this nudges every query that way.

Describing each argument

Argument names and types already help: query: str tells the model to send one string called query. When an argument needs more explanation, write a Google-style Args: section and pass parse_docstring=True. LangChain then puts each line into the schema as that argument's description (verified):

@tool(parse_docstring=True)
def search_recipes(query: str, max_results: int = 5) -> str:
    """Search the web for recipes.

    Args:
        query: Short search query, e.g. "garlic fried rice".
        max_results: How many results to return (1-10).
    """
    ...

# parameters sent to the model:
# {"query":       {"type": "string",  "description": "Short search query, e.g. \"garlic fried rice\"."},
#  "max_results": {"type": "integer", "description": "How many results to return (1-10).", "default": 5}}
# required: ["query"]   (max_results has a default, so it is optional)

Notice that a parameter with a default value becomes optional for the model. For full control (enums, numeric limits, nested objects), you can pass a Pydantic model as args_schema=…. Pydantic appears in step 17.

Small, focused tools

One tool should do one job. A tool called kitchen_helper(action: str, data: str) that searches, converts units or saves favourites depending on action forces the model to learn a mini-language from a docstring. Three tools, search_recipes(query), convert_units(amount, from_unit, to_unit) and save_favourite(title, url), each have an obvious purpose and obvious arguments. Some guidelines:

  • Verb plus object names: search_recipes, get_weather, save_favourite. Avoid tool1, helper, do_it.
  • Few, simple arguments. Strings, numbers and booleans with clear names. Every extra argument is another chance for the model to get something wrong.
  • Don't give the model work your code can do. If the tool always needs the user's ID, get it in code, not as an argument the model fills in.
  • Few tools overall. Every tool adds tokens to each request and one more option to confuse. Add tools when testing shows a need, not "just in case".
  • Idempotent where possible ("calling twice has the same effect as once"). Models sometimes repeat calls. Searching twice is harmless; ordering twice isn't.

Return values: what happens to them

Whatever your function returns becomes the content of a ToolMessage, which is appended to the conversation and read by the model on its next call. Strings are used as they are. Other values are converted: the repo's web_search returns Tavily's response dict, and the ToolMessage content becomes that dict as a JSON string (verified). So:

  • Return text or JSON-friendly data (dicts, lists, strings, numbers). The model reads it as text.
  • Return what the model needs, not everything you have. The model doesn't need relevance scores, image lists or response timings to write a recipe. This matters a lot, as the token section below shows.
  • Make results self-explanatory. {"query": "garlic rice", "results": [...]} tells the model what was searched. A bare list of 20 URLs doesn't.
  • Need to keep the full data for your code? Use @tool(response_format="content_and_artifact") and return a pair (content, artifact). The model only sees content, while the full artifact is stored on ToolMessage.artifact for your program (verified, sketch below).

One special option: @tool(return_direct=True) makes the agent stop right after that tool and use the tool's result as the final message, with no further model call (verified: the run ends with the ToolMessage). It's useful when the tool's output is the answer. For print_document, that would have guaranteed the exact document text.

Errors: what happens when a tool fails

Tools talk to the outside world, so they fail: the network drops, the API key is wrong, the free credits run out. Using a fake model with the project's locked versions, there are three distinct cases:

That's why step 16's tool wraps the search:

@tool
def web_search(query: str) -> Dict[str, Any]:
    """Search the web for recipes and cooking information. Use short, specific queries."""
    logging.info(f"searching for {query}")
    try:
        return tavily_client.search(query, max_results=5)
    except Exception as error:
        logging.warning(f"search failed: {error}")
        return {"error": f"Search failed: {error}. Answer from what you already know."}

Line by line

Line(s)CodeWhat it does & why
1@toolTurns the function into a StructuredTool, so the agent can describe it to the model and run it.
2def web_search(query: str) -> Dict[str, Any]:One string argument, so the schema is {"query": string}. The return hint documents the result for humans; it isn't sent to the model.
3"""Search the web for recipes … Use short, specific queries."""The description the model reads: purpose (recipes) plus a usage hint (short queries).
4logging.info(f"searching for {query}")Records each query in the terminal, which shows you how the model is using the tool (step 14).
5–6try: return tavily_client.search(query, max_results=5)The real work. max_results=5 caps how many results come back, which also caps the tokens the model must read.
7–8except Exception as error: logging.warning(…)Catches any failure (network, bad key, no credits) and logs it as a warning, so you see the real cause.
9return {"error": f"Search failed: {error}. Answer from what you already know."}Turns the failure into a result. The model reads it and can still suggest a recipe, instead of the whole program crashing. The message also tells the model what to do next.

Rule of thumb: return errors the model can do something about ("nothing found", "search failed, answer without it", "date must be YYYY-MM-DD"). Let real bugs raise so you see them during development. Be careful what an error message contains, too. It goes to the model and may end up in the answer, so never include keys or internal details.

Side effects and safety

A tool runs real code on your machine because a model asked it to, and the model's request can be influenced by the user and by any text it has read, including web pages (prompt injection, chapter 3). Treat every tool argument as untrusted input, the same way you'd treat a form field on a website.

  • Never execute model-written code or shell commands with eval, exec or subprocess on raw arguments.
  • Validate in code. The schema checks types, not intent. Check ranges, lengths and allowed values inside the tool. For file tools, make sure a path stays inside an allowed folder.
  • Enforce permissions in code, not in the prompt. "Only delete the user's own files" in a docstring is a suggestion. An if in the tool is a rule.
  • Least privilege. Give tools API keys and database users with only the rights they need.
  • Bound the loop. A recursion_limit (chapter 4) caps how many tool calls one request can trigger. That also caps cost: each Tavily search uses credits.
  • Use human approval for risky actions. LangChain supports pausing an agent before a tool runs, a topic from the video's advanced roadmap (chapter 10).

Why the model skipped print_document

In step 8 the agent first answered "tell me what you want included…" and never called the tool (43:19). With the default settings, the model decides whether to use a tool. It does so by comparing the request with the tool descriptions and with what it could do on its own. Here, everything pointed towards "no tool":

  • The task looked trivial. Writing "a document for Luca" is something the model can do in text. The presenter says so: "this task is so simple that our agent doesn't even think it needs to rely on a tool" (43:19).
  • The docstring didn't say why the tool is needed. "Generate the propre document" doesn't tell the model that the tool produces the official, always-identical document, which was the presenter's actual reason for using it (40:30: "we don't want difference in our students documents").
  • The system prompt allowed alternatives. The final prompt removes them: "use your tools … DO Not say anything else".

A better docstring would be: "Create the official enrollment document for a student. Always use this when a student introduces themselves; never write the document yourself." If the tool must run every time, that's a sign you don't need the model to decide at all. Call the function in code, or use return_direct=True so the tool's exact output is the reply.

Tools that return too much text

A Tavily search returns a dictionary with the query, a list of results (each with a title, URL, a text snippet and a relevance score) and some extra fields, depending on the options you pass. The repo returns all of it to the model. That whole dictionary becomes a ToolMessage, and then:

  • it is read as input tokens on the next model call;
  • it is re-sent on every later call in the same run, and in every later turn if you use memory (step 18);
  • each extra search adds another block of the same size.

Three ways to shrink it, from simplest to most flexible:

  1. Ask for less. tavily_client.search(query, max_results=5), as in step 16. Tavily's search has more options (search depth, topic, included domains). Check the Tavily docs for what each costs in credits.
  2. Return only what the model needs, as text: 
    @tool
def web_search(query: str) -> str:
    """Search the web for recipes and cooking information. Use short, specific queries."""
    response = tavily_client.search(query, max_results=5)
    lines = [f"- {r['title']} ({r['url']}): {r['content'][:300]}" for r in response["results"]]
    return "\n".join(lines) or "No results found."
  3. Split model view and program view with content_and_artifact: the model gets the short text, your code keeps the full response (for example to show sources or log them). 
    @tool(response_format="content_and_artifact")
def web_search(query: str):
    """Search the web for recipes and cooking information. Use short, specific queries."""
    response = tavily_client.search(query, max_results=5)
    summary = "\n".join(f"- {r['title']} ({r['url']})" for r in response["results"])
    return summary, response      # model sees summary; ToolMessage.artifact holds response

Trimming has a second benefit beyond cost. Less text means less room for injected instructions hidden in a web page, and less irrelevant detail to distract the model.

Common mistakes
  • No docstring at all. @tool raises ValueError: Function must have a docstring if description not provided. (verified). Always write one.
  • Calling the tool like a function: web_search("garlic"). A tool object is invoked with web_search.invoke({"query": "garlic"}) (38:57).
  • Forgetting to pass the tool to the agent: defining @tool isn't enough; it must be in tools=[...].
  • Missing type hints. Without query: str the schema is vague and the model guesses the argument type.
  • Letting exceptions escape. One failed search crashes the whole run (verified). Catch and return a helpful error.
  • Returning huge raw API responses. Trim to what the model needs.
  • Two tools with the same name in one agent. The model can't tell them apart; give every tool a unique name.
Common misconceptions
  • "The model reads my tool's code." It only sees the name, description and argument schema.
  • "If I give the agent a tool, it will use it." It uses it when it believes it should. Descriptions and prompts drive that.
  • "Schema validation makes a tool safe." It checks types. Safety comes from what the tool is allowed to do and what you check inside it.
  • "The return type hint tells the model what comes back." It doesn't appear in the schema. Describe the result in the docstring if it matters.
Recap
  • @tool builds a StructuredTool: .name from the function, .description from the docstring, .args from the type hints. Only these reach the model.
  • Good descriptions say what, when and how. parse_docstring=True adds per-argument descriptions. Defaults make arguments optional.
  • One job per tool, few simple arguments, few tools, idempotent where possible.
  • Return values become ToolMessage content (dicts as JSON). content_and_artifact separates what the model sees from what your code keeps. return_direct ends the run with the tool's output.
  • Invalid arguments are reported back to the model automatically. Uncaught exceptions crash the run, so catch expected failures and return a helpful message (step 16).
  • Treat tool arguments as untrusted. Add safeguards in code as tools gain the power to write, send or spend.
  • Models skip tools that look unnecessary. Explain what the tool provides, tighten the prompt, or don't use an agent for it.
  • Tool results dominate token usage. Ask for less, and return less.
