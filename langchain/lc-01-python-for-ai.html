Python Essentials for AI Apps

Virtual environments, packages, imports, functions, decorators, type hints, dictionaries and environment variables.

What you will learn

The video moves fast through the Python side of things. It runs uv init, adds a few packages, writes @tool above a function and reads response["messages"][-1].content, without stopping to explain the Python behind each one. This chapter covers that Python. It is not a full Python course. It covers the parts that show up in this project, so the code in every step stops looking like magic.

You will learn:

  • what the Python interpreter is and what a virtual environment does for you;
  • how uv differs from pip, and what pyproject.toml and uv.lock are for;
  • how imports find your own files and installed packages (why from prompt import SYSTEM_CHEF_PROMPT works);
  • functions, return values, type hints and docstrings, and why LangChain reads the last two;
  • what a decorator is, and what @tool does to your function;
  • dictionaries, lists, indexing with [-1] and f-strings;

  • environment variables, the .env file and load_dotenv().
Why this matters for your project. Almost every error a beginner hits in this course is a Python or environment problem, not a LangChain problem. Examples: ModuleNotFoundError because a package is missing (18:59), a missing API key because load_dotenv() was not called (69:24), and a terminal where the virtual environment was not activated (81:41). Once you understand the pieces below, you can read those errors and fix them yourself.

The interpreter: what python main.py actually does

Python is an interpreted language. You don't compile your code into an .exe first. A program called the interpreter (python.exe on Windows, python3 on many Macs) reads your .py file from top to bottom and runs each line as it goes. When you type python main.py in the terminal, three things happen:

  1. The shell finds a python program. It searches the folders listed in your PATH environment variable and uses the first python it finds. Which one it finds decides which packages are available. This is exactly what activating a virtual environment changes.
  2. The interpreter runs your file from line 1. Imports are executed first (because they are at the top), then module-level code such as load_dotenv() and agent = create_agent(...), then everything below in order.
  3. The program ends when the last line has run, or earlier if an error is not handled. Anything kept only in memory is gone, which is why InMemorySaver forgets everything when the script exits (step 10).

The presenter uses Python 3.12 (step 3). The repo pins this with a .python-version file and requires-python = ">=3.12" in pyproject.toml. Check yours with python --version. If two different versions answer in two different terminals, you have two interpreters installed, which is normal. The virtual environment decides which one this project uses.

Virtual environments: one box of packages per project

A package is code someone else wrote and published, such as langchain or openai. If you install packages into your system Python, every project on your computer shares them. Then project A needs langchain 1.3 and project B needs an older version, and one of them breaks.

A virtual environment (often called a venv) solves this. It is a folder, here .venv, that contains its own python program and its own site-packages folder for installed packages. Each project gets its own. Nothing you install there leaks into other projects.

Activating the environment

Creating the folder isn't enough. Your terminal must use it. On Windows PowerShell the presenter runs .venv\Scripts\activate. On macOS or Linux it is source .venv/bin/activate. Activation does one simple thing: it puts .venv\Scripts at the front of PATH for that terminal session, so python now means the venv's interpreter. The prompt then shows the environment's name in brackets, which was (Beginner) in the video.

Activation is per terminal window. Open a new terminal (or restart VS Code) and you must activate again. Forgetting this is one of the mistakes in the video (81:41): the code is right, but python is the system one, which has no langchain, so you get ModuleNotFoundError.

New to uv run? Skipping activation entirely

uv has a shortcut: uv run python main.py (or just uv run main.py) finds the project's .venv, makes sure it matches uv.lock, and runs your script with it. You don't need to activate anything. The video uses activation plus python main.py, which works too. Pick one habit and stick to it.

Packages: pip, uv, pyproject.toml and uv.lock

pip is Python's built-in package installer: pip install langchain downloads the package from PyPI (the Python Package Index) into whichever environment is active. It does not, by itself, write down what you installed. uv is a newer, much faster tool that also manages the whole project. The presenter prefers it because it "takes care of a lot of the syncing between the packages" (09:10). The commands from the video:

CommandWhat it does
uv initTurns the current folder into a project: creates pyproject.toml, main.py, .gitignore, .python-version and a README.
uv venv --python 3.12Creates .venv using Python 3.12 (uv can download that version if you don't have it).
uv add langchainAdds the package to dependencies in pyproject.toml, resolves exact versions of it and everything it needs, writes them to uv.lock, and installs them into .venv.
uv lockRecomputes uv.lock from pyproject.toml without installing.
uv syncMakes .venv match uv.lock exactly: installs what's missing and removes what isn't listed. This is what a teammate runs after cloning.
pip install uvOne way to install uv itself (the uv docs also offer a standalone installer).

Here is the repo's pyproject.toml, the human-readable list of what the project needs:

[project]
name = "acl-fasteat-agent"
version = "0.1.0"
description = "Add your description here"
readme = "README.md"
requires-python = ">=3.12"
dependencies = [
    "dotenv>=0.9.9",
    "langchain>=1.3.12",
    "langchain-openai>=1.3.4",
    "tavily>=1.1.0",
]

Each line in dependencies is a dependency with a version range: >=1.3.12 means "1.3.12 or newer". A range is flexible, so two people could end up with different versions. That's what the lockfile uv.lock prevents: it records the exact version of every package, including the dozens of indirect ones (langgraph, pydantic, httpx …), plus checksums. Commit both files to git. Never edit uv.lock by hand.

Package name versus import name

The name you install is not always the name you import. This trips up many beginners:

You install (PyPI name)You importNote
langchainfrom langchain.agents import create_agentSame name.
langchain-openailangchain_openai (used for you by init_chat_model)Dashes become underscores, because a dash is not allowed in a Python name.
python-dotenvfrom dotenv import load_dotenvThe repo installs dotenv, a deprecated shim that only pulls in python-dotenv. Step 16 adds python-dotenv directly.
tavily-pythonfrom tavily import TavilyClientTavily's official SDK. The video installs a different package called tavily that uses the same import name. See step 9 and chapter 9.

The last row shows why this matters for safety. Since the import line looks the same either way, nothing in your code tells you whether you installed the official package or a look-alike. Always check the package page (author, homepage, repository) before you uv add something.

Imports and modules: how Python finds code

Every .py file is a module. The file prompt.py is the module prompt, and tools.py is the module tools. An import statement loads a module and gives you names from it. The chef project's main.py mixes both kinds of imports:

from dotenv import load_dotenv
from langchain.agents import create_agent
from prompt import SYSTEM_CHEF_PROMPT, CHEF_PROMPT
from langchain.messages import HumanMessage
from tools import web_search
from photo_decoder import choose_image_file, build_image_message
import logging

When Python meets from prompt import …, it searches a list of folders called sys.path, in order. When you run python main.py, the first entry is the folder that contains main.py. That's why prompt.py, tools.py and photo_decoder.py are found: they sit right next to main.py. The next entries are the standard library (logging, base64, pathlib) and the active environment's site-packages (langchain, dotenv, tavily).

The two forms do the same work: import logging gives you the module, so you write logging.info(...). from prompt import CHEF_PROMPT copies one name into your file, so you write CHEF_PROMPT directly. A dotted name like langchain.agents is a module inside a package (a folder of modules).

Importing a module runs it

The first time a module is imported, Python runs the whole file from top to bottom. Every function definition is created, and every line at module level executes. Look at the repo's tools.py:

load_dotenv()

tavily_client = TavilyClient()

These lines run as soon as main.py reaches from tools import web_search, long before any search happens. That's why every module in the project calls load_dotenv() itself: TavilyClient() needs the key at import time. It's also why a missing TAVILY_API_KEY fails on the import line, not when the tool is used. Keep module-level code small: constants, a client object, and function definitions.

Don't name your files after packages. Because your script's folder comes first in sys.path, a file called langchain.py, tavily.py or logging.py in your project hides the real package. The result is confusing errors such as ImportError: cannot import name 'TavilyClient'. The lesson files in this course have distinct names (models_agents.py, tools.py), which is why they're safe. Note that tools.py would clash if you ever installed a package called tools.

Functions, return values and type hints

A function is a named, reusable block of code. You define it with def, it takes parameters, and it can give back a value with return. Here is the real one that turns an image into text the model can read:

def image_to_data_url(image_path: Path) -> str:
    image_path = image_path.expanduser().resolve()

    if not image_path.is_file():
        raise FileNotFoundError(f"Image not found: {image_path}")

    mime_type, _ = mimetypes.guess_type(str(image_path))
    if not mime_type or not mime_type.startswith("image/"):
        raise ValueError(f"Not an image file: {image_path}")

    image_b64 = base64.b64encode(image_path.read_bytes()).decode("utf-8")
    return f"data:{mime_type};base64,{image_b64}"
  • image_path: Path is a parameter with a type hint: "this should be a Path object". -> str after the parentheses says "this function returns a string".
  • Indentation (four spaces) marks the function's body. Python has no curly braces, so indentation is the structure. Mixing tabs and spaces causes IndentationError.
  • mime_type, _ = … is unpacking: guess_type returns two values, and the underscore is the usual name for "I don't need this one".
  • raise stops the function with an error. return stops it with a value. A function with no return returns None.

An important fact about type hints: Python itself does not enforce them. You could pass a number to image_to_data_url and Python would only fail later, on .expanduser(). Hints are documentation for humans and for tools such as VS Code, which uses them for autocomplete and warnings. Some libraries also read them while your program runs. LangChain's @tool is one of them: it turns query: str into "this tool takes a string called query" for the model. In tool functions, type hints are therefore part of the behaviour, not just decoration (chapter 5).

Hint in this projectMeaning
name: strA text string.

-> HumanMessageReturns a LangChain message object.
Dict[str, Any]A dictionary with string keys and values of any type. Imported from typing. Since Python 3.9 you can also write dict[str, Any].

Docstrings

A docstring is a string literal on the first line inside a function, written with triple quotes:

def choose_image_file() -> Path:
    """Open a local file picker when no image path is passed on the command line."""

Python stores it in the function's __doc__ attribute, and editors show it when you hover over the function name. For normal functions it is documentation. For a LangChain tool it becomes the description the model reads to decide whether and how to call the tool. That's why the presenter says "it is important that for our tool we have a very good doc string" (38:09).

Decorators: what @tool really does

A decorator is a function that takes your function and returns something new in its place. The @ line is shorthand. These two snippets are equivalent:

# With the decorator syntax (what the video writes)
@tool
def print_document(name: str) -> str:
    """use this tool to generate the propre document for your student"""
    return f"this is the document of {name}"

# Exactly the same thing, written out by hand
def print_document(name: str) -> str:
    """use this tool to generate the propre document for your student"""
    return f"this is the document of {name}"

print_document = tool(print_document)

After decoration, the name print_document no longer refers to a plain function. It refers to a LangChain StructuredTool object that wraps your function. The presenter calls it "an annotation" (37:20). In Python the correct word is decorator. The tool object reads three things from your function: its name, its type hints and its docstring. That's why you call it with print_document.invoke({"name": "kitty"}) (38:57) rather than print_document("kitty").

Dictionaries, lists and indexing

Two container types appear on almost every line that talks to an agent:

  • A list is an ordered sequence in square brackets: [HumanMessage(...), AIMessage(...)]. Items are numbered from 0. Negative numbers count from the end: [-1] is the last item, [-2] the one before it.
  • A dictionary (dict) maps keys to values in curly braces: {"messages": [...]}. You read a value with its key in square brackets: response["messages"]. A missing key raises KeyError. response.get("messages") returns None instead.

An agent takes a dict and returns a dict. Its "messages" key holds a list. The last item in that list is the model's final answer. So this line, which appears in nearly every step, reads from left to right:

print(response["messages"][-1].content)

Notice the switch from brackets to a dot. response is a dict, so you use ["messages"]. Each message is an object (an instance of a class), so you use .content. Writing response.messages raises AttributeError, and message["content"] raises TypeError. Dicts can also nest, as in the memory config from step 10: {"configurable": {"thread_id": "1"}}, a dict whose value is another dict.

f-strings

An f-string is a string with an f before the opening quote. Anything inside { } is evaluated and inserted as text:

name = "Luca"
f"this is the document of {name}"          # 'this is the document of Luca'
f"data:{mime_type};base64,{image_b64}"     # builds a data URL (step 11)
f"{key} is missing. Add it to your .env file."   # step 16's error message

Forget the f and the braces are printed literally: "this is the document of {name}". The opposite mistake causes one of the bugs this guide fixes. In the repo's photo_decoder.py, "text": "prompt" sends the five letters prompt instead of the variable prompt. Quotes turn a name into text. See step 16.

Errors: try, except, finally

When something goes wrong, Python raises an exception. If nothing catches it, the program stops and prints a traceback. You can catch expected problems and recover. The project's file picker is a complete example:

    root = None
    try:
        root = Tk()
        root.withdraw()
        root.attributes("-topmost", True)
        filename = filedialog.askopenfilename(
            title="Choose an image",
            filetypes=[
                ("Images", "*.png *.jpg *.jpeg *.webp"),
                ("All files", "*.*"),
            ],
        )
    except TclError:
        filename = input("Image path: ").strip().strip('"').strip("'")
    finally:
        if root is not None:
            root.destroy()

    if not filename:
        raise SystemExit("No image selected.")

    return Path(filename).expanduser()
  • try: runs the risky code: opening a graphical window can fail, for example on a server with no screen.
  • except TclError: catches only that kind of error and falls back to typing a path. Other errors are not caught and still crash, which is good: you want to see bugs.
  • finally: always runs. Here it closes the hidden window even if something failed.
  • raise SystemExit("No image selected.") ends the program with a clear message instead of a traceback.

Catching Exception (almost every error) is sometimes right, as in step 16's search tool, which turns any search failure into a message the model can read. Do it only at a boundary like that, and log what you caught. A bare except: that silently ignores everything hides real problems.

New to tracebacks? Read them from the bottom up

A traceback lists the chain of function calls that led to the error, oldest first. The last line is the most useful one: the exception type and message, e.g. ModuleNotFoundError: No module named 'langchain_openai'. The lines just above it show the file and line number where it happened. Look for the last frame that points to your file (not to site-packages): that's usually where to fix things. Chapter 8 goes deeper.

if __name__ == "__main__":

Every module has a built-in variable __name__. When you run a file directly (python photo_decoder.py), it is set to "__main__". When the file is imported (from photo_decoder import …), it's set to the module's name ("photo_decoder"). So this idiom means "run this part only when the file is the program, not when it is imported":

# photo_decoder.py (idea: a quick self-test you can run on its own)
def image_to_data_url(image_path: Path) -> str:
    ...

if __name__ == "__main__":
    path = choose_image_file()
    print(image_to_data_url(path)[:80], "...")

The project's files don't use it. They are small scripts, and module-level code is fine there. It becomes useful as soon as one file is both a library and a runnable script. Remember the earlier rule: importing a module runs it. Without the guard, importing photo_decoder would open a file picker.

Environment variables and .env

An environment variable is a named text value that the operating system hands to every program it starts, such as PATH or OPENAI_API_KEY. Libraries read their API keys from environment variables so that keys never have to appear in your code. ChatOpenAI reads OPENAI_API_KEY, and TavilyClient() reads TAVILY_API_KEY.

Typing set/export commands in every terminal is tedious, so projects keep them in a .env file (one NAME=value per line) and load it at start-up with load_dotenv() from the python-dotenv package. In the installed version, load_dotenv() with no arguments:

  • looks for .env starting in the folder of the script that calls it, then in each parent folder;
  • copies each entry into os.environ, the running program's environment;
  • does not overwrite a variable that is already set (pass override=True to change that). An old key set system-wide therefore wins over the one in .env, a classic source of "but I changed the key!" confusion.

Step 16 adds an early check so a missing key produces a friendly message instead of a deep traceback:

load_dotenv()

for key in ("OPENAI_API_KEY", "TAVILY_API_KEY"):
    if not os.getenv(key):
        raise SystemExit(f"{key} is missing. Add it to your .env file.")

os.getenv(key) returns the value, or None if it isn't set. not None and not "" are both True, so an empty value is caught too. The loop walks over a tuple (a list that can't be changed, written with parentheses).

Common mistakes
  • Venv not active: ModuleNotFoundError for a package you did install. Activate .venv (or use uv run) and check the prompt shows its name.
  • Package added to the wrong project: running uv add in another folder updates that project's pyproject.toml. Run it in the folder that contains your pyproject.toml.
  • Running from the wrong folder: python Beginner\main.py from a parent folder still finds the sibling modules (Python uses the script's folder), but relative file paths such as "photo.jpg" are resolved against the current folder. Use paths relative to the project folder, or absolute paths.
  • .env in the wrong place or misnamed (.env.txt, which Windows can create silently). Keep it in the project folder, next to main.py.
  • Quotes around a variable: "prompt" is text; prompt is the variable.
  • Calling a tool like a function: after @tool, use .invoke({"name": "Luca"}).
  • Windows only, rare: if the environment variable SSLKEYLOGFILE is set, importing langchain_openai can crash with an OPENSSL_Uplink error. Unset it.
Common misconceptions
  • "Type hints make Python check my types." They don't at runtime. But LangChain reads them for tools, so in tool functions they matter.
  • "Activating the venv is permanent." It lasts for one terminal session.
  • "uv.lock is generated junk I can ignore." It's what makes everyone's install identical. Commit it.
  • "load_dotenv() is part of LangChain." It comes from python-dotenv. LangChain only reads the resulting environment variables.
Recap
  • The interpreter runs your file top to bottom. Which python runs decides which packages exist.
  • A virtual environment (.venv) is a per-project interpreter plus packages. Activate it per terminal, or use uv run.
  • uv add updates pyproject.toml (what you want) and uv.lock (exactly what you got). Teammates run uv sync.
  • Imports search the script's own folder first, then the standard library and site-packages. Importing a module runs its top-level code.
  • Type hints and docstrings are optional for Python but essential for LangChain tools. @tool is a decorator that wraps your function in a tool object.
  • response["messages"][-1].content: dict key, last list item, object attribute.
  • try/except/finally handles expected failures. Read tracebacks from the bottom.
  • Keys live in .env, are loaded by load_dotenv(), and are kept out of git by .gitignore.
