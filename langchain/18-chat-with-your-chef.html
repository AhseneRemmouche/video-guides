Chat with Your Chef: Memory + Streaming

An interactive loop that remembers the photo and streams every answer.

Extension · verified against LangChain 1.3.12

Extension, not in the video. chat_chef.py was run end-to-end against LangChain 1.3.12 and LangGraph 1.2.9 with the offline test harness described in step 16 (fake chat model, canned Tavily result, no file picker). The harness confirmed that the image message, the follow-up questions, the memory across turns and the streaming filter all work with these versions. The conversation shown on this page is illustrative.

Goal

The chef from step 14 answers once and exits. If you want a different recipe, or ask "can I make it without eggs?", you have to start again and pick the photo again. In this step you build a chat with your chef: you send the photo once, then keep asking follow-up questions in the terminal. The chef remembers the photo and everything said so far, and every answer appears word by word as it's generated.

You already know both ingredients. This step simply combines them:

Quick refresher: memory with a checkpointer

An agent by itself forgets everything between two invoke or stream calls. In step 10 you gave it a checkpointer, InMemorySaver(), which saves the conversation state after every run. A thread ID in the config tells the checkpointer which conversation to load and extend. Same thread ID: same conversation. New thread ID: a fresh start.

InMemorySaver keeps everything in your computer's memory (RAM), so all conversations disappear when the program exits. That's fine for a chat session. For memory that survives a restart you'd use a database-backed checkpointer; the handbook chapter Memory, State & Checkpointers explains the options.

Quick refresher: streaming

Streaming means receiving the answer in small pieces while the model is still writing it, instead of waiting for the whole text. With stream_mode="messages", agent.stream(…) gives you pairs of (token, metadata): token is a small piece of a message, and metadata says which part of the agent produced it. You print each piece immediately, so the user sees the answer "typing" itself, as in step 7.

import sys
from pathlib import Path

from dotenv import load_dotenv
from langchain.agents import create_agent
from langchain.messages import AIMessageChunk, HumanMessage
from langgraph.checkpoint.memory import InMemorySaver

from photo_decoder import build_image_message, choose_image_file
from prompt import CHEF_PROMPT, SYSTEM_CHEF_PROMPT
from tools import web_search

load_dotenv()

agent = create_agent(model="gpt-5-nano",
                     tools=[web_search],
                     system_prompt=SYSTEM_CHEF_PROMPT,
                     checkpointer=InMemorySaver())

config = {"configurable": {"thread_id": "kitchen-1"}}


def ask(message):
    """Send one message to the chef and print the answer as it streams in."""
    for token, metadata in agent.stream({"messages": [message]}, config, stream_mode="messages"):
        if isinstance(token, AIMessageChunk) and token.text:
            print(token.text, end="", flush=True)
    print("\n")


path = Path(sys.argv[1]) if len(sys.argv) > 1 else choose_image_file()
ask(build_image_message(path, CHEF_PROMPT))

while True:
    question = input("You (q to quit): ").strip()
    if question.lower() in {"q", "quit", "exit"}:
        break
    if question:
        ask(HumanMessage(content=question))

Why the filter on line 26 matters

In step 7 the agent had no tools, so every streamed piece was part of the answer and the lesson printed everything that had .content. The chef does have a tool. With stream_mode="messages" the stream also yields:

  • AI chunks that carry a tool call: the model deciding to call web_search. Their text is empty; the call is in tool_call_chunks.
  • ToolMessages: the complete search result, a long JSON-like text with titles, URLs and page snippets.

Printed as-is, the second kind would dump a wall of raw search data in the middle of your chat. Checking isinstance(token, AIMessageChunk) keeps only the model's own words. Using .text instead of .content is also safer: .content may be a string or a list of content blocks depending on the model, while .text always gives you just the plain text (an empty string if there's none).

How the photo stays in memory, and what it costs

You only send the photo in turn 1, yet in turn 3 you can ask "what else could I make with the green thing on the left?" and the chef knows what you mean. Here's why: the checkpointer saved turn 1's HumanMessage, including its base64 image. At the start of every new turn, the agent loads the whole saved history, appends your new question, and sends all of it to the model. Models have no memory of their own; "memory" always means "we send the past again".

That has a price. Every turn re-sends the image, the search results from earlier turns, and all previous answers. Each of those costs input tokens. So turn 5 costs more than turn 1, even if your question is one word, and a very long session can eventually approach the model's context window limit. For a short chat about one photo this is fine. For long sessions you'd trim or summarise old messages; the handbook chapter Memory, State & Checkpointers shows how.

What you should see

What you should see

The first recipe appears word by word. Then a You (q to quit): prompt. Follow-up answers also stream in and clearly refer to the earlier recipe and the photo. Typing q ends the program silently. The conversation below is illustrative; your answers will differ.

You won't see INFO log lines: this file doesn't call logging.basicConfig, to keep the chat clean. A failed search still prints a search failed: … warning, because Python shows warnings by default. If you'd like a start-up key check, copy lines 20–22 of the fixed main.py (step 16) after load_dotenv().

Common mistakes

  • Forgetting config in agent.stream(…): ValueError: Checkpointer requires one or more of the following 'configurable' keys: thread_id, checkpoint_ns, checkpoint_id.
  • Creating a new config inside the loop with a new thread ID (for example from a counter): every turn starts a fresh conversation and the chef "forgets" the photo.
  • Creating the agent inside ask: each call would get a new, empty InMemorySaver, so memory is lost. Create the agent and checkpointer once, at the top.
  • Dropping flush=True: on some terminals the text then appears in bursts instead of word by word.
  • Printing token.content without the type check: raw search results fill the screen after the first question.
  • Stopping with Ctrl+C prints a KeyboardInterrupt traceback. It's harmless; use q for a clean exit.
  • Sending a second photo in the same thread: it works (call ask(build_image_message(…)) again), but now two images are re-sent every turn. Start a new thread ID for a new photo.
Recap
  • chat_chef.py = streaming (step 7) + checkpointer memory (step 10) + the chef, inside a while True loop.
  • input() reads a question; q, quit or exit breaks the loop; empty lines are skipped.
  • All turns share {"configurable": {"thread_id": "kitchen-1"}}, passed to agent.stream as the second argument.
  • Print only AIMessageChunk pieces with .text; that hides tool calls and raw search results.
  • Memory means re-sending: the photo and the whole history go to the model every turn, so cost grows as the chat gets longer.
