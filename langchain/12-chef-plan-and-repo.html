The plan: a personal chef agent (71:24 to 75:31)

The presenter draws the project on a whiteboard tool before writing any code. At 71:48 they say that everything taught so far is enough to build it alone, and at 75:31 they suggest you pause the video and try. The drawing has four kinds of pieces:

  • A system prompt (73:02): the instructions that tell the model who it is. Here: "you are a chef". This is the same system_prompt you used in step 8.
  • A user prompt (73:02): what you, the user, want right now. Here: "find me a good recipe".
  • An image (73:25 to 74:42): a photo of your ingredients. The model can't open a file on your computer, so the image is converted to base64 text first, exactly like in step 11.

The output (75:07) is a recipe.

New to project planning? Why draw before you code

A beginner's first instinct is to open the editor and start typing. For anything bigger than one file, that usually ends with code that is hard to change. Drawing the inputs, the processing and the outputs first gives you three things:

  • A checklist. Each box is a piece of work. The presenter literally goes back to the drawing several times (82:12, 86:20) and says "this is done".
  • File boundaries. Pieces that do different jobs go in different files. You will see below that every box becomes one file.
  • Early questions. "How does the model see my photo?" is a question you want to answer before writing 50 lines, not after.

The drawing doesn't need special software. Paper works.

System prompt vs user prompt

These two look similar (both are text) but they play different roles. The system prompt is fixed: it describes the job and stays the same for every run. The user prompt is the request for this run. At 85:29 the presenter notices they had written the first prompt as a user prompt and renames it, saying it is really the system prompt "because this is basically telling him who he is and what he has to do". Step 13 writes both in prompt.py.

How the photo reaches the model

A chat model only receives what you send in the request. It can't open C:\Users\you\Pictures\fridge.jpg, because that file is on your computer and the model runs on OpenAI's servers. So the program reads the file's bytes, encodes them as base64 text, wraps that text in a data URL and puts it in the message next to the user prompt. This is the multimodal message from step 11.

Create the GitHub repository (75:31 to 78:51)

New to Git and GitHub? Repository, README, public and private

Git is a program on your computer that records the history of a folder: every time you commit, it saves a snapshot of your files with a message. A folder that Git tracks is called a repository ("repo").

GitHub is a website that hosts copies of Git repositories online. You push your snapshots to it and clone (download) repos from it. Git and GitHub are different things: Git works offline without GitHub, and GitHub is one of several hosting sites.

  • README: a file named README.md at the top of the repo. GitHub shows it on the repo's front page, so it's the first thing visitors read. The .md means Markdown: plain text where # Title becomes a heading.
  • Public: anyone on the internet can see and clone the code. Good for portfolio projects. Only you (and people you invite) can change it.
  • Private: only you and people you invite can see it. Good for work in progress or anything you don't want to share.

Either way, never commit secrets such as API keys. Even a private repo can be shared later, and Git keeps old versions forever. That's why step 13 puts the keys in a .env file that Git ignores.

  1. Sign in to GitHub

    Go to github.com and sign in, or create a free account. Your username becomes part of every repo URL: https://github.com/<your-username>/<repo-name>.

  2. Start a new repository

    Click the + menu at the top right and choose New repository (or the green New button on your repositories list).

  3. Name it ACL_FastEat_Agent

    The presenter first types "ACL agent image" (75:56), then picks "FastEat agent" because the app goes from ingredients to a recipe fast (76:21). ACL is short for the channel name, AI Career Lab. You can use any name; letters, numbers, -, _ and . are allowed, and spaces become -. Keep it short, because it becomes the folder name when you clone.

  4. Write a description

    The presenter writes: "This project is a LangChain based agent that rely on images to create the needed recipe instantly" (76:46 to 77:59; the grammar is theirs). The description appears under the repo name and in search results. It's optional but helps visitors.

  5. Choose Public or Private

    The presenter's repo is public: you can open it at github.com/Mohamad-Hachem/ACL_FastEat_Agent. For a portfolio project, public is the usual choice. You can change it later under the repo's Settings.

  6. Tick "Add a README file"

    At 77:59 the presenter adds the README "so people can also read our project". GitHub then creates the repo with one first commit (named "Initial commit") containing a README.md with the repo name as a heading and the description underneath. A repo that already has a commit can be cloned straight away.

  7. Click "Create repository"

    GitHub opens the new repo's page and shows the README.

  8. Copy the HTTPS clone URL

    Click the green Code button, make sure the HTTPS tab is selected and click the copy icon (78:23). The URL looks like https://github.com/<your-username>/ACL_FastEat_Agent.git. Step 13 pastes it after git clone.

Common mistakes

  • Forgetting "Add a README file". The repo is then completely empty and GitHub shows setup instructions instead of files. Cloning still works (you get an empty folder and a warning), but it's simpler to tick the box.
  • Copying the browser address instead of the clone URL. https://github.com/user/ACL_FastEat_Agent usually works too, but copying from the Code button avoids typos in the name.
  • Using the presenter's URL. Cloning Mohamad-Hachem/ACL_FastEat_Agent gives you their finished code, and you won't be able to push to it. Use your own repo's URL.
  • Adding a GitHub .gitignore template and a README, then running uv init is fine, but be aware that step 13 also creates a .gitignore. If you picked GitHub's Python template, just add .env to the existing file instead of creating a new one.
