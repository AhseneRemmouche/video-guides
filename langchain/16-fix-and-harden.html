Fix & Harden the Chef

Fix the two prompt bugs, use the official Tavily SDK, accept an image path, and handle missing keys and search errors.

Extension · verified against LangChain 1.3.12

About steps 16–19. These steps are not in the video. They fix problems found in the repo (commit ea320de) and add features the video's roadmap points to. Every file on these pages was run end-to-end against the repo's locked versions (LangChain 1.3.12, langchain-core 1.4.9, LangGraph 1.2.9, langchain-openai 1.3.4) with an offline test harness: the chat model was replaced by a fake one with the same LangChain interfaces, the Tavily search returned a canned result, and the file picker was skipped. All 13 checked files passed.

What that proves: the imports, APIs, message flow, tool calling, error handling and image messages work with these versions. What it does not prove: the exact wording a real model will answer with. Test with your own keys.

Nothing here changes how the chef works from the outside: you still run one command, pick a photo and get a recipe. It just gets more correct and harder to break.

Fix 1: the chef never sees your request (photo_decoder.py)

This is the most important fix. Look at line 52 of the repo's photo_decoder.py:

def build_image_message(image_path: Path, prompt) -> HumanMessage:
    return HumanMessage(
        content=[
            {"type": "text", "text": "prompt"},
            {"type": "image_url", "image_url": {"url": image_to_data_url(image_path)}},
        ]
    )

The function receives your request in the parameter prompt. But line 52 writes "prompt" with quotes. In Python, quotes make a string literal: the letters p-r-o-m-p-t. So the text block the model receives is literally the six-letter word prompt, not "please find me a good recipe to cook". The offline harness confirmed this: the fake model recorded the text prompt.

New to variables vs strings? Why the quotes change everything

A variable is a name that points to a value. Inside build_image_message, the name prompt points to whatever text the caller passed in, here CHEF_PROMPT from prompt.py.

A string literal is text written directly in the code between quotes. "prompt" is always the same six letters, p r o m p t, no matter what. It has nothing to do with the variable of the same name.

prompt = "please find me a good recipe to cook"
print(prompt)     # please find me a good recipe to cook
print("prompt")   # prompt

Python cannot warn you here, because both lines are valid code. Editors help a little: VS Code shows an unused parameter (like prompt in the buggy version) in a faded colour. That faded colour is a hint that something is off.

Why did it still "work" in the video? The system prompt already tells the model to look at the photo, find the ingredients and search for a recipe. So even with a meaningless user text, the model has enough instructions to do the job. The bug only shows when you change CHEF_PROMPT, for example to "find me a vegetarian dessert", and nothing changes in the answers.

How it happened. In step 11 the text block held a fixed sentence, "tell me what is the image about", so quotes were correct there. When the presenter added a prompt parameter for the chef (at 83:30), the quotes stayed around the new name. It's an easy slip to make.

    image_path = image_path.expanduser().resolve()

    if not image_path.is_file():
        raise FileNotFoundError(f"Image not found: {image_path}")

Fix 2: the missing space (prompt.py)

The repo's prompt.py builds the system prompt from two strings joined with a backslash at the end of the line:

CHEF_PROMPT= "please find me a good recipe to cook"

SYSTEM_CHEF_PROMPT = "You are the best chef in the world. your mission is to look and understand what are the ingredients in the photo." \
"once you do that search online for a recipe that only need these ingredients"

When Python sees two string literals next to each other, it glues them together exactly as they are, with nothing in between. The first string ends with photo. and the second starts with once, so the model receives …ingredients in the photo.once you do that…. Models are forgiving, so it still worked, but prompts are instructions: sloppy instructions give less predictable results.

New to long strings in Python? Backslashes vs parentheses

Python lets you split one long string across several lines in two ways:

  • A backslash \ at the end of a line means "this statement continues on the next line". It works, but it's fragile: a single space after the backslash is a syntax error, and the second line looks like it isn't part of anything.
  • Parentheses ( … ) around the pieces. Inside brackets Python ignores line breaks, so you can put each piece on its own indented line. This is the style most Python code uses (PEP 8, the official style guide, recommends it).

Either way, the pieces are joined with nothing in between. You must put the space yourself, at the end of each piece (or at the start of the next one). Ending each piece with a space is the easiest habit to check by eye.

    "and understand which ingredients are in it. "

)

Fix 3: use the official Tavily package

In the video (at 49:54) the presenter runs uv add tavily, and the repo's pyproject.toml depends on tavily>=1.1.0. On PyPI, the package named tavily (version 1.1.0, described as "Simple API TAVILY") is published by an individual, not by Tavily. Tavily's own SDK is called tavily-python (author Tavily AI, source on github.com/tavily-ai/tavily-python, version 0.8.5 when this guide was checked). Both are imported the same way: from tavily import TavilyClient. That's why the mix-up is so easy.

The source of the installed tavily 1.1.0 was read while writing this guide: it only calls https://api.tavily.com with your key, so it isn't harmful in that version. But it isn't maintained by Tavily, and any future version could do something else with the key it receives. The safe habit is to install packages from the company that runs the service.

New to supply-chain risks? Why the package name matters

When you run uv add something, uv downloads whatever package currently has that name on PyPI, the public Python package index. Anyone can publish a package with any free name. Attackers use this: they publish look-alike names (reqeusts instead of requests, or a short name a real company never claimed) and wait for developers to install them. This is called a supply-chain attack, because the danger comes in through your dependencies rather than your own code.

Your API keys are in your environment, and every package you import runs with full access to them. So before installing a package that handles keys, check three things on its PyPI page: who the author is, which GitHub repository it links to, and whether the service's own documentation names it. Tavily's docs install tavily-python.

The same applies, more mildly, to dotenv. The PyPI package dotenv is a deprecated shim: an almost empty package whose only job is to depend on python-dotenv, the real library. It works, but it adds a middle-man. Depend on python-dotenv directly. Your code doesn't change: the import is still from dotenv import load_dotenv.

  1. Remove the old packages 
    uv remove tavily dotenv

    Remove them first: tavily and tavily-python both install a folder called tavily into .venv. Having both would make it unclear whose code import tavily loads.

  2. Add the official packages 
    uv add tavily-python python-dotenv
  3. Check the result

    Open pyproject.toml; the dependencies list should match the file below (your version numbers may be newer). uv.lock changes too: commit both files so teammates get the same packages with uv sync.

Fix 4: a search error shouldn't crash the chef (tools.py)

A web search can fail for reasons that have nothing to do with your code: no internet, a wrong or expired key, the free monthly credits used up, a timeout. In the repo, web_search simply calls tavily_client.search(query). If that raises an exception, it travels up through the agent and the whole program stops with a traceback.

That's not a guess: in LangGraph 1.2.9 the tool runner's default error handler only turns argument errors (the model sent bad arguments) into messages. Every other exception is re-raised. So the tool has to catch its own errors.

New to try / except? Catching errors so the program can continue

When something goes wrong at run time, Python raises an exception. If no code catches it, the program stops and prints a traceback. A try block lets you say "attempt this, and if it fails, do that instead":

try:
    result = risky_call()
except Exception as error:
    result = f"failed: {error}"

except Exception catches almost every error type. as error stores the exception in a variable, so you can log or show its message. In application code you usually catch narrower types, but a tool is a special case: any failure should become a message for the model, not a crash.

The fixed tool catches the error, logs a warning, and returns a small dict with an "error" key. LangChain turns that return value into a ToolMessage, exactly like a successful result. The model reads "Search failed… Answer from what you already know." and writes a recipe from its own knowledge instead. The user gets an answer, and your log shows what went wrong.

  1. Replace the contents of tools.py

    Note that the logging.basicConfig(…) block is gone from this file. main.py already configures logging, and configuring it in two places is confusing: only the first call to basicConfig takes effect, so the result depends on which file happens to be imported first. Configure logging once, in the entry point.

from tavily import TavilyClient
from dotenv import load_dotenv
from langchain.tools import tool
from typing import Dict, Any
import logging

load_dotenv()

tavily_client = TavilyClient()


@tool
def web_search(query: str) -> Dict[str, Any]:
    """Search the web for recipes and cooking information. Use short, specific queries."""
    logging.info(f"searching for {query}")
    try:
        return tavily_client.search(query, max_results=5)
    except Exception as error:
        logging.warning(f"search failed: {error}")
        return {"error": f"Search failed: {error}. Answer from what you already know."}

Fix 5: pass the photo on the command line, and check the keys (main.py)

Two small usability improvements. First, opening a file dialog every time is slow when you test the same photo again and again, and it doesn't work at all on a machine without a screen. The fixed main.py accepts an optional path:

python main.py path/to/photo.jpg

If you don't give a path, the file picker opens as before. Second, if a key is missing from .env, the repo fails deep inside the OpenAI client with a long traceback (openai.OpenAIError: Missing credentials…), or worse, only when the search runs. The fix checks both keys at start-up and stops with one clear sentence.

New to sys.argv? How a program reads what you type after its name

When you run python main.py photos/fridge.jpg, Python stores the words after python in a list called sys.argv ("argument vector"):

  • sys.argv[0] is the script name, "main.py". It's always there.
  • sys.argv[1] is the first extra word, "photos/fridge.jpg". It only exists if you typed one.

So len(sys.argv) > 1 means "the user typed something after the script name". Reading sys.argv[1] without that check would crash with IndexError when no path was given.

Words are split on spaces. If your path contains spaces, wrap it in quotes: python main.py "C:\Users\me\My Photos\fridge.jpg". For bigger command-line interfaces Python has the argparse module; for one optional value, sys.argv is enough.

About SystemExit. raise SystemExit("message") stops the program, prints message to the terminal, and returns a non-zero exit code (which tells scripts and CI tools "this failed"). Unlike other exceptions, Python doesn't print a traceback for it. That makes it the right choice for errors the user can fix, like a missing key: they need one clear instruction, not 30 lines of library internals.

What you should see

The same three INFO lines as in step 14 (creating, choosing, invoking), one or more searching for … lines, then the recipe. When you pass a path, no dialog opens. If you removed a key, you see only TAVILY_API_KEY is missing. Add it to your .env file. and the program stops. Answers vary from run to run, because the model's wording isn't fixed.

Common mistakes

  • Leaving the quotes in: "text": "prompt" still runs without any error. Search the file for "prompt" to be sure it's gone.
  • A space after the backslash if you kept the backslash style in prompt.py: SyntaxError: unexpected character after line continuation character. Use parentheses instead.
  • uv add tavily out of habit: check pyproject.toml for the exact name tavily-python.
  • ModuleNotFoundError: No module named 'tavily' after the swap: the virtual environment isn't active, or uv add failed. Activate .venv and run uv sync.
  • A path with spaces without quotes: only the first word reaches sys.argv[1], and you get FileNotFoundError: Image not found. Wrap the path in quotes.
  • "OPENAI_API_KEY is missing" although it's in .env: load_dotenv() looks for .env in the script's folder and its parent folders. Check that the file sits next to main.py, is named exactly .env (Windows sometimes saves it as .env.txt), and that the variable name is spelled exactly as in the error.
  • Catching the error but returning nothing (except: pass): the tool returns None, and the model gets no explanation. Always return a message.

Recap
  • "prompt" with quotes is a fixed word; prompt without quotes is your variable. The fix makes the chef actually read your request.
  • Python joins neighbouring strings with no space; use parentheses and end each piece with a space.
  • Install Tavily's official tavily-python and the real python-dotenv: same imports, trusted publishers.
  • A tool should catch its own errors and return a message, so one failed search doesn't end the whole run.
  • sys.argv[1] lets you pass the photo on the command line; a start-up key check gives a clear message instead of a traceback.
