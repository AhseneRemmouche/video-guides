What's Next: MCP, Middleware, Multi-Agent & Your Roadmap

The intermediate and advanced topics from the video's roadmap, and how to keep learning.

At the end of the video (103:07) the presenter tells you that you are no longer a beginner. You can build a model call, an agent, tools, memory, image input, and a working AI personal chef. The video opens (01:08–02:42) with a roadmap for the rest of the series: an intermediate part (MCP, context and state, multi-agent systems, and a multi-agent wedding planner project) and an advanced part (middleware, managing long conversations, human in the loop, dynamic agents, and a third project). This chapter gives you a beginner-friendly preview of every one of those topics, so the names mean something when you meet them, shows how each could improve the chef, and ends with a learning roadmap and practice projects you can do on your own.

Why this matters for your project. The chef is a single agent with one tool that runs once. Every topic below removes one of those limits: more tools without writing them (MCP), per-user settings (context), specialist helpers (multi-agent), control over each step (middleware), long chats (summarisation), safe actions (human in the loop) and agents that adapt per request (dynamic agents). The snippets are previews; follow the official docs for full details, since these APIs are newer and change faster than the basics.

Intermediate 1: MCP, tools from outside your code

Every tool in the chef is written by hand in tools.py. The Model Context Protocol (MCP) is an open standard for connecting AI applications to tools and data that live in separate programs, called MCP servers. One server might give access to a file system, another to GitHub, a database, or a calendar. Any MCP-capable application can use any MCP server, so integrations are written once and reused everywhere.

LangChain connects to MCP servers with a separate package, langchain-mcp-adapters (published by the LangChain team; 0.3.2 when checked). Its MultiServerMCPClient connects to one or more servers and turns their tools into ordinary LangChain tools. The shape below follows the package's README; it uses async/await, which the chef does not use yet, and was not run in this guide's harness:

from langchain_mcp_adapters.client import MultiServerMCPClient
from langchain.agents import create_agent

client = MultiServerMCPClient({
    "pantry": {
        "command": "python",
        "args": ["/full/path/to/pantry_server.py"],
        "transport": "stdio",
    },
})

tools = await client.get_tools()
agent = create_agent(model="gpt-5-nano", tools=[web_search, *tools])

Here pantry_server.py is an imaginary MCP server that knows what is in your kitchen. The chef would get its tools next to web_search without you writing them in tools.py. Two transports exist: stdio (the client starts the server as a local program) and HTTP (the server is a web service).

Intermediate 2: context and state

You already know state: the dictionary with messages that flows through the agent and is saved by the checkpointer (chapter 6). Two related ideas come next:

IdeaWhat it isChef example
Custom state (state_schema)Extra keys in the state that change during the run and are saved with the threadA shopping_list the agent fills as it goes
Runtime context (context_schema)Read-only information you pass in for one call, such as who the user is; not part of the conversationThe user's id and diet: "vegetarian"
Store (store)Long-term memory across threadsSaved preferences per user

Both state_schema and context_schema are parameters of create_agent in LangChain 1.3.12. Context is passed per call with agent.invoke(..., context=...). The LangChain docs call the broader skill of deciding what the model sees at each step context engineering. A small example appears under "dynamic agents" below.

Intermediate 3: multi-agent systems

A multi-agent system splits a big job between several agents, each with its own instructions and tools. The video's second project, a wedding planner, is described as multi-agent: you can imagine one agent for venues, one for catering, one for the budget. Why split? A single agent with twenty tools and a giant prompt gets confused; specialists with a few tools each are easier to prompt, test and debug.

The LangChain docs describe several patterns. The simplest is subagents as tools: a main agent (sometimes called a supervisor) calls other agents exactly like it calls a tool. A sketch for the chef, illustrative:

nutrition_agent = create_agent(
    model="gpt-5-nano",
    system_prompt="You are a nutritionist. Estimate calories and allergens of a recipe.",
)

@tool
def check_nutrition(recipe: str) -> str:
    """Ask the nutrition expert about a recipe's calories and allergens."""
    response = nutrition_agent.invoke({"messages": [HumanMessage(recipe)]})
    return response["messages"][-1].content

chef = create_agent(model="gpt-5-nano",
                    tools=[web_search, check_nutrition],
                    system_prompt=SYSTEM_CHEF_PROMPT)

Other patterns in the docs include handoffs (control passes from one agent to another, which then talks to the user) and routers (a first step decides which specialist should handle a request). Each extra agent means extra model calls, so multi-agent designs cost more and are harder to trace (chapter 8). Start with one agent and split only when it struggles.

Advanced 1: middleware

Middleware is code that runs around the agent's steps: before or after each model call, around each tool call, or at the start and end of a run. It is how you add behaviour (logging, limits, summarising, approval, changing the prompt) without rewriting the agent loop. create_agent takes a middleware list, and langchain.agents.middleware in LangChain 1.3.12 offers:

  • Hooks for your own middleware: decorators such as before_model, after_model, wrap_model_call, wrap_tool_call, before_agent, after_agent and dynamic_prompt, or a class based on AgentMiddleware.
  • Ready-made middleware, including SummarizationMiddleware, HumanInTheLoopMiddleware, ModelCallLimitMiddleware, ToolCallLimitMiddleware, ModelRetryMiddleware, ToolRetryMiddleware, ModelFallbackMiddleware, PIIMiddleware, ContextEditingMiddleware and TodoListMiddleware.

You have already seen three of these in earlier chapters: summarisation (chapter 6) and the two call limits (chapter 9).

Advanced 2: managing long conversations

Chapter 6 showed why long threads become slow, expensive and eventually too big for the context window, and the three answers: trim, summarise, delete. The advanced part of the series covers these properly. In LangChain 1.3.12 the building blocks are trim_messages for lists you manage yourself, SummarizationMiddleware to summarise old messages automatically, and ContextEditingMiddleware to clear old tool results (which are often the biggest messages, like the chef's Tavily results). Combined with a persistent checkpointer, these let the chat chef from step 18 run for a long session without the cost of each turn growing forever.

Advanced 3: human in the loop

Human in the loop means the agent pauses before a sensitive action and waits for a person to approve, edit or reject it. The chef only searches, so it doesn't need this yet. But imagine a tool order_groceries that spends real money: you would want to see the order first. LangChain 1.3.12 provides HumanInTheLoopMiddleware; it needs a checkpointer, because the paused run is saved in the thread and resumed later. This flow was run in the harness with a fake model:

from langchain.agents import create_agent
from langchain.agents.middleware import HumanInTheLoopMiddleware
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import Command

agent = create_agent(
    model="gpt-5-nano",
    tools=[web_search, order_groceries],
    checkpointer=InMemorySaver(),
    middleware=[HumanInTheLoopMiddleware(interrupt_on={"order_groceries": True})],
)
config = {"configurable": {"thread_id": "kitchen-1"}}

result = agent.invoke({"messages": [HumanMessage("Order what I need for fried rice")]}, config)
print(result["__interrupt__"])

result = agent.invoke(Command(resume={"decisions": [{"type": "approve"}]}), config)
Line(s)CodeWhat it does & why

10HumanInTheLoopMiddleware(interrupt_on={"order_groceries": True})Pause before every call to order_groceries. True allows all decisions (approve, edit, reject, respond). Tools not listed, like web_search, run without asking.

Advanced 4: dynamic agents

The chef's system prompt, model and tools are fixed when create_agent runs. A dynamic agent changes them per request: a different prompt for each user, a bigger model only for hard questions, or fewer tools in some situations. Middleware makes this possible. For example, dynamic_prompt builds the system prompt from the runtime context just before each model call. This was run in the harness with a fake model, and the model received "You are a helpful chef. The user is vegetarian. Only suggest vegetarian recipes.":

from dataclasses import dataclass
from langchain.agents import create_agent
from langchain.agents.middleware import dynamic_prompt, ModelRequest

@dataclass
class ChefContext:
    diet: str

@dynamic_prompt
def chef_prompt(request: ModelRequest) -> str:
    diet = request.runtime.context.diet
    return f"You are a helpful chef. The user is {diet}. Only suggest {diet} recipes."

agent = create_agent(model="gpt-5-nano", tools=[web_search],
                     middleware=[chef_prompt], context_schema=ChefContext)

agent.invoke({"messages": [message]}, context=ChefContext(diet="vegetarian"))

The same idea with wrap_model_call can swap the model for each call (for example, a small model for simple steps and a larger one for the final recipe), and ModelFallbackMiddleware switches to a backup model when the first one fails. Combined with step 19, this is how you would build a chef that picks its model at run time.

Your learning roadmap

The video's advice on studying (02:42–04:59) applies here too: learning is a marathon, so work in small sessions rather than binge-watching. The presenter recommends the Pomodoro method (25 minutes of focus, a 5-minute break, and a longer break after several rounds) with a timer such as pomofocus.io. A sensible order for the topics above:

  1. Consolidate the basics. Do the extension steps 16–19 if you haven't: fix the bugs, add structured output, the chat loop and provider switching. Reread chapters 1–5 of this handbook where something felt unclear.
  2. Memory and debugging. Add a SQLite checkpointer to the chat chef and inspect its state; write one fake-model test (chapters 6 and 8).
  3. Middleware basics. Add call limits and a before_model logging hook; then summarisation.
  4. Context and dynamic prompts. Pass the user's diet as context.
  5. Human in the loop. Add a tool with a side effect (even a fake one that writes a file) and require approval.
  6. MCP. Connect one trusted MCP server, or write a tiny one.
  7. Multi-agent. Split a job between two specialists only after you have felt a single agent struggle.

Common misconceptions
  • "Advanced means I need all of it." Most useful agents need a few of these features. Add one when a real problem asks for it.
  • "Multi-agent is always smarter." It is more complex and more expensive. A single well-prompted agent with good tools is often enough.
  • "MCP replaces tools." MCP is a way to deliver tools; the agent still uses normal tool calling.
  • "Human in the loop slows everything down." It only pauses on the tools you list; everything else runs normally.
  • "Tutorial code is production code." Newer APIs change between versions. Pin versions with uv.lock and check the docs for the version you use.
Recap
  • The series roadmap: intermediate (MCP, context and state, multi-agent, wedding planner) and advanced (middleware, long conversations, human in the loop, dynamic agents).
  • MCP brings tools from separate servers; in Python via langchain-mcp-adapters and MultiServerMCPClient.
  • Context (per call, read-only), state (per thread, changing) and store (across threads) hold different information.
  • Multi-agent systems split work between specialists, often as subagents called like tools.
  • Middleware hooks around model and tool calls power summarisation, limits, approvals and dynamic behaviour.
  • HumanInTheLoopMiddleware + a checkpointer pauses before chosen tools; resume with Command(resume={"decisions": [...]}).
  • dynamic_prompt and context_schema adapt the agent per request.
  • Learn in small sessions, one feature at a time, on a project you already know.
