What Tools Are & Your First Tool

The @tool decorator, docstrings, tool.invoke, system prompts, and ToolMessages in the trace.

▶ Watch this part (35:23)

Goal

So far your agent could only talk. In this step you give it its first tool: a small Python function the agent may decide to run. You'll turn a function into a tool with @tool, test it on its own, hand it to the agent along with a system prompt, and then read the full message trace to see exactly how the agent used it.

The tool here is deliberately trivial (it returns "this is the document of Luca"), and that turns out to be instructive: the model first refuses to bother with it. In step 9 you'll swap it for a real web search tool, and the chef project's whole job (finding recipes online) rests on what you learn here.

What tools are for

The presenter starts with the "why" (35:23–36:32). If all a model can do is input → output, an agent "would not really have much of a difference in our life". The power comes in the middle: "the agent is able to choose between the different tools that it has and then use these tools to come up with better decision making or to do the task in a better way". After using its tools, it can produce "a far better output than the output that we have from a simple model. Obviously, this depends on the task".

New to tools? How a model can "run" a function it cannot touch

The model lives on OpenAI's servers; your function lives on your computer. The model can't run your code. Here is what really happens (it's called a tool call):

  1. LangChain sends the model a description of each tool: its name, what it's for, and which inputs it takes.
  2. If the model thinks a tool would help, it doesn't answer in words. It replies with a structured request: "please call print_document with name="Luca"".
  3. The agent (on your computer) runs the real function and sends the result back as a tool message.
  4. The model reads the result and writes its final answer.

That cycle is the agent loop. See How an Agent Thinks for a longer walk-through.

Step by step

  1. Create a new file tools.py

    In the same project folder as models_agents.py, create tools.py (36:32). The presenter starts a fresh file on purpose: "repetition is also good for us so we can remember".

  2. Load the key and import what you need

    load_dotenv (for the OpenAI key), create_agent, tool from langchain.tools, and HumanMessage. Call load_dotenv() (36:56).

  3. Write the tool

    Put @tool on the line above a function print_document(name: str) -> str, give it a docstring, and return an f-string (37:20–38:33). "It is important that for our tool we have a very good docstring."

  4. Test the tool on its own

    Before involving any AI, call the tool yourself (38:33–39:20). Tools are invoked like agents, with a dictionary of their inputs:

    print(print_document.invoke({"name": "kitty"}))

    Run python tools.py: it prints this is the document of kitty. This costs nothing (no model involved) and proves the function works. Delete the line afterwards.

  5. Create the agent with tools and a system prompt

    create_agent(model="gpt-5-nano", tools=[print_document], system_prompt="...") (39:44–40:30). Pass the tool itself (no parentheses) inside a list.

  6. Invoke the agent and print two things

    Send HumanMessage(content="Hello I am a student and my name is Luca") (41:39), then print the last message's content and, under a separator, the whole response["messages"] list "so you guys understand how tools are being used" (42:30).

  7. Run it with python tools.py. If the model answers in words without using the tool, read "When the model ignores your tool" below: the presenter hit exactly that.

The complete file

Code transcribed from the video (frames at 45:30), run against the repo's locked versions (langchain 1.3.12). The docstring typo "propre" is the presenter's; it doesn't stop the tool working.

from dotenv import load_dotenv
from langchain.agents import create_agent
from langchain.tools import tool
from langchain.messages import HumanMessage

load_dotenv()


@tool
def print_document(name: str) -> str:
    """use this tool to generate the propre document for your student"""
    return f"this is the document of {name}"


agent = create_agent(model="gpt-5-nano",
                     tools=[print_document],
                     system_prompt="YOU are an employee that use your tools for generating documents. DO Not say anything else")

response = agent.invoke(
    {"messages": [HumanMessage(content="Hello I am a student and my name is Luca")]}
)

print("this is the AI last response: ")
print(response["messages"][-1].content)

print("--------------- this is the details -----------------")
print(response["messages"])

New to decorators? What the @ line does

A decorator is a function that takes your function and returns an upgraded version of it. Writing

@tool
def print_document(name: str) -> str:
    ...

is shorthand for print_document = tool(print_document). After that line, the name print_document refers to a tool object, not a bare function. That's why you test it with print_document.invoke({"name": "kitty"}); calling it like a normal function, print_document("kitty"), now raises TypeError: 'StructuredTool' object is not callable.

New to docstrings and type hints? They become the tool's "instruction label"

Python itself mostly ignores docstrings and type hints; they're notes for humans and tools. @tool is one of those tools: it turns them into a schema, a precise description in JSON format that the model reads. For this file, LangChain builds:

{
  "title": "print_document",
  "description": "use this tool to generate the propre document for your student",
  "type": "object",
  "properties": { "name": { "title": "Name", "type": "string" } },
  "required": ["name"]
}

The model never sees your function's code, only this. So a clear name, a clear docstring and accurate type hints are what make a tool usable. The handbook chapter Designing Good Tools goes deeper.

New to system prompts? Instructions that frame the whole conversation

A prompt is the text you give a model. The system prompt is a special one: it isn't part of the chat, it sets the rules for it ("you are an employee", "only use your tools"). create_agent(system_prompt="...") puts it at the very start of every request as a SystemMessage. It doesn't show up in response["messages"], but the model reads it each time.

Models give system instructions a lot of weight, which makes the system prompt your main steering wheel. In the chef project, all of prompt.py is one long system prompt.

When the model ignores your tool (43:19–45:25)

The first run did not use the tool. The answer was along the lines of "Tell me what you want included. I'll generate the document if you'd like." The presenter's diagnosis: "this task is so simple that our agent doesn't even think it needs to rely on a tool" (43:19). Tools are offers, not orders: the model decides on its own whether calling one is worth it, and for "write a sentence with a name in it" it felt it could do the job itself. The presenter tightened the system prompt twice:

TrySystem prompt (as spoken in the video)Result
1 (40:06)"you are a teacher who wants to use your tools to generate the right document for your students"No tool call; the model offers to write a document itself.
2 (43:41)"use the right tool for students"Still no tool call: "Hi Luca, nice to meet you. I can generate a clean student…". Only Human and AI messages in the trace, "I am not seeing any tool messages" (44:30).
3 (45:00)"YOU are an employee that use your tools for generating documents. DO Not say anything else"Tool called. The answer is the tool's text: "this is the document of Luca" (45:25).

"This is the issue with a very simple task. So it's also good to know when we are relying and when we're not" (45:25). Real tools, like web search in step 9, do something the model genuinely cannot do on its own, so the model reaches for them far more willingly. If a model still skips a tool you need, try in this order: make the docstring say clearly when to use it, give the tool a descriptive name, then make the system prompt explicit.

Reading the trace: four messages

With the strict prompt, the details printout (45:49–47:22) contains four messages. The presenter scrolls through them: the human message, "another AI message that is empty. Hm. Interesting", then "something called a tool message", and "at the end we have another AI response".

Shortened, the printed list looks roughly like this (ids and metadata replaced by …):

[HumanMessage(content='Hello I am a student and my name is Luca', id='…'),
 AIMessage(content='', tool_calls=[{'name': 'print_document', 'args': {'name': 'Luca'}, 'id': 'call_…', 'type': 'tool_call'}], …),
 ToolMessage(content='this is the document of Luca', name='print_document', tool_call_id='call_…', id='…'),
 AIMessage(content='this is the document of Luca', …)]

Look in it for tool_calls=[{'name': 'print_document', ...}] and a ToolMessage. If neither appears, the model answered without the tool: run it again or tighten the system prompt.

Common mistakes:

  • No docstring: @tool fails immediately with ValueError: Function must have a docstring if description not provided.
  • Forgetting @tool and testing with print_document.invoke(...): AttributeError: 'function' object has no attribute 'invoke'.
  • Calling the tool like a function after decorating it, print_document("kitty"): TypeError: 'StructuredTool' object is not callable. Use .invoke({"name": "kitty"}).
  • tools=[print_document()]: the parentheses try to run the tool while building the list. Pass the tool object itself.
  • Expecting the tool to always run: the model decides. A trivial tool plus a soft prompt often means no tool call; check the details printout before assuming your code is broken.
  • Reading only [-1] while debugging: you miss whether a tool ran at all. Print the whole list, as the presenter does.
Recap
  • A tool is a Python function the agent may choose to run; @tool turns the function into a tool object.
  • The function name, docstring and type hints become the schema the model reads, so write them carefully.
  • Test tools alone with tool.invoke({"name": "kitty"}) before giving them to an agent.
  • create_agent(..., tools=[...], system_prompt="..."): the system prompt steers when tools are used; for trivial tasks the model may skip the tool unless told firmly.
  • A tool run leaves a trace: HumanMessage → AIMessage with tool_calls → ToolMessage → final AIMessage.
