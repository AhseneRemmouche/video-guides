How Git saves your work

New to commits? Working folder, staging area, history and remote

Git doesn't save every change automatically. You decide what goes into each snapshot (a commit), in two moves:

  • Working folder: your files as they are on disk right now, including unsaved experiments.
  • Staging area: a "ready to save" list. git add puts files (or changes) on it. It lets you commit some changes and leave others for later.
  • History (local repository, the hidden .git folder): git commit takes everything on the staging list and saves it as one snapshot with a message, the time and your name.
  • Remote (here: GitHub, named origin): git push uploads the commits GitHub doesn't have yet.

Nothing reaches GitHub until you push. And a commit is permanent history: if a secret gets committed, deleting the file later doesn't remove it from older commits. That's why .gitignore matters so much.

Step by step (101:56 to 102:45)

  1. See what Git sees 
    git status

    status lists files that are new ("untracked"), modified, or staged. It changes nothing, so run it as often as you like. Read the list carefully: anything you don't want on GitHub (keys, the virtual environment, generated files) must not be in it.

  2. Add anything that shouldn't be uploaded to .gitignore

    In the video, git status lists __pycache__/ among the untracked files (102:02). That's the folder where Python caches compiled versions of your modules: it appeared when main.py imported prompt, tools and photo_decoder. It's regenerated automatically and differs between machines, so it doesn't belong in Git. The presenter adds __pycache__/ as line 2 of .gitignore, under .env ("we would like to add this to our gitignore"), and runs git status again to check that it's gone from the list (102:02 to 102:20).

  3. Stage everything 
    git add .

    add puts files on the staging list; . means "this folder and everything in it", except what .gitignore excludes. Run git status again afterwards: staged files are listed under "Changes to be committed".

  4. Commit with a message 
    git commit -m "creating our personal Agent"

    commit saves the staged files as one snapshot. -m gives the message on the command line (without it, Git opens a text editor and waits). The quotes are needed because the message contains spaces. This is the exact message of the repo's commit ea320de.

  5. Push to GitHub 
    git push

    push uploads your new commits to the remote. No extra words are needed because you cloned the repo: git clone already set up origin (your GitHub URL) and linked your main branch to origin/main. The first time, Git may ask you to sign in to GitHub; on Windows, Git Credential Manager opens a browser window for that.

  6. Refresh the repo page on GitHub (102:45)

    Your files appear, with "creating our personal Agent" as the latest commit message next to each one.

Why .venv doesn't need a line (yet)

The committed file matches the video exactly: .env and __pycache__/. The commit contains .gitignore, .python-version, main.py, photo_decoder.py, prompt.py, pyproject.toml, tools.py and uv.lock, and no virtual environment.

.venv stayed out without a line because, when uv creates .venv, it puts a small .gitignore containing * ("ignore everything here") inside it. That's why it never showed up in git status. Adding .venv/ to your own .gitignore anyway is a good habit: it's explicit, and it protects you if the environment was created by another tool.

Writing good commit messages

A commit message is a note to your future self and your teammates. Some simple habits:

  • Say what changed, in a few words: "Add web search tool", "Fix prompt not sent to the model".
  • Many teams use the imperative ("Add", "Fix", not "Added", "Fixing"), because it reads like an instruction: "this commit will add web search".
  • One topic per commit. If the message needs "and", consider two commits.

The video's "creating our personal Agent" is fine for a first commit that contains the whole project.

What you should see

  • After git commit: a summary like [main ...] creating our personal Agent and "8 files changed" (if your project matches the repo).
  • After git push: lines ending with something like main -> main.
  • On GitHub: your files listed, "2 commits" in the header, the README still shown below the file list, and no .env, .venv or __pycache__.

Common mistakes

  • Running git add . before checking git status. Always look first. If you staged something by mistake, git restore --staged <file> takes it off the list before you commit.
  • Adding a folder to .gitignore after it was committed. .gitignore only affects files Git doesn't track yet. To stop tracking one, run git rm -r --cached <folder>, then commit.
  • Forgetting -m: Git opens an editor (often Vim) in the terminal. In Vim, type your message, press Esc, then type :wq and Enter.
  • Committing but not pushing, then wondering why GitHub didn't change. A commit is local until you push.
  • Running Git commands in the wrong folder: "not a git repository". cd into ACL_FastEat_Agent first.

What's next in the series

At 103:07 the presenter marks the beginner part as done: "You are no longer a beginner." The roadmap shown at the start of the video (01:32 to 02:16) splits the series into three levels, each ending with a project, and the presenter mentions a later video that combines everything (01:08).

What those intermediate and advanced words mean, in one line each:

  • MCP (Model Context Protocol): a standard way to plug ready-made tools and data sources into an agent, instead of writing each tool yourself.
  • Multi-agent systems: several specialised agents working together, for example one for the venue and one for the menu in a wedding planner.
  • Middleware: code that runs around every model or tool call in an agent, for logging, limits, trimming or checks.
  • Human in the loop: the agent pauses and asks a person to approve an action before doing it.

The handbook chapter What's Next: MCP, Middleware, Multi-Agent & Your Roadmap explains each of these with examples and suggests what to study in what order.
