How an Agent Thinks

The agent loop, message by message: what the model sees, when it calls tools, and why it stops.

In the video, a single line such as agent.invoke({"messages": [...]}) sometimes returns one message and sometimes four or more. It can search the web several times, or remember your favourite colour. This page opens the box. Using the project's own examples, it follows an agent message by message: what the model sees, when it calls a tool, why it stops, and what memory really saves.

Read it alongside step 05 (first agent), step 08 (first tool), step 09 (web search) and step 10 (memory). Everything described here was checked against the repo's locked versions (langchain 1.3.12, langgraph 1.2.9) with an offline test harness.

Model versus agent

A chat model is a function from messages to one reply: text in, text out. It cannot look anything up, and it forgets everything between calls. An agent wraps that model in a loop and gives it tools. The model can then say "run web_search for me", read the result, and decide what to do next.

The video shows the difference directly. With the web_search tool, "give me the lastest news of the day" (the typo is the presenter's) produces a summary of real headlines (around 54:20). With the tools removed, the same agent answers that it can't pull real-time headlines (at 55:07).

Everything is a list of messages

An agent's input and output have the same shape: a dictionary with one key, "messages", whose value is a list. Each item is a message with a role. While the agent works it appends messages to this list. When it finishes, it hands the whole list back to you. That's why the video always reads the answer with response["messages"][-1].content: [-1] is the last message, the final answer.

New to message roles? Who says what

Chat models don't receive one long string. They receive a conversation, where every message is labelled with who wrote it. LangChain has a class for each role. Under the hood, the OpenAI API uses the names in the third column.

The model reads the roles to understand the conversation. In step 06 the presenter writes an AIMessage by hand ("Rome (Italian: Roma).") so that the follow-up "tell me more about it" makes sense. The model has no memory, so the history is the memory.

One detail surprises many beginners. The system prompt you pass to create_agent(system_prompt=...) is sent to the model on every model call, but it is not stored in response["messages"]. Verified: in the step 8 example the model receives SystemMessage, HumanMessage on its first call, but the returned list starts with the HumanMessage.

The loop in one picture

Here is the whole algorithm. It has two working steps (LangGraph calls them nodes) and one question:

  1. Model node. Send the system prompt plus every message so far to the model. Append its reply (an AIMessage) to the list.
  2. Question. Does that AIMessage contain any tool calls? If not, stop: the reply is the final answer.
  3. Tools node. If it does, run each requested tool with the arguments the model chose. Append one ToolMessage per call. Then go back to step 1.

Trace 1: print_document (step 8)

In step 08 the presenter gives the agent one tool and a strict system prompt. Here is the code from that step, shortened to the lines that matter for the loop:

@tool
def print_document(name: str) -> str:
    """use this tool to generate the propre document for your student"""
    return f"this is the document of {name}"

agent = create_agent(model="gpt-5-nano",
                     tools=[print_document],
                     system_prompt="YOU are an employee that use your tools for generating documents. DO Not say anything else")

response = agent.invoke(
    {"messages": [HumanMessage(content="Hello I am a student and my name is Luca")]}
)

The user never says "print a document". The model works out from the system prompt and the tool's docstring that it should call print_document, and that the argument name should be "Luca". This is the run the presenter scrolls through at 45:49–47:22, step by step:

New to "the model calls a tool"? What really happens

The model never runs code. It only writes text. When an agent has tools, LangChain sends the model a short description of each one: the name (print_document), the description (the docstring) and the input schema (from the type hint name: str). The model can then answer in a special structured format that means "please call print_document with {"name": "Luca"}".

LangChain reads that request, calls your Python function with those arguments, wraps the return value in a ToolMessage and sends everything back to the model. From the model's point of view, it asked a question and someone answered. That's why a tool must return something the model can read, such as a string or a dictionary.

Why the model ignored the tool at first. Before the strict system prompt, the presenter's agent simply chatted with Luca and never called print_document (43:19–45:25). Calling a tool is always the model's choice. A vague docstring ("generate the propre document") and a task the model can answer alone make skipping it likely. The presenter fixed it with a strict system prompt. Clear docstrings help too. The handbook chapter Designing Good Tools covers this.

Trace 2: web_search (step 9), several laps

In step 09 the tool is web_search, which calls the Tavily API and returns a dictionary of results. For "give me the lastest news of the day" the model doesn't stop after one search. The presenter remarks that the agent uses its tools "over and over" (at 54:20): each search result can prompt the model to search again with a more specific query.

Two practical consequences:

  • Cost and speed. Every lap resends the whole growing list, including the search results. Web results are long, so the context window and the token bill grow quickly. The presenter checks the Tavily dashboard afterwards to see how many searches were used (around 55:54).
  • Trust. Search results go straight into the model's input as ToolMessages. A web page could contain instructions aimed at the model. That's prompt injection, covered in the handbook chapter Security, Secrets & Cost.

A single AIMessage can also ask for several tools at once (for example two searches with different queries). The tools node then runs all of them and adds one ToolMessage per call, each with its own tool_call_id.

Why the loop stops

The loop has exactly one normal exit: the model replies with an AIMessage that has no tool calls. Nothing in your code counts searches or decides the answer is "good enough". The model makes that decision each time it is called.

LangGraph also has a safety net: a maximum number of steps per run, the recursion limit. If a confused model kept calling tools forever, the run would stop with a GraphRecursionError instead of looping endlessly. You can set it per call, for example agent.invoke({...}, {"recursion_limit": 10}). Each model call and each tools run counts as one step. You won't hit it in this guide's projects.

What create_agent actually builds

create_agent doesn't return a model. It returns a LangGraph CompiledStateGraph: a small program made of nodes (steps) and edges (arrows between them), with shared state (the messages list). You can ask the graph for its node names. Verified with the locked versions:

agent = create_agent(model="gpt-5-nano", tools=[print_document])
print(type(agent).__name__)             # CompiledStateGraph
print(list(agent.get_graph().nodes))    # ['__start__', 'model', 'tools', '__end__']

agent = create_agent(model="gpt-5-nano")  # no tools
print(list(agent.get_graph().nodes))    # ['__start__', 'model', '__end__']
New to graphs? Nodes, edges and state

In programming, a graph is a set of boxes joined by arrows, like a flowchart. Each box (node) is a function that does one job. Each arrow (edge) says what runs next. A conditional edge is an arrow with a question on it: "if the last message has tool calls, go to tools, otherwise go to the end".

All nodes share one state, here a dictionary holding the messages list. A node reads the state, does its job and returns what to add. LangGraph is the library that runs these graphs, and create_agent writes this one for you so you don't have to.

Because the agent is a graph, every option of create_agent plugs into a specific place. system_prompt is used by the model node. tools creates the tools node. checkpointer saves the state between steps, which is the next section. response_format (step 17) and middleware (on the video's advanced roadmap) also hook into these nodes.

Memory: what the checkpointer saves

By default, every invoke starts with only the messages you pass in. In step 10 the presenter says "My favorite color is green" in one call, then asks "what is my favorite color" in a second call. The agent has no idea (around 60:10). The second call's model saw exactly one message.

The fix adds two things. A checkpointer (InMemorySaver()) saves the graph's state after every step. A thread ID in the config says which conversation the state belongs to. On the next invoke with the same thread ID, LangGraph first loads the saved messages, then appends your new message, so the model sees the whole history.

agent = create_agent(model="gpt-5-nano",
                     checkpointer=InMemorySaver())

config = {"configurable":{"thread_id":"1"}}

response = agent.invoke(
    {"messages": [HumanMessage(content="My favorite color is green")]},
    config
)

What exactly is stored? The checkpointer stores the graph's state, the messages list, under the thread ID. It saves a new snapshot ("checkpoint") after each step, so it could even resume a run that was interrupted halfway. InMemorySaver keeps all of this in a Python dictionary in your computer's RAM.

Memory versus history you pass yourself. In step 06 your code passed Human, AI and Human messages by hand. In step 10 the checkpointer does the same thing for you. Either way, the model only "remembers" what is in the list it receives. The checkpointer keeps that list between calls.

The chef, end to end

The chef project (steps 13–14) uses the same loop with an image. main.py creates the agent with tools=[web_search] and system_prompt=SYSTEM_CHEF_PROMPT, asks you to pick a photo, builds one multimodal HumanMessage and invokes the agent. It has no checkpointer: one question, one answer.

Two findings from verifying the repo are visible right here, in what the model receives:

  • In photo_decoder.py the text block is {"type": "text", "text": "prompt"}: the string "prompt" in quotes, not the variable prompt. The harness confirmed the model receives the literal word prompt. The chef still works in the video because the system prompt already says what to do. The fix ("text": prompt) is in step 16.
  • SYSTEM_CHEF_PROMPT joins two strings without a space, so the model reads "…in the photo.once you do that…". It's harmless here, but it's the kind of detail you only notice by looking at exactly what the model receives. Also fixed in step 16.

When the model decides to search, the tools node runs web_search, and its logging.info line shows the query the model wrote. In the video's run those are lines like "searching for recipe using oyster sauce" (around 100:24). Each such log line is one lap of the loop.

Where streaming fits

agent.stream(..., stream_mode="messages") runs the same loop but hands you pieces as they are produced instead of waiting for the end (step 07). With tools, the stream includes more than the final answer: you also receive the ToolMessages from the tools node. The lesson code prints anything with .content, so a tool's result would be printed too. The chat chef in step 18 prints only the model's text chunks (AIMessageChunk), so you see the answer and not the raw search results.

Common mistakes when reasoning about agents

  • Expecting the model to run your function. It only asks. If a tool raises an error, the error comes from your Python code, on your machine.
  • Reading response["messages"][0] for the answer. Item 0 is your own question. The answer is [-1].
  • Calling create_agent.invoke(...). create_agent is the factory. Call invoke on the agent it returned, or you get AttributeError: 'function' object has no attribute 'invoke' (at 70:11).
  • Adding a checkpointer but no config. You get ValueError: Checkpointer requires one or more of the following 'configurable' keys: thread_id, .... Pass {"configurable": {"thread_id": "1"}} as the second argument.
  • Using a new thread ID by accident. A different ID is a different conversation, so the agent "forgets". Build the config once and reuse the same variable, as step 10 does.
  • Assuming memory survives a restart. InMemorySaver is lost when the script ends.
Recap
  • An agent's input and output are {"messages": [...]}. The list only grows, and the answer is always [-1].
  • The loop: model node → if the AIMessage has tool_calls, tools node adds ToolMessages → back to the model. It stops when the model replies without tool calls.
  • An "empty" AIMessage is a tool request. Its tool_calls carry the name, the arguments and an ID that the ToolMessage's tool_call_id answers.
  • create_agent builds a LangGraph graph with nodes model and tools. The system prompt is sent on every model call but isn't stored in the result.
  • Memory = checkpointer + thread ID. It saves the messages per thread after each step and reloads them on the next invoke. InMemorySaver lasts only while the program runs.
  • Every lap costs a model call. Look at exactly what the model receives: that's how the chef's "prompt" bug was found.
