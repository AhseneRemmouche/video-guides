Short-Term Memory

InMemorySaver as a checkpointer plus a thread_id so the agent remembers earlier turns.

▶ Watch this part (56:39)

Goal

Tell the agent "My favorite color is green", then ask "what is my favorite color?" in a second call. Out of the box, the agent has no idea. In this step you find out why, and fix it with two small additions: a checkpointer that saves the conversation, and a thread ID that says which conversation you're in. This is called short-term memory: the agent remembers earlier turns of the same conversation while your program runs.

The presenter introduces memory here, before images, at 56:39. The chat version of the chef in step 18 uses exactly this technique.

Version 1: an agent that forgets

  1. Create a new file called in_memory_agent.py next to tools.py (57:02).
  2. Type the first version: one agent, two separate invoke calls.
  3. Run it with python in_memory_agent.py.
from dotenv import load_dotenv
from langchain.agents import create_agent
from langchain.messages import HumanMessage

New to "stateless" calls? Why each invoke is independent

A chat model is stateless: it keeps nothing between requests. Every time you call it, it reads the messages you send, writes a reply, and forgets everything. ChatGPT seems to remember because the app sends the whole conversation again with every new question.

You did this by hand in step 06: you built a list with a HumanMessage, an AIMessage and another HumanMessage, and the agent understood the follow-up. That works, but you have to keep and grow the list yourself.

A checkpointer automates it. It stores the message list for you after each call and puts it back in front of the next one. Your code stays as short as version 1.

Version 2: an agent that remembers

  1. Import InMemorySaver from LangGraph (60:55).
  2. Pass checkpointer=InMemorySaver() to create_agent (60:33). The presenter compares it to "a checkpoint in any game".
  3. Create a config with a thread_id (61:40–62:04), and pass it as the second argument of both invoke calls (62:30).
  4. Run it again. This time the second answer says your favorite color is green (63:15).
from dotenv import load_dotenv
from langchain.agents import create_agent
from langchain.messages import HumanMessage
from langgraph.checkpoint.memory import InMemorySaver


load_dotenv()


agent = create_agent(model="gpt-5-nano",
                     checkpointer=InMemorySaver())

config = {"configurable":{"thread_id":"1"}}

response = agent.invoke(
    {"messages": [HumanMessage(content="My favorite color is green")]},
    config
)

print(response["messages"][-1].content)


response = agent.invoke(
    {"messages": [HumanMessage(content="what is my favorite color")]},
    config
)

print(response["messages"][-1].content)

New to checkpointers? A save point for your conversation

The presenter's analogy is a video game checkpoint (60:55). When you reach a checkpoint, the game saves your progress. If you come back later, you continue from there instead of from the start.

A checkpointer does the same for an agent. Under the hood, the agent is a LangGraph graph with a state: a dictionary whose main entry is "messages". After each step of the graph (model call, tool call), LangGraph writes a snapshot of that state, a checkpoint, to the checkpointer. On the next invoke with the same thread, it reads the latest snapshot back.

When the new input arrives, LangGraph doesn't replace the saved messages; it appends the new ones. That's why you only pass the new question.

InMemorySaver is the simplest checkpointer: it keeps snapshots in a Python dictionary in RAM. LangGraph also offers checkpointers that write to a database (for example SQLite or Postgres, installed as separate packages), which survive a restart. The handbook chapter Memory, State & Checkpointers goes deeper.

Threads: one notebook per conversation

Why do we need a thread ID at all? Because one agent can hold many conversations at once (61:40): you and a friend, or many users of an app. The checkpointer keeps a separate history per thread_id, like separate notebooks. Change the ID and you open a fresh notebook.

alice = {"configurable": {"thread_id": "alice"}}
bob = {"configurable": {"thread_id": "bob"}}

agent.invoke({"messages": [HumanMessage(content="My favorite color is green")]}, alice)
agent.invoke({"messages": [HumanMessage(content="what is my favorite color")]}, bob)
# bob's thread is empty: the agent doesn't know (it was alice who said green)
agent.invoke({"messages": [HumanMessage(content="what is my favorite color")]}, alice)
# alice's thread has the earlier message: "green"

Memory grows with every turn

Each call on a thread re-sends the whole saved history to the model. That's what makes memory work, but it has a cost: the conversation gets longer every turn, so each call uses more tokens, and very long threads can eventually exceed the model's context window. For this lesson it doesn't matter. The video's roadmap lists "managing long conversations" as an advanced topic.

What you should see

The mistake that's easy to make: forgetting the config

The presenter warns at 62:04: "when we are using checkpointer it's very important to give it the configuration". If you add a checkpointer but call agent.invoke(...) without config, LangGraph doesn't know which notebook to open, and it stops with this error (verified):

ValueError: Checkpointer requires one or more of the following 'configurable' keys: thread_id, checkpoint_ns, checkpoint_id

Common mistakes

  • No config on one of the calls. You get the ValueError above. Every invoke (and stream) on an agent with a checkpointer needs it.
  • Misspelled keys. "thread_id" must be spelled exactly; "threadId" or "thread-id" are not recognised, and the run fails (we saw KeyError: 'thread_id' with "threadId"). (LangChain also accepts a short form without the outer level, {"thread_id": "1"}, and moves it into "configurable" for you; we tested it. Stick to the full form from the video, which is what the documentation shows.)
  • Different thread IDs by accident. "1" and "one", or "user-1" and "user1", are different labels. Different labels mean different conversations, and the agent "forgets".
  • Creating a new InMemorySaver() for each call. Memory lives inside that one object. If you build a new agent with a new saver before each question, every question starts empty. Create the agent once and reuse it.
  • Expecting memory after restarting the program. See below.
  • Importing from the wrong place. It's from langgraph.checkpoint.memory import InMemorySaver, not from langchain.

When the program ends, the memory is gone

InMemorySaver keeps everything in RAM. When python in_memory_agent.py finishes, the process ends and the RAM is freed. Run the file again and thread "1" is empty. That's why this is called short-term memory: it lasts as long as your program runs. For memory that survives restarts, use a checkpointer that writes to a database (see the handbook chapter Memory, State & Checkpointers).

Video vs repo. This lesson file is not in the repo. The repo's chef (main.py) runs a single invoke and has no memory; step 18 (Chat with Your Chef) adds an InMemorySaver and a thread_id to it, exactly as on this page.

Recap
  • Each invoke is independent: without memory, the model only sees the messages you pass in that call.
  • checkpointer=InMemorySaver() (from langgraph.checkpoint.memory) saves the conversation state after each step.
  • config = {"configurable": {"thread_id": "1"}} tells the agent which conversation to load and save; pass it to every call.
  • With memory, call #2 sees Human, AI, Human (3 messages) and can answer "green".
  • Different thread IDs are separate conversations; forgetting the config raises a ValueError.
  • InMemorySaver lives in RAM: the memory disappears when the program ends, and history grows (more tokens) with every turn.
