Debugging, Logging & LangSmith

Reading tracebacks, logging, inspecting the messages list, and tracing runs.

Agents fail in two ways. Some failures are loud: Python stops and prints a red traceback. Others are silent: the program runs, the chef answers, and the answer is quietly worse than it should be because the model never received your instruction. The video hits both kinds, and the chef repo contains two silent bugs (found while preparing this guide, fixed in step 16). This chapter gives you a toolkit for both: how to read a traceback, the errors you will meet most often, how to look inside the agent's messages list, how to use Python logging well, the debug=True switch, LangSmith tracing, and how to test an agent without spending money on a real model.

Why this matters for your project. An agent is a loop with a model, tools and a web service in it (chapter 4). When something goes wrong you need to know which step went wrong: your Python code, the message you built, the model's choice, the tool, or the network. Every technique here answers "what actually happened?".

Reading a Python traceback

When an exception is not handled, Python prints a traceback: the chain of calls that led to the error, then the error itself. Beginners often read it from the top and get lost in library code. Read it from the bottom up.

At 70:11 in the video, the presenter's code called create_agent.invoke(...) instead of agent.invoke(...). The traceback had this shape (paths shortened; illustrative layout from Python 3.12):

Traceback (most recent call last):
  File "...\Beginner\multi_model_messages.py", line 62, in <module>
    response = create_agent.invoke(
               ^^^^^^^^^^^^^^^^^^^
AttributeError: 'function' object has no attribute 'invoke'

Here the message says create_agent is a function, and functions have no invoke. The fix is to call create_agent(...) once to build an agent, store it in agent, and call agent.invoke(...). When a traceback is long, everything inside .venv\Lib\site-packages is library code. Libraries can have bugs, but in beginner projects the cause is almost always in the last frame of your own file or in how you called the library.

New to exceptions? What "raise" and "catch" mean

An exception is Python's way of saying "I can't continue". Code raises it (for example raise ValueError("Not an image file") in photo_decoder.py). If nothing catches it with try/except, the program stops and prints the traceback. Each exception has a type (ValueError, FileNotFoundError...) that tells you the category of problem, and a message with the details.

Silent bugs: when nothing crashes

The hardest bugs in this project raise no error at all:

  • The chef never sees the request. photo_decoder.py sends the literal text "prompt" instead of the variable prompt. The run "works" because the system prompt explains the task.
  • A missing space. prompt.py joins two strings with a \ line continuation, so the model reads "...in the photo.once you do that...".
  • A setting that is ignored. temperature=1.0 with gpt-5-nano: langchain-openai 1.3.4 drops any other value for gpt-5* reasoning models, so changing it would make no difference (see chapter 2).
  • The model ignores a tool. At 43:19–45:25 the model did not call the simple tool until the system prompt was made strict.

Tracebacks cannot find these. You find them by looking at what was actually sent and received, which is what the rest of this chapter is about.

Look inside: print the messages

The single most useful debugging habit with LangChain agents: print the whole messages list, not just the last answer. At 26:45 the presenter printed response["messages"] to show the AIMessage with its token counts and metadata. Raw printing is hard to read, so use a loop or pretty_print() (a method on every LangChain message):

response = agent.invoke({"messages": [message]})

for m in response["messages"]:
    m.pretty_print()

last = response["messages"][-1]
print("tool calls:", getattr(last, "tool_calls", None))
print("tokens:", last.usage_metadata)

See every step as it happens

Printing after the run shows the end result. To watch the steps one by one, stream updates. Each item is a dictionary keyed by the step (node) that just ran, such as "model" or "tools", with the messages it added. Checked with LangGraph 1.2.9:

for update in agent.stream({"messages": [message]}, stream_mode="updates"):
    for step_name, data in update.items():
        print(f"--- {step_name} ---")
        for m in data["messages"]:
            m.pretty_print()

This complements stream_mode="messages" from step 7: "messages" streams tokens for the user, "updates" streams whole steps for you, the developer.

The debug switch

create_agent has a debug parameter (default False). With debug=True the underlying LangGraph graph prints its internal events while it runs: lines starting with [values] show the full state, lines starting with [updates] show what each step changed. Verified with LangChain 1.3.12:

agent = create_agent(model="gpt-5-nano",
                     tools=[web_search],
                     system_prompt=SYSTEM_CHEF_PROMPT,
                     debug=True)

It is very verbose (each [values] line repeats the whole state, including your base64 photo), so switch it on for one run, read, and switch it off again.

Logging: a diary for your program

print is fine for a quick look. For anything you keep, use Python's logging module, as the presenter does in step 14 (main.py, lines 9–12):

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s | %(levelname)s | %(message)s",
)

Each log line gets a time, a level and your message, and in the real run (100:24) you could watch the agent search for "recipe using oyster sauce" and "garlic fried...". The level is the key idea: every message has a severity, and the configured level is a threshold.

LevelUse it forExample in the chef
DEBUGDetails only useful while debuggingThe full text block sent to the model
INFONormal milestoneslogging.info("invoking our agent...")
WARNINGSomething odd, but the program continueslogging.warning(f"search failed: {error}") in step 16's tools.py
ERRORAn operation failedThe agent call raised an exception
CRITICALThe program cannot continueNo API key at all

Three practical tips:

  • Configure once, in the entry file. The repo calls logging.basicConfig in both main.py and tools.py. Only the first call has an effect (later calls do nothing once logging is set up), which is why step 16 keeps it only in main.py. In library-style files, you can use logger = logging.getLogger(__name__) and logger.info(...), so each line can show which module wrote it.
  • Turn up a library's logs only when needed. For example logging.getLogger("httpx").setLevel(logging.WARNING) hides the HTTP request lines that some libraries log at INFO.
  • Never log secrets or whole images. Don't log API keys or headers; log the length of a data URL, not the data URL itself. Logs are often copied into issues and chats.

Tracing with LangSmith

LangSmith is LangChain's hosted platform for observability. When tracing is on, every agent run is recorded as a trace: a tree of every model call and tool call, with inputs, outputs, token counts, timings and errors, viewable in a web UI. It is the same information as the messages list, but organised, searchable and kept across runs. The langsmith Python package is already installed as a dependency of langchain (0.10.2 in the locked environment), so no code change is needed: you turn tracing on with environment variables, for example in your .env file:

LANGSMITH_TRACING=true
LANGSMITH_API_KEY=your-langsmith-key-here
LANGSMITH_PROJECT=personal-chef

LANGSMITH_TRACING switches tracing on, LANGSMITH_API_KEY is a key you create in your LangSmith account, and LANGSMITH_PROJECT (optional) groups runs under a project name. These are the names in the official quickstart at the time of writing; older tutorials use LANGCHAIN_TRACING_V2 and LANGCHAIN_API_KEY, which the SDK still reads. Because the chef calls load_dotenv() at start-up, the variables are picked up automatically. Check the LangSmith docs for current plans and limits.

Tracing sends your data to a third party. A trace contains everything the agent saw: prompts, search results and the base64 photo. That is great for debugging and a problem for private data. Use a separate project for experiments, don't trace sensitive data unless your organisation allows it, and keep LANGSMITH_API_KEY in .env like any other key (chapter 9).

Testing without spending money

Every real run costs tokens, needs network access and gives a slightly different answer each time. That makes real models bad for automated tests. The code in this guide was verified the other way: an offline harness replaced the chat model with a fake model that returns prepared answers, replaced Tavily's search with a canned result and replaced the file picker. No API keys were used.

langchain_core includes fake chat models for exactly this. GenericFakeChatModel (in langchain_core.language_models.fake_chat_models) returns the messages you give it, one per call, and supports streaming. You can pass it to create_agent instead of a model name. This test was run against LangChain 1.3.12:

from langchain.agents import create_agent
from langchain.messages import HumanMessage
from langchain_core.language_models.fake_chat_models import GenericFakeChatModel
from langgraph.checkpoint.memory import InMemorySaver


def test_agent_remembers_the_thread():
    fake = GenericFakeChatModel(messages=iter(["Nice!", "Green, you told me."]))
    agent = create_agent(model=fake, checkpointer=InMemorySaver())
    config = {"configurable": {"thread_id": "test"}}

    agent.invoke({"messages": [HumanMessage("My favorite color is green")]}, config)
    response = agent.invoke({"messages": [HumanMessage("what is my favorite color")]}, config)

    assert [m.type for m in response["messages"]] == ["human", "ai", "human", "ai"]
Line(s)CodeWhat it does & why
3from langchain_core.language_models.fake_chat_models import GenericFakeChatModelThe fake model. It has the same interface as a real chat model, so the agent cannot tell the difference.
7def test_agent_remembers_the_thread():A test function. Test runners such as pytest run every function whose name starts with test_ (pytest is not part of the project; install it if you want to use it).
8GenericFakeChatModel(messages=iter([...]))The two answers it will give, in order. iter(...) turns the list into an iterator, which is what the class expects.
9–10create_agent(model=fake, checkpointer=InMemorySaver())The same agent setup as step 10, with the fake model passed as an object instead of a string.

Limits: in this version GenericFakeChatModel does not implement bind_tools (it raises NotImplementedError), so for an agent with tools you need a small subclass or another fake that accepts tools and returns prepared AIMessages with tool_calls. That is what the harness for this guide did. Test tools on their own with tool.invoke({...}), as in step 8, and replace network calls (like Tavily) with canned data so tests never depend on the internet.

A debugging routine

  1. Reproduce it. Find the smallest input that shows the problem (one photo, one question).
  2. Read the last line of the traceback, then the last frame in your own file.
  3. No traceback? Print the messages list (or stream "updates") and check each message against what you expected.
  4. Add logging around the suspicious step, at DEBUG level, then raise the level back.
  5. Trace with LangSmith if the run has many steps or you need timings and token counts.
  6. Fix, then lock it in with a small fake-model test so the bug cannot come back silently.
Common misconceptions
  • "Read the traceback from the top." Start at the bottom: error type and message, then your own file's line.
  • "No error means it works." The "prompt" bug ran without errors in the video. Look at the messages.
  • "debug=True is a logging level." It is a LangGraph switch that prints graph events; Python logging is separate.
  • "I can test an agent by checking its exact answer." Real answers vary. Test your logic with fakes; judge real answers by hand or with evaluations.
  • "Tracing is private." Traces are stored on LangSmith's servers. Treat them like any other place your data goes.
Recap
  • Read tracebacks bottom-up: error type and message, then your last frame.
  • Most beginner errors point to the environment (venv, packages), secrets (.env, load_dotenv), your code, or config (thread_id).
  • Silent bugs need inspection: pretty_print() every message, check tool calls, tool results and usage_metadata.
  • stream_mode="updates" and create_agent(..., debug=True) show each step as it runs.
  • Use logging levels, configure once, never log keys or whole images.
  • LangSmith tracing is switched on with LANGSMITH_TRACING=true and LANGSMITH_API_KEY; it sends your data to LangSmith.
  • GenericFakeChatModel lets you test agent logic offline for free; fake tools and network calls too.
