Multimodal Input & Structured Output

Images and files as content blocks, and getting typed data back with response_format.

The chef project does two things that go beyond "send text, get text": it sends a photo to the model (step 11 and step 13), and in the extension step 17 it gets back a typed recipe instead of a paragraph. This chapter explains both sides. First the input side: how images (and other files) travel inside a message as content blocks, what a data URL is, why file size matters and which models can see. Then the output side: structured output with response_format and a Pydantic model, the two strategies LangChain can use, what happens when the model returns invalid data, and when structured output is the right choice.

Why this matters for your project. The chef's whole idea is "photo in, recipe out". If you understand content blocks you can send several photos, a photo by URL, or switch providers (step 19) without guessing. If you understand structured output you can save recipes to a database, show them in an app, or make a shopping list, because your code receives fields, not prose.

Part 1: Multimodal input

Multimodal means "more than one kind of data": text plus images, audio, video or documents. A multimodal model (also called a vision model when it accepts images) can take those as input. LangChain does not do the "seeing"; it only packages the image in the format the provider expects.

Content: a string or a list of blocks

So far, every message had a plain string as its content: HumanMessage(content="My favorite color is green"). For mixed input, content becomes a list of content blocks. Each block is a dictionary with a "type" key saying what it carries. Here is the message builder from the lesson in step 11 (transcribed from the video):

def build_image_message(image_path: Path) -> HumanMessage:
    return HumanMessage(
        content=[
            {"type": "text", "text": "tell me what is the image about"},
            {"type": "image_url", "image_url": {"url": image_to_data_url(image_path)}},
        ]
    )
The repo's text block sends the word "prompt". In the chef repo, photo_decoder.py line 52 is {"type": "text", "text": "prompt"}: the string "prompt", not the variable prompt. The offline harness confirmed the model receives the literal word. It still seemed to work in the video because the system prompt tells the model what to do. Step 16 fixes it to "text": prompt. This is a good reminder to check what your blocks really contain (see chapter 8).

Data URLs: an image as text

A request to the model is JSON text, so a photo's raw bytes cannot be pasted in directly. The lesson converts the file into a data URL: a string that contains the file itself, encoded as base64. Lines 42–47 of the lesson file do it:

    mime_type, _ = mimetypes.guess_type(str(image_path))
    if not mime_type or not mime_type.startswith("image/"):
        raise ValueError(f"Not an image file: {image_path}")

    image_b64 = base64.b64encode(image_path.read_bytes()).decode("utf-8")
    return f"data:{mime_type};base64,{image_b64}"
New to base64? Why the image gets bigger

Base64 rewrites any bytes using only 64 "safe" characters (A–Z, a–z, 0–9, + and /), so binary data can travel inside text formats like JSON. Every 3 bytes become 4 characters, which is why the encoded image is about a third larger than the file on disk. It is an encoding, not encryption: anyone can decode it, so a base64 photo is exactly as private as the photo itself.

The provider-neutral image block

The chef uses OpenAI's own block shape ("type": "image_url"). LangChain 1.x also defines a standard image block that each provider package translates for you, which helps when you switch models as in step 19. This was checked with langchain-openai 1.3.4: both blocks below are converted into OpenAI's image_url format before sending.

HumanMessage(content=[
    {"type": "text", "text": "Which ingredients do you see?"},
    {"type": "image", "base64": image_b64, "mime_type": "image/jpeg"},
])

HumanMessage(content=[
    {"type": "text", "text": "Which ingredients do you see?"},
    {"type": "image", "url": "https://example.com/fridge.jpg"},
])

Notice that the standard block takes the raw base64 string and the MIME type as separate keys, instead of one combined data URL.

File size, cost and quality

  • Images use tokens. Providers turn an image into tokens, and larger or higher-detail images generally cost more and take longer. The exact rule differs by provider and model, so check its vision documentation.
  • Size limits exist. Providers limit the size and number of images per request and the accepted formats. The lesson's file picker allows *.png *.jpg *.jpeg *.webp; a format the provider does not support produces an error from the API, not from LangChain.
  • Phone photos are large. Resizing a photo before encoding it (with an image library) usually keeps enough detail to recognise ingredients while making the request much smaller. That is an optional improvement; the project does not do it.
  • Memory multiplies it. With a checkpointer (step 18), the image block stays in the thread and is resent on every follow-up question.

Which models can see?

Only models that accept image input can read the photo. The video uses gpt-5-nano, which accepted the image in the presenter's runs. Many current models from OpenAI, Anthropic and Google accept images; many small local models do not. Model lists change often, so check the provider's model page "at the time of writing" for your model. If you send an image to a text-only model, expect an error from the provider or a model that ignores the picture. Some providers also accept audio, video or PDF files as content blocks; support varies widely, so treat it as provider-specific.

Part 2: Structured output

A normal agent answer is free text: response["messages"][-1].content. That is great for a human to read and awkward for a program. If you want to save the recipe, count its steps or list its ingredients in an app, you would have to parse prose, and the prose changes every time. Structured output asks the model to answer in a fixed shape that your code can rely on.

Describe the shape with Pydantic

In LangChain you describe the shape with a Pydantic class. This is the Recipe model from step 17 (structured_chef.py, lines 15–23):

class Recipe(BaseModel):
    """A recipe that uses the ingredients found in the photo."""

    title: str = Field(description="Name of the dish")
    ingredients_seen: list[str] = Field(description="Ingredients you recognised in the photo")
    ingredients: list[str] = Field(description="Everything the recipe needs, with quantities")
    steps: list[str] = Field(description="Cooking steps, in order")
    minutes: int = Field(description="Total cooking time in minutes")
    source_url: str | None = Field(default=None, description="Web page the recipe came from, if any")

Each attribute is a field with a type hint (str, list[str], int, str | None) and a description. LangChain turns this class into a JSON Schema, a machine-readable description of the shape. The docstring and the descriptions are sent to the model, so they work like small prompts: write them for the model.

Then you pass the class to create_agent and read the result from a new key (lines 26–29 and 34):

agent = create_agent(model="gpt-5-nano",
                     tools=[web_search],
                     system_prompt=SYSTEM_CHEF_PROMPT,
                     response_format=Recipe)
recipe: Recipe = response["structured_response"]

recipe is a real Recipe object: recipe.title is a string, recipe.minutes is an integer, recipe.steps is a list you can loop over. The agent still keeps its normal messages list as well.

Two strategies: provider-native or tool calling

How does LangChain get the model to answer in that shape? In LangChain 1.3.12 (langchain/agents/structured_output.py) there are two strategies:

ProviderStrategyToolStrategy
How it worksUses the provider's built-in structured output mode: the schema is sent as a JSON-schema response format and the provider constrains the answer.Adds an extra, artificial tool named after your schema (here Recipe). The model "calls" it with the fields as arguments; LangChain catches that call.
Works withModels whose provider supports native structured outputAny model that supports tool calling
If the data is invalidRaises StructuredOutputValidationErrorBy default (handle_errors=True) sends the error back to the model and lets it try again

If you pass the bare class, as step 17 does, LangChain chooses automatically: it uses ProviderStrategy when it detects the model supports native structured output, otherwise ToolStrategy. With gpt-5-nano it picks the provider-native mode (verified in the harness). You can also choose explicitly:

from langchain.agents.structured_output import ProviderStrategy, ToolStrategy

agent = create_agent(model="gpt-5-nano", tools=[web_search], response_format=ToolStrategy(Recipe))
agent = create_agent(model="gpt-5-nano", tools=[web_search], response_format=ProviderStrategy(Recipe))

When the model returns invalid data

Models make mistakes. A model might write "minutes": "twenty" when the schema says int. Pydantic refuses it. What happens next depends on the strategy. The harness reproduced this with ToolStrategy and a fake model that first sent "twenty" and then 20; the messages list looked like this:

human  recipe
ai     (calls the Recipe tool with minutes="twenty")
tool   Error: Failed to parse structured output for tool 'Recipe': ... 1 validation error for Recipe
       minutes
         Input should be a valid integer ...
ai     (calls the Recipe tool again with minutes=20)
tool   Returning structured response: title='Fried rice' minutes=20

With ProviderStrategy there is no retry loop: invalid data raises StructuredOutputValidationError, which you can catch like any other exception. Native modes make invalid output much rarer, but you should still handle the error in a program that must not crash:

from langchain.agents.structured_output import StructuredOutputValidationError

try:
    response = agent.invoke({"messages": [build_image_message(path, CHEF_PROMPT)]})
except StructuredOutputValidationError as error:
    raise SystemExit(f"The chef returned a recipe in the wrong shape: {error}")

ToolStrategy lets you control retries with handle_errors: True (the default), False (raise immediately), a custom message string, an exception type, or a function that builds the message.

Tips for good schemas

  • Describe every field. Field(description=...) is read by the model. "Total cooking time in minutes" is far better than nothing.
  • Make optional things optional. source_url: str | None = None lets the model say "no source" instead of inventing a URL. Required fields push the model to fill them, even with made-up values (a hallucination).
  • Keep it small and flat. A few clear fields work better than a deep tree of nested objects.
  • Validation is about shape, not truth. Pydantic checks that minutes is an integer, not that the recipe really takes 20 minutes.

Common misconceptions
  • "LangChain looks at the image." The model does. LangChain only packages it.
  • "Base64 hides the image." It is an encoding anyone can reverse, not encryption.
  • "Any model can read photos." Only vision-capable models; check the model page.
  • "Structured output means the answer is correct." It means the answer has the right shape. Content can still be wrong.
  • "I must parse JSON myself." No: response["structured_response"] is already a validated Pydantic object.
Recap
  • Mixed input uses a list of content blocks in one message: a text block plus image blocks.
  • A data URL is data:<mime>;base64,<bytes>; base64 makes files about 33% larger.
  • Images can go as a data URL, an https URL or a provider file id; LangChain's standard {"type": "image", ...} block is translated per provider.
  • Images cost tokens; only vision-capable models can read them; memory resends them.
  • response_format=Recipe returns a validated object in response["structured_response"].
  • ProviderStrategy uses the provider's native mode and raises on bad data; ToolStrategy uses an extra tool and retries by default.
  • Describe every field, make optional fields optional, and remember validation checks shape, not truth.
