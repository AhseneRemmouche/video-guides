Conversation History & the Model Shortcut

Send Human/AI/Human messages so the agent understands follow-ups; pass the model as a string.

▶ Watch this part (28:21)

Goal

A real chat is more than one question. In this step you send the agent a short conversation: a question, the AI's earlier answer, and a follow-up that only makes sense with that history ("tell me more about it"). You'll see why the model needs the whole history every time. Then you'll delete the separate model object and give create_agentcreateAgent just the model's name as a string, a shortcut you'll use for the rest of the course.

This matters for the project: the personal chef must remember what was in your fridge photo when you ask a follow-up. Step 10 automates that with memory, but it works exactly the way you'll build it by hand here.

The idea: the model only knows what you send it

The presenter introduces this at 28:21: "the agent can see multiple things. We can tell it actually there has been a conversation". They simulate one, Human → AI → Human, and add: "This is basically what happens when you talk to ChatGPT" (29:33). And the key sentence: "If the AI did not have this previous conversation, it will not know that it needs to talk to me more about [Rome]" (29:55).

New to how chat models "remember"? They don't: you resend the history

A chat model has no memory between calls. Each call is independent: the model reads the messages you send in that call, writes an answer, and forgets everything. This is called being stateless.

So how does ChatGPT follow a conversation? The app keeps the history and sends the whole conversation again with every new question. The model re-reads it all each time, which is why longer chats use more tokens (and cost more).

There is also a limit to how much the model can read at once, called the context window. Very long conversations eventually have to be shortened. The handbook chapter on memory and state covers that; for now your conversation is three short messages.

New to AIMessage? Writing the AI's lines yourself

In step 5 the agent created an AIMessage as its reply. Here you create one yourself: AIMessage(content="Rome (Italian: Roma).")new AIMessage("Rome (Italian: Roma)."). It tells the model "earlier in this chat, you said this". The model can't tell whether it really said it; it trusts the history you send.

That's powerful (you can replay a saved chat, or show the model an example of the style you want) and also a responsibility: if you put words in the AI's mouth, it will build on them. The presenter copied the content from the agent's real answer in step 5, so the history is honest.

The model shortcut: just say its name

"I don't even need to create a model to create an agent" (30:17). When you pass a string, create_agent hands it to init_chat_model, which infers the provider from how the name starts. You can also be explicit with "provider:model". In TypeScript, createAgent hands the string to initChatModel in the same way.

TypeScript detail: "openai:" also switches the API. Reading LangChain.js's source showed that when the string starts with "openai:", createAgent also turns on OpenAI's newer Responses API (useResponsesApi: true). A bare "gpt-5-nano", as this lesson uses, goes through the usual Chat Completions API. Both reach the same model; with the Responses API the message content can be a list of blocks instead of a string, which is one more reason the lessons print .text. (We could not run either against OpenAI: no key.)

Provider names in the string are written with a dash in JavaScript, for example "google-genai:…", where Python writes google_genai. For Ollama: "ollama:llama3.2", which is what MODEL_ID holds with MODEL_PROVIDER=ollama.

New to providers? One code style, many model companies

A provider is the company (or local program) that runs the model: OpenAI, Anthropic, Google, a local Ollama install, and so on. Each has its own API, but LangChain hides the differences behind the same chat-model interface, so agent.invoke(...) works the same whichever you pick.

The presenter mentions this at 31:23: "we can use multiple things like Gemini. We can also use Claude. You can use any provider that you like". To switch, you install that provider's LangChain package (for example langchain-anthropic; in TypeScript the matching @langchain/… package, added with pnpm add), put its API key in .env, and change the model string. Step 19 does exactly that for the chef project.

When should you still build the model yourself with init_chat_model (await initChatModel(...))? When you want settings other than the defaults (such as temperature for a model that supports it). The string shortcut always uses defaults.

Common mistakes:

  • Missing comma between messages: a syntax error, and the file does not run at all. Every item in an array needs a comma before the next one (a comma after the last one is optional).
  • Brackets in the wrong order at the end: the array closes with ], then the object with }, then the call with ). VS Code highlights matching pairs.
  • Forgot to import AIMessage or forgot new in front of it: the message cannot be created. Add it to the import on line 2, and write new AIMessage(...).
  • A typo in the model name or provider, such as "olama:llama3.2": the provider cannot be found or the model does not exist. Copy names exactly; in TypeScript provider names use dashes (google-genai).
  • Wrong message order, for example putting the follow-up first: the model reads the chat in array order and gets confused.

Common mistakes:

  • Missing comma between messages: SyntaxError: invalid syntax. Perhaps you forgot a comma? Every item in a list except the last needs a comma after it.
  • Brackets in the wrong order at the end: the list closes with ] before the dictionary closes with }, and the call closes with ) last. VS Code highlights matching pairs when you click next to one.
