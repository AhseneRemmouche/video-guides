The React web app

Upload a fridge photo, watch the chef stream a recipe, follow the tool calls, and keep chatting on the same thread.

TypeScript · verified with LangChain.js 1.5.16, gemma4 and llama3.2

TypeScript only, not in the video. This page has no Python version. It builds on step 11 (sending an image as a data URL), step 14 (the chef agent with web search) and step 18 (memory and streaming), and puts the same chef in a web page. The code is in the TypeScript project fasteat-agent-ts, in the folders server/ and web/. We ran it for real with Ollama (gemma4 for the photo, llama3.2 for the chef), with curl and in Chrome. We had no OpenAI or Tavily key, so those paths were not run.

Goal

Until now the chef ran in a terminal. In this step it gets a web page. A visitor drops a photo of their fridge on the page (or picks it with a button), clicks Find a recipe, and sees three things: the ingredients the model found in the photo, the recipe appearing word by word, and a side panel that lists every tool call the chef made, with its result. Then they can keep asking questions in the same conversation ("Make it vegetarian"). You will read every file of the app, from the server to the last line of the user interface.

The idea in brief

  • Two programs, two terminals. A Node.js server (server/) owns the models, the agent and the keys. A React app (web/) runs in the browser and only shows things. The browser never talks to OpenAI, Ollama or Tavily directly, so your keys stay on the server.
  • Two models, one after the other. First a vision model looks at the photo and lists the ingredients. Then a text-only chef agent turns that list into a recipe. The command-line chef of step 14 does both in one agent; the reason for the split is explained below.
  • The server streams. Two API endpoints, POST /api/photo and POST /api/chat, send what happens as Server-Sent Events: the ingredient list, answer tokens, tool calls, tool results, and "done" or "error".
  • Memory per conversation. A MemorySaver checkpointer and a thread id, as in steps 10 and 18, let the chef remember the recipe when you ask a follow-up.
New to React? Components, state and why the page redraws itself

React is a library for building user interfaces out of components: functions that return a description of what the screen should look like, written in JSX (HTML-like tags inside TypeScript, in .tsx files). You never change the page by hand. Instead you keep the data that matters in state, created with the hook useState. Calling a state setter, such as setMessages(...), tells React "this data changed"; React calls your component again and updates only the parts of the page that differ. In this app, every event from the server becomes one state change, and the chat and the side panel follow automatically.

New to Server-Sent Events? How a server streams to a browser

A normal HTTP request gets one reply and is finished. With Server-Sent Events (SSE), the server keeps the reply open and writes small text messages into it whenever it has something new. Each message has an event: line (its type) and a data: line (its content), and ends with a blank line. This is how the recipe appears word by word: each new token from the model becomes one event. It is the web version of the streaming you used in step 18, where the tokens went to the terminal.

New to web servers? What an API endpoint and Hono are

A web server listens on a port (here 8787) and answers requests. An API endpoint is one address plus a method, like POST /api/photo, that runs a piece of your code and returns data instead of a web page. Hono is a small TypeScript framework for writing such servers: you create an app, register a function per endpoint with app.post(path, handler), and start it. The handler receives a context object c with the request (c.req) and helpers to build the response.

Why two models: look first, then cook

In step 14 one agent gets the photo, looks at it, searches the web and writes the recipe. The web app splits that work:

  1. decodeIngredients() sends the photo to the vision model with one instruction: list the ingredients, one per line. It is a single question and a single answer, with no tools.
  2. The server sends that list to the browser at once (the "Seen in the photo" box), then gives it, as plain text, to the chef agent.
  3. The chef agent is a normal text agent with the web_search tool and memory. It never sees the photo, only the list.

Two reasons. On Ollama, llama3.2 cannot see images (ollama show lists no vision capability) while gemma4 can; the split lets each model do the job it can do. And the visitor sees what the model thought was in the fridge before the recipe arrives, so a wrong guess is easy to spot. With MODEL_PROVIDER=openai both steps use the same gpt-5-nano, which can do both.

Run it

  1. Open a terminal in the project folder fasteat-agent-ts. If you have not done it yet for the earlier steps, run pnpm install.
  2. Choose the models in .env (copy .env.example if you have no .env yet). With MODEL_PROVIDER=openai you need OPENAI_API_KEY. With MODEL_PROVIDER=ollama (what we used) you need no key, but ollama list must show llama3.2 and gemma4; if one is missing, run ollama pull llama3.2 or ollama pull gemma4. TAVILY_API_KEY is optional.
  3. Start the API server: pnpm api. It prints FastEat chef API on http://localhost:8787. Leave this terminal open; the server's log lines appear here.
  4. Open a second terminal in the same folder and start the web app: pnpm web. Vite prints the address of the app.
  5. Open http://localhost:5173 in your browser. Drop a photo on the dashed area, or click Choose a photo. The sample data/fridge.png (a drawing of a fridge with 12 labelled items) works for a first try.
  6. Click Find a recipe. Then type a follow-up question in the box at the bottom and press Send.
  7. To stop, press Ctrl+C in each terminal.

The server: server/upload.ts

Anything that arrives from a browser can be wrong or hostile, so the server checks the photo before any model sees it. This small file holds that check.

// Checks a photo sent by the browser before any model sees it.
export const MAX_IMAGE_BYTES = 5 * 1024 * 1024; // 5 MB
export const IMAGE_TYPES = ["image/png", "image/jpeg", "image/webp", "image/gif"];

export type Upload = { mimeType?: unknown; data?: unknown };

/** Returns { dataUrl } for a good photo, or { error } with a message the user can act on. */
export function checkUpload({ mimeType, data }: Upload): { dataUrl: string } | { error: string } {
  if (typeof mimeType !== "string" || !IMAGE_TYPES.includes(mimeType)) {
    return { error: `Please send a photo (PNG, JPEG, WebP or GIF), not "${String(mimeType || "unknown type")}".` };
  }
  if (typeof data !== "string" || !/^[A-Za-z0-9+/]+={0,2}$/.test(data)) {
    return { error: "The photo is missing or is not base64 text." };
  }
  const bytes = Math.floor((data.length * 3) / 4) - (data.endsWith("==") ? 2 : data.endsWith("=") ? 1 : 0);
  if (bytes > MAX_IMAGE_BYTES) {
    return { error: `The photo is ${(bytes / 1024 / 1024).toFixed(1)} MB; the limit is 5 MB.` };
  }
  return { dataUrl: `data:${mimeType};base64,${data}` };
}

The server: server/app.ts

This file defines the two endpoints and one helper, relayChef, that runs the chef and turns everything that happens into events for the browser.

// The web app's API. Two routes, both answer with a stream of Server-Sent Events:
//   POST /api/photo  { threadId, mimeType, data }  data = the photo as base64 text (5 MB at most)
//   POST /api/chat   { threadId, message }          a follow-up question in the same conversation
// Events: "ingredients" (what the vision model saw), "token" (answer text), "tool_call", "tool_result",
// "done" and "error". A bad photo gets a plain 400 answer with { error } instead.
import { isAIMessage, isToolMessage, type BaseMessage } from "@langchain/core/messages";
import { Hono } from "hono";
import { streamSSE, type SSEStreamingApi } from "hono/streaming";
import { CHEF_PROMPT } from "../chef/prompt.js";
import { log } from "../src/logger.js";
import { chefAgent, decodeIngredients } from "./agent.js";
import { checkUpload, type Upload } from "./upload.js";

type Send = (event: string, data: unknown) => Promise<void>;

/** Run the chef and forward what happens to the browser, step by step. */
async function relayChef(send: Send, text: string, threadId: string) {
  const stream = await chefAgent.stream(
    { messages: [{ role: "user", content: text }] },
    {
      configurable: { thread_id: threadId },
      streamMode: ["messages", "updates"], // tokens as they are written, and each finished step
    },
  );
  for await (const [mode, chunk] of stream) {
    if (mode === "messages") {
      const [token, meta] = chunk;
      // Only text the model writes; tool results also pass through this stream.
      if (meta.langgraph_node === "model_request" && token.text) await send("token", token.text);
      continue;
    }
    for (const update of Object.values(chunk)) {
      const messages = (update as { messages?: BaseMessage[] } | undefined)?.messages ?? [];
      for (const m of messages) {
        if (isAIMessage(m)) {
          for (const call of m.tool_calls ?? []) await send("tool_call", { id: call.id, name: call.name, args: call.args });
        } else if (isToolMessage(m)) {
          await send("tool_result", { id: m.tool_call_id, name: m.name, content: m.text });
        }
      }
    }
  }
}

/** Open the event stream, run the work, and always finish with "done" or "error". */
function events(sse: SSEStreamingApi, work: (send: Send) => Promise<void>) {
  const send: Send = (event, data) => sse.writeSSE({ event, data: JSON.stringify(data) });
  return work(send).then(
    () => send("done", {}),
    (error: Error) => {
      log.warning(error.message);
      return send("error", error.message);
    },
  );
}

export const app = new Hono();

app.post("/api/photo", async (c) => {
  const { threadId, ...upload } = await c.req.json<Upload & { threadId: string }>();
  const checked = checkUpload(upload);
  if ("error" in checked) return c.json({ error: checked.error }, 400);

  return streamSSE(c, (sse) =>
    events(sse, async (send) => {
      log.info("decoding the photo...");
      const ingredients = await decodeIngredients(checked.dataUrl);
      await send("ingredients", ingredients);
      log.info("asking the chef...");
      await relayChef(send, `Ingredients seen in my fridge photo:\n${ingredients}\n\n${CHEF_PROMPT}`, threadId);
    }),
  );
});

app.post("/api/chat", async (c) => {
  const { threadId, message } = await c.req.json<{ threadId: string; message: string }>();
  return streamSSE(c, (sse) => events(sse, (send) => relayChef(send, message, threadId)));
});

The web app: web/src/sse.ts

The browser has a built-in reader for Server-Sent Events, EventSource, but it can only send GET requests without a body. Our endpoints need a JSON body (the photo is in it), so this file sends a POST with fetch and reads the event stream itself.

// POST a JSON body and read the Server-Sent Events that come back.
// (The browser's EventSource only does GET requests, so we read the stream ourselves.)
export type AgentEvent =
  | { event: "ingredients"; data: string }
  | { event: "token"; data: string }
  | { event: "tool_call"; data: { id: string; name: string; args: Record<string, unknown> } }
  | { event: "tool_result"; data: { id: string; name: string; content: string } }
  | { event: "done"; data: Record<string, never> }
  | { event: "error"; data: string };

export async function postEvents(url: string, body: unknown, onEvent: (e: AgentEvent) => void) {
  const response = await fetch(url, {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify(body),
  });
  if (!response.ok || !response.body) {
    // A refused photo comes back as { error: "..." }.
    const problem = await response.json().catch(() => null) as { error?: string } | null;
    throw new Error(problem?.error ?? `Server answered ${response.status}`);
  }

  const reader = response.body.pipeThrough(new TextDecoderStream()).getReader();
  let buffer = "";
  for (;;) {
    const { value, done } = await reader.read();
    if (done) break;
    buffer += value;
    // Events are separated by a blank line; each has "event: ..." and "data: ..." lines.
    const blocks = buffer.split(/\r?\n\r?\n/);
    buffer = blocks.pop()!; // the last piece may be incomplete: keep it for the next read
    for (const block of blocks) {
      const event = block.match(/^event: (.*)$/m)?.[1];
      const data = block.match(/^data: (.*)$/m)?.[1];
      if (event && data !== undefined) onEvent({ event, data: JSON.parse(data) } as AgentEvent);
    }
  }
}

The web app: web/src/App.tsx

The whole user interface is one component. Read it in five parts: the helpers before the component (lines 4–20), the state (23–31), the event handler handle (37–59), the actions (61–111), and the JSX that draws the page (117–179).

import { useRef, useState, type DragEvent, type FormEvent } from "react";
import { postEvents, type AgentEvent } from "./sse";

type Message = { role: "user" | "assistant"; text: string; image?: string; ingredients?: string };
type Step = { id: string; name: string; args: Record<string, unknown>; result?: string };
type Photo = { file: File; preview: string };

// The same rules as the server (server/upload.ts), so mistakes show up before the upload.
const IMAGE_TYPES = ["image/png", "image/jpeg", "image/webp", "image/gif"];
const MAX_BYTES = 5 * 1024 * 1024;

/** The file's bytes as base64 text (what the server expects). */
function readAsBase64(file: File): Promise<string> {
  return new Promise((resolve, reject) => {
    const reader = new FileReader();
    reader.onload = () => resolve(String(reader.result).split(",")[1]); // drop the "data:...;base64," part
    reader.onerror = () => reject(reader.error);
    reader.readAsDataURL(file);
  });
}

export default function App() {
  const [threadId, setThreadId] = useState(() => crypto.randomUUID()); // one memory per conversation
  const [messages, setMessages] = useState<Message[]>([]);
  const [steps, setSteps] = useState<Step[]>([]);
  const [photo, setPhoto] = useState<Photo | null>(null);
  const [problem, setProblem] = useState("");
  const [dragging, setDragging] = useState(false);
  const [input, setInput] = useState("");
  const [busy, setBusy] = useState(false);
  const picker = useRef<HTMLInputElement>(null); // the hidden file input behind "Choose a photo"

  // Change only the last message (the answer being written).
  const updateLast = (change: (m: Message) => Message) =>
    setMessages((all) => [...all.slice(0, -1), change(all[all.length - 1])]);

  function handle(e: AgentEvent) {
    switch (e.event) {
      case "ingredients":
        updateLast((m) => ({ ...m, ingredients: e.data }));
        break;
      case "token":
        updateLast((m) => ({ ...m, text: m.text + e.data }));
        break;
      case "tool_call": {
        const call = e.data;
        setSteps((all) => (all.some((s) => s.id === call.id) ? all : [...all, call]));
        break;
      }
      case "tool_result": {
        const result = e.data;
        setSteps((all) => all.map((s) => (s.id === result.id ? { ...s, result: result.content } : s)));
        break;
      }
      case "error":
        updateLast((m) => ({ ...m, text: `${m.text}\n[Error: ${e.data}]` }));
        break;
    }
  }

  async function run(url: string, body: unknown, question: Message) {
    setBusy(true);
    setMessages((all) => [...all, question, { role: "assistant", text: "" }]);
    try {
      await postEvents(url, body, handle);
    } catch (error) {
      handle({ event: "error", data: (error as Error).message });
    } finally {
      setBusy(false);
    }
  }

  function choose(file: File | undefined) {
    if (!file) return;
    if (!IMAGE_TYPES.includes(file.type)) return setProblem("Please choose a photo (PNG, JPEG, WebP or GIF).");
    if (file.size > MAX_BYTES) return setProblem(`This photo is ${(file.size / 1024 / 1024).toFixed(1)} MB; the limit is 5 MB.`);
    setProblem("");
    if (photo) URL.revokeObjectURL(photo.preview);
    setPhoto({ file, preview: URL.createObjectURL(file) });
  }

  function drop(event: DragEvent) {
    event.preventDefault();
    setDragging(false);
    choose(event.dataTransfer.files[0]);
  }

  async function sendPhoto() {
    if (!photo || busy) return;
    const data = await readAsBase64(photo.file);
    void run("/api/photo", { threadId, mimeType: photo.file.type, data }, {
      role: "user", text: "What can I cook with this?", image: photo.preview,
    });
    setPhoto(null); // the preview URL stays alive: the message shows it
  }

  function send(event: FormEvent) {
    event.preventDefault();
    const text = input.trim();
    if (!text || busy) return;
    setInput("");
    void run("/api/chat", { threadId, message: text }, { role: "user", text });
  }

  function newConversation() {
    setThreadId(crypto.randomUUID());
    setMessages([]);
    setSteps([]);
    setPhoto(null);
    setProblem("");
  }

  // What an answer shows before its first word arrives.
  const placeholder = (m: Message, isLast: boolean) =>
    isLast && busy ? (m.ingredients ? "Looking for a recipe…" : "Looking at your photo…") : "";

  return (
    <div className="page">
      <header>
        <div>
          <p className="eyebrow">FastEat</p>
          <h1>What can I cook from my fridge?</h1>
        </div>
        <button className="ghost" onClick={newConversation} disabled={busy}>New conversation</button>
      </header>

      <main>
        <section className="chat" aria-label="Conversation">
          <div
            className={`drop ${dragging ? "over" : ""}`}
            onDragOver={(e) => { e.preventDefault(); setDragging(true); }}
            onDragLeave={() => setDragging(false)}
            onDrop={drop}
          >
            {photo ? (
              <img className="preview" src={photo.preview} alt="The fridge photo you chose" />
            ) : (
              <p>Drop a photo of your fridge here, or</p>
            )}
            <div className="row">
              <button type="button" className="ghost" onClick={() => picker.current?.click()} disabled={busy}>
                {photo ? "Choose another" : "Choose a photo"}
              </button>
              <input ref={picker} type="file" accept={IMAGE_TYPES.join(",")} hidden
                onChange={(e) => { choose(e.target.files?.[0]); e.target.value = ""; }} />
              {photo && <button onClick={() => void sendPhoto()} disabled={busy}>Find a recipe</button>}
            </div>
            {problem && <p className="problem" role="alert">{problem}</p>}
          </div>

          {messages.map((m, i) => (
            <article key={i} className={`bubble ${m.role}`}>
              {m.image && <img className="thumb" src={m.image} alt="Your fridge photo" />}
              {m.ingredients && <p className="seen"><strong>Seen in the photo:</strong> {m.ingredients.split("\n").join(", ")}</p>}
              <p>{m.text || placeholder(m, i === messages.length - 1)}</p>
            </article>
          ))}

          <form onSubmit={send}>
            <input value={input} onChange={(e) => setInput(e.target.value)} placeholder="Ask the chef a follow-up question" disabled={busy} />
            <button disabled={busy || !input.trim()}>Send</button>
          </form>
        </section>

        <aside aria-label="What the chef did">
          <h2>What the chef did</h2>
          {steps.length === 0 && <p className="muted">Web searches appear here as they happen.</p>}
          <ol>
            {steps.map((s) => (
              <li key={s.id}>
                <code>{s.name}({JSON.stringify(s.args)})</code>
                {s.result !== undefined ? <pre>{s.result}</pre> : <span className="muted"> running…</span>}
              </li>
            ))}
          </ol>
        </aside>
      </main>
    </div>
  );
}

What you should see

What you should see. These are our real runs with MODEL_PROVIDER=ollama and no Tavily key. The wording of the answers will differ from ours.

  • With curl (the photo data/fridge.png posted to /api/photo): an ingredients event with the 12 labelled items, one per line: MILK, EGGS, CHEESE, TOMATOES, SPINACH, CHICKEN, CARROTS, YOGURT, ONIONS, SOY SAUCE, BUTTER, LIME. Then a tool_call for web_search with {"query":"recipe using milk eggs cheese tomatoes spinach chicken carrots yogurt onions soy sauce butter lime"}, a tool_result with the no-key message, 417 token events and done. It took 79 seconds on a small laptop whose memory was nearly full, so do not take that time as typical.
  • In Chrome: the same flow. The "Seen in the photo" box filled first, the side panel showed the web_search call and the no-key message, and the chef (llama3.2) wrote "Chicken and Spinach Stir-Fry with Yogurt Sauce".
  • In the pnpm api terminal: log lines such as ... | INFO | decoding the photo..., ... | INFO | asking the chef... and ... | INFO | searching for ....

The answer shows raw Markdown, such as **Ingredients:** with the asterisks. The model writes Markdown, and the app prints text as it is. Turning it into bold text and lists is a "try it yourself" idea below.

Common problems.

  • Why pnpm api and not pnpm server? pnpm has a built-in command called server, and built-in commands win over scripts with the same name: pnpm server runs pnpm's own command and exits without starting anything. Naming the script api avoids the clash.
  • Wrong file type or photo too big. The page checks first: a PDF shows "Please choose a photo (PNG, JPEG, WebP or GIF)." and a large file shows "This photo is … MB; the limit is 5 MB." under the drop zone, and nothing is sent. If something skips the page (a curl command, your own script), the server answers 400 with { "error": "..." }, for example Please send a photo (PNG, JPEG, WebP or GIF), not "application/pdf".; in the page that sentence would appear as [Error: ...] in the answer bubble. Fix: send a PNG, JPEG, WebP or GIF under 5 MB (shrink large phone photos first).
  • Only pnpm web is running. The page loads, but every request ends with an error in the answer bubble, and the pnpm web terminal reports a proxy error, because Vite has nowhere to forward /api. Start pnpm api in the other terminal.
  • Port already in use. If pnpm api fails with EADDRINUSE, another program (often a server you started earlier and forgot) uses port 8787. Stop it, or start with another port (PORT variable) and change the proxy target in web/vite.config.ts to match. If 5173 is busy, Vite picks the next free port and prints it; open that address.
  • A model or key is missing. The server starts without calling any model, so it prints its address even if something is wrong. The problem shows when you send a photo: the answer bubble gets [Error: ...] and the server terminal a WARNING line. With OpenAI and no key, the message starts with Missing credentials; add OPENAI_API_KEY to .env or set MODEL_PROVIDER=ollama. With Ollama, check that it is running and that ollama list shows gemma4 and llama3.2. Restart pnpm api after editing .env.
  • "Looking at your photo…" for a long time. On a computer without a strong graphics card, the vision model can take a while, and the chef too (our whole run took 79 seconds). Wait, or use a smaller photo.
  • The chef forgot the conversation. MemorySaver keeps conversations in the server's memory. Restarting pnpm api erases them all. Click New conversation and send the photo again.
  • Wrong ingredients. The sample fridge has printed labels, which makes it easy for a small vision model. A real photo is harder, and the model may miss or invent items. Check the "Seen in the photo" box before trusting the recipe.

Try it yourself

  1. Render the Markdown. Add a Markdown library such as react-markdown (pnpm add react-markdown) and use it for the answer text on line 155 of App.tsx, so **Ingredients:** becomes bold. (We did not add it; check the library's documentation for its current usage.)
  2. Check memory. After a recipe, ask "Make it vegetarian, please." in the same conversation. Then click New conversation and ask the same question without a photo. The difference is the thread id.
  3. Change the decoder's question. In server/agent.ts, change INGREDIENTS_PROMPT to also ask for quantities ("2 eggs"), restart pnpm api, and compare the "Seen in the photo" box.
  4. Watch the raw events. Open the browser's developer tools (F12), tab Network, send a photo and click the photo request. You can see the events arrive one by one.
  5. Add web search. Put a TAVILY_API_KEY in .env, restart pnpm api, and look at the side panel: the result box now holds real search results instead of the no-key message.
Recap
  • The app is two programs: a Hono server that owns the models and the agent (pnpm api, port 8787) and a React app served by Vite (pnpm web, port 5173), which forwards /api to the server.
  • The browser sends the photo as base64 inside JSON. The page and the server both check type (PNG, JPEG, WebP, GIF) and size (5 MB); the server answers 400 with { error } for a bad photo.
  • A vision model lists the ingredients first; a text-only chef agent with web_search and MemorySaver turns the list into a recipe and answers follow-ups on the same thread.
  • Everything comes back as Server-Sent Events: ingredients, token, tool_call, tool_result, then done or error. sse.ts reads them from a POST with fetch.
  • App.tsx keeps everything in useState; each event becomes a state change and React redraws the page. Tool calls and results are paired by id.
