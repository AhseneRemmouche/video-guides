Agents Under the Hood

The agent loop, how create_agent builds a LangGraph graph, and when an agent is the right tool.

What you will learn

From step 5 on, every program calls create_agent(...) and then agent.invoke(...). That one call can make several model calls, run tools in between, and stop by itself. This chapter opens the box. You will see that create_agent builds a small LangGraph graph, what that graph's state is, what limits keep it from looping forever, and when you should not use an agent at all.

The companion page How an Agent Thinks walks through the loop message by message. This chapter focuses on the machinery.

You will learn:

  • what makes an agent different from a single model call;
  • the graph create_agent builds: a model node, a tools node and a conditional edge (verified in langchain/agents/factory.py);
  • the agent's state: the messages list and how it grows;
  • the recursion limit: what it counts, its value in these versions, and how to set your own;
  • how the same loop looks when written by hand in LangGraph;
  • agents versus fixed workflows, and how LangChain and LangGraph relate.
Why this matters for your project. The chef is an agent: it decides on its own whether to search, what to search for, and how many times. Knowing the loop explains why the trace has an empty AIMessage (46:12), why answers with searches take longer and cost more, what stream_mode="messages" is streaming, and what checkpointers save in step 10.

What makes something an agent

A plain model call is one request and one response: text in, text out. An agent is a model that is allowed to act. You give it tools, and it runs in a loop. On each turn the model looks at everything so far and decides: call a tool (and which, with what arguments), or answer and stop. The important shift is who controls the flow. In ordinary code, you decide what happens next. In an agent, the model decides, within the tools and limits you give it.

That's the agent loop:

  1. Call the model with the system prompt, the messages so far, and the tool descriptions.
  2. Inspect the reply. If the AIMessage contains tool_calls, go to 3. If not, it is the final answer: stop.
  3. Run the requested tools and add one ToolMessage per call to the messages.
  4. Go back to 1. The model now sees the tool results and decides again.

The graph that create_agent builds

create_agent doesn't run a hidden while loop. It builds a LangGraph state graph: a set of nodes (functions that do work) joined by edges (what runs next), all sharing one state. It then compiles the graph and returns it. The object you call .invoke on is a CompiledStateGraph. Reading factory.py in the installed LangChain 1.3.12, and inspecting agent.get_graph(), gives exactly this shape:

PieceWhat it does
model nodeSends the system prompt plus state["messages"] to the chat model (with the tools bound), and returns the new AIMessage to add to the state.
tools nodeA ToolNode. For each tool call in the last AIMessage it runs the matching tool and returns a ToolMessage with the same tool_call_id. When the model asks for several tools at once, each call is dispatched separately, so they can run in parallel.
Edge START → modelEvery run begins with a model call.
Conditional edge after modelLooks at the last AIMessage: pending tool calls → tools; none → END.
Edge tools → modelResults always go back to the model (unless a tool is marked return_direct=True, which can end the run right after the tool).

You can print the graph yourself. print(agent.get_graph().draw_mermaid()) outputs a diagram in Mermaid syntax that you can paste into any Mermaid viewer. When you add middleware (an advanced topic from the video's roadmap, chapter 10), extra nodes such as SomeMiddleware.before_model are inserted around these two. The core loop stays the same.

A run, step by step

Here is the step 8 run as it travels between your code, the graph, the OpenAI API and your tool function:

State: the messages list

Every node reads and updates a shared state. For create_agent the state schema is AgentState, a typed dict whose main key is messages. A second key, structured_response, is filled when you use response_format (step 17). The installed source declares:

class AgentState(TypedDict, Generic[ResponseT]):
    messages: Required[Annotated[list[AnyMessage], add_messages]]
    jump_to: NotRequired[...]              # private, used by middleware
    structured_response: NotRequired[...]  # only with response_format

The interesting part is Annotated[…, add_messages]. add_messages is a reducer: it says how a node's output is merged into the state. Nodes don't return the whole list. They return only their new messages, such as {"messages": [ai_message]}, and add_messages appends them (or replaces a message that has the same id). That's why the list only ever grows during a run, and why the result you get back contains the whole conversation.

You can watch this happen with stream_mode="updates", which yields each node's output as soon as it finishes (verified):

for update in agent.stream({"messages": [HumanMessage("Hello I am a student and my name is Luca")]},
                           stream_mode="updates"):
    print(update)

# {'model': {'messages': [AIMessage(content='', tool_calls=[...])]}}
# {'tools': {'messages': [ToolMessage(content='this is the document of Luca', ...)]}}
# {'model': {'messages': [AIMessage(content='This is the document of Luca.')]}}

The modes you are most likely to use: "messages" streams tokens from the model as they are generated (what step 7 uses), "updates" gives one entry per finished node, and "values" gives the full state after each step. With a checkpointer (step 10), the state is saved after each step under your thread_id. The next invoke on the same thread starts from the saved messages and appends your new HumanMessage. That's all short-term memory is.

The recursion limit: how the loop is stopped

Nothing in the loop itself guarantees it ends. A confused model could call tools forever. LangGraph protects you with a recursion limit: the maximum number of steps (one step is one round of nodes running, such as one model or one tools execution) in a single run. When the limit is reached before END, LangGraph raises GraphRecursionError.

The value has changed across versions, so check rather than trust a tutorial. Here is what the installed versions do:

  • create_agent attaches {"recursion_limit": 9_999} to the graph it returns (in factory.py, with a comment linking a LangGraph issue). agent.config shows it.
  • LangGraph 1.2.9's own default for graphs is 10007, and can be changed with the LANGGRAPH_DEFAULT_RECURSION_LIMIT environment variable. Older LangGraph versions used 25, which is the number many older articles mention.

So with the project's versions, a runaway agent can make thousands of model calls before it's stopped. Every call costs money. For anything beyond experiments, set your own limit per call in the config:

from langgraph.errors import GraphRecursionError

try:
    response = agent.invoke(
        {"messages": [message]},
        {"recursion_limit": 10},     # at most 10 steps: about 4 search rounds + the answer
    )
except GraphRecursionError:
    print("The chef took too many steps. Try a clearer photo or question.")

Each tool round uses two steps (model, then tools), plus one for the final model call. The config dict is the same one that carries configurable.thread_id, so with memory you'd pass {"configurable": {"thread_id": "1"}, "recursion_limit": 10}.

The same loop, written by hand

Seeing the loop built from LangGraph pieces makes create_agent much less mysterious. This sketch builds a working version of the step 8 agent. It's not how you should build agents normally, because create_agent adds structured output, middleware, error handling and more. But it shows that there is no magic:

from langgraph.graph import StateGraph, MessagesState, START
from langgraph.prebuilt import ToolNode, tools_condition
from langchain.chat_models import init_chat_model

model = init_chat_model("openai:gpt-5-nano").bind_tools([print_document])

def call_model(state: MessagesState):
    return {"messages": [model.invoke(state["messages"])]}   # add_messages appends it

builder = StateGraph(MessagesState)
builder.add_node("model", call_model)
builder.add_node("tools", ToolNode([print_document]))
builder.add_edge(START, "model")
builder.add_conditional_edges("model", tools_condition)   # tool_calls → "tools", else END
builder.add_edge("tools", "model")
graph = builder.compile()

graph.invoke({"messages": [HumanMessage("Hello I am a student and my name is Luca")]})

bind_tools attaches the tool schemas to every request so the model knows the tools exist. tools_condition is LangGraph's ready-made version of the conditional edge. MessagesState is a state with just a messages key using add_messages. This is the level where LangGraph shines: you can add your own nodes (a "check the photo" step, a human approval step), branches and loops.

When not to use an agent

Agents are flexible because the model decides the steps. That same flexibility makes them less predictable, slower and more expensive than code that follows fixed steps. A workflow is a sequence you define in code. It may still call models, but you decide the order.

Workflow (fixed steps)Agent (model decides)
Control flowYour codeThe model, within limits
PredictabilityHigh: same steps every timeLower: steps vary per input
Cost and latencyKnown in advanceVaries with the number of tool rounds
DebuggingLike ordinary codeRead the message trace (chapter 8)
Good forKnown procedures: "extract, then search, then format"Open-ended tasks where the path depends on what is found

The chef could be written either way. As a workflow: one vision call that returns the ingredient list, one Tavily search built from that list in code, and one final call that writes the recipe. That's exactly three calls, always. As an agent (the video's choice), the model may search zero, one or several times. For a learning project, and for tasks where you can't predict the steps, the agent is great. When the steps are always the same, a workflow is usually the better engineering choice. Many real apps mix both: a fixed workflow with an agent inside one step.

LangChain versus LangGraph

The two names appear together everywhere, and the course imports from both (from langchain.agents import create_agent, from langgraph.checkpoint.memory import InMemorySaver). They are layers of one stack from the same company:

  • LangChain (langchain plus langchain-core and provider packages) gives you the building blocks: a standard chat model interface, messages, tools, and ready-made agents through create_agent. Start here.
  • LangGraph is the lower-level runtime for stateful, multi-step programs: graphs of nodes, state with reducers, checkpointing, interrupts for human approval, streaming. Every LangChain agent runs on it. Reach for it directly when create_agent isn't flexible enough, for example for custom workflows or multi-agent systems.

You don't have to choose one. Most projects start with create_agent and only drop to raw LangGraph for the parts that need it.

Common mistakes
  • AttributeError: 'function' object has no attribute 'invoke': calling create_agent.invoke(...) instead of agent.invoke(...) (70:11). create_agent is the factory; the graph it returns is what you invoke.
  • Expecting the agent to "just know" to stop. It stops when the model replies without tool calls, or at the recursion limit. Set a sensible limit.
  • Reading response["messages"][0] for the answer. Index 0 is your own message; the answer is [-1].
  • Building a new agent inside a loop for every question. Build it once and invoke it many times; with memory, reuse the same thread_id.
  • Using an agent for a fixed procedure, then fighting the model to follow the steps. Write the steps in code.
Common misconceptions
  • "The agent is a smarter model." It's the same model called in a loop, with tools.
  • "The model executes the tools." The graph's tools node runs them in your Python process.
  • "The recursion limit is 25." That was LangGraph's old default. With these versions, create_agent sets 9,999.
  • "LangGraph replaces LangChain." LangChain's agents are built on LangGraph; they work together.
Recap
  • An agent is a model in a loop: model → tools → model … until a reply without tool calls.
  • create_agent compiles a LangGraph graph: START → model, a conditional edge to tools or END, and tools → model. Without tools it's just START → model → END.
  • State is AgentState; messages uses the add_messages reducer, so each node's new messages are appended.
  • stream_mode: "messages" for tokens, "updates" per node, "values" for full state.
  • Each node execution is one step. create_agent sets recursion_limit 9,999 in these versions. Pass a smaller one in the config and catch GraphRecursionError.
  • Prefer a fixed workflow when the steps never change. Use an agent when the path depends on the results.
  • LangChain gives high-level building blocks; LangGraph is the runtime beneath them.
