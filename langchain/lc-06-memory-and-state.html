Memory, State & Checkpointers

Short-term vs long-term memory, threads, persistent checkpointers and trimming long conversations.

In step 10 the agent forgot your favourite colour, then remembered it after two small changes: an InMemorySaver and a thread_id. This chapter explains what really happened there. You will learn why a model has no memory of its own, what LangChain means by state, how checkpointers and threads work, the difference between short-term and long-term memory, how to keep memory after the program exits, and how to stop a long conversation from becoming slow and expensive.

Why this matters for your project. The chef from steps 12–15 answers one photo and stops. As soon as you want follow-up questions ("can I make it without eggs?"), as in step 18, you need memory. And as soon as several people use the chef, you need one conversation per person, memory that survives a restart, and a plan for conversations that grow too long.

Why an agent forgets

A chat model is stateless: every request is answered only from the text inside that request. When you call agent.invoke(...) twice, the second call knows nothing about the first unless your code sends the earlier messages again. The model on OpenAI's servers does not keep a notebook about you.

The video shows two ways to give the model the past:

  • By hand (step 6): you build a list with a HumanMessage, an AIMessage and another HumanMessage, and send the whole list. It works, but your code must store and resend everything.
  • With a checkpointer (step 10): LangChain saves the conversation after every step and loads it again on the next call with the same thread id. You only send the new message.

The verified behaviour from the offline harness: without a checkpointer the second call reaches the model with 1 message, so it cannot know the colour. With a checkpointer it reaches the model with 3 messages (Human, AI, Human), so it can.

New to "stateless"? What it means and why APIs work this way

A stateless service treats every request as brand new. It is the normal design for web APIs: any of thousands of servers can answer your request because none of them needs to remember you. The price is that the client (your Python program) must send everything the server needs each time. For a chat model, "everything" is the list of messages so far, which all count towards the model's context window.

State: what the agent actually carries

An agent built with create_agent is a LangGraph graph (see chapter 4). As it runs, it passes a Python dictionary called the state from node to node. In LangChain 1.3.12 the default state (AgentState) has these keys:

KeyWhat it holdsWhere you saw it
messagesThe list of every message in the conversation: human, AI, tool. New messages are appended, not replaced.response["messages"][-1].content in every lesson
structured_responseThe typed object when you use response_format (chapter 7).response["structured_response"] in step 17

The "appended, not replaced" part is the important detail. When the checkpointer loads a thread and you invoke with {"messages": [HumanMessage(...)]}, your new message is added to the saved list. That is why the lesson code only sends the new question.

Checkpointers and checkpoints

A checkpointer is an object that saves a snapshot of the state, called a checkpoint, after every step of the graph, and loads the latest snapshot when the same thread is used again. Here is the lesson code from step 10 (transcribed from the video):

agent = create_agent(model="gpt-5-nano",
                     checkpointer=InMemorySaver())

config = {"configurable":{"thread_id":"1"}}

response = agent.invoke(
    {"messages": [HumanMessage(content="My favorite color is green")]},
    config
)

Three things work together: the checkpointer passed to create_agent, a config dictionary whose "configurable" key holds a thread_id, and passing that config as the second argument of every invoke (or stream) call.

You can look at the saved state yourself with agent.get_state(config). This was checked against LangGraph 1.2.9 with a fake model:

snapshot = agent.get_state(config)
for message in snapshot.values["messages"]:
    print(message.type, "|", message.content)

After the two calls of step 10 this prints four lines: human, ai, human, ai. It is the quickest way to answer "what does the agent remember right now?".

The error you get when you forget the config. With a checkpointer but no config, the call fails with: 
ValueError: Checkpointer requires one or more of the following 'configurable' keys: thread_id, checkpoint_ns, checkpoint_id
The fix is to pass config to every call: agent.invoke({...}, config). A second common slip is a typo in the keys, such as "configurables" or "threadid". The value of thread_id can be any string; "1" and "kitchen-1" both work.

Threads: one conversation per thread id

A thread is one separate conversation inside the same checkpointer. The thread_id is its name. Two calls with the same id share history; two calls with different ids are strangers. In step 18 the chat chef uses one fixed thread:

config = {"configurable": {"thread_id": "kitchen-1"}}

That is fine for a program one person runs in a terminal. In an app with many users, give each user (or each chat window) its own id, for example built from a user id you already have. Never let two people share a thread: one person would see the other's messages, photos and preferences.

def config_for(user_id: str, chat_number: int) -> dict:
    """Build a config so every user and chat gets its own thread."""
    return {"configurable": {"thread_id": f"user-{user_id}-chat-{chat_number}"}}

agent.invoke({"messages": [HumanMessage("Any ideas for dinner?")]}, config_for("alice", 1))

This uses an f-string to build the id. The user_id must come from something you trust, such as your login system, never from text the user typed into the chat.

Short-term memory vs long-term memory

LangChain's documentation separates two kinds of memory. They solve different problems and use different objects:

Short-term memoryLong-term memory
ScopeOne thread (one conversation)Across threads: every conversation of a user, or the whole app
What is storedThe agent's state, mainly the messages listFacts you choose to keep: "Alice is vegetarian", "Bob has no oven"
ObjectA checkpointer: create_agent(..., checkpointer=...)A store: create_agent(..., store=...)
Saved whenAutomatically, after every stepOnly when your code (often a tool) writes to it
Example in this guideSteps 10 and 18Not in the video; covered below as a next step

A tiny long-term memory example

LangGraph ships InMemoryStore (in langgraph.store.memory). Values are dictionaries saved under a namespace (a tuple, like a folder path) and a key. A tool can read the store through a special runtime argument of type ToolRuntime; LangChain fills it in and hides it from the model, so the model only sees user_id. The snippet below was run against LangChain 1.3.12 with a fake model:

from langchain.agents import create_agent
from langchain.tools import tool, ToolRuntime
from langgraph.store.memory import InMemoryStore

store = InMemoryStore()
store.put(("users", "alice"), "preferences", {"diet": "vegetarian"})

@tool
def get_diet(user_id: str, runtime: ToolRuntime) -> str:
    """Look up the user's saved diet preferences."""
    item = runtime.store.get(("users", user_id), "preferences")
    return str(item.value) if item else "No preferences saved."

agent = create_agent(model="gpt-5-nano", tools=[get_diet], store=store)

Like InMemorySaver, InMemoryStore lives in RAM and is lost when the program exits. LangGraph also offers database-backed stores; see the long-term memory page in "Learn more". In a real app, do not let the model choose whose data it reads: take the user id from your own code (for example from the config or a context object) rather than from a tool argument the model fills in. The example keeps it simple on purpose.

Keeping memory after the program exits

InMemorySaver stores checkpoints in a Python dictionary in RAM. That is perfect for learning and tests, but when python main.py finishes, the memory is gone (verified finding: InMemorySaver loses everything when the program exits). For memory that survives restarts, use a checkpointer that writes to a file or a database. At the time of writing, the LangGraph team publishes these as separate packages on PyPI:

Package (install with uv)ClassWhere data livesGood for
built in (langgraph)InMemorySaverRAM of your Python processLearning, tests, one-off scripts
langgraph-checkpoint-sqliteSqliteSaverA single file on diskLocal apps, prototypes, one machine
langgraph-checkpoint-postgresPostgresSaverA PostgreSQL database serverWeb apps with many users and several servers

These packages are not installed in the chef project, so the snippet below was not run in this guide's harness. It follows the pattern in the LangGraph persistence docs; check the current docs before using it:

uv add langgraph-checkpoint-sqlite
from langgraph.checkpoint.sqlite import SqliteSaver

with SqliteSaver.from_conn_string("chef_memory.sqlite") as checkpointer:
    agent = create_agent(model="gpt-5-nano",
                         tools=[web_search],
                         system_prompt=SYSTEM_CHEF_PROMPT,
                         checkpointer=checkpointer)
    config = {"configurable": {"thread_id": "kitchen-1"}}
    agent.invoke({"messages": [HumanMessage("What did we cook last time?")]}, config)

from_conn_string opens a connection and is used with with, so the file is closed properly when the block ends. Run the script twice: the second run can see the first run's messages, because they are in chef_memory.sqlite. Add that file to your .gitignore: it contains everything users said, including photos turned into base64.

Growing history means growing cost

Memory has a price. With a checkpointer, every new question sends the whole thread to the model: all earlier questions, answers, tool results and images. Providers charge per token of input and output, and each model has a maximum context window. So in a long chat:

  • each turn costs more than the one before, because the input keeps growing;
  • answers get slower, because the model must read more text first;
  • eventually the history no longer fits in the context window and the request fails;
  • the model can lose track of what matters, because the important bit is buried in old text.

Tool results make this worse. A single Tavily search result in the chef project is a dictionary with several web pages' titles, URLs and text snippets; it is saved in the thread as a ToolMessage and resent on every later turn. The photo is saved too, as a long base64 string.

Trimming and summarising long conversations

There are three common ways to keep a thread under control. They trade detail for size:

TechniqueHow it worksProsCons
TrimSend only the most recent messages that fit a token budget (plus the system message).Simple, cheap, predictableOld details are simply not seen
SummariseAsk a model to write a short summary of old messages, then keep the summary plus recent messages.Keeps the gist of the whole conversationAn extra model call; summaries can drop or distort details
DeleteRemove specific messages from the saved state (for example big tool results you no longer need).PreciseYou must decide what is safe to remove

Trimming with trim_messages

trim_messages is exported from langchain.messages in LangChain 1.3.12. You give it a list of messages and a budget; it returns a shorter list. This snippet was run in the harness:

from langchain.messages import trim_messages
from langchain_core.messages.utils import count_tokens_approximately

recent = trim_messages(
    messages,
    strategy="last",
    token_counter=count_tokens_approximately,
    max_tokens=2000,
    include_system=True,
    start_on="human",
)
Line(s)CodeWhat it does & why
1from langchain.messages import trim_messagesImports the trimming helper from the same module that gives you HumanMessage.
2from langchain_core.messages.utils import count_tokens_approximatelyA quick token estimate that needs no network call. Exact counts depend on the model's tokenizer; an estimate is enough for a budget.
4–5recent = trim_messages(messages,Takes your full list and returns a new, shorter list. The original list is not changed.
6strategy="last",Keep the newest messages, which are usually the most relevant.
7token_counter=count_tokens_approximately,How to measure each message.
8max_tokens=2000,The budget. Pick it well below the model's context window to leave room for the answer.
9include_system=True,Always keep the system message; without it the chef forgets it is a chef.
10start_on="human",Make the kept part start with a human message, so it never begins with a lonely AI answer or a ToolMessage whose tool call was cut off (providers reject that).

trim_messages works on any list you send to a model yourself, as in step 6. With create_agent, the agent builds the model input for you, so the clean place to trim or summarise is a middleware, which runs just before each model call.

Summarising with SummarizationMiddleware

LangChain 1.3.12 ships a ready-made middleware for this. Its constructor takes a model to write the summaries, a trigger (when to summarise) and keep (how much recent history to leave untouched). The construction below was checked against the installed package; the token number is an arbitrary example:

from langchain.agents import create_agent
from langchain.agents.middleware import SummarizationMiddleware
from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(
    model="gpt-5-nano",
    tools=[web_search],
    system_prompt=SYSTEM_CHEF_PROMPT,
    checkpointer=InMemorySaver(),
    middleware=[
        SummarizationMiddleware(
            model="gpt-5-nano",
            trigger=("tokens", 4000),
            keep=("messages", 20),
        )
    ],
)

Read it as: "when the thread passes about 4,000 tokens, summarise everything except the last 20 messages". Middleware is introduced properly in chapter 10; the video lists "managing long conversations" as an advanced topic for a later part of the series.

Common misconceptions
  • "The model remembers me." It does not. Your program resends the history every time; LangChain just automates it.
  • "A checkpointer makes the chef remember yesterday." Only if it writes to disk or a database. InMemorySaver forgets on exit.
  • "More memory is always better." Every remembered message is resent and paid for. Long, noisy history can make answers worse, not better.
  • "thread_id is a security feature." It is just a label. If a user can choose any thread id, they may read someone else's chat. Build it from a trusted user id.
  • "Memory and RAG are the same thing." Memory is about this user's past conversation and facts; retrieval (RAG) is about searching documents. Agents often use both.
Recap
  • Chat models are stateless; memory means resending the right earlier messages.
  • The agent's state is a dictionary; messages is appended to after every step.
  • A checkpointer saves a checkpoint after every step; the thread_id in {"configurable": {"thread_id": ...}} picks the conversation. Forgetting the config raises a ValueError.
  • One thread per user and chat; build the id from trusted data.
  • Short-term memory = checkpointer (per thread); long-term memory = store (across threads).
  • InMemorySaver is RAM-only; langgraph-checkpoint-sqlite and langgraph-checkpoint-postgres persist.
  • Long threads cost more and eventually overflow the context window: trim (trim_messages), summarise (SummarizationMiddleware) or delete.
