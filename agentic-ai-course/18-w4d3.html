Super-steps (lecture 8)

From the docs, on the slide: "A super-step can be considered a single iteration over the graph nodes. Nodes that run in parallel are part of the same super-step, while nodes that run sequentially belong to separate super-steps." The presenter's version is simpler: "Every time you invoke the graph, that is a super-step." Don't imagine the human as a node; each message from the user is a new invocation.

The key consequence: "The reducer… applies during carrying out a single super step… But the reducer doesn't handle the separate super steps. A separate super step is an entirely fresh invocation." That is why yesterday's chatbot forgot your name. A checkpointer "freezes a record of the state after each super step" so the next one can pick it up.

Each run then appears as a row with input, output, latency, tokens and cost: "fractions of fractions of a cent".

The search tool is LangChain's GoogleSerperAPIWrapper, "a nice little convenient wrapper around the same thing that we set up before", using SERPER_API_KEY. LangChain's Tool turns any function into a tool: a name, the function, and a description, "this is going to take away all of the gumph about building that JSON object". The custom push tool is "super easy": Week 1's Pushover function, wrapped the same way.

/** Google search through serper.dev (Python: GoogleSerperAPIWrapper().run). Without SERPER_API_KEY it returns
 *  canned text that is clearly labelled as a stand-in, so the labs still run end to end. */
export async function serperRun(query: string): Promise<string> {
  const key = process.env.SERPER_API_KEY;
  console.log(`[search] ${query}${key ? "" : " (stand-in: no SERPER_API_KEY)"}`);
  if (!key) {
    return `Search results (canned offline stand-in, not a real search) for "${query}": ` +
      "1. Paris is the capital and largest city of France. 2. The euro (EUR) is the currency of France. " +
      "3. Exchange rates change every day; check a live source such as xe.com.";
  }
  const res = await fetch("https://google.serper.dev/search", {
    method: "POST",
    headers: { "X-API-KEY": key, "Content-Type": "application/json" },
    body: JSON.stringify({ q: query }),
  });
  const data = (await res.json()) as { answerBox?: { answer?: string; snippet?: string }; organic?: { title: string; snippet: string }[] };
  // like the Python wrapper: the answer box if there is one, otherwise the snippets of the organic results
  if (data.answerBox?.answer || data.answerBox?.snippet) return (data.answerBox.answer ?? data.answerBox.snippet)!;
  return (data.organic ?? []).slice(0, 8).map((r) => `${r.title}: ${r.snippet}`).join(" ");
}

/** Send a push notification to the user (Pushover). Without the keys the message is printed instead. */
export async function push(text: string): Promise<string> {
  const token = process.env.PUSHOVER_TOKEN, user = process.env.PUSHOVER_USER;
  if (!token || !user) {
    console.log(`[push not sent: no PUSHOVER_TOKEN/PUSHOVER_USER] ${text}`);
    return "success (printed, Pushover keys not set)";
  }
  await fetch("https://api.pushover.net/1/messages.json", { method: "POST", body: new URLSearchParams({ token, user, message: text }) });
  return "success"; // Day 5's push returns "success"; the Day 3 version returned None and LangSmith showed null
}

Tool calling in a graph (lecture 10)

Tools touch your code in two places. When calling the model, you must send the tools' JSON; when it answers, you check whether it asked for a tool, run it, and send the result back: "the quite long-winded handle_tool_call method in the first week". LangGraph covers both.

  • llm.bind_tools(tools) returns a model that always sends the tool definitions: "some nice sort of magic… it's sort of hiding from us some of the implementation… which can make it hard to debug."
  • ToolNode is "a canned node that when it's invoked is going to see whether any of the message is asking to call one of the tools… and if so, it will run them."
  • tools_condition is a ready-made conditional edge: tool calls go to "tools", anything else ends the run. "When I used to say that tool calling is just an if statement: this is the if statement."

The State switches from BaseModel to TypedDict ("you can stick with Pydantic if you'd prefer"), so nodes read state["messages"] and return a plain dict.

# Step 4: Create Edges


graph_builder.add_conditional_edges( "chatbot", tools_condition, "tools")

# Any time a tool is called, we return to the chatbot to decide the next step
graph_builder.add_edge("tools", "chatbot")
graph_builder.add_edge(START, "chatbot")
// Steps 2–5 in one function, because we build the same graph three times with a different checkpointer
function buildGraph(checkpointer?: BaseCheckpointSaver) {
  return new StateGraph(State)
    .addNode("chatbot", chatbot)
    .addNode("tools", new ToolNode(tools)) // runs whichever tools the last AI message asked for
    // toolsCondition looks at the last message: tool calls → "tools", otherwise → END
    .addConditionalEdges("chatbot", toolsCondition, ["tools", END])
    // Any time a tool is called, we return to the chatbot to decide the next step
    .addEdge("tools", "chatbot")
    .addEdge(START, "chatbot")
    .compile({ checkpointer });
}

Memory with a checkpointer (lecture 11)

The same name test still fails: "it's all down to super steps." The fix is one object and one argument. MemorySaver "doesn't mean like saving memories. It's talking about saving to in-memory stores… rather than to disk". Then each invoke gets a config with a thread ID, "a bit hacky, a bit hokey"; "thread ID doesn't mean like a technical thread, it's meant to be like a conversation thread."

from langgraph.checkpoint.memory import MemorySaver

memory = MemorySaver()

Cell 26 rebuilds the same graph (with a print(state) in the chatbot) and compiles it with graph_builder.compile(checkpointer=memory).

config = {"configurable": {"thread_id": "1"}}

def chat(user_input: str, history):
    result = graph.invoke({"messages": [{"role": "user", "content": user_input}]}, config=config)
    return result["messages"][-1].content

// OK it's time to add Memory! The reducer combines updates *within* one invoke; a checkpointer saves the state
// after every step, keyed by thread_id, so the next invoke on the same thread starts where the last one ended.
console.log("\n--- MemorySaver, thread 1");
const memory = new MemorySaver();
graph = buildGraph(memory);

# Most recent first

Now "what's my name?" gets "Your name is Ed." And "what's the big deal?" over keeping a list yourself: get_state returns the current snapshot, get_state_history every snapshot (most recent first), and adding a checkpoint_id to the config lets you "rewind to a previous moment and then replay that through the graph". That is time travel: "If something falls over, you can restart it from any snapshot."

config = {"configurable": {"thread_id": "1", "checkpoint_id": ...}}
graph.invoke(None, config=config)

Experiments in the video: relaunching the chat window still remembers; a new MemorySaver() forgets; thread "2" is a separate conversation; back on thread "1" it remembers again.

Memory in SQLite (lecture 12)

"It's just different name of a variable, but exactly the same approach." After a full kernel restart, the rebuilt graph greets him with "Hello again, Ed!": persistent memory "with changing like one word". Asked to resend the push notification, the trace shows only the push tool: it "didn't bother doing the search again because it had that in its memory."

import sqlite3
from langgraph.checkpoint.sqlite import SqliteSaver

db_path = "memory.db"
conn = sqlite3.connect(db_path, check_same_thread=False)
sql_memory = SqliteSaver(conn)
// And now let's store in SQL — the state survives a restart of the program
console.log("\n--- SqliteSaver, thread 3 (memory.db)");
const sql_memory = SqliteSaver.fromConnString("memory.db"); // Python: SqliteSaver(sqlite3.connect("memory.db"))
graph = buildGraph(sql_memory);
const sqlConfig = { configurable: { thread_id: "3" } };
console.log(await chat("hi there, my name is Ed", sqlConfig));
// a brand-new saver on the same file, as if the program had been restarted
graph = buildGraph(SqliteSaver.fromConnString("memory.db"));
console.log(await chat("What's my name?", sqlConfig), "  <- read back from memory.db");

Cells 33–34 repeat the graph with compile(checkpointer=sql_memory) and the chat on thread "3": "since it's SQL it kind of remembers from my tests".

Line 80 builds a brand-new saver on the same file, standing in for the kernel restart: the answer comes back from memory.db. The package is @langchain/langgraph-checkpoint-sqlite.

Video vs repo. On screen the lab 2 chat function was first called invoke_graph and renamed to chat. The repo already contains memory.db (with its -shm and -wal files) from the author's runs, so an old thread ID may "remember" things you never said.

Common mistakes

  • Forgetting the edge from tools back to the chatbot: the tool runs and its result is never used.
  • No config on invoke: with a checkpointer, every call needs a thread_id.
  • Reusing a thread ID by accident: old memories, especially in memory.db, leak into new tests.
  • Adding LangSmith keys after load_dotenv: run it again, as the presenter did ("maybe I should have done that in the other order").
  • Expecting the reducer to give memory: it only merges within one super-step.
Recap
  • One user turn is one super-step; reducers work inside it, checkpointers carry state between them.
  • Tool(name, func, description) (TypeScript: DynamicTool) wraps a function; bind_tools sends the schemas.
  • ToolNode runs requested tools; tools_condition is the if statement; an edge must lead back to the chatbot.
  • compile(checkpointer=MemorySaver()) plus a thread_id gives memory; SqliteSaver makes it survive restarts.
  • LangSmith traces every node, model call and tool call from environment variables alone.
