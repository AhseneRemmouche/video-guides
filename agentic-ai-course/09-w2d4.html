What this day builds

"One of the classic cross-business agentic use cases": a deep-research agent like the button in ChatGPT. Given a question, it plans a handful of web searches, runs them all at once, writes a long markdown report and emails it. The ingredients are all from earlier in the week plus one new one: a hosted tool, OpenAI's WebSearchTool, which runs on OpenAI's servers. Day 4 stays in a notebook (4_lab4.ipynb); Day 5 turns it into modules and an app.

TypeScript: the four agents live in src/deep_research/agents.ts, the pipeline in src/deep_research/manager.ts, and pnpm lab4 "your query" runs it in the console. Those are the same files Day 5 reuses for the React app, so the TypeScript side is already "modules" today.

Hosted tools and what they cost (lecture 15, 02:32–04:45)

So far every tool ran on your machine. OpenAI also offers tools that run on their side: WebSearchTool (search the web), FileSearchTool (search your uploaded vector stores) and ComputerTool (screenshots and clicks). Only the first is used; a locally run "computer tool" comes later in the course. The presenter's warning: web search "is not that cheap for some reason": 2.5 cents per call with GPT-4o-mini at the lowest setting. Ten searches per research is 25 cents, "which means that you can quite quickly add up to $2–$3", which is what his first attempt cost. Hence three searches by default, and a pricing link to check because "OpenAI might change the pricing all the time".

No OpenAI key? Hosted tools exist only on OpenAI's API, so this guide's local runs replaced WebSearchTool with a function tool that returns canned text (the TypeScript file does the same in local mode, lines 16–32 below). Everything else in the pipeline is real: structured outputs, parallel runs, the writer and the email agent. Expect a report about canned content.

Agent 1: the search agent (lecture 15, 04:45–08:39)

The instructions are lifted "verbatim from OpenAI's documentation", so "we can probably take it on good authority that this is a well written prompt": summarise results in 2–3 paragraphs under 300 words, succinctly, no fluff, for someone else to synthesise. Two settings matter. search_context_size="low" keeps the cost down (medium is the default, high "quite a lot more"). ModelSettings(tool_choice="required") is "a nice handy thing to have to one side": it makes the tool call mandatory, so the agent cannot answer from memory. The first search for "Latest AI Agent frameworks in 2025" came back listing LangChain, LangGraph, CrewAI, Semantic Kernel, AutoGen, then "OpenAI Gym, that's a reinforcement learning framework", Rasa and JADE: "mixed accuracy". The trace shows the tool used was web_search with token counts.

Agent 2: the planner, with structured outputs (lecture 16)

The planner takes a query and returns "a handful of searches that it should run". HOW_MANY_SEARCHES = 3 is a cost decision: "run it with three to start with, see your cost: 10 cents, 20 cents, and if you're enjoying yourself then splash out". The schema has two Pydantic classes. WebSearchItem has a reason and a query; WebSearchPlan has one field, searches, a list of items. New today: each field carries a description with Field(description=...) (the video writes it as a docstring under the field). "By annotating these fields with this comment, we ensure that that information is actually provided to the model, so it knows why it's populating these fields." And why ask for a reason at all, and first? Because "by asking the model to output its rationale first, you encourage the model to be thinking through… you get better queries as a side effect", which is "chain of thought prompting": next-token prediction makes the query consistent with the reason that precedes it (02:58–03:55).

# With massive thanks to student Wes C. for discovering and fixing a nasty bug with this!

class WebSearchItem(BaseModel):
    reason: str = Field(description="Your reasoning for why this search is important to the query.")

    query: str = Field(description="The search term to use for the web search.")


class WebSearchPlan(BaseModel):
    searches: list[WebSearchItem] = Field(description="A list of web searches to perform to best answer the query.")

Five small functions, then showtime (lecture 17, 04:06–10:18)

"We have five functions… they're pretty straightforward." plan_searches runs the planner. perform_searches creates one asyncio task per planned item and gathers them: "perfect time for" the parallelism from Day 1. search builds the input for the search agent from both the query and the reason ("there's more than one reason why we asked for a reason: it's also so we can give some context here"). write_report and send_email run the last two agents. The final cell the presenter types himself, fighting Cursor's autocomplete ("sometimes Cursor is too good"): start, plan, search, write, email, "Hooray!".

async def plan_searches(query: str):
    """ Use the planner_agent to plan which searches to run for the query """
    print("Planning searches...")
    result = await Runner.run(planner_agent, f"Query: {query}")
    print(f"Will perform {len(result.final_output.searches)} searches")
    return result.final_output

async def perform_searches(search_plan: WebSearchPlan):
    """ Call search() for each item in the search plan """
    print("Searching...")
    tasks = [asyncio.create_task(search(item)) for item in search_plan.searches]
    results = await asyncio.gather(*tasks)
    print("Finished searching")
    return results

async def search(item: WebSearchItem):
    """ Use the search agent to run a web search for each item in the search plan """
    input = f"Search term: {item.query}\nReason for searching: {item.reason}"
    result = await Runner.run(search_agent, input)
    return result.final_output
  /** Plan the searches to perform for the query */
  async planSearches(query: string): Promise<WebSearchPlan> {
    console.log("Planning searches...");
    const result = await run(plannerAgent, `Query: ${query}`);
    const plan = result.finalOutput!;
    console.log(`Will perform ${plan.searches.length} searches`);
    return plan;
  }

  /** Perform the searches for the plan, in parallel; report progress as each one completes */
  async performSearches(plan: WebSearchPlan): Promise<string[]> {
    console.log("Searching...");
    let numCompleted = 0;
    const tasks = plan.searches.map((item) =>
      this.search(item).then((r) => {
        numCompleted += 1;
        console.log(`Searching... ${numCompleted}/${plan.searches.length} completed`);
        return r;
      }),
    );
    const results = (await Promise.all(tasks)).filter((r): r is string => r !== null);
    console.log("Finished searching");
    return results;
  }

New to asyncio.create_task? Tasks versus plain coroutines

search(item) alone is a coroutine object that does nothing until awaited. asyncio.create_task(search(item)) hands it to the event loop right away and returns a task, a handle you can await later, cancel, or pass to gather. Creating all tasks in a list comprehension means they all start now; await asyncio.gather(*tasks) then waits for the whole batch. The * unpacks the list because gather takes its coroutines as separate arguments. The Day 5 module uses asyncio.as_completed(tasks) instead, which yields tasks in the order they finish, so it can print "Searching... 2/3 completed" as it goes.

Common mistakes

  • The bill: every search agent run costs about 2.5 cents at "low". Keep HOW_MANY_SEARCHES small while you develop; raise it for a final run.
  • tool_choice="required" with no tools: the model is told it must call a tool but has none; give the agent its tool list.
  • The search agent answers from memory: you left tool_choice at its default; the model may skip the search.
  • AttributeError: 'str' object has no attribute 'searches': the planner has no output_type, so final_output is text.
  • Schema errors from OpenAI's structured outputs: optional fields and some types are not allowed in strict mode; keep schemas simple (strings, booleans, lists of models).
  • The email never comes: as on Day 2: spam folder, verified sender, key in .env; the email agent's trace span shows whether send_email was called.
  • Real web search in TypeScript without OpenAI: webSearchTool() only works on OpenAI's API. In local mode replace the canned localSearch body with a call to a search API of your choice.

Recap
  • Hosted tools run on OpenAI's servers: WebSearchTool(search_context_size="low"); they cost per call and only work on OpenAI's API.
  • ModelSettings(tool_choice="required") forces the tool call.
  • Structured outputs with described fields: Field(description=...) / .describe() tells the model what each field means; asking for a reason before the query improves the queries.
  • The pipeline is four agents and five small async functions; create_task + gather (or map + Promise.all) runs the searches concurrently.
  • The whole run sits in one trace, which shows what ran in parallel and what did not.
