State is immutable, and reducers merge it (lecture 4)

"You will never change the contents of this object… you don't ever do what's called mutating it." The state is a snapshot you may want to return to, so a node receives one state and returns "a different instance of state than the one that came in". The slide's (admittedly "quite artificial") example:

def my_counting_node(old_state: State) -> State:
    count = old_state.count
    count += 1
    new_state = State(count=count)
    return new_state

(The slide writes the parameter as State: old_state, type and name swapped; the notebook gets it right.)

Then the reducer: "For each field in your State, you can specify a special function called a reducer. When you return a new State, LangGraph uses the reducer to combine this field with existing State." Why not just overwrite the field? Because "the graph can run multiple nodes at the same time… there's no risk that one node runs and it overwrites the progress that a different node made at the same time."

Annotated, and the State class (lecture 5)

load_dotenv(override=True) is back: "Crew was doing this for us, by the way." Then a detour through Python's Annotated, live-coded with shout. It adds "extra information… Python doesn't make any use of this at all", but another library can read it, and "LangGraph is going to want us to annotate, in order to tell it something": which reducer to use.

def shout(text: Annotated[str, "something to be shouted"]) -> str:
    print(text.upper())
    return text.upper()

shout("hello")

// TypeScript has no Annotated; a doc comment plays that role for people, and Annotation(...) plays it for LangGraph.

  console.log(text.toUpperCase());
  return text.toUpperCase();
}
shout("hello");

TypeScript has no Annotated. A doc comment carries the note for people, and LangGraph gets its reducer through Annotation(...) below. Lines 22–25 call the reducer directly, so you can see it append rather than replace:

// The reducer idea: a reducer is the function LangGraph calls to combine the old value of a field with a node's new value.
// messagesStateReducer (also exported as addMessages, Python's add_messages) appends messages instead of replacing them.
const combined = messagesStateReducer([new HumanMessage("hi")], [new AIMessage("hello there")]);
console.log("reducer result:", combined.map((m) => `${m.getType()}: ${m.content}`));

Step 1, the State. "You can use any python object; but it's most common to use a TypedDict or a Pydantic BaseModel." The course uses BaseModel today. add_messages is the reducer "LangGraph comes with… out of the box": "It assumes this is a list. And if you return something with items in the list, it just combines it with everything else in the list before it."


class State(BaseModel):
        
    messages: Annotated[list, add_messages]
// Step 1: Define the State object
const State = Annotation.Root({
  // <stored type, type a node may return>; reducer = how updates are merged; default = the starting value
  messages: Annotation<BaseMessage[], BaseMessageLike[]>({ reducer: messagesStateReducer, default: () => [] }),
});
CodeWhat it does & why
class State(BaseModel): messages: Annotated[list, add_messages]Python: one field, a list, with add_messages as its reducer.

The two types are what is stored and what a node may return; messagesStateReducer is the JavaScript name of add_messages; default is the starting value.

A node, edges, compile (lecture 6)

Step 3, a node: a function that takes the old state and returns a new one. Here the old state is not even used, "which is unusual, but just for this example".

def our_first_node(old_state: State) -> State:

    reply = f"{random.choice(nouns)} are {random.choice(adjectives)}"
    messages = [{"role": "assistant", "content": reply}]

    new_state = State(messages=messages)

    return new_state

graph_builder.add_node("first_node", our_first_node)
// Step 2: Start the Graph Builder with this State class
// Step 3: Create a Node — any function that takes the old state and returns an update
function our_first_node(old_state: typeof State.State): typeof State.Update {
  const reply = `${pick(nouns)} are ${pick(adjectives)}`;
  const messages = [{ role: "assistant", content: reply }];
  return { messages }; // the reducer appends this to old_state.messages
}

Then run it. invoke "is the key LangChain word invoke. Sorry I said LangChain. It's the graph word invoke." In the video every reply is nonsense: "hi there" gets "Muffins are haunted", "for real?" gets "Pickles are untrustworthy". The printed result holds HumanMessage and AIMessage objects: "this is the result of the reducer running… it also does some of this packaging up."

def chat(user_input: str, history):
    message = {"role": "user", "content": user_input}
    messages = [message]
    state = State(messages=messages)
    result = graph.invoke(state)
    print(result)
    return result["messages"][-1].content


gr.ChatInterface(chat, type="messages").launch()
// That's it! Showtime! — the Gradio ChatInterface becomes a plain function we call with a few messages
async function chat(user_input: string) {
  const result = await graph.invoke({ messages: [{ role: "user", content: user_input }] });
  console.log(result.messages.map((m) => `${m.getType()}: ${m.content}`));
  return result.messages.at(-1)!.content;
}
console.log("user: hi there →", await chat("hi there"));
console.log("user: you don't say →", await chat("you don't say"));

The same five steps with an LLM (lecture 7)

ChatOpenAI is LangChain's model wrapper, "the sibling to LangGraph". "You don't need to use LangChain's LLMs for this… you could directly call the LLM yourself… But… most of the community examples go from LangGraph to LangChain."

# Step 3: Create a Node

llm = ChatOpenAI(model="gpt-4o-mini")

def chatbot_node(old_state: State) -> State:
    response = llm.invoke(old_state.messages)
    new_state = State(messages=[response])
    return new_state

graph_builder.add_node("chatbot", chatbot_node)
// Now the 5 steps again, but with an LLM in the node
const llm = makeLLM();

async function chatbot_node(old_state: typeof State.State): Promise<typeof State.Update> {
  const response = await llm.invoke(old_state.messages);
  return { messages: [response] };
}

// TypeScript gives each compiled graph its own type (it knows the node names), so the new graph gets a new name
const chatbotGraph = new StateGraph(State)
  .addNode("chatbot", chatbot_node)
  .addEdge(START, "chatbot")
  .addEdge("chatbot", END)
  .compile();
console.log(chatbotGraph.getGraph().drawMermaid());

// That's it! And, let's do this:
async function chatWithLLM(user_input: string) {
  const result = await chatbotGraph.invoke({ messages: [{ role: "user", content: user_input }] });
  return result.messages.at(-1)!.content;
}
console.log("user: hi there, my name is Ed →", await chatWithLLM("hi there, my name is Ed"));
// each invoke starts from an empty state, so the graph has no memory yet (that is Day 3's checkpointing)
console.log("user: what's my name? →", await chatWithLLM("what's my name?"));

Common mistakes

  • Mutating the state: return a new state (or an update), never edit the one you received.
  • Forgetting the reducer: without add_messages the field is replaced on every update.
  • Passing an instance to StateGraph: it takes the class (in TypeScript, the Annotation.Root object).
  • Expecting memory: each invoke is independent until a checkpointer is added on Day 3.
  • Calling invoke before compile(): the builder lays out the graph; only the compiled graph runs.
Recap
  • Nodes receive the state and return updates; the state itself is never changed in place.
  • A reducer, attached with Annotated (Python) or Annotation (TypeScript), decides how updates merge; add_messages appends.
  • Five steps: State, StateGraph(State), add_node, add_edge, compile(); then invoke.
  • A node does not need an LLM; with one, it is llm.invoke(messages).
  • No memory between invocations yet.
