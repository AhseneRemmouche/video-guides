Week 3 Day 3 · Stock picker: structured outputs and custom tools

Pydantic outputs on tasks, a custom push-notification tool, and a hierarchical crew where a manager agent delegates the work.

Course lectures (Udemy) · code verified against the repo

What this day builds

A stock picker: one agent finds companies trending in the news for a sector, another researches them, a third picks the best one, sends you a push notification and explains its choice. "Purely for our own investigatory purposes and you should not use this to make any trading decisions, please." Three ideas are new this day: structured outputs in CrewAI (a task's answer as a typed object), a custom tool you write yourself, and the hierarchical process, where a manager agent decides which agent does what. "As you'll see, we'll have a bit of an adventure with that."

TypeScript: pnpm stocks (or pnpm stocks "Healthcare") in week3-ts. The schemas become zod objects in src/stockpicker.ts, the push tool is in src/tools.ts, and the manager is runHierarchical in src/minicrew.ts.

The agents and tasks (lecture 10)

"When defining tasks the trick is to be very clear, very simple" (04:12). And a pro tip (06:23): use the same words everywhere. "In previous versions, when I was iterating on this, I had inconsistent language between agents and tasks and it definitely causes less stability." So "trending companies" appears in the agents, the tasks and the class names alike. Each task names an agent, a context and an output file; the first two files end in .json because their output will be structured.

Structured outputs in CrewAI (lecture 11)

The idea is the same as Week 2: describe the shape you want as Pydantic classes, and "by giving the fields with that name and with that description, we are going to force the agent to produce that information in its response". A wrapper class holding a list "is a way to organize it so that one task can result in a bunch of trending companies". In CrewAI the switch is one argument on the task, output_pydantic=: "this is the way that you do structured outputs in crew".

class TrendingCompany(BaseModel):
    """ A company that is in the news and attracting attention """
    name: str = Field(description="Company name")
    ticker: str = Field(description="Stock ticker symbol")
    reason: str = Field(description="Reason this company is trending in the news")

class TrendingCompanyList(BaseModel):
    """ List of multiple trending companies that are in the news """
    companies: List[TrendingCompany] = Field(description="List of companies trending in the news")

class TrendingCompanyResearch(BaseModel):
    """ Detailed research on a company """
    name: str = Field(description="Company name")
    market_position: str = Field(description="Current market position and competitive analysis")
    future_outlook: str = Field(description="Future outlook and growth prospects")
    investment_potential: str = Field(description="Investment potential and suitability for investment")

class TrendingCompanyResearchList(BaseModel):
    """ A list of detailed research on all the companies """
    research_list: List[TrendingCompanyResearch] = Field(description="Comprehensive research on all trending companies")

// Structured outputs (CrewAI's output_pydantic) become zod schemas; the crew runs hierarchically: a manager agent
// delegates every task to the three workers. Day 4's memory is a JSON file read into two agents' prompts (memory.ts).

import { consoleEvents, loadCrew, runHierarchical } from "./minicrew.js";
import { pushTool, searchTool } from "./tools.js";
import { memoryPrompt, recall, remember } from "./memory.js";

const TrendingCompany = z.object({
  name: z.string().describe("Company name"),
  ticker: z.string().describe("Stock ticker symbol"),
  reason: z.string().describe("Reason this company is trending in the news"),
});
const TrendingCompanyList = z.object({
  companies: z.array(TrendingCompany).describe("List of companies trending in the news"),
});
const TrendingCompanyResearch = z.object({
  name: z.string().describe("Company name"),
  market_position: z.string().describe("Current market position and competitive analysis"),
  future_outlook: z.string().describe("Future outlook and growth prospects"),
  investment_potential: z.string().describe("Investment potential and suitability for investment"),
});
const TrendingCompanyResearchList = z.object({
  research_list: z.array(TrendingCompanyResearch).describe("Comprehensive research on all trending companies"),
});

const inputs = { sector: process.argv[2] ?? "Technology", current_date: new Date().toISOString() };
const crew = await loadCrew("crews/stock_picker", inputs);

// Day 4: the finder and the picker remember; the researcher does not ("we want it to go and do research every time").
const MEMORY_FILE = "memory/stock_picker.json";
const past = await recall(MEMORY_FILE);
for (const name of ["trending_company_finder", "stock_picker"]) crew.agents[name]!.backstory += memoryPrompt(past);

const outputs = await runHierarchical(crew, "manager", {
  tools: { trending_company_finder: [searchTool], financial_researcher: [searchTool], stock_picker: [pushTool] },
  outputTypes: { find_trending_companies: TrendingCompanyList, research_trending_companies: TrendingCompanyResearchList },
  outputDir: "output/stock_picker",
  onEvent: consoleEvents,
});
const date = new Date().toISOString();
await remember(MEMORY_FILE, [
  { date, task: "find_trending_companies", output: outputs.find_trending_companies ?? "" },
  { date, task: "pick_best_company", output: outputs.pick_best_company ?? "" },
]);
console.log("\n\n=== FINAL DECISION ===\n\n" + outputs.pick_best_company);

The manager and the hierarchical process (lecture 11, 06:02–08:39)

Only three methods have @agent. "Did we have a fourth agent? Yes, we did, but that fourth agent is a bit different. It's the manager, and we don't want that to be in the list of the general agents." So it is built as a local variable inside crew(), with allow_delegation=True, "telling crew that we want it to be able to delegate to other agents. That would be the equivalent of the handoff in the OpenAI Agents SDK". process=Process.hierarchical "means that we are going to assign an LLM to figure out which agent does what task". You can pass a whole agent (manager_agent=) or just a model (manager_llm=); "I found it perform slightly better if I get the opportunity to describe the role of the manager. But both did work. But as you'll see, neither works perfectly. Haha. It's an adventure."

In the TypeScript runner the manager gets one tool per worker, made with Week 2's asTool; the description tells it to give full context, because a delegated agent knows nothing else.

/** Process.hierarchical: a manager agent receives every task and delegates to the workers, which are its tools. */
export async function runHierarchical(crew: Awaited<ReturnType<typeof loadCrew>>, managerName: string, opts: CrewOptions = {}) {
  const managerCfg = crew.agents[managerName];
  if (!managerCfg) throw new Error(`No manager agent ${managerName} in agents.yaml`);
  const outputs: Record<string, string> = {};
  const workers = Object.entries(crew.agents).filter(([n]) => n !== managerName);
  // CrewAI gives the manager "Delegate work to coworker" and "Ask question to coworker" tools; here each worker is
  // one tool (agent as a tool, as in Week 2).
  const coworkerTools = workers.map(([n, cfg]) =>
    makeAgent(n, cfg, opts).asTool({ toolName: n, toolDescription: `Delegate work to ${cfg.role.trim()}. Give full context: they know nothing else.` }),
  );
  const makeManager = (outputType?: z.ZodTypeAny) =>
    new Agent({
      name: managerName,
      instructions: instructionsFor(managerCfg),
      model: modelFor(managerCfg.llm),
      tools: coworkerTools,
      ...(outputType ? { outputType } : {}),
    });
  for (const [taskName, t] of Object.entries(crew.tasks)) {
    const context = (t.context ?? Object.keys(outputs)).map((n) => outputs[n] ?? "").filter(Boolean).join("\n\n----------\n\n");
    opts.onEvent?.({ type: "task_start", task: taskName, agent: managerCfg.role.trim() });
    const agent = makeManager(opts.outputTypes?.[taskName]);
    const result = await run(agent, taskPrompt(t, context), { maxTurns: 20 });
    const output = asText(result.finalOutput);
    outputs[taskName] = output;
    await saveOutput(t, output, opts);
    opts.onEvent?.({ type: "task_end", task: taskName, agent: managerCfg.role.trim(), output });
  }
  return outputs;
}

A custom tool (lecture 12, 02:52–06:33)

The generated project already has tools/custom_tool.py "that has a kind of typical layout for these sorts of tools"; he renames it push_tool.py. "When you set up a custom tool you have to first describe using a Pydantic object the schema of what will be passed in to your custom tool. And then you end up writing an _run method, which is going to take that schema as its parameters." The body is the Pushover code from Week 1, "exactly the same code".

from crewai.tools import BaseTool
from typing import Type
from pydantic import BaseModel, Field
import os
import requests


class PushNotification(BaseModel):
    """A message to be sent to the user"""
    message: str = Field(..., description="The message to be sent to the user.")

class PushNotificationTool(BaseTool):
    

    name: str = "Send a Push Notification"
    description: str = (
        "This tool is used to send a push notification to the user."
    )
    args_schema: Type[BaseModel] = PushNotification

    def _run(self, message: str) -> str:
        pushover_user = os.getenv("PUSHOVER_USER")
        pushover_token = os.getenv("PUSHOVER_TOKEN")
        pushover_url = "https://api.pushover.net/1/messages.json"

        print(f"Push: {message}")
        payload = {"user": pushover_user, "token": pushover_token, "message": message}
        requests.post(pushover_url, data=payload)
        return '{"notification": "ok"}'
/** Push notification through Pushover (prints only when the keys are missing). */
export const pushTool = tool({
  name: "send_push_notification",
  description: "This tool is used to send a push notification to the user.",
  parameters: z.object({ message: z.string().describe("The message to be sent to the user.") }),
  execute: async ({ message }) => {
    console.log(`Push: ${message}`);
    const user = process.env.PUSHOVER_USER, token = process.env.PUSHOVER_TOKEN;
    if (user && token) {
      await fetch("https://api.pushover.net/1/messages.json", { method: "POST", body: new URLSearchParams({ user, token, message }) });
    }
    return '{"notification": "ok"}';
  },
});

Common mistakes

  • The manager in self.agents: if you decorate it with @agent, it becomes a worker too and may delegate to itself. Build it inside crew().
  • Inconsistent vocabulary: calling them "newsworthy companies" in one place and "trending companies" in another made the presenter's early versions unstable.
  • Hierarchical runs that wander: the manager may re-delegate, rephrase tasks and take a long time. Use a strong model for the manager.
  • Believing claimed actions: "a push notification has been prepared" without a tool means nothing happened.
  • ticker: "N/A" everywhere: the schema forces the field to exist, not to be right. Schemas guarantee shape, not truth.
  • Pushover silently failing: the tool ignores the HTTP response; if no notification arrives, check the keys.
Recap
  • Structured outputs in CrewAI: Pydantic classes plus output_pydantic= on the task; in TypeScript, zod schemas as the agent's outputType.
  • A custom tool is a BaseTool subclass with name, description, args_schema and _run.
  • Process.hierarchical with a manager_agent (built outside @agent, allow_delegation=True) lets an LLM assign the tasks.
  • Give a manager a stronger model, keep the vocabulary consistent, and expect autonomy to be less predictable.
  • Check traces for real tool calls; models will claim actions they cannot perform.
