Part 1: other models through the same SDK (lecture 12)

Day 1 said a model name string means OpenAI. Many other providers expose an OpenAI-compatible endpoint: the same Chat Completions protocol at a different base URL. "Any time that we have this approach, we will be able to easily use the OpenAI Agents SDK" (02:58). The recipe has three lines per provider: a base URL, an AsyncOpenAI client with that URL and the provider's key, and an OpenAIChatCompletionsModel that names the model and holds the client. You then pass that model object to Agent(model=…) instead of a string.

GEMINI_BASE_URL = "https://generativelanguage.googleapis.com/v1beta/openai/"
DEEPSEEK_BASE_URL = "https://api.deepseek.com/v1"
GROQ_BASE_URL = "https://api.groq.com/openai/v1"
// ---------- It's easy to use any model with an OpenAI-compatible endpoint ----------
// Python: AsyncOpenAI(base_url, api_key) + OpenAIChatCompletionsModel(model=..., openai_client=...)
// TypeScript: new OpenAI({ baseURL, apiKey }) + new OpenAIChatCompletionsModel(client, "model-name")
const GEMINI_BASE_URL = "https://generativelanguage.googleapis.com/v1beta/openai/";
const DEEPSEEK_BASE_URL = "https://api.deepseek.com/v1";

function providerModel(baseURL: string, apiKey: string | undefined, modelName: string) {
  if (LOCAL) {
    // local stand-in: every "provider" is the same Ollama server, so the code path is exercised without any keys

    return new OpenAIChatCompletionsModel(client, MODEL);
  }
  return new OpenAIChatCompletionsModel(new OpenAI({ baseURL, apiKey }), modelName);
}

The run that would not stop (lecture 13, 00:00–02:02)

The presenter kicked off the rebuilt SDR at the end of lecture 12 and came back to "a cautionary tale": the run "appeared to lose its way, going back again and again to get more and more emails generated". The trace list showed 14 tool calls and more than 300 seconds before he cancelled it; a second run finished normally with one call per writer. His diagnosis points at one sentence in the instructions, "you can use the tools multiple times if you're not satisfied with the results": "that's really giving this kind of autonomy and potentially an infinite loop to the agent." The lesson: "there is inherent instability with these autonomous agent frameworks, and that's something that you need to code explicitly for." Two more observations from that trace: the three writers really do run in parallel ("because they're very I/O bound"), and Llama 3.3 on Groq "took a really long time on one of them".

New to "max turns"? The safety limit the SDK already has

Each time the agent loop goes back to the model counts as a turn. Runner.run accepts max_turns= (the JS run takes { maxTurns }) and raises MaxTurnsExceededError when the limit is reached; the default is 10. It is a blunt instrument but it guarantees that a looping agent stops. Combine it with instructions that say how many times a tool may be used, and with guardrails for the content.

Part 2: structured outputs and an input guardrail (lecture 13, 03:44–10:07)

Where guardrails can live

A guardrail is a check, and "the special thing about guardrails here is that guardrails can themselves be agents": an LLM can be the judge. But the SDK only lets you attach them in two places, "either to the input at the very beginning, the input of the first agent, or the output of the last agent. You can't insert guardrails all over the place." Input guardrails protect against inappropriate requests; output guardrails against answers that should not reach the user.

A schema for the checker's answer

The guardrail will ask an LLM "is there a person's name in this message?" and needs a yes/no plus the name, not prose. So the first step is a Pydantic class, NameCheckOutput, with two fields: is_name_in_message: bool and name: str. "We're defining a schema." A guardrail_agent then gets output_type=NameCheckOutput: "we are telling this agent we don't want you to output text… we want you to output an object that conforms to this schema." Behind the scenes it is JSON: "any time you hear magical stuff like that, it usually means we're talking about JSON" (Day 4, 05:33). You could use the same trick for the emails themselves, with subject, recipient and body fields; that is one of today's exercises.

class NameCheckOutput(BaseModel):
    is_name_in_message: bool
    name: str

guardrail_agent = Agent( 
    name="Name check",
    instructions="Check if the user is including someone's personal name in what they want you to do.",
    output_type=NameCheckOutput,
    model="gpt-4o-mini"
)
// ---------- Structured outputs + an input guardrail ----------
// Python: a Pydantic BaseModel as output_type. TypeScript: a zod schema as outputType.
const NameCheckOutput = z.object({ is_name_in_message: z.boolean(), name: z.string() });

const guardrailAgent = new Agent({
  name: "Name check",
  instructions: "Check if the user is including someone's personal name in what they want you to do.",
  outputType: NameCheckOutput,
  model: MODEL,
});

// Python: @input_guardrail async def guardrail_against_name(ctx, agent, message) -> GuardrailFunctionOutput
// TypeScript: an object with a name and an execute function returning { outputInfo, tripwireTriggered }
const guardrailAgainstName: InputGuardrail = {
  name: "guardrail_against_name",
  execute: async ({ input, context }) => {
    const text = typeof input === "string" ? input : JSON.stringify(input);
    const result = await run(guardrailAgent, text, { context: context.context });
    const found = result.finalOutput;
    return { outputInfo: { found_name: found }, tripwireTriggered: found?.is_name_in_message ?? false };
  },
};

New to structured outputs? What happens between your class and the model

Your Pydantic class (or zod schema) is converted into a JSON schema: {"type": "object", "properties": {"is_name_in_message": {"type": "boolean"}, "name": {"type": "string"}}, "required": [...]}. The SDK sends that schema with the request and asks for a response in that format; OpenAI's models can be constrained to produce only valid JSON for it. The reply, for example {"is_name_in_message": true, "name": "Alice"}, is parsed and validated into an instance of your class. If the model returns something that does not fit, you get a validation error instead of silently wrong data. Smaller or older models may not support the constrained mode and then simply try their best, which is one reason the course recommends GPT-4o-mini for these labs.

Part 3: the careful sales manager (lecture 14)

Same name, instructions, tools, handoffs and model as yesterday's manager; the one difference is input_guardrails=[guardrail_against_name]. The presenter anticipates the objection: why check for a name you typed yourself? Because in a product "this kind of input wouldn't just be hard coded in a notebook. It would be typed in by your users, your sales team" (01:15), and you want to make sure "no one types in your CEO's actual name, or perhaps there'll be other PII like phone numbers". The first run uses the message with "Alice": "bam, there's been an exception. You might think bug in my code, but no. The exception is what happens when a guardrail is triggered." The trace shows the guardrail span with output {"is_name_in_message": true, "name": "Alice"}. The second run says "from Head of Business Development" and goes through; the resulting email is signed exactly that way and, amusingly, ends "© 2023 ComplAI", "a slight sign of the results of knowledge cut-offs there."

Exercises (lecture 14, 04:01)

  • Try other models: anything with an OpenAI-compatible endpoint, including OpenRouter for Claude and Ollama for free local models.
  • Add more input guardrails, and an output guardrail (the symmetric @output_guardrail receives the agent's output instead of the message). The "© 2023" footer is a candidate: trip when the output contains an outdated year.
  • Use structured outputs for the emails: a Pydantic class with subject, recipient and body, "a more robust, more bulletproof way of doing it".
  • Put a user interface around the SDR (Week 1's Gradio skills).

Common mistakes

  • AuthenticationError from a provider: the key for that provider is missing or the .env was not reloaded. Each provider needs its own key; the course marks them all optional.
  • 404 or "model not found" from a compatible endpoint: the model name belongs to another provider, or the base URL lacks the /v1 (DeepSeek, Groq) or the trailing slash (Gemini).
  • The guardrail "does nothing": you attached it to the Email Manager instead of the first agent. Input guardrails only run on the agent that Runner.run starts with.
  • Catching the exception too broadly: except Exception hides real bugs. Catch InputGuardrailTripwireTriggered specifically.
  • Structured output comes back as a string: you forgot output_type, or the provider does not support JSON-schema responses; then .is_name_in_message raises AttributeError.
  • Looping runs: see the cautionary tale above; add max_turns and tighten the instructions.
Recap
  • Any provider with an OpenAI-compatible endpoint works with the SDK: AsyncOpenAI(base_url, api_key) + OpenAIChatCompletionsModel(model, openai_client), then Agent(model=that_object).
  • Autonomy can loop: a permissive instruction gave 14 tool calls and a cancelled run. Limit turns and wording.
  • Structured output: a Pydantic class (or zod schema) as output_type makes final_output a typed object; underneath it is a JSON schema in the request.
  • Guardrails attach to the input of the first agent or the output of the last. A guardrail can run its own agent and returns GuardrailFunctionOutput(output_info, tripwire_triggered).
  • A tripped guardrail raises InputGuardrailTripwireTriggered: an expected outcome you should catch, not a bug.
