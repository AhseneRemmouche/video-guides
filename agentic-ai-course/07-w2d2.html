What this day builds

The first real project with the SDK: an automated sales development rep for an imaginary company, ComplAI, that sells a SaaS tool for SOC 2 compliance. The presenter builds it in three layers (lecture 6, 00:00–00:48): first a plain workflow where your Python code calls three agents and then a fourth; then tools, so an agent can send an email by calling a function; then agents that call other agents, in two different ways, as tools and through a handoff. Emails go out through SendGrid.

The TypeScript version is src/lab2.ts in the week2-ts project, run with pnpm lab2. It is one file that goes through the same three layers in order; the excerpts below carry the real line numbers of that file.

Setting up SendGrid (lecture 6, 01:10–03:07)

SendGrid, a Twilio company, sends "transactional" emails from their servers and is free at the volumes used here. The presenter is clear that no cold emails go out into the world: every email goes back to you.

  1. Create an account at sendgrid.com ("Start for free").
  2. Create an API key: Settings (left sidebar) ▸ API Keys ▸ Create API Key (top right). Copy it.
  3. Verify a sender: Settings ▸ Sender Authentication ▸ "Verify a Single Sender". Enter your own email address and click the verification email. Only that address may appear as the from of an email.
  4. Add the key to .env: one new line, SENDGRID_API_KEY=SG..... Save the file.
  5. Test it. The notebook's test cell sends a plain-text email and prints the HTTP status. 202 means accepted. Edit the two addresses first: the from_email must be your verified sender and the to_email an inbox you own; the presenter asks you not to send him emails ("otherwise I will get flooded").

If SendGrid gives trouble. The notebook lists an SSL fix for CERTIFICATE_VERIFY_FAILED (run uv pip install --upgrade certifi, then import certifi, os; os.environ['SSL_CERT_FILE'] = certifi.where()), an alternative implementation with Resend in community_contributions/2_lab2_with_resend_email, and the simplest fallback: replace the sending code with a Pushover call or a line written to a file. Check your spam folder before debugging: "several students have missed that the emails arrived in Spam".

A streamed run (lecture 6, 05:31–07:17)

Instead of Runner.run the presenter shows Runner.run_streamed, which returns the answer piece by piece. There is no await on that line: it returns an object whose stream_events() is iterated with async for. The boilerplate inside the loop keeps only the events that carry a text delta and prints each delta without a newline, so the email appears word by word.


result = Runner.run_streamed(sales_agent1, input="Write a cold sales email")
async for event in result.stream_events():
    if event.type == "raw_response_event" and isinstance(event.data, ResponseTextDeltaEvent):
        print(event.data.delta, end="", flush=True)
// Streaming: Python's Runner.run_streamed + "async for event" becomes run(..., { stream: true }) + toTextStream()
console.log("--- streamed email from the professional agent ---");
const streamed = await run(salesAgent1, "Write a cold sales email", { stream: true });
for await (const chunk of streamed.toTextStream()) process.stdout.write(chunk);
await streamed.completed;

Three runs at once with gather (lecture 7, 00:00–02:07)

Layer 2: tools (lectures 7–8)

A function becomes a tool (lecture 7, 04:38–08:44)

Think back to Week 1: a tool needed a JSON description of its parameters and a handle_tool_calls function with an if-chain. The SDK removes all of it. You write a normal function with type hints and a docstring, and put the decorator @function_tool above it. Printing send_email afterwards shows it is no longer a function but a FunctionTool with a name, a description taken from the docstring, and params_json_schema, "all of the boilerplate JSON that we had to write last time". "That's what a good framework should do: take out the boilerplate but leave us in full control."

@function_tool
def send_email(body: str):
    """ Send out an email with the given body to all sales prospects """
    sg = sendgrid.SendGridAPIClient(api_key=os.environ.get('SENDGRID_API_KEY'))
    from_email = Email("ed@edwarddonner.com")  # Change to your verified sender
    to_email = To("ed.donner@gmail.com")  # Change to your recipient
    content = Content("text/plain", body)
    mail = Mail(from_email, to_email, "Sales email", content).get()
    sg.client.mail.send.post(request_body=mail)
    return {"status": "success"}
// Python wraps a function with @function_tool and reads the docstring + type hints.
// TypeScript has no runtime types, so the tool() helper takes a zod schema for the parameters.
const sendEmailTool = tool({
  name: "send_email",
  description: "Send out an email with the given body to all sales prospects",
  parameters: z.object({ body: z.string() }),
  execute: async ({ body }) => sendEmail("Sales email", body),
});

New to decorators? What @something above a function means

A decorator is a function that takes your function and returns something else in its place. @function_tool above def send_email is shorthand for send_email = function_tool(send_email). After that line, the name send_email refers to the FunctionTool object the decorator built, which still knows how to call your original code. That is why print(send_email) shows a tool and not a function. Decorators show up everywhere in this course: @function_tool, @input_guardrail (Day 3), and later @agent, @task and @tool in CrewAI and LangGraph.

An agent becomes a tool (lecture 8, 00:00–02:54)

"Something a bit confusing": a whole agent can also be a tool. sales_agent1.as_tool(tool_name="sales_agent1", tool_description="Write a cold sales email") creates a FunctionTool like the one above; its parameter schema has a single input string, and when the tool is called it runs the agent and returns the agent's answer. "It's a wrapper around the agent that turns the agent into a tool. That's all it is." The notebook spells out the three wrappers one by one ("I could have done this with a fancy loop") and collects four tools: the three wrapped agents and the real send_email function.

The Sales Manager: an agent that plans (lecture 8, 02:54–06:24)

Now the difference from layer 1: "we're giving an agent the ability to choose what to run when… we're letting the agent decide." The manager's instructions tell it to use the tools, never write emails itself, try all three writers, pick the best and send it with send_email. The presenter admits he is "probably over spelling it out" but "it's never a bad thing to be very precise and instructive with your prompts". The run took 18 seconds; the email arrived in his inbox; the trace shows sales_agent1, 2, 3 and then send_email, and inside each sales tool, the wrapped agent's own call. "You should look through the trace and understand the interactions between tools and agents."

Layer 3: handoffs (lectures 9–10)

Tools versus handoffs (lecture 9, 00:58–02:23)

Both let an agent collaborate with another agent, so "it's a bit confusing". The conceptual difference: a tool is "a little feature to help with its job"; a handoff is "passing an entire job to another agent", delegating responsibility for a specialist task. The technical difference is simpler and matters more: with tools, control comes back ("request–response"); with a handoff, "you've done your piece, and you are now passing control to the other agent, and the flow does not come back to you again."

The exercises (lecture 10, 03:12–06:13)

  • Which agentic design patterns did we use? Parallelization (three writers at once), an orchestrator that delegates to workers (the manager), a form of evaluator (the picker), and prompt chaining inside the Email Manager (subject → HTML → send).
  • Which single line turned the "workflow" into an "agent" under Anthropic's definition? The moment the Sales Manager received tools=tools and was told to use them: from then on the LLM, not your Python, decided what to call and in what order. (The presenter calls the definition "a little bit hand-wavy" but says there was "a clear moment".)
  • Add tools and agents: for example a mail-merge tool that fills in real names from a list.
  • Hard challenge: use a SendGrid inbound webhook so a reply to the email triggers the agents again and the SDR holds a conversation. Mostly "engineering stuff rather than much agentic stuff", so skip it if it does not appeal.
  • Commercial angle: any end-to-end business process that works through conversations and tools can be automated this way, not only sales: the presenter's example is recruitment at his company.

Common mistakes

  • NameError: name 'asyncio' is not defined: the import is missing; the presenter hit exactly this. Add import asyncio at the top.
  • No email arrives: check spam; check that from_email is your verified sender and the key is in .env (and that you re-ran load_dotenv(override=True) after saving it); print result and look for SSL errors; open the trace and see whether send_email was called at all.
  • Status 401 or 403 from SendGrid: the key is wrong, or the sender is not verified.
  • The manager writes the email itself instead of calling tools: weaker models ignore "never generate sales emails yourself". Strengthen the instructions or force tool use with ModelSettings(tool_choice="required") (Day 4).
  • Passing an Agent where a tool is expected: an agent goes in handoffs=[…]; in tools=[…] it must be wrapped with as_tool(...).
  • Re-running cell 36 after cell 38: cell 36 uses the name tools, which cell 38 reassigns to the three writers. Running cells out of order gives the Email Manager the wrong tools. Run top to bottom, or rename the lists.
  • execute never called: the model's arguments did not match the zod schema (for example a missing field); the SDK reports a validation error back to the model. Keep parameter names simple and described.
Recap
  • Layer 1: your code orchestrates; asyncio.gather / Promise.all run three writers at once; a picker agent chooses.
  • Layer 2: @function_tool / tool({...}) turns a function into a tool with a generated schema; as_tool / asTool turns an agent into a tool; a manager with tools= decides what to call: that line makes it an agent.
  • Layer 3: handoffs=[agent] passes control to a specialist agent that finishes the job; handoff_description tells the manager what it does.
  • Tools return control; handoffs transfer it. The trace shows both: nested spans for tools, a "Handoff →" row and a new top-level agent for a handoff.
  • Autonomy ("use the tools multiple times") is powerful and unstable; Day 3 adds guardrails.
