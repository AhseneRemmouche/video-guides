Week 3 Day 1 · CrewAI: agents, tasks and a debate

CrewAI's agents, tasks, crews and YAML config, LiteLLM model strings, and a two-agent debate judged by a third; in TypeScript, a small crew runner on the Agents SDK.

What this day builds

Week 3 switches framework to CrewAI, "the fan favourite". Its vocabulary is different from Week 2: agents get a role, a goal and a backstory; work is described as tasks; a crew runs the tasks. Most of it is written in YAML files instead of code. Day 1's project is a debate: one agent argues for a motion, then against it, and a second agent, the judge, decides which side was more convincing.

About the TypeScript version this week. CrewAI exists only for Python. To follow Week 3 in TypeScript, this guide built a small crew runner on the OpenAI Agents SDK from Week 2, src/minicrew.ts (about 160 lines), that reads the same agents.yaml and tasks.yaml files, copied unchanged from the course into week3-ts/crews/. It builds the prompts with CrewAI's own wording (taken from CrewAI's source) and runs the tasks in order or through a manager. It does not reproduce CrewAI's memory system, knowledge sources or planning (Day 4 adds a simple file-based memory instead). It is a teaching port: it shows what a crew does underneath, in code you can read.

What CrewAI is (lectures 1–3)

"CrewAI" is three things (lecture 1, 01:06): CrewAI Enterprise, a platform to deploy, run and monitor agents; CrewAI UI Studio, a no-code builder; and the open-source framework, which is the only part the course uses. The website upsells the first two; "I don't hold it against them for a moment": OpenAI and Anthropic earn from their models, CrewAI must earn from hosting.

The framework has two flavours (03:42). Crews are "autonomous solutions with AI teams of agents with different roles", for "autonomous problem-solving, creative collaboration, or exploratory tasks". Flows are "structured automations by dividing complex tasks into precise workflows", for "deterministic outcomes, auditability, or precise control over execution". The course uses Crews only.

Agent, Task, Crew (lecture 2)

ConceptDefinition from the slideWeek 2 equivalent
Agent"An autonomous unit, with an LLM, a role, a goal, a backstory, memory, tools"Agent with instructions
Task"A specific assignment to be carried out, with a description, expected output, agent"none: you passed a message to Runner.run
Crew"A team of agents and tasks", run either sequentially (tasks in the order defined) or hierarchically (a manager LLM assigns them)your own Python orchestration

CrewAI is more "opinionated" than the Agents SDK (01:43): it makes you write a role, goal and backstory, then turns them into a system prompt for you, a step "somewhat hidden from you". That enforces good prompting habits but gives you less control and makes debugging harder. Why does a backstory help at all? The "more scientific" answer (lecture 4, 07:58): a model predicts the most likely next tokens, and text that starts with a convincing backstory makes consistent, expert-sounding continuations more likely.

One string for any model: LiteLLM (lecture 3)

"CrewAI uses the super-simple LiteLLM under the hood to interface with almost any LLM": you name a model as provider/model and set the provider's key in .env. Examples from the slide: openai/gpt-4o-mini, anthropic/claude-…, gemini/gemini-2.0-flash, groq/llama-3.3-70b-versatile, ollama/llama3.2 (with base_url="http://localhost:11434"), and OpenRouter. This flexibility "is where Crew really has an edge over OpenAI Agents SDK", which needed a client object per provider.

The agents: a debater and a judge

Anything in curly braces, like {motion}, is a template value filled in from the inputs you give when you start the crew. The > after each key is YAML's "folded" block: the following indented lines are joined into one paragraph.

debater:
  role: >
    A compelling debater
  goal: >
    Present a clear argument either in favor of or against the motion. The motion is: {motion}
  backstory: >
    You're an experienced debator with a knack for giving concise but convincing arguments.
    The motion is: {motion}
  llm: openai/gpt-4o-mini

judge:
  role: >
    Decide the winner of the debate based on the arguments presented
  goal: >
    Given arguments for and against this motion: {motion}, decide which side is more convincing,
    based purely on the arguments presented.
  backstory: >
    You are a fair judge with a reputation for weighing up arguments without factoring in
    your own views, and making a decision based purely on the merits of the argument.
    The motion is: {motion}
  llm: anthropic/claude-sonnet-4-6

The tasks: propose, oppose, decide

Three tasks, two for the debater and one for the judge. Each has a description, an expected output, the agent, and a file to write. Naming rule from lecture 5 (01:40): "you cannot call your tasks the same thing as you call your agents", so the judge's task is decide, not judge.

propose:
  description: >
    You are proposing the motion: {motion}.
    Come up with a clear argument in favor of the motion.
    Be very convincing.
  expected_output: >
    Your clear argument in favor of the motion, in a concise manner.
  agent: debater
  output_file: output/propose.md

oppose:

    Your clear argument against the motion, in a concise manner.

  description: >
    Review the arguments presented by the debaters and decide which side is more convincing.

Wiring it up: crew.py

The generated file is full of comments; "I do find that these comments get in the way a bit," so he deletes them. What remains is a class with decorators (met in Week 2): @CrewBase on the class, @agent on each method that returns an Agent, @task on each method that returns a Task, and @crew on the method that returns the Crew. The @agent and @task decorators are what fill self.agents and self.tasks.

from crewai import Agent, Crew, Process, Task
from crewai.project import CrewBase, agent, crew, task


@CrewBase
class Debate():
    """Debate crew"""


    agents_config = 'config/agents.yaml'
    tasks_config = 'config/tasks.yaml'

    @agent
    def debater(self) -> Agent:
        return Agent(
            config=self.agents_config['debater'],
            verbose=True
        )

    @agent
    def judge(self) -> Agent:
        return Agent(
            config=self.agents_config['judge'],
            verbose=True
        )

    @task
    def propose(self) -> Task:
        return Task(
            config=self.tasks_config['propose'],
        )

    @task
    def oppose(self) -> Task:
        return Task(
            config=self.tasks_config['oppose'],
        )

    @task
    def decide(self) -> Task:
        return Task(
            config=self.tasks_config['decide'],
        )


    @crew
    def crew(self) -> Crew:
        """Creates the Debate crew"""

        return Crew(
            agents=self.agents, # Automatically created by the @agent decorator
            tasks=self.tasks, # Automatically created by the @task decorator
            process=Process.sequential,
            verbose=True,
        )
// ---------- the YAML files ----------
export type AgentConfig = { role: string; goal: string; backstory: string; llm?: string };
export type TaskConfig = { description: string; expected_output: string; agent: string; context?: string[]; output_file?: string };

/** Fill {placeholders} from the inputs, like kickoff(inputs=...) does. Unknown placeholders are left alone. */
export function interpolate(text: string, inputs: Record<string, string>) {
  return text.replace(/\{(\w+)\}/g, (m, key) => (key in inputs ? inputs[key]! : m));
}

export async function loadCrew(dir: string, inputs: Record<string, string>) {
  const read = async (f: string) => YAML.parse(interpolate(await readFile(join(dir, f), "utf-8"), inputs));
  return { agents: (await read("agents.yaml")) as Record<string, AgentConfig>, tasks: (await read("tasks.yaml")) as Record<string, TaskConfig> };
}

What CrewAI sends to the model

CrewAI's prompt-building is "somewhat hidden". This guide read it in CrewAI's source (crewai/translations/en.json): the system prompt is "You are {role}. {backstory}\nYour personal goal is: {goal}"; the task message is the description plus "This is the expected criteria for your final answer: {expected_output}\nyou MUST return the actual complete content as the final answer, not a summary.", followed by "This is the context you're working with:" and the earlier outputs. CrewAI also adds instructions for its "Thought: … Final Answer:" text format. The TypeScript runner reproduces the first three pieces and uses the Agents SDK's native tool calling instead of the text format.

// ---------- CrewAI's prompt wording ----------
/** CrewAI "role_playing": the system prompt built from role, backstory and goal. */
export function instructionsFor(a: AgentConfig) {
  return `You are ${a.role.trim()}. ${a.backstory.trim()}\nYour personal goal is: ${a.goal.trim()}`;
}

/** CrewAI "expected_output" and "task_with_context" slices. */
export function taskPrompt(t: TaskConfig, context: string) {
  let prompt =
    `${t.description.trim()}\n\nThis is the expected criteria for your final answer: ${t.expected_output.trim()}\n` +
    `you MUST return the actual complete content as the final answer, not a summary.`;
  if (context) prompt += `\n\nThis is the context you're working with:\n${context}`;
  return prompt;
}

The runner itself (minicrew.ts, lines 103–120): for each task it collects the context, builds the agent, runs it, saves the file.

/** Process.sequential: run every task in the order of tasks.yaml. */
export async function runSequential(crew: Awaited<ReturnType<typeof loadCrew>>, opts: CrewOptions = {}) {
  const outputs: Record<string, string> = {};
  for (const [taskName, t] of Object.entries(crew.tasks)) {
    const cfg = crew.agents[t.agent];
    if (!cfg) throw new Error(`Task ${taskName} names unknown agent ${t.agent}`);
    // No "context" listed → all previous outputs (CrewAI's NOT_SPECIFIED rule); a list → only those tasks.
    const context = (t.context ?? Object.keys(outputs)).map((n) => outputs[n] ?? "").filter(Boolean).join("\n\n----------\n\n");
    opts.onEvent?.({ type: "task_start", task: taskName, agent: cfg.role.trim() });
    const agent = makeAgent(t.agent, cfg, opts, opts.outputTypes?.[taskName]);
    const result = await run(agent, taskPrompt(t, context), { maxTurns: 15 });
    const output = asText(result.finalOutput);
    outputs[taskName] = output;
    await saveOutput(t, output, opts);
    opts.onEvent?.({ type: "task_end", task: taskName, agent: cfg.role.trim(), output });
  }
  return outputs;
}

Common mistakes

  • A task with the same name as an agent: "you will have a problem with conflicting names". Some people suffix tasks with _task.
  • crewai run from the wrong folder: run it inside the project folder (3_crew/debate), where its pyproject.toml is.
  • Chroma or "Microsoft Visual C++ 14.0 or greater is required" on Windows: install the Build Tools from the setup guide. (This guide's first run on Windows compiled one package, chroma-hnswlib, during the environment build.)
  • Agent method name differs from the YAML key: self.agents_config['debater'] raises KeyError.
  • Placeholder not filled: the input key in main.py must match the name in braces exactly (motion).
  • A YAML indentation slip: the lines under role: > must be indented more than role; YAML is whitespace-sensitive.
  • Typing your key into the crewai create prompt: it creates a second .env inside the project. Press Enter; the root .env is used.
Recap
  • CrewAI's open-source framework, Crews flavour: agents (role, goal, backstory, llm), tasks (description, expected output, agent), a crew with a process.
  • YAML holds the prompts; crew.py wires them with @CrewBase, @agent, @task, @crew; main.py sets the inputs and calls kickoff.
  • {placeholders} in YAML are filled from kickoff(inputs=…).
  • Model strings are LiteLLM's provider/model, so each agent can use a different company's model.
  • In a sequential crew a task sees every earlier output unless you list its context. CrewAI turns role, backstory and goal into the system prompt with a fixed template.
