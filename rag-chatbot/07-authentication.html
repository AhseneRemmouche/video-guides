Adding Authentication

Clerk sign-in, sign-up and sign-out with a navigation bar.

▶ Watch this part (16:30)

Goal

Before giving the AI access to internal information, you need to control who can use it. This step adds Clerk, a complete authentication solution with pre-built UI and user management, plus a navigation bar with Sign In, Sign Up and Sign Out buttons.

New to authentication? Authentication vs authorization

Two words that sound alike but mean different things:

  • Authentication ("authN") answers "Who are you?". The user proves their identity, usually with an email and password, or by signing in with Google or GitHub.
  • Authorization ("authZ") answers "What are you allowed to do?". Once the app knows who you are, it decides which pages and actions you can use. Roles such as "admin" are part of this (see RBAC).

Think of an office building: showing your ID badge at the front desk is authentication; the badge only opening certain floors is authorization. This page sets up authentication. The next page uses it for a simple authorization rule: "you must be signed in to use the chatbot".

Writing authentication yourself is hard and risky (password hashing, email verification, password resets, social logins, attacks). A service like Clerk does all of it for you, so you only add a few components.

Part A: set up Clerk in the dashboard

  1. Create an account

    Sign up at clerk.com and verify your email. The free plan is enough for this tutorial.

  2. Create an application
    • Name it RAG Chatbot. This name appears on Clerk's sign-in screens ("Sign in to RAG Chatbot"), so pick something your users will recognise.
    • Choose the sign-in options. The defaults are Email (with password) and Google. The presenter also enabled GitHub. The preview on the right updates as you change them. You can change these options later in the dashboard without touching your code.
    • Click Create application.
  3. Choose Next.js on the instructions page, then follow its steps below. Clerk shows the install command, your keys, and starter code tailored to the framework you pick.

Development vs production: a new Clerk application starts in a development instance. Its keys start with pk_test_ and sk_test_ and work on localhost. When you deploy for real users you create a production instance with pk_live_/sk_live_ keys.

  2. Add your Clerk API keys

    Copy the publishable key and secret key from the setup page into .env.local. Use your own keys.

    OPENAI_API_KEY=sk-...

    Line by line

    Line(s)CodeWhat it does & why
    1OPENAI_API_KEY=sk-...Your existing OpenAI key from earlier. Leave it as it is. Each line in an env file is NAME=value, with no spaces around = and no quotes needed.
    2NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY=pk_test_...The publishable key identifies your Clerk application. It is safe to show publicly: the browser needs it so Clerk's sign-in UI knows which app it belongs to. The NEXT_PUBLIC_ prefix is what makes this possible (see the primer below). Clerk looks for exactly this name, so don't rename it.
    3CLERK_SECRET_KEY=sk_test_...The secret key lets your server talk to Clerk with full rights (verify sessions, read and manage users). It must never reach the browser, so it has no NEXT_PUBLIC_ prefix. Anyone who has it can act as your app's back end.
    New to NEXT_PUBLIC_? Why the prefix matters

    Next.js reads .env.local on the server. By default, no environment variable is sent to the browser. That is a safety feature: secrets stay on the server.

    If a variable's name starts with NEXT_PUBLIC_, Next.js copies its value into the JavaScript it sends to the browser when it builds the app. Anyone can then see it with the browser's developer tools. So the rule is simple:

    • Values the browser needs and that are safe to reveal (the Clerk publishable key): use NEXT_PUBLIC_.
    • Secrets (OPENAI_API_KEY, CLERK_SECRET_KEY, database passwords): never use NEXT_PUBLIC_.

    Accidentally writing NEXT_PUBLIC_CLERK_SECRET_KEY would publish your secret to every visitor. Read more about API keys in the glossary.

    Common mistakes:

    • Not restarting the dev server. Next.js reads .env.local only when it starts. Stop it with Ctrl+C and run npm run dev again. Otherwise you get an error like "Missing publishableKey".
    • Copy-paste errors: a missing character, an extra space, or the two keys swapped. Publishable keys start with pk_, secret keys with sk_.
    • Committing the file: .env.local is listed in .gitignore by default. Keep it that way so your secrets never end up on GitHub.
  3. Create the middleware

    Because the project uses a src/ folder, the file goes in src/middleware.ts, not the project root. Paste the code from Clerk's setup page. It gives you access to auth data in every request and is where you will configure protected routes in step 8.

    import { clerkMiddleware } from "@clerk/nextjs/server";

export default clerkMiddleware();

export const config = {
  matcher: [
    // Skip Next.js internals and all static files, unless found in search params
    "/((?!_next|[^?]*\\.(?:html?|css|js(?!on)|jpe?g|webp|png|gif|svg|ttf|woff2?|ico|csv|docx?|xlsx?|zip|webmanifest)).*)",
    // Always run for API routes
    "/(api|trpc)(.*)",
  ],
};

    The matcher tells Next.js which requests run through the middleware. It runs on every page and API route, but skips static files like images and CSS.

    Next.js 16+: the middleware.ts convention was renamed to proxy.ts. middleware.ts still works but shows a deprecation warning. Clerk's current quickstart shows the right file name for your version.

    Common mistake: putting middleware.ts in the project root, or inside src/app. With a src/ folder it must sit directly in src/, next to the app folder. In the wrong place it is silently ignored.

  4. Wrap the app with ClerkProvider

    ClerkProvider is a React component that gives the whole app access to Clerk's context. The video does this a little differently from the setup page: in the existing src/app/layout.tsx, import ClerkProvider from @clerk/nextjs and wrap the returned JSX with it.

    New to providers and context? How data reaches every component

    Normally data flows down through props, one level at a time. If dozens of components all need to know "who is signed in", passing that through every level would be painful.

    React's context solves this. A provider component wraps part of the app and makes some data available to every component inside it, at any depth, without props. Components read it directly (Clerk's buttons and hooks like useUser() do this behind the scenes).

    That is why ClerkProvider goes at the very top, in the root layout: everything in the app is inside it. If a Clerk component is rendered outside the provider, it throws an error saying it must be used within ClerkProvider.

    New to sessions? How the app remembers you are signed in

    HTTP requests are independent: the server doesn't automatically know that two requests come from the same person. After you sign in, Clerk creates a session and stores a small signed token in a browser cookie. The browser sends that cookie with every request. The middleware reads it and knows who you are, without asking for your password again. Signing out deletes the session.

Part C: the navigation bar

  1. Create src/components/navigation.tsx

    Clerk provides pre-built components that handle all the auth flows:

    ComponentBehaviour
    SignedOutRenders its children only when the user is not signed in.
    SignedInRenders its children only when the user is signed in.
    SignInButton / SignUpButtonOpen the sign-in or sign-up flow. mode="modal" opens a dialog instead of redirecting to another page.
    SignOutButtonSigns the user out.

    Each Clerk button wraps a shadcn Button (ghost for Sign In, default for Sign Up, outline for Sign Out).

    New to modals? Dialog vs redirect

    A modal is a dialog box that opens on top of the current page and dims the background. You must finish or close it before using the page behind it. With mode="modal", clicking Sign In opens Clerk's sign-in form in such a box, and the user never leaves your page.

    The alternative, mode="redirect" (the default), sends the browser to a separate sign-in page and brings the user back afterwards. Both work; a modal feels quicker for small apps.

  3. Make room for the navbar on the chat page

    The navbar is h-16 (4rem) tall, so subtract that from the chat container height:

    <div className="max-w-4xl mx-auto p-6 relative size-full h-[calc(100vh-4rem)]">

    calc(100vh-4rem) means "the full height of the browser window minus 4rem". Without this change the page would be 4rem taller than the window, the whole page would scroll, and the prompt box would be pushed partly off screen.

Test the auth flow

  1. Check the navbar

    "RAG Chatbot" is on the top left, with Sign In and Sign Up on the top right.

  2. Sign up

    Click Sign Up, create an account with email and password, and verify your email. You return to the home page, and the header now shows Sign Out.

  3. Sign out, then sign in

    Click Sign Out. Then click Sign In, enter your credentials, and you return to the home page.

How to know it worked: the buttons on the right switch between Sign In / Sign Up and Sign Out as you sign in and out, and the new user appears under Users in the Clerk dashboard.

Common problems:

  • "Missing publishableKey" error: the key name is misspelled in .env.local, or the dev server wasn't restarted.
  • "clerkMiddleware() was not run" or similar: middleware.ts is in the wrong folder or misnamed.
  • "must be used within ClerkProvider": ClerkProvider isn't wrapping the <html> in layout.tsx.
  • Navbar doesn't appear: <Navigation /> was imported but not placed inside <body>.
Recap
  • Clerk is installed with keys in .env.local, middleware in src/middleware.ts and ClerkProvider in the root layout.
  • A navigation bar switches between Sign In/Sign Up and Sign Out depending on whether the user is signed in.
  • Anyone can still open /chat. The next step fixes that.
