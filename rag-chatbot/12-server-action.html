Creating the Server Action

Parse a PDF, chunk it, embed it and store it in Neon.

▶ Watch this part (39:38)

Goal

Build the server action that ties everything together: PDF file → text → chunks → embeddings → rows in Neon.

New to server actions? How they differ from API routes

Your app has two halves: the browser (what the user sees) and the server (where secrets like your OpenAI key and database password live). Processing a PDF needs those secrets, so it must happen on the server. There are two ways in Next.js to let the browser ask the server to do something:

API route (step 5's /api/chat)Server action (this page)
How you write itA route.ts file exporting GET/POST functions that receive a Request.A normal async function in a file that starts with "use server".
How the browser calls itYou write a fetch to a URL, choose the method, and parse the response yourself.You import the function and call it: await processPdfFile(formData). Next.js turns the call into a request for you.
Good forPublic endpoints, streaming chat responses, webhooks, being called by other apps.Your own forms and buttons: "upload this", "save that".

It feels like calling a local function, but it isn't: behind the scenes the arguments are sent over HTTP (a POST request), the function runs on the server, and its return value is sent back. That's why arguments and return values must be simple data (strings, numbers, plain objects, FormData, files): you can't send a class instance or a function across the network.

Because anyone can trigger that request, treat a server action like a public endpoint. (Step 16 adds the check that only admins may upload.)

Step by step

  1. Install the PDF parser 
    npm install pdf-parse

    pdf-parse reads a PDF file's bytes and gives you back its text. Run the command in your project folder.

  2. Mark pdf-parse as an external server package

    pdf-parse should not be bundled into the server build. Next.js will load it from node_modules with a normal require instead.

    import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  serverExternalPackages: ["pdf-parse"],
};

export default nextConfig;

  3. Create src/app/upload/actions.ts with the "use server" directive at the top.

    That directive makes every exported function a server action: code that runs on the server but can be called directly from Client Components. It works like an RPC call, with no API route to write.

    RPC means "remote procedure call": calling a function that actually runs on another computer. The folder src/app/upload/ is the same folder that will hold the upload page in step 13, so the page and its action live side by side. A file named actions.ts doesn't become a page or a URL, because only files named page.tsx or route.ts do.

  4. Import what you need: the PDF parser, db, the documents table and the two utilities.

    TypeScript complains that pdf-parse has no types, so install them:

    npm install @types/pdf-parse

    Packages under @types/ contain only type descriptions (no runnable code) written by the community for libraries that ship without them. They make the red underline on import pdf from "pdf-parse" disappear and give you autocomplete for data.text.

  5. Write processPdfFile(formData: FormData)

    FormData is how browsers send files to servers. Wrap everything in try/catch. On error, log "PDF processing error" and return { success: false, error: "Failed to process PDF" }.

  6. Get the file and extract the text

    formData.get("pdf") as File, then File → ArrayBuffer → Node.js Buffer → pdf(buffer), which extracts the text.

  7. Guard against empty PDFs

    If data.text is missing or only whitespace (for example a scanned PDF with only images), return { success: false, error: "No text found in PDF" }.

  8. Chunk, embed and build the records

    chunkContent(data.text) splits the text. generateEmbeddings(chunks) embeds every chunk in one API call. Chunks and embeddings come back in the same order, so pair them by index.

  9. Insert and report

    await db.insert(documents).values(records) stores all rows in one statement. Then return success: true with a message saying how many chunks were created.

New to FormData, File, ArrayBuffer and Buffer? The journey of the bytes

FormData is a standard browser object that holds labelled values, like a small envelope with named compartments. The upload page puts the chosen file in the compartment labelled "pdf"; the server action takes it out with formData.get("pdf"). The label must be identical on both sides.

The PDF then changes shape three times before pdf-parse can read it:

ShapeWhat it isWhy you need it
FileThe web's standard "uploaded file" object: a name (handbook.pdf), a type (application/pdf), a size, and the bytes, which you have to ask for.It's what you get out of FormData.
ArrayBufferA raw block of bytes in memory, with no extra information. file.arrayBuffer() reads the file's contents into one. It returns a Promise, because reading can take time.The standard JavaScript way to hold binary data.
BufferNode.js's own byte container, with handy extra methods. Buffer.from(arrayBuffer) wraps the same bytes without copying them.pdf-parse (v1) is an older Node.js library and expects a Buffer.

Think of it as: a parcel (File) → unpacked contents (ArrayBuffer) → put in the box the PDF reader likes (Buffer).

Complete file

// src/app/upload/actions.ts
"use server";

import pdf from "pdf-parse";
import { db } from "@/lib/db-config";
import { documents } from "@/lib/db-schema";
import { generateEmbeddings } from "@/lib/embeddings";
import { chunkContent } from "@/lib/chunking";

export async function processPdfFile(formData: FormData) {
  try {
    const file = formData.get("pdf") as File;

    // Convert File to Buffer and extract text
    const bytes = await file.arrayBuffer();
    const buffer = Buffer.from(bytes);
    const data = await pdf(buffer);

    if (!data.text || data.text.trim().length === 0) {
      return {
        success: false,
        error: "No text found in PDF",
      };
    }

    // Chunk the text
    const chunks = await chunkContent(data.text);

    // Generate embeddings
    const embeddings = await generateEmbeddings(chunks);

    // Store in database
    const records = chunks.map((chunk, index) => ({
      content: chunk,
      embedding: embeddings[index],
    }));

    await db.insert(documents).values(records);

    return {
      success: true,
      message: `Created ${records.length} searchable chunks`,
    };
  } catch (error) {
    console.error("PDF processing error:", error);
    return {
      success: false,
      error: "Failed to process PDF",
    };
  }
}

Why return { success, error } instead of throwing an error?

A function can report failure in two ways: throw an error, or return a value that says "it failed". For server actions, returning is the friendlier choice:

  • Predictable shape. The page always gets an object and only has to check result.success, then show result.message or result.error. No try/catch needed on the page.
  • Your message survives. In production, Next.js hides the message of errors thrown in server actions from the browser (the user would see a generic error) so that secrets in error messages don't leak. A returned string arrives exactly as you wrote it.
  • Expected vs unexpected. "This PDF has no text" is a normal situation, not a crash. Returning it as data makes that clear.
// On the page (step 13), roughly:
const result = await processPdfFile(formData);
if (result.success) showGreen(result.message);
else showRed(result.error);

pdf-parse version note: the video and the GitHub repo use the classic v1 API (the repo's package.json pins "pdf-parse": "^1.1.1") (import pdf from "pdf-parse" plus @types/pdf-parse). Version 2 of pdf-parse changed the API to a class (new PDFParse({ data: buffer }) then .getText()). If pdf(buffer) doesn't exist after installing, either pin v1 to match the video:

npm install pdf-parse@1.1.1 @types/pdf-parse

or adapt the three parsing lines to the v2 API.

In that command, @1.1.1 after a package name asks npm for that exact version instead of the newest one, and listing two packages installs both at once.

Server action body size: server actions accept request bodies up to 1 MB by default. For bigger PDFs, raise the limit in next.config.ts with experimental: { serverActions: { bodySizeLimit: "10mb" } }.

How to know it worked: you can't test this action on its own yet; the upload page in step 13 calls it. For now, check that actions.ts shows no red underlines, and that the dev server still starts after you edited next.config.ts (restart it). After step 13, a successful upload shows "Created N searchable chunks", and the documents table in Neon's Tables view fills with rows.

Common mistakes:

  • "use server" missing or not at the very top: the page then fails to import the action, often with an error about server-only modules such as fs.
  • A different key on each side: the page appends "pdf", so the action must read formData.get("pdf"). Any mismatch gives null and "Failed to process PDF".
  • ENOENT: no such file or directory, open './test/data/05-versions-space.pdf': pdf-parse is being bundled. Check serverExternalPackages in next.config.ts and restart the dev server.
  • An error like pdf is not a function: you probably installed pdf-parse v2. See the version note above.
  • Looking for errors in the browser console. console.error in a server action prints in the terminal where npm run dev runs.

This action is the indexing step. Extract → chunk → embed → store is the document-indexing pipeline of RAG. It runs once per upload so that questions never have to re-read your documents. Why this matters, and when you need to re-index, is explained in Indexing Explained.

Recap
  • processPdfFile takes a PDF from a form, extracts its text, chunks it, embeds every chunk in one batch, and stores { content, embedding } rows in Neon.
  • It returns { success, message } or { success, error } for the UI to display.
