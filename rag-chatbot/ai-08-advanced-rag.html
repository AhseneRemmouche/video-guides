Advanced RAG

Chunking strategies, hybrid search, reranking, query rewriting, citations and RAG failure modes.

The chatbot you built in Part 1 is a complete, working RAG system: chunk the documents, embed them, find the 3 closest chunks to a question, and let the model answer from them. For a single handbook that works surprisingly well. As the knowledge base grows, and as users ask messier questions, you'll start to see failures: the bot can't find a form by its code, quotes last year's policy, or answers from the wrong paragraph.

This chapter is a toolbox of techniques that fix those failures. You'll learn:

  • chunking strategies beyond fixed-size, and how to choose size and overlap;
  • why to store metadata (source, page, section) with every chunk;
  • hybrid search: combining keyword search with vector search in Postgres, merged with reciprocal rank fusion;
  • reranking, query rewriting, multi-query and HyDE;
  • contextual retrieval, citations, updates and duplicates, and per-user access control;
  • agentic RAG, a table of common failure modes, and how to measure improvements.

Why this matters for your chatbot. Each technique here is optional. Adding all of them at once would make the app slower, more expensive and harder to debug. The skill is to notice a specific failure, pick the technique that fixes it, and measure whether it helped. The failure-modes table near the end is the best place to start when something goes wrong.

Chunking strategies

Chunking decides what a search result can be. If the answer to a question is split across two chunks, or buried in a chunk that is mostly about something else, no search technique can fully fix it. That makes chunking the first thing to look at.

StrategyHow it worksGood forWatch out for
Fixed-sizeCut every N characters or tokens, with some overlap.Simple, predictable, works on any text.Cuts mid-sentence or mid-table; ignores structure.
RecursiveTry to split at big boundaries first (paragraphs), then smaller ones (lines, spaces) only if a piece is still too big.A strong default for prose.Still blind to headings and meaning.
By document structureSplit at headings, sections, list items, table rows, Markdown/HTML elements, or pages.Handbooks, manuals, legal text, docs with clear headings.Sections vary wildly in length; very long ones still need splitting.
SemanticEmbed sentences and start a new chunk where the meaning shifts (similarity between neighbouring sentences drops).Long unstructured text that changes topic.Extra embedding cost at indexing time; harder to predict and debug.

What this project does

Step 11 uses LangChain's RecursiveCharacterTextSplitter with chunkSize: 900, chunkOverlap: 150 and separators: [" "]. Because the only separator is a space, it behaves like a fixed-size splitter that never cuts a word in half. As step 11 notes, removing the separators line uses LangChain's defaults (paragraphs, then lines, then spaces, then characters), which tends to produce cleaner chunks. That is the cheapest chunking upgrade available.

Size and overlap trade-offs

Smaller chunks (e.g. 300–500 chars)Larger chunks (e.g. 1,500–3,000 chars)
Search precisionHigh: each vector is about one thing.Lower: each vector is a blend of several topics.
Context per resultLittle: the answer may need the neighbouring chunk.Plenty: surrounding explanation comes along.
Rows and storageMore rows, more vectors.Fewer rows.
Tokens sent to the modelFewer per result.More per result.

Overlap repeats the end of one chunk at the start of the next, so a sentence near a boundary appears whole in at least one chunk. 10–20% of the chunk size is a common rule of thumb (150 of 900 is about 17%). More overlap means more duplicated text and more rows. There is no universally correct size: try two or three settings on your own documents and measure (see How to measure).

A popular middle ground is "small to search, big to read" (sometimes called parent-document retrieval): embed small chunks for precise search, but when one matches, hand the model the larger section it belongs to.

Store metadata with every chunk

Right now each row in documents holds id, content and embedding, and nothing else. The database doesn't know which file a chunk came from. Adding a few columns unlocks most of the techniques in this chapter:

Column (example)Enables
source (file name or document id)Citations, deleting/replacing one document, removing duplicates
page, section (heading)Precise citations ("Handbook, p. 12, Time Off"); contextual retrieval
org_id / owner_idAccess control: only search what the user may see
created_at, versionPrefer the newest version; audit what changed
content_hashSkip chunks that are already stored

A migration for the most useful one might look like this (illustrative; in this project you'd add the column to db-schema.ts and let drizzle-kit generate the SQL as in step 9):

ALTER TABLE documents ADD COLUMN source text;
CREATE INDEX documents_source_idx ON documents (source);

The server action in step 12 already has the file in hand, so filling it is one extra field per record: { content: chunk, embedding: embeddings[index], source: file.name }.

Hybrid search: keywords + vectors

Vector search finds meaning but is weak at exact strings: form codes ("HR-104B"), product names, error codes, people's names. Classic keyword search is the opposite: it is excellent at exact words and knows nothing about synonyms. Hybrid search runs both and merges the results, so each covers the other's blind spot.

New to keyword search? What BM25 and full-text search are

Keyword search engines split text into words, normalise them (lower-case, "requests" → "request"), and build an index from each word to the rows that contain it, like the index at the back of a book.

To rank results, they score how well each row matches. The best-known scoring formula is BM25. Roughly, it rewards rows that contain the query's words often, gives more weight to rare words (a match on "HR-104B" counts far more than a match on "the"), and avoids favouring a row just because it is long.

Postgres has built-in full-text search. Its ts_rank function is a similar idea but not the same formula as BM25. For hybrid search in RAG, that difference rarely matters. Some Postgres extensions and dedicated search engines provide true BM25 if you need it.

Full-text search in Postgres

Three building blocks:

  • tsvector: a processed version of a text, a sorted list of normalised words ("lexemes"). to_tsvector('english', content) creates one.
  • tsquery: a processed search query. websearch_to_tsquery('english', 'vacation days') turns ordinary user input into one.
  • @@: "does this tsvector match this tsquery?" and ts_rank(tsvector, tsquery): "how well?"

You can store the tsvector as a generated column, so Postgres keeps it up to date on every insert, and index it with a GIN index (the right index type for "which rows contain this word"):

ALTER TABLE documents
  ADD COLUMN content_tsv tsvector
  GENERATED ALWAYS AS (to_tsvector('english', content)) STORED;

CREATE INDEX documents_content_tsv_idx ON documents USING gin (content_tsv);

-- Keyword search on its own:
SELECT id, content, ts_rank(content_tsv, query) AS rank
FROM documents, websearch_to_tsquery('english', 'HR-104B form') AS query
WHERE content_tsv @@ query
ORDER BY rank DESC
LIMIT 5;

Reciprocal rank fusion (RRF), simply

Now you have two ranked lists, and their scores are on different scales: cosine similarity is between −1 and 1, ts_rank is some small positive number. You can't just add them. Reciprocal rank fusion ignores the scores and uses only the positions:

RRF score of a chunk = sum over each list of 1 ÷ (k + its rank in that list)

k is a constant, commonly 60, that stops the #1 spot from dominating. A chunk missing from a list gets nothing from that list. Example with k = 60:

ChunkVector rankKeyword rankRRF score
A141/61 + 1/64 ≈ 0.0164 + 0.0156 = 0.0320
B2(not found)1/62 ≈ 0.0161
C(not found)11/61 ≈ 0.0164

A wins because both methods liked it. C (the exact keyword hit) edges past B. That's the behaviour you want: agreement is rewarded, and a strong result from either method still makes the cut.

Here is the whole thing in one illustrative SQL query. $1 is the question's embedding and $2 is the question text:

WITH semantic AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY distance) AS rank
  FROM (
    SELECT id, embedding <=> $1::vector AS distance
    FROM documents
    ORDER BY distance          -- raw distance, so the HNSW index is used
    LIMIT 20
  ) AS nearest
),
keyword AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY score DESC) AS rank
  FROM (
    SELECT id, ts_rank(content_tsv, query) AS score
    FROM documents, websearch_to_tsquery('english', $2) AS query
    WHERE content_tsv @@ query
    ORDER BY score DESC
    LIMIT 20
  ) AS matches
)
SELECT d.id, d.content,
       COALESCE(1.0 / (60 + s.rank), 0) + COALESCE(1.0 / (60 + k.rank), 0) AS rrf_score
FROM semantic s
FULL OUTER JOIN keyword k ON s.id = k.id
JOIN documents d ON d.id = COALESCE(s.id, k.id)
ORDER BY rrf_score DESC
LIMIT 3;

Reading it top to bottom: semantic takes the 20 nearest chunks by vector distance and numbers them 1–20. keyword does the same for the 20 best keyword matches. The FULL OUTER JOIN keeps chunks that appear in either list (or both); COALESCE(…, 0) gives 0 points for a list a chunk isn't in. The final ORDER BY keeps the 3 best fused scores. In this project you would run it with Drizzle's db.execute(sql`…`).

If you prefer to fuse in TypeScript (for example when the two searches come from different systems), RRF is a few lines:

// Each list holds chunk ids, best first.
function reciprocalRankFusion(lists: number[][], k = 60): number[] {
  const scores = new Map<number, number>();
  for (const list of lists) {
    list.forEach((id, index) => {
      const rank = index + 1;
      scores.set(id, (scores.get(id) ?? 0) + 1 / (k + rank));
    });
  }
  return [...scores.entries()].sort((a, b) => b[1] - a[1]).map(([id]) => id);
}

reciprocalRankFusion([[7, 3, 9], [12, 7]]); // [7, 12, 3, 9]: 7 is in both lists, so it wins

Note that hybrid results have no single "similarity", so the tutorial's 0.5 threshold no longer applies directly. You can keep a threshold on the vector side only, or rely on reranking to drop weak candidates.

Reranking

Vector search is fast because the question and each chunk are embedded separately; the chunk vectors were computed long before the question existed. That speed costs some accuracy: the model never looked at the question and the chunk together.

A reranker does a second pass. It takes the question and each candidate chunk as a pair and outputs a relevance score. Models built for this are called cross-encoders. They are much more accurate at judging "does this passage answer this question?", and much slower, so you only run them on a short list:

  1. Retrieve a wide net cheaply: 20–50 candidates from vector or hybrid search.
  2. Rerank those candidates with the cross-encoder.
  3. Send only the top 3–5 to the chat model.

Options: hosted rerank APIs (several embedding providers also offer one), open-weight cross-encoder models you run yourself, or, as a simple fallback, asking a cheap chat model to score each candidate with generateObject. The AI SDK version used in this project (v5) has no built-in rerank helper, so you would call the reranking provider's own SDK or HTTP API from inside the tool's execute function. Reranking adds latency (another network call per question), so measure whether the quality gain is worth it.

Better queries: rewriting, multi-query and HyDE

Users ask short, vague or conversational questions: "and what about part-timers?" only makes sense next to the previous message. Searching for that literal text finds nothing useful. These techniques improve the query before searching.

Query rewriting

Ask a model to turn the user's latest message (plus the conversation) into a standalone search query: "and what about part-timers?" → "vacation days for part-time employees". In this project the chat model already does this for free: when it calls searchKnowledgeBase, it writes the query argument itself, and the tool's .describe("The search query to find relevant documents") guides it. Good tool descriptions are a cheap form of query rewriting (see Tool Calling in Depth).

Multi-query

Generate several differently worded queries, search with each, and fuse the results with RRF. This helps when the documents use vocabulary the user didn't.

import { generateObject } from "ai";
import { openai } from "@ai-sdk/openai";
import { z } from "zod";

const { object } = await generateObject({
  model: openai("gpt-5-mini"),
  schema: z.object({
    queries: z.array(z.string()).describe("2 to 3 short search queries"),
  }),
  prompt: `Write 2 to 3 different search queries that would find company policy text answering this question.
Question: ${question}`,
});

const resultLists = await Promise.all(
  object.queries.map((q) => searchDocuments(q, 10, 0.3)),
);
// then fuse resultLists (by id) with reciprocalRankFusion

generateObject with a zod schema returns typed data instead of prose; see Structured Output.

HyDE (hypothetical document embeddings)

A question and its answer are phrased very differently. "How many vacation days do I get?" looks nothing like "Employees with 0–2 years of service receive 15 days of PTO annually." HyDE asks a model to write a plausible answer first (which may be factually wrong), embeds that fake answer, and searches with its vector. Because the fake answer is shaped like a policy paragraph, it often lands closer to the real one. The fake answer is only used for searching; it is never shown to the user.

Trade-off. Each of these adds at least one extra model call before searching, which means more latency and cost on every question. Try them when you see "the answer is in the documents but search can't find it" failures, not by default.

Contextual retrieval

A chunk taken out of its document often loses information that made it understandable. Imagine a chunk that reads: "Employees in this category receive 20 days." Which category? Which document? Which year? Its embedding knows nothing about "part-time staff in the 2025 Germany handbook", so a question mentioning those things won't find it.

Contextual retrieval fixes this at indexing time: before embedding, prepend a short piece of context to each chunk. That can be as simple as the document title and section heading ("Employee Handbook 2025 › Time Off › Part-time staff:"), or a one or two sentence summary that a model writes for each chunk by reading it alongside the whole document. The extra text is embedded (and can be included in the keyword index) along with the chunk. Anthropic has published a description of this technique; see Learn more. The cost is one model call per chunk at indexing time, which prompt caching can reduce because the same document is sent repeatedly.

Citations and grounding

An answer is grounded when it is based on retrieved sources rather than the model's general knowledge. Showing those sources lets users check the answer and builds trust. It also makes debugging much easier for you.

Today the tool returns one string, numbering each chunk: [1] …, [2] …. The model sees the numbers, but the user can't tell where they came from. With a source column you can return structured data instead:

execute: async ({ query }) => {
  // assumes searchDocuments now also selects documents.source
  const results = await searchDocuments(query, 3, 0.5);
  if (results.length === 0) {
    return { results: [], note: "No relevant information found in the knowledge base." };
  }
  return {
    results: results.map((r, i) => ({
      ref: i + 1,
      source: r.source,
      text: r.content,
    })),
  };
},

Tool results are part of the message stream, so the chat page can read them. Step 23 renders tool parts in the UI; a "Sources" list under the answer is the same idea, reading source from the searchKnowledgeBase output. Then tell the model in the system prompt to cite like "[1]". The step-22 prompt already says "Say which document facts you used". Citations don't guarantee correctness (a model can cite a source and still misread it), but they make errors visible.

Updates, deletes and duplicates

Documents change. The current project can only add chunks, which leads to two problems described in Indexing Explained ("When you must re-index"): an updated handbook leaves the old version's chunks behind, so the bot may quote outdated rules, and uploading the same PDF twice stores every chunk twice, filling the 3 result slots with copies.

With a source column, a "replace" becomes delete-then-insert in one transaction:

BEGIN;
DELETE FROM documents WHERE source = 'employee-handbook.pdf';
-- INSERT the new version's chunks here
COMMIT;

A transaction makes the two steps all-or-nothing, so a failed upload never leaves the knowledge base with neither version. For duplicates, you can check for an existing source before inserting, or store a hash of each chunk's text with a unique constraint. A cleaner long-term design is the separate sources table with a foreign key, described under "Document management" in step 17.

Access control: multi-tenant retrieval

If several companies or departments share one database, each user must only ever retrieve chunks they are allowed to see. A model can't be trusted to "ignore" chunks it shouldn't use: once text is in its context, it may repeat it. The filter must happen in the database query, using an identity the server trusts.

import { auth } from "@clerk/nextjs/server";
import { and, eq, gt } from "drizzle-orm";

const { orgId } = await auth();   // from the signed-in session, never from the model
// ...
.where(and(gt(similarity, threshold), eq(documents.orgId, orgId)))

Never let the model choose the filter. Don't add orgId to the tool's inputSchema. A user could say "search organisation 42's documents" (a form of prompt injection) and the model might comply. Read the identity from the session on the server, as step 16 does for roles. More in Security & Safety.

Agentic RAG

In classic RAG, the code always searches exactly once, before the model runs. In agentic RAG, the model decides whether to search, what to search for, and how many times. This project has been agentic from the start: search is a tool the model can call (step 15, with stopWhen: stepCountIs(2), enough for one search and an answer). Step 22 goes further: stepCountIs(6) and a system prompt that says "You may search more than once with different wording", so the model can search, see that the results don't cover the question, and search again with a better query. It can also combine search with the getCurrentDate and calculator tools.

Fixed pipelineAgentic
PredictabilityHigh: same steps every timeLower: the model chooses
Cost/latencyFixedVaries; more steps = more tokens
Handles small talk ("hi")Searches anywaySkips the search
Handles multi-part questionsOne search may miss partsCan search once per part

Always cap the number of steps (that's what stopWhen does). Agents and their patterns are covered in What Are AI Agents? and Agent Patterns.

Common failure modes and fixes

When the bot gives a bad answer, first find out which stage failed: look at what the tool returned (the onStepFinish logging from step 22 prints every tool call). If the right chunk was retrieved, the problem is generation. If it wasn't, the problem is retrieval or indexing.

How to measure

Every technique in this chapter is a trade: more quality for more latency, cost or complexity. The only way to know if a change helped is to measure before and after on the same set of questions. In short:

  • Build a small test set: 20–50 real questions, each with the chunk (or document section) that contains the answer and a reference answer. That's your ground truth.
  • Retrieval metrics: did the right chunk appear in the top k (hit rate, also called recall@k)? How high was it ranked (for example, mean reciprocal rank)? These need no model to judge and are cheap to run.
  • Answer metrics: is the answer correct, and is it faithful (supported by the retrieved chunks, not invented)? Often judged by a model (LLM-as-judge) plus spot checks by a human.
  • Change one thing at a time (chunk size, hybrid on/off, reranker on/off), rerun, compare.

The full method, with code, is in Evaluating AI Applications. Cost and latency monitoring is in Running AI in Production.

Common misconceptions

  • "A bigger context window means I don't need good retrieval." Stuffing in more chunks costs more, is slower, and models can still miss the one relevant sentence. Precise retrieval still matters.
  • "More techniques = better RAG." Each stage adds latency and new ways to fail. Add techniques in response to measured failures.
  • "Retrieval makes hallucinations impossible." It reduces them. The model can still misread or ignore sources, which is why citations and evaluation matter.
Recap
  • Diagnose first: was the right chunk retrieved? If not, fix indexing/retrieval; if yes, fix the prompt or model.
  • Chunking sets what can be found. This project uses 900/150 split on spaces; recursive defaults or heading-based splitting are easy upgrades.
  • Store metadata (source, page, section, org) with each chunk. It enables citations, updates, deduplication and access control.
  • Hybrid search adds keyword matching (Postgres tsvector + ts_rank) to vector search; reciprocal rank fusion merges the two lists by rank.
  • Reranking uses a slower, more accurate cross-encoder on a shortlist. Query rewriting, multi-query and HyDE improve the query.
  • Contextual retrieval prepends document context to each chunk before embedding.
  • Filter by tenant in SQL using the session, never via the model. Agentic RAG lets the model search multiple times, within a step cap.
  • Measure every change against a fixed test set.
