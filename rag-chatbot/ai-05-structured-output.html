Structured Output

Getting typed JSON instead of prose with generateObject and zod.

What you will learn

So far your chatbot produces prose: sentences written for a human to read. That is perfect for answering questions, but sometimes your code needs to use what the model produced: save a document's title in the database, decide which path a question should take, or show three clickable follow-up questions. For that you want structured output: data in a predictable shape, such as a JSON object with named fields, that your program can rely on.

In this chapter you will learn:

  • why prose is hard for programs to use;
  • what JSON and JSON Schema are;
  • how generateObject and streamObject from the AI SDK v5 turn a Zod schema into typed, validated data;
  • the output modes 'object', 'array', 'enum' and 'no-schema';
  • how to guide each field with .describe(), and how to handle failures (NoObjectGeneratedError);
  • three worked examples for this project: document metadata, question intent, and suggested follow-up questions;
  • when to use structured output and when to use tool calling.
Why this matters for your chatbot. Right now, an uploaded PDF becomes anonymous chunks: the documents table from step 9 stores only content and embedding. The bot cannot say which policy a chunk came from, which department owns it, or whether it is still in effect. One generateObject call at upload time could extract all of that. Structured output is also what powers routing, classification, form filling and most "AI feature inside a normal app" use cases.

Why prose is hard for programs

Imagine you ask a model "What is the title and effective date of this document?". You might get any of these:

  • "The title is Remote Work Policy and it takes effect on 1 March 2025."
  • "Title: Remote Work Policy. Effective: March 1st, 2025."
  • "Sure! This document, titled 'Remote Work Policy', becomes effective 2025-03-01. Let me know if you need anything else."

A human reads all three easily. Your code cannot. You could write a regular expression to pull out the title, but the wording changes from run to run, dates come in many formats, and one day the model will add a friendly sentence that breaks your pattern. This approach is fragile: it works in testing and fails in production.

What you really want is this, every time:

{
  "title": "Remote Work Policy",
  "effectiveDate": "2025-03-01"
}
New to JSON? The data format programs share

JSON (JavaScript Object Notation) is a text format for data. It has objects in curly braces with "key": value pairs, arrays in square brackets, and simple values: strings in double quotes, numbers, true/false and null (meaning "no value").

{
  "title": "Expense Policy",
  "pages": 4,
  "approved": true,
  "tags": ["finance", "travel"],
  "reviewDate": null
}

Almost every language can read JSON. In JavaScript, JSON.parse(text) turns JSON text into an object, and JSON.stringify(obj) does the reverse. Your browser and server already exchange JSON all the time, for example the { messages } body that useChat sends to /api/chat.

JSON Schema: describing the shape

JSON alone is not enough: you also need to say which fields, of which types, are expected. JSON Schema is a standard way to describe that, written in JSON itself. It says things like "this is an object; it has a title that is a string; department must be one of these values; these fields are required".

You will rarely write JSON Schema by hand. In this project you already describe shapes with Zod (the tool inputs in step 15), and the AI SDK converts Zod schemas into JSON Schema for you. A Zod schema like the metadata one later in this chapter becomes, roughly:

{
  "type": "object",
  "properties": {
    "title": { "type": "string", "description": "The document's title, exactly as written on it" },
    "department": {
      "type": "string",
      "enum": ["HR", "Finance", "IT", "Legal", "Operations", "Other"]
    },
    "effectiveDate": { "type": ["string", "null"] },
    "summary": { "type": "string" }
  },
  "required": ["title", "department", "effectiveDate", "summary"],
  "additionalProperties": false
}

This JSON Schema is what actually travels to the model provider. Many providers support a "structured outputs" or "JSON mode" feature that uses the schema to constrain what the model may generate, so the reply is valid JSON in the right shape. Where a provider lacks that, the AI SDK puts the schema into the prompt instead. Either way, the SDK checks the result against your schema before giving it to you.

generateObject: your first structured call

generateObject is the structured cousin of generateText. Instead of text, its result has an object field whose TypeScript type is inferred from your schema. The smallest possible example:

import { generateObject } from "ai";
import { openai } from "@ai-sdk/openai";
import { z } from "zod";

const { object } = await generateObject({
  model: openai("gpt-5-mini"),
  schema: z.object({
    title: z.string(),
    effectiveDate: z.string().nullable(),
  }),
  prompt: "Extract the title and effective date from: Remote Work Policy, effective 1 March 2025.",
});

console.log(object.title); // "Remote Work Policy"

Key options (checked against the AI SDK 5.0.47 type definitions used by this project):

OptionMeaning
modelThe model to call, exactly as in streamText.
schemaA Zod schema (or a JSON Schema via jsonSchema()). Required for 'object' and 'array' output.
output'object' (default), 'array', 'enum' or 'no-schema'. See the next section.
schemaName, schemaDescriptionOptional name and description of the whole output. Some providers use them as extra guidance.
mode'auto' (default and recommended), 'json' or 'tool': how the schema is delivered to the provider. Leave it on 'auto' unless you have a specific reason.
system, prompt, messagesThe same prompt options as generateText. Everything from chapter 4 still applies.
experimental_repairTextAn optional function that gets a chance to fix broken JSON text before parsing.

The result also includes usage (token counts), finishReason and the raw response, like generateText.

.describe(): hints for each field

Field names alone are often ambiguous. Is date the date the document was written, approved, or takes effect? In which format? Zod's .describe("…") attaches a description that ends up in the JSON Schema's description, which the model reads. You used this already: z.string().describe("The search query to find relevant documents") in the search tool.

Good descriptions say what the field means, its format and what to do when the information is missing:

effectiveDate: z
  .string()
  .nullable()
  .describe("Date the document takes effect, as YYYY-MM-DD, or null if the document doesn't state one"),

That last part ("or null if…") is the structured-output version of "say what to do when unsure" from chapter 4. Without it, a model that must produce a string will often invent a plausible date.

Tip: prefer .nullable() for "might be missing". A field that is .optional() may simply be left out; a field that is .nullable() is always present but may be null. Some providers' strict structured-output modes require every property to be present (OpenAI's strict mode, for example, which is an opt-in provider option in the @ai-sdk/openai version this project uses). Using .nullable() works everywhere and forces the model to make an explicit "not found" decision.

Worked example 1: extracting document metadata

Here is a complete helper that extracts a title, department, effective date and a one-line summary from the text of an uploaded document. It would live next to the other helpers in src/lib/.

// src/lib/extract-metadata.ts
import { generateObject, NoObjectGeneratedError } from "ai";
import { openai } from "@ai-sdk/openai";
import { z } from "zod";

export const documentMetadataSchema = z.object({
  title: z.string().describe("The document's title, exactly as written on it"),
  department: z
    .enum(["HR", "Finance", "IT", "Legal", "Operations", "Other"])
    .describe("The department that owns this document"),
  effectiveDate: z
    .string()
    .nullable()
    .describe("Date the document takes effect, as YYYY-MM-DD, or null if not stated"),
  summary: z.string().describe("One sentence describing what the document covers"),
});

export type DocumentMetadata = z.infer<typeof documentMetadataSchema>;

export async function extractMetadata(text: string): Promise<DocumentMetadata | null> {
  try {
    const { object } = await generateObject({
      model: openai("gpt-5-mini"),
      schema: documentMetadataSchema,
      schemaName: "DocumentMetadata",
      schemaDescription: "Metadata about a company document",
      prompt: `Extract metadata from the company document below.
Use only information found in the document.

<document>
${text.slice(0, 8000)}
</document>`,
    });
    return object;
  } catch (error) {
    if (NoObjectGeneratedError.isInstance(error)) {
      console.error("No valid metadata generated:", error.text);
      return null;
    }
    throw error;
  }
}

How you would add it to the project

The natural place is the upload server action, processFile in src/app/upload/actions.ts (step 12, updated in step 21). It already has the full extracted text before chunking. A sketch:

// after: const text = await extractText(file, buffer);
const metadata = await extractMetadata(text);

const chunks = await chunkContent(text);
const embeddings = await generateEmbeddings(chunks);

const records = chunks.map((chunk, index) => ({
  content: chunk,
  embedding: embeddings[index],
  title: metadata?.title ?? file.name,
  department: metadata?.department ?? null,
  effectiveDate: metadata?.effectiveDate ?? null,
}));

To make this work you would also need to:

  1. Add columns such as title, department and effectiveDate to the documents table in src/lib/db-schema.ts, then generate and run a migration as in step 9. (A cleaner design is a separate files table with one row per upload, and a reference from each chunk to its file, so metadata isn't repeated on every chunk.)
  2. Return the metadata from searchDocuments so the search tool can include it: [1] (HR · Leave Policy · effective 2025-03-01) …. Now the model can cite document titles and notice outdated policies.

Cost note: this adds one model call per upload. Uploads are rare and admin-only (step 16), so that is usually a good trade.

Worked example 2: classifying a question's intent

Classification is the simplest structured output: pick one label from a list. Use output: 'enum':

import { generateObject } from "ai";
import { openai } from "@ai-sdk/openai";

export async function classifyIntent(question: string) {
  const { object: intent } = await generateObject({
    model: openai("gpt-5-mini"),
    output: "enum",
    enum: ["policy_question", "calculation", "small_talk", "out_of_scope"],
    system: "Classify the employee's message. policy_question = about company rules, benefits or procedures. calculation = needs arithmetic only. small_talk = greetings or thanks. out_of_scope = anything else.",
    prompt: question,
  });
  return intent; // one of the four strings above
}

Notes:

  • With output: 'enum' you pass enum instead of schema. The SDK guarantees the result is one of those strings (or throws).
  • Define each label in the instructions. Label names alone ("calculation") leave edge cases unclear.
  • What could you do with it? Answer small_talk without tools, politely decline out_of_scope, or log intents to learn what employees actually ask. This is the routing pattern from chapter 10. Remember it adds a model call (and some latency) before every answer, so only add it if you use the result.

Worked example 3: suggested follow-up questions

After the bot answers, showing two or three clickable follow-up questions helps users explore. Use output: 'array': the schema describes one element, and you get back an array.

import { generateObject } from "ai";
import { openai } from "@ai-sdk/openai";
import { z } from "zod";

export async function suggestFollowUps(question: string, answer: string) {
  const { object } = await generateObject({
    model: openai("gpt-5-mini"),
    output: "array",
    schema: z.object({
      question: z.string().describe("A short follow-up question, under 12 words"),
    }),
    prompt: `An employee asked: <question>${question}</question>
The assistant answered: <answer>${answer}</answer>
Suggest 3 natural follow-up questions the company documents could answer.`,
  });
  return object.slice(0, 3).map((s) => s.question);
}

The prompt asks for 3, and the code also keeps at most 3 with slice(0, 3). Asking politely and then enforcing in code is a good habit: models usually follow counts, but your UI should never break if they don't.

Streaming it with streamObject

streamObject takes the same options but returns immediately and lets you read the object while it is being generated. Its result has a partialObjectStream (growing, incomplete versions of the object), an elementStream for 'array' output (each finished element as soon as it is complete), and helpers like toTextStreamResponse() for sending it from a route handler. On the client, the experimental_useObject hook from @ai-sdk/react reads that stream and gives you a growing object.

import { streamObject } from "ai";
import { openai } from "@ai-sdk/openai";
import { suggestionsSchema } from "./schema";
// ./schema.ts contains:
// export const suggestionsSchema = z.object({
//   questions: z.array(z.string()).describe("3 short follow-up questions"),
// });

export async function POST(req: Request) {
  const { question, answer } = await req.json();
  const result = streamObject({
    model: openai("gpt-5-mini"),
    schema: suggestionsSchema,
    prompt: `Question: ${question}\nAnswer: ${answer}\nSuggest 3 follow-up questions.`,
  });
  return result.toTextStreamResponse();
}
"use client";
import { experimental_useObject as useObject } from "@ai-sdk/react";
import { suggestionsSchema } from "@/app/api/suggestions/schema";

// inside your chat page component:
const { object, submit, isLoading } = useObject({
  api: "/api/suggestions",
  schema: suggestionsSchema,
});
// call submit({ question, answer }) when an answer finishes,
// then render object?.questions as buttons that send the text with sendMessage

Two practical notes: the schema lives in its own file (schema.ts next to the route) because both the server route and the "use client" page need it, and a Next.js route.ts file should only export HTTP handlers like POST; and because object is partial while streaming, use optional chaining (object?.questions) and expect some entries to be incomplete until loading ends. For something as short as three questions, plain generateObject is often simpler; streaming pays off for long objects that users watch appear.

Validation and errors

What can go wrong, and how the SDK reports it:

  • The model returns text that is not valid JSON (rare with providers' structured-output modes, possible with others) or JSON in the wrong shape (missing field, wrong type, value not in the enum). generateObject throws a NoObjectGeneratedError. It carries text (what the model actually wrote), cause (the parse or validation error), usage, response and finishReason. Log text: it tells you whether the problem is the prompt, the schema or the model.
  • The output is cut off because it hit a token limit. The JSON is incomplete, so parsing fails with the same error, and finishReason is "length". Fix: ask for less, or raise maxOutputTokens.
  • Network or provider errors (timeouts, rate limits, bad keys) are thrown as other error types; the SDK retries some automatically (maxRetries, default 2).

With streamObject, errors don't throw from the call itself (it returns immediately); use its onError callback, and the final object promise rejects if the finished object doesn't match the schema.

Valid is not the same as true. Schema validation proves the shape: effectiveDate is a string or null. It does not prove the date is correct, or even that it appears in the document. Models can still hallucinate values that fit the schema perfectly. For important fields, add checks in code (is the date a real date? does the title appear in the text?), keep a human in the loop for high-stakes data, and measure accuracy on real documents (chapter 12).
Common misconceptions
  • "I can just ask for JSON in the prompt and call JSON.parse." It works often, and fails sometimes: extra prose, code fences around the JSON, trailing commas, missing fields. generateObject handles the provider features, parsing and validation for you.
  • "Structured output makes the model smarter." It controls format, not knowledge. A wrong answer in a perfect JSON object is still wrong.
  • "Bigger schemas are fine." Deeply nested schemas with dozens of fields are harder for models to fill well. Prefer small, focused schemas, and split big extractions into several calls if needed.

Structured output vs tool calling

Tool calling (chapter 6) also makes the model produce JSON that matches a Zod schema: the tool's inputSchema. In fact one of generateObject's delivery modes, mode: 'tool', works by offering the model a single tool and forcing it to call it. So when should you use which?

Structured output (generateObject)Tool calling (tools in streamText)
PurposeThe JSON is the final result.The JSON is a request to act; your code runs and the model continues.
Who decidesYou always get an object (or an error).The model decides whether and which tool to call (unless you set toolChoice).
StepsOne call, one object.Often several steps: call tool, read result, answer.
Typical useExtraction, classification, generating data for your UI or database.Looking things up (search, date), doing things (calculator, sending email).
In this projectDocument metadata, intent, follow-ups (this chapter).searchKnowledgeBase, getCurrentDate, calculator (steps 15 and 22).

You can also combine them: generateText and streamText accept an experimental_output option (for example Output.object({ schema })) so an agent can use tools and then return a structured final answer. As the name says, it is experimental in AI SDK v5, so check the docs before relying on it.

Recap
  • Prose is for people; programs need structured data with a predictable shape.
  • JSON is the data format; JSON Schema describes its shape. You write Zod, the AI SDK converts it.
  • generateObject returns a parsed, validated, typed object; streamObject streams partial objects.
  • Output modes: 'object', 'array' (schema per element), 'enum' (pick a label), 'no-schema'.
  • Use .describe() to explain each field, its format, and what to do when information is missing; prefer .nullable().
  • Catch NoObjectGeneratedError and log its text. Remember: valid shape doesn't mean correct content.
  • Use structured output when the JSON is the result; use tool calling when the model needs to act and continue.
