Setting Up the Vector Database

Neon Postgres + pgvector + Drizzle schema and migrations.

▶ Watch this part (25:31)

The upload feature has three parts

  1. A UI where users upload documents. This project keeps it simple and only accepts PDFs.
  2. A server action that processes each PDF. It extracts the text, splits it into smaller chunks, and turns each chunk into a vector embedding with OpenAI's embedding model. Chunking makes semantic search more accurate and efficient, and it is a crucial step in RAG.
  3. A vector database to store the embeddings. This becomes the knowledge base you search when users ask questions.

You start with the database, because the embeddings need somewhere to go before you can process any PDFs.

New to databases? What databases, tables, rows and columns are

A database is a program that stores data permanently and lets you search it quickly. Unlike a variable in your code, data in a database survives when your app restarts or your computer turns off.

A relational database (like Postgres) organises data in tables, much like spreadsheets:

  • A table is one sheet, for one kind of thing. Here there will be one table called documents.
  • A column is one field every row has, with a fixed type: a number, some text, a vector…
  • A row is one record. Here, one row = one chunk of text from a PDF plus its embedding.

So after you upload a 10-page PDF, the documents table might look like this:

idcontentembedding
1"Employees get 25 vacation days per year…"[0.012, -0.034, … 1,536 numbers]
2"…per year. Unused days can be carried over…"[0.008, -0.021, …]
3"Remote work is allowed two days a week…"[-0.041, 0.017, …]

A vector database is simply a database that can also store vectors (long lists of numbers) and find the vectors closest to a given one. Postgres becomes a vector database once you add the pgvector extension, which you do on this page.

Part A: create a Neon project

Neon is serverless Postgres that supports vector operations (the pgvector extension), which makes it a good fit for storing embeddings.

"Serverless" here means you never install or run a database server yourself. Neon runs Postgres in the cloud for you, and it can pause the database when nobody uses it (that is why the free plan is cheap to offer). Your app talks to it over the internet.

  1. Create an account at neon.com.

    Click Sign up (or Get started). You can sign up with GitHub, Google or an email address. The free plan is enough for this whole project, and no credit card is needed.

  2. Create a project

    Right after signing up, Neon shows a Create project form (later you can reach it from the dashboard with New project). Fill it in like this:

    • Name: RAG Chatbot
    • Postgres version: 17
    • Cloud provider: AWS, in a region close to you

    Click Create project.

    A project is Neon's container for one database setup. It automatically contains a database called neondb and a user (a "role") that owns it. Picking a region close to you makes every query a little faster, because the data travels a shorter distance.

  3. Copy the connection string

    On the Connect to your database card, click Connect, then Copy snippet. Paste it into .env.local without the leading psql and quotes:

    OPENAI_API_KEY=sk-...
NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY=pk_test_...
CLERK_SECRET_KEY=sk_test_...
NEON_DATABASE_URL=postgresql://user:password@ep-xxxx.region.aws.neon.tech/neondb?sslmode=require

    The snippet Neon gives you is a command for psql (Postgres's own terminal client), so it looks like psql 'postgresql://…'. You only want the part inside the quotes. If your copied string ends with extra options such as &channel_binding=require, keep them: they are part of the address.

    That's all you need from the Neon console. Everything else is done in code.

New to connection strings? What each part means and why it's secret

A connection string is a single line of text that tells a program where the database is and how to log in. It is built like a web address:

postgresql://user:password@ep-xxxx.region.aws.neon.tech/neondb?sslmode=require
└─protocol─┘ └user┘└password┘└──────────host (the server)─────┘└db─┘└─options──┘
  • postgresql://: the kind of database to speak to.
  • user:password: the login. The real password is inside this string.
  • ep-xxxx…neon.tech: the address of your Neon database server.
  • /neondb: which database on that server.
  • ?sslmode=require: insist on an encrypted connection, so nobody can read the traffic.

Why it's secret: anyone who has this string can read, change or delete all your data. That is why it goes in .env.local (which create-next-app already lists in .gitignore, so Git never uploads it) and why its name does not start with NEXT_PUBLIC_: only variables with that prefix are sent to the browser. If you ever leak it, open the Neon console and reset the role's password, then paste the new string.

How to know it worked: .env.local (in your project root, next to package.json) now has a line starting with NEON_DATABASE_URL=postgresql://, with no spaces around = and no quotes or psql in front.

Common mistakes:

  • Leaving psql ' at the start or ' at the end. The driver then can't read the address and every database command fails.
  • Copying a string where the password is hidden as ****. If the snippet shows stars, click Show password (or the eye icon) before copying.
  • Naming the variable differently (for example DATABASE_URL). The code on this page reads NEON_DATABASE_URL exactly.

Part B: install the database packages

npm install @neondatabase/serverless drizzle-orm drizzle-kit dotenv

Run this in the terminal, inside your project folder. npm is Node's package manager, install downloads the listed packages into node_modules and records them in package.json. You can list several packages in one command, separated by spaces. A name starting with @ (like @neondatabase/serverless) is a scoped package: @neondatabase is the publisher, serverless is the package.

PackageRole
@neondatabase/serverlessNeon's database driver for TypeScript (queries over HTTP). A driver is the low-level piece that actually sends your queries to the database and brings back the results. Using HTTP instead of a long-lived connection suits serverless hosting, where your code starts and stops for each request.
drizzle-ormA type-safe ORM, so you write TypeScript instead of SQL. "Type-safe" means TypeScript knows your table's columns, so a typo like documents.contnet is flagged in your editor before you run anything.
drizzle-kitThe CLI for generating and running migrations (database changes). You use it with npx drizzle-kit … below. It is a development tool, used from the terminal, not by your app while it runs.
dotenvLoads environment variables. Needed because drizzle-kit and the db config run outside Next.js's own env loading.
New to SQL and ORMs? What they are and why Drizzle is used

SQL (Structured Query Language) is the language databases like Postgres understand. A few examples:

SELECT content FROM documents WHERE id = 1;          -- read
INSERT INTO documents (content) VALUES ('Hello');     -- add a row
CREATE TABLE notes (id serial PRIMARY KEY, body text); -- create a table

An ORM (Object-Relational Mapper) lets you do the same from your normal programming language. With Drizzle you write:

await db.insert(documents).values({ content: "Hello" });

and Drizzle turns it into the INSERT INTO … SQL for you. Benefits for a beginner: autocomplete for table and column names, type errors when you pass the wrong kind of value, and one place (the schema file) that describes your tables. Drizzle stays close to SQL, so what you learn transfers.

Part C: the database connection

Create src/lib/db-config.ts:

import { drizzle } from "drizzle-orm/neon-http";
import { neon } from "@neondatabase/serverless";
import { config } from "dotenv";

config({ path: ".env.local" });

const sql = neon(process.env.NEON_DATABASE_URL!);
export const db = drizzle(sql);
  • config({ path: ".env.local" }) loads the environment variables from .env.local.
  • neon(...) creates an SQL client from the connection string. The ! tells TypeScript the value is definitely set.
  • drizzle(sql) wraps the client in a Drizzle instance. db is what the rest of the app imports.

Part D: the schema

Create src/lib/db-schema.ts to define the documents table:

import { pgTable, serial, text, vector, index } from "drizzle-orm/pg-core";

export const documents = pgTable(
  "documents",
  {
    id: serial("id").primaryKey(),
    content: text("content").notNull(),
    embedding: vector("embedding", { dimensions: 1536 }), // text-embedding-3-small
  },
  (table) => [
    index("embeddingIndex").using(
      "hnsw",
      table.embedding.op("vector_cosine_ops")
    ),
  ]
);

export type InsertDocument = typeof documents.$inferInsert;
export type SelectDocument = typeof documents.$inferSelect;
Column / partMeaning
idAuto-incrementing primary key.
contentThe actual text chunk from the PDF (cannot be null).
embeddingA vector with 1,536 dimensions, the output size of OpenAI's text-embedding-3-small model. These two must always match.
Third argument → index(...)Creates an HNSW index (Hierarchical Navigable Small World) on the embedding using cosine distance. Searching vectors without an index is slow. HNSW makes similarity search fast. The syntax is boilerplate you can copy as-is.
$inferInsert / $inferSelectTypeScript types for inserting and reading rows, derived from the schema.

New to Postgres extensions? Why vector has to be switched on

Plain Postgres knows numbers, text, dates and so on, but not vectors. An extension is an add-on that teaches Postgres new tricks. pgvector adds:

  • a new column type, vector(n);
  • distance operators, such as <=> for cosine distance;
  • vector indexes such as HNSW.

Neon has pgvector installed on its servers, but each database must enable it once with CREATE EXTENSION vector;. Until then, any table using the vector type fails with an error like type "vector" does not exist. That's why Part F enables it first.

This tells Drizzle where the schema is, where to write migrations and how to connect.

Part F: enable pgvector, then create the table

New to migrations? What generate --custom, generate and migrate each do

A migration is a file of SQL that changes the database's structure (creating a table, adding a column, enabling an extension). Migrations are numbered and kept in your project, so the exact history of changes can be replayed on any new database, in the same order. Think of them as "save points" for your database's shape.

CommandWhat it doesTouches the database?
npx drizzle-kit generate --customCreates a new, empty numbered SQL file in migrations/ for you to fill in by hand. Used for things the schema file can't describe, like enabling an extension.No, it only writes a file.
npx drizzle-kit generateCompares your schema file with a snapshot of what earlier migrations already did, and writes a new SQL file containing only the differences (here: create the documents table and its index).No, it only writes a file.
npx drizzle-kit migrateConnects to the database and runs every migration file that hasn't been applied yet, in order. It records which ones ran in a bookkeeping table (__drizzle_migrations), so running it again does nothing.Yes. This is the only one that changes Neon.

In each command, npx runs a CLI tool from your project's node_modules, drizzle-kit is the tool, generate/migrate is the sub-command, and --custom is a flag (an option that changes how the sub-command behaves).

  1. Generate an empty custom migration

    Postgres needs the vector extension before it can store vectors. This is an important step.

    npx drizzle-kit generate --custom

    This creates a new, empty SQL file in migrations/.

    The file name is a number plus two random words (for example 0000_material_thaddeus_ross.sql). Yours will have different words; that's normal. The number at the front is what keeps the order.

  2. Add the extension to that file 
    -- Custom SQL migration file, put your code below! --
CREATE EXTENSION IF NOT EXISTS vector;
    Line(s)CodeWhat it does & why
    1-- Custom SQL migration file, put your code below! --A comment that drizzle-kit writes into every custom migration. In SQL, anything after -- on a line is ignored. You can leave it.
    2CREATE EXTENSION IF NOT EXISTS vector;The line you add. It enables pgvector in this database. IF NOT EXISTS makes it safe to run on a database where the extension is already on (it does nothing instead of throwing an error). The ; ends the SQL statement.
  3. Run the migration 
    npx drizzle-kit migrate

    You should see drizzle-kit report that migrations were applied, with no red error text.

  4. Check it in Neon

    Open the Neon console → SQL Editor and run:

    SELECT extname, extversion FROM pg_extension WHERE extname = 'vector';

    You should see vector listed with its version number.

    In words: "from Postgres's built-in list of enabled extensions (pg_extension), show the name and version of the one called vector". No rows means the migration didn't run.

  5. Generate the migration for the documents table 
    npx drizzle-kit generate

    A second migration file appears. It contains SQL roughly like this:

    CREATE TABLE "documents" (
	"id" serial PRIMARY KEY NOT NULL,
	"content" text NOT NULL,
	"embedding" vector(1536)
);
--> statement-breakpoint
CREATE INDEX "embeddingIndex" ON "documents" USING hnsw ("embedding" vector_cosine_ops);
    Line(s)CodeWhat it does & why
    1CREATE TABLE "documents" (Creates the table named in your schema. The double quotes are Postgres's way of quoting names exactly as written.
    2"id" serial PRIMARY KEY NOT NULL,The SQL for serial("id").primaryKey(): an auto-numbered integer that uniquely identifies each row.
    3"content" text NOT NULL,The SQL for text("content").notNull().
    4"embedding" vector(1536)The pgvector column with 1,536 dimensions. This line only works because migration 0000 enabled the extension first.
    5);Ends the column list and the CREATE TABLE statement.
    6--> statement-breakpointA marker drizzle-kit adds between statements. Some drivers can only run one statement at a time, so migrate splits the file here and runs each part separately. For SQL it is just a comment.
    7CREATE INDEX "embeddingIndex" ON "documents" USING hnsw ("embedding" vector_cosine_ops);The SQL for the third argument of pgTable: an HNSW index named embeddingIndex on the embedding column, organised for cosine distance.

    You never write this file by hand: drizzle-kit translated your TypeScript schema into it. Reading it is a good way to learn what your schema means in SQL.

  6. Apply it 
    npx drizzle-kit migrate

    Only the new file runs; migration 0000 is skipped because it is already recorded as applied.

  7. Check it in Neon

    In the console, open Tables. The documents table should be there with id, content and embedding (vector(1536)).

    The table is empty for now. Rows appear after you upload your first PDF in step 13.

Common mistakes:

  • Running the commands in the wrong folder. drizzle-kit looks for drizzle.config.ts in the current folder. Run them from the project root (where package.json is).
  • type "vector" does not exist when migrating: the extension migration is missing or empty. Check that the 0000 file contains the CREATE EXTENSION line and that its number is lower than the table migration's.
  • Running generate before generate --custom. The table migration then gets number 0000 and runs first, causing the error above. Delete the generated files (the SQL file and the migrations/meta folder) and start Part F again in the right order, as long as you haven't migrated yet.
  • Editing a migration after it has been applied. migrate won't run it again. Make changes in the schema and run generate to get a new migration instead.
  • Connection errors (url is undefined, password authentication failed): recheck the NEON_DATABASE_URL line in .env.local.

Why index at all, and how does HNSW work? Without the index, every question compares its vector with every stored row. The Indexing Explained page covers the problem, how the layered graph works, the operator classes, the costs, and an important catch: the search query has to sort by distance for this index to be used.

Why a separate custom migration? The extension must exist before the CREATE TABLE that uses the vector type runs. Putting it in its own earlier migration keeps the order correct on every new database you set up.

  • The documents table stores each text chunk and its 1,536-dimension embedding, with an HNSW index for fast cosine-similarity search.
