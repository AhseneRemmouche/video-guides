Prompting vs RAG vs Fine-Tuning

A decision guide, plus local and open models.

Sooner or later every AI project hits the same question: "The model doesn't do what I want. Should I write a better prompt, add my documents with RAG, or train my own model?" Beginners often jump straight to the most impressive-sounding answer, which is usually "fine-tune it". This chapter gives you a calm, practical way to decide.

You will learn:

  • what prompting, RAG and fine-tuning each are, in plain words;
  • the single most important difference: RAG changes what the model knows, fine-tuning changes how it behaves;
  • a decision flowchart and a comparison table you can reuse on real projects;
  • how the three combine, and when the real answer is tools, structured output or an agent instead;
  • what open-weight and local models are (for example with Ollama), what hardware they need, what quantization means, and the trade-offs;
  • what "distillation" means, at a high level;
  • four worked scenarios, each with a recommended approach.
Why this matters for your chatbot. The chatbot you built in Part 1 already uses two of the three techniques: a carefully written system prompt (prompting) and a searchKnowledgeBase tool over your PDFs (RAG, step 15). In step 22 it also became an agent with several tools. Understanding why those choices were made, and why fine-tuning was not used, will help you make the right call when you extend it or start your next project.

Three ways to make a model do what you want

An LLM arrives "pre-trained": it has read an enormous amount of public text and learned general language skills. Out of the box it knows nothing about your company, and it has its own default style. There are three main levers to adapt it.

A helpful analogy: imagine you hire a very smart new employee.

  • Prompting is handing them a clear instruction sheet on their first day: "You answer HR questions. Be concise. If you don't know, say so."
  • RAG is giving them access to the company's reference binder and telling them: "Before answering, look it up." They don't memorise the binder. They read the right page each time.
  • Fine-tuning is sending them on a training course that reshapes their habits: how they write, which format they use, how they handle certain kinds of request. After the course they behave differently by default, without needing the instruction sheet every time.

Notice that the training course is the slowest and most expensive option, and it is the worst way to teach someone facts that change every month. That intuition carries over almost exactly to LLMs.

Prompting: instructions and examples in the input

Prompting means changing only the text you send to the model. Nothing about the model itself changes. You write a system prompt that describes the role, the rules and the output style, and you may add a few examples of good answers (this is called few-shot prompting). Chapter 4, Prompt Engineering, covers the craft in depth.

This project's chat route (step 5, extended in step 15) shows prompting in action. The system prompt from the original repo:

system: `You are a helpful assistant with access to a knowledge base.
          When users ask questions, search the knowledge base for relevant information.
          Always search before answering if the question might relate to uploaded documents.
          Base your answers on the search results when available. Give concise answers that correctly answer what the user is asking for. Do not flood them with all the information from the search results.`,

Every sentence is a behaviour you wanted: use the knowledge base, search first, stay grounded, be concise. You got all that without training anything.

Strengths: instant to change (edit a string, save, reload), free to try, works with any model, easy to version in Git. Limits: the instructions are re-sent on every request, so very long prompts cost more tokens and add latency. A prompt also can't give the model facts it doesn't have, and it can't hold more than fits in the context window.

RAG: give the model the right facts at question time

RAG (Retrieval-Augmented Generation) is what Part 1 of this guide built. When a question arrives, you search your own documents for the most relevant passages and put them into the model's input, so it can answer from them. In this project:

  1. PDFs are split into chunks (step 11).
  2. Each chunk is turned into an embedding (step 10) and stored in Postgres with pgvector (step 9, step 12).
  3. At question time, the model calls the searchKnowledgeBase tool, which runs a semantic search (step 14) and returns the top passages.
  4. The model writes an answer grounded in those passages (step 15).

The model itself is unchanged. What changes is the knowledge it can see for this one question. Upload a new policy PDF and the very next question can use it. Delete a document and it's gone from answers.

Strengths: knowledge stays fresh, you can show which passage an answer came from (citations), you can control who sees which documents, and you don't need a machine-learning team. Limits: answers are only as good as retrieval. If search returns the wrong chunk, the model answers from the wrong facts. There is also extra work per question (embed the query, query the database). Chapter 8, Advanced RAG, shows how to improve retrieval.

Fine-tuning: change the model's default behaviour

New to training? What "training a model" actually means

A model is a huge set of numbers called weights (also parameters). Training means showing the model examples and nudging those numbers, little by little, so its outputs get closer to the examples. Pre-training does this on a vast amount of general text. It takes enormous computing power and is done by the model's creator.

Fine-tuning is a second, much smaller round of training that starts from an already-trained model and nudges it with your examples. The result is a new version of the model (or a small add-on to it) that behaves the way your examples did, even without being told.

Using a model to produce answers, as your chatbot does on every request, is called inference. Training changes the model. Inference only uses it.

For fine-tuning you prepare many example conversations that show the ideal answer. Several providers, including OpenAI, accept training data as a file with one JSON example per line (often called JSONL). A single example looks roughly like this (format shown for illustration; always follow your provider's current fine-tuning guide):

{"messages": [
  {"role": "system", "content": "You are Acme's support assistant."},
  {"role": "user", "content": "Can I return shoes I wore once?"},
  {"role": "assistant", "content": "Short answer: yes, within 30 days. Here's how: 1) ... 2) ..."}
]}

(In a real file each example sits on one single line. It is spread out here so you can read it.) You upload the file, start a training job, wait, and receive a new model name that you use like any other model.

What fine-tuning changes, and what it doesn't

Fine-tuning is good at teaching behaviour:

  • Style and tone: always sound like your brand, always use British spelling, always be very brief.
  • Format: always answer in a specific layout, such as a summary line followed by numbered steps.
  • Narrow skills: classify support tickets into your 12 categories, or extract fields from a document type the base model handles poorly.
  • Shorter prompts: behaviour that used to need a long system prompt and many examples becomes the default, so each request is smaller.

Fine-tuning is a poor way to teach knowledge:

  • The model doesn't store your documents like a database. It absorbs patterns. It may remember a fact, half-remember it, or blend it with something else, and it will still hallucinate confidently.
  • Facts go stale. When the vacation policy changes, you'd have to prepare new data and train again.
  • You can't point to a source. The model can't say "this came from page 4 of the handbook", because the fact is now spread through its weights.
  • You can't easily enforce permissions. If a fact is in the weights, every user of that model can potentially get it out.
Common misconception: "Fine-tune the model on our documents so it knows them." This is the most frequent beginner mistake in this area. Fine-tuning on raw documents mostly teaches the model to sound like your documents, not to reliably recall them. For "answer questions about our documents", use RAG. Step 2 makes the same point: RAG updates instantly, fine-tuning needs retraining every time content changes.

The key idea: knowledge vs behaviour

If you remember one thing from this chapter, make it this:

RAG changes what the model knows (for this question). Fine-tuning changes how the model behaves (for every question). Prompting is the cheap, instant way to try both, and it's always your first step.

Ask yourself: is the problem that the model doesn't know something, or that it knows enough but does it the wrong way?

  • "It doesn't know our refund policy" is a knowledge problem, so reach for RAG.
  • "It knows, but answers are too long and in the wrong tone" is a behaviour problem, so improve the prompt first, and only consider fine-tuning if the prompt can't get you there reliably.
  • "It needs to look at today's order status" is neither. It's an action / live data problem, so give it a tool (more on that below).

A decision flowchart

Here is a rule-of-thumb flowchart. It isn't a law, but it gets most real projects to a sensible starting point. Read it top to bottom. A "yes" sends you right to an approach. Several can be "yes" at once, in which case you combine approaches.

Two things about the flowchart are worth spelling out:

  • Prompting is always the start. Every other approach still needs a good prompt. Even a fine-tuned model gets a system prompt.
  • "Good enough" must be measured, not guessed. Before you decide that prompting has failed, build a small test set of real questions with expected answers and check results consistently. That's the subject of Chapter 12, Evaluating AI Applications. Fine-tuning without an eval means you can't tell whether it helped.

Combining them

These are not rivals. Real systems mix them, because each solves a different problem:

  • Prompting + RAG is the most common combination, and it's exactly what this project does. The prompt says how to use the knowledge base ("search first, base your answer on the results, be concise"). RAG supplies what to answer with.
  • RAG + fine-tuning: a company might fine-tune a model to always answer in its strict support format and brand voice, and use RAG so the facts in that answer come from up-to-date documents. Fine-tuning handles the form, RAG handles the content.
  • Prompting + tools + RAG: the agent from step 22 combines a detailed system prompt, a knowledge-base search tool, a date tool and a calculator.

A sensible order to add them: prompt first, then RAG if knowledge is missing, then tools if actions or live data are needed, and fine-tuning last, only if evaluation shows a behaviour gap the others can't close. This is a rule of thumb, not a law, but it keeps cost and complexity down.

When tools, structured output or agents are the answer instead

Many problems that look like "the model needs more knowledge" or "the model needs training" are really one of these:

The model needs live data or must do something: tools

RAG is for documents that change now and then. It isn't for data that changes every second (stock levels, order status, today's date) or for actions (book a meeting, create a ticket). For those, give the model a tool: a function it can call that queries the live system or performs the action. You did exactly this in step 22: instead of hoping the model knows today's date, it calls getCurrentDate. Instead of hoping it does arithmetic right, it calls calculator. The system prompt says so explicitly:

2. If the answer depends on today's date, call getCurrentDate.
3. For any arithmetic, call calculator instead of calculating in your head.

No amount of fine-tuning makes a model reliably know today's date. A three-line tool does. See Chapter 6, Tool Calling in Depth.

The task has several steps: an agent

If answering takes several decisions in a row ("search the policy, check the date, calculate the remaining days, then answer"), you need an agent: a model that calls tools in a loop until it's done. That's what stopWhen: stepCountIs(6) enables in the step 22 route. See Chapter 9, What Are AI Agents?.

Code must read the output: structured output

If another program reads the model's answer, for example to fill a form or save to a database, you need data in an exact shape. Fine-tuning can make a format more likely, but structured output makes it enforced: you describe the shape with a zod schema and the AI SDK validates the model's answer against it.

import { generateObject } from "ai";
import { openai } from "@ai-sdk/openai";
import { z } from "zod";

const { object } = await generateObject({
  model: openai("gpt-5-mini"),
  schema: z.object({
    category: z.enum(["benefits", "leave", "payroll", "other"]),
    urgent: z.boolean(),
  }),
  prompt: "Classify this HR question: 'My salary was not paid this month!'",
});
// object is typed: { category: "benefits" | "leave" | "payroll" | "other"; urgent: boolean }

See Chapter 5, Structured Output.

Open and local models

So far everything has used OpenAI's hosted models through the internet. There is another family of options: open-weight models that you can download and run yourself, even on your own laptop.

New to open weights? What "open" means for a model

A model's weights are the numbers it learned during training. With a hosted, closed model you never see the weights: you send text to the provider's API and get text back. With an open-weight model, the creator publishes the weights as files you can download and run on your own hardware.

"Open weights" is not always the same as "open source" in the strict software sense. Each model comes with its own license, and some licenses restrict commercial use, the number of users, or certain purposes. Always read the license of the exact model you download (Chapter 16 comes back to this).

Running a model locally

A local model runs on your own machine or server instead of a provider's cloud. Tools such as Ollama make this approachable: you install it, download a model with one command, and it runs a small local server that your code can call. Other tools exist too. The model families available change quickly, so browse the tool's model library rather than relying on a list in a book.

Why would you do this?

  • Privacy and data control. Prompts and documents never leave your machine or your company network. This can matter for sensitive data, although "local" doesn't remove your other data-protection duties.
  • Offline use and no per-request bill. Once downloaded, the model runs without internet and without per-token fees. You pay instead in hardware and electricity.
  • Control. The model never changes or disappears unless you change it, which helps reproducibility. You can also fine-tune open weights yourself.
  • Learning. Running a model yourself teaches you a lot about tokens, speed and memory.

Hardware: why GPUs and memory matter

Running a model means doing a huge number of multiplications for every token it generates. A GPU (graphics card) does many of these in parallel, so it's much faster than a normal processor (CPU) for this work. Some computers share one pool of memory between CPU and GPU, which also works well.

The main limit is memory: the model's weights must fit in your GPU memory (or system memory) to run at a useful speed. Bigger models, meaning more parameters, need more memory and run slower, but are generally more capable. Small models can run on an ordinary laptop. Large ones need serious hardware. Rule of thumb: start with a small model, check that it works for your task, and only move up if you need to.

Quantization: shrinking models to fit

Quantization stores each weight with fewer bits, for example a rough 4-bit number instead of a precise 16-bit one. Think of it like saving a photo as a smaller, more compressed JPEG: the file is much smaller and loads faster, and most of the time you can barely tell the difference, but some detail is lost. Quantized models use far less memory, which is often what makes local use possible at all. The cost is some loss of quality, which tends to grow as you squeeze harder. Local-model tools usually offer several quantized versions of the same model so you can choose your trade-off.

Using a local model from this project's code

Many local runtimes, Ollama included, can expose an OpenAI-compatible endpoint: a local URL that accepts the same request format as OpenAI's API. That means the AI SDK's OpenAI provider can talk to it if you point it at a different base URL. A sketch:

import { createOpenAI } from "@ai-sdk/openai";
import { streamText } from "ai";

// Point the OpenAI provider at a local, OpenAI-compatible server.
// The URL and model name come from your local tool's documentation.
const local = createOpenAI({
  baseURL: process.env.LOCAL_LLM_BASE_URL, // e.g. a localhost URL ending in /v1
  apiKey: "not-needed-locally",            // some servers ignore it, the SDK still expects a value
});

const result = streamText({
  model: local.chat("your-local-model-name"), // .chat() uses the widely supported Chat Completions format
  prompt: "Explain RAG in one sentence.",
});

Notes for beginners:

  • createOpenAI creates a custom OpenAI provider. baseURL tells it where to send requests instead of OpenAI's servers. Keep the URL in .env.local like any other setting.
  • local.chat(…) asks for the Chat Completions request format, which OpenAI-compatible servers most commonly implement. In AI SDK v5, plain openai("…") uses OpenAI's newer Responses API, which local servers may not support.
  • The AI SDK also has a dedicated OpenAI-compatible provider package and community providers for specific local tools. See the providers section of the AI SDK docs.
  • Embeddings are a separate decision. This project's schema declares vector("embedding", { dimensions: 1536 }) because text-embedding-3-small produces 1,536 numbers. A local embedding model will usually produce a different number of dimensions, and vectors from different models can't be compared with each other. Switching embedding models means changing the column, running a migration and re-embedding every document.
Pitfall: "local" doesn't mean "same behaviour". If you swap the hosted model for a small local one, tool calling and instruction-following may get noticeably worse. The agent from step 22 might stop calling tools when it should, or format calls incorrectly. Re-run your test questions after any model change.

Distillation, briefly

Distillation means training a smaller "student" model to imitate a larger "teacher" model. You run the big, expensive model on many inputs, collect its answers, and fine-tune the small model on those input/answer pairs. The student ends up much better at that kind of task than it would be on its own, while staying small, fast and cheap to run.

Many of the small models you can download were produced partly this way. Some providers also offer distillation workflows on their platforms. Two cautions: a student usually doesn't fully match its teacher, especially outside the tasks it was trained on, and model providers' terms of use may restrict using their outputs to train other models. Read the terms before you try it.

Worked scenarios

Here's how the reasoning plays out on four realistic requests.

1. "An HR chatbot that answers questions about our policies"

Answer: RAG (plus a good prompt). This is a knowledge problem: the facts are private, live in documents, and change over time. It's exactly the project you built. Fine-tuning would be slower, stale after the next policy update, and unable to cite sources or respect who may see which document. Improve it with better chunking, citations that show which document was used, and an eval set (Chapters 8 and 12).

2. "Every answer must sound like our brand voice"

Answer: prompting first; fine-tuning if prompting can't make it consistent. This is a behaviour problem. Start with a system prompt that describes the voice, plus a few short examples of on-brand answers. Measure it on a set of typical questions. If the voice is still inconsistent across many requests, or the examples make every prompt too long and costly, a fine-tune on a few hundred high-quality, on-brand examples is a reasonable next step. If the bot also answers factual questions, keep RAG for the facts.

3. "The output must be valid JSON that our system imports"

Answer: structured output. Describe the exact shape with a schema and use generateObject or streamObject. The SDK checks the result against the schema, so your code gets typed data or a clear error. Fine-tuning a format only makes it likely, never guaranteed.

4. "Employees should be able to request leave from the chat"

Answer: tools / an agent. This is an action, not knowledge. Give the agent a tool such as createLeaveRequest that calls your HR system, keep RAG for the leave policy, and keep a human in the loop: show the request and ask the user to confirm before it is submitted (Chapter 10). No amount of training lets a model submit a form by itself.

A quick self-test. For any new idea, finish this sentence: "The model is failing because it…". "…doesn't know X" points to RAG. "…knows X but says it the wrong way" points to prompting, then fine-tuning. "…can't do or see X right now" points to tools. "…returns X in a shape my code can't read" points to structured output.
Pitfalls
  • Fine-tuning too early. It's the slowest and most expensive option to iterate on. Exhaust prompting and fix retrieval first.
  • Blaming the model for bad retrieval. If the RAG bot gives wrong answers, check what the search returned first (log the tool results, as step 22 does with onStepFinish). Often the fix is chunking or search, not the model.
  • Stuffing everything into the prompt. Pasting all your documents into the system prompt "works" for tiny demos, then breaks the context window and your budget as content grows. That's the problem RAG solves.
  • No evaluation. Without a test set you can't tell whether a change (new prompt, new model, fine-tune) made things better or worse.
  • Ignoring licenses and terms. Open-weight model licenses and provider terms differ. Read them before building a product on a model or on its outputs.
Recap
  • Prompting changes the instructions, RAG changes the knowledge the model sees, and fine-tuning changes the model's default behaviour.
  • Always start with a good prompt and a small evaluation set.
  • Use RAG for private or changing facts. It stays fresh, can cite sources and can respect permissions. That's why this project uses it.
  • Use fine-tuning for style, format or narrow skills at scale, not to "teach documents".
  • Use tools or agents for live data and actions, and structured output when code must read the answer.
  • Open-weight and local models (for example via Ollama) trade capability and convenience for privacy and control. Quantization makes them fit on smaller hardware at some cost in quality.
  • A local model with an OpenAI-compatible endpoint can be used from the AI SDK with createOpenAI({ baseURL }), but test tool calling and remember that embeddings must all come from the same model.
  • Distillation trains a small model to imitate a big one for a specific job.
