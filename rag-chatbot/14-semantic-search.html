Implementing Semantic Search

Cosine-similarity search over the stored embeddings.

▶ Watch this part (54:22)

Goal

Write searchDocuments(query), a function that finds the stored chunks closest in meaning to a natural-language question. The presenter calls it "the heart of our RAG system".

This is the "retrieval" in RAG (Retrieval-Augmented Generation): before the AI answers, you retrieve the few pieces of your documents that matter for the question. Normal keyword search looks for the same words. Semantic search looks for the same meaning.

Cosine similarity in one paragraph

Every chunk and every query is a vector. Cosine distance measures how dissimilar two vectors are by the angle between them: 0 means they point the same way. pgvector computes this distance, and 1 − distance turns it into a similarity score, where higher is more similar. You keep only results above a threshold, sort by similarity, and take the top few. The HNSW index from step 9 keeps this fast even with thousands of rows.

New to cosine similarity? The intuition, without the maths

An embedding is a list of numbers (here 1,536 of them) that describes the meaning of a piece of text. You can picture it as an arrow pointing somewhere in a huge space. Texts about similar things point in similar directions.

Imagine just two dimensions, like arrows on a sheet of paper:

  • "How many vacation days do I get?" and "PTO allowance for employees" point almost the same way. The angle between them is small.
  • "How many vacation days do I get?" and "Expense reports must include receipts" point in quite different directions. The angle is large.

Cosine similarity turns that angle into a score: 1 = same direction (same meaning), 0 = unrelated (at right angles), −1 = opposite. It ignores the arrows' length and only cares about direction, which is what you want for meaning.

pgvector gives you the distance, which is simply 1 − similarity: 0 = identical direction, 2 = opposite. Small distance = close in meaning. So "similarity above 0.5" is the same as "distance below 0.5".

DistanceSimilarity (1 − distance)Meaning
0.10.9Very close in meaning
0.50.5The threshold: just on the edge
0.80.2Mostly unrelated, filtered out

Step by step

  1. Create src/lib/search.ts and import from Drizzle
    HelperPurpose
    cosineDistanceBuilds the SQL for the pgvector cosine distance between a column and a vector.
    descSorts in descending order.
    gt"Greater than", for the threshold filter.
    sqlWrites raw SQL expressions when needed.

    Also import db, the documents table and generateEmbedding (the single-text version).

  2. Define the signature
    • query: string: what the user is searching for.
    • limit: number = 5: how many results to return.
    • threshold: number = 0.5: the minimum similarity. Anything below 0.5 is ignored.
  3. Embed the query with await generateEmbedding(query).
  4. Compute similarity

    sql<number>`1 - (${cosineDistance(documents.embedding, embedding)})`. This is one SQL expression, calculated by the database for every row.

  5. Query the most relevant chunks

    Select id, content and the computed similarity; then .where(gt(similarity, threshold)), .orderBy(desc(similarity)) and .limit(limit). Return the result.

New to query builders? How Drizzle turns method calls into SQL

A database understands SQL, a language of commands like SELECT … FROM … WHERE … ORDER BY … LIMIT …. An ORM such as Drizzle lets you build that command with TypeScript methods instead of writing a string by hand. Each method adds one clause:

DrizzleSQL it adds
db.select({ … })SELECT id, content, …
.from(documents)FROM documents
.where(gt(similarity, 0.5))WHERE … > 0.5
.orderBy(desc(similarity))ORDER BY … DESC
.limit(5)LIMIT 5

Nothing is sent to the database until you await the chain. The benefits: typos in column names become TypeScript errors, the result has the right types, and values are passed safely as parameters.

New to the sql template tag? What sql<number>`…` means

A template literal is a string in backticks where ${…} inserts a value: `Hello ${name}`. Putting a function name right before the backticks makes it a tagged template: the function receives the text pieces and the inserted values separately, and decides what to do with them.

Drizzle's sql tag uses this to build a piece of raw SQL safely. Text you write goes into the query as-is; values inserted with ${…} are either SQL pieces (like the result of cosineDistance(…), a column) or become parameters (like $1), never pasted in as text. That prevents SQL injection.

The <number> part is a TypeScript generic: it tells TypeScript "this expression produces a number". It doesn't change the SQL; it only gives similarity the right type in the results.

Complete file (tutorial version)

// src/lib/search.ts
import { cosineDistance, desc, gt, sql } from "drizzle-orm";
import { db } from "./db-config";
import { documents } from "./db-schema";
import { generateEmbedding } from "./embeddings";

/**
 * Search for similar documents using Drizzle ORM with cosineDistance
 */
export async function searchDocuments(
  query: string,
  limit: number = 5,
  threshold: number = 0.5
) {
  // Generate embedding for the search query
  const embedding = await generateEmbedding(query);

  // Calculate similarity using Drizzle's cosineDistance function
  // This creates a SQL expression for similarity calculation
  const similarity = sql<number>`1 - (${cosineDistance(
    documents.embedding,
    embedding
  )})`;

  // Use Drizzle's query builder for the search
  const similarDocuments = await db
    .select({
      id: documents.id,
      content: documents.content,
      similarity,
    })
    .from(documents)
    .where(gt(similarity, threshold))
    .orderBy(desc(similarity))
    .limit(limit);

  return similarDocuments;
}

The return type is inferred as { id: number; content: string; similarity: number }[].

Roughly the SQL that runs

SELECT id, content, 1 - (embedding <=> $1) AS similarity
FROM documents
WHERE 1 - (embedding <=> $1) > 0.5
ORDER BY similarity DESC
LIMIT 5;

<=> is pgvector's cosine-distance operator. The vector_cosine_ops HNSW index speeds up queries that order by this distance, ascending, which this query does not (see below).

$1 is a placeholder: the query vector is sent separately from the SQL text, as a parameter.

New to database indexes? Why "uses the index" matters

An index is like the index at the back of a book: instead of reading every page to find a word, you jump straight to the right pages. Without an index, the database does a sequential scan: it computes the distance for every row, then sorts them all.

The HNSW index from step 9 is a special index for vectors that can find the nearest vectors quickly (approximately, but very accurately). Postgres decides by itself whether to use an index; it only can when the query asks for exactly what the index was built for. You can check its decision with EXPLAIN.

Important: this query does not use the HNSW index. pgvector only uses the index when the query sorts by the raw distance (embedding <=> …, ascending). This query sorts by 1 - distance, descending. That's the same order mathematically, but Postgres can't tell, so every question scans and sorts the whole table. This was verified on pgvector 0.8.0 with the repo's schema and Drizzle's generated SQL. It doesn't matter for one handbook, but it does as the knowledge base grows. The fix is one line: sort by the distance instead.

Recommended version (uses the index)

// src/lib/search.ts
import { cosineDistance, gt, sql } from "drizzle-orm";
import { db } from "./db-config";
import { documents } from "./db-schema";
import { generateEmbedding } from "./embeddings";

/**
 * Search for similar documents using Drizzle ORM with cosineDistance
 */
export async function searchDocuments(
  query: string,
  limit: number = 5,
  threshold: number = 0.5,
) {
  // Generate embedding for the search query
  const embedding = await generateEmbedding(query);

  // Cosine distance: 0 = same direction, 2 = opposite. This is what the HNSW index sorts by.
  const distance = cosineDistance(documents.embedding, embedding);

  // Similarity = 1 - distance, used for the threshold and returned to the caller
  const similarity = sql<number>`1 - (${distance})`;

  const similarDocuments = await db
    .select({
      id: documents.id,
      content: documents.content,
      similarity,
    })
    .from(documents)
    .where(gt(similarity, threshold))
    // Order by the raw distance (ascending) so Postgres can use the HNSW index
    .orderBy(distance)
    .limit(limit);

  return similarDocuments;
}

Tuning the threshold. If the bot says it found nothing for questions you know are covered, lower the threshold (for example to 0.3). If it pulls in unrelated chunks, raise it. The best value depends on the embedding model and your chunk size.

Common mistakes

  • Using generateEmbeddings (plural) for the query: it expects an array and returns an array of vectors, which doesn't fit cosineDistance.
  • Different embedding models for chunks and queries: similarity scores become meaningless. Both must be text-embedding-3-small.
  • Keeping desc with the distance, as in .orderBy(desc(distance)): that returns the least similar chunks first.
  • Empty results every time: check that the documents table actually has rows (upload a PDF in step 13), then try a lower threshold.

How to know it worked: there's no page for this function yet, so you'll test it through the chatbot in step 15. For now, it's enough that the file has no red TypeScript errors in your editor.
