Turn the Chatbot into an AI Agent

Several tools, multi-step reasoning and step logging: a real agent loop.

Goal

Right now your chatbot has one tool, searchKnowledgeBase, and at most two steps: search once, then answer (step 15). In this step you turn it into a small AI agent:

  • Several tools. Next to the knowledge-base search, the model gets a getCurrentDate tool and a calculator tool.
  • The model chooses the order. You don't write "first search, then calculate". The model looks at the question and the tool descriptions and decides which tool to call next, based on what it has learned so far.
  • Up to 6 steps. Instead of stopping after two model calls, the loop may run up to six, so the model can search, check the date, do some maths and then answer.
  • Step logging. Every step is printed in the terminal, so you can watch the agent think.

Only two files are involved: you replace src/app/api/chat/route.ts and add a new helper, src/lib/calculator.ts. The chat page doesn't change in this step. In step 23 you'll make the agent's steps visible in the browser too.

New to AI agents? What makes an agent different from a chatbot

A plain chatbot does one thing per question: it sends your message to the LLM and shows the reply. With tool calling, the model can ask your code to run a function (like a search) and then use the result. That is already a small step towards an agent.

An agent goes further: it runs in a loop. In each round (a step) the model looks at everything it knows so far and decides: "Do I call another tool, or do I have enough to answer?" It keeps going until it answers or hits a limit you set.

A real-life comparison: a chatbot is like a librarian who answers from memory. An agent is like a librarian who can walk to the shelves, check the calendar on the wall, use a calculator, and come back with an answer, choosing for themselves which of those to do and in what order.

The three ingredients you'll see in the code are: tools (what the agent can do), a system prompt (how it should work) and a stop condition (when it must stop). The handbook chapter What Are AI Agents? explains the idea in depth.

Read the diagram from left to right: the question goes to the model. In each step the model either asks for a tool (top) or writes the answer (bottom). A tool's result goes back to the model, which starts the next step. The loop repeats, and it is stopped after 6 steps at the latest, even if the model still wants more tools.

The three tools and why each one exists

ToolWhat it doesWhy the model needs it
searchKnowledgeBaseFinds the 3 most relevant chunks of your uploaded documents (unchanged from step 15).The model has never seen your company's documents. Without this tool it would guess, or invent an answer (a hallucination).
getCurrentDateReturns today's date from the server's clock, in two formats.A model doesn't know what day it is. It only knows what was in its training data, which stops at a cutoff date months or years in the past. Questions like "is the deadline next week?" need the real date.
calculatorEvaluates a maths expression such as 2000 * 0.15 exactly, using the mathjs library.Models are unreliable at arithmetic. They often get simple sums right, but they can slip on longer numbers, percentages or several operations in a row. A calculator is always exact, and it's cheap.
New to these model limits? Why a model can't tell the date or count reliably

The date. An LLM is a frozen snapshot. It was trained on text up to a certain point in time (its training cutoff) and then stopped learning. When you ask it today's date, there's nothing in the conversation that says so, so it can only guess, and the guess is usually somewhere around its cutoff. Your server, on the other hand, has a clock. The getCurrentDate tool simply lets the model read that clock.

Arithmetic. An LLM doesn't calculate the way a calculator does. It reads and writes tokens (pieces of words and numbers) and predicts the most likely next token. A number like 1234567 may be split into several tokens, and the model "predicts" the digits of the result instead of computing them. Often the prediction is right; sometimes it's confidently wrong. Handing the maths to real code removes that risk.

The general lesson: let the model decide what to do, and let ordinary code do things that must be exact.

    New to evaluating expressions safely? Why not just use JavaScript's eval

    JavaScript has a built-in function, eval, that runs any string as code. eval("2 + 2") gives 4, so it may look like a free calculator. Never use it on text you don't control. eval doesn't only do maths: it can run any JavaScript, including code that reads your environment variables (your API keys), deletes files or calls other servers.

    Where does the expression come from? The model writes it. And the model is influenced by the user's message and by your documents, so a user (or a sneaky sentence inside an uploaded PDF) could try to make the model send something nasty. This is called prompt injection. Treat everything a model sends to a tool as untrusted input, exactly like data from a web form.

    mathjs has its own parser that only understands maths, not JavaScript, which is already much safer. Switching off the six risky functions and capping the length closes the remaining gaps that the mathjs documentation warns about. The handbook chapter Security & Safety for AI Apps covers this way of thinking in detail.

    // src/app/api/chat/route.ts
import {
  convertToModelMessages,
  type InferUITools,
  stepCountIs,
  streamText,
  tool,
  type UIDataTypes,
  type UIMessage,
} from "ai";
import { openai } from "@ai-sdk/openai";
import { z } from "zod";
import { searchDocuments } from "@/lib/search";
import { calculate } from "@/lib/calculator";

const tools = {
  searchKnowledgeBase: tool({
    description: "Search the knowledge base for relevant information",
    inputSchema: z.object({
      query: z.string().describe("The search query to find relevant documents"),
    }),
    execute: async ({ query }) => {
      try {
        const results = await searchDocuments(query, 3, 0.5);

        if (results.length === 0) {
          return "No relevant information found in the knowledge base.";
        }

        return results.map((r, i) => `[${i + 1}] ${r.content}`).join("\n\n");
      } catch (error) {
        console.error("Search error:", error);
        return "Error searching the knowledge base.";
      }
    },
  }),

  getCurrentDate: tool({
    description:
      "Get today's date. Use it whenever a question depends on the current date, such as deadlines or how long until or since a date.",
    inputSchema: z.object({}),
    execute: async () => {
      const now = new Date();
      return {
        isoDate: now.toISOString().slice(0, 10),
        readable: now.toLocaleDateString("en-US", {
          weekday: "long",
          year: "numeric",
          month: "long",
          day: "numeric",
        }),
      };
    },
  }),

  calculator: tool({
    description:
      "Evaluate a math expression and return the exact result. Always use this for arithmetic instead of calculating yourself. Supports + - * / ^, parentheses, and percentages written as decimals (15% of 2000 is 0.15 * 2000).",
    inputSchema: z.object({
      expression: z
        .string()
        .describe(
          'A math expression, for example "2000 * 0.15" or "(20 - 3) * 8"',
        ),
    }),
    execute: async ({ expression }) => {
      try {
        return { expression, result: calculate(expression) };
      } catch (error) {
        return {
          expression,
          error: error instanceof Error ? error.message : "Invalid expression",
        };
      }
    },
  }),
};

export type ChatTools = InferUITools<typeof tools>;
export type ChatMessage = UIMessage<never, UIDataTypes, ChatTools>;

const SYSTEM_PROMPT = `You are a helpful company assistant with access to tools.

Tools:
- searchKnowledgeBase: look up company documents (policies, benefits, procedures).
- getCurrentDate: get today's date.
- calculator: do any arithmetic exactly.

How to work:
1. If the question might relate to company documents, search the knowledge base first. You may search more than once with different wording.
2. If the answer depends on today's date, call getCurrentDate.
3. For any arithmetic, call calculator instead of calculating in your head.
4. Combine the results and give a concise answer. Say which document facts you used.
5. If the tools don't give you the information, say so honestly instead of guessing.

If the user attaches images, look at them carefully and use what you see together with the knowledge base.`;

export async function POST(req: Request) {
  try {
    const { messages }: { messages: ChatMessage[] } = await req.json();

    const result = streamText({
      model: openai("gpt-5-mini"),
      messages: convertToModelMessages(messages),
      tools,
      system: SYSTEM_PROMPT,
      // An agent may need several tool calls before it can answer
      stopWhen: stepCountIs(6),
      onStepFinish: ({ toolCalls, finishReason }) => {
        for (const call of toolCalls) {
          console.log(`[agent] called ${call.toolName}`, call.input);
        }
        console.log(`[agent] step finished: ${finishReason}`);
      },
    });

    return result.toUIMessageStreamResponse();
  } catch (error) {
    console.error("Error streaming chat completion:", error);
    return new Response("Failed to stream chat completion", { status: 500 });
  }
}

Why 6 steps?

A step is one call to the model. A question like "If I start my vacation 10 days from today, did I give enough notice?" might need: one or two searches, one date lookup, one calculation, and one final step to write the answer. That's about 4–5 steps. Six leaves a little room for a retry (for example a second search with different words, or a corrected calculator expression).

The limit is a safety belt, not a target. It exists because:

  • Every step costs money and time. Each step sends the whole conversation plus all earlier tool results to the model again, so later steps are bigger than earlier ones. Ten steps can easily cost several times more than two (see cost control).
  • Models can loop. A confused model might search for the same thing again and again. A hard cap guarantees the request ends.

Six is a rule of thumb for this app's three tools, not a magic number. If you add more tools or harder tasks, count how many tool calls a typical hard question needs, add one for the answer and one or two for retries.

What happens at the limit: if step 6 still ends with a tool call, the loop simply stops there. The model never gets the step in which it would have written its answer, so the user may see no reply text. In the terminal you'd see six "step finished: tool-calls" lines in a row. If that happens often, the tool descriptions or the prompt are probably unclear, rather than the limit being too low.

New to callbacks and server logs? Where onStepFinish's output appears

A callback is a function you hand to another piece of code, which calls it later when something happens. Here you give onStepFinish to streamText, and the AI SDK calls it each time a step completes. You don't call it yourself.

console.log prints wherever the code is running. route.ts is a route handler, so it runs on the server, which during development is the npm run dev process. That's why the [agent] lines appear in the terminal where you started npm run dev, not in the browser's DevTools console. (Code in the chat page, a Client Component, logs to the browser console instead. See server vs client.)

Logging each step is the simplest form of observability: being able to see what your AI app actually did, not just its final answer.

A worked example

Suppose the handbook PDF you uploaded says vacation requests must be submitted at least two weeks in advance (the example handbook in the video does). A user asks:

"If I start my vacation 10 days from today, did I give enough notice?"

Here is how the agent might work through it. This is an illustrative trace, not captured output: the real model may pick different search words, call the tools in a slightly different order, or call two tools in the same step. The date is an example.

StepThe model decides…Tool callTool result
1"This is about a company rule. Search first."searchKnowledgeBase({ query: "vacation request notice period" })"[1] … Vacation requests must be submitted at least two weeks in advance through the HR portal …"
2"The answer depends on today's date."getCurrentDate({}){ isoDate: "2025-03-03", readable: "Monday, March 3, 2025" }
3"Two weeks is 14 days. How far short is 10 days?"calculator({ expression: "14 - 10" }){ expression: "14 - 10", result: "4" }
4"I have everything. Answer."noneFinal answer, for example: "No. The policy requires at least two weeks' notice (14 days). Starting on Thursday, March 13, gives only 10 days, 4 days short. Submit the request through the HR portal and consider moving your start date to March 17 or later."

In the terminal, that run would print something like this (also illustrative):

[agent] called searchKnowledgeBase { query: 'vacation request notice period' }
[agent] step finished: tool-calls
[agent] called getCurrentDate {}
[agent] step finished: tool-calls
[agent] called calculator { expression: '14 - 10' }
[agent] step finished: tool-calls
[agent] step finished: stop

Notice what nobody programmed: the order. You never wrote "search, then date, then calculator". The model chose it from the question, the tool descriptions and the system prompt. Also notice that the step-4 dates ("March 13", "March 17") were worked out by the model itself, since the calculator only does numbers, not calendar dates. Check such details when you test. The handbook chapter Agent Patterns, Memory & Multi-Agent Systems compares this "let the model decide" style with fixed workflows.

Test it

Save both files. Keep the terminal running npm run dev visible next to the browser, open http://localhost:3000/chat, sign in and try these questions:

  1. Date only: "What's today's date?" → one getCurrentDate call, then the answer. The date should match your computer's calendar.
  2. Maths only: "What is 17.5% of 2,340?" → a calculator call with something like 0.175 * 2340; the answer should be 409.5.
  3. Documents + maths: "What's 15% of the annual education budget?" → a search (the handbook says $2,000, see step 15), then calculator with 2000 * 0.15 → 300.
  4. Documents + date + maths: the vacation-notice question from the worked example above.
  5. No tools needed: "Hi!" → the model should answer directly: a single "step finished: stop" line and no tool calls. (Because the prompt says "search first" for anything that might be about the documents, an occasional unnecessary search is possible.)

How to know it worked: for each question the terminal shows [agent] called … lines with sensible inputs, a step finished: tool-calls after each tool step, and a final step finished: stop. The chat shows only the final answer for now; that's expected. Step 23 adds the tool calls to the page.

Common mistakes:

  • "Module not found: Can't resolve 'mathjs'" – npm install mathjs wasn't run, or was run in another folder. Run it in the folder that contains package.json, then restart npm run dev.
  • "Module not found: Can't resolve '@/lib/calculator'" – the helper is missing or misnamed. It must be exactly src/lib/calculator.ts.
  • You look for the [agent] lines in the browser console – they are server logs. Look in the terminal running npm run dev.
  • The page fails to compile – check the backticks of SYSTEM_PROMPT: one at the start (line 82) and one before the ; at the end (line 96).
  • The date is off by one day – isoDate is in UTC, while readable uses the server's own time zone. Around midnight they can differ. On many hosting platforms servers run in UTC. If the exact day matters for your users, pass their time zone to toLocaleDateString (the timeZone option).

Pitfalls

  • Too many steps, too much cost. Raising stepCountIs to 20 "just in case" means a confused model can make 20 paid calls, each bigger than the last. Keep the cap low and watch the logs: if a question regularly needs many steps, improve the tools or the prompt instead.
  • Vague tool descriptions. The model chooses tools almost entirely from their names and descriptions. "Does math" or "date" is too thin. Say what the tool does, when to use it and what input format it expects, with an example, the way the calculator's description does. The handbook chapter Tool Calling in Depth has a checklist for good tool design.
  • The model doesn't call a tool. Sometimes it does the maths "in its head" or guesses the date anyway. Make the instruction explicit in both the description and the system prompt (as this file does: "Always use this for arithmetic"), and test with questions where the tool is clearly needed. Tool use is likely, not guaranteed.
  • Trusting tool input. Whatever the model sends to a tool can be influenced by users and documents. Validate it (zod), limit it (the 200-character cap) and never pass it to eval, a shell command or raw SQL. See Security & Safety for AI Apps.
  • Tools that crash. If execute throws, the tool result becomes an error. Returning a clear error message instead (as the search and calculator tools do) lets the model explain the problem or retry.
Recap
  • An agent is a model in a loop: in each step it decides whether to call a tool or answer, and you cap the loop with stopWhen: stepCountIs(6).
  • getCurrentDate gives the model the real date; calculator (mathjs, locked down and length-limited) gives it exact arithmetic.
  • Clear tool descriptions and a numbered system prompt steer which tools the model uses and in what order. You don't hard-code the order.
  • onStepFinish logs every step to the terminal running npm run dev, so you can see what the agent did.
