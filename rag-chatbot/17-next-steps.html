What you built

A complete RAG chatbot, built from scratch. Here is the full request flow, as the presenter summarises it:

  1. The user enters a prompt in the chat UI (/chat, built with AI Elements and useChat).
  2. The prompt goes to the route handler (POST /api/chat), which Clerk middleware protects.
  3. The model calls the search tool (searchKnowledgeBase), which runs a semantic search over the vector database (searchDocuments → cosine similarity in Neon/pgvector).
  4. The relevant content is found and formatted as numbered snippets and combined with the user's prompt in the model's context.
  5. The AI writes a natural-language answer grounded in those snippets.
  6. The answer streams back to the user.

Around that loop you also have authentication (only signed-in users can chat) and role-based access control (only admins can add knowledge through /upload).

Reading the diagram, box by box

  • The top bar: Clerk middleware. It sits across the whole width because every request passes through it first (step 8 and step 16). It checks two things: are you signed in (otherwise you go to sign-in), and, for /upload only, are you an admin (otherwise you go to the home page).
  • Top row, left to right: the "ask a question" path.
    • /chat is the page in the browser. useChat keeps the conversation and sends it to the server; AI Elements draw the chat bubbles and the input box.
    • /api/chat is the route handler on the server. streamText talks to OpenAI, allowing 2 steps (tool call, then answer).
    • searchKnowledgeBase is the tool. When the model calls it, it embeds the query and asks the database for the top 3 chunks with similarity of at least 0.5.
    • Neon · pgvector is the database in the cloud. The documents table holds every chunk and its embedding; the HNSW index helps find nearest vectors fast.
  • Bottom row: the "add knowledge" path.
    • /upload is the admin page with the PDF file input.
    • processPdfFile is the server action. Its pipeline, read left to right: pdf-parse pulls the text out of the PDF → chunkContent splits it into overlapping pieces → generateEmbeddings turns each piece into a vector → insert saves them.
    • The arrow that turns upward into the Neon box shows that both paths meet in the same table: uploads write chunks, chat questions read them.

Ideas for extending it

The video suggests three directions. Here is what each could involve:

IdeaWhere to start
Support more file types (DOCX, TXT, Markdown, web pages)In processPdfFile, branch on file.type and use a different text extractor for each type. The chunking and embedding steps stay the same.
Document management (list, delete, re-upload)Add a sources table (file name, uploader, date) and a sourceId foreign key on documents, so you can delete all of one file's chunks together. Build an admin-only list page.
Tune the chunking strategyThis guide already raised them to chunkSize: 900 / chunkOverlap: 150 (step 11). Next, try the default separators (paragraph → line → space), and adjust the search limit and threshold to match.

The three ideas in plain words

  • More file types. Right now only PDFs work, because pdf-parse only reads PDFs. Every file type needs its own "text extractor", a small piece of code or library that pulls plain text out. A .txt or Markdown file is the easiest: await file.text() already gives you the text. A Word file (DOCX) needs a library that understands its format; a web page needs to be downloaded and stripped of its HTML tags. Once you have plain text, the rest of the pipeline (chunk, embed, insert) is identical. file.type is the file's MIME type, a label like "application/pdf" or "text/plain" that tells you which extractor to use.
  • Document management. At the moment the database stores chunks but forgets which file they came from. If a handbook changes, you can't remove its old chunks. A second table, sources, gives each uploaded file one row. Each chunk then stores the id of its source in a foreign key column (sourceId): a column that points to a row in another table. Deleting a file then means "delete all chunks with this sourceId, then the source row". You'd add these tables with a new migration, like in step 9.
  • Chunking strategy. How you cut text into chunks strongly affects answer quality. Chunks that are too small lose context ("it costs $2,000" — what does?); chunks that are too big mix several topics and match questions less precisely. Separators are where the splitter prefers to cut: ideally between paragraphs, then between lines, then between words, so sentences stay whole. After changing chunk sizes, re-upload your documents and re-check the search limit and threshold, since bigger chunks mean fewer are needed per answer.

More ideas (not from the video)

  • Cite sources: return the chunk id or file name from the tool and render a tool-searchKnowledgeBase part in the chat, so users can see where an answer came from.
  • Per-team knowledge: store an orgId on each chunk and filter by it in searchDocuments (Clerk Organizations).
  • Re-ranking: fetch the top 10 by vector similarity, then re-rank them with a cross-encoder or an LLM before passing the top 3 to the model.
  • Server-side role check inside processPdfFile (see the note on step 16).

In plain words: citing sources means showing users which document snippets the answer was based on, so they can trust and check it. Per-team knowledge means each company or department only searches its own documents; storing an orgId on each chunk and adding a WHERE orgId = … filter keeps them apart. Re-ranking is a two-pass search: a fast, rough vector search picks 10 candidates, then a slower, more careful model reads each one with the question and picks the best 3. A cross-encoder is a model built for exactly that job: it scores how well a question and a passage match.

New to npm and npx? The words that appear in every command
  • npm is the Node.js package manager. It downloads packages (code other people published) into node_modules and records them in package.json.
  • npm install X adds package X to your project. You can list several packages separated by spaces.
  • -D (short for --save-dev) marks a package as a dev dependency: needed while developing or building, not by the running app. Type packages (@types/…) are a typical example.
  • npx runs a command-line tool from a package, downloading it temporarily if needed, instead of installing it into your project.
  • @latest asks for the newest published version of that tool.
  • A name starting with @, like @clerk/nextjs, is a scoped package: @clerk is the organisation, nextjs the package.
  • Everything after # on a line is a comment, written here for you; the terminal ignores it.

Run every command in the project folder (the one containing package.json). Running them elsewhere installs packages into the wrong place.

New to environment variables? Why secrets live in .env.local

An environment variable is a named setting given to your program from the outside, instead of being written in the code. Your code reads it with process.env.NAME.

Next.js loads .env.local automatically when the dev server starts. Keeping keys there means they never appear in your source code, and the file is listed in .gitignore so it's never uploaded to GitHub. Anyone with your API key can spend your money or read your data.

Two rules to remember: the file is only read at start-up, so restart npm run dev after editing it; and only variables whose name starts with NEXT_PUBLIC_ are sent to the browser. All others stay on the server.

Variable by variable

LineVariableWhat it is & where it's used
1OPENAI_API_KEY=sk-...Your secret OpenAI key (created in the OpenAI dashboard and added in step 4). The @ai-sdk/openai provider reads this exact name automatically for chat and embeddings. Server-only: never prefix it with NEXT_PUBLIC_.
2NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY=pk_test_...Clerk's publishable key (step 7). It's meant to be public: the browser needs it so Clerk's sign-in components know which Clerk app they belong to, hence the NEXT_PUBLIC_ prefix. pk_test_ means a development instance.
3CLERK_SECRET_KEY=sk_test_...Clerk's secret key. Used on the server (middleware, auth()) to verify sessions and call Clerk's backend. Must stay private.
4NEON_DATABASE_URL=postgresql://...neon.tech/neondb?sslmode=requireThe connection string for your Neon database (step 9): protocol postgresql://, then user and password, host (….neon.tech), database name (neondb) and sslmode=require (always use an encrypted connection). Read in db-config.ts and drizzle.config.ts. It contains a password, so keep it secret.

Common mistakes: spaces around = or quotes copied from a web page can break a value; a typo in a variable name (for example OPEN_AI_API_KEY) means the code reads undefined; and forgetting to restart the dev server means old values are still used. If you ever commit a key to Git by accident, revoke it in the provider's dashboard and create a new one.
