Indexing Explained

What indexing means in RAG, why we do it, and how the HNSW index works.

Two meanings of "indexing"

In a RAG app, "indexing" refers to two related but different things. This project does both:

1 · Indexing your documents2 · The database index (HNSW)
WhatTurning each PDF into stored, searchable rows: text → chunks → embeddings → database.A data structure in Postgres that finds the closest vectors without comparing against every row.
WhenOnce per document, at upload time.Created once by a migration, then updated automatically on every insert.
WhySo a question can be answered by looking up a few passages instead of reading every document.So that lookup stays fast as the knowledge base grows from dozens of rows to millions.
WhereStep 10, 11, 12, 13 (and 21)Step 9 (created), step 14 (used)

Think of a textbook. Part 1 is writing the index at the back of the book: someone reads the book once and records which topics are on which pages. Part 2 is sorting that index alphabetically, so you can jump to the right entry instead of reading the whole index line by line.

New to database indexes? The phone-book analogy

Imagine a phone book with a million names printed in random order. To find "Martin, Sarah" you would have to read every line until you hit it. That's what a database does on a table with no index: a sequential scan, row after row.

A real phone book is sorted alphabetically. You open it near the middle, see "L", jump forward to "M", and find Sarah in a few seconds without looking at 99.9% of the pages. A database index is that sorted structure: a separate, organised copy of one column (plus a pointer back to each row) that lets the database jump close to the answer.

  • An index speeds up reads that can use its ordering.
  • It slows down writes a little, because every new row must also be filed in the right place in the index.
  • It takes extra space, like the pages of an index at the back of a book.

Alphabetical order works for names. Vectors of 1,536 numbers can't be sorted alphabetically, so they need a special kind of index, HNSW, explained in Part 2.

Part 1: Indexing your documents

Why not just give the model all the documents?

The simplest alternative to RAG is to paste every document into every prompt. It breaks down quickly:

  • It doesn't fit. A model's context window is limited. One handbook may fit, but a company's thousands of PDFs never will.
  • It's expensive and slow. You pay for every input token on every question, and the model has to read all of it before it answers.
  • Answers get worse. Models are less reliable at finding one sentence buried in a huge context than in a short, relevant one.

RAG sends the model only the 3 most relevant chunks. To find those chunks quickly, the documents must be prepared in advance, and that preparation is indexing.

Why prepare in advance instead of at question time?

Search by meaning (semantic search) compares embeddings. If embeddings were computed when a question arrives, every question would have to embed every chunk of every document. That's thousands of API calls per question. Indexing moves that work to upload time:

Done whenEmbedding calls
Upload a PDF (indexing)Once per document1 batched call for all its chunks (embedMany)
Ask a question (retrieval)Every question1 call, for the question only (embed)

This is the core trade-off of RAG: do the heavy work once when you write the data, so every read is cheap.

The indexing pipeline in this project

  1. Extract. pdf-parse pulls the raw text out of the PDF. Images and scans need a vision model instead (step 21).
  2. Chunk. chunkContent splits the text into overlapping pieces (step 11). Why: one embedding for a whole document is a blur of every topic in it. Small chunks let the search return exactly the paragraph about vacation days.
  3. Embed. generateEmbeddings turns every chunk into a 1,536-number vector in one API call (step 10). Why: vectors are what make search by meaning possible. "PTO" and "vacation days" end up close together.
  4. Store. Each chunk is inserted as a row with its text and its vector (step 12). The text is kept so it can be handed to the model later. The vector is what gets searched.
  5. Index. Postgres adds each new row to the HNSW index automatically. You never call it yourself. See Part 2.

What one indexed row looks like

{
  "id": 7,
  "content": "Employees with 0–2 years of service receive 15 days of PTO annually. Employees with 3–5 years receive 20 days. Vacation requests should be submitted at least two weeks in advance through the HR portal. …",
  "embedding": [0.0123, -0.0347, 0.0082, …, -0.0191]   // 1,536 numbers
}

Part 2: The database index (HNSW)

The problem: searching without an index

To answer "which chunks are closest to this question?", the database could compare the question's vector with every stored vector, sort all of them, and keep the top 3. That's called a sequential scan, and its cost grows with the table:

Rows (chunks)Number crunching per question (rows × 1,536)In practice
30 (one handbook)~46 thousand operationsInstant. An index doesn't matter yet.
100,000~154 millionNoticeable on every question.
10,000,000~15 billionFar too slow for a chat.

The solution: an approximate nearest-neighbour index

HNSW (Hierarchical Navigable Small World) organises the vectors as a layered graph. Each vector is linked to a handful of its nearest neighbours:

  • It is approximate (ANN, approximate nearest neighbour). It can occasionally miss one of the true top results, in exchange for being dramatically faster. With realistic, clustered embeddings recall is typically very high. In a test for this page, 3,000 clustered 1,536-dimension vectors gave the same top 3 as an exact search in 100% of 30 queries, about 8× faster. The gap grows with table size.
  • Uniformly random vectors are the worst case: everything is about equally far from everything else, and recall drops. Real embeddings aren't like that.
New to "approximate" search? What recall means and why a rare miss is acceptable

An exact search checks every row, so it is guaranteed to return the true 3 closest chunks. An approximate search only checks the rows it reaches by walking the graph, so once in a while it may return, say, the 4th-closest chunk instead of the 3rd-closest.

Recall measures how often it gets it right: "100% recall" means the approximate top 3 were exactly the same as the exact top 3. Think of asking a local for directions: they get you to the right street almost every time, much faster than checking every street on a map.

For RAG, a rare near-miss barely matters. The chunks that are found are still very close in meaning, and the model only needs relevant passages, not mathematically perfect ones.

The index definition, line by line

(table) => [
  index("embeddingIndex").using(
    "hnsw",
    table.embedding.op("vector_cosine_ops")
  ),
]
PartMeaning
index("embeddingIndex")The index's name in Postgres. You will see it in query plans.

The resulting SQL, from the repo's migration:

CREATE INDEX "embeddingIndex" ON "documents" USING hnsw ("embedding" vector_cosine_ops);

The operator class must match the query

Operator classSQL operatorDrizzle helperDistance
vector_cosine_ops ✓ (this project)<=>cosineDistanceCosine: compares direction, which suits text embeddings

An index built with vector_cosine_ops can only speed up queries that sort by <=>, ascending, with a LIMIT.

What an index costs

  • Slower inserts: every new chunk has to be linked into the graph. Uploads take a little longer, which is fine because uploads are rare and questions are frequent.
  • Memory and disk: the graph is stored next to the table and is fastest when it fits in RAM.
  • Tuning knobs (pgvector defaults shown): m = 16 (links per node) and ef_construction = 64 (build effort), set with WITH (m = 16, ef_construction = 64); plus hnsw.ef_search = 40 (search effort per query, set with SET hnsw.ef_search = 100;). Higher values improve recall but cost speed. The defaults are fine for this project.

Part 3: Does the tutorial's search actually use the index?

No, as written it doesn't. The search in step 14 sorts by similarity, descending: .orderBy(desc(similarity)) where similarity = 1 - distance. Mathematically that's the same order as distance ascending, but Postgres can't see that. It only uses the HNSW index when the ORDER BY is the raw <=> expression in ascending order. So every question does a full scan and sort, and the index the tutorial creates sits unused.

How this was verified

This was tested on Postgres with pgvector 0.8.0 (via PGlite), using the repo's exact table and index migrations and the SQL that Drizzle generates for search.ts:

QueryORDER BY (generated by Drizzle)Plan at 5,000 rows
Tutorial (desc(similarity))1 - (embedding <=> $4) descSort over a full scan. Index not used, even with sequential scans disabled.
Fixed (orderBy(distance))embedding <=> $4Index Scan using "embeddingIndex"

The fix: sort by distance

Keep computing similarity for the threshold and the result, but sort by the raw distance. Results are the same, and Postgres can now use the index. This version was type-checked against the repo:

// src/lib/search.ts
import { cosineDistance, gt, sql } from "drizzle-orm";
import { db } from "./db-config";
import { documents } from "./db-schema";
import { generateEmbedding } from "./embeddings";

/**
 * Search for similar documents using Drizzle ORM with cosineDistance
 */
export async function searchDocuments(
  query: string,
  limit: number = 5,
  threshold: number = 0.5,
) {
  // Generate embedding for the search query
  const embedding = await generateEmbedding(query);

  // Cosine distance: 0 = same direction, 2 = opposite. This is what the HNSW index sorts by.
  const distance = cosineDistance(documents.embedding, embedding);

  // Similarity = 1 - distance, used for the threshold and returned to the caller
  const similarity = sql<number>`1 - (${distance})`;

  const similarDocuments = await db
    .select({
      id: documents.id,
      content: documents.content,
      similarity,
    })
    .from(documents)
    .where(gt(similarity, threshold))
    // Order by the raw distance (ascending) so Postgres can use the HNSW index
    .orderBy(distance)
    .limit(limit);

  return similarDocuments;
}

Check it yourself in Neon

Paste this into Neon's SQL Editor (in the Neon console, open your project and choose SQL Editor in the sidebar). It borrows a stored vector as the "question", so you don't have to paste 1,536 numbers:

EXPLAIN
SELECT id FROM documents
ORDER BY embedding <=> (SELECT embedding FROM documents LIMIT 1)
LIMIT 3;

New to EXPLAIN? How to read a query plan

EXPLAIN shows the plan Postgres chose: the steps it will take to answer your query. The output is a small tree of lines. Read it from the most indented lines upwards: inner steps run first and feed their rows to the step above them.

-- illustrative shape only: your names and numbers will differ
Limit  (cost=… rows=3 width=…)
  InitPlan 1
    ->  Limit  (cost=… rows=1 width=…)
          ->  Seq Scan on documents documents_1  (cost=… rows=… width=…)
  ->  Index Scan using "embeddingIndex" on documents  (cost=… rows=… width=…)
        Order By: (embedding <=> …)
  • Node names say what happens: Seq Scan = read every row; Index Scan using "…" = use that index; Sort = sort rows in memory; Limit = stop after N rows.
  • cost=A..B is Postgres's own estimate in abstract units: A is the cost before the first row comes out, B the total. Only compare costs of plans in the same database; they aren't milliseconds.
  • rows is how many rows it expects; width is the expected average row size in bytes.
  • InitPlan is a subquery that runs once before the main query, here the one that fetches the sample vector.

EXPLAIN ANALYZE actually runs the query and adds real timings. The exact layout of the output varies a little between Postgres versions.

  • Look for Index Scan using "embeddingIndex" in the output.
  • A small Seq Scan line for the subquery is normal. The output also shows a Seq Scan for the subquery (SELECT embedding FROM documents LIMIT 1) that fetches the sample vector. That line is expected. What matters is whether the ORDER BY uses Index Scan using "embeddingIndex".
  • On a small table you'll see a Seq Scan even with the fix. That's correct: with a few dozen rows, reading them all is cheaper than walking a graph, so Postgres chooses the scan. In testing, the switch to the index happened somewhere between 30 and 5,000 rows. The fix matters as your knowledge base grows.
  • Replace the ORDER BY line with ORDER BY 1 - (embedding <=> (SELECT embedding FROM documents LIMIT 1)) DESC to see the tutorial's plan, which always sorts.
Recap
  • Indexing documents (extract → chunk → embed → store) happens once per upload, so each question only needs to embed itself and look up 3 chunks. That's why RAG is cheap, fast and current.
  • The HNSW index lets Postgres find the nearest vectors without comparing every row. It's approximate, but very accurate on real embeddings.
  • The index only helps a query that orders by the matching distance operator (<=>, ascending). Use .orderBy(distance) in search.ts so the index the tutorial creates is actually used.
  • Re-index (clear and re-upload) after changing chunking or the embedding model, and watch out for duplicate uploads.
