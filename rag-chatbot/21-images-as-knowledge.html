Images & Scanned PDFs as Knowledge

Make images and scanned PDFs searchable with a vision model.

Extension · code type-checked against the repo

Goal

So far the knowledge base only learns from PDFs that contain real text. This step adds two sources:

  • Images: a photo of a notice board, a screenshot of a policy, a diagram or a whiteboard.
  • Scanned PDFs: PDFs that are just pictures of pages. In step 12 they failed with "No text found in PDF".

The approach is to let a vision model read the file and return its text, then reuse the existing chunk → embed → store pipeline. The chat side doesn't change: the extracted text becomes ordinary chunks that searchKnowledgeBase finds.

New to scanned PDFs? Why some PDFs have no text inside

A PDF can hold two very different things:

  • A text PDF (made by "Save as PDF" in Word, Google Docs or a browser) stores the actual letters and their positions. You can select and copy the text, and pdf-parse can read it. This is called having a text layer.
  • A scanned PDF (made by a scanner, a phone scanning app or "print to PDF" of a photo) stores only pictures of pages. To a computer it's a grid of coloured dots; there are no letters to extract. pdf-parse returns an empty string.

Quick test: open the PDF and try to highlight a sentence with the mouse. If you can't select individual words, it's a scan.

New to OCR and vision models? How a model "reads" a picture

OCR (optical character recognition) is software that looks at an image of text and works out which letters are in it. Classic OCR engines do only that: they find letters, line by line.

A multimodal (vision) model like gpt-4.1-mini can do OCR and understand the picture. It can read a crooked photo of a notice board, follow the reading order of a two-column layout, and, if there is hardly any text, describe what it sees ("a whiteboard listing three Q3 goals"). You ask for this in plain English, with a prompt.

The trade-offs: each call costs money and takes a few seconds, and, like any model, it can occasionally misread or invent a word. That's why text PDFs still go through the free, exact pdf-parse path first.

Every path ends in the same place: one plain text string. From there, nothing new is needed, because the existing pipeline only cares about text.

Step by step

  1. Create the vision text extractor

    extractTextWithVision(data, mediaType) sends the file and an instruction to gpt-4.1-mini with the AI SDK's generateText:

    • Images go in as an { type: "image" } content part. PDFs go in as a { type: "file", mediaType: "application/pdf" } part. The OpenAI provider in the repo's version sends PDFs to the model directly, and the model reads both the page images and any text.
    • The prompt asks for only the extracted text, in reading order. For a picture with little text (a photo or a diagram), it asks for a short factual description instead, so the image can still be found by meaning ("whiteboard with Q3 goals").

    Create src/lib/extract-text.ts:

    // src/lib/extract-text.ts
import { generateText } from "ai";
import { openai } from "@ai-sdk/openai";

const OCR_PROMPT = `Extract all readable text from this file, in reading order.
Return only the extracted text, with no commentary.
If the file contains little or no text (for example a photo or a diagram),
describe what it shows in a few factual sentences instead.`;

// Uses a vision-capable model to read text from an image or a scanned PDF.
export async function extractTextWithVision(data: Buffer, mediaType: string) {
  const { text } = await generateText({
    model: openai("gpt-4.1-mini"),
    messages: [
      {
        role: "user",
        content: [
          { type: "text", text: OCR_PROMPT },
          mediaType.startsWith("image/")
            ? { type: "image", image: data, mediaType }
            : { type: "file", data, mediaType },
        ],
      },
    ],
  });

  return text;
}

  2. Generalise the server action

    Rename processPdfFile to processFile and send every file type through one small router, extractText:

    FileHow the text is extracted
    PDF with a text layerpdf-parse, exactly as before. Fast and free.
    PDF with no textProbably scanned, so it goes to extractTextWithVision(buffer, "application/pdf"). This is the case that failed in step 12.
    PNG / JPEG / WebP / GIFextractTextWithVision(buffer, file.type).
    Anything elseThrows "Unsupported file type…". The catch passes that message to the UI.

    The rest of the function is the step 12 pipeline: chunkContent → generateEmbeddings → db.insert. The form field is renamed from "pdf" to "file", and the code checks file instanceof File instead of casting, so a missing upload returns a clear error.

    Replace the whole content of src/app/upload/actions.ts with:

    // src/app/upload/actions.ts
"use server";

import pdf from "pdf-parse";
import { db } from "@/lib/db-config";
import { documents } from "@/lib/db-schema";
import { generateEmbeddings } from "@/lib/embeddings";
import { chunkContent } from "@/lib/chunking";
import { extractTextWithVision } from "@/lib/extract-text";

const IMAGE_TYPES = ["image/png", "image/jpeg", "image/webp", "image/gif"];

async function extractText(file: File, buffer: Buffer) {
  if (file.type === "application/pdf") {
    const data = await pdf(buffer);
    if (data.text.trim().length > 0) {
      return data.text;
    }
    // No text layer: probably a scanned PDF, so let the vision model read it
    return extractTextWithVision(buffer, "application/pdf");
  }

  if (IMAGE_TYPES.includes(file.type)) {
    return extractTextWithVision(buffer, file.type);
  }

  throw new Error(`Unsupported file type: ${file.type || "unknown"}`);
}

export async function processFile(formData: FormData) {
  try {
    const file = formData.get("file");
    if (!(file instanceof File)) {
      return { success: false, error: "No file provided" };
    }

    const buffer = Buffer.from(await file.arrayBuffer());
    const text = await extractText(file, buffer);

    if (!text || text.trim().length === 0) {
      return { success: false, error: "No text found in file" };
    }

    // Same pipeline as before: chunk, embed, store
    const chunks = await chunkContent(text);
    const embeddings = await generateEmbeddings(chunks);

    const records = chunks.map((chunk, index) => ({
      content: chunk,
      embedding: embeddings[index],
    }));

    await db.insert(documents).values(records);

    return {
      success: true,
      message: `Created ${records.length} searchable chunks from ${file.name}`,
    };
  } catch (error) {
    console.error("File processing error:", error);
    return {
      success: false,
      error:
        error instanceof Error && error.message.startsWith("Unsupported")
          ? error.message
          : "Failed to process file",
    };
  }
}

  3. Raise the server action body limit

    Server actions reject request bodies over 1 MB by default, and phone photos and scans are usually bigger. Raise the limit in next.config.ts:

    New to body size limits? Why servers refuse big uploads by default

    Every request has a body: the data sent along with it (here, the uploaded file inside FormData). Servers set a maximum body size to protect themselves: without one, anyone could send a 5 GB request and tie up memory and bandwidth.

    Next.js sets the limit for server actions to 1 MB by default. That's plenty for forms and text PDFs, but a single phone photo is often 2–5 MB. If the file is too big, the action never runs: the request fails, and the upload page shows its generic "An error occurred while processing the file" message (the terminal shows an error saying the body exceeded the 1 MB limit).

    Raising the limit to 10 MB is a deliberate trade-off: big enough for photos and short scans, small enough to stay safe. Hosting platforms can have their own, separate limits; on Vercel, for example, request bodies to functions are limited to about 4.5 MB regardless of this setting.

    import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  serverExternalPackages: ["pdf-parse"],
  experimental: {
    serverActions: {
      bodySizeLimit: "10mb", // default is 1mb; photos and scans are often bigger
    },
  },
};

export default nextConfig;

  4. Update the upload page

    These are small changes to the step 13 page, so its structure stays the same:

    • Import and call processFile instead of processPdfFile, and append the file under "file".
    • accept=".pdf,image/png,image/jpeg,image/webp,image/gif".
    • Generic wording: the "Upload Knowledge" title, the "Upload a PDF or an image…" label, "Processing file…" and "Failed to process file".
    • The input id and the label's htmlFor become file-upload.
    // src/app/upload/page.tsx
"use client";

import { useState } from "react";
import { processFile } from "./actions";
import { Card, CardContent } from "@/components/ui/card";
import { Label } from "@/components/ui/label";
import { Input } from "@/components/ui/input";
import { Alert, AlertDescription, AlertTitle } from "@/components/ui/alert";
import { Loader2 } from "lucide-react";

export default function KnowledgeUpload() {
  const [isLoading, setIsLoading] = useState(false);
  const [message, setMessage] = useState<{
    type: "error" | "success";
    text: string;
  } | null>(null);

  const handleFileUpload = async (e: React.ChangeEvent<HTMLInputElement>) => {
    const file = e.target.files?.[0];
    if (!file) return;

    setIsLoading(true);
    setMessage(null);

    try {
      const formData = new FormData();
      formData.append("file", file);

      const result = await processFile(formData);

      if (result.success) {
        setMessage({
          type: "success",
          text: result.message || "File processed successfully",
        });
        e.target.value = "";
      } else {
        setMessage({
          type: "error",
          text: result.error || "Failed to process file",
        });
      }
    } catch (err) {
      setMessage({
        type: "error",
        text: "An error occurred while processing the file",
      });
    } finally {
      setIsLoading(false);
    }
  };

  return (
    <div className="min-h-screen bg-gray-50 py-12 px-4">
      <div className="max-w-4xl mx-auto">
        <h1 className="text-3xl font-bold text-gray-900 mb-8 text-center">
          Upload Knowledge
        </h1>
        <Card className="mb-6">
          <CardContent className="pt-6">
            <div className="space-y-4">
              <div>
                <Label htmlFor="file-upload">
                  Upload a PDF or an image (PNG, JPEG, WebP, GIF)
                </Label>
                <Input
                  id="file-upload"
                  type="file"
                  accept=".pdf,image/png,image/jpeg,image/webp,image/gif"
                  onChange={handleFileUpload}
                  disabled={isLoading}
                  className="mt-2"
                />
              </div>

              {isLoading && (
                <div className="flex items-center gap-2">
                  <Loader2 className="h-5 w-5 animate-spin" />
                  <span className="text-muted-foreground">
                    Processing file...
                  </span>
                </div>
              )}

              {message && (
                <Alert
                  variant={message.type === "error" ? "destructive" : "default"}
                >
                  <AlertTitle>
                    {message.type === "error" ? "Error!" : "Success!"}
                  </AlertTitle>
                  <AlertDescription>{message.text}</AlertDescription>
                </Alert>
              )}
            </div>
          </CardContent>
        </Card>
      </div>
    </div>
  );
}

Test it

Here is everything that happens, in order, when you upload an image or a scanned PDF:

  1. Upload an image with text, for example a screenshot of a policy paragraph. Expect "Success! Created N searchable chunks from screenshot.png".
  2. Check Neon. The new rows' content is the text the model read from the image.
  3. Ask about it in /chat. The answer comes from the image's content, retrieved through the normal search tool.
  4. Upload a scanned PDF (or "print to PDF" an image). Before this step it failed with "No text found". Now the vision model reads it.
  5. Upload an unsupported file: switch the file picker to "All files" and choose a .docx. You see "Unsupported file type: …".

To check Neon, open your project in the Neon console, go to the SQL Editor and run SELECT id, content FROM documents ORDER BY id DESC LIMIT 5;. This shows the five newest rows; their content should match the words in your image.

How to know it worked: the green success alert names your file, the newest rows in Neon contain readable text (not a description of "an image of text"), and a question in /chat about something only written in the image gets a correct answer.

Common mistakes:

  • Uploading a photo fails with "An error occurred while processing the file" – the file is over the body size limit. Check that next.config.ts has bodySizeLimit and that you restarted the dev server.
  • "No file provided" for every upload – the page still appends "pdf" while the action reads "file". Both must say "file".
  • Build error "has no exported member 'processPdfFile'" – the page still imports the old name.
  • "Failed to process file" for images – look at the terminal: a 401 means the API key is wrong or missing; restart after editing .env.local.
  • Stored content starts with "Here is the extracted text:" – the prompt was shortened. Keep the "Return only the extracted text, with no commentary" line.

Things to watch:

  • Cost: each image or scanned PDF costs one vision call on top of the embeddings. Text PDFs still use free local parsing.
  • Accuracy: vision OCR is very good on clear screenshots but can misread handwriting or poor scans. Spot-check important documents in Neon.
  • Long scanned PDFs: one call reads the whole document and the answer length is limited, so a 100-page scan may come back incomplete. For big scans, split the PDF into page ranges first, or use a dedicated OCR service.
Recap
  • extractTextWithVision turns images and scanned PDFs into text with one generateText call.
  • processFile picks the cheapest method for each file and then runs the unchanged chunk → embed → store pipeline.
  • Your knowledge base now accepts text PDFs, scanned PDFs and images, and the chat side didn't change at all.
