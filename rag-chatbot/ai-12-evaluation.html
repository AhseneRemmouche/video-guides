Evaluating AI Applications

Test sets, metrics, LLM-as-judge and regression testing for prompts and RAG.

You have built a chatbot that answers questions from a handbook. You asked it "How many vacation days do I get?", it said "15 days for 0–2 years of service, 20 days for 3–5 years", and you were happy. But how do you know it still works tomorrow, after you change the prompt, the chunk size or the model? Clicking around and "eyeballing" a few answers does not scale, and it misses the quiet breakages. This chapter teaches you to evaluate an AI application: write down what "correct" means, measure it automatically, and re-run those measurements every time you change something.

You will learn:

  • why AI apps need a different kind of testing than normal code;
  • how to build a small test set for this chatbot from the handbook facts used in the video;
  • the main kinds of checks: simple text checks, retrieval metrics (did the right chunk come back?), answer metrics (is the answer correct and grounded?), LLM-as-judge and human review;
  • how to write a tiny evaluation script in TypeScript, and how to use it as a regression test when you change chunk size, model or prompt;
  • how to keep measuring quality after launch (online evaluation), and which pitfalls to avoid.

Why this matters for your chatbot: in step 11 this guide changed the chunk size from the video's 150 / 20 to 900 / 150. That one change affects every answer the bot gives. Without an evaluation you can only hope it was an improvement. With one, you can show it: "before: 6 of 10 questions retrieved the right passage; after: 9 of 10".

Why AI apps need evals

An eval (short for evaluation) is a repeatable test that measures how well an AI system does a task. It is the AI version of a unit test, but with two big differences.

1. The output is not deterministic

Normal code is deterministic: add(2, 3) returns 5 every single time, so a test can say "expect exactly 5". An LLM is different. It picks each next token with some randomness (see temperature), so the same question can produce:

  • "You get 15 days of PTO per year if you have 0–2 years of service."
  • "Employees with up to two years of service receive 15 days annually; 3–5 years: 20 days."

Both are correct, but they are different strings. So you cannot test with "the answer must equal this exact text". You need checks that tolerate different wording but still catch wrong facts.

2. Changes break things silently

In normal code, a breaking change usually causes an error, a red test or a crash. In an AI app, the most common failures produce no error at all:

  • You reword the system prompt to make answers shorter, and the model stops calling searchKnowledgeBase for some questions. It now answers from its general knowledge, confidently and wrongly (a hallucination).
  • You change the chunk size, and the passage with "two weeks in advance" now sits in a chunk that no longer passes the 0.5 similarity threshold.
  • The provider updates a model, or you switch to a newer one, and its style or tool-use habits change.

Everything still "works": the page loads, an answer streams in. Only an eval notices that the answer is now worse.

New to testing? What a test is and why developers write them

A test is a small program that runs your code with a known input and checks the output against what you expect. If the check fails, the test reports it. Developers run tests automatically before every release, so mistakes are caught by a machine instead of by a user.

// A classic, deterministic test
const result = add(2, 3);
if (result !== 5) throw new Error(`Expected 5, got ${result}`);

A regression is when something that used to work stops working after a change. A regression test is a test you keep running forever so that old bugs never come back unnoticed. Evals play exactly this role for prompts, models and retrieval settings.

The parts of this app you can evaluate

A RAG chatbot is a pipeline. When an answer is wrong, the fault can be in different places, so it pays to measure each stage separately.

  • Retrieval (step 14): given a question, does searchDocuments return the chunk that contains the answer?
  • Tool use (step 15, step 22): does the model call searchKnowledgeBase when it should, calculator for arithmetic, and getCurrentDate for date questions?
  • Answer: is the final text correct, supported by the retrieved chunks, and actually answering the question?

Building a test set for this chatbot

Every eval starts with a test set (also called a dataset or golden set): a list of questions together with what a correct answer must contain. The expected facts are your ground truth: the answers you know are right because you checked them in the source document.

The video's sample handbook gives us real, checkable facts (see step 15):

  • PTO: 15 days per year for 0–2 years of service, 20 days for 3–5 years.
  • Vacation requests must be submitted at least two weeks in advance through the HR portal.
  • An annual education budget of $2,000 per employee.

Turn these into "golden questions". Write each question the way a real employee might ask it, and list the facts a correct answer must include. Add a few variations in wording, because users rarely use the document's exact words.

// evals/test-set.ts
export type TestCase = {
  id: string;

  // Phrases that must appear in a retrieved chunk (retrieval check)
  expectedInChunk: string[];
  // Facts that must appear in the final answer (answer check)
  expectedInAnswer: string[];
};

export const testSet: TestCase[] = [

Rule of thumb for a first test set: start with 20–50 cases that cover your most common question types, a few tricky phrasings, a few multi-step questions, and a few questions that should not be answered. Add a new case every time a user reports a bad answer. Over time the set becomes a record of everything that has ever gone wrong.

Where do good test questions come from?
  • The documents themselves. Read the handbook and write one question per important fact.
  • Real users. After launch, your logs (see "Online evaluation" below) show what people actually ask. Real questions are messier than the ones you invent.
  • An LLM, with your review. You can ask a model to propose questions for each chunk ("write 3 questions this passage answers"). This is fast, but always read and correct them: generated questions tend to copy the document's wording, which makes retrieval look better than it is.
  • Negative cases. Questions on topics not in the documents, and requests the bot should refuse.

Types of checks

There is no single "accuracy" number for an AI app. You combine several checks, from cheap and strict to expensive and flexible.

CheckWhat it measuresCostGood for

Exact and "contains" checks

The simplest check: does the answer contain the expected text? For facts like numbers, this works surprisingly well. Make it a little forgiving: compare lowercase text, accept alternatives ("two weeks" or "2 weeks"), and ignore formatting such as **bold** markers.

Limits: a contains-check passes "You do not get 15 days" because "15" appears. And it cannot judge whether an answer is helpful. Use it as a fast first filter, not as the only check.

Retrieval metrics: did the right chunk come back?

Retrieval is the foundation of RAG: if the chunk with "$2,000" never reaches the model, the model cannot answer correctly (or, worse, invents a number). Retrieval is also cheap to test, because you can call searchDocuments directly without the chat model.

Some standard metrics, where k is how many results you retrieve (this app uses searchDocuments(query, 3, 0.5), so k = 3):

  • Hit rate @ k: the share of questions where at least one relevant chunk is in the top k. If 9 of 10 questions get the right chunk in the top 3, hit rate@3 = 0.9. This is the most useful single number to start with.
  • Recall @ k: when the answer is spread over several chunks, the share of all relevant chunks that made it into the top k. If a question needs 2 chunks and 1 came back, recall@3 = 0.5.
  • MRR (mean reciprocal rank): rewards putting the right chunk first. For each question, take 1 divided by the position of the first relevant chunk (1st place = 1, 2nd = 0.5, 3rd = 0.33, not found = 0), then average over all questions. An MRR close to 1 means the best chunk is usually ranked first.
A worked MRR example

Four test questions. The position of the first chunk containing the expected phrase:

QuestionFirst relevant chunk atReciprocal rank
pto-new11 / 1 = 1.00
pto-senior21 / 2 = 0.50
notice11 / 1 = 1.00
educationnot in top 30

MRR = (1 + 0.5 + 1 + 0) / 4 = 0.625. Hit rate@3 = 3 / 4 = 0.75. The "education" miss is the one to investigate: maybe "courses or training" is too far in meaning from "education budget", or the similarity is just under the 0.5 threshold.

How do you know which chunk is "relevant"? The simplest way, used below, is to check whether the chunk text contains an expected phrase. That avoids depending on database ids, which change every time you re-upload with a new chunk size.

Answer metrics

Once retrieval works, judge the final answer. The three most common answer qualities for RAG are:

  • Faithfulness (also called groundedness): is every claim in the answer supported by the retrieved chunks? An answer that says "20 days, plus 5 bonus days" when the chunk says nothing about bonus days is unfaithful, even if it sounds plausible. Faithfulness is your hallucination detector.
  • Relevance: does the answer address the question that was asked? "Vacation requests go through the HR portal" is true but not relevant to "How many days do I get?".
  • Correctness: does the answer match the ground truth? This needs your expected facts. An answer can be faithful to a wrong chunk and still be incorrect.

Contains-checks cover correctness for simple facts. Faithfulness and relevance are about meaning, so they are usually measured with an LLM judge.

LLM-as-judge with a rubric

LLM-as-judge means using a language model to grade another model's output. You give the judge the question, the retrieved context, the answer and a rubric (a clear scoring guide), and ask it for scores. To make the scores machine-readable, use structured output: the AI SDK's generateObject with a zod schema forces the reply into a typed object.

// evals/judge.ts
import { generateObject } from "ai";
import { openai } from "@ai-sdk/openai";
import { z } from "zod";

const scoreSchema = z.object({
  faithfulness: z
    .number()
    .int()
    .min(1)
    .max(5)
    .describe("5 = every claim is supported by the context; 1 = mostly unsupported"),
  relevance: z
    .number()
    .int()
    .min(1)
    .max(5)
    .describe("5 = directly answers the question; 1 = off-topic"),
  correctness: z
    .number()
    .int()
    .min(1)
    .max(5)
    .describe("5 = matches the reference facts; 1 = contradicts them"),
  reasoning: z.string().describe("One or two sentences explaining the scores"),
});

export async function judgeAnswer(input: {
  question: string;
  context: string;
  answer: string;
  referenceFacts: string[];
}) {
  const { object } = await generateObject({
    model: openai("gpt-4.1"), // ideally a different model from the one being tested
    schema: scoreSchema,
    temperature: 0,
    system:
      "You are a strict grader for a company handbook assistant. " +
      "Judge only from the context and reference facts given. " +
      "Do not use outside knowledge.",
    prompt: [
      `Question: ${input.question}`,
      `Context retrieved from the handbook:\n${input.context}`,
      `Reference facts: ${input.referenceFacts.join("; ") || "(none: the answer should say the information was not found)"}`,
      `Answer to grade:\n${input.answer}`,
    ].join("\n\n"),
  });

  return object; // { faithfulness, relevance, correctness, reasoning }
}

A judge is a model too. It can be wrong, inconsistent or biased (for example towards longer answers, or towards answers written in its own style). Before trusting it, grade 20–30 answers yourself and compare. If you and the judge disagree often, improve the rubric (make the criteria more concrete) before relying on its numbers.

Human review

People remain the final reference. A practical routine for a small team:

  • Review a small random sample of real conversations every week, plus every conversation that got a thumbs-down.
  • Use the same rubric as the judge, so you can measure how well the judge agrees with humans.
  • Turn every confirmed bad answer into a new test case.

For an HR assistant, involve someone who knows the policies. A developer may not notice that "two weeks" should have been "two weeks through the HR portal".

A small eval script

Here is a complete, minimal retrieval eval for this project. It calls the real searchDocuments function from step 14 with the same settings as the chat tool (limit 3, threshold 0.5), checks each result for the expected phrases, and prints hit rate@3 and MRR.

// evals/retrieval.ts
import { searchDocuments } from "../src/lib/search";
import { testSet } from "./test-set";

function matches(text: string, expected: string) {
  const haystack = text.toLowerCase();
  return expected
    .split("|")
    .some((option) => haystack.includes(option.toLowerCase()));
}

async function main() {
  const cases = testSet.filter((c) => c.expectedInChunk.length > 0);
  let hits = 0;
  let reciprocalRankSum = 0;

  for (const testCase of cases) {
    const results = await searchDocuments(testCase.question, 3, 0.5);

    const rank = results.findIndex((r) =>
      testCase.expectedInChunk.every((phrase) => matches(r.content, phrase)),
    );

    if (rank >= 0) {
      hits++;
      reciprocalRankSum += 1 / (rank + 1);
      console.log(`PASS ${testCase.id} (rank ${rank + 1})`);
    } else {
      const best = results[0]?.similarity.toFixed(3) ?? "no results";
      console.log(`FAIL ${testCase.id} (top similarity: ${best})`);
    }
  }

  console.log(`\nHit rate@3: ${(hits / cases.length).toFixed(2)}`);
  console.log(`MRR:        ${(reciprocalRankSum / cases.length).toFixed(2)}`);
}

main();

Evaluating full answers

To test the whole agent (search, calculator, final answer), the eval needs to run the same model, system prompt and tools as src/app/api/chat/route.ts. Calling the HTTP route from a script is awkward because it requires a Clerk sign-in. A cleaner design is to move the shared settings into their own module, for example src/lib/agent.ts exporting tools and SYSTEM_PROMPT, import them in the route, and import the same module in the eval:

import { generateText, stepCountIs } from "ai";
import { openai } from "@ai-sdk/openai";
import { tools, SYSTEM_PROMPT } from "../src/lib/agent"; // shared with route.ts
import { testSet } from "./test-set";

async function main() {
  for (const testCase of testSet) {
    const { text, steps } = await generateText({
      model: openai("gpt-5-mini"),
      system: SYSTEM_PROMPT,
      tools,
      stopWhen: stepCountIs(6),
      prompt: testCase.question,
    });

    const toolsUsed = steps.flatMap((s) => s.toolCalls.map((c) => c.toolName));
    const missing = testCase.expectedInAnswer.filter(
      (fact) => !fact.split("|").some((o) => text.toLowerCase().includes(o.toLowerCase())),
    );

    console.log(missing.length === 0 ? "PASS" : "FAIL", testCase.id, toolsUsed, missing);
  }
}

main();

Key ideas: generateText runs the same agent loop as streamText but returns the finished result, which is easier to check. steps tells you which tools were called, so you can also assert "the education-math case must call calculator". The loop sits inside an async main function, like the retrieval script, because await is only allowed inside async functions in this kind of script. Add the judge from the previous section for faithfulness and relevance by passing it the tool results from steps as the context.

Run it several times. Because answers vary, a case that passes once may fail on the next run. For important cases, run each question 3–5 times and report the pass rate (for example "notice: 4/5"). A case that sometimes fails is a real problem for some of your users.

Regression testing: change one thing, re-run everything

Evals pay off when you change something. Typical changes in this project:

  • Chunk size and overlap (step 11): 150 / 20 in the video and repo, 900 / 150 in this guide.
  • Search settings (step 15): limit 3, threshold 0.5.
  • Model: gpt-5-mini for chat, text-embedding-3-small for embeddings.
  • Prompt: the system prompt, rewritten in step 22 for the agent.

The workflow is always the same:

  1. Record a baseline. Run the evals on the current version and save the numbers (and the per-case PASS/FAIL list).
  2. Change one thing. For example, switch chunkSize from 150 to 900 and chunkOverlap from 20 to 150.
  3. Rebuild what depends on it. A chunking change only takes effect for newly uploaded documents, so clear the documents table (or use a fresh Neon branch) and re-upload the handbook. Otherwise you are measuring a mix of old and new chunks.
  4. Re-run the same evals and compare with the baseline, case by case.
  5. Decide. Keep the change only if the important numbers improve and no important case got worse.

A plausible (illustrative, not measured) outcome of the 150 → 900 change: with 150-character chunks, "15 days" and "two weeks in advance" may sit in separate chunks, so a broad question retrieves only part of the answer. With 900-character chunks, the whole vacation paragraph fits in one chunk, so hit rate rises; but each chunk mixes more topics, so similarity scores for very narrow questions may drop closer to the 0.5 threshold. Only your eval tells you which effect wins for your documents.

Automate it. Once the scripts exist, you can run them in a CI pipeline (a server that runs checks on every code change, such as GitHub Actions) whenever someone edits route.ts, chunking.ts or search.ts. Because evals call paid APIs and take time, many teams run a small, fast set on every change and the full set nightly or before a release.

Online evaluation: measuring quality with real users

Everything above is offline evaluation: you run it yourself, on your test set, before release. Online evaluation measures quality in production, on real traffic. Both are needed: offline evals catch regressions before users see them; online signals show you questions you never thought of.

  • Explicit feedback. Add thumbs-up / thumbs-down buttons under each assistant message. Store the message id, the rating, an optional comment, and the user id. A rising thumbs-down rate after a release is a strong warning sign.
  • Implicit signals. The user immediately rephrases the same question, copies the answer, or gives up. These are noisier than explicit ratings but much more plentiful.
  • Logging. Record each conversation's question, the tool calls and their results, the final answer, the model name and token usage. In step 22 the onStepFinish callback already logs every tool call to the terminal; in production you would send the same data to a database or an observability tool (see Running AI in Production).
  • Sampled judging. Run the LLM judge automatically on a small random share of real conversations (for example 5%) and chart faithfulness over time.

A minimal feedback table, sketched with Drizzle like the documents table of step 9:

export const feedback = pgTable("feedback", {
  id: serial("id").primaryKey(),
  messageId: text("message_id").notNull(),
  userId: text("user_id").notNull(),
  rating: integer("rating").notNull(), // 1 = thumbs up, -1 = thumbs down
  comment: text("comment"),
  createdAt: timestamp("created_at").defaultNow().notNull(),
});

Privacy: logged conversations contain whatever users typed, possibly personal data (PII). Tell users you store them, limit who can read them, and delete them after a fixed period. See Security & Safety.

Pitfalls

Common pitfalls in AI evaluation

  • Tiny test sets. With 5 questions, one flaky answer moves your score by 20 percentage points. Small differences between two versions ("82% vs 80%") are often just noise. Grow the set, and re-run several times before drawing conclusions.
  • Judging with the same model. A model grading its own answers tends to be lenient towards its own style and blind to its own mistakes. Use a different (often stronger) judge model, and check it against human grades.
  • Overfitting prompts to the tests. If you keep tweaking the system prompt until every test passes ("if asked about education, say $2,000"), you have taught the prompt your test set, not made the bot better. Keep a held-out set of questions you never look at while tuning, and use it only to confirm.
  • Testing only happy paths. Include out-of-scope questions, ambiguous ones, and questions where the correct answer is "I don't know".
  • Stale ground truth. When the handbook changes (say the education budget rises), update the expected facts too, or your evals will "fail" correct answers.
  • Mixing changes. Changing chunk size, model and prompt at once makes it impossible to know which change caused an improvement or a regression.
  • Forgetting to re-index. After a chunking or embedding-model change, old chunks in the database still use the old settings.
Recap
  • AI outputs vary and changes break things silently, so you need evals: repeatable, automated quality measurements.
  • Start with a test set of golden questions and expected facts from your documents, like 15/20 PTO days, two weeks' notice and the $2,000 education budget.
  • Measure retrieval separately (hit rate@k, recall@k, MRR) by calling searchDocuments directly.
  • Measure answers for correctness, faithfulness and relevance using contains-checks, an LLM judge with a rubric (generateObject + zod), and human review.
  • Record a baseline, change one thing (such as chunk size 150/20 → 900/150), re-index, re-run, compare.
  • After launch, collect feedback and logs, and turn bad answers into new test cases.
  • Avoid tiny test sets, self-judging and overfitting the prompt to the tests.
