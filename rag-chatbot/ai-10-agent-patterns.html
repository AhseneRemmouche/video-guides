Agent Patterns, Memory & Multi-Agent Systems

Chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer, memory and human-in-the-loop.

In the previous chapter you met the agent loop and the difference between workflows and agents. This chapter is a toolbox. You will learn the common patterns for combining model calls, described in Anthropic's article "Building effective agents", each with a small diagram or table, an example from this HR / company-documents chatbot, and AI SDK v5 code for the most useful ones. Then we cover memory, planning, multi-agent systems, human-in-the-loop approval and guardrails.

Why this matters for your chatbot. Your project already uses one pattern: a single tool-using agent (step 22). As you add features ("route IT questions elsewhere", "check answers before showing them", "let employees actually submit a vacation request"), you will need to pick the next pattern. Knowing the menu helps you choose the simplest one that works instead of jumping straight to a complicated multi-agent system.

The building block: the augmented LLM

Every pattern below is built from the same unit: a model call that can use retrieval, tools and memory. Anthropic's article calls this the augmented LLM. In this project it is one streamText call with the searchKnowledgeBase tool. Patterns are just different ways of wiring several of these units together, either with your code in charge (workflows) or with the model in charge (agents).

New to Promise.all and running things in parallel?

An async function returns a Promise: a placeholder for a value that arrives later. If you await two calls one after another, the second starts only when the first ends. Promise.all([a(), b()]) starts both immediately and waits until both finish, returning their results in an array in the same order.

// Sequential: about 2 + 2 = 4 seconds
const x = await slowTwoSeconds();
const y = await slowTwoSeconds();

// Parallel: about 2 seconds
const [a, b] = await Promise.all([slowTwoSeconds(), slowTwoSeconds()]);

Model calls are slow network requests, so running independent ones in parallel is one of the easiest ways to cut latency. It does not reduce cost: you still pay for every call.

1. Prompt chaining

Break a task into a fixed sequence of steps. Each model call takes the previous call's output as input. Between steps you can add a "gate": a plain code check that stops the chain if something is wrong.

HR example: (1) answer the question from the knowledge base, (2) gate: does the answer mention at least one document fact? If not, reply "I couldn't find this in our documents", (3) translate the answer into the employee's preferred language.

Use it when the task naturally splits into fixed subtasks and each one is easier for the model on its own.

2. Routing

A first, cheap model call classifies the input. Your code then sends it down a path built for that category: a different prompt, different tools, or even a different (cheaper or stronger) model. Routing keeps each path focused, so improving one category does not hurt the others.

The AI SDK's generateObject has an output: "enum" mode that forces the model to answer with exactly one of the labels you list (see Structured Output):

import { generateObject } from "ai";
import { openai } from "@ai-sdk/openai";

export async function routeQuestion(question: string) {
  const { object: category } = await generateObject({
    model: openai("gpt-5-mini"),
    output: "enum",
    enum: ["company-policy", "it-support", "small-talk", "other"],
    system: "Classify the employee's message. Reply with one label only.",
    prompt: question,
  });

  switch (category) {
    case "company-policy":
      return answerWithKnowledgeBase(question); // e.g. the step 22 agent
    case "it-support":
      return answerItQuestion(question);
    case "small-talk":
      return answerBriefly(question); // no tools: cheaper and faster
    default:
      return "Sorry, I can only help with company policies and IT questions.";
  }
}

3. Parallelization: sectioning and voting

Run several model calls at the same time and combine the results in code. Anthropic's article describes two flavours:

FlavourHow it worksHR example
SectioningSplit a task into independent parts that run side by side.Answer the question in one call while a second call checks the question for personal data (PII) or off-topic requests. Or summarise each chapter of a long handbook in parallel.
VotingRun the same task several times (or with different prompts) and compare.Ask three times "Does this answer contradict the policy text?" and flag it if two or more say yes.
import { generateObject, generateText } from "ai";
import { openai } from "@ai-sdk/openai";
import { z } from "zod";

const model = openai("gpt-5-mini");

const [answer, check] = await Promise.all([
  generateText({ model, system: SYSTEM_PROMPT, prompt: question }),
  generateObject({
    model,
    schema: z.object({
      containsPersonalData: z.boolean(),
      offTopic: z.boolean(),
    }),
    prompt: `Check this employee message:\n\n${question}`,
  }),
]);

if (check.object.containsPersonalData || check.object.offTopic) {
  return "Please don't share personal data here, and keep questions work-related.";
}
return answer.text;

Both calls start together, so the check adds almost no waiting time. The trade-off: you pay for the main answer even when the check rejects the question. That is often worth it for speed; if cost matters more, run the check first (a chain).

4. Orchestrator-workers

A central "orchestrator" model looks at the task and decides at run time which subtasks are needed, sends each to a "worker" call, then combines the results. The difference from sectioning: the subtasks are not known in advance.

HR example: "Compare our parental leave, sick leave and remote-work policies for someone in their first year." The orchestrator (a generateObject call returning an array of subtasks) produces three subtasks; each worker searches the knowledge base for one policy and summarises it; a final call writes the comparison. You can implement the workers with Promise.all over the subtask array.

5. Evaluator-optimizer

One call generates, another evaluates against clear criteria and gives feedback, and the loop repeats until the evaluator is satisfied or a round limit is hit. It works well when you can state what "good" looks like, and when feedback measurably improves the result. It is closely related to LLM-as-judge evaluation (chapter 12).

import { generateObject, generateText } from "ai";
import { openai } from "@ai-sdk/openai";
import { z } from "zod";

const model = openai("gpt-5-mini");
const MAX_ROUNDS = 3;

let draft = (
  await generateText({
    model,
    prompt: `Write a short, friendly announcement of this policy change:\n\n${policyText}`,
  })
).text;

for (let round = 1; round <= MAX_ROUNDS; round++) {
  const { object: review } = await generateObject({
    model,
    schema: z.object({
      approved: z.boolean(),
      feedback: z.string().describe("Specific fixes if not approved"),
    }),
    prompt: `Policy:\n${policyText}\n\nAnnouncement:\n${draft}\n\n` +
      "Approve only if every fact matches the policy and the tone is friendly.",
  });

  if (review.approved) break;

  draft = (
    await generateText({
      model,
      prompt: `Improve this announcement.\nFeedback: ${review.feedback}\n\n${draft}`,
    })
  ).text;
}

If the loop ends without approval, do not silently publish: show the last feedback to a human. That is the human-in-the-loop idea you will see below.

6. Autonomous agents

The model uses tools in a loop, deciding everything itself, until it finishes or hits a limit. This is what step 22 built, and chapter 9 covers it in depth. Use it for open-ended tasks where you cannot predict the steps, and only with step limits, good logging and tools that cannot cause serious harm.

Patterns combine. Real systems mix them. A sensible next version of this chatbot could route each question, send policy questions to the step 22 agent, and run a parallel safety check, without any of the more complex patterns.

Memory

An LLM has no memory between calls. Each request starts from zero, and the model only "knows" what is in that request. Everything we call memory is your code deciding what to put back into the prompt.

Short-term memory: the conversation

Short-term memory is the conversation history inside the context window. In this project, useChat in the browser keeps the list of messages and sends the whole list on every request; the route handler turns it into model messages with convertToModelMessages(messages). That is why you can ask a follow-up like "and what about part-time staff?" and the model understands.

The problem: history grows. Every message (and every tool result) costs tokens on every later request, and eventually the conversation does not fit. Common strategies:

  • Sliding window: send only the last N messages.
  • Summarisation: when the history gets long, ask a model to summarise older messages into a short paragraph and send that instead.
  • Trim tool results: keep the final answers but drop bulky old search results.

In the AI SDK, prepareStep can return a modified messages array, which is one place to apply trimming inside an agent loop.

Long-term memory: facts stored outside the conversation

Long-term memory survives after the chat ends. You store information in a database and fetch the relevant parts into the prompt later. Two common shapes:

  • Structured facts: a table such as user_preferences(user_id, key, value): "prefers answers in French", "works in the Berlin office". Simple and reliable.
  • Vector memory: store past notes or conversation summaries with an embedding, and retrieve the most similar ones with semantic search, exactly the way this project retrieves document chunks from Neon with pgvector (step 9, step 14).

Memory can be written by your code (e.g. save a summary after each chat) or by the model through a tool such as rememberFact({ fact }). If the model writes memory, validate what it stores: a wrong "fact" saved once will be repeated in every later conversation.

Kinds of memory at a high level

KindRemembers…HR chatbot example
EpisodicSpecific past events and conversations"Last week you asked about carrying over vacation days."
SemanticGeneral facts and knowledge"This user is in the Berlin office"; the company policies themselves
ProceduralHow to do thingsThe system prompt's "How to work" steps

These terms are borrowed from psychology and used loosely in AI; treat them as a way to think about what to store, not as strict categories.

Memory and privacy. Storing what employees say is storing personal data. Decide what you keep, for how long, who can see it, and let users see or delete it. See chapter 13 and chapter 16.

Planning

Planning means working out the steps before doing them. There are two common approaches:

  • Implicit planning: the model decides one step at a time inside the loop (ReAct style). This is what step 22 does, and the system prompt's numbered list nudges the order.
  • Explicit planning ("plan-and-execute"): a first call writes a plan as structured data (for example, a list of subtasks from generateObject); code or an agent then executes each item; optionally the plan is revised after each step. Orchestrator-workers is a form of this.

Explicit plans are easier to show to users, log, and check ("does this plan include anything risky?"). They can also go stale when an early step reveals something unexpected, so long tasks often re-plan.

Multi-agent systems

A multi-agent system uses several agents, each with its own instructions and tools, that cooperate. Two common shapes:

  • Supervisor and sub-agents: one "supervisor" agent talks to the user and delegates to specialists. A simple way to build this in the AI SDK is to wrap a sub-agent as a tool whose execute runs another generateText loop.
  • Handoffs: the conversation is passed from one agent to another ("transfer to the IT agent"), and the new agent takes over with its own prompt and tools.
// A sub-agent wrapped as a tool the supervisor can call
const askPolicyExpert = tool({
  description: "Ask the policy expert a question about company HR policies.",
  inputSchema: z.object({ question: z.string() }),
  execute: async ({ question }) => {
    const { text } = await generateText({
      model: openai("gpt-5-mini"),
      system: "You answer only from the company knowledge base. Cite facts.",
      tools: { searchKnowledgeBase: tools.searchKnowledgeBase },
      stopWhen: stepCountIs(4),
      prompt: question,
    });
    return text;
  },
});

Honest trade-offs:

BenefitsCosts
Each agent has a short, focused prompt and a small tool set, which models handle better than one giant prompt with dozens of tools.More model calls: more cost and latency. A supervisor plus two sub-agents can easily mean many calls for one question.
Teams can own and test agents separately.Information gets lost between agents: the sub-agent only sees what the supervisor passes it.

For this project, with three simple tools, a single agent is clearly the right choice. Consider multiple agents only when one agent's prompt and tool list become too large to work reliably.

Human-in-the-loop

Human-in-the-loop means a person approves, edits or rejects what the AI proposes before it takes effect. It matters most for actions that change things: sending email, submitting forms, deleting data, spending money. The current project's tools only read, so it does not need approval. Now imagine adding a submitVacationRequest tool.

In the AI SDK v5, a tool without an execute function is not run on the server. The model's tool call is streamed to the browser instead, where your UI can show "Submit vacation from Dec 1 to Dec 5? [Approve] [Cancel]". When the user clicks, the browser supplies the tool's result with addToolResult from useChat, and the conversation continues.

submitVacationRequest: tool({
  description: "Submit a vacation request for the signed-in employee. Requires user approval.",
  inputSchema: z.object({
    startDate: z.string().describe("First day of leave, YYYY-MM-DD"),
    endDate: z.string().describe("Last day of leave, YYYY-MM-DD"),
  }),
  // No execute: the call goes to the browser, which asks the user first.
}),
const { messages, sendMessage, addToolResult } = useChat({
  // After the user answers, automatically send the result back to the model
  sendAutomaticallyWhen: lastAssistantMessageIsCompleteWithToolCalls,
});

// While rendering message parts:
if (part.type === "tool-submitVacationRequest" && part.state === "input-available") {
  return (
    <div>
      Submit leave from {part.input.startDate} to {part.input.endDate}?
      <button onClick={async () => {
        const res = await fetch("/api/vacation", { method: "POST", body: JSON.stringify(part.input) });
        addToolResult({ tool: "submitVacationRequest", toolCallId: part.toolCallId,
          output: res.ok ? "Submitted" : "Submission failed" });
      }}>Approve</button>
      <button onClick={() => addToolResult({ tool: "submitVacationRequest",
        toolCallId: part.toolCallId, output: "The user cancelled." })}>Cancel</button>
    </div>
  );
}

Notice where the real action happens: in your own /api/vacation route handler, which must check the user's identity with Clerk (as in step 16) and validate the dates. The approval button is a user-experience safeguard, not a security boundary.

Guardrails

Guardrails are checks around the model that keep inputs and outputs within acceptable bounds. They can be plain code or another model call:

  • Input guardrails: block off-topic requests, detect personal data, detect obvious prompt injection attempts (the parallel check above is one).
  • Tool guardrails: validate tool inputs (zod schemas, length limits like calculate()'s 200-character cap), restrict what tools can reach (least privilege), require approval for risky ones.
  • Output guardrails: check the answer cites a document, contains no secrets, and matches a required format before it is shown.
  • Loop guardrails: step limits, token budgets, timeouts (chapter 9).

No single guardrail is perfect; use several layers. Chapter 13 goes deeper.

Picking the simplest pattern that works

A practical order to try things in (a rule of thumb, in the spirit of Anthropic's advice):

  1. One good call: clear prompt, good retrieval, maybe one tool.
  2. A workflow: chaining, routing or parallelization when one call is not enough and the steps are predictable.
  3. A bounded agent: when the steps really depend on intermediate results.
  4. Evaluator loops or multiple agents: only when you can measure that they improve results enough to justify the extra cost and complexity.
Common misconceptions
  • "Multi-agent is the advanced, better version." It is a different trade-off, usually more expensive and harder to debug. Many strong products are single agents or workflows.
  • "The model remembers our last chat." Only if your code stores it and puts it back into the prompt.
  • "An evaluator makes answers correct." It catches some errors; the evaluator is a model too and can be wrong. Measure with real test questions.
  • "A frontend Approve button makes actions safe." The server must still check permissions and validate input.
Recap
  • All patterns are built from the augmented LLM: a model call with retrieval, tools and memory.
  • Workflow patterns (your code in charge): prompt chaining, routing, parallelization (sectioning/voting), evaluator-optimizer.
  • Model-led patterns: orchestrator-workers (model plans the subtasks) and autonomous agents (model drives the whole loop).
  • Routing is easy with generateObject({ output: "enum" }); parallelization with Promise.all; evaluator-optimizer with a bounded loop.
  • Memory is what your code puts back into the prompt: short-term (history, trimmed or summarised) and long-term (database or vector store).
  • Multi-agent systems split work across focused agents, at the price of cost, latency and debugging effort.
  • Human-in-the-loop: tools without execute go to the browser for approval via addToolResult; the server still enforces permissions.
  • Layer guardrails on inputs, tools, outputs and the loop. Pick the simplest pattern that works.
