Adding Role-Based Access Control

Only admins can upload documents, using Clerk metadata.

▶ Watch this part (01:05:46)

Goal

Right now any signed-in user can upload PDFs to the knowledge base, which is probably not what you want in a real application. Only admins (for example HR staff) should be able to upload, while regular users can only chat. You implement this with Clerk's user metadata.

New to roles and RBAC? Who may do what

Authentication answers "who are you?" (you signed in, so Clerk knows you). Authorization answers "what are you allowed to do?".

RBAC (role-based access control) is the simplest common way to do authorization: you give each user a role, such as "admin" or "user", and decide permissions per role instead of per person. "Admins can upload" is one rule, no matter how many admins you have. Making someone an admin is just changing their role.

In this app there are two roles: admin (chat and upload) and user (chat only). A user with no role at all is treated like user.

Part A: type the roles

  1. Create types/globals.d.ts in the project root (next to src/, not inside it).
  2. Turn it into a module with export {};.
  3. Define the roles: "admin" | "user". Admins can upload documents. Users can only use the chat.
  4. Extend Clerk's session claims type

    Declare a global CustomJwtSessionClaims interface with metadata.role?: Roles. This extends Clerk's session claims everywhere, so whenever you read the user's role, TypeScript gives you autocompletion and type safety.

export {};

export type Roles = "admin" | "user";

declare global {
  interface CustomJwtSessionClaims {
    metadata: {
      role?: Roles;
    };
  }
}
New to declare global and .d.ts files? Adding to someone else's types

A file ending in .d.ts is a declaration file: it contains only TypeScript types, no running code. It's never sent to the browser; it only teaches the editor and the compiler about shapes of data.

Clerk's library defines an empty, global interface called CustomJwtSessionClaims on purpose, as a "slot" for you to fill. In TypeScript, if you declare an interface with the same name again, the two declarations are merged. So by writing your own CustomJwtSessionClaims with a metadata.role field, Clerk's types now know that field exists.

declare global { … } means "these declarations belong to the global scope", where Clerk's interface lives. That only works inside a module, and a file only counts as a module if it has at least one import or export. That's the job of the odd-looking export {};: it exports nothing, but turns the file into a module.

This technique (adding fields to another library's types) is called module augmentation or global augmentation.

Part B: protect /upload in the middleware

  1. Import NextResponse from next/server. You use it to redirect non-admins.
  2. Create a matcher for admin-only routes: createRouteMatcher(["/upload"]).
  3. Read the role: const { sessionClaims } = await auth();, then sessionClaims?.metadata?.role === "admin".
  4. Redirect non-admins: if the request is an admin route and the user isn't an admin, build new URL("/", req.url) and return NextResponse.redirect(url).
  5. Otherwise, run the normal authentication check from step 8.
import { clerkMiddleware, createRouteMatcher } from "@clerk/nextjs/server";
import { NextResponse } from "next/server";

const isPublicRoute = createRouteMatcher(["/", "/sign-in(.*)", "/sign-up(.*)"]);
const isAdminRoute = createRouteMatcher(["/upload"]);

export default clerkMiddleware(async (auth, req) => {
  const { sessionClaims } = await auth();
  const isAdmin = sessionClaims?.metadata?.role === "admin";

  if (isAdminRoute(req) && !isAdmin) {
    const url = new URL("/", req.url);
    return NextResponse.redirect(url);
  }

  if (!isPublicRoute(req)) {
    await auth.protect();
  }
});

export const config = {
  matcher: [
    // Skip Next.js internals and all static files, unless found in search params
    "/((?!_next|[^?]*\\.(?:html?|css|js(?!on)|jpe?g|webp|png|gif|svg|ttf|woff2?|ico|csv|docx?|xlsx?|zip|webmanifest)).*)",
    // Always run for API routes
    "/(api|trpc)(.*)",
  ],
};
New to JWTs and session claims? How the server knows your role on every request

When you sign in, Clerk gives your browser a session token, stored in a cookie and sent automatically with every request. Clerk's token is a JWT (JSON Web Token): a small piece of JSON, digitally signed by Clerk, so nobody can change it without the signature breaking.

The fields inside a JWT are called claims, for example the user id (sub) and expiry time (exp). Your middleware reads them with auth() as sessionClaims. Because the role is inside the token, checking it is instant: no extra request to Clerk or your database on every page load.

The catch: a token only contains the claims you configure, and it's only reissued every so often. That's why Part C adds metadata to the token, and why a role change can take a moment to apply.

New to redirects? What NextResponse.redirect does

A redirect is an HTTP response that says "don't show anything here, go to this other address instead". It has a 3xx status code (Next.js uses 307, "temporary redirect") and a Location header with the new URL. The browser follows it automatically, so the user just lands on the new page.

NextResponse.redirect needs a full URL, not just "/". new URL("/", req.url) builds one by taking the current request's origin (for example http://localhost:3000) and replacing the path with /. That way it works on localhost and in production without changes.

Part C: put the role into the session token (Clerk dashboard)

The code reads sessionClaims.metadata, but Clerk doesn't include metadata in the session token by default. You have to add it.

  1. Clerk dashboard → Configure → Sessions

    Scroll down to Customize session token and edit the claims JSON:

    {
  "metadata": "{{user.public_metadata}}"
}

    This tells Clerk to include the user's public metadata in every session token. Click Save.

  2. Make yourself an admin

    Go to Users and select your account (it should be the only one). Scroll to User metadata and click Edit next to Public:

    {
  "role": "admin"
}

    Click Save. You are now an admin.

Why public metadata? Clerk has public, private and unsafe metadata. Public metadata can be read by the frontend but changed only from the backend or the dashboard, so users can't make themselves admins. That makes it a good place to store roles.

New to Clerk metadata? Public vs private vs unsafe

Metadata is extra JSON data you attach to a user in Clerk. There are three kinds, and the difference is who can read and who can write:

KindFrontend can read?Frontend can write?Good for
PublicYesNo (backend or dashboard only)Roles, plan names: things the UI may show but users must not change
PrivateNoNo (backend only)Secrets about the user, such as an internal billing id
UnsafeYesYesHarmless preferences, such as a chosen theme

A role stored in unsafe metadata would be a security hole: any user could set "role": "admin" on themselves from the browser.

The claims template "{{user.public_metadata}}" is a Clerk shortcode: when it creates a token, Clerk replaces it with that user's public metadata object, so the token contains "metadata": { "role": "admin" }.

Test it

  1. As admin: open /upload. You can reach the PDF upload page.
  2. Set your role back to "user" in the dashboard and save. Refresh, then open /upload. You are redirected to the home page.
  3. Set it to "admin" again. /upload works again.

The session token is refreshed periodically, roughly every minute. If a role change doesn't seem to apply, refresh the page, or sign out and back in.

Common mistakes

  • Always redirected, even as admin: usually the session token template from Part C wasn't saved, so metadata is missing from the token. Check Configure → Sessions again, then sign out and back in.
  • Typo in the JSON: "Admin" or "admin " (with a space) is not "admin". The comparison is exact.
  • Metadata put in the wrong box: it must be Public metadata, because the token template reads user.public_metadata.
  • Editing the old file: the middleware lives in src/middleware.ts (next to app/), not inside src/app/. Next.js ignores a middleware file in the wrong place.

Going further (not in the video): the middleware protects the /upload page. For defence in depth, also check the role inside the server action (processPdfFile, or processFile after step 21), because a server action can be called independently of the page that uses it. For example: const { sessionClaims } = await auth(); from @clerk/nextjs/server, then return an error if the role isn't "admin".

Recap
  • Roles live in Clerk's public metadata and reach your code through the customized session token.
  • types/globals.d.ts makes sessionClaims.metadata.role type-safe.
  • The middleware redirects non-admins away from /upload, while every non-public route still requires sign-in.
