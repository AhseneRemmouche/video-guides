Embedding Utility

generateEmbedding and generateEmbeddings with text-embedding-3-small.

▶ Watch this part (35:11)

Goal

The server action (step 12) needs two helpers. This page builds the first: turning text into embeddings. You need embeddings in two places:

  • When processing a PDF: many chunks at once, so use a batch function.
  • When a user searches: one query, so use a single function.

What an embedding is

An embedding is a list of numbers, here 1,536 of them, that captures what a piece of text means. "How many vacation days do I get?" and "PTO allowance per year" share almost no words, but their vectors are close together. That is what lets the search in step 14 find passages by meaning.

New to embeddings? An intuitive picture with just 2 numbers

Imagine a tiny embedding model that describes every sentence with only 2 numbers: how much it is about time off (first number) and how much it is about computers (second number). Each sentence becomes a point on a map:

SentenceVector [time off, computers]
"How many vacation days do I get?"[0.9, 0.1]
"PTO allowance per year"[0.85, 0.15]
"How do I reset my laptop password?"[0.05, 0.95]

The first two points sit almost on top of each other; the third is far away in a different direction. So "closeness on the map" = "similar meaning", even though the first two sentences share no important words.

A real model does the same thing with 1,536 numbers instead of 2. Nobody chose what each number means: the model learned them from huge amounts of text. You can't draw 1,536 dimensions, but the maths is identical: you measure the angle between two arrows (that's cosine similarity, used in step 14). A small angle means similar meaning.

Key facts to remember:

  • The same text always gives (essentially) the same vector.
  • Every vector from one model has the same length (1,536 here), no matter if the text is 3 words or 3 paragraphs.
  • Vectors are only comparable if they come from the same model.

Step by step

  1. Create src/lib/embeddings.ts and import embed from ai and openai from @ai-sdk/openai.

    Both packages were installed in step 4 (the AI SDK and its OpenAI provider), and the provider reads your OPENAI_API_KEY from .env.local automatically, so there is nothing new to install or configure.

  2. Write generateEmbedding (single, used for search queries)
    • It takes a string and returns an array of numbers, the embedding vector.
    • Clean the text first: replace every newline with a space (replaceAll).
    • Call embed with model: openai.textEmbeddingModel("text-embedding-3-small") and value: input. This model produces 1,536-dimension vectors, exactly what the schema in step 9 expects.
    • Destructure embedding from the result and return it.
  3. Write generateEmbeddings (batch, used for PDF processing)

    You could call generateEmbedding once per chunk, but that is many API calls, which is slow and expensive. Instead, import embedMany and embed every chunk in one request:

    • It takes texts: string[] and maps each one to a cleaned version, giving inputs.
    • Call embedMany with the same model and values: inputs.
    • Destructure and return embeddings, one vector per input, in the same order.
New to batching? Why one call for many texts beats many calls

Every call to OpenAI is an HTTP request that travels over the internet and back. That round trip has a fixed cost (often a few hundred milliseconds) no matter how small the text is.

  • One by one: a PDF with 40 chunks = 40 round trips, one after another. That's 40 waits, and 40 chances to hit OpenAI's rate limit (the maximum number of requests per minute).
  • Batch: 40 chunks in one request = one round trip. OpenAI processes them together and returns 40 vectors in the same order you sent them.

You pay per token either way, so batching doesn't change the price of the text itself; it saves time and requests. (For very large inputs, embedMany automatically splits the list into several requests if it exceeds the model's per-call limit.) A search question is only one text, so the single embed is the natural fit there.

Complete file

// src/lib/embeddings.ts
import { embed, embedMany } from "ai";
import { openai } from "@ai-sdk/openai";

export async function generateEmbedding(text: string): Promise<number[]> {
  const input = text.replaceAll("\n", " ");

  const { embedding } = await embed({
    model: openai.textEmbeddingModel("text-embedding-3-small"),
    value: input,
  });

  return embedding;
}

export async function generateEmbeddings(texts: string[]): Promise<number[][]> {
  const inputs = texts.map((text) => text.replaceAll("\n", " "));

  const { embeddings } = await embedMany({
    model: openai.textEmbeddingModel("text-embedding-3-small"),
    values: inputs,
  });

  return embeddings;
}

New to Promise<number[]>? Reading the return types

An async function doesn't return its value immediately. It returns a Promise: an object that says "the value will be ready later". The caller uses await to pause until it's ready:

const vector = await generateEmbedding("vacation days"); // number[]
console.log(vector.length); // 1536

Reading the types from the inside out:

  • number: one number, like 0.0123.
  • number[]: an array of numbers, like [0.0123, -0.045, …]. One vector.
  • number[][]: an array of arrays of numbers. A list of vectors.
  • Promise<…>: "you'll get this later, after await".

Writing the return type explicitly is optional (TypeScript can work it out), but it documents what the function gives back and makes TypeScript complain if you accidentally return the wrong thing.

Video vs repo: in the video the presenter types text.replace("\n", " "), which only replaces the first newline. The GitHub repo uses replaceAll, which replaces every newline, and adds explicit return types (Promise<number[]> and Promise<number[][]>). Use the repo version shown above.

The embedding model must be the same for stored chunks and for search queries. Vectors from different models can't be compared. If you switch models, change the dimensions in the schema and re-embed every document.

How to know it worked: nothing visible happens yet, because nothing calls these functions until step 12. Your editor should show no red underlines in the file. You'll see the result when you upload a PDF and the embedding column in Neon fills with long lists of numbers.

Common mistakes:

  • Using openai("text-embedding-3-small") instead of openai.textEmbeddingModel(…). The plain openai(…) form is for chat models.
  • Typing value in embedMany or values in embed. Each function expects its own name.
  • Forgetting await: you'd get a Promise object instead of the numbers, and the database insert would fail.
  • A wrong or missing OPENAI_API_KEY shows up later as a 401 error when you upload. Restart npm run dev after editing .env.local.
Recap
  • generateEmbedding: one string in, one 1,536-number vector out. Used for search queries.
  • generateEmbeddings: many strings in one API call. Used for PDF chunks.
