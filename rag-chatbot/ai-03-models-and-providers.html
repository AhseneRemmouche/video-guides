Models, Providers & Choosing One

Closed vs open-weight models, providers, local models, and how to pick a model for a job.

Your chatbot uses OpenAI models, but OpenAI is only one of many companies offering them, and you can even run models on your own computer. This chapter explains the landscape: closed versus open-weight models, the main providers, which properties to compare, how running a model locally works, how to switch providers in the AI SDK, and how to choose a model for each job in this project.

Why this matters for your chatbot. Choosing a model is a trade-off between quality, speed, cost and privacy. A model that is perfect for an agent's reasoning may be wasteful for reading text out of a scanned PDF. Knowing how to compare and swap models lets you make the app cheaper, faster or more private without rewriting it.

A note on time. This field changes every few months. The providers and model names below are examples at the time of writing (2025), not recommendations or rankings. Before choosing, always check each provider's current model list and pricing page.

Models and providers: two different things

A model is the trained network itself, for example gpt-5-mini or text-embedding-3-small. A provider is whoever runs that model and gives you access to it, usually through an API. Often they are the same company (OpenAI makes and serves GPT models), but not always: cloud platforms such as Amazon Bedrock, Google Cloud Vertex AI and Microsoft Azure host models from several makers, and services or tools like Ollama run open models made by others.

In the AI SDK, "provider" also means the small package that knows how to talk to one of these services, such as @ai-sdk/openai, which you installed in step 4.

Closed models vs open-weight models

Remember from chapter 1 that a model's knowledge lives in its parameters, also called weights.

  • Closed (proprietary) models: the weights are secret. You can only use the model through the maker's API or its cloud partners. Examples: OpenAI's GPT models, Anthropic's Claude models, Google's Gemini models.
  • Open-weight models: the weights are published for download, so anyone can run the model on their own hardware or pick any hosting company. Examples: Meta's Llama family, many Mistral models, Google's Gemma, and models from DeepSeek and Alibaba's Qwen team, among others.
Closed models via APIOpen-weight models
SetupSign up, get an API key, call it. Minutes.Use a host that serves them (just as easy), or run them yourself (needs hardware and know-how).
Where data goesTo the provider's servers, under their data policy.Can stay entirely on your own machines if you self-host.
ControlThe provider can update or retire a model; you follow their schedule.You can pin an exact version forever and fine-tune it yourself.
Cost modelPay per token.Pay for hardware or hosting; per-token cost can be low at high volume, but you run the infrastructure.
CapabilityOften where the newest frontier capabilities appear first.Has improved quickly; strong options exist for many tasks. Compare on your own use case.

Common misconception: "open-weight" means "open source" with no strings attached. Many open-weight models come with their own licence, which may restrict certain uses or very large companies, and the training data is usually not published. Read the licence before using a model in a product (chapter 16 touches on licensing).

Small vs large models

Most providers offer a family in several sizes, such as a "mini" or "nano" next to a full-size model. In this project, every model name ends in -mini or -small, which is a sensible default for learning and for many production apps.

Small modelsLarge models
Faster and much cheaper per token.Slower and more expensive.
Great for focused tasks: classification, extraction, OCR, short answers grounded in retrieved text.Better at complex reasoning, nuanced writing, long multi-step agent work and unusual questions.
Can run on modest hardware if open-weight.Open-weight large models need serious GPU hardware.

Rule of thumb: start with a small model, measure, and only move up if quality is not good enough. RAG helps small models a lot, because the hard part (knowing the facts) is done by retrieval; the model mostly needs to read and summarise.

Running models locally

A local model runs on your own computer or server instead of a provider's cloud. Reasons to do it: privacy (data never leaves your machine), working offline, no per-token bill, and experimentation. Reasons not to: you need suitable hardware, local models are usually smaller and less capable than the largest cloud models, and you take on the operations work.

Ollama

Ollama is a popular free tool that downloads and runs open-weight models on macOS, Windows and Linux. After installing it, one command downloads and starts a model:

ollama pull llama3.2
ollama run llama3.2

Line by line

Line(s)CodeWhat it does & why
1ollama pull llama3.2ollama is the CLI program; pull downloads a model's weights to your disk; llama3.2 is the model's name in Ollama's library. Downloads are often several gigabytes.
2ollama run llama3.2Loads the model into memory and opens an interactive chat in the terminal. Ollama also runs a local server (by default on port 11434) that your code can call.

Model names in Ollama's library change over time; check its website for current ones.

New to GPUs and quantization? What decides whether a model runs on your machine

A model's parameters must fit in memory while it runs. A GPU (graphics card) is a chip that does many multiplications in parallel, which is exactly what neural networks need, so models run far faster on a GPU than on a normal CPU. The GPU's own memory (VRAM) is usually the limit. Apple Silicon Macs share memory between CPU and GPU, which is why they are popular for local models.

Rough idea: each parameter is a number. Stored at 16 bits (2 bytes), a 7-billion-parameter model needs about 14 GB just for its weights, more than many laptops have free.

Quantization stores each parameter with fewer bits, for example 4 bits instead of 16. That makes the same 7-billion-parameter model need roughly a quarter of the memory (around 4 GB for the weights), so it fits on ordinary machines and runs faster. The cost is a small loss of quality, which is usually acceptable at moderate levels. Tools like Ollama typically download quantized versions by default.

Rule of thumb, not a guarantee: small models (a few billion parameters) run on a decent laptop; tens of billions need a strong GPU or a high-memory Mac; the largest open models need server hardware.

You can call a local Ollama model from the AI SDK through Ollama's OpenAI-compatible endpoint, using the official @ai-sdk/openai-compatible package (you would install it with npm install @ai-sdk/openai-compatible):

import { createOpenAICompatible } from "@ai-sdk/openai-compatible";
import { generateText } from "ai";

const ollama = createOpenAICompatible({
  name: "ollama",
  baseURL: "http://localhost:11434/v1",
});

const { text } = await generateText({
  model: ollama("llama3.2"),
  prompt: "Explain pgvector in one sentence.",
});

Local models and this project. A local chat model will only work as a drop-in for the agent if it supports tool calling well; many small models struggle with it. Also, embeddings must always come from the same embedding model, and your database column is fixed at 1,536 dimensions (step 9). Switching embedding models means changing the column and re-embedding every document.

Switching providers in the AI SDK

The AI SDK gives every provider the same interface, so switching the chat model is usually a two-line change. Say you wanted to try an Anthropic Claude model in the chat route. First, install the provider package from the project folder:

npm install @ai-sdk/anthropic

Here npm is the Node package manager, install downloads a package and records it in package.json, and @ai-sdk/anthropic is the official AI SDK provider for Anthropic. Then add your key to .env.local (the provider reads ANTHROPIC_API_KEY by default) and restart the dev server:

ANTHROPIC_API_KEY=your-key-here

Finally, change the import and the model: line in src/app/api/chat/route.ts:

import { anthropic } from "@ai-sdk/anthropic";

const result = streamText({
  model: anthropic("claude-sonnet-4-5"),
  messages: convertToModelMessages(messages),
  tools,
  system: SYSTEM_PROMPT,
  stopWhen: stepCountIs(6),
});

Common mistakes when switching

  • Forgetting the API key or not restarting npm run dev after editing .env.local: you get an "API key is missing" style error.
  • Typos in the model ID: the provider returns a "model not found" error. Copy IDs from the provider's docs.
  • Assuming identical behaviour: different models follow prompts differently. Re-test your system prompt and tools; you may need to adjust wording.
  • Provider-specific options: settings under providerOptions (for example OpenAI-only options) do not carry over to another provider.

API keys, rate limits and usage tiers

New to rate limits? What they are and what happens when you hit one

A rate limit is a cap the provider puts on how much you can use per time window, typically requests per minute and tokens per minute (sometimes per day). It protects the provider's servers and stops one account from using everything.

When you exceed it, the API answers with HTTP status 429 ("Too Many Requests"). The AI SDK automatically retries some failed calls a couple of times with increasing waits (the maxRetries option controls this), but if you keep sending too much, requests will fail and users will see errors.

  • API keys identify your account and are billed to it. Keep them secret on the server, in .env.local, never in client code or Git (you did this in step 4). Use separate keys for development and production so you can revoke one without breaking the other.
  • Usage tiers: several providers, including OpenAI, raise your rate limits automatically as your account's payment history grows. A brand-new account usually has low limits, which matters if you plan a launch or a demo with many users.
  • Spending limits: most provider dashboards let you set budgets or alerts. Set one before you deploy anything public.
  • Different models, different limits: limits are often per model, so a fallback model can also be a way to handle traffic spikes (chapter 14).

A decision checklist

Run through these questions for each AI job in your app. They are a practical guide, not a formula.

  1. What is the job? Generate text, call tools, embed text, read images, transcribe audio, speak? This decides the kind of model before anything else.
  2. Which modalities in and out? Rule out models that cannot accept your inputs.
  3. Does it need tools or structured output? Rule out models with weak or no support.
  4. How hard is the reasoning? Simple and focused → small fast model. Multi-step, ambiguous → larger or reasoning model.
  5. Is a person waiting? If yes, latency matters a lot; prefer fast models and streaming.
  6. How much context? Estimate tokens for system prompt + history + retrieved chunks + answer.
  7. What data are you sending? Check retention, training-use and region policies; consider zero data retention, a cloud platform you already trust, or a local model.
  8. What volume and budget? Multiply calls per day by tokens per call; check the provider's current prices.
  9. Test on your own examples. Try two or three candidates on 10–20 realistic questions and compare. Your test beats any public leaderboard for your use case.
  10. Plan for change. Keep model IDs in one place (a constant or environment variable) so swapping later is trivial.

Recap
  • A model is the trained network; a provider serves it (and in the AI SDK, is the package that talks to it).
  • Closed models are API-only; open-weight models can be self-hosted but come with licences and hardware needs.
  • Compare models on quality, latency, cost tier, context size, modalities, tool calling, reasoning, data retention and rate limits, never on "which is best" in general.
  • Start small; move up only when your tests show you need to.
  • Local models (for example via Ollama) need memory; quantization shrinks them at a small quality cost.
  • Switching chat providers in the AI SDK means installing the package (e.g. @ai-sdk/anthropic), adding its key, and changing model:. Embedding changes require re-embedding.
  • Protect API keys, know your rate limits and usage tier, and set spending limits.
  • This project uses five models for five jobs: chat, embeddings, vision, STT and TTS.
