Integrating Search Tool for AI

Give the model a searchKnowledgeBase tool — the full RAG loop.

▶ Watch this part (58:50)

Goal

You can now upload documents, search them, and chat with the AI. This step connects them. You give the model a tool called searchKnowledgeBase, and the model decides when to call it, reads the results and answers from them. This completes the RAG loop.

New to tool calling? How an AI "uses" your function

An LLM can only produce text. It can't open your database. Tool calling is a trick that lets it ask you to run code on its behalf:

  1. Along with the conversation, you send the model a list of tools: a name, a description and the shape of the input each one needs.
  2. The model reads the question. If it decides a tool would help, instead of answering it replies with a structured request, for example: "call searchKnowledgeBase with { query: "vacation policy" }".
  3. The AI SDK sees this request, runs your execute function on your server, and sends the result back to the model.
  4. The model reads the result and writes the final answer.

The model never runs code itself. It only chooses which tool to call and with what arguments. Your server stays in control of what actually happens.

Step by step

All the changes are in src/app/api/chat/route.ts.

  1. Add imports

    tool from ai lets you define tools for the AI. z from zod defines the tool's input schema. searchDocuments comes from @/lib/search.

  2. Define the tool before the POST handler
    • description: "Search the knowledge base for relevant information". The model reads this to decide when to use the tool.
    • inputSchema: z.object({ query: z.string().describe(...) }). This tells the model what arguments to provide.
    • execute: an async function that receives { query } and runs the search.
  3. Implement execute
    • Call searchDocuments(query, 3, 0.5). Limiting to 3 results keeps the context focused. 0.5 is already the default, so you can leave it out.
    • If there are no results, return "No relevant information found in the knowledge base".
    • Otherwise format each result as [1] content, [2] content… joined by blank lines, and return that string.
    • In catch, log "Search error:" and return "Error searching the knowledge base", so the model gets a readable message instead of a crash.
  4. Export typed message types

    Import InferUITools and UIDataTypes from ai, then add these after the tools:

    • ChatTools = InferUITools<typeof tools>
    • ChatMessage = UIMessage<never, UIDataTypes, ChatTools>. Use never because there is no metadata.

    With these, TypeScript knows about your tools throughout the app. Update the POST handler so messages is typed as ChatMessage[].

  5. Pass the tools and a system prompt to streamText

    Use tools (shorthand, since key and value are the same) and a system prompt that tells the AI when to search and how to answer. The presenter pasted the prompt. It is reproduced in full below.

  6. Allow two steps

    When the AI uses a tool, that is one step. It then needs another step to process the results and reply. Import stepCountIs and add stopWhen: stepCountIs(2). Without it, generation would stop after the tool call and the user would never see an answer.

New to Zod schemas? Describing the shape of data

Zod is a library for describing what data should look like, and checking it at runtime. TypeScript types disappear when your code runs; a Zod schema still exists and can validate real data.

const schema = z.object({ query: z.string() });
schema.parse({ query: "vacation" });  // OK, returns the object
schema.parse({ query: 42 });          // throws: expected string

For tools, the schema does two jobs. The AI SDK converts it into a JSON description that is sent to the model, so the model knows it must provide a query string. .describe("…") adds a hint the model reads. When the model's arguments come back, they're checked against the same schema before execute runs, and TypeScript knows query is a string.

New to system prompts? The model's standing instructions

A chat with an LLM is a list of messages, each with a role. User messages come from the person, assistant messages from the AI, and the system message is a set of instructions from you, the developer, that applies to the whole conversation. The user never sees it.

The system prompt is where you set behaviour: "search before answering", "be concise", "base your answer on the results". The model follows it fairly reliably, but it's guidance, not a guarantee. If answers are too long or the model skips the search, the system prompt is the first thing to adjust.

New to steps and stopWhen? Why one request can need two model calls

A step is one round-trip to the model: send messages, get a reply. In the tool flow, the first reply is "please call the tool" (step 1). After execute runs, the SDK must call the model again with the tool result so it can write the answer (step 2).

By default streamText stops after one step. stopWhen: stepCountIs(2) means "keep going until 2 steps have happened". If the model answers directly without a tool, it simply finishes after step 1. If you wanted the model to be able to search twice (for example once for "vacation" and once for "sick leave"), you'd raise it to 3 or more.

Complete file

// src/app/api/chat/route.ts
import {
  streamText,
  UIMessage,
  convertToModelMessages,
  tool,
  InferUITools,
  UIDataTypes,
  stepCountIs,
} from "ai";
import { openai } from "@ai-sdk/openai";
import { z } from "zod";
import { searchDocuments } from "@/lib/search";

const tools = {
  searchKnowledgeBase: tool({
    description: "Search the knowledge base for relevant information",
    inputSchema: z.object({
      query: z.string().describe("The search query to find relevant documents"),
    }),
    execute: async ({ query }) => {
      try {
        // Search the vector database
        const results = await searchDocuments(query, 3, 0.5);

        if (results.length === 0) {
          return "No relevant information found in the knowledge base.";
        }

        // Format results for the AI
        const formattedResults = results
          .map((r, i) => `[${i + 1}] ${r.content}`)
          .join("\n\n");

        return formattedResults;
      } catch (error) {
        console.error("Search error:", error);
        return "Error searching the knowledge base.";
      }
    },
  }),
};

export type ChatTools = InferUITools<typeof tools>;
export type ChatMessage = UIMessage<never, UIDataTypes, ChatTools>;

export async function POST(req: Request) {
  try {
    const { messages }: { messages: ChatMessage[] } = await req.json();

    const result = streamText({
      model: openai("gpt-5-mini"),
      messages: convertToModelMessages(messages),
      tools,
      system: `You are a helpful assistant with access to a knowledge base. 
          When users ask questions, search the knowledge base for relevant information.
          Always search before answering if the question might relate to uploaded documents.
          Base your answers on the search results when available. Give concise answers that correctly answer what the user is asking for. Do not flood them with all the information from the search results.`,
      stopWhen: stepCountIs(2),
    });

    return result.toUIMessageStreamResponse();
  } catch (error) {
    console.error("Error streaming chat completion:", error);
    return new Response("Failed to stream chat completion", { status: 500 });
  }
}

Video vs repo, the model: the repo's final route.ts uses openai("gpt-5-mini"), while the video uses gpt-4.1-mini and recommends it for following along. Both work. As the presenter explains in step 5, gpt-5-mini needs an extra setup step if your OpenAI organization has zero data retention enabled. The repo's tool messages also end with a period ("…knowledge base."). That has no effect on behaviour.

Why the chat page needs no changes. Tool calls arrive as message parts of type tool-searchKnowledgeBase. The page's switch only renders "text" parts and returns null for anything else (the default case), so tool calls stay invisible and only the final answer shows. To show "Searching…" in the UI, add a case "tool-searchKnowledgeBase":, typing useChat<ChatMessage>() so it is checked.

New to TypeScript generics? Reading InferUITools<typeof tools> and UIMessage<…>

A generic is a type with "blanks" you fill in, written in angle brackets. You already know one from everyday code: Array<string> means "an array, and the blank (what's inside) is string".

  • typeof tools asks TypeScript for the type of the tools object you wrote: its tool names, their inputs and outputs.
  • InferUITools<…> is a helper from the AI SDK that takes that type and converts it into the format chat messages use for tool parts. You never write those types by hand; they're inferred (worked out) from your code.
  • UIMessage<Metadata, DataParts, Tools> is the type of one chat message, with three blanks. You fill in never for metadata ("this never exists"), the SDK's default UIDataTypes for custom data parts, and your ChatTools for tools.

These are only types: they vanish when the code runs and change no behaviour. Their value is that your editor now knows a message can contain a part of type "tool-searchKnowledgeBase" with an input { query: string }, and warns you about typos.

Test the full RAG system

  1. Make sure a PDF has been uploaded on /upload.
  2. Ask "What is our vacation policy?" on /chat

    The AI searches the knowledge base and answers from the handbook. In the video: PTO of 15 days for 0–2 years of service and 20 days for 3–5 years, with requests submitted at least two weeks in advance through the HR portal. These figures match the PDF.

  3. Ask "Are there any professional development benefits?"

    Answer: yes, an annual education budget of $2,000 per employee.

Common mistakes

  • Forgetting stopWhen: the chat shows nothing (or an empty reply) after a question, because generation stopped right after the tool call.
  • No documents uploaded: the tool returns "No relevant information found…" and the AI says it doesn't know. Upload a PDF on /upload first.
  • The AI answers without searching: the question may not look document-related to it. Rephrase, or make the system prompt stricter ("Always search the knowledge base before answering").
  • "Search error:" in the terminal: usually the database URL or OpenAI key is missing from .env.local. Restart npm run dev after editing it.

The AI doesn't need to know your documents in advance. It looks up the relevant information when a question is asked and uses it to answer accurately.

Recap
  • The tool's description and inputSchema tell the model when and how to search. execute runs searchDocuments and returns numbered snippets.
  • The system prompt pushes the model to search first and keep answers short and grounded.
  • stopWhen: stepCountIs(2) allows one step for the tool call and one for the answer.
  • Last feature: restrict uploads to admins.
