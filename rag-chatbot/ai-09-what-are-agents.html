What Are AI Agents?

The agent loop, workflows vs agents, and when an agent is (and isn't) the right tool.

"Agent" is one of the most used (and most stretched) words in AI right now. In this chapter you will learn what an AI agent actually is, how the agent loop works step by step, how agents differ from simpler "workflows", and, just as important, when you should not build one. You will then see exactly how this project became an agent in step 22, with a full multi-step trace, and which AI SDK building blocks control the loop.

Why this matters for your chatbot. Up to step 15, the chatbot could make one search and then answer. After step 22 it can search, check today's date, do arithmetic and combine the results, deciding for itself which tool to use next. That small change turns a "question → answer" bot into a system that plans its own steps. Understanding the loop helps you debug it, keep it cheap, and keep it safe.

A plain definition

An AI agent is a large language model (LLM) that uses tools in a loop to work towards a goal, deciding its own next step each time. Three parts of that sentence matter:

  • Uses tools. The model can ask your code to run functions (search a database, read the date, call an API). This is tool calling, covered in depth in Tool Calling in Depth.
  • In a loop. After a tool runs, its result goes back to the model, which can then call another tool, or the same tool again, or answer.
  • Deciding its own next step. Your code does not say "first search, then calculate". The model looks at what it knows so far and chooses. That is the difference between an agent and a fixed program.

A useful mental picture: a normal chatbot is like asking a colleague a question and getting an answer straight from memory. An agent is like asking a colleague who can walk to the filing cabinet, check the calendar, use a calculator, and then come back with an answer, choosing for themselves which of those to do.

New to "tools"? What a tool is, in one minute

A tool is a normal function in your code (TypeScript here) plus a short description and an input schema. You send the description and schema to the model. The model cannot run code itself; instead it replies with a structured request such as "please call calculator with { "expression": "30 - 10 + 1" }". The AI SDK sees that request, runs your function, and sends the result back to the model.

// What the model "sees" (simplified): a name, a description and an input shape
calculator: "Evaluate a math expression and return the exact result."
  input: { expression: string }

// What the model replies with when it wants the tool:
{ toolName: "calculator", input: { expression: "30 - 10 + 1" } }

The model only ever asks. Your code decides whether and how to run the request. That is an important safety property you will come back to later.

The agent loop

Every agent, from a tiny demo to a large coding assistant, runs some version of the same loop:

  1. Observe: the model reads everything it has so far: the system prompt, the conversation, and any earlier tool results.
  2. Think: it decides what is missing. ("I need the vacation policy. I also need today's date.")
  3. Act: it requests a tool call. Your code runs the tool.
  4. Observe the result: the tool's output is added to the conversation.
  5. Repeat until the model decides it has enough, or a stopping rule ends the loop.
  6. Answer: the model writes a final text reply instead of another tool call.

In the AI SDK, one pass round this loop is called a step. A step is one request to the model plus, if the model asked for tools, running those tools. That word matters, because the setting that controls the loop, stopWhen: stepCountIs(6), counts steps.

Workflows vs agents

Anthropic's article "Building effective agents" draws a helpful line that many teams now use. Paraphrasing it:

  • A workflow is a system where LLMs and tools are orchestrated through predefined code paths. Your code decides the order: "call the model to classify, then search, then call the model to answer".
  • An agent is a system where the LLM dynamically directs its own process and tool usage. The model decides the order, how many steps, and when it is done.

The same article calls both of these "agentic systems", and it builds both on one basic building block it calls the augmented LLM: a model enhanced with retrieval, tools and memory. Your step 15 chatbot is already an augmented LLM.

New to "orchestration"? What the word means here

Orchestration just means "deciding what runs, in which order, with which inputs". In a workflow, you write the orchestration as ordinary code: const category = await classify(q); if (category === "policy") { … }. In an agent, you hand the orchestration to the model: it picks the next tool based on what it has seen.

Levels of autonomy

"Is it an agent?" is less useful than "how much control does the model have?". The scale below is an informal way to think about it (it is a teaching aid, not an official standard):

LevelWhat the model controlsExample in this project's world
0 · Single callOnly the words of one replyStep 5: question in, streamed answer out
1 · Augmented callThe reply, using context your code fetchedCode searches first, pastes chunks into the prompt, model answers
2 · WorkflowIndividual steps inside a path your code fixedClassify the question, then run the matching pipeline
3 · Tool-using agent (bounded)Which tools to call, how often, when to stop, within a step limitStep 22: three tools, at most 6 steps
4 · Autonomous agentLong multi-step tasks, possibly with actions that change things"File my vacation request, update the team calendar and notify my manager"

Each level up gives more flexibility and also more ways to go wrong. Move up only when the level below cannot do the job.

When to use an agent (and when not to)

A rule of thumb from Anthropic's article, and a good one for beginners: find the simplest solution that works, and only add complexity when it clearly improves results. Many useful AI features are a single, well-prompted model call with good retrieval.

Choose…When…Example
A single callThe task is one well-defined transformation and all needed information can be put in the prompt.Summarise this uploaded policy in five bullet points.
A workflowThe steps are known in advance and you want predictable cost, speed and behaviour.Classify each support message, then send it to the right prompt.
An agentYou cannot predict the steps; the number and order of tool calls depend on what earlier tools return."Can I take vacation from the 1st, given today's date and our notice rules?"

Why agents cost more than they look

  • Cost: every step is a full model call, and each call re-sends the growing conversation (all earlier tool results included). Six steps can easily cost several times one call. See Running AI in Production for cost control.
  • Latency: steps run one after another, so waiting time adds up. Streaming the intermediate steps to the UI (as step 23 does) makes the wait feel shorter and more honest.
  • Predictability: the same question can take a different path on a different run, which makes testing harder (see Evaluating AI Applications).
  • Errors compound: if each step is right, say, 95% of the time, a chain of several steps is right less often than any single step, because one mistake early (a bad search query) feeds every later step. This is simple probability, and it is the main reason to keep agents short and tools reliable.
Common misconceptions
  • "An agent is a smarter model." No. It is the same model, called several times, with tools. The model does not get more intelligent; it gets more chances and more information.
  • "More autonomy is always better." No. Autonomy trades predictability for flexibility. For many business features, a workflow is the better product.
  • "Agents need a special framework." No. The loop is a few lines of code. The AI SDK gives it to you with one option, stopWhen.
  • "The model runs the tools." No. The model only requests tool calls; your server runs them.

The ReAct pattern: reason, then act

The agent loop you saw above has a name in research: ReAct, short for "Reasoning and Acting", from a 2022 research paper titled "ReAct: Synergizing Reasoning and Acting in Language Models". The idea is that the model alternates between:

  • Thought: a short piece of reasoning about what to do next.
  • Action: a tool call.
  • Observation: the tool's result.

…repeating until it can give a final answer. Interleaving thinking with real observations helps the model correct itself: if a search returns nothing, the next thought can be "try different wording" rather than inventing an answer (a hallucination).

Thought: The question depends on the company's notice rule. Search for it.
Action: searchKnowledgeBase({ query: "vacation request notice period" })
Observation: [1] Vacation requests must be submitted at least 14 days ...
Thought: I need today's date to count the days.
Action: getCurrentDate({})
Observation: { isoDate: "2025-11-10", ... }
...
Final answer: Yes, ...

Modern tool-calling APIs build this in: the "action" is a structured tool call rather than text you have to parse, and with reasoning models the "thought" often happens inside the model before it emits a tool call. You do not need to write "Thought/Action/Observation" prompts yourself; the AI SDK's tool loop is a ReAct-style loop.

How this project became an agent (step 22)

In step 15 the route had one tool, searchKnowledgeBase, and stopWhen: stepCountIs(2): one step to call the search, one step to answer. That is a minimal loop: enough for "search once, then reply", but not for questions that need several kinds of information.

Step 22 changed three things:

  1. Three tools instead of one: searchKnowledgeBase (company documents), getCurrentDate (today's date, since a model has no clock) and calculator (exact arithmetic, since models are unreliable at maths).
  2. A system prompt that explains how to work: search first when relevant, call getCurrentDate for date questions, use the calculator for any arithmetic, and say honestly when the tools do not have the answer.
  3. A bigger step budget and logging: stopWhen: stepCountIs(6) plus an onStepFinish callback that prints every tool call.

Here is the heart of it, copied from code/22-route.ts (lines 102–115):

    const result = streamText({
      model: openai("gpt-5-mini"),
      messages: convertToModelMessages(messages),
      tools,
      system: SYSTEM_PROMPT,
      // An agent may need several tool calls before it can answer
      stopWhen: stepCountIs(6),
      onStepFinish: ({ toolCalls, finishReason }) => {
        for (const call of toolCalls) {
          console.log(`[agent] called ${call.toolName}`, call.input);
        }
        console.log(`[agent] step finished: ${finishReason}`);
      },
    });

A concrete trace: "Can I request vacation starting on December 1?"

Let us follow one question through the loop. The document text and dates below are made up for illustration; your knowledge base will contain whatever PDFs you uploaded, and your log will show your real date.

Suppose a user asks: "Can I request vacation starting on 2025-12-01?" and the uploaded HR policy contains a sentence like "Vacation requests must be submitted at least 14 calendar days before the first day of leave."

StepModel decidesTool result (observation)finishReason
1This is about company rules: call searchKnowledgeBase({ query: "vacation request notice period" })[1] Vacation requests must be submitted at least 14 calendar days before…tool-calls
2The answer depends on today: call getCurrentDate({}){ isoDate: "2025-11-10", readable: "Monday, November 10, 2025" }tool-calls
3November has 30 days, so days from Nov 10 to Dec 1 is (30 − 10) + 1: call calculator({ expression: "(30 - 10) + 1" }){ expression: "(30 - 10) + 1", result: "21" }tool-calls
421 is at least 14, so the rule is met. Write the answer.(no tool) "Yes. December 1 is 21 days away, and the policy requires at least 14 days' notice, so you can still request it…"stop

In the server terminal, the onStepFinish logging would print something like this (illustrative):

[agent] called searchKnowledgeBase { query: 'vacation request notice period' }
[agent] step finished: tool-calls
[agent] called getCurrentDate {}
[agent] step finished: tool-calls
[agent] called calculator { expression: '(30 - 10) + 1' }
[agent] step finished: tool-calls
[agent] step finished: stop

Four steps, well inside the limit of six. A few things worth noticing:

  • The order was not written anywhere in code. The system prompt suggests a strategy, but the model chose these three tools in this order because of this question. A question like "What is 15% of 2000?" would skip straight to the calculator.
  • Models may call several tools in one step. Many models can request searchKnowledgeBase and getCurrentDate together in step 1 (a "parallel tool call"), finishing in fewer steps. Both are correct.
  • The weak point is visible. In step 3 the model itself worked out the formula (30 - 10) + 1; the calculator only did the arithmetic. If the model had miscounted days in the month, the answer would be wrong while looking confident. A dedicated daysBetween(start, end) tool would remove that risk. This is a general lesson: move error-prone reasoning into deterministic tools.
  • "Working days" are harder. If the policy said "10 working days", the agent would need weekends and public holidays. None of the three tools knows those, so a well-behaved agent should say so (rule 5 in the system prompt) rather than guess. A countWorkingDays tool backed by a holiday calendar would be the proper fix.

The user sees each of these steps in the chat because step 23 renders every tool part (input, status and result) in the UI.

AI SDK building blocks for agents

The AI SDK v5 gives you a small set of options that control the loop. All of these work with both generateText and streamText.

stopWhen: when the loop ends

stopWhen takes one stop condition or an array of them (the loop stops when any is met). It is only checked after a step that produced tool results; a step where the model answers in plain text ends the loop anyway. Two helpers are built in: stepCountIs(n) and hasToolCall(name). You can also write your own: a stop condition is just a function that receives the steps so far and returns true to stop.

import { hasToolCall, stepCountIs, type StopCondition } from "ai";

// Stop if the total tokens used across all steps passes a budget
const tokenBudget = (max: number): StopCondition<any> => ({ steps }) =>
  steps.reduce((sum, s) => sum + (s.usage.totalTokens ?? 0), 0) > max;

stopWhen: [stepCountIs(6), hasToolCall("finalAnswer"), tokenBudget(20_000)],

prepareStep: change settings before each step

prepareStep is a function called before every step. It receives the step number, the steps so far, the model and the messages, and may return changes for this step only: a different model, toolChoice, activeTools (a subset of tools), system prompt or messages. Return undefined to keep the defaults.

prepareStep: ({ stepNumber }) => {
  // Near the limit: take tools away so the model must answer now
  if (stepNumber >= 4) {
    return { toolChoice: "none" };
  }
  return undefined;
},

Typical uses: force a search on the first step, switch to a cheaper model for simple follow-up steps, hide risky tools until a condition is met, or trim old messages when the conversation gets long.

onStepFinish: watch every step

You have already seen this in the project. It receives the finished step, including toolCalls, toolResults, text, finishReason and usage (token counts). Use it for logging, tracing, cost tracking, and saving intermediate results.

The Experimental_Agent class

In ai 5.0.47 (the version this project uses), the package also exports an Agent class under the name Experimental_Agent. It bundles the settings you would otherwise pass to generateText/streamText (model, system, tools, stopWhen, prepareStep, onStepFinish, and so on) into one reusable object. In this version it has three methods: generate(…), stream(…), and respond({ messages }), which returns a streaming HTTP response for useChat.

import { Experimental_Agent as Agent, stepCountIs } from "ai";
import { openai } from "@ai-sdk/openai";

const hrAgent = new Agent({
  model: openai("gpt-5-mini"),
  system: SYSTEM_PROMPT,
  tools, // the same three tools as step 22
  stopWhen: stepCountIs(6),
});

// One-off use, e.g. in a script or test:
const { text, steps } = await hrAgent.generate({
  prompt: "Can I request vacation starting on 2025-12-01?",
});

Limits of agents and how to guard against them

FailureWhat it looks likeSafeguard
LoopsThe model searches the same thing again and again, or alternates between two tools without progress.A step limit (stepCountIs); prepareStep that removes tools near the limit; log and alert on repeated identical calls.
Cost blow-upsEach step re-sends the whole history; large tool results (long documents) multiply the cost.Token budgets (a custom stop condition); keep tool results short (the search tool returns only 3 chunks); per-user rate limits.
Slow answersMany sequential steps; a slow external API.Timeouts, e.g. abortSignal: AbortSignal.timeout(30_000); stream steps to the UI; prefer fewer, better tools.
Hallucinated tool callsThe model calls a tool that does not exist, or passes invalid input.The AI SDK validates inputs against your zod schema and reports errors; validate again inside execute (as calculate() limits length and disables risky functions).
Wrong but confident answersA bad early step (poor search query) poisons later steps.Tell the model to admit uncertainty; return clear "no results" messages from tools; evaluate with real test questions (chapter 12).
Harmful actionsAn agent with write tools does something irreversible, possibly because of prompt injection hidden in a document.Least privilege (this project's tools are read-only); human approval before risky actions (chapter 10); guardrails (chapter 13).
How to know your agent is healthy. Watch the [agent] lines in the terminal while you test. Healthy runs use few steps, call tools that make sense for the question, and end with step finished: stop. If you often see six steps and no stop, the agent is hitting the limit: improve tool descriptions or the system prompt before raising the limit.
Pitfalls
  • Forgetting stopWhen: the default is one step, so the model requests a tool and the reply ends with no answer.
  • Raising the step limit to "fix" bad answers. More steps usually means more cost, not better reasoning. Fix the tools and instructions first.
  • Vague tool descriptions. The description is the only thing the model knows about a tool; "Search the knowledge base" is weaker than saying what is in it and when to use it.
  • Letting tools throw. The project's tools catch errors and return a message, so the model can recover instead of the whole request failing.
Recap
  • An agent is an LLM using tools in a loop towards a goal, choosing its own next step.
  • The loop: observe → think → act (tool) → observe the result → repeat → answer. Each pass is a "step".
  • Components: model, instructions, tools, memory, stopping condition, environment. Only the first is AI.
  • Workflows follow predefined code paths; agents let the model direct the process (Anthropic's framing). Start with the simplest option that works.
  • Agents cost more, are slower and less predictable, and errors compound across steps.
  • ReAct (reason + act) is the research name for the loop that tool-calling APIs now provide.
  • Step 22 made this project an agent with three tools, a working-method system prompt, stopWhen: stepCountIs(6) and onStepFinish logging.
  • Control the loop with stopWhen, prepareStep and onStepFinish; Experimental_Agent packages the same settings into a reusable object.
  • Guard against loops, cost blow-ups and bad tool calls with step limits, budgets, timeouts, validation and least privilege.
