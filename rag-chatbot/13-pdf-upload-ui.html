Building PDF Upload UI

An /upload page that calls the server action.

▶ Watch this part (45:09)

Goal

Build /upload: a page with a file input that sends the chosen PDF to processPdfFile, shows a spinner while it works, and then shows a success or error alert.

In step 12 you wrote the server action processPdfFile, which does the heavy work (read the PDF, split it into chunks, embed them, save them). This page is the "front door" for it: the part a human actually sees and clicks.

New to forms and file inputs? What they are and why they matter

An HTML file input is the "Choose file" button you have seen on many websites. You create it with <input type="file">. When the user picks a file, the browser does not upload anything yet. It just remembers the chosen file and fires a change event.

Your code listens for that event, reads the chosen file from e.target.files (a list, because some inputs allow several files), and decides what to do with it.

To send a file to a server you normally wrap it in a FormData object. Think of FormData as an envelope with labelled slots: you put the file in a slot called "pdf", and the server opens the envelope and asks for the slot called "pdf". If the labels don't match, the server finds an empty slot.

const formData = new FormData();
formData.append("pdf", file);   // label "pdf", value = the File
formData.get("pdf");            // later, on the server: gives the File back
New to React state? Why the page needs useState

A component is a function that returns what should appear on screen. State is data the component remembers between renders. When state changes, React runs the function again and updates the screen.

useState is a hook that gives you two things: the current value and a function to change it.

const [count, setCount] = useState(0);
// count is 0 at first; calling setCount(1) re-renders the component with count = 1

This page needs two pieces of state: "are we busy?" (to show a spinner and disable the input) and "what message should we show?" (success or error).

Step by step

  1. Create src/app/upload/page.tsx with a basic PDFUpload component and "use client" at the top. It needs client-side state for uploads and loading states.

    In the App Router, the folder name becomes the URL: src/app/upload/page.tsx is shown at /upload. The file must be called exactly page.tsx. The "use client" line is needed because useState and onChange only work in the browser.

  2. Import what you need
    • useState, plus the server action processPdfFile from ./actions.
    • shadcn/ui components: Card, CardContent, Label, Input, Alert, AlertTitle and AlertDescription.
    • The Loader2 spinner icon from lucide-react (installed with shadcn).

    Common mistake: if you get "Module not found: Can't resolve '@/components/ui/alert'" (or card, label, input), that component was not added yet. Add it from the project folder with npx shadcn@latest add alert (replace alert with the missing name).

  3. Add state
    • isLoading, starting as false.
    • message, starting as null. Its type is either { type: "error" | "success"; text: string } or null.

    In the video the state is first named messages/setMessages, which causes a "cannot find message" error. It is renamed to message / setMessage. Use the singular names from the start.

  4. Build the layout
    • A full-height grey container (min-h-screen bg-gray-50 py-12 px-4), then a centred max-w-4xl mx-auto column.
    • An h1 heading, "PDF Upload".
    • A Card → CardContent → a space-y-4 div holding the Label and the file Input. htmlFor and id link the two, and accept=".pdf" limits the picker to PDF files.
    • The input is disabled while isLoading is true.
  5. Add the loading indicator

    When isLoading is true, show a spinning Loader2 with "Processing PDF…". In the video the presenter moves it outside the label and input. In the repo it sits in the same space-y-4 container, just below the input group.

  6. Add the alert

    When message is set, show an Alert. Its variant is "destructive" for errors and "default" for success. The title is "Error!" or "Success!", and the description shows message.text.

  7. Write handleFileUpload
    1. Get the first selected file. If there isn't one, return.
    2. Set isLoading to true and clear any previous message.
    3. Build a FormData and append the file under the key "pdf". The server action reads this key with formData.get("pdf").
    4. await processPdfFile(formData).
    5. On success, show the server's message (or "PDF processed successfully") and reset the input with e.target.value = "". Otherwise show the server's error (or "Failed to process PDF").
    6. In catch, show "An error occurred while processing the PDF". In finally, set isLoading back to false.
New to loading states? Why the spinner and the disabled input matter

Processing a PDF takes a few seconds: the server reads the file, splits it, and calls OpenAI to create embeddings. Without feedback the page would look frozen, and the user might pick the file again, uploading it twice and storing duplicate chunks.

A loading state is a simple true/false flag. You set it to true just before the slow work, and back to false when it ends, whether it worked or failed. While it is true you show a spinner and disable the input. Putting the "set back to false" in a finally block guarantees it always happens, so the page can never get stuck in "loading" forever.

New to controlled vs uncontrolled inputs? Why this input has no value prop

In React, a controlled input gets its value from state: <input value={name} onChange={…} />. React is the single source of truth, and the input always shows what state says.

An uncontrolled input keeps its own value inside the browser. React only listens to its events. File inputs are always uncontrolled: for security reasons, browsers don't let JavaScript put a file into a file input. That's why this page has no value= prop on the input and no state holding the file.

You are allowed to clear a file input, by setting its value to an empty string. That's exactly what e.target.value = "" does after a successful upload. It has a nice side effect: if the user later picks the same file again, the browser sees a change and fires onChange again. Without the reset, picking the same file twice would do nothing.

Complete file

// src/app/upload/page.tsx
"use client";

import { useState } from "react";
import { processPdfFile } from "./actions";
import { Card, CardContent } from "@/components/ui/card";
import { Label } from "@/components/ui/label";
import { Input } from "@/components/ui/input";
import { Alert, AlertDescription, AlertTitle } from "@/components/ui/alert";
import { Loader2 } from "lucide-react";

export default function PDFUpload() {
  const [isLoading, setIsLoading] = useState(false);
  const [message, setMessage] = useState<{
    type: "error" | "success";
    text: string;
  } | null>(null);

  const handleFileUpload = async (e: React.ChangeEvent<HTMLInputElement>) => {
    const file = e.target.files?.[0];
    if (!file) return;

    setIsLoading(true);
    setMessage(null);

    try {
      const formData = new FormData();
      formData.append("pdf", file);

      const result = await processPdfFile(formData);

      if (result.success) {
        setMessage({
          type: "success",
          text: result.message || "PDF processed successfully",
        });
        e.target.value = "";
      } else {
        setMessage({
          type: "error",
          text: result.error || "Failed to process PDF",
        });
      }
    } catch (err) {
      setMessage({
        type: "error",
        text: "An error occurred while processing the PDF",
      });
    } finally {
      setIsLoading(false);
    }
  };

  return (
    <div className="min-h-screen bg-gray-50 py-12 px-4">
      <div className="max-w-4xl mx-auto">
        <h1 className="text-3xl font-bold text-gray-900 mb-8 text-center">
          PDF Upload
        </h1>
        <Card className="mb-6">
          <CardContent className="pt-6">
            <div className="space-y-4">
              <div>
                <Label htmlFor="pdf-upload">Upload PDF File</Label>
                <Input
                  id="pdf-upload"
                  type="file"
                  accept=".pdf"
                  onChange={handleFileUpload}
                  disabled={isLoading}
                  className="mt-2"
                />
              </div>

              {isLoading && (
                <div className="flex items-center gap-2">
                  <Loader2 className="h-5 w-5 animate-spin" />
                  <span className="text-muted-foreground">
                    Processing PDF...
                  </span>
                </div>
              )}

              {message && (
                <Alert
                  variant={message.type === "error" ? "destructive" : "default"}
                >
                  <AlertTitle>
                    {message.type === "error" ? "Error!" : "Success!"}
                  </AlertTitle>
                  <AlertDescription>{message.text}</AlertDescription>
                </Alert>
              )}
            </div>
          </CardContent>
        </Card>
      </div>
    </div>
  );
}

Video vs repo: in the repo the label and input sit in their own inner <div>, and both the loader and the alert are inside the card's space-y-4 container, so all three stack with even spacing. The label reads "Upload PDF File". The behaviour is the same as in the video.

Common mistakes

  • Wrong file name or folder: it must be src/app/upload/page.tsx (not Page.tsx, not upload.tsx). Otherwise /upload shows a 404.
  • Forgetting "use client": you get an error that useState only works in Client Components.
  • Key mismatch: formData.append("pdf", …) here and formData.get("pdf") in actions.ts must use the same string.
  • Writing onChange={handleFileUpload()}: the parentheses call the function immediately during render. Pass the name only.
  • A scanned PDF (just photos of pages) has no text layer, so you get "No text found in PDF". Use a PDF where you can select text.

Test it

  1. Open localhost:3000/upload (you must be signed in).

    Make sure the dev server is running (npm run dev in the project folder). localhost means "this computer".

  2. Upload a PDF

    The presenter uses an AI-generated "TechCorp Solutions employee handbook". It has sections on health and wellness benefits, professional development, code of conduct, performance reviews, expense reimbursement and communication guidelines. Any PDF with real text works.

  3. Watch the feedback

    You see a spinner, then "Success! Created N searchable chunks". The video shows 28 chunks with its 150-character setting. With 900 / 150 the same handbook produces far fewer, larger chunks. Each new chunk advances about 750 characters instead of about 130, so expect roughly 5–6 times fewer.

  4. Check Neon

    Refresh the documents table. Each row has content and an embedding. Open neighbouring rows to see the ~150-character overlap from step 11.

How to know it worked: the spinner appears and the input greys out; after a few seconds the spinner disappears, a "Success!" alert shows the chunk count, and the input goes back to "No file chosen". In Neon, the documents table has new rows. If you see "Error!", look at the terminal running npm run dev: the server action logs PDF processing error: followed by the real cause (often a missing OPENAI_API_KEY or database URL in .env.local; restart the dev server after editing that file).

Uploading the same PDF twice stores its chunks twice. Search then returns duplicate snippets. If that happens while testing, delete the extra rows in Neon's table view.

Recap
  • The client page builds a FormData with key "pdf" and calls the server action directly, with no fetch and no API route.
  • PDFs are now processed and stored as searchable vectors.
