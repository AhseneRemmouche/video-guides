Running AI in Production

Cost, latency, rate limits, caching, observability and deployment.

On your laptop the chatbot works for one person: you. In production it must work for many people at once, every day, at a cost the company accepts, without surprising slowdowns, and in a way you can debug when someone says "it gave me a weird answer yesterday". This chapter covers what changes when an AI app goes live.

You will learn:

  • where the cost of this app comes from, how to measure it with the AI SDK's usage data, and how to reduce it;
  • what makes AI responses feel slow (latency) and how to speed them up;
  • how to stay reliable when the provider rate-limits you, times out or fails;
  • which kinds of caching help;
  • how to see what the app is doing (observability): logging, tracing with OpenTelemetry, and LLM-specific tools;
  • how to deploy on Vercel with Neon, and a go-live checklist.

Why this matters for your chatbot: the agent from step 22 can make up to 6 model calls for one question, each re-sending the whole conversation. Uploads call a vision model and an embedding model. Without measurement you won't know what a question costs, why it took 12 seconds, or why it failed for one user at 9:02 this morning.

Cost: where the money goes

AI providers charge mainly per token, a piece of a word (very roughly 4 characters of English text). Prices are listed per million tokens, differ by model, and change often, so this chapter gives no prices: check your provider's pricing page. What matters is understanding which tokens you pay for.

UsageHow it is billed (typically)Where in this app
Input tokensEverything you send: system prompt, tool definitions, conversation history, tool results, imagesEvery chat step (step 5, step 22)
Output tokensEverything the model generates, usually priced higher than inputAnswers and tool-call arguments
Reasoning tokensHidden "thinking" tokens of reasoning models, billed as output even though you don't see themgpt-5-mini in the chat route is a reasoning model
EmbeddingsInput tokens only; embedding models are much cheaper per token than chat modelsEvery upload (step 10, step 12) and every search query (step 14)
VisionImages are converted to input tokens; bigger and more detailed images cost moreImages in chat (step 18), OCR of uploads (step 21)
Speech to textBilled by audio length or audio tokens, depending on the modelstep 19
Text to speechBilled by input text and/or generated audio, depending on the modelstep 20

The agent multiplies input tokens

This is the most important cost insight for agents. A model has no memory between calls, so every step re-sends everything so far. A rough, illustrative estimate for one question to the step 22 agent (token counts are rules of thumb, not measurements):

  • System prompt + three tool definitions: roughly 500 tokens.
  • The question: about 20 tokens.
  • Three 900-character chunks from the search tool: about 3 × 225 ≈ 700 tokens.

Step 1 (decide to search) sends about 520 input tokens. Step 2 (answer) sends those 520 again plus the tool call and the 700 tokens of results: about 1,250. If the agent searches twice and calls the calculator, there are 4 steps, and the input grows each time. Ten turns into a conversation, the history alone can be thousands of tokens per step. Long conversations and many steps get expensive quickly.

Measure it: the usage data

You don't need to estimate by hand. Every AI SDK call reports token usage: generateText returns usage (last step) and totalUsage (all steps); streamText gives the same in its onFinish callback; embed and embedMany return usage.tokens.

const result = streamText({
  model: openai("gpt-5-mini"),
  messages: convertToModelMessages(messages),
  tools,
  system: SYSTEM_PROMPT,
  stopWhen: stepCountIs(6),
  onFinish: ({ totalUsage, steps }) => {
    console.log("[usage]", {
      steps: steps.length,
      inputTokens: totalUsage.inputTokens,
      outputTokens: totalUsage.outputTokens,
      reasoningTokens: totalUsage.reasoningTokens,
      cachedInputTokens: totalUsage.cachedInputTokens,
    });
  },
});

Line(s)CodeWhat it does & why

Multiply the totals by your model's current per-token prices to get the cost of each question. In production, store these numbers (with user id, model and timestamp) in a table or an observability tool, so you can answer "what does an average question cost?" and "which user or feature is the most expensive?". Also set a monthly budget and alerts in the provider's dashboard.

Reducing cost

  • Use the smallest model that passes your evals. Many tasks (classification, OCR of clean text, short answers) don't need the largest model. Prove it with the test set from Evaluating AI Applications before switching.
  • Shorter prompts. Every word in the system prompt is paid for on every step of every question.
  • Fewer, better chunks. The search tool returns 3 chunks (searchDocuments(query, 3, 0.5)). Returning 10 would roughly triple the tool-result tokens. A higher threshold drops weak matches.
  • Trim history. Send only the last N messages, or summarise older ones, instead of the whole conversation.
  • Limit output with maxOutputTokens, and keep the "give concise answers" instruction.
  • Limit steps. stepCountIs(6) caps the agent loop; look at how many steps typical questions need and keep the cap close to that.
  • Batch embeddings. Step 10 uses embedMany to embed all chunks of a document in one request instead of one call per chunk. The token price is the same, but you make far fewer requests, which is faster and less likely to hit rate limits. Some providers also offer discounted batch APIs for work that does not need an immediate answer.
  • Cache (see below).
  • Resize images before sending them to a vision model, when full resolution is not needed.

Latency: making it feel fast

Latency is how long the user waits. For chat, two numbers matter:

  • Time to first token (TTFT): from pressing Send until the first words appear. This is what makes an app feel fast or slow.
  • Total time: until the answer is complete.

Ways to reduce latency:

  • Streaming. Already done since step 5: streamText + toUIMessageStreamResponse() sends words as they are generated, so users start reading after the first token instead of waiting for the whole answer.
  • Show progress. Step 23 renders each tool call ("Searching the knowledge base…") so the wait before the answer feels shorter.
  • Fewer steps. Each agent step is a full model round trip. Clear tool descriptions and a good system prompt avoid unnecessary searches.
  • Parallel tool calls. A model can request several tool calls in one step (for example, two searches with different wording); the AI SDK executes them together rather than one after another, saving a round trip.
  • Smaller or faster models. Smaller models usually respond faster. Reasoning models "think" before answering, which improves hard questions but adds delay; some offer a setting to reduce reasoning effort (for OpenAI via providerOptions; check the provider docs).
  • Shorter input. Fewer input tokens means less to process before the first token.
  • Region choice. Put your server functions and your Neon database in the same (or nearby) region. The search tool makes database calls on every question; a server in Europe talking to a database in the US adds a long round trip each time.
  • Caching, below, skips work entirely.

Reliability: when things go wrong

In production, external calls fail: the provider is overloaded, your account hits its limits, the network blips, a request hangs. Plan for each case.

Rate limits and 429 errors

Providers limit how many requests and tokens you can use per minute (a rate limit), with limits that depend on your account tier. When you exceed them, the API answers with HTTP status 429 Too Many Requests. Busy apps hit this at peak times, and big uploads can hit token-per-minute limits on embeddings.

Retries with backoff

The AI SDK retries failed calls automatically. The maxRetries setting defaults to 2 (so up to 3 attempts in total), with exponential backoff: it waits a bit before the first retry and longer before each next one, and respects the provider's "retry after" hints when present. Retrying immediately would just hit the same limit again.

const { embeddings } = await embedMany({
  model: openai.textEmbeddingModel("text-embedding-3-small"),
  values: inputs,
  maxRetries: 5, // uploads are not interactive: worth waiting longer
});

For interactive chat, keep retries low (the user is waiting); for background work such as indexing documents, allow more.

Timeouts and cancellation

A call that hangs is worse than one that fails. The AI SDK functions accept an abortSignal, a standard JavaScript way to cancel work:

// Cancel if the user closes the tab or stops the request
const result = streamText({
  // …model, messages, tools, system, stopWhen…
  abortSignal: req.signal,
});

// Or give up after 60 seconds (e.g. for OCR during upload)
const { text } = await generateText({
  // …model, messages…
  abortSignal: AbortSignal.timeout(60_000),
});

req.signal is the request's own abort signal: when the browser disconnects, generation stops, so you stop paying for tokens nobody will read. AbortSignal.timeout(ms) is built into Node.js and modern browsers and creates a signal that fires after the given number of milliseconds.

Fallbacks

If a model or provider is down, you can fall back to another one. A simple pattern for non-streaming calls:

async function extractTextWithFallback(messages: ModelMessage[]) {
  try {
    return await generateText({ model: openai("gpt-4.1-mini"), messages });
  } catch (error) {
    console.error("Primary model failed, trying fallback", error);
    return await generateText({ model: openai("gpt-4.1"), messages });
  }
}

Because the AI SDK uses one interface for all providers, the fallback could also be a different provider's model. Two cautions: run your evals on the fallback model too (it may behave differently), and remember that with streamText errors can happen after streaming has started, so a simple try/catch around the call does not catch them; fallbacks for streams need more care.

Graceful error UI

  • Hide internals. By default, toUIMessageStreamResponse() sends the browser a generic "An error occurred." message instead of the real error, so stack traces and provider details don't leak. You can pass an onError function to map known errors to friendly text, and log the real error on the server.
  • Offer a retry. useChat exposes an error value and a regenerate() function. Show "Something went wrong. Try again" with a button that calls regenerate().
  • Return clear statuses. The routes in this project already return 400 for bad input and 500/502 for failures (for example the transcription route in step 19); keep messages short and non-technical for users.

Caching

Caching means saving a result so you can reuse it instead of computing it again. Three kinds are useful here:

CacheWhat is reusedWatch out for
Response cacheThe full answer to a repeated question ("How many vacation days do I get?" is asked by everyone)Only for questions that don't depend on the user or the date; clear it when documents change; exact-text matching misses rephrasings
Embedding cacheThe embedding of a text you embedded before (same text + same model = same vector)Store the model name with the vector; switching models invalidates everything
Provider prompt cachingThe provider reuses processing of a repeated prompt prefix (system prompt, tool definitions)Works best when the unchanging parts come first; rules differ by provider

Response caching is the biggest saving but the riskiest: a cached answer can be stale or wrong for a different user. A safe version caches only the first message of a conversation, keyed by the normalised question text plus a "knowledge base version" that you bump on every upload.

Embedding caching is simple and safe. The question "how many vacation days do I get" produces the same embedding every time, so you can store question text → vector in a table or key-value store and skip the API call when it is already there.

Provider prompt caching happens on the provider's side. Some providers apply it automatically for long prompts with a repeated beginning (OpenAI does this, for prompts above a minimum length); others require you to mark which parts to cache (Anthropic, for example, uses explicit cache markers). Cached input tokens are usually cheaper and faster. In the AI SDK, usage.cachedInputTokens shows how many input tokens were served from the cache. To benefit, keep the system prompt and tool definitions stable and at the start of every request, as this project already does.

Observability: seeing what the app does

Observability is the ability to understand what your system did, from the data it records. For an AI app you want to answer: which tools did the agent call, with what inputs, what came back, how long each step took, how many tokens it used, and what the user saw.

Logging

The agent route already logs each step with onStepFinish:

      onStepFinish: ({ toolCalls, finishReason }) => {
        for (const call of toolCalls) {
          console.log(`[agent] called ${call.toolName}`, call.input);
        }
        console.log(`[agent] step finished: ${finishReason}`);
      },

That is a good start for development. For production, improve it in three ways: log structured data (JSON objects with fields such as userId, chatId, step, toolName, durationMs, usage) so you can search and aggregate; add an id that links all steps of one request; and remember that logs contain users' questions, which are personal data (see Security & Safety). On Vercel, anything written with console.log in a function appears in the project's runtime logs.

Tracing with OpenTelemetry

A trace records one request as a tree of timed operations ("spans"): the chat request, inside it each model call, inside those each tool call. OpenTelemetry (OTel) is the open standard for producing traces, supported by most monitoring tools. The AI SDK can emit OpenTelemetry spans for its calls through the experimental_telemetry option (marked experimental, so details may change):

const result = streamText({
  // …model, messages, tools, system, stopWhen…
  experimental_telemetry: {
    isEnabled: true,
    functionId: "chat-agent",
    metadata: { route: "/api/chat" },
    recordInputs: true,  // set to false to keep prompts out of traces
    recordOutputs: true, // set to false to keep answers out of traces
  },
});

Telemetry is off by default. functionId names this call so you can group traces; metadata adds your own fields; recordInputs and recordOutputs control whether prompt and response text are included, which matters for privacy. You also need to register an OpenTelemetry exporter in your app; in Next.js this is done in an instrumentation.ts file (for example with the @vercel/otel package), as described in the AI SDK and Next.js telemetry docs.

LLM observability tools

Generic logging tools work, but LLM-focused tools show conversations, prompts, tool calls, token costs and evaluation scores side by side. Examples at the time of writing (2025), listed neutrally: Langfuse, LangSmith, Braintrust, Helicone and Arize Phoenix. Many accept OpenTelemetry data from the AI SDK. Choose based on hosting (cloud or self-hosted), data-privacy needs and price, and check their current docs.

Deploying on Vercel

The project is a standard Next.js app, so it deploys to Vercel (the company behind Next.js and the AI SDK) or any host that runs Next.js. Vercel-specific points:

  • Environment variables. .env.local is not uploaded (and must not be committed). Add OPENAI_API_KEY, NEON_DATABASE_URL, NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY, CLERK_SECRET_KEY and any other variables in the Vercel dashboard under the project's settings (Environment Variables). You can set different values for Production, Preview and Development. Changes apply to new deployments, so redeploy after editing them.
  • Clerk production instance. Clerk uses separate development and production instances with different keys; set up the production instance and your domain before launch.
  • Function duration. Route handlers run as serverless functions with a maximum duration that depends on your plan and settings. A streaming agent answer with several steps can take a while. Next.js lets you set the limit per route with a route segment config export:
// Allow streaming responses up to 60 seconds
export const maxDuration = 60;

maxDuration is a number of seconds; the platform caps it according to your plan, so check Vercel's current limits. If a function exceeds it, the response is cut off mid-stream.

  • Request body size. Vercel limits the request body sent to a function to about 4.5 MB, regardless of Next.js settings. This affects the project in two places: the bodySizeLimit: "10mb" server action setting from step 21 cannot raise it, and the chat's image attachments (up to 4 images of 4 MB each, sent as base64, which adds about 33%, in step 18) can exceed it. For large files in production, upload them directly from the browser to object storage (for example Vercel Blob or S3) and send only the URL or a reference to your server, or lower the limits in the UI.
  • Native packages. next.config.ts already lists pdf-parse in serverExternalPackages so it is loaded at runtime instead of bundled; keep that in production.
  • Preview deployments. Every branch gets its own URL. Point previews at a separate database (see Neon branches below) so testing never touches production data.

The database in production

  • Neon branches. Neon can create a branch of your database: an instant copy-on-write copy of its data and schema. Use one branch for production, and separate branches for development, previews and eval runs. You can test a migration or a re-chunking experiment on a branch and throw it away.
  • Migrations. Apply schema changes with Drizzle migrations (step 9) as a deliberate deployment step, tested on a branch first, never by editing the production database by hand.
  • Connection handling. Serverless functions can open many short-lived connections at once. The project uses Neon's HTTP driver (drizzle-orm/neon-http with @neondatabase/serverless), which sends each query as an HTTP request and suits serverless well. If you switch to a regular TCP Postgres driver, use Neon's pooled connection string (the host contains -pooler), which puts a connection pooler in front of the database.
  • Index maintenance. The HNSW index from step 9 keeps searches fast as the table grows (see Indexing explained). Check with EXPLAIN that queries still use it after schema changes. After deleting or replacing many documents, Postgres's routine VACUUM cleans up; rebuilding the index (REINDEX) after very large changes can restore search quality and speed. Index builds on big tables need memory and time, so do them outside peak hours.
  • Backups and restore. Know how to restore your data: Neon supports restoring to an earlier point in time within your plan's history window. Test it once before you need it.
  • Re-indexing documents. Changing the chunk size or embedding model means re-processing every document. Keep the original files somewhere (the project currently stores only chunks, not the source PDFs), or you cannot rebuild the knowledge base.

Monitoring quality

An app can be fast, cheap and error-free while giving bad answers. Watch quality as closely as uptime:

  • User feedback: thumbs up/down rate over time, and the comments.
  • Sampled automatic grading: run the LLM judge from Evaluating AI Applications on a small share of real conversations.
  • Retrieval health: how often the search tool returns "No relevant information found". A rise suggests users ask about topics missing from the knowledge base, or that something broke.
  • Agent health: average steps per question and how often the 6-step limit is reached.
  • Regression evals before every change to the prompt, model, chunking or search settings.

Common misconceptions

  • "Streaming makes it cheaper." It makes it feel faster; you pay for the same tokens.
  • "Batching embeddings makes them cheaper." With the standard API, the token price is the same; you save requests and time. (Separate discounted batch APIs are a different, asynchronous product.)
  • "The cheapest model is always cheapest." A weaker model that needs more agent steps, longer prompts or retries can cost more per correct answer. Measure.
  • "Works on localhost means works in production." Function time limits, body size limits, cold starts, regions and rate limits only show up when deployed.

Go-live checklist

  1. Secrets set in the Vercel dashboard for each environment; none in git; none with NEXT_PUBLIC_ except the Clerk publishable key.
  2. Clerk production instance configured, sign-up restricted as needed, admin roles assigned (step 16).
  3. Database: production Neon branch, migrations applied, HNSW index present, a separate branch for development and previews, restore tested.
  4. Knowledge base uploaded with the final chunk settings; source files kept; only documents all users may read (until access control exists).
  5. Limits: stopWhen step cap, maxOutputTokens, per-user rate limit, input length checks, upload sizes that fit the platform's body limit.
  6. export const maxDuration on long-running routes, within your plan's limit.
  7. Reliability: sensible maxRetries, abortSignal (request signal or timeouts), friendly error UI with retry.
  8. Cost: usage logged per request, provider budget and alerts set, cost per question estimated.
  9. Observability: structured logs or OpenTelemetry traces, with privacy settings decided (recordInputs/recordOutputs), and a log retention period.
  10. Quality: eval suite passing on the production configuration; feedback buttons live; a weekly review routine.
  11. Security: the checklist in Security & Safety for AI Apps worked through.
  12. Region: functions and Neon database in the same or nearby region.
Recap
  • Cost comes from input, output, reasoning, embedding, vision and audio usage; agents multiply input tokens because every step re-sends the context.
  • Measure with the AI SDK's usage / totalUsage (e.g. in onFinish), then reduce with smaller models, shorter prompts, fewer chunks, trimmed history, caching and batched embeddings.
  • Latency: stream, show progress, cut steps, use parallel tool calls and faster models, and keep the database near your functions.
  • Reliability: automatic retries with backoff (maxRetries, default 2), abortSignal for cancellation and timeouts, fallbacks, and a friendly error UI.
  • Observability: structured logs from onStepFinish/onFinish, and OpenTelemetry traces via experimental_telemetry.
  • On Vercel: env vars in the dashboard, export const maxDuration for long streams, and a request body limit of about 4.5 MB.
  • Neon in production: branches, migrations, the pooled connection string for TCP drivers, index maintenance and tested restores.
