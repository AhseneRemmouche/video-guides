Tool Calling in Depth

How function calling works under the hood and how to design good tools.

What you will learn

A language model can only produce text. It cannot query your database, read the clock or do exact arithmetic. Tool calling (also called function calling) is how you get around that: you describe functions to the model, the model asks for one to be run, your code runs it, and the result goes back to the model. You met this in step 15 (one search tool) and extended it in step 22 (three tools and up to six steps). This chapter opens the box.

You will learn:

  • exactly what is sent back and forth during a tool call, with a sequence diagram;
  • the AI SDK tool() helper: description, inputSchema and execute;
  • tools without execute, for client-side actions and human approval;
  • multi-step runs with stopWhen, the toolChoice options and parallel tool calls;
  • how to handle errors inside tools (return a message or throw?);
  • how to design good, safe tools, using the project's calculator as a case study;
  • how tool calls appear in useChat messages (tool-NAME parts and their states), as rendered in step 23.
Why this matters for your chatbot. Tools are what turned a chat model into a RAG system (search) and then into an agent (search + date + calculator, several steps). Every new capability you add, such as looking up a colleague, filing a ticket or reading a calendar, will be a tool. Designing tools well decides whether the model uses them correctly; securing them decides whether a clever prompt can make your app do something harmful.

What happens under the hood

The key idea: the model never runs anything. It only writes a structured request. Here is the full round trip for "How many vacation days do I get?":

  1. You send tool definitions. Along with the messages, the AI SDK sends each tool's name, description and input shape (converted from your Zod schema into JSON Schema).
  2. The model returns a tool call. Instead of (or before) normal text, it replies with "call searchKnowledgeBase with {"query":"vacation days entitlement"}", plus an ID for this call. The step ends with the finish reason tool-calls.
  3. Your code executes. The AI SDK validates the input against your schema and runs your execute function on your server.
  4. The result goes back. The SDK adds the tool call and its result to the conversation and calls the model again. This is a new step.
  5. The model continues. It reads the result and either writes the answer or calls another tool, until it finishes or your stopWhen condition stops it.

What travels over the wire looks roughly like this (simplified: each provider uses its own format, and the AI SDK translates for you):

// Sent with the request: one tool definition
{
  "name": "searchKnowledgeBase",
  "description": "Search the knowledge base for relevant information",
  "parameters": {
    "type": "object",
    "properties": {
      "query": { "type": "string", "description": "The search query to find relevant documents" }
    },
    "required": ["query"]
  }
}

// Returned by the model: a tool call instead of text
{ "toolCallId": "call_abc123", "toolName": "searchKnowledgeBase", "input": { "query": "vacation days entitlement" } }

Two things follow from this. First, the description and the .describe() texts are literally the only information the model has about your tool, so they are prompts and deserve the same care. Second, the tool definitions are sent on every request and count as input tokens, so dozens of tools with long descriptions have a real cost.

The AI SDK tool() helper

In AI SDK v5 a tool is created with tool({ description, inputSchema, execute }) and passed to streamText or generateText in a tools object. The object's key becomes the tool's name (that is why the project's tools are called searchKnowledgeBase, getCurrentDate and calculator).

PropertyWhat it is
descriptionPlain-language explanation of what the tool does and when to use it. Read by the model.
inputSchemaA Zod schema for the input. Converted to JSON Schema for the model, and used to validate the model's input before execute runs. It also gives execute its TypeScript types.
executeAn async function (input, options) => result that runs on your server. options includes the toolCallId, the conversation messages and an abortSignal. Optional: without it, the tool call is handed to the client (see below).
outputSchema, toModelOutputOptional, more advanced: describe the output type, or control exactly what the model sees from the result (for example, sending a short text version of a big object).

The return value of execute can be a string (sent to the model as text) or any JSON-serialisable object (sent as JSON). The project uses both: the search tool returns a formatted string, getCurrentDate and calculator return objects.

Case study: the calculator tool

calculator: tool({
  description:
    "Evaluate a math expression and return the exact result. Always use this for arithmetic instead of calculating yourself. Supports + - * / ^, parentheses, and percentages written as decimals (15% of 2000 is 0.15 * 2000).",
  inputSchema: z.object({
    expression: z
      .string()
      .describe(
        'A math expression, for example "2000 * 0.15" or "(20 - 3) * 8"',
      ),
  }),
  execute: async ({ expression }) => {
    try {
      return { expression, result: calculate(expression) };
    } catch (error) {
      return {
        expression,
        error: error instanceof Error ? error.message : "Invalid expression",
      };
    }
  },
}),

Tools without execute: client-side tools and human approval

If you leave out execute, the SDK cannot run the tool on the server. Instead, the tool call is streamed to the browser and the run pauses there, waiting for a result. The browser can then supply one. This enables two useful patterns:

  • Client-side tools: things only the browser can do, such as reading the user's location or local time. You handle them in useChat's onToolCall callback and send the result with addToolResult.
  • Human approval: before a risky action (submitting a leave request, sending an email), the model calls a tool that has no execute. Your UI renders the request with Approve / Deny buttons, and the user's click becomes the tool result.
// Server: a tool with no execute
askForConfirmation: tool({
  description: "Ask the user to confirm before submitting a leave request.",
  inputSchema: z.object({ message: z.string() }),
}),

// Client: resend automatically once every tool call has a result
const { messages, sendMessage, addToolResult } = useChat<ChatMessage>({
  sendAutomaticallyWhen: lastAssistantMessageIsCompleteWithToolCalls,
});

// While rendering a part of type "tool-askForConfirmation" in state "input-available":
<button
  onClick={() =>
    addToolResult({ tool: "askForConfirmation", toolCallId: part.toolCallId, output: "Approved" })
  }
>
  Approve
</button>

Here lastAssistantMessageIsCompleteWithToolCalls is a helper exported from ai. The project does not use these patterns yet; chapter 10 discusses when human-in-the-loop is worth it. The important principle: for actions with real-world side effects, a person (or code you wrote) should decide, not the model alone.

Multi-step runs with stopWhen

Each model call is a step. By default streamText and generateText stop after one step, so if the model calls a tool, you would get the tool call but no answer. stopWhen tells the SDK when to stop looping:

ConditionMeaningIn this project
stepCountIs(n)Stop after at most n steps.stepCountIs(2) in step 15 (search, then answer); stepCountIs(6) in step 22 (several searches, date, calculator, answer).
hasToolCall("name")Stop right after a specific tool is called.Not used. Handy for a "finalAnswer" tool pattern.
An array, e.g. [stepCountIs(10), hasToolCall("finalAnswer")]Stop when any condition is met.Not used.

The run also stops naturally whenever the model replies with text and no tool calls. So stepCountIs(6) is a ceiling, a safety limit on cost and loops, not a target. If the ceiling is hit while the model still wants tools, the user gets no final answer, so log it (step 22's onStepFinish prints each step's finishReason) and adjust.

Two related options let you change things between steps: prepareStep (a function called before each step that can return a different model, toolChoice, activeTools, system or messages) and activeTools (limit which tools are available). onStepFinish runs after each step, which is where step 22 logs tool calls.

toolChoice: who decides whether a tool is called

ValueEffectWhen to use
"auto" (default)The model decides whether to call a tool, and which.Almost always, including this project.
"required"The model must call some tool.When an answer without a tool would be wrong. Careful: if it applies to every step of a multi-step run, the model can never write a plain final answer.
"none"The model must not call tools.For a step where you want only text, e.g. a final summarising step.
{ type: "tool", toolName: "searchKnowledgeBase" }The model must call this specific tool.To force a search on the first step, then go back to "auto".

A safe way to "always search first" is to force it only on step 0:

const result = streamText({
  model: openai("gpt-5-mini"),
  messages: convertToModelMessages(messages),
  tools,
  stopWhen: stepCountIs(6),
  prepareStep: ({ stepNumber }) =>
    stepNumber === 0
      ? { toolChoice: { type: "tool", toolName: "searchKnowledgeBase" } }
      : undefined,
});

Returning undefined from prepareStep keeps the normal settings for that step. The trade-off: even "hi" now triggers a search. Prompt instructions ("Always search before answering…") are softer but cheaper.

Parallel tool calls

A model may request several tool calls in one step. Ask "How do vacation and sick leave differ?" and it may call searchKnowledgeBase twice at once, once per topic. The AI SDK runs all the execute functions of a step concurrently (with Promise.all) and sends all results back together in the next step. All of this counts as one step for stopWhen.

Consequences for you:

  • Tools that may run at the same time should not interfere with each other (for example, two calls updating the same database row).
  • Each result is matched to its call by toolCallId, so the order doesn't matter.
  • Some providers let you turn parallel calls off (OpenAI has a parallelToolCalls provider option), which can help when tools must run in sequence.

Errors inside tools: return or throw?

Things go wrong: the database is unreachable, the expression is invalid, the search finds nothing. You have two options.

Return an error message as the result (what this project does). The search tool returns "Error searching the knowledge base." and "No relevant information found in the knowledge base."; the calculator returns { expression, error }. The model reads the message like any result and can react: rephrase the search, fix the expression, or tell the user honestly. The UI shows the part as output-available, because from the SDK's point of view the tool succeeded.

Throw an error. The AI SDK catches it and records a tool error. In a multi-step run, the error's message is sent to the model as the tool result in the next step, so it can still react, and in the UI the part ends in the output-error state with an errorText. Invalid input from the model (wrong types) and calls to unknown tool names also end up as tool errors that the model sees and can correct.

Watch what your error messages reveal. In the AI SDK version this project uses, the default for toUIMessageStreamResponse() sends a thrown error's message to the browser as errorText. If an error message contains a connection string, SQL or a stack detail, the user may see it. Either catch errors inside execute and return a safe message (as the project does, while logging details with console.error), or pass an onError function to toUIMessageStreamResponse that returns a generic message.

Rule of thumb: return expected failures the model can do something about ("nothing found", "invalid expression"); throw (or let errors bubble) for genuine bugs and outages, with a safe message.

Designing good tools

PrincipleWhyExample
Clear, specific namesThe name is the first hint. Verb + object reads best.searchKnowledgeBase, getCurrentDate, not tool1 or helper.

Narrow inputsFewer, simpler fields mean fewer mistakes and less room for abuse.One expression string, not "any JavaScript". Use z.enum for fixed choices and limits like length.
One job per toolA do-everything tool with a mode field confuses the model.Separate getCurrentDate and calculator instead of a "utilities" tool.
Concise resultsResults become input tokens for the next step: big results cost money, add latency and bury the useful part.The search tool returns the top 3 chunks, numbered, not whole documents or raw database rows with embeddings.

Safe side effectsReading is low risk; writing, sending and deleting are not.Require human approval (a tool without execute) before irreversible actions.

Security of tools

A tool is code that runs on your server because a model asked. The model's request can be influenced by the user and by any text the model has read, including uploaded documents (prompt injection). So treat every tool input as untrusted user input.

  • Never let the model run arbitrary code. The tempting shortcut for a calculator is JavaScript's eval(expression). That would let a crafted "expression" run any code on your server. The project instead uses src/lib/calculator.ts, a private mathjs instance with risky functions (import, createUnit, evaluate, parse, simplify, derivative) disabled, following the mathjs security guidance for untrusted input.
  • Validate inputs. Zod checks types before execute runs; add business limits in code too. calculate() rejects expressions longer than 200 characters (throw new Error("Expression is too long")), which caps how much work a single call can cause.
  • Enforce permissions in code, not in the prompt. If a tool reads or changes per-user data, get the user's identity from your auth system (Clerk's auth() on the server), never from a model-supplied field like userId. Upload permission in step 16 is enforced the same way: in code.
  • Least privilege. Give the database user behind a read-only tool read-only rights. Don't expose a generic "run SQL" tool.
  • Bound the loop. stopWhen: stepCountIs(n) limits how many tool calls one request can trigger.
  • Treat tool results as untrusted too. Search results contain document text that might include injected instructions. Chapter 13 covers defences.
New to eval? Why it's dangerous

eval("2 + 2") runs a string as JavaScript code and returns 4. That seems perfect for a calculator, but it runs any code, for example code that reads your environment variables (including your API keys) or deletes files. If the string comes from a model, which may be steered by a user or a document, you have handed control of your server to whoever writes the most persuasive text. A dedicated expression parser that only understands math, with dangerous features switched off, is the safe alternative.

How tool calls appear in useChat messages

On the browser side, each assistant message from useChat has a parts array. Text arrives as parts with type: "text"; each tool call arrives as a part whose type is tool- plus the tool's name: tool-searchKnowledgeBase, tool-getCurrentDate, tool-calculator. Because the route exports ChatMessage = UIMessage<never, UIDataTypes, ChatTools> (from InferUITools<typeof tools>), TypeScript knows each tool's input and output types.

A tool part moves through these states:

stateMeaningFields available
input-streamingThe model is still writing the tool's input.input may be partial or undefined.
input-availableInput is complete; the tool is running (or, without execute, waiting for the client).input
output-availableThe tool finished and returned a result.input, output
output-errorThe tool threw an error, or the call could not be completed.input (may be undefined), errorText

Every part also has a toolCallId. Step 23 renders these parts with the AI Elements Tool components:

case "tool-searchKnowledgeBase":
case "tool-getCurrentDate":
case "tool-calculator":
  return (
    <Tool key={`${message.id}-${i}`}>
      <ToolHeader type={part.type} state={part.state} />
      <ToolContent>
        <ToolInput input={part.input} />
        <ToolOutput
          output={part.output}
          errorText={part.errorText}
        />
      </ToolContent>
    </Tool>
  );

Common misconceptions
  • "The model runs my function." It only asks. Your server runs it, after validation, and you can refuse.
  • "If I describe a tool, the model will always use it." With toolChoice: "auto" the model decides. Improve descriptions and the system prompt, or force it with toolChoice/prepareStep.
  • "More steps means smarter answers." More steps means more cost and latency. Raise stepCountIs only when the task needs it.
  • "Zod validation makes a tool safe." It checks shape, not intent. A valid string can still be malicious; the tool's own logic must be safe.
Recap
  • Tool calling: you send tool definitions (JSON Schema), the model returns a tool call, your code executes it, the result goes back, the model continues.
  • tool({ description, inputSchema, execute }); the key in the tools object is the tool name. Descriptions are prompts.
  • Tools without execute pause for the client: use them for browser-only actions and human approval (addToolResult).
  • stopWhen (stepCountIs, hasToolCall) bounds the loop; toolChoice and prepareStep control when tools are called.
  • Several tool calls can happen in one step; the SDK runs them concurrently.
  • Return expected failures as messages; thrown errors become output-error parts and their message can reach the browser.
  • Good tools: clear names, "when to use" descriptions, narrow inputs, concise results, idempotent, safe side effects.
  • Never let the model run arbitrary code; validate inputs and enforce permissions in code, as the project's calculator does.
  • In the UI, tool calls are tool-NAME parts that move through input-streaming → input-available → output-available or output-error.
