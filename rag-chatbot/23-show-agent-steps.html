Show the Agent's Work in the UI

Render every tool call (input, status, result) in the chat.

Extension · code type-checked against the repo

About this step. Like step 22, this is not in the video. The code was type-checked (tsc --noEmit) and production-built (next build) against the GitHub repo's exact package versions (Next.js 15.5.3, ai 5.0.47 and the repo's AI Elements). It hasn't been run against live OpenAI, Clerk or Neon accounts, so test it with your own keys.

Goal

In step 22 your agent learned to search, check the date and calculate, but only the terminal shows those steps. The user sees a "thinking" spinner and then an answer. In this step you show every tool call in the chat, as a small card with the tool's name, a live status badge, the input the model chose and the result it got back.

Only one file changes: src/app/chat/page.tsx. You don't install anything: the card component already exists in the repo at src/components/ai-elements/tool.tsx.

Why show the agent's work?

  • Trust. An answer like "you're 4 days short" is easier to believe when the user can see the policy text it came from and the calculation 14 - 10. If a step is wrong, the user can spot it instead of trusting a confident but mistaken answer.
  • Debugging. When an answer is bad, the cards tell you why at a glance: the search used poor words, found nothing, the calculator got a wrong expression, or a tool wasn't called at all. That's much faster than reading server logs.
  • Feedback while waiting. An agent can take several seconds to work through four or five steps. Cards that appear and update one by one show that something is happening.

What the Tool component renders

AI Elements components are source files copied into your project, so you can open src/components/ai-elements/tool.tsx and read exactly what each piece does. Here is a summary:

PieceWhat it renders
ToolThe outer card: a collapsible box (built on shadcn's Collapsible) with a border, rounded corners and a bottom margin. It starts closed, so only the header shows until the user clicks it.
ToolHeaderThe clickable bar that opens and closes the card. It shows a wrench icon, the part's type (for example tool-calculator), a status badge and a chevron (▾) that flips when the card is open.
ToolContentThe part that slides open when the header is clicked. It holds the input and output sections.
ToolInputA section titled "Parameters" with the tool's input as nicely formatted, syntax-highlighted JSON, for example { "expression": "14 - 10" }.
ToolOutputA section titled "Result" with the tool's output (objects as formatted JSON, strings as text in a code box), or titled "Error" on a red background if the tool failed. While there is no output and no error yet, it renders nothing.

The status badge follows the tool part's state. A tool part moves through these states while the agent works:

StateMeaningBadge
input-streamingThe model is still writing the tool's input; it arrives piece by piece, so it may be incomplete."Pending" (empty circle)
input-availableThe input is complete and the tool's execute is running on the server."Running" (pulsing clock)
output-availableThe tool finished and its result is in part.output."Completed" (green check)
output-errorThe tool failed (for example execute threw an error); the message is in part.errorText."Error" (red cross)

Handled errors still say "Completed". Your step 22 tools catch their own errors and return a message (the search returns "Error searching the knowledge base.", the calculator returns { expression, error }). For the AI SDK that's a normal result, so the card shows "Completed" with the error inside the Result JSON. The red "Error" state only appears when execute actually throws. Both are fine: the returned message lets the model explain or retry.

Step by step

All the changes are in src/app/chat/page.tsx. Compared with the step 20 version, only three things are new (the two files were compared line by line):

  1. Import the Tool components and the message type

    Import Tool, ToolContent, ToolHeader, ToolInput and ToolOutput from @/components/ai-elements/tool, and import the type ChatMessage from your chat route: import type { ChatMessage } from "@/app/api/chat/route";.

  2. Give useChat the message type

    Change useChat() to useChat<ChatMessage>(). Now TypeScript knows the exact names of your three tools and the shape of their inputs and outputs.

  3. Render the three tool part types

    Add three case labels to the parts switch, one per tool, sharing one block that renders a Tool card.

New to generics? What useChat<ChatMessage>() means

Some functions work with many kinds of data, and you can tell them which kind with a type argument in angle brackets. These are called generics. You've already seen one: useState<string | null>(null) in step 18 tells React the state holds a string or null.

useChat() on its own assumes a generic message where a tool part's type is just "tool- followed by any text". TypeScript can't check anything about it. useChat<ChatMessage>() says: "my messages are ChatMessages", the type you exported from route.ts in step 15, which (since step 22) knows all three tools. Now:

  • part.type can only be one of a known list, including exactly "tool-searchKnowledgeBase", "tool-getCurrentDate" and "tool-calculator". A typo like case "tool-calculater": becomes a red error in your editor instead of a card that silently never shows.
  • Inside each case, TypeScript knows that part has state, input, output and errorText, and what each contains (for example that the calculator's input is { expression: string }).

Type arguments only exist while you write code. They are removed when the code is compiled and don't change what runs in the browser.

New to import type? Why importing from a server file is safe here

The chat page is a Client Component ("use client"): it is sent to the user's browser. route.ts is server code: it talks to OpenAI with your secret key, queries the database and runs mathjs. That code must never be shipped to the browser.

import type { ChatMessage } from "@/app/api/chat/route"; imports only a type. Types are pure TypeScript information; they are completely erased when the code is compiled. So the browser bundle contains nothing from route.ts: no server code, no secrets, no database driver.

A normal import { … } of a value from route.ts would be a different story: the bundler would try to pull the route's server-only code (and its dependencies) into the browser bundle, which typically fails to build or ships code that doesn't belong there. The word type is what makes this import safe.

Complete file

Replace the whole content of src/app/chat/page.tsx with this:

// src/app/chat/page.tsx
"use client";

import { Fragment, useState } from "react";
import { useChat } from "@ai-sdk/react";
import { Loader2Icon, MicIcon, SquareIcon, Volume2Icon } from "lucide-react";
import {
  Conversation,
  ConversationContent,
  ConversationScrollButton,
} from "@/components/ai-elements/conversation";
import { Message, MessageContent } from "@/components/ai-elements/message";
import {
  PromptInput,
  PromptInputActionAddAttachments,
  PromptInputActionMenu,
  PromptInputActionMenuContent,
  PromptInputActionMenuTrigger,
  PromptInputAttachment,
  PromptInputAttachments,
  PromptInputBody,
  PromptInputButton,
  type PromptInputMessage,
  PromptInputSubmit,
  PromptInputTextarea,
  PromptInputToolbar,
  PromptInputTools,
} from "@/components/ai-elements/prompt-input";
import { Response } from "@/components/ai-elements/response";
import { Loader } from "@/components/ai-elements/loader";
import { Action, Actions } from "@/components/ai-elements/actions";
import {
  Tool,
  ToolContent,
  ToolHeader,
  ToolInput,
  ToolOutput,
} from "@/components/ai-elements/tool";
import type { ChatMessage } from "@/app/api/chat/route";
import { toDataUrlParts } from "@/lib/to-data-url";
import { useVoiceRecorder } from "@/hooks/use-voice-recorder";
import { useSpeechPlayer } from "@/hooks/use-speech-player";

export default function RAGChatBot() {
  const [input, setInput] = useState("");
  const [formKey, setFormKey] = useState(0);
  const [inputError, setInputError] = useState<string | null>(null);
  const { messages, sendMessage, status } = useChat<ChatMessage>();
  const player = useSpeechPlayer();
  const recorder = useVoiceRecorder((text) =>
    setInput((prev) => (prev ? `${prev} ${text}` : text)),
  );

  const handleSubmit = async (message: PromptInputMessage) => {
    const text = message.text?.trim() ?? "";
    const hasFiles = Boolean(message.files?.length);
    if (!text && !hasFiles) {
      return;
    }

    const files = hasFiles
      ? await toDataUrlParts(message.files ?? [])
      : undefined;

    if (text) {
      sendMessage({ text, files });
    } else if (files) {
      sendMessage({ files });
    }

    setInput("");
    setInputError(null);
    setFormKey((key) => key + 1); // remount PromptInput to clear its attachments
  };

  return (
    <div className="max-w-4xl mx-auto p-6 relative size-full h-[calc(100vh-4rem)]">
      <div className="flex flex-col h-full">
        <Conversation className="h-full">
          <ConversationContent>
            {messages.map((message, index) => {
              const text = message.parts
                .map((part) => (part.type === "text" ? part.text : ""))
                .join(" ")
                .trim();
              const isStreamingThis =
                status === "streaming" && index === messages.length - 1;
              const canListen =
                message.role === "assistant" && text !== "" && !isStreamingThis;

              return (
                <div key={message.id}>
                  {message.parts.map((part, i) => {
                    switch (part.type) {
                      case "text":
                        return (
                          <Fragment key={`${message.id}-${i}`}>
                            <Message from={message.role}>
                              <MessageContent>
                                <Response>{part.text}</Response>
                              </MessageContent>
                            </Message>
                          </Fragment>
                        );
                      case "file":
                        if (!part.mediaType.startsWith("image/")) {
                          return null;
                        }
                        return (
                          <Fragment key={`${message.id}-${i}`}>
                            <Message from={message.role}>
                              <MessageContent>
                                {/* biome-ignore lint/performance/noImgElement: data: URLs can't go through next/image optimisation */}
                                <img
                                  src={part.url}
                                  alt={part.filename ?? "Attached image"}
                                  className="max-h-64 rounded-md"
                                />
                              </MessageContent>
                            </Message>
                          </Fragment>
                        );
                      case "tool-searchKnowledgeBase":
                      case "tool-getCurrentDate":
                      case "tool-calculator":
                        return (
                          <Tool key={`${message.id}-${i}`}>
                            <ToolHeader type={part.type} state={part.state} />
                            <ToolContent>
                              <ToolInput input={part.input} />
                              <ToolOutput
                                output={part.output}
                                errorText={part.errorText}
                              />
                            </ToolContent>
                          </Tool>
                        );
                      default:
                        return null;
                    }
                  })}
                  {canListen && (
                    <Actions className="mt-1">
                      <Action
                        tooltip={
                          player.playingId === message.id ? "Stop" : "Listen"
                        }
                        disabled={player.loadingId === message.id}
                        onClick={() =>
                          player.playingId === message.id
                            ? player.stop()
                            : player.play(message.id, text)
                        }
                      >
                        {player.loadingId === message.id ? (
                          <Loader2Icon className="size-4 animate-spin" />
                        ) : player.playingId === message.id ? (
                          <SquareIcon className="size-4" />
                        ) : (
                          <Volume2Icon className="size-4" />
                        )}
                      </Action>
                    </Actions>
                  )}
                </div>
              );
            })}
            {(status === "submitted" || status === "streaming") && <Loader />}
          </ConversationContent>
          <ConversationScrollButton />
        </Conversation>

        {(inputError || recorder.error) && (
          <p className="mt-2 text-sm text-destructive">
            {inputError ?? recorder.error}
          </p>
        )}

        <PromptInput
          key={formKey}
          onSubmit={handleSubmit}
          className="mt-4"
          accept="image/png,image/jpeg,image/webp,image/gif"
          multiple
          maxFiles={4}
          maxFileSize={4 * 1024 * 1024}
          onError={(err) => {
            // PromptInput reuses the form's onError prop for file errors
            if ("code" in err) setInputError(err.message);
          }}
        >
          <PromptInputBody>
            <PromptInputAttachments>
              {(attachment) => <PromptInputAttachment data={attachment} />}
            </PromptInputAttachments>
            <PromptInputTextarea
              value={input}
              onChange={(e) => setInput(e.target.value)}
            />
          </PromptInputBody>
          <PromptInputToolbar>
            <PromptInputTools>
              <PromptInputActionMenu>
                <PromptInputActionMenuTrigger />
                <PromptInputActionMenuContent>
                  <PromptInputActionAddAttachments label="Add images" />
                </PromptInputActionMenuContent>
              </PromptInputActionMenu>
              <PromptInputButton
                onClick={recorder.isRecording ? recorder.stop : recorder.start}
                disabled={recorder.isTranscribing}
                variant={recorder.isRecording ? "destructive" : "ghost"}
                aria-label={
                  recorder.isRecording ? "Stop recording" : "Record a question"
                }
              >
                {recorder.isTranscribing ? (
                  <Loader2Icon className="size-4 animate-spin" />
                ) : recorder.isRecording ? (
                  <SquareIcon className="size-4" />
                ) : (
                  <MicIcon className="size-4" />
                )}
              </PromptInputButton>
            </PromptInputTools>
            <PromptInputSubmit disabled={!input && !status} status={status} />
          </PromptInputToolbar>
        </PromptInput>
      </div>
    </div>
  );
}

New to bundle size? What "first-load JS" means and why it grew

When someone opens a page, the browser downloads the JavaScript that page needs before it becomes interactive. next build prints a table with a "First Load JS" number for each route: how much JavaScript is downloaded the first time that page is opened. Smaller means faster, especially on phones and slow connections.

The ToolInput and ToolOutput sections show JSON through the repo's CodeBlock component, which uses a syntax highlighter (react-syntax-highlighter, the library that colours code). That library is fairly large. In the production build made when this step was tested, the first-load JS for /chat went from about 506 kB to about 744 kB.

For a learning project that's acceptable. If it matters for your app, two optional optimisations:

  • Lazy-load the card. Load the Tool component (and with it the highlighter) only when the first tool part appears, for example with Next.js's next/dynamic. The rest of the chat page loads without it.
  • Keep details collapsed and lighter. The cards already start closed. You could go further and show only the header (name and status) by default, rendering the JSON with a plain <pre> instead of the highlighter, or only after the user opens the card.

Test it

Save the file. The dev server reloads automatically. Open http://localhost:3000/chat, sign in and ask an agent question such as:

"If I start my vacation 10 days from today, did I give enough notice?"

  1. Watch the cards appear. A tool-searchKnowledgeBase card shows up with a "Pending" or "Running" badge, then switches to "Completed". Then the next tool's card appears below it, and so on, in the order the model chose.
  2. Open a card. Click its header. You see "Parameters" (for example { "query": "vacation request notice period" }) and "Result" (the numbered document snippets, or { "isoDate": …, "readable": … }, or { "expression": "14 - 10", "result": "4" }).
  3. Read the answer. The final text appears below the cards. Check that it matches the results you see in them.
  4. Compare with the terminal. The [agent] lines from step 22 should list the same tools in the same order as the cards.
  5. Try a plain question such as "Hi!". Usually no cards appear, only the answer.

How to know it worked: every tool the agent uses gets its own card, the badge changes from Pending/Running to Completed without reloading the page, and opening a card shows real inputs and results. Without this step, the same question showed only the spinner and the final answer.

Common mistakes:

  • No cards appear, but the answer does – the case labels don't match your tool names. They must be tool- + the exact key in route.ts (capital letters matter: tool-searchKnowledgeBase). With useChat<ChatMessage>(), TypeScript flags a wrong name; without the type argument, it can't.
  • Type errors on part.state or part.input – you probably left useChat() without <ChatMessage>, or route.ts doesn't export ChatMessage.
  • A build error about server-only modules in the chat page – the import from @/app/api/chat/route is missing the word type.
  • "Module not found: Can't resolve '@/components/ai-elements/tool'" – your project doesn't have the Tool component. It ships with the repo; if you set up AI Elements yourself, add it with the AI Elements CLI.
  • You only ever see one search card – that's not a UI problem. The model decided one search was enough. Ask a question that needs the date or arithmetic too.

Ideas for polishing (optional, not in the verified code): show friendlier titles than tool-calculator (for example "Calculator") by editing tool.tsx, since ToolHeader prints the raw type; or hide the cards behind a "Show steps" toggle for non-technical users while keeping them for admins. Recap
  • Each tool call reaches the page as a message part named tool- + the tool's name, with a state, an input and, when finished, an output or errorText.
  • useChat<ChatMessage>(), with a type-only import from the route, makes TypeScript know your three tools, so the case labels and props are checked.
  • AI Elements' Tool card shows the name, a live status badge, the parameters and the result, collapsed by default.
  • Showing the agent's steps builds trust and makes bad answers easy to debug; the cost is a bigger /chat bundle (about 506 kB → 744 kB first-load JS), which lazy-loading can reduce.
