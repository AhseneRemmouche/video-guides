LLMs, RAG, agents and the LangChain ecosystem

What LLMs are, why RAG and agents exist, and how LangChain, LangGraph and LangSmith fit together. Read with book Part I (chapters 1-2).

Read with Part I · Introduction (chapters 1–2) of the book. This page explains the ideas in its own words and links them to the labs.

Before you write a single line of LangChain code it helps to know what the pieces are: what a language model actually does, why people bolt a search step onto it (RAG), what turns a model into an agent, and which of the many langchain-* packages you need for what. This chapter gives you that map.

You will learn:

  • what a large language model (LLM) is, in plain words: tokens, next-token prediction, the context window and parameters;
  • how to tell model families apart (open or proprietary, small or large, local or behind an API, text or more);
  • why retrieval-augmented generation (RAG) exists and what it fixes;
  • what an agent is: a model, some tools and a loop;
  • the LangChain ecosystem as it is today, including one package that is being retired, and how each package shows up in the 16 labs of this guide.
Why this matters for your project. The lab project is an assistant for Harbor City Library, a fictional library with three branches. Every lab adds one idea from this chapter: talking to a model (lab 01), feeding it the library's own policies (labs 04–07), and letting it call tools such as a catalog search (labs 09–15). Knowing the big picture tells you why each lab exists.

What an LLM is

A large language model is a program that has learned, from a huge amount of text, to continue text. You give it some text; it returns the text that most plausibly comes next. That is the whole trick. Answering questions, translating, summarising and writing code are all "continue this text" once the text is set up the right way.

Tokens: the pieces a model reads and writes

Models do not read letters or whole words. They read tokens: short pieces of text, often a whole common word, part of a rarer word, a space plus a word, or a punctuation mark. Each model has its own fixed list of tokens (its vocabulary), and a tokenizer that cuts text into them.

You can see tokens at work in lab 01. When we streamed an answer and printed a | after every piece that arrived, the output looked like this:

3) stream: Read|,| study|,| and| research|.|||

Notice that the comma and the full stop arrive as their own pieces, and that " study" carries its leading space. Those streamed pieces are close to the model's tokens. The same lab printed the token counts the server reported for one short question and answer:

   usage: {'input_tokens': 36, 'output_tokens': 40, 'total_tokens': 76}

Tokens matter for three practical reasons: hosted models bill by the token, every model has a maximum number of tokens it can handle at once, and the time an answer takes grows with the number of tokens it has to write.

Next-token prediction

Under the hood, the model does one thing over and over: given all the tokens so far, it computes a score for every token in its vocabulary — how likely that token is to come next. One token is picked (the most likely one, or a random pick weighted by the scores), appended to the text, and the whole thing repeats. It stops when it picks a special "end" token, or when your code says "that is enough tokens".

Two consequences follow, and you will meet both in the labs. First, the model has no separate "fact store" it checks: if the most plausible continuation is wrong, it writes it anyway, fluently. That is a hallucination — in lab 03 llama3.2 confidently described a maker space called the "Innovation Studio" that our library does not have. Second, nothing inside the loop guarantees that it stops. In lab 02 the model kept repeating "e-book" until our 512-token cap cut it off.

New to "temperature"? Why the same question can give different answers

The step "pick one token" can be strict (always take the highest score) or loose (pick randomly, with likely tokens picked more often). Temperature is the dial between the two: 0 means nearly always the top token, higher values spread the choice out. Low temperature gives repeatable, focused answers; higher temperature gives more variety, and more chances of odd choices. All labs use temperature=0 so that runs are as repeatable as possible — but even then, tiny numeric differences can change an answer, so your output will differ from ours.

The context window

The model can only "see" a limited number of tokens at a time: its context window. Everything has to fit in it together: the instructions, the earlier conversation, any documents you paste in, the question, and the answer the model is writing. Anything that does not fit is simply not seen.

The window size is a property of the model (how much it was trained to handle) and a setting of the software that runs it. A bigger window costs memory. This is why harbor/config.py asks Ollama for a context of 8192 tokens: with Ollama's larger default, most of the model was pushed onto the CPU of our 4 GB graphics card. With 8192, ollama ps showed 3.4 GB in use, split 32 % CPU / 68 % GPU, and a 76-token answer took about 4.5 seconds once the model was loaded. The next chapter covers these settings in detail.

Parameters: the size of a model

A model's knowledge lives in its parameters (also called weights): billions of numbers adjusted during training. "3B" means about three billion of them. The labs use llama3.2 in its 3B size. As a rough rule of thumb, more parameters mean more knowledge and better reasoning, but also more memory, slower answers and higher cost. A 3B model fits on a laptop; the largest hosted models need data-centre hardware. Do not confuse parameters (fixed numbers inside the model) with the settings you pass when you call it (temperature, maximum tokens), which some libraries also call "parameters".

New to model training? Where chat models come from

First a model is pre-trained on a very large text collection to predict the next token. That gives a "base model" that continues text well but does not follow instructions reliably. It is then post-trained on examples of conversations and on human (or AI) preferences, which turns it into a chat model that answers questions, follows a system message and can request tools. All the models you call from LangChain in this guide are chat models. Training happens once, before you download the model; nothing you do in the labs changes its parameters.

Families of models

There are many models and new ones appear constantly, so it is more useful to know the questions that separate them than any list of names. The ones below are the ones that change your code or your setup. Names are examples at the time of writing; check the providers' current documentation.

Can you download the weights?Open-weight (llama3.2, gemma4, many others) vs proprietary (only reachable through the maker's API)Open-weight models can run on your own machine or servers; proprietary ones need an account and an API key. Read the licence either way.
Where does it run?Local (Ollama on your laptop) vs hosted API Local: free per call, private, limited by your hardware. Hosted: no hardware, usually larger models, pay per token, your data leaves your machine.

"Bigger models make fewer mistakes" is only a rule of thumb: a well-chosen small model with good context (RAG, tools) often beats a big model guessing. There are no rankings in this guide on purpose — they change every few months.

Why RAG: giving the model your knowledge

A model only knows what was in its training data, frozen at some date. It has never seen Harbor City Library's loan rules, and it never will — they are private (and, here, invented). Ask about them and you get a plausible guess, like the "Innovation Studio" of lab 03.

Retrieval-augmented generation fixes this without retraining anything. Before the model answers, your code searches your own documents for the passages most relevant to the question, and pastes them into the prompt with an instruction such as "answer only from this context". The model then writes from text it can see instead of from memory.

What RAG gives you:

  • Private knowledge. Your documents never have to be part of any training run.
  • Fresh knowledge. Change a policy file, rebuild the index, and the next answer uses the new rule. No retraining.
  • Citations. Because you know which chunks you pasted in, you can show the reader where an answer came from. In this project harbor/knowledge.py tags every chunk with its file name for exactly that reason.
  • Less guessing — but not none. In lab 07 llama3.2 answered "What happens if I owe 20 EUR?" with "I don't know. [fees.md]" — it even cited the right file — instead of applying the policy's "15 EUR or more blocks the card" rule. Retrieval puts the facts in front of the model; using them correctly is still up to the model.

The search step is done by a retriever, usually backed by a vector store that finds text with a similar meaning, sometimes combined with plain keyword search. The RAG pipeline chapter covers loading, splitting, embedding and retrieving step by step.

What an agent is

RAG always does the same thing: search, then answer. Many questions need a decision first. "Is a book by Mara Quint available?" needs a catalog search, then an availability check for the right item, then an answer. An agent lets the model make those decisions itself.

An agent is three things:

  1. A model that can do tool calling: instead of only writing text, it can reply "please run check_availability with item_id='B004'". The model never runs anything itself; it only asks.
  2. Tools: ordinary Python functions with a name, a description and typed arguments, which your code runs when the model asks. The lab project has four: search_catalog, check_availability, get_member_account and place_hold (in harbor/catalog.py).
  3. A loop — the agent loop: call the model; if it asked for tools, run them, add their results to the conversation and call the model again; stop when it answers with plain text.

That last point is also the weakness. A small model makes poor choices: in lab 09 llama3.2 told a reader two books were "available" without ever calling check_availability (one had 0 copies), and in lab 11 it fetched member M-1001's account for a stranger because that id appeared as an example in the tool's description. Good agent design limits what the model is allowed to decide — for example, the app, not the model, should say whose account may be read.

The loop can be written by hand, built as a graph with LangGraph (labs 08–13), or created in one call with LangChain's create_agent (labs 14–15). Tools can also come from another program through the Model Context Protocol (MCP), which lab 10 uses.

Multi-agent systems, briefly

When one agent has too many tools or too many jobs, its choices get worse. A multi-agent system splits the work: for example a "supervisor" agent that routes each request to a specialised agent (one for the catalog, one for member accounts), or agents handing a conversation over to each other. Each sub-agent has a smaller prompt and fewer tools, so it is easier to get right and to test. The price is more model calls and more places for things to go wrong. The labs stay with a single agent; the official multi-agent docs describe the common patterns.

The LangChain ecosystem today

LangChain started as one big Python package and has been split into several, each with a clear job. If you read older tutorials you will find imports that no longer exist, so it is worth knowing the current layout (the versions installed in the lab project are given in brackets).

PackageJobExample import used in the labs
langchain-core (1.6.10)The base interfaces every other package implements: messages, the chat-model and embedding interfaces, prompt templates, output parsers, tools, documents, and the Runnable interface behind LCEL. Small, few dependencies. from langchain_core.prompts import ChatPromptTemplate
langchain (1.4.5)The high-level package: create_agent, agent middleware, init_chat_model, the tool decorator with runtime context. from langchain.agents import create_agent
langchain-classic (1.0.8)Older chains and retrievers that were moved out of langchain when it was slimmed down for version 1. Kept for compatibility. from langchain_classic.retrievers import EnsembleRetriever

Real warning: langchain-community is being sunset. Whenever a lab imports from it (labs 04 and 07), Python prints this at the top of the output: 
DeprecationWarning: `langchain-community` is being sunset and is no longer actively maintained. See https://github.com/langchain-ai/langchain-community/issues/674 for details and migration guidance toward standalone integration packages.
A deprecation warning does not break anything today: the code still runs. It tells you to plan a move. For new code, prefer a dedicated provider package (like langchain-ollama) when one exists, and follow the migration notes linked in the warning for the rest.

LCEL in one paragraph

Almost every LangChain object — a prompt, a model, a parser, a retriever — is a Runnable: it has invoke, stream and batch methods. The LangChain Expression Language (LCEL) lets you join Runnables with the | operator so the output of one becomes the input of the next. The result, a chain, is itself a Runnable. You will first meet it in lab 03 as prompt | model | StrOutputParser(); lab 16 takes it apart.

Common misconceptions
  • "The model looks things up." A plain model only predicts tokens from its parameters. It looks things up only if your code does retrieval or gives it tools.
  • "Temperature 0 means the answer is correct." It means the answer is (mostly) repeatable. A repeatable wrong answer is still wrong.
  • "The model runs the tools." It only asks for them. Your code (or LangGraph, or create_agent) runs them — so your code decides what is allowed.
  • "A bigger context window solves everything." It costs memory and time (see the 4 GB GPU numbers above), and models can still overlook information in a long prompt. Sending the right few chunks beats sending everything.
  • "Old tutorial imports are just typos." Imports like langchain.retrievers no longer exist in langchain 1.x; the classes moved to langchain_classic or a provider package.
  • "A DeprecationWarning means the code is broken." It still runs; it is notice to migrate.
Recap
  • An LLM predicts the next token again and again; tokens are small pieces of text, and usage is counted in them (lab 01: 36 in, 40 out).
  • The context window holds instructions, history, documents, question and answer together; the labs set it to 8192 tokens to fit a 4 GB GPU.
  • Models differ by openness, where they run, size, modality and purpose; LangChain hides most of that behind one interface.
  • RAG pastes your own documents into the prompt, giving private, fresh, citable answers — but the model can still misuse them.
  • An agent is a model plus tools plus a loop; the model only asks for tool calls, your code runs them.
  • langchain-core defines the interfaces; langchain adds agents; langchain-classic keeps older pieces; langchain-community is being sunset; provider packages like langchain-ollama connect models; LangGraph orchestrates; LangSmith observes.
