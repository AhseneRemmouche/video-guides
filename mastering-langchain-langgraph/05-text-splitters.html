Text splitters

Split the policies with the recursive and the Markdown-header splitters and compare the chunks. Book chapter 7.

Lab · code run on a local model (llama3.2 via Ollama)
Read with chapter 7 · Text Splitters (Part III of the book). This lab is our own hands-on exercise on the same topic; the ideas are explained in our own words.

Goal

Lab 04 gave you six Documents, one per policy file. A search should not return a whole file when the question is about one rule in it: the extra text costs space in the prompt and can distract the model. In this lab you cut the Documents into smaller pieces called chunks with text splitters, compare three settings, and see a real mistake a splitter makes. You also write harbor/knowledge.pysrc/knowledge.ts, the shared module that every later RAG lab and agent imports.

The idea in brief

Splitting is the second stage of the RAG pipeline (load, split, embed, store, retrieve). The concept chapter The RAG pipeline explains why chunk size is a trade-off. In short:

  • Too big: a chunk mixes several topics, its meaning gets blurry, and fewer chunks fit in the model's context window.
  • Too small: a chunk loses the context that makes it understandable (a sentence without its heading, or a heading without its sentence).
  • Overlap: neighbouring chunks may repeat a little text, so a sentence cut at a border still appears whole in one of them.

A good chunk is one that makes sense on its own. With well-structured files, the best cut points are the document's own headings.

New to text splitting? What a splitter actually does

A splitter takes long text and returns a list of shorter strings (or Documents). chunk_size is the maximum length of a chunk, measured here in characters (not words or tokens). chunk_overlap is how many characters at the end of one chunk may be repeated at the start of the next. split_documents(docs) splits a list of Documents and copies each Document's metadata onto every chunk made from it, so every chunk still knows its source file.

In LangChain.js the same options are written in camelCase inside one object: { chunkSize: 400, chunkOverlap: 60 }, and the method is splitDocuments(docs), which returns a Promise, so you await it. It also adds one key of its own to each chunk's metadata: loc: { lines: { from, to } }, the line numbers of the chunk in the original file.

New to the recursive splitter? How it chooses where to cut

RecursiveCharacterTextSplitter has a list of separators, from "best" to "worst". By default it is ["\n\n", "\n", " ", ""]: blank line (between paragraphs), line break, space (between words), and finally nothing (between any two characters). It splits on the first separator, then glues small neighbouring pieces back together until a chunk is almost chunk_size long. Any piece that is still too long is split again with the next separator. That second round is the "recursive" part.

"""Load, split and index the library's policy documents. Labs 04-07 build this step by step."""
from pathlib import Path

from langchain_community.document_loaders import DirectoryLoader, TextLoader
from langchain_core.vectorstores import InMemoryVectorStore
from langchain_text_splitters import RecursiveCharacterTextSplitter

from harbor.config import DATA, get_embeddings


def load_policies():
    loader = DirectoryLoader(str(DATA / "policies"), glob="*.md", loader_cls=TextLoader,
                             loader_kwargs={"encoding": "utf-8"})
    return loader.load()


def split(docs, chunk_size=400, chunk_overlap=60):
    splitter = RecursiveCharacterTextSplitter(chunk_size=chunk_size, chunk_overlap=chunk_overlap,
                                              separators=["\n## ", "\n\n", "\n", ". ", " ", ""])
    return splitter.split_documents(docs)


def build_vector_store(chunks=None):
    chunks = chunks if chunks is not None else split(load_policies())
    return InMemoryVectorStore.from_documents(chunks, get_embeddings())


def format_docs(docs):
    """Turn retrieved chunks into one context string, each chunk tagged with its source file."""
    return "\n\n".join(f"[{Path(d.metadata['source']).name}]\n{d.page_content}" for d in docs)
// Load, split and index the library's policy documents. Labs 04-07 build this step by step.
import path from "node:path";
import type { Document } from "@langchain/core/documents";
import { DirectoryLoader } from "@langchain/classic/document_loaders/fs/directory";
import { TextLoader } from "@langchain/classic/document_loaders/fs/text";
import { MemoryVectorStore } from "@langchain/classic/vectorstores/memory";
import { RecursiveCharacterTextSplitter } from "@langchain/textsplitters";
import { DATA, getEmbeddings } from "./config.js";

export async function loadPolicies(): Promise<Document[]> {
  const loader = new DirectoryLoader(path.join(DATA, "policies"), { ".md": (p) => new TextLoader(p) });
  return loader.load();
}

export async function split(docs: Document[], chunkSize = 400, chunkOverlap = 60): Promise<Document[]> {
  const splitter = new RecursiveCharacterTextSplitter({
    chunkSize, chunkOverlap, separators: ["\n## ", "\n\n", "\n", ". ", " ", ""],
  });
  return splitter.splitDocuments(docs);
}

export async function buildVectorStore(chunks?: Document[]): Promise<MemoryVectorStore> {
  return MemoryVectorStore.fromDocuments(chunks ?? (await split(await loadPolicies())), getEmbeddings());
}

/** Turn retrieved chunks into one context string, each chunk tagged with its source file. */
export function formatDocs(docs: Document[]): string {
  return docs.map((d) => `[${path.basename(d.metadata.source)}]\n${d.pageContent}`).join("\n\n");
}

"""Lab 05: split documents into chunks that fit a prompt and still make sense alone."""
from pathlib import Path

from langchain_text_splitters import MarkdownHeaderTextSplitter, RecursiveCharacterTextSplitter

from harbor.knowledge import load_policies

docs = load_policies()

chunks = await smart.splitDocuments(docs);
console.log(`\n2) Recursive, size 400, heading-first: ${chunks.length} chunks`);

// 3. Split on Markdown headings and keep the headings as metadata. LangChain.js has no
//    MarkdownHeaderTextSplitter, so here is a small one: a new section starts at every "# " or "## " line.
function splitOnHeadings(text: string) {
  const sections: { metadata: Record<string, string>; pageContent: string }[] = [];
  const current: Record<string, string> = {};
  let lines: string[] = [];
  const flush = () => {
    if (lines.join("").trim()) sections.push({ metadata: { ...current }, pageContent: lines.join("\n").trim() });
    lines = [];
  };
  for (const line of text.split("\n")) {
    const heading = line.match(/^(#{1,2}) (.*)/);
    if (!heading) { lines.push(line); continue; }
    flush();
    if (heading[1] === "#") { current.page = heading[2].trim(); delete current.section; }
    else current.section = heading[2].trim();
  }
  flush();
  return sections;
}
const sections = docs.flatMap((d) => splitOnHeadings(d.pageContent));
console.log(`\n3) Split on headings: ${sections.length} sections`);
for (const s of sections.slice(0, 3)) console.log(`   ${JSON.stringify(s.metadata)}  ${JSON.stringify(s.pageContent.slice(0, 60))}`);

What happened in part 1: the orphan heading

The first two fees chunks look fine: each starts at a heading and contains its rule. The third one is just '## Lost or damaged items', a 24-character chunk with a heading and no content. Here is why. The section "Lost or damaged items" is longer than 200 characters, so the splitter cannot keep it in one piece. It splits that section at the next separator, "\n", which sits right after the heading. The paragraph that follows is still too long to join the heading, so the heading is left alone and the paragraph is cut again at spaces.

The result is a chunk that will never answer anything, and a paragraph that lost its heading. We checked the other files too (by running the same splitter and printing every chunk): ## Central Library, ## Lighthouse Branch, ## E-books and audiobooks, ## Study rooms and ## Maker space are also orphaned, and the shortest chunks (14 characters) are ## Study rooms and ## Maker space.

Overlap, seen in the same file

Chunks 4 and 5 above also show what chunk_overlap=40 does. Chunk 4 ends with "…we refund the replacement price but" and chunk 5 starts with "we refund the replacement price but not the processing fee." The 35-character phrase appears in both, so whichever chunk is retrieved, the sentence is not completely lost.

What happened in part 2: heading-first chunks

With chunk_size=400 and "\n## " as the first separator, the six files become 12 chunks: exactly two per file (we confirmed this by printing every chunk offline). Each chunk starts at a heading and holds one or two whole sections. The example, chunks[3], is the second chunk of digital.md: it starts at ## Wi-Fi and computers, and, because both sections fit in 400 characters, it also contains the whole ## Printing section. Keep that in mind: in lab 06 a search for "printing price" returns this very chunk.

Why no visible overlap here? The overlap only re-uses whole pieces from the end of the previous chunk, and the pieces at this level are whole sections, all longer than 60 characters. So when cuts happen at headings, the chunks simply do not overlap. That is fine: a cut at a heading does not break a sentence.

What happened in part 3: splitting on Markdown headings

Python has a ready-made MarkdownHeaderTextSplitter; LangChain.js does not, so the TypeScript lab writes splitOnHeadings itself (about 20 lines). It does not count characters at all. It cuts at every # and ## line and stores the heading text as metadata. The six files have 17 ## sections in total (three in each file, two in rooms.md), so you get 17 pieces, the same number as the Python splitter, and each one knows its page and section. That metadata is useful: you could later filter on "section = Late fees" or show the section title next to an answer. The price: the pieces can be any length, so in a real project you often run a size-based splitter on them afterwards. Writing a splitter yourself is a good reminder that a splitter is just a function from text to pieces.

Common mistakes
  • Overlap bigger than the chunk size. The default chunkOverlap is 200, so new RecursiveCharacterTextSplitter({ chunkSize: 10 }) throws Cannot have chunkOverlap >= chunkSize (the check in the package's source). Always set both numbers together.
  • Thinking chunkSize is in words or tokens. Here it counts characters. 400 characters is roughly 60 to 80 English words.
  • Forgetting await before splitDocuments. You get a Promise, and chunks.map on the next line fails; pnpm typecheck catches this before you run.
  • Losing the source. splitOnHeadings(d.pageContent) receives only a string, so its pieces have no source (part 3 of this lab). Use splitDocuments(docs) when you need to know where a chunk came from, or add the metadata yourself.
  • Forgetting the copy { ...current }. If you push current itself, all the sections of one file share one object, so they all end up with that file's last heading (the three printed lines would all say Lighthouse Branch).
  • Reading chunks[3] as "the third chunk". Arrays count from 0, so chunks[3] is the fourth chunk (the second one of digital.md).
  • Changing the chunk size in only one place. Change it in src/knowledge.ts and every later lab uses it; but the numbers in labs 06 and 07 (12 chunks, the scores) will change too.
