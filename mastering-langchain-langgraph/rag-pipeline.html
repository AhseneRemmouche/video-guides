The RAG pipeline: load, split, embed, retrieve

Documents and metadata, chunking strategies, embeddings, vector stores and retrieval strategies. Read with book Part III (chapters 6-9).

Read with Part III · Integrations and Utilities for RAG in LangChain (chapters 6–9) of the book. This page explains the ideas in its own words and links them to the labs.

A language model only knows what was in its training data and what you put in its prompt. It has never read the Harbor City Library's fee rules, so when you ask it about them it either refuses or, worse, makes something up (lab 03 saw it invent an "Innovation Studio"). Retrieval-augmented generation (RAG) fixes this in a simple way: before the model answers, your code looks up the few passages that matter and pastes them into the prompt. This chapter walks through every stage of that pipeline: loading files, splitting them into pieces, turning the pieces into numbers, storing them, and finding the right ones again.

Why this matters for your project. Labs 04, 05, 06 and 07 build this pipeline for the library's six policy files, and every later agent reuses it through harbor/knowledge.py. When an answer is wrong, you need to know which stage broke: did the right text never get found, or did the model ignore it? This chapter gives you the vocabulary and the mental model to tell the difference.

The big picture: two phases

A RAG system does its work at two different moments. The first phase, indexing, happens once, ahead of time (and again whenever the documents change). The second phase, answering, happens for every question. Keeping the two apart in your head explains a lot: indexing can be slow and thorough, while answering must be fast, so the expensive work of reading and embedding every file is done in advance.

New to RAG? What it is and why it matters

RAG is not a library or a model. It is a pattern: retrieve relevant text, augment the prompt with it, then let the model generate an answer. The model still writes the sentence, but the facts come from your documents. Two big wins follow: answers can be grounded in private or recent information the model never saw, and you can show the source so a reader can check it.

RAG does not make a model smarter. If the right passage is not retrieved, or the model misreads it, the answer is still wrong. The rest of this chapter is about reducing both risks.

Documents and metadata

Every stage of the pipeline passes around the same small object: a Document. It has two parts. page_content is the text itself, the part that gets embedded and eventually pasted into the prompt. metadata is a plain Python dictionary of labels about that text: which file it came from, which row, which section, which branch.

from langchain_core.documents import Document

doc = Document(
    page_content="Books are loaned for 21 days.",
    metadata={"source": "loans.md", "section": "Loan periods"},
)
print(doc.page_content, doc.metadata["source"])   # Books are loaned for 21 days. loans.md

Metadata looks like a detail, but you will use it constantly. It lets the RAG chain print [fees.md] after an answer (see format_docs in harbor/knowledge.py), it lets the evaluation in lab 07 check whether the right file came back, and it lets a search stay inside one file or one branch. A good rule: anything you might later want to filter on, show, or debug with belongs in metadata, not buried in the text.

Document loaders: getting text in

A document loader reads some source and returns a list of Documents. They all share one method, load(), so you can swap one for another without touching the rest of the pipeline. What differs is how a source is cut into Documents and which metadata is filled in.

In lab 04 the CSV loader was told which column is the source and which columns become metadata, so the first book came back as text (id: B001, title: …) plus {'source': 'B001', 'row': 0, 'branch': 'Central Library', 'format': 'book', 'available': '1'}. Notice the '1' in quotes: CSV values arrive as strings, so the lab compares with != "0", not with a number.

Other sources follow the same idea. A PDF loader usually gives one Document per page, with the page number in metadata, so an answer can cite "page 12". A web loader fetches a page and strips the HTML, keeping the URL as the source. Office files, e-mails, databases and cloud drives all have loaders too. The quality varies a lot: PDFs with columns, tables or scanned images often come out as jumbled text. Always print a few loaded Documents before you build anything on top of them; a bad load poisons every later stage.

The langchain-community sunset warning. The loaders in the labs (TextLoader, DirectoryLoader, CSVLoader) and BM25Retriever come from langchain_community. With the installed version (0.4.2), importing it prints a real deprecation notice: "langchain-community is being sunset and is no longer actively maintained". It is a warning, not an error: the code still runs (you can see it at the top of the outputs of labs 04 and 07). It tells you where things are heading: integrations are moving to their own standalone packages (as langchain-ollama already did). For new projects, check the current integration page of the official docs first and prefer a dedicated package when one exists.

Why split documents at all?

Our policy files are short (between 508 and 574 characters each, as lab 04 printed), so why cut them up? Real documents are not: a handbook can have hundreds of pages. Splitting helps for three reasons:

  • Precision. An embedding squeezes a whole text into one list of numbers. A text about fees, Wi-Fi and opening hours becomes a blurry average of all three and is never a strong match for any single question. A short passage about one topic gives a sharp vector.
  • Room in the prompt. The retrieved text is pasted into the prompt, which must fit the model's context window (the labs set 8,192 tokens). Small pieces let you include several sources.
  • Focus and cost. Less irrelevant text in the prompt means fewer distractions for the model and less work per answer, which matters on a small local model.

The pieces are called chunks. Each chunk is itself a Document, and the splitter copies the original metadata onto every chunk, so source survives the cut.

Text splitters and the size/overlap trade-off

A text splitter takes Documents and returns smaller ones. Two settings matter everywhere. chunk_size is the maximum length of a chunk (in characters, unless you tell the splitter to count tokens). chunk_overlap is how much text neighbouring chunks may share, so a sentence cut in half still appears whole in at least one chunk.

The recursive character splitter

The general-purpose choice is RecursiveCharacterTextSplitter. It has a list of separators in order of preference. It first tries to cut at the first one (by default a blank line, so paragraphs stay together); any piece still too long is cut at the next separator (a line break), then a space, and only as a last resort in the middle of a word. Then it packs neighbouring pieces back together as long as they fit the size limit. The result: chunks that respect the structure of the text as much as the size allows.

The project's own splitter adds one separator at the front: "\n## ", the start of a Markdown section. That one change makes chunks begin at headings:

def split(docs, chunk_size=400, chunk_overlap=60):
    splitter = RecursiveCharacterTextSplitter(chunk_size=chunk_size, chunk_overlap=chunk_overlap,
                                              separators=["\n## ", "\n\n", "\n", ". ", " ", ""])
    return splitter.split_documents(docs)

Lab 05 compared the two settings on the same six files. With size 200 and overlap 40 it got 30 chunks between 14 and 198 characters long, and one of them was nothing but the heading ## Lost or damaged items: a chunk with a title and no content, useless to retrieve and a waste of a search slot. With size 400, overlap 60 and the heading separator first, it got 12 chunks, each starting at a section. The diagram shows what happened to fees.md.

There is no universally right size. Use these rules of thumb and then measure (see "Evaluating retrieval" below):

Embeddings: meaning as numbers

An embedding model turns a text into a fixed-length list of numbers, a vector. The model was trained so that texts with similar meaning get similar vectors, even when they share no words. In lab 06, nomic-embed-text turned "When does the library open?" into 768 numbers, starting [-0.075, 0.012, -0.14, -0.067]. No single number means anything you can name ("number 3 is about fees"); meaning lives in the pattern as a whole. The length (768 here) is called the dimension, and it is fixed by the model: every text, a single word or a whole page, becomes exactly 768 numbers.

New to vectors? Think of arrows

A vector with two numbers, like [3, 4], is an arrow on a sheet of paper: 3 steps right, 4 steps up. With three numbers it is an arrow in a room. With 768 numbers nobody can picture it, but the maths is the same: you can still ask whether two arrows point in the same direction. Diagrams like the one below draw two dimensions to give you the intuition; the real thing has 768.

To compare two vectors, the labs use cosine similarity: the cosine of the angle between the two arrows. Pointing the same way gives 1, at right angles gives 0, opposite gives −1. It ignores the arrows' length, which is handy because length mostly reflects things like text size rather than topic. InMemoryVectorStore computes exactly this, so in its results higher means closer (some other stores report a distance instead, where lower is closer; check the docs of the store you use).

import math

def cosine(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    return dot / (math.sqrt(sum(x * x for x in a)) * math.sqrt(sum(y * y for y in b)))

print(cosine([1, 0], [1, 0]))    # 1.0   same direction
print(cosine([1, 0], [0, 1]))    # 0.0   unrelated
print(cosine([1, 0], [-1, 0]))   # -1.0  opposite

Two lessons from lab 06's scores. First, "Can I make things with a laser?" found the maker-space chunk (0.663) although the chunk talks about a "laser cutter" and the question never says "maker space": meaning, not exact words. Second, the scores are close together (0.676 against 0.615 for the late-fee question) and an unrelated chunk always gets some score. A vector search never says "nothing matches"; it always returns the k nearest chunks, even if all of them are poor. Scores are only comparable within one model and one store, so do not hard-code a threshold you read in a blog post.

Query embeddings and document embeddings

LangChain embedding classes have two methods: embed_documents for many texts at indexing time and embed_query for the question. Some embedding models are trained to expect a short task prefix that marks a text as a search query or as a document, and their model cards say so; providers may add it for you or leave it to you. In langchain-ollama 1.1.0, embed_query simply calls embed_documents on one text, so in these labs both sides are embedded in exactly the same way. The rule that never changes: index and query with the same embedding model. Vectors from two different models live in different spaces, and comparing them gives meaningless numbers (often with no error at all).

Vector stores: keeping and searching the vectors

A vector store keeps each chunk's text, metadata and vector, and answers the question "which stored vectors are closest to this one?". The labs use InMemoryVectorStore from langchain_core: a Python dictionary plus a cosine computation over every entry. That is perfect for learning and for a dozen chunks. It is not built for millions of chunks or for several programs sharing one index, which is what dedicated stores are for.

KindExamples (at the time of writing)Where data livesWhen to use
In memoryInMemoryVectorStoreYour Python process; gone when it ends unless you dump itLearning, tests, tiny data sets

Database or serverPostgreSQL with pgvector, Chroma server, managed vector databasesA separate serviceSeveral apps or users, updates over time, production

All of them implement the same LangChain interface (add_documents, similarity_search, as_retriever), so the rest of your code barely changes when you switch. Large stores use approximate nearest-neighbour indexes that trade a tiny bit of accuracy for a lot of speed; the in-memory store compares against every vector, which is exact but slow at scale.

Metadata filters restrict a search before ranking. Lab 06 searched only inside branches.md. In InMemoryVectorStore the filter is a Python function that receives each Document; most database-backed stores take a dictionary instead (each store documents its own filter syntax):

only_branches = store.similarity_search("open on Sunday", k=2,
                                        filter=lambda d: d.metadata["source"].endswith("branches.md"))

Persistence. Embedding costs time, so you do not want to redo it at every start. Lab 06 saved the in-memory store to a JSON file with dump and loaded it back with load, and the reloaded store answered "printing price" with the chunk that starts at ## Wi-Fi and computers (in the 400-character split it also holds the printing prices) without embedding a single chunk again. load still needs the embeddings object, because every new question must be embedded with the same model.

Retrievers: strategies for finding the right chunks

A retriever is anything that takes a question string and returns a list of Documents. That small contract is the point: a retriever is a Runnable, so it plugs into a chain with |, and you can swap strategies without touching the prompt or the model. Lab 07 builds five of them over the same 12 chunks:

dense = store.as_retriever(search_kwargs={"k": 2})
mmr = store.as_retriever(search_type="mmr", search_kwargs={"k": 2, "fetch_k": 6})
bm25 = BM25Retriever.from_documents(chunks, k=2)
hybrid = EnsembleRetriever(retrievers=[bm25, dense], weights=[0.5, 0.5])
multi = MultiQueryRetriever.from_llm(retriever=dense, llm=get_model())

New to BM25? Keyword search with a sense of proportion

BM25 is a classic search-engine formula from long before LLMs. For each word of the question it asks: does the chunk contain it, how often, and how rare is the word across all chunks? "Wi-Fi" appears in one chunk, so it is a strong signal; "the" appears everywhere, so it counts for almost nothing. It also stops rewarding a word after a few repetitions and favours shorter chunks slightly. No model, no vectors: it runs in a blink and needs the rank-bm25 package.

Hybrid search and rank fusion

BM25 scores and cosine scores are on completely different scales, so you cannot just add them. The EnsembleRetriever merges by rank instead, with a method called reciprocal rank fusion: each document gets weight / (rank + c) from every list it appears in, and the totals decide the final order. In the installed langchain-classic, c defaults to 60 and ranks start at 1. A document that both retrievers like rises to the top even if neither put it first.

def rrf(rankings, weights, c=60):
    scores = {}
    for ranking, w in zip(rankings, weights):
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] = scores.get(doc_id, 0) + w / (rank + c)
    return sorted(scores, key=scores.get, reverse=True)

print(rrf([["fees", "loans"], ["digital", "fees"]], [0.5, 0.5]))   # ['fees', 'digital', 'loans']

Multi-query, and when the rewrites drift

The multi-query retriever asks the model for several rewrites of the question, runs the base retriever for each, and returns the union of the results. In lab 07 the log shows what llama3.2 produced for "What is the Wi-Fi password?": the list of "queries" included the model's own preamble ("Here are three alternative versions…") and a closing paragraph, and the real rewrites drifted to generic questions about Wi-Fi at "my home or office" and "common Wi-Fi network names and passwords". The retriever turns each output line into a query, so chatty lines become searches too. A small model rewriting questions can make retrieval worse; here multi-query scored 11 of 12, no better than plain vector search.

Compression and reranking

Two more ideas you will meet in the docs. Contextual compression wraps a retriever and post-processes what it returns: drop chunks that are not relevant, or cut each chunk down to the sentences that matter, so the prompt holds less noise. Reranking retrieves generously (say 20 candidates) with a fast method, then re-scores them with a slower, more accurate model that reads the question and each chunk together (a cross-encoder or an LLM), and keeps the best few. Both trade extra computation for precision. The labs do not use them; try them only once you can measure whether they help.

Evaluating retrieval

You cannot judge a retriever by trying two questions by hand. Lab 07 uses a tiny but real method: a question set (evals/questions.jsonl, 12 questions, each with the file that holds its answer) and one metric, the hit rate: in how many questions did the expected file appear among the retrieved chunks? It checks only retrieval, not the final answer, which makes it fast, cheap and free of model randomness for most strategies.

Read these numbers carefully. With 12 questions, one question is more than 8 percentage points, so differences of one are a hint, not a verdict. The vector miss is instructive: the membership file speaks of "visitors" and a "temporary card", while the question says "visiting for a month". Meaning-based search should bridge that, and on this run it did not. BM25 matched the words. That is why hybrid, which got both, is a common default. Grow your question set from real user questions, especially the ones that failed, and rerun it after every change to chunking, embedding model or retriever.

The RAG chain, and how it fails

Lab 07 then assembles the full chain in one line of LCEL:

prompt = ChatPromptTemplate.from_messages([
    ("system", "You answer questions about Harbor City Library using only the context below. "
               "If the context does not contain the answer, say you don't know. "
               "End with the source file in brackets.\n\nContext:\n{context}"),
    ("human", "{question}"),
])
rag = {"context": hybrid | format_docs, "question": RunnablePassthrough()} | prompt | get_model() | StrOutputParser()

Read it left to right. The dictionary runs two things on the same question: the hybrid retriever followed by format_docs (which joins the chunks and tags each with its file name) fills context, and RunnablePassthrough passes the question through unchanged. The prompt template receives both, the model answers, and the output parser turns the reply message into a plain string.

Two of the five answers were good ("You can keep a DVD for 7 days. [loans.md]"). The other three are worth more, because they show the typical failures:

  • "What happens if I owe 20 EUR?" → "I don't know. [fees.md]". The hybrid retriever had a perfect score, and re-running the retriever alone shows the chunk with the rule "If you owe 15 EUR or more, your card is blocked" among the results. Retrieval worked; the model did not apply a threshold rule to a number that was not written in the text. The cited file even shows it saw the right source.
  • "Do kids pay late fees?" → "Yes, kids do pay late fees. According to the context, Junior cards never pay late fees." The second sentence is right and contradicts the first. The model did not connect "kids" with "junior cards" before committing to "Yes".
  • "Can I bring my dog to the library?" → "I don't know. [branches.md]". Saying "I don't know" is correct, since no policy mentions pets, but the source tag is decoration: there was nothing in branches.md to cite. A citation is only as honest as the model producing it.

The habit to build: when a RAG answer is wrong, print the retrieved chunks before changing anything. If the answer is not in them, work on loading, splitting and retrieval. If it is, work on the prompt, the model, or the way the rule is written. Lab 08 rebuilds this chain as a graph so you can watch each step, and the companion guide AI Engineering builds RAG in plain Python if you want to see the same pipeline without a framework.

Common misconceptions and pitfalls
  • "RAG stops hallucinations." It reduces them when the right chunk is found and the model uses it. Lab 07 shows both conditions failing separately.
  • Mixing embedding models. Indexing with one model and querying with another gives nonsense scores, usually without an error.
  • Trusting a single score. Vector search always returns k results; a high-looking score does not mean the chunk answers the question.
  • Tuning chunk size by feel. Change one setting, rerun the question set, compare hit rates.
  • Forgetting stale indexes. A saved store does not notice that a policy file changed.
  • Dropping metadata. Without source you can neither cite nor evaluate.
  • Assuming the citation is checked. The model writes [fees.md] itself; it can cite a file that says nothing on the subject.
Recap
  • RAG has an indexing phase (load, split, embed, store) and an answering phase (embed the question, retrieve, prompt the model).
  • A Document is text plus metadata; loaders decide what one Document is, and metadata powers citations, filters and evaluation.
  • Splitting gives sharper embeddings and room in the prompt; size and overlap trade context against precision, and small chunks can strand a heading (lab 05).
  • Embeddings are fixed-length vectors (768 for nomic-embed-text); cosine similarity compares their directions; always use the same model for chunks and questions.
  • Vector stores range from in-memory to databases; they share one interface, support metadata filters and can be saved and reloaded.
  • Retrievers are swappable: similarity, MMR, BM25, hybrid with rank fusion, multi-query; measure them with a hit rate on a question set (lab 07: BM25 and hybrid 12/12).
  • A correct retrieval does not guarantee a correct answer: check which stage failed before fixing.
