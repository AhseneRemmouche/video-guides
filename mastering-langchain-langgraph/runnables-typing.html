Runnables, LCEL, typing and Pydantic

The Runnable interface behind every chain, composition, and the Python typing and Pydantic it relies on. Read with book Part VI (chapters 17-18).

Read with Part VI · Appendixes (chapters 17–18) of the book. This page explains the ideas in its own words and links them to the labs.

Every lab in this guide used two kinds of plumbing without stopping to look at it. The first is LangChain's Runnable interface: the reason a prompt, a model, a parser, a retriever and even a compiled LangGraph graph all have invoke, batch and stream, and the reason you can join them with |. The second is Python's typing system and the Pydantic library, which describe the shape of the data flowing through all that plumbing: what a tool accepts, what the graph's state holds, what structured output must look like.

This chapter takes both apart. It follows lab 16, which rebuilds the pieces one by one, and points back to the code you already ran.

Why this matters for your project. When a chain breaks, the error is almost always about shape: a prompt that expected {context} got a string, a tool argument had the wrong type, a model's JSON failed validation. Knowing what each Runnable takes and returns, and how type hints and Pydantic models become the JSON schemas a model sees, turns those errors from mysteries into one-line fixes.

The Runnable interface: one shape for every component

A Runnable is any object that takes one input and produces one output through a fixed set of methods. LangChain's prompt templates, chat models, output parsers, retrievers and tools are Runnables. So is any function you wrap in RunnableLambda, and so is a compiled LangGraph graph (we checked: the lab 11–13 agent graph passes isinstance(graph, Runnable)). Because they share one interface, you learn the methods once.

MethodWhat it doesSeen in
invoke(input)Run once, return the output.Every lab.
batch([in1, in2, ...])Run on many inputs (in parallel threads by default), return a list of outputs in the same order.Labs 01 and 16 (count.batch(["a", "abc", "hello"]) gave [1, 3, 5]).
stream(input)Yield the output in pieces as they are produced. For a model, the pieces are tokens.Labs 01 and 13 (streaming).

astream_eventsAn async stream of detailed events from every inner step (start, chunk, end), for building UIs.Not used.
batch_as_completedLike batch, but yields each result as soon as it is ready, with its index.Not used.
New to async? What ainvoke and await are for

Most of the time a program calling a model is waiting: for the network, for Ollama to generate tokens. Normal ("synchronous") code blocks during that wait. Async code, written with async def and await, lets one Python process start many waits at once and continue whichever finishes first. That is how a web server answers many visitors with one process. You only need the a-methods when you are already inside async code; in a plain script, invoke is simpler. Running an async function from a script needs asyncio.run(...), as lab 10 does for the MCP client.

Composition with |: RunnableSequence

LCEL (LangChain Expression Language) is not a separate language. It is the | operator on Runnables. a | b builds a RunnableSequence: invoking it invokes a, then passes a's output to b. Lab 16 shows it with two tiny functions:

shout = RunnableLambda(lambda text: text.upper())
count = RunnableLambda(len)
chain = shout | count
chain.invoke("library")   # the real output printed: RunnableSequence -> 7

The chain from lab 03, prompt | model | StrOutputParser(), is exactly the same thing with three bigger pieces. The trick to reading any chain is to know the type that travels along each arrow:

Two details are worth knowing. First, plain Python values on either side of | are converted for you: a function becomes a RunnableLambda and a dictionary becomes a RunnableParallel (next section), as long as one side is already a Runnable. That is why retriever | format_docs works in lab 07 and lab 16 even though format_docs is a normal function. Second, streaming flows through a sequence only as far as each step can stream. A model and a StrOutputParser pass tokens along; a plain function waits for its whole input. On our two-lambda chain, list(chain.stream("abc")) gives a single chunk, [3].

Dicts, RunnableParallel, RunnablePassthrough and .assign

A RunnableParallel runs several Runnables on the same input and returns a dict of their outputs. You write it either as RunnableParallel(upper=shout, length=count) or as a plain dict inside a chain. Lab 16 printed {'upper': 'HARBOR', 'length': 6} for the input "harbor".

Two helpers make dicts easy to build:

  • RunnablePassthrough() returns its input unchanged. In a parallel step it means "also keep the original input under this key". Lab 07's RAG chain uses it so the question reaches the prompt next to the retrieved context: {"context": hybrid | format_docs, "question": RunnablePassthrough()} | prompt | ....
  • RunnablePassthrough.assign(key=runnable) takes a dict, computes one new key from it, and returns the dict with the new key added. Lab 16 printed {'text': 'open on Sunday', 'words': 3}: the original key kept, words added.

Lab 16 combines both into a RAG chain that keeps its intermediate values, which a plain prompt | model | parser chain throws away:

rag = (
    RunnableParallel(context=retriever | format_docs, question=RunnablePassthrough())
    | RunnablePassthrough.assign(answer=prompt | get_model() | StrOutputParser())
)
result: Answer = rag.invoke("How much does 3D printing cost?")

RunnableLambda: any function as a Runnable

RunnableLambda(fn) wraps a function that takes one argument. If you need several values, pass a dict and read its keys, as the .assign example does with lambda d: len(d["text"].split()). Wrapping gives the function every Runnable method for free: lab 16 calls count.batch(...) on len. Use it for small glue steps (formatting documents, picking a key, cleaning text). If the function grows into real logic with branches and loops, that is a sign the work belongs in a LangGraph node instead.

Config: tags, names, callbacks and concurrency

Every Runnable method takes an optional second argument, config, a dictionary (typed as RunnableConfig) that travels to every inner step. You have used it since lab 11 without the name: {"configurable": {"thread_id": "sam"}} is a config.

KeyWhat it is for
configurableValues read by components at run time, such as LangGraph's thread_id.
tags, metadataLabels attached to the run and every inner step, so traces (for example in LangSmith) can be filtered.
run_nameA readable name for this run in traces instead of "RunnableSequence".
callbacksObjects notified when steps start, stream and end; logging and tracing tools plug in here.
max_concurrencyThe most inner calls batch may run at once. Useful with a local model that can only serve one request at a time.
recursion_limitThe most steps a LangGraph graph may take before it stops with an error.
count.batch(["a", "abc"], config={"max_concurrency": 2})
chain.invoke("x", config={"tags": ["lab16"], "run_name": "shout-then-count", "metadata": {"branch": "central"}})
named = chain.with_config(run_name="shout-then-count")   # bake the config into a new Runnable

Retries, fallbacks and failing safely

Real calls fail: a network blip, a model server that is restarting, a parser that meets bad JSON. Runnables have two wrappers for this, both shown in lab 16.

  • .with_retry(stop_after_attempt=3, wait_exponential_jitter=False) runs the step again when it raises. The other options are retry_if_exception_type (which exceptions count; by default any Exception) and the backoff settings. Lab 16's flaky function raises ConnectionError twice; the printed result was ok after 3 attempts: ping. Lab 16 turns off the random waiting between attempts (the "jitter") so the demo runs instantly; for real network calls, leave it on.
  • .with_fallbacks([other]) tries the next Runnable when the first raises (filter with exceptions_to_handle). Lab 16's broken step divides by zero, and the output was fallback answer. A common use is a second model: a local model as the backup for a hosted one, or the other way round.
  • batch(inputs, return_exceptions=True) returns the exception object in place of a failed item instead of failing the whole batch. We checked: RunnableLambda(lambda x: 1/x).batch([1, 0], return_exceptions=True) gives [1.0, ZeroDivisionError('division by zero')].

Schemas: every Runnable can describe its input and output

get_input_jsonschema() and get_output_jsonschema() return a JSON schema for what a Runnable accepts and returns. For the lab 16 prompt, the input schema lists required: ['context', 'question']: the template's variables. That is a quick way to find out what dict a chain expects before you call it, and a schema is also what you would publish if you served the chain as an API. The output schema of prompt | get_model() is titled ChatOllamaOutput.

When LCEL is enough, and when to move to LangGraph

LCEL chain is enoughUse LangGraph
The steps always run in the same order.The next step depends on a decision (a router, as in lab 08).
The model is called once or a fixed number of times.The model loops with tools until it is done (labs 09–15).
Data flows forward only.Steps read and write a shared state; you need to go back.
Nothing has to survive between calls.You need threads, checkpoints, memory, interrupts or time travel.

The two mix well: any chain can be a LangGraph node's body, and a compiled graph is a Runnable you can put in a chain. The current official docs centre on create_agent and LangGraph; the Runnable pieces live on in langchain_core as the lower-level toolkit underneath both. The previous chapter, LangChain agents and middleware, has a decision tree.

Python typing for this code

New to type hints? What they are, and what they are not

A type hint is a note in the code saying what type a variable, argument or return value should have: def check_availability(item_id: str) -> str. Plain Python does not check hints when the program runs; a wrong type goes through silently. Hints help in three ways: your editor autocompletes and warns, type checkers such as mypy or pyright find mistakes before you run, and libraries can read them. That last point is why they matter so much here: LangChain reads a tool's hints to build the schema the model sees, LangGraph reads the state's hints to decide how to merge updates, and Pydantic reads a model's hints to validate data.

FormMeaningWhere in the labs
str, int, float, boolThe basic types.Every tool: search_catalog(query: str) -> str.
list[str], dict[str, int]A list of strings; a dict from strings to ints. The part in brackets describes the items.Lab 08 state: docs: list[Document].
int | None"An int, or None". The older spelling is Optional[int]; they mean the same. Optional in this sense does not mean "may be left out"; it means "may be None".Lab 02: max_pages: int | None.
Literal["children", "teens", "adults"]Only these exact values. In a schema it becomes an enum, which strongly guides the model.Lab 02 audience; lab 08 Route.
TypedDictA dict with named, typed keys. At run time it is a normal dict. total=False makes every key optional.Lab 08 State; lab 16 Answer.

Lab 16 adds a hint to a plain variable, result: Answer = rag.invoke(...). It changes nothing at run time (we checked that a TypedDict happily holds a wrong type), but it tells your editor and the next reader which three keys come back.

Annotated with reducers: how LangGraph merges updates

In a LangGraph state, a node returns only the keys it changes. For a plain key, the new value replaces the old one. For a key annotated with a reducer, LangGraph calls the reducer with the old and the new value. operator.add concatenates lists; add_messages appends messages but replaces a message that has the same id. That last rule is exactly what fixed the time-travel bug in lab 13: a new message was appended until we reused the original message's id. We checked this small graph offline:

import operator
from typing import Annotated, TypedDict

from langgraph.graph.message import add_messages


class State(TypedDict):
    messages: Annotated[list, add_messages]     # append, or replace by id
    visited: Annotated[list[str], operator.add]  # concatenate lists
    step: int                                    # no reducer: overwrite

# start {"visited": ["start"], "step": 0}; node a returns {"visited": ["a"], "step": 1};
# node b returns {"visited": ["b"], "step": 2}
# final state: {'messages': [], 'visited': ['start', 'a', 'b'], 'step': 2}

Pydantic: shapes that are checked

Pydantic (version 2.14 in our project) turns a class with type hints into a validator. You subclass BaseModel, list fields with hints, and every time you create an instance Pydantic checks and converts the data. Lab 02's BookRequest is a full example. The parts you will use most:

  • The class docstring becomes the schema's description. LangChain sends it to the model, so write it for the model.
  • Field(description=...) describes one field to the model. This is your main lever on what the model puts there.
  • Defaults: Field(default=None) makes a field optional; Field(default_factory=list) gives each instance its own new empty list.
  • Constraints: max_length / min_length on strings and lists, gt / ge / lt / le on numbers, pattern on strings. They are checked in Python and written into the JSON schema: max_length=4 on a list becomes "maxItems": 4, and gt=0 becomes "exclusiveMinimum": 0. In lab 02, Ollama enforced that maxItems while generating, which stopped the runaway "e-book" list.
from typing import Literal

from pydantic import BaseModel, Field, ValidationError


class BookRequest(BaseModel):
    """A visitor's request for something to read."""
    genre: str = Field(description="One genre, like 'mystery'")
    formats: list[Literal["book", "e-book", "audiobook"]] = Field(default_factory=list, max_length=4)
    max_pages: int | None = Field(default=None, gt=0)


r = BookRequest(genre="mystery", formats=["book"])
r.model_dump()        # {'genre': 'mystery', 'formats': ['book'], 'max_pages': None}
r.model_dump_json()   # '{"genre":"mystery","formats":["book"],"max_pages":null}'
BookRequest.model_validate({"genre": "poetry"})   # build from a dict: formats=[] max_pages=None

try:
    BookRequest(genre="mystery", formats=["book"] * 5, max_pages=-3)
except ValidationError as e:
    print(e)

The last call fails, and the error lists every problem at once, with the field, the rule and the bad input. This is the real text from our run:

BookRequest.model_json_schema() returns the schema as a dict. For this class it contains the description, an enum for the formats, "maxItems": 4, "exclusiveMinimum": 0 and "required": ["genre"]: only fields without a default are required.

How LangChain turns your types into tool and output schemas

The model never sees your Python. It sees JSON schemas, built from your hints:

  • Tools. @tool reads the function's name, docstring and argument hints. Wrap a hint in Annotated[str, "Member id like M-1001"] and the text becomes that argument's description; pass @tool(args_schema=SomeModel) to use a Pydantic class instead. Special parameters such as runtime: ToolRuntime are left out (the previous chapter). We checked a place_hold written this way: the schema has both arguments as required, and member_id carries its description. (Lab 11's privacy bug came from exactly such an example id in a description.)
  • Structured output. with_structured_output(BookRequest) and create_agent(response_format=...) send the schema to the model (as a tool, or as the provider's JSON format), then validate the reply with the same class. A reply that breaks a rule becomes a ValidationError, or, with include_raw=True, a parsing_error next to parsed: None, as in lab 02.

Pitfalls and misconceptions

  • "Type hints are checked." Not by plain Python. Only Pydantic models (and libraries that read hints) enforce them. A TypedDict or dataclass will hold a wrong type silently.
  • Passing a string where a chain expects a dict. A prompt with {context} and {question} needs a dict with both keys; check get_input_jsonschema(). Put a RunnableParallel in front to build the dict from one string.
  • A RunnableLambda with two parameters. It receives one input. Pass a dict and read its keys.
  • Retrying something that will never succeed. with_retry on a bug (a typo, a bad schema) only wastes time; restrict it with retry_if_exception_type to temporary errors such as ConnectionError.
  • A mutable default. Write Field(default_factory=list), not a shared list, for list fields.
  • Forgetting the reducer. Without add_messages (or MessagesState), each node's messages overwrite the history instead of extending it.
  • "Optional means I can leave it out." int | None only allows None; Pydantic still requires the field unless it has a default.
  • Trusting a validated object. Validation proves the shape. Lab 02's duplicate format and invented page count, and lab 14's "Main Branch", all passed.
Recap
  • Prompts, models, parsers, retrievers, tools, wrapped functions and compiled graphs are all Runnables with invoke, batch, stream and async twins.
  • a | b is a RunnableSequence; a dict is a RunnableParallel; RunnablePassthrough keeps the input and .assign adds keys.
  • A config dict carries configurable (thread ids), tags, metadata, run names, callbacks and max_concurrency to every step.
  • with_retry repeats a failing step, with_fallbacks switches to another, return_exceptions=True keeps a batch going.
  • get_input_jsonschema() tells you what a chain expects; lab 16's prompt needs context and question.
  • Type hints are read by libraries: Literal becomes an enum, Annotated carries reducers and descriptions, ToolRuntime[Visitor] is a generic.
  • Pydantic validates data, reports every error at once, and its constraints (like max_length → maxItems) shape the schema the model sees.
