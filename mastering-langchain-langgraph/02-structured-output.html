Structured output

Get validated Pydantic objects back, catch a runaway list with include_raw, and limit it with the schema. Book chapter 4.

Lab · code run on a local model (llama3.2 via Ollama)
Read with chapter 4 · Generating Structured Outputs of the book (Part II · Integrations and Utilities for LLMs in LangChain). This lab is our own hands-on exercise; it does not reproduce the book's examples.

A library visitor writes "My 8-year-old loves crabs and the beach…". A catalog search cannot use that sentence, but it can use audience="children" and max_pages=40. In this lab the model fills in a typed PythonTypeScript object instead of writing free text — and you will watch it fail in an instructive way, catch the failure safely, and fix it in the schema.

Goal

  • Describe the data you want as a Pydantic class and get validated objects back with with_structured_output.
  • Use include_raw=True so a parsing failure returns information instead of crashing your program.
  • Limit a list with Field(max_length=…) and see why a valid object can still be wrong.
  • Describe the data you want as a Zod schema and get validated objects back with withStructuredOutput.
  • Use includeRaw: true so a parsing failure returns information instead of crashing your program.
  • Limit an array with .max(…) and see why a valid object can still be wrong.

The idea in brief

Structured output means the model's answer must fit a schema you define. LangChain turns your Pydantic class (in TypeScript: your Zod schema) into a JSON schema. For ChatOllama the default method is "json_schema": the schema is sent to Ollama as its format setting, and Ollama only lets the model produce text that fits it (this is called constrained decoding). LangChain then parses the JSON back into your class. The result has the right shape — right field names, allowed values, right types. Nothing guarantees the values are true. LangChain.js works the same way with Ollama: in our run the array limit written in the Zod schema was enforced while the model wrote (see the output below). The concept chapter Chat models, structured output and prompts (section "Structured output") compares the three methods and tells the same runaway story from the concept side.

New to Pydantic? Classes that check their own data

Pydantic is a Python library for data classes with validation. You write a class that inherits from BaseModel and give each field a type hint (topic: str). When you create an object, Pydantic checks every value and raises a ValidationError if one doesn't fit. It can also describe the class as a JSON schema (BookRequest.model_json_schema()), which is what LangChain sends to the model, and turn an object back into a plain dictionary (.model_dump()).

New to Literal and int | None? Type hints that limit values

Literal["children", "teens", "adults"] means "exactly one of these three strings"; in the JSON schema it becomes an enum, so the model cannot write "kids". list[Literal[…]] is a list whose items must each be one of the listed words. int | None means "a whole number or nothing"; with default=None the field becomes optional. See also type hints.

New to Zod? Schemas that check data and give you a type

Zod is the TypeScript world's usual validation library. You build a schema from small pieces: z.string(), z.number().int(), z.enum(["a", "b"]) ("exactly one of these strings"; it becomes an enum in the JSON schema), z.array(…) and z.object({ … }). Methods refine a piece: .describe("…") adds a description, .nullable() allows null, .max(4) on an array allows at most 4 items. Schema.parse(value) checks a value at run time and throws a ZodError if it doesn't fit. TypeScript types disappear when the code runs, so a run-time check like this is the only way to know that data coming from outside (here: from a model) really has the shape you expect.

New to z.infer? One schema, one type

A Zod schema is a value (it exists when the code runs); a TypeScript type is not. type BookRequest = z.infer<typeof BookRequest> asks TypeScript to work out the type that matches the schema: { topic: string; audience: "children" | "teens" | "adults"; … }. You write the shape once and get both the run-time check and the editor's type help. Giving the value and the type the same name is allowed, because TypeScript keeps values and types apart. See also type hints, the Python equivalent.

"""Lab 02: get typed, validated data back instead of free text."""
from typing import Literal

from pydantic import BaseModel, Field

from harbor.config import get_model


class BookRequest(BaseModel):
    """What a library visitor is looking for."""
    topic: str = Field(description="The subject, in two to four words")
    audience: Literal["children", "teens", "adults"] = Field(description="Who the book is for")
    formats: list[Literal["book", "e-book", "audiobook", "DVD"]] = Field(description="Formats the visitor accepts")
    max_pages: int | None = Field(default=None, description="Maximum length if the visitor gives one, else null")


model = get_model()
structured = model.with_structured_output(BookRequest)

requests = [
    "My 8-year-old loves crabs and the beach. Anything short, under 40 pages? Paper or e-book is fine.",
    "I'd like an audiobook on the history of our harbor for my commute.",
]
for text in requests:
    result = structured.invoke(text)
    print(type(result).__name__, result.model_dump())

# include_raw=True also returns the raw AIMessage and any parsing error, so a failure does not raise.
vague = "Something fun to read."
raw = model.with_structured_output(BookRequest, include_raw=True).invoke(vague)
print("\ninclude_raw keys:", list(raw))
print("parsed:", raw["parsed"])
print("parsing_error:", str(raw["parsing_error"])[:200] if raw["parsing_error"] else None)
print("output tokens:", raw["raw"].usage_metadata["output_tokens"])


# A schema can also limit size: max_length becomes "maxItems" in the JSON schema, which Ollama enforces.
class BookRequestV2(BookRequest):
    formats: list[Literal["book", "e-book", "audiobook", "DVD"]] = Field(max_length=4, description="Formats the visitor accepts")


fixed = model.with_structured_output(BookRequestV2, include_raw=True).invoke(vague)
print("\nwith max_length=4:", fixed["parsed"], "| error:", fixed["parsing_error"])
// Lab 02: get typed, validated data back instead of free text.
import { z } from "zod";
import { getModel } from "../src/config.js";

const Format = z.enum(["book", "e-book", "audiobook", "DVD"]);

// What a library visitor is looking for. z.infer turns the schema into a TypeScript type.
const BookRequest = z.object({
  topic: z.string().describe("The subject, in two to four words"),
  audience: z.enum(["children", "teens", "adults"]).describe("Who the book is for"),
  formats: z.array(Format).describe("Formats the visitor accepts"),
  max_pages: z.number().int().nullable().describe("Maximum length if the visitor gives one, else null"),
});
type BookRequest = z.infer<typeof BookRequest>;

const model = getModel();
const structured = model.withStructuredOutput(BookRequest, { name: "BookRequest" });

const requests = [
  "My 8-year-old loves crabs and the beach. Anything short, under 40 pages? Paper or e-book is fine.",
  "I'd like an audiobook on the history of our harbor for my commute.",
];
for (const text of requests) {
  const result: BookRequest = await structured.invoke(text);
  console.log(typeof result, result);
}

// includeRaw: true also returns the raw AIMessage and the parsed value, so a failure does not throw.
const vague = "Something fun to read.";
const raw = await model.withStructuredOutput(BookRequest, { name: "BookRequest", includeRaw: true }).invoke(vague);
console.log("\nincludeRaw keys:", Object.keys(raw));
console.log("parsed:", raw.parsed);
console.log("output tokens:", (raw.raw as { usage_metadata?: { output_tokens: number } }).usage_metadata?.output_tokens);

// A schema can also limit size: .max(4) becomes "maxItems" in the JSON schema, which Ollama enforces.
const BookRequestV2 = BookRequest.extend({ formats: z.array(Format).max(4).describe("Formats the visitor accepts") });
const fixed = await model.withStructuredOutput(BookRequestV2, { name: "BookRequest", includeRaw: true }).invoke(vague);
console.log("\nwith .max(4):", fixed.parsed);

Reading the output

Lines 1–12: two good-looking objects. Node prints each object over several lines, after the word object (from typeof). The crab request became audience: 'children', formats: [ 'e-book', 'book' ] and max_pages: 40 — all taken from the sentence. The harbor request became an adult audiobook request. But look at max_pages: 200: the visitor never mentioned a length. The model invented it, even though the field description says "else null". These are the same values as in the Python run.

Lines 14–16: the runaway list. For "Something fun to read." the answer used all 512 output tokens (output tokens: 512) and could not be parsed. This TypeScript lab does not print the text the model wrote, but the Python version of the lab does, and there the model repeated "e-book" in formats again and again: the schema allows an array of any length, so nothing forced it to close. The answer stopped only because getModel() caps every answer at 512 tokens, which cut the JSON in the middle. Because of includeRaw: true we got parsed: null instead of a crash. Notice the keys: [ 'raw', 'parsed' ]. LangChain.js gives you no error message here; to see what went wrong, print raw.raw.content, the text the model actually wrote.

Lines 1–2: two good-looking objects. The crab request became audience='children', formats=['e-book', 'book'] and max_pages=40 — all taken from the sentence. Lines 4–7: the runaway list. For "Something fun to read." the model started a valid object, then wrote "e-book" into formats again and again. The schema allows a list of any length, so nothing forced the list to close. It stopped only because get_model() caps every answer at 512 tokens — output tokens: 512 proves it hit the cap. The JSON was cut in the middle, could not be parsed, and because of include_raw=True we got parsed: None plus the error instead of a crash.

This once froze the whole server. When we first wrote this lab, get_model() had no num_predict. The same generation never ended: the lab hung, and the Ollama server stayed busy with it, so other requests could not get through either. We had to stop the stuck llama-server process by hand. That is why harbor/config.py now sets num_predict=512 for every lab (and src/config.ts sets numPredict: 512): always cap the output of a model you don't fully control.

Lines 18–23: the fix, and its limit. With .max(4) the schema says "maxItems": 4, Ollama refuses a fifth item, and the object parses: parsed is an object, not null. But read the values: 'e-book' appears twice, and max_pages: 2000 came from nowhere. The object is valid; it is not correct.

Common mistakes.
  • Reading .content from the result → undefined (and a type error in pnpm typecheck). A structured runnable returns your object (or { raw, parsed } with includeRaw: true), not an AIMessage. Use result.topic, raw.parsed.
  • Using raw.parsed without checking it → TypeError: Cannot read properties of null when parsing failed. Check if (raw.parsed === null) first.
  • Looking for parsing_error → it does not exist in LangChain.js. Log raw.raw.content to see what the model wrote.
  • Forgetting await → you print a pending Promise instead of the object.
  • No output cap → a runaway generation can hang your program and the Ollama server. Keep numPredict (it comes from getModel(); a bare new ChatOllama({ model: … }) has none).
  • Unbounded arrays → give every array a .max(…); small models can repeat an item until they hit the cap.
  • Trusting the values → a valid object can still hold invented numbers (max_pages 200 and 2000 here). Check them against the request.
  • Thinking the description is enforced → "two to four words" and "else null" are only hints. LangChain sends them inside the schema, and constrained decoding enforces types, enums and limits such as maxItems, not meanings.
Common mistakes.

Recap
  • model.with_structured_output(MyPydanticClass) returns objects of your class; for ChatOllama the default method sends the JSON schema as Ollama's format.
  • Types, Literal enums and Field(max_length=…) (→ maxItems) are enforced while the model writes; descriptions are only hints.
  • model.withStructuredOutput(zodSchema, { name }) returns plain objects checked by Zod; z.infer gives you the matching TypeScript type.
  • Types, z.enum and .max(…) on arrays (→ maxItems) are enforced while the model writes; descriptions are only hints.
  • An unbounded list let llama3.2 repeat "e-book" until the 512-token cap; without the cap it froze the Ollama server.
  • include_raw=True returns raw, parsed and parsing_error, so failures don't crash your program.
  • includeRaw: true returns raw and parsed (no parsing_error; parsed is null on failure), so failures don't crash your program.
  • A schema constrains shape, not truth: a duplicate format and invented page counts (200, 2000) passed validation. Next, lab 03 builds reusable prompts.
