Structured output

Get validated Pydantic objects back, catch a runaway list with include_raw, and limit it with the schema. Book chapter 4.

Lab · code run on a local model (llama3.2 via Ollama)
Read with chapter 4 · Generating Structured Outputs of the book (Part II · Integrations and Utilities for LLMs in LangChain). This lab is our own hands-on exercise; it does not reproduce the book's examples.

A library visitor writes "My 8-year-old loves crabs and the beach…". A catalog search cannot use that sentence, but it can use audience="children" and max_pages=40. In this lab the model fills in a typed Python object instead of writing free text — and you will watch it fail in an instructive way, catch the failure safely, and fix it in the schema.

Goal

  • Describe the data you want as a Pydantic class and get validated objects back with with_structured_output.
  • Use include_raw=True so a parsing failure returns information instead of crashing your program.
  • Limit a list with Field(max_length=…) and see why a valid object can still be wrong.

The idea in brief

Structured output means the model's answer must fit a schema you define. LangChain turns your Pydantic class into a JSON schema. For ChatOllama the default method is "json_schema": the schema is sent to Ollama as its format setting, and Ollama only lets the model produce text that fits it (this is called constrained decoding). LangChain then parses the JSON back into your class. The result has the right shape — right field names, allowed values, right types. Nothing guarantees the values are true. The concept chapter Chat models, structured output and prompts (section "Structured output") compares the three methods and tells the same runaway story from the concept side.

New to Pydantic? Classes that check their own data

Pydantic is a Python library for data classes with validation. You write a class that inherits from BaseModel and give each field a type hint (topic: str). When you create an object, Pydantic checks every value and raises a ValidationError if one doesn't fit. It can also describe the class as a JSON schema (BookRequest.model_json_schema()), which is what LangChain sends to the model, and turn an object back into a plain dictionary (.model_dump()).

New to Literal and int | None? Type hints that limit values

Literal["children", "teens", "adults"] means "exactly one of these three strings"; in the JSON schema it becomes an enum, so the model cannot write "kids". list[Literal[…]] is a list whose items must each be one of the listed words. int | None means "a whole number or nothing"; with default=None the field becomes optional. See also type hints.

"""Lab 02: get typed, validated data back instead of free text."""
from typing import Literal

from pydantic import BaseModel, Field

from harbor.config import get_model


class BookRequest(BaseModel):
    """What a library visitor is looking for."""
    topic: str = Field(description="The subject, in two to four words")
    audience: Literal["children", "teens", "adults"] = Field(description="Who the book is for")
    formats: list[Literal["book", "e-book", "audiobook", "DVD"]] = Field(description="Formats the visitor accepts")
    max_pages: int | None = Field(default=None, description="Maximum length if the visitor gives one, else null")


model = get_model()
structured = model.with_structured_output(BookRequest)

requests = [
    "My 8-year-old loves crabs and the beach. Anything short, under 40 pages? Paper or e-book is fine.",
    "I'd like an audiobook on the history of our harbor for my commute.",
]
for text in requests:
    result = structured.invoke(text)
    print(type(result).__name__, result.model_dump())

# include_raw=True also returns the raw AIMessage and any parsing error, so a failure does not raise.
vague = "Something fun to read."
raw = model.with_structured_output(BookRequest, include_raw=True).invoke(vague)
print("\ninclude_raw keys:", list(raw))
print("parsed:", raw["parsed"])
print("parsing_error:", str(raw["parsing_error"])[:200] if raw["parsing_error"] else None)
print("output tokens:", raw["raw"].usage_metadata["output_tokens"])


# A schema can also limit size: max_length becomes "maxItems" in the JSON schema, which Ollama enforces.
class BookRequestV2(BookRequest):
    formats: list[Literal["book", "e-book", "audiobook", "DVD"]] = Field(max_length=4, description="Formats the visitor accepts")


fixed = model.with_structured_output(BookRequestV2, include_raw=True).invoke(vague)
print("\nwith max_length=4:", fixed["parsed"], "| error:", fixed["parsing_error"])

Reading the output

Lines 1–2: two good-looking objects. The crab request became audience='children', formats=['e-book', 'book'] and max_pages=40 — all taken from the sentence. The harbor request became an adult audiobook request. But look at max_pages: 200: the visitor never mentioned a length. The model invented it, even though the field description says "else null".

Lines 4–7: the runaway list. For "Something fun to read." the model started a valid object, then wrote "e-book" into formats again and again. The schema allows a list of any length, so nothing forced the list to close. It stopped only because get_model() caps every answer at 512 tokens — output tokens: 512 proves it hit the cap. The JSON was cut in the middle, could not be parsed, and because of include_raw=True we got parsed: None plus the error instead of a crash.

This once froze the whole server. When we first wrote this lab, get_model() had no num_predict. The same generation never ended: the lab hung, and the Ollama server stayed busy with it, so other requests could not get through either. We had to stop the stuck llama-server process by hand. That is why harbor/config.py now sets num_predict=512 for every lab: always cap the output of a model you don't fully control.

Line 9: the fix, and its limit. With Field(max_length=4) the schema says "maxItems": 4, Ollama refuses a fifth item, and the object parses: error: None. But read the values: 'e-book' appears twice, and max_pages=2000 came from nowhere. The object is valid; it is not correct.

What you should see. Two lines starting with BookRequest and a dictionary; then the include_raw block; then the max_length=4 line with error: None. Your values will differ. The vague request may or may not run away on your machine — if your parsed is an object and output tokens is small, the model simply behaved this time; run it again or try the experiments below. Whatever happens, the program must not crash: that is the point of include_raw=True.
Common mistakes.
  • Reading .content from the result → AttributeError: 'BookRequest' object has no attribute 'content'. A structured runnable returns your class (or a dict with include_raw=True), not an AIMessage. Use result.topic, raw["parsed"].
  • Using raw["parsed"] without checking it → AttributeError: 'NoneType' object has no attribute … when parsing failed. Check if raw["parsing_error"]: first.
  • No output cap → a runaway generation can hang your program and the Ollama server. Keep num_predict (it comes from get_model(); a bare ChatOllama(model=…) has none).
  • Unbounded lists → give every list a max_length; small models can repeat an item until they hit the cap.
  • Trusting the values → a valid object can still hold invented numbers (max_pages 200 and 2000 here). Check them against the request.
  • Thinking the description is enforced → "two to four words" and "else null" are only hints. LangChain sends them inside the schema but does not add them to your prompt, and constrained decoding enforces types, enums and limits such as maxItems, not meanings.

Try it yourself

  1. Add a request. Append "A DVD about whales for my teenage son." to the requests list (lines 20–23) and run. Check that audience is 'teens', formats contains 'DVD', and whether max_pages is None or invented again.
  2. Catch invented page counts in code. After line 25 add, indented by four spaces like the lines around it, if result.max_pages and str(result.max_pages) not in text: result.max_pages = None. Run: the harbor request now prints 'max_pages': None when the model invents a number, while the crab request keeps its 40, because "40" is in its text.
  3. See the schema. Add print(BookRequestV2.model_json_schema()) at the end and find 'maxItems': 4, the enum lists and your descriptions.
  4. Look at the raw JSON. At the end add print(fixed["raw"].content). You see the exact text the model wrote — a JSON string — before LangChain parsed it into BookRequestV2.
Recap
  • model.with_structured_output(MyPydanticClass) returns objects of your class; for ChatOllama the default method sends the JSON schema as Ollama's format.
  • Types, Literal enums and Field(max_length=…) (→ maxItems) are enforced while the model writes; descriptions are only hints.
  • An unbounded list let llama3.2 repeat "e-book" until the 512-token cap; without the cap it froze the Ollama server.
  • include_raw=True returns raw, parsed and parsing_error, so failures don't crash your program.
  • A schema constrains shape, not truth: a duplicate format and invented page counts (200, 2000) passed validation. Next, lab 03 builds reusable prompts.
