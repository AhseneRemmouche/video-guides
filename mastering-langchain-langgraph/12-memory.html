Short-term and long-term memory

Trim long conversations and remember a member's preferences across threads with a store. Book chapter 13.

Lab · code run on a local model (llama3.2 via Ollama)
Read with chapter 13 · Implementing Memory of the book (Part IV · Build Agents with LangGraph). This lab is our own example on the Harbor City Library project; it does not reproduce the book's code.

Goal. Lab 11 gave each conversation its own history. That raises two new problems. First, a long conversation keeps growing, and every model call sends all of it. Second, what a member tells the assistant in one conversation is gone in the next one, because each thread is separate. In this lab you solve both: you trim the history that goes to the model (short-term memory), and you save facts in a store that every thread of the same member can read (long-term memory).

The idea in brief

Short-term memory is the conversation of one thread, kept by the checkpointer. It is limited by the model's context window (8192 tokens in this project) and by speed: more tokens, slower answers. trim_messages keeps only the most recent part.

Long-term memory is information that outlives a single conversation, such as a member's preferences. LangGraph keeps it in a store, a key-value database organised in folders called namespaces. The store is shared by all threads; the namespace decides whose facts you read. The concept chapter Agents with LangGraph compares the two kinds of memory in more depth.

New to tokens and context windows? Why a long chat is a problem

Models read text as tokens (pieces of words; in English roughly four characters each). The context window is the maximum number of tokens a model can read in one request: the system message, the whole history and the new question together. This project sets it to 8192 tokens in harbor/config.py. If the history grows past it, the oldest text is cut off in an uncontrolled way, and long before that every answer gets slower, because the model must read everything again on each call. Trimming decides yourself what is dropped.

New to key-value stores and namespaces? How the store is organised

A key-value store saves a value (here a small dictionary such as {"text": "..."}) under a key (here "note-0"). A namespace is a tuple of strings that works like a folder path: ("members", "M-1002", "preferences") is the "preferences" folder of member M-1002. store.put(namespace, key, value) saves one item; store.search(namespace) lists the items in that folder (up to 10 by default). InMemoryStore keeps everything in memory, like InMemorySaver in lab 11; LangGraph also has database-backed stores, and stores can add semantic search when you give them an embedding model.

Actions

  1. In the project folder, create labs/12_memory.py with the content below. It does not use the shared agent graph: it builds a smaller graph with a single model node and no tools, so the memory behaviour is easy to see.
  2. Run it: uv run python -m labs.12_memory. Ollama must be running with llama3.2.
  3. Compare part 1 (trimming, no model call) with part 2 (two threads that share one store).

The lab: labs/12_memory.py

"""Lab 12: short-term memory (keep the conversation small) and long-term memory (facts across threads)."""
from langchain_core.messages import AIMessage, HumanMessage, SystemMessage, trim_messages
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import START, MessagesState, StateGraph
from langgraph.store.base import BaseStore
from langgraph.store.memory import InMemoryStore

from harbor.config import get_model

model = get_model()

# 1. Short-term: trim_messages keeps only the most recent part of a long conversation.
history = []
for i in range(1, 7):
    history += [HumanMessage(f"Question {i}: tell me about branch number {i}."), AIMessage(f"Answer {i}: ...")]
kept = trim_messages(history, max_tokens=40, token_counter="approximate", strategy="last", start_on="human")
print(f"1) trim_messages: {len(history)} messages -> {len(kept)} kept:", [m.content[:11] for m in kept])

# 2. Long-term: a store holds facts by namespace, shared by every thread of the same member.
store = InMemoryStore()


def call_model(state: MessagesState, config, *, store: BaseStore):
    member = config["configurable"]["member_id"]
    namespace = ("members", member, "preferences")
    last = state["messages"][-1].content
    if last.lower().startswith("remember"):  # a deliberately simple rule for what to save
        store.put(namespace, f"note-{len(store.search(namespace))}", {"text": last})
    notes = [item.value["text"] for item in store.search(namespace)]
    system = SystemMessage("You are Harbor City Library's assistant. Answer briefly. "
                           f"What this member asked you to remember: {notes or 'nothing yet'}")
    recent = trim_messages(state["messages"], max_tokens=500, token_counter="approximate", strategy="last",
                           start_on="human")
    return {"messages": [model.invoke([system] + recent)]}


builder = StateGraph(MessagesState)
builder.add_node("model", call_model)
builder.add_edge(START, "model")
graph = builder.compile(checkpointer=InMemorySaver(), store=store)


def ask(thread, text):
    config = {"configurable": {"thread_id": thread, "member_id": "M-1002"}}
    print(f"   [{thread}] {text}\n   -> {graph.invoke({'messages': [('user', text)]}, config)['messages'][-1].content}")


print("\n2) Long-term memory across two threads of member M-1002:")
ask("monday", "Remember: I only read books in large print.")
ask("friday", "Can you suggest how I should look for a new novel?")
print("   stored:", [i.value for i in store.search(("members", "M-1002", "preferences"))])

What you should see

  • Part 1: 12 messages -> 2 kept: ['Question 6:', 'Answer 6: .']. Only the last round fits in 40 approximate tokens. This part is computed without the model, so your numbers will be the same.
  • Part 2, friday thread: the answer starts from the stored preference: "Since you mentioned you only read in large print". The friday thread never saw the monday message; the fact came from the store through the system message.
  • stored: exactly one note, {'text': 'Remember: I only read books in large print.'}. The friday question did not start with "remember", so nothing new was saved.

Short-term memory: what trim_messages did

Each fake question is about 15 tokens by the approximate count and each short answer about 9, so the last round costs about 24 tokens. Adding the round before it would need about 48, more than the budget of 40. So the newest round is kept and the first five rounds are dropped.

Trimming is the simplest short-term strategy. Others you will meet: deleting old messages from the state for good, or replacing old rounds with a summary written by the model. Each trades detail for size; trimming simply forgets the oldest part.

Long-term memory: one node, step by step

On Monday, the message starts with "Remember", so put saves it as note-0, then search reads it straight back into the system message. On Friday, in a thread with no history, search finds the same note because the namespace (member M-1002) is the same, and the model's answer uses it.

Look closely at the answers. This graph has no tools and no policy documents. The monday answer promises to "check the print size before recommending or shelving books", and the friday answer mentions a "large print fiction section" and "bestseller lists". None of that exists in the project's data: the model made it up to sound helpful. Memory gave it the preference correctly; it did not give it facts about the library. In a real assistant you would combine memory with tools or retrieval (labs 07 and 09).

Deciding what to remember: real apps are more careful

The rule on line 27, "save any message that starts with remember", is deliberately simple so the mechanism is easy to see. Real applications think much harder about what goes into long-term memory:

  • Privacy. Saved text can contain personal data (health, address, reading habits). Store only what the feature needs, and keep it in the member's own namespace so it can never appear in another member's prompt.
  • Consent. Tell people what is remembered and let them turn it off. "Remember" as an explicit command is actually a reasonable consent signal; silently extracting facts from every message is not.
  • Viewing and deletion. Members should be able to see and delete their notes. With a store this is store.search(namespace) and store.delete(namespace, key); in many countries the law requires it.
  • Quality. Many apps let the model extract structured facts ("prefers large print") instead of saving raw messages, deduplicate them, and update old facts instead of piling up new ones.
  • Who decides the namespace. As in line 24, the member id must come from the app, never from the conversation. Otherwise lab 11's leak would now leak stored preferences too.

Common mistakes

  • Forgetting store=store in compile(). Then LangGraph has no store to inject into call_model: the store parameter receives None, and the first call fails with AttributeError: 'NoneType' object has no attribute 'search' (or 'put', for a "Remember" message).
  • Missing member_id in the config. Line 24 then fails with KeyError: 'member_id'. Every call needs both thread_id and member_id inside "configurable".
  • Putting the member id in the namespace from user text. Anyone could then read anyone's notes by typing another id. Take it from the login.
  • Trimming so hard that the question is lost. A tiny max_tokens can leave nothing useful. Without start_on="human" the kept part may start with an answer whose question is gone.
  • Expecting InMemoryStore to survive a restart. Like InMemorySaver, it lives in the process. Use a database-backed store for real users.

Try it yourself

  1. Change the budget. On line 16, set max_tokens=60, then 80. With the approximate counter we measured 4 kept messages for 60 and 6 for 80 (part 1 needs no model, so it runs in a second; you can stop the program with Ctrl+C after the first line).
  2. Another member's folder. At the end, add print(store.search(("members", "M-1003", "preferences"))). It prints []: M-1002's note lives only in M-1002's namespace, so a thread of member M-1003 would get nothing yet in its system message.
  3. Two notes. Add ask("monday", "Remember: I prefer the Northside Branch.") before the friday call. The final stored: line now lists two notes, note-0 and note-1.
  4. Forget on request. At the end, add store.delete(("members", "M-1002", "preferences"), "note-0") and print the search again: the list is empty.
Recap
  • Short-term memory is one thread's conversation; trim_messages sends only the newest part to the model (12 messages became 2 with a 40-token budget).
  • Long-term memory lives in a store, organised by namespaces such as ("members", "M-1002", "preferences"), and is shared by every thread.
  • A node gets the store by declaring a store parameter; put saves, search reads, and the notes reach the model as text in the system message.
  • The friday thread used the large-print preference saved on Monday, but the model still invented library sections.
  • The "Remember:" rule is a demo. Real apps decide carefully what to store, with privacy, consent and deletion in mind, and always take the member id from the app.
