Retrievers and a RAG chain

Compare vector, MMR, BM25, hybrid and multi-query retrievers on 12 questions, then answer with RAG. Book chapter 9.

Lab · code run on a local model (llama3.2 via Ollama)
Read with chapter 9 · Retrievers (Part III of the book). This lab is our own hands-on exercise on the same topic; the ideas are explained in our own words.

Goal

Lab 06 searched the vector store directly. In LangChain, the standard interface for "give me the chunks for this question" is a retriever. In this lab you build five retrievers (vector, MMR, BM25, hybrid and multi-query), score them on 12 test questions, and then plug the best one into a complete RAG chain that answers with llama3.2. The results include real failures, and they are the most useful part of the lab.

The idea in brief

Retrieval is the last stage of the pipeline before the model answers. The concept chapter The RAG pipeline describes each retriever type. The key ideas:

  • A retriever is a runnable: you call .invoke("question") and get a list of Documents. Because all retrievers share that interface, you can swap one for another without changing the rest of the chain.
  • Different retrievers fail differently. Vector search understands paraphrases but can miss exact words; BM25 matches exact words but not synonyms. Combining them (hybrid) often beats both.
  • You cannot judge a retriever by trying one question. You need a small test set with known answers, which is what evals/questions.jsonl is.
New to BM25? Keyword search with a smart score

BM25 is a classic search-engine formula. It splits the question and every chunk into words and scores a chunk higher when it contains the question's words, especially words that are rare across all chunks ("laser" counts more than "the"). It needs no model and no embeddings, so it is fast and fully predictable. Its weakness: "colour" and "color" are different words to it, and so are "kids" and "junior". The LangChain version here (BM25Retriever, from langchain_community) uses the rank-bm25 package and, by default, splits text on spaces only.

New to MMR? Relevance plus variety

Maximal Marginal Relevance first fetches more candidates than you need (fetch_k=6), takes the most similar one, and then keeps picking the candidate that is similar to the question but different from what was already picked. It avoids returning two nearly identical chunks. The flip side: if the second-best chunk was the right one but looked like the first, MMR may swap it for something less relevant.

Actions

  1. Create evals/questions.jsonl: 12 test questions, each with the file that holds the answer.
  2. Create labs/07_retrievers.py. It uses all four functions of harbor/knowledge.py, including format_docs for the first time.
  3. Check that pyproject.toml lists langchain-classic (for EnsembleRetriever and MultiQueryRetriever) and rank-bm25 (for BM25Retriever). Both are in the project's dependencies, so uv installed them already.

The lab script

"""Lab 07: compare retrievers on 12 questions, then answer with a RAG chain."""
import json
import logging
import sys
from pathlib import Path

from langchain_classic.retrievers import EnsembleRetriever, MultiQueryRetriever
from langchain_community.retrievers import BM25Retriever
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnablePassthrough

from harbor.config import ROOT, get_model
from harbor.knowledge import build_vector_store, format_docs, load_policies, split

chunks = split(load_policies())
store = build_vector_store(chunks)
questions = [json.loads(line) for line in open(ROOT / "evals" / "questions.jsonl", encoding="utf-8")]

dense = store.as_retriever(search_kwargs={"k": 2})
mmr = store.as_retriever(search_type="mmr", search_kwargs={"k": 2, "fetch_k": 6})
bm25 = BM25Retriever.from_documents(chunks, k=2)
hybrid = EnsembleRetriever(retrievers=[bm25, dense], weights=[0.5, 0.5])
multi = MultiQueryRetriever.from_llm(retriever=dense, llm=get_model())

print("1) Did the right file come back in the results?")
for name, retriever in [("vector", dense), ("MMR", mmr), ("BM25", bm25), ("hybrid", hybrid), ("multi-query", multi)]:
    hits, misses = 0, []
    for q in questions:
        files = {Path(d.metadata["source"]).name for d in retriever.invoke(q["question"])}
        if q["source"] in files:
            hits += 1
        else:
            misses.append(q["question"])
    print(f"   {name:<12} {hits}/{len(questions)}   missed: {misses}")

# Multi-query asks the model for other phrasings of the question. Turn on its log to see them.
print("\n   The phrasings multi-query generated for 'What is the Wi-Fi password?':")
logging.basicConfig(stream=sys.stdout, format="   %(message)s")
logging.getLogger("langchain_classic.retrievers.multi_query").setLevel(logging.INFO)
multi.invoke("What is the Wi-Fi password?")

# 2. A RAG chain: retrieve -> fill the prompt -> model -> string.
prompt = ChatPromptTemplate.from_messages([
    ("system", "You answer questions about Harbor City Library using only the context below. "
               "If the context does not contain the answer, say you don't know. "
               "End with the source file in brackets.\n\nContext:\n{context}"),
    ("human", "{question}"),
])
rag = {"context": hybrid | format_docs, "question": RunnablePassthrough()} | prompt | get_model() | StrOutputParser()

print("\n2) RAG answers")
for q in questions[:4] + [{"question": "Can I bring my dog to the library?"}]:
    print(f"   Q: {q['question']}\n   A: {rag.invoke(q['question'])}")

How the hybrid retriever merges two lists

EnsembleRetriever does not compare BM25 scores with cosine scores (they are on different scales). It only uses each document's rank in each list. Every document gets weight / (rank + 60) from each list it appears in, the parts are added, and the documents are sorted by the total. A chunk that both methods rank highly wins. Note that the fused list keeps every document from both lists, so hybrid can return up to 4 chunks here while vector, MMR and BM25 return 2.

Part 1: what the scores tell you

  • Vector missed "I'm visiting for a month. Can I borrow books?" The question and the policy ("Visitors can buy a temporary card") share almost no words or phrasing, so the two nearest chunks by meaning came from other files.
  • MMR missed "How much is a colour print?", a question plain vector search got right. Since MMR always keeps the single most similar chunk and then swaps the rest for variety, the likely story is that the digital.md chunk was second-best and got replaced by a "more different" one.
  • BM25 got all 12, but read the metric carefully. For the visitor question we ran BM25 offline (it needs no model) and it returned the membership.md chunk "Card types", which mentions temporary cards but not the 10 EUR price, which is in the other membership.md chunk. Right file, not quite the right chunk.
  • Hybrid got all 12, partly because it returns up to 4 chunks while the others return 2. More chunks means more chances to include the right file, and also more text in the prompt.
  • Multi-query missed the same visitor question as vector, because every rewrite still goes through the same vector search.

Multi-query: when the rewrites go wrong

Look at the generated queries for "What is the Wi-Fi password?". The retriever's built-in prompt asks for "3 different versions" separated by new lines, and its parser treats every non-empty line of the answer as one query. llama3.2 wrote five lines: an introduction ("Here are three alternative versions…"), three questions, and a closing paragraph. All five were searched as if they were questions. Worse, the three real rewrites drifted away from the library: "access the wireless network at my home or office", "default network name and password for a typical Wi-Fi connection", "common Wi-Fi network names and passwords … in public places". The model did not know the question was about Harbor City Library, so it "improved" it into a generic one.

It still scored 11/12 because the vector search on those lines often lands on the right file anyway, and the union of five searches returns many chunks. Two fixes you could try: pass your own prompt= to from_llm that says "output only the questions, one per line, about a public library", and pass include_original=True so the user's own question is always searched too.

Part 2: the RAG chain and its failures

New to RAG chains? What the model actually receives

For "How long can I keep a DVD?", format_docs turns the retrieved chunks into text like [loans.md] followed by the chunk, a blank line, the next [file] and chunk, and so on. That string replaces {context} in the system message. So the model sees: rules, then the policy text with file names, then the question. That is why it can end with [loans.md]: it copies a tag it sees in the context. It does not check anything; it only writes text that fits.

The first two answers are correct and cite the right file ("7 days [loans.md]", "twice … [loans.md]"). The other three are worth studying:

Common mistakes
  • Importing from the old path. from langchain.retrievers import EnsembleRetriever fails in LangChain 1.x with ModuleNotFoundError; use langchain_classic.retrievers and make sure langchain-classic is installed.
  • Missing rank-bm25. BM25Retriever is only a wrapper; without the rank-bm25 package it raises an ImportError asking you to install it.
  • Looking for the multi-query log in the wrong place. Without lines 39–40 you see no generated queries at all, because the logger's default level hides INFO messages.
  • Forgetting format_docs. {"context": hybrid, …} would put the Python repr of a list of Document objects into the prompt: it works, but the model sees Document(metadata=…) noise and no clean [file] tags.
  • Trusting the source tag. As the dog question shows, the bracketed file name is text the model copied, not proof. For real citations, return the retrieved Documents alongside the answer from your own code.

Try it yourself

  1. Change BM25 to k=1 on line 22. BM25 then drops to 8/12 (we checked this offline, since BM25 needs no model): with only one chunk per question, a near miss becomes a miss. Watch what happens to the hybrid line, which now gets fewer BM25 chunks.
  2. Add include_original=True to MultiQueryRetriever.from_llm(...) on line 24. Your own question is then searched as well as the rewrites.
  3. Add a test case to evals/questions.jsonl, for example {"question": "Can I renew a DVD?", "source": "loans.md", "answer": "yes, twice"}, and run again: the scores are now out of 13.
  4. Make the system prompt stricter, for example add "If a rule gives a threshold, compare the user's number with it." and ask the 20 EUR question again. Note what changes, and remember that one run proves little with a small model.
Recap
  • A retriever turns a question into a list of Documents; all retrievers share .invoke, so they are easy to swap and compare.
  • On our 12 questions: vector 11, MMR 11, BM25 12, hybrid 12, multi-query 11. Keyword search was hard to beat on this data.
  • Hybrid (EnsembleRetriever) fuses ranks, not scores, and keeps everything both lists found.
  • Multi-query treated the model's preamble and closing lines as queries, and its rewrites drifted to home Wi-Fi.
  • The RAG chain is {"context": hybrid | format_docs, "question": RunnablePassthrough()} | prompt | model | StrOutputParser().
  • Failures: "I don't know" for 20 EUR although the rule was retrieved, a self-contradicting kids answer, and a source tag on a non-answer. Check answers, not only retrieval. Next, lab 08 rebuilds this pipeline as a LangGraph graph.
