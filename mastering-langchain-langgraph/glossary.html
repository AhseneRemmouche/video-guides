Glossary

Every technical term in this guide, explained for beginners.

This page explains every technical word used in the labs and concept chapters, in plain language. Each entry says what the word means, why it matters, and where you meet it in the Harbor City Library project. Words in a definition that have their own entry are links, so you can follow a chain of ideas. If you are completely new, read the LLM, RAG and agent entries first, then the concept chapter LLMs, RAG, agents and the LangChain ecosystem.

The definitions are written for this companion in its own words, from general knowledge and the official LangChain, LangGraph, MCP, Ollama and Pydantic documentation. Examples come from the lab project only.

Models and messages

LLM (large language model)
A program trained on huge amounts of text that predicts the next piece of text, one token at a time. Because it is so good at predicting, it can answer questions, summarise, translate and write code. It does not look facts up; it only produces likely text, which is why it can hallucinate. The labs use the small local model llama3.2 through Ollama; see the first concept chapter and lab 01.
Token
The unit of text a model reads and writes: often a whole short word, sometimes part of a longer word or a punctuation mark. Models have limits counted in tokens (the context window, the maximum answer length), and costs and speed are measured in tokens too. In lab 01 the reply's usage_metadata shows how many tokens went in and came out, and harbor/config.py caps each answer at 512 tokens with num_predict.
Context window
The maximum number of tokens a model can look at in one call: the instructions, the conversation so far, any retrieved text and the answer it is writing. Anything that does not fit is lost or causes an error. A bigger window also needs more memory, so the labs set num_ctx=8192 in harbor/config.py to keep llama3.2 mostly on a small GPU. Lab 12 trims long conversations so they keep fitting.
Prompt
The input you send to a model: a question, instructions, examples and any extra context. The wording of a prompt changes the answer a lot, so prompts are usually built from a prompt template rather than typed by hand each time. Every lab sends prompts; lab 03 is about building them well.
System message
A special message at the start of a conversation that tells the model its role and rules, for example "You are Harbor City Library's assistant. Answer briefly." The user does not see it, but the model treats it as standing instructions. You meet SystemMessage in lab 01 and in the agent's SYSTEM constant in harbor/agent_graph.py.
Chat model
A model that takes a list of messages and returns a new message, instead of plain text in and text out. In LangChain every chat model has the same methods (invoke, stream, batch), so you can swap providers without rewriting your code. The labs use ChatOllama from get_model(); lab 01 also builds the same model with init_chat_model("ollama:...").
Message
One turn in a conversation, with a role and some content. LangChain has a class per role: SystemMessage (the rules), HumanMessage (the user), AIMessage (the model) and ToolMessage (the result of a tool). A whole conversation is just a list of these. See lab 01 and the agent labs from lab 09 on.
AI message
What a chat model returns. Its content holds the text answer; it can also carry tool_calls (requests to run tools) and usage_metadata (token counts). In lab 09 the model replies with an AI message whose tool_calls list asks for check_availability with B004.
Temperature
A setting that controls how random the model's word choices are. At 0 it almost always picks the most likely next token, so answers are steadier from run to run; higher values give more varied, creative text. get_model() uses temperature=0, which suits a library assistant that should state facts. Even at 0, small models can still give different answers on different machines.
Streaming
Receiving the model's answer piece by piece while it is being generated, instead of waiting for the whole thing. It makes an app feel faster because the user sees text appear immediately. Lab 01 streams with model.stream(...); lab 08 streams graph steps (stream_mode="updates") and lab 13 streams tokens out of a graph (stream_mode="messages").
Batch
Running the same model or chain on several independent inputs in one call, getting a list of results back in the same order. LangChain runs the inputs in parallel threads, so it is usually faster than a loop. Lab 01 translates "library" into two languages with model.batch([...]), and lab 16 shows that every runnable has batch.

Structured output and typing

Structured output
Asking the model for data in a fixed shape (fields with types) instead of free text, so your program can use it directly. In LangChain you describe the shape with a Pydantic model and call model.with_structured_output(...); you get a validated object back. Lab 02 shows that a schema controls the shape but not the truth of the values; lab 14 does the same for an agent with response_format.
Pydantic
A Python library for describing data with classes and checking (validating) that real data matches. You write a class that inherits from BaseModel, list its fields with type hints, and Pydantic raises an error when a value has the wrong type. It can also produce a JSON Schema, which is how the model learns the expected shape. See lab 02 and the typing chapter.
JSON Schema
A standard way to describe what valid JSON looks like: which keys exist, their types, which are required, and limits such as a maximum list length. Models and tools exchange these schemas so each side knows the expected data. In lab 02, Field(max_length=4) turns into "maxItems": 4 in the schema, and Ollama enforces it.
Type hint
A note in Python code that says what kind of value a variable, argument or return value should be, like query: str or -> str. Python does not enforce them by itself, but editors, Pydantic and LangChain read them: a tool's argument schema is built from its type hints. See lab 16 and the typing chapter.
TypedDict
A Python way to describe a dictionary with known keys and value types, without creating a full class. It is only a description for tools and readers; at run time it is a normal dict. LangGraph uses it for state: lab 08 defines class State(TypedDict, total=False), and lab 16 describes a chain's result with class Answer(TypedDict).
Hallucination
When a model states something false or invented with full confidence. It happens because a model produces likely-sounding text, not checked facts. In lab 03 the model invented an "Innovation Studio", and in lab 10 it invented a book and its availability. RAG and tools reduce it by giving the model real data, but do not remove it.

Prompts and chains

Prompt template
A reusable prompt with placeholders such as {question} that are filled in at run time. LangChain's ChatPromptTemplate turns a dictionary of values into a list of messages, and MessagesPlaceholder leaves a slot for a whole chat history. Introduced in lab 03 and used in the RAG chain of lab 07.
Few-shot prompting
Putting a few worked examples (input and the desired output) into the prompt so the model copies their style and format. It often works better than describing the format in words. Lab 03 uses FewShotChatMessagePromptTemplate to show the model how to tag a book title.
Chain
Several steps joined so the output of one becomes the input of the next, for example prompt template, then model, then output parser. In LangChain you join them with the pipe |, which is LCEL. Lab 03 builds prompt | model | StrOutputParser(); lab 07 adds a retriever in front to make a RAG chain.
LCEL (LangChain Expression Language)
The way of composing runnables with the | operator and with dictionaries. a | b makes a sequence; a dict like {"context": ..., "question": ...} runs branches in parallel on the same input. The result is itself a runnable, so it can be invoked, streamed or batched. Lab 16 takes it apart.
Runnable
LangChain's common interface: anything with invoke, batch and stream (plus async versions). Models, prompt templates, retrievers, output parsers and compiled graphs are all runnables, which is why they fit together. Lab 16 turns plain functions into runnables with RunnableLambda and adds with_retry and with_fallbacks.
Output parser
A step at the end of a chain that turns the model's AI message into something easier to use. StrOutputParser, used in labs 03, 07 and 16, simply keeps the text content as a Python string.

RAG: documents, chunks and retrieval

Document
LangChain's container for a piece of text: page_content (the text itself) plus a metadata dictionary. Loaders produce documents, splitters cut them into smaller documents, and retrievers return them. In lab 04 each policy file becomes one document and each catalog row becomes one more.
Metadata
Extra facts about a document that are not part of its text, such as the file it came from (source), the branch or the format. Metadata lets you filter searches and show where an answer came from. Lab 04 keeps branch, format and available from the CSV, lab 06 filters a search to branches.md, and format_docs tags each chunk with its file name.
Document loader
A class that reads a source (a file, a folder, a CSV, a web page...) and returns a list of documents. Lab 04 uses TextLoader, DirectoryLoader and CSVLoader from langchain_community, which now prints a deprecation warning.
Text splitter
A tool that cuts long documents into smaller chunks, ideally at natural boundaries like headings and paragraphs. The project's split() in harbor/knowledge.py uses RecursiveCharacterTextSplitter with chunks of 400 characters and 60 of overlap, trying a ## heading first. Lab 05 compares it with a Markdown-header splitter.
Chunk
One small piece of a document produced by a text splitter. Small chunks make search precise and keep the prompt short, but a chunk that is too small loses meaning: in lab 05 a 200-character setting left the heading "## Lost or damaged items" alone in its own chunk. (The pieces you get while streaming are also called chunks; that is a different thing.)
Chunk overlap
The number of characters that two neighbouring chunks share. Repeating a little text at the edges means a sentence cut in half still appears whole in one of the two chunks. The project uses 60 characters of overlap; see lab 05.
Embedding
A list of numbers (a vector) that represents the meaning of a text, so that texts with similar meaning get similar lists. An embedding model produces them; the labs use nomic-embed-text, which returns 768 numbers per text. Lab 06 prints the first few numbers of one embedding.
Vector store
A database that keeps embeddings next to their documents and can quickly find the ones closest to a question's embedding. The project uses LangChain's InMemoryVectorStore (it lives in memory); lab 06 also saves it to a JSON file with dump and reloads it without re-embedding.
Cosine similarity
A score that measures how closely two vectors point in the same direction: near 1 means very similar meaning, lower means less related. Vector stores use it (or a similar measure) to rank chunks against a question. Lab 06 prints these scores with similarity_search_with_score; higher is closer.
Retriever
Any component that takes a question and returns relevant documents. A vector store becomes one with as_retriever(), but retrievers can also use keywords (BM25) or combine methods. Because a retriever is a runnable, it fits into a chain. Lab 07 compares five of them on 12 test questions.
MMR (maximal marginal relevance)
A retrieval method that picks results that are relevant to the question but also different from each other, so you do not get several near-copies of the same chunk. In lab 07 it fetches 6 candidates (fetch_k) and keeps the 2 best varied ones (k).
BM25
A classic keyword-search ranking: it scores documents by how often the question's words appear in them, giving more weight to rare words. It needs no embeddings and is good at exact terms like names or ids. Lab 07 uses BM25Retriever (with the rank-bm25 package).
Hybrid search
Combining keyword search (BM25) with meaning-based vector search and merging their results, so you get the strengths of both. Lab 07 does this with EnsembleRetriever from langchain_classic.retrievers, giving each side a weight of 0.5, and uses it in the RAG chain.
Multi-query retrieval
Asking a model to rewrite the user's question in several ways, searching with each version, and merging the results. It can catch documents that use different words from the question, but it depends on the model's rewrites: in lab 07, llama3.2's phrasings drifted toward generic home Wi-Fi questions.
RAG (retrieval-augmented generation)
A pattern where you first find relevant text in your own data, then give it to the model in the prompt and ask it to answer only from that text. It lets a model answer about information it was never trained on (like Harbor City Library's rules) and lowers hallucination. Built in labs 04 to 07, as a graph in lab 08; explained in the RAG pipeline chapter.

The LangChain ecosystem

LangChain
An open-source framework (Python and JavaScript) for building apps with LLMs. It gives one interface for many model providers plus ready-made pieces: prompt templates, loaders, splitters, vector stores, retrievers, tools and agents. It is split into packages such as langchain, langchain-core and provider packages like langchain-ollama. See the first concept chapter.
LangGraph
A library from the same team for building apps as a graph of steps that share state. It adds loops, branching, saved progress (checkpointers), pauses for a human and streaming, which agents need. LangChain's create_agent is built on it. From lab 08 on; see the LangGraph chapter.
LangSmith
A hosted platform from the LangChain company for watching what an LLM app does: it records each run's steps (traces), inputs, outputs and timings, and helps you test and evaluate. It works with LangChain and LangGraph code once you set its API key. The labs do not use it (everything runs offline); it is described in the first concept chapter.

LangGraph

State
The shared data that flows through a LangGraph graph. Each node reads the state and returns only the keys it wants to change. Lab 08 defines its own state as a TypedDict (question, route, docs, answer); the agent labs use the ready-made MessagesState, whose only key is messages.
Node
One step in a graph: a plain Python function that receives the state and returns an update. In lab 08 the nodes are classify, retrieve and generate; in harbor/agent_graph.py they are model and tools.
Edge
A connection that says which node runs next. A normal edge always goes to the same place, like builder.add_edge("tools", "model"). The special names START and END mark where a run begins and stops.
Conditional edge
An edge that chooses the next node at run time by calling a function on the state. In lab 08, the function pick_next sends library questions to retrieve and all others to decline; in the agent, the prebuilt tools_condition goes to tools if the model asked for tool calls and to END otherwise.
Graph
The whole workflow: nodes joined by edges, sharing a state. You describe it with a StateGraph builder, then call compile() to get a runnable app you can invoke or stream. Unlike a chain, a graph can loop. See lab 08.
Reducer
A rule that says how a node's update is combined with the existing value of a state key. Without one, the new value replaces the old one. MessagesState uses the add_messages reducer, which appends new messages, but replaces a message that has the same id. Lab 13 depends on that: reusing the original message's id is what makes an edit replace it instead of adding a copy.

Tools, agents and MCP

Tool
A Python function the model is allowed to ask for, described by a name, a description and an argument schema. The model only reads that description, so its wording matters: in lab 11 and lab 14 the model copied example ids from tool descriptions. The project's tools live in harbor/catalog.py: search_catalog, check_availability, get_member_account and place_hold. See lab 09.
Tool calling
The model's ability to answer with a structured request ("run check_availability with item_id='B004'") instead of text. bind_tools tells the model which tools exist; the model never runs them itself, your code (or a ToolNode) does and sends back the result. Lab 09 shows both steps by hand.
ToolNode
A prebuilt LangGraph node that reads the tool calls in the last AI message, runs the matching tools and adds their results as ToolMessages to the state. It replaces the hand-written loop from the start of lab 09 and is used in harbor/agent_graph.py.
Agent
An LLM app where the model decides, step by step, which tools to use and when it is done, instead of following a fixed chain. That flexibility is powerful but less predictable: in lab 09 the agent claimed books were available without checking. See labs 09 to 15 and the LangGraph chapter.
Agent loop
The cycle at the heart of an agent: call the model, run any tools it asked for, give it the results, and repeat until it answers without tool calls. The diagram above shows it as a graph. It is built by hand in lab 09 and created for you by create_agent in lab 14.
MCP (Model Context Protocol)
An open standard for connecting AI apps to tools and data. A program offers tools, resources and prompts as an MCP server, and any compatible client can use them, whatever language or framework each side is written in. See lab 10 and modelcontextprotocol.io.
MCP server
A program that offers capabilities over MCP. harbor/mcp_server.py uses FastMCP to offer two tools (search_catalog, check_availability) and one resource (catalog://genres). It knows nothing about LangChain. See lab 10.
MCP client
The side that connects to MCP servers and uses what they offer. In lab 10, MultiServerMCPClient from langchain-mcp-adapters starts the server, turns its tools into LangChain tools and reads its resource. Tool results arrive as MCP content blocks.
stdio (standard input/output)
The basic text channels every program has: it reads from standard input and writes to standard output (and errors to standard error). With the stdio transport, an MCP client starts the server as a child process and exchanges messages over these channels, so no network port is needed. Used in lab 10.

State and memory

Checkpointer
A LangGraph component that saves the graph's state after every step, per thread. It is what gives an agent memory between calls, and it makes pauses and time travel possible. Lab 11 uses InMemorySaver (lost when the program ends) and SqliteSaver (saved in a file, survives a restart).
Thread
One conversation, identified by a thread_id you pass in the config. Each thread has its own history in the checkpointer, so "lea" and "sam" in lab 11 do not see each other's messages.
Checkpoint
One saved snapshot of a thread's state, taken after a step of the graph. A thread builds up a list of them; get_state returns the latest and get_state_history lists them all. See lab 11 and lab 13.
Short-term memory
What an agent remembers inside one thread: the messages of the current conversation, kept by the checkpointer. Long conversations can outgrow the context window, so lab 12 keeps only the most recent part with trim_messages.
Long-term memory
Facts an agent keeps across threads, such as a member's favourite genres. They live in a store, not in the conversation history, so a new conversation can still use them. See lab 12.
Store
LangGraph's key-value storage for long-term memory. You put a value under a namespace and a key, and search or get it later from any thread. Lab 12 uses InMemoryStore.
Namespace
A tuple of strings that works like a folder path inside a store, keeping different users' data apart. Lab 12 stores notes under ("members", member, "preferences"), so each member gets their own folder.
Human in the loop
Letting a person check or approve an agent's action before it happens, especially actions that change something (here, place_hold). The graph pauses with an interrupt and continues with the person's decision. Built by hand in lab 13 and with HumanInTheLoopMiddleware in lab 15.
Interrupt
LangGraph's way to pause a run: calling interrupt(...) inside a node stops the graph, saves a checkpoint and returns the payload under __interrupt__. You resume later with Command(resume=...), and that value becomes the return value of interrupt. It needs a checkpointer. See lab 13.
Time travel
Going back to an earlier checkpoint of a thread, optionally changing the state there with update_state, and running again from that point. The old history stays; the new run is a fork. In lab 13 the edit only replaced the message once the original id was reused (see reducer).

LangChain agents and middleware

create_agent
LangChain's function (from langchain.agents) that builds a complete agent loop as a LangGraph graph from a model, a list of tools and a system prompt. It also accepts a checkpointer, a context_schema, a response_format for structured output and middleware. See lab 14 and the agents chapter.
Runtime context
Data your application passes to an agent for one call, such as who is logged in, that the model cannot see or change. In lab 14 you pass context=Visitor(member_id="M-1002"), and the my_account tool reads it through ToolRuntime. This fixes the privacy problem of lab 11, where the model chose whose account to read.
Middleware
Code that runs around every model call or tool call of a create_agent agent, without changing the agent itself. It can log, change messages, stop runaway loops or ask a human for approval. Lab 15 uses a @before_model function plus PIIMiddleware, ModelCallLimitMiddleware and HumanInTheLoopMiddleware.
PII (personally identifiable information)
Data that can identify a person: a name with an address, an email, a phone number, a card number. It should not be sent to a model or a log unless it is really needed. In lab 15, PIIMiddleware("email", strategy="redact") replaced an email with [REDACTED_EMAIL] before the model saw it.

Python and tooling

Ollama
A free program that downloads and runs open models on your own computer and serves them through a local API. The labs use it for llama3.2 (chat) and nomic-embed-text (embeddings) through the langchain-ollama package, so nothing leaves your machine and no API key is needed. ollama ps shows which models are loaded and how much runs on the GPU. See lab 01.
uv
A fast tool for managing Python projects: it installs packages listed in pyproject.toml, records exact versions in a lock file and creates the project's virtual environment. You run every lab with uv run python -m labs.01_chat_models (changing the lab name) and the tests with uv run pytest.
Virtual environment
A private folder of Python packages for one project, so its versions do not clash with other projects or with the system Python. uv creates one in .venv inside the project and uses it automatically with uv run.
Deprecation
A warning that a feature or package still works but will be removed or is no longer maintained, so you should plan to move away from it. In labs 04 and 07, importing from langchain_community prints a DeprecationWarning saying the package is being sunset. Some classes have already moved, like EnsembleRetriever to langchain_classic.retrievers.
async (asynchronous code)
A Python style where a function marked async def can pause at await while it waits for something slow (a network reply, another process) and let other work run meanwhile. Async functions are started with asyncio.run(...). The MCP adapters are async, so lab 10 uses await client.get_tools() and agent.ainvoke(...), the async version of invoke.

TypeScript and the web app

TypeScript
JavaScript with types added: you can write that a variable holds a string or that a function returns a list of messages, and the checker (tsc) reports mistakes before you run anything. The types are removed before the code runs, so it runs wherever JavaScript runs. Every lab has a TypeScript version in harbor-library-ai-ts, run with tsx on Node.js; pick it with the "Code in:" switch at the top of each page.
Node.js
The program that runs JavaScript outside the browser, on your computer or a server. The TypeScript labs and the web app's API server run on it (we used Node 24; the project needs 22 or newer). It comes with npm, and you install pnpm on top of it.
pnpm
A package manager for Node.js, the TypeScript counterpart of uv. pnpm install installs the exact versions listed in package.json and its lock file, and pnpm lab 01, pnpm test or pnpm api run the short commands defined under "scripts" in that file.
tsx
A small tool that runs a TypeScript file directly (tsx server/index.ts), converting it to JavaScript on the fly, so there is no separate build step. It only converts; it does not check types (that is pnpm typecheck). Not to be confused with .tsx, the file extension for TypeScript with JSX used by React.
ESM (ES modules)
The standard JavaScript module system: files share code with import and export. The TypeScript project is set to ESM ("type": "module" in package.json), which is why imports end in .js even for .ts files, and why await can be used at the top level of a file, outside any function.
Zod
A TypeScript library for describing the shape of data, the counterpart of Pydantic. z.object({ title: z.string() }) both checks data at run time and gives you a type (z.infer). LangChain.js uses Zod schemas for structured output and for the arguments of a tool; it turns them into JSON Schema for the model.
Vitest
A test runner for TypeScript and JavaScript, the counterpart of pytest. pnpm test runs the 7 offline tests in tests/offline.test.ts, which check the shared code without calling a model.
React
A JavaScript library for building user interfaces from components. You keep data in state and describe what the page should look like for that state; React updates the page when the state changes. The web app of lab 17 is one React component, App.tsx.
React component
A function that returns a description of part of the page, written in JSX (HTML-like tags inside TypeScript, in .tsx files). React calls it again whenever its state changes. Components can contain other components, like <App /> inside <StrictMode> in main.tsx.
React hook
A function whose name starts with use and that gives a component extra abilities. useState gives it memory between redraws: const [busy, setBusy] = useState(false) returns the current value and a setter, and calling the setter makes React redraw. Hooks must be called at the top level of the component, never inside a condition or loop.
Vite
A development server and build tool for web front ends. During development it converts .tsx files for the browser on request and reloads the page when you save. In lab 17 it also works as a proxy: requests to /api are forwarded to the Hono server, so the browser sees a single address.
SSE (Server-Sent Events)
A simple way for a server to push a stream of messages to a browser over one HTTP response that stays open. Each message has an event: line, a data: line and a blank line after it. The web app uses it to show the answer token by token and each tool call as it happens, the browser counterpart of streaming.
Hono
A small, fast web framework for TypeScript. You create an app, register one function per endpoint with app.post("/api/chat", ...), and start it on Node.js with @hono/node-server. Its streamSSE helper writes Server-Sent Events.
API endpoint
One address on a server plus an HTTP method, such as POST /api/chat, that runs code and returns data rather than a web page. The lab 17 server has two: /api/chat for a new question and /api/resume for a librarian's decision on a paused hold.
Async iterator
A sequence whose items arrive over time, read with for await (const item of sequence); each step waits until the next item is ready. agent.stream(...) and getStateHistory(...) return one in LangChain.js. See also async.
