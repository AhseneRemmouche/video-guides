LangChain agents and middleware

create_agent, runtime context, structured responses, and the middleware hooks around model and tool calls. Read with book Part V (chapters 15-16).

Read with Part V · LangChain Agent (chapters 15–16) of the book. This page explains the ideas in its own words and links them to the labs.

In Part 4 of this guide you built an agent by hand: a LangGraph graph with a model node, a tools node and a conditional edge between them. LangChain 1.x packages that exact loop into one function, create_agent, and adds a clean way to plug extra behaviour around every model call and every tool call: middleware.

This chapter explains what create_agent builds, how to pass information that the model must not control (who is logged in), how to get a typed object back instead of free text, and how middleware hooks work, in which order they run, and which ready-made middleware ships with the installed langchain 1.4.5.

Why this matters for your project. The Harbor City Library assistant reads member accounts and can place holds. Those are exactly the places where an agent needs guard rails: the model must never choose whose account to read (lab 11 showed it will), an email address typed by a visitor should not reach the model, a runaway loop must stop, and a person should approve every hold. Lab 14 and lab 15 add each of these in a few lines.

From a hand-written graph to create_agent

New to agents? What "agent" means in this guide

An agent is a program where a language model decides, step by step, what to do next. The model can answer directly, or it can ask to run a tool (a normal Python function with a name, a description and typed arguments). Your code runs the tool, gives the result back to the model, and asks again. That repeat-until-done cycle is the agent loop. The model never runs code itself; it only writes a request such as check_availability(item_id="B006"), which is called tool calling.

Labs 09 to 13 wrote the loop out in full in harbor/agent_graph.py: create a StateGraph, add a "model" node that calls the model with the tools bound, add a "tools" node (ToolNode), connect them with tools_condition, and compile. That is about fifteen lines, and every agent you write needs the same fifteen lines.

create_agent (imported from langchain.agents) writes them for you. Here is the call from lab 14:

agent = create_agent(
    model=get_model(),
    tools=[search_catalog, check_availability, my_account],
    system_prompt="You are Harbor City Library's assistant. Use the tools. Answer briefly.",
    context_schema=Visitor,
    checkpointer=InMemorySaver(),
)

The result is not a new kind of object. It is a compiled LangGraph graph, the same type you got from builder.compile() in lab 08. That is why everything you learned in Part 4 still works on it: invoke, stream, a checkpointer with a thread_id, get_state, interrupts and Command(resume=...).

What the graph looks like inside

Lab 14 prints the nodes that create_agent built. The real output is ['__start__', 'model', 'tools', '__end__']: the same two working nodes as the hand-written version. __start__ and __end__ are LangGraph's entry and exit points.

The state of this graph is a dictionary with a "messages" list (plus a few internal keys, and "structured_response" when you ask for one). You pass {"messages": [("user", "...")]} and get back the whole conversation, including every AI message with its tool calls and every tool result. Lab 14 reads the tool calls out of that list to print which tools the model used.

When to use create_agent and when to write the graph

Both are LangGraph underneath, so this is a choice about how much you write yourself, not about power.

  • Use create_agent when your program is "a model with tools, looping until it answers". Add behaviour with middleware instead of new nodes. This covers most assistants, including the library one.
  • Write a StateGraph when the flow is not one loop: fixed steps in a set order (classify, then retrieve, then answer, as in lab 08), several branches that run in parallel, custom state keys that several nodes share, or several agents that hand work to each other.
  • Mix them. A create_agent agent is a compiled graph, so it can be one node inside a larger hand-written graph.
  • No loop at all? If the model is called once in a fixed pipeline (prompt, model, parser), a plain LCEL chain is enough (see the next chapter).

Runtime context: identity comes from the app, not the model

In lab 11 a visitor in a fresh conversation asked "What is my member id?". llama3.2 called get_member_account('M-1001'), an id it copied from the example in the tool's description, and showed Lea Martin's account to someone who was not Lea. Nothing was hacked: the tool simply accepted member_id as an argument, and anything that is a tool argument is chosen by the model.

The fix is to take identity out of the model's hands. Your application already knows who is logged in (a session, a token, a login form). It passes that fact to the agent as runtime context: a small object given to invoke that tools and middleware can read, but that the model never sees and cannot change.

@dataclass
class Visitor:
    member_id: str  # set by the application after login, never by the model


@tool
def my_account(runtime: ToolRuntime[Visitor]) -> str:
    """Show the logged-in member's own loans, holds and fees."""
    m = MEMBERS[runtime.context.member_id]
    ...

agent.invoke({"messages": [("user", text)]}, config, context=Visitor(member_id="M-1002"))

Three pieces work together:

  1. context_schema=Visitor tells create_agent the type of the context object.
  2. context=Visitor(member_id="M-1002") on each invoke supplies the value for this run. In a web app this comes from the session, never from the chat text.
  3. A tool parameter annotated ToolRuntime[Visitor] is filled in by LangChain when the tool runs. runtime.context is your Visitor. The parameter is removed from the schema the model sees: we checked, and the JSON schema sent for my_account has no properties at all. The model can call the tool, but it cannot pass a member id.

Be honest about what this does and does not fix. In the real lab 14 run, llama3.2 still ignored my_account for "What do I owe, and what do I have on loan?", called check_availability('B004') (again the example id from a tool description) and then asked the visitor for their library card number. Runtime context closed the privacy hole; it did not make a 3-billion-parameter model pick the right tool. The same code with HARBOR_MODEL=gemma4 called my_account with no arguments and answered correctly for M-1002 (one loan due 2026-10-25, no fees), and for the availability question called search_catalog then check_availability('B006') and gave the correct "4 of 5 copies" answer. Lab 14's page shows both outputs.

What else ToolRuntime gives a tool

AttributeWhat it holds

runtime.stateThe current graph state, for example the messages so far.
runtime.storeThe long-term store passed to create_agent(store=...), if any.
runtime.configThe run's config (thread id, tags, callbacks).

New to ToolRuntime[Visitor]? What the square brackets mean

ToolRuntime is a generic class: a class that takes a type as a parameter, the way list[str] means "a list whose items are strings". ToolRuntime[Visitor] means "a runtime whose context is a Visitor". Python does not check this while the program runs; it is a type hint that lets your editor autocomplete runtime.context.member_id and warn you about typos. LangChain also uses the annotation to recognise the parameter and hide it from the model. The next chapter, Runnables, LCEL, typing and Pydantic, explains generics and dataclasses in more detail.

Structured responses: a typed final answer

An agent normally ends with a text message. Sometimes your code needs fields instead: a title, a number of copies, a branch name. response_format asks the agent to finish with a validated object, which appears in the result under "structured_response". This is the agent version of with_structured_output from lab 02 (structured output).

class Availability(BaseModel):
    title: str
    copies_available: int
    branch: str


for label, strategy in [("ToolStrategy", ToolStrategy(Availability)), ("ProviderStrategy", ProviderStrategy(Availability))]:
    typed = create_agent(get_model(), [search_catalog, check_availability], response_format=strategy,
                         system_prompt="Find the item with search_catalog, then check_availability.")
    result = typed.invoke({"messages": [("user", "Is 'Build Your Own Radio' available?")]})

There are two ways to get a structured answer out of a model, and LangChain names them as strategies. Lab 14 runs the same question once with each, so you can compare them:

StrategyHow it worksNeeds
ToolStrategy(schema)Your schema is turned into one more tool (here a tool named Availability). The agent is finished when the model calls that tool; its arguments are validated and become structured_response. If validation fails, by default (handle_errors=True) the error goes back to the model so it can try again.Any model that supports tool calling.
ProviderStrategy(schema)The provider's own "JSON output that matches this schema" feature constrains what the model writes.A model and provider with native structured output support.
a bare schema, e.g. response_format=AvailabilityLangChain picks for you: provider strategy if the model's profile says it supports native structured output, otherwise tool strategy.Nothing extra.

For a bare schema, which one would our model get? We checked in the installed packages: our ChatOllama instance reports no model profile, so LangChain would fall back to the tool strategy.

Look at the details in the outputs. With ToolStrategy, llama3.2 called check_availability and gemma4 called search_catalog then check_availability, but both finished with a text message instead of calling the Availability tool, so there was nothing to validate and structured_response was None. With ProviderStrategy, neither model called any tool: the reply had to be JSON matching the schema from the very first step, so they filled it in straight away. llama3.2 returned Availability(title='Function call', copies_available=1, branch='Main Branch'); gemma4 got the title right but said 5 copies at "Main Branch". The catalog says 1 of 1 at Central Library, and the library has no Main Branch. The object passed validation because a schema checks shape, not truth (the same lesson as lab 02).

With these local models, a typed final answer from the agent itself was not reliable. A sturdier pattern is to let the agent do its normal tool work, then make a separate, single with_structured_output call that only has to copy facts from the tool results into the schema. We did not run this in the labs; the code below builds without error in the installed versions, but test it with your own model:

agent = create_agent(get_model(), [search_catalog, check_availability],
                     system_prompt="Find the item with search_catalog, then check_availability.")
result = agent.invoke({"messages": [("user", "Is 'Build Your Own Radio' available?")]})

# Step 2: one structured call that only copies facts from the tool results.
facts = "\n".join(m.content for m in result["messages"] if m.type == "tool")
extract = get_model().with_structured_output(Availability)
answer = extract.invoke(f"Fill in the fields using only these tool results:\n{facts}")

Whatever pattern you use, check for None before using a structured result, and compare the values against the tool output in your tests.

Middleware: hooks around the agent loop

New to middleware? The idea in one paragraph

Middleware is code that sits between two parts of a system and sees everything that passes. Web frameworks use it to check logins or log every request without touching each page. In a LangChain agent, middleware sits between the agent loop and the model or the tools. A middleware can look at the state, change it, change the request sent to the model, retry a failed call, stop the run, or pause it for a human. You add it with create_agent(..., middleware=[...]); the agent's own code does not change.

Each middleware implements one or more hooks. There are two kinds. Node-style hooks run at a fixed point, receive (state, runtime), and may return a dictionary of state updates (or None for "no change"). Wrap-style hooks receive the request plus a handler function that performs the real call; they decide whether to call it, how many times, and what to do with the result.

HookKindWhen it runsTypical use
before_agentnodeOnce per invoke, before the loop starts.Load data, check input once.
before_modelnodeBefore every model call.Trim or summarise history, redact PII, count calls.
wrap_model_callwrapAround every model call.Change the prompt, model or tool list for this call; retry; fall back to another model.
after_modelnodeAfter every model reply, before tools run.Inspect tool calls, pause for approval, stop a loop.
wrap_tool_callwrapAround every tool execution.Retry a tool, catch its errors, block or edit a call.
after_agentnodeOnce, after the loop ends.Log the outcome, clean up.

Node-style hooks become real nodes in the graph. When we built an agent with a @before_model function named x and an @after_agent function named y, the node list became ['__start__', 'model', 'x.before_model', 'y.after_agent', '__end__']. Wrap-style hooks add no node: they wrap the existing model and tools nodes from the inside. Every hook also has an async twin (abefore_model, awrap_model_call, …) used when you call ainvoke.

In which order do several middleware run?

The list order matters. We verified it with two tracing middleware, middleware=[A, B], on a fake model that called one tool and then answered:

  • before_agent and before_model run in list order: A, then B.
  • Wrap hooks nest: the first in the list is the outermost layer. A's wrap_model_call starts, calls B's, which calls the model; B finishes first, then A.
  • after_model and after_agent run in reverse order: B, then A. Think of layers of an onion: you leave through them in the opposite order you entered.

Lab 15 shows why this matters. Its custom log_calls hook is first in the list and PIIMiddleware second. The real output: the log line printed 'My email is sam.okoro@example.com. Is item B006 available?', but the message the model saw was 'My email is [REDACTED_EMAIL]. Is item B006 available?'. The logger ran before the redaction. If your logs must never contain an email, put the PII middleware before the logger.

The built-in middleware used in lab 15

Lab 15 builds one agent with four middleware:

middleware=[
    log_calls,
    PIIMiddleware("email", strategy="redact"),                    # emails never reach the model
    ModelCallLimitMiddleware(run_limit=4, exit_behavior="end"),   # stop runaway loops
    HumanInTheLoopMiddleware(interrupt_on={"place_hold": True}),  # a person approves every hold
],

PIIMiddleware: personal data

PII (personally identifiable information) is data that points to a real person: an email, a card number, an IP address. PIIMiddleware(pii_type, strategy=...) detects one type. Built-in types are "email", "credit_card", "ip", "mac_address" and "url"; you can name your own type and pass a regex or a function as detector. Strategies: "redact" (replace with [REDACTED_EMAIL]), "mask" (keep the last characters), "hash" (a stable placeholder, so the same email always maps to the same token) and "block" (raise an error). By default it checks the user's input before each model call; apply_to_output=True and apply_to_tool_results=True extend it to the model's replies and to tool results. It replaces the text in the conversation state itself, which is why lab 15 can print the redacted message from r["messages"][0].

ModelCallLimitMiddleware: a budget for the loop

A confused model can call tools forever. run_limit caps model calls in one invoke; thread_limit caps them across the whole conversation (it needs a checkpointer to remember the count). When the limit is hit, exit_behavior="end" stops the run with an explanatory AI message, and "error" raises an exception instead. On a local model this also protects your machine: lab 02 showed what one runaway generation can do to an Ollama server.

HumanInTheLoopMiddleware: approve, edit or reject

This is the human-in-the-loop pattern from lab 13, without writing interrupt() yourself. interrupt_on={"place_hold": True} means: after the model proposes a place_hold call, pause before it runs. The middleware works in after_model, so it sees the proposed tool calls before the tools node. The run returns with "__interrupt__"; its value lists the action_requests (tool name, arguments, and a description). Lab 15 printed [('place_hold', {'item_id': 'B010', 'member_id': 'M-1002'})]. You resume with one decision per paused call:

from langgraph.types import Command

# approve: run the call as proposed
Command(resume={"decisions": [{"type": "approve"}]})

# edit: run a corrected call instead
Command(resume={"decisions": [{"type": "edit",
                               "edited_action": {"name": "place_hold",
                                                 "args": {"member_id": "M-1002", "item_id": "B011"}}}]})

# reject: do not run it, and tell the model why (what lab 15 does)
Command(resume={"decisions": [{"type": "reject", "message": "Holds on B010 are paused this week."}]})

After the reject in lab 15, the model received a tool message starting "User rejected the tool call for place_hold with reason: …" and answered the visitor that holds on B010 are paused this week. When the reviewer edits a call, the middleware adds a note to the tool result telling the model a person replaced its call, so the model does not try the original again. You can restrict which decisions are allowed per tool with an InterruptOnConfig dictionary, for example {"place_hold": {"allowed_decisions": ["approve", "reject"]}}. The installed version also knows a fourth decision, "respond", where the person answers on behalf of the tool. Remember that pausing needs a checkpointer and a thread_id: the paused state has to be saved somewhere.

More ready-made middleware

The installed langchain.agents.middleware module ships more classes. The labs do not run them; the descriptions below come from their documentation and signatures in langchain 1.4.5, and every example call below builds an agent without error in our offline check. Check the official docs for current options before using them.

Writing your own middleware

There are two ways to write one, and they produce the same kind of object.

A decorated function: one hook

For a single hook, decorate a function. Lab 15's logger is a @before_model function that returns None ("no state change"). The decorators are before_agent, before_model, after_model, after_agent, wrap_model_call, wrap_tool_call, plus dynamic_prompt, a shortcut that builds the system prompt for each call. This example turns tool crashes into a message the model can read, and builds the prompt from the runtime context:

from langchain.agents.middleware import dynamic_prompt, wrap_tool_call
from langchain_core.messages import ToolMessage


@wrap_tool_call
def friendly_errors(request, handler):
    try:
        return handler(request)  # run the real tool
    except Exception as e:
        return ToolMessage(f"Tool failed: {e}. Try another id.", tool_call_id=request.tool_call["id"])


@dynamic_prompt
def by_branch(request):
    return f"You are the assistant of {request.runtime.context.branch}."

by_branch assumes a context dataclass that has a branch field, passed with context_schema. A node-style hook can also return a dictionary such as {"messages": [...]} to update the state, and, when declared with @before_model(can_jump_to=["end"]), return {"jump_to": "end"} to stop the run early.

A class: several hooks and settings

When a middleware needs settings or more than one hook, subclass AgentMiddleware and override the hooks you need. This is the tracer we used to verify the order above (name must be unique per instance, because node names are built from it):

from langchain.agents.middleware import AgentMiddleware


class Trace(AgentMiddleware):
    def __init__(self, tag):
        super().__init__()
        self.tag = tag

    @property
    def name(self):
        return "Trace" + self.tag

    def before_model(self, state, runtime):
        print(self.tag, "before_model,", len(state["messages"]), "messages")

    def wrap_model_call(self, request, handler):
        print(self.tag, "wrap_model_call: in")
        response = handler(request)  # call the next layer, finally the model
        print(self.tag, "wrap_model_call: out")
        return response

    def after_model(self, state, runtime):
        print(self.tag, "after_model")


agent = create_agent(model, tools, middleware=[Trace("A"), Trace("B")])

Pitfalls and misconceptions

  • "The system prompt protects private data." It does not. If a tool takes member_id as an argument, the model chooses it (lab 11). Put identity in runtime context and read it with ToolRuntime.
  • Assuming structured_response is always there. With the tool strategy, a model that answers in text leaves it None (lab 14, with both llama3.2 and gemma4). Check for None.
  • "It validated, so it is correct." With the provider strategy, both models skipped the tools and returned a valid Availability object with invented values ("Main Branch"). Validation checks the shape, never the facts.
  • Ignoring middleware order. A logger placed before PIIMiddleware logs the raw email (lab 15). "before" hooks run in list order, "after" hooks in reverse.
  • Human in the loop without a checkpointer. A pause must be saved to be resumed; pass a checkpointer and a thread_id, and resume on the same thread.
  • Forgetting handler(request) in a wrap hook. If you never call it, the model or tool never runs. Call it once (or several times, for retries) and return its result.
  • Two instances of the same custom class with the same name. Node names come from name; give each instance a distinct one.
  • Expecting middleware to make a weak model smart. Limits, retries and approvals make an agent safer and more predictable, not more accurate. Lab 14's wrong tool choice (llama3.2) came from the model, not the framework.
Recap
  • create_agent builds the same model ⇄ tools LangGraph loop you wrote by hand; the result is a compiled graph.
  • Its main options: model, tools, system_prompt, checkpointer, store, context_schema, response_format, middleware.
  • Runtime context carries facts the app knows (who is logged in); tools read it through ToolRuntime, and the model cannot see or set it.
  • response_format uses a tool strategy (an extra tool) or a provider strategy (forced JSON). In lab 14 the first gave None and the second skipped the tools and invented values, with both local models; a separate structured call after the agent is sturdier.
  • Six hooks: before_agent, before_model, wrap_model_call, after_model, wrap_tool_call, after_agent. "Before" in list order, wraps nested, "after" reversed.
  • Built-ins cover PII, call limits, human approval, summarisation, retries, fallbacks, tool selection, context editing and to-do lists.
  • Write your own with a decorator (one hook) or an AgentMiddleware subclass (several hooks, settings).
