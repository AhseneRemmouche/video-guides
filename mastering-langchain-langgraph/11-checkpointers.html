Checkpointers and threads

Give the agent per-conversation memory, inspect checkpoints, and survive a restart with SQLite. Book chapter 12.

Lab · code run on a local model (llama3.2 via Ollama)
Read with chapter 12 · Checkpointers of the book (Part IV · Build Agents with LangGraph). This lab is our own example on the Harbor City Library project; it does not reproduce the book's code.

Goal. Until now, every call to the library agent started from an empty page: tell it your name, ask again a second later, and it has forgotten. In this lab you give the agent a checkpointer, so each conversation (a thread) keeps its own history. You look inside that saved history, and you make it survive a restart by writing it to a SQLite file. Along the way the run shows a real privacy bug, which is the most important lesson on this page.

The idea in brief

A compiled LangGraph graph does not remember anything by itself. A checkpointer is a small storage object you hand to compile(). After every step of the graph it saves a checkpoint: a snapshot of the state (here, the list of messages) plus "which node runs next". Snapshots are filed under a thread_id that you pass in the config. Next time you call the graph with the same thread_id, it loads the latest snapshot first and adds your new message to it. Different thread_id, different history. The concept chapter Agents with LangGraph explains the theory; this page is the hands-on part.

New to threads and checkpoints? What they are and why they matter

Think of a library's help desk. Each visitor gets a folder; every time something happens in their conversation, the librarian adds a dated page to that folder. The folder is the thread (named by a thread_id such as "lea"), each page is a checkpoint, and the filing cabinet is the checkpointer.

Why it matters: a chat model only sees the messages you send in the current request. To "remember" a conversation, the application must store the earlier messages and send them again. A checkpointer does that storing for you, per thread, so two visitors never see each other's conversation (as long as your app gives them different thread ids).

New to SQLite? What it is and why it's used here

SQLite is a complete SQL database that lives in a single file and needs no server.

Python ships with it (the built-in sqlite3 module). InMemorySaver keeps checkpoints in the Python process's memory, so they disappear when the program ends. SqliteSaver (from the langgraph-checkpoint-sqlite package, version 3.1.2 here) writes them to a file such as runs/checkpoints.sqlite, so another run of the program can continue the same thread.

Node.js reaches it through a driver package: @langchain/langgraph-checkpoint-sqlite (version 1.1.0 here) uses better-sqlite3. MemorySaver (the TypeScript name of Python's InMemorySaver) keeps checkpoints in the Node process's memory, so they disappear when the program ends. SqliteSaver writes them to a file such as runs/checkpoints.sqlite, so another run of the program can continue the same thread.

For many users at once you would pick a server database (LangGraph also has a Postgres checkpointer).

The shared agent graph

This file (harbor/agent_graph.pysrc/agent-graph.ts) appears here for the first time. Labs 12 and 13 import SYSTEM or the builder from it.

"""The library agent as a LangGraph graph (the loop from lab 09), reused by labs 11-13."""
from langchain_core.messages import SystemMessage
from langgraph.graph import START, MessagesState, StateGraph
from langgraph.prebuilt import ToolNode, tools_condition

from harbor.catalog import READ_TOOLS
from harbor.config import get_model

SYSTEM = SystemMessage("You are Harbor City Library's assistant. Use the tools to look things up. "
                       "Remember what the visitor told you earlier in the conversation. Answer briefly.")


def build_builder(tools=READ_TOOLS):
    model = get_model().bind_tools(tools)

    def call_model(state: MessagesState):
        return {"messages": [model.invoke([SYSTEM] + state["messages"])]}

    builder = StateGraph(MessagesState)
    builder.add_node("model", call_model)
    builder.add_node("tools", ToolNode(tools))
    builder.add_edge(START, "model")
    builder.add_conditional_edges("model", tools_condition)
    builder.add_edge("tools", "model")
    return builder
// The library agent as a LangGraph graph (the loop from lab 09), reused by labs 11-13 and the web app.
import { SystemMessage } from "@langchain/core/messages";
import type { StructuredToolInterface } from "@langchain/core/tools";
import { MessagesAnnotation, START, StateGraph } from "@langchain/langgraph";
import { ToolNode, toolsCondition } from "@langchain/langgraph/prebuilt";
import { READ_TOOLS } from "./catalog.js";
import { getModel } from "./config.js";

export const SYSTEM = new SystemMessage(
  "You are Harbor City Library's assistant. Use the tools to look things up. " +
    "Remember what the visitor told you earlier in the conversation. Answer briefly.",
);

export function buildBuilder(tools: StructuredToolInterface[] = READ_TOOLS) {
  const model = getModel().bindTools(tools);

  async function callModel(state: typeof MessagesAnnotation.State) {
    return { messages: [await model.invoke([SYSTEM, ...state.messages])] };
  }

  return new StateGraph(MessagesAnnotation)
    .addNode("model", callModel)
    .addNode("tools", new ToolNode(tools))
    .addEdge(START, "model")
    .addConditionalEdges("model", toolsCondition)
    .addEdge("tools", "model");
}

The lab

The lab file is labs/11_checkpointers.pylabs/11-checkpointers.ts. It has four parts: no checkpointer, an in-memory checkpointer with two threads, a look inside the saved state, and a SQLite file that survives a restart.

"""Lab 11: checkpointers give a graph a memory per conversation (thread) and let it survive restarts."""
import sqlite3

from langgraph.checkpoint.memory import InMemorySaver
from langgraph.checkpoint.sqlite import SqliteSaver

from harbor.agent_graph import build_builder
from harbor.config import RUNS


def show(result, start):
    """Print the tool calls and the final answer of one turn (messages from index `start` on)."""
    for m in result["messages"][start:]:
        if m.type == "ai" and m.tool_calls:
            print("      tool call:", [(c["name"], c["args"]) for c in m.tool_calls])
    print(f"   -> {result['messages'][-1].content}")


def ask(graph, thread, text):
    config = {"configurable": {"thread_id": thread}}
    before = len(graph.get_state(config).values.get("messages", []))
    print(f"   [{thread}] {text}   ({before} earlier messages loaded)")
    show(graph.invoke({"messages": [("user", text)]}, config), before)


# 1. Without a checkpointer every call starts from zero.
plain = build_builder().compile()
print("1) No checkpointer:")
for text in ["Hi, I'm Lea, member M-1001.", "What is my member id?"]:
    print(f"   {text}")
    show(plain.invoke({"messages": [("user", text)]}), 0)

# 2. With a checkpointer, each thread_id keeps its own history.
graph = build_builder().compile(checkpointer=InMemorySaver())
print("\n2) InMemorySaver, two threads:")
ask(graph, "lea", "Hi, I'm Lea, member M-1001.")
ask(graph, "lea", "What is my member id?")
ask(graph, "sam", "What is my member id?")

# 3. The saved state: messages so far and the checkpoints that led there.
config = {"configurable": {"thread_id": "lea"}}
state = graph.get_state(config)
print(f"\n3) Thread 'lea' has {len(state.values['messages'])} messages and "
      f"{len(list(graph.get_state_history(config)))} checkpoints; next node: {state.next or 'none (finished)'}")

# 4. SqliteSaver writes checkpoints to a file, so a new process (or a restart) can continue the thread.
RUNS.mkdir(exist_ok=True)
db_path = RUNS / "checkpoints.sqlite"
db_path.unlink(missing_ok=True)
with sqlite3.connect(db_path, check_same_thread=False) as conn:
    durable = build_builder().compile(checkpointer=SqliteSaver(conn))
    print("\n4) SqliteSaver:")
    ask(durable, "ines", "Hello, I'm Ines, member M-1003. I love cooking books.")
with sqlite3.connect(db_path, check_same_thread=False) as conn:  # a fresh connection, as after a restart
    durable = build_builder().compile(checkpointer=SqliteSaver(conn))
    ask(durable, "ines", "Which genre do I like?")
    rows = conn.execute("SELECT COUNT(*) FROM checkpoints WHERE thread_id = 'ines'").fetchone()[0]
    print(f"   {rows} checkpoint rows stored for thread 'ines' in {db_path.name}")
// Lab 11: checkpointers give a graph a memory per conversation (thread) and let it survive restarts.
import { mkdirSync, rmSync } from "node:fs";
import path from "node:path";
import type { BaseMessage } from "@langchain/core/messages";
import { MemorySaver } from "@langchain/langgraph";
import { SqliteSaver } from "@langchain/langgraph-checkpoint-sqlite";
import { buildBuilder } from "../src/agent-graph.js";
import { RUNS } from "../src/config.js";
import { toolCalls } from "../src/show.js";

type Graph = ReturnType<ReturnType<typeof buildBuilder>["compile"]>;

/** Print the tool calls and the final answer of one turn (messages from index `start` on). */
function show(messages: BaseMessage[], start: number) {
  const calls = toolCalls(messages.slice(start));
  if (calls.length) console.log("      tool call:", JSON.stringify(calls));
  console.log(`   -> ${messages.at(-1)?.content}`);
}

async function ask(graph: Graph, thread: string, text: string) {
  const config = { configurable: { thread_id: thread } };
  const before = ((await graph.getState(config)).values.messages ?? []).length;
  console.log(`   [${thread}] ${text}   (${before} earlier messages loaded)`);
  show((await graph.invoke({ messages: [{ role: "user", content: text }] }, config)).messages, before);
}

// 1. Without a checkpointer every call starts from zero.
const plain = buildBuilder().compile();
console.log("1) No checkpointer:");
for (const text of ["Hi, I'm Lea, member M-1001.", "What is my member id?"]) {
  console.log(`   ${text}`);
  show((await plain.invoke({ messages: [{ role: "user", content: text }] })).messages, 0);
}

// 2. With a checkpointer, each thread_id keeps its own history.
const graph = buildBuilder().compile({ checkpointer: new MemorySaver() });
console.log("\n2) MemorySaver, two threads:");
await ask(graph, "lea", "Hi, I'm Lea, member M-1001.");
await ask(graph, "lea", "What is my member id?");
await ask(graph, "sam", "What is my member id?");

// 3. The saved state: messages so far and the checkpoints that led there.
const config = { configurable: { thread_id: "lea" } };
const state = await graph.getState(config);
let checkpoints = 0;
for await (const _ of graph.getStateHistory(config)) checkpoints++;
console.log(`\n3) Thread 'lea' has ${state.values.messages.length} messages and ${checkpoints} checkpoints; ` +
  `next node: ${state.next.length ? state.next : "none (finished)"}`);

// 4. SqliteSaver writes checkpoints to a file, so a new process (or a restart) can continue the thread.
mkdirSync(RUNS, { recursive: true });
const dbPath = path.join(RUNS, "checkpoints.sqlite");
rmSync(dbPath, { force: true });
console.log("\n4) SqliteSaver:");
const first = SqliteSaver.fromConnString(dbPath);
await ask(buildBuilder().compile({ checkpointer: first }), "ines", "Hello, I'm Ines, member M-1003. I love cooking books.");
first.db.close();
const second = SqliteSaver.fromConnString(dbPath); // a fresh connection, as after a restart
await ask(buildBuilder().compile({ checkpointer: second }), "ines", "Which genre do I like?");
let rows = 0;
for await (const _ of second.list({ configurable: { thread_id: "ines" } })) rows++;
console.log(`   ${rows} checkpoints stored for thread 'ines' in ${path.basename(dbPath)}`);
second.db.close();

Inside a thread: why 8 messages make 10 checkpoints

A checkpoint is written at the start of each run and after every super-step (one round of nodes). One turn where the model calls one tool goes: input saved → START hands over → model asks for a tool → tools runs it → model answers. That is 5 snapshots and 4 new messages. Two turns: 10 snapshots and 8 messages. Thread ines in SQLite had the same shape, which is why the table also holds 10 rows (and why list() counted 10).

The privacy bug: Sam saw Lea's account

Read this carefully: the run leaked a member's private data.

Thread sam is brand new (0 earlier messages loaded). Nobody told the agent any member id. Still, the model called get_member_account({'member_id': 'M-1001'}) and answered Your member ID is M-1001, Lea Martin. The TypeScript run did exactly the same: [["get_member_account",{"member_id":"M-1001"}]] and the same answer. The tool result it received contained Lea's loans and her 2.40 EUR fee. In a real library app, any visitor who asks "What is my member id?" would get another person's account.

Why did it happen? Not because of memory: the checkpointer kept the threads apart correctly. It happened because the model chooses the tool arguments. When it decided to call get_member_account, it needed some member_id. The only id it could see was in the tool's description, which bind_toolsbindTools sends with every request: "Member ids look like M-1001." (line 36 of harbor/catalog.pyline 70 of src/catalog.ts). A small model copied that example value as if it were the visitor's id.

The fix has two parts.

  1. Never let the model decide whose data to read. The logged-in user's identity must come from your application (the login session), not from the conversation. Lab 14 does exactly this: its my_account tool takes no member id at all; it reads runtime.context.member_id from a ToolRuntime that the app fills in (runtime context). The model cannot change it, so it cannot read anyone else's account.
  2. Never put real-looking ids in tool descriptions. Describe the format in words ("an id starting with M- followed by four digits") or use an obviously fake placeholder. Models treat examples as hints, and here the example was a real member.

Also check permissions inside the tool itself, so even a wrong argument returns "not allowed" instead of data.

Look again at part 1. Without a checkpointer, the second call "What is my member id?" answered Your member ID is M-1001. It looks as if the agent remembered Lea. It did not: that call had no history at all. It called get_member_account('M-1001') for the same reason as Sam's thread: the id was copied from the tool description. Lea's thread in part 2 also called the tool on her second turn instead of reading the id from the 4 loaded messages. This is why the lab prints the tool calls: a correct-looking answer can come from the wrong place.

Common mistakes

  • Forgetting the thread_id. A graph compiled with a checkpointer refuses to run without one: ValueError: Checkpointer requires one or more of the following 'configurable' keys: thread_id, checkpoint_ns, checkpoint_id. Pass {"configurable": {"thread_id": "..."}} as the second argument of invoke.
  • Reusing one thread id for different users. Then they share one conversation. In a real app derive the thread id from the logged-in user plus a conversation id, never from what the user types.
  • Sending the whole history yourself as well. With a checkpointer, pass only the new message. If you resend old messages they are appended again and the conversation doubles.
  • Trusting a right answer. As shown above, "Your member ID is M-1001" came from a copied example, not from memory. Look at the tool calls.
  • Windows: OPENSSL_Uplink ... no OPENSSL_Applink at start-up. On our machine an SSLKEYLOGFILE environment variable caused it; running with that variable removed (env -u SSLKEYLOGFILE uv run python -m labs.11_checkpointers in Git Bash) fixed it.
  • Forgetting the thread_id. A graph compiled with a checkpointer needs one to know where to save. Pass { configurable: { thread_id: "..." } } as the second argument of invoke; the key is thread_id with an underscore, not threadId.
  • Treating the history as a list. getStateHistory and list() are async iterators: graph.getStateHistory(config).length does not exist. Walk them with for await (lines 46 and 61).
  • Forgetting await. getState and invoke return Promises. Without await you get a pending Promise, and .values is undefined.
  • Leaving the database open. Close each saver's connection with .db.close() when you are done (lines 57 and 63), as you would close any file.

Recap
  • A checkpointer saves a snapshot of the graph's state after every step, filed by thread_id; pass it with compile(checkpointer=...) and the thread with {"configurable": {"thread_id": ...}}.
  • get_state returns the latest snapshot (.values, .next); get_state_history lists all of them (10 for two turns here).
  • InMemorySaver forgets on exit; SqliteSaver writes to a file, so a restarted program loaded the 4 earlier messages.
  • A checkpointer saves a snapshot of the graph's state after every step, filed by thread_id; pass it with compile({ checkpointer }) and the thread with { configurable: { thread_id } }.
  • getState returns the latest snapshot (.values, .next); getStateHistory is an async iterator over all of them (10 for two turns here), walked with for await.
  • MemorySaver forgets on exit; SqliteSaver.fromConnString(path) writes to a file, so a restarted program loaded the 4 earlier messages, and list() counted 10 checkpoints.
  • The model chooses tool arguments. It copied M-1001 from a tool description and leaked Lea's account to a new visitor, in Python and in TypeScript alike. Identity must come from the app (lab 14's ToolRuntime context), and descriptions must not contain real-looking ids.
  • Memory makes the history available; a small model may still not use it (the genre question).
