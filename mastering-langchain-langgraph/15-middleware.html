Middleware

Add logging, PII redaction, a call limit and human approval around every model and tool call. Book chapter 16.

Lab · code run on a local model (llama3.2 via Ollama)
Read with chapter 16 · Middlewares of the book. The ideas behind this lab are explained in the concept chapter LangChain agents and middleware.

Goal

Add four guard rails to the library agent without touching its loop: a log line before every model call, removal of email addresses before the model sees them, a limit on the number of model calls, and a human approval step before any hold is placed. Each one is a middleware: a piece of code that create_agent runs around every model call or tool call.

The idea in brief

  • Middleware plugs into fixed points of the agent loop, called hooks: before_model, after_model, wrap_model_call, wrap_tool_call, before_agent and after_agent. A hook can read the state, change it, or stop the run.
  • Order matters. before_model hooks run in the order of your middleware=[...] list; after_model hooks run in the reverse order. You will see a real consequence of this in the output.
  • Ready-made middleware ships with langchain. This lab uses three: PIIMiddleware, ModelCallLimitMiddleware and HumanInTheLoopMiddleware, plus one hook you write yourself with @before_model.

The full explanation is in LangChain agents and middleware. This lab builds on lab 14 (create_agent) and lab 13 (interrupts).

New to decorators? What @before_model does to a function

A decorator is a function that takes your function and returns something new built from it. You apply it by writing @name on the line above def. You already used @tool, which turns a function into a tool. @before_model turns a function with the parameters (state, runtime) into a middleware object whose before_model hook calls your function. The middleware takes its name from the function (here log_calls), and your function's return value decides what happens: None means "change nothing", a dictionary means "update the state with these values".

New to PII? What it is and why an agent should hide it

PII (personally identifiable information) is any data that points to a real person: an email address, a phone number, a card number, an IP address. Everything you send to a model may be logged, stored in a trace or, with a cloud provider, leave your machine. A simple rule protects your users: if the model does not need a piece of personal data to do its job, remove it before the model sees it. Here the model only needs the item id to check availability, not the visitor's email.

The code

"""Lab 15: middleware: hooks that run around every model and tool call of a create_agent agent."""
from langchain.agents import create_agent
from langchain.agents.middleware import (HumanInTheLoopMiddleware, ModelCallLimitMiddleware, PIIMiddleware,
                                         before_model)
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import Command

from harbor.catalog import ALL_TOOLS
from harbor.config import get_model


@before_model
def log_calls(state, runtime):
    """A custom hook: print what the model is about to see. Returning None changes nothing."""
    last = state["messages"][-1]
    print(f"      [before_model] {len(state['messages'])} messages, last from {last.type}: {str(last.content)[:60]!r}")
    return None


agent = create_agent(
    get_model(),
    ALL_TOOLS,
    system_prompt="You are Harbor City Library's assistant. Use the tools. Answer briefly.",
    middleware=[
        log_calls,
        PIIMiddleware("email", strategy="redact"),                    # emails never reach the model
        ModelCallLimitMiddleware(run_limit=4, exit_behavior="end"),   # stop runaway loops
        HumanInTheLoopMiddleware(interrupt_on={"place_hold": True}),  # a person approves every hold
    ],
    checkpointer=InMemorySaver(),
)

print("1) PII redaction + logging:")
r = agent.invoke({"messages": [("user", "My email is sam.okoro@example.com. Is item B006 available?")]},
                 {"configurable": {"thread_id": "a"}})
print("   the model saw:", repr(r["messages"][0].content))
print("   answer:", r["messages"][-1].content)

print("\n2) Human in the loop for place_hold:")
config = {"configurable": {"thread_id": "b"}}
r = agent.invoke({"messages": [("user", "I'm member M-1002, please place a hold on B010.")]}, config)
if "__interrupt__" in r:
    request = r["__interrupt__"][0].value
    print("   paused for review:", [(a["name"], a["args"]) for a in request["action_requests"]])
    r = agent.invoke(Command(resume={"decisions": [{"type": "reject", "message": "Holds on B010 are paused this week."}]}),
                     config)
print("   after the decision:", r["messages"][-1].content)

Reading the output

Part 1: logging and PII redaction

Look closely at the first [before_model] line: it still shows sam.okoro@example.com. That is not a failure of the redaction. log_calls is first in the list, so its before_model ran before the PII middleware. One step later, PIIMiddleware replaced the message in the state, and the line the model saw: 'My email is [REDACTED_EMAIL]. Is item B006 available?' shows what the model actually received. The second log line ("3 messages, last from tool") is the second model call, after check_availability returned "4 of 5 copies available at Lighth…". The answer is correct, and the model never knew the email.

Part 2: human approval for place_hold

The model asked for place_hold with {'item_id': 'B010', 'member_id': 'M-1002'}. Right after that model call, HumanInTheLoopMiddleware called interrupt() and the run stopped; invoke returned with an __interrupt__ entry. Our code then resumed with a reject decision. The tool did not run. Instead the middleware added a tool message, visible in the next log line: "User rejected the tool call for `place_hold` with reason: Ho…". The model read it and explained the refusal to the visitor ("holds on B010 are paused this week").

The decision types (checked in the installed package)

We read the source of langchain.agents.middleware.human_in_the_loop in the installed langchain 1.4.5. The resume value must be a dictionary with a "decisions" list containing exactly one decision per paused tool call, in the same order as action_requests; otherwise the middleware raises a ValueError. With interrupt_on={"place_hold": True}, four decision types are allowed:

DecisionShapeWhat happens
approve{"type": "approve"}The tool runs with the arguments the model wrote.
edit{"type": "edit", "edited_action": {"name": ..., "args": {...}}}The tool call the reviewer wrote runs instead. The result the model reads starts with a note saying a human replaced the call.
reject{"type": "reject", "message": "..."} (message optional)The tool does not run. The model gets an error tool message: "User rejected the tool call for `place_hold` with reason: …", or, without a message, a text telling it not to retry unless the user asks.
respond{"type": "respond", "message": "..."}The tool does not run. Your message is returned to the model as if it were the tool's successful result (useful for "ask the user" tools).

To allow fewer types, pass a configuration instead of True, for example {"place_hold": {"allowed_decisions": ["approve", "reject"]}}. Sending a type that is not allowed raises a ValueError.

The call limit

ModelCallLimitMiddleware did not trigger in our run: each part used two model calls (see the two [before_model] lines per part), below the limit of 4. It is a safety net for the day a model gets stuck calling tools in circles. Its before_model hook counts the calls of the current run; when the count has reached the limit, it adds an AI message and jumps to the end instead of calling the model.

What you should see. In part 1, the "the model saw" line contains [REDACTED_EMAIL] every time, because redaction is plain code, not the model. In part 2, if the model calls place_hold, you see a "paused for review" line with the tool's name and arguments, then a [before_model] line whose last message is the rejection, then an answer. The wording of the answers will differ from ours.

Common mistakes.

  • No checkpointer. Human-in-the-loop pauses the run with an interrupt; without checkpointer= there is no saved state to resume.
  • Resuming with a different thread_id. The Command must be sent with the same config as the paused run (line 46 reuses config).
  • Wrong resume format. Command(resume="no") worked for the hand-written interrupt of lab 13, but this middleware expects {"decisions": [...]} with one decision per paused call.
  • Assuming the paused path always happens. If the model answers without calling place_hold, there is no __interrupt__; that is why line 42 checks for it.
  • Thinking the logger proves redaction failed. The first log line shows the raw email only because log_calls runs before PIIMiddleware. Check what is stored in the state, as line 36 does.

Try it yourself

  1. Log after redaction. Move log_calls below PIIMiddleware(...) in the list (line 25 after line 26). The first [before_model] line now shows [REDACTED_EMAIL], because the PII hook runs first.
  2. Another strategy. Change strategy="redact" to "mask" or "hash" and look at the "the model saw" line: the address is now partly hidden or replaced by a hash. With "block" the run raises an error instead.
  3. Approve the hold. On line 45 use {"decisions": [{"type": "approve"}]}. Now place_hold really runs (in memory only) and the next log line shows its result, "Hold placed on The Cartographer's Daughter for Sam Okoro…".
  4. Hit the limit. Set run_limit=1. If the model calls a tool in its first step (as in our run), the second model call is blocked and the answer of part 1 becomes "Model call limits exceeded: run limit (1/1)".
Recap
  • Middleware adds behaviour around the agent loop through hooks; you pass it as middleware=[...] to create_agent, and each hook becomes a node in the graph.
  • before_model hooks run in list order, after_model hooks in reverse order. That is why our logger saw the email before PIIMiddleware removed it.
  • PIIMiddleware("email", strategy="redact") replaced the address with [REDACTED_EMAIL] in the stored message, so the model never saw it.
  • ModelCallLimitMiddleware stops runaway loops; ours never reached the limit of 4 calls.
  • HumanInTheLoopMiddleware pauses before chosen tools and returns action_requests; resume with Command(resume={"decisions": [...]}) using approve, edit, reject or respond.
