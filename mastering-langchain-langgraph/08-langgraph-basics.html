LangGraph fundamentals

Rebuild RAG as a graph with state, nodes, a router and conditional edges, and stream its steps. Book chapter 10.

Lab · code run on a local model (llama3.2 via Ollama)
Read with chapter 10 · Fundamentals of LangGraph of the book (Part IV · Build Agents with LangGraph). This lab is our own example on the Harbor City Library project.

Goal. Rebuild the question-answering pipeline from lab 07 as a graph instead of a chain. The graph first decides whether a question is about the library at all. Library questions go through retrieval and an answer; everything else gets a polite refusal without ever touching the vector store. Along the way you will meet the four building blocks of every LangGraph program: state, nodes, edges and a compiled graph.

Why the project needs it. A chain always runs the same steps in the same order. An agent has to choose what to do next, loop, and stop when it is done. LangGraph is the tool the rest of this guide uses for that. Labs 09 to 13 all build on what you learn here.

The idea in brief

A LangGraph program is a small state machine. The state is a dictionary that every step can read. A node is a plain Python function: it receives the current state and returns only the keys it wants to change. An edge says which node runs next. A conditional edge calls a small routing function that looks at the state and returns the name of the next node. That is the whole model. The concept chapter LangGraph and agents explains it in more depth.

New to graphs and state machines? What they are and why they matter

In computer science a graph is just "boxes and arrows": the boxes (nodes) are steps, the arrows (edges) say what can come after what. A state machine adds a shared piece of data, the state, which each step reads and updates. You already use this idea when you draw a flowchart on paper.

Why bother for an AI app? Because a model's answer decides what happens next. "Is this a library question?", "Did the model ask for a tool?", "Did the user approve?" are all branches. Writing them as a graph keeps each step small and testable, makes the branches visible (you can print the picture), and lets LangGraph add features later, like saving the state after every step (lab 11) or pausing for a human (lab 13).

New to TypedDict? A dictionary with a declared shape

A TypedDict is a normal Python dict at run time. The class only describes which keys exist and what type each value should have, so your editor and LangGraph know the shape of the state. total=False means "none of these keys is required". That fits this lab: the run starts with only question, and the other keys appear as nodes fill them in. Python itself does not check the types while the program runs.

The code

"""Lab 08: the RAG chain rebuilt as a LangGraph graph with a router."""
from typing import Literal, TypedDict

from langchain_core.documents import Document
from langgraph.graph import END, START, StateGraph
from pydantic import BaseModel

from harbor.config import get_model
from harbor.knowledge import build_vector_store, format_docs

retriever = build_vector_store().as_retriever(search_kwargs={"k": 2})
model = get_model()


class State(TypedDict, total=False):
    question: str
    route: str
    docs: list[Document]
    answer: str


class Route(BaseModel):
    route: Literal["library", "other"]


def classify(state: State) -> State:
    prompt = ("Is this question about a public library (cards, loans, fees, branches, rooms, digital services)? "
              f"Answer 'library' or 'other'.\nQuestion: {state['question']}")
    return {"route": model.with_structured_output(Route).invoke(prompt).route}


def retrieve(state: State) -> State:
    return {"docs": retriever.invoke(state["question"])}


def generate(state: State) -> State:
    prompt = (f"Answer in one or two sentences using only this context. If it is not there, say you don't know.\n\n"
              f"{format_docs(state['docs'])}\n\nQuestion: {state['question']}")
    return {"answer": model.invoke(prompt).content}


def decline(state: State) -> State:
    return {"answer": "I can only help with Harbor City Library questions."}


def pick_next(state: State) -> str:
    return "retrieve" if state["route"] == "library" else "decline"


builder = StateGraph(State)
builder.add_node("classify", classify)
builder.add_node("retrieve", retrieve)
builder.add_node("generate", generate)
builder.add_node("decline", decline)
builder.add_edge(START, "classify")
builder.add_conditional_edges("classify", pick_next, ["retrieve", "decline"])
builder.add_edge("retrieve", "generate")
builder.add_edge("generate", END)
builder.add_edge("decline", END)
graph = builder.compile()

print("1) The graph as Mermaid text (paste it into mermaid.live to see it):")
print(graph.get_graph().draw_mermaid())

print("2) Running it. stream_mode='updates' shows each node as it finishes:")
for question in ["How many items can a junior card borrow?", "Who won the football match yesterday?"]:
    print(f"\n   Q: {question}")
    for update in graph.stream({"question": question}, stream_mode="updates"):
        for node, change in update.items():
            shown = {k: (f"{len(v)} documents" if k == "docs" else v) for k, v in change.items()}
            print(f"   [{node}] {shown}")

How the state fills up

The key rule: a node returns only what it changes, and LangGraph merges that into the state. You never copy the whole state forward by hand. Here is the first question's run, step by step.

What is a reducer, and why don't we need one here?

When a node returns a key, LangGraph has to decide how to combine the new value with the old one. The default is simple: the new value replaces the old one. A reducer is a function you attach to a key to change that rule, for example "append to the list instead of replacing it". This lab writes each key once, so replacing is exactly right. Lab 09 uses MessagesState, whose messages key has a reducer that appends new messages to the conversation.

Compared with the chain of lab 07

In lab 07 the RAG answer came from an LCEL chain: {"context": retriever | format_docs, "question": RunnablePassthrough()} | prompt | model | StrOutputParser(). That is a straight pipe: data flows left to right, every step runs every time. The graph does the same retrieve-then-generate work, but adds a decision in front and keeps the intermediate results (route, docs) in a state you can look at.

Common mistakes (each checked on a tiny offline graph with the same LangGraph version):
  • A node returns a string instead of a dict, e.g. return model.invoke(prompt).content. You get InvalidUpdateError: Expected dict, got …. Wrap it: return {"answer": …}.
  • A typo in a returned key, e.g. {"answr": …}. There is no error: keys that are not in State are silently dropped, and the final state simply has no answer. If a value "disappears", compare its key with the State class.
  • The router returns a name that is not a target. If pick_next returned "retriever" (with an r), the run stops with KeyError: 'retriever'. Router return values must match node names exactly.
  • Reading a key no node has set yet. With total=False nothing is guaranteed, so state["docs"] in a node that can run before retrieve raises KeyError: 'docs'. Use state.get("docs", []) when a key may be missing.
  • Forgetting compile(): calling builder.invoke(…) gives AttributeError: 'StateGraph' object has no attribute 'invoke'.

Try it yourself

  1. Watch the whole state instead of the updates. On line 68 change stream_mode="updates" to stream_mode="values" and print each item. You now get the complete state after every step, the same picture as the "How the state fills up" diagram (the first item is the input itself).
  2. Add your own question. Put "Can I book a meeting room at Northside?" in the list on line 66. It should be classified library and answered from rooms.md. Then try something borderline, like "What is a good book about the sea?", and see which way the router goes.
  3. Get the final state in one call. Replace the inner loop with print(graph.invoke({"question": question})["answer"]). invoke runs the same graph but returns only the final state.
  4. Retrieve more context. On line 11 set "k": 4. The [retrieve] line will show '4 documents' and the prompt for generate gets longer.
Recap
  • The state is a TypedDict; total=False lets it start with only the question.
  • Nodes are plain functions that return only the keys they change; LangGraph merges them.
  • A conditional edge calls a router (pick_next) that returns the next node's name.
  • compile() turns the builder into a runnable; draw_mermaid() prints its picture.
  • stream_mode="updates" shows each node's change as it finishes; the off-topic question skipped retrieval entirely.
