Document loaders

Load Markdown files, a folder and a CSV catalog into Documents with metadata. Book chapter 6.

Lab · code run on a local model (llama3.2 via Ollama)
Read with chapter 6 · Document Loaders (Part III of the book). This lab is our own hands-on exercise on the same topic; the ideas are explained in our own words.

Goal

So far the model has only seen text that you typed into a prompt. A library assistant has to answer from the library's own rules and catalog. Before any of that text can be searched, it has to be read from disk into a shape LangChain understands. That shape is the Document, and the classes that create Documents from files are called document loaders.

In this lab you add the library's data (six policy files and a catalog) and load it in three ways: one file, a whole folder, and a CSV table. You will see what a Document contains and why its metadata matters later.

The idea in brief

This is the first stage of the RAG pipeline: load, then split (lab 05), embed and store (lab 06), retrieve and answer (lab 07). The concept chapter The RAG pipeline shows the whole picture; this page zooms in on loading.

Every loader, whatever the file type, gives back the same thing: a Python listJavaScript array (Document[]) of Document objects. A Document has just two important fields:

  • page_contentpageContent: a string with the text itself. This is what will be split, embedded and shown to the model.
  • metadata: a dictionaryplain object (Record<string, any>) with facts about the text, such as which file it came from. The model usually never sees it, but your code uses it to filter results and to cite sources.
New to document loaders? What they are and why they matter

A loader is a small class that knows how to read one kind of source (text files, CSV, PDF, web pages, databases) and turn it into Documents. You create it with the location of the data and some options, then call .load(), which reads everything and returns a list. Some loaders also offer .lazy_load(), which hands Documents over one at a time; that saves memory for very large sources.In TypeScript .load() is asynchronous: it returns a Promise, so you write await loader.load() to get the array.

Why not just use open(...).read()readFileSync(...) from node:fs? You could, for one file. Loaders give you a common format, so a splitter or vector store does not care whether the text came from Markdown, CSV or a PDF. They also fill in the source metadata for you, which you need later to say "this answer came from fees.md".

New to metadata? Why a dictionary next to the text is so useful

Metadata is "data about the data": the file name, a row number, a branch, a date. It travels with the text through every later step. When a chunk is retrieved in lab 07, its metadata still says which file it came from, so the answer can cite it. When you search in lab 06, you can filter on metadata ("only branches.md"). In this lab you filter books by the available column without reading the text at all.

The data: six policy files

Each policy file has one # title line and two or three ## section headings, each followed by a short paragraph. That regular shape matters in lab 05, where the splitter cuts at the ## headings. The files are short on purpose (about 510 to 575 characters each) so you can read every chunk yourself. Notice a few facts you will meet again: the 15 EUR block rule in fees.md, the Wi-Fi network name in digital.md, and the temporary card in membership.md.

The lab script

"""Lab 04: load files into LangChain Documents (text + metadata)."""
from pathlib import Path

from langchain_community.document_loaders import CSVLoader, DirectoryLoader, TextLoader

from harbor.config import DATA

# 1. One file.
doc = TextLoader(str(DATA / "policies" / "loans.md"), encoding="utf-8").load()[0]
print("1) TextLoader:", type(doc).__name__, "| metadata:", {"source": Path(doc.metadata["source"]).name})
print("   first 80 characters:", repr(doc.page_content[:80]))

# 2. A whole folder: one Document per file.
policies = DirectoryLoader(str(DATA / "policies"), glob="*.md", loader_cls=TextLoader,
                           loader_kwargs={"encoding": "utf-8"}).load()
print(f"\n2) DirectoryLoader: {len(policies)} documents")
for d in policies:
    print(f"   {Path(d.metadata['source']).name:<16} {len(d.page_content):>5} characters")

# 3. A CSV: one Document per row. source_column decides what goes into metadata["source"].
books = CSVLoader(str(DATA / "catalog.csv"), source_column="id", encoding="utf-8",
                  metadata_columns=["branch", "format", "available"]).load()
print(f"\n3) CSVLoader: {len(books)} documents (one per row)")
print("   page_content:", repr(books[0].page_content[:120]))
print("   metadata:    ", books[0].metadata)

# 4. Metadata is what lets you filter later: here, books available right now.
available = [b for b in books if b.metadata["available"] != "0"]
print(f"\n4) {len(available)} of {len(books)} titles have a copy on the shelf")
// Lab 04: load files into LangChain Documents (text + metadata).
import path from "node:path";
import { Document } from "@langchain/core/documents";
import { CSVLoader } from "@langchain/community/document_loaders/fs/csv";
import { DirectoryLoader } from "@langchain/classic/document_loaders/fs/directory";
import { TextLoader } from "@langchain/classic/document_loaders/fs/text";
import { CATALOG } from "../src/catalog.js";
import { DATA } from "../src/config.js";

// 1. One file.
const [doc] = await new TextLoader(path.join(DATA, "policies", "loans.md")).load();
console.log("1) TextLoader:", doc.constructor.name, "| metadata:", { source: path.basename(doc.metadata.source) });
console.log("   first 80 characters:", JSON.stringify(doc.pageContent.slice(0, 80)));

// 2. A whole folder: one Document per file. The map says which loader handles which extension.
const policies = await new DirectoryLoader(path.join(DATA, "policies"), { ".md": (p) => new TextLoader(p) }).load();
console.log(`\n2) DirectoryLoader: ${policies.length} documents`);
for (const d of policies) {
  console.log(`   ${path.basename(d.metadata.source).padEnd(16)} ${String(d.pageContent.length).padStart(5)} characters`);
}

// 3. A CSV: one Document per row, every column as "name: value" text. Metadata holds the file and line.
const rows = await new CSVLoader(path.join(DATA, "catalog.csv")).load();
console.log(`\n3) CSVLoader: ${rows.length} documents (one per row)`);
console.log("   pageContent:", JSON.stringify(rows[0].pageContent.slice(0, 120)));
console.log("   metadata:   ", { ...rows[0].metadata, source: path.basename(rows[0].metadata.source) });

// 4. Metadata is what lets you filter later. The JS CSVLoader cannot copy columns into metadata,
//    so build the Documents yourself: the text to search goes in pageContent, the fields to filter on in metadata.
const books = Object.values(CATALOG).map((b) => new Document({
  pageContent: `${b.title} by ${b.author} (${b.genre}, ${b.year})`,
  metadata: { source: b.id, branch: b.branch, format: b.format, available: b.available },
}));
const available = books.filter((b) => b.metadata.available !== "0");
console.log(`\n4) ${available.length} of ${books.length} titles have a copy on the shelf`);
console.log("   example:", available[0].pageContent, available[0].metadata);

Anatomy of a Document

How a CSV row becomes a Document

The JS CSVLoader reads each row as an object (column name to value) with the d3-dsv package, and writes every column into pageContent as name: value lines. Its only options are column (use one column as the whole text) and separator; there is no way to move columns into the metadata, which is always { source, line }. When you need fields to filter on, build the Documents yourself, as part 4 of the lab does.

CSVLoader reads each row as a dictionary (column name to value). Columns that are not in metadata_columns are written into page_content as name: value lines. The columns you list go into metadata instead. That is why the printed page_content has year and then genre, but no format between them.

New to CSV? How the file is read

CSV ("comma-separated values") is a plain-text table. The first line names the columns; each later line is one row. Python's built-in csv module, which CSVLoader uses, turns each line into a dictionary like {"id": "B001", "title": "...", "copies": "3", ...}. Every value is text: the module does not guess numbers. If you need a number, convert it yourself with int(...).d3-dsv (used by CSVLoader) and the few lines in src/catalog.ts (which simply split each line on commas) both turn each line into an object like { id: "B001", title: "...", copies: "3", ... }. Every value is text: nothing guesses numbers. If you need a number, convert it yourself with Number(...). Splitting on commas only works because no field in this file contains a comma; a real CSV parser also handles quoted fields.

The DeprecationWarning: what "sunset" means for you

The TypeScript run prints no warning, but the same news reaches you at another moment: when you run pnpm install, pnpm marks @langchain/community as deprecated (a package author can flag a version that way on the npm registry, and every install shows it). It means the same as the DeprecationWarning that the Python version prints when it imports langchain-community: the community integrations are being "sunset", retired in favour of standalone integration packages. Only CSVLoader comes from that package in this lab; TextLoader and DirectoryLoader come from @langchain/classic.

The first lines of the output are not an error. The program ran to the end and printed every result. Python prints a DeprecationWarning when a library wants to tell developers that something will go away or stop being looked after. This one says that the langchain-community package "is being sunset and is no longer actively maintained" and points to a GitHub issue with migration guidance toward standalone integration packages.

"Sunset" means a planned, gradual retirement:

  • Today: the code works. Your project pins langchain-community 0.4.2 in uv.lock, so uv installs exactly that version every time, and it keeps working the same way.Your project pins @langchain/community 1.1.29 in package.json and pnpm-lock.yaml, so pnpm install installs exactly that version every time, and it keeps working the same way.
  • From now on: do not expect new features or bug fixes in that package. If a loader has a bug, it may never be fixed there.
  • Later: when you start a new project, or need a fix, look for the integration in its own package (the link in the warning lists the plan). Common mistakes
  • Running from the wrong folder. pnpm lab 04 must be started in the project folder (the one with package.json); elsewhere pnpm cannot find the lab script.
  • Forgetting await. Without it, load() gives you a Promise, not an array. pnpm typecheck reports the mistake, and at run time the destructuring const [doc] = … fails because a Promise is not iterable.
  • d3-dsv missing or in the wrong version. CSVLoader imports it only when it parses the file, so the error appears at that point, not at the import line. The loader's source code then throws Please install d3-dsv as a dependency with, e.g. `pnpm install d3-dsv@2`. Keep the version 2 that package.json pins.
  • Looking for source_column or metadata_columns. They exist only in the Python loader. In JS, build the Documents yourself (part 4).
  • Comparing CSV values with numbers. b.metadata.available !== 0 is always true, because "0" (a string) is never strictly equal to 0 (a number). You would get 12 of 12, and the type checker does not warn you, because metadata values have the type any.

Recap
  • Loaders turn files into a list of Document objects: page_content (text) plus metadata (a dict)pageContent (text) plus metadata (an object); in TypeScript you await the load().
  • TextLoader reads one file, DirectoryLoader a whole folder (one Document per file), and CSVLoader one Document per row.
  • source_column chooses what goes into metadata["source"]; metadata_columns moves columns from the text into the metadata.
  • The JS CSVLoader puts every column in the text and only { source, line } in the metadata; when you need fields to filter on, build Documents yourself with new Document({ pageContent, metadata }).
  • CSV values are strings; compare with "0", not 0.
