Embeddings and a vector store

Embed the chunks, search by meaning with scores and filters, and save the store to disk. Book chapter 8.

Lab · code run on a local model (llama3.2 via Ollama)
Read with chapter 8 · Embeddings and Vector Stores (Part III of the book). This lab is our own hands-on exercise on the same topic; the ideas are explained in our own words.

Goal

You have 12 tidy chunks. Now you need a way to find the right ones for a question, even when the question uses different words than the policy ("How much do I pay if a book is late?" versus "Adult cards pay 0.20 EUR per item per day late"). In this lab you turn text into embeddings (lists of numbers that capture meaning), put all chunks in a vector store, search it with scores and a metadata filter, and save it to disk and load it back.

The idea in brief

Embedding and storing are stages three and four of the RAG pipeline. The concept chapter The RAG pipeline covers the theory; here is the short version:

  • An embedding model reads a text and returns a fixed-length list of numbers (a vector). Texts with similar meaning get vectors that point in similar directions. We use nomic-embed-text running in Ollama; it returns 768 numbers per text.
  • A vector store keeps each chunk's text, vector and metadata together. To search, it embeds the question with the same model and returns the chunks whose vectors are closest.
  • "Closest" is measured here with cosine similarity: a score where higher means more similar.
New to embeddings? What the numbers mean

Think of each vector as an arrow in a space with 768 directions instead of the usual two or three. The embedding model was trained so that texts about the same thing produce arrows pointing roughly the same way: "late fee" and "pay if a book is late" end up close, "Wi-Fi password" ends up somewhere else. You never read the numbers yourself; you only compare them.

Two rules matter in practice. First, the question and the chunks must be embedded by the same model, or the arrows live in different spaces and comparisons are meaningless. Second, an embedding model is not a chat model: it never writes text. It is small and fast (it runs fine next to llama3.2).

New to cosine similarity? How two vectors get a score

Cosine similarity measures the angle between two arrows. Pointing the same way gives 1, at right angles gives 0, opposite gives -1. Length does not matter, only direction. With text embeddings, scores for related texts are higher than for unrelated ones, but the exact numbers depend on the model, so compare scores within one search ("0.676 beats 0.615") rather than treating 0.6 as a universal threshold.

The lab script

"""Lab 06: embed chunks, store them, and search by meaning."""
from pathlib import Path

from langchain_core.vectorstores import InMemoryVectorStore

from harbor.config import RUNS, get_embeddings
from harbor.knowledge import load_policies, split

embeddings = get_embeddings()

# 1. An embedding is a list of numbers; similar texts get similar lists.
vector = embeddings.embed_query("When does the library open?")
print(f"1) one embedding: {len(vector)} numbers, starting {[round(x, 3) for x in vector[:4]]}")

# 2. Build the store: every chunk is embedded once.
chunks = split(load_policies())
store = InMemoryVectorStore.from_documents(chunks, embeddings)
print(f"\n2) stored {len(chunks)} chunks")

# 3. Similarity search with scores (cosine similarity: higher is closer).
for question in ["How much do I pay if a book is late?", "Is there Wi-Fi?", "Can I make things with a laser?"]:
    print(f"\n3) {question}")
    for doc, score in store.similarity_search_with_score(question, k=2):
        print(f"   {score:.3f}  {Path(doc.metadata['source']).name:<13} {doc.page_content[:70]!r}")

# 4. Filter on metadata: search only inside one file.
only_branches = store.similarity_search("open on Sunday", k=2,
                                        filter=lambda d: d.metadata["source"].endswith("branches.md"))
print("\n4) filtered to branches.md:", [d.page_content[:50] for d in only_branches])

# 5. Save to disk and load it back without re-embedding.
RUNS.mkdir(exist_ok=True)
store.dump(str(RUNS / "policies_store.json"))
again = InMemoryVectorStore.load(str(RUNS / "policies_store.json"), embeddings)
print("\n5) reloaded store answers:", again.similarity_search("printing price", k=1)[0].page_content[:60])
// Lab 06: embed chunks, store them, and search by meaning.
import { mkdirSync, readFileSync, writeFileSync } from "node:fs";
import path from "node:path";
import { MemoryVectorStore } from "@langchain/classic/vectorstores/memory";
import { RUNS, getEmbeddings } from "../src/config.js";
import { loadPolicies, split } from "../src/knowledge.js";

const embeddings = getEmbeddings();

// 1. An embedding is a list of numbers; similar texts get similar lists.
const vector = await embeddings.embedQuery("When does the library open?");
console.log(`1) one embedding: ${vector.length} numbers, starting ${JSON.stringify(vector.slice(0, 4).map((x) => +x.toFixed(3)))}`);

// 2. Build the store: every chunk is embedded once.
const chunks = await split(await loadPolicies());
const store = await MemoryVectorStore.fromDocuments(chunks, embeddings);
console.log(`\n2) stored ${chunks.length} chunks`);

// 3. Similarity search with scores (cosine similarity: higher is closer).
for (const question of ["How much do I pay if a book is late?", "Is there Wi-Fi?", "Can I make things with a laser?"]) {
  console.log(`\n3) ${question}`);
  for (const [doc, score] of await store.similaritySearchWithScore(question, 2)) {
    console.log(`   ${score.toFixed(3)}  ${path.basename(doc.metadata.source).padEnd(13)} ${JSON.stringify(doc.pageContent.slice(0, 70))}`);
  }
}

// 4. Filter on metadata: search only inside one file.
const onlyBranches = await store.similaritySearch("open on Sunday", 2, (d) => d.metadata.source.endsWith("branches.md"));
console.log("\n4) filtered to branches.md:", onlyBranches.map((d) => d.pageContent.slice(0, 50)));

// 5. Save to disk and load it back without re-embedding. The vectors are plain arrays, so JSON is enough.
mkdirSync(RUNS, { recursive: true });
const file = path.join(RUNS, "policies_store.json");
writeFileSync(file, JSON.stringify(store.memoryVectors));
const again = new MemoryVectorStore(embeddings);
again.memoryVectors = JSON.parse(readFileSync(file, "utf-8"));
console.log("\n5) reloaded store answers:", (await again.similaritySearch("printing price", 1))[0].pageContent.slice(0, 60));

Reading the scores

For the late-fee question, the winner is the fees chunk (0.676). The runner-up is the e-books chunk of digital.md (0.615), which is not random: it contains "there are never late fees on digital items". The model saw "late fees" in both. For the laser question, the gap is larger (0.663 versus 0.459): only one chunk talks about a laser cutter. A big gap between first and second place usually means a clear answer; a small gap means the store is less sure. Remember that a store always returns k results, even when nothing is relevant; lab 07 shows what that does to an answer.

Filtering with metadata

The first chunk contains both the Central Library (open on Sunday afternoon) and the Northside Branch (closed on Sunday), which is why it holds the answer to "open on Sunday" for two branches at once.

Saving and loading the store

Embedding is the expensive part of indexing. With 12 chunks it does not matter, but with thousands of pages you do not want to re-embed everything each time the program starts. dump writes the store as JSON and load reads it back. Each entry in the file has four keys: id (a random UUID), vector (768 numbers), text and metadata.MemoryVectorStore has no dump/load, so the lab writes the store's memoryVectors array to JSON and sets it on a new store. Each entry in the file has three keys: content (the text), embedding (768 numbers) and metadata, which holds source and the loc.lines that the splitter added. This is a shortcut that relies on the store's internal format, so a future version could change it; a database-backed store is the robust choice for a real project. The metadata keeps the absolute path of the source file, so if you move the project, the file names still print correctly, but the full paths point to the old place.

Why "printing price" returned the Wi-Fi chunk

Part 5 searched for "printing price" and printed ## Wi-Fi and computers. That looks wrong, but it is not. In lab 05 we saw that at 400 characters digital.md is cut into two chunks, and the second one contains both the Wi-Fi section and the Printing section (we checked by running split() offline and looking for the word "Printing": it is only in that chunk). So the store found the right text; the lab only printed the first 60 characters, which happen to be about Wi-Fi.

Common mistakes
  • The embedding model is not pulled. If you skipped ollama pull nomic-embed-text, the first embedding call fails with an error from Ollama saying the model was not found.
  • Ollama is not running. Unlike labs 04 and 05, this lab calls a model; you get a connection error. Start the Ollama app (or ollama serve) first.
  • Mixing embedding models. If you build and dump the store with one model, then load it with a different HARBOR_EMBED_MODEL, the question vectors no longer match the stored ones. Results become nonsense, or the comparison fails if the vector lengths differ. Re-embed when you change models.
  • Treating scores as absolute. 0.6 is not "good" or "bad" by itself; compare candidates for the same question.
  • Passing a dict as filter. InMemoryVectorStore expects a function (lambda d: …). Other stores use their own filter syntax, so check the store's docs when you switch.
  • Passing an object as the filter. MemoryVectorStore expects a function as the third argument ((d) => …); pnpm typecheck rejects an object there. Other stores use their own filter syntax, so check the store's docs when you switch.
  • Forgetting the brackets around await. await again.similaritySearch(…)[0] takes [0] of the Promise (which is undefined) before waiting. Write (await again.similaritySearch(…))[0], as line 37 does.
