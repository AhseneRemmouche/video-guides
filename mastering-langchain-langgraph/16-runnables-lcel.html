Runnables and LCEL

Take apart the chains: sequences, parallel branches, assign, retries, fallbacks and schemas. Book chapters 17-18.

Lab · code run on a local model (llama3.2 via Ollama)
Read with chapters 17–18 · Runnables and LCEL, Python Typing and Pydantic of the book. The ideas behind this lab are explained in the concept chapter Runnables, LCEL, typing and Pydantic.

Goal

Since lab 03 you have written chains like prompt | model | parser. This lab takes that syntax apart. You will turn plain Python functions into Runnables, connect them with |, run branches side by side, add keys to a dictionary as it flows through, describe the data with a TypedDict, and make a step survive failures with retries and fallbacks. Only one part calls the model; the rest runs instantly. In TypeScript the pipe is the method .pipe(), and the dictionary types are plain TypeScript type declarations that the compiler checks.

The idea in brief

  • A Runnable is anything with the same small interface: invoke (one input), batch (a list of inputs) and stream (output in pieces). Prompts, models, parsers, retrievers and compiled graphs are all Runnables.
  • LCEL (LangChain Expression Language) is the way you combine them: a | b makes a sequence, a dictionary of Runnables runs them in parallel on the same input, and .assign adds new keys while keeping the old ones.
  • Every Runnable gets extra powers for free: with_retry, with_fallbacks, input and output schemas.

In LangChain.js the same interface exists, with async methods (await r.invoke(...)). a | b becomes a.pipe(b) or RunnableSequence.from([a, b]); RunnableParallel becomes RunnableMap.from({...}); RunnableLambda(f) becomes RunnableLambda.from(f); with_retry and with_fallbacks become withRetry and withFallbacks.

The full explanation, including Python typing and Pydantic, is in Runnables, LCEL, typing and Pydantic.

New to arrow functions? Small functions without a name

(text: string) => text.toUpperCase() is an arrow function: it takes text (a string) and returns text.toUpperCase(). It is the same as function f(text: string) { return text.toUpperCase(); }, without the name. Arrow functions are handy for tiny steps in a chain; with curly braces (as in flaky, lines 37–41) they can hold several statements and need an explicit return.

New to lambda? Small functions without a name

lambda text: text.upper() is a function written in one expression: it takes text and returns text.upper(). It is the same as writing def f(text): return text.upper(), without the name. Lambdas are handy for tiny steps in a chain. len (Python's built-in "how long is this?") is already a function, so it can be passed directly, as on line 13.

"""Lab 16: Runnables and LCEL: the pieces every chain in labs 03-07 was made of."""
from typing import TypedDict

from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnableLambda, RunnableParallel, RunnablePassthrough

from harbor.config import get_model
from harbor.knowledge import build_vector_store, format_docs

# 1. Any function becomes a Runnable, with invoke / batch / stream for free.
shout = RunnableLambda(lambda text: text.upper())
count = RunnableLambda(len)
print("1) invoke:", shout.invoke("quiet please"), "| batch:", count.batch(["a", "abc", "hello"]))

# 2. The pipe | feeds one Runnable's output into the next (a RunnableSequence).
chain = shout | count
print("2) sequence:", type(chain).__name__, "->", chain.invoke("library"))

# 3. A dict (RunnableParallel) runs branches on the same input; .assign adds keys and keeps the rest.
stats = RunnableParallel(upper=shout, length=count)
print("3) parallel:", stats.invoke("harbor"))
print("   assign:  ", RunnablePassthrough.assign(words=lambda d: len(d["text"].split())).invoke({"text": "open on Sunday"}))


# 4. Type hints document the shapes that flow through a chain, and help your editor catch mistakes.
class Answer(TypedDict):
    question: str
    context: str
    answer: str


retriever = build_vector_store().as_retriever(search_kwargs={"k": 2})
prompt = ChatPromptTemplate.from_template("Answer in one sentence from this context:\n{context}\n\nQuestion: {question}")
rag = (
    RunnableParallel(context=retriever | format_docs, question=RunnablePassthrough())
    | RunnablePassthrough.assign(answer=prompt | get_model() | StrOutputParser())
)
result: Answer = rag.invoke("How much does 3D printing cost?")
print("\n4) RAG with the context kept:", {k: v[:70] for k, v in result.items()})

# 5. Resilience: retry a flaky step, and fall back to another Runnable if it still fails.
attempts = {"n": 0}


def flaky(text):
    attempts["n"] += 1
    if attempts["n"] < 3:
        raise ConnectionError("temporary network problem")
    return f"ok after {attempts['n']} attempts: {text}"


print("5) with_retry:", RunnableLambda(flaky).with_retry(stop_after_attempt=3, wait_exponential_jitter=False).invoke("ping"))
broken = RunnableLambda(lambda _: 1 / 0)
print("   with_fallbacks:", broken.with_fallbacks([RunnableLambda(lambda _: "fallback answer")]).invoke("x"))

# 6. Every chain can describe its input and output schema.
print("6) input schema of the prompt:", prompt.get_input_jsonschema()["required"])

import { StringOutputParser } from "@langchain/core/output_parsers";
import { ChatPromptTemplate } from "@langchain/core/prompts";
import { RunnableLambda, RunnableMap, RunnablePassthrough, RunnableSequence } from "@langchain/core/runnables";
import { getModel } from "../src/config.js";
import { buildVectorStore, formatDocs } from "../src/knowledge.js";

// 1. Any function becomes a Runnable, with invoke / batch / stream for free.
const shout = RunnableLambda.from((text: string) => text.toUpperCase());
const count = RunnableLambda.from((text: string) => text.length);
console.log("1) invoke:", await shout.invoke("quiet please"), "| batch:", await count.batch(["a", "abc", "hello"]));

// 2. .pipe() feeds one Runnable's output into the next (a RunnableSequence).
const chain = shout.pipe(count);
console.log("2) sequence:", chain.constructor.name, "->", await chain.invoke("library"));

// 3. A RunnableMap runs branches on the same input; RunnablePassthrough.assign adds keys and keeps the rest.
const stats = RunnableMap.from({ upper: shout, length: count });
console.log("3) parallel:", await stats.invoke("harbor"));
console.log("   assign:  ", await RunnablePassthrough.assign({ words: (d: { text: string }) => d.text.split(" ").length })
  .invoke({ text: "open on Sunday" }));

// 4. Types document the shapes that flow through a chain; the compiler checks them for you.
type Answer = { question: string; context: string; answer: string };

const retriever = (await buildVectorStore()).asRetriever({ k: 2 });
const prompt = ChatPromptTemplate.fromTemplate("Answer in one sentence from this context:\n{context}\n\nQuestion: {question}");
const rag = RunnableSequence.from([
  RunnableMap.from({ context: retriever.pipe(RunnableLambda.from(formatDocs)), question: new RunnablePassthrough<string>() }),
  RunnablePassthrough.assign({ answer: prompt.pipe(getModel()).pipe(new StringOutputParser()) }),
]);
const result: Answer = await rag.invoke("How much does 3D printing cost?");
console.log("\n4) RAG with the context kept:", Object.fromEntries(Object.entries(result).map(([k, v]) => [k, v.slice(0, 70)])));

// 5. Resilience: retry a flaky step, and fall back to another Runnable if it still fails.
let attempts = 0;
const flaky = RunnableLambda.from((text: string) => {
  attempts++;
  if (attempts < 3) throw new Error("temporary network problem");
  return `ok after ${attempts} attempts: ${text}`;
});
console.log("5) withRetry:", await flaky.withRetry({ stopAfterAttempt: 3 }).invoke("ping"));
const broken = RunnableLambda.from((): string => { throw new Error("division by zero"); });
console.log("   withFallbacks:", await broken.withFallbacks([RunnableLambda.from(() => "fallback answer")]).invoke("x"));

// 6. Every prompt knows which variables it needs.
console.log("6) input variables of the prompt:", prompt.inputVariables);

Parts 1–3: the building blocks

New to type? Shapes the compiler checks

LCEL chains pass objects around a lot, and a typo in a key (result.contxt) is easy to make. In TypeScript, type Answer = { question: string; context: string; answer: string } names the shape, and writing const result: Answer asks the compiler to check it: pnpm typecheck and your editor underline result.contxt before you run anything. Like Python's TypedDict, it is erased when the code runs, so it does not validate values; a Zod schema does that (lab 02).

New to TypedDict? Types for dictionaries

LCEL chains pass dictionaries around a lot, and a typo in a key ("contxt") only shows up when the code runs. A TypedDict lists the keys a dictionary should have and the type of each value. It changes nothing at runtime (the value is still an ordinary dict), but editors such as VS Code and type checkers such as mypy or pyright read the annotation and underline result["contxt"] before you run anything. Pydantic models (lab 02) go one step further and validate the values at runtime.

Part 4: a RAG chain that keeps its context

The chain in lab 07 returned only the answer string. Here, thanks to RunnableParallel (RunnableMap) and assign, the result keeps the question and the retrieved context next to the answer. That is useful for showing sources to the user, or for checking afterwards whether the answer really came from the context.

Part 5: retries and fallbacks

Real chains call networks and models, and those fail sometimes. with_retry tries the same step again; with_fallbacks switches to another step. Both return a new Runnable, so you can still pipe them into a chain. In TypeScript: withRetry({ stopAfterAttempt: 3 }) and withFallbacks([fallback]).

New to retries? Why the default waits longer each time

When a server is overloaded, hammering it with instant retries makes things worse. That is why with_retry in Python by default waits between attempts, a little longer each time and with some randomness ("exponential backoff with jitter"), so many clients do not retry at the same moment. The lab turns the waiting off only to keep the demo fast. Retry only errors that can go away (network, rate limits); a bug like 1 / 0 fails every time, which is why the lab uses a fallback for it. The TypeScript lab passes only stopAfterAttempt and leaves the other retry settings at their defaults.

Common mistakes.

  • Forgetting await. Every invoke and batch returns a promise; console.log(shout.invoke("x")) prints Promise { <pending> }.
  • Steps that don't fit together. In a sequence, each step receives exactly what the previous one returned. count.pipe(shout) hands a number to a function that calls toUpperCase, which numbers do not have.
  • Losing data in a chain. prompt.pipe(model).pipe(parser) returns only the answer. Use RunnablePassthrough.assign({...}) when later steps (or your app) still need the earlier keys.
  • Expecting a type to validate. const result: Answer is checked by the compiler only; at run time nothing checks the values. Use a Zod schema when values must be checked.
  • Retrying everything. withRetry repeats the step for any error; retrying a real bug just fails three times, slower.
  • Ollama not running. Parts 1–3 work, then part 4 fails with a connection error. Start Ollama and run again.

  2. Too few retries. On line 42, set stopAfterAttempt: 2. The step fails twice and the program stops with the "temporary network problem" error, because the third, successful attempt never happens.
  3. A misspelled key. After line 32, add console.log(result.contxt); and run pnpm typecheck. The compiler reports that contxt does not exist on type Answer: this is what the type on line 24 buys you.
  4. Batch a parallel step. Add console.log(await stats.batch(["a", "harbor"]));. You should get [ { upper: 'A', length: 1 }, { upper: 'HARBOR', length: 6 } ]: composed Runnables have batch too.

  • A TypedDict documents the dictionaries flowing through a chain for your editor; it does not validate at runtime.
  • with_retry repeats a failing step (ours succeeded on attempt 3); with_fallbacks switches to another Runnable.
  • get_input_jsonschema() describes what a Runnable expects; the prompt requires ['context', 'question'].
