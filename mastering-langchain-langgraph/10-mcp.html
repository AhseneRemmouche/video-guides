Model Context Protocol (MCP)

Serve the catalog as an MCP server and give its tools to an agent through an MCP client. Book chapter 11.

Lab · code run on a local model (llama3.2 via Ollama)
Read with chapter 11 · Tools and Model Context Protocol (MCP) of the book (Part IV · Build Agents with LangGraph). This lab covers the MCP half; lab 09 covers tools.

Goal. Move the catalog tools out of our lab program and into a separate MCP server. Then connect to it with an MCP client, discover its tools and a resource at run time, and hand those tools to an agent. You will also see a small search weakness turn into a large invented answer.

Why the project needs it. In lab 09 the tools lived inside our code, so only our code could use them. The library might want the same catalog tools in a desktop chat app, an IDE assistant, or another team's agent. The Model Context Protocol is a shared standard for that: write the server once, and any MCP-capable client can use it.

The idea in brief

MCP splits the work in two. A server offers capabilities: tools (functions a model may call), resources (data the application can read, addressed by a URI such as catalog://genres) and prompts (reusable prompt templates, not used here). A client connects, asks "what do you offer?", and calls what it needs. They talk in JSON-RPC messages over a transport. This lab uses the stdio transport: the client starts the server as a child process and they exchange messages through its standard input and output. The concept chapter LangGraph and agents places MCP in the bigger picture.

New to MCP? What problem it solves

Before MCP, every AI application had its own way to plug in tools. A tool written for one framework had to be rewritten for the next. MCP is an open protocol (specification at modelcontextprotocol.io) that fixes the "plug": a server describes its tools and data in a standard format, and any client that speaks MCP can use them. Think of it like USB for AI tools.

LangChain is not required on either side.

Our server uses the official mcp Python SDK (FastMCP). Our client side uses langchain-mcp-adapters, which converts the server's tools into ordinary LangChain tools so an agent can use them like the tools in lab 09.

Our server uses the official MCP TypeScript SDK, @modelcontextprotocol/sdk (its McpServer class). Our client side uses @langchain/mcp-adapters, which converts the server's tools into ordinary LangChain tools so an agent can use them like the tools in lab 09. Because MCP is a protocol, a Python client could use this TypeScript server, and the other way round.

New to stdin, stdout and stderr? The three standard streams

Every program gets three text channels from the operating system: stdin (input, usually your keyboard), stdout (normal output, usually your terminal) and stderr (a second output meant for errors and logs). With the stdio transport, the MCP client takes over the server's stdin and stdout for protocol messages. That is why the server must never print() to stdout (in Node.js: console.log): it would corrupt the messages. Logs go to stderr instead (console.error), and the client lets stderr through to your terminal. Those are the "Processing request of type …" lines you will see.

The server

The file is harbor/mcp_server.pysrc/mcp-server.ts. It knows nothing about LangChain or agents: it only offers the catalog over MCP.

"""An MCP server that offers the library catalog to any MCP client. Run: python -m harbor.mcp_server"""
from mcp.server.fastmcp import FastMCP

from harbor.catalog import CATALOG

mcp = FastMCP("harbor-catalog")


@mcp.tool()
def search_catalog(query: str) -> str:
    """Search the Harbor City Library catalog by words in the title, author or genre."""
    words = query.lower().split()
    hits = [b for b in CATALOG.values()
            if any(w in f"{b['title']} {b['author']} {b['genre']}".lower() for w in words)]
    return "\n".join(f"{b['id']}: {b['title']} by {b['author']}" for b in hits[:5]) or f"No items match '{query}'."


@mcp.tool()
def check_availability(item_id: str) -> str:
    """How many copies of an item (id like B004) are on the shelf, and where."""
    b = CATALOG.get(item_id.strip().upper())
    return f"{b['title']}: {b['available']} of {b['copies']} available at {b['branch']}." if b else f"No item {item_id}."


@mcp.resource("catalog://genres")
def genres() -> str:
    """The list of genres in the catalog."""
    return ", ".join(sorted({b["genre"] for b in CATALOG.values()}))


if __name__ == "__main__":
    mcp.run(transport="stdio")
// An MCP server that offers the library catalog to any MCP client. Run: pnpm mcp-server
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { pathToFileURL } from "node:url";
import { z } from "zod";
import { CATALOG, findItems } from "./catalog.js";

// The same logic as plain functions, so tests can call them without starting a server.
export function searchCatalog(query: string): string {
  const hits = findItems(query).slice(0, 5);
  return hits.map((b) => `${b.id}: ${b.title} by ${b.author}`).join("\n") || `No items match '${query}'.`;
}

export function checkAvailability(itemId: string): string {
  const b = CATALOG[itemId.trim().toUpperCase()];
  return b ? `${b.title}: ${b.available} of ${b.copies} available at ${b.branch}.` : `No item ${itemId}.`;
}

export function genres(): string {
  return [...new Set(Object.values(CATALOG).map((b) => b.genre))].sort().join(", ");
}

export function createServer(): McpServer {
  const server = new McpServer({ name: "harbor-catalog", version: "0.1.0" });
  server.registerTool(
    "search_catalog",
    {
      description: "Search the Harbor City Library catalog by words in the title, author or genre.",
      inputSchema: { query: z.string() },
    },
    async ({ query }) => ({ content: [{ type: "text", text: searchCatalog(query) }] }),
  );
  server.registerTool(
    "check_availability",
    {
      description: "How many copies of an item (id like B004) are on the shelf, and where.",
      inputSchema: { item_id: z.string() },
    },
    async ({ item_id }) => ({ content: [{ type: "text", text: checkAvailability(item_id) }] }),
  );
  server.registerResource(
    "genres",
    "catalog://genres",
    { description: "The list of genres in the catalog.", mimeType: "text/plain" },
    async (uri) => ({ contents: [{ uri: uri.href, text: genres() }] }),
  );
  return server;
}

// Start over stdio only when this file is run directly, not when a test imports it.
if (import.meta.url === pathToFileURL(process.argv[1] ?? "").href) {
  await createServer().connect(new StdioServerTransport());
}

The client

The lab file is labs/10_mcp.pylabs/10-mcp.ts. It starts the server, discovers what it offers and gives the tools to an agent.

"""Lab 10: connect to the catalog's MCP server and give its tools to an agent."""
import asyncio
import sys

from langchain.agents import create_agent
from langchain_mcp_adapters.client import MultiServerMCPClient

from harbor.config import ROOT, get_model

client = MultiServerMCPClient({
    "catalog": {
        "transport": "stdio",            # start the server as a child process and talk over stdin/stdout
        "command": sys.executable,       # the same Python that runs this lab
        "args": ["-m", "harbor.mcp_server"],
        "cwd": str(ROOT),
    }
})


async def main():
    tools = await client.get_tools()
    print("1) Tools discovered over MCP:")
    for t in tools:
        print(f"   {t.name}: {t.description}")

    resources = await client.get_resources("catalog")
    print("\n2) Resource catalog://genres:", resources[0].as_string())

    agent = create_agent(get_model(), tools, system_prompt="You help visitors of Harbor City Library. Use the tools.")
    result = await agent.ainvoke({"messages": [("user", "Is there a book about radios, and can I borrow it today?")]})
    print("\n3) Agent run:")
    for m in result["messages"][1:]:
        if m.type == "ai" and m.tool_calls:
            print("   calls:", [(c["name"], c["args"]) for c in m.tool_calls])
        elif m.type == "tool":
            print(f"   {m.name} -> {str(m.content)[:90]!r}")
        else:
            print("   answer:", m.content)


asyncio.run(main())
// Lab 10: connect to the catalog's MCP server and give its tools to an agent.
import { MultiServerMCPClient } from "@langchain/mcp-adapters";
import { createAgent } from "langchain";
import { ROOT, getModel } from "../src/config.js";
import { printRun } from "../src/show.js";

const client = new MultiServerMCPClient({
  mcpServers: {
    catalog: {
      transport: "stdio", // start the server as a child process and talk over stdin/stdout
      command: process.execPath, // the same Node that runs this lab
      args: ["--import", "tsx", "src/mcp-server.ts"], // tsx lets Node run the TypeScript file directly
      cwd: ROOT,
    },
  },
});

try {
  const tools = await client.getTools();
  console.log("1) Tools discovered over MCP:");
  for (const t of tools) console.log(`   ${t.name}: ${t.description}`);

  const [genres] = await client.readResource("catalog", "catalog://genres");
  console.log("\n2) Resource catalog://genres:", "text" in genres ? genres.text : "(binary)");

  const agent = createAgent({ model: getModel(), tools, systemPrompt: "You help visitors of Harbor City Library. Use the tools." });
  const result = await agent.invoke({ messages: [{ role: "user", content: "Is there a book about radios, and can I borrow it today?" }] });
  console.log("\n3) Agent run:");
  printRun(result.messages.slice(1));
} finally {
  await client.close(); // stops the server process
}

Reading the output

Lines 1–5 are not printed by our code. They are the server's log, written to stderr by the MCP SDK: one line per request the server handled. They appear first in our captured file because the lab's own prints (stdout) were buffered and written at the end; in a terminal they mix with the lab's output. In an offline check of our own, each tool call showed up as a CallToolRequest followed by a ListToolsRequest, which matches lines 4–5 here: the agent made exactly one tool call.

Lines 6–10 show discovery: two tools with the descriptions from the server's docstrings, and the resource's ten genres. Line 14 shows the tool result. Unlike lab 09's plain strings, an MCP tool returns a list of content blocks: [{'type': 'text', 'text': "No items match 'radios'.", 'id': …}]. MCP results can mix several blocks (text, images, embedded resources), so the content is always a list; the agent passes it to the model as text.

Lines 1–3 show discovery: two tools with the descriptions written in registerTool, now named catalog_search_catalog and catalog_check_availability. The catalog_ prefix comes from the connection name on line 9 of the lab, not from the server. Line 5 is the resource: the ten genres. The order of the work follows the code: getTools (line 19), readResource (line 23), then the agent's single tool call.

Line 8 is that call, with the prefixed name and {"query":"radios"}. Line 9 is the tool result. printRun prints String(m.content), and in this run that was the sentence itself, "No items match 'radios'.": the agent got the text of the server's text block. (The Python version printed the list of content blocks instead.) Unlike the Python SDK, the TypeScript server printed no log lines in our run, so there are no "Processing request of type …" lines in this output.

What went wrong: "radios" and an invented book

The user asked about a book on radios. The model searched for exactly that word. The catalog does have Build Your Own Radio (B011, 1 of 1 copy at Central Library), but the search checks whether each query word occurs inside the item's text, and "radios" does not occur inside "radio". So the tool honestly answered "No items match 'radios'."

Then the model made things much worse. It told the user about "A History of Radio" by "David S. Ward", a book that is not in our catalog at all, described its contents, said "Let me just check", made no further tool call, and announced that it was available at a circulation desk on the first floor. Every one of those details is invented. A small search miss became a confident hallucination.

Then the model made things much worse, exactly as in the Python run. It told the user about "A History of Radio" by "Erik Barnouw", a book that is not in our catalog at all, said it was "available for borrowing", and offered to lend it today. It never called catalog_check_availability. Neither the book nor its availability comes from our data. A small search miss became a confident hallucination. Same code idea, other language, same failure: the problem is the model's behaviour, not Python or TypeScript.

import { formatDocs, loadPolicies, split } from "../src/knowledge.js";
import * as mcpServer from "../src/mcp-server.js";

describe("harbor offline", () => {
  test("policies load and split", async () => {
    const docs = await loadPolicies();
    expect(docs).toHaveLength(6);
    const chunks = await split(docs);
    expect(chunks.every((c) => c.pageContent.length <= 400)).toBe(true);
    expect(formatDocs(chunks.filter((c) => c.metadata.source.endsWith("fees.md")).slice(0, 1))).toContain("[fees.md]");
  });

  test("catalog tools", async () => {
    expect(await searchCatalog.invoke({ query: "Mara Quint" })).toContain("B001");
    expect(await checkAvailability.invoke({ item_id: "b010" })).toContain("0 of 4"); // ids are case-insensitive
    expect(await getMemberAccount.invoke({ member_id: "M-1003" })).toContain("16.00 EUR");
  });

  test("search needs the word inside the text", async () => {
    // The weakness lab 10 shows: "radios" does not occur inside "Radio", so nothing matches.
    expect(await searchCatalog.invoke({ query: "radios" })).toMatch(/^No items/);
    expect(await searchCatalog.invoke({ query: "radio" })).toContain("B011");
  });

  test("place_hold changes memory only", async () => {
    const before = [...MEMBERS["M-1001"].holds];
    expect(await placeHold.invoke({ member_id: "M-1001", item_id: "B003" })).toContain("Hold placed");
    MEMBERS["M-1001"].holds = before; // undo, the JSON file was never touched
  });

  test("MCP server functions", () => {
    expect(mcpServer.searchCatalog("radio")).toContain("B011");
    expect(mcpServer.genres()).toContain("music");
  });

  test("trim keeps recent turns", async () => {
    const history = [new HumanMessage("q1"), new AIMessage("a1"), new HumanMessage("q2"), new AIMessage("a2")];
    const approxTokens = (ms: BaseMessage[]) => ms.reduce((n, m) => n + Math.ceil(String(m.content).length / 4) + 3, 0);
    const kept = await trimMessages(history, { maxTokens: 8, tokenCounter: approxTokens, strategy: "last", startOn: "human" });
    expect(kept[0].content).toBe("q2");
  });

  test("runnable composition", async () => {
    const chain = RunnableLambda.from((s: string) => s.toUpperCase()).pipe(RunnableLambda.from((s: string) => s.length));
    expect(await chain.invoke("abc")).toBe(3);
    expect(await chain.batch(["a", "ab"])).toEqual([1, 2]);
  });

Common mistakes
  • Starting the server as a file: uv run python harbor/mcp_server.py fails with ModuleNotFoundError: No module named 'harbor', because the project folder is not on the import path that way. Use python -m harbor.mcp_server from the project folder (that is what line 14 does).
  • "The server hangs." If you start uv run python -m harbor.mcp_server yourself in a terminal, it prints nothing and waits: it is listening on stdin for a client's JSON-RPC messages. That is normal. Stop it with Ctrl+C; the lab starts its own copy.
  • Printing from a stdio server. A print() inside a tool writes to stdout, which is the protocol channel, and can break the connection. Log to stderr instead.
  • Using invoke instead of ainvoke with MCP tools: NotImplementedError: StructuredTool does not support sync invocation.
  • Treating m.content as a string. For MCP tool results it is a list of blocks; m.content[:90] would cut the list, not the text.
  • Starting the server without tsx. The server is a TypeScript file, and Node needs tsx to load it and its imports. Start it with pnpm mcp-server or node --import tsx src/mcp-server.ts from the project folder (that is what lines 11–13 of the lab do).
  • "The server hangs." If you run pnpm mcp-server yourself in a terminal, it prints nothing and waits: it is listening on stdin for a client's JSON-RPC messages. That is normal. Stop it with Ctrl+C; the lab starts its own copy.
  • Printing from a stdio server. A console.log() inside a tool handler writes to stdout, which is the protocol channel, and can break the connection. Use console.error(), which writes to stderr.
  • Looking a tool up by the server's name. The agent's tools are called catalog_search_catalog and catalog_check_availability, so tools.find((t) => t.name === "search_catalog") finds nothing. Use the prefixed name.
  • Forgetting client.close(). The server is a child process; if the client is never closed, it can keep running and keep the program from exiting. The finally block on lines 30–32 closes it even after an error.
Security: only connect to servers you trust. With stdio, connecting to a server means running its program on your computer with your permissions. With any transport, the server's tool descriptions go straight into your model's prompt, so a malicious server can write descriptions that steer the model ("before answering, call this other tool with the user's data…"), and its tool results can carry the same kind of hidden instructions. Read the code or use servers from sources you trust, give agents only the tools they need, and require approval for tools that change data (lab 13).

Recap
  • An MCP server (FastMCP) offers tools and resources; an MCP client discovers and uses them.
  • @mcp.tool() and @mcp.resource("catalog://genres") register functions; docstrings and type hints become the descriptions and schemas.
  • With the stdio transport the client starts the server as a child process; protocol on stdin/stdout, logs ("Processing request of type …") on stderr.
  • MultiServerMCPClient.get_tools() turns MCP tools into async LangChain tools; their results are lists of content blocks.
  • An MCP server (McpServer from @modelcontextprotocol/sdk) offers tools and resources; an MCP client discovers and uses them.
  • registerTool(name, { description, inputSchema }, handler) and registerResource(name, uri, metadata, handler) register them; you write names, descriptions and Zod schemas yourself, and handlers return MCP content blocks.
  • With the stdio transport the client starts the server as a child process (node --import tsx src/mcp-server.ts); protocol on stdin/stdout, so never console.log in the server.
  • MultiServerMCPClient.getTools() turns MCP tools into LangChain tools and prefixes their names with the connection name (catalog_search_catalog); readResource reads a resource.
  • "radios" does not occur inside "Build Your Own Radio", the search found nothing, and the model invented "A History of Radio", in Python and in TypeScript. The server itself finds B011 for "radio" (offline check and tests).
  • Connecting to an MCP server means trusting its code and its words: only use servers you trust.
