Agents with LangGraph

State graphs, tools and MCP, checkpoints, memory, human-in-the-loop, time travel and streaming. Read with book Part IV (chapters 10-14).

Read with Part IV · Build Agents with LangGraph (chapters 10–14) of the book. This page explains the ideas in its own words and links them to the labs.

A RAG chain is a straight line: retrieve, prompt, answer. Many useful assistants are not straight lines. They branch ("is this even a library question?"), loop ("call a tool, look at the result, maybe call another"), remember earlier turns, and sometimes stop to wait for a person. LangGraph is LangChain's library for exactly that: you describe your program as a graph of steps that share a piece of state, and LangGraph runs it, saves it after every step, and lets you pause, resume, rewind and stream it.

Why this matters for your project. Labs 08 to 13 turn the library's RAG chain into a graph, give the model tools to search the catalog and read member accounts, serve those tools over MCP, add conversation memory, and make a librarian approve every hold. Every real failure in those labs (an invented availability, a member's data shown to someone else, a replay that answered nothing) comes from one of the ideas below. Understanding them is how you predict and prevent such bugs.

Graphs: state, nodes and edges

A LangGraph program has three ingredients.

  • State: a dictionary that every step can read, usually described with a TypedDict so you (and your editor) know which keys exist. In lab 08 it has question, route, docs and answer.
  • Nodes: ordinary Python functions. Each receives the current state and returns a dictionary with only the keys it wants to change. Lab 08's retrieve returns {"docs": …} and touches nothing else.
  • Edges: which node runs next. A normal edge always goes to the same place. A conditional edge calls a small routing function that looks at the state and returns the name of the next node.

Two special names mark the boundaries: START (where input enters) and END (where the run stops). You add everything to a StateGraph builder, then call compile(), which checks the wiring (for example, that every edge points to a real node) and returns a runnable graph with invoke, stream and friends.

Lab 08 also printed the compiled graph as Mermaid text with graph.get_graph().draw_mermaid(). You can paste that text into any Mermaid viewer to see the picture; it is the quickest way to check that the graph you built is the graph you meant. In its output, normal edges are --> and conditional ones -.->, for example classify -.-> retrieve;.

New to graphs? Boxes and arrows, nothing more

In computing, a graph is a set of boxes (nodes) joined by arrows (edges). A flowchart is a graph. What makes LangGraph's graphs useful for agents is that arrows may point backwards, forming a loop, and that the path can depend on the data. A plain chain cannot loop; a graph can, as many times as the routing function says.

Reducers: how updates are merged into state

When a node returns {"answer": "…"}, LangGraph must merge it into the state. By default it simply replaces the old value. That is right for answer, but wrong for a conversation: if each node replaced the message list, every reply would erase the history. A reducer is a function attached to one key that decides how an update combines with the current value. You attach it with Annotated:

import operator
from typing import Annotated, TypedDict

from langgraph.graph import END, START, StateGraph


class State(TypedDict):
    question: str                               # no reducer: a new value replaces the old one
    notes: Annotated[list[str], operator.add]   # reducer: lists are concatenated


def a(state: State):
    return {"question": "B", "notes": ["from a"]}


builder = StateGraph(State)
builder.add_node("a", a)
builder.add_edge(START, "a")
builder.add_edge("a", END)
print(builder.compile().invoke({"question": "A", "notes": ["start"]}))
# {'question': 'B', 'notes': ['start', 'from a']}

For chat messages LangGraph provides add_messages, and the ready-made MessagesState (used from lab 09 on) is just a state with one key, messages, annotated with it. It is smarter than operator.add: a message with a new id is appended, but a message whose id matches one already in the list replaces it. That second rule is easy to forget, and lab 13 tripped over it (see "Time travel" below).

from langchain_core.messages import HumanMessage
from langgraph.graph.message import add_messages

old = [HumanMessage("Hold B003", id="1")]
print(len(add_messages(old, [HumanMessage("Is B006 available?")])))              # 2: appended
print(add_messages(old, [HumanMessage("Is B006 available?", id="1")])[0].content)  # replaced

Tools and the agent loop

A tool is a Python function the model may ask you to run. With LangChain's @tool decorator, the function's name becomes the tool name, its docstring becomes the description, and its type hints become a JSON schema for the arguments. Those three things are all the model ever sees of your tool, so they are part of your prompt.

@tool
def check_availability(item_id: str) -> str:
    """Tell how many copies of an item (id like B004) are on the shelf, and at which branch."""
    b = CATALOG.get(item_id.strip().upper())
    if not b:
        return f"There is no item {item_id}."
    return f"{b['title']}: {b['available']} of {b['copies']} copies available at {b['branch']}."

Lab 09 printed what the model receives for this tool: the name, the docstring, and the argument schema {'item_id': {'title': 'Item Id', 'type': 'string'}}. Note the example id "B004" in the docstring: it helps the model format ids, and later labs show it can also be copied blindly.

Tool calling works in four moves:

  1. model.bind_tools(tools) sends the tool schemas along with every request. The model still runs no code.
  2. The model replies with an AI message whose tool_calls list says what it wants, for example [{'name': 'check_availability', 'args': {'item_id': 'B004'}, 'id': '…', 'type': 'tool_call'}] (lab 09).
  3. Your code runs the function with those arguments and wraps the result in a ToolMessage carrying the same call id ("The Quiet Engine: 1 of 2 copies available at Central Library.").
  4. You send the conversation back to the model, which either asks for another tool or writes the answer.

Repeating moves 2 to 4 until the model stops asking is the agent loop, and a model running in such a loop is what people call an agent. LangGraph ships the two pieces you need: ToolNode, a node that executes every tool call in the last AI message and appends the results, and tools_condition, a routing function that goes to "tools" if the last message has tool calls and to END otherwise. The project's reusable agent is just this:

def build_builder(tools=READ_TOOLS):
    model = get_model().bind_tools(tools)

    def call_model(state: MessagesState):
        return {"messages": [model.invoke([SYSTEM] + state["messages"])]}

    builder = StateGraph(MessagesState)
    builder.add_node("model", call_model)
    builder.add_node("tools", ToolNode(tools))
    builder.add_edge(START, "model")
    builder.add_conditional_edges("model", tools_condition)
    builder.add_edge("tools", "model")
    return builder
An agent can skip the tool and still sound sure. Asked "Do you have any books by Mara Quint? Is one available?", lab 09's agent called search_catalog, found two titles, and answered that both are "available" without ever calling check_availability. One of them has no copy on the shelf. Nothing in the loop forces a tool call; the model decides. Small models do this more often. Defences: tool descriptions that say when to use them, a system prompt that forbids guessing stock, tests that check which tools were called, and, for critical facts, putting the check in your own code instead of the model's hands.

MCP: tools served by another program

Defining tools inside your app works until you want to reuse them in another app, or use tools somebody else wrote. The Model Context Protocol (MCP) is an open standard for that: an MCP server offers capabilities, and any MCP client can discover and use them, whatever language or framework each side uses. The application that hosts the model (here, our Python lab) creates one client connection per server.

A server can offer three kinds of things:

PrimitiveWhat it isWho usually decides to use itIn the lab
ToolsFunctions with a schema that do something or look something upThe model, through tool callssearch_catalog, check_availability
ResourcesRead-only data addressed by a URIThe applicationcatalog://genres
PromptsReusable prompt templates with argumentsThe user, for example from a menunone

Messages travel over a transport. With stdio, the client starts the server as a child process and they talk through its standard input and output; nothing listens on the network, which makes it the simple, private choice for local tools. With Streamable HTTP, the server is a web service (one endpoint, by default /mcp in the Python SDK's FastMCP) that many clients can reach, possibly with authentication. An older HTTP + SSE transport still exists but the current specification replaces it with Streamable HTTP.

Lab 10 starts harbor/mcp_server.py over stdio with MultiServerMCPClient from langchain-mcp-adapters, lists its tools and its resource, and hands the tools to an agent. Three things in its output are worth knowing about. The server's log lines ("Processing request of type ListToolsRequest") appear on stderr, which is fine for stdio because only stdout carries protocol messages; the reverse would be a bug, since printing to stdout from a stdio server corrupts the stream. Tool results come back as MCP content blocks ([{'type': 'text', 'text': "No items match 'radios'.", …}]), not a plain string. And the agent, faced with "No items match 'radios'" (the search looks for each query word inside titles, authors and genres, and "radios" does not occur in "Build Your Own Radio"), invented a book called "A History of Radio" and said it was available. MCP moves tools around; it does nothing about a model ignoring their results.

Connecting over HTTP instead only changes the connection settings. The values below match the installed packages (mcp 1.30.0, langchain-mcp-adapters 0.3.2), but the labs do not run this variant:

# server side, instead of mcp.run(transport="stdio"):
mcp.run(transport="streamable-http")          # serves http://127.0.0.1:8000/mcp by default

# client side
client = MultiServerMCPClient({
    "catalog": {"transport": "streamable_http", "url": "http://127.0.0.1:8000/mcp"},
})
Third-party MCP servers are code you run. A stdio server is a program on your machine with your user's permissions; an HTTP server sees whatever your agent sends it. Tool names and descriptions from a server go straight into the model's prompt, so a malicious or careless server can steer your agent (prompt injection) or ask it for data it should not send. Before connecting one: read its source or use one from a publisher you trust, pin its version, give it the least access it needs (separate credentials, read-only where possible), and require human approval for tools that change things or send data out. The official MCP security best practices page (linked below) goes deeper.

Checkpointers: threads and saved state

Without help, a compiled graph forgets everything between calls. In lab 11, two separate invoke calls without one cannot see each other. (The second call still answered "M-1001", but only because the model copied the example id from the tool's description, the bug described below.) A checkpointer fixes this by saving the full state after every step of the graph. Each save is a checkpoint. Checkpoints are grouped by thread, a conversation id you pass in the config:

def ask(graph, thread, text):
    config = {"configurable": {"thread_id": thread}}
    before = len(graph.get_state(config).values.get("messages", []))
    print(f"   [{thread}] {text}   ({before} earlier messages loaded)")
    show(graph.invoke({"messages": [("user", text)]}, config), before)

When you invoke with a thread_id, LangGraph loads that thread's latest checkpoint, applies your new input through the reducers (so the user message is appended to the history), and runs. Two methods let you look inside: get_state(config) returns the latest snapshot (its values, and next, the nodes that would run next), and get_state_history(config) lists every checkpoint of the thread, newest first. After two turns, lab 11's thread "lea" held 8 messages in 10 checkpoints: one per step, including the model and tool steps, not one per question.

CheckpointerSurvives a restart?Use for
InMemorySaverNoLearning, tests, notebooks
SqliteSaverYes, in a local fileSingle-process apps, demos, local tools
PostgresSaverYes, in a databaseProduction with several workers

InMemorySaver ships with langgraph; the others are separate packages, langgraph-checkpoint-sqlite (installed for the labs) and langgraph-checkpoint-postgres. All of them save the same checkpoints, so switching is a one-line change at compile time.

Lab 11 closed the SQLite connection, opened a fresh one as if the program had restarted, and the thread "ines" continued with "4 earlier messages loaded". Persistence worked. The answer did not: asked "Which genre do I like?", llama3.2 searched the catalog for the word "genre" instead of reading its own history. A checkpointer guarantees the history is there; it cannot make the model use it.

The privacy bug: identity must come from the app

Lab 11 contains a bug on purpose. In thread "sam", a different visitor asks "What is my member id?". The model has no idea who is asking, so it called get_member_account('M-1001'), copying the example id from the tool's own description, and answered "Your member ID is M-1001, Lea Martin." It revealed one member's account to someone else. The root cause is a design mistake, not a model mistake: the model was allowed to choose whose data to read. Anything the model writes into a tool argument can be guessed, copied or manipulated by the user.

The fix is to remove member_id from the tool's arguments and give the tool the logged-in member from your application (a session, a token), outside the model's reach. Lab 14 does this with runtime context; the next concept chapter explains it. The same rule applies to thread ids: derive them from the authenticated user, never from something the visitor typed, or one person can load another's conversation.

Memory: short-term and long-term

Short-term memory is the conversation inside one thread, kept by the checkpointer. Its problem is growth: every turn adds messages, and eventually the history no longer fits the context window, or simply makes each call slow and distracting. Two common remedies:

  • Trimming: send only the most recent part. Lab 12's trim_messages call cut 12 messages to 2 with a tiny 40-token budget, keeping the last question and answer. Options such as start_on="human" make sure the kept part starts at a user message, because a history that starts with an orphan tool result confuses models. Trimming before the model call leaves the saved state untouched.
  • Summarizing: ask the model to summarize older turns into one message, then delete those turns from the state. Deletion uses the reducer again: return RemoveMessage objects with the ids to drop.
from langchain_core.messages import RemoveMessage
from langgraph.graph import MessagesState


def forget_old(state: MessagesState):
    # add_messages treats RemoveMessage(id=...) as "delete the message with this id"
    return {"messages": [RemoveMessage(id=m.id) for m in state["messages"][:-6]]}

Long-term memory is information that should outlive a single thread: a member's preferences, facts learned last week. LangGraph keeps it in a store, separate from the checkpointer. A store saves JSON values under a key inside a namespace, a tuple that works like a folder path. Compile the graph with store=... and any node that declares a store parameter receives it:

def call_model(state: MessagesState, config, *, store: BaseStore):
    member = config["configurable"]["member_id"]
    namespace = ("members", member, "preferences")
    last = state["messages"][-1].content
    if last.lower().startswith("remember"):  # a deliberately simple rule for what to save
        store.put(namespace, f"note-{len(store.search(namespace))}", {"text": last})

In lab 12 the "friday" thread had never seen the "monday" conversation, yet it suggested the large-print section, because the note came in through the system prompt. Two design choices deserve attention. First, the namespace contains the member id from the config, so the privacy rule above applies: it must come from the app. Second, the "what to save" rule is deliberately naive (messages starting with "remember"); real systems let the model call a "save memory" tool or extract facts after each conversation, and then must deal with outdated or wrong memories. Stores can also search by meaning if you create them with an embedding index, for example InMemoryStore(index={"embed": embeddings, "dims": 768}) and then store.search(namespace, query="print size").

Human in the loop

Some actions should not happen just because a model asked. Placing a hold changes a member's account, so lab 13 pauses before it. Human in the loop in LangGraph rests on one function, interrupt(), and on the checkpointer (it is required, because the paused run must be saved somewhere).

def approve(state: MessagesState):
    """Pause before any place_hold call and ask a librarian. Other tools run without asking."""
    last = state["messages"][-1]
    holds = [c for c in last.tool_calls if c["name"] == "place_hold"]
    if holds:
        decision = interrupt({"question": "Approve this hold?", "calls": holds})
        if decision != "yes":
            refused = AIMessage("A librarian did not approve this hold, so I did not place it.")
            return Command(goto=END, update={"messages": [refused]})
    return Command(goto="tools")

When interrupt(value) runs, the graph stops, saves a checkpoint, and invoke returns with an __interrupt__ entry carrying value, so your app can show the librarian what is pending (lab 13 printed the place_hold call and next node: ('approve',)). Later, possibly in another process, you call graph.invoke(Command(resume="yes"), config) with the same thread. The node runs again from its first line, and this time interrupt() returns "yes" instead of pausing. The node also returns a Command, which updates state and chooses the next node in one go, so no separate conditional edge is needed. In the lab, "yes" placed the hold and "no" produced the refusal message.

Because the node restarts from its first line, any code before interrupt() runs twice. Keep side effects (writing to a database, sending an email) after the interrupt, or in a separate node.

Time travel: rewinding and forking

Since every step is saved, you can go back. Time travel means picking an earlier checkpoint from get_state_history and either replaying from it (graph.invoke(None, checkpoint_config)) or first changing it with update_state, which creates a fork: a new checkpoint branching off the old one, while the original history stays intact. It is the tool for "what if the user had asked something else here?" and for debugging a bad run step by step.

Lab 13's thread "hold-1" had 6 checkpoints, steps −1 to 4. The lab took step 0 (the user's message, next node model), replaced that message with "Is item B006 available?", and replayed. The forked run answered with B006's availability, and the thread then had 11 checkpoints because the old branch was kept. The first attempt failed: the edited message had no id, so add_messages appended it after the original hold request. The model saw both, asked for the hold again, hit the approval interrupt, and the replay ended without an answer. Reusing the original message's id made the reducer replace it:

first_input = next(s for s in history if s.next == ("model",) and len(s.values["messages"]) == 1)
original = first_input.values["messages"][0]
# Reusing the message id REPLACES that message; a message without its id would be appended instead.
edited = HumanMessage("I'm member M-1002. Is item B006 available?", id=original.id)
fork = graph.update_state(first_input.config, {"messages": [edited]})
replayed = graph.invoke(None, fork)

Streaming: watching a graph work

Streaming means receiving results while the graph is still running. graph.stream(input, config, stream_mode=...) yields pieces as they become available, and the mode decides what a piece is (lab 08 printed updates such as [classify] {'route': 'library'}; lab 13 streamed tokens and kept those whose metadata says langgraph_node == "model"):

ModeEach item isGood forIn the labs
valuesThe full state after each stepSimple UIs that redraw everythingnone
updatesOnly what each node returned, keyed by node nameProgress views, debuggingLab 08
messages(token, metadata) pairs from model calls inside nodesTyping effect in chat UIsLab 13
customAnything your node sends with a stream writerYour own progress messagesnone

The installed version also offers "checkpoints", "tasks" and "debug" for low-level inspection. You can pass a list of modes; each item then comes as a (mode, data) pair:

from langgraph.config import get_stream_writer


def retrieve(state):
    writer = get_stream_writer()
    writer({"progress": "searching the policies"})   # arrives in the "custom" stream
    ...


for mode, data in graph.stream(inputs, stream_mode=["updates", "custom"]):
    print(mode, data)

Note that "messages" mode streams tokens even though the node calls model.invoke, not model.stream: LangGraph hooks into the model's callbacks. That is why lab 13 could print the maker-space answer word by word with no change to call_model. When a graph has several model calls (a router and a writer, say), the metadata tells you which node a token came from, so filter on it.

Everything on this page also exists in a prebuilt form: create_agent, used in lab 10 and explained in LangChain agents and middleware, builds the same model-and-tools loop for you. Knowing the graph underneath is what lets you debug it. For a video introduction to the same ideas, see the companion guide LangGraph crash course.

Common misconceptions and pitfalls
  • "The agent checked." Read the tool calls, not the answer. Lab 09 claimed availability without calling the availability tool; lab 10 invented a book after an empty search.
  • Letting the model pick identities. Member ids, thread ids and namespaces must come from your app's login, never from a tool argument the model fills (lab 11).
  • Forgetting the reducer. A message list without add_messages is overwritten each step; an edited message without its id is appended instead of replaced (lab 13).
  • Expecting memory without a checkpointer or thread id. No checkpointer, no history; a new thread_id, a blank conversation.
  • Assuming a saved history is a used history. SQLite restored 4 messages in lab 11; the model still answered as if it had not read them.
  • Side effects before interrupt(). The node reruns from the top on resume.
  • Trusting any MCP server. Its tool descriptions enter your prompt and its code runs with your permissions.
  • Printing to stdout in a stdio MCP server. Log to stderr; stdout is the protocol channel.
Recap
  • A LangGraph program is state plus nodes plus edges; conditional edges route with a function; START and END mark the boundaries; compile() checks and builds it, and draw_mermaid() shows it.
  • Reducers decide how updates merge: replace by default, append with operator.add, and append or replace-by-id with add_messages.
  • Tools get their schema from name, docstring and type hints; bind_tools lets the model request them; ToolNode runs them; tools_condition closes the agent loop.
  • MCP lets separate programs serve tools, resources and prompts over stdio or Streamable HTTP; treat third-party servers as untrusted code.
  • Checkpointers save state after every step, per thread; get_state and get_state_history let you inspect it; identity must come from the app.
  • Short-term memory is the thread's messages (trim or summarize them); long-term memory lives in a store under namespaces shared across threads.
  • interrupt() and Command(resume=...) add human approval; forking a checkpoint is time travel; stream modes values, updates, messages and custom show a run as it happens.
