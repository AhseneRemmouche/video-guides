LangChain agents with create_agent

Build the agent in a few lines, pass the logged-in user as context, and ask for a typed result. Book chapter 15.

Lab · code run on a local model (llama3.2 via Ollama)
Read with chapter 15 · Fundamentals of LangChain Agents of the book. The ideas behind this lab are explained in the concept chapter LangChain agents and middleware.

Goal

In labs 09 to 13 you wrote the agent loop by hand as a LangGraph graph. In this lab you build the same agent with one function call, create_agent, and you fix the privacy bug from lab 11: the model will no longer choose whose account it reads. You will also ask the agent for a typed final answer (a Pydantic object) and see, with two different local models, how reliable that is. In TypeScript the function is createAgent and the typed answer is described with a Zod schema instead of a Pydantic class; we ran the TypeScript version with llama3.2 only.

The idea in brief

  • create_agent builds the loop for you. You give it a model, a list of tools and a system prompt. It returns a compiled LangGraph graph with a model node and a tools node, exactly the loop you wrote by hand.
  • Identity comes from the app, not from the model. The logged-in member is passed as runtime context. A tool reads it through ToolRuntime. The model never sees a member_id argument, so it cannot type someone else's id.
  • response_format asks for a typed final answer. Two strategies exist: ToolStrategy (the schema becomes an extra tool the model must call) and ProviderStrategy (the model provider forces JSON output). With our small local models neither gave a trustworthy object, and you will see exactly why.

The same ideas in LangChain.js. createAgent({ model, tools, systemPrompt }) comes from the langchain package. Its model node is called model_request (Python: model). The context type is a Zod schema given as contextSchema, and the context itself travels in the config object: { configurable: {...}, context: {...} }. A tool reads it from its second argument, a ToolRuntime. The two strategies are the functions toolStrategy() and providerStrategy(), passed as responseFormat.

The full explanation, with more background, is in LangChain agents and middleware.

New to runtime context? Why the model must not choose the member id

A model only produces text. When it "calls a tool", it writes the tool's name and the argument values it thinks are right. If a tool has an argument member_id, the model fills it in, and it can fill in anything: a guess, an id from an example, an id another user typed. In lab 11 llama3.2 copied M-1001 from the tool's description and showed Lea Martin's account to a different visitor.

The fix is a rule you will meet in every real application: facts the application already knows for sure (who is logged in, which shop, which language) are passed by your code, not asked from the model. LangChain calls this "context". Your code passes it on every invoke, and tools read it. The model does not even know the value exists.

"""Lab 14: the same agent in a few lines with create_agent, plus a typed final answer and per-user context."""
from dataclasses import dataclass

from langchain.agents import create_agent
from langchain.agents.structured_output import ProviderStrategy, ToolStrategy
from langchain.tools import ToolRuntime, tool
from langgraph.checkpoint.memory import InMemorySaver
from pydantic import BaseModel

from harbor.catalog import MEMBERS, check_availability, search_catalog
from harbor.config import get_model


@dataclass
class Visitor:
    member_id: str  # set by the application after login, never by the model


@tool
def my_account(runtime: ToolRuntime[Visitor]) -> str:
    """Show the logged-in member's own loans, holds and fees."""
    m = MEMBERS[runtime.context.member_id]  # the id comes from the app's context, so no one can ask for another member
    return f"{m['name']}: loans {m['loans']}, holds {m['holds']}, fees {m['fees_eur']:.2f} EUR"


agent = create_agent(
    model=get_model(),
    tools=[search_catalog, check_availability, my_account],
    system_prompt="You are Harbor City Library's assistant. Use the tools. Answer briefly.",
    context_schema=Visitor,
    checkpointer=InMemorySaver(),
)

print("1) Graph nodes create_agent built:", list(agent.get_graph().nodes))

config = {"configurable": {"thread_id": "sam"}}
for text in ["What do I owe, and what do I have on loan?", "Is The Little Crab Who Could on the shelf?"]:
    result = agent.invoke({"messages": [("user", text)]}, config, context=Visitor(member_id="M-1002"))
    calls = [(c["name"], c["args"]) for m in result["messages"] if m.type == "ai" for c in m.tool_calls]
    print(f"\n2) Q: {text}\n   tools: {calls[-2:]}\n   A: {result['messages'][-1].content}")


# 3. response_format: the agent's last step returns a validated object instead of free text.
class Availability(BaseModel):
    title: str
    copies_available: int
    branch: str


print("\n3) response_format, two strategies:")
for label, strategy in [("ToolStrategy", ToolStrategy(Availability)), ("ProviderStrategy", ProviderStrategy(Availability))]:
    typed = create_agent(get_model(), [search_catalog, check_availability], response_format=strategy,
                         system_prompt="Find the item with search_catalog, then check_availability.")
    result = typed.invoke({"messages": [("user", "Is 'Build Your Own Radio' available?")]})
    used = [c["name"] for m in result["messages"] if m.type == "ai" for c in m.tool_calls]
    print(f"   {label:<17} tools called: {used}\n   {'':<17} structured_response: {result.get('structured_response')!r}")
// Lab 14: the same agent in a few lines with createAgent, plus a typed final answer and per-user context.
import type { ToolRuntime } from "@langchain/core/tools";
import { MemorySaver } from "@langchain/langgraph";
import { createAgent, providerStrategy, tool, toolStrategy } from "langchain";
import { z } from "zod";
import { MEMBERS, checkAvailability, searchCatalog } from "../src/catalog.js";
import { getModel } from "../src/config.js";
import { toolCalls } from "../src/show.js";

const Visitor = z.object({
  member_id: z.string(), // set by the application after login, never by the model
});

const myAccount = tool(
  (_input, runtime: ToolRuntime<unknown, z.infer<typeof Visitor>>) => {
    const m = MEMBERS[runtime.context.member_id]; // the id comes from the app's context, so no one can ask for another member
    return `${m.name}: loans ${JSON.stringify(m.loans)}, holds ${JSON.stringify(m.holds)}, fees ${m.fees_eur.toFixed(2)} EUR`;
  },
  {
    name: "my_account",
    description: "Show the logged-in member's own loans, holds and fees.",
    schema: z.object({}),
  },
);

const agent = createAgent({
  model: getModel(),
  tools: [searchCatalog, checkAvailability, myAccount],
  systemPrompt: "You are Harbor City Library's assistant. Use the tools. Answer briefly.",
  contextSchema: Visitor,
  checkpointer: new MemorySaver(),
});

console.log("1) Graph nodes createAgent built:", Object.keys((await agent.graph.getGraphAsync()).nodes));

const config = { configurable: { thread_id: "sam" }, context: { member_id: "M-1002" } };
for (const text of ["What do I owe, and what do I have on loan?", "Is The Little Crab Who Could on the shelf?"]) {
  const result = await agent.invoke({ messages: [{ role: "user", content: text }] }, config);
  console.log(`\n2) Q: ${text}\n   tools: ${JSON.stringify(toolCalls(result.messages).slice(-2))}\n   A: ${result.messages.at(-1)?.content}`);
}

// 3. responseFormat: the agent's last step returns a validated object instead of free text.
const Availability = z.object({
  title: z.string(),
  copies_available: z.number().int(),
  branch: z.string(),
});

console.log("\n3) responseFormat, two strategies:");
const typedAgents = {
  toolStrategy: createAgent({
    model: getModel(),
    tools: [searchCatalog, checkAvailability],
    responseFormat: toolStrategy(Availability), // the answer is one more "tool" the model must call
    systemPrompt: "Find the item with search_catalog, then check_availability.",
  }),
  providerStrategy: createAgent({
    model: getModel(),
    tools: [searchCatalog, checkAvailability],
    responseFormat: providerStrategy(Availability), // the provider's own JSON-schema mode shapes the answer
    systemPrompt: "Find the item with search_catalog, then check_availability.",
  }),
};
for (const [label, typed] of Object.entries(typedAgents)) {
  try {
    const result = await typed.invoke({ messages: [{ role: "user", content: "Is 'Build Your Own Radio' available?" }] });
    const used = toolCalls(result.messages).map(([name]) => name);
    console.log(`   ${label.padEnd(17)} tools called: ${JSON.stringify(used)}\n   ${"".padEnd(17)} structuredResponse:`, result.structuredResponse);
  } catch (error) {
    console.log(`   ${label.padEnd(17)} failed: ${(error as Error).message.slice(0, 160)}`);
  }
}

New to Zod? Why the context is a Zod schema

Zod describes the shape of data in a way that still exists while the program runs (TypeScript types vanish when the code runs). z.object({ member_id: z.string() }) is such a description. LangChain.js uses it for the context (contextSchema), for tool arguments (schema) and for typed answers (responseFormat), and z.infer<typeof Visitor> gives you the matching TypeScript type for free, so you write the shape only once.

New to dataclasses? What @dataclass does

@dataclass is a decorator from Python's standard library. You list fields with their type hints and Python writes the boring parts for you: an __init__ that takes those fields, a readable repr and an equality check. So Visitor(member_id="M-1002") works without you writing a constructor. Unlike Pydantic, a dataclass does not validate types at runtime; here that is fine, because your own code creates it, not the model.

Part 3: a typed final answer with response_format

Sometimes your code needs the agent's answer as data, not as a sentence: for example to show the number of copies in a web page. response_format asks create_agent to end with a validated object, stored in result["structured_response"] (in TypeScript: responseFormat and result.structuredResponse). There are two strategies, and the lab tries both on the question "Is 'Build Your Own Radio' available?" (truth: 1 of 1 copies at the Central Library).

New to structured output? A quick reminder

Structured output means asking the model for data that follows a schema (a JSON Schema generated from your Pydantic class) instead of free text. In lab 02 you did this for a single model call with with_structured_output. The lesson there still applies: a schema controls the shape of the answer, not whether the values are true.

  • ToolStrategy(Availability) adds the schema to the model as one more tool. The model can call the real tools first; to finish, it must "call" the Availability tool with the final values, and LangChain validates them.
  • ProviderStrategy(Availability) uses the provider's own structured-output feature. For Ollama, langchain-ollama turns it into the JSON schema sent in the request's format field, so the model is forced to answer with JSON in that shape.

With ToolStrategy, both models used the real tools (gemma4 in the right order) but finished with plain text instead of calling the Availability tool, so there was no typed object. With ProviderStrategy, both models answered with valid JSON immediately and called no tools at all, so the values came from nowhere: llama3.2 even put "Function call" as the title, and gemma4 got the title right only because it was in the question. There is no "Main Branch" in Harbor City. Pydantic accepted both objects because the types were right. Lesson: with these local models, typed final answers from an agent were not reliable, and ProviderStrategy skipped the tools entirely.

A more robust pattern to try

A common way around this is to split the job in two. Let the agent do what it is good at (call tools and answer in text), then make a separate, single model call with with_structured_output(Availability) whose only job is to copy facts from the agent's messages into the schema. The second call has no tools to juggle, and it reads the tool results directly. We did not run this pattern in the lab, so treat the sketch below as a starting point and check its output yourself. The sketch is in Python; in TypeScript the same idea is getModel().withStructuredOutput(Availability), invoked on a text built from result.messages.

result = agent.invoke({"messages": [("user", "Is 'Build Your Own Radio' available?")]})
transcript = "\n".join(f"{m.type}: {m.content}" for m in result["messages"])
extractor = get_model().with_structured_output(Availability)
answer = extractor.invoke("Fill the fields using only the tool results below.\n\n" + transcript)

What you should see. Line 1 of the output is always [ '__start__', 'model_request', 'tools', '__end__' ]. The rest depends on the model: with llama3.2 expect wrong tool choices and invented details like ours (our run invented a "$2.50" fee). In part 3, structuredResponse may be undefined, and providerStrategy may print failed: Failed to parse structured output …. That is the real behaviour of a small local model, not a bug in your code.

Common mistakes.

  • Passing the context in the wrong place. In LangChain.js it goes inside the config object, next to configurable: { configurable: { thread_id }, context: { member_id } }. Without it, runtime.context.member_id has nothing to read and the tool fails when the model calls it.
  • Reading the runtime from the first argument. The first argument is what the model sent (matching schema); the ToolRuntime is the second argument.
  • Adding a member_id field to the tool's schema "to be safe". Every field of schema is shown to the model and filled by it. That brings the lab 11 leak back.
  • Filtering on the node name "model". createAgent in LangChain.js calls it "model_request".
  • Reading the tool calls of the last turn only. With a checkpointer, result.messages is the whole thread. Line 39 collects calls from every turn, which is why question 2 can show a call from question 1.
  • Running node labs/14-create-agent.ts. Use pnpm lab 14 from the project folder; it runs the file through tsx.
