Chat models, structured output and prompts

Messages, model parameters, providers, structured output strategies and prompt templates. Read with book Part II (chapters 3-5).

Read with Part II · Integrations and Utilities for LLMs in LangChain (chapters 3–5) of the book. This page explains the ideas in its own words and links them to the labs.

Every LangChain program, however clever, ends up doing the same thing: build a list of messages, send it to a chat model, and turn what comes back into something your code can use. This chapter covers those three moves — the chat-model interface, structured output, and prompt templates — and the settings that decide whether a small local model behaves.

You will learn:

  • the chat-model interface: invoke, stream, batch and their async twins;
  • the four kinds of messages and what an AI message carries besides its text;
  • how provider packages and init_chat_model("provider:model") pick the model;
  • the settings that matter most locally: temperature, output cap, context size and reasoning;
  • how structured output works, the three strategies behind it, and why a schema constrains shape but not truth;
  • how prompt templates build messages from variables, chat history and examples, and how prompt | model | parser joins it all up.
Why this matters for your project. The Harbor City Library assistant needs to talk to readers (lab 01), turn a vague request into data a catalog search can use (lab 02), and reuse the same carefully written instructions everywhere (lab 03). Every later lab — RAG chains, tools, agents — is built from these pieces.

The chat-model interface

A chat model in LangChain is an object with a small, fixed set of methods. Whether it talks to Ollama on your laptop or to a hosted service, the methods are the same. That is the point of the interface: you can swap the model and keep the code.

MethodInputReturnsUse it when
invoke(x)a string, a list of messages, or a prompt valueone AIMessageyou want the whole answer at once
stream(x)samean iterator of AIMessageChunk piecesa person is watching and should see text appear as it is written
batch([x1, x2, …])a list of inputsa list of AIMessage, in the same orderyou have several independent questions
ainvoke, astream, abatchsamesame, but must be awaitedyour program is async (a web server, an MCP client)

Lab 01 calls all three synchronous methods. A batch runs its inputs in parallel threads, but on a small local machine the model server may still answer them one after another, so do not expect a speed-up there. Streaming is about how it feels to the reader. The async versions look like this:

import asyncio

from harbor.config import get_model


async def main():
    model = get_model()
    reply = await model.ainvoke("What is a public library? Answer in one sentence.")
    print(reply.content)
    async for chunk in model.astream("Name three things people do in a library."):
        print(chunk.content, end="", flush=True)


asyncio.run(main())
New to async? Why there are two versions of every method

A normal (synchronous) call blocks: your program waits doing nothing until the model answers. In an async program, await says "while this waits, run other work". A web server answering many readers at once, or lab 10's MCP client, needs that. The rule: inside an async def function use the a… methods with await; in a plain script use the normal ones. Mixing them up gives a coroutine object instead of an answer, or blocks everything.

Messages: who says what

Chat models take a list of messages, each with a role. LangChain has a class for each role, in langchain_core.messages.

ClassRoleWritten byExample from the labs
SystemMessagesystemyou, the developer"You are the assistant of Harbor City Library. Be brief and friendly."
HumanMessageuserthe person (or your code on their behalf)"Hi! Can you help me find a book about the sea?"
AIMessageassistantthe modelits answer, or a request to call tools
ToolMessagetoolyour code, after running a tool"The Quiet Engine: 1 of 2 copies available at Central Library." (lab 09)

Passing a plain string to invoke is a shortcut for a list with one HumanMessage. The system message comes first and sets the rules for the whole conversation; the model is trained to give it more weight than the user's text, but not absolute obedience.

What comes back: content and metadata

An AIMessage is more than its text. The fields you will use most:

  • content — the answer. Usually a string; with some providers and multimodal models it can be a list of typed blocks (text, images, reasoning). .text always gives you the plain text, and .content_blocks gives the blocks in LangChain's standard format.
  • tool_calls — the tools the model asked for, as name, arguments and id (empty when it just answered).
  • usage_metadata — token counts, the same keys for every provider. Lab 01 printed {'input_tokens': 36, 'output_tokens': 40, 'total_tokens': 76}.
  • response_metadata — provider-specific details, such as the model name and why generation stopped.

Providers and init_chat_model

Each model provider has its own LangChain package — langchain-ollama here; other providers publish their own — containing a chat-model class that speaks that provider's API. You can create the class directly, as harbor/config.py does:

    return ChatOllama(model=MODEL, temperature=temperature, num_ctx=NUM_CTX, num_predict=num_predict,
                      reasoning=False, **kwargs)

Or you can let LangChain pick the class from a string. init_chat_model (from langchain.chat_models) reads a "provider:model" string, imports the matching provider package and creates its class. Lab 01 does it and prints the class it got:

5) init_chat_model: ChatOllama -> ready
from langchain.chat_models import init_chat_model

local = init_chat_model("ollama:llama3.2", temperature=0, num_ctx=8192)
# A hosted provider works the same way once its package is installed and its API key is set:
# hosted = init_chat_model("<provider>:<model name>", temperature=0)

Use the class directly when you need provider-specific options and want your editor to autocomplete them; use init_chat_model when the model should be chosen by configuration (an environment variable, a settings file). The labs do the first in harbor/config.py, but still let you change the model with the HARBOR_MODEL environment variable.

Model settings that matter

Settings are passed when you create the model. These four decided how the labs behaved on our machine:

Setting (ChatOllama)Lab valueWhat it doesWhat we saw
temperature0How random the choice of each next token is. 0 = almost always the most likely token.More repeatable runs — but not identical ones; your output will still differ.
num_predict512Maximum number of tokens the model may write in one answer. Hosted providers usually call this max_tokens.Added after a generation in lab 02 never stopped and blocked the Ollama server; we had to stop its stuck process.
num_ctx8192Size of the context window Ollama reserves for the model.With Ollama's larger default, most of the model ran on the CPU of our 4 GB GPU. With 8192: 3.4 GB, 32 % CPU / 68 % GPU, a 76-token answer in about 4.5 s warm.
reasoningFalseTurns hidden "thinking" on or off for models that support it. With True the thinking is returned separately (in additional_kwargs).Off, because thinking made gemma4 much slower here; llama3.2 does not think anyway.

Local or hosted?

The labs run locally with Ollama: free per call, nothing leaves your machine, and it works offline once the model is downloaded. The price is your hardware's limits — a 3B model that sometimes ignores instructions, and settings you must tune yourself, as above. A hosted model removes the hardware problem and is usually much larger, but costs money per token, needs an API key kept out of your code, and sends your data to the provider. Because both sit behind the same interface, a sensible path is to develop locally and switch only the model line if you need more quality.

Structured output

Free text is fine for a person but awkward for a program. If the next step is a catalog search, you want {"topic": "harbor history", "audience": "adults", "formats": ["audiobook"]}, not a friendly paragraph. Structured output means asking the model for data in a fixed shape and getting back a checked Python object.

In LangChain you describe the shape as a Pydantic model (or a TypedDict, or a raw JSON schema) and call model.with_structured_output(Schema). That returns a new Runnable that, when invoked, returns an instance of your class. Lab 02 uses this schema:

class BookRequest(BaseModel):
    """What a library visitor is looking for."""
    topic: str = Field(description="The subject, in two to four words")
    audience: Literal["children", "teens", "adults"] = Field(description="Who the book is for")
    formats: list[Literal["book", "e-book", "audiobook", "DVD"]] = Field(description="Formats the visitor accepts")
    max_pages: int | None = Field(default=None, description="Maximum length if the visitor gives one, else null")

Each part of the class does a job. The docstring and the description texts are sent to the model as instructions. Literal[...] restricts a field to a fixed list of values. int | None with a default makes a field optional. Field can also add limits — ge/le for numbers, min_length/max_length for strings and lists — and every limit is written into the JSON schema the model receives.

New to Pydantic? Classes that check their own data

Pydantic lets you declare a class with type hints; when you create an instance, it checks every value and raises a ValidationError if something does not fit (a string where an int belongs, a value outside a Literal). It can also export the class as a JSON schema with BookRequest.model_json_schema() — which is exactly what LangChain sends to the model. So one class does two jobs: it tells the model what to produce and it checks what the model produced.

Three strategies, one method

How does the model get pushed into the right shape? There are three strategies, chosen with the method= argument. For ChatOllama the default is "json_schema".

"Constrained decoding" means the server, at each step of next-token prediction, removes every token that would break the schema. The model cannot write "audience": "pirates" because the tokens for it are not allowed. That is why lab 02's two clear requests came back perfectly shaped:

BookRequest {'topic': 'crab books for kids', 'audience': 'children', 'formats': ['e-book', 'book'], 'max_pages': 40}
BookRequest {'topic': 'harbor history', 'audience': 'adults', 'formats': ['audiobook'], 'max_pages': 200}

Look closely at the second line: the reader never mentioned a page limit, and the schema said "else null", yet the model filled in 200. Keep that in mind.

The runaway list, and include_raw

The third request in lab 02 was deliberately vague: "Something fun to read." The model started a valid object, then wrote "e-book" into the formats list again and again. The schema allowed a list of any length, so constrained decoding never forced it to close the list. Before the labs had an output cap, this generation simply never ended and froze the Ollama server. With num_predict=512 it stops at 512 tokens — in the middle of the JSON, which then cannot be parsed.

Normally a parsing failure raises an exception. With include_raw=True you get a dictionary instead, with the raw AIMessage, the parsed object (or None) and the error (or None), so your code can log the raw text and decide what to do:

include_raw keys: ['raw', 'parsing_error', 'parsed']
parsed: None
parsing_error: Failed to parse BookRequest from completion {"topic": "funny stories", "audience": "adults", "formats": ["book", "audiobook", "e-book", "e-book", "e-book", "e-book", "e-book", "e-book", "e-book", "e-b
output tokens: 512

The fix lives in the schema. Field(max_length=4) on the list becomes "maxItems": 4 in the JSON schema, Ollama enforces it during decoding, and the list must close after four items:

with max_length=4: topic='funny stories' audience='adults' formats=['book', 'audiobook', 'e-book', 'e-book'] max_pages=2000 | error: None
Shape, not truth. Structured output guarantees that formats is a list of allowed words of at most four items. It cannot guarantee the list makes sense (a duplicate), or that max_pages came from the reader (2000 was invented; so was the 200 earlier). Treat structured output like any user input: validate the values that matter in your own code (for example, set max_pages to None unless a number appears in the request, or remove duplicates with a Pydantic validator).

Prompt templates

The text you send to a model is the prompt. Real prompts are mostly fixed instructions with a few changing parts: the branch, the language, the reader's question. A prompt template stores the fixed part once and fills in the variables on every call, so the wording is consistent and you never glue strings together by hand.

Variables and from_messages

ChatPromptTemplate.from_messages takes a list of (role, text) pairs; each {name} in the text is a variable. Lab 03 fills one in and prints exactly what the model would receive:

system: You are the assistant of Harbor City Library's Lighthouse Branch. Answer in French, in one sentence.
 human: When is story time?

Calling prompt.format_messages(...) like this is the best debugging tool for prompts: you see the real messages, not what you think you wrote. If you forget a variable, the template raises an error (a KeyError naming the missing variable) instead of sending a half-filled prompt.

Partial variables

Sometimes a variable is known early and stays the same — the branch for a kiosk installed at the Lighthouse Branch, say. partial() fills some variables now and returns a new template that only asks for the rest:

from langchain_core.prompts import ChatPromptTemplate

prompt = ChatPromptTemplate.from_messages([
    ("system", "You are the assistant of Harbor City Library's {branch}. Answer in {language}, in one sentence."),
    ("human", "{question}"),
])
kiosk = prompt.partial(branch="Lighthouse Branch", language="English")
print(kiosk.input_variables)  # ['question']

MessagesPlaceholder: room for a whole conversation

A variable holds one string. A MessagesPlaceholder("history") holds a whole list of messages, inserted at that point. That is how a template carries a chat history. In lab 03 the history said "My name is Lea and I love science fiction", and the model answered "Your name is Lea, and your favourite genre is science fiction!" — it "remembered" only because the history was pasted in.

Few-shot templates

Describing an output format in words is hard; showing it is easy. A few-shot prompt includes a few example inputs with the exact outputs you want. FewShotChatMessagePromptTemplate turns a list of example dictionaries into pairs of human/AI messages. Lab 03 gave two examples of catalog tags such as science fiction · adults · 2021, and the model tagged a new title in the same style: historical fiction · adults · 2019. The format was copied perfectly; the content (genre, year) was a guess, since the model knows nothing about that book.

prompt | model | parser

A template, a model and an output parser are all Runnables, so the | operator of LCEL can join them into a chain. Calling the chain runs them in order, each output feeding the next input:

chain = prompt | model | StrOutputParser()

Lab 03's chain also shows the limit of prompting alone: asked "Do you have a maker space?", the chain answered with a detailed description of an "Innovation Studio" that does not exist. A good template makes the answer well-formed; only real data — retrieval in labs 04–07, tools in labs 09–15 — makes it true.

Pitfalls
  • No output cap. Without num_predict (or max_tokens), one runaway generation can block a local server. Set it in the one function that creates your model.
  • Unbounded lists in schemas. Add max_length to every list field you send as a structured-output schema.
  • Trusting valid output. A parsed object can still hold invented values (max_pages=200, 2000). Validate what matters.
  • Exceptions you did not expect. Without include_raw=True, a parse failure raises. Use it where a bad answer must not crash the program, and log raw.
  • Literal braces in templates. { and } mark variables; to put real braces (for example a JSON example) in a template, double them: {{ and }}.
  • Mixing sync and async. model.ainvoke(...) without await returns a coroutine, not an answer.
  • Assuming the model remembers. It only sees the messages in this call; pass history explicitly (MessagesPlaceholder) or use a checkpointer.
  • Huge context by default. On a small GPU, a large num_ctx pushes the model onto the CPU and makes every call slow. Choose the size you need.
Recap
  • Every chat model has invoke, stream, batch and async versions; it takes messages and returns an AIMessage with content, tool calls and usage_metadata.
  • Four message roles: system (your rules), human, AI, tool; the whole list is resent on every call.
  • Provider packages hold the model classes; init_chat_model("ollama:llama3.2") picks one from a string.
  • The labs set temperature=0, num_predict=512, num_ctx=8192 and reasoning=False in one place, each for a reason we hit in practice.
  • with_structured_output returns validated Pydantic objects; method= chooses json_schema (default for Ollama), function_calling or json_mode; include_raw=True turns failures into data.
  • Field(max_length=4) fixed lab 02's runaway list — but schemas constrain shape, not truth.
  • Templates fill variables, accept partial values, insert histories with MessagesPlaceholder and teach formats with few-shot examples; prompt | model | parser is your first chain.
