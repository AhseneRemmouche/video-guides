API Design

CRUD over HTTP, REST vs GraphQL vs gRPC, relationships, pagination, idempotency, versioning, rate limiting and CORS.

▶ Watch this part (23:49)

Now that we know the protocols, let us use them to build something: an API (Application Programming Interface). An API is the front door to your system — it defines how other programs ask for data and send data in. This section goes from the basics up to the best practices that separate a passable API from an excellent one (at 23:49). We will use an e-commerce store, Shopify-style, as the running example.

CRUD: the four basic operations

Most of API design is about defining the inputs (for example the product details a seller provides when adding a product) and the outputs (the information returned when someone queries a product), and deciding how these operations are exposed (at 24:11). Nearly every data-driven app boils down to four operations called CRUD: Create, Read, Update, Delete (at 24:35).

In a REST API these map cleanly onto HTTP methods and URLs (at 24:35):

POST    /api/products        create a product (details in the body)
GET     /api/products        list all products
GET     /product/{id}        fetch one product
PUT     /product/{id}        update a product (replace)
PATCH   /product/{id}        update a product (partial)
DELETE  /product/{id}        remove a product

To create a product you send a POST to /api/products with the product details in the request body — usually in JSON (at 25:20):

{
  "name": "Ceramic Mug",
  "price": 12.5,
  "inStock": true
}
New to APIs? What an API actually is

An API is a contract. It lists the requests a program can make (“send a POST to /api/products with these fields”) and what it will get back (“a JSON product, or a 404”). Because the contract is fixed, a web page, a mobile app and another server can all use the same backend without knowing how it works inside. CRUD is just the most common shape that contract takes.

Choosing a paradigm: REST vs GraphQL vs gRPC

When you design an API you pick a communication protocol (HTTP, WebSockets) and a data format (JSON, XML, or protocol buffers) (at 25:20). The combination tends to follow one of three paradigms (at 25:44):

  • REST (Representational State Transfer): stateless, uses the standard HTTP methods, usually exchanges JSON, and is easy for any client to consume. Its weakness is over-fetching or under-fetching — you often get more or less than you need, and may have to call several endpoints (at 26:09).
  • GraphQL: the client asks for exactly the fields it needs, avoiding over- and under-fetching. Queries are strongly typed. But complex queries can strain the server, all requests are sent as POST, and it typically returns HTTP 200 even on errors, with the error details in the response body (at 26:31).
  • gRPC (Google Remote Procedure Call): built on HTTP/2 (with features like multiplexing and server push) and protocol buffers. It is very efficient with bandwidth and resources, which makes it great for microservices. The trade-off is that it is less human-readable than JSON and needs HTTP/2 support (at 26:55).
In an interview, say: “I would default to REST for a public API because any client can consume it. I would reach for GraphQL if clients need very different slices of the same data, and gRPC for internal microservice-to-microservice traffic where speed matters more than readability.”

Modelling relationships

Real data is connected: a user has orders, an order has products (at 27:21). You design endpoints that reflect these relationships by nesting resources in the URL. For example, to fetch the orders belonging to one user you query GET /users/{id}/orders (at 27:21).

Pagination

Listing endpoints can return thousands of rows. Pagination hands back one page at a time so you never overwhelm the client or the server (at 27:21). The common approach uses limit (how many) and offset (how many to skip); you can also filter by a start and end date (at 27:44).

GET /api/products?limit=3&offset=4

Illustrative: skip the first 4 products, then return the next 3.

GET should be safe and idempotent

A well-designed GET request should be idempotent: calling it multiple times does not change anything and always returns the same result (at 27:44). Crucially, GET must never mutate data — it is for retrieval only. If you need to create or change something, use POST, PUT or PATCH (at 28:06).

New to “idempotent”? A plain-English definition

An operation is idempotent if doing it once and doing it ten times leave the system in the same state. Reading a page is idempotent — refresh all you like, nothing changes. Deleting a specific product by id is also idempotent (after the first delete, it is already gone). POST is not idempotent: send it twice and you may create two products. Interviewers ask about this because it decides whether a client can safely retry a failed request.

Common mistake: using a GET request to change data (for example GET /product/5/delete). Browsers, proxies and caches assume GET is safe, so they may repeat it or cache it — silently deleting or duplicating data. Keep every state change behind POST/PUT/PATCH/DELETE.

Versioning for backward compatibility

When you change an API, you must not break the clients already using it (at 28:06). The common practice is versioning: introduce a new version, like v2, so the old v1 API keeps serving existing clients while v2 serves new ones (at 28:06). In GraphQL the equivalent is to add new fields (v2 fields) without removing the old ones, so the API evolves without breaking anyone (at 28:29).

Protecting the API: rate limiting and CORS

Two more best practices guard the door (at 28:29). Rate limiting caps how many requests a user can make in a time window; it stops any single user from flooding your API and helps prevent denial-of-service (DoS) attacks (at 28:52). CORS (Cross-Origin Resource Sharing) lets you control which domains are allowed to call your API, preventing unwanted cross-site interactions (at 28:52).

In an interview, say: “For a public API I would add rate limiting per API key to protect against abuse and DoS, version the endpoints so changes stay backward compatible, and set a strict CORS allow-list so only our own front-end domains can call it from the browser.”
Recap
  • An API is the contract for how programs talk to your system; most of it is CRUD — create, read, update, delete.
  • In REST, CRUD maps to HTTP methods and URLs: POST /api/products, GET /api/products, PUT/PATCH/DELETE /product/{id}.
  • Paradigms: REST (simple, JSON, can over/under-fetch), GraphQL (ask for exactly what you need; all POST; 200 even on errors), gRPC (HTTP/2 + protocol buffers; fast; great for microservices; less readable).
  • Model relationships by nesting URLs (/users/{id}/orders); paginate large lists with limit and offset.
  • GET must be idempotent and never mutate data — use POST/PUT/PATCH/DELETE to change things.
  • Keep changes backward compatible with versioning (v2); protect the API with rate limiting and CORS.
