Load Balancing

Load-balancing algorithms, health checks, hardware/software/cloud balancers, and what to do when a balancer fails.

▶ Watch this part (42:31)

When one server can no longer handle every request on its own, you add more servers — and then you need something to decide which server each request should go to. That something is a load balancer. This page explains what it does, the main algorithms it uses to pick a server, how it avoids sending traffic to broken servers, the forms it comes in, and why the balancer itself must not become the weak link.

What a load balancer is

A load balancer sits in front of a pool of servers and spreads incoming traffic across them so that no single server bears too much load (at 42:31). By sharing the work out, it increases both the capacity of the application (more requests handled per second) and its reliability (if one server is busy, others pick up the slack). A load balancer is a specific kind of reverse proxy: it stands in front of your servers, and clients only ever talk to it, never to the servers directly.

New to the idea of a pool of servers? What it means

A "pool" is just the group of identical servers running copies of the same application. Each copy can serve any request, because they all read and write the same shared database. Adding a server to the pool adds capacity; removing one (say, for maintenance) removes capacity. The load balancer's whole job is to decide, for each arriving request, which member of the pool should answer it.

The algorithms: how it picks a server

There is no single "best" way to choose a server. The right choice depends on whether your servers are equally powerful, how long requests take, and whether a user must keep talking to the same server. The presenter walks through the common strategies (at 42:54).

Round robin

The simplest strategy. Each server in the pool gets a request in a sequential, rotating order; when the last server is reached, it loops back to the first (at 42:54). Round robin works well when the servers have similar specifications and the load is spread evenly, because it makes no attempt to measure how busy each server is — it just takes turns.

Least connections and least response time

The least-connections algorithm directs each new request to the server with the fewest active connections (at 43:16). It suits longer tasks, or cases where the load is not evenly distributed, because it reacts to how busy each server actually is rather than blindly rotating. The least-response-time algorithm goes further: it chooses the server with both the lowest response time and the fewest active connections (at 43:16), aiming to give each request the fastest possible answer.

Weighted and geographic

Real pools are rarely made of identical machines. The weighted variants — weighted round robin or weighted least connections — assign each server a weight based on its capacity or performance, so a server with more CPU or more RAM is handed more requests (at 44:02). The geographic algorithm instead routes each request to the server closest to the user, or to a specific region (at 44:24); it is useful for global services where reducing latency is the priority.

IP hashing and consistent hashing

Some applications need a client to keep talking to the same server — for example when that server is holding the user's session in memory. IP hashing achieves this: it runs the client's IP address through a hash function, and the result decides which server receives the request (at 43:38). Because the same IP always hashes to the same value, that client consistently reaches the same server — this is called session persistence.

Consistent hashing is a more advanced relative. Imagine a hash space drawn as a circle whose end wraps around to the beginning — a "hash ring" (at 44:24). Both the servers (nodes) and the keys are hashed onto the ring, and a key is served by the next node going around the circle. This keeps a client on the same server, and — importantly — when one node is added or removed, only a small slice of keys has to move, instead of reshuffling everything.

New to "session persistence"? Why a client gets stuck to one server

If a server keeps information about you in its own memory — your shopping cart, your logged-in session — then your next request must come back to that same server, or your cart looks empty. Routing you to a fixed server (by hashing your IP, for example) is called session persistence or "sticky sessions". The cleaner long-term fix is to store session data in a shared place (like a database or Redis) so any server can serve you, but sticky routing is a common stopgap.

Health checks: only send traffic to healthy servers

A pool is only useful if the balancer knows which members are actually working. An essential feature of load balancers is the continuous health checking of servers, so traffic is only directed to servers that are online and responsive (at 44:47). If a server fails a health check, the balancer stops sending requests to it until it comes back online — so a single crashed server causes no visible errors for users.

The forms a load balancer comes in

Load balancers are not always a box you buy. They come as hardware appliances, software you install, managed cloud services, and virtual appliances (at 45:11).

  • Hardware: dedicated appliances such as F5 BIG-IP (known for high performance and features like global server load balancing) and Citrix, formerly NetScaler.
  • Software: open-source programs you run yourself, such as HAProxy (for TCP and HTTP applications) and Nginx (a web server that also works as a load balancer and reverse proxy).
  • Cloud: managed services like AWS Elastic Load Balancing, Azure Load Balancer, and Google Cloud Load Balancer — the provider runs the balancer for you.
  • Virtual: software-defined appliances such as VMware Avi, deployable on-premises or in the cloud.

Do not let the balancer become the single point of failure

Here is the catch. If every request must pass through the load balancer, then the balancer itself is a single point of failure: if it goes down, all of the servers behind it become unreachable, even though they are perfectly healthy (at 46:44). The fix is to build redundancy and fault tolerance into the balancing layer too.

  • Redundant balancers in pairs: run more than one load balancer, often in a pair. If one fails, the other takes over — a technique called failover (at 47:06).
  • Health-check the balancers themselves: monitor the balancers continuously, so problems are detected early, before they cause a real disruption (at 47:06).
  • Auto-scaling and self-healing: modern infrastructure can detect a failed balancer and automatically replace it with a new instance, with no manual intervention (at 47:30).
  • DNS failover: reroute traffic away from the IP address of a failed balancer to a pre-configured standby IP — a second balancer ready to take over (at 47:30).
New to "single point of failure"? Why one box can sink the whole system

A single point of failure (SPOF) is any one component whose failure stops the entire system, no matter how healthy everything else is. A lone load balancer is a classic SPOF: ten healthy servers are useless if the one door in front of them is locked. Removing SPOFs means duplicating the critical parts so there is always a backup ready — that is what redundancy and failover buy you.

In an interview, say this

"A load balancer spreads traffic across a pool to raise capacity and reliability, and I pick the algorithm to fit the workload — round robin for equal servers, least connections for uneven or long requests, weighted when machines differ in power, and IP or consistent hashing when a client must stay on one server. It uses health checks so traffic only reaches healthy servers. And because the balancer is itself a single point of failure, I run a redundant pair with failover." Naming the trade-off behind each algorithm is what interviewers are listening for.

Common mistake

Adding a load balancer and then forgetting that you have just created a new single point of failure. A lone balancer in front of ten servers means one crash takes down all ten. Always pair it with redundancy (a standby balancer and failover). A second common slip is choosing round robin for servers of very different sizes — the small ones get overloaded while the big ones idle; use a weighted algorithm instead.

Recap
  • A load balancer is a reverse proxy that spreads traffic across a pool of servers, raising capacity and reliability; clients see only the balancer.
  • Round robin takes turns (equal servers); least connections and least response time watch how busy or fast each server is; weighted accounts for different-sized machines; geographic routes to the nearest region.
  • IP hashing and consistent hashing keep a client on the same server (session persistence); consistent hashing moves only a few keys when the pool changes.
  • Health checks route traffic only to servers that are online and responsive.
  • Load balancers come as hardware (F5, Citrix), software (HAProxy, Nginx), cloud (AWS ELB, Azure, GCP), and virtual (VMware Avi).
  • The balancer is itself a single point of failure — fix it with redundant pairs and failover, health checks on the balancers, auto-scaling/self-healing, and DNS failover to a standby IP.
