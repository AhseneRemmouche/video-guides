Caching

Browser, server and database caching; cache-control, hits/misses, write-around/through/back policies and eviction.

▶ Watch this part (29:15)

Imagine a website whose server lives in a data center in Finland. For visitors in Europe the page might load in about 100 milliseconds, but for visitors in Mexico the same page can take three to five seconds (at 29:15). We cannot move the server closer to everyone, so instead we keep copies of data nearer to where it is needed. That is the idea behind caching — and it is one of the first things a system-design interviewer expects you to reach for when a system feels slow.

Caching is a technique for improving the performance and efficiency of a system. It works by storing a copy of some data in a fast, temporary place, so that future requests for that same data can be served quickly instead of being computed or fetched from scratch every time (at 29:37). This page covers where caches live, how we measure whether a cache is helping, how data gets written into a cache, and what happens when a cache runs out of room.

New to caching? What it is and why it matters

A cache is a small, fast store that holds copies of data you are likely to ask for again. The original, trustworthy copy still lives somewhere slower and bigger (a database, a disk, a far-away server). The cache is a shortcut, not the source of truth. Because a cache is temporary, it can be cleared or can fall out of date, so every caching design has to answer two questions: how does fresh data get in, and what gets thrown out when the cache is full? The rest of this page answers both.

Four places a cache can live

The video calls out four common places to store a cache (at 29:51). Each one sits at a different point on the journey a request takes from the user to the database, and each saves a different kind of work.

Browser caching

With browser caching we store a website's resources on the user's own computer. When the user revisits the site, the browser can load those files from the local cache instead of fetching everything from the server again (at 30:01). The files — HTML, CSS and the JavaScript bundle — are kept in a dedicated cache directory on the client's hard drive that the browser manages for you. Users can turn caching off in their browser settings, and developers can switch it off while building: in Chrome there is a Disable cache checkbox in the Network tab of the developer tools (at 30:23).

How long should the browser keep a file? The server answers that with the Cache-Control header. In the example from the video the value is 7,200 seconds, which is two hours (at 30:46).

Cache-Control: max-age=7200

Hits, misses and the cache ratio

When the data a request needs is already in the cache, that is a cache hit, and the response is fast. When it is not there, that is a cache miss, and the system has to go and fetch the data from the original source (at 30:46). The cache ratio is the share of all requests that were served from the cache; a higher ratio means the cache is doing more of the work and is therefore more effective (at 31:10).

You can see which one happened by reading the X-Cache response header. If it says MISS the cache was missed; if it says HIT the response came from the cache (at 31:10).

X-Cache: MISS
In an interview, say: "I would track the cache hit ratio. A low ratio means the cache is not holding the right data, so it adds latency instead of removing it." Tying a cache to a number you can measure shows you think about whether it actually helps.

Server caching and write policies

Server caching stores frequently accessed data on the server side, so the app can avoid expensive work such as repeating a database query (at 31:10). The cache sits either in memory — for example in Redis, an in-memory database — or on disk, sometimes on a separate cache server. The rule is simple: before querying the database, the server checks the cache. If the data is there it is returned directly; if not, the server queries the database, returns the result, and stores a copy in the cache for next time (at 31:32).

New to Redis? Why an in-memory store is so fast

Redis keeps its data in RAM rather than on a disk. RAM is far faster to read than a disk, so a lookup can finish in well under a millisecond. The trade-off is that RAM is smaller and more expensive, and its contents are lost if the machine loses power. That is exactly why Redis is popular as a cache: a cache is meant to be a fast, replaceable copy, so losing it is not a disaster — the real data still lives in the database.

When data changes, how does the new value reach both the cache and the permanent storage? That choice is the cache's write policy, and the video describes three (at 31:56).

  • Write-around: data is written straight to permanent storage, bypassing the cache. Good when writes are not performance-critical and you do not expect to read the new value back soon (at 31:56).
  • Write-through: data is written to the cache and the permanent storage at the same time. This keeps the two consistent, but each write is a little slower because it has to touch both (at 32:18).
  • Write-back: data is written to the cache first and copied to permanent storage later. Writes feel fast, but if the server crashes before the copy happens, that data can be lost (at 32:18).
Common mistake: assuming write-back is simply "the fast one" and always best. It trades durability for speed. If a crash between the cache write and the storage write would lose data you cannot afford to lose — an order, a payment — write-through is the safer choice.

Eviction policies: what to drop when the cache is full

A cache is small on purpose, so eventually it fills up. When it does and new data needs room, the cache must remove something. The rules that decide what to remove are called eviction policies (at 32:41). The three the video names are:

  • LRU (least recently used): remove the item that has not been read for the longest time.
  • FIFO (first in, first out): remove the item that was added earliest, regardless of how often it is used.
  • LFU (least frequently used): remove the item that has been requested the fewest times.

Database caching

Database caching means caching the results of database queries to speed up data-driven applications (at 33:05). It can be done inside the database system itself, or through an external caching layer such as Redis or Memcached. The flow mirrors server caching: when a query comes in, first check whether its result is already stored. If it is, return the cached result and skip the database. If it is not, run the query, return the result, and store it for next time (at 33:05).

Database caching is most valuable for read-heavy applications, where a handful of queries run very frequently (at 33:28). It uses the same eviction policies as server-side caching, so LRU, FIFO and LFU apply here too.

In an interview, say: "Caching gives fast reads and takes load off the database, but it adds the risk of serving stale data. I would set a sensible Cache-Control lifetime and pick a write policy that matches how fresh the data has to be." Naming the downside shows you understand the trade-off, not just the benefit.
Recap
  • Caching keeps a fast, temporary copy of data so future requests are served quicker; it can live in the browser, a CDN, the server, or the database.
  • A cache hit is served from the cache; a cache miss falls back to the origin. The cache ratio measures how often hits happen, and the X-Cache header shows HIT or MISS per response.
  • Cache-Control sets how long content may be cached (for example max-age=7200, two hours).
  • Write policies decide when the cache and permanent storage are updated: write-around bypasses the cache, write-through updates both together, write-back updates the cache first and storage later.
  • When a cache fills up, eviction policies (LRU, FIFO, LFU) decide what to remove.
  • Database caching stores query results, often in Redis or Memcached, and shines in read-heavy apps.
