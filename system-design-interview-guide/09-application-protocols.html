Application-Layer Protocols

HTTP, WebSockets, email (SMTP/IMAP/POP3), FTP/SSH, WebRTC/MQTT/AMQP and RPC — and when to use each.

▶ Watch this part (18:50)

Two devices can only talk if they agree on a set of rules for the conversation. Those rules are called protocols. In the last section we looked at the lower layers (IP, TCP, UDP, ports). This section sits one layer up: the application-layer protocols — the languages your apps actually speak to move data around. In an interview you are expected to know which protocol fits which job, and why. Let us walk through the essential ones (at 18:50).

HTTP: the language of the web

The most common one is HTTP (HyperText Transfer Protocol). It is built on top of TCP/IP, and it is a request–response protocol: the client asks, the server answers, and the exchange is over (at 18:50). HTTPS is simply HTTP with the traffic encrypted, so nobody in the middle can read it.

The key idea to remember is that HTTP is stateless. The presenter describes it as “a conversation with no memory” (at 19:14): each interaction is separate, with no recollection of the past. The server does not have to store any context between requests. Instead, every request carries all the information needed to understand it — who you are, what you want, and any data. The request is made of headers (details like the URL and the method) and a body (the actual data being sent).

New to TCP/IP? What “built on top of” means

Protocols stack in layers. TCP/IP (the lower layers) handles getting bytes reliably from one machine to another — splitting data into packets, numbering them, and re-sending lost ones. HTTP sits on top and does not worry about any of that. It just says “here is a request” and trusts TCP/IP to deliver it. Each layer solves one problem so the layer above does not have to.

Each response includes a status code, a short number that tells the client how the request went (at 19:37). They come in four families:

  • 2xx — success: the request was received and processed (for example 200 OK).
  • 3xx — redirection: the client must take a further step to finish the request (for example 301 Moved Permanently).
  • 4xx — client error: the request was bad or cannot be fulfilled (for example 404 Not Found). The problem is on the caller's side.
  • 5xx — server error: something went wrong on the server (for example 500 Internal Server Error).

Each request also carries a method that says what action you want (at 20:00). The common ones are GET (fetch data), POST (usually create data on the server), PUT and PATCH (update a record), and DELETE (remove a record).

GET /api/products HTTP/1.1
Host: shop.example.com
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json

[ { "id": 1, "name": "Mug" } ]

Illustrative: a GET request (top) and the server's 200 response (bottom). The request has no body; the response carries the data.

In an interview, say: “HTTP is stateless, so each request is self-contained. That is what lets us put many identical servers behind a load balancer — any one of them can handle any request, because none of them needs to remember the last one.”

WebSockets: a two-way, always-open channel

HTTP is a one-way street: the client speaks first, every time. For real-time updates we use WebSockets instead (at 20:23). A WebSocket is a two-way communication channel over a single, long-lived connection. Once it is open, the server can push updates to the client without being asked. This is important for anything where the data changes constantly without the overhead of repeated HTTP request–response cycles — chat apps, live sport scores, and stock-market feeds (at 20:46).

Email, files and remote access

Email uses a small family of protocols (at 21:08). SMTP is the standard for sending email — it moves messages between servers. To read email, clients use one of two protocols: IMAP keeps messages on the server so you can access and manage them from multiple devices, while POP3 downloads messages to one local device (at 21:31), which suits email managed from a single machine.

For files and remote machines there are two classics (at 21:31). FTP (File Transfer Protocol) transfers files between a client and a server — handy for website maintenance and large uploads or backups. SSH (Secure Shell) lets you operate network services securely over an unsecured network; it is the usual way to log in to a remote machine and run commands, or to move files safely (at 21:55).

Real-time and message-based protocols

Three protocols handle specialised real-time and messaging jobs (at 22:19):

  • WebRTC enables browser-to-browser voice calls, video chat and file sharing with no plugins — the backbone of video conferencing and live streaming.
  • MQTT is a lightweight messaging protocol for devices with limited processing power and low bandwidth, such as IoT sensors.
  • AMQP is a protocol for message-oriented middleware, providing robustness and security for enterprise-level messaging — the protocol behind tools like RabbitMQ (at 22:41).
New to “message broker” and middleware? What AMQP is for

Instead of one service calling another directly, the sender (a producer) drops a message into a broker — a dedicated piece of software that holds messages in queues. A consumer picks them up when it is ready. This decouples the two sides: if the consumer is slow or briefly offline, messages wait safely in the queue instead of being lost. That is what “message-oriented middleware” means, and AMQP is the agreed language for it.

RPC: calling a function on another machine

Finally, RPC (Remote Procedure Call) lets a program on one computer run code on another computer (at 23:04). You invoke a function as if it were a local call, when in reality it executes on a remote machine. RPC abstracts away the network details, so the developer interacts with remote functions seamlessly, as if they were local. Many of the other protocols use RPC mechanisms under the hood — for example, an HTTP request can trigger RPC calls on the backend to process data (at 23:26).

Common mistake: reaching for HTTP polling when the data updates constantly. Hammering the server with “any news yet?” requests wastes bandwidth and still lags behind real time. If the server needs to push changes the moment they happen, say WebSocket (or Server-Sent Events) instead.
Recap
  • Application-layer protocols are the agreed languages apps use to exchange data on top of TCP/IP.
  • HTTP is a stateless request–response protocol: each request is self-contained, carries a method (GET/POST/PUT/PATCH/DELETE), and gets back a status code (2xx success, 3xx redirect, 4xx client error, 5xx server error). HTTPS is the encrypted version.
  • WebSockets keep one long-lived, two-way connection open so the server can push real-time updates — chat, live scores, stock feeds.
  • Email: SMTP sends; IMAP reads from many devices; POP3 downloads to one device. Files and remote access: FTP and SSH.
  • Specialised: WebRTC (browser-to-browser media), MQTT (IoT), AMQP (enterprise message brokers like RabbitMQ).
  • RPC lets you call a function that runs on another machine as if it were local, hiding the network.
