The CAP Theorem

Consistency, availability and partition tolerance — and why a distributed system can only guarantee two.

▶ Watch this part (08:44)

When you spread an application across many machines, you buy speed and resilience — but you also sign up for a hard rule. The CAP theorem describes that rule. It is one of the most quoted ideas in a system-design interview, so it pays to understand it rather than just memorise the three letters. This page explains what each letter means, why you can only ever pick two of the three, and how real systems make that choice.

What the CAP theorem says

The CAP theorem (also called Brewer's theorem, after the computer scientist Eric Brewer) is a set of principles for making trade-offs in a distributed system — an application whose data lives on more than one machine (at 8:44). It points at three properties and tells us a blunt truth: a distributed system can guarantee only two of them at the same time.

The three properties are:

  • Consistency — every node (every machine holding a copy of the data) sees the same data at the same time. If you change the data on one node, that change is reflected on all of them before anyone reads again. The presenter compares it to editing a shared Google Doc: the moment one person makes an edit, everyone else sees it (at 9:09).
  • Availability — the system is always operational and responds to every request, no matter what is happening behind the scenes. The presenter compares it to a reliable online store: whenever you visit, it is open and ready to take your order (at 9:33).
  • Partition tolerance — the system keeps working even when the network between nodes is disrupted, so some machines temporarily cannot talk to the others. The presenter compares it to a group chat where, even if one person loses connection, the rest keep chatting (at 9:33).
New to distributed systems and nodes? Start here

A single computer is simple: there is one copy of the data, and it is either up or down. A distributed system runs on many computers at once so it can serve more users and survive a machine dying. Each of those machines is called a node. The catch is that the nodes must stay in step with one another over a network, and networks are unreliable. Almost every hard idea in distributed systems — including CAP — comes from the fact that nodes cannot share data instantly or perfectly.

Why a partition forces the choice

The three letters sound equal, but in practice partition tolerance is not optional for a real distributed system. Networks fail, cables are cut, and packets get lost. A network partition is exactly that: a break in communication that splits your nodes into groups that can no longer reach each other (at 9:33).

During normal operation you can have consistency and availability together with no drama. The theorem only bites when a partition happens. At that moment a node that receives a request has two choices, and they pull in opposite directions:

Why is it only ever two, not three?

Imagine a partition has split your nodes, and a write lands on one side. If you answer every request (availability), the other side has not heard about that write, so some nodes now hold stale data — you have lost consistency. If instead you insist every node agree before answering (consistency), the side that cannot reach the others has to wait or refuse — you have lost availability. As long as the partition exists, you cannot have both. That is the whole theorem in one sentence.

How consistency actually works

It helps to picture consistency as a write that is not finished until every node agrees on the new value. A client writes a value; the node that received it propagates the change; only when all copies match does a later read return the fresh value.

Making the choice in a real design

Because partition tolerance is a fact of networked life, the practical question is almost always "consistency or availability during a partition?". The presenter gives the classic example: a banking system chooses consistency and partition tolerance (CP), even if it means some transactions take longer or are briefly rejected (at 9:55). You would rather a transfer pause than let two ATMs both hand out the last $100.

In an interview, say this

"CAP only forces a choice during a network partition. The rest of the time I can be both consistent and available. So for this feature the real question is: when a partition happens, do I pause to stay correct (CP) or stay up and reconcile later (AP)?" Framing it around the partition shows you understand the theorem instead of reciting it.

Common mistake

Claiming a system "has all three" of CAP, or proudly labelling a design "CA". You cannot have all three at once, and a real distributed system must tolerate partitions, so "CA" is not a practical option — dropping partition tolerance means dropping the idea that your nodes are ever disconnected, which is wishful thinking. Pick CP or AP and justify it.

Recap
  • The CAP theorem says a distributed system can guarantee only two of consistency, availability and partition tolerance at the same time.
  • Consistency = every node shows the same latest data; availability = the system always responds; partition tolerance = it keeps working when nodes cannot reach each other.
  • Partitions really happen, so the live choice is usually CP (stay correct, maybe pause) versus AP (stay up, maybe stale).
  • A banking system picks CP; a social feed can live with AP. State which you chose and why.
  • Never claim all three, and treat "CA" as a red flag rather than a design.
