Throughput & Latency

RPS, QPS and data throughput vs latency, and why improving one can hurt the other.

▶ Watch this part (12:58)

Once a system works correctly, the next thing an interviewer asks is how fast it is. The word "fast" actually hides two separate measurements that beginners constantly mix up: throughput and latency (at 12:58). They are not the same thing, and — this is the part people miss — improving one can quietly make the other worse. This page explains both, the units we measure them in, and the trade-off between them.

Throughput: how much work per unit of time

(at 12:58) Throughput measures how much work your system gets through in a fixed slice of time. Think of a checkout counter: throughput is how many customers it serves per hour, no matter how long any single customer takes. In the video it comes in three flavours, each with its own unit.

  • Server throughput — measured in requests per second (RPS) (at 13:00). This is how many client requests one server can handle each second. A higher RPS usually means the server can support more users at the same time.
  • Database throughput — measured in queries per second (QPS) (at 13:21). This is how many queries a database can process each second. Like RPS, a higher QPS generally signals better performance.
  • Data throughput — measured in bytes per second (at 13:44). This is how much raw data moves across a network or through the system in a given period.

The rule of thumb from the video: for all three, higher is generally better, because it means the system can do more work in the same amount of time.

New to "requests per second"? What RPS really counts

A "request" is one call from a client to your server — for example, loading a page or submitting a form. If a server handles 12,000 of those every second, its throughput is 12,000 RPS. RPS does not say how long any single request took; it only counts how many finished per second. That is why throughput and latency are different questions.

Latency: how long one request takes

(at 13:44) Latency measures how long it takes to handle a single request — the time from sending the request to getting the response back. Back at the checkout counter, latency is how long one customer waits in line and gets served, while throughput is how many customers pass through per hour. A system can have high throughput and still feel slow to one user if each individual request has high latency.

Server:   RPS = 12,000 requests/sec
Database: QPS = 40,000 queries/sec
Latency:  85 ms per request      (all numbers illustrative)

The trade-off: improving one can hurt the other

(at 14:08) Here is the catch an interviewer wants to hear: optimising for one of these can force a sacrifice in the other. The classic example is batching. Instead of answering every request the moment it arrives, you collect several and process them together in one trip. Grouping work this way raises throughput — you get more total work done per second — but each item now has to wait for the group to fill up, so its individual latency goes up. There is no single "fastest" setting; you tune toward whichever matters more for the use case.

New to batching? A quick picture

Batching is like a delivery van waiting until it has several parcels before leaving, rather than driving off with each parcel the instant it arrives. The van makes fewer trips and moves more parcels per hour (higher throughput), but the first parcel waits longer before the van departs (higher latency). Databases, message queues and logging systems all use batching for exactly this reason.

In an interview, say… "Throughput and latency are two different axes, not one speed number. Throughput is work per second (RPS for servers, QPS for databases); latency is the time for a single request. For this feature I'd optimise for low latency because users are waiting on each response, and accept slightly lower throughput." Naming the trade-off out loud is exactly what the interviewer is listening for.
Common mistake Treating "high throughput" and "low latency" as the same thing, or assuming that raising one automatically improves the other. A batched pipeline can have excellent throughput and poor per-request latency at the same time. Always state which one your design is optimising for, and what it costs.
Recap
  • Throughput = how much work per unit of time: server RPS (requests/sec), database QPS (queries/sec), and data bytes/sec. Higher is generally better.
  • Latency = how long a single request takes to get a response. Lower is generally better.
  • They are separate measurements: a system can have high throughput and still feel slow per request.
  • Optimising one can hurt the other. Batching raises throughput but raises per-request latency.
  • In an interview, state which one you are optimising for and name the trade-off.
