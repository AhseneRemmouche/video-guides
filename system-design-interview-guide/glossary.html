Glossary

Every system-design term in this crash course, explained for beginners.

Every term this course uses, explained in plain language for someone preparing for a first system-design interview. Terms are grouped by topic. Each step page links the first time it uses a term, and the link lands on its definition here.

Computer internals

How a single computer stores and runs your program, from the smallest unit of data up to the chips that hold and process it.

Bit
The smallest unit of data a computer holds: a single 0 or 1. Everything else is built from bits.
Byte
A group of 8 bits, enough to store one character such as the letter "A". Storage sizes grow from bytes to kilobytes (KB), megabytes (MB), gigabytes (GB) and terabytes (TB).
Disk storage
Long-term, non-volatile storage that keeps data even when the power is off. It holds the operating system, applications and files, usually hundreds of gigabytes to several terabytes, and comes as an HDD or an SSD.
HDD (hard disk drive)
A disk that stores data on spinning magnetic platters. It is cheap per gigabyte but slower than an SSD, with typical read speeds of about 80 to 160 MB/s.
SSD (solid-state drive)
A disk with no moving parts that stores data in flash memory. It is faster than an HDD, with typical speeds of about 500 to 3,500 MB/s.
RAM (random-access memory)
Fast, volatile memory that holds the variables and runtime data a program is using right now. It needs power to keep its contents, and is much faster than disk, often above 5,000 MB/s.
Volatile memory
Memory that loses everything it holds when the power is cut, such as RAM and CPU cache. Non-volatile storage, such as a disk, keeps its data without power.
Cache memory
A very small (megabytes) but extremely fast memory inside the CPU that stores frequently used data. The CPU checks its cache levels (L1, then L2, then L3) before going to the slower RAM; L1 access is measured in nanoseconds.
CPU (central processing unit)
The chip that runs the program, repeating a fetch-decode-execute cycle over machine code. It is the brain of the computer.
Compiler
A tool that translates code written in a high-level language into the machine code the CPU can run directly.
Machine code
The low-level instructions, expressed in binary, that a CPU executes directly. High-level source code is compiled down to machine code before it runs.
Motherboard
The main circuit board that connects all the parts of a computer, letting the CPU, RAM, cache and disk communicate with each other.

Production architecture & operations

The parts and practices that keep a real, deployed application running, shipping updates and recovering from problems.

CI/CD
Continuous integration and continuous deployment: an automated pipeline (for example Jenkins or GitHub Actions) that pushes new code through tests and out to production. It makes releases frequent and repeatable.
Logging
Recording what an application does so you can look back and understand its behaviour. Logs are usually stored on an external server; backend tools include pm2 and frontend tools include Sentry.
Monitoring
Continuously watching a system's health and metrics so you notice problems early, often by reading its logs and performance data.
Alerting
Automatically notifying the team when something goes wrong, for example a push notification that lands in a Slack channel so an engineer can respond quickly.
Staging environment
A test environment that closely mirrors production, used to reproduce and fix bugs safely. You debug here rather than in production, where real users would be affected.
Hotfix
A quick, temporary patch rolled out to fix an urgent problem in production. It buys time until a proper, well-tested fix can follow.

Design principles & CAP theorem

The goals a good design aims for and the core trade-off every distributed system must face.

System design
The practice of deciding how the parts of a whole system fit together and reasoning about the trade-offs between them. A system-design interview tests this thinking, not your ability to write code.
Scalability
How well a system keeps working as the number of users or the amount of data grows. A scalable design can handle much more load without being rebuilt.
Maintainability
How easy it is for future developers to understand, fix and improve a system. Clear, simple designs are cheaper to maintain over time.
Efficiency
Making the best use of resources such as CPU, memory, storage and network so the system does its job without waste.
CAP theorem
Brewer's theorem, which states that a distributed system can guarantee only two of three properties at once: Consistency, Availability and Partition tolerance. When the network splits, you must choose which one to give up.
Consistency
In CAP, the guarantee that every node sees the same data at the same time, like a shared document where everyone sees each edit. Choosing consistency can mean refusing to answer until all nodes agree.
Availability
In CAP, the guarantee that the system always responds to a request. More broadly, availability is a measure of how reliably a service is up, expressed in "nines" (see uptime).
Partition tolerance
The ability of a distributed system to keep working when the network connection between its nodes is broken (a network partition). Real networks fail, so most distributed systems must tolerate partitions.
Distributed system
A system whose work is spread across several machines (nodes) that cooperate over a network. Spreading work out adds scale but also the CAP trade-off.
Node
One machine or server that takes part in a distributed system. The nodes share data and work with each other over the network.

Reliability & performance

How we promise, measure and protect a service's dependability, and how we talk about its speed.

SLO (service level objective)
An internal goal a team sets for its service, for example "respond within 300 ms, 99.9% of the time". It is a target the team aims to meet.
SLA (service level agreement)
A formal contract with customers promising a level of service, for example 99.99% availability. Breaking an SLA can mean refunds or penalties.
Uptime (nines of availability)
How much of the time a service is working, measured in "nines". 99.9% ("three nines") allows about 8.76 hours of downtime per year, while 99.999% ("five nines") allows only about 5 minutes per year.
Downtime
The time a service is not working and cannot respond to users. Higher uptime targets mean less allowed downtime.
Reliability
How consistently a system does what it should, without failing. It is one of the measures of a dependable, available service.
Fault tolerance
The ability of a system to keep working correctly even when some of its parts fail. It is usually achieved with redundancy and graceful degradation.
Redundancy
Keeping spare, backup components ready to take over if a primary one fails. A redundant design has no single part whose failure stops everything.
Graceful degradation
Designing a system so that if some features fail, the core keeps working instead of the whole thing going down. Users lose extras, not everything.
Throughput
How much work a system completes per unit of time, such as requests per second, queries per second or bytes per second. Higher throughput is generally better.
Latency
The time it takes to get a response for a single request. Lower latency feels faster; optimising throughput (for example by batching) can sometimes raise latency.
RPS (requests per second)
A measure of server throughput: how many requests a server can handle each second.
QPS (queries per second)
A measure of database throughput: how many queries a database can handle each second.

Networking

How data finds its way across the internet, from addresses and packets to the transport rules and the naming system.

IP address
A unique identifier for a device on a network, used to send data to the right place. It comes in two versions, IPv4 and IPv6.
IPv4
The older IP address format, 32 bits long, giving about 4 billion possible addresses. That supply is nearly exhausted, which is why IPv6 exists.
IPv6
The newer IP address format, 128 bits long, giving a vastly larger pool of addresses than IPv4.
Packet
A small chunk that data is split into so it can travel across a network. Each packet carries an IP header plus a piece of the actual content.
IP header
The part of a packet, defined by the Internet Protocol, that records the sender's and receiver's IP addresses so the network knows where to deliver it.
TCP (Transmission Control Protocol)
A reliable transport protocol that sets up a connection with a three-way handshake and uses sequence numbers to deliver data complete and in order. It is used when accuracy matters more than raw speed.
UDP (User Datagram Protocol)
A faster transport protocol with no connection setup and no delivery guarantee. It suits live video calls and streaming, where speed matters more than perfect delivery.
Three-way handshake
The three-message exchange TCP uses to open a connection before data flows, so both sides agree they are ready to talk.
DNS (Domain Name System)
The internet's phone book, which translates a human-friendly domain name into the IP address of a server. It is overseen by ICANN, and registrars such as Namecheap or GoDaddy sell domain names.
DNS record
An entry in DNS that maps a domain to information such as an IP address. Common types include A and AAAA records.
A record
A DNS record that points a domain name to an IPv4 address. The matching AAAA record points to an IPv6 address.
Port
A number that identifies a specific service on a machine, such as 80 for HTTP or 22 for SSH. An IP address together with a port forms a unique endpoint.
Firewall
A security barrier that monitors and controls network traffic, allowing wanted connections and blocking unwanted ones.
Public IP
An IP address that is reachable from the wider internet. It lets devices outside your local network find your machine.
Private IP
An IP address used only inside a local network and not reachable directly from the internet. Many devices can share one public IP behind it.
Static IP
An IP address that stays the same over time, useful for servers that other machines must always find at a fixed location.
Dynamic IP
An IP address that can change over time, typically assigned automatically to everyday devices.

Protocols & APIs

The agreed languages applications use to talk to each other, and the design choices behind the interfaces they expose.

HTTP (HyperText Transfer Protocol)
The request-response protocol of the web, running on top of TCP/IP. A client sends a request and the server sends back a response.
HTTPS
HTTP with encryption, so data between the client and server is protected in transit and cannot be easily read or tampered with.
Status code
A three-digit number in an HTTP response that says what happened: 2xx success, 3xx redirect, 4xx client error and 5xx server error.
HTTP method
The verb in an HTTP request that says what action to take, such as GET, POST, PUT, PATCH or DELETE.
Stateless
A design where each request carries everything the server needs and the server keeps no memory of previous requests. HTTP is stateless, which makes it easier to scale.
WebSocket
A two-way, long-lived connection that lets a server push real-time updates to the client. It suits chat, live scores and stock feeds.
SMTP
The protocol used to send email between mail servers.
IMAP
An email protocol for reading mail that stays on the server, so you can access the same inbox from multiple devices.
POP3
An email protocol that downloads mail to a single device, typically removing it from the server.
FTP (File Transfer Protocol)
A protocol for transferring files between computers over a network.
SSH (Secure Shell)
A protocol for securely logging in to a remote machine and running commands on it over an encrypted connection.
WebRTC
A protocol for real-time browser-to-browser voice, video and file sharing, without routing media through a central server.
MQTT
A lightweight messaging protocol designed for IoT devices and low-bandwidth or unreliable networks.
AMQP
An enterprise messaging protocol used by message brokers such as RabbitMQ, where producers send messages through a broker to consumers.
RPC (remote procedure call)
A style where your code calls a function that actually runs on another machine as if it were local, hiding the network details.
API (application programming interface)
A defined set of endpoints and rules that lets one program use another's features or data.
CRUD
The four basic operations on data: create, read, update and delete. Most APIs map these onto HTTP methods.
REST
A popular API style that is stateless and uses standard HTTP methods and usually JSON. It is simple and widely understood, but can over-fetch or under-fetch data.
GraphQL
An API style where the client asks for exactly the fields it needs in one strongly typed query. Requests use POST, and it returns 200 even on errors, placing error details in the response body.
gRPC
A high-performance API style built on HTTP/2 and protocol buffers. It is efficient and great for communication between microservices, but less human-readable than JSON.
Protocol buffers
A compact, strongly typed binary data format from Google, used by gRPC. It is smaller and faster to parse than JSON but not human-readable.
JSON (JavaScript Object Notation)
A lightweight, human-readable text format for structured data, widely used to send data in APIs.
Idempotent
An operation that has the same effect no matter how many times you repeat it. A GET request should be idempotent and must never change data.
Pagination
Returning a large result set in smaller pages, for example with limit and offset or date-range filters, instead of all at once.
Versioning
Keeping older clients working by offering a new version of an API (for example a v2 endpoint) alongside the old one. In GraphQL you add new fields rather than removing old ones.
Rate limiting
Capping how many requests a client can make in a period of time, which protects an API from abuse and denial-of-service attacks.
CORS (cross-origin resource sharing)
A browser security mechanism that controls which other domains are allowed to call your API.

Caching, CDNs & proxies

Techniques that store copies of data closer to users and servers that sit in the middle of requests to speed things up and add control.

Caching
Keeping a copy of data in fast, temporary storage so future requests for it are quicker. Caches can live in the browser, on a server, in a CDN or in a database.
Cache hit
When requested data is already in the cache and can be returned without going to the original source. A higher ratio of hits means the cache is more effective.
Cache miss
When requested data is not in the cache, so the system must fetch it from the slower original source. Response headers such as X-Cache show whether a request was a HIT or a MISS.
Cache-Control
An HTTP header that tells browsers and CDNs how long to cache a response, for example a max-age of 7200 seconds (2 hours).
Write-around
A write policy that writes data straight to storage and bypasses the cache. It suits data whose writes are not critical to serve immediately.
Write-through
A write policy that writes to the cache and the storage together. It keeps them consistent but is slower because every write touches both.
Write-back
A write policy that writes to the cache first and to storage later. It is fast but risks losing data if the system crashes before the storage write happens.
Eviction policy
The rule a cache uses to decide what to remove when it is full, such as LRU, FIFO or LFU.
LRU (least recently used)
An eviction policy that removes the item that has gone unused for the longest time when the cache needs space.
CDN (content delivery network)
A network of geographically distributed servers that serve static content such as images, video, CSS and JavaScript from the edge location nearest the user, lowering latency.
Pull-based CDN
A CDN that fetches content from your origin server the first time it is requested and then caches it. It needs less management and suits regularly updated static content.
Push-based CDN
A CDN where you upload content to the origin and it is distributed out to the edge servers. It needs more management and suits large, infrequently updated files.
Proxy server
A server that sits between a client and another server, often to add caching, anonymising or load balancing. The two main kinds are forward proxies and reverse proxies.
Forward proxy
A proxy placed in front of clients that hides the client's IP address and can control internet access, monitor usage, cache and anonymise outgoing requests.
Reverse proxy
A proxy placed in front of servers that hides them and handles load balancing, web acceleration and security. Load balancers, CDNs, web application firewalls and SSL offloading are all reverse-proxy roles.

Load balancing & databases

How traffic is spread across servers, and the kinds of databases, guarantees and scaling techniques that store a system's data.

Load balancer
A kind of reverse proxy that spreads incoming traffic across several servers so no single one is overwhelmed, improving capacity and reliability. It can use algorithms such as round robin, least connections or IP hashing, and is itself a single point of failure unless made redundant.
SQL (relational) database
A database that stores data in tables and is queried with SQL, for example PostgreSQL, MySQL or SQLite. It is great for transactions, complex queries and data integrity, and is ACID-compliant.
NoSQL database
A flexible, often schema-less database that relaxes strict consistency and drops foreign keys for scale and speed. Types include key-value (Redis), document (MongoDB) and graph (Neo4j), and it suits unstructured data and quick iteration.
In-memory database
A database that keeps all its data in RAM for very fast access, such as Redis or Memcached. It is ideal for caching and session storage.
ACID
The four guarantees that make relational transactions trustworthy: Atomicity, Consistency, Isolation and Durability. Together they keep a database in a valid, reliable state.
Atomicity
The ACID guarantee that a transaction is all-or-nothing: either every part of it succeeds, or none of it is applied.
Isolation
The ACID guarantee that concurrent transactions do not interfere with each other, so each behaves as if it ran on its own.
Durability
The ACID guarantee that once a transaction is committed, its data persists even if the system then crashes.
Sharding
Splitting a database into shards spread across several servers, so each holds part of the data. Strategies include range-based, directory-based and geographic sharding, and it is a way to scale horizontally.
Replication
Keeping copies of the data on more than one server for high availability. The main patterns are master-slave and master-master.
Master-slave replication
A replication pattern with one write master and one or more read-only slaves. Writes go to the master and reads can be spread across the slaves.
Indexing
Adding an index on frequently queried columns so the database can find matching rows quickly, speeding up reads at the cost of some extra write and storage overhead.
Query optimization
Making queries run faster, for example by minimising joins and using tools like EXPLAIN or a query analyser to see how a query runs.
Redis
A popular in-memory key-value store, used for caching, session storage and as a fast NoSQL database.
