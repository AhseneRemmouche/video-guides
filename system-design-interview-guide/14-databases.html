Databases: Types, Scaling & Performance

SQL, NoSQL and in-memory databases; ACID; vertical vs horizontal scaling; sharding; replication; indexing and query optimisation.

▶ Watch this part (47:53)

A system-design interview is incomplete without a deep dive into databases (at 47:53). This page covers the main database types, the ACID properties that relational databases guarantee, the two ways to scale a database, how sharding and replication spread data across machines, the techniques that make queries faster, and a reminder about the CAP theorem that ties it all together.

Types of database

There are different types of database, each designed for specific tasks and challenges (at 48:16). Picking the right type is one of the first decisions in a design, so be ready to justify your choice.

Relational / SQL

Think of a relational database like a well-organised filing cabinet, where files are neatly sorted into drawers and folders (at 48:16). SQL databases — PostgreSQL, MySQL, SQLite — store data in tables and are queried with the SQL language. They are great for transactions, complex queries, and data integrity, and they are ACID-compliant.

NoSQL

NoSQL databases drop the strict consistency guarantee of ACID in exchange for flexibility (at 49:28). Picture a brainstorming board of sticky notes you can add or remove in any shape or form. They are schema-less — no fixed table structure and no foreign keys linking tables together — which makes them good for unstructured data, scalability, and quick iteration. They come in families: key-value (Redis), document (MongoDB), and graph (Neo4j).

In-memory

An in-memory database keeps everything in RAM rather than on disk, like a whiteboard for quick calculations (at 50:16). That makes data retrieval lightning fast. Examples are Redis and Memcached, used primarily for caching and session storage.

ACID: the promises a relational database keeps

Relational databases are ACID-compliant, which means they maintain four properties (at 49:04):

  • Atomicity — a transaction is all-or-nothing. Either every step happens, or none does.
  • Consistency — after a transaction, the database is left in a valid state.
  • Isolation — transactions run independently, as if one at a time, without interfering with each other.
  • Durability — once a transaction is committed, the data is there to stay, even after a crash.
New to "transaction"? What it means in a database

A transaction is a group of database operations treated as one unit of work. Moving money is two operations — take from account A, add to account B — but it must behave as one: both succeed or both fail. ACID is the set of promises that make this safe, so you never end up with money taken from A but never added to B.

Scaling a database: up versus out

When one database server is no longer enough, you have two directions to grow (at 50:39).

Vertical scaling (scale up) improves a single server by adding more CPU, more RAM, faster or larger disk storage, or a better network (at 50:39). It is simple, but there is a hard maximum limit to what one machine can hold — so it only takes you so far.

Horizontal scaling (scale out) adds more machines to the pool instead of upgrading one (at 51:01). It supports much greater growth, and it is what makes real scalability possible — but the data now has to be distributed across the cluster, which is done with sharding or replication.

Sharding: split the data across servers

Sharding means distributing different portions — shards — of the data set across multiple servers (at 51:25). You split the data into smaller chunks and spread them out, so each server holds and serves only part of the whole. Common strategies:

  • Range-based: distribute rows by the range of a key (for example, users A–M on one server, N–Z on another).
  • Directory-based: use a lookup service that knows which server holds which data and directs each request accordingly.
  • Geographic: split the data by geographic location, keeping each region's data close to its users.
New to "shard"? What the word means

A shard is just one piece of a split-up database. If your users table is too big for one server, you cut it into parts and put each part on a different server — each of those parts is a shard. Together the shards hold the complete data set, but no one server holds all of it. The tricky part is routing each query to the shard that actually has the row you want.

Replication: keep copies for availability

Replication keeps copies of the data on multiple servers for high availability (at 51:48). There are two main arrangements:

  • Master-slave: one master database handles writes, and several read-only slave databases serve reads. Great for read-heavy workloads.
  • Master-master: multiple databases that can both read and write. More flexible for writes, but keeping the copies in agreement is harder.

Making queries faster

Scaling gives you capacity, but you also want each query to return faster (at 52:11). Three techniques:

Caching: database caching can be done through in-memory databases like Redis, to cache frequent queries and boost performance (at 52:33).

Indexing: creating an index on a frequently queried column significantly speeds up retrieval times (at 52:33). An index is like the index at the back of a book — instead of scanning every page (every row), the database jumps straight to the matching rows.

CREATE INDEX idx_users_email ON users (email);

Query optimisation: optimise queries for fast access — minimise joins and use tools like the SQL query analyser or the EXPLAIN plan to understand how a query performs (at 52:56). Running EXPLAIN shows whether your query uses an index or falls back to scanning the whole table:

EXPLAIN SELECT * FROM users WHERE email = 'a@b.com';
-- Index Scan using idx_users_email on users  (cost=0.29..8.30 rows=1)
New to "index"? Why it speeds reads but can slow writes

A database index is a separate, sorted structure that maps a column's values to the rows that hold them — like a book index mapping topics to page numbers. Lookups on that column become fast because the database no longer scans every row. The trade-off: every insert, update, or delete now also has to update the index, so writes get a little slower and the index uses extra storage. Index the columns you search on often, not every column.

Always come back to CAP

In all of these choices — type, scaling, sharding, replication — remember the CAP theorem: a distributed database can only guarantee two of Consistency, Availability, and Partition tolerance at once (at 52:56). Sharding and replication spread data across the network, so a network partition is always possible, and you will have to decide which of consistency or availability you are willing to give up when it happens.

In an interview, say this

"I'd start by matching the database type to the workload — relational and ACID for transactions and integrity, NoSQL for flexible, unstructured, fast-changing data, in-memory like Redis for caching. To scale, I prefer scaling out over scaling up once a single machine is maxed: shard to divide the data, replicate for read-heavy traffic and availability. For speed I index the columns I query on and use EXPLAIN to check the plan. And I state the CAP trade-off my design makes." Naming the trade-off, not just the tool, is what scores.

Common mistake

Reaching for "just use NoSQL, it scales" without saying what you give up — NoSQL drops the strict consistency of ACID, which is the wrong choice for money or inventory. Two more frequent slips: assuming vertical scaling has no ceiling (it has a hard hardware limit), and indexing every column — each index speeds reads but slows every write and costs storage, so index only the columns you actually filter or join on.

Recap
  • Three database families: relational/SQL (tables, SQL, ACID — transactions and integrity), NoSQL (schema-less, flexible, scales — drops strict consistency), and in-memory (Redis, Memcached — fast, for caching and sessions).
  • ACID = Atomicity (all-or-nothing), Consistency (valid state after), Isolation (independent transactions), Durability (committed data persists).
  • Vertical scaling upgrades one machine (hard limit); horizontal scaling adds machines via sharding (range, directory, geographic) or replication.
  • Master-slave = one write master + read-only slaves; master-master = multiple read/write nodes.
  • Faster queries come from caching (Redis), indexing frequently queried columns, and query optimisation (fewer joins, check with EXPLAIN).
  • Remember CAP: a distributed database guarantees only two of consistency, availability, and partition tolerance.
