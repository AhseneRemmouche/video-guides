Pillars of System Design & Trade-offs

Scalability, maintainability and efficiency, and the three jobs of any system: moving, storing and transforming data.

▶ Watch this part (07:13)

Now that you can picture a production app, step back and ask the question every interviewer is really asking: what makes a design good? This page covers the pillars of good system design, the three jobs every system does with data, and the idea that ties them all together — that every decision is a trade-off (at 7:13).

What makes a design good

Good design in system architecture comes down to a few principles. Scalability means the system keeps working as its user base grows. Maintainability means future developers can understand and improve it without fear. Efficiency means making the best use of your resources. And good design also means planning for failure: a system that stays composed when things go wrong, not just when everything runs smoothly (at 7:13). We measure that last quality with reliability and fault tolerance.

New to scalability? What it really means

Scalability is the ability to handle more work — more users, more requests, more data — by adding resources, without rewriting the system. A design that runs fine for 100 users but falls over at 100,000 is not scalable. The later pages on load balancing, caching and database scaling are all about achieving it.

The three jobs of a system

At its heart, any system does three things with data (at 7:58). Moving data is about letting data flow smoothly from one part of the system to another — user requests reaching servers, or transfers between databases — where you optimise for speed and security. Storing data is more than picking SQL or NoSQL; it is about understanding access patterns, indexing strategies, and backups, so data is both safe and available when needed. Transforming data is about turning raw data into meaningful information — aggregating log files for analysis, or converting user input into another format.

New to SQL vs NoSQL? The short version

SQL (relational) databases store data in tables with a fixed schema and are great for transactions, complex queries and strict integrity. NoSQL databases relax that structure: they are flexible and schema-less, which suits unstructured data and quick iteration. Neither is “better” — the right choice depends on how you need to read and write your data. A later page covers both in depth.

New to indexing? Why it speeds things up

An index is an extra lookup structure the database keeps on a column, like the index at the back of a book. Without it, finding a row can mean scanning every record; with it, the database jumps near the answer. You add indexes to the columns you query most — it speeds up reads, at the cost of a little extra work on writes.

Every decision is a trade-off

Here is the idea that runs through all of system design: there is no free lunch. A system optimised for read operations might perform poorly on writes. Gaining performance might cost you some simplicity, adding complexity. So it is never about finding a perfect solution — it is about finding the best solution for your specific use case, and making informed decisions about where you can afford to compromise (at 10:17).

This is also why getting the design right early matters so much. Code can be refactored fairly easily, but redesigning a whole system is a monumental task — it is costly to redo later. That is why it pays to invest time up front and lay a solid foundation that can support future features and user growth (at 14:08).

In an interview, say: “Good design balances scalability, maintainability and efficiency while planning for failure. Every system moves, stores and transforms data, and every choice is a trade-off — so for this use case I would optimise for X and accept the cost in Y.” Naming the compromise is what separates a strong answer from a list of buzzwords.
Common mistake: claiming one option is simply “the best” — fastest, most scalable, most reliable, all at once. Interviewers push back on absolute answers. There is no perfect solution, only the best fit for the requirements you were given, so always state what you are trading away.
Recap
  • Good design rests on scalability, maintainability and efficiency — plus planning for failure.
  • Every system does three jobs: moving data, storing data, and transforming data.
  • Moving data optimises for speed and security; storing data means access patterns, indexing and backups; transforming data turns raw data into meaning.
  • Every decision is a trade-off — optimising reads can slow writes, performance can cost simplicity.
  • Redesigning a system is far costlier than refactoring code, so invest in the design up front.
