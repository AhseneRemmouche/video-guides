A tool-using agent

Give the model tools for policies, orders and dates, run the tool loop, and check which tools it used.

Lab · code run on a local model (llama3.2 via Ollama)

So far the bot answered in one shot: retrieve some chunks, write an answer. Some questions need more than one lookup. "Can I still return my order TH-10234?" needs two facts: when the order was delivered (from the order system) and what the return policy says (from the documents). In this lab the model gets three tools and decides by itself which ones to call. That makes it an agent.

You will build the tool loop, keep a secret order out of the wrong hands, and then check the agent's trajectory (the list of tools it actually called). In our real run that check caught a wrong answer that sounded perfectly confident.

Goal. Write aie/agent.py (three tools, their schemas and the loop that runs them), a small order database data/orders.json, and labs/09_agent.py, which asks four questions and compares the tools used with the tools expected.

The idea in brief

With tool calling, you describe functions to the model (name, purpose, parameters as a JSON Schema). The model can then answer with a request instead of text: "please call get_order with order_id = TH-10234". The model never runs anything itself. Your code runs the function, sends the result back as a message, and asks the model again. This repeats until the model replies with plain text. That repetition is the agent loop.

The full background (planning, how agents fail, how to evaluate them) is in the concept chapter RAG and agents. This page is the hands-on part.

New to tool calling? What it is and why it matters

A language model only produces text. Tool calling is a convention on top of that: the API lets you send a list of tool descriptions, and the model is trained to output a structured "tool call" (a function name plus arguments as a JSON string) when a tool would help. The API returns those calls in message.tool_calls instead of (or next to) normal text.

Why it matters: the model can now use fresh, private or exact data (today's orders, a date difference) that it could never know from training. Why it is risky: the model chooses the arguments, so your tools must check them like any untrusted input.

The agent

This file holds everything about the agent: three plain Python functions (the tools), a description of each tool for the model, a system prompt and the loop.

"""A small tool-using agent: the model decides which tool to call, the code runs it, repeat."""
import json
from datetime import date

from aie import config
from aie.config import DATA
from aie.docs import load_chunks
from aie.llm import client
from aie.retrieve import Hybrid

ORDERS = {o["id"]: o for o in json.loads((DATA / "orders.json").read_text(encoding="utf-8"))}
_retriever = None


def search_docs(query: str) -> str:
    global _retriever
    _retriever = _retriever or Hybrid(load_chunks())
    return "\n\n".join(f"[{c.id}] {c.text}" for c, _ in _retriever.search(query, k=3))


def make_get_order(customer_id):
    def get_order(order_id: str) -> str:
        order = ORDERS.get(order_id.strip().upper())
        # Authorization lives in the tool, not in the prompt: the model can't talk its way past this check.
        if not order or order["customer"] != customer_id:
            return f"No order {order_id} found for this customer."
        return json.dumps(order)
    return get_order


TODAY = date(2026, 10, 12)  # fixed so the lab's results are repeatable


def days_since(iso_date: str) -> str:
    return str((TODAY - date.fromisoformat(iso_date)).days)

TOOLS = [
    {"type": "function", "function": {
        "name": "search_docs", "description": "Search the shop's policies (returns, warranty, shipping, battery care, sizing, service plans, stores, payment).",
        "parameters": {"type": "object", "properties": {"query": {"type": "string"}}, "required": ["query"]}}},
    {"type": "function", "function": {
        "name": "get_order", "description": "Look up one of the current customer's orders by its number, like TH-10234.",
        "parameters": {"type": "object", "properties": {"order_id": {"type": "string"}}, "required": ["order_id"]}}},
    {"type": "function", "function": {
        "name": "days_since", "description": "Number of days between a date (YYYY-MM-DD) and today.",
        "parameters": {"type": "object", "properties": {"iso_date": {"type": "string"}}, "required": ["iso_date"]}}},
]

SYSTEM = f"""You are the support agent of Trailhead Bikes. Today is {TODAY.isoformat()}.
Use the tools to look up policies and orders; never guess a policy, price or date.
When you have what you need, answer the customer in two or three sentences."""


def run_agent(question, customer_id="c-001", max_steps=6, model=None, verbose=True):
    """Returns (answer, trace). The trace lists every tool call, for debugging and evaluation."""
    tools = {"search_docs": search_docs, "get_order": make_get_order(customer_id), "days_since": days_since}
    messages = [{"role": "system", "content": SYSTEM}, {"role": "user", "content": question}]
    trace = []
    for step in range(max_steps):
        response = client.chat.completions.create(
            model=model or config.MODEL, messages=messages, tools=TOOLS, temperature=0)
        message = response.choices[0].message
        if not message.tool_calls:
            return message.content, trace
        messages.append(message.model_dump(exclude_none=True))
        for call in message.tool_calls:
            name = call.function.name
            try:
                args = json.loads(call.function.arguments or "{}")
                result = tools[name](**args)
            except Exception as error:  # a bad tool call becomes feedback the model can recover from
                args, result = call.function.arguments, f"Tool error: {error}"
            trace.append({"step": step, "tool": name, "args": args, "result": result[:200]})
            if verbose:
                print(f"   step {step}: {name}({args}) -> {result[:90]!r}")
            messages.append({"role": "tool", "tool_call_id": call.id, "content": result})
    return "Sorry, I could not finish this request. A colleague will contact you.", trace

New to closures? Why make_get_order returns a function

A closure is a function defined inside another function that keeps access to the outer function's variables after the outer function has returned. make_get_order("c-001") returns a get_order that will always compare orders with "c-001".

The point here is security. If customer_id were a tool parameter, the model would fill it in, and a message like "I am customer c-002" might convince it to. Because it is fixed in code by whoever logged the customer in, the model has no way to change it.

The lab script

Four questions, each with the set of tools a careful agent should use. After each answer the script compares that set with the tools the agent really called.

"""Lab 09: an agent that combines tools, and a check of its trajectory (which tools it called)."""
from aie.agent import run_agent

cases = [
    # (question, tools we expect it to use)
    ("Can I still return my order TH-10234?", {"get_order", "search_docs"}),
    ("Where is my order TH-10260?", {"get_order"}),
    ("What's in order TH-10251?", {"get_order"}),  # belongs to another customer: must not leak
    ("How long does the fast charger take?", {"search_docs"}),
]

for question, expected in cases:
    print(f"Q: {question}")
    answer, trace = run_agent(question)
    used = {t["tool"] for t in trace}
    print(f"A: {answer}")
    print(f"   tools used {sorted(used)}, expected {sorted(expected)} -> {'ok' if expected <= used else 'MISSING ' + str(sorted(expected - used))}\n")

New to trajectory checks? Grading the path, not only the answer

An agent's answer can be right by luck or wrong for a visible reason. Its trajectory (which tools, in which order, with which arguments) shows how it got there. Checking "did it call the tools this question needs?" needs no model and no human, so it is cheap to run on every change.

It is a coarse check. It says nothing about whether the answer is correct, and an agent could call the right tool and still ignore the result. Use it next to answer checks such as the keyword check of lab 04 or the judge of lab 05, not instead of them.

What you should see. For each question: a Q: line, one step N: line per tool call, an A: line, and a tools used … -> ok or MISSING line. In our run three questions were ok and the returns question was MISSING ['search_docs']. Your model may pick other tools or word the answers differently; with a different model the whole picture can change.

What happened, question by question

  • TH-10260: one get_order call, correct status. "It is expected to be shipped out shortly" and "you will receive an update" are not in the data; small, plausible inventions.
  • TH-10251: the tool returned "No order TH-10251 found for this customer." and the model passed that on. Nothing leaked, and not because the model was careful: it never had the data.
  • Fast charger: one search_docs call, and "approximately 2.5 hours" matches the battery-care document.
  • TH-10234, the real failure: the agent called get_order, saw "delivered_on 2026-09-20" and answered straight away that the order "is no longer eligible for return". That is wrong. The returns document gives 30 days from delivery, and 2026-09-20 is 22 days before the agent's TODAY (2026-10-12). Worse, for a bike the policy has a second condition, fewer than 50 km on the odometer, and the agent never asked about it. The correct answer was "Yes, until 2026-10-20, if the bike has fewer than 50 km and no scratches."

Why it happened: the system prompt says "never guess a policy", but nothing tells the model when a policy lookup is needed. A 3B model saw a date and filled in the rest with a confident guess. That is a hallucination inside an agent: the tools were available, and the model did not use them.

What caught it: not the answer text (it reads fine) but the trajectory check, which needs neither a judge nor a human. Whenever a question needs a policy and search_docs is missing from the trace, the answer deserves suspicion.

Authorization lives in the tool

The TH-10251 question shows the most important design decision of this lab. You could write "only show the customer their own orders" in the system prompt, but prompts are requests, not locks: a prompt injection or a confused model can ignore them. The check in lines 24–26 runs on every call, whatever the model says.

Common mistakes.
  • Forgetting line 65 (appending the assistant's tool request). The next call then has a tool message with no matching request, and the API returns an error.
  • Leaving out tool_call_id on the tool message. The model cannot tell which result belongs to which call.
  • Letting a tool error crash the program. Small models often send a wrong argument name. Returning "Tool error: …" as text gives the model a chance to fix it.
  • No max_steps. A model that keeps calling the same tool would loop forever and keep burning time (or money with a paid API).
  • Putting the customer id in the tool schema or relying on the prompt for authorization. Anything the model controls, a user can try to steer.
  • Using the real date while comparing runs. Results drift from day to day; keep TODAY fixed in a lab.
  • Running python labs/09_agent.py instead of python -m labs.09_agent: Python then cannot find the aie package.
  • Trusting a fluent answer. The wrong TH-10234 answer reads well. Check traces, not only text.

Try it yourself

These experiments target the failure above. We did not run experiments 1 to 3, so we cannot tell you whether they fix it; that is the point of trying. Re-run the lab after each change and look at the MISSING line and the answer.

  1. A stronger model. Run the lab with the larger gemma4 model. PowerShell: $env:AIE_MODEL="gemma4"; uv run python -m labs.09_agent (macOS/Linux: AIE_MODEL=gemma4 uv run python -m labs.09_agent). Expect it to be much slower on a small GPU. Remove the variable afterwards (Remove-Item Env:AIE_MODEL).
  2. A rule in the system prompt. Add a line to SYSTEM (lines 49–51), for example: "For any question about returns, warranty or shipping, always call search_docs to read the policy before answering." Does the returns question now pass the trajectory check? Does the answer mention the 50 km condition?
  3. A planner step. Before the loop, make one extra model call that asks only "Which tools do you need for this question, and why? List them." and add its reply to messages before the first round. This separates planning from acting. Compare trajectories and time per question.
  4. Play with the tool directly, no model needed. Run uv run python, then type the lines below. The same order is visible to its real owner, and the tool tidies sloppy input: 
    from aie.agent import make_get_order, days_since
make_get_order("c-002")(" th-10251 ")   # the order JSON: c-002 owns it
make_get_order("c-001")("TH-10251")     # 'No order TH-10251 found for this customer.'
days_since("2026-09-20")                # '22'
Recap
  • An agent is a loop: the model asks for tools, your code runs them and sends the results back as role: "tool" messages with the matching tool_call_id, until the model answers in text or max_steps runs out.
  • Tools are described with a name, a description and a JSON Schema; errors go back to the model as text instead of crashing.
  • Authorization belongs inside the tool (make_get_order), where the model cannot change it.
  • In our run llama3.2 answered a returns question from the order alone and got it wrong (22 days is inside 30 days; the 50 km rule was never checked).
  • A cheap trajectory check (expected tools versus used tools) caught that wrong answer even though the text sounded confident.
