Synthetic data for fine-tuning

Generate question-answer pairs from the documents, filter and deduplicate them, and export a fine-tuning file.

Lab · code run on a local model (llama3.2 via Ollama)

Finetuning needs examples: hundreds or thousands of questions with the answers you want the model to give. Writing them all by hand is slow. A common shortcut is synthetic data: ask a model to write the examples from your own documents, then filter out the bad ones. In this lab you generate question-answer pairs from the eight Trailhead documents, check them with two cheap filters, and export them in the chat format that most finetuning services accept.

Goal. Generate pairs with llama3.2 and a schema, drop pairs whose numbers are not in the source document, remove duplicates, write runs/finetune.jsonl in the chat JSONL format, and see what the filters cannot catch.
This lab does not train a model. It stops at the training file. Training even a small model needs more memory, time and care than our 4 GB laptop GPU allows. What you would do with the file, when finetuning is worth it, and how LoRA reduces the cost are explained in the concept chapter Finetuning. How to judge and clean data in general is in Dataset engineering.

The idea in brief

Synthetic data is cheap to produce and easy to scale: one prompt per document, a few seconds per call. Its weakness is quality. A model can misread the document, invent a number, ask a question the document doesn't answer, or write the same question five times. So synthetic data is always generate, then filter. Our filters are deliberately simple and fast:

  • Grounding check: every number in the answer must appear in the source document. Invented prices or day counts are the most damaging errors for a shop, and numbers are easy to check with code.
  • Deduplication: questions that are identical after lower-casing and removing punctuation are kept once.

The result is formatted as conversations (system, user, assistant), one per line, because that is what supervised finetuning on a chat model trains on.

New to finetuning data? What a training example looks like

A chat model is finetuned on whole conversations. Each example says: "given this system message and this user message, the assistant should reply with this." During training the model's numbers are nudged so that the assistant reply becomes more likely. Whatever is in your examples is what the model learns: the facts, but also the length, tone and format of the answers. If every answer in the file is a short fragment without citations, the finetuned model learns to answer in short fragments without citations. That is why the content of the file matters more than its size.

New to JSONL? One JSON object per line

JSONL ("JSON Lines") is a text file where each line is one complete JSON object. You already use it for the eval set (evals/qa.jsonl). It suits datasets because you can add, count, shuffle or split examples line by line, and a tool can read a huge file without loading it all at once. The catch: an object must stay on one line, so newlines inside a text are written as \n.

Generation and filters

"""Generate question-answer pairs from the documents, then filter them."""
import re

from pydantic import BaseModel

from aie.llm import chat_json


class QA(BaseModel):
    question: str
    answer: str


class QAList(BaseModel):
    pairs: list[QA]


GEN_PROMPT = """Write {n} different questions a customer might ask that this document answers,
each with a short correct answer taken from the document. Vary the wording; some questions should be casual.
Reply with JSON: {{"pairs": [{{"question": "...", "answer": "..."}}]}}"""


def generate(doc_text, n=4):
    messages = [{"role": "system", "content": GEN_PROMPT.format(n=n)}, {"role": "user", "content": doc_text}]
    return chat_json(messages, QAList, temperature=0.8).pairs


def normalize(text):
    return " ".join("".join(ch for ch in text.lower() if ch.isalnum() or ch == " ").split())


def is_grounded(pair, doc_text):
    """Cheap filter: every number in the answer must appear in the document."""
    return all(num in doc_text for num in re.findall(r"\d+(?:[.,]\d+)?", pair.answer))
// Generate question-answer pairs from the documents, then filter them.
import { z } from "zod";
import { chatJson } from "./llm.js";

export const QA = z.object({ question: z.string(), answer: z.string() });
export const QAList = z.object({ pairs: z.array(QA) });
export type QA = z.infer<typeof QA>;

const genPrompt = (n: number) => `Write ${n} different questions a customer might ask that this document answers,
each with a short correct answer taken from the document. Vary the wording; some questions should be casual.
Reply with JSON: {"pairs": [{"question": "...", "answer": "..."}]}`;

export async function generate(docText: string, n = 4): Promise<QA[]> {
  const messages = [{ role: "system" as const, content: genPrompt(n) }, { role: "user" as const, content: docText }];
  return (await chatJson(messages, QAList, "QAList", undefined, { temperature: 0.8 })).pairs;
}

/** Lower case, letters, digits and single spaces only: "Do you ship?!" and "do you  ship" become equal. */
export function normalize(text: string): string {
  return text.toLowerCase().replace(/[^\p{L}\p{N} ]/gu, "").split(" ").filter(Boolean).join(" ");
}

/** Cheap filter: every number in the answer must appear in the document. */
export function isGrounded(pair: QA, docText: string): boolean {
  return (pair.answer.match(/\d+(?:[.,]\d+)?/g) ?? []).every((num) => docText.includes(num));
}

The lab script

"""Lab 13: build a fine-tuning dataset from your documents: generate, filter, deduplicate, export."""
import json

from aie.config import RUNS
from aie.docs import load_docs
from aie.rag import load_prompt
from aie.synth import generate, is_grounded, normalize

kept, seen = [], set()
stats = {"generated": 0, "not grounded": 0, "duplicate": 0}
for doc_id, text in load_docs().items():
    for pair in generate(text):
        stats["generated"] += 1
        if not is_grounded(pair, text):
            stats["not grounded"] += 1
            print(f"  dropped (a number is not in {doc_id}): {pair.answer[:90]!r}")
            continue
        key = normalize(pair.question)
        if key in seen:
            stats["duplicate"] += 1
            continue
        seen.add(key)
        kept.append((doc_id, pair))

# Chat format used by most fine-tuning APIs: one JSON object with a "messages" list per line.
system = load_prompt("baseline").strip()
out = RUNS / "finetune.jsonl"
out.parent.mkdir(exist_ok=True)
with open(out, "w", encoding="utf-8", newline="\n") as f:
    for _, pair in kept:
        f.write(json.dumps({"messages": [
            {"role": "system", "content": system},
            {"role": "user", "content": pair.question},
            {"role": "assistant", "content": pair.answer}]}, ensure_ascii=False) + "\n")

print(f"\n{stats} -> kept {len(kept)} examples in runs/{out.name}")
for doc_id, pair in kept[:4]:
    print(f"  [{doc_id}] Q: {pair.question}\n  {' ' * len(doc_id)}   A: {pair.answer}")

import { mkdirSync, writeFileSync } from "node:fs";
import path from "node:path";
import { RUNS } from "../src/config.js";
import { loadDocs } from "../src/docs.js";
import { loadPrompt } from "../src/rag.js";
import { generate, isGrounded, normalize, type QA } from "../src/synth.js";

const kept: [docId: string, pair: QA][] = [];
const seen = new Set<string>();
const stats = { generated: 0, "not grounded": 0, duplicate: 0 };
for (const [docId, text] of Object.entries(loadDocs())) {
  for (const pair of await generate(text)) {
    stats.generated += 1;
    if (!isGrounded(pair, text)) {
      stats["not grounded"] += 1;
      console.log(`  dropped (a number is not in ${docId}): ${JSON.stringify(pair.answer.slice(0, 90))}`);
      continue;
    }
    const key = normalize(pair.question);
    if (seen.has(key)) {
      stats.duplicate += 1;
      continue;
    }
    seen.add(key);
    kept.push([docId, pair]);
  }
}

// Chat format used by most fine-tuning APIs: one JSON object with a "messages" list per line.
const system = loadPrompt("baseline").trim();
const out = path.join(RUNS, "finetune.jsonl");
mkdirSync(RUNS, { recursive: true });
const lines = kept.map(([, pair]) => JSON.stringify({ messages: [
  { role: "system", content: system },
  { role: "user", content: pair.question },
  { role: "assistant", content: pair.answer },
] }) + "\n");
writeFileSync(out, lines.join(""), "utf8");

console.log(`\n${JSON.stringify(stats)} -> kept ${kept.length} examples in runs/${path.basename(out)}`);
for (const [docId, pair] of kept.slice(0, 4)) {
  console.log(`  [${docId}] Q: ${pair.question}\n  ${" ".repeat(docId.length)}   A: ${pair.answer}`);
}

What the filters cannot see

The grounding check is a text search

is_groundedisGrounded asks "does this number appear in the document?" with num in doc_textdocText.includes(num). That is a search for characters, not for numbers. The battery document contains "10 and 30 degrees", so an answer that says "3 hours" passes: the character "3" is inside "30". We checked this directly, without any model call:

In TypeScript, save these lines as check.ts in the project folder:

import { loadDocs } from "./src/docs.js";
import { isGrounded } from "./src/synth.js";
const t = loadDocs()["battery-care"]!;
console.log(isGrounded({ question: "q", answer: "About 3 hours." }, t), isGrounded({ question: "q", answer: "About 7 hours." }, t));
pnpm tsx check.ts

It prints true false, the same result as the Python check (the test is the same plain text search). Delete check.ts when you are done.

uv run python -c "from aie.docs import load_docs; from aie.synth import QA, is_grounded; t = load_docs()['battery-care']; print(is_grounded(QA(question='q', answer='About 3 hours.'), t), is_grounded(QA(question='q', answer='About 7 hours.'), t))"
True False

"3 hours" is accepted although no "3" appears on its own anywhere in the battery document; "7 hours" is correctly rejected. The same happens with "1" inside "10" or "5" inside "50". A stricter version would match whole numbers only (for example with a regular expression and word boundaries), and an even better one would also check the unit. Even then, a number can be in the document and still be the wrong number for that question: "4.5" is in the document as a charging time, so an answer giving 4.5 as the range would pass.

Good-looking questions can still be weak

Look at the third example in the output: "Is there a way to prevent the battery light from blinking red?" with the answer "If the battery light blinks red three times, the battery is too cold or too hot to charge. Do not open the battery case; this voids the warranty." Both sentences are copied from the document, but they don't answer the question: the customer asked how to prevent the blinking, and the answer only says what it means, then adds a warranty rule nobody asked about. There is no digit in it ("three" is a word), so the grounding check has nothing to test, and it is not a duplicate. It was kept. Neither filter can judge whether an answer actually answers its question.

Look at the fourth example in the output: "What happens if I try to charge my e-bike battery with the case open?" with the answer "It voids the warranty, so don't open the battery case while trying to charge it." The document says that opening the battery case voids the warranty; it says nothing about charging with an open case. The question invents a situation, and the answer stitches two sentences together. It has no numbers, so the grounding check can't object, and it is not a duplicate. It was kept. Neither filter can judge whether a question makes sense or whether a customer would ever ask it.

The deduplication has a similar limit. It only removes questions that are identical after normalization. In our Python run, the file contained,Our file contains, from the sizing document, both "Can I exchange my bike for another size within a certain timeframe?" and "How long do I have to exchange my bike for another size?". They ask the same thing in different words, and both were kept. Look for pairs like these in your own file. Near-duplicates like these are usually caught by comparing embeddings, the same trick as the semantic cache in lab 11.

Common mistakes
  • Trusting "0 dropped". Zero rejections can mean clean data or a filter that can't see the problems. Our filter passes "3 hours" for a document that only says "30 degrees". Read a sample of the file yourself, every time.
  • Generating from the documents and testing on questions from the same documents. If you later finetune on this file, keep the eval set (evals/qa.jsonl) separate and written independently, or the scores will look better than the model is.
  • Using the eval questions as training data. Never copy eval cases into a training file; the eval would then measure memory, not skill.
  • Finetuning to teach facts that change. Prices and delivery times change; a finetuned model keeps the old ones until you train again. Facts usually belong in documents and RAG; finetuning suits style, format and behaviour. See Finetuning.
  • Broken JSONL. Writing json.dumps(..., indent=2) spreads one example over many lines and the file is no longer JSONL. Keep one object per line, as line 34 does. In TypeScript the same mistake is JSON.stringify(obj, null, 2).
  • Expecting the same counts as ours. Temperature 0.8 means a different set of pairs every run, and occasionally chat_jsonchatJson may fail validation more than its retries allow and stop the script with a ValidationErrorZodError. Run it again.

Recap
  • Synthetic data means generate, then filter: generate() asks llama3.2 for 4 pairs per document as validated JSON, at temperature 0.8 for variety.
  • Our run: 32 generated, 0 not grounded, 0 duplicates, 32 kept, written to runs/finetune.jsonl.
  • Each line is {"messages": [system, user, assistant]}; the assistant text is what a finetuned model learns to produce, including its style.
  • The filters are cheap and limited: the grounding check is a text search ("3" passes because of "30"), and they kept a weak, invented question and paraphrased duplicates. A person must read the data.
  • This lab does not train a model. The Finetuning chapter explains the next steps and when they are worth it.
