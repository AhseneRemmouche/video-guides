RAG and agents

Retrieval architectures and optimizations, then agents: tools, planning, failure modes and evaluation. Read with book chapter 6.

Read with chapter 6 · RAG and Agents of the book. This page explains the ideas in its own words and links them to the labs.

A foundation model only knows what was in its training data, frozen at some date, and it knows none of your private documents. Two patterns fix this. Retrieval-augmented generation (RAG) finds the relevant pieces of your own data and pastes them into the prompt, so the model answers from them. An agent goes further: the model decides by itself which tools to call (search, look up an order, compute a date), reads the results, and keeps going until it can answer.

This chapter explains both, from the inside: how retrieval actually ranks text, how to measure and improve it, what an agent loop is, how agents fail, and how to keep their tools safe.

Why this matters for your project. The Trailhead Bikes bot becomes useful in this part of the labs. Lab 06 builds and measures three retrievers, lab 07 answers from retrieved chunks, and lab 09 turns the bot into an agent with three tools. All the numbers on this page come from those real runs.

Why RAG: context beats memory

In lab 04 the bot answered 20 questions from memory alone. Its keyword pass rate was 30 %. It invented a five-year frame warranty, quoted shipping prices in dollars and said it delivers to Switzerland. Nothing was wrong with the model: it simply had never seen the shop's policies, so it produced plausible text, which is what a model does when it lacks facts. That is a hallucination.

In lab 07 the same model, with the same questions, first retrieves three chunks of the shop's documents and answers from them with the rag_v2 prompt. The keyword pass rate went to 80 %, and most answers cite the chunk they came from, like [shipping#0]. This is called grounding: the answer is tied to a source you can check.

There is a price. The average input grew from about 63 tokens per question (baseline) to about 372 (RAG), because each prompt now carries three chunks. The answers in that run were still faster on average (5.8 s against 8.8 s), likely because the grounded answers were much shorter; timings on your machine will differ. And RAG brings new ways to fail: if the retriever brings back the wrong chunk, the model faithfully answers from the wrong text. Look at q08 in lab 07: asked about Switzerland, the bot said "I don't know". The shipping document lists the countries it serves, and Switzerland is not among them, so the right answer ("no") has to be inferred from an absence, which the small model did not do. Whether the miss comes from retrieval or from the model is something only a separate retrieval measurement can tell you. A RAG system is only as good as its retriever, which is why most of this chapter is about retrieval.

New to RAG vs long context? Why not paste all the documents every time?

Our eight policy documents would fit in a modern context window. For a small, stable knowledge base that is a reasonable choice. But real knowledge bases have thousands of pages, cost grows with every token you send on every call, long prompts are slower, and models can overlook facts buried in the middle of a long context (see Prompt engineering). Retrieval sends only the few relevant pieces. Many systems combine both: a generous context, filled by a retriever.

The two halves of a RAG system

A RAG system has an offline part and an online part. Indexing runs once, or whenever documents change: split each document into chunks, compute whatever the search needs (word counts, embeddings) and store it. Querying runs on every question: the retriever finds the best chunks, the code pastes them into the prompt, and the model writes the answer. In our project, aie/docs.py does the splitting, aie/retrieve.py holds the retrievers, and aie/rag.py builds the prompt.

Retrieval algorithms

A retriever takes a question and returns a ranked list of chunks with scores. There are two big families, and our lab builds one of each and then combines them.

Term-based retrieval: BM25

Term-based retrieval matches words. The classic scoring function is BM25, which has powered search engines for decades. For each word of the question that appears in a chunk, it adds points, following three intuitions:

  • Rare words matter more. "the" is in every chunk and tells you nothing; "hygiene" or "odometer" is in very few and is a strong signal. This weight is the inverse document frequency (idf), computed once per word: the fewer chunks contain the word, the higher its idf.
  • More occurrences help, with diminishing returns. A word appearing twice is a better sign than once, but ten times is not ten times better. The parameter k1 (1.5 in our code) controls how fast it saturates.
  • Long chunks are penalised a little. A long text contains many words by chance. The parameter b (0.75) controls how much the chunk length counts.

Our BM25 class in aie/retrieve.py is about 20 lines of plain Python. Before counting, tokenize lowercases the text, keeps letters and numbers and drops a short list of stopwords. BM25 is fast, needs no model, is easy to explain, and is excellent at exact terms: product names, order numbers, error codes. Its weakness is that it knows nothing about meaning. In lab 06, BM25 missed q08, "Do you deliver to Switzerland?", because the shipping document says "We ship to …" and lists the countries; "deliver" is not there, and "Switzerland" is not either (it lists the countries served, not the ones excluded). The three chunks it returned all came from the warranty document.

Embedding-based retrieval: vector search

Embedding-based (or "dense") retrieval matches meaning. An embedding model turns any text into a vector, a list of numbers, such that texts with similar meaning get vectors that point in similar directions. We use nomic-embed-text through Ollama. At indexing time every chunk is embedded once; at query time the question is embedded and compared with every chunk vector using cosine similarity. Our EmbeddingIndex normalises all vectors to length 1, so cosine similarity becomes a single matrix product: self.matrix @ q.

With 23 chunks, comparing the question with every vector takes no time. With millions, comparing with all of them is too slow, so vector databases use approximate nearest neighbour (ANN) indexes. They organise vectors into clusters or graphs so that a search only visits a small part of the collection and returns almost the best matches, much faster. You trade a little recall for a lot of speed, and most libraries let you tune that trade-off.

Embeddings have their own blind spots: exact identifiers, rare names and numbers. In lab 06 the embedding retriever missed q06, "Where do I find the frame number?". The answer is in the warranty document, but all three chunks it returned came from the sizing guide, which is full of frame sizes. "Frame" dominated the meaning; "number" did not pull hard enough.

New to embedding models? The prefixes our code adds

nomic-embed-text was trained to expect a short task prefix: chunks are embedded as search_document: … and questions as search_query: …. Leaving them out still "works" but usually ranks worse. Other embedding models have other conventions, or none, so read the model card. Also, never mix vectors from two different embedding models in one index: their numbers are not comparable.

Because they fail on different questions, combining them is a good bet. That is hybrid search. The scores themselves can't be added (BM25 scores are unbounded; cosine similarities sit between −1 and 1), so a popular trick ignores the scores and uses only the ranks: reciprocal rank fusion (RRF). Every chunk gets 1 / (c + rank) from each list it appears in, and the totals decide the final order. The constant c = 60 is the common default from the original RRF paper; it stops the first rank from dominating everything. Here is the whole function from our code:

def reciprocal_rank_fusion(result_lists, k=3, c=60):
    """Merge ranked lists: each chunk gets 1/(c + rank) from every list it appears in."""
    scores, by_id = {}, {}
    for results in result_lists:
        for rank, (chunk, _) in enumerate(results, start=1):
            scores[chunk.id] = scores.get(chunk.id, 0.0) + 1 / (c + rank)
            by_id[chunk.id] = chunk
    best = sorted(scores, key=scores.get, reverse=True)[:k]
    return [(by_id[i], scores[i]) for i in best]

Our Hybrid class asks each retriever for its top 10 (pool=10), fuses them, and keeps the top 3.

Here are the real lab 06 results on the 18 answerable questions (23 chunks from 8 documents, top 3 retrieved):

retriever        hit@1   hit@3     MRR
BM25               83%     94%    0.89
Embeddings         89%     94%    0.91
Hybrid (RRF)       89%     94%    0.92

On this tiny set the three are close, and hybrid is only slightly ahead on MRR. Hybrid fixed q08 (the BM25 miss) but still missed q06, because both of its inputs ranked sizing chunks high for that question. Don't over-read differences of one question out of 18; with a small eval set, a single question moves hit@1 by more than 5 points. The lesson is the method, not the winner: measure your retrievers on your questions.

Evaluating retrieval

Retrieval can be tested on its own, without the model, which is fast and repeatable. You need questions labelled with where the answer lives; our evals/qa.jsonl has a source document for every answerable question. Common measures:

  • Hit rate at k (hit@k): the share of questions where a correct source appears in the top k results. Lab 06 counts a hit when any of the top 3 chunks comes from the expected document.
  • Mean reciprocal rank (MRR): for each question take 1 / (rank of the first correct result), or 0 if it's missing, then average. Rank 1 gives 1, rank 2 gives 0.5, rank 3 gives 0.33. It rewards putting the right chunk first.
  • Precision and recall: of the chunks you returned, how many were relevant (precision); of all relevant chunks, how many you returned (recall). They need every relevant chunk labelled, which takes more work.
  • Context relevance: whether the retrieved text actually helps answer the question, often judged by an AI judge when there are no labels. Even then, check the judge against human labels (lab 05).

Then evaluate the whole pipeline end to end, as lab 07 does. Good retrieval with a bad prompt still gives bad answers, and the reverse.

Making retrieval better

Chunking

How you cut documents matters as much as how you search them. Chunks that are too big dilute the match and waste tokens; chunks that are too small lose the context that makes them understandable. Common strategies: fixed size in characters or tokens; along natural boundaries (sentences, paragraphs, headings); or recursive splitting that tries big boundaries first and smaller ones only when needed. Our chunk_doc keeps whole paragraphs and starts a new chunk when the next paragraph would push it past about 60 words (max_words=60).

Overlap repeats a bit of the previous chunk at the start of the next, so a fact that sits on a boundary is not cut in half. Ours repeats the last paragraph (overlap=1). The cost is some duplicated text in the index and occasionally two near-identical chunks in the results.

Contextual retrieval: give each chunk its context

A chunk read alone can be ambiguous. "It is free on orders over 100 EUR": what is free, shipping or returns? A simple fix is to prefix every chunk with information about where it came from. Our chunk_doc starts every chunk with its document title ("Shipping", "Returns and refunds"), which helps both BM25 (the title words become searchable) and embeddings (the vector carries the topic). A stronger version asks a model to write a one- or two-sentence summary of how each chunk fits into its document and prepends that before indexing. It costs one model call per chunk at indexing time, not per question.

Reranking

First-stage retrievers must be fast because they look at everything. A reranker is a slower, more accurate model that looks only at the top candidates, reading the question and each chunk together, and reorders them. The usual pattern: retrieve 20–50 candidates cheaply, rerank, keep the best 3–5 for the prompt. Our hybrid retriever does a light version of this idea (pool of 10 per retriever, fused, top 3), without a reranking model.

Query rewriting

Users don't phrase questions the way documents are written. Query rewriting uses a model (or rules) to turn the user's message into a better search query before retrieval. Two typical cases: a follow-up in a conversation ("and in Annecy?") must become a full question ("Is the Annecy store open on Monday?"), because the retriever does not see the chat history; and a question can be expanded with synonyms ("deliver" → "ship, shipping, delivery countries"), which would have rescued BM25 on q08. Rewriting adds a model call per question, so measure whether it pays off.

RAG beyond text

Not all knowledge is prose. Order data, prices and stock levels live in tables and databases. For those, "retrieval" can mean running a query: the model writes SQL (text-to-SQL) or, more safely, calls a fixed function with parameters, and the result rows go into the context. Our agent's get_order tool is the safe version: the model passes an order number; the code looks it up in data/orders.json and checks who owns it. If you let a model write SQL, give it a read-only account limited to the tables it needs, because generated queries can be wrong or manipulated by injected text.

Agents

An agent is a model that acts in an environment through tools, choosing what to do next based on what it has seen so far (planning). The environment is whatever the tools can reach: a document store, an orders database, a calendar, a codebase, the web. RAG is a fixed pipeline where your code always retrieves once; an agent decides whether to retrieve, what to search for, and what to do with the result.

Kinds of tools

  • Knowledge tools read information: search_docs (hybrid search over the policies) and get_order (one order as JSON) in our agent.
  • Capability tools do what models are bad at: arithmetic, dates, code execution, unit conversion. Our days_since computes the days between a date and the fixed TODAY (2026-10-12), instead of trusting the model's arithmetic.
  • Write actions change the world: create a return label, refund a payment, send an email, update a database. Our lab has none on purpose. They are the most useful and the most dangerous kind (see security below).

The tool loop

With tool calling, the model never runs anything itself. You describe each tool (name, description, JSON schema of its arguments) in the request. The model replies either with a normal answer or with one or more tool calls: "call get_order with {"order_id": "TH-10234"}". Your code runs the function, appends the result as a tool message, and calls the model again. This repeats until the model answers without a tool call or a step limit is reached. Here is the loop from aie/agent.py:

    for step in range(max_steps):
        response = client.chat.completions.create(
            model=model or config.MODEL, messages=messages, tools=TOOLS, temperature=0)
        message = response.choices[0].message
        if not message.tool_calls:
            return message.content, trace
        messages.append(message.model_dump(exclude_none=True))
        for call in message.tool_calls:
            name = call.function.name
            try:
                args = json.loads(call.function.arguments or "{}")
                result = tools[name](**args)
            except Exception as error:  # a bad tool call becomes feedback the model can recover from
                args, result = call.function.arguments, f"Tool error: {error}"
            trace.append({"step": step, "tool": name, "args": args, "result": result[:200]})
            if verbose:
                print(f"   step {step}: {name}({args}) -> {result[:90]!r}")
            messages.append({"role": "tool", "tool_call_id": call.id, "content": result})

Three design choices are worth copying. The step limit (max_steps=6) stops endless loops and caps cost. A failing tool call becomes an error message the model can read and correct, instead of crashing the program. And every call is recorded in a trace, which is what makes the agent debuggable and testable.

Planning and reflection

For a question like "Can I still return my order TH-10234?" a good plan has four steps: look up the order to get its delivery date, look up the return policy, compute the days since delivery, then compare. Some agents write such a plan explicitly before acting; others plan one step at a time, deciding each next tool call from the results so far (our loop works like this). Plans can be wrong, so many systems add reflection: after a step, or before answering, the model (or a second model) checks "Did I get everything I need? Does the answer follow from the results?" and corrects course. Reflection improves results on hard tasks but costs extra calls and latency. Keep agents as simple as the task allows: a fixed pipeline is easier to test than a free-form agent, and many problems don't need autonomy.

How agents fail

Agents add new failure modes on top of the model's usual mistakes. It helps to name them, because each has a different fix:

FailureWhat happensTypical fix
Planning errorSkips a needed step, does steps in the wrong order, stops too earlyClearer system prompt, explicit plan step, reflection, a stronger model
Wrong toolCalls a tool that can't help, or one that doesn't existBetter tool names and descriptions; fewer, more distinct tools
Wrong argumentsRight tool, bad input: invalid JSON, wrong date format, invented IDStrict schemas, validation, return readable errors so the model can retry
Goal failureCompletes steps but doesn't solve the task, or breaks a constraint (time, budget)Evaluate final outcomes, not just steps; step and cost limits
Tool failureThe tool itself is wrong, slow or downTest tools like normal code; timeouts and fallbacks

Evaluating agents by trajectory

Checking only the final answer hides why an agent failed. The trajectory (the sequence of tool calls with their arguments and results) shows it. Useful checks: did it call the tools it needed, with valid arguments? How many steps and tokens did it use? Did it call anything it should not have?

Lab 09 does the simplest trajectory check: for each question, a set of tools we expect to see. On the question "Can I still return my order TH-10234?", llama3.2 called only get_order and then told the customer the order could not be returned. That is wrong: it was delivered on 2026-09-20, 22 days before the agent's fixed date of 2026-10-12, inside the 30-day window. The trajectory check flagged the missing search_docs call, which points straight at the cause: a planning error, the model answered a policy question without reading the policy. Without the trace you would only know "wrong answer".

Memory, briefly

An agent's "memory" comes in three forms. The model's own knowledge is in its weights. Short-term memory is the conversation so far, held in the messages list and limited by the context window. Long-term memory is anything you store outside the model (past conversations, user preferences, notes the agent wrote) and bring back with retrieval when relevant, which makes it another RAG problem. Long conversations eventually need summarising or trimming, and stored memories need the same care as any personal data.

Security: tools are where damage happens

A chatbot that says something wrong is embarrassing. An agent that does something wrong can refund the wrong person or leak another customer's data. And everything the agent reads, including tool results and retrieved documents, can contain an injected instruction (see Prompt engineering). So:

  • Put authorization in the tool, not in the prompt. Our make_get_order(customer_id) builds a get_order function bound to the logged-in customer. If the order belongs to someone else, it answers "No order … found for this customer" whatever the model asks. In lab 09, asking about TH-10251 (customer c-002) as c-001 got exactly that refusal. The model can't talk its way past a check it doesn't control.
  • Least privilege. Give each agent only the tools and data it needs. A support bot does not need a "delete customer" tool.
  • Confirm write actions. Anything that spends money, sends messages or can't be undone should be shown to a human (the customer or an employee) for approval, with limits such as a maximum refund amount enforced in code.
  • Validate arguments like any untrusted input: types, formats, ranges, IDs that must exist.
  • Log trajectories so you can audit what happened and spot abuse (labs 12 and 10 show logging and guardrails).
Pitfalls and common misconceptions
  • "RAG stops hallucinations." It reduces them. If retrieval misses, the model either declines or invents; a wrong chunk gives a confidently wrong answer; and even with the right chunk a small model can fail to draw the conclusion (q08 in lab 07).
  • "Embeddings are always better than keywords." Lab 06: each missed a question the other got. Hybrid is a safer default; measure on your data.
  • Tuning the generator when retrieval is the problem. Measure retrieval separately (hit rate, MRR) before rewriting prompts.
  • Changing the embedding model without re-indexing. Old and new vectors are not comparable.
  • Chunks that make no sense alone. Add the title or a short context line to each chunk.
  • Reading too much into a tiny eval set. One question out of 18 is more than 5 points.
  • Judging agents only by final answers. Keep the trace; check which tools were called and with what.
  • Permissions in the prompt. "Only show the customer's own orders" must be code in the tool.
  • An agent where a pipeline would do. Autonomy adds cost, latency and new failure modes.
Recap
  • RAG puts relevant chunks of your data into the prompt; in our labs the keyword pass rate went from 30 % (memory) to 80 % (retrieved context).
  • Indexing (chunk, embed, store) happens offline; retrieval and generation happen per question.
  • BM25 matches rare exact words using idf; embeddings match meaning; hybrid search fuses both with RRF (1/(60 + rank)).
  • Lab 06: BM25 83 % / 94 % / 0.89, embeddings 89 % / 94 % / 0.91, hybrid 89 % / 94 % / 0.92 (hit@1 / hit@3 / MRR).
  • Measure retrieval on its own (hit rate, MRR, precision and recall, context relevance), then end to end.
  • Improve it with better chunking and overlap, titles or context on each chunk, reranking and query rewriting.
  • An agent = model + tools + planning in a loop; tools read knowledge, extend capabilities or write to the world.
  • Agents fail by bad plans, wrong tools, wrong arguments, unmet goals or broken tools; evaluate the trajectory (lab 09 caught a missing search_docs).
  • Put authorization and limits in tool code, confirm write actions, and log everything.
