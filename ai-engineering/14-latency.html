Latency and throughput

Measure time to first token, time per token and throughput with streaming and parallel requests.

Lab · code run on a local model (llama3.2 via Ollama)

"The bot is slow" is not something you can fix. "The first word appears after 0.4 s, then each token takes 160 ms, and the server handles one request at a time" is. In this last lab you measure the speed of the local model the way inference engineers do: time to first token (TTFT), time per output token (TPOT) and throughput. You will also find out something about your own setup that no benchmark from elsewhere could tell you.

Goal. Stream one answer and time its first and following chunks; send the same request 1, 4 and 8 times at once with an async clientwith Promise.all and compare total tokens per second; explain the numbers from what the server is doing.

The idea in brief

A model answers in two phases. First it reads the whole prompt at once (prefill); the wait until the first token appears is the TTFT. Then it writes the answer one token at a time (decode); the time per token is the TPOT. Total latency is roughly TTFT plus TPOT times the number of tokens. Throughput is a property of the server, not of one answer: how many tokens per second it produces for all users together. A server that can work on several requests in the same step (batching) gets much higher throughput than one that serves them one after another. The concept chapter Inference optimization explains these phases, the metrics and the techniques in depth.

New to streaming? Why the first token matters most

Without streaming, the API returns the answer only when it is complete, so the user stares at a spinner for the whole latency (15about 12 seconds in this lab). With stream=Truestream: true, the server sends small pieces ("chunks") as soon as they are generated, and the user starts reading after the TTFT. The total time is the same; the wait feels much shorter. That is why chat apps stream, and why TTFT is measured separately.

New to async TypeScript? What Promise.all does

A call to the model returns a Promise: a value that will arrive later. await pauses the function until it arrives, and while it waits, Node.js can work on other things. Calling one() four times without awaiting gives you four promises, so all four requests are already on their way. Promise.all([a, b, c]) then waits until all of them are done and returns their results in order. It is the TypeScript counterpart of Python's asyncio.gather. Node.js runs one event loop for the whole program (the scheduler that switches between waiting tasks) and starts it for you, so there is nothing to create or close. The OpenAI JavaScript client is already async, so the lab uses the same client for everything.

New to async Python? What asyncio.gather does

Normal Python code waits for each network call to finish before starting the next. With asyncio, a function marked async def can pause at await while it waits for the network, letting other tasks run. asyncio.gather(a, b, c) starts several such tasks and waits until all are done. All of them run on one event loop, the scheduler that switches between waiting tasks. asyncio.run(main()) creates an event loop, runs main() to the end and then closes the loop. That last detail caused the bug described under "Common mistakes".

The code

"""Lab 14: measure time to first token, time per output token, and throughput with parallel requests."""
import asyncio
import time

from openai import AsyncOpenAI

from aie import config
from aie.llm import client

PROMPT = [{"role": "user", "content": "In three sentences, how should I store an e-bike battery for the winter?"}]


def stream_once():
    start = time.perf_counter()
    first, pieces = None, 0
    stream = client.chat.completions.create(model=config.MODEL, messages=PROMPT, stream=True, temperature=0)
    for event in stream:
        if event.choices and event.choices[0].delta.content:
            first = first or time.perf_counter()
            pieces += 1
    end = time.perf_counter()
    return first - start, (end - first) / max(pieces - 1, 1), end - start, pieces


print("1) Streaming one answer (3 runs)")
for _ in range(3):
    ttft, tpot, total, pieces = stream_once()
    print(f"   TTFT {ttft:5.2f} s   TPOT {tpot * 1000:4.0f} ms   total {total:5.2f} s   {pieces} chunks")

aclient = AsyncOpenAI(base_url=config.BASE_URL, api_key=config.API_KEY)


async def one():
    r = await aclient.chat.completions.create(model=config.MODEL, messages=PROMPT, temperature=0)
    return r.usage.completion_tokens


async def burst(n):
    start = time.perf_counter()
    tokens = await asyncio.gather(*(one() for _ in range(n)))
    seconds = time.perf_counter() - start
    return seconds, sum(tokens) / seconds


async def main():
    # One event loop for all bursts: the async client must not outlive the loop it was used in.
    for n in (1, 4, 8):
        seconds, tps = await burst(n)
        print(f"   {n} at once: {seconds:5.1f} s wall time, {tps:5.1f} output tokens/s in total")


print("\n2) Throughput: the same request sent 1, 4 and 8 times at once")
asyncio.run(main())
// Lab 14: measure time to first token, time per output token, and throughput with parallel requests.
import type { ChatCompletionMessageParam } from "openai/resources/chat/completions";
import * as config from "../src/config.js";
import { client } from "../src/llm.js";

const PROMPT: ChatCompletionMessageParam[] = [
  { role: "user", content: "In three sentences, how should I store an e-bike battery for the winter?" },
];
const now = () => performance.now() / 1000;

async function streamOnce() {
  const start = now();
  let first: number | undefined;
  let pieces = 0;
  const stream = await client.chat.completions.create({ model: config.MODEL, messages: PROMPT, stream: true, temperature: 0 });
  for await (const event of stream) {
    if (event.choices[0]?.delta.content) {
      first ??= now();
      pieces += 1;
    }
  }
  const end = now();
  first ??= end;
  return { ttft: first - start, tpot: (end - first) / Math.max(pieces - 1, 1), total: end - start, pieces };
}

console.log("1) Streaming one answer (3 runs)");
for (let i = 0; i < 3; i++) {
  const { ttft, tpot, total, pieces } = await streamOnce();
  console.log(`   TTFT ${ttft.toFixed(2).padStart(5)} s   TPOT ${Math.round(tpot * 1000).toString().padStart(4)} ms   ` +
    `total ${total.toFixed(2).padStart(5)} s   ${pieces} chunks`);
}

async function one(): Promise<number> {
  const r = await client.chat.completions.create({ model: config.MODEL, messages: PROMPT, temperature: 0 });
  return r.usage?.completion_tokens ?? 0;
}

async function burst(n: number) {
  const start = now();
  // Promise.all starts all n requests before waiting for any of them, like asyncio.gather in Python.
  const tokens = await Promise.all(Array.from({ length: n }, () => one()));
  const seconds = now() - start;
  return { seconds, tps: tokens.reduce((a, b) => a + b, 0) / seconds };
}

console.log("\n2) Throughput: the same request sent 1, 4 and 8 times at once");
for (const n of [1, 4, 8]) {
  const { seconds, tps } = await burst(n);
  console.log(`   ${n} at once: ${seconds.toFixed(1).padStart(5)} s wall time, ${tps.toFixed(1).padStart(5)} output tokens/s in total`);
}

Reading the output

One answer: TTFT and TPOT

The numbers fit together. For run 3: 0.35 s + 89 gaps × 0.160 s ≈ 14.6 s, which is the measured total of 14.62 s. A TPOT of about 160 ms means roughly 6 tokens per second, which is also what the single-request throughput test measured (5.8 tokens per second).For run 3: 0.17 s + 89 gaps × 0.122 s ≈ 11.0 s, which is the measured total of 11.07 s. A TPOT of about 122 ms means roughly 8 tokens per second, close to what the single-request throughput test measured (7.7 tokens per second). With a short prompt like this one, prefill is quick and decode dominates; for a RAG prompt with 350 input tokens (lab 12) the TTFT would be a larger share.

Why is the first run slower? Run 1 had a TTFT of 1.18 s, runs 2 and 3 about 0.4 s1.26 s, runs 2 and 3 0.29 s and 0.17 s. It was not a cold start: loading llama3.2 from disk takes 35–56 s on this machine, so the model was already in memory. Likely reasons are one-time work on the first request and the fact that runs 2 and 3 send exactly the same prompt, which a server can partly reuse (prefix caching). We did not check which applies to our Ollama version. The general habit matters more than the cause: run measurements several times and report the first one separately.

Throughput: no gain at all

If the server batched requests, sending 4 at once would take only a little longer than sending 1, and the total tokens per second would rise sharply. Ours did the opposite: 4 requests took about 4 times as long, 8 took about 8 to 98 times as long, and the throughput stayed at about 5.47.5–7.7 tokens per second. The async clientPromise.all did send the requests together; the server queued them.

Why? ollama ps lists the models currently loaded, with their memory size, how they are split between CPU and GPU, and their context length. During our Python run it showed llama3.2 loaded at 10 GB with a 65536-token context, running 79 % on the CPU and 21 % on the GPU. The model file is only 2.0 GB; most of the rest is memory reserved for the KV cache of such a long context window. That does not fit in the T500's 4 GB, so most of the work ran on the CPU, which is much slower and leaves no room to serve several requests side by side.

Settings to try (we did not)

Ollama has settings that control exactly this, set as environment variables for the Ollama server (not for your Python scriptNode.js program). At the time of writing, the Ollama FAQ documents OLLAMA_NUM_PARALLEL (how many requests a loaded model works on at the same time) and OLLAMA_CONTEXT_LENGTH (the default context length). A smaller context could let more of the model fit on the GPU, and parallel requests could raise throughput if memory allows. We did not change these settings and did not measure their effect, so we can't tell you what they will do on your machine. Check the FAQ for the current defaults and how to set them on your system, restart Ollama, run ollama ps, and run this lab again. Whatever you change, re-run the eval set afterwards: a shorter context window must still fit your longest RAG prompts.

Common mistakes
  • Awaiting each request inside a loop. for (let i = 0; i < n; i++) tokens.push(await one()); waits for each answer before sending the next, so nothing runs at the same time and the "4 at once" test measures nothing new. Create all the promises first and await them together with Promise.all, as line 42 does. (The Python version of this lab hit a different bug, "Event loop is closed", which cannot happen in Node.js: there is one event loop for the whole program.)
  • Calling asyncio.run() several times with one async client. Our first version of part 2 ran each burst in its own asyncio.run(): 
    for n in (1, 4, 8):
    seconds, tps = asyncio.run(burst(n))
    print(f"   {n} at once: {seconds:5.1f} s wall time, {tps:5.1f} output tokens/s in total")
    The first burst worked; the next one crashed with RuntimeError: Event loop is closed. Each asyncio.run() creates a new event loop and closes it at the end, but the AsyncOpenAI client keeps its network connections open for reuse, and those belong to the first, now closed loop. The fix is the version in the file: put all bursts in one async def main() and call asyncio.run(main()) once (lines 45–53). Creating the async client inside main() would also work.
  • Averaging the first run with the others. Our first TTFT was three times the othersfour to seven times the others. A cold start after loading the model is worse still (35–56 s here). Report them separately.
  • Assuming parallel requests are faster. Sending requests concurrently only helps if the server batches them. Ours didn't: 8 at once took 135.7 s97.2 s. Measure before you build on it.
  • Comparing with numbers from the internet. TPOT depends on the GPU, the model's size and quantization, the context length and the server settings. Your own measurement is the only one that applies to you.
  • Speeding up without re-checking quality. A smaller model, a lower reasoning effort or a shorter context can make answers worse. Re-run the eval set after each change.

Try it yourself

  1. Shorter answers, same TPOT. Change the prompt in line 107 to "In one sentence, ..." and run again. The number of chunks and the total time should drop a lot, while TPOT stays about the same: decode time is proportional to the number of output tokens.
  2. Look at your own setup. Run ollama ps while the lab runs. Note the size, the CPU/GPU split and the context length. If your model is 100 % on the GPU, compare your TPOT with our 160–180 ms120–131 ms.
  3. Measure a cold start. Run ollama stop llama3.2 to unload the model, then run the lab again. The first TTFT should now include loading the model and be much larger than our 1.18 s1.26 s (on our machine a first call after loading took 35–56 s).
Recap
  • TTFT is the wait for the first chunk; TPOT is the time per chunk after that; total ≈ TTFT + (chunks − 1) × TPOT. Ours: TTFT 1.18 / 0.42 / 0.35 s, TPOT 160–180 ms, about 15–16 s for about 90 chunks.TTFT 1.26 / 0.29 / 0.17 s, TPOT 120–131 ms, about 11–12 s for 90–94 chunks.
  • The first run was slower; always repeat measurements and report the first one separately.
  • Throughput did not grow with concurrency (5.8 → 5.4 → 5.47.7 → 7.7 → 7.5 tokens/s): our Ollama server answered requests one after another, with the model 79 % on the CPU because of a 65536-token context on a 4 GB GPU.
  • OLLAMA_NUM_PARALLEL and OLLAMA_CONTEXT_LENGTH are the settings to explore; we did not test them, so measure the effect yourself.
  • Use one asyncio.run(main()) per program; calling asyncio.run() repeatedly with one async client gives "Event loop is closed".
  • Promise.all sends requests together, but they only finish faster if the server works on them together. Differences between our Python and TypeScript runs come from the moment, not the language.

Where to go next

You now have the whole loop of AI engineering in one small project: a model behind one wrapper, an eval set and a calibrated judge, retrieval and a grounded prompt, an agent with checked tools, guardrails, caches and a router, traces and feedback, a dataset for finetuning, and speed measurements. Three habits carry over to any project:

  • Repeat the eval after every change. A new prompt, a different model, a lower cache threshold, a shorter context window: each can make answers worse in ways you only see on the eval set from lab 04, extended with the cases from lab 12.
  • Measure on your own setup. Our numbers come from one laptop and one run each; yours will differ, and only yours count.
