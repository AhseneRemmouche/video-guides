Retrieval: BM25, embeddings and hybrid

Chunk the documents, build three retrievers and measure hit rate and MRR on the eval set.

Lab · code run on a local model (llama3.2 via Ollama)

Until now the bot answered from memory, and in lab 04 that gave a keyword pass rate of about 30 %. The fix is to hand the model the right piece of the shop's policies for each question. Before we can do that, we need a retriever: a function that takes a question and returns the few most relevant pieces of text.

In this lab you cut the 8 policy documents into small pieces, build three retrievers (one based on keywords, one based on meaning, one combining both) and measure how often each one finds the right document. No answers are generated yet: we test the retrieval part alone, because if it fails, the answer will fail too.

Goal. Split data/docs/ into 23 chunks, build BM25, embedding and hybrid retrievers, and score them with hit@1, hit@3 and MRR on the 18 questions whose source document we know.

The idea in brief

Retrieval is the "R" of RAG. The concept chapter RAG and agents (read with chapter 6 · RAG and Agents of the book) explains it in depth; here is what you need for this lab.

  • Chunking. A whole document is too long and too mixed to paste for every question. We split it into chunks of about 60 words, made of whole paragraphs.
  • Keyword search (BM25). A chunk scores high when it contains the question's words, especially rare ones. Fast, exact, but blind to synonyms.
  • Semantic search (embeddings). A model turns each text into a list of numbers (a vector); texts with similar meaning get similar vectors. Finds synonyms, but can be fooled by texts that "sound" related.
  • Hybrid search. Run both and merge the two ranked lists with reciprocal rank fusion (RRF).
  • Measuring. For each question we know the source document (the source field of evals/qa.jsonl), so we can check whether the retriever found it, and at which rank.
New to retrieval? Why not paste all the documents every time?

Our 8 documents are short, so in this toy shop you could paste everything into every prompt. Real knowledge bases have thousands of pages, far more than a model's context window. Even when everything fits, more text means more tokens to pay for, slower answers, and a model that is more easily distracted by irrelevant paragraphs. Retrieval picks the few pieces that matter, so the prompt stays small and focused.

Step 1: cut the documents into chunks

"""Load the knowledge base and split it into chunks."""
from dataclasses import dataclass

from aie.config import DATA


@dataclass
class Chunk:
    id: str      # "returns#0"
    doc: str     # "returns"
    title: str   # "Returns and refunds"
    text: str


def load_docs():
    """Return {doc_id: markdown text} for every file in data/docs."""
    return {p.stem: p.read_text(encoding="utf-8") for p in sorted((DATA / "docs").glob("*.md"))}


def chunk_doc(doc_id, text, max_words=60, overlap=1):
    """Split one document into chunks of whole paragraphs, about max_words long.

    Each chunk repeats the last `overlap` paragraphs of the previous one, and every chunk starts
    with the document title so it still makes sense on its own.
    """
    lines = text.strip().splitlines()
    title = lines[0].lstrip("# ").strip()
    paragraphs = [p.strip() for p in "\n".join(lines[1:]).split("\n\n") if p.strip()]
    chunks, current = [], []
    for para in paragraphs:
        if current and sum(len(p.split()) for p in current) + len(para.split()) > max_words:
            chunks.append(current)
            current = current[-overlap:] if overlap else []
        current.append(para)
    if current:
        chunks.append(current)
    return [Chunk(f"{doc_id}#{i}", doc_id, title, f"{title}\n\n" + "\n\n".join(c)) for i, c in enumerate(chunks)]


def load_chunks(max_words=60, overlap=1):
    return [c for doc_id, text in load_docs().items() for c in chunk_doc(doc_id, text, max_words, overlap)]

New to chunking? Why paragraphs, ~60 words and overlap?

There is no perfect chunk size. Small chunks are precise (the retrieved text is mostly about the question) but may cut a fact away from its context. Large chunks keep context but bring noise and cost more tokens in the prompt. Our documents are made of short, self-contained paragraphs, so "whole paragraphs, about 60 words" keeps each fact intact. Overlap is cheap insurance: a sentence like "After that, use the normal return process" needs the sentence before it. Adding the title to every chunk is another cheap trick: it puts the topic word ("Warranty", "Shipping") into every piece. Real systems tune these choices by measuring, exactly as this lab does.

Step 2: three retrievers

"""Three retrievers over the same chunks: BM25 (keywords), embeddings (meaning) and hybrid (both)."""
import math
import re
from collections import Counter

import numpy as np

from aie.llm import embed

STOPWORDS = set("a an and are as at be can do does for from how i in is it my of on or the to what when where which who with you your".split())


def tokenize(text):
    return [w for w in re.findall(r"[a-z0-9]+(?:\.[0-9]+)?", text.lower()) if w not in STOPWORDS]


class BM25:
    """Okapi BM25: scores a chunk higher when it contains rare query words, often, in a short text."""

    def __init__(self, chunks, k1=1.5, b=0.75):
        self.chunks, self.k1, self.b = chunks, k1, b
        self.docs = [Counter(tokenize(c.text)) for c in chunks]
        self.lengths = [sum(d.values()) for d in self.docs]
        self.avg_len = sum(self.lengths) / len(self.lengths)
        n = len(chunks)
        df = Counter(word for d in self.docs for word in d)
        self.idf = {w: math.log(1 + (n - f + 0.5) / (f + 0.5)) for w, f in df.items()}

    def search(self, query, k=3):
        scores = []
        for doc, length in zip(self.docs, self.lengths):
            score = 0.0
            for word in tokenize(query):
                tf = doc.get(word, 0)
                if tf:
                    norm = tf + self.k1 * (1 - self.b + self.b * length / self.avg_len)
                    score += self.idf[word] * tf * (self.k1 + 1) / norm
            scores.append(score)
        order = np.argsort(scores)[::-1][:k]
        return [(self.chunks[i], float(scores[i])) for i in order]


class EmbeddingIndex:
    """Embeds every chunk once; a query is embedded and compared by cosine similarity."""

    def __init__(self, chunks):
        self.chunks = chunks
        # nomic-embed-text expects these task prefixes; other embedding models simply ignore them.
        self.matrix = self._normalize(embed([f"search_document: {c.text}" for c in chunks]))

    @staticmethod
    def _normalize(vectors):
        m = np.array(vectors, dtype=np.float32)
        return m / np.linalg.norm(m, axis=1, keepdims=True)

    def search(self, query, k=3):
        q = self._normalize(embed([f"search_query: {query}"]))[0]
        scores = self.matrix @ q
        order = np.argsort(scores)[::-1][:k]
        return [(self.chunks[i], float(scores[i])) for i in order]


def reciprocal_rank_fusion(result_lists, k=3, c=60):
    """Merge ranked lists: each chunk gets 1/(c + rank) from every list it appears in."""
    scores, by_id = {}, {}
    for results in result_lists:
        for rank, (chunk, _) in enumerate(results, start=1):
            scores[chunk.id] = scores.get(chunk.id, 0.0) + 1 / (c + rank)
            by_id[chunk.id] = chunk
    best = sorted(scores, key=scores.get, reverse=True)[:k]
    return [(by_id[i], scores[i]) for i in best]


class Hybrid:
    def __init__(self, chunks):
        self.bm25, self.dense = BM25(chunks), EmbeddingIndex(chunks)

    def search(self, query, k=3, pool=10):
        return reciprocal_rank_fusion([self.bm25.search(query, pool), self.dense.search(query, pool)], k=k)

BM25, gently

For each question word that appears in a chunk, BM25 adds rarity × frequency:

score(chunk) = sum over question words of
               idf(word) × tf × (k1 + 1) / (tf + k1 × (1 − b + b × length / avg_len))
  • idf: rare words matter more. "annecy" (1 chunk out of 23) weighs 2.77; "frame" (6 chunks) weighs 1.31.
  • tf with saturation: the second occurrence helps, the tenth barely does.
  • length: in a chunk longer than average the same count is worth a bit less.
New to embeddings? Vectors, prefixes and cosine similarity

An embedding model reads a text and outputs a fixed-length list of numbers (for nomic-embed-text, 768 of them). The model was trained so that texts with similar meaning point in similar directions in that 768-dimensional space. "Do you deliver to Switzerland?" and "We ship to France, Belgium…" share no important word, but their vectors are close because both are about shipping destinations.

To compare two vectors we use the angle between them: the cosine similarity. If both vectors are first scaled to length 1 (normalised), the cosine is just the dot product (multiply matching numbers, add them up). That's why the code normalises once and then uses @.

Some embedding models are trained with task prefixes so that a short question and a long passage land near each other. nomic-embed-text is one of them: search_query: for questions, search_document: for stored texts. Other models (for example OpenAI's) don't need prefixes; the comment on line 48 notes they are simply treated as text.

Reciprocal rank fusion, worked example

Suppose (illustrative) BM25 ranks chunks A, B, C and embeddings rank B, D, A. With c = 60: rank 1 is worth 1/61 = 0.0164, rank 2 is 1/62 = 0.0161, rank 3 is 1/63 = 0.0159.

Step 3: measure the retrievers

New to retrieval metrics? hit@k and MRR with a worked example

For each question we look at the documents of the top 3 chunks and find the rank of the first chunk from the right document.

  • hit@k: the share of questions where the right document is somewhere in the top k. hit@1 = "first result right"; hit@3 = "in the 3 chunks the model will see".
  • MRR (mean reciprocal rank): each question scores 1/rank (1 for rank 1, 0.5 for rank 2, 0.33 for rank 3, 0 if missing), then we average. It rewards finding the right document early.

Worked example with three questions: right document at rank 1, at rank 2, and missing. hit@1 = 1/3 = 33 %, hit@3 = 2/3 = 67 %, MRR = (1 + 0.5 + 0) / 3 = 0.50.

Now our real BM25 line (18 questions): 15 at rank 1, 2 at rank 2 and 1 missed. hit@1 = 15/18 = 83 %, hit@3 = 17/18 = 94 %, MRR = (15 × 1 + 2 × 0.5) / 18 = 16/18 = 0.89. That is exactly what the program prints.

These are document-level checks: we only ask whether the right document was found, not whether the chunk contains the exact sentence. That's good enough here because our documents are short; a stricter eval would label the expected chunk.

"""Lab 06: measure three retrievers on the questions whose source document we know."""
from aie.docs import load_chunks
from aie.evalset import load_qa

chunks = load_chunks()
print(f"{len(chunks)} chunks from {len({c.doc for c in chunks})} documents\n")

questions = [q for q in load_qa() if q["source"]]
retrievers = {"BM25": BM25(chunks), "Embeddings": EmbeddingIndex(chunks), "Hybrid (RRF)": Hybrid(chunks)}
K = 3

print(f"{'retriever':<14}{'hit@1':>8}{'hit@3':>8}{'MRR':>8}")
misses = {}
for name, retriever in retrievers.items():
    hit1 = hit3 = rr = 0.0
    for q in questions:
        docs = [chunk.doc for chunk, _ in retriever.search(q["question"], k=K)]
        if q["source"] in docs:
            rank = docs.index(q["source"]) + 1
            hit1 += rank == 1
            hit3 += 1
            rr += 1 / rank
        else:

Reading the two misses

q08 "Do you deliver to Switzerland?", missed by BM25. After stopwords, the question is ['deliver', 'switzerland']. No chunk contains either word: the shipping document says "We ship to France, Belgium…", and "delivery" (in returns and service plans) is a different word to our tokenizer. So every chunk scored exactly 0. argsort still returns three positions, and with all scores equal they are simply the last three chunks of the list: warranty#2, warranty#1, warranty#0. That is why the output shows three warranty chunks: they were not "found", they were picked by default. Embeddings understood that "deliver" and "ship" mean the same thing, and the hybrid kept that.

q06 "Where do I find the frame number?", missed by embeddings and hybrid. The answer ("stamped under the bottom bracket") is the last detail of warranty#2, a chunk mostly about warranty exclusions and claims. Meanwhile every sizing chunk starts with the title "Frame size guide" and talks about frame sizes. To the embedding model, "frame number" sounds like sizing. BM25 did get this one, at rank 2 (the rare word number appears in the warranty chunk), but in the hybrid the embedding list's three sizing chunks outvoted it.

Common mistakes.
  • Running the file directly (python labs/06_retrieval.py): you get ModuleNotFoundError: No module named 'aie'. Run it as a module from the project folder: uv run python -m labs.06_retrieval.
  • Embedding model not pulled: Ollama answers with a "model not found" error for nomic-embed-text. Run ollama pull nomic-embed-text.
  • Ollama not running: a connection error from the openai client. Start the Ollama app (or ollama serve).
  • Forgetting the prefixes with nomic-embed-text: nothing crashes, but scores get worse. Keep search_document: and search_query: paired.
  • Changing an eval question's source document or a document's file name: doc is the file name without .md, and it must match the source field exactly.
  • Trusting a "result" that scored 0: BM25 always returns k chunks. In a real app, drop results whose score is 0.

  3. Change the chunk size. Replace line 6 with chunks = load_chunks(max_words=120), or load_chunks(overlap=0). Watch the chunk count and the table change. Bigger chunks make "the right document" easier to hit but put more noise in each chunk.

Recap
  • aie/docs.py turns 8 documents into 23 chunks: whole paragraphs, about 60 words, 1 paragraph of overlap, title at the top of each chunk.
  • BM25 scores rare question words that appear often in short chunks; it misses synonyms (q08: "deliver" vs "ship").
  • Embeddings compare meaning with cosine similarity on normalised vectors; nomic-embed-text needs the search_document: / search_query: prefixes. They can be fooled by look-alike topics (q06).
  • Hybrid search fuses both ranked lists with RRF, 1/(60 + rank), and had the best MRR in our run (0.92).
  • hit@k asks "is the right document in the top k?"; MRR also rewards finding it early. Always read the misses.
