Inference optimization

Latency and cost metrics, what slows inference down, and techniques at the model and service level. Read with book chapter 9.

Read with chapter 9 · Inference Optimization of the book. This page explains the ideas in its own words and links them to the labs.

Every time the Trailhead Bikes bot answers a customer, a model runs on a computer somewhere and produces text one piece at a time. That run is called inference. This chapter explains what happens during inference, how to measure whether it is fast and cheap enough, why it is slow, and which tricks make it faster at three levels: the model itself, the server that runs it, and your application.

Why this matters for your project. On our lab machine (an NVIDIA T500 with 4 GB of GPU memory) a warm llama3.2 answer takes roughly 5 to 10 seconds, the first call after loading a model takes 35 to 56 seconds, and one gemma4 answer with hidden thinking took 95 to 110 seconds. Those numbers decide whether a customer waits or leaves. In lab 14 you measure speed yourself, and in lab 11 you skip the model entirely for some requests. This page gives you the vocabulary and mental model behind both labs.

What inference is: two phases

Training a model means changing its parameters. Inference means using a model whose parameters are fixed: you give it a prompt and it predicts the next token, then the next, until it stops. A language model only ever predicts one token at a time; a long answer is just many predictions in a row, each one fed back as input for the next.

Inference has two phases that behave very differently:

  • Prefill. The model reads the whole prompt (system prompt, retrieved documents, the question). All prompt tokens are already known, so the model can process them together, in parallel, in one big pass. At the end of this pass it can predict the first output token.
  • Decode. The model generates the answer. Each new token depends on the one before it, so this part is sequential: one forward pass per output token. A 100-token answer needs about 100 passes.
New to tokens and forward passes? What they are and why they matter

A tokenizer cuts text into tokens: whole short words, pieces of longer words, punctuation. "Trailhead" might become two or three tokens. A forward pass is one run of the input through all the layers of the transformer, ending with a probability for every possible next token. Prefill is one forward pass over many tokens at once; decode is one forward pass per new token. Costs and limits (price per token, context window) are counted in tokens, which is why our wrapper aie/llm.py records input_tokens and output_tokens for every call.

The numbers that describe speed and cost

Latency is how long one user waits. For a chat product it splits into parts that users feel differently:

MetricWhat it measuresWhat makes it worse
Time to first token (TTFT)Seconds from sending the request until the first piece of the answer arrives. With streaming, this is when the user sees the bot "start typing".Long prompts (big RAG context), a queue of other requests, loading the model, hidden thinking tokens.
Time per output token (TPOT)Average gap between two output tokens during decode. Its inverse is "tokens per second" for one user.Bigger models, slower GPU memory, many requests sharing the GPU.
Total latencyFrom request to the last token. Roughly TTFT plus TPOT times the number of output tokens.Everything above, plus long answers.
ThroughputWork done per second by the whole server, usually output tokens per second across all users, or requests per minute.Serving requests one at a time instead of in batches.
GoodputThroughput that counts only requests that met your targets, for example "TTFT under 1 s and TPOT under 50 ms" (illustrative targets).Pushing throughput so high that individual requests become too slow.
UtilizationHow busy the hardware is. Tools like nvidia-smi report the share of time the GPU was running something.Idle gaps between requests; tiny batches.

Two of these deserve a warning. First, latency and throughput pull against each other. Packing more requests together raises throughput, but each request now shares the GPU and may get slower. Goodput exists precisely to stop you from celebrating a throughput number that came from making users wait. Second, "100 % GPU utilization" does not mean the GPU is used well. The common utilization number says the GPU was doing some work during each sampling period, not how much of its arithmetic power was used. Engineers also look at how much of the theoretical compute (or memory bandwidth) a job actually achieves, which is usually far below the peak.

Also report latency as a distribution, not one average. Look at the median (p50) and at slow cases such as p90 or p99: the one customer in a hundred who waits 40 seconds is real, and an average hides them.

Why inference is slow: compute-bound vs memory-bound

A GPU has two resources that matter here: compute (how many multiplications per second its cores can do) and memory bandwidth (how many bytes per second it can move from its memory into those cores). A job is compute-bound when the cores are the bottleneck and memory-bandwidth-bound when the cores sit waiting for data.

Prefill is usually compute-bound: the model loads each weight once and uses it for every prompt token in the pass, so there is a lot of math per byte loaded. Decode is usually memory-bound: to produce one token for one request, the GPU must read essentially all of the model's weights from memory, do a small amount of math with them, and then read them all again for the next token. The cores finish their math quickly and wait for the next load.

This gives you a useful back-of-the-envelope rule. If a model's weights take S gigabytes and the GPU can move B gigabytes per second, one request can decode at most about B / S tokens per second. As an illustrative example (not our hardware): a 2 GB model on a GPU that moves 100 GB/s tops out near 50 tokens per second for a single user. Real numbers are lower because of overheads. The rule explains three things you will see in practice:

  • Shrinking the weights (quantization, smaller models) speeds up decode almost directly.
  • Serving several requests together is nearly free during decode: the weights are read once and used for all of them, which is why batching raises throughput so much.
  • Buying a GPU with more compute but the same memory bandwidth may not make single-user chat any faster.

Hardware basics, with our 4 GB GPU

For inference, the first questions about any accelerator are: how much memory does it have (does the model fit at all?) and how fast is that memory (how quickly can it decode?). Compute speed matters most for long prompts and big batches.

Our lab GPU, an NVIDIA T500, has 4 GB of memory. llama3.2 has about 3 billion parameters. Stored at 16 bits (2 bytes) each, that would be about 6 GB, which would not fit. The model Ollama downloads is 2.0 GB, which tells you the weights are stored with far fewer bits per parameter: it is a quantized version. Weights are not the only thing in memory, though. The runtime also needs room for working buffers and for the KV cache (explained below), which grows with the length of the conversation.

That is why the labs warn that switching between llama3.2 (the app model) and gemma4 (the judge) is slow on this machine, and why the first call after loading a model takes 35 to 56 seconds while warm calls take 5 to 10. Model loading is part of real-world latency too: servers keep popular models loaded ("warm") for exactly this reason.

In data centres the same questions apply at a larger scale: accelerators with tens of gigabytes of very fast memory, several of them per machine, linked by fast connections. Product names and specs change quickly, so check vendors' current documentation rather than any list you read in a book or guide.

Where to optimize: three levels

Speed-ups come from three places. You rarely control all three. When you call a hosted API, the provider owns the model and the service levels, and your levers are mostly in the application. When you run models yourself, as in our labs with Ollama, all three are yours.

Model-level techniques

Quantization

Quantization stores each weight with fewer bits, for example 8 or 4 bits instead of 16. The model file shrinks, it fits on smaller GPUs, and because decode is memory-bound, fewer bytes to read means faster tokens. The cost is some loss of precision, which may or may not hurt quality on your task. The only way to know is to run your own eval set (lab 04) on both versions. Quantization can also be applied to the KV cache and to the activations, not only to the weights.

Distillation

Distillation trains a smaller "student" model to imitate a larger "teacher" model, often using the teacher's outputs as training data. You end up with a model that is cheaper to serve and keeps much of the teacher's skill on the tasks you trained it for. It connects directly to dataset engineering and to the synthetic data you generate in lab 13. Check the teacher model's licence before using its outputs to train another model.

Pruning

Pruning removes parts of a model that contribute little: individual weights, attention heads or whole layers. It can make the model smaller, but removing individual weights only speeds things up if the hardware and software can skip the zeros efficiently, which is often not the case. In practice you will meet quantization and distillation far more often than pruning.

Speculative decoding

Since decode is memory-bound, checking several tokens in one pass costs about the same as generating one. Speculative decoding uses that fact. A small, fast draft model guesses the next few tokens. The big target model then checks all of those guesses in a single forward pass. It keeps the guesses up to the first one it disagrees with, and replaces that one with its own token. When the draft model guesses well, you get several tokens for the price of about one big-model pass. When it is set up correctly, the output follows the same distribution as the big model alone, so quality does not change; only speed does.

The KV cache and attention optimizations

Inside a transformer, attention lets each new token look back at every earlier token. To do that it computes two vectors per earlier token per layer, called a key (K) and a value (V). These do not change once computed, so servers store them in a KV cache instead of recomputing them at every step. Prefill fills the cache with the prompt's keys and values; each decode step adds one more entry.

The KV cache is so central that many optimizations target it: storing it in fewer bits, sharing keys and values between attention heads so there are fewer of them to store, limiting attention to a window of recent tokens, and managing the cache in small pages (like an operating system manages RAM) so that memory is not wasted on reserved but unused space. There are also faster ways to compute attention itself that reorganize the work to reduce memory traffic without changing the result. You do not need to implement any of this; you need to know it exists, so that "this server supports long contexts and many users cheaply" makes sense to you.

Service-level techniques

Batching: static, dynamic and continuous

Because decode reads all the weights anyway, processing many requests in the same step is far cheaper than processing them one after another. That is batching, and there are three common styles:

  • Static batching waits until it has a fixed number of requests, runs them together, and returns all results when the slowest one finishes. Simple, but short answers wait for long ones, and the first request waits for the batch to fill.
  • Dynamic batching starts a batch when it is full or when a time limit passes, whichever comes first, so a lone request is not stuck forever.
  • Continuous batching (also called in-flight batching) works at the level of decode steps: when one request finishes, a waiting request takes its slot at the next step. The GPU stays full and short answers leave early. Modern LLM servers use this.

Whether your server batches at all is a setting. At the time of writing, the Ollama FAQ documents OLLAMA_NUM_PARALLEL, the number of requests each loaded model works on at the same time, and notes that memory use grows with it. In lab 14 you send the same request 1, 4 and 8 times at once; compare the wall time and total tokens per second to see whether your setup ran them together or queued them. Check the current FAQ for the default on your version. In our run the answer was clear: 1, 4 and 8 requests took 15.7, 67.6 and 135.7 s, and throughput stayed flat at 5.8, 5.4 and 5.4 output tokens per second, so this server answered them one after another. ollama ps showed why there was no room for more: llama3.2 was loaded at 10 GB with a 65536-token context and ran 79 % on the CPU, 21 % on the GPU, because the KV cache for that context does not fit our 4 GB GPU. We did not change OLLAMA_NUM_PARALLEL or OLLAMA_CONTEXT_LENGTH, so we cannot say what they would gain here.

Prompt caching (prefix reuse)

Many requests start with the same text: the same system prompt, the same tool descriptions, the same long document. Prefill for that shared beginning produces the same KV cache entries every time. Prompt caching keeps those entries and reuses them when a new request starts with exactly the same prefix, so only the new part needs prefill. This lowers TTFT and, with hosted APIs that support it, often lowers the price of the cached input tokens (see the provider docs linked below for current rules).

The design rule that follows is simple: put what never changes first and what changes last. Our prompt prompts/rag_v2.txt already has that shape: fixed rules at the top, then the retrieved context, and the customer's question arrives as a separate message at the end. Any byte that differs, even a timestamp at the top of the system prompt, breaks the match from that point on.

Parallelism: replicas, tensor and pipeline

When one GPU is not enough, there are two different problems. If the model fits but there are too many users, run replicas: several copies of the model behind a load balancer. If the model does not fit on one GPU, split it. Tensor parallelism splits each layer's big matrix operations across several GPUs that work on the same token at the same time; it can cut latency but needs very fast links between GPUs. Pipeline parallelism gives each GPU a different group of layers and passes the work along like an assembly line; it lets huge models run but adds hand-off delays. You will mostly meet these as settings in serving software, not as code you write.

Application-level techniques: what you control in our project

Streaming

Streaming sends each piece of the answer as soon as it is generated instead of waiting for the end. It does not make the total faster, but the user starts reading after TTFT instead of after the total latency, which feels much faster. Lab 14 uses stream=True and timestamps the first piece to measure TTFT. One catch: if a guardrail must check the full answer before the user sees it (as our output guardrail in lab 10 does with citations), streaming and checking pull against each other. Common compromises are checking in chunks, or streaming and retracting, each with trade-offs.

Caching whole answers

The fastest model call is the one you never make. In lab 11 an exact cache answers a question it has seen before (after lower-casing and squeezing spaces), and a semantic cache answers a question whose embedding is close enough to a cached one (cosine similarity at least 0.9). A cache hit skips retrieval and generation completely. The risk is a wrong hit: "How long does express shipping take?" is very similar to "How long does standard shipping take?" but needs a different answer, which is exactly the case lab 11 prints a warning about. In our real run, a fresh answer took 4.00 s while the exact cache answered the repeat in under 0.01 s and the semantic cache answered a lower-case copy in 0.06 s (the time to embed the question). Personal answers (anything about one customer's order) must never be served from a shared cache.

Routing to smaller models

Not every message needs your biggest model, or any model. A router classifies each message and sends it to the cheapest path that can handle it. In lab 11, aie/router.py sorts messages into smalltalk, policy_question, order_question and out_of_scope; smalltalk and out-of-scope messages get a fixed reply without any generation. The router itself costs a model call, so it only pays off if it is cheaper than the work it saves. In our real run each routing decision with llama3.2 took 2.3 to 4.4 seconds, close to the cost of a full answer, and one of the four messages ("Thanks a lot!") was misrouted as out_of_scope. In production the router is often a much smaller model or a simple classifier.

Reasoning effort and output length

Decode time grows with every output token, including tokens the user never sees. Reasoning models produce hidden "thinking" tokens before the answer. Our wrapper passes AIE_REASONING_EFFORT (default none) as reasoning_effort. With gemma4 on our T500, turning thinking off cut one answer from about 95 to 110 seconds (roughly 350 to 400 hidden thinking tokens) to about 13 seconds (32 tokens). That is the decode rule in action: fewer output tokens, proportionally less time. Thinking can improve hard answers, so treat effort as a setting to evaluate, not a switch to always turn off. The same logic applies to visible output: "answer in one to three sentences" in rag_v2 is also a latency and cost decision.

How to measure it (lab 14)

Optimizing without measuring is guessing. Lab 14 measures the numbers from this page with nothing but the OpenAI Python SDK against Ollama:

  • TTFT: time from sending a streaming request until the first chunk with content arrives.
  • TPOT: time from the first to the last chunk, divided by the number of gaps between chunks. With Ollama a chunk is usually about one token, so this is close to TPOT, but it is a chunk count, not an exact token count.
  • Throughput: send N identical requests at once with asyncio.gather and divide the total output tokens (from the usage field) by the wall time.
    for event in stream:
        if event.choices and event.choices[0].delta.content:

Our real run on the T500: TTFT 1.18 s on the first of three streamed answers and 0.42 and 0.35 s on the next two (repeat runs are often faster, which is why you report the first one separately), TPOT 163, 179 and 160 ms, and about 15 to 16 s in total for about 90 chunks. With a short prompt, decode is nearly all of the time.

Good measurement habits: run each measurement several times and ignore or report separately the first one (it may include loading the model); keep the prompt, model and temperature fixed; measure on hardware like your production hardware; and record both latency and quality, because a faster setup that answers worse is not an improvement. Our aie/llm.py wrapper records seconds and token counts on every call, and lab 12 stores them in a trace table, so you can watch these numbers on real traffic rather than only in a benchmark script.

New to async code? Why lab 14 uses asyncio for throughput

A normal Python call waits for the answer before the next line runs, so a loop of 8 calls sends them one after another. AsyncOpenAI plus asyncio.gather sends all 8 requests without waiting, and then waits for all of them together. That is how you simulate several customers arriving at the same moment. Whether the server then works on them in parallel is up to the server, which is exactly what the experiment reveals.

Common misconceptions and pitfalls
  • "Average latency looks fine, so we are fine." Look at p90 and p99 and at TTFT separately; users notice the slow tail and the wait before the first word.
  • Measuring the cold start as if it were normal. Our first call after loading takes 35 to 56 s; warm calls take 5 to 10 s. Mixing them gives meaningless averages.
  • Optimizing speed without re-running evals. Quantization, smaller models, lower reasoning effort and semantic caches can all quietly lower quality. Re-run the eval set after each change.
  • Assuming 100 % GPU utilization means efficient. It only means the GPU was busy, not that it used its compute or bandwidth well.
  • Putting variable text at the top of the prompt. A date or user name first defeats prefix caching for everything after it.
  • Sharing cached answers across customers. Only cache answers that are the same for everyone, like policy questions.
  • Trusting benchmark numbers from elsewhere. Speed depends on hardware, model version, prompt length and server settings. Measure your own setup.
Recap
  • Inference has a parallel, compute-heavy prefill (reads the prompt, sets TTFT) and a sequential, memory-bound decode (one pass per token, sets TPOT).
  • Track TTFT, TPOT, total latency (as percentiles), throughput, goodput and utilization; latency and throughput trade against each other.
  • Decode speed is mostly limited by how fast the GPU can read the weights, so smaller weights and batching help most.
  • Model level: quantization, distillation, pruning, speculative decoding, KV cache and attention optimizations.
  • Service level: continuous batching, prompt (prefix) caching, replicas and model parallelism.
  • Application level, where our labs work: streaming, exact and semantic answer caches, routing, shorter outputs and lower reasoning effort.
  • Measure with real requests (lab 14), several runs, warm models, and re-check quality after every speed-up.
