Architecture and user feedback

Building up a production architecture step by step, monitoring, and designing feedback loops. Read with book chapter 10.

Read with chapter 10 · AI Engineering Architecture and User Feedback of the book. This page explains the ideas in its own words and links them to the labs.

By the last labs, the Trailhead Bikes bot is no longer "a prompt sent to a model". It retrieves documents, calls tools, checks what comes in and what goes out, skips the model when it can, and writes down everything it does. This chapter builds that architecture one layer at a time, the same way you should build a real system: start with the simplest thing that works and add a component only when you can name the problem it solves. Then it covers how to watch the system in production and how to learn from the people who use it.

Why this matters for your project. Each layer below matches code you run: lab 10 (guardrails), lab 11 (caches and a router) and lab 12 (tracing and feedback). Seeing them as one picture tells you where a new feature belongs, and where to look when something goes wrong.

Step 1: just call the model

The simplest AI application sends the user's message to a model and shows the reply. That is lab 01: one function, chat() in aie/llm.py, talks to an OpenAI-compatible API (Ollama locally) and returns the text along with token counts and seconds.

This version is fine for a demo, and it is the right starting point for a baseline: lab 04 measures it and finds that, without the shop's documents, it invents policies. That measured failure is the reason for step 2. Notice that the wrapper already reads the base URL, model name and key from settings: switching from Ollama to a hosted provider is a configuration change, not a code change.

Step 2: add context (RAG and tools)

A model only knows what it was trained on and what is in its prompt. To answer about Trailhead Bikes, it needs the shop's documents (RAG, lab 06 and lab 07) and, for order questions, live data from tools (tool calling, lab 09). This is usually the single biggest quality jump, and it adds new parts that can fail: retrieval can miss, a tool can return an error.

Two design choices from the labs belong to this step. Authorization lives in the tool (make_get_order only returns orders of the current customer), not in the prompt, because a prompt can be talked around and code cannot. And retrieved text is treated as reference material, not instructions (rule 4 of prompts/rag_v2.txt), because documents can carry indirect prompt injection, which lab 08 demonstrates.

Step 3: add guardrails on input and output

Once real people can type anything, you need checks that do not depend on the model behaving. Guardrails sit on both sides of the model:

  • Input guardrails run before the model sees the message. In aie/guardrails.py, check_input rejects very long messages and messages that match simple prompt injection patterns, and redact_pii replaces e-mail addresses, French phone numbers and card numbers with placeholders. That protects the customer's personal data from the model provider and from your logs.
  • Output guardrails run before the customer sees the reply. check_output allows "I don't know", otherwise requires at least one citation, rejects citations of chunks the model was not given, and blocks a promise the shop never makes (free bikes).

Guardrails have costs. They add latency (a model-based checker is another model call), they block some legitimate messages (false positives) and miss some attacks (false negatives). Pattern lists like ours are easy to get around; production systems add classifier models or provider moderation endpoints on top. And an output check that needs the whole answer conflicts with streaming (see Inference optimization). Measure all three: how often each guardrail fires, how often it fires wrongly, and how much time it adds.

Our real run of lab 10 (one run with llama3.2; yours may differ) shows both kinds of surprise. The injection attempt was blocked at input, as designed. The message with an e-mail address and a card number had its personal data redacted, but was then blocked at output: the model answered without a citation ("We are investigating this issue..."), so the customer got the fallback. That is arguably the right outcome for a billing problem, but for the wrong reason. And "What is the capital of Australia?" passed with "I don't know", yet the model still appended two unrelated citations, [stores#0] [sizing#1]; check_output returns early on "I don't know", so it never looked at them. Guardrails need their own test cases, like everything else.

Step 4: add a router and a gateway

As soon as you have more than one way to answer, something must choose. A router classifies the incoming message and sends it down the right path. In lab 11, aie/router.py asks the model for one of four labels with structured output; thanks and greetings get a canned reply, off-topic requests get a polite refusal, policy questions go to the RAG bot and order questions go to the agent with order tools.

A model gateway is the single door through which all your code reaches models. It hides the differences between providers, keeps API keys in one place, retries and falls back to another model when one fails, enforces rate limits and budgets, and logs every call. Our project has a tiny version of this idea: every lab calls models through aie/llm.py, which reads AIE_BASE_URL, AIE_MODEL and the other settings, so the rest of the code never knows which provider is behind it.

A router is a model too, so it can be wrong, and it is not free. In our real run of lab 11, "Thanks a lot!" was labelled out_of_scope instead of smalltalk, so a polite thank-you got "I can only help with Trailhead Bikes questions". Each routing decision took 2.3 to 4.4 seconds with llama3.2, about as long as a whole RAG answer on that machine, which is why production routers are usually much smaller models or simple classifiers. A policy question misrouted as smalltalk would be worse: a cheerful non-answer. Give the router its own small eval set, log its decisions, and make the fallback for an unsure route the more capable path, not the canned reply.

Step 5: add caches

Many customers ask the same things. Caches return a stored answer without running retrieval or generation. Lab 11 puts two in front of the bot: an exact cache keyed on the lower-cased, space-normalised question, and a semantic cache that compares embeddings and accepts a match at similarity 0.9 or higher. Further down, the model server can keep a prompt (prefix) cache, which speeds up prefill but still runs the model.

Caches raise questions the model never did. When do entries expire, for example after a policy document changes? Which answers are safe to share between customers (policy questions) and which never are (anything about one person's order)? Where should the cache sit relative to guardrails? Our lab checks the cache before anything else, which is fine for a demo; a production system would usually run input guardrails first so a blocked message never reaches the cache, and only cache answers that passed the output guardrail. Lab 11 itself prints the classic semantic-cache risk: "standard shipping" and "express shipping" questions look alike to embeddings but need different answers.

The real run of lab 11 makes the trade-off concrete. A fresh answer took 4.00 s, the exact cache answered the repeat in under 0.01 s, and the semantic cache answered the lower-case copy in 0.06 s (similarity 1.00). The paraphrase "How many days does standard delivery take?" scored 0.88, just below the 0.9 threshold, so it went to the model although the cached answer would have been right; the express question scored 0.82 and correctly went to the model too. Lower the threshold to catch the paraphrase and you move closer to serving the wrong answer for express. There is no free setting: pick the threshold with a labelled set of question pairs.

Step 6: agent patterns and write actions

The last step gives the system more autonomy. An agent (lab 09) decides which tools to call and in what order. All of our tools only read: search_docs, get_order, days_since. The real jump in risk comes with write actions: cancelling an order, issuing a refund, sending an e-mail. A wrong read gives a wrong answer that a human may catch; a wrong write changes the world.

Sensible rules for write actions: give each tool the narrowest permission it needs (the lab's get_order already refuses other customers' orders); ask a human to confirm anything irreversible or costly; cap amounts and rates in code; make actions undoable where you can; and log every action with the full trajectory that led to it. Prompt injection matters most here: text in a document or e-mail that convinces the agent to "issue a refund" is a real attack, not a funny screenshot.

Monitoring and observability

Once the system is live, you need to know what it is doing. Monitoring watches known numbers and alerts when they cross a line (for example, "error rate above the threshold we agreed"). Observability is the broader property of being able to ask new questions about what happened, after the fact, without shipping new code. For AI systems the key tool is tracing: recording, for each request, every step it went through.

Cost is usually computed rather than logged: tokens times the provider's current price per token, which is why storing token counts is enough. Lab 12 runs a small dashboard query: number of answers, average seconds, average input and output tokens, and the share of thumbs up. In our real run it printed "5 answers, 4.8 s average, 358 input / 19 output tokens, 60% thumbs up". Notice the ratio: most tokens are input (rules plus retrieved chunks), which is typical for RAG and is why prompt length matters for cost and TTFT.

Metrics to watch

Group them by question. Is it working? Error rate, timeouts, fallback rate, guardrail block rate. Is it fast and affordable? TTFT and total latency as percentiles, tokens and cost per request, cache hit rate. Is it good? Thumbs-up rate, share of "I don't know" answers, citation rate, results of an AI judge run on a sample of real traffic (the approach of lab 05). How is it used? Route distribution, popular topics, conversation length. A metric is only useful if you know what you would do when it moves.

Drift: things change under you

An AI system can get worse without anyone changing your code. A hosted model may be updated behind the same name. Someone edits a prompt. The policy documents change but the cache still holds old answers. Customers start asking about a new product the documents do not cover. Defences: pin model versions where the provider allows it; keep prompts as versioned files (our prompts/ folder) and log which version answered (the prompt column); re-run the eval set on every change to model, prompt, retriever or documents; and watch the quality metrics over time, not only right after a release.

Orchestration frameworks: when to use one

An orchestration framework is a library that provides ready-made building blocks for pipelines like this: connectors to model providers and vector stores, retrievers, prompt templates, agent loops, tracing hooks. Well-known examples at the time of writing include LangChain, LlamaIndex and Haystack; check their own docs for current features.

A framework helps when you need many integrations quickly, when your team already standardises on one, or when its tracing and evaluation tooling saves you real work. It hurts when its layers hide the exact prompt sent to the model, when an upgrade changes behaviour you depended on, or when debugging means reading the framework's source. This lab project deliberately uses plain Python: a few small modules in aie/, each readable in a minute, with every prompt in a text file. For a pipeline of this size that is easier to understand, test (uv run pytest runs 8 offline tests) and change. A good rule: start with plain code, and adopt a framework when you can name the specific pieces it would save you from writing and maintaining.

User feedback

User feedback is the only quality signal that comes from the people the system is for, on the questions they actually ask. Your eval set is your guess about what users will ask; feedback tells you where the guess was wrong.

Explicit and implicit feedback

Explicit feedbackImplicit feedback
What it isThe user deliberately tells you what they think.You infer satisfaction from what the user does.
ExamplesThumbs up or down, star ratings, a written comment, choosing the better of two answers, reporting a problem.Copying the answer, editing a draft before sending it, clicking "regenerate", rephrasing the same question, abandoning the chat, asking for a human, conversation length, coming back the next day.
StrengthsClear meaning; comments explain why.Plentiful; every user produces it without extra effort.
WeaknessesFew users give it; those who do are not typical.Ambiguous: a long conversation can mean engaged or stuck; leaving can mean satisfied or gave up.

Implicit signals need interpretation that depends on the product. For a support bot, a short conversation that ends without asking for a human is probably good; for a writing assistant, heavy edits to a draft suggest the draft was weak, and the edited version is itself valuable: it shows what the user wanted. Treat each implicit signal as a hypothesis and check a sample of conversations by hand before trusting it.

When and how to ask

Ask at natural moments and keep it cheap: a thumbs control under each answer that the user can ignore, a short question at the end of a conversation, or a comparison when you show two drafts anyway. Ask more directly when something seems wrong (the user rephrased three times) or when the stakes are high (before an action is confirmed). Do not interrupt every message; people stop answering, and the few who still answer are not representative. Make it clear what happens with feedback, and do not store personal data from comments without the user's consent and a reason.

Biases and limits

  • Who answers: very happy and very annoyed users rate more often than the middle, so the rates are skewed.
  • What is rated: users judge tone, length and speed as well as correctness, and often cannot tell whether a policy answer is right. A confident wrong answer can get a thumbs up.
  • Interface effects: which button comes first, default choices and wording change the results; this is a cousin of the position bias seen in AI judges.
  • Feedback loops: if you optimise only for thumbs up, the system can drift toward pleasing answers rather than accurate ones.
  • Volume: a handful of ratings on a new feature says little. Our lab 12 has five rated answers; it shows the mechanics, not a statistic.

Turning feedback into eval cases (lab 12)

The most valuable use of a thumbs down is not the rate; it is the specific example. Lab 12 runs simulated traffic (five questions with ratings and comments written into the script), logs each answer with log_trace, stores each rating with log_feedback, then selects the thumbs-down answers and writes them to evals/from_feedback.jsonl with the status "needs a human to write the expected answer".

new_cases = [{"id": f"fb-{tid}", "question": q, "bad_answer": a, "user_comment": c,
              "status": "needs a human to write the expected answer"} for tid, q, a, c in bad]

The human step matters, and our real run shows why. The ratings and comments in lab 12 are written into the script before the bot answers, so they are simulated. For "Can I return a bike I rode 80 km?" the bot said no, correctly applying the 50 km limit in data/docs/returns.md, and the scripted customer still gave a thumbs down with the comment "Unfair policy, I only rode it twice". The complaint is about the policy, not the answer: a thumbs down on a correct answer. Real feedback has the same problem: users misread answers, rate the wrong message, or are unhappy for reasons unrelated to correctness. The second thumbs-down ("Not clear") was on an "I don't know" answer to "Is express shipping available for helmets?", which may be a correct refusal or a retrieval gap. Only a person who reads the policy can tell, write the expected answer, and decide whether the case joins evals/qa.jsonl. Once it does, every future change to the prompt, retriever or model is checked against it. Over time, the eval set drifts toward the questions real customers ask, which is exactly what you want.

Common misconceptions and pitfalls
  • Building all six layers on day one. Each layer adds latency, cost and failure modes. Add one when a measurement shows the problem it solves.
  • Logging raw personal data. Traces are a goldmine and a liability. Redact before logging (lab 10's redact_pii) and decide how long to keep them.
  • Trusting the router and caches blindly. Both make silent mistakes. Log their decisions and evaluate them like any other model output.
  • Letting the model decide permissions. Access control and limits on write actions belong in code, not in the prompt.
  • Reading the thumbs-up rate as accuracy. It measures satisfaction among people who chose to click. Use it to find examples, then judge them properly.
  • Collecting feedback nobody reads. If thumbs-down answers never become eval cases or fixes, the button is decoration.
  • Assuming nothing changed because the code did not. Models, documents and users drift; re-run evals and watch quality metrics over time.
Recap
  • Build up in layers: call the model; add context (RAG, tools); add input and output guardrails; add a router and a gateway; add caches; then agents and, carefully, write actions.
  • Labs map onto the layers: guardrails in lab 10, caches and router in lab 11, tracing and feedback in lab 12, with aie/llm.py as a minimal gateway.
  • Log a trace per request: input, output, context, model and prompt version, tokens, latency, errors, tool calls, and the user's feedback linked by id.
  • Watch metrics for reliability, speed and cost, quality and usage, and expect drift from models, prompts, documents and users.
  • Use an orchestration framework when it saves specific work; plain code is often clearer for small pipelines like ours.
  • Combine explicit and implicit feedback, ask at natural moments, remember its biases, and turn failures into eval cases reviewed by a human.
