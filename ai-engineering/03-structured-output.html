Structured output with a schema

Turn customer messages into validated JSON with Pydantic, and learn why valid JSON can still be wrong.

Lab · code run on a local model (llama3.2 via Ollama)
Goal of this lab. Turn free-text customer messages into a small, typed "ticket" (intent, order number, urgency, summary) that code can use. You make the model answer in JSON that follows a schema, validate it with PydanticZod, and retry automatically when it doesn't. Then you see the most important lesson of the lab: valid JSON is not the same as a correct answer.

The idea in brief

A model normally answers with free text. That's fine for a person, but a program needs fields it can trust: "is this about a return?", "which order?". Structured output means asking the model for data in a fixed format, usually JSON, described by a JSON Schema. Many servers, including Ollama and OpenAI, accept the schema in the request (response_format) and steer the model's sampling so the output has the right shape. On our side, Pydantic checks the result again and turns it into a Python object.Zod checks the result again and gives you a typed TypeScript object.

The schema controls the shape of the answer, not its truth. A model can fill a perfectly valid order_id field with a number it made up: a hallucination in a neat JSON box. The concept chapter Foundation models explains why this happens; it pairs with chapter 2 of the book, Understanding Foundation Models.

New to JSON and JSON Schema? What they are and why they matter

JSON is a text format for data: objects in { } with "name": value pairs, lists in [ ], strings in double quotes, numbers, true/false and null. Almost every language can read it.

A JSON Schema is itself a JSON document that describes what valid data looks like: which fields are required, which type each one has, which values are allowed, which text pattern a string must match. A program can check any JSON against it automatically.

New to Pydantic? What it is and why it matters

Pydantic lets you describe data as a Python class with type hints. From that one class it can (1) produce the JSON Schema, (2) parse JSON text and check every field (model_validate_json), raising a ValidationError that lists what is wrong, and (3) give you a normal Python object with attributes (ticket.order_id). One class, used both to tell the model what to produce and to check what it produced. That is the "Pydantic pattern" used here and in the judge (lab 05) and router (lab 11).

New to Zod? What it is and why it matters

Zod lets you describe data as a schema object written in TypeScript, such as z.object({ urgent: z.boolean() }). From that one schema it can (1) produce the JSON Schema (z.toJSONSchema), (2) check any value (safeParse), which returns either the checked data or an error that lists what is wrong, and (3) give the TypeScript type of valid data, so your editor knows that ticket.order_id is string | null. One schema, used both to tell the model what to produce and to check what it produced. The same pattern is used here and in the judge (lab 05) and router (lab 11).

Why check at all, when TypeScript has types? Types are only checked before the program runs. The model's answer arrives while it runs, as plain text, so only a run-time check like Zod can tell whether it matches.

"""One small wrapper around an OpenAI-compatible API (Ollama locally, or OpenAI).

Every call returns the text plus what it cost: tokens and seconds. Later labs log these numbers.
"""
import json
import time
from dataclasses import dataclass

from openai import OpenAI
from pydantic import BaseModel, ValidationError

from aie import config

client = OpenAI(base_url=config.BASE_URL, api_key=config.API_KEY)


@dataclass
class Reply:
    text: str
    model: str
    input_tokens: int
    output_tokens: int
    seconds: float


def chat(messages, model=None, **params):
    """Send a list of {"role", "content"} messages and return a Reply."""
    if isinstance(messages, str):
        messages = [{"role": "user", "content": messages}]
    if config.REASONING_EFFORT and "reasoning_effort" not in params:
        params["reasoning_effort"] = config.REASONING_EFFORT
    start = time.perf_counter()
    response = client.chat.completions.create(model=model or config.MODEL, messages=messages, **params)
    usage = response.usage
    return Reply(
        text=response.choices[0].message.content or "",
        model=response.model,
        input_tokens=usage.prompt_tokens if usage else 0,
        output_tokens=usage.completion_tokens if usage else 0,
        seconds=time.perf_counter() - start,
    )


def chat_json(messages, schema: type[BaseModel], model=None, retries=2, **params):
    """Ask for JSON that matches a Pydantic model; validate it and retry with the error if it doesn't."""
    if isinstance(messages, str):
        messages = [{"role": "user", "content": messages}]
    messages = list(messages)
    response_format = {
        "type": "json_schema",
        "json_schema": {"name": schema.__name__, "schema": schema.model_json_schema()},
    }
    for attempt in range(retries + 1):
        reply = chat(messages, model=model, response_format=response_format, **params)
        try:
            return schema.model_validate_json(reply.text)
        except ValidationError as error:
            if attempt == retries:
                raise
            messages += [
                {"role": "assistant", "content": reply.text},
                {"role": "user", "content": f"That JSON was invalid: {error.errors()[:3]}. Reply with corrected JSON only."},
            ]


def embed(texts, model=None):
    """Return one embedding vector (a list of floats) per input text."""
    response = client.embeddings.create(model=model or config.EMBED_MODEL, input=list(texts))
    return [item.embedding for item in response.data]


def to_json(obj):
    return json.dumps(obj, ensure_ascii=False, indent=2)

import OpenAI from "openai";
import type { ChatCompletionCreateParamsNonStreaming, ChatCompletionMessageParam } from "openai/resources/chat/completions";
import { z } from "zod";
import * as config from "./config.js";

export const client = new OpenAI({ baseURL: config.BASE_URL, apiKey: config.API_KEY });

export type Message = ChatCompletionMessageParam;
export type Params = Partial<Omit<ChatCompletionCreateParamsNonStreaming, "messages" | "model">>;

export interface Reply {
  text: string;
  model: string;
  inputTokens: number;
  outputTokens: number;
  seconds: number;
}

/** Send a list of {role, content} messages (or one string) and return a Reply. */
export async function chat(messages: Message[] | string, model?: string, params: Params = {}): Promise<Reply> {
  if (typeof messages === "string") messages = [{ role: "user", content: messages }];
  if (config.REASONING_EFFORT && !("reasoning_effort" in params)) {
    params = { ...params, reasoning_effort: config.REASONING_EFFORT };
  }
  const start = performance.now();
  const response = await client.chat.completions.create({ model: model ?? config.MODEL, messages, ...params });
  return {
    text: response.choices[0]?.message.content ?? "",
    model: response.model,
    inputTokens: response.usage?.prompt_tokens ?? 0,
    outputTokens: response.usage?.completion_tokens ?? 0,
    seconds: (performance.now() - start) / 1000,
  };
}

/** Ask for JSON that matches a Zod schema; validate it and retry with the error if it doesn't. */
export async function chatJson<S extends z.ZodType>(
  messages: Message[] | string,
  schema: S,
  name: string,
  model?: string,
  params: Params = {},
  retries = 2,
): Promise<z.infer<S>> {
  messages = typeof messages === "string" ? [{ role: "user", content: messages }] : [...messages];
  const response_format = {
    type: "json_schema" as const,
    json_schema: { name, schema: z.toJSONSchema(schema) as Record<string, unknown> },
  };
  for (let attempt = 0; ; attempt++) {
    const reply = await chat(messages, model, { ...params, response_format });
    let data: unknown;
    try {
      data = JSON.parse(reply.text);
    } catch {
      data = undefined; // not JSON at all: safeParse below reports it
    }
    const result = schema.safeParse(data);
    if (result.success) return result.data;
    if (attempt === retries) throw result.error;
    messages.push(
      { role: "assistant", content: reply.text },
      {
        role: "user",
        content: `That JSON was invalid: ${JSON.stringify(result.error.issues.slice(0, 3))}. Reply with corrected JSON only.`,
      },
    );
  }
}

/** Return one embedding vector (an array of numbers) per input text. */
export async function embed(texts: string[], model?: string): Promise<number[][]> {
  const response = await client.embeddings.create({ model: model ?? config.EMBED_MODEL, input: texts });
  return response.data.map((item) => item.embedding);
}

Every answer is valid JSON and passed validation. And yet two of the three are wrong in a dangerous way: the model invented order numbers (123456789 and ST-001234) for messages that contain none. A program that looks up these orders would fail, or worse, find someone else's order. The intents are also shaky (a battery problem labelled shipping), and one summary calls the Volt e-bike battery a "car". The TypeScript run invented exactly the same two numbers as our Python run: at temperature 0 the same request to the same model gives (nearly) the same answer, whatever language sends it.

Why did validation not catch it? The schema said order_id is "a string or null". "123456789" is a string. The schema was too loose to tell a real order number from an invented one, and the prompt never said "don't invent one".

"""Lab 03: turn a free-text customer message into validated JSON."""
from typing import Literal

from pydantic import BaseModel, Field

from aie.llm import chat_json


class Ticket(BaseModel):
    intent: Literal["return", "warranty", "shipping", "order_status", "other"]
    order_id: str | None = Field(pattern=r"^TH-\d{5}$", description="Order number like TH-10234, or null if the message has none")
    urgent: bool
    summary: str = Field(description="One short sentence")


SYSTEM = (
    "Extract a support ticket from the customer's message. Reply with JSON only.\n"
    "intent: return, warranty (something broken or not working), shipping, order_status or other.\n"
    "order_id: copy it only if it appears in the message, otherwise null. Never invent one."
)
messages = [
    "Hi, my order TH-10251 still hasn't arrived and I need the helmet for a race on Saturday!",
    "The battery of my Volt won't charge since yesterday, the light blinks red.",
    "Do you have stores in Paris?",
]

for text in messages:
    ticket = chat_json([{"role": "system", "content": SYSTEM}, {"role": "user", "content": text}], Ticket, temperature=0)
    # Valid JSON is not the same as a correct answer: check facts you can check in code.
    if ticket.order_id and ticket.order_id not in text:
        print(f"  (model invented order_id {ticket.order_id}; replaced with None)")
        ticket.order_id = None
    print(text)
    print("  ->", ticket.model_dump())

  },
  "required": [
    "intent",
    "order_id",
    "urgent",
    "summary"
  ],
  "title": "Ticket",

}

This is the JSON Schema Zod builds from the final Ticket schema, i.e. what chatJson sends in response_format (printed with JSON.stringify(z.toJSONSchema(Ticket), null, 2), zod 4.6.7):

{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "properties": {
    "intent": {
      "type": "string",
      "enum": [
        "return",
        "warranty",
        "shipping",
        "order_status",
        "other"
      ]
    },
    "order_id": {
      "anyOf": [
        {
          "type": "string",
          "pattern": "^TH-\\d{5}$"
        },
        {
          "type": "null"
        }
      ],
      "description": "Order number like TH-10234, or null if the message has none"
    },
    "urgent": {
      "type": "boolean"
    },
    "summary": {
      "type": "string",
      "description": "One short sentence"
    }
  },
  "required": [
    "intent",
    "order_id",
    "urgent",
    "summary"
  ],
  "additionalProperties": false
}

It says the same thing as the schema Pydantic builds in the Python version (same fields, enum, pattern and required list). Small differences: Zod adds no title fields, names the JSON Schema version on the first line ($schema), and adds "additionalProperties": false (no extra fields allowed).

Valid JSON is not correct JSON

This lab shows four different levels of "right". Each needs a different tool, and only the first is free.

Common mistakes.
  • Trusting a field because it validated. Our first attempt validated perfectly and invented two order numbers. Check what you can check in code.
  • A loose schema. str | None accepts any text. Add Literal, pattern, number ranges and descriptions where you know the format.
  • A loose schema. z.string().nullable() accepts any text. Add z.enum, .regex, number ranges (.min, .max) and descriptions where you know the format.
  • Forgetting temperature=0temperature: 0 for extraction: the same message could give a different ticket each run.
  • Leaving AIE_MODEL set in PowerShell. Every later lab would then run on gemma4 (slow). Run Remove-Item Env:AIE_MODEL or open a new terminal.
  • Assuming retries are free. Each retry is another full model call; if the model keeps failing, the third failure raises a ValidationErrorthrows a ZodError and stops the script.

Recap
  • Structured output: send a JSON Schema in response_format so the model answers in a fixed shape.
  • The Pydantic pattern: one class produces the schema and validates the answer into a typed object.
  • The same pattern with Zod: one schema produces the JSON Schema and checks the answer, which then has a TypeScript type.
  • chat_jsonchatJson retries up to twice, showing the model its invalid JSON and the errors, then raisesthrows.
  • Tight types (Literal, patternz.enum, .regex) and a clear prompt removed the invented order numbers.
  • Valid JSON ≠ correct: llama3.2 labelled everything return; gemma4 got all three right. Meaning needs evaluation (next lab).
