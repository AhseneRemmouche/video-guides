An AI judge, checked against humans

Grade answers with a stronger model and a written rubric, then measure how often it agrees with human labels.

Lab · code run on a local model (llama3.2 via Ollama)

In lab 04 the keyword check gave a score of 30 %, and you found four verdicts that were plainly wrong. Reading every answer yourself would fix that, but you can't do it after every change. This lab hands the grading to a second, larger model with a written rubric: an AI judge. Then it asks the question that matters most: how often does the judge agree with a careful human?

Goal of this lab. Build a judge (gemma4, a rubric, the reference document, a structured verdict), run it on 20 answers that a human has already labelled, and measure agreement: judge vs human, and keyword check vs human. Then study the cases where the judge and the human disagree.

The idea in brief

An AI judge is a model prompted to grade another model's output. You give it the question, the answer and something to compare against (here the shop document the answer should come from), plus a rubric: written rules for what counts as correct. It returns a verdict. Unlike a keyword check, it can understand "we do not offer express delivery" as meaning "not available", and it can spot invented extras around a correct keyword.

But a judge is itself a model, so it can be wrong, inconsistent, or biased in ways you can't see by reading its code. That is why you calibrate it: run it on examples where you already know the right verdict (human labels) and count how often it agrees. Only then do you let it grade new runs. The concept chapters Evaluation methods (AI as a judge) and Evaluating AI systems (building an evaluation pipeline) cover the theory.

  2. Create src/judge.ts with the rubric, the Verdict schema and the judge() function.
  3. Create evals/judge_calibration.jsonl: 20 saved baseline answers, each labelled correct or not by a human.
  4. Create labs/05_judge.py.

Step 1: the judge, aie/judge.pysrc/judge.ts

"""An AI judge: a (usually stronger) model grades an answer against the reference document."""
from typing import Literal

from pydantic import BaseModel

from aie import config
from aie.docs import load_docs
from aie.llm import chat_json

RUBRIC = """You grade answers from a bike shop's support assistant.

You get the customer's question, the shop's reference document and the assistant's answer.
The answer is CORRECT when:
- it answers the question the way the reference document does, and
- it states no number, policy or fact that contradicts or is missing from the reference.
If the reference says no document covers the question, the answer is CORRECT only if it says it doesn't know
or points to support, without inventing facts.
Extra politeness or advice that adds no new facts is fine.

First explain your reasoning in two or three sentences, then give the verdict."""


class Verdict(BaseModel):
    reasoning: str
    verdict: Literal["correct", "incorrect"]


def judge(question, answer, source):
    reference = load_docs()[source] if source else "No document covers this question."
    prompt = f"QUESTION:\n{question}\n\nREFERENCE DOCUMENT:\n{reference}\n\nASSISTANT'S ANSWER:\n{answer}"
    return chat_json(
        [{"role": "system", "content": RUBRIC}, {"role": "user", "content": prompt}],
        Verdict, model=config.JUDGE_MODEL, temperature=0,
    )

New to "thinking" models? Why reasoning_effort is set to none

gemma4 is a reasoning model: by default it writes a long hidden chain of thought before the visible answer. That costs tokens and time. On our machine, one judge answer took about 95–110 seconds with thinking on (around 350–400 hidden thinking tokens) and about 13 seconds with reasoning_effort set to none (32 tokens).

The wrapper in aie/llm.pysrc/llm.ts sends reasoning_effort on every call, taken from AIE_REASONING_EFFORT (default none). The judge still reasons, but briefly and visibly, in the reasoning field the rubric asks for. That is a trade-off: less thinking may mean less careful verdicts. Calibration is how you find out whether the cheaper setting is good enough.

New to human labels? They are judgements too

It is tempting to call human labels "the ground truth". They are better described as one careful person's judgement. Look at q05 (incomplete), q16 (right answer, invented reason) and q20 (true in the world, unsupported by the documents). Two reasonable people could label each of them differently.

In practice teams write labelling guidelines, have two people label the same items, and measure how often they agree with each other. If two humans agree only 85 % of the time, a judge that agrees 85 % with one of them is about as good as a second human. Here there is only one labeller, so treat the agreement numbers as rough.

Step 3: the calibration script, labs/05_judge.pylabs/05-judge.ts

"""Lab 05: grade answers with an AI judge, then check the judge against human labels."""
from aie import config
from aie.config import EVALS
from aie.evalset import load_jsonl, load_qa
from aie.evaluate import keyword_pass
from aie.judge import judge

qa = {q["id"]: q for q in load_qa()}
labelled = load_jsonl(EVALS / "judge_calibration.jsonl")
print(f"Judge model: {config.JUDGE_MODEL}\n")

agree_judge = agree_keyword = 0
for row in labelled:
    q = qa[row["id"]]
    v = judge(row["question"], row["answer"], q["source"])
    judge_ok = v.verdict == "correct"
    keyword_ok = keyword_pass(q, row["answer"])
    agree_judge += judge_ok == row["human_correct"]
    agree_keyword += keyword_ok == row["human_correct"]
    flag = "" if judge_ok == row["human_correct"] else "   <-- judge disagrees with human"
    print(f"{row['id']}  human={'ok ' if row['human_correct'] else 'bad'}  judge={'ok ' if judge_ok else 'bad'}  keyword={'ok ' if keyword_ok else 'bad'}{flag}")
    if flag:
        print(f"      judge said: {v.reasoning[:160]}")

n = len(labelled)
print(f"\nAgreement with human labels: judge {agree_judge}/{n} = {agree_judge / n:.0%}, keyword check {agree_keyword}/{n} = {agree_keyword / n:.0%}")
// Lab 05: grade answers with an AI judge, then check the judge against human labels.
import path from "node:path";
import * as config from "../src/config.js";
import { EVALS } from "../src/config.js";
import { loadJsonl, loadQa } from "../src/evalset.js";
import { keywordPass } from "../src/evaluate.js";
import { judge } from "../src/judge.js";

interface Labelled { id: string; question: string; answer: string; human_correct: boolean }

const qa = new Map(loadQa().map((q) => [q.id, q]));
const labelled = loadJsonl<Labelled>(path.join(EVALS, "judge_calibration.jsonl"));
console.log(`Judge model: ${config.JUDGE_MODEL}\n`);

const pct = (a: number, n: number) => `${Math.round((100 * a) / n)}%`;
let agreeJudge = 0;
let agreeKeyword = 0;
for (const row of labelled) {
  const q = qa.get(row.id)!;
  const v = await judge(row.question, row.answer, q.source);
  const judgeOk = v.verdict === "correct";
  const keywordOk = keywordPass(q, row.answer);
  agreeJudge += Number(judgeOk === row.human_correct);
  agreeKeyword += Number(keywordOk === row.human_correct);
  const flag = judgeOk === row.human_correct ? "" : "   <-- judge disagrees with human";
  const ok = (b: boolean) => (b ? "ok " : "bad");
  console.log(`${row.id}  human=${ok(row.human_correct)}  judge=${ok(judgeOk)}  keyword=${ok(keywordOk)}${flag}`);
  if (flag) console.log(`      judge said: ${v.reasoning.slice(0, 160)}`);
}

const n = labelled.length;
console.log(`\nAgreement with human labels: judge ${agreeJudge}/${n} = ${pct(agreeJudge, n)}, keyword check ${agreeKeyword}/${n} = ${pct(agreeKeyword, n)}`);

Read the disagreements

The totals are close, so it is the individual rows that tell you something. The keyword check's four misses are the ones you found in lab 04: substring accidents (q08, q13), a missed invented extra (q02) and a missed polite refusal (q19). The judge got all four right. Its three misses are of a different kind:

  • q01, judge stricter than the human. The answer says 30 days and a full refund (right) and adds that you can "exchange it for a different size/color", which the returns document doesn't mention. The human accepted it; the judge said incorrect. Its printed reasoning stops at "the assistant mentions the option", and the only option in the answer is that exchange, so it most likely applied rubric line 1512 literally ("no ... fact that ... is missing from the reference").
  • q16, judge stricter than the human. "Closed on Mondays" is right, but the reason ("French public holiday schedule") is invented. The human called it harmless; the judge, whose reasoning agrees the store is closed on Monday, still said incorrect, which points to line 1512 again. (Its reasoning is cut at 160 characters; print all of v.reasoning to see the full text.)
  • q20, judge more lenient than the human. "No, we don't sell skateboards" is stated as a fact, but no document says it. Rubric lines 16–1713–14 say an answer to an uncovered question is correct only if it says it doesn't know or points to support. The judge accepted the confident "no" anyway; its reasoning calls it "a definitive 'no'" plus "helpful advice".

So who is right? For q01 and q16 you could argue the judge is: the rubric says no missing facts, and the human made an exception. That means the rubric doesn't say what the human actually believes ("small harmless extras are fine"). For q20 the judge did not follow its own rubric. These are the two lessons of calibration: disagreements show you either a weakness of the judge or a gap between your rubric and your real standard, and you only find them by comparing with labels.

Rubric wording matters

The judge did exactly what line 1512 said, and that is the point: a judge follows the words you wrote, not the standard in your head. Small wording choices change verdicts:

  • "No fact missing from the reference" makes every harmless invented detail a failure. If you want q16 to pass, write it down: for example "A small detail that does not change the policy is acceptable" (and accept that the judge must now decide what "small" means).
  • Binary verdicts (correct/incorrect) are easy to count but hide partial answers like q05. Some teams use a 1–5 scale or separate criteria (correct facts, complete, no inventions), each with its own verdict.
  • A few worked examples in the rubric (a few-shot prompt), especially of borderline cases, often help more than longer rules.

Whenever you change the rubric, run the calibration again. A rubric edit that fixes q16 might break something else.

New to judge biases? Known ways AI judges go wrong

AI judges have well-known tendencies you should test for, not assume away:

  • Position bias: when comparing two answers, judges often prefer the one shown first (or second). The usual fix is to judge both orders.
  • Length bias: longer, more detailed answers tend to look better, even when the extra text is invented.
  • Self-preference: a model may rate text written by itself or its own model family more favourably.
  • Leniency toward confident, fluent text: q20 is a small example: a confident "no" was accepted.
  • Drift: if the judge model or its version changes, its verdicts change. Record the judge model with every score.

What a judge costs

The keyword check grades 20 answers in a fraction of a second, for free, and gives the same result every time. The judge needed one call to a larger model per answer: about 10 minutes for 20 answers on our machine. With a paid API, that is also money for every eval run, and the judge's prompt is long because it contains the whole reference document. A human is the most expensive of all, which is why you use humans to check the judge on a small sample and let the judge grade the rest.

Common mistakes.
  • The run seems frozen after the first lines: it is just slow. gemma4 loads first, and switching between llama3.2 and gemma4 reloads models on a small GPU. Wait, or check activity with ollama ps in a second terminal.
  • model "gemma4" not found: run ollama pull gemma4, or set AIE_JUDGE_MODEL in .env to a judge model you have.
  • Very slow answers (minutes each): AIE_REASONING_EFFORT was set to something other than none, so the model thinks at length before every verdict.
  • pydantic.ValidationErrorA ZodError after retries: the judge returned a verdict other than correct/incorrect or broken JSON three times. Check that the model supports structured output, or try again.
  • KeyError: 'q21'TypeError: Cannot read properties of undefined (reading 'source'): a row in judge_calibration.jsonl has an id that is not in qa.jsonl.
  • Trusting the judge because it "explains itself". A fluent reasoning is not proof; q20's reasoning sounds sensible and still contradicts the rubric.

Recap
  • An AI judge is a model plus a rubric plus a reference; here gemma4 at temperature 0 with reasoning_effort none, returning a validated Verdict.
  • reasoning comes before verdict so the decision follows from the comparison.
  • Calibrate before trusting: on 20 human-labelled answers the judge agreed 17/20 (85 %), the keyword check 16/20 (80 %), failing on different questions.
  • Disagreements (q01, q16 stricter; q20 lenient) revealed a rubric that says more than the human meant, and a judge that ignored a rule.
  • Human labels are judgements too; write notes, and ideally measure agreement between two humans.
  • Judges cost time and money (about 10 minutes for 20 answers on our machine) and have biases; use humans to check the judge and cheap checks everywhere else.
