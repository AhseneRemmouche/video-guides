Automated Security Scanning

Shift security left: add software composition analysis (SCA) and static analysis (SAST, Bandit) to the pipeline.

▶ Watch this part (389:08)

Your pipeline already proves the code is formatted and the logic works. But code can be perfectly tidy and still be dangerous: a library you installed might have a known hole, or your own code might use a weak algorithm. This step adds two security guards to the pipeline so those problems are caught automatically, within minutes of writing the code, instead of after it reaches your server (at 388:44).

The idea behind this is called shift-left (at 389:08): move security checks to the earliest point in the process rather than leaving them until just before release. You will add two kinds of check — Software Composition Analysis (SCA), which audits the third-party libraries you install, and Static Application Security Testing (SAST), which scans the code you write yourself — and wire them in so a finding fails the build before anything else even runs.

The concepts the presenter explains

Two different guards for two different risks (at 389:31). SCA looks outward at other people's code — the hundreds of thousands of lines you pull in with pnpm install or pip install. SAST looks inward at your own source code. You need both because a flaw can hide in either place.

Attackers target popular packages, not just you (at 393:33). If a widely used library like Axios has a hole, breaking it compromises thousands of sites at once. SCA checks your package.json and requirements.txt against databases of known problems (CVEs) and fails the build if any dependency is affected.

SAST reads your code like an auditor (at 427:23). A tool called Bandit scans every Python file for dangerous patterns — hardcoded passwords, weak cryptography, unsafe functions — before the app ever runs.

Fail fast (at 389:31). If the code is insecure there is no point spending compute on formatting or tests. You will make the lint jobs wait for the security jobs, so a security failure halts the pipeline immediately.

New to shift-left? Why "earlier" means "cheaper"

"Shift-left" imagines your project as a timeline running left (planning) to right (release). Traditionally security sat on the far right, just before shipping, so any flaw found there forced a late, expensive scramble. Shifting it left means checking security while you code and in every CI run. A problem caught the moment you write it is a two-minute fix; the same problem found after launch can mean rewrites, downtime, or a breach (at 390:20).

New to CVEs and vulnerability databases?

A vulnerability is a known weakness that an attacker can exploit. When one is found in public software it gets a CVE id (Common Vulnerabilities and Exposures), recorded in public databases along with a severity score from 0 to 10 (at 401:58). SCA tools download your dependency list, look up each package in those databases, and report any matches. The higher the score, the more urgent the fix.

Step 1 — Audit frontend dependencies (SCA)

  1. Create .github/workflows/frontend-vulnerability-check.yml with the configuration below (at 395:09).
name: Frontend vulnerability check

on:
  workflow_call:

jobs:
  vulnerability-check:
    name: Audit dependencies
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: ./frontend
    steps:
      - name: Check out repository
        uses: actions/checkout@v6

      - name: Set up pnpm
        uses: pnpm/action-setup@v6
        with:
          version: "11"

      - name: Set up Node.js
        uses: actions/setup-node@v6
        with:
          node-version: "22"
          cache: "pnpm"
          cache-dependency-path: frontend/pnpm-lock.yaml

      - name: Install dependencies
        run: pnpm install --frozen-lockfile

      - name: Run security audit
        run: pnpm audit

Step 2 — Audit backend dependencies (SCA)

  1. Create .github/workflows/backend-vulnerability-check.yml (at 397:31). Instead of a built-in command, the backend uses the official pip-audit action.

Step 3 — Scan your own code with Bandit (SAST)

  1. Create .github/workflows/backend-sast-check.yml with the configuration below. Bandit is the SAST tool for Python; it hunts for risks like hardcoded passwords, weak crypto, and dangerous use of exec().
name: Backend SAST check

on:
  workflow_call:

jobs:
  bandit-check:
    name: Bandit SAST scan
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: ./backend
    steps:
      - name: Check out repository
        uses: actions/checkout@v6

      - name: Set up Python
        uses: actions/setup-python@v6
        with:
          python-version: "3.13"
          cache: "pip"

      - name: Install Bandit
        run: pip install bandit

      - name: Run Bandit
        run: bandit -r . -ll

import hashlib
hashlib.md5()  # weak algorithm: Bandit reports this as High severity
New to Bandit severity vs confidence?

Bandit labels each finding two ways (at 427:45). Severity is how dangerous the issue is (Low, Medium, High). Confidence is how sure Bandit is that it really found that pattern. They are independent: a pile of Low-severity findings can all have High confidence, meaning Bandit is certain they exist but also certain they do not matter. The -ll flag filters on severity, so you only act on the issues that are both real and worth fixing.

Step 4 — Plug the security jobs into the orchestrator

Open ci.yml. Add the three new security jobs at the top of the jobs list, then make the existing lint jobs depend on them with needs (at 399:33).

# ...

jobs:
  frontend-vulnerability-check:
    name: Frontend vulnerability
    uses: ./.github/workflows/frontend-vulnerability-check.yml

  backend-vulnerability-check:
    name: Backend vulnerability
    uses: ./.github/workflows/backend-vulnerability-check.yml

  backend-sast-check:
    name: Backend SAST
    uses: ./.github/workflows/backend-sast-check.yml

  frontend-lint-format-check:
    name: Frontend lint
    needs: frontend-vulnerability-check
    uses: ./.github/workflows/frontend-lint-format-check.yml

  backend-lint-format-check:
    name: Backend lint
    needs: [backend-vulnerability-check, backend-sast-check]
    uses: ./.github/workflows/backend-lint-format-check.yml

Step 5 — Update the gatekeeper

  1. Scroll to the bottom of ci.yml and add the three security jobs to the pipeline-success job's needs array, so the final gate also watches them (at 400:21).
  2. Commit and push. Open a pull request and watch the security jobs spin up first.
  pipeline-success:
    name: Pipeline success
    needs:
      [
        frontend-vulnerability-check,
        backend-vulnerability-check,
        backend-sast-check,
        frontend-lint-format-check,
        backend-lint-format-check,
        frontend-unit-tests,
        backend-unit-tests,
      ]
    runs-on: ubuntu-latest

What you should see
  • In the Actions tab, the visual graph now shows Frontend vulnerability, Backend vulnerability and Backend SAST running first, with arrows into the lint jobs (at 400:48).
  • On clean code, every job is green and pipeline-success passes — the presenter's final run took about a minute and a half (at 430:06).
  • If pip-audit finds a flaw, its log shows a table with the package name, current version, the CVE id, and a severity score (at 401:58).
  • When you add the MD5 flaw, the Bandit job fails with one High severity issue pointing at the exact line (at 429:19).
Common mistakes
  • Using pnpm version 10 with these workflows — pnpm 11 needs Node.js 22 or newer, and the extra supply-chain protection only comes with version 11 (at 396:42).
  • Pointing pip-audit at the wrong file. Use requirements.txt, or the project directory if you rely on pyproject.toml (at 397:56).
  • Expecting Bandit to fail on every warning. With -ll it ignores Low severity issues on purpose, so a passing scan can still list Low findings.
  • Forgetting to add the new jobs to pipeline-success's needs. The scans would run but the gatekeeper would not wait for them, so a failure could slip through.
  • Leaving a deliberate test flaw (like the MD5 line) in your code. It is only for the demo — remove it immediately (at 429:43).
Security note

SCA and SAST catch different problems and neither replaces the other: pnpm audit and pip-audit only know about published vulnerabilities in other people's packages, while Bandit reads your code for risky patterns. Even together they are "static" checks — they read code at rest and cannot see flaws that only appear while the app runs. That gap is why the next step adds DAST (OWASP ZAP) to attack the live application. Run these checks on every pull request, not just before release, so a vulnerable dependency or a weak algorithm can never reach production unnoticed.

Recap
  • Shift-left means running security checks inside CI, the moment code is written, instead of at release time.
  • SCA audits third-party libraries: pnpm audit for the frontend and the pip-audit action for the backend, both failing the build on a known CVE.
  • SAST scans your own code: Bandit with bandit -r . -ll reports only Medium and High severity issues and fails the job on a serious finding.
  • You added three reusable workflows and placed them first in ci.yml, with the lint jobs set to needs them — the Fail Fast strategy.
  • Adding the security jobs to pipeline-success's needs lets the single required check block a merge whenever any scan fails.
  • These checks are static; DAST (next step) covers what only shows up when the app is running.
