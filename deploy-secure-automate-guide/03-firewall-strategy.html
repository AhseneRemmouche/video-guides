The Firewall Strategy

Lock the server down with the UFW firewall and stop brute-force logins with Fail2Ban.

▶ Watch this part (57:19)

Your server now has strong locks on the front door: you log in with SSH keys and the root account is disabled. But a fresh Linux machine still accepts connections on every network port. In this step you close all those open windows. You turn on a firewall that blocks everything by default and only lets through the traffic you trust, then you add a tool that automatically bans the bots that keep knocking.

What you will set up (at 57:19)

The presenter lays out the plan for this session (at 57:43). First you configure UFW, the Uncomplicated Firewall that ships with Ubuntu, to deny all incoming traffic and open only the ports you trust. Next you install Fail2Ban, which watches your login logs and automatically bans any address that fails too many times (at 58:10). Finally you learn about the DigitalOcean Recovery Console, the safety net that lets you back in through the browser if you ever lock yourself out (at 58:34).

New to ports? What they are and why we block them

A port is a numbered doorway into your server. Each network service listens on its own number: SSH on 22, web traffic (HTTP) on 80, secure web traffic (HTTPS) on 443. A single machine has 65,535 of these doorways. By default Linux will answer on any of them if a program is listening, and attackers scan the whole internet looking for a door left ajar. A firewall lets you decide which doorways are open to the world and slam the rest shut.

New to firewalls? The mental model

A firewall is a guard standing between the internet and your server. Every incoming packet is checked against a list of rules. The most important rule is the default policy. When the default is "deny incoming", the guard turns away everything unless a specific rule says "let this one in". You then add a short allow-list: SSH now, and HTTP and HTTPS later when you install the web server. UFW is just a friendly front end for Linux's built-in firewall, so you do not have to learn the raw iptables syntax.

Configure the firewall with UFW

Connect to the server with your SSH alias, then follow these commands in order. The order matters: you must allow SSH before you turn the firewall on, or you will cut off your own connection (at 64:40).

  1. Check the current status. A fresh server reports Status: inactive (at 64:15). 
    sudo ufw status
  2. Allow SSH first. This opens port 22 so you keep access once the firewall is live (at 65:02). 
    sudo ufw allow OpenSSH
  3. Enable the firewall. UFW warns that it may disrupt existing SSH connections. Type y and press Enter (at 65:26). 
    sudo ufw enable
    Command may disrupt existing ssh connections. Proceed with operation (y|n)? y
Firewall is active and enabled on system startup
  4. Verify the active rules. The verbose view shows the default policy and your allow-list (at 65:52). 
    sudo ufw status verbose
    Status: active
Logging: on (low)
Default: deny (incoming), allow (outgoing), disabled (routed)
New profiles: skip

To                             Action      From
--                             ------      ----
22/tcp (OpenSSH (v6))          ALLOW IN    Anywhere (v6)
22/tcp (v6)                    ALLOW IN    Anywhere (v6)

Line by line

CommandWhat it does & why
sudo ufw statusufw is the firewall tool; status prints whether it is active and lists the rules. sudo runs it as administrator because firewall settings are system-wide. On a new server this says inactive, which means every port is open.
sudo ufw allow OpenSSHallow adds an exception to the deny-by-default policy. OpenSSH is a named application profile that stands for "TCP port 22". Running this before enabling the firewall is what keeps you from being locked out.
sudo ufw enableenable switches the firewall on and sets it to start automatically on every reboot. From this moment the default policy (deny incoming) is enforced for all ports except the ones you allowed.
sudo ufw status verboseThe verbose flag adds detail: the logging level and, most importantly, the Default: line. deny (incoming) is the rule that blocks every unlisted port; allow (outgoing) means your server can still reach out to the internet (for updates and so on).
What you should see

After ufw enable, the status should read Status: active with Default: deny (incoming) and an ALLOW IN line for 22/tcp (OpenSSH). Exit and reconnect with ssh my-website to confirm you still have access (at 67:04).

Common mistakes
  • Running sudo ufw enable before sudo ufw allow OpenSSH. This closes port 22 and your current session may be your last. If it happens, use the Recovery Console below.
  • Allowing a raw port number when a profile exists. ufw allow OpenSSH is clearer than ufw allow 22 because the name documents what the rule is for.
  • Forgetting that the firewall also protects you from yourself: a service you start on a random port will not be reachable until you add a rule for it.
Security note

Keep the allow-list as short as possible. Every open port is a possible way in. When you install Nginx in a later step you will come back and run sudo ufw allow 'Nginx Full' to open 80 and 443; until then, keeping them shut is the safer choice (at 67:04).

Stop brute-force bots with Fail2Ban

A firewall decides which ports are open, but it cannot tell a real user apart from a bot hammering the SSH door. If you read the authentication log (at 62:11) you will see a stream of failed logins from automated scanners trying common usernames like admin, root and test (at 58:34). Even though they cannot get in (you disabled password login), they waste CPU and fill your disk with log lines.

2025-12-07T10:59:44 sshd[615989]: Invalid user docker from 142.93.130.134
2025-12-07T11:01:28 sshd[616006]: Invalid user dspace from 142.93.130.134
2025-12-07T11:05:09 sshd[616037]: Invalid user elastic from 142.93.130.134
2025-12-07T11:05:38 sshd[616045]: Invalid user admin from 94.156.152.7

Fail2Ban watches that log in real time. When one address fails too many times, it tells the firewall to block that address completely. This is called an IP ban (at 60:34).

New to Fail2Ban? How the ban actually happens

Fail2Ban is a background service that tails your log files. Each service it protects is called a "jail". The sshd jail reads the SSH log and counts failures per source address. When the count crosses your limit within a time window, Fail2Ban inserts a temporary firewall rule that drops every packet from that address. After the ban time passes, it removes the rule automatically. You do not run anything by hand; it reacts on its own (at 60:59).

  1. Install Fail2Ban. It is in Ubuntu's default repositories. The -y answers "yes" to the prompts automatically (at 67:51). 
    sudo apt install fail2ban -y
  2. Create a local config. The default ban is only 10 minutes, which is too short. Never edit the shipped .conf file; create a .local file instead so updates cannot overwrite your changes (at 69:01). 
    sudo nano /etc/fail2ban/jail.local
  3. Paste the SSH jail settings. This turns on protection for SSH and raises the ban to one day (at 70:13). 
    [sshd]
enabled = true
bantime = 1d
maxretry = 5
findtime = 10m
  4. Restart so the new config is read. A common slip is to change the file but forget this step, so the old value stays in effect (at 72:40). 
    sudo systemctl restart fail2ban
  5. Make it start on boot. 
    sudo systemctl enable fail2ban
sudo systemctl start fail2ban

Line by line

LineSettingWhat it does & why
1[sshd]The name of the jail. It tells Fail2Ban to apply these rules to the SSH service, reading the SSH authentication log.
2enabled = trueTurns this jail on. Without it the section is ignored and no bans happen.
3bantime = 1dHow long a banned address stays blocked. 1d means one day. The default (10 minutes) is too short because persistent bots simply return later.
4maxretry = 5How many failures are allowed before a ban. Keep this at around 3 to 5. Do not set it to 1, or a single typo of your own could lock you out (at 70:38).
5findtime = 10mThe sliding window the failures must fit inside. Five failures spread over more than ten minutes will not trigger a ban; five within ten minutes will (at 71:03).

Verify Fail2Ban is working

  1. Confirm the ban time. The result is in seconds; 86400 is exactly 24 hours (at 72:15). 
    sudo fail2ban-client get sshd bantime
  2. Check the jail status. This shows how many addresses have been caught and which are currently banned (at 73:02). 
    sudo fail2ban-client status sshd
    Status for the jail: sshd

What you should see

get sshd bantime should return 86400. In the status output, any address under Banned IP list means the tool is doing its job (at 73:26). Watch the difference between Total banned and Currently banned: a count of 4 total with 1 currently banned just means three earlier bans have already expired.

Common mistakes
  • Editing jail.conf instead of jail.local. The next package update will overwrite jail.conf and silently undo your settings.
  • Changing bantime but not restarting the service, so get sshd bantime keeps returning 600 (at 72:40).
  • Setting maxretry = 1. One fumbled key and your own address is banned.

Your safety net: the Recovery Console

What if you make a mistake, like enabling the firewall before allowing SSH, and lock yourself out? DigitalOcean provides a Recovery Console that reaches the machine through your browser, bypassing SSH entirely (at 73:50). In the dashboard, open your droplet, click Access in the left sidebar, then Launch Recovery Console. Log in with your user password, then run the command you missed (at 75:36):

sudo ufw allow OpenSSH

Close the browser window and connect normally again from your terminal (at 75:58):

ssh my-website
Security note

The Recovery Console asks for a password. If you created your user without one, set it first with DigitalOcean's "Reset Root Password" button on the same Access page (at 74:17). Also test that root login is still refused: trying ssh root@your-ip should fail, proving the hardening from the previous step is intact (at 76:44).

Recap
  • A fresh server accepts traffic on every port; a firewall closes all of them except the ones you allow.
  • sudo ufw allow OpenSSH must come before sudo ufw enable, or you lock yourself out.
  • Default: deny (incoming) is the rule that blocks every unlisted port; each ALLOW IN row is a deliberate exception.
  • Fail2Ban reads your SSH log and bans an address after maxretry failures within findtime, for bantime.
  • Put custom settings in jail.local, not jail.conf, and restart the service so they take effect.
  • If you get locked out, the DigitalOcean Recovery Console reaches the server through the browser so you can fix the rule.
