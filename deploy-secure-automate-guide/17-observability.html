Observability: GoAccess & btop

Turn Nginx logs into readable analytics with GoAccess and watch resources live with btop++.

▶ Watch this part (545:00)

Your app is live and traffic is flowing through Cloudflare, but right now you are flying blind. A running server with no monitoring is like driving with a blacked-out windshield: you are moving, but you cannot see the obstacles until you hit one. This lesson gives you eyes. You will turn Nginx's own logs into traffic reports with GoAccess, watch your server's hardware live with btop, and learn to spot the single IP address that is hammering your site.

This is observability: the ability to understand what a system is doing from the outside, using the data it already produces. The best part is that you need no heavy JavaScript trackers, no Google Analytics, and no cookie-consent banners. Every answer is already sitting in your server's log files.

What the presenter explains

Client-side trackers slow down your frontend and force privacy banners (at 545:00). Because you run Nginx, you already have a perfect data source: the access log, which records every request for a page, an API endpoint, or a static file. GoAccess parses those raw log lines into a live, readable report. btop is a modern terminal monitor that draws your CPU, memory, disk, and network as live graphs so you can watch a small server that has very little room for error.

New to log files? What they are and why they matter

A log file is a plain text file where a program writes one line for each thing it does. Nginx writes one line every time a browser asks for something: the visitor's IP address, the time, the URL they wanted, and the status code it returned (200 for success, 404 for not found). Nobody reads these lines by hand, but a tool like GoAccess can count and group millions of them in seconds. The file lives at /var/log/nginx/<your_domain>-access.log on your server.

Turn Nginx logs into a live report with GoAccess

  1. Install GoAccess from Ubuntu's package manager.
  2. Point it at your access log and tell it the log format.
  3. Read the dashboard with the arrow keys; press q to quit.
sudo apt install goaccess -y
sudo goaccess /var/log/nginx/<your_domain>-access.log --log-format=COMBINED

The terminal instantly switches into an interactive, graphical dashboard inside your SSH session (at 548:30). Navigate the panels with the arrow keys, press Tab to move between them, and press q to return to the shell.

Line by line

Line(s)CodeWhat it does & why
1sudoRuns the next command as the administrator. Reading another user's log files and (later) binding privileged resources needs root rights.
1goaccessThe log analyzer itself. It reads lines of log text and groups them into counts: visitors, URLs, status codes, and more.
1/var/log/nginx/<your_domain>-access.logThe input file. This is the access log Nginx writes for your site. Replace <your_domain> with your real domain name.
1--log-format=COMBINEDTells GoAccess how each line is laid out. COMBINED is the standard Nginx format (IP, time, request, status, bytes, referrer, user agent). Without this flag GoAccess cannot parse the file and will ask you to pick a format.
What you should see

The terminal clears and fills with coloured panels: total requests, unique visitors, top requested URLs, static files, and HTTP status codes. The numbers update as you scroll. Key panels to read:

  • Unique visitors — real daily visitors, separate from total page views.
  • Requested files — which URLs are actually drawing traffic.
  • Static assets — images, CSS, and JS, kept apart from application logic.
  • HTTP status codes — how often visitors hit 404 or 500 errors.

Build a secure web dashboard

The terminal view is great for a quick check, but you may want a dashboard in a browser. GoAccess can write a standalone HTML report. Because that report exposes your internal traffic, you must lock it behind a password so the public cannot read it. You will use Nginx HTTP basic authentication.

  1. Install the Apache utilities that include the password tool.
  2. Create an encrypted password file for an admin user.
  3. Add a protected location to your Nginx site, test, and reload.
  4. Generate the HTML report into your frontend folder.
sudo apt install apache2-utils -y
sudo htpasswd -c /etc/nginx/.htpasswd admin
sudo nano /etc/nginx/sites-available/<your_domain>.com

Inside your secure port 443 server block, paste this location rule right above your general single-page-app fallback routes:

location = /analytics.html {
    root /web_app/frontend/dist;
    auth_basic "Restricted Area";
    auth_basic_user_file /etc/nginx/.htpasswd;
}

Line by line

Line(s)CodeWhat it does & why
1location = /analytics.html {Matches one exact URL. The = means "only this path", so the rule applies to the report file and nothing else.
2root /web_app/frontend/dist;Tells Nginx the file lives in your built frontend folder. The report will be written here in the next step.
3auth_basic "Restricted Area";Turns on password protection for this path. The text is the message shown in the browser's login box.
4auth_basic_user_file /etc/nginx/.htpasswd;Points at the encrypted password file you just created. Only users in that file can open the page.
5}Closes the location block.
sudo nginx -t
sudo systemctl reload nginx
sudo goaccess /var/log/nginx/<your_domain>-access.log -o /web_app/frontend/dist/analytics.html --log-format=COMBINED

Here the extra flag -o /web_app/frontend/dist/analytics.html means "write the output to this HTML file" instead of drawing in the terminal. Open https://<your_domain>.com/analytics.html and the browser pauses to ask for your username and password before the charts load.

Common mistakes
  • Forgetting sudo nginx -t before reload. If the config has a typo, a reload can take Nginx down. Always test first; it prints syntax is ok when safe.
  • Putting the location block in the plain HTTP (port 80) server instead of the HTTPS (port 443) one, so the protection never applies to the real site.
  • Losing the password you set with htpasswd. Re-run the command to reset it (drop -c after the first time, or it overwrites the whole file).
Security note

Basic authentication sends the password on every request, so it is only safe over HTTPS, which you already have. Never place the raw analytics.html or the goaccess.json export in a public, unprotected folder: your traffic data reveals your visitors' IP addresses and your busiest endpoints, which is exactly what an attacker wants to know.

Keep the report fresh automatically

The HTML report is a snapshot: it only shows data up to the second you ran the command. Worse, Linux uses log rotation (logrotate) to stop files growing forever. Every night it compresses yesterday's log into a file ending in .gz. If your report only reads today's active text file, it resets to near-zero every morning (at 560:10). A scheduled job fixes both problems: it runs on a timer and it reads the archives too.

sudo crontab -e

At the bottom of the cron file, add this single entry to rebuild the dashboard every hour, on the hour:

0 * * * * zgrep -h . /var/log/nginx/<your_domain>-access.log* | goaccess - -o /web_app/frontend/dist/analytics.html --log-format=COMBINED

Line by line

Line(s)CodeWhat it does & why
10 * * * *The cron schedule: minute 0 of every hour, every day. This is why the report never goes stale.
1zgrep -h .zgrep searches inside compressed files without decompressing them to disk first. The pattern . matches any non-empty line; -h hides filenames so only log content flows through.
1...access.log*The * wildcard matches both today's access.log and every older .gz archive, so the full history is included.
1|The pipe. It passes the whole merged stream of log lines straight into the next command.
1goaccess -The - (dash) tells GoAccess to read from standard input (the pipe) instead of opening a file on disk.
1-o /web_app/frontend/dist/analytics.htmlWrites the rebuilt report to the protected file your Nginx rule serves.
1--log-format=COMBINEDSame format flag as before, so GoAccess knows how to read each line.
New to cron? What a scheduled job is

Cron is the built-in Linux scheduler. Each line in a crontab is one job: five time fields (minute, hour, day-of-month, month, day-of-week) followed by the command to run. An asterisk means "every". So 0 * * * * reads as "at minute 0 of every hour". You edit the list with crontab -e; the jobs then run quietly in the background with no terminal open.

Watch your hardware live with btop

Traffic is only half the picture. Running Nginx, FastAPI, and Meilisearch together on a small server leaves little room for error, so you need to see CPU, memory, disk, and network in real time (at 565:40). Ubuntu ships with top, but it is text-heavy and hard to read. btop draws the same data as clean, live graphs.

  1. Download the precompiled binary for 64-bit Linux.
  2. Extract it, then install it system-wide.
  3. Grant sensor access, clean up, and launch it.
wget https://github.com/aristocratos/btop/releases/download/v1.4.0/btop-x86_64-linux-musl.tbz
tar -xjf btop-x86_64-linux-musl.tbz
cd btop
sudo make install
sudo make setcap
cd ..
rm -rf btop btop-x86_64-linux-musl.tbz
btop

1wget https://github.com/.../btop-x86_64-linux-musl.tbzDownloads btop version 1.4.0 as a single precompiled file. Check the releases page for newer versions or other CPU types.
2tar -xjf btop-x86_64-linux-musl.tbzExtracts the archive. -x extract, -j for the bzip2 compression of .tbz, -f names the file.

New to swap memory? Why it matters here

RAM is fast memory your programs run in. Swap is a reserved area on the much slower disk that Linux uses as overflow. When RAM fills up, the kernel moves rarely-used (cold) pages into swap to avoid crashing. That saves the server, but anything in swap is slow to reach, so heavy swapping makes your whole app feel sluggish. In btop, watching swap fill up is an early warning that your server is short on RAM.

Common mistakes
  • Skipping sudo make setcap, then wondering why the power and per-core panels are blank.
  • Running a load test on the server while watching btop there. The monitor itself and the test both steal CPU, distorting the numbers. Watch btop on the server, but drive the load from your laptop (next lesson).
  • Leaving the downloaded .tbz and unpacked folder behind, slowly wasting disk on a small box.

Find the one IP that is hammering you

In the GoAccess Requested files panel you will often see endless hits on paths like /wp-login.php or /admin/config.php. Your FastAPI and Vue app has no such files, so these are automated bots scanning for known flaws (at 578:20). Nginx safely answers them with 404, but they still waste memory and clutter your logs. A short Python script finds the worst offenders for you.

sudo goaccess /var/log/nginx/<your_domain>-access.log -o /web_app/goaccess.json --log-format=COMBINED
nano /web_app/find_bad_actors.py
import json
import sys

try:
    with open('/web_app/goaccess.json', 'r') as f:
        data = json.load(f)
except FileNotFoundError:
    print("Error: Could not find goaccess.json file.")
    sys.exit(1)

hosts = data.get('hosts', {}).get('data', [])

print(f"{'IP Address':<20} {'Total Hits':<15} {'Traffic Share':<15}")
print("-" * 50)

for host in hosts[:10]:
    ip = host.get('data')
    hits = host.get('hits', {}).get('count', 0)
    percent = host.get('hits', {}).get('percent', "0.00%")
    print(f"{ip:<20} {hits:<15} {percent:<15}")

print("-" * 50)
print("Review Checklist:")
print("Look for severe traffic imbalances (outliers). If the top IP has")
print("thousands of hits while others have fewer than 50, block it.")

Common mistakes

Do not ban entries blindly. Look for an extreme outlier. In the output above the top IP has over 35% of all traffic while the next drops to a normal baseline: the top address is clearly an automated scanner, and the lower ones are real people. Banning a busy-but-legitimate visitor would lock out a genuine user. The actual firewall block (with UFW) comes in the maintenance lesson.

Recap
  • Observability means understanding your server from the data it already produces — no extra trackers needed.
  • GoAccess turns the Nginx access log into a live terminal dashboard, or a secure, password-protected HTML report.
  • A cron job with zgrep rebuilds the report hourly and reads the compressed .gz archives, so history survives log rotation.
  • btop shows CPU, memory/swap, disk, and network live; the memory panel is critical on a small server.
  • A short Python script over the GoAccess JSON export reveals the outlier IPs worth blocking.
