Manual Deployment: Code, Python, Node & Swap

Copy the app to the server, set up Python and Node, and add swap memory so a small server can build it.

▶ Watch this part (79:07)

Your server is secure, but empty. In this step you put it to work: you move your project from your laptop up to the machine, install the runtimes your app needs (Python for the backend, Node.js for the frontend), add "swap" memory so a small server can finish a heavy build, and then preview the result safely through an encrypted SSH tunnel without opening a single new port.

The plan for this session (at 79:32)

The presenter walks through the roadmap (at 80:40). You transfer the project with the scp command and fix its file ownership. You install the runtimes: Python for the backend, Node.js for the frontend (at 81:04). You set up swap memory so the build does not crash for lack of RAM. Finally you use an SSH tunnel to view the site in your own browser before opening anything to the public.

Move the project to the server

You could copy files one by one, but that is slow. Instead you compress the whole project into a single archive, upload it, and unpack it on the server (at 82:45). You exclude the big folders that can be rebuilt remotely.

  1. Compress the project on your laptop. Run this inside your project folder (at 83:10). 
    tar -czvf source_code.tar.gz --exclude='node_modules' --exclude='venv' --exclude='__pycache__' --exclude='.git' .
  2. Upload it with scp. Thanks to the SSH alias you set up earlier, you only type my-website instead of the full IP and key path. It lands in /tmp/ because your user can always write there (at 83:58). 
    scp source_code.tar.gz my-website:/tmp/
  3. Connect and confirm it arrived. 
    ssh my-website
ls /tmp/source_code.tar.gz

New to scp? How it relates to SSH

SSH opens an encrypted connection to a remote machine so you can run commands there. scp rides on that same connection to copy files instead. Because you already taught your SSH config about my-website (the IP, user and key), scp inherits all of it; you never retype the address. Anything you send is encrypted in transit, just like your login.

Alternative: pulling code with git

Instead of uploading an archive, you can let the server download the code itself. If your project is on GitHub, you can use git on the server to clone it. The author's own source is public, so this works as a practice dummy (at 79:54).

git clone https://github.com/ImadSaddik/ImadSaddikWebsite.git
WordWhat it does & why
gitThe version-control tool. It can download ("clone") a complete repository from a remote host.
cloneThe subcommand that copies a whole repository, including its history, into a new folder.
https://...gitThe repository URL. Git fetches everything at that address into a folder named after the repo.

This guide follows the scp path because it also works for private code that is not on GitHub, and it uploads exactly what is on your machine.

Organize the files on the server

Keep application code out of your home directory. A neutral location like /web_app keeps your app separate from personal files such as .ssh and avoids permission problems later (at 85:13).

  1. Create the folder. 
    sudo mkdir /web_app
  2. Move the archive in and extract it. 
    sudo mv /tmp/source_code.tar.gz /web_app/
cd /web_app
sudo tar -xzvf source_code.tar.gz
  3. Check the files are there. 
    ls
# Output: README.md ...
  4. Take ownership. Because you used sudo, the files belong to root. Hand them to your own user so you do not need sudo for every small edit (at 86:51). 
    sudo chown -R <your_username>:<your_username> /web_app
  5. Confirm the new ownership. Look at the third and fourth columns. 
    ls -la /web_app
    total 44
drwxrwxr-x 7 <your_username> <your_username> 4096 Oct 28 07:20 .
drwxr-xr-x 23 root           root            4096 Oct 28 07:19 ..
...
drwxrwxr-x 6 <your_username> <your_username> 4096 Oct 26 21:37 frontend
  6. Install the Python build tools. 
    sudo apt install python3-pip python3-venv python3-dev -y

Run the backend in a virtual environment

Before wiring up the production servers, make sure the app runs at all. A Python virtual environment keeps this project's packages separate from the system's, so nothing collides (at 88:24).

  1. Create and activate the environment. When the prompt shows (venv) before your username, it is active (at 88:47). 
    cd /web_app/backend

python3 -m venv venv
source venv/bin/activate
  2. Install the backend packages into it. Make sure (venv) is showing first, so everything stays inside the project (at 89:13). 
    pip install -r requirements.txt
  3. Start the app for a quick test with uvicorn (at 89:37). 
    uvicorn main:app --host 0.0.0.0 --port 8000
    INFO: Started server process [5602]
INFO: Waiting for application startup.
INFO: Application startup complete.
INFO: Uvicorn running on http://0.0.0.0:8000 (Press CTRL+C to quit)
  4. Confirm the firewall is doing its job. If UFW is active, port 8000 is not reachable from outside, which is what you want. 
    sudo ufw status
  5. Test the API from inside the server. Open a second SSH session and ask the health endpoint. A JSON reply means the backend is alive. Then stop it with Ctrl+C. 
    curl http://127.0.0.1:8000/api/health

New to virtual environments? Why not just install globally?

If you installed every project's packages into the system Python, two projects that need different versions of the same library would fight. A virtual environment is a private folder holding its own Python and its own packages. Activate it, and pip installs into that folder only; deactivate it, and the system Python is untouched. You can delete and rebuild a venv at any time, which is exactly why you excluded it from the upload earlier.

What you should see

After source venv/bin/activate, your prompt starts with (venv). After uvicorn starts, you see Application startup complete. The curl health check returns JSON like {"status": "ok"} (at 90:27).

Common mistakes
  • Running pip install before activating the venv. The packages then land in the system Python and the app may not find them. Check for the (venv) marker first (at 89:13).
  • Expecting http://your-ip:8000 to open in your browser. The firewall blocks port 8000 on purpose; test with curl from inside instead.
  • Closing the terminal and expecting the app to keep running. This uvicorn command is only for a quick test; it stops when the terminal does.

Install Node.js and build the frontend

The Vue.js frontend needs Node.js. The cleanest way to install it is NVM, the Node Version Manager (at 94:12).

  1. Install NVM. 
    curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.3/install.sh | bash
  2. Load NVM into the current shell. Without this, the nvm command is "not found" until you open a new terminal (at 94:59). 
    source ~/.bashrc
  3. Install the latest LTS Node.js. LTS means "Long Term Support", the stable line (at 95:24). 
    nvm install --lts
  4. Install pnpm, the package manager this project uses with npm (at 96:09). 
    npm install -g pnpm@latest-10
  5. Install the frontend dependencies. 
    cd /web_app/frontend
pnpm install
  6. Try to build. On a small server this will probably fail (at 96:58). 
    pnpm run build
    Building for production...Killed
ELIFECYCLE Command failed with exit code 137.

Why did the build get "Killed"? (at 96:58)

Compiling a modern frontend briefly needs a lot of memory. The cheapest droplets have very little RAM. When the build asks for more than exists, the Linux kernel steps in and kills the process to protect the system. The Killed message and exit code 137 are the signs of this "Out of Memory" event. The fix is to give the system more memory to fall back on: a swap file.

Add swap memory so the build can finish

Swap memory borrows space from the SSD and uses it as slow extra RAM. It is slower than real memory, but it stops the build from crashing (at 98:09).

  1. Create a 2 GB swap file. 2 GB is a good starting size (at 98:57). 
    sudo fallocate -l 2G /swapfile
  2. Lock it down. Only root should read or write it (at 100:08). 
    sudo chmod 600 /swapfile
  3. Format and turn it on. 
    sudo mkswap /swapfile
sudo swapon /swapfile
  4. Verify it is active. 
    sudo swapon --show
    NAME      TYPE  SIZE USED PRIO
/swapfile file  2G   0B   -2
  5. Make it survive reboots. Add it to the filesystem table so it loads on every boot (at 102:32). 
    echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

pnpm run build
  2. If you hit a heap-limit error, tell Node.js it may use more memory, then build (at 104:31).

Security note

chmod 600 /swapfile is not optional. Swap can contain whatever was recently in memory, including secrets. Leaving it world-readable would let any user on the box read that data. The 600 permission limits it to root (at 100:57).

Preview the site through an SSH tunnel

The build created a dist folder of static files. Serve it with a quick Python web server, then view it on your laptop without opening a public port (at 104:56).

  1. Start a temporary web server in the build folder. 
    cd /web_app/frontend/dist
python3 -m http.server 8080
  2. Open a tunnel from your laptop. In a new local terminal, forward your laptop's port 8080 to the server's port 8080 (at 108:12). 
    # Syntax: ssh -L <local_port>:localhost:<remote_port> <alias>
ssh -L 8080:localhost:8080 my-website
  3. Visit the site. Open http://localhost:8080 in your browser. The request travels through the tunnel to the server and back. Press Ctrl+C in both terminals when done.

Line by line

CommandWhat it does & why
python3 -m http.server 8080Python's built-in web server. -m http.server runs the module; 8080 is the port it listens on. It serves the files in the current folder (here, the built dist). It is only for a quick preview.
ssh -L 8080:localhost:8080 my-websiteOpens an SSH connection and a tunnel. -L means local port forwarding. The three parts are: the port to open on your laptop (8080), then localhost:8080 as seen from the server (where the Python server is listening). Traffic to your laptop's 8080 is forwarded, encrypted, to the server's 8080.
New to SSH tunnels? Why this is safer than opening a port

You could open port 8080 in the firewall, but then the whole internet could reach your unfinished site. An SSH tunnel avoids that. Because you are already allowed in over SSH, the tunnel carries your browser's traffic through that same trusted, encrypted connection to a port that is only visible inside the server. Close the SSH session and the tunnel disappears, leaving nothing exposed (at 109:24).

What you should see

Your Vue.js app loads at http://localhost:8080 in your browser (at 110:11). The pages, styles and images appear, even though no new port was opened on the server.

Common mistakes
  • Trying to reach http://your-ip:8080 directly. The firewall blocks it; that is why you need the tunnel.
  • Expecting API calls to work in this preview. The backend is not wired up through a proxy yet, so API requests will fail. You are only checking that the HTML and CSS load (at 108:59).
  • Forgetting the server side. The tunnel does nothing unless python3 -m http.server 8080 is actually running on the server.
Recap
  • Compress with tar, upload with scp to /tmp/, then move to /web_app and chown it to your user.
  • Run the backend inside a Python venv so its packages stay isolated; test it with uvicorn and curl.
  • Install Node.js with NVM and the frontend deps with pnpm; a low-RAM build can be Killed for lack of memory.
  • A swap file (fallocate → chmod 600 → mkswap → swapon) adds virtual RAM; add it to /etc/fstab so it survives reboots.
  • If the build still fails, raise Node's heap with NODE_OPTIONS="--max-old-space-size=2048".
  • Preview the built site through an ssh -L tunnel, reaching a private server port without opening the firewall.
