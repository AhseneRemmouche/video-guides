Secure Management: SSH Tunnel & Backups

Reach the Meilisearch dashboard safely over an SSH tunnel and automate backups with a scheduled script.

▶ Watch this part (247:50)

Meilisearch is running in production, hidden behind your firewall. Two jobs remain to make it safe to operate day to day. First, protect the data: if the server crashes or the database is corrupted, you could lose everything, so you schedule automatic backups. Second, make it manageable: port 7700 is blocked from the internet, which is great for security but awkward when you want a visual dashboard. The trick is an SSH tunnel — you reach the locked-down engine without opening a single public port (at 245:47).

Security note. The whole point of this step is to manage a private service without weakening the firewall. Opening port 7700 to the world just to use an admin dashboard would be a bad trade. Instead you ride your existing, already-allowed SSH connection, and close it the moment you are done.

Part 1 — Schedule automatic backups

Right now your data lives on the edge: one disk failure and it is gone. The fix is to have Meilisearch take a snapshot on a timer. A snapshot is an exact copy of the database that acts as a safety net (at 216:14). You turn this on by adding two flags to the same systemd unit file you wrote in the last step.

New to backups? Snapshots, and how this differs from cron

A backup is simply a spare copy of your data you can restore from after something goes wrong. On Linux, people often schedule recurring jobs with cron, the classic time-based scheduler. Here you do not need cron at all: Meilisearch has its own built-in timer. You tell it how many seconds to wait between snapshots with --schedule-snapshot, and it quietly writes a fresh copy on that schedule. Fewer moving parts, one less thing to configure.

sudo nano /etc/systemd/system/meilisearch.service

Add --schedule-snapshot and --snapshot-dir to the ExecStart command so the final block looks exactly like this (at 248:13).

ExecStart=/usr/local/bin/meilisearch \
  --db-path "/var/lib/meilisearch/data" \
  --dump-dir "/var/lib/meilisearch/dumps" \
  --schedule-snapshot 86400 \
  --snapshot-dir "/var/lib/meilisearch/snapshots"
Line(s)CodeWhat it does & why
1ExecStart=/usr/local/bin/meilisearch \The command systemd runs to launch the engine. The \ continues it onto the next lines.
2--db-path "/var/lib/meilisearch/data" \Where the live database is stored. Unchanged from the last step.
3--dump-dir "/var/lib/meilisearch/dumps" \Where dumps (migration files) are written. Unchanged.
4--schedule-snapshot 86400 \Take a snapshot every 86,400 seconds, which is exactly 24 hours (at 248:37). Lower it to 3600 for hourly backups if your data changes a lot.
5--snapshot-dir "/var/lib/meilisearch/snapshots"Where to save the snapshot files, kept inside the system user's own directory so permissions stay tidy.

Save and exit. The snapshots folder does not exist yet, so create it and give it to the meilisearch user (at 249:00).

sudo mkdir -p /var/lib/meilisearch/snapshots
sudo chown -R meilisearch:meilisearch /var/lib/meilisearch/snapshots
Line(s)CodeWhat it does & why
1sudo mkdir -p /var/lib/meilisearch/snapshotsCreates the folder the engine will write backups into. -p makes parents as needed and does not error if it exists.
2sudo chown -R meilisearch:meilisearch /var/lib/meilisearch/snapshotsGives the folder to the service user so it has permission to write snapshot files. Without this the scheduled backup would fail silently.

Reload systemd and restart to apply the new backup policy.

sudo systemctl daemon-reload
sudo systemctl restart meilisearch
What you should see. After the first interval, a snapshot file appears in /var/lib/meilisearch/snapshots. From now on Meilisearch quietly saves a safe copy every day with no further action from you.

Part 2 — Reach the dashboard through an SSH tunnel

Because UFW blocks port 7700, nobody on the internet can reach Meilisearch — including you. To inspect documents or tweak settings with a GUI without poking a hole in the firewall, you use SSH tunneling again, the same technique you used to preview the front-end build earlier (at 247:50).

New to SSH tunnels? What local port forwarding means

An SSH tunnel is a secure, encrypted pipe built on top of your normal SSH connection. With local port forwarding you tell SSH: "listen on a port on my laptop, and forward anything that arrives there, through the encrypted connection, to a port on the server." Your browser talks to localhost on your laptop; the request travels the pipe and comes out at the server's port 7700 as if it were local. Nothing new is exposed to the internet, because the traffic rides inside the SSH connection (port 22) that is already allowed.

Run this on your local computer (not on the server) and leave the window open (at 250:35).

ssh -L 7700:127.0.0.1:7700 my-website
Line(s)CodeWhat it does & why
1sshOpens a normal SSH connection to the server — the same encrypted channel you log in with.
1-LTurns on local port forwarding. It is what makes this a tunnel rather than a plain login.
17700 (first)The port to open on your laptop. Traffic you send to localhost:7700 enters the tunnel here.
1127.0.0.1The address to connect to from the server's side of the tunnel. 127.0.0.1 means "the server itself," where Meilisearch is listening.
17700 (second)The port on the server to forward to — Meilisearch's port.
1my-websiteThe SSH alias for your server, from the config file you set up earlier.

If you never set up an SSH config alias, use the full connection string instead.

ssh -L 7700:127.0.0.1:7700 -i ~/.ssh/<YOUR_KEY_NAME> <YOUR_USERNAME>@<YOUR_DROPLET_IP>

Connect the visual dashboard

With the tunnel open, use the open-source tool meilisearch-ui to manage your indexes visually, without installing anything on the server. Go to https://meilisearch-ui.vercel.app/ and click "Add Instance" (at 252:12).

  1. Name: a descriptive label, for example Production DB.
  2. Host: http://127.0.0.1:7700 — this hits your local tunnel, which forwards to the server.
  3. API Key: your production master key.
Security note. Wondering why a secure https:// site can talk to an insecure http:// host without the browser blocking it? Modern browsers make a built-in exception for 127.0.0.1 and localhost, so local development and tunneling work without SSL errors (at 252:12).

Close the tunnel when you are done

When you finish managing data, close the terminal running the SSH command or press Ctrl+C. That instantly breaks the tunnel and cuts off access (at 254:57). Because the whole session happened inside the encrypted pipe, the data was never exposed to the public internet.

Common mistakes. "Address already in use" when you run ssh -L usually means a local Meilisearch is still running on port 7700 (at 251:01) — stop it and retry. Running the ssh -L command on the server instead of your laptop (it must run locally). Setting the dashboard host to the server's public IP instead of 127.0.0.1:7700, which bypasses the tunnel and fails.
Recap
  • You scheduled daily snapshots with --schedule-snapshot 86400 and --snapshot-dir, so Meilisearch backs itself up without cron.
  • Only the most recent snapshot is kept, so backups never fill the disk, and a snapshot is your restore path if data is lost.
  • You reached the private engine with an SSH tunnel (ssh -L 7700:127.0.0.1:7700 my-website), local port forwarding that rides your existing SSH connection.
  • You connected the meilisearch-ui dashboard to http://127.0.0.1:7700 — the laptop end of the tunnel — with your production master key.
  • No public port was ever opened: the firewall stayed closed and the traffic stayed inside the encrypted pipe.
  • Closing the terminal breaks the tunnel instantly, sealing the engine off from the outside world again.
