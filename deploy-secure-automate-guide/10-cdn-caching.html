The CDN Layer & Caching

Serve static front-end assets worldwide through Cloudflare's CDN with strict end-to-end SSL.

▶ Watch this part (282:42)

Your site is now live and secure on its own domain, but there is one problem no code can fix: physical distance. If your server sits in Morocco, a visitor in Sydney waits while every request crosses oceans. In this lesson you put a CDN in front of your app using Cloudflare. Cloudflare copies your static assets onto edge servers all over the world, so each visitor downloads the front end from a machine near them. You will hand DNS control to Cloudflare, set end-to-end encryption to Full (strict), restore real visitor IPs in your logs, and tune Nginx caching so updates never leave users stuck on a stale page.

Concept 1: why distance costs you speed

The author measured load times from several cities using an uptime test (around 283:10). Nearby users saw the site in a fraction of a second, but Beijing took over 3.9 seconds because the signal had to travel halfway around the planet. That delay is latency, and you cannot remove it by making the server faster, the bottleneck is the length of the cable.

New to CDNs and edge servers? What they are

A CDN, or Content Delivery Network, is a worldwide fleet of servers that keep copies of your files close to users. Each of those machines is an edge server, so called because it sits at the outer edge of the network, near people, instead of in one central data centre. When a visitor requests your site, the CDN serves the copy from the nearest edge instead of making the request travel all the way to your origin server. Your origin is still the source of truth; the edges are fast local mirrors.

Step-by-step: put Cloudflare in front of your site

  1. Create a free Cloudflare account and, on the dashboard, click Add then Connect a domain (around 286:00).
  2. Enter your domain (for example yourdomain.com), leave "Quick scan for DNS records" checked so Cloudflare imports the A and CNAME records you made in Porkbun, optionally block AI crawlers, and click Continue.
  3. Choose the Free plan. It includes everything a personal site needs.
  4. Check the proxy status on the imported records (see the table below).
  5. Hand over DNS authority by replacing Porkbun's nameservers with the two Cloudflare gives you.
  6. Set SSL/TLS to Full (strict) before the switch finishes, this step is not optional.

Concept 2: Full (strict) and the two SSL legs

With Cloudflare in the middle, there are now two connections, not one: browser to Cloudflare, and Cloudflare to your origin. Full (strict) encrypts both legs and makes Cloudflare verify the real Let's Encrypt certificate you installed last lesson (around 290:30). Because that certificate is already valid, strict mode gives you true end-to-end encryption with no extra work.

New to Cloudflare's SSL modes? What the options mean

Cloudflare offers several encryption modes. "Flexible" encrypts only the first leg (browser to Cloudflare) and talks to your origin over plain HTTP, which is insecure and causes redirect loops when your origin already forces HTTPS. "Full" encrypts both legs but does not check your origin's certificate, so a fake one would be accepted. "Full (strict)" encrypts both legs and verifies that your origin presents a valid, trusted certificate. Since you installed a real Let's Encrypt certificate in the previous lesson, strict is both the safest choice and the one that avoids the "Too Many Redirects" error.

Concept 3: cache hits and misses at the edge

When a request reaches an edge server, one of two things happens. If the edge already has a fresh copy of the file, that is a cache hit and it answers instantly. If it does not, that is a cache miss: the edge fetches the file from your origin once, stores it, and serves every later visitor from the fast local copy.

Step-by-step: restore real visitor IPs

Now that traffic flows through Cloudflare, your Nginx logs and FastAPI app see Cloudflare's IP on every request instead of the real visitor, which breaks analytics and geolocation (around 300:10). Fix it at the server level by trusting Cloudflare's IP ranges and reading the real IP from the CF-Connecting-IP header.

Create a config file in Nginx's conf.d directory (Nginx loads every file there automatically):

sudo nano /etc/nginx/conf.d/cloudflare.conf

Paste the following:

Test, reload, then watch the live access log while you open the site in a browser:

sudo nginx -t
sudo systemctl reload nginx
sudo tail -f /var/log/nginx/<your_domain>.com-access.log
What you should see. Before the fix, the first column of every log line was a Cloudflare IP like 172.70.240.61. After the fix, you see your own ISP's IP address, proof the real visitor IP is now recorded.

Concept 4: cache the right things, never the wrong things

A CDN caches aggressively by default, which is dangerous for a Single Page Application. If the browser caches your index.html, a returning visitor may load yesterday's entry point, which points at JavaScript files your last deploy already deleted, leaving a blank white screen (around 303:40). The rule is simple: never cache the entry point, cache the hashed assets forever.

New to Cache-Control headers? What they do

When a server sends a file, it can attach a Cache-Control header that tells browsers and CDNs how long they may reuse their saved copy. no-cache and no-store mean "do not keep a reusable copy; always ask again". max-age=31536000 is a number of seconds (here one year) the copy stays fresh. immutable promises the file will never change, so the browser does not even bother re-checking. Good caching headers are the difference between instant repeat visits and a page that refetches everything every time, or worse, one that shows stale code.

Open your site's Nginx config and replace the existing location / block with these three blocks inside the secure (port 443) server block:

sudo nano /etc/nginx/sites-available/<your_domain>.com
# 1. Never cache the entry point
# The browser must always check the server for the latest version of the app.
location = /index.html {
    root /web_app/frontend/dist;
    add_header Cache-Control "no-cache, no-store, must-revalidate";
}

# 2. Cache assets forever
# Vite adds a unique hash to filenames in the /assets directory.
# If the code changes, the filename changes. Therefore, we can cache these heavily.
location /assets/ {
    root /web_app/frontend/dist;
    add_header Cache-Control "public, max-age=31536000, immutable";
}

# 3. Handle SPA routing (Fallback)
# If the request is not for a specific asset or index.html, fall back to index.html
location / {
    root /web_app/frontend/dist;
    try_files $uri $uri/ /index.html;
}

Common mistakes. Accidentally caching index.html (the blank-white-screen bug after a deploy). Using immutable on files whose names do not change, which pins old content in users' browsers. And forgetting sudo nginx -t before reloading, a stray brace breaks the whole config.

The trade-off you just made

Adding a CDN buys real benefits but adds a middleman (around 306:30).

Recap
  • Distance creates unavoidable latency; a CDN fixes it by serving static assets from edge servers near each user (Beijing fell from 3.9s to 1.5s).
  • Proxy your A and CNAME records (orange cloud), keep email records DNS-only, delete the old NS records, and hand DNS authority to Cloudflare's nameservers.
  • Set SSL/TLS to Full (strict) so both legs, browser→Cloudflare and Cloudflare→origin, are encrypted and your Let's Encrypt cert is verified; skipping it causes a redirect loop.
  • cloudflare.conf trusts Cloudflare's IP ranges and reads CF-Connecting-IP, restoring real visitor IPs in your logs.
  • Cache rules: never cache index.html, cache hashed /assets/ for a year with immutable, and fall back to index.html for SPA routing.
