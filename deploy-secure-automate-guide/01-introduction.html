Introduction & Architecture

The deployment problem, the example app (FastAPI + Vue + Meilisearch), and the manual-first, six-module roadmap.

▶ Watch this part (00:00)

You built a web app and it runs beautifully on your machine. Then a friend asks for the link, and you realise there is no link. The app lives on your laptop, and nobody else can reach it. This first lesson explains the problem this whole course solves: taking an app from your computer to a real server where anyone in the world can use it. We will meet the example app we deploy, agree on a "do it by hand first" philosophy, and map the full journey from an empty machine to a secure, global, self-healing system.

There is almost no typing in this lesson. It is a mental map. Every later lesson fills in one part of the big picture you are about to see, so it is worth going slowly here.

The problem: users cannot reach your laptop

When you run an app during development, it answers only on localhost — a special address (127.0.0.1) that means "this same computer". Your browser can open it because your browser is on the same machine. A user in another city has no route to your laptop at all (at 01:32). Laptops sleep, change networks, and sit behind home routers that block incoming connections. They were never meant to serve the public.

The fix is to put the code somewhere that is always on, always reachable, and has a public address: a rented server in a data centre. Moving your code there, and making it survive the open internet, is what we call deployment (at 01:57). The place it ends up running is the production environment.

New to "server" and "production"? What they mean

A server is just a computer whose job is to answer requests from other computers over a network. It has no screen on your desk; you talk to it over the internet. Production is the environment where real users meet your app, as opposed to your development machine where only you do. "Shipping to production" means making your work live.

Rent a server, or let a platform hide it?

You have two broad ways to get into production (at 02:22). The first is a managed platform such as Netlify, Vercel, or similar: you connect a GitHub repository, click a button, and the platform builds and runs your code for you. The second is to rent a bare server yourself — on DigitalOcean, AWS, Linode, or even a Raspberry Pi at home — install the operating system, and configure everything by hand.

Managed platforms are wonderful once you understand what they do. The trap for a beginner is that they hide the mechanics behind a layer of abstraction (at 03:11). When something breaks at 2 a.m., you cannot debug a black box you never understood. The author's advice: learn the manual way once, because going from manual to managed later is easy, but the reverse is not (at 03:35).

The core philosophy: do it manually first

This is the idea the whole course is built on: before you automate anything, you must know how to do it by hand (at 04:22). Automation that you do not understand is just a faster way to break things. By running each step yourself first, you feel why each piece exists, so later, when we replace the manual steps with scripts and pipelines, the automation is a convenience and not a mystery (at 04:46).

The example app we will deploy

To make the lessons concrete, the course deploys one real full-stack application the author built and ran in production for eight months (at 05:33). It has three parts:

  • A Vue.js front end — the pages and buttons the user sees in the browser.
  • A FastAPI back end — the Python program that answers requests and holds the logic.
  • A self-hosted Meilisearch engine — a fast search service we run on the same server (at 05:55).

Do not worry if your own app uses Ruby, Go, or a different framework. The mechanics — a server, a firewall, a reverse proxy, HTTPS, a pipeline — are universal (at 06:17). You would just swap the install commands for your stack.

New to "front end", "back end", and "search engine"? A quick map

The front end is the part that runs in the browser: the visual interface. The back end is the program running on the server that does the real work — reading data, checking rules, returning answers. A search engine like Meilisearch is a specialised back-end service built to find matching text extremely quickly, far faster than scanning a database row by row.

The full target architecture

Here is where we are heading. By the final lesson, a user's request does not hit your app directly. It passes through several layers, each with a job: a CDN for speed, a Nginx reverse proxy as the front door, Gunicorn running your FastAPI workers, Meilisearch for search, and scheduled backups keeping your data safe.

New to "reverse proxy" and "CDN"? Why there are so many layers

A reverse proxy (here, Nginx) is a single front door that receives every request and decides where to send it: static files one way, /api calls to your app another way. It also handles HTTPS and shields your app from the raw internet. A CDN (content delivery network, here Cloudflare) keeps copies of your static files in data centres around the world, so a user in Tokyo is served from nearby instead of from your one server in Germany. Both add speed and safety; neither replaces your app.

What exactly is a "droplet"?

On DigitalOcean, a rented server is called a droplet. It is a virtual machine: software carves one powerful physical computer into several independent virtual ones, and you rent one of those slices (at 02:48). To you it behaves exactly like a real computer running Ubuntu; you just never see the hardware. Other providers call the same thing an "instance" or "VPS".

The six-module roadmap

The course is six modules, each building on the one before (at 06:17 onward). This guide follows the same path, one lesson per idea.

  1. Module 1 — The foundation. Rent the server, lock it down with SSH keys, create a non-root user, and build a firewall (at 06:17).
  2. Module 2 — The application runtime. Move the code over, install Python and Node, add swap memory, and run the back end with Gunicorn behind Nginx (at 07:26).
  3. Module 3 — Data & search. Self-host Meilisearch under its own user, back it up on a schedule, and reach its dashboard through an SSH tunnel (at 08:58).
  4. Module 4 — Global delivery & security. Register a domain, add HTTPS with Let's Encrypt, and put Cloudflare in front for speed (at 10:07).
  5. Module 5 — The automation pipeline. Protect the main branch, add pre-commit checks, and build a CI/CD pipeline that tests and deploys for you (at 11:41).
  6. Module 6 — Optimization & maintenance. Read traffic with GoAccess, watch resources with btop, load-test with Locust, and ban abusive bots (at 13:35).

Security is a thread through everything

A server on the public internet is attacked within minutes of coming online — automated bots scan every address constantly. So security is not one lesson; it runs through the whole course. We build it up in layers, so that even if one layer is breached, others still stand (at 06:40). The next lesson starts the first layers.

What you should have by the end of the course

A live app with its own domain and HTTPS, reachable worldwide and fast, protected by a firewall and key-only SSH, searchable through self-hosted Meilisearch, backed up automatically, and deployed by a pipeline that tests your code before it ever goes out. Most importantly, you will understand every piece.

Common mistakes (before you even begin)
  • Rushing. The author's advice is "slow is smooth, and smooth is lasting." Understand each line before moving on.
  • Jumping straight to a managed platform to skip the hard parts — you lose the understanding this course exists to give.
  • Skipping modules. Each one depends on the last; the firewall assumes SSH is set up, the pipeline assumes the app runs.
  • Treating placeholders like <your_username> as literal text. They are blanks to fill in, brackets removed.
Security note

From the moment your server has a public address, it is a target. Do not postpone the security steps "until the app works" — by then bots may already be inside. In this course, security comes first (the firewall and SSH hardening are Module 1), before we ever deploy a line of application code. Treat that ordering as deliberate, not optional.
