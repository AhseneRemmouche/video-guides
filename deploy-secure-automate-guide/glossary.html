Glossary

Every deployment, server, security and CI/CD term in this course, explained for beginners.

Every important word used across this course, explained in plain English for people who can build an app but have never deployed one. Terms are grouped by topic so you can learn them in context. Other pages link here the first time they use a word, so keep this page handy as a reference.

Deployment basics

Deployment
The act of putting your application onto a computer that is always on and reachable from the internet, so other people can actually use it. This whole course is about doing a deployment, by hand first and then automatically.
Production
The real, live version of your app that actual users visit, as opposed to the copy running on your own laptop. Mistakes in production affect real people, so it needs extra care around security and reliability.
localhost
A name that always means "this computer". When your app runs on localhost only you can open it, because no one else on the internet can reach your laptop. Fixing that is the reason we deploy.
FastAPI
A Python framework for building web APIs (the back end). In this course it is the part of the example app that handles requests and talks to the search engine.
Vue.js
A JavaScript framework for building the front end (the pages a user sees in the browser). We build it into plain files and let the web server deliver them.

Servers & access

Server
A computer that runs all the time and answers requests over the network. Instead of buying one, we rent a small server in a data centre and install our app on it.
Droplet
DigitalOcean's name for a rented virtual server. In this course the whole app lives on one droplet running Ubuntu.
VPS
Short for Virtual Private Server: a slice of a bigger physical machine that behaves like your own dedicated computer. A droplet is one example of a VPS.
DigitalOcean
The cloud hosting company used in this course. You create an account, rent a droplet, and get a fresh Ubuntu server you connect to over the internet.
Ubuntu
A popular, free version of the Linux operating system. The server runs Ubuntu 24.04, so every command in this course is a Linux command.
SSH
Secure Shell: the encrypted way to log in to your server from your laptop and type commands on it. You run ssh user@server-ip and get a remote terminal.
SSH key pair
Two matching files used to log in without a password: a public key that acts like a lock you put on the server, and a private key that acts like the only key that opens it. We create them with ssh-keygen.
Public key
The half of your SSH key pair that you copy onto the server. Think of it as a padlock anyone can see; it can lock things but cannot unlock them, so sharing it is safe.
Private key
The half of your SSH key pair that stays secret on your laptop and proves who you are. Anyone who steals it can log in as you, so you never share it or copy it to the server.
Passphrase
An optional password that encrypts your private key on disk. Even if someone copies the key file, they still need the passphrase to use it, adding a second layer of protection.
Root user
The all-powerful administrator account on Linux that can change or delete anything. It is convenient but risky, so we use it only to set things up and then stop logging in as root.
sudo
A command that lets a normal user run a single action with administrator powers, after proving who they are. It means you work as a safe everyday user but can still do admin tasks when needed.
Non-root user
A regular login account (created with adduser) that you use for daily work instead of root. We give it sudo rights so it can do admin tasks while limiting accidental damage.
sshd_config
The main configuration file for the SSH server, at /etc/ssh/sshd_config. We edit it to turn off root login and password login so only key-based logins are allowed.
scp
Secure Copy: a command that copies files between your laptop and the server over the same encrypted SSH connection. It is one of the simple ways to move your app's code onto the server.
Git
A version-control tool that tracks changes to your code and lets you clone it onto the server with one command. Using Git to pull your project is the other common way to get code onto the server.

Firewall & secure access

Firewall
A gatekeeper that decides which network connections are allowed in and out of the server. By default we block everything coming in and then open only the few doors the app truly needs.
UFW
Uncomplicated Firewall: Ubuntu's easy front end for managing firewall rules. We set it to deny all incoming traffic, then allow SSH, HTTP and HTTPS, and switch it on.
Fail2Ban
A tool that watches log files for repeated failed logins and temporarily bans the attacking IP address. It stops password-guessing bots from hammering your SSH door.
Port
A numbered door on a server for a particular kind of traffic, such as 22 for SSH, 80 for HTTP and 443 for HTTPS. The firewall's job is to open only the ports you really use.
SSH tunnel
A private, encrypted connection built on top of SSH that lets you reach a service on the server as if it were running on your own laptop. We use it to open a dashboard without exposing it to the public internet.
Port forwarding
The technique behind an SSH tunnel: traffic sent to a chosen port on your laptop is quietly carried through SSH to a port on the server. It lets you reach an internal-only service safely.

Linux runtime & processes

Swap memory
Space on the server's disk that Linux uses as extra, slower RAM when real memory runs low. On a small server it stops programs from crashing during memory spikes, such as installing packages.
RAM
The fast, temporary memory a computer uses for whatever it is doing right now. Small servers have little RAM, which is why we add swap as a safety net.
Python virtual environment
A private folder that holds a project's own copy of Python and its packages, separate from the rest of the system. It keeps each app's dependencies from clashing with others.
pip
Python's package installer. You run pip install inside a virtual environment to download the libraries your app needs, like FastAPI and Gunicorn.
Node.js
A runtime that lets JavaScript run outside the browser. We install it on the server to build the Vue front end into static files.
npm
Node's package manager, used to install the front end's JavaScript dependencies and to run its build step.
Gunicorn
A production-grade web server for Python apps. It launches and manages several worker processes so your FastAPI app can handle many requests at once, which the built-in dev server cannot do reliably.
Uvicorn
A fast server that knows how to run modern async Python apps like FastAPI. We run Uvicorn workers under Gunicorn so we get both solid process management and async speed.
Worker process
One of several copies of your app that Gunicorn runs side by side. More workers means more requests handled at the same time, up to the limits of the server's CPU and memory.
Unix socket
A special file on the server that two local programs use to talk to each other directly, without going over the network. Gunicorn listens on one, and Nginx talks to it through that file, which is fast and private.
Supervisor
A tool that starts your app, watches it, and restarts it if it crashes or the server reboots. It keeps Gunicorn running without you having to log in and start it by hand.
systemd
The system that Ubuntu uses to start, stop and supervise background programs. Many services, such as Meilisearch, are managed by systemd so they run automatically.
systemd unit
A small configuration file that tells systemd how to run one service: what command to launch, which user to run it as, and when to start it. We write one so Meilisearch starts on boot.
Daemon
A program that runs quietly in the background with no window, waiting to do its job, such as a web server or a search engine. Services managed by systemd or Supervisor run as daemons.
Dedicated user
A separate, low-privilege account created just to run one service. If that service is ever broken into, the attacker is boxed into a limited account instead of controlling the whole server.
cron
Linux's built-in scheduler that runs a command automatically on a timetable you set. We use it to run the backup script and other maintenance jobs at regular times.

Web layer & networking

Nginx
A fast web server that sits at the front and receives every visitor's request first. It serves the front end files and passes app requests back to Gunicorn.
Reverse proxy
A server placed in front of your app that receives requests from the outside and forwards them to the right internal service. Here Nginx is the reverse proxy: it faces the internet so your app does not have to.
Static assets
Files that do not change per request, such as the built HTML, CSS, JavaScript and images of the Vue front end. Nginx can serve them directly and very quickly.
HTTP
The basic language web browsers and servers use to request and send web pages. On its own it is unencrypted, so anyone in between can read it; HTTPS fixes that.
HTTP header
A small line of extra information attached to each request or response, such as the content type or caching rules. Some headers are used to make the site more secure.
Security header
An HTTP response header that tells the browser to behave more safely, for example by refusing to be shown inside another site's frame. We add a set of them in Nginx to harden the front end.
Content Security Policy (CSP)
A security header that lists exactly which sources the browser is allowed to load scripts and other content from. It blocks injected or malicious scripts that are not on your approved list.

Search & data

Meilisearch
A lightweight, fast search engine you run yourself. In this course it powers the app's search feature and lives on the same droplet as its own service.
Search engine
A program that stores your data in a way designed for quick text search and returns matching results as the user types. Meilisearch is the search engine used here.
Index
The organised structure a search engine builds from your data so it can find matches almost instantly, much like the index at the back of a book. You load your documents into an index before you can search them.
Master key
A secret password that protects Meilisearch so only your app can read or change its data. Without it, anyone who reached the service could tamper with your search data.
Data dump
A single export file containing all of Meilisearch's data. You create a dump to move or back up the search data and import it to restore everything.
Backup
A saved copy of your important data, kept so you can recover it if the server fails or data is lost. We write a script and schedule it with cron so backups happen automatically.

Domains, TLS & CDN

Domain
The human-friendly name people type to reach your site, such as example.com, instead of a numeric server address. You register one and point it at your server.
DNS
The Domain Name System: the internet's phone book that translates a domain name into the server's IP address. When you set up a domain you are really adding entries to DNS.
A record
A DNS entry that maps a domain name directly to a server's IPv4 address. Adding an A record for your domain is what makes it point at your droplet.
HTTPS
HTTP with encryption added, shown by the padlock in the browser. It keeps data private between the visitor and your server and is now expected for every real site.
TLS
Transport Layer Security: the technology that encrypts the connection and makes HTTPS secure. It is the modern successor to the older SSL and the two names are often used loosely.
SSL certificate
A digital file that proves your domain is really yours and lets the browser set up an encrypted TLS connection. Without a valid certificate, browsers warn visitors the site is not secure.
Let's Encrypt
A free, automated certificate authority that issues SSL certificates. Its certificates last 90 days, which is short on purpose, so we set up automatic renewal.
Certbot
The tool that talks to Let's Encrypt to request, install and later renew your certificate for you. It can also update your Nginx config to use HTTPS.
Auto-renewal
A scheduled job (a timer or cron task) that renews your Let's Encrypt certificate before it expires. Because the certificates last only 90 days, auto-renewal keeps HTTPS working without you remembering to act.
CDN
A Content Delivery Network: a worldwide set of servers that keep copies of your static files close to users. It makes the site load faster and shields your server from some traffic.
Cloudflare
The CDN and security service used in this course. It sits in front of your site, serving cached files from the edge and encrypting traffic end to end with strict (full) SSL.
Edge server
One of the CDN's many servers spread around the world, close to groups of users. A visitor is served from the nearest edge server, which cuts the distance data has to travel.
Caching
Keeping a ready-made copy of a response so it can be handed out again without redoing the work. The CDN caches your static files at the edge so repeat visitors get them almost instantly.
Cache hit
When a requested file is already stored in the cache and can be served straight away, instead of going all the way back to your server (a cache miss). More cache hits means a faster site and less load.
Latency
The delay between asking for something and starting to get it, usually measured in milliseconds. Serving from a nearby edge server lowers latency, which is why cached pages feel instant.

CI/CD & automation

CI/CD
Continuous Integration and Continuous Delivery: the practice of automatically testing every change and then shipping it to the server with little or no manual work. The last part of the course builds a CI/CD pipeline.
GitHub Actions
GitHub's built-in automation service that runs jobs for you whenever you push code or open a pull request. We use it to run tests, security scans and deployments.
Workflow
A YAML file in your repository that tells GitHub Actions what to run and when, such as "on every pull request, run the tests". Each workflow is made of one or more jobs.
Pipeline
The full chain of automated stages a change passes through, for example lint, test, scan and deploy. If any stage fails, the change is stopped before it reaches production.
Branch protection
GitHub rules that guard an important branch like main, for example requiring a pull request and passing checks before anyone can merge. It stops broken or unreviewed code from landing.
Pull request
A proposal to merge your changes into another branch, where they can be reviewed and automatically tested first. It is the normal place where CI checks run before code is accepted.
pre-commit
A tool that runs small checks on your laptop the moment you try to commit, such as formatting and secret scanning. It catches problems early, before they ever reach the repository.
Linting
Automatically checking code for likely mistakes and style problems. A linter flags issues so they are fixed before the code is merged.
Formatting
Automatically rewriting code to a consistent style, such as spacing and quotes. It keeps the whole project looking the same and removes pointless arguments about layout.
Unit test
A small test that checks one piece of code, like a single function, in isolation. Unit tests are fast and form the base layer of automated testing.
Integration test
A test that checks that several parts of the app work correctly together, such as the API talking to the search engine. It catches problems that unit tests miss.
End-to-end test
A test that drives the whole running app the way a real user would, from the front end through to the back end. It is the most realistic but also the slowest kind of test.
Continuous integration
The habit of merging and automatically testing small changes often, so problems are found quickly. It is the "CI" half of CI/CD.
Continuous delivery
Automatically shipping tested changes to the server, so a release is a routine, low-risk event. It is the "CD" half of CI/CD and is driven from the pipeline over SSH.
Rollback
Quickly switching the live site back to the previous working version when a new release goes wrong. Keeping old releases around makes a rollback fast and safe.
Zero-downtime deploy
Releasing a new version without the site ever going offline. We do this by preparing the new release beside the old one and then flipping a symlink to it in a single, atomic switch.

Security testing

Vulnerability
A weakness in your app, its dependencies or its setup that an attacker could abuse. The goal of security scanning is to find and fix vulnerabilities before anyone exploits them.
DAST
Dynamic Application Security Testing: scanning the app while it is actually running, by sending it real requests and watching how it responds. It finds problems that only appear in a live, working system.
SAST
Static Application Security Testing: scanning your source code without running it, looking for insecure patterns. It catches risky code early, right in the pipeline.
SCA
Software Composition Analysis: scanning the third-party libraries your app depends on for known vulnerabilities. Since most code in a project comes from dependencies, this check matters a lot.
Bandit
A SAST tool for Python that reads your code and flags common security problems, such as hard-coded passwords. We run it automatically in the pipeline.
OWASP ZAP
A free, widely used DAST tool that probes a running web app for security issues. We point it at the live app in the pipeline to catch problems that static scans cannot.
Shift-left
The idea of moving testing and security checks as early as possible in the development process, rather than leaving them to the end. Problems caught early are cheaper and easier to fix.

Observability & maintenance

Observability
Being able to see what your live system is doing through its logs, metrics and dashboards. Good observability lets you spot problems and understand traffic without guessing.
GoAccess
A tool that reads Nginx's log files and turns them into a readable report of who visited, what they asked for, and any errors. It helps you understand real traffic to your site.
btop
A colourful live monitor for the server that shows CPU, memory, disk and network use in real time. It is a quick way to see whether the server is healthy or under strain.
Log
A running record a program writes of what it did and any errors it hit. Logs are your main evidence when you need to find out what went wrong.
Log retention
A policy for how long you keep log files before deleting or compressing old ones. Sensible retention gives you enough history to investigate problems without filling up the disk.
Load testing
Deliberately sending your app a lot of simulated traffic to see how it copes and where it slows down. It tells you the limits of your server before real users hit them.
Locust
A load-testing tool that simulates many users at once and reports how the app responds. We use it to find how much traffic the droplet can handle.
RPS
Requests per second: how many requests your app successfully handles each second. It is a key number for judging capacity during a load test.
Throughput
The total amount of work the system gets through in a given time, such as the number of requests served per second. Higher throughput means the app can serve more users.
IP ban
Blocking a specific internet address so it can no longer reach your server. We ban abusive IPs found in the GoAccess report to stop bots and attackers.
