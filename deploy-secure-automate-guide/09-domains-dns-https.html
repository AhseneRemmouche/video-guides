Domains, DNS & HTTPS

Register a domain, point DNS at the server, and get auto-renewing HTTPS with Let's Encrypt.

▶ Watch this part (256:35)

So far your app has only been reachable through a raw IP address like 142.93.130.134, and every byte travels in plain text. Browsers show a "Not Secure" warning, and typing numbers is no way to share a website. In this lesson you give your app a real domain name, point that name at your DNS server with an A record, and turn on encryption so the address starts with HTTPS instead of plain HTTP. You will get a free certificate from Let's Encrypt using a tool called Certbot, and then set up auto-renewal so it never expires on you.

What you will build

By the end of this lesson, a visitor can type https://yourdomain.com and reach your Vue front end over an encrypted connection, with a padlock in the address bar. Anyone who tries plain http:// is redirected to the secure version automatically, and the certificate renews itself forever without you lifting a finger (around 256:35).

Concept 1: What DNS actually does

Computers find each other by IP address, but people remember names. DNS is the phonebook of the internet: it translates a human name like imadsaddik.com into the machine address 142.93.130.134 (around 258:00). When you own a domain, you add records in your registrar's dashboard that say "this name belongs to this IP". The most important one is the A record, which maps the bare domain straight to your droplet's IPv4 address.

New to DNS? What it is and why it matters

DNS stands for Domain Name System. Every time you open a website, your browser first asks a DNS server "what is the IP address for this name?" and only then connects. Without DNS you would have to memorise numbers for every site. When you buy a domain you become responsible for its records, the little rows that tell the world where your name points. Changes are not instant: they take a few minutes to a couple of days to spread to every DNS server on earth. That spreading is called propagation.

Step-by-step: register a domain and point it at your server

  1. Register the domain. Pick a registrar (the course uses Porkbun; Namecheap or GoDaddy work the same way). Search for the name you want and check the renewal price, not just the first-year discount. Aim for a sustainable cost, around $10–$15 a year for a .com (around 257:10).
  2. Skip the upsells. At checkout the registrar will push email hosting, site builders and premium DNS. You need none of them, only the domain itself.
  3. Open the DNS panel. In the Domain Management dashboard, hover over your domain and click the DNS link. Delete any default records the registrar created (ALIAS, CNAME, _acme-challenge) so they cannot conflict with yours (around 260:30).
  4. Add the A record. Type A, leave Host/Name blank, paste your droplet's IP into Answer/Value, and set TTL to 600. Click Add.
  5. Add the CNAME record. Type CNAME, Host/Name www, Answer/Value your root domain. This makes www.yourdomain.com reach the same site. Click Add.
  6. Wait for propagation. Usually under 15 minutes. Check it at whatsmydns.net, then load http://yourdomain.com and confirm your app appears.

The two DNS records you create

Common mistakes. Forgetting to delete the registrar's default records, which quietly override yours. Pasting the wrong IP into the A record. Putting something in the Host field of the A record (it must be blank for the root domain). And expecting the change to be instant, propagation can take up to 48 hours even though it is usually minutes.

Concept 2: HTTP versus HTTPS

Right now your domain loads over HTTP, which sends everything as readable text that anyone on the network path can see. HTTPS wraps the same traffic in TLS encryption, proven by an SSL certificate that also tells the browser "yes, this really is yourdomain.com" (around 263:00). The certificate is what flips the browser from a "Not Secure" label to a padlock.

New to TLS and SSL certificates? What they are

TLS (Transport Layer Security) is the modern encryption used by every "s" in "https". People still say "SSL", the older name, out of habit. An SSL/TLS certificate is a small signed file your server presents to prove its identity. A trusted authority, here Let's Encrypt, checks that you really control the domain and then signs the certificate. The browser already trusts Let's Encrypt, so it trusts your site. The handshake that sets up the encrypted channel happens in milliseconds before any page content is sent.

Step-by-step: get the certificate with Certbot

Certbot automates the hard parts: it proves you own the domain, downloads the certificate, and safely rewrites your Nginx config to enable HTTPS (around 266:40).

  1. SSH into the server.
ssh my-website
  1. Install Certbot and its Nginx plugin.
sudo apt install certbot python3-certbot-nginx -y

Concept 3: what Certbot changed in your Nginx file

Certbot does not just download a file; it rewrites your Nginx config. It is worth understanding the two changes (around 272:10). Reopen the file to see them:

sudo nano /etc/nginx/sites-available/<your_project_name>

Change 1: the HTTPS upgrade

Your original server block used to listen 80;. Certbot upgraded it to listen on secure port 443 and added lines pointing at the new cryptographic keys.

server {
    server_name <your_domain>.com www.<your_domain>.com;

    # ... (Your location blocks for / and /api remain untouched) ...

    # Certbot added these lines to handle SSL encryption
    listen 443 ssl;
    ssl_certificate /etc/letsencrypt/live/<your_domain>.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/<your_domain>.com/privkey.pem;
    include /etc/letsencrypt/options-ssl-nginx.conf;
    ssl_dhparam /etc/letsencrypt/ssl-dhparams.pem;
}

Line by line

Line(s)CodeWhat it does & why
1server {Opens the block that defines one website for Nginx.
2server_name ...;The names this block answers to, your root domain and the www subdomain. This is the line Certbot matched on.
4# ... location blocks ...A reminder that your existing routing for / (the Vue app) and /api (the backend) is left exactly as it was.
7listen 443 ssl;The key change: serve this site on port 443 (the HTTPS port) with SSL/TLS turned on, instead of plain port 80.
8ssl_certificate .../fullchain.pem;Points to the public certificate chain the browser receives. "fullchain" includes Let's Encrypt's intermediate certificate so browsers can verify trust.
9ssl_certificate_key .../privkey.pem;Points to the private key that proves the server owns that certificate. This file stays secret on the server.
10include .../options-ssl-nginx.conf;Pulls in Certbot's recommended secure TLS settings (safe protocols and ciphers) so you do not have to tune them yourself.
11ssl_dhparam .../ssl-dhparams.pem;Supplies Diffie-Hellman parameters that strengthen the key exchange during the handshake.

Change 2: the HTTP redirect

Because the block above now only listens on 443, Certbot added a second, separate block to catch old http:// traffic on port 80 and permanently redirect it (HTTP status 301) to the secure version.

server {
    if ($host = www.<your_domain>.com) {
        return 301 https://$host$request_uri;
    }

    if ($host = <your_domain>.com) {
        return 301 https://$host$request_uri;
    }

    listen 80;
    server_name <your_domain>.com www.<your_domain>.com;
    return 404;
}

Line by line

Line(s)CodeWhat it does & why
1server {A brand-new, separate block whose only job is handling insecure port-80 requests.
2–4if ($host = www...) { return 301 ...; }If someone visits the www name over HTTP, send a 301 (permanent) redirect to the same path on https://.
6–8if ($host = <your_domain>.com) { ... }The same redirect for the bare root domain.
10listen 80;This block listens on the plain HTTP port, where the redirects are issued.
11server_name ...;The names this redirect block applies to.
12return 404;A safety net: any port-80 request whose host does not match above gets a 404 instead of leaking content.
Nice bonus. Because your front-end Axios baseURL is just / (relative routing) from Module 2, you do not change any app code. When the page loads over https://, every /api call inherits the secure origin automatically, and since front end and back end share one domain through Nginx, there are no CORS settings to touch.

Concept 4: certificates expire, so automate renewal

Let's Encrypt certificates are valid for only 90 days. That short life limits the damage if a key is ever stolen, but it means you must renew often. Certbot installs a background timer automatically, but the course recommends testing it and adding an explicit schedule so you are never surprised (around 276:00).

First, do a dry run that checks renewal without touching your live certificates:

sudo certbot renew --dry-run
What you should see.
Congratulations, all simulated renewals succeeded:
/etc/letsencrypt/live/<your_domain>.com/fullchain.pem (success)
New to cron? What a scheduled job is

Cron is the Linux job scheduler. It reads a small table where each line says "at this time, run this command", then runs those commands for you in the background forever. Each line has five time fields, minute, hour, day-of-month, month, and day-of-week, followed by the command. A * means "every". It is the standard way to automate repeating server chores like renewing certificates or taking backups.

Add an explicit cron job

Edit the root user's cron table:

sudo crontab -e

If asked, press 1 to choose nano. Add this line at the very bottom:

0 0 * * 0 certbot renew --quiet

Line by line

FieldValueWhat it does & why
1 (minute)0Run at minute 0 of the hour.
2 (hour)0Run at hour 0, that is, midnight.
3 (day of month)*Any day of the month.
4 (month)*Any month.
5 (day of week)0Only on Sunday. Together the fields read "at midnight every Sunday".
commandcertbot renewAsks Certbot to renew any certificate that is close to expiry. It is smart: it only requests a new one when the current cert is within 30 days of expiring.
flag--quietSuppresses normal output so the job does not spam your logs; it speaks up only on a real error.

Add a post-renewal hook so Nginx picks up the new cert

When Certbot downloads a fresh certificate, Nginx keeps using the old one it loaded into memory at start-up until it is reloaded. Fix this with a hook script Certbot runs automatically after every successful renewal (around 280:10). Create the file:

sudo nano /etc/letsencrypt/renewal-hooks/post/reload-nginx.sh

Paste this inside:

#!/bin/bash
systemctl reload nginx

Line by line

Line(s)CodeWhat it does & why
1#!/bin/bashThe "shebang". It tells the system to run this file with the Bash shell. Every shell script starts with it.
2systemctl reload nginxReloads Nginx so it reads the freshly renewed certificate from disk. A reload applies the change without dropping active connections.

Save and exit, then make the script executable so Certbot has permission to run it:

sudo chmod +x /etc/letsencrypt/renewal-hooks/post/reload-nginx.sh
Common mistakes. Forgetting chmod +x, which leaves the hook un-runnable so Nginx silently keeps the expired cert. Editing the wrong user's crontab (certificate renewal must run as root). And skipping the dry run, which is the only safe way to confirm renewal works before you depend on it.
Security note. Your privkey.pem is the one secret that must never leave the server, anyone who copies it can impersonate your site. Certbot stores it under /etc/letsencrypt with root-only permissions, so do not loosen those permissions or copy the key elsewhere. Pairing a 90-day certificate with automatic renewal is itself a security feature: short-lived keys limit how long a leaked key is useful.
Recap
  • DNS translates your domain into your droplet's IP; an A record (root, blank host) carries the traffic and a CNAME forwards the www prefix.
  • HTTP is plain text; HTTPS wraps it in TLS, proven by an SSL certificate that flips the browser to a padlock.
  • sudo certbot --nginx -d yourdomain.com -d www.yourdomain.com proves ownership, downloads a free Let's Encrypt certificate, and rewrites Nginx for you.
  • Certbot turns one listen 80 block into a secure listen 443 ssl block plus a small block that 301-redirects HTTP to HTTPS.
  • Certificates last 90 days; a Sunday-midnight cron job (certbot renew --quiet) plus a post-renewal hook that reloads Nginx keeps your site secure forever, hands-off.
