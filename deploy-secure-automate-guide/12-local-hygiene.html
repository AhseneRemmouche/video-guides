Local Hygiene: Branch Protection & pre-commit

Protect the main branch with rulesets and catch lint, format and secret issues before commit with pre-commit.

▶ Watch this part (329:31)

So far you have deployed everything by hand. That is the best way to understand a Linux server, but doing it on every change is slow and risky. This module begins the shift to a CI/CD pipeline. Before automating anything in the cloud, though, you lock down your local workflow, because a mistake caught on your laptop takes seconds to fix, while one caught after deployment can take hours.

Local hygiene has two layers. First, branch protection on GitHub stops broken code from being pushed straight into your main branch. Second, pre-commit hooks run on your machine and refuse to create a commit until your code is clean.

The concepts

Protect the branch you ship from (at 5:30). You push from your main or master branch, so a stray git push there could put untested code into production. A GitHub ruleset forces every change to arrive through a pull request instead, and blocks dangerous actions like deleting the branch or force-pushing over its history.

Catch errors before the commit exists (at 5:36). Git has built-in hooks: hidden scripts that run automatically on actions like committing. Writing raw shell hooks for every teammate is painful, so the pre-commit framework manages them from one small YAML file. It downloads the tools, runs them on your staged files, and blocks the commit if anything fails. Here it runs linting and formatting for both the Python backend and the Vue frontend.

New to linting and formatting? How they differ

Linting looks for problems: unused variables, undefined names, risky patterns. A linter (Ruff for Python, ESLint for JavaScript and Vue) can often fix the simple ones for you. Formatting is about looks: consistent spacing, indentation, and line length, so every file reads the same no matter who typed it. Ruff's formatter and Prettier handle that. Running both on every commit means your Git history stays tidy and code reviews focus on logic, not whitespace.

Step 1 — Protect the default branch on GitHub

Branch protection is free for public repositories. You create a ruleset that targets your default branch and turns on a few safety switches (at 5:31).

  1. Open your repository on GitHub and click the Settings tab.
  2. In the left sidebar, under Code and automation, click Branches.
  3. Click Add branch ruleset.
  4. Name it Main branch protection and set Enforcement status to Active.
  5. Under Target branches, click Add target and choose Include default branch.
  6. In Branch rules, enable: Restrict deletions, Block force pushes, and Require a pull request before merging with Required approvals set to 0.
  7. Click Create.

What each setting does

SettingValueWhat it does & why
Ruleset nameMain branch protectionA descriptive label so you can find and edit this rule later (you will add status checks to it in the CI chapter).
Enforcement statusActiveTurns the rules on. A ruleset can also be left in "Evaluate" mode to preview its effect, but Active is what actually protects the branch.
Target branchesInclude default branchApplies the rules specifically to main or master, whichever is your default, without naming it by hand.
Restrict deletionsonStops anyone, including you, from accidentally deleting the main branch.
Block force pushesonDisables git push --force on the branch. Force pushing rewrites history and can permanently erase past commits, so this is critical.
Require a pull request before mergingon, approvals 0Forces every change through a pull request. Zero approvals is the solo-developer sweet spot: you still get the habit and the record of a PR, but you can merge it yourself immediately. On a team you would set this to 1 or 2.
Common mistakes. Leaving enforcement on "Disabled" or "Evaluate" means the rules look configured but never actually block anything. Also, if you set Required approvals above 0 while working solo, you will be unable to merge your own pull requests and will get stuck.

To prove the lock works, try to push a commit straight to your main branch. GitHub rejects it (at 5:34):

remote: error: GH013: Repository rule violations found for refs/heads/master.
remote:
remote: - Changes must be made through a pull request.
remote:
To https://github.com/ImadSaddik/ImadSaddikWebsite.git
 ! [remote rejected] master -> master (push declined due to repository rule violations)
error: failed to push some refs to 'https://github.com/ImadSaddik/ImadSaddikWebsite.git'
What you should see. The GH013 error above. It means the lock is working: from now on you create a feature branch, commit there, and open a pull request to merge into main.

Step 2 — Write the pre-commit config

Create a file named .pre-commit-config.yaml in the root of your project. You build it in two parts: backend tools first, then frontend tools (at 5:38).

New to Git hooks? Where do these scripts live?

Every Git repository has a hidden .git/hooks/ folder. Git looks there for scripts named after events, like pre-commit (runs just before a commit is saved) or pre-push. If the script exits with an error, Git cancels the action. The pre-commit framework simply writes a small launcher into .git/hooks/pre-commit for you and reads which tools to run from your YAML file, so you never hand-edit that hidden folder.

First, the backend. Ruff is a fast Python linter and formatter that replaces older tools like Flake8, Black, and isort.

repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: "v0.15.12"
    hooks:
      - id: ruff
        name: ruff (lint)
        args: [--fix]
        files: ^backend/
      - id: ruff-format
        name: ruff (format)
        files: ^backend/

Next, the frontend. ESLint catches logic bugs in JavaScript and Vue files, and Prettier handles the visual formatting. Append this to the same file.

  - repo: https://github.com/pre-commit/mirrors-eslint
    rev: "v9.39.1"
    hooks:
      - id: eslint
        name: eslint (frontend)
        files: ^frontend/.*\.(js|vue)$
        types: [file]
        args: [--fix, --config, frontend/eslint.config.js]
        additional_dependencies:
          - eslint@9.39.1
          - eslint-plugin-vue@10.6.2
          - eslint-config-prettier@10.1.8
          - globals@16.5.0
          - vue-eslint-parser@10.2.0

  - repo: local
    hooks:
      - id: prettier-frontend
        name: prettier (frontend)
        entry: npx prettier --write
        language: node
        language_version: system
        files: ^frontend/.*\.(js|vue|css|scss|html|json)$
        types_or: [javascript, vue, css, scss, html, json]

Step 3 — Install and test the hooks

The YAML file is just text until you install the framework. Do this on your local computer, not the droplet, from the root of your project (at 5:42).

# Create a virtual environment if you haven't already
python3 -m venv venv

# Activate it
source venv/bin/activate
pip install pre-commit
pre-commit install
pre-commit run --all-files

Line by line

CommandWhat it does & why
python3 -m venv venvCreates an isolated Python environment in a folder called venv, so the tools you install do not touch your system Python.
source venv/bin/activateSwitches your terminal into that environment. Your prompt changes to show (venv).
pip install pre-commitInstalls the pre-commit framework into the virtual environment.
pre-commit installReads .pre-commit-config.yaml and writes a launcher script into .git/hooks/pre-commit. From now on, every git commit triggers your linters and formatters first.
pre-commit run --all-filesRuns all hooks against every file right now, instead of waiting for your next commit. The first run is slow because it downloads Ruff, ESLint and the Node dependencies.

Once it finishes, you should see a checklist like this:

ruff (lint)........................................................Passed
ruff (format)......................................................Passed
eslint (frontend)..................................................Passed
prettier (frontend)................................................Passed
What you should see. Four green Passed lines. If a hook fails, it often fixes the formatting automatically; you then stage the new changes with git add . and run the commit again.

Step 4 — The emergency bypass

Hooks are strict on purpose, but sometimes you must save a broken, work-in-progress state right now, for example before switching tasks. The --no-verify flag skips the hooks entirely (at 5:46).

git commit -m "WIP: saving a broken state" --no-verify
Security note. Use --no-verify sparingly. Bypassing local hooks does not make the problems disappear; it just pushes them downstream, where your cloud CI/CD pipeline will catch them and force you to fix them anyway. Never use it to sneak unformatted or insecure code past review.
What is coming next in the pipeline?

Local hooks only run on your machine. In the next chapter you move the same checks to the cloud with GitHub Actions, which spins up a clean Linux machine on every pull request and runs your linters and tests there. You will then return to this ruleset and add a required status check, so a pull request simply cannot be merged until the pipeline is green.

Bonus — A hand-written Git hook (from the handbook repo)

The pre-commit framework is the recommended path, but it helps to see what a raw Git hook looks like underneath. The author's own handbook repository ships a plain shell hook that turns edited slide files (.odp) into PDFs automatically, plus a tiny installer. This shows the exact file the framework normally writes for you.

#!/bin/bash

# Redirect stdout/stderr to terminal to make sure user sees messages
exec 1>&2

# Check if libreoffice is installed
if ! command -v libreoffice &> /dev/null; then
    echo "Warning: libreoffice not found. Skipping PDF generation."
    exit 0
fi

# Loop through all staged .odp files
git diff --cached --name-only --diff-filter=ACM | grep '\.odp$' | while read -r file; do
    echo "Detected change in $file. Generating PDF"

    # Convert
    outdir=$(dirname "$file")
    libreoffice --headless --convert-to pdf "$file" --outdir "$outdir"

    if [ $? -eq 0 ]; then
        # Add the generated PDF to staging area
        pdf_file="${file%.odp}.pdf"
        echo "PDF generated: $pdf_file"
        git add "$pdf_file"
    else
        echo "Failed to generate PDF for $file"
        exit 1
    fi
done

7–10if ! command -v libreoffice &> /dev/null; then … fiChecks whether LibreOffice is installed. If not, it prints a warning and exits with 0 (success), so the commit still proceeds instead of failing on a machine without LibreOffice.

25–28else … exit 1If the conversion failed, prints an error and exits with 1, which aborts the commit.

And the installer that copies this hook into place:

#!/bin/bash

echo "Installing git hooks"

REPO_ROOT=$(git rev-parse --show-toplevel)
cp "$REPO_ROOT/scripts/git-hooks/pre-commit" "$REPO_ROOT/.git/hooks/pre-commit"
chmod +x "$REPO_ROOT/.git/hooks/pre-commit"

echo "Success! Pre-commit hook installed."

Recap
  • Branch protection via a GitHub ruleset forces changes through a pull request and blocks force pushes and deletions of your default branch.
  • For a solo developer, set Required approvals to 0: you still open a PR, but you can merge it yourself.
  • A direct push to a protected branch is rejected with a GH013 error.
  • .pre-commit-config.yaml defines hooks: Ruff (lint and format) for the backend, ESLint and Prettier for the frontend, each scoped to its own folder.
  • pip install pre-commit, then pre-commit install wires the hooks into .git/hooks/; pre-commit run --all-files tests them.
  • git commit --no-verify skips the hooks in an emergency, but your cloud CI will still catch the issues.
  • Under the hood a hook is just a script in .git/hooks/; the handbook's install-hooks.sh copies a tracked hook there and makes it executable.
