Running the Backend: Gunicorn & Supervisor

Serve FastAPI with Gunicorn and uvicorn workers, and keep it running in the background with Supervisor.

▶ Watch this part (110:00)

Your backend already runs — but only while you babysit it. In the last step you started the API by hand with a single uvicorn command. The moment you close the terminal, log out, or the server reboots, your site goes dark. In this step you make the backend production‑ready: a real process manager runs several worker processes for you, exposes them over a private file instead of a public port, and restarts everything automatically if it ever crashes.

What you will build

You will put two new tools in front of your FastAPI app. Gunicorn is a robust process manager that launches and watches several Uvicorn workers. Supervisor sits one level higher and watches Gunicorn itself, bringing it back to life after a crash or a reboot. The app will no longer listen on a network port; instead Gunicorn opens a Unix socket file that only programs on the same machine (later, Nginx) can talk to.

The concepts

At (111:50) the presenter opens the slide that explains the three pieces working together: Supervisor, Gunicorn, and Uvicorn. You already met Uvicorn when you ran the app by hand, so why add two more tools?

Why Gunicorn and Uvicorn together

Think of a restaurant. Gunicorn is the manager: it decides how many cooks to hire, keeps an eye on them, and replaces any cook who collapses. Each Uvicorn worker process is a cook that actually prepares the orders. One cook can only do so much at once; several cooks handle more customers in parallel. FastAPI is asynchronous (ASGI), and Gunicorn on its own only knows how to run old‑style synchronous (WSGI) apps, so you tell Gunicorn to use Uvicorn's special worker class to bridge the gap.

New to processes and workers? What they are and why it matters

A process is a running copy of a program with its own slice of memory. When you ran uvicorn main:app you started exactly one process. A worker is simply one of several identical processes all running your app, so requests can be served in parallel instead of one at a time. The handbook suggests a starting count of (2 × CPU cores) + 1; on a small server three workers is a safe balance.

Why Supervisor

At (114:41) the presenter calls Supervisor a watchdog — a term from engineering for a component that hits the reset button when a system freezes. If Gunicorn or its workers crash (115:05), Supervisor notices within seconds and starts everything again, so your API is healthy and ready for users without you logging in. Supervisor runs as a background service, a daemon, that starts on boot.

The private socket

When you tested with uvicorn you used port 8000. In production the backend will instead listen on a Unix socket file. At (125:06) the presenter notes Nginx is not installed yet, so you test the socket directly with curl. A socket file is faster than a network port and more secure, because it never opens a connection to the outside world — only processes on the same machine that have permission can read it.

Steps

  1. Install Gunicorn into the virtual environment. Move into the backend folder and activate the same venv you made earlier, then install Gunicorn inside it so it uses your project's Python.
  2. Write the gunicorn_start script that tells Gunicorn exactly how to launch your app, and make it executable.
  3. Install Supervisor and create a log folder owned by your user.
  4. Write the Supervisor .conf file so Supervisor knows to run and watch your script.
  5. Tell Supervisor to load the config and start the service, then confirm it is RUNNING.
  6. Test the API through the socket with curl, and confirm the socket file exists.
  7. Check for orphan processes and clean them up safely.

Step 1 — Install Gunicorn

At (115:28) the presenter stresses testing manually first, which you did. Now install the manager. Activate the environment so Gunicorn installs alongside your app's packages, not system‑wide.

cd /web_app/backend
source venv/bin/activate
pip install gunicorn
Line(s)CodeWhat it does & why
1cd /web_app/backendMoves into the backend folder where your main.py and venv live. Gunicorn must be run from here so it can import main:app.
2source venv/bin/activateActivates the project's virtual environment. Without this, pip would install Gunicorn into the system Python, and your app's packages would be invisible to it.
3pip install gunicornDownloads and installs Gunicorn inside the active venv. This keeps the manager and its workers using the exact same Python and libraries as your app.

Step 2 — Create the startup script

Create a shell script in the backend root (not inside venv, which may be deleted and recreated on future deploys). Open it with nano:

# Ensure you are in /web_app/backend
nano gunicorn_start
Replace the placeholders. Swap <your_project_name> for a short name for your app (for example my_blog), and set USER and GROUP to match your Linux username. The example numbers and names below are from the handbook; use your own.
#!/bin/bash

NAME='<your_project_name>'
APPDIR=/web_app/backend
SOCKFILE=/web_app/backend/gunicorn.sock
USER=<your_username>
GROUP=<your_username>
# Increase this if you have more traffic or a more complex app
NUM_WORKERS=3
TIMEOUT=120

# Gunicorn needs to use Uvicorn's worker class for FastAPI
WORKER_CLASS=uvicorn.workers.UvicornWorker

# We use "*" because we are running behind Nginx via a Unix Socket.
FORWARDED_ALLOW_IPS="*"

echo "Starting $NAME"

cd $APPDIR
source venv/bin/activate

# Create the run directory if it doesn't exist
RUNDIR=$(dirname $SOCKFILE)
test -d $RUNDIR || mkdir -p $RUNDIR

# Start Gunicorn
exec venv/bin/gunicorn main:app \
  --name $NAME \
  --workers $NUM_WORKERS \
  --worker-class $WORKER_CLASS \
  --timeout $TIMEOUT \
  --user=$USER --group=$GROUP \
  --bind=unix:$SOCKFILE \
  --forwarded-allow-ips="$FORWARDED_ALLOW_IPS" \
  --log-level=debug \
  --log-file=-

New to Unix sockets? What --bind=unix:... really does

A Unix domain socket is a special file two programs on the same machine use to talk to each other. Instead of sending data out over the network card and back, the kernel hands it straight across, which is faster and never leaves the box. Because it is a file, normal file permissions decide who may use it — so later you can grant Nginx access and keep everyone else out.

Step 4 — Configure Supervisor

At (121:54) the presenter creates the config file. Supervisor reads every .conf file in /etc/supervisor/conf.d/. Create one named after your project:

sudo nano /etc/supervisor/conf.d/<your_project_name>.conf
[program:<your_project_name>]
command = /web_app/backend/gunicorn_start
user = <your_username>
stdout_logfile = /web_app/backend/logs/supervisor.log
redirect_stderr = true
environment=LANG=en_US.UTF-8,LC_ALL=en_US.UTF-8
stopasgroup = true
killasgroup = true
stopwaitsecs = 10

Line by line

Line(s)DirectiveWhat it does & why
1[program:<your_project_name>]Names this Supervisor program. The name in square brackets is how you refer to it with supervisorctl later.
2command = /web_app/backend/gunicorn_startThe exact command Supervisor runs and watches — your startup script. If it stops, Supervisor runs it again.
3user = <your_username>Runs the script as your non‑root user, matching the USER set in the script.
4stdout_logfile = /web_app/backend/logs/supervisor.logWhere Supervisor saves the program's output — the folder you just created. This is where you look when something breaks.
5redirect_stderr = trueSends error output into the same log file as normal output, so you only have one file to read.
6environment=LANG=en_US.UTF-8,LC_ALL=en_US.UTF-8Sets language and encoding environment variables for the process, avoiding text-encoding bugs.
7stopasgroup = trueWhen Supervisor stops the program, it signals the whole process group (master and all workers), not just the master.
8killasgroup = trueSame idea for a forced kill. Together with stopasgroup, this prevents orphaned workers lingering in the background.
9stopwaitsecs = 10Gives the program up to 10 seconds to shut down cleanly before Supervisor forces it.

Step 6 — Test through the socket

Nginx is not installed yet, so you cannot visit the site in a browser. Instead, at (125:06) the presenter uses curl with the --unix-socket flag to talk to the backend through the socket file directly.

curl --unix-socket /web_app/backend/gunicorn.sock http://localhost/api/health
Line(s)CodeWhat it does & why
1curl --unix-socket /web_app/backend/gunicorn.sock http://localhost/api/healthcurl makes an HTTP request. --unix-socket tells it to send the request over that socket file instead of the network. The http://localhost host is ignored for routing but required by the syntax; /api/health is the endpoint. A JSON reply like {"status": "ok"} proves Gunicorn is serving your app.

Confirm the socket file itself exists. The first character of the permissions must be an s:

ls -l /web_app/backend/gunicorn.sock
srwxr-xr-x 1 <your_username> <your_username> 0 Feb 8 13:00 /web_app/backend/gunicorn.sock
^

Step 7 — Spot and clean up orphan processes

At (131:06) the presenter checks the process list and finds extra workers. A healthy setup is a small family tree: Supervisor spawns one Gunicorn master, and the master spawns the workers. With NUM_WORKERS=3 you should see 4 processes total (1 master + 3 workers).

ps aux | grep <your_project_name>

At (131:06) the presenter finds extra “orphan” (or “zombie”) processes whose parent died, so they were adopted by the system init process (PID 1). They keep eating RAM while doing no work. The handbook shows them adding up to over 100MB on a tiny server. The quick fix at (133:04) kills every Gunicorn process and lets Supervisor restart a clean set — at the cost of a few seconds of downtime.

Common mistakes that create orphans
  • Running gunicorn_start by hand to test it, then closing the terminal without stopping it.
  • Changing the worker count (say 3 to 1) and starting the new process without killing the old one first.
# Kill every single Gunicorn process
sudo pkill -f gunicorn

# Wait for Supervisor to wake up
sleep 5

# Check again, you should see only fresh processes
ps aux | grep <your_project_name>
Line(s)CodeWhat it does & why
2sudo pkill -f gunicornKills every process whose full command line matches gunicorn. -f matches the whole command, not just the program name. This stops the master, the workers, and every orphan at once.
5sleep 5Pauses 5 seconds to give Supervisor time to notice the crash and launch a fresh master and workers.
8ps aux | grep <your_project_name>Lists processes again so you can confirm only the fresh set (1 master + 3 workers) remains.

If you cannot afford even a few seconds of downtime, remove the orphans surgically instead. At (135:21) ask Supervisor for the master's process id, then at (136:12) read the parent column to tell the good tree from the orphans.

sudo supervisorctl pid <your_project_name>
# Example Output: 833505
ps -ef | grep gunicorn
Line(s)CodeWhat it does & why
1sudo supervisorctl pid <your_project_name>Prints the PID of the Gunicorn master that Supervisor manages — the “good” one to keep. Memorise this number.
1ps -ef | grep gunicornLists all Gunicorn processes in full format. -e selects every process; -f shows the PPID (parent process id) column that reveals the hierarchy.

Kill only the orphans you identified (those whose parent is 1), leaving the master and its real workers running:

# Syntax: sudo kill <pid_1> <pid_2> <pid_3> ... <pid_n>
sudo kill 29492 60096 783416
Use your own numbers. The PIDs above are from the handbook author's server. Always read the PPIDs from your terminal and kill only the ones whose parent is 1. Copying these exact numbers could kill the wrong process.
Security note

Two choices in this step harden the app. The workers run as your non‑root user (--user/--group), so a compromised worker cannot touch the whole system. And binding to a Unix socket instead of a port (--bind=unix:...) means the backend never opens a door to the internet — the firewall you set earlier stays fully closed around it.

Recap
  • You installed Gunicorn into the project's virtual environment and wrote gunicorn_start, which launches three Uvicorn workers bound to a private Unix socket file.
  • The key flags: --workers sets parallelism, --worker-class uvicorn.workers.UvicornWorker lets Gunicorn run async FastAPI, and --bind=unix:... uses a socket instead of a port.
  • Supervisor runs and watches the script from /etc/supervisor/conf.d/<your_project_name>.conf, restarting it after crashes and reboots, with stopasgroup/killasgroup preventing orphans.
  • You confirmed RUNNING status, tested the API through the socket with curl --unix-socket, and learned to tell healthy workers (parent = master) from orphans (parent = init/PID 1).
  • The backend is now production‑ready but still private. Next, Nginx becomes the public front door.
