Continuous Integration & Unit Tests

Run linting, formatting and unit tests automatically on every pull request with GitHub Actions.

▶ Watch this part (357:20)

In the last step you locked down your laptop: branch protection stopped anyone pushing straight to master, and pre-commit hooks reformatted your code before each commit. That is a great first line of defence, but it only runs on your machine. A teammate can skip the hooks, or your laptop can have a different tool version than your server, and broken code still slips in. This step moves those exact same checks into the cloud so they run automatically, on a clean machine, every single time — and so a pull request cannot be merged until they pass.

This is Continuous Integration (CI): the first half of the CI/CD idea. You will build a small pipeline with GitHub Actions that checks out your code, installs dependencies, runs linting and formatting checks, then runs your unit tests — and turns the merge button red if anything fails.

What you will build

The presenter builds five files that work together (at 358:30). Four of them are small, focused "reusable" workflow files — one each for frontend lint, backend lint, frontend tests and backend tests. The fifth, ci.yml, is the orchestrator that calls the other four and decides whether the whole run passed.

The concepts the presenter explains

A CI pipeline spins up a brand-new computer (at 357:20). Every time you push or open a pull request, GitHub rents you a clean Linux machine, downloads your repository onto it, installs the exact dependencies, and runs your checks from scratch. Because it starts empty every time, it catches problems your laptop hides.

Small reusable files beat one giant file (at 362:27). Putting the whole pipeline in one file makes failures hard to find in the logs. Instead each job lives in its own file and is marked as a reusable template with the workflow_call trigger (at 364:04). A single orchestrator file then calls each one.

Two keywords do all the work: uses and run (at 367:21). A step either uses a ready-made community action (like downloading your code or installing Node.js), or it runs a shell command exactly as you would type it in a terminal.

Caching makes repeat runs fast (at 372:03). If your dependencies have not changed, there is no need to download them again. Telling GitHub to cache pnpm or pip saves a copy and reuses it next time.

needs forces an order (at 378:41). By default every job runs at the same time. The needs keyword says "do not start this job until that one succeeds", so tests only run after linting passes. A final pipeline-success job watches all of them and reports one overall red or green mark (at 379:52).

New to CI/CD? What it is and why it matters

CI/CD stands for Continuous Integration and Continuous Delivery. Continuous Integration is the habit of merging small changes often and having a robot check every change automatically. Continuous Delivery is the next step (covered later): shipping those checked changes to your server automatically. In this step you build the CI half. The payoff is confidence: when the robot is green, you know the code builds, is formatted, and passes its tests — without trusting anyone to remember to check by hand.

New to YAML? The format these files are written in

YAML is a plain-text format for settings, built on indentation. Two spaces of indent means "this belongs to the line above". A key: value pair sets one setting. A line starting with - is a list item. GitHub Actions reads these YAML files to know what to do. The indentation is not decoration — getting it wrong changes the meaning, so always indent with spaces, never tabs.

New to runners and ubuntu-latest?

A "runner" is the throwaway computer GitHub gives your job. runs-on: ubuntu-latest asks for the newest Ubuntu Linux image. It is wiped after the job, so nothing you install there sticks around — which is exactly why it is a fair, repeatable test. That also means every job must install what it needs from scratch (or restore it from the cache).

Step 1 — Create the frontend lint workflow

  1. In your project, create the folder .github/workflows/ if it does not exist (at 361:14). GitHub watches this exact folder for pipeline files.
  2. Inside it, create a file named frontend-lint-format-check.yml and paste the configuration below.
name: Frontend lint & format

on:
  workflow_call:

jobs:
  lint-format:
    name: Lint & format
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: ./frontend
    steps:
      - name: Check out repository
        uses: actions/checkout@v6

      - name: Set up pnpm
        uses: pnpm/action-setup@v6
        with:
          version: "11"

      - name: Set up Node.js
        uses: actions/setup-node@v6
        with:
          node-version: "22"
          cache: "pnpm"
          cache-dependency-path: frontend/pnpm-lock.yaml

      - name: Install dependencies
        run: pnpm install

      - name: Run ESLint
        run: pnpm run lint

      - name: Check Prettier formatting
        run: pnpm run format:check

Step 2 — Create the backend lint workflow

  1. Create .github/workflows/backend-lint-format-check.yml with the configuration below. It mirrors the frontend file but swaps the tools for Python ones (at 368:55).

Step 3 — Add unit test workflows

The presenter is clear: this course does not teach you to write tests, only to plug your existing test suite into the pipeline (at 373:36). GitHub Actions treats your tests as a black box — it only cares about the exit code they return.

New to exit codes? Why 0 and 1 matter

Every command a computer runs ends with a number called the exit code. By convention 0 means success and any other number (usually 1) means failure. Testing tools like Pytest and Vitest follow this rule: all tests pass, they exit 0; one test fails, they exit 1. GitHub Actions reads that number — a non-zero exit instantly fails the step and stops the pipeline (at 398:30 in the handbook text). That is why "just run the test command" is enough; the exit code does the rest.

  1. Create .github/workflows/frontend-unit-tests.yml (below). It reuses the Node.js setup and ends with one new command.
  2. Create .github/workflows/backend-unit-tests.yml (below). Same idea, but it installs from requirements.txt and runs Pytest.

Step 4 — Tie it together with the orchestrator

  1. Create ci.yml directly inside .github/workflows/. This is the file GitHub actually watches and runs.
  2. Paste the configuration below, then commit and push all five files.
name: CI pipeline

on:
  push:
    branches: [master]
  pull_request:
    branches: [master]
  workflow_dispatch:

jobs:
  frontend-lint-format-check:
    name: Frontend lint
    uses: ./.github/workflows/frontend-lint-format-check.yml

  backend-lint-format-check:
    name: Backend lint
    uses: ./.github/workflows/backend-lint-format-check.yml

  frontend-unit-tests:
    name: Frontend tests
    needs: frontend-lint-format-check
    uses: ./.github/workflows/frontend-unit-tests.yml

  backend-unit-tests:
    name: Backend tests
    needs: backend-lint-format-check
    uses: ./.github/workflows/backend-unit-tests.yml

  pipeline-success:
    name: Pipeline success
    needs:
      [
        frontend-lint-format-check,
        backend-lint-format-check,
        frontend-unit-tests,
        backend-unit-tests,
      ]
    runs-on: ubuntu-latest
    if: always()
    steps:
      - name: Pipeline succeeded
        if: "!contains(needs.*.result, 'failure') && !contains(needs.*.result, 'cancelled')"
        run: echo "All checks passed successfully!"
      - name: Pipeline failed
        if: contains(needs.*.result, 'failure') || contains(needs.*.result, 'cancelled')
        run: |
          echo "Some checks failed or were cancelled."
          exit 1

Step 5 — See it run, then enforce it

Push a branch with a deliberate mistake and open a pull request. The matching job turns red, its dependent test job is skipped, and pipeline-success goes red too. But there is a catch the presenter flags (at 383:30): the Merge button is still clickable. The pipeline is only advising you — it is not yet blocking anything.

  1. In your repository, open Settings → Rulesets and select the branch protection ruleset you made earlier (at 383:53).
  2. Scroll to Branch rules and tick Require status checks to pass.
  3. Click Add checks, search for Pipeline success, and add it to the required list.
  4. Click Save changes.

Now a failed pull request shows a greyed-out, unclickable Merge button with the message "merging is blocked" (at 384:18). Because you required only the single pipeline-success job, you never have to touch these settings again — adding future checks (security scans, end-to-end tests) just means editing ci.yml.

What you should see
  • In the Actions tab, a run named CI pipeline with five jobs. On clean code, all five show green check marks (at 384:42).
  • Click into a job to watch each step run in order: Check out repository, Set up Python/Node, Install dependencies, then the lint or test step.
  • On a passing pull request, the step logs print All checks passed successfully!
  • After enabling the required check, a failing pull request shows the Merge button greyed out.
Common mistakes
  • Putting the files anywhere other than .github/workflows/ — GitHub only reads that exact path, so nothing runs.
  • Forgetting on: workflow_call in a reusable file, or expecting a reusable file to run by itself. It only runs when ci.yml calls it.
  • Wrong indentation in YAML (or tabs instead of spaces). The run fails to parse before any step executes.
  • Expecting the pipeline to block a merge before you tick Require status checks to pass. Until then the red mark is only a suggestion (at 383:30).
  • Assuming local pre-commit hooks are enough. Editing a file straight on GitHub, as the presenter does (at 385:07), skips those hooks entirely — only the cloud pipeline catches it.
Security note

Always pin actions to a version, like actions/checkout@v6, rather than a moving tag. A community action runs with access to your repository, so an unpinned reference could pull in changed, untrusted code without warning. Pinning, plus requiring the pipeline to pass before merge, means code cannot reach master without first clearing every automated check.

Recap
  • CI runs your checks on a fresh cloud machine for every push and pull request, so nothing depends on one person's laptop.
  • You wrote four small reusable workflows (frontend/backend lint, frontend/backend tests), each triggered by workflow_call.
  • A step either uses a prebuilt action or runs a shell command; caching makes repeat runs fast.
  • ci.yml orchestrates them: needs sets the order, and pipeline-success aggregates one overall pass or fail.
  • Tests are a black box judged only by their exit code: 0 passes, 1 fails and stops the pipeline.
  • Marking pipeline-success as a required status check is what actually blocks the merge button when the pipeline is red.
