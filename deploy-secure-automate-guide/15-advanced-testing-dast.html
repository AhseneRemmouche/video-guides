Advanced Testing & DAST

Add integration and end-to-end tests, and dynamic application security testing with OWASP ZAP.

▶ Watch this part (431:17)

So far your pipeline has only read your code while it sits still: it checked the formatting, scanned for secrets, and ran isolated unit tests. But a real web application is not a static script. It is a live system of connected services that only shows its true behaviour once everything is running together. In this lesson you bring the whole application to life inside the GitHub Actions runner: a temporary database, the backend, and the frontend all start up, then three new kinds of checks run against the living system.

You will add three layers, in order: backend integration tests that prove the API can talk to a real Meilisearch database; end-to-end tests with Playwright that drive a real browser like a user would; and a DAST scan with OWASP ZAP that attacks your running API the way a hacker would. Each one plugs into the same pipeline you have been building.

What this lesson is not

This lesson does not teach you how to write integration or end-to-end tests from scratch (at 431:42). It shows you how to take tests you already have and wire them into GitHub Actions so they run correctly in the cloud. The focus is the infrastructure around the tests, not the test code itself.

The idea: from static text to a living system

A unit test checks one function in isolation (at 435:15). That is fast and cheap, but it cannot tell you whether two real services actually cooperate. Integration tests check that your backend can reach an external service such as Meilisearch or a database. End-to-end tests go further still: they open a browser, load the real page, and click through it, so they need the frontend, backend, and database all running at the same time (at 446:51). The presenter lays out exactly this order at 431:42: integration first, then end-to-end, then a dynamic security scan.

New to the test pyramid? What it is and why it matters

The pyramid is a rule of thumb for how to split your testing effort. Most of your tests should be unit tests, because they are quick and pinpoint exactly which function broke. You need fewer integration tests, and only a handful of slow end-to-end tests, because each higher layer costs more time and is harder to debug. Following this shape keeps your pipeline fast while still proving the whole system works.

New to integration tests? What they check

An integration test checks that your code works with another real piece of software, not a fake stand-in. For this project the backend relies on Meilisearch to answer search queries, so the integration test starts a real Meilisearch, points the backend at it, and runs queries. You cannot use a fake database here: the whole point is to prove the two programs really talk to each other (at 435:15).

Step 1: Backend integration tests against a live Meilisearch

To test the real connection in GitHub Actions you cannot use a fake database. You download the real Meilisearch program, start it inside the Ubuntu runner, and run pytest against it (at 439:33). Create the file below.

  1. In your repository, create .github/workflows/backend-integration-tests.yml.
  2. Paste the full workflow shown next.
  3. Commit and push it on a branch, then open a pull request so the pipeline runs it.
name: Backend integration tests

on:
  workflow_call:

env:
  MEILISEARCH_MASTER_KEY: "aStrongMasterKeyForTestingPurposes"
  MEILISEARCH_URL: "http://localhost:7700"
  MEILISEARCH_INDEX_NAME: "articles_test"
  MEILISEARCH_DOWNLOAD_MAX_RETRIES: "3"
  MEILISEARCH_DOWNLOAD_RETRY_DELAY: "5"

jobs:
  tests:
    name: Run integration tests
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: ./backend
    steps:
      - name: Check out repository
        uses: actions/checkout@v6

      - name: Set up Python
        uses: actions/setup-python@v6
        with:
          python-version: "3.13"
          cache: "pip"

      - name: Install dependencies
        run: pip install -r requirements-dev.txt

      - name: Download Meilisearch binary
        run: |
          MAX_RETRIES="${MEILISEARCH_DOWNLOAD_MAX_RETRIES}"
          RETRY_DELAY="${MEILISEARCH_DOWNLOAD_RETRY_DELAY}"
          for i in $(seq 1 $MAX_RETRIES); do
            echo "Attempt $i of $MAX_RETRIES to download Meilisearch..."
            if curl -L https://install.meilisearch.com | sh; then
              echo "Meilisearch downloaded successfully!"
              chmod +x meilisearch
              break
            else
              if [ $i -lt $MAX_RETRIES ]; then
                echo "Download failed. Retrying in $RETRY_DELAY seconds..."
                sleep $RETRY_DELAY
              else
                echo "Download failed after $MAX_RETRIES attempts"
                exit 1
              fi
            fi
          done

      - name: Start Meilisearch
        run: |
          ./meilisearch --master-key="${MEILISEARCH_MASTER_KEY}" &
          echo "Waiting for Meilisearch to start..."
          for i in {1..30}; do
            if curl -s http://localhost:7700/health | grep -q "available"; then
              echo "Meilisearch is ready!"
              break
            fi
            echo "Attempt $i: Meilisearch not ready yet..."
            sleep 1
          done
          if ! curl -s http://localhost:7700/health | grep -q "available"; then
            echo "Meilisearch failed to start after 30 attempts"
            exit 1
          fi

      - name: Run integration tests
        run: pytest tests/integration --tb=short -v
        env:
          MEILISEARCH_URL: ${{ env.MEILISEARCH_URL }}
          MEILISEARCH_MASTER_KEY: ${{ env.MEILISEARCH_MASTER_KEY }}
          MEILISEARCH_INDEX_NAME: ${{ env.MEILISEARCH_INDEX_NAME }}

Step 2: End-to-end tests with Playwright

End-to-end tests open a real browser and click through your site like a user (at 432:06). Because the user needs to see the interface and load real data, these tests require the frontend, backend, and database all running at once (at 446:51). First install Playwright and set up its config.

  1. In frontend/, run the install command below. Playwright will create a config file for you (at 453:49).
  2. Open frontend/playwright.config.js and make it match the version shown, so it behaves well inside GitHub Actions.
  3. Create .github/workflows/e2e-tests.yml with the workflow that boots the whole stack.
pnpm create playwright
import { defineConfig, devices } from "@playwright/test";

export default defineConfig({
  testDir: "./tests/e2e",
  fullyParallel: true,
  forbidOnly: !!process.env.CI,
  retries: process.env.CI ? 2 : 0,
  workers: undefined,
  reporter: process.env.CI ? [["list"], ["github"]] : "html",
  expect: {
    timeout: 10 * 1000,
  },
  use: {
    baseURL: "http://localhost:8080",
    trace: "on-first-retry",
    screenshot: "only-on-failure",
  },
  projects: [
    {
      name: "chromium",
      use: { ...devices["Desktop Chrome"] },
    },
    {
      name: "firefox",
      use: { ...devices["Desktop Firefox"] },
    },
  ],
  webServer: {
    command: "pnpm run dev",
    url: "http://localhost:8080",
    reuseExistingServer: !process.env.CI,
    timeout: 120 * 1000,
  },
});

Now the workflow that starts the entire system. This is the longest job in the pipeline because it boots the database, the backend, and the frontend, then runs the browser tests.

name: E2E tests

on:
  workflow_call:

env:
  MEILISEARCH_MASTER_KEY: "aStrongMasterKeyForTestingPurposes"
  MEILISEARCH_URL: "http://localhost:7700"
  MEILISEARCH_INDEX_NAME: "articles_test"
  MEILISEARCH_DOWNLOAD_MAX_RETRIES: "3"
  MEILISEARCH_DOWNLOAD_RETRY_DELAY: "5"

jobs:
  tests:
    name: Run E2E tests
    runs-on: ubuntu-latest
    timeout-minutes: 30
    steps:
      - name: Check out repository
        uses: actions/checkout@v6

      - name: Set up Python
        uses: actions/setup-python@v6
        with:
          python-version: "3.13"
          cache: "pip"

      - name: Install backend dependencies
        working-directory: ./backend
        run: pip install -r requirements.txt

      - name: Download Meilisearch binary
        working-directory: ./backend
        run: |
          MAX_RETRIES="${MEILISEARCH_DOWNLOAD_MAX_RETRIES}"
          RETRY_DELAY="${MEILISEARCH_DOWNLOAD_RETRY_DELAY}"
          for i in $(seq 1 $MAX_RETRIES); do
            echo "Attempt $i of $MAX_RETRIES to download Meilisearch..."
            if curl -L https://install.meilisearch.com | sh; then
              echo "Meilisearch downloaded successfully!"
              chmod +x meilisearch
              break
            else
              if [ $i -lt $MAX_RETRIES ]; then
                echo "Download failed. Retrying in $RETRY_DELAY seconds..."
                sleep $RETRY_DELAY
              else
                echo "Download failed after $MAX_RETRIES attempts"
                exit 1
              fi
            fi
          done

      - name: Start Meilisearch
        working-directory: ./backend
        run: |
          ./meilisearch --master-key="${MEILISEARCH_MASTER_KEY}" &
          echo "Waiting for Meilisearch to start..."
          for i in {1..30}; do
            if curl -s http://localhost:7700/health | grep -q "available"; then
              echo "Meilisearch is ready!"
              break
            fi
            echo "Attempt $i: Meilisearch not ready yet..."
            sleep 1
          done
          if ! curl -s http://localhost:7700/health | grep -q "available"; then
            echo "Meilisearch failed to start after 30 attempts"
            exit 1
          fi

      - name: Start backend server
        working-directory: ./backend
        run: |
          uvicorn main:app --host 0.0.0.0 --port 8000 &
          echo "Waiting for backend to start..."
          for i in {1..30}; do
            if curl -s http://localhost:8000/api/health | grep -q "ok"; then
              echo "Backend is ready!"
              break
            fi
            echo "Attempt $i: Backend not ready yet..."
            sleep 1
          done
          if ! curl -s http://localhost:8000/api/health | grep -q "ok"; then
            echo "Backend failed to start after 30 attempts"
            exit 1
          fi
        env:
          MEILISEARCH_URL: ${{ env.MEILISEARCH_URL }}
          MEILISEARCH_MASTER_KEY: ${{ env.MEILISEARCH_MASTER_KEY }}
          MEILISEARCH_INDEX_NAME: ${{ env.MEILISEARCH_INDEX_NAME }}

      - name: Seed E2E test data
        working-directory: ./backend
        run: python -m tests.test_data
        env:
          MEILISEARCH_URL: ${{ env.MEILISEARCH_URL }}
          MEILISEARCH_MASTER_KEY: ${{ env.MEILISEARCH_MASTER_KEY }}
          MEILISEARCH_INDEX_NAME: ${{ env.MEILISEARCH_INDEX_NAME }}

      - name: Set up pnpm
        uses: pnpm/action-setup@v4
        with:
          version: "11"

      - name: Set up Node.js
        uses: actions/setup-node@v6
        with:
          node-version: "22"
          cache: "pnpm"
          cache-dependency-path: frontend/pnpm-lock.yaml

      - name: Install frontend dependencies
        working-directory: ./frontend
        run: pnpm install

      - name: Get Playwright version
        id: playwright-version
        working-directory: ./frontend
        run: echo "version=$(pnpm list @playwright/test --json | jq -r '.[0].devDependencies["@playwright/test"].version')" >> $GITHUB_OUTPUT

      - name: Cache Playwright browsers
        uses: actions/cache@v4
        id: playwright-cache
        with:
          path: ~/.cache/ms-playwright
          key: ${{ runner.os }}-playwright-${{ steps.playwright-version.outputs.version }}
          restore-keys: |
            ${{ runner.os }}-playwright-

      - name: Install Playwright browsers (if no cache)
        if: steps.playwright-cache.outputs.cache-hit != 'true'
        working-directory: ./frontend
        run: pnpm exec playwright install --with-deps chromium firefox

      - name: Install Playwright dependencies (if cache hit)
        if: steps.playwright-cache.outputs.cache-hit == 'true'
        working-directory: ./frontend
        run: pnpm exec playwright install-deps chromium firefox

      - name: Run E2E tests
        working-directory: ./frontend
        run: pnpm run test:e2e
        env:
          CI: true

      - name: Upload Playwright report
        uses: actions/upload-artifact@v5
        if: ${{ !cancelled() }}
        with:
          name: playwright-report
          path: frontend/playwright-report/
          retention-days: 30

Step 3: Dynamic security scanning with OWASP ZAP (DAST)

Earlier you ran SAST, which reads your raw source code for flaws. Some weaknesses only appear when the app is running (at 465:01). DAST interacts with your live application like a real attacker, probing its inputs and routes. You will use the OWASP ZAP API scan: point it at FastAPI's auto-generated openapi.json, and ZAP learns every route and tests them one by one (at 463:01).

New to DAST and OWASP ZAP? What they do

DAST stands for Dynamic Application Security Testing. Unlike a static scan that reads code, a dynamic scan runs against the live, started application and sends real requests to look for weaknesses. OWASP ZAP (Zed Attack Proxy) is a free, trusted, open-source tool that performs exactly this kind of scan (at 462:37). Because FastAPI publishes an openapi.json describing every route, ZAP reads that file and knows precisely what to attack, instead of guessing by clicking around.

  1. Create .github/workflows/dast-scan.yml with the workflow below. It boots Meilisearch and the backend, then runs the ZAP action against the running API (at 462:10).
  2. Create .github/zap-rules.tsv to silence false alarms that only happen because the CI server has no Nginx in front of it.

  workflow_call:

      ENVIRONMENT: "development"
      MEILISEARCH_DOWNLOAD_MAX_RETRIES: "3"
      MEILISEARCH_DOWNLOAD_RETRY_DELAY: "5"
    defaults:
      run:
        working-directory: ./backend
    steps:
      - name: Check out repository
        uses: actions/checkout@v6

      - name: Set up Python
        uses: actions/setup-python@v6
        with:
          python-version: "3.13"
          cache: "pip"

      - name: Install backend dependencies
        run: pip install -r requirements.txt

      - name: Download Meilisearch binary
        run: |

              chmod +x meilisearch
              break
            else
              if [ $i -lt $MAX_RETRIES ]; then
                echo "Download failed. Retrying in $RETRY_DELAY seconds..."
                sleep $RETRY_DELAY
              else
                echo "Download failed after $MAX_RETRIES attempts"
                exit 1
              fi
            fi
          done

      - name: Start Meilisearch
        run: |
          ./meilisearch --master-key="${MEILISEARCH_MASTER_KEY}" &
          echo "Waiting for Meilisearch to start..."
          for i in {1..30}; do

              echo "Meilisearch is ready!"
              break
            fi
            echo "Attempt $i: Meilisearch not ready yet..."
            sleep 1
          done
          if ! curl -s http://localhost:7700/health | grep -q "available"; then
            echo "Meilisearch failed to start after 30 attempts"
            exit 1
          fi

      - name: Seed test data
        run: python -m tests.test_data

      - name: Start backend
        run: |
          nohup uvicorn main:app --host 0.0.0.0 --port 8000 &
          echo "Waiting for backend to start..."
          for i in {1..30}; do
            if curl -s http://localhost:8000/api/health | grep -q "ok"; then
              echo "Backend is ready!"
              break
            fi
            echo "Attempt $i: Backend not ready yet..."
            sleep 1
          done
          if ! curl -s http://localhost:8000/api/health | grep -q "ok"; then
            echo "Backend failed to start after 30 attempts"
            exit 1
          fi

        uses: zaproxy/action-api-scan@v0.10.0
        with:
          target: "http://localhost:8000/openapi.json"
          format: openapi
          rules_file_name: ".github/zap-rules.tsv"
          allow_issue_writing: false
          fail_action: true

Common mistakes
  • Forgetting the trailing & when starting Meilisearch, the backend, or a dev server. Without it the step hangs forever and never runs your tests (at 439:33).
  • Running tests before the service is ready. Always poll the /health endpoint first, or you get "connection refused".
  • Over-ignoring in zap-rules.tsv. Silence only alerts that are genuinely handled in production. Do not blanket-ignore real findings (at 472:31).
  • The Meilisearch download can 404 if you grab it minutes after a new release, before its files are published. Just re-run the job (at 466:36).
What you should see

Integration tests connect to a real Meilisearch and pass. The end-to-end job boots the full stack and runs many browser tests across two engines in parallel (the presenter sees 178 tests at 459:18). The ZAP scan reports it found your API's routes from openapi.json (15 URLs in the video), and once your rules file is in place it skips the Nginx-handled headers and passes (at 474:09).

Security note

The ZAP step in the pipeline is a deliberately fast, lightweight scan of the backend API so it does not slow every commit (at 468:35). It does not cover the full frontend. The handbook sets up a separate, heavier daily scan for that, run overnight. Also remember: once your rules file stabilises, a new ZAP failure almost certainly means a real security issue that needs immediate attention (at 474:54).

Recap
  • The test pyramid: many fast unit tests at the base, fewer integration tests in the middle, a handful of slow end-to-end tests on top. This lesson added the two upper layers plus a live security scan.
  • Integration tests start a real Meilisearch inside the runner and prove the backend can talk to it — download, background-start, poll /health, then run pytest.
  • End-to-end tests boot the whole stack (frontend, backend, seeded database) and drive it with Playwright across Chromium and Firefox, uploading a report artifact for debugging.
  • DAST with OWASP ZAP attacks the running API using FastAPI's openapi.json; zap-rules.tsv silences alerts that production Nginx already handles.
  • All three jobs plug into ci.yml with needs ordering and feed the single required pipeline-success gate.
