Continuous Delivery & Rollback

Deploy automatically from the pipeline with a zero-downtime atomic release and a rollback path.

▶ Watch this part (520:00)

You have tested your code and scanned it for vulnerabilities. The last step is to actually ship it: move everything to your DigitalOcean production server. This lesson builds a continuous delivery workflow that compiles the frontend, backs up your live data, transfers the new code over SSH, swaps the Python environment safely, and restarts the services — all from a button in GitHub Actions (at 479:59).

There is one deliberate difference from the test pipeline: deployment does not happen automatically. Even with great tests, you want a human to approve before live code is overwritten (at 480:22). You will also build a rollback step, so if an install fails halfway the old environment is instantly restored and your site stays up. Done right, the whole update is zero-downtime: users never see an error while you ship.

The deployment workflow does five things in order (at 480:22):

  1. Compile the Vue frontend into static files Nginx can serve.
  2. Back up the live SQLite database and the Meilisearch search engine.
  3. Safely transfer the new code and built frontend to the server with rsync.
  4. Perform an atomic swap of the Python virtual environment, rolling back if it fails.
  5. Restart the backend and reload the web server, verifying each one.
New to continuous delivery? How it differs from CI

Continuous integration (CI) checks every change: it lints, tests, and scans your code so you know it is correct. Continuous delivery (CD) is the next step: it takes code that already passed CI and ships it to a real server. Here CD is kept separate from CI and triggered by hand, so a person consciously decides when to go live (at 478:00). CI runs on every push; CD runs when you click the button.

Step 1: Build the frontend into a shippable artifact

Nginx serves plain static files, so the Vue code must be compiled first (at 480:47). This reusable workflow builds the frontend and uploads the result as an artifact that the deploy job can download later, because the two jobs run on different machines (at 481:34).

  1. Create .github/workflows/frontend-build.yml with the workflow below.
  2. Add it to ci.yml (shown next) so it runs after the end-to-end tests.
name: Frontend build

on:
  workflow_call:

jobs:
  build:
    name: Build frontend
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: ./frontend
    steps:
      - name: Check out repository
        uses: actions/checkout@v6

      - name: Set up pnpm
        uses: pnpm/action-setup@v4
        with:
          version: "11"

      - name: Set up Node.js
        uses: actions/setup-node@v6
        with:
          node-version: "22"
          cache: "pnpm"
          cache-dependency-path: frontend/pnpm-lock.yaml

      - name: Install dependencies
        run: pnpm install

      - name: Build frontend
        run: pnpm build

      - name: Upload build artifacts
        uses: actions/upload-artifact@v5
        with:
          name: frontend-build
          path: frontend/dist
          retention-days: 1

Step 2: Prepare the server — backups and passwordless permissions

Before GitHub can deploy, the server needs two things: a way to trim old backups so the disk never fills, and permission to restart services without a password prompt (at 485:09).

First, the rolling-backup cleaner. It keeps a fixed number of recent backups and deletes the rest. Create it on the server:

sudo nano /usr/local/bin/clean_backups.sh
#!/bin/bash

# 1. Get the number of backups to keep from the first argument
# ${1:-5} means: "Use argument 1, but if it is empty, default to 5"
KEEP_COUNT=${1:-5}

# 2. Calculate the offset for tail
# If we want to keep 5, we need to start deleting from the 6th file.
# So Offset = Keep Count + 1
OFFSET=$((KEEP_COUNT + 1))

echo "Starting cleanup. Retention policy: Keep last $KEEP_COUNT files."

clean_old_files() {
  TARGET_DIR=$1
  if [ -d "$TARGET_DIR" ]; then
    echo "Cleaning $TARGET_DIR"
    cd "$TARGET_DIR" || exit
    ls -tp | grep -v '/$' | tail -n +$OFFSET | xargs -I {} rm -- "{}"
  else
    echo "Directory $TARGET_DIR does not exist. Skipping."
  fi
}

clean_old_files "/web_app/backups"
clean_old_files "/var/lib/meilisearch/dumps"

Make it executable:

sudo chmod +x /usr/local/bin/clean_backups.sh

Now the permissions. The deploy job must restart Nginx and Supervisor and run the backup cleaner, all with sudo. A pipeline cannot type a password, so grant those exact commands passwordless (at 487:32). Open the sudoers file safely:

sudo visudo

Add this line at the very bottom, replacing the username with your own:

<your_username> ALL=(ALL) NOPASSWD: /usr/sbin/nginx, /usr/bin/systemctl reload nginx, /usr/bin/supervisorctl restart all, /usr/bin/supervisorctl status all, /usr/local/bin/clean_backups.sh

Security note

Passwordless sudo on a tight, explicit list is a safety feature, not a hole. Even if someone stole your automated SSH key, they could only reload Nginx, restart Supervisor, or clean backups. Any other sudo command still demands a password and is blocked (at 488:47). Never grant blanket NOPASSWD: ALL.

Step 3: Protect live data with an rsync exclude file

The deploy uses rsync to copy files to the server. By default rsync --delete makes the server match the repository exactly — so anything on the server but not in GitHub (your live database, your backups) would be deleted (at 489:58). An exclude file tells rsync what to leave alone.

  1. Create rsync_exclude.txt in your project root on your local computer.
  2. Commit and push it to master.

Step 4: GitHub environments, the approval gate, and secrets

The pipeline needs a safe way to log in to the server, plus a human checkpoint. A GitHub environment named production with a required reviewer gives you the approval gate (at 491:06), and repository secrets store the login details (at 492:15).

  1. In your repo, go to Settings → Environments → New environment, name it production, and configure it.
  2. Check Required reviewers, add yourself, and save. Now every deploy pauses for approval (at 491:29).
  3. Go to Settings → Secrets and variables → Actions and add four secrets: DIGITAL_OCEAN_HOST_IP, DIGITAL_OCEAN_USERNAME, MEILISEARCH_MASTER_KEY, and DIGITAL_OCEAN_SSH_KEY (at 492:15).
  4. If you do not have a dedicated deploy key, create one with no passphrase, put the public half on the server, and paste the private half into the secret.
ssh-keygen -t rsa -b 4096 -f ~/.ssh/github_actions_key -C "github_actions"
cat ~/.ssh/github_actions_key.pub
nano ~/.ssh/authorized_keys
cat ~/.ssh/github_actions_key
Why no passphrase on this key?

A passphrase protects a key by asking for it each time it is used. That is good for a human, but a pipeline runs unattended — if the key had a passphrase, the deploy would freeze waiting for someone to type it (at 493:04). So this one dedicated automation key is created with no passphrase, and its power is limited by the tight passwordless-sudo list you set earlier.

Step 5: The deployment workflow

Now the deploy itself. Because deployment is kept separate from the test pipeline, it uses a manual trigger (at 495:04). The file is long, but it is the five stages you already know: build, back up with polling, rsync, atomic venv swap, and verified restart/reload. Create .github/workflows/deploy.yml:

name: Manual deploy

on:
  workflow_dispatch:

jobs:
  build:
    name: Build frontend
    uses: ./.github/workflows/frontend-build.yml

  deploy:
    name: Deploy
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: production
      url: https://imadsaddik.com

    steps:
      - name: Check out repository
        uses: actions/checkout@v6

      - name: Download frontend artifact
        uses: actions/download-artifact@v6
        with:
          name: frontend-build
          path: ./frontend/dist

      - name: Create backups (SQLite & Meilisearch)
        uses: appleboy/ssh-action@v1.2.4
        env:
          MEILISEARCH_KEY: ${{ secrets.MEILISEARCH_MASTER_KEY }}
        with:
          host: ${{ secrets.DIGITAL_OCEAN_HOST_IP }}
          username: ${{ secrets.DIGITAL_OCEAN_USERNAME }}
          key: ${{ secrets.DIGITAL_OCEAN_SSH_KEY }}
          envs: MEILISEARCH_KEY
          script: |
            set -e

            BACKEND_DIR="/web_app/backend"
            BACKUP_DIR="/web_app/backups"
            BACKUP_RETENTION_COUNT=5
            TIMESTAMP=$(date +%Y%m%d%H%M%S)

            mkdir -p $BACKUP_DIR

            echo "Backing up SQLite database..."
            if [ -f "$BACKEND_DIR/visitors.db" ]; then
              cp "$BACKEND_DIR/visitors.db" "$BACKUP_DIR/visitors_$TIMESTAMP.db"
              echo "SQLite backup created successfully."
            else
              echo "Warning: No SQLite database found in $BACKEND_DIR"
            fi

            echo "Triggering Meilisearch dump..."
            if [ -z "$MEILISEARCH_KEY" ]; then
              echo "Error: MEILISEARCH_KEY secret is empty."
              exit 1
            fi

            DUMP_RESPONSE=$(curl -s -w "\n%{http_code}" -X POST 'http://127.0.0.1:7700/dumps' \
              -H "Authorization: Bearer $MEILISEARCH_KEY")
            HTTP_CODE=$(echo "$DUMP_RESPONSE" | tail -n1)
            RESPONSE_BODY=$(echo "$DUMP_RESPONSE" | sed '$d')

            if [ "$HTTP_CODE" -ge 200 ] && [ "$HTTP_CODE" -lt 300 ]; then
              echo "Meilisearch dump request accepted (HTTP $HTTP_CODE)."

              TASK_UID=$(echo "$RESPONSE_BODY" | grep -o '"taskUid":[0-9]*' | cut -d':' -f2)
              if [ -z "$TASK_UID" ]; then
                echo "Error: Could not extract taskUid from response."
                echo "Response: $RESPONSE_BODY"
                exit 1
              fi

              echo "Dump task created with UID: $TASK_UID"
              echo "Waiting for dump to complete..."

              # Poll task status until completion (max 60 seconds)
              MAX_ATTEMPTS=30
              ATTEMPT=0
              while [ $ATTEMPT -lt $MAX_ATTEMPTS ]; do
                TASK_RESPONSE=$(curl -s "http://127.0.0.1:7700/tasks/$TASK_UID" \
                  -H "Authorization: Bearer $MEILISEARCH_KEY")
                TASK_STATUS=$(echo "$TASK_RESPONSE" | grep -o '"status":"[^"]*"' | cut -d'"' -f4)

                if [ "$TASK_STATUS" = "succeeded" ]; then
                  echo "Meilisearch dump completed successfully."
                  break
                elif [ "$TASK_STATUS" = "failed" ]; then
                  echo "Error: Meilisearch dump task failed."
                  echo "Task response: $TASK_RESPONSE"
                  exit 1
                else
                  # Status is "enqueued" or "processing"
                  ATTEMPT=$((ATTEMPT + 1))
                  sleep 2
                fi
              done

              if [ $ATTEMPT -eq $MAX_ATTEMPTS ]; then
                echo "Error: Meilisearch dump timed out after 60 seconds."
                echo "Last task status: $TASK_STATUS"
                exit 1
              fi
            else
              echo "Error: Meilisearch dump request failed with HTTP $HTTP_CODE"
              echo "Response: $RESPONSE_BODY"
              exit 1
            fi

            echo "Cleaning old backups..."
            sudo /usr/local/bin/clean_backups.sh $BACKUP_RETENTION_COUNT
            echo "Backup process finished successfully."

      - name: Rsync files to droplet
        uses: easingthemes/ssh-deploy@v5.1.0
        with:
          SSH_PRIVATE_KEY: ${{ secrets.DIGITAL_OCEAN_SSH_KEY }}
          REMOTE_HOST: ${{ secrets.DIGITAL_OCEAN_HOST_IP }}
          REMOTE_USER: ${{ secrets.DIGITAL_OCEAN_USERNAME }}
          SOURCE: "./"
          TARGET: "/web_app/"
          ARGS: "-avzr --delete --exclude-from='rsync_exclude.txt'"

      - name: Create backend .env file
        uses: appleboy/ssh-action@v1.2.4
        env:
          MEILISEARCH_KEY: ${{ secrets.MEILISEARCH_MASTER_KEY }}
        with:
          host: ${{ secrets.DIGITAL_OCEAN_HOST_IP }}
          username: ${{ secrets.DIGITAL_OCEAN_USERNAME }}
          key: ${{ secrets.DIGITAL_OCEAN_SSH_KEY }}
          envs: MEILISEARCH_KEY
          script: |
            echo "Creating backend .env file..."
            cat > /web_app/backend/.env <<EOF
            MEILISEARCH_URL=http://127.0.0.1:7700
            MEILISEARCH_INDEX_NAME=articles
            MEILISEARCH_MASTER_KEY=$MEILISEARCH_KEY
            ENVIRONMENT=production
            EOF

      - name: Install Python dependencies (atomic venv swap)
        uses: appleboy/ssh-action@v1.2.4
        with:
          host: ${{ secrets.DIGITAL_OCEAN_HOST_IP }}
          username: ${{ secrets.DIGITAL_OCEAN_USERNAME }}
          key: ${{ secrets.DIGITAL_OCEAN_SSH_KEY }}
          script: |
            set -e

            BACKEND_DIR="/web_app/backend"
            cd $BACKEND_DIR

            echo "Backing up current venv..."
            if [ -d "venv" ]; then
              mv venv venv_backup
              echo "Current venv backed up to venv_backup."
            fi

            echo "Creating new virtual environment..."
            python3 -m venv venv

            echo "Installing Python dependencies..."
            source venv/bin/activate
            if pip install -r requirements.txt; then
              echo "Python dependencies installed successfully."
            else
              echo "Error: Failed to install Python dependencies."
              echo "Rolling back to previous venv..."
              deactivate
              rm -rf venv
              if [ -d "venv_backup" ]; then
                mv venv_backup venv
                echo "Rollback complete."
              fi
              exit 1
            fi
            deactivate

            # Clean up backup after successful deploy
            if [ -d "venv_backup" ]; then
              rm -rf venv_backup
              echo "Cleaned up venv_backup."
            fi

            echo "Virtual environment setup completed successfully."

      - name: Restart backend service
        uses: appleboy/ssh-action@v1.2.4
        with:
          host: ${{ secrets.DIGITAL_OCEAN_HOST_IP }}
          username: ${{ secrets.DIGITAL_OCEAN_USERNAME }}
          key: ${{ secrets.DIGITAL_OCEAN_SSH_KEY }}
          script: |
            set -e

            echo "Restarting FastAPI backend service..."
            if sudo supervisorctl restart all; then
              echo "FastAPI backend restarted successfully."
            else
              echo "Error: Failed to restart FastAPI backend."
              exit 1
            fi

            # Verify the service is running
            sleep 5
            if sudo supervisorctl status all | grep -q "RUNNING"; then
              echo "FastAPI backend is running."
            else
              echo "Error: FastAPI backend failed to start properly."
              sudo supervisorctl status all
              exit 1
            fi

      - name: Reload Nginx
        uses: appleboy/ssh-action@v1.2.4
        with:
          host: ${{ secrets.DIGITAL_OCEAN_HOST_IP }}
          username: ${{ secrets.DIGITAL_OCEAN_USERNAME }}
          key: ${{ secrets.DIGITAL_OCEAN_SSH_KEY }}
          script: |
            set -e

            echo "Testing Nginx configuration..."
            if sudo nginx -t; then
              echo "Nginx configuration is valid."
            else
              echo "Error: Nginx configuration test failed."
              exit 1
            fi

            echo "Reloading Nginx..."
            if sudo nginx -t; then
              echo "Configuration OK. Reloading Nginx..."
              sudo systemctl reload nginx
            else
              echo "Nginx configuration test failed! Not reloading."
              exit 1
            fi

            echo "Deployment complete!"

Step 6: Trigger your first deployment

  1. Open a pull request with your new files, let CI pass, and merge into master (at 515:05).
  2. Go to the Actions tab, pick Manual deploy in the sidebar, click Run workflow on the master branch (at 515:56).
  3. When the build finishes, the run pauses. Click Review deployments, select production, and Approve and deploy (at 516:45).
  4. Watch the logs: GitHub backs up your data, rsyncs the code, swaps the venv, restarts the backend, and reloads Nginx (at 517:10).
What you should see

The build job produces the artifact, then the run waits for your approval. After you approve, the backup step logs "SQLite backup created successfully" and the Meilisearch dump id, then rsync, the venv swap ("Virtual environment setup completed successfully"), the backend reporting RUNNING, and finally "Deployment complete!". Your change (the presenter's was a year label of 2026) appears live on the site (at 547:02).

Common mistakes
  • Leaving a command out of the sudoers list. The presenter's first deploy failed because supervisorctl status all and nginx -t were missing from the passwordless list, so sudo demanded a password and the step froze (at 542:38, 544:36). List every exact command the pipeline runs.
  • Forgetting to add the server-only files (socket, logs, scripts) to rsync_exclude.txt; without them --delete wipes those files on the server (at 531:06).
  • Giving the automation SSH key a passphrase — the deploy will hang waiting for input (at 493:04).
  • Building one giant workflow at once. Add one step, run it, fix failures, then add the next (at 547:26).
Security note

Two layers protect production: the required-reviewer approval gate stops anyone from deploying by mistake (at 491:29), and the tight passwordless-sudo list limits what a stolen key could ever do (at 488:47). Keep the real MEILISEARCH_MASTER_KEY only in GitHub Secrets and the server's own .env — never print it in logs or commit it.

Recap
  • Continuous delivery ships code that already passed CI; here it is a separate, manually triggered workflow with a human approval gate.
  • The deploy runs five stages over SSH: build the frontend, back up the database and search engine (polling until the dump succeeds), rsync the files, atomically swap the Python environment, and restart the backend and reload Nginx with verification.
  • The atomic swap renames the old environment aside, builds a new one, and on any failure restores the old one — that is the rollback that keeps the site up.
  • rsync_exclude.txt stops --delete from erasing live data; a tight passwordless-sudo list and a passphrase-free deploy key let the pipeline act without hanging, while staying locked down.
  • Because almost all the work happens while the old version still serves traffic, the final switch is quick and the update is effectively zero-downtime.
