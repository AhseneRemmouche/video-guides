Self-Hosting Meilisearch

Install Meilisearch, run it as a dedicated user under a systemd service, and load your exported data.

▶ Watch this part (204:29)

Your app is online: Nginx serves the Vue front end and proxies the API to Gunicorn. That is enough for a plain website. But modern apps need fast, typo-tolerant search, and an ordinary SQL database is slow at full-text search and bad at spelling mistakes. The fix is a dedicated search engine. In this step you install Meilisearch on the same server as your backend, lock it away behind your firewall so the public internet can never reach it, run it as a background service, and load your existing search data into it.

Even if your own project does not need search, follow along. The real skill here is bigger than Meilisearch: you are learning how to deploy an internal database or background service that is completely hidden from the internet (at 205:16). That pattern works for Redis, Postgres, or anything else you self-host.

Security note. Hosting the search engine on the same machine as the backend gives you three wins the handbook calls out: zero network latency (the API talks to it over localhost), no monthly bill for a managed search service, and maximum security — because Meilisearch sits behind your UFW firewall, it is invisible to the public internet.

Where Meilisearch sits in your stack

Before any commands, picture where this new piece runs. Everything happens inside the one server you already rented. The only doors open to the internet are ports 80 and 443 (web traffic) and 22 (SSH). Meilisearch listens on port 7700, but that port is blocked by UFW, so only programs already on the server — your backend — can reach it.

What you will do, and in what order

The presenter lays out the roadmap at 206:05: install the engine, isolate it with a dedicated system user, run it as a systemd service, give it a secret master key, and load your data from a dump. Here is the whole journey on one line.

New to search engines? What Meilisearch is and why you need one

A search engine is a program built for one job: find matching text fast, even when the user misspells it. Meilisearch is an open-source engine written in Rust. You give it documents (for example, your articles), it builds an index (a lookup structure, like the index at the back of a book), and then it answers "find me X" queries in milliseconds. An ordinary SQL database can search text too, but it was not built for it: it is slow on large text fields and cannot forgive a typo. Running a dedicated engine next to your API keeps searches instant.

Step 1 — Export your local data (Option 1)

There are two ways to get data into production. Option 1: export the data from the Meilisearch you already run on your laptop. Option 2: seed from scratch using the reference repo's script — if you pick that, skip straight to installing the binary. The rest of this section is Option 1.

Meilisearch offers two kinds of backup, and the difference matters (at 215:48). A snapshot is an exact copy of the database files, good only on the same Meilisearch version. A dump is a set of instructions to rebuild the database from scratch, so it survives a move to a different machine or version. Because your laptop and server are not identical, you migrate with a dump.

  1. On your local machine, with your local Meilisearch running, ask it to create a dump (at 217:00).
curl -X POST 'http://localhost:7700/dumps' \
  -H 'Authorization: Bearer <YOUR_LOCAL_MASTER_KEY>'
Line(s)CodeWhat it does & why
1curl -X POST 'http://localhost:7700/dumps' \curl sends an HTTP request from the terminal. -X POST sets the method to POST (you are asking the server to create something). The URL hits your local engine's /dumps endpoint. The trailing \ continues the command on the next line.
2-H 'Authorization: Bearer <YOUR_LOCAL_MASTER_KEY>'-H adds an HTTP header. Meilisearch is protected by a master key, so every request must carry it as a Bearer token. Replace the placeholder (and drop the angle brackets) with your local key.

Meilisearch answers with JSON. Creating a dump is asynchronous (it runs in the background), so you get back a taskUid to track it (at 217:24).

{
  "taskUid": 1,
  "indexUid": null,
  "status": "enqueued",
  "type": "dumpCreation",
  "enqueuedAt": "2026-03-18T10:00:00.000000Z"
}
  1. Check when the task finishes by querying it with its id (at 217:24).
curl -X GET 'http://localhost:7700/tasks/<YOUR_TASK_UID>' \
  -H 'Authorization: Bearer <YOUR_LOCAL_MASTER_KEY>'
What you should see. When the task's status reads succeeded, a file like 20260318-100000.dump appears in your local dumps/ folder. That file is what you ship to the server.

If you prefer Python to raw curl, the official SDK does the same thing. Make sure your local virtual environment is active first.

pip install meilisearch
import meilisearch

meilisearch_client = meilisearch.Client("http://localhost:7700", "<YOUR_LOCAL_MASTER_KEY>")
task = meilisearch_client.create_dump()

meilisearch_client.wait_for_task(task.task_uid)
print("Dump created successfully!")
Line(s)CodeWhat it does & why
1import meilisearchLoads the SDK you just installed so you can call it from Python.
3meilisearch_client = meilisearch.Client("http://localhost:7700", "<...>")Creates a client pointed at your local engine, passing the URL and the master key. Nothing happens on the server yet; this just prepares the connection.
4task = meilisearch_client.create_dump()Starts the dump and returns a task object — the SDK equivalent of the curl POST above.
6meilisearch_client.wait_for_task(task.task_uid)Blocks until the background task finishes, so you do not race ahead before the file exists.
7print("Dump created successfully!")Confirms it is done so you know the dump file is ready.

Step 2 — Install Meilisearch on the server

Now move to the server. Connect with your SSH shortcut, then download the engine with its official script.

ssh my-website
curl -L https://install.meilisearch.com | sh
Line(s)CodeWhat it does & why
1curl -L https://install.meilisearch.com | shcurl -L downloads the install script, following any redirects (-L). The | pipes that script straight into sh, which runs it. The script fetches one pre-compiled binary named meilisearch into the current folder — self-contained, so you do not install Rust or any dependency.

The binary lands in your current directory. Make it executable and move it to /usr/local/bin/ so the command works from anywhere on the system, which you need when it runs as a service later (at 209:20).

chmod +x ./meilisearch
sudo mv ./meilisearch /usr/local/bin/
Line(s)CodeWhat it does & why
1chmod +x ./meilisearchchmod +x marks the downloaded file as executable. Without the execute bit, Linux refuses to run it.
2sudo mv ./meilisearch /usr/local/bin/mv moves the file into /usr/local/bin/, a folder on every user's PATH. sudo is needed because that folder is system-owned. Now typing meilisearch works from any directory.
meilisearch --version
What you should see. A version number prints with no error. That confirms the binary is installed and on your PATH.

Step 3 — Create a dedicated system user

Earlier you learned never to run things as root. Now you go one step further and give Meilisearch its own dedicated system user (at 209:43). A system user is a "dummy" account that exists only to own files and run a background process. It has no password and cannot log in, which makes it immune to SSH brute-force attacks (at 210:30). The table below is the distinction the presenter draws on the slide.

sudo useradd -d /var/lib/meilisearch -s /bin/false -m -r meilisearch
Line(s)CodeWhat it does & why
1sudo useraddThe low-level command to add a user. Unlike adduser (used in Chapter 1), it does not prompt for a password or full name — ideal for a non-interactive service account.
1-d /var/lib/meilisearchSets the user's home directory. Instead of the default /home/meilisearch, it uses /var/lib/meilisearch, the standard Linux location for a service's data.
1-s /bin/falseSets the user's shell to /bin/false, a dummy shell that exits immediately. This is what makes it impossible to log in as this user.
1-mTells useradd to actually create the home directory named by -d.
1-rCreates a system user (a reserved, low numbered account) rather than a normal login user.
1meilisearchThe name of the new user. It owns the engine's files and runs its process.

Now create a folder for the actual database files and make the new user own everything in its home directory.

sudo mkdir -p /var/lib/meilisearch/data
sudo chown -R meilisearch:meilisearch /var/lib/meilisearch
Line(s)CodeWhat it does & why
1sudo mkdir -p /var/lib/meilisearch/dataCreates the data folder where the engine stores its database. -p creates any missing parent folders and does not error if they already exist.
2sudo chown -R meilisearch:meilisearch /var/lib/meilisearchchown changes ownership to the meilisearch user and group. -R applies it recursively to everything inside. Without this the service would be denied access to its own files.

Step 4 — Transfer and import the dump (Option 1)

If you seeded from scratch (Option 2), skip to Step 5. Otherwise, copy the dump up to the server. You send it to /tmp/ first because /tmp/ is writable by any user, whereas the locked-down /var/lib/meilisearch is not. Log out of SSH, then from your local terminal run scp.

scp /path/to/your/local/dumps/<YOUR_DUMP_FILE.dump> my-website:/tmp/
Line(s)CodeWhat it does & why
1scp"Secure copy" — copies a file over the same encrypted SSH connection you log in with.
1/path/to/your/local/dumps/<YOUR_DUMP_FILE.dump>The source: the dump file on your laptop. Replace it with the real path and filename.
1my-website:/tmp/The destination: your server (via the my-website SSH alias) and the folder /tmp/. The colon separates host from path.

SSH back in, move the file into the Meilisearch directory, and immediately hand ownership to the meilisearch user.

ssh my-website
sudo mv /tmp/<YOUR_DUMP_FILE.dump> /var/lib/meilisearch/
sudo chown meilisearch:meilisearch /var/lib/meilisearch/<YOUR_DUMP_FILE.dump>
Line(s)CodeWhat it does & why
1sudo mv /tmp/<YOUR_DUMP_FILE.dump> /var/lib/meilisearch/Moves the dump from the temporary folder into the engine's home directory, where the service can find it.
2sudo chown meilisearch:meilisearch /var/lib/meilisearch/<YOUR_DUMP_FILE.dump>Gives the file to the meilisearch user. Skip this and the service crashes: it will not have permission to read a file your admin account uploaded.

Step 5 — Run Meilisearch as a service

You do not want to babysit the engine in a terminal. You want it to run in the background, start on boot, and restart if it crashes — in other words, run as a daemon. For your FastAPI backend you used Supervisor. For Meilisearch you use systemd, Ubuntu's built-in service manager (at 222:08).

New to systemd? What a service manager does

systemd is the first program Linux starts when it boots, and its job is to start and watch over every other background service. You describe a service in a small text file called a systemd unit (a "unit file"). systemd reads that file and knows how to launch the program, when to start it, and what to do if it dies. You then control it with systemctl start, stop, enable (start on boot), and status.

Why systemd here and Supervisor for the API? The rule of thumb (at 222:31): manage low-level infrastructure (databases, Redis, Meilisearch) with the OS's native tool, systemd; manage application code (your Python API) with a higher-level tool like Supervisor, which is easier to restart during deployments.

Create the secure environment file

Never hardcode the master key inside the service file — it would show up in the server's process list. Instead, put it in a protected environment file (at 224:05). Meilisearch automatically reads any variable starting with MEILI_.

sudo mkdir -p /etc/meilisearch
sudo nano /etc/meilisearch/env
MEILI_ENV=production
MEILI_MASTER_KEY=<YOUR_STRONG_MASTER_KEY>
Line(s)CodeWhat it does & why
1MEILI_ENV=productionPuts the engine in production mode, which enforces the master key and disables the development-only unprotected search preview.
2MEILI_MASTER_KEY=<YOUR_STRONG_MASTER_KEY>Sets the master key every request must present. Replace the placeholder with a long random string (at least 16 bytes), no spaces or quotes. This is the one secret guarding your whole search engine.
Common mistakes. Do not reuse the default development key the docs show (at 223:42) — that is only safe on your laptop. Do not wrap the key in quotes or add spaces; Meilisearch reads the value literally. And remember to delete the angle brackets around the placeholder.

Lock the file so only the meilisearch user and root can read it.

sudo chown meilisearch:meilisearch /etc/meilisearch/env
sudo chmod 600 /etc/meilisearch/env
Line(s)CodeWhat it does & why
1sudo chown meilisearch:meilisearch /etc/meilisearch/envGives the file to the service user, so the engine can read its own secret.
2sudo chmod 600 /etc/meilisearch/env600 means: owner can read and write, nobody else can even read. This stops other accounts from seeing the master key.

Create the systemd unit file

Now write the unit file that tells Ubuntu how to run Meilisearch. A unit file has three sections: [Unit] (what and when), [Service] (how to run it), and [Install] (how to enable it on boot).

sudo nano /etc/systemd/system/meilisearch.service

If you are importing a dump (Option 1), leave the file exactly as below and replace <YOUR_DUMP_FILE.dump> with your filename. If you are seeding from scratch (Option 2), delete the two lines starting with --import-dump and --ignore-dump-if-db-exists.

[Unit]
Description=Meilisearch search engine
After=network.target

[Service]
Type=simple
User=meilisearch
Group=meilisearch

# Load environment variables from the secure file
EnvironmentFile=/etc/meilisearch/env

WorkingDirectory=/var/lib/meilisearch

ExecStart=/usr/local/bin/meilisearch \
  --db-path "/var/lib/meilisearch/data" \
  --dump-dir "/var/lib/meilisearch/dumps" \
  --import-dump "/var/lib/meilisearch/<YOUR_DUMP_FILE.dump>" \
  --ignore-dump-if-db-exists

Restart=on-failure

[Install]
WantedBy=multi-user.target
Line(s)CodeWhat it does & why
1[Unit]Starts the section that describes the unit and its ordering.
2Description=Meilisearch search engineA human-readable name shown in systemctl status and logs.
3After=network.targetTells Linux not to start the service until the networking stack is fully up (at 227:37).
5[Service]Starts the section that defines how to run the program.
6Type=simpleSays the ExecStart command is the main process and stays in the foreground — the normal type for a long-running server.
7–8User=meilisearch / Group=meilisearchRuns the process as the locked-down system user, not as root. This is the isolation you set up in Step 3.
11EnvironmentFile=/etc/meilisearch/envLoads MEILI_ENV and MEILI_MASTER_KEY from your secure file, keeping the secret out of this file and the process list.
13WorkingDirectory=/var/lib/meilisearchSets the folder the process runs in, so relative paths resolve inside the service's own home.
15–19ExecStart=/usr/local/bin/meilisearch \ ...The exact command systemd runs. It points to the binary, then --db-path (where the database lives) and --dump-dir (where future dumps are saved). The \ continues the command across lines.
18--import-dump "/var/lib/meilisearch/<YOUR_DUMP_FILE.dump>" \On first start, loads your migrated data from the dump file (at 229:38). Replace the placeholder with your filename.
19--ignore-dump-if-db-existsA safety flag: skip the import if a database already exists in data, so a restart never wipes live data with the old dump.
21Restart=on-failureIf the process crashes or is killed (for example, out of memory), systemd restarts it automatically (at 230:25).
23–24[Install] / WantedBy=multi-user.targetTies the service to the normal multi-user boot stage, so enable makes it start on every reboot.

Enable and start the service

Tell systemd to re-read its files, enable the service on boot, and start it now.

sudo systemctl daemon-reload
sudo systemctl enable meilisearch
sudo systemctl start meilisearch

Clean up the service file

Once the data is imported, remove the import flags. Leaving --import-dump in place forever is a hidden trap: if that .dump file is ever deleted, Meilisearch will crash on the next reboot looking for a file that no longer exists (at 239:51). Reopen the file and delete these two lines from the ExecStart command.

sudo nano /etc/systemd/system/meilisearch.service
--import-dump "/var/lib/meilisearch/<YOUR_DUMP_FILE.dump>" \
--ignore-dump-if-db-exists

Then reload systemd and restart with the clean config.

sudo systemctl daemon-reload
sudo systemctl restart meilisearch

cd /web_app/backend

Common mistakes. Forgetting daemon-reload after editing the unit file (systemd keeps the stale config). Leaving a mismatched master key between /etc/meilisearch/env and the backend .env (every search fails authorization). Skipping the chown on the dump file (the service crashes on start, unable to read it).
Recap
  • You installed the Meilisearch binary into /usr/local/bin/ so it runs from anywhere.
  • You created a dedicated, login-less system user to own and run the engine, isolating it from your other accounts.
  • You migrated local data with a dump (safe across machines) rather than a snapshot, moving it via /tmp and fixing ownership.
  • You wrote a systemd unit with a secured environment file, so the engine runs as a daemon, starts on boot, and restarts on failure — with the master key kept out of the process list.
  • You removed the one-time import flags and connected FastAPI with the matching master key, confirming live searches in journalctl.
  • Meilisearch now listens only on 127.0.0.1:7700, invisible behind UFW.
