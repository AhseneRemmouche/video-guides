Nginx Reverse Proxy & Security Headers

Put Nginx in front of the app over a Unix socket and add HTTP security headers, including a Content-Security-Policy.

▶ Watch this part (141:53)

Your backend is alive, but it is hiding behind a private socket file and your Vue.js build is just a folder of files sitting on the server. Nobody from the outside can reach either one. In this step you install a web server that becomes the public front door: it serves your frontend, forwards API calls to the backend, and — crucially — adds the security headers that tell browsers how to protect your users.

What you will build

You will install Nginx and configure it as a reverse proxy. At (141:27) the presenter frames the plan: sync the frontend and backend URLs, install Nginx, understand the dreaded 502 Bad Gateway, then lock everything down with HTTP security headers — above all a Content Security Policy.

The concepts

What a reverse proxy does

At (150:38) the presenter explains that Nginx receives every request and decides what to do with it. If the user wants a web page, Nginx reads the finished files from your Vue.js dist folder and sends them back. If the request starts with /api, Nginx forwards it through the Unix socket to Gunicorn. A “forward proxy” works on behalf of the client; a reverse proxy works on behalf of the server, standing in front of it.

New to Nginx and reverse proxies? Why not just expose the backend?

Nginx is a fast, battle‑tested web server. Putting it in front of your app gives you one place to serve static files efficiently, terminate HTTPS later, add security headers, and hide the backend from the internet. A reverse proxy is simply a server that accepts public requests and quietly passes some of them to another program behind it. Your users only ever talk to Nginx; they never know Gunicorn exists.

Static files versus the API

The split is the heart of the configuration. Your frontend is a pile of static assets — files that never change per request, so Nginx can hand them straight back. The API is dynamic: it must run code, so Nginx forwards those requests to the backend. At (152:41) the presenter walks a concrete example: a search for /api/articles is caught by Nginx, sent through the socket to Gunicorn, handed to the FastAPI endpoint, and the response travels all the way back.

Prepare the frontend code

Before configuring Nginx, you make the frontend and backend behave as if they share one origin, which avoids cross‑origin (CORS) headaches. This is three small edits plus a rebuild.

Step 1 — Use a relative API base URL

Open where you configure Axios (usually main.js) and point it at the current host:

// In main.js
import axios from 'axios';

axios.defaults.baseURL = "/";

2import axios from 'axios';Brings in the Axios HTTP client your Vue app uses to call the API.
4axios.defaults.baseURL = "/";Sets every request to be relative to the current site. In development it hits your local server; in production it hits your domain. No hard‑coded address to change between environments.

Step 2 — Proxy /api in Vite for local development

Because the base URL is now /, the Vue dev server must forward /api calls to your local FastAPI. Add a server block to vite.config.js:

...

export default defineConfig({
  ...

  server: {
    port: 8080,
    proxy: {
      "/api": {
        target: "http://localhost:8000",
        changeOrigin: true,
      },
    },
  },
});
Line(s)CodeWhat it does & why
6–7server: { / port: 8080,Configures the Vite dev server to run on port 8080.

Common mistake. The ... lines are not code to paste. They mean “keep your existing config”. Only add the server block; do not delete your plugins or other settings.

Step 3 — Remove the backend CORS middleware

Since both sides now share an origin, the browser will not block requests, so the CORS workaround in FastAPI is no longer needed. Delete this whole block from main.py:

# Remove this entire block from main.py
app.add_middleware(
    CORSMiddleware,
    allow_origins=settings.CORS_ORIGINS,
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)

Step 4 — Rebuild the frontend

Vue bakes the new base URL into minified files at build time, so you must rebuild. If your server has low RAM, use the memory flag from the previous step.

cd /web_app/frontend
pnpm run build
NODE_OPTIONS="--max-old-space-size=2048" pnpm run build

Step 6 — Build the config block by block

At (151:29) the presenter shows the diagram of why Nginx is needed. You assemble the file in pieces so each part is clear. First, the upstream block names the backend socket:

upstream <your_project_name>_app_server {
    server unix:/web_app/backend/gunicorn.sock fail_timeout=0;
}

Then the server block listens for web traffic and the two location blocks route it. Here is the complete first version (security headers come later):

upstream <your_project_name>_app_server {
    server unix:/web_app/backend/gunicorn.sock fail_timeout=0;
}

server {
    listen 80;
    server_name <your_droplet_ip>;

    access_log /var/log/nginx/<your_project_name>-access.log;
    error_log /var/log/nginx/<your_project_name>-error.log;

    location / {
        root /web_app/frontend/dist;
        try_files $uri $uri/ /index.html;
    }

    location /api {
        proxy_pass http://<your_project_name>_app_server;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header Host $http_host;
        proxy_redirect off;
    }
}

Line by line

Line(s)CodeWhat it does & why
1upstream <your_project_name>_app_server {Defines a named backend group you can refer to below, instead of repeating the long socket path.
2server unix:/web_app/backend/gunicorn.sock fail_timeout=0;Points the group at the Unix socket Gunicorn created. fail_timeout=0 tells Nginx never to mark the backend as “down”, so it resumes the instant Supervisor restarts Gunicorn.
5–6server { / listen 80;Opens the main server block and listens on port 80, standard unencrypted HTTP (HTTPS comes in a later chapter).
7server_name <your_droplet_ip>;Responds to requests for this address. You replace the IP with your domain name once you have one.
9–10access_log ... / error_log ...Dedicated log files for this site. When something breaks, these tell you exactly what went wrong — you will use the error log to debug the 502 shortly.
12location / {Matches all normal page requests (anything not caught by a more specific block).
13root /web_app/frontend/dist;Tells Nginx the files live in your Vue build folder, which holds the finished HTML, CSS and JS.
14try_files $uri $uri/ /index.html;Tries the exact file, then a folder, and if neither exists returns index.html. This lets Vue Router handle the route instead of showing a 404 — essential for a single‑page app.
17location /api {Catches every URL starting with /api. Note: no trailing slash (see the warning below).
18proxy_pass http://<your_project_name>_app_server;Hands the request to the upstream group — that is, through the Unix socket to Gunicorn. This single line is what connects Nginx to your backend.
19proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;Passes the real client IP to FastAPI. Without it, every request would look like it came from Nginx itself.
20proxy_set_header Host $http_host;Forwards the original Host header so the backend knows which domain the user asked for.
21proxy_redirect off;Stops Nginx rewriting redirect URLs from FastAPI, which could otherwise leak an internal server name instead of your public domain.
Watch the trailing slashes. Use location /api, not location /api/: the slash can trigger a 301 redirect that drops the JSON body of POST requests, giving strange 405 or 422 errors. And never add a slash to the end of proxy_pass (..._app_server/;): Nginx would strip /api from the path, and your FastAPI routes that expect the /api prefix would all return 404.

Step 8 — Test, and understand the 502

Visit http://<your_droplet_ip> in a browser. The frontend loads, but at (174:09) API calls return a 502 Bad Gateway. This is expected, and worth understanding. Check the error log:

sudo cat /var/log/nginx/<your_project_name>-error.log
connect() to unix:/web_app/backend/gunicorn.sock failed (13: Permission denied)

Gunicorn created the socket as your user, but Nginx runs as a separate user called www-data, which has no permission to open your file. Static files work because Nginx can read the dist folder directly; the API fails because it needs the socket. The fix is to add www-data to your group and let the group traverse your folders.

sudo usermod -aG <your_username> www-data
getent group <your_username>
chmod g+x /web_app /web_app/backend
sudo systemctl reload nginx
Line(s)CodeWhat it does & why
1sudo usermod -aG <your_username> www-dataAdds the Nginx user www-data to your group. -aG means “append to this group” without removing its other groups. This grants group‑level access to the socket.
2getent group <your_username>Prints your group's members so you can confirm www-data now appears at the end.
3chmod g+x /web_app /web_app/backendGrants the group “execute” on these folders. On a directory, execute means “may pass through”; without it Nginx is blocked before it even reaches the socket.
4sudo systemctl reload nginxReloads Nginx so it picks up its new group membership. Refresh the browser and the 502 errors are gone.
What you should see

After the reload, refresh your site. The Vue frontend loads and API calls succeed — search bars and data pages work. Your reverse proxy is now serving both halves of the app.

Add security headers

At (181:52) the presenter makes the point: the firewall protects the server, but browsers have their own defences that only switch on if your server tells them to. You do that with HTTP response headers. At (182:38) he tests the baseline at SecurityHeaders.com — a fresh install scores an F.

New to HTTP headers? What a header is

Every HTTP response carries invisible metadata lines called headers, sent before the page content. Most describe the content (its type, length, cache rules). A security header instead instructs the browser to enable a protection — for example, “never load this page inside a frame” or “only run scripts from these domains”. The server adds them with Nginx's add_header directive.

Add these header lines inside the server block. First, transport and content protections:

    # HSTS (2 Years)
    add_header Strict-Transport-Security "max-age=63072000; includeSubDomains; preload" always;

    # CORP (Allow sharing)
    add_header Cross-Origin-Resource-Policy "cross-origin" always;

    # Anti-Clickjacking
    add_header X-Frame-Options "SAMEORIGIN" always;

    # Stop MIME sniffing
    add_header X-Content-Type-Options "nosniff" always;

    # Privacy
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;

    # Disable unused features
    add_header Permissions-Policy "camera=(), microphone=(), geolocation=(), payment=()" always;

Line by line: each security header

HeaderValueWhat it does & why
Strict-Transport-Securitymax-age=63072000; includeSubDomains; preloadHSTS. Forces the browser to use HTTPS for the next two years (63,072,000 seconds), including subdomains. It does nothing over plain HTTP today but secures the site the moment you add SSL. The always keyword sends the header even on error responses.
Cross-Origin-Resource-Policycross-originCORP. Controls whether other sites may load your resources (like images). cross-origin allows public assets to be shared; use same-origin to lock them to your site only.
X-Frame-OptionsSAMEORIGINPrevents clickjacking by stopping other sites putting your pages in a hidden <iframe>. SAMEORIGIN lets only your own domain frame your content.
X-Content-Type-OptionsnosniffForces the browser to trust the declared file type and not “sniff” it. Blocks an attack where a malicious script is disguised as an image.
Referrer-Policystrict-origin-when-cross-originA privacy shield. When users click links to other sites, it sends only your root domain, not the full URL path, protecting their browsing details.
Permissions-Policycamera=(), microphone=(), geolocation=(), payment=()A hardware lock. The empty () disables camera, microphone, geolocation and payment APIs, so injected code cannot reach your users' devices.

Craft a Content Security Policy

At (184:36) the presenter calls CSP the strongest defence against cross‑site scripting (XSS) — and the one that takes the most work. A CSP is a strict allow‑list: by default a browser runs any script a page asks for, but with a CSP it only loads scripts, styles, images and frames from the domains you name. Anything else is blocked.

You build a CSP iteratively. At (193:24) the presenter stresses there is no one‑size‑fits‑all policy: start by blocking everything, open your site, read the console errors, and relax the rules one by one until the site works with nothing extra allowed.

At (201:41) the presenter adds the finished CSP to Nginx. Open the config again and add this header inside the server block:

add_header Content-Security-Policy "default-src 'self'; font-src 'self' https://fonts.gstatic.com https://cdnjs.cloudflare.com; img-src 'self' data:; script-src 'self'; style-src 'self' 'unsafe-inline' https://cdnjs.cloudflare.com https://fonts.googleapis.com; connect-src 'self'; frame-src 'self'; upgrade-insecure-requests;" always;

Line by line: the CSP directives

DirectiveValueWhat it does & why
default-src'self'The fallback for any resource type not named below. 'self' means “only from my own domain”. Everything starts locked to your origin.
font-src'self' https://fonts.gstatic.com https://cdnjs.cloudflare.comWhere fonts may load from: your site, Google Fonts' file host, and the cdnjs CDN used for icon fonts.
img-src'self' data:Images from your domain, plus data: so inline base64/SVG images encoded in the HTML are allowed.
script-src'self'Scripts only from your own domain. This is the directive that stops injected third‑party scripts — the core XSS defence.
style-src'self' 'unsafe-inline' https://cdnjs.cloudflare.com https://fonts.googleapis.comStylesheets from your site and the two CDNs, plus 'unsafe-inline' to permit inline styles the app uses.
connect-src'self'Limits where JavaScript may send fetch/XHR requests to your own origin — which is exactly where your /api calls go.
frame-src'self'Only your own domain may be loaded in frames on your pages.
upgrade-insecure-requests(flag)Tells the browser to automatically rewrite any http:// request to https://, closing mixed‑content gaps once SSL is on.
Security note — 'unsafe-inline'

'unsafe-inline' in style-src is a deliberate trade‑off. It is acceptable when your inline styles never come from user input. But if your site has any field where users submit data, avoid it: an attacker who injects styles into your database could have them run in every visitor's browser. Prefer removing inline styles over allowing them.

sudo systemctl reload nginx

Recap
  • You prepared the frontend to use a relative API base URL, proxied /api in Vite for development, removed the now‑unneeded CORS middleware, and rebuilt.
  • You installed Nginx as a reverse proxy: location / serves the Vue dist files, and location /api uses proxy_pass to reach Gunicorn through the Unix socket.
  • You enabled the site with a symlink into sites-enabled, opened the firewall with Nginx Full, and fixed the 502 Bad Gateway by adding www-data to your group and granting group execute on the app folders.
  • You added seven security headers, including a Content Security Policy built iteratively, taking the site's security grade from F to A.
