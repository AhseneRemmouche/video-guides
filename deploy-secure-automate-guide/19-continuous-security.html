Continuous Security & Maintenance

Ban abusive IPs, manage disk space and log retention, and keep the production server healthy over time.

▶ Watch this part (612:00)

Your server is now observed (lesson 17) and load-tested (lesson 18). This final lesson turns that visibility into action: you will ban abusive IP addresses that your traffic reports expose, stop log files and caches from filling the disk, keep a full year of useful traffic history, and schedule a deep overnight security scan so the production system stays hardened long after launch day. Then we wrap up the whole course.

What "continuous security" means

A deployment is never "finished". New bots probe your server every hour, disks slowly fill, and new code can quietly re-introduce vulnerabilities. Continuous security is the habit of watching, cleaning, and re-scanning on a schedule instead of only once. In the video this is the last subchapter of Module 6 (at 613:08), and it closes three loose ends: blocking persistent attackers, managing disk and log retention, and automating a heavy security scan that is too slow to run on every commit.

Part 1 · Ban abusive IP addresses

Open your GoAccess dashboard and look at the Requested files (URLs) panel (at 582:31). You will see requests for paths like /wp-login.php or .env that do not exist on a FastAPI + Vue site. These come from bots scanning the internet for weak servers. Nginx drops them with a 404, but they still waste bandwidth and clutter your logs, so persistent offenders should be blocked completely (at 584:27).

New to bots and scanners? What they are and why they matter

Most "attacks" on a small site are not targeted. They are automated programs that crawl every IP address on the internet, requesting well-known vulnerable files (old WordPress logins, leaked .env secrets, admin panels). If your site ever leaks such a file, they grab it. Because your stack has none of those files, the scans fail — but one determined scanner can still send thousands of requests. Blocking it at the firewall stops the noise before it reaches your application.

Find the top offenders

Rather than reading thousands of log lines by hand, export the dashboard as JSON and let a short Python script rank the busiest IPs (at 585:37).

  1. Export today's GoAccess statistics into a raw data file instead of HTML.
  2. Create a small diagnostic script in your project root.
  3. Run it to print the top traffic sources with their share of all hits.
sudo goaccess /var/log/nginx/<your_domain>-access.log -o /web_app/goaccess.json --log-format=COMBINED

nano /web_app/find_bad_actors.py
import json
import sys

try:
    with open('/web_app/goaccess.json', 'r') as f:
        data = json.load(f)
except FileNotFoundError:
    print("Error: Could not find goaccess.json file.")
    sys.exit(1)

hosts = data.get('hosts', {}).get('data', [])

print(f"{'IP Address':<20} {'Total Hits':<15} {'Traffic Share':<15}")
print("-" * 50)

for host in hosts[:10]:
    ip = host.get('data')
    hits = host.get('hits', {}).get('count', 0)
    percent = host.get('hits', {}).get('percent', "0.00%")
    print(f"{ip:<20} {hits:<15} {percent:<15}")

print("-" * 50)
print("Review Checklist:")
print("Look for severe traffic imbalances (outliers). If the top IP has")
print("thousands of hits while others have fewer than 50, block it.")

Common mistakes
  • Do not ban blindly. The video warns (at 585:13) to look for extreme imbalances only. A list where the top IP has a few hundred hits and the rest have dozens is normal human traffic.
  • Banning your own IP by mistake locks you out of the website (not SSH, but still annoying). Double-check the address before you block it.

Block the attacker at the firewall

Once you have a clear outlier, drop it with UFW (at 588:26). This blocks the attacker at the network layer, so their packets never reach Nginx or your app. (This is the same firewall you configured in lesson 03, where Fail2Ban already auto-bans SSH brute-force attempts; here you add a manual rule for a web scanner.)

sudo ufw deny from 45.148.10.246 to any

Part 2 · Manage disk usage

Load tests, backups, and software caches all write files that grow quietly. If a Linux disk ever hits 100% full, services can no longer write and your database can crash. Before deleting anything, find where the space is going (at 605:17) with NCDU, an interactive disk-usage browser that is far easier than raw du -h.

sudo apt install ncdu -y
sudo ncdu /
Line(s)CodeWhat it does & why
1sudo apt install ncdu -yInstalls NCDU (NCurses Disk Usage). -y auto-confirms the install prompt.
2sudo ncdu /Scans from the root directory / (everything). sudo lets it read every folder. The result is a tree sorted by size.

Move with the arrow keys, press Enter to open a folder, ? for help, and d to delete a highlighted item you are sure about (for example an old pip cache). Press q to quit (at 607:40).

What you should see

A list topped by your biggest folders — typically system libraries, your Python environment, and your web app. In the video the droplet shows about 6.2 GB used (at 606:30). Do not delete system or runtime folders; only remove caches and old backups you recognise.

Part 3 · Log retention policy

Two kinds of logs pull in opposite directions. System logs from the systemd-journald daemon can grow to 10% of your disk by default — too much on a small server, so you cap them. Nginx access logs, by contrast, are valuable fuel for your traffic charts, so you keep them longer. Setting both limits is your log retention policy (at 608:02).

Cap the systemd journal

sudo nano /etc/systemd/journald.conf

Find the line #SystemMaxUse=, remove the #, and set a hard limit:

SystemMaxUse=100M
sudo systemctl restart systemd-journald
Line(s)CodeWhat it does & why
1SystemMaxUse=100MTells the journal daemon to use at most 100 MB on disk. Once reached, it deletes the oldest entries first. Removing the leading # is what activates the setting.
1sudo systemctl restart systemd-journaldRestarts the logging service so it re-reads the config and enforces the new limit immediately.

Keep a year of Nginx logs

By default Ubuntu rotates Nginx logs daily but deletes them after 14 days, so you lose your traffic history every two weeks (at 609:13). Raise the retention to 365 days.

sudo nano /etc/logrotate.d/nginx

Find the line rotate 14 and change it to 365:

/var/log/nginx/*.log {
        daily
        missingok
        rotate 365
        compress
        delaycompress
        notifempty
        create 0640 www-data adm
        sharedscripts
        # ...
}
Line(s)CodeWhat it does & why
1/var/log/nginx/*.log {The policy applies to every Nginx log file.
2dailyRotate (start a fresh file) once a day.
3missingokDo not error if a log file is temporarily absent.
4rotate 365Keep 365 old daily files before deleting — a full year of history. This is the one value you change.
5–6compress / delaycompressGzip old logs to save space, but wait one cycle so yesterday's file stays readable for tools.
7notifemptySkip rotation when the log is empty.
8create 0640 www-data admAfter rotating, create the new log file with safe permissions and the right owner/group.
9sharedscriptsRun post-rotate scripts once for all matched files, not once per file.
New to log rotation? Why it exists

A log file that is never rotated grows forever and eventually fills the disk. "Rotation" means: once a day, rename the current log, start a fresh empty one, compress the old ones, and delete files older than the limit. logrotate does this automatically. Your only choice is how many days of history to keep — small for noisy system logs, large for the traffic logs you actually analyse.

Common mistakes

Keeping 365 days of Nginx logs on a very small disk, or on a site with huge traffic, can itself fill the disk. The video (at 609:38) says to confirm you have room first. If space is tight, choose a smaller number like 90.

Automate a monthly cleanup

To keep the server tidy without remembering to do it, write a small script and run it on a schedule with cron (at 610:23).

sudo nano /usr/local/bin/monthly_cleanup.sh
#!/bin/bash
# Enforce immediate termination if any step encounters an unhandled error
set -e

echo "Starting automated system cleanup routine"

apt-get clean
apt-get autoremove -y

journalctl --vacuum-time=2d

rm -rf /home/*/.cache/pip
rm -rf /home/*/.local/share/pnpm/store

echo "System cleanup completed successfully."

sudo crontab -e

Add this line at the bottom of the cron file:

0 3 1 * * /usr/local/bin/monthly_cleanup.sh >> /var/log/cleanup.log 2>&1
Line(s)CodeWhat it does & why
1chmod +x …monthly_cleanup.shMarks the script as executable so cron can run it.

1/usr/local/bin/monthly_cleanup.shThe command to run at that time.
1>> /var/log/cleanup.log 2>&1Appends normal output to a log file, and 2>&1 sends error output to the same place, so you can check what happened.
New to cron? How a schedule line works

Cron runs commands at fixed times. Each line starts with five time fields — minute, hour, day-of-month, month, day-of-week — followed by the command. A * means "every". So 0 3 1 * * reads left to right as "at 3:00, on the 1st, every month, regardless of weekday". You edit the schedule with crontab -e; use sudo for the root user's crontab.

Part 4 · Ongoing hardening: a nightly deep security scan

In Module 5 you practised shifting security left — a fast, lightweight OWASP ZAP API check ran on every pull request. A full Dynamic Application Security Testing (DAST) scan, which crawls the whole live front end and fuzzes every input, is far too slow for that (6–30 minutes). The fix is a separate scheduled workflow that boots the entire stack overnight and runs the heavy scan (at 613:08, 614:40).

New to DAST? How it differs from the earlier scans

Earlier scans were static (SAST, reading your source code) or checked only the API definition. DAST is dynamic: it treats your running site like a real attacker would, clicking links, submitting forms, and probing for cross-site scripting, SQL injection and broken access control. Because it needs the whole app running — Meilisearch, FastAPI and the built Vue front end — and tries thousands of payloads, it is thorough but slow, which is exactly why it runs on a schedule rather than on every commit.

Create the workflow file at .github/workflows/daily-deep-security-scan.yml (at 616:40). This runs via GitHub Actions:

name: Daily deep security scan (DAST)

on:
  schedule:
    - cron: "0 6 * * *"
  workflow_dispatch:

jobs:
  deep_scan:
    name: Full OWASP ZAP scan
    runs-on: ubuntu-latest
    timeout-minutes: 30
    env:
      MEILISEARCH_MASTER_KEY: "aStrongMasterKeyForTestingPurposes"
      MEILISEARCH_URL: "http://localhost:7700"
      MEILISEARCH_INDEX_NAME: "articles_test"
      ENVIRONMENT: "development"
      MEILISEARCH_DOWNLOAD_MAX_RETRIES: "3"
      MEILISEARCH_DOWNLOAD_RETRY_DELAY: "5"
    steps:
      - name: Check out repository
        uses: actions/checkout@v6

      - name: Set up Python
        uses: actions/setup-python@v6
        with:
          python-version: "3.13"
          cache: "pip"

      - name: Install backend dependencies
        working-directory: ./backend
        run: pip install -r requirements.txt

      - name: Download Meilisearch binary
        working-directory: ./backend
        run: |
          MAX_RETRIES="${MEILISEARCH_DOWNLOAD_MAX_RETRIES}"
          RETRY_DELAY="${MEILISEARCH_DOWNLOAD_RETRY_DELAY}"
          for i in $(seq 1 $MAX_RETRIES); do
            echo "Attempt $i of $MAX_RETRIES to download Meilisearch..."
            if curl -L https://install.meilisearch.com | sh; then
              echo "Meilisearch downloaded successfully!"
              chmod +x meilisearch
              break
            else
              if [ $i -lt $MAX_RETRIES ]; then
                echo "Download failed. Retrying in $RETRY_DELAY seconds..."
                sleep $RETRY_DELAY
              else
                echo "Download failed after $MAX_RETRIES attempts"
                exit 1
              fi
            fi
          done

      - name: Start Meilisearch
        working-directory: ./backend
        run: |
          ./meilisearch --master-key="${MEILISEARCH_MASTER_KEY}" &
          echo "Waiting for Meilisearch to start..."
          for i in {1..30}; do
            if curl -s http://localhost:7700/health | grep -q "available"; then
              echo "Meilisearch is ready!"
              break
            fi
            echo "Attempt $i: Meilisearch not ready yet..."
            sleep 1
          done
          if ! curl -s http://localhost:7700/health | grep -q "available"; then
            echo "Meilisearch failed to start after 30 attempts"
            exit 1
          fi

      - name: Start backend server
        working-directory: ./backend
        run: |
          uvicorn main:app --host 0.0.0.0 --port 8000 &
          echo "Waiting for backend to start..."
          for i in {1..30}; do
            if curl -s http://localhost:8000/api/health | grep -q "ok"; then
              echo "Backend is ready!"
              break
            fi
            echo "Attempt $i: Backend not ready yet..."
            sleep 1
          done
          if ! curl -s http://localhost:8000/api/health | grep -q "ok"; then
            echo "Backend failed to start after 30 attempts"
            exit 1
          fi
        env:
          MEILISEARCH_URL: ${{ env.MEILISEARCH_URL }}
          MEILISEARCH_MASTER_KEY: ${{ env.MEILISEARCH_MASTER_KEY }}
          MEILISEARCH_INDEX_NAME: ${{ env.MEILISEARCH_INDEX_NAME }}
          ENVIRONMENT: ${{ env.ENVIRONMENT }}

      - name: Seed test data
        working-directory: ./backend
        run: python -m tests.test_data

      - name: Set up pnpm
        uses: pnpm/action-setup@v4
        with:
          version: "11"

      - name: Set up Node.js
        uses: actions/setup-node@v6
        with:
          node-version: "22"
          cache: "pnpm"
          cache-dependency-path: frontend/pnpm-lock.yaml

      - name: Install frontend dependencies
        working-directory: ./frontend
        run: pnpm install

      - name: Build frontend
        working-directory: ./frontend
        run: pnpm build

      - name: Start frontend (Production preview)
        working-directory: ./frontend
        run: |
          nohup pnpm preview --host &
          echo "Waiting for frontend to start..."
          for i in {1..30}; do
            if curl -s http://localhost:8080/ | grep -q "<title>Imad Saddik</title>"; then
              echo "Frontend is ready!"
              break
            fi
            echo "Attempt $i: Frontend not ready yet..."
            sleep 1
          done
          if ! curl -s http://localhost:8080/ | grep -q "<title>Imad Saddik</title>"; then
            echo "Frontend failed to start after 30 attempts"
            exit 1
          fi

      - name: Run ZAP full scan
        uses: zaproxy/action-full-scan@v0.13.0
        with:
          target: "http://localhost:8080"
          rules_file_name: ".github/zap-rules.tsv"
          allow_issue_writing: false
          fail_action: true

What you should see

After merging and triggering the workflow manually, a single job runs through installing Python, downloading and seeding Meilisearch, starting the backend, building and previewing the front end, and finally the ZAP scan. In the video it passes in about 6 minutes (at 624:07) — roughly three times the lightweight PR scan, which is why it stays off the commit path.

Security note

The master key in the workflow (aStrongMasterKeyForTestingPurposes) is a throwaway value for an ephemeral test runner only. Never put your real production Meilisearch master key, or any live secret, in a workflow file — use GitHub encrypted secrets for anything that matters.

Recap
  • Turn GoAccess data into action: export JSON, rank IPs with find_bad_actors.py, and sudo ufw deny only the clear outliers.

  • Schedule a heavy OWASP ZAP full scan nightly with GitHub Actions — too slow for every commit, but essential for catching drift.
