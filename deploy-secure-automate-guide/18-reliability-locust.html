Reliability: Load Testing with Locust

Simulate concurrent users with Locust to find how much traffic your server can handle before it struggles.

▶ Watch this part (590:25)

Watching a quiet, idle server over SSH tells you it works, but not how it behaves when real users arrive all at once. You do not want to discover that your app crashes under pressure on the day it goes viral. In this lesson you will deliberately stress your live backend from your laptop using Locust, read the numbers it reports, and find the point where your server starts to struggle. Then you will add the long-term safeguards that keep a small server reliable: disk analysis, log retention, and an automated cleanup routine.

Load testing means simulating many users hitting your site at the same time so you can measure how it copes before your real visitors do. Locust is an open-source tool, written in Python, that lets you describe a user's behaviour in a small script and then run hundreds of copies of that user at once (at 590:25).

What the presenter explains

You write a Python script that defines what a user does: browse the homepage, pause a few seconds, then fire a heavy search query (at 591:40). Locust spawns many such users and reports two key numbers in real time: requests per second (how much work your server is doing) and response time in milliseconds (how slow each request feels). You raise the number of users until failures appear, which tells you your capacity. Crucially, you always run the test from your own computer, never from the server, because a test running on the server would steal the very CPU you are trying to measure.

New to load testing? Why simulate users at all

When you click around your own site, you are one user making one request at a time. Real traffic is dozens or hundreds of people acting at once, competing for the same CPU, memory, and database. Load testing recreates that crowd on demand so you can see the breaking point in a safe 10-minute test instead of during a real traffic surge. The output is a capacity number you can trust, like "my server handles about 16 requests per second before it strains".

Install Locust on your laptop

Run it from your laptop, not the server

A large load test consumes a lot of CPU. Running it on the production server would compete with your app and distort every measurement. Activate your local Python virtual environment first, then install Locust there.

pip install locust

Write the test scenario

Create a file named locustfile.py inside your local project at backend/tests/load/. It describes a realistic mix of user actions, weighted so the heaviest operation (search) runs most often.

import random


from locust import FastHttpUser, between, task

class WebsiteUser(FastHttpUser):
    # Simulate a realistic human delay between tasks (1 to 5 seconds)
    wait_time = between(1, 5)

    search_queries = ["inkscape", "python", "meilisearch", "astronomy", "elasticsearch"]
    article_types = ["blog-post", "course-post", "astronomy-post"]
    sort_fields = ["date", "popularity", "engagement", "claps"]
    sort_orders = ["asc", "desc"]

    @task(1)
    def get_article_claps_count(self):
        article_name = "ElasticsearchChangeHeapSize"
        endpoint = f"/api/articles/{article_name}/claps-count"
        self.client.get(endpoint, name="/articles/[name]/claps-count")

    @task(4)
    def view_homepage(self):
        self.client.get("/", name="/")

    @task(7)
    def get_latest_articles(self):
        endpoint = "/api/articles/latest"
        article_type = random.choice(self.article_types)
        payload = {"articleType": article_type}
        self.client.post(endpoint, json=payload, name=endpoint)

    @task(7)
    def get_recommendations(self):
        endpoint = "/api/articles/recommendations"
        payload = {
            "articleType": "blog-post",
            "documentNameToIgnore": "ElasticsearchChangeHeapSize",
            "documentTags": ["elasticsearch"],
        }
        self.client.post(endpoint, json=payload, name=endpoint)

    @task(10)
    def search_articles(self):
        endpoint = "/api/search"
        query = random.choice(self.search_queries)
        article_type = random.choice(self.article_types)
        sort_field = random.choice(self.sort_fields)
        sort_order = random.choice(self.sort_orders)

        payload = {
            "query": query,
            "articleType": article_type,
            "size": 10,
            "sortBy": {"field": sort_field, "order": sort_order},
        }
        self.client.post(endpoint, json=payload, name=endpoint)

Why FastHttpUser instead of HttpUser?

Locust offers two base classes. The standard HttpUser uses Python's familiar requests library. FastHttpUser uses a faster, C-based HTTP client (geventhttpclient) that needs far less CPU on your laptop. That lets one machine simulate many more users — up to 5 to 6 times as many on normal laptop hardware — which is why the script inherits from it.

Read the results

While your laptop drives traffic, watch two places at once (at 598:10):

  • The Locust dashboard — track RPS and the Failures column. 502 Bad Gateway errors mean Nginx is timing out because your FastAPI/Gunicorn queue is full.
  • btop on the server — in a separate SSH terminal, watch your CPU cores and swap. If CPU locks at 100%, your Gunicorn worker cluster is saturated.
Security note

Do not run load tests continuously for hours against a cloud instance. Your provider may read a massive, sustained traffic spike as an attack or an outgoing denial-of-service event and flag or suspend your account. Run the test for 5 to 10 minutes, gather your numbers, then click Stop.

Understand the numbers

After about 5 minutes against a minimal cloud instance, the summary looks like this:

Type     Name                            # reqs      # fails    Avg (ms)   Max (ms)    RPS
--------------------------------------------------------------------------------------------
GET      /                                 1124           0         64        210   3.20
POST     /api/articles/latest              1945           0         78        340   5.50
POST     /api/search                       2499           0         72       1100   7.10
--------------------------------------------------------------------------------------------
Total                                      5568           0         71       1100  15.80

The server sustained nearly 16 RPS with zero failures — roughly 1.3 million requests per day if kept up. Average response time stayed around 75 ms. The occasional spike to 1100 ms on /api/search is normal tail latency: brief, rare slow requests caused by background work like log writes or garbage collection. As long as your median and 95th-percentile times stay low, the site feels fast.

New to RPS, throughput and latency?

RPS (requests per second) and throughput both describe how much work your server gets done per unit of time — the higher, the more traffic you can serve. Latency is the delay for a single request, measured in milliseconds — the lower, the snappier the site feels. They trade off: as you push throughput up, latency eventually rises because requests start queueing. The goal is the highest RPS you can reach while latency stays acceptable.

Keep the server reliable over time

Load tests create logs, and logs, backups, and caches grow quietly until they fill the disk. If a Linux system hits 100% disk usage, services can no longer write files and your database can crash (at 605:30). Three safeguards prevent this.

Find big directories with NCDU

sudo apt install ncdu -y
sudo ncdu /

NCDU scans from the root directory and shows an interactive file tree sorted by size. Press Enter to open a folder, ? for help, and d to delete a highlighted file you no longer need (such as an old manual backup).

Cap the systemd journal

By default Ubuntu lets system logs use up to 10% of the disk, which can be 1 GB or more. Pin it to 100 MB instead.

sudo nano /etc/systemd/journald.conf

Find the line #SystemMaxUse=, remove the #, and set the value:

SystemMaxUse=100M
sudo systemctl restart systemd-journald

Keep a year of Nginx logs

By contrast, your Nginx access logs feed your GoAccess traffic charts, so you want to keep them. Ubuntu deletes them after only 14 days; change that to 365.

sudo nano /etc/logrotate.d/nginx

Find rotate 14 and change it to rotate 365:

/var/log/nginx/*.log {
        daily
        missingok
        rotate 365
        compress
        delaycompress
        notifempty
        create 0640 www-data adm
        sharedscripts
        # ...
}

Line by line

Line(s)CodeWhat it does & why
1/var/log/nginx/*.log {The rule applies to every .log file in the Nginx log folder.

9sharedscriptsRun any post-rotate script once for all matched files, not once per file.

Automate monthly cleanup

Finally, a scheduled script flushes stale caches and packages so you never have to remember.

sudo nano /usr/local/bin/monthly_cleanup.sh
#!/bin/bash
# Enforce immediate termination if any step encounters an unhandled error
set -e

echo "Starting automated system cleanup routine"

apt-get clean
apt-get autoremove -y

journalctl --vacuum-time=2d

rm -rf /home/*/.cache/pip
rm -rf /home/*/.local/share/pnpm/store

echo "System cleanup completed successfully."

sudo chmod +x /usr/local/bin/monthly_cleanup.sh
sudo crontab -e

Add this line at the bottom:

0 3 1 * * /usr/local/bin/monthly_cleanup.sh >> /var/log/cleanup.log 2>&1

What you should see

After the test, the Locust summary shows a steady RPS with 0 failures and low average response time. On the server, disk stays well under full, system logs are capped, and a year of Nginx logs is archived for GoAccess. Each month, /var/log/cleanup.log gains a fresh "System cleanup completed successfully." line.

Common mistakes
  • Running locust from the wrong folder, so it cannot find locustfile.py. Change into backend/tests/load/ first.
  • Pointing the Host field at localhost instead of your production domain, so you only test your laptop.
  • Capping the Nginx logs the same way as system logs. Keep them for 365 days — they are your traffic history, not noise.
  • Leaving a load test running for hours and tripping your provider's abuse detection.
Recap
  • Load testing simulates a crowd so you learn your capacity before real users do — always from your laptop, never the server.
  • A Locust locustfile.py describes weighted user tasks; FastHttpUser lets one laptop generate far more users.
  • Read RPS and failures in Locust, and CPU and swap in btop, together: 502 errors or pinned CPU mark your limit.
  • Tail latency (rare p95 spikes) is normal; judge health by the median and 95th percentile.
  • Protect the disk long-term: find big files with NCDU, cap the journal at 100 MB, keep Nginx logs 365 days, and run a monthly cleanup script via cron.
