Prompt Claude for a Three.js scene

How to ask Claude (in Co-work mode) for a Three.js or Remotion 3D scene, and what to include so it runs first time.

Extension - our own code, rendered to a real MP4

You have now read a full Three.js scene (Step 12) and its Remotion version (Step 13). You do not have to write the next one from scratch. This step shows how to ask Claude to generate a 3D scene for you — and, just as important, what to put in the prompt so the result actually drops into the project and records cleanly. This page is an extension; the video only prompts for the finished AI video, never for code.

Part 1 taught the heart of this workflow: a good prompt is specific. The two prompts in the video each named the audience, the topic, the tool and the exact output wanted. We reuse that same style here, only now the output is code — a Three.js or @remotion/three scene.

New here? What "prompting for code" means

Claude can write code, not just prose. In Co-work mode — the same mode the video used — you describe what you want and Claude produces files you can copy into your project. The skill is the same as in Part 1: be precise. Vague prompts give generic results; a prompt that names the library, the version, the shapes, the timeline and the output format gives code that fits your project with little editing. Remember too that language models are non-deterministic: ask twice and you get two different scenes, so run again if the first is not what you pictured.

What to specify

Think of the prompt as a short brief. The more of these you pin down, the closer the first draft lands:

  1. Library and version. Say Three.js for a standalone page, or @remotion/three when it must live in Remotion. Name the versions you use (here three 0.182.0 and remotion 4.0.420) so the code matches your installed packages.
  2. Primitives or models. Ask for built-in primitives (box, sphere, cylinder, cone) if you want zero asset files — that is how our airplane is built. Only ask for loaded 3D models if you have files to load.
  3. The timeline and voice-over to sync to. Tell Claude the length and what happens when, so the motion matches the narration. Ours is a 37.3-second voice-over with nine lines; point Claude at your timeline.
  4. Output as a Remotion composition. If it must render to video, ask for a component registered as a composition (like Explainer3D in Step 13), not a loose HTML page.
  5. Deterministic animation from the frame, not the wall clock. Spell this out: drive every value from useCurrentFrame, never from Date.now() or performance.now(). This one line is what keeps the render repeatable.

Example prompts

Here is a prompt for a standalone Three.js page, in the same plain, specific style as Part 1:

Write one standalone HTML file that uses Three.js version 0.182.0, loaded
from a CDN with an import map (no build step). Build a cartoon airplane for
a kids' explainer about how airplanes fly. Use only primitives: a cylinder
fuselage, a cone nose, and flat boxes for the wings, tail and fin. Group the
parts so the plane moves as one. Add a sky-blue background, an ambient light
and a directional "sun", and a few clouds made of spheres. Animate the plane
drifting across while gently bobbing and banking. Also support a ?t=SECONDS
URL that freezes a single frame instead of animating.

And here is one for a version that lives inside Remotion and records to video:

Turn that airplane scene into a Remotion composition using @remotion/three
(remotion 4.0.420). Put it in src/ThreeExplainer.tsx and register it as a
composition named Explainer3D. Use ThreeCanvas, not a plain react-three-fiber
Canvas. Drive all motion from useCurrentFrame and useVideoConfig (never from
Date.now or performance.now) so each frame is deterministic. Match my
voice-over timeline in timeline.json: it is 37.3 seconds, 30 fps, nine lines.
Add the voice-over with an Audio tag pointing at public/voiceover.mp3. Keep
the same primitives, lights and camera as the standalone page.
Why name the frame, not the clock?

A browser animation usually reads the real time that has passed and moves things accordingly. That is fine on screen but bad for recording: the renderer draws frames one at a time, and real time does not pace itself to match. If the scene is built from useCurrentFrame — a fixed number per frame — the picture is a pure function of that number, so frame 300 is always the same. Asking for this in the prompt is the difference between a video that plays smoothly and one that stutters or drifts. Step 13 shows exactly what the frame-driven version looks like.

What you should see. A specific brief gives you code close to what Steps 12 and 13 contain: a scene built from primitives, grouped, lit, and — for the Remotion version — animated from the frame and registered as a composition. Read it, paste the file into your project, and tweak numbers (colours, sizes, speeds) by hand. Treat Claude's first draft as a strong starting point, not a finished product.
Common mistakes.
  • Leaving out the version. Without "three 0.182.0" or "remotion 4.0.420" you may get code for an older API that does not match your installed packages.
  • Not saying "composition". Ask only for "a Three.js scene" and you may get a standalone HTML page that cannot render to video. Say you want a Remotion composition.
  • Forgetting the determinism line. If you do not ask for frame-driven animation, Claude may reach for Date.now(), and the render will drift.
  • Pasting without reading. Because output is non-deterministic, always read the code against Steps 12–13 before trusting it. Run the prompt again if the scene is off.
Recap
  • You can prompt Claude in Co-work mode to write a Three.js or @remotion/three scene, using Part 1's "be specific" style.
  • Name five things: library and version, primitives vs models, the timeline and voice-over to sync to, output as a Remotion composition, and deterministic animation from the frame.
  • The determinism line (frame, not wall clock) is the one that keeps the render clean.
  • Output is non-deterministic, so read the result against Steps 12–13, paste it in, and adjust by hand — then render it in Step 15.
