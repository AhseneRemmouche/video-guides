How Data Flows Through the App

From a dropdown click to a rendered card: state, query keys, fetch, Zod, the cache, Suspense and re-renders.

You pick "London" in the dropdown, and a moment later every card shows London's weather. Between those two moments a lot happens: a piece of state changes, React re-renders, a geocoding request turns the name into coordinates, four cards ask TanStack Query for the same data, a fetch goes out, Zod checks the answer, and Suspense swaps skeletons for real cards. This page follows that one click from start to finish.

Read it alongside step 06 (useQuery), step 14 (geocoding) and step 19 (Suspense). Code references are to the repo's final files (src/App.tsx, src/api.ts, the cards in src/components/cards/). The request orders and error messages quoted here were recorded in a real browser running the production build with test data (see How the code was verified). Where something is reasoned from the code instead, the text says so.

The cast: who holds what

Only one component owns the data that drives everything: App. It keeps four pieces of state with useState, and passes what each child needs down as props. The children never talk to each other. When the dropdown wants a new city, it calls the setLocation function it was handed.

The whole journey at a glance

Here is the click on "London", message by message. Time flows down. The numbers match the stops described in the sections below.

Stop 1: the click changes state in App

The dropdown is a shadcn Select. When you choose a city, its onValueChange calls setLocation(value), the setter from this line in App.tsx:

const [coordinates, setCoords] = useState<Coords>({ lat: 50, lon: 45 })
const [location, setLocation] = useState("Tokyo")
const [mapType, setMapType] = useState("clouds_new")
const [isSidePanelOpen, setIsSidePanelOpen] = useState(false)

Calling a setter does two things: it stores the new value, and it tells React to re-render App. Re-rendering means React calls the App function again from the top. This time useState("Tokyo") ignores its starting value and returns "London". Every child App returns is rendered again too, with whatever new props it now gets.

Note the two location-like states. location is the city name (or the word "custom"). coordinates holds the last place you clicked on the map; its starting value { lat: 50, lon: 45 } is only used for those "custom" clicks.

New to re-rendering? What it is and why it matters

A React component is a function that returns a description of the screen. React calls it, compares the result with what's on the page, and changes only the differences. A component runs again ("re-renders") when its own state changes, when its parent re-renders, or when something it subscribes to (a context, a query) changes.

Two consequences matter on this page. First, every local variable in the component is recalculated on each render, which is how coords stays in sync without being state. Second, rendering should only calculate. Anything that reaches outside React (a network request you start by hand, a map listener) belongs in an effect or in a library like TanStack Query that handles it for you.

Stop 2: the geocode query

The OpenWeather weather APIs want coordinates, not names. So right after its state, App asks TanStack Query for the coordinates of the current city:

const { data: geocodeData } = useQuery({
  queryKey: ["geocode", location],
  queryFn: () => getGeocode(location),
})

The query key ["geocode", "London"] is the name of this piece of data. TanStack Query looks it up in its cache. If it has never seen that key, it calls the query function, getGeocode("London"), and meanwhile returns data: undefined. When the answer arrives, it stores it under the key and re-renders App, and this time geocodeData is an array like [{ name: "London", lat: ..., lon: ..., country: "GB", ... }]. If you switch back to a city you've already picked, the data is in the cache and comes back on the very first render, with no waiting.

This is plain useQuery, not the Suspense version: App must keep rendering the header and dropdown while the city is being looked up, so it can't pause.

Stop 3: deriving coords

coords, the value every card and the map receive, is not state. It's a plain variable recalculated on every render of App:

const coords =
  location === "custom"
    ? coordinates
    : { lat: geocodeData?.[0].lat ?? 0, lon: geocodeData?.[0].lon ?? 0 }

Deriving it like this is good React practice: storing it in a second useState would mean keeping two copies in sync by hand. The question is what to do while there is no answer yet. The repo falls back to 0 with ??, and that has consequences.

The "no" branch hides three different situations, and the repo handles each one badly:

  • Still loading. geocodeData is undefined, so coords becomes { lat: 0, lon: 0 }, a point in the Gulf of Guinea. The cards immediately ask for that point's weather (next section).
  • Found nothing. OpenWeather answers an unknown name with an empty array []. Then geocodeData?.[0] is undefined, and .lat on it throws TypeError: Cannot read properties of undefined (reading 'lat'). The ?. only guards geocodeData itself, not the [0] after it. The whole page goes blank (verified with a mocked []).
  • Failed. If the geocode request throws, for example because the answer has no local_names (required by the repo's GeocodeSchema, but missing for many real places), the query ends in an error and App never reads it. The app then silently shows the weather for 0, 0 while the dropdown still says the city (verified).

Step 25 makes coords null until a place is known, renders skeletons instead of the cards while it is null, makes local_names optional, and shows a message for the other two cases:

Why the repo asks for latitude 0, longitude 0 first

In the browser test of the repo, the very first page load sent these requests, in this order: One Call for 0, 0; Air Pollution for 0, 0; geocode Tokyo; One Call for Tokyo (35.68, 139.69); Air Pollution for Tokyo. The presenter notices the symptom at about 2:28:00 in step 15 ("it flickers to looks like the middle of the ocean first") and first puts it down to the key approach used for the map. At about 2:30:40 they trace it to the ?? 0 fallback while the city is still loading and leave the fix for later; it stays in the final code, and step 25 fixes it.

Why do the 0, 0 requests even leave before the geocode request? Because the two hooks start their fetches at different moments:

The same flicker on every city change (reasoned from the code). The browser test recorded the first load. Reading the code, the same thing happens each time you pick a city you haven't picked before: the new key ["geocode", "London"] starts with no data, so coords drops back to 0, 0 for a moment. If the 0, 0 weather is still in the cache from the first load (unused entries are kept for 5 minutes), the cards can show the ocean's weather for an instant before London's arrives. Step 25's null fixes this too.

Stop 4: query keys and the shared cache

Each of the four weather cards calls its own hook, with the same key:

const { data } = useSuspenseQuery({
  queryKey: ["weather", coords],
  queryFn: () => getWeather({ lat: coords.lat, lon: coords.lon }),
})

Four components, one request. TanStack Query turns the key into a string (a "hash") and keeps one cache entry per hash. The first card to ask starts the fetch; the other three see that a fetch for the same key is already running and simply wait for it. When it finishes, all four get the same data. Objects inside a key are compared by content, with their properties in sorted order, so the brand-new coords object App creates on every render still matches the existing entry as long as lat and lon are the same.

Two settings decide how long an entry lives and when it is refreshed:

  • Stale time (default 0) is how long data counts as fresh. Stale data is still shown, but TanStack Query refetches it in the background, for instance when a component using it appears again or when you come back to the browser tab. Step 26 sets it to 5 minutes, so switching between two cities doesn't refetch either one.
  • gcTime (default 5 minutes) is how long an entry no component is using stays in memory before it is thrown away.

One more detail: when you click the map, location becomes "custom", so the geocode key becomes ["geocode", "custom"] and the app looks up a city called "custom". The answer is never used, because coords takes the coordinates branch. The browser test confirmed it: after a click the app sent onecall, air_pollution and geo/1.0/direct?q=custom. Step 25 adds enabled: location !== "custom" to that useQuery, and the same test then shows only the two weather requests.

Stop 5: fetch, JSON, Zod

When a key isn't cached, TanStack Query calls its query function. All three functions in src/api.ts follow the same three lines:

const res = await fetch(
  `https://api.openweathermap.org/data/3.0/onecall?lat=${lat}&lon=${lon}&units=imperial&exclude=minutely,alerts&appid=${API_KEY}`
)
const data = await res.json()
return weatherSchema.parse(data)

fetch sends the request and waits for the response. res.json() reads the body as JSON. Then weatherSchema.parse(data) checks every field against the schema: if the data matches, it is returned with a full TypeScript type, so the cards can write data.current.temp without guessing. If not, parse throws a ZodError, the promise rejects, and TanStack Query treats the query as failed.

Stop 6: Suspense and the skeletons

Between "fetch started" and "data arrived", what does a card show? The cards use useSuspenseQuery, which never returns empty data. If the data isn't in the cache, the hook suspends the component: it throws the pending promise, and React stops rendering that card. The nearest <Suspense> above it catches this and shows its fallback instead, in this app a skeleton shaped like the card:

<Suspense fallback={<CurrentSkeleton />}>
  <CurrentWeather coords={coords} />
</Suspense>

The side panel works the same way with its own Suspense and SidePanelSkeleton around the AirPollution part (step 22). App itself is not inside any Suspense, which is another reason it uses plain useQuery: if App suspended, there would be nothing above it to show a fallback.

Stop 7: what re-renders, frame by frame

Put together, here is what you see on screen in the fixed app (after step 25) when you change the city:

  1. Render 1 (the click). setLocation("London") re-renders App. The geocode key changes, its data is undefined, so coords is the fallback. Every child re-renders with the new props.
  2. Render 2 (geocode arrives). TanStack Query re-renders App because the query it subscribed to has data. coords now holds London's latitude and longitude. The cards get a new key, find nothing cached, and suspend.
  3. Render 3 (weather arrives). The cache entry is filled and React renders the suspended cards again. This time useSuspenseQuery returns the data and the real cards replace the skeletons. The map receives the same coords and pans there (step 15).

When something goes wrong

So far everything worked. Now imagine the API refuses: the key is wrong, or your OpenWeather account doesn't have the separate "One Call by Call" subscription that One Call 3.0 requires. OpenWeather answers with status 401 and a JSON body containing a message. In the repo, this happens next (all verified in the browser):

  1. Zod gets the error body. The repo doesn't check res.ok, so the error JSON is parsed as weather and fails with a ZodError about "path": ["lat"], "expected number, received undefined". True, but it hides the real reason.
  2. TanStack Query retries. The default is 3 retries with growing pauses, for every failing key. With an invalid key the test recorded 28 requests in 20 seconds. Retrying can't fix a wrong key.
  3. The error is thrown during render. After the last retry, useSuspenseQuery throws the error out of the card. Nothing catches it, because the repo has no error boundary.
  4. The page goes blank. When an error escapes all components, React removes the whole app from the page. The map, the dropdown and the side panel vanish with the broken card.

An error boundary is to errors what Suspense is to waiting: a component placed above others that catches what they throw and shows a fallback. Step 26 combines it with TanStack Query's QueryErrorResetBoundary, so the "Try again" button clears the failed query and fetches it again, instead of immediately re-throwing the cached error.

Common mistakes when you change this flow

  • Leaving something out of the query key. If getWeather started using the map type or the units, but the key stayed ["weather", coords], the cache would hand out data for the old setting. Everything the query function uses belongs in the key.
  • Copying query data into useState. Then you have two copies that drift apart. Read data from the hook wherever you need it; the shared cache makes this cheap.
  • Using useSuspenseQuery without a Suspense above it. React then suspends the nearest boundary it can find, possibly the whole page. Each suspending component needs a <Suspense> close above it.
  • Using a fake fallback value for "not loaded yet". ?? 0 turns "unknown" into a real place. Prefer null and handle it.
Recap
  • App owns the state (location, coordinates); the dropdown and the map change it through setLocation and onMapClick.
  • coords is derived on every render: the map click for "custom", otherwise the geocode answer. In the repo, "no answer yet" becomes 0, 0, which is why the first requests go to the middle of the ocean; step 25 uses null.
  • useSuspenseQuery starts fetching during render, plain useQuery after the commit, which explains the recorded request order.
  • A query key names a cache entry. The four cards share ["weather", coords], so One Call is fetched once; a cached key costs no request.
  • Each query function runs fetch → res.json() → schema.parse. Check res.ok first, or error answers become confusing Zod errors.
  • Suspense shows the skeletons while a card waits; an error boundary (step 26) catches a failed card so the rest of the dashboard survives.
