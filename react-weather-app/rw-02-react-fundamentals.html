React Fundamentals

Components, JSX, props, state, rendering, effects, context and the rules of hooks.

What you will learn

React is a library for building user interfaces out of small, reusable pieces called components. You describe what the screen should look like for the current data, and React works out how to update the page when the data changes. This chapter explains the handful of ideas the whole weather dashboard rests on:

  • components and JSX, and what JSX turns into;
  • props (data going down) and callbacks (events going up);
  • state with useState, and where to keep it;
  • rendering: what happens when state changes, and why rendering must be pure;
  • effects with useEffect, including cleanup;
  • context and providers, using the project's ThemeProvider;
  • the rules of hooks, lists and keys, Suspense and StrictMode.
Why this matters for your project. Almost every bug fixed in the extension steps is a React-fundamentals bug: a side effect in the render body (the map click listener that piles up, step 25), state that never reaches storage (the theme that resets, step 27), a value computed before its data exists (the 0,0 requests). Once you can trace "state changes → component renders → effect runs", these bugs become easy to see.

The app is a tree of components

A component is a JavaScript function whose name starts with a capital letter and which returns a description of some UI. Components use other components, so the whole app forms a tree. main.tsx is the root: it finds the empty <div id="root"> in index.html and tells React to render into it.

const queryClient = new QueryClient()

createRoot(document.getElementById("root")!).render(
  <StrictMode>
    <QueryClientProvider client={queryClient}>
      <ThemeProvider>
        <App />
      </ThemeProvider>
    </QueryClientProvider>
  </StrictMode>
)

JSX: HTML-like syntax that is really JavaScript

JSX lets you write markup inside JavaScript. It looks like HTML, but it is compiled into ordinary function calls. We compiled a tiny card with esbuild using the same "automatic" JSX runtime that the project selects with "jsx": "react-jsx" in tsconfig.app.json:

type Props = { title: string; temp: number }

function MiniCard({ title, temp }: Props) {
  return (
    <div className="p-4">
      <h2>{title}</h2>
      <p>{Math.round(temp)}°F</p>
    </div>
  )
}

export default MiniCard

import { jsx, jsxs } from "react/jsx-runtime";
function MiniCard({ title, temp }) {
  return /* @__PURE__ */ jsxs("div", { className: "p-4", children: [
    /* @__PURE__ */ jsx("h2", { children: title }),
    /* @__PURE__ */ jsxs("p", { children: [
      Math.round(temp),
      "\xB0F"
    ] })
  ] });
}
var jsx_default = MiniCard;
export {
  jsx_default as default
};

Each tag became a call that creates a plain object ("an element") describing a div, its props and its children. The types disappeared. Rendering that element with react-dom/server gives the HTML React would put on the page:

<div class="p-4"><h2>Current Weather</h2><p>72<!-- -->°F</p></div>

Conditions and lists

Because braces hold expressions, conditional UI uses expressions too. LocationDropdown.tsx shows the "Custom" item only after a map click with {location === "custom" && (<SelectItem value="custom">Custom</SelectItem>)}: if the left side is false, React renders nothing. For either/or, use a ternary condition ? a : b, as SidePanel.tsx does to choose "translate-x-0" or "translate-x-full".

Lists are arrays of elements built with map. Each item needs a key: a string or number that is unique among its siblings and stays the same for the same item across renders. React uses keys to match old and new items, so it can keep the right DOM nodes and state when a list changes.

      {data.hourly.map((hour) => (
        <div
          key={hour.dt}
          className="flex flex-col 2xl:justify-between gap-2 items-center p-2"

hour.dt (the forecast hour's timestamp) is a good key: unique and stable. Not every list in the repo has one. The quality badges in SidePanel.tsx ({Object.keys(pollutant).map((quality) => (<span className=...>) have no key. We rendered the same pattern in development mode and React printed its standard warning:

Each child in a list should have a unique "key" prop.

Check the render method of `Badges`. See https://react.dev/link/warning-keys for more information.

The page still works (the list never reorders), but the fix is one attribute: <span key={quality} ...>. Avoid array indexes as keys when items can be inserted, removed or reordered.

Props: passing data down

Props are the arguments of a component. The parent writes them as JSX attributes; the child receives them as one object, usually destructured right in the parameter list (see chapter 1). TypeScript describes them with a Props type:

type Props = {
  children: ReactNode
  title?: string
  className?: string
  childrenClassName?: string
}

export default function Card({
  children,
  title,
  className,
  childrenClassName,
}: Props) {

children is special: it is whatever you put between the opening and closing tags. <Card title="Current Weather"> ...lots of JSX... </Card> passes that JSX as children, and Card decides where to place it. This is how one Card component gives every panel the same frame. The ? marks optional props, so <Card> without a title is allowed.

Props are read-only. A child must never change the object it was given. If a child needs to change something that its parent owns, the parent passes down a function, and the child calls it. That is the second half of the pattern:

The project uses this pattern for every interactive piece: LocationDropdown gets setLocation, MapTypeDropdown gets setMapType, MobileHeader and SidePanel get setIsSidePanelOpen, and Map gets onMapClick. The type for a raw state setter is Dispatch<SetStateAction<string>>; onMapClick is typed as a plain function, (lat: number, lon: number) => void, which hides how App reacts and is often the cleaner choice.

State: a component's memory

Ordinary variables inside a component are recreated every time the function runs, so they can't remember anything. State is memory that React keeps for a component between renders. You create it with useState(initialValue), which returns the current value and a setter. App.tsx has four pieces:

  const [coordinates, setCoords] = useState<Coords>({ lat: 50, lon: 45 })
  const [location, setLocation] = useState("Tokyo")
  const [mapType, setMapType] = useState("clouds_new")
  const [isSidePanelOpen, setIsSidePanelOpen] = useState(false)

Calling a setter does two things: it stores the new value, and it schedules a re-render of that component. On the next render useState returns the new value. The variable you already have does not change in the middle of the current render — a setter is a request for the next render, not an assignment.

When the new value depends on the old one, pass a function to the setter. ThemeProvider does this: setTheme((prev) => (prev === "dark" ? "light" : "dark")). React calls the function with the latest value, which is safe even if several updates are queued.

Where should state live?

Put state in the closest common parent of every component that needs it. The city name is needed by the dropdown (to show it), by App (to geocode it) and, through coords, by every card, the map and the side panel. So it lives in App. This is called lifting state up. The theme is needed by deeply nested toggles, so it lives in a provider (see Context below).

Equally important is what is not state. coords in App.tsx is computed during render from location, coordinates and the geocode result. That is correct: if a value can be calculated from existing state or props, calculate it. Copying it into a second useState would create two sources of truth that can disagree.

New to "server state"? Why the weather data is not in useState

The weather, geocoding and air quality responses are not stored with useState at all. They live in TanStack Query's cache, which handles loading, caching, retries and sharing between components. A useful split: client state (what the user chose: city, map type, panel open) goes in useState; server state (copies of data owned by an API) goes in a data-fetching library. See chapter 6.

Rendering: what happens when state changes

"Rendering" means React calling your component function to get its JSX. It happens in three phases:

  1. Trigger. The first render happens at createRoot(...).render(...). Later renders happen when a component's state (or a context it reads) changes.
  2. Render. React calls the component, which returns new JSX. React then renders its children too, because they might depend on the new values.
  3. Commit. React compares the new element tree with the previous one and changes only the DOM nodes that differ. After that, it runs effects.

Rendering must be pure

A pure function returns the same output for the same input and changes nothing outside itself. React may call your components extra times (StrictMode does so on purpose in development), so anything that "does something" during render will happen too often. The repo's MapClick component breaks this rule:

  const map = useMap()
  map.panTo([coords.lat, coords.lon])

  map.on("click", (e) => {
    const { lat, lng } = e.latlng
    onMapClick(lat, lng)
  })

  return null

map.on("click", ...) runs on every render and never removes the previous listener, so listeners accumulate as the app re-renders. Side effects like subscribing, fetching or touching the DOM belong in an effect or an event handler. Step 25 replaces this with react-leaflet's useMapEvents hook and moves panTo into a useEffect.

Effects: synchronising with the outside world

An effect is code that runs after React has updated the screen, to keep something outside React in sync with your state: the <html> element's class, a Leaflet map, a timer, a network connection. You write it with useEffect(setup, dependencies):

function MapTileLayer() {
  const map = useMap()

  useEffect(() => {
    const tileLayer = new MaptilerLayer({
      style: "basic-dark",
      apiKey: "YOUR_MAPTILER_KEY",
    })
    tileLayer.addTo(map)

    return () => {
      map.removeLayer(tileLayer)
    }
  }, [map])

  return null
}

(The repo hard-codes a real MapTiler key on line 58; it is replaced here with a placeholder.) The three parts of an effect:

  • Setup (the function body): create the layer and add it to the map.
  • Cleanup (the function it returns): undo the setup. React calls it before running the effect again and when the component disappears.
  • Dependencies ([map]): the values the effect uses. React re-runs the effect only when one of them changes. [] means "only after the first render"; leaving the array out means "after every render".

ThemeProvider uses an effect to copy React state into the DOM, which is exactly the job effects are for:

  useEffect(() => {
    const root = document.documentElement
    if (theme === "dark") {
      root.classList.add("dark")
    } else {
      root.classList.remove("dark")
    }
  }, [theme])

Whenever theme changes, the class on <html> follows, and Tailwind's dark: classes switch (chapter 4). No cleanup is needed because running it twice gives the same result. A useful test before writing an effect: is there an external system to sync with? If you are only computing a value from props or state, compute it during render instead (as coords is). If you are reacting to a click, do it in the click handler.

Context: sharing values without passing props through every level

Passing theme as a prop from App to MobileHeader to LightDarkToggle would work but becomes tedious ("prop drilling"). Context lets a component provide a value once, and any descendant read it directly. The project's ThemeProvider is the textbook pattern (step 24; the presenter creates the context at about 5:41:42 and notes it is always defined outside a component):

  1. Create the context once, at module level: const ThemeContext = createContext<ThemeContextType | undefined>(undefined). The default undefined is what readers get when no provider is above them.
  2. Provide a value in a component that owns the state: <ThemeContext.Provider value={{ theme, toggleTheme }}>{children}</ThemeContext.Provider>.
  3. Read it anywhere below with useContext(ThemeContext), wrapped in the custom hook useTheme() that throws a clear error if the provider is missing.

QueryClientProvider in main.tsx is the same idea: it puts the QueryClient into context so that every useQuery call shares one cache. Context is best for values many components need and that change rarely (theme, current user, language, a client object). One detail: value={{ theme, toggleTheme }} creates a new object on every ThemeProvider render, so all readers re-render whenever the provider does. In a small app this is fine; in bigger apps people wrap the value in useMemo.

Hooks and their rules

Functions whose names start with use are hooks: useState, useEffect, useContext, TanStack Query's useQuery and useSuspenseQuery, react-leaflet's useMap, and the project's own useTheme. React identifies each hook call by its position in the component, so two rules apply:

  1. Call hooks only at the top level of a component or custom hook — never inside if, loops, nested functions or after an early return.
  2. Call hooks only from React functions — components or other hooks, not regular helpers or event handlers.

The project's ESLint setup (eslint-plugin-react-hooks, see chapter 3) catches both. We linted a deliberately broken component with the project's config:

import { useEffect, useState } from "react"

export default function HooksDemo({ show }: { show: boolean }) {
  if (show) {
    const [count, setCount] = useState(0)
    console.log(count, setCount)
  }
  const [city] = useState("Tokyo")
  useEffect(() => {
    document.title = city
  }, [])
  return null
}

   5:31  error    React Hook "useState" is called conditionally. React Hooks must be called in the exact same order in every component render  react-hooks/rules-of-hooks
  11:6   warning  React Hook useEffect has a missing dependency: 'city'. Either include it or remove the dependency array                      react-hooks/exhaustive-deps

The second message is just as useful: the effect reads city but doesn't list it, so it would never re-run when the city changes. Treat exhaustive-deps warnings as bugs until proven otherwise.

A custom hook is simply a function starting with use that calls other hooks. useTheme is one. They let you share logic (not state: each component that calls a custom hook gets its own state).

Suspense and StrictMode in one paragraph each

Suspense. A component can tell React "I can't render yet, my data is still loading" (this is called suspending). React then shows the fallback of the nearest <Suspense> above it. The project wraps each card: <Suspense fallback={<CurrentSkeleton />}><CurrentWeather coords={coords} /></Suspense>. useSuspenseQuery inside the card does the suspending, so the card code can assume data is always there. Each card has its own boundary, so they appear independently. Errors are the mirror image: a thrown error goes to the nearest error boundary, which the repo doesn't have yet (step 26 adds them). Details in step 19 and chapter 6.

StrictMode. <StrictMode> in main.tsx renders nothing visible. In development only, it calls components twice and runs effects setup → cleanup → setup, to surface impure renders and missing cleanups early. If you see a console.log printed twice during npm run dev, this is usually why; production builds don't do it.

Common misconceptions
  • "After setLocation("Seoul"), location is "Seoul"." Not in the current render. The new value arrives on the next render.
  • "useEffect is for fetching data." It can be, but in this project TanStack Query fetches. Effects are for syncing with non-React systems (the DOM class, Leaflet layers).
  • "Anything a component does goes in its body." The body is for calculating JSX. Listeners, requests and DOM changes go in effects or event handlers — the MapClick leak is the cost of forgetting this.
  • "Context replaces all props." Use props for most data; use context for values that many distant components need.
  • "Keys are just to silence a warning." Keys are how React matches list items across renders; wrong keys move state to the wrong item.
  • "Effects run twice, so my code is broken." In development under StrictMode that is expected. Make the effect safe to repeat by writing a proper cleanup.
Recap
  • Components are capitalised functions that return JSX; JSX compiles to jsx() calls that describe elements.
  • Props go down (read-only, including children); events go up through callbacks like setLocation and onMapClick.
  • useState keeps memory between renders; a setter schedules a re-render. Keep state in the closest common parent and derive everything you can (like coords).
  • Rendering must be pure; side effects go in useEffect with dependencies and a cleanup, or in event handlers.
  • Context (ThemeProvider + useTheme, QueryClientProvider) shares values with a whole subtree.
  • Hooks run at the top level only; the react-hooks lint rules enforce this. Lists need stable keys; Suspense shows fallbacks while children load.
