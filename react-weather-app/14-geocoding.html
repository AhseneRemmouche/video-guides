Geocoding

Turn a city name into coordinates with the OpenWeather Geocoding API.

▶ Watch this part (02:12:48)

Goal

The dropdown gives you a city name, but OpenWeather's One Call API only accepts coordinates. "How do I have any idea what the latitude and longitude coordinates of Tokyo actually are?" (2:12:54). The answer is geocoding: OpenWeather has a second endpoint that turns a place name into latitude and longitude.

In this step you:

  1. write getGeocode(location) in api.ts and a Zod schema for its answer;
  2. keep the selected city in App as location state and geocode it with useQuery;
  3. derive the coordinates the cards use: from the map click when location is "custom", otherwise from the geocode result;
  4. make the dropdown controlled, so picking a city updates location.

At the end, picking Dubai or Rome updates every card. The map itself still stays put; step 15 fixes that. You will also meet four weaknesses of this code that the browser test found, all fixed in step 25.

New to geocoding? Names in, coordinates out

Geocoding converts a place description ("Tokyo", "London, GB") into coordinates. The reverse, coordinates to a name, is reverse geocoding. OpenWeather's Direct geocoding endpoint is /geo/1.0/direct. You send q (city name, optionally with state and country codes separated by commas), limit (how many matches, up to 5) and your appid API key.

The answer is always a JSON array, even with limit=1: one object per match, with name, local_names (the name in other languages), lat, lon, country and sometimes state. If nothing matches, the array is empty: []. Keep that in mind; it matters below.

Many cities share a name (London, UK and London, Canada). With limit=1 you get OpenWeather's first match. "I think it's sensible enough to assume there'll only be one source of information for any given city" (2:15:35); for this app's twelve famous cities that is true.

The API function

This is the function the presenter writes, identical to lines 15–21 of the repo's src/api.ts (the repo file also contains getWeather from step 5 and getAirPollution from step 20). Add import { GeocodeSchema } from "./schemas/geocodeSchema" at the top of the file.

export async function getGeocode(location: string) {
  const res = await fetch(
    `http://api.openweathermap.org/geo/1.0/direct?q=${location}&limit=1&appid=${API_KEY}`
  )
  const data = await res.json()
  return GeocodeSchema.parse(data)
}

Two URL weaknesses (fixed in step 25)

  • http://: on the dev server (http://localhost) this works. Once the app is deployed on an https:// site, browsers block plain-http requests from it as mixed content, and the dropdown would stop working. The One Call URL in getWeather already uses https://; OpenWeather serves the geocoding endpoint over https too. (Explained, not tested on a deployed site.)
  • No encodeURIComponent: ${location} is pasted raw into the URL. "New York" contains a space; browsers encode it for you, so this city works. But a name containing & or # would break the query string (everything after & becomes a new parameter). Wrap inserted values: q=${encodeURIComponent(location)}.

The schema

import z from "zod"

export const GeocodeSchema = z.array(
  z.object({
    name: z.string(),
    local_names: z.record(z.string(), z.string()),
    lat: z.number(),
    lon: z.number(),
    country: z.string(),
    state: z.string().optional(),
  })
)

Verified bug: a required local_names breaks cities that don't have it

The browser test mocked a geocode answer without local_names, which OpenWeather does for many places. GeocodeSchema.parse threw a ZodError, TanStack Query retried the query three times and then marked it as failed, and the app silently showed the weather for latitude 0, longitude 0 (the fallback below) while the dropdown still said the city. No error message anywhere. The twelve cities in the dropdown happen to have local_names today, so you won't see it with them, but any other city can trigger it. Fix (step 25): local_names: z.record(z.string(), z.string()).optional(). The general lesson: in a schema for someone else's API, make every field you don't use optional, or leave it out (Zod ignores unknown keys by default).

Geocode in App and derive the coordinates

New to ?. and ??? Optional chaining and nullish coalescing

Optional chaining a?.b means "if a is null or undefined, stop and give undefined; otherwise read a.b". geocodeData?.[0] is the same for an index: while the query is loading, geocodeData is undefined, and ?. prevents a crash.

Nullish coalescing x ?? y means "use x, unless it is null or undefined, then use y". Unlike ||, it keeps 0 (a valid latitude!).

Careful: ?. protects only the step it is written on. geocodeData?.[0].lat protects geocodeData being undefined, not [0] being undefined. If the array is empty, [0] is undefined and .lat on it throws. The safe form is geocodeData?.[0]?.lat.

Try the video's version: App.tsx at 2:25:40

Transcribed from the video at 2:23:00 (geocode and coords, then renamed to geocodeData at 2:23:48) and 2:24:11 (dropdown props), not separately built.

import DailyForecast from "./components/cards/DailyForecast"
import HourlyForecast from "./components/cards/HourlyForecast"
import CurrentWeather from "./components/cards/CurrentWeather"
import AdditionalInfo from "./components/cards/AdditionalInfo"
import Map from "./components/Map"
import { useState } from "react"
import type { Coords } from "./types"
import LocationDropdown from "./components/dropdowns/LocationDropdown"
import { useQuery } from "@tanstack/react-query"
import { getGeocode } from "./api"

function App() {
  const [coordinates, setCoords] = useState<Coords>({ lat: 50, lon: 45 })
  const [location, setLocation] = useState("Tokyo")

  const { data: geocodeData } = useQuery({
    queryKey: ["geocode", location],
    queryFn: () => getGeocode(location),
  })

  const onMapClick = (lat: number, lon: number) => {
    setCoords({ lat, lon })
    setLocation("custom")
  }

  const coords =
    location === "custom"
      ? coordinates
      : { lat: geocodeData?.[0].lat ?? 0, lon: geocodeData?.[0].lon ?? 0 }

  return (
    <div className="flex flex-col gap-8">
      <LocationDropdown location={location} setLocation={setLocation} />
      <Map coords={coords} onMapClick={onMapClick} />
      <CurrentWeather coords={coords} />
      <HourlyForecast coords={coords} />
      <DailyForecast coords={coords} />
      <AdditionalInfo coords={coords} />
    </div>
  )
}

export default App

Verified bug: requests for latitude 0, longitude 0 on every load

On the first render the geocode query has not answered yet, so geocodeData is undefined and ?? 0 makes coords = { lat: 0, lon: 0 }. The cards don't wait: they immediately fetch the weather for 0, 0, a spot in the Atlantic Ocean south of Ghana. The browser test of the finished app recorded this request order on a normal load:

  1. onecall for 0, 0
  2. air_pollution for 0, 0 (the side panel, added in step 20)
  3. geocode for Tokyo
  4. onecall for 35.68, 139.69
  5. air_pollution for 35.68, 139.69

Two wasted requests per load, and every city change repeats the trick (the cards briefly fetch 0, 0 while the new city is geocoded). The presenter notices the symptom in step 15 as a map that flickers "to the middle of the ocean" (2:28:00). At 2:30:40 they correctly trace it to this fallback and plan to address it with Suspense; the 0, 0 requests remain in the final code. Fix (step 25): when there are no coordinates yet, render nothing (or a skeleton) instead of inventing 0, 0.

Verified bug: an empty geocode result crashes the whole app

If the geocoding API returns [] (no match), geocodeData is an empty array, geocodeData?.[0] is undefined, and .lat on it throws:

TypeError: Cannot read properties of undefined (reading 'lat')

The error happens while App renders, and there is no error boundary, so React unmounts everything: a blank page. With the twelve fixed cities this needs an unusual answer from the API, but the same code path runs for any city you ever add. Fix (step 25): read const place = geocodeData?.[0] and handle "no place" explicitly; the fixed app shows "Could not find "Tokyo". Pick another city or click the map."

Verified: a map click geocodes the city "custom"

After a map click, location is "custom", so the key becomes ["geocode", "custom"] and the query runs getGeocode("custom"): a real request asking OpenWeather for a place called "custom" (seen in the browser test). The result is ignored, because the ternary uses coordinates for "custom", but the request is wasted and its answer could even fail validation. TanStack Query's enabled option says when a query may run. The step-25 version adds one line to this useQuery:

  const { data: geocodeData, error: geocodeError } = useQuery({
    queryKey: ["geocode", location],
    queryFn: () => getGeocode(location),
    enabled: location !== "custom", // a map click sets "custom": there is no city to look up
  })

A ZodError on the way: wind_gust

When the presenter saves and refreshes (2:23:04), the page crashes with a ZodError from the weather schema: expected a number at current.wind_gust, received undefined. Some places report no gusts, and OpenWeather then simply leaves the field out. The fix is one word in src/schemas/weatherSchema.ts:

wind_gust: z.number().optional(),

"Hopefully that should fix our page crashing issue" (2:23:26). It does. It is the same lesson as local_names: a field the API doesn't always send must be optional in the schema.

Control the dropdown

Picking a city still did nothing, because the Select kept its choice to itself. The presenter passes the state down and wires it up (2:24:11–2:25:18).

New to typing a setter? Dispatch<SetStateAction<string>>

useState("Tokyo") returns a pair: the value (string) and a setter. React's own type for that setter is Dispatch<SetStateAction<string>>. Read it inside out: SetStateAction<string> is "either a new string, or a function that takes the old string and returns a new one"; Dispatch<X> is "a function that takes an X and returns nothing". "This is how setter functions are normally typed in React" (2:24:32). A simpler alternative is a callback prop like onChange: (city: string) => void, which hides that the parent uses useState.

What you should see

  • On load the dropdown says "Tokyo" and the cards show Tokyo's weather (after a brief moment for 0, 0, which you may not notice).
  • In DevTools → Network, a request named direct?q=Tokyo&limit=1&appid=… whose response contains lat and lon.
  • Picking Dubai, then Rome, updates all cards ("Boom. Our information updates", 2:25:42). The map does not move yet.
  • Clicking the map still works and updates the cards; the dropdown button goes blank (no "custom" item until step 16).

Common mistakes

  • queryFn: getGeocode without the arrow: TanStack Query calls it with its own context object, so the URL contains [object Object]. Write () => getGeocode(location).
  • location missing from the query key: the first city is cached forever and the dropdown appears broken (the same mistake as step 11).
  • Forgetting setLocation("custom") in onMapClick: the derived coords keep using the dropdown city, so map clicks seem to do nothing.
  • Writing geocodeData[0].lat without ?.: TypeScript (strict mode) reports "'geocodeData' is possibly 'undefined'", and at runtime it would crash while loading.
  • value without onValueChange: the dropdown is frozen on Tokyo: React keeps forcing the value back.
  • A ZodError about wind_gust or local_names: the API omitted a field your schema requires. Make it .optional().

For how location, the query keys, the cache and re-renders fit together across the whole app, read How Data Flows Through the App. Zod's optional fields and error messages are covered in Validating Data with Zod.

Recap
  • getGeocode(location) calls /geo/1.0/direct?q=…&limit=1 and validates the array with GeocodeSchema.
  • App holds location (a city or "custom") and coordinates (the last map click); useQuery(["geocode", location]) geocodes the city.
  • coords is derived on every render: coordinates for "custom", else geocodeData?.[0] with a ?? 0 fallback.
  • The dropdown is controlled with value={location} and onValueChange; wind_gust became optional after a ZodError.
  • Verified weaknesses, fixed in step 25: weather fetched for 0, 0 on every load, a crash on an empty result, a required local_names, a geocode request for "custom" (fixed with enabled), plus http:// and an unencoded city name.
