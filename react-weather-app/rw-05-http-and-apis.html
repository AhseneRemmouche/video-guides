HTTP, REST APIs & API Keys

Requests and responses, status codes, query strings, CORS, HTTPS and keeping keys safe.

What you will learn

The weather dashboard has no server of its own. Everything it shows comes from OpenWeather (and the base map from MapTiler), fetched directly by the browser. This chapter explains what actually travels over the network when the app loads, and the web rules that decide whether those requests succeed:

  • requests and responses: methods, URLs, headers, bodies and JSON;
  • the anatomy of the OpenWeather URLs, query strings and URL encoding;
  • HTTP status codes, and why fetch doesn't throw on a 401;
  • HTTPS and mixed content;
  • CORS: what it is and why it doesn't bite this app;
  • API keys: what they protect, why a browser app can't hide one, and what to do about it.
Why this matters for your project. Four of the problems found while testing the finished app are HTTP problems: no res.ok check (a bad key shows up as a cryptic Zod error), two http:// URLs that browsers will block once the site is on HTTPS, One Call 3.0 needing its own subscription, and keys that end up public in the deployed JavaScript. Step 25, step 26 and step 28 fix them; this chapter explains why they happen.

Requests and responses

HTTP is a conversation of single exchanges. The browser (the client) sends a request; a server sends back exactly one response.

Request partIn this app
Method — what you want to doAlways GET ("give me this resource"), the default for fetch. Other methods like POST send data to create or change something.
URL — which resourcehttps://api.openweathermap.org/data/3.0/onecall?lat=...
Headers — metadataAdded by the browser: Origin, Accept, User-Agent...
BodyNone (GET requests don't send one).
Response partIn this app
Status code — how it went200 OK normally; 401 Unauthorized for a bad key.
HeadersContent-Type: application/json, Access-Control-Allow-Origin: * (more on that below).
BodyJSON text: the weather, the geocoding result, or an error object.

An API (here: a web API) is a set of URLs designed for programs rather than people: you ask in a documented format and get structured data back. OpenWeather's APIs are "REST-style": each URL names a resource, you read it with GET, and the answer is JSON.

New to the Network tab? How to watch requests

Press F12 (or right-click → Inspect) and open the Network tab, then reload the page. Each row is one request. Filter by Fetch/XHR to see only API calls. Click a row to see its URL and query parameters, request and response headers, status code and the response body ("Preview" or "Response"). When something fails, this is the first place to look: the status code and body usually tell you why. Remember that anyone can do this on your deployed site, including reading any key in a URL.

URL encoding

Some characters have a meaning inside URLs: & separates parameters, ? starts the query, # starts a fragment, and spaces are not allowed at all. A value that contains them must be encoded. getGeocode pastes the city in directly (q=${location}). For "New York" this happens to work because browsers encode the space for you, but a name containing & or # would break the URL. Two standard tools do it properly:

encodeURIComponent("New York")            // "New%20York"
encodeURIComponent("São Paulo & Co")      // "S%C3%A3o%20Paulo%20%26%20Co"

const u = new URL("https://api.openweathermap.org/geo/1.0/direct")
u.searchParams.set("q", "New York")
u.searchParams.set("limit", "1")
u.toString() // "https://api.openweathermap.org/geo/1.0/direct?q=New+York&limit=1"

Both forms (%20 and +) mean a space in a query string. Step 25 wraps the city in encodeURIComponent. The dropdown only offers fixed city names today, but code tends to outlive such assumptions — a search box would make this matter at once.

Status codes and what fetch does with them

Every response starts with a three-digit status code. The first digit tells you the category:

RangeMeaningExamples you may meet here
2xxSuccess200 OK
3xxRedirect — look elsewhere301/302; fetch follows them automatically
4xxClient error — your request is wrong400 bad parameters, 401 missing/invalid key or no subscription, 404 wrong path, 429 too many requests
5xxServer error — their problem500, 502, 503; often temporary, worth a retry

We sent real requests to OpenWeather with a made-up key. Both endpoints answered 401 with a small JSON error object:

HTTP/1.1 401 Unauthorized
Content-Type: application/json; charset=utf-8
Access-Control-Allow-Origin: *

{"cod":401, "message": "Invalid API key. Please see https://openweathermap.org/faq#error401 for more info."}

HTTP/1.1 401 Unauthorized

{"cod":401, "message": "Please note that using One Call 3.0 requires a separate subscription to the One Call by Call plan. Learn more here https://openweathermap.org/price. If you have a valid subscription to the One Call by Call plan, but still receive this error, then please see https://openweathermap.org/faq#error401 for more info."}

The second message is important for anyone following the video: a regular OpenWeather key works for geocoding and air pollution, but One Call 3.0 answers 401 until the account also has the "One Call by Call" subscription. If your cards fail while the side panel works, this is the first thing to check (check OpenWeather's site for the current plans and terms).

fetch resolves on errors

Here is the trap. fetch only rejects (throws, when awaited) if no response arrived at all: no network, unknown host, a blocked request. Any HTTP response, including 401 or 500, counts as success:

const res = await fetch("https://api.openweathermap.org/data/2.5/air_pollution?lat=35.68&lon=139.69&appid=INVALID")
console.log("ok:", res.ok, "status:", res.status, res.statusText)
console.log("body:", await res.json())
try {
  await fetch("https://no-such-host.invalid/")
} catch (e) {
  console.log("network error ->", e.name + ":", e.message)
}

ok: false status: 401 Unauthorized
body: {
  cod: 401,
  message: 'Invalid API key. Please see https://openweathermap.org/faq#error401 for more info.'
}
network error -> TypeError: fetch failed

(Browsers word the network error differently, e.g. "Failed to fetch", but it is the same TypeError.) The repo's helpers go straight from fetch to res.json() to Zod. With a bad key, the JSON is { cod, message }, so Zod reports that lat was "expected number, received undefined" — true, but useless. Checking res.ok first turns it into a clear message. This is the helper from step 25:

async function fetchJson<T extends z.ZodType>(url: string, schema: T): Promise<z.infer<T>> {
  const res = await fetch(url)
  if (!res.ok) {
    const body = await res.json().catch(() => null)
    throw new Error(`OpenWeather request failed (${res.status}): ${body?.message ?? res.statusText}`)
  }
  return schema.parse(await res.json())
}

Retries deserve a word. TanStack Query retries a failed query three times by default, with increasing delays. That is helpful for a flaky network or a 503, but pointless for a 401: the key won't fix itself. In the browser test with an invalid key, the committed app made 28 requests in 20 seconds before giving up. Retrying too eagerly is also how you hit 429 Too Many Requests. Chapter 6 shows how to tune retry.

HTTPS and mixed content

HTTPS is HTTP inside an encrypted, authenticated connection (TLS). Nobody between you and the server can read or change the data, and the browser checks the server's certificate so you know you're talking to the real host. On plain http://, anyone on the network path — public Wi-Fi, for example — can read the request, including the appid in the URL.

Two of the three API URLs in the repo use plain HTTP:

    `http://api.openweathermap.org/geo/1.0/direct?q=${location}&limit=1&appid=${API_KEY}`
    `http://api.openweathermap.org/data/2.5/air_pollution?lat=${lat}&lon=${lon}&appid=${API_KEY}`

During development nothing goes wrong: the page itself is http://localhost:5173, and OpenWeather still answers plain HTTP (we checked with curl; it does not redirect). The problem appears after deployment. Static hosts normally serve your site over HTTPS, and browsers enforce a mixed content rule: a secure (https://) page may not load scripts or make fetch requests to insecure (http://) URLs. The requests are blocked before they leave the browser, and the console shows a "Mixed Content" error. In this app that would mean no city lookup and no air-quality panel. (This was reasoned from the rule, not tested on a deployed site.)

CORS: who may read the response

Browsers follow the same-origin policy: JavaScript on one origin (scheme + host + port, e.g. http://localhost:5173) may not read responses from another origin unless that server agrees. The agreement is called CORS (Cross-Origin Resource Sharing) and is expressed in response headers. The browser sends an Origin header with the request; if the response says Access-Control-Allow-Origin with that origin or *, the browser hands the response to your code. If not, your code gets a network error and the console shows a CORS message — even though the server did answer.

OpenWeather allows everyone. We sent a request with an Origin header and got:

HTTP/1.1 401 Unauthorized
Access-Control-Allow-Origin: *
Access-Control-Allow-Credentials: true
Access-Control-Allow-Methods: GET, POST

That is why the app can call the API directly from the browser, from localhost or from any deployed domain. Some APIs don't send these headers; then a browser app can't call them directly and needs a server in between.

A common misunderstanding is to treat CORS as a security feature for the API. It isn't: tools like curl or a server don't check CORS at all. It stops a malicious web page from reading data from other sites using the visitor's browser and cookies. "Preflight" OPTIONS requests appear only for non-simple requests (custom headers, JSON bodies, methods like PUT); the app's plain GET calls don't trigger them.

API keys: identification, not secrecy

An API key identifies who is calling, so the provider can apply limits, track usage and (for paid plans) bill the right account. The app sends its OpenWeather key as appid on every request, including each weather map tile. The key comes from import.meta.env.VITE_API_KEY, and Vite pastes its value into the JavaScript bundle at build time (verified in chapter 3). So once deployed, the key is public: it is in the downloaded JavaScript and in every request in the Network tab. The repo also hard-codes a MapTiler key in Map.tsx (line 58; replaced by a placeholder in this guide), which makes it public on GitHub too.

There is no way to hide a secret in code that runs in the visitor's browser. Your options:

ApproachWhat it gives youFits
Accept a public key, but restrict itSome providers let you limit a key to your domains (MapTiler's dashboard has allowed origins). Check what your provider offers; for the OpenWeather key, real protection needs a proxy.Map keys, demo projects
Keep keys out of gitPut them in .env.local (ignored by the repo's .gitignore), never in source files. Prevents leaks in the repository; does not hide them in the deployed app.Always
Proxy through your own serverThe browser calls your endpoint; the server adds the key and forwards. The key never reaches the browser, and you can add caching and rate limits.Paid keys, anything you care about
Rotate a leaked keyCreate a new key in the provider dashboard and delete the old one. Removing it from git history is not enough — assume it was copied.After any leak

A proxy can be very small. This Node script (standard library only) forwards three allowed OpenWeather paths and adds the key from the server's environment. We ran it with a fake key: /api/geo/1.0/direct?q=Tokyo&limit=1 came back with OpenWeather's 401 JSON, and any other path returned 404.

import http from "node:http"

const API_KEY = process.env.OPENWEATHER_KEY // lives only on the server
const ALLOWED = new Set(["/data/3.0/onecall", "/geo/1.0/direct", "/data/2.5/air_pollution"])

http
  .createServer(async (req, res) => {
    const url = new URL(req.url, "http://localhost")
    const path = url.pathname.replace(/^\/api/, "")
    if (!ALLOWED.has(path)) {
      res.writeHead(404).end()
      return
    }
    url.searchParams.set("appid", API_KEY)
    const upstream = await fetch(`https://api.openweathermap.org${path}?${url.searchParams}`)
    res.writeHead(upstream.status, { "Content-Type": "application/json" })
    res.end(await upstream.text())
  })
  .listen(8787)

The allow-list matters: without it, your proxy would let anyone use your key for any OpenWeather endpoint. A real deployment would add error handling, caching and rate limiting, and usually runs as a serverless function on the same host as the site. The weather map tiles would need the same treatment, since their URLs carry the key too. Step 28 and chapter 10 discuss the deployment side.

Common misconceptions
  • "fetch throws when the server returns an error." Only on network failure. Check res.ok or res.status.
  • "It works locally, so the URLs are fine." Mixed content only shows up on an HTTPS page. Use https:// everywhere.
  • "A .env file keeps my key secret." It keeps it out of the source files. Any VITE_ value is still inlined into the public bundle.
  • "CORS errors mean the server is down" / "CORS secures the API." CORS errors mean the server didn't grant permission to your origin; and CORS is a browser rule, not API protection.
  • "A 401 always means a wrong key." For One Call 3.0 it can also mean the separate subscription is missing — read the message body.
  • "Retrying always helps." Retry 5xx and network errors; don't hammer an API with requests that will fail the same way.
Recap
  • A request has a method, URL, headers and (sometimes) a body; a response has a status code, headers and a body — JSON for these APIs.
  • URLs = scheme + host + path + query string; encode user input with encodeURIComponent or URLSearchParams.
  • 2xx success, 4xx your mistake, 5xx theirs. fetch resolves for all of them, so check res.ok before parsing.
  • One Call 3.0 answers 401 without the separate "One Call by Call" subscription; the error body says so.
  • HTTPS pages can't call http:// APIs (mixed content); OpenWeather sends Access-Control-Allow-Origin: *, so CORS allows direct browser calls.
  • Keys in browser code are public. Restrict them where possible, keep them out of git, and use a small server proxy when a key must stay secret.
