TanStack Query in Depth

The cache, query keys, staleTime, retries, suspense queries, errors and devtools.

In step 4 the presenter wrapped the app in a QueryClientProvider. In step 6 they fetched weather with useQuery. In step 19 they switched the cards to useSuspenseQuery so skeletons could show while data loads. Those three steps use a small part of what TanStack Query does. This chapter explains what happens underneath: the cache, query keys, "fresh" and "stale" data, automatic retries, suspense queries, queries that must wait for something, refreshing data on purpose, and the devtools.

Why this matters for your project. Four of the bugs found when testing this app come from TanStack Query behaviour that the video never mentions. The lat 0 / lon 0 requests come from a query that should have waited. The 28 requests in 20 seconds after a bad key come from the default retries. The blank page comes from a suspense query throwing an error with nothing there to catch it. Once you know the rules in this chapter, each of these becomes easy to spot and fix (step 25, step 26).

Every library fact below was checked in the versions locked in the project: @tanstack/react-query and @tanstack/query-core 5.90.5. Snippets marked verified were run with Node or type-checked with the project's own tsc settings.

Server state is different from component state

React's useState holds data that your app owns: which city is selected, whether the side panel is open, which map layer is shown. Nobody else can change it. Weather data is different. It lives on OpenWeather's servers. Your app only holds a copy, and that copy gets old. People call this kind of data server state.

Server state brings questions that useState does not answer. Is the copy still recent enough? Two components need the same data: do we download it twice? The request failed: do we try again? The user switches back to a city: can we show the old data instantly? TanStack Query answers all of these with one object, the QueryClient, and one hook family, useQuery and friends.

The QueryClient and its cache

The project creates exactly one client, with no options, in src/main.tsx:

const queryClient = new QueryClient()

createRoot(document.getElementById("root")!).render(
  <StrictMode>
    <QueryClientProvider client={queryClient}>

The client owns a QueryCache: think of it as a dictionary. Each entry ("a query") stores the last data, the last error, a status, the time the data arrived, and the list of components currently using it (TanStack calls those observers). The QueryClientProvider is a React context provider, so every hook below it reaches the same cache. Create the client once, outside any component. If you created it inside a component, every re-render would make a fresh, empty cache.

Query keys: the name of a cache entry

A query key is an array that names the data. Every card in the project uses the same one:

const { data } = useSuspenseQuery({
  queryKey: ["weather", coords],
  queryFn: () => getWeather({ lat: coords.lat, lon: coords.lon }),
})

That is src/components/cards/CurrentWeather.tsx lines 12–15; DailyForecast, HourlyForecast and AdditionalInfo repeat it. TanStack Query turns the key into a string (a hash) and uses it to find the entry. Two hooks with keys that hash the same share one entry. The presenter points this out at 37:16 and again at 52:47: four cards, one request.

Here is that claim checked directly against the installed query-core. Four requests for the same key start at the same moment; the query function runs once:

const coords = { lat: 35.68, lon: 139.69 }
const opts = { queryKey: ["weather", coords], queryFn: () => getWeather(coords) }
await Promise.all([qc.fetchQuery(opts), qc.fetchQuery(opts), qc.fetchQuery(opts), qc.fetchQuery(opts)])
// four fetchQuery calls, queryFn ran: 1

hashKey(["weather", { lat: 35.68, lon: 139.69 }])
// '["weather",{"lat":35.68,"lon":139.69}]'
hashKey(["weather", { lat: 1, lon: 2 }]) === hashKey(["weather", { lon: 2, lat: 1 }])
// true

Two things follow. First, the hash is plain JSON, so a new coords object with the same numbers still finds the same entry. That is lucky for this app, because App.tsx builds a new { lat, lon } object on every render. Second, the order of properties inside an object does not matter (the hash sorts them), but the order of array items does: ["weather", coords] and [coords, "weather"] are different keys.

Put every input in the key

The rule is simple: anything the query function uses must be in the key. At 1:57:25 the presenter explains why coords was added: with a fixed ["weather"] key, changing the location would keep showing "whatever the first cache value is". The function would get new coordinates, but TanStack Query would think it already had the answer. The same rule explains ["geocode", location] in App.tsx. If you later add a units switch (the app is fixed to units=imperial), the units must join the key: ["weather", coords, units].

Keys also work as a hierarchy. ["weather"] is a prefix of every ["weather", coords] key. Several client methods, such as invalidateQueries, match by prefix, so one call can target every city at once. Keep the first item a stable word like "weather" for that reason.

New to hashing? Why a key is turned into a string

JavaScript compares objects by identity, not by content: { lat: 1 } === { lat: 1 } is false, because they are two different objects in memory. A cache that compared keys that way would miss every time, since React components create new objects on every render. So TanStack Query converts the key into text with JSON.stringify (after sorting object properties). Two keys that produce the same text are "the same key". This is also why keys must be serializable: plain strings, numbers, booleans, arrays and plain objects. Functions or class instances do not belong in a key.

The life of a query: status and fetchStatus

A query has two separate states. status says what data you have: pending (nothing yet), success (data available) or error. fetchStatus says whether a request is running right now: fetching, paused (no network) or idle. They are independent: a query can be success and fetching at the same time, which means "showing old data while getting new data in the background".

Fresh, stale and garbage collected: staleTime and gcTime

Two timers control how long the cache trusts and keeps data. They are easy to confuse, so here they are side by side, with the defaults read from query-core 5.90.5:

OptionQuestion it answersDefaultWhere the default lives
staleTimeHow long is data considered fresh, so no refetch happens?0: stale immediatelyquery.js: isStaleByTime(staleTime = 0)
gcTimeHow long is an unused entry kept before it is deleted?5 minutes in the browser (Infinity on a server)removable.js: isServer ? Infinity : 5 * 60 * 1e3

With staleTime: 0, data is fresh for no time at all. That sounds wasteful, but stale data is still shown; it is only refetched when a trigger happens. The default triggers are: a new component mounts that uses the key, the browser window regains focus, and the network reconnects (refetchOnMount, refetchOnWindowFocus, refetchOnReconnect all default to "yes, if stale"). In this app that means: switch to another browser tab and back, and the weather is downloaded again.

One special case matters here. Suspense queries clamp staleTime to at least 1,000 ms (MIN_SUSPENSE_TIME_MS in react-query/build/modern/suspense.js). Without that, a component that suspends and then re-mounts would find stale data and start fetching again in a loop.

gcTime starts counting only when no component uses the entry any more. Pick Tokyo, then Paris: the Tokyo entry loses its observers and gets 5 minutes. Switch back within that time and Tokyo appears instantly from the cache (and, because it is stale, is refetched in the background).

The improved setup in step 26 changes both retry and staleTime for the whole app:

const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      retry: 1, // one quick retry instead of three: a wrong key or missing subscription won't fix itself
      staleTime: 5 * 60 * 1000, // weather data stays fresh for 5 minutes: switching back to a city reuses it
    },
  },
})

Retries and exponential backoff

When a query function throws (or its promise rejects), TanStack Query does not give up at once. In retryer.js the defaults are:

function defaultRetryDelay(failureCount) {
  return Math.min(1e3 * 2 ** failureCount, 3e4);
}
// ...
const retry = config.retry ?? (isServer ? 0 : 3);

So in the browser a failing query is tried 4 times in total (1 + 3 retries), waiting 1 s, 2 s and 4 s between attempts. The wait doubles each time and never exceeds 30 s. This pattern is called exponential backoff: it gives a struggling server time to recover and avoids hammering it.

Retries help with temporary problems (a dropped connection, a server hiccup). They do not help with permanent ones. In the browser test with an invalid key, OpenWeather answered 401 every time. Every query key went through its retries, and 28 requests were recorded in 20 seconds before the page went blank. Step 26 sets retry: 1. You can be smarter and skip retries for errors that will never fix themselves. This was type-checked against the project:

new QueryClient({
  defaultOptions: {
    queries: {
      // the message comes from fetchJson in step 25: "OpenWeather request failed (401): ..."
      retry: (failureCount: number, error: Error) =>
        !error.message.includes("(401)") && failureCount < 2,
      retryDelay: (attempt: number) => Math.min(1000 * 2 ** attempt, 30_000),
    },
  },
})

useQuery or useSuspenseQuery?

Both hooks read from the same cache. They differ in how they report "not ready yet" and "failed".

useQueryuseSuspenseQuery

The rows about enabled, errors and placeholderData come straight from the installed source of useSuspenseQuery.js, which calls the base hook with enabled: true, suspense: true, throwOnError: defaultThrowOnError, placeholderData: void 0. defaultThrowOnError throws only when there is no data yet; if old data exists and a background refetch fails, the card keeps the old data.

That throwing is why the committed app shows a blank page when OpenWeather fails: the error travels up to the root, and React removes the whole tree when nothing catches it. Step 26 wraps each card in a WeatherErrorBoundary that uses TanStack's QueryErrorResetBoundary, so one card can fail, show a message and a "Try again" button, while the others keep working.

At 3:15:14 the presenter notices that a Suspense fallback did not appear while only one card was wrapped, and concludes it is "all or nothing" because the cards are "subscribed to the exact same query". The practical lesson in the final code is simple: every component that calls a suspense query gets its own <Suspense> with its own skeleton, so each card decides what to show while the shared entry loads.

Queries that must wait: enabled and skipToken

The weather depends on coordinates, and the coordinates depend on the geocode query. That is a dependent query. The committed code does not wait. It fills in zeros while the city is still loading:

const coords =
  location === "custom"
    ? coordinates
    : { lat: geocodeData?.[0].lat ?? 0, lon: geocodeData?.[0].lon ?? 0 }

With that, the cards immediately ask for ["weather", {lat: 0, lon: 0}]. The browser test recorded the order: One Call for 0,0, Air Pollution for 0,0, then the geocode for Tokyo, then One Call and Air Pollution for Tokyo. Two wasted requests on every load, and a flash of the Gulf of Guinea (the presenter sees it at about 2:28:00). TanStack Query offers two ways to say "not yet":

// 1. enabled: the query exists but does not run while the condition is false
const { data } = useQuery({
  queryKey: ["weather", coords],
  queryFn: () => getWeather(coords!),
  enabled: coords !== null,
})

// 2. skipToken: same effect, and TypeScript knows coords is not null inside the function
const result = useQuery({
  queryKey: ["weather", coords],
  queryFn: coords ? () => getWeather(coords) : skipToken,
})

Both were type-checked inside the project. skipToken is exported by @tanstack/query-core 5.90.5 (it is a Symbol) and re-exported by @tanstack/react-query. With a disabled or skipped query, isPending is true but isFetching is false: "no data and not trying".

Neither works with useSuspenseQuery, which the cards use. enabled is not part of its options, and passing skipToken is a TypeScript error (its queryFn type is Exclude<..., SkipToken>) and logs skipToken is not allowed for useSuspenseQuery in development. For suspense, the fix is to not render the component until the input exists. That is what step 25 does: coords becomes null until the geocode arrives, and each card slot renders its skeleton instead of the card.

const place = geocodeData?.[0]
// null until we know where to look: no requests for lat 0 / lon 0 while the city is loading
const coords: Coords | null =
  location === "custom" ? coordinates : place ? { lat: place.lat, lon: place.lon } : null
// ...
{coords ? <CurrentWeather coords={coords} /> : <CurrentSkeleton />}

After this change the browser test recorded 3 requests on load, all for Tokyo.

The fixed app also uses enabled where it fits, on the plain useQuery for geocoding. In the repo, a map click sets location to "custom", and the geocode query then dutifully asked OpenWeather to look up a city called "custom" (verified in the browser test). Step 25 switches that query off for map clicks:

  const { data: geocodeData, error: geocodeError } = useQuery({
    queryKey: ["geocode", location],
    queryFn: () => getGeocode(location),
    enabled: location !== "custom", // a map click sets "custom": there is no city to look up
  })

So the project shows both techniques: enabled for the useQuery that must sometimes not run, and "don't render it yet" for the suspense queries.

Refreshing data on purpose: refetch and invalidation

Sometimes you want new data now: a "Refresh" button, or after the user changes a setting. There are two tools.

  • refetch() is returned by useQuery and useSuspenseQuery. It re-runs this query immediately.
  • queryClient.invalidateQueries({ queryKey }) marks every matching entry as stale and refetches the ones that are currently on screen. Matching is by prefix, so ["weather"] hits every city.
import { useQueryClient } from "@tanstack/react-query"

export function RefreshButton() {
  const queryClient = useQueryClient()
  return (
    <button onClick={() => queryClient.invalidateQueries({ queryKey: ["weather"] })}>
      Refresh weather
    </button>
  )
}

A detail checked in Node: after invalidateQueries on an entry that no component uses, the entry is marked isInvalidated: true but the query function is not called. It runs the next time a component mounts with that key. Invalidation is "this is out of date", not "download everything now".

Sharing options with queryOptions

The project copies the same key and function into four files. If one copy changes and the others do not, the cards stop sharing a cache entry. The queryOptions helper lets you define the pair once (type-checked in the project):

import { queryOptions } from "@tanstack/react-query"

export const weatherQuery = (coords: Coords) =>
  queryOptions({
    queryKey: ["weather", coords],
    queryFn: () => getWeather(coords),
  })

// in each card:
const { data } = useSuspenseQuery(weatherQuery(coords))

Seeing the cache: the devtools

TanStack ships a separate package, @tanstack/react-query-devtools (version 5.104.1 on npm at the time of writing; install a version that matches your @tanstack/react-query). It adds a floating panel that lists every query key, its status, when it was updated and its data. It is the fastest way to see the lat 0 / lon 0 entry for yourself. The project does not include it. The official docs show this setup, and state that the devtools are only included in bundles when process.env.NODE_ENV is 'development', so they disappear from production builds:

npm i @tanstack/react-query-devtools
import { ReactQueryDevtools } from "@tanstack/react-query-devtools"

<QueryClientProvider client={queryClient}>
  <ThemeProvider>
    <App />
  </ThemeProvider>
  <ReactQueryDevtools initialIsOpen={false} />
</QueryClientProvider>
Common misconceptions
  • "Each useQuery call makes its own request." No. Calls with the same key share one entry and one request.
  • "Stale data is deleted." No. Stale data stays on screen; it is just allowed to be refetched. Deletion is gcTime's job, and only for unused entries.
  • "staleTime: 0 means a request on every render." No. Refetches need a trigger: mount, window focus, reconnect, invalidation or refetch().
  • "Retries fix errors." Only temporary ones. A 401 stays a 401; the default 3 retries just multiply requests (step 26 lowers it to 1).
  • "enabled: false works with useSuspenseQuery." It is not an option there. Don't render the component until its input exists.
  • "I can leave a variable out of the key if the function reads it." Then the cache returns old data when that variable changes, exactly the bug the presenter fixes at 1:57:25.
Recap
  • One QueryClient per app; its cache maps hashed query keys to data, status and observers.
  • Same key, same entry, one request: the four cards share ["weather", coords]. Every input of the query function belongs in the key.
  • staleTime (default 0) decides when to refetch; gcTime (default 5 min in the browser) decides when unused data is forgotten. Suspense raises staleTime to at least 1 s.
  • Default retries in the browser: 3, waiting 1 s, 2 s, 4 s (capped at 30 s). Lower or customise them for permanent errors.
  • useSuspenseQuery suspends and throws; pair it with <Suspense> and an error boundary. It has no enabled and rejects skipToken.
  • Dependent queries wait with enabled / skipToken (useQuery) or by not rendering the component (suspense).
  • refetch() re-runs one query; invalidateQueries marks matching keys stale and refetches the active ones.
