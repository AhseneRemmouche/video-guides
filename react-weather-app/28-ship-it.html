Smaller Bundle & Safe Deployment

Lazy-load the map, understand what VITE_ variables expose, and deploy without leaking keys.

Extension · built and browser-tested

Extension: not in the video. This step builds on steps 25–27. The code was type-checked, linted, built and run in headless Chrome against the production build with mocked OpenWeather answers (including at phone width, 390 px). The bundle sizes come from npm run build output; the key exposure was checked by building with a fake key and searching the output files.

What that proves: the map loads as a separate file, the numbers below are real, and any VITE_ value ends up in the JavaScript sent to visitors. What it does not prove: how fast the app is on your users' connections, or the exact steps on any particular hosting service. The proxy code on this page is an illustrative sketch, not part of the tested project.

Goal

The app works and handles errors. Before you put it on the internet, two questions are left: how much does a visitor have to download before they see anything, and what happens to your API keys once the site is public? In this step you split the map into its own file, add a .env.example and a safer .gitignore, learn exactly what VITE_ variables expose and how to limit the damage, and deploy the build to a static host.

Part 1: a smaller first download

npm run build on the repo produces one JavaScript file with everything in it, and Vite prints a warning:

dist/index.html                    0.48 kB │ gzip:   0.31 kB
dist/assets/index-….css           51.22 kB │ gzip:  13.75 kB
dist/assets/index-….js         2,005.92 kB │ gzip: 558.90 kB
(!) Some chunks are larger than 500 kB after minification. Consider: ...

About 2 MB of JavaScript (about 559 kB compressed, which is what actually travels over the network) has to download and run before any card appears. Most of it is the map: Leaflet, react-leaflet and especially the MapTiler SDK. The cards don't need any of that. So we tell Vite to put the map in a separate file and load it only when it's needed.

New to code splitting and lazy loading? One app, several files

A bundle is the JavaScript file a build produces from all your modules. Code splitting means producing several files instead of one. Bundlers like Vite split automatically wherever your code uses a dynamic import: import("./components/Map") written as a function call. Unlike a normal import … from at the top of a file, it loads the module later, when the line runs, and returns a promise.

Lazy loading in React is React.lazy: you give it a function that does the dynamic import, and you get back a component you can render normally. The first time it renders, React starts the download and suspends, so the nearest Suspense shows its fallback until the file has arrived. The same mechanism you used for data in step 19 now works for code.

// The map pulls in Leaflet and MapTiler (most of the JavaScript). Loading it lazily lets
// the cards appear first while the map code downloads in a separate file.

function App() {
  const [coordinates, setCoords] = useState<Coords>({ lat: 50, lon: 45 })
  const [location, setLocation] = useState("Tokyo")
  const [mapType, setMapType] = useState("clouds_new")
  const [isSidePanelOpen, setIsSidePanelOpen] = useState(false)

  const { data: geocodeData, error: geocodeError } = useQuery({
    queryKey: ["geocode", location],
    queryFn: () => getGeocode(location),
    enabled: location !== "custom", // a map click sets "custom": there is no city to look up
  })

  const onMapClick = (lat: number, lon: number) => {
    setCoords({ lat, lon })
    setLocation("custom")
  }

  const place = geocodeData?.[0]
  // null until we know where to look: no requests for lat 0 / lon 0 while the city is loading
  const coords: Coords | null =
    location === "custom" ? coordinates : place ? { lat: place.lat, lon: place.lon } : null

  return (
    <>
      <MobileHeader setIsSidePanelOpen={setIsSidePanelOpen} />
      <div className="flex flex-col gap-8 pt-4 p-8 xs:pt-8 lg:w-[calc(100dvw-var(--sidebar-width))] 2xl:h-screen 2xl:min-h-[1120px]">
        <div className="flex flex-col gap-4 xs:flex-row xs:gap-8">
          <div className="flex flex-col md:flex-row gap-2 md:gap-4">
            <h1 className="text-2xl font-semibold">Location: </h1>
            <LocationDropdown location={location} setLocation={setLocation} />
          </div>
          <div className="flex flex-col md:flex-row gap-2 md:gap-4">
            <h1 className="text-2xl font-semibold whitespace-nowrap">
              Map Type:{" "}
            </h1>
            <MapTypeDropdown mapType={mapType} setMapType={setMapType} />
          </div>
          <div className="ml-auto flex gap-4 items-center">
            <div className="hidden xs:block">
              <LightDarkToggle />
            </div>
            <button
              onClick={() => setIsSidePanelOpen(true)}
              className="hidden xs:block"
            >
              <Hamburger className="size-6 lg:hidden" />
            </button>
          </div>
        </div>
        {location !== "custom" && geocodeError && (
          <p role="alert" className="text-red-500">
            {geocodeError.message}
          </p>
        )}
        {location !== "custom" && geocodeData && !place && (
          <p role="alert" className="text-red-500">
            Could not find "{location}". Pick another city or click the map.
          </p>
        )}
        <div className="grid grid-cols-1 2xl:flex-1 2xl:min-h-0 md:grid-cols-2 2xl:grid-cols-4 2xl:grid-rows-4 gap-4">
          <div className="relative h-120 2xl:h-auto col-span-1 md:col-span-2 2xl:col-span-4 2xl:row-span-2 order-1">
            <Suspense fallback={<div className="size-full rounded-xl bg-muted animate-pulse" />}>
              {coords && <Map coords={coords} onMapClick={onMapClick} mapType={mapType} />}
            </Suspense>
            <MapLegend mapType={mapType} />
          </div>
          <div className="col-span-1 2xl:row-span-2 order-2">
            <WeatherErrorBoundary title="Current Weather">
              <Suspense fallback={<CurrentSkeleton />}>
                {coords ? <CurrentWeather coords={coords} /> : <CurrentSkeleton />}
              </Suspense>
            </WeatherErrorBoundary>
          </div>
          <div className="col-span-1 order-3 2xl:order-4 2xl:row-span-2">
            <WeatherErrorBoundary title="Daily Forecast">
              <Suspense fallback={<DailySkeleton />}>
                {coords ? <DailyForecast coords={coords} /> : <DailySkeleton />}
              </Suspense>
            </WeatherErrorBoundary>
          </div>
          <div className="col-span-1 md:col-span-2 2xl:row-span-1 order-4 2xl:order-3">
            <WeatherErrorBoundary title="Hourly Forecast (48 Hours)">
              <Suspense fallback={<HourlySkeleton />}>
                {coords ? <HourlyForecast coords={coords} /> : <HourlySkeleton />}
              </Suspense>
            </WeatherErrorBoundary>
          </div>
          <div className="col-span-1 md:col-span-2 2xl:row-span-1 order-5">
            <WeatherErrorBoundary title="Additional Weather Info">
              <Suspense fallback={<AdditionalInfoSkeleton />}>
                {coords ? <AdditionalInfo coords={coords} /> : <AdditionalInfoSkeleton />}
              </Suspense>
            </WeatherErrorBoundary>
          </div>
        </div>
      </div>
      {coords && (
        <SidePanel
          coords={coords}
          isSidePanelOpen={isSidePanelOpen}
          setIsSidePanelOpen={setIsSidePanelOpen}
        />
      )}
    </>
  )
}

Part 2: what VITE_ variables really expose

In step 5 the OpenWeather key went into .env as VITE_API_KEY, and in step 25 the MapTiler key joined it as VITE_MAPTILER_KEY. That keeps the keys out of Git. It does not keep them secret from visitors.

New to build-time environment variables? Why .env does not hide a key from visitors

An environment variable is a named value given to a program from outside its code. In a server program it stays on the server. A Vite app is different: there is no server code at all, only files that the visitor's browser downloads and runs. When you run npm run build, Vite replaces every import.meta.env.VITE_… in your code with the value itself, as plain text (see Vite env variables). The VITE_ prefix is Vite's safety switch: variables without it are never copied into browser code, precisely because whatever is copied is public.

You can see it for yourself. Build with a fake key and search the output:

VITE_API_KEY=TESTKEY npm run build
grep -c TESTKEY dist/assets/*.js
repo build:     dist/assets/index-….js: 2   (both uses in the one bundle)
step 28 build:  dist/assets/index-….js: 1   (api.ts)
                dist/assets/Map-….js:   1   (the weather tile layer URL)

Anyone can do the same with your deployed site: open DevTools → Network, click any request to api.openweathermap.org, and read appid=… in the URL. Or open the JavaScript file and search for it. The MapTiler key appears the same way in its tile requests.

Add .env.example and ignore .env

The repo's .gitignore (from Vite's template) ignores *.local, so .env.local is safe, but a file named exactly .env is not ignored. One git add . and your keys are in the history. Add it explicitly, and commit an example file instead so others know which variables to set:

# Copy this file to .env and fill in your own keys. Never commit .env.
# VITE_ variables are built into the JavaScript the browser downloads: anyone can read them.
VITE_API_KEY=your-openweather-key
VITE_MAPTILER_KEY=your-maptiler-key

Limit what a public key can do

Since the keys can't be hidden in a browser-only app, the next best thing is to make a copied key useless elsewhere:

  • MapTiler keys can be restricted to allowed origins (your site's address) in the MapTiler account dashboard. Requests from other websites using your key are then refused. Look for the key's settings in your MapTiler account and check MapTiler's documentation for the current steps. Keep http://localhost:5173 in the list (or use a separate development key) so local development keeps working.
  • OpenWeather keys travel in the URL as appid=… and are not restricted to a website in the same way. If someone copies yours, their calls count against your account. To keep this key truly secret you need a small piece of code that runs on a server, a proxy.

The proxy idea (illustrative)

A proxy is a tiny server-side function that sits between your app and OpenWeather. The browser calls your address without any key; the function adds the key, which it reads from a server-only environment variable (no VITE_ prefix, never in the bundle), calls OpenWeather, and passes the answer back. Many static hosts offer "serverless functions" or "edge functions" for exactly this; each has its own file location and syntax.

// A generic serverless function using the standard Request/Response API.
// Check your host's docs for where this file goes and how it is exported.
export default async function handler(request) {
  const { searchParams } = new URL(request.url)
  const lat = Number(searchParams.get("lat"))
  const lon = Number(searchParams.get("lon"))
  if (!Number.isFinite(lat) || !Number.isFinite(lon)) {
    return new Response("lat and lon are required", { status: 400 })
  }
  const key = process.env.OPENWEATHER_KEY // server-only: no VITE_ prefix
  const res = await fetch(
    `https://api.openweathermap.org/data/3.0/onecall?lat=${lat}&lon=${lon}&units=imperial&exclude=minutely,alerts&appid=${key}`
  )
  return new Response(await res.text(), {
    status: res.status,
    headers: { "content-type": "application/json" },
  })
}

The app would then call something like /api/weather?lat=…&lon=… instead of OpenWeather. Two things to keep in mind: the proxy only lets through the requests you allow (here only One Call, only numeric coordinates), so nobody can use it as a free door to the rest of your account; and the app also puts the key in the weather map tile URL (Map.tsx) and calls geocoding and air pollution, so a complete solution needs a route for each. Rate limiting on the proxy is a good next step.

Part 3: deploy the build

This app is a static site: after npm run build, the dist/ folder contains an index.html, some CSS and JavaScript files and images. Any host that can serve files can run it; there is no server code to start. The exact screens differ per host, so here are the general steps. Check your host's documentation for the details.

  1. Build and preview locally

    Run npm run build, then npm run preview, and test the address it prints. This is the same code your visitors will get (it's how the broken marker of step 25 was found). Don't open dist/index.html by double-clicking: the files are referenced from the site root (/assets/…), which doesn't work from file://.

  2. Push your project to a Git repository

    Without .env (now ignored). Most hosts build straight from the repository.

  3. Create the site on your host and set the build settings

    Build command: npm run build. Output (publish) directory: dist. Many hosts detect Vite and fill these in for you.

  4. Add the environment variables in the host's dashboard

    Add VITE_API_KEY and VITE_MAPTILER_KEY with your values in the host's settings for environment variables. They must exist when the build runs, because Vite pastes them in at build time. If you add or change one after deploying, trigger a new build.

  5. Deploy, then restrict the keys

    Once you know your site's address (it will be https://…, which is why step 25 switched every API URL to https), add it to the MapTiler key's allowed origins.

This app has a single page and no client-side router, so you don't need the "redirect every path to index.html" rule that many hosts ask about for single-page apps.

What you should see

  • npm run build lists a separate Map-….js and Map-….css; index-….js is about 623 kB (177 kB gzip) instead of 2,006 kB (verified).
  • In DevTools → Network on a fresh load, Map-….js is requested after index-….js; on a slow connection (Network → throttling) you briefly see the pulsing map placeholder while the cards already load.
  • git status doesn't list .env; .env.example is ready to commit.
  • On the deployed site: all requests are https and the app looks like your npm run preview test.

Common mistakes

  • Keeping the static import Map from … next to the lazy one: TypeScript reports a duplicate name, and if you rename one, the static import pulls the map back into the main file.
  • Lazy-loading a file without a default export: lazy fails at run time. Either export the component as default or map it: lazy(() => import("./X").then((m) => ({ default: m.X }))).
  • Thinking .env makes a key secret: it only keeps it out of Git. Any VITE_ value is in the downloaded JavaScript.
  • Putting a real secret in a VITE_ variable (a database password, a paid API's secret key): never do this in a browser app. Use a server function.
  • Setting the variables after the first deploy and expecting them to work: rebuild. Also check the names: a missing VITE_ prefix makes the value undefined in the browser.
  • Committing .env before adding it to .gitignore: ignoring it later doesn't remove it from the history. Replace the keys.
Recap
  • React.lazy + Suspense split the map into its own file: the first JavaScript download goes from 558.90 kB to 177.48 kB gzip.
  • Every VITE_ variable is pasted into the bundle at build time and readable by any visitor (verified with a fake key).
  • .env.example documents the variables; .gitignore now ignores .env.
  • Restrict the MapTiler key to your site's origin; a truly secret OpenWeather key needs a server-side proxy.
  • Deploy dist/ to any static host: build command npm run build, output dist, variables set in the host's dashboard before the build.
