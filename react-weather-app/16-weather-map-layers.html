Weather Map Layering

Overlay OpenWeather tiles (clouds, rain, wind...) and a map-type dropdown.

▶ Watch this part (02:31:43)

Goal

Right now the map shows streets and a marker, but no weather. In this step you lay a second set of map images on top of the first one: OpenWeather's weather map layers (clouds, rain, pressure, wind, temperature). A new dropdown, Map Type, lets the user choose which layer to see. By the end, the dashboard header has two labelled dropdowns, and the map changes colour when you pick a different layer.

The code is small (one extra <TileLayer>, one state variable and a copy of the location dropdown), but it introduces an idea you will meet in every web map: a map is a stack of layers, and each layer is made of many small square images called tiles.

What the presenter explains

Weather maps are free tiles from OpenWeather (at 2:31:48). On the OpenWeather "Weather maps" docs page, the presenter shows the world map with a cloud layer, a precipitation layer, sea level pressure and wind speed: "there's a few different layers I think that if we added to our app could make it really cool". A second TileLayer (2:32:35): "we have this tile layer here that's doing our actual map. We can actually just make another one of those." The base map's TileLayer from step 11 stays; a second one with OpenWeather's URL goes right below it.

Layer names (2:33:18): the {layer} part of the URL is "the layer name … the cloud layer is just clouds new. Precipitation layer is precipitation new." So the app needs to store one of these strings: clouds_new, precipitation_new, pressure_new, wind_new, temp_new.

Reuse the dropdown you already have (2:33:40): the map has "no context of knowing what layer the user wants to see", so the choice lives in App as state, and a copy of LocationDropdown sets it.

Layers stay aligned (2:38:39): because both tile layers sit inside the same MapContainer, zooming or dragging moves them together. "They all stay relative to each other … which is exactly what we want cuz that's how map layering should work."

New to map tiles? What {z}/{x}/{y} means

A web map is not one giant picture. The world is cut into square images, usually 256 × 256 pixels, called tiles. Leaflet works out which tiles cover the part of the world you're looking at and downloads only those.

  • {z} is the zoom level. At zoom 0 the whole world fits in one tile. Each zoom level splits every tile into four, so zoom 1 has 2 × 2 tiles, zoom 2 has 4 × 4, and zoom 5 (the app's starting zoom) has 32 × 32.
  • {x} is the column, counted from the left (from longitude −180°).
  • {y} is the row, counted from the top (from the far north).

Every tile server that follows this "XYZ" scheme can be used with a Leaflet TileLayer: OpenStreetMap for the streets, OpenWeather for the weather. That's why adding weather was "not nearly as hard as it might look" (2:32:12). The handbook chapter Maps on the Web goes deeper.

New to template literals? Backticks, ${} and the curly braces that stay

A template literal is a string written between backticks `…`. Inside it, ${expression} is replaced by the value of the expression: `map/${mapType}/` becomes "map/clouds_new/".

Plain curly braces without a dollar sign, like {z}, are just characters. JavaScript leaves them alone, and Leaflet later replaces them with numbers. That's why both kinds can live in one URL.

In JSX, the outer { } in url={`…`} means "this prop is a JavaScript expression". With plain quotes, url="…${mapType}…", the text ${mapType} would be sent to OpenWeather as it is.

New to "lifting state up"? Why mapType lives in App

In React, data flows down: a parent passes props to its children. Siblings can't talk to each other directly. MapTypeDropdown and Map are siblings, so the shared value must live in their closest common parent, App.

  1. App owns mapType with useState.
  2. App gives the value and the setter to the dropdown.
  3. The dropdown calls the setter. React re-renders App.
  4. App passes the new value to Map, which builds a new tile URL.

This is the same pattern as location in step 13. The handbook chapter React Fundamentals covers it in more detail.

Common mistakes.
  • Quotes instead of backticks around the URL: the request literally contains ${mapType} and no weather appears.
  • A typo in a layer name (cloud_new, clouds-new): those tile requests fail and the map looks as if nothing happened. Copy the names from the docs.
  • Splitting the value instead of the label: value={city.split("_")[0]} would send "clouds" to OpenWeather, which isn't a layer name.
  • Forgetting to pass mapType to <Map>: TypeScript reports "Property 'mapType' is missing in type …" in App.tsx.
  • The open list is hidden behind the map: the z-1001 class on SelectContent is missing.
  • No weather at all, even with the right URL: open one tile URL from the Network tab in a new browser tab. If it returns an error about the key, check VITE_API_KEY in .env and restart npm run dev after changing it.

Recap
  • A web map is a stack of layers; a TileLayer fetches 256-pixel squares addressed by zoom, column and row.
  • OpenWeather's weather maps are just another tile URL: …/map/{layer}/{z}/{x}/{y}.png?appid=KEY.
  • ${mapType} is filled in by JavaScript; {z}/{x}/{y} are filled in by Leaflet for each tile.
  • mapType state lives in App; MapTypeDropdown writes it, Map reads it.
  • split("_")[0] + capitalize change only the label; the value stays the API name.
  • A conditional "Custom" item keeps the location dropdown from going blank after a map click.
