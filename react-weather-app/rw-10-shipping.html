Shipping a React App

Production builds, environment variables, bundle size, deployment, monitoring and security.

The video ends with a dashboard that runs on localhost. Getting it in front of real users is a separate skill: building optimised files, understanding what your environment variables really do, keeping the download small, putting the files on a host, serving everything over HTTPS, finding out when something breaks, and not leaking keys. Step 28 did the hands-on part for this app. This chapter explains the background, using what we measured on this project, and ends with a checklist you can reuse for any React app.

Why this matters for your project. Several problems in this app only appear after npm run build or after deploying: the broken map marker (production build only), blocked http:// requests (HTTPS sites only), a 2 MB JavaScript file, and API keys that end up readable by anyone. None of them shows up on the dev server. Shipping safely means knowing where the dev server and the real world differ.

Facts below were checked in the installed vite 7.1.11 and in builds of the project (the original repo and the fixed version from steps 25–28). Hosting is described in general terms; check each provider's own documentation, since their dashboards and offers change.

Dev server versus production build

npm run dev starts Vite's dev server. It serves your source files almost as they are, transforms each one when the browser asks for it, and pushes changes instantly (HMR). That is great for development and useless for users: it is slow to load over the internet, unminified, and needs Node running.

npm run build runs the project's script tsc -b && vite build. First TypeScript checks every file (any type error stops the build). Then Vite bundles your code and all dependencies into a few optimised files in dist/. The result for the fixed app (step 28):

dist/
├── index.html                 tiny: just loads the two files below
├── vite.svg                   copied from public/
└── assets/
    ├── index-[hash].js        about 623 kB: React, TanStack Query, Zod, your cards
    ├── index-[hash].css       about 36 kB: Tailwind output
    ├── Map-[hash].js          about 1,384 kB: Leaflet + MapTiler SDK, loaded later
    └── Map-[hash].css         about 16 kB: Leaflet styles

The [hash] is a short fingerprint of the file's content, for example index-EqZpLb9q.js. When the content changes, the name changes. That lets a host tell browsers "cache files in assets/ forever": a new deploy produces new names, so nobody gets stuck with old code. index.html itself must not be cached for long, since it is the file that points to the current names.

Always test the build locally with npm run preview, which serves dist/ like a real host. The broken marker described in chapter 8 was invisible in npm run dev and obvious in npm run preview.

Environment variables: what VITE_ really means

The project reads its OpenWeather key with import.meta.env.VITE_API_KEY (in api.ts and Map.tsx). Vite loads environment variables from files in the project root, in this order, later files winning (from getEnvFilesForMode in Vite's source):

FileLoaded whenCommit it?
.envalwaysonly if it has no secrets
.env.localalwaysno (*.local is in the default .gitignore)
.env.[mode], e.g. .env.productionin that mode (vite build = production)only if it has no secrets
.env.[mode].localin that modeno

Only names starting with the envPrefix, 'VITE_' by default, are exposed to your code. Vite also provides built-ins: import.meta.env.MODE, DEV, PROD, BASE_URL and SSR. Env files are read when Vite starts, so restart the dev server after editing .env.

Here is the part that surprises people. import.meta.env.VITE_* is not read at run time from a secure place. During the build, Vite replaces each use with the literal value. We verified this: building with VITE_API_KEY=TESTKEY put the text TESTKEY twice into dist/assets/*.js, once per file that reads it. Anyone can open the browser's developer tools, look at the JavaScript, and read your key. The VITE_ prefix exists precisely to stop you exposing variables by accident; it does not hide the ones you do expose. Step 28's .env.example says it plainly:

# Copy this file to .env and fill in your own keys. Never commit .env.
# VITE_ variables are built into the JavaScript the browser downloads: anyone can read them.
VITE_API_KEY=your-openweather-key
VITE_MAPTILER_KEY=your-maptiler-key

Two more details from this project. The original .gitignore ignores *.local but not .env, so a key in .env could be committed by accident; step 28 adds .env to it. And the repo's Map.tsx had a real MapTiler key typed directly into the source (replaced by "YOUR_MAPTILER_KEY" in this guide). A key committed to a public repo stays in its git history even after you delete the line, so the only real fix is to revoke it and create a new one in the provider's dashboard.

Keeping API keys safe (as safe as possible)

If every key in a browser app is public, what can you do? It depends on the provider:

  • Restrict the key. Some providers let you limit a key to certain websites. MapTiler keys can be restricted to allowed origins in the MapTiler dashboard; then a copied key does not work on someone else's site. This is the right approach for keys that are designed to live in the browser, like map keys.
  • Proxy the request. For a key that must stay secret, the browser should never see it. You put a tiny server (often a "serverless function" offered by the same host) between the browser and the API. The browser calls your endpoint; the function adds the key on the server and forwards the request. The key lives in the host's server-side environment settings, not in a VITE_ variable. This is what protecting the OpenWeather key would need.
  • Accept and limit. For a personal demo, you may decide a public key is acceptable. Then use a separate key just for the demo, watch its usage, and know how to rotate it.

One catch for this app: the OpenWeather weather-map tiles are loaded by Leaflet straight from tile.openweathermap.org with ?appid= in the URL. Even with a proxy for the JSON calls, the tiles would also have to go through your proxy for the key to stay hidden.

Bundle size and lazy loading

Every visitor downloads your JavaScript before the app can start, and on a phone with a weak connection every megabyte costs seconds. The repo's build produced one JavaScript file of 2,005.92 kB (558.90 kB after gzip compression), and Vite printed a warning, because its chunkSizeWarningLimit defaults to 500 kB.

Most of that weight is the map: Leaflet plus the MapTiler SDK, which includes a full vector-map renderer. Step 28 applies code splitting with lazy loading: the map's code goes into its own file that the browser fetches separately, so the cards can render first.

// The map pulls in Leaflet and MapTiler (most of the JavaScript). Loading it lazily lets
// the cards appear first while the map code downloads in a separate file.
const Map = lazy(() => import("./components/Map"))
// ...
<Suspense fallback={<div className="size-full rounded-xl bg-muted animate-pulse" />}>
  {coords && <Map coords={coords} onMapClick={onMapClick} mapType={mapType} />}
</Suspense>

import("./components/Map") with parentheses is a dynamic import: Vite sees it and creates a separate chunk. lazy turns that promise into a component that suspends until the code arrives, and the <Suspense> fallback (a pulsing grey box) fills the space meanwhile. The result: the main file dropped to 623.35 kB (177.48 kB gzipped) and the map chunk is 1,383.59 kB (385.67 kB gzipped). The total is similar, but the part needed for the first paint is less than a third.

Good candidates for lazy loading are big pieces that are not needed at first: maps, charts, rich editors, admin pages, rarely opened dialogs. Do not lazy-load tiny components; every chunk is an extra request.

Hosting a static single-page app

After the build, this app is just files: no Node server, no database. Any static host can serve it. Vite's deployment guide covers many (Netlify, Vercel, Cloudflare Pages, GitHub Pages and others, at the time of writing). The settings are almost always the same three:

SettingValue for this projectWhy
Build commandnpm run buildruns tsc -b && vite build on the host
Output (publish) directorydistwhere Vite writes the files
Environment variablesVITE_API_KEY, VITE_MAPTILER_KEYset in the host's dashboard; your .env is not committed, and they are needed at build time

Two common traps. If the site lives in a sub-folder (for example a GitHub Pages project site at /repo-name/), set Vite's base option to that path, or the browser will look for /assets/... at the domain root and get 404s; the built index.html currently points to /assets/index-[hash].js. And apps with client-side routing need a "rewrite everything to index.html" rule; this dashboard has no routes, so it does not.

HTTPS and mixed content

Every serious host serves your site over HTTPS. Browsers then block mixed content: an HTTPS page is not allowed to fetch from a plain http:// address, because that request could be read or changed on the way. The repo's api.ts uses http:// for two of its three APIs:

    `http://api.openweathermap.org/geo/1.0/direct?q=${location}&limit=1&appid=${API_KEY}`
// ...
    `http://api.openweathermap.org/data/2.5/air_pollution?lat=${lat}&lon=${lon}&appid=${API_KEY}`

On http://localhost this works, so nobody notices. Once deployed on HTTPS, geocoding and air pollution would fail (this was explained from the code and browser rules, not tested on a deployed site). Step 25 uses one BASE_URL = "https://api.openweathermap.org" for all three. Rule: write https:// for every external URL from day one; the One Call URL and the tile URLs in the repo already do.

Knowing when it breaks: errors and monitoring

On your machine you see errors in the console. In production, errors happen on other people's devices and you never see them unless you collect them. Three layers help:

  1. Catch them in the UI. React error boundaries stop one failing component from blanking the whole page. Step 26's WeatherErrorBoundary shows a message and a "Try again" button per card.
  2. Report them. The boundary's componentDidCatch is the natural place to send an error to a monitoring service. Step 26 logs it with console.error(`${this.props.title} failed`, error, info.componentStack); in production you would replace or add a call to your service's SDK there. Errors outside React (event handlers, timers) are caught with the browser's window error and unhandledrejection events. Hosted error-monitoring services (Sentry is a well-known example at the time of writing) do this setup for you.
  3. Make the reports readable. Production code is minified, so a stack trace says a.b is undefined at index-EqZpLb9q.js:1:48213. Source maps translate that back to your files. Vite's build.sourcemap defaults to false; 'hidden' creates the maps without linking them from the bundle, so you can upload them to your monitoring service without publishing your source.

Common misconceptions
  • "Environment variables are secret." On a server, yes. In a Vite browser app, VITE_* values are pasted into the public JavaScript.
  • "If it works in npm run dev, it works in production." The marker and mixed-content bugs prove otherwise. Test the build.
  • "Deleting a committed key from the code removes it." Git history keeps it. Revoke and rotate.
  • "Lazy loading reduces total size." It moves code out of the first download; the total stays about the same.
  • "I need a Node server to host a React app." Not for a client-only Vite app: dist/ is static files.
  • "Changing .env on the host updates the live site." Values are baked in at build time; you must rebuild and redeploy.
Recap
  • npm run build type-checks, bundles, minifies and fingerprints into dist/; test it with npm run preview.
  • Vite loads .env, .env.local, .env.[mode], .env.[mode].local; only VITE_ names reach your code, and they are replaced with their values at build time: public.
  • Restrict browser keys by origin, proxy secret keys through a server, rotate any key that was committed.
  • Lazy-load heavy parts with lazy(() => import(...)) + <Suspense>: 2,006 kB became 623 kB + a 1,384 kB map chunk.
  • Static hosts need a build command, an output folder and build-time env vars; set base for sub-folder hosting.
  • Use https:// everywhere; browsers block http:// requests from HTTPS pages.
  • Catch errors with boundaries, report them to a monitoring service, and keep (hidden) source maps to read them.
