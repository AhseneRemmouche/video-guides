Fetching from the OpenWeather API

Get an API key, store it in an env variable, and fetch the One Call API.

▶ Watch this part (09:22)

Goal

Get real weather data. You create an OpenWeather account and an API key, store the key in an environment variable, and write getWeather, the function that asks OpenWeather's One Call API for the weather at any latitude and longitude. This chapter runs from 09:22 to 20:10.

"We want this weather dashboard to show real-time up-to-date factual data on our page, not just some mumbo jumbo hard-coded garbage. This is where OpenWeather comes in. This whole entire project is not possible without them" (09:24).

Read this before you start: One Call 3.0 needs its own subscription. The main API in this project, One Call API 3.0, is not part of OpenWeather's basic free plan. OpenWeather's own documentation, visible on screen at 25:20, says: "One Call 3.0 is included in the 'One Call by Call' subscription only". Without that subscription every request is refused with HTTP 401 and the message "Please note that using One Call 3.0 requires a separate subscription to the One Call by Call plan." Every weather card in the app then fails, while the air-pollution panel (a different API) still works. Subscribe to "One Call by Call" in your OpenWeather account (the Subscribe button on the One Call API 3.0 page) before testing. The presenter says it asks for payment details but that they stay within the free daily allowance; check OpenWeather's current pricing page for the limits.

New to APIs and HTTP? What happens when the app "calls an API"

An API on the web is a server that answers requests sent to particular addresses. Your app sends an HTTP request ("GET this URL") and the server sends back a response: a status code (200 = OK, 401 = not authorised, 404 = not found...) and a body, here text in JSON format.

The URL carries your question. Everything after the ? is the query string: name=value pairs joined by &, for example lat=33.44&lon=-94.04. The appid pair carries your API key, which tells OpenWeather who is asking (and whose quota to count).

"If you try to hit this whole URL with no API key, we're going to get an error ... telling us that we're forbidden from accessing it. If you've worked with APIs in the past ... this is pretty much how all APIs work. If you want to use the service, you have to get a key through the service first" (11:18). (The presenter says "error 400"; OpenWeather actually answers a missing or wrong key with 401.)

A brand-new key can take some time before OpenWeather accepts it; if you get 401 Invalid API key right after creating one, wait a little and try again. New to environment variables in Vite? What import.meta.env really does

An environment variable is a named setting kept outside the code, so the same code can run with different values (your key, a teammate's key, a production key). Vite loads .env, .env.local and a few other files when the dev server or the build starts, and exposes every VITE_ variable to your code as import.meta.env.VITE_... (see Vite env).

Two consequences beginners often miss:

  • Changes need a restart. Vite reads the file at start-up. After editing .env.local, stop the dev server and run npm run dev again.
  • The value is not hidden from users. Vite replaces import.meta.env.VITE_API_KEY with the actual text of your key when it serves or builds the code. This was verified for this guide: building with VITE_API_KEY=TESTKEY puts "TESTKEY" into the JavaScript files in dist/assets/ (twice). Anyone visiting a deployed copy can read it in the browser's developer tools or the network tab, where it appears in every request URL.

So .env.local keeps the key out of your Git repository, which matters. It does not keep it secret from the people using your site. The presenter calls this "a safe and protected way" (13:08); that is true for the repository, not for a deployed app. Protecting an OpenWeather key in production needs a small server (a proxy) that adds the key on the server side. Step 28 explains the options.

New to async, await and fetch? Waiting for the network

A request over the internet takes time (tens to hundreds of milliseconds). JavaScript does not stop and wait; instead fetch immediately returns a promise, an object that will hold the answer later.

async/await lets you write waiting code that reads top to bottom. Inside a function marked async, await somePromise pauses that function until the promise has its value, while the rest of the page keeps working. An async function always returns a promise itself, which is exactly what TanStack Query's queryFn expects (step 06).

fetch is built into every browser: "fetch is the standard way in JavaScript of interacting with HTTP ... you can also use something like Axios, but for this video, we're going to keep things simple and just use fetch" (15:20). Its answer is a Response; await res.json() reads the body and turns the JSON text into a JavaScript object.

  1. Version 1: a hard-coded URL (14:59–16:10)

    The presenter copies the example URL from the docs, wraps it in backticks ("instead of using quotes, we're going to use template quotes, so we can inject some stuff in there"), parses the JSON and returns it:

The finished src/api.ts

By the end of the video the file has three functions. getWeather is what you just wrote, plus the Zod check from step 07 on line 12. getGeocode comes in step 14 and getAirPollution in step 20.

import { AirPollutionSchema } from "./schemas/airPollutionSchema"
import { GeocodeSchema } from "./schemas/geocodeSchema"
import { weatherSchema } from "./schemas/weatherSchema"

const API_KEY = import.meta.env.VITE_API_KEY

export async function getWeather({ lat, lon }: { lat: number; lon: number }) {

Testing the finished app in a real browser (with fake but valid OpenWeather answers) showed three weaknesses in this file. They do not stop the app from working on your own computer, but you should know them:

1. No res.ok check (lines 11, 19, 33). fetch does not fail when the server answers with an error status; it only fails when there is no answer at all. So when OpenWeather replies 401 (invalid key, or no One Call subscription), the code parses the error message {"cod":401,"message":"..."} as if it were weather, and Zod rejects it with a cryptic error such as ZodError ... "path": ["lat"] ... expected number, received undefined. TanStack Query then retries (3 times by default, with growing pauses; 28 requests were recorded in 20 seconds across the app's queries), and finally the page goes blank because nothing catches the error. Step 25 adds the check and a readable message, and step 26 shows the error on the card with a "Try again" button.

  const res = await fetch(url)
  if (!res.ok) {
    const body = await res.json().catch(() => null)
    throw new Error(`OpenWeather request failed (${res.status}): ${body?.message ?? res.statusText}`)
  }

2. http:// for geocoding and air pollution (lines 17 and 31). On localhost this works. Once the site is deployed on https://, browsers block plain http:// requests from it (mixed content), so the city lookup and the side panel would fail. One Call (line 9) already uses https://. The fix is to write https:// everywhere; OpenWeather supports it for all three (step 25).

3. The city is not encoded (line 17). q=${location} inserts the text as-is. "New York" contains a space; browsers happen to encode that, but a name with & or # would break the URL. encodeURIComponent(location) makes any text safe inside a query string (step 25).

What you should see

  • A file .env.local next to package.json with one line, VITE_API_KEY="...". In VS Code's sidebar it appears greyed out, because Git ignores it.
  • src/api.ts matching the 20:12 version, with no red underlines.
  • Optional check: paste the full URL with your real key and some coordinates into the browser's address bar. You should see a long JSON text starting with {"lat":...,"lon":...,"timezone":.... If you see {"cod":401, ...}, read the message: an invalid key, or no One Call subscription.

Common mistakes

  • Forgetting to restart the dev server after creating or editing .env.local. import.meta.env.VITE_API_KEY stays undefined, and the request URL ends in appid=undefined (visible in the browser's Network tab).
  • Naming the variable API_KEY or REACT_APP_API_KEY (the old Create React App convention). Vite only exposes names that start with VITE_.
  • Putting .env.local inside src/. Vite looks for it in the project root.
  • Normal quotes instead of backticks: "...lat=${lat}..." sends the literal text ${lat}. Only backticks make ${...} work.
  • A 401 even with a correct key: the account has no One Call by Call subscription, or the key is brand new and not active yet.
  • Committing a .env file (not .env.local). The template's .gitignore does not cover it; add it.
  • Swapping latitude and longitude. Both are numbers, so TypeScript cannot tell. Latitude is north-south (−90 to 90), longitude east-west (−180 to 180). Using the object form { lat, lon } makes this mistake less likely.
Recap
  • One Call API 3.0 gives current, hourly and daily weather for any coordinates; it needs the separate "One Call by Call" subscription.
  • The key lives in .env.local as VITE_API_KEY; *.local in .gitignore keeps it out of Git. A plain .env would not be ignored.
  • import.meta.env.VITE_API_KEY reads it; restart the dev server after changes. Any VITE_ value ends up in the browser and is public once deployed.
  • getWeather({ lat, lon }) builds the URL with a template literal (units=imperial, exclude=minutely,alerts), awaits fetch, parses JSON and returns it.
  • The final api.ts lacks a res.ok check and uses http:// for two APIs; step 25 fixes both.
