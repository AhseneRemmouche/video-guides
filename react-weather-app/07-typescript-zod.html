TypeScript Support with Zod

Describe the API response with a Zod schema and get typed data.

▶ Watch this part (23:18)

Goal

Replace the type any on the weather data with an exact type, by describing the One Call response with a Zod schema and checking every answer against it. This chapter runs from 23:17 to 28:33.

"Working with data that has type any is generally a big no-no with modern TypeScript apps, primarily because it makes it so easy to try and access things that don't actually exist, and it just leads to a lot of potential errors" (23:41). "Having smart types where you can get IntelliSense and you can know what properties exist and what you can and can't do is super super helpful as a developer, and lacking it makes developing 10 times harder" (24:03).

New to Zod? A schema is a type that also checks at run time

TypeScript types exist only while you write code; they are erased before the code runs. So TypeScript cannot know what an API will really send. You could write a type by hand (type Weather = { lat: number; ... }) and tell TypeScript "trust me", but if OpenWeather sends something different, nothing notices until the page crashes somewhere else.

Zod solves both problems with one description. A schema such as z.object({ lat: z.number() }) is a real JavaScript object that exists at run time:

  • schema.parse(value) checks a value (validation). If it matches, you get it back; if not, it throws a ZodError that says exactly which field is wrong.
  • TypeScript can read the schema too, so parse returns the exact type, and z.infer<typeof schema> gives you that type by name.

"It's basically a type validation library that will ensure all of your API calls are typed properly ... It'll also throw errors if your API response doesn't match the type that you give it" (24:03). The lockfile pins Zod 4.1.12.

    Two things the schema does on purpose. Fields that the API sends but the schema does not list (such as snow) are not an error: z.object simply leaves them out of the result (verified with Zod 4.1.12). And minutely and alerts are not listed because the URL excludes them.

    Required fields that are sometimes missing. If any field marked required is absent from a real answer, parse throws and the whole query fails, even though 99% of the data was fine. wind_gust in current was fixed this way; in hourly and daily it is still required, and OpenWeather describes gusts as sent "where available". If a card ever fails with a ZodError whose path ends in "wind_gust", add .optional() there too. The same lesson bites harder in step 14, where a required local_names breaks the city lookup for many places.

  5. Use the schema in getWeather (27:07–27:30)

    "Instead of just returning data like we are here, what we can actually do is we can return the weather schema ... make sure we import that from the schema we just made. .parse, and then we pass in our data just like this." The file at 27:30 (VS Code's automatic import adds a semicolon, which Prettier removes on save):

    import { weatherSchema } from "./schemas/weatherSchema"

const API_KEY = import.meta.env.VITE_API_KEY

export async function getWeather({ lat, lon }: { lat: number; lon: number }) {
  const res = await fetch(
    `https://api.openweathermap.org/data/3.0/onecall?lat=${lat}&lon=${lon}&units=imperial&exclude=minutely,alerts&appid=${API_KEY}`
  )
  const data = await res.json()
  return weatherSchema.parse(data)
}

Naming the type with z.infer (not in the video)

The video never needs the type's name, because useQuery passes it on automatically. When you want to pass the weather data to a component as a prop or write a helper function, you can derive the type from the schema instead of writing it again:

import { z } from "zod"
import { weatherSchema } from "./schemas/weatherSchema"

type Weather = z.infer<typeof weatherSchema>

function describe(weather: Weather) {
  return `${weather.current.temp}°F, ${weather.current.weather[0].description}`
}

New to reading Zod errors? parse versus safeParse

A ZodError lists one entry per problem, each with a path (where in the object, for example ["hourly", 3, "wind_gust"] = the wind_gust of the fourth hourly item), what was expected, and a message. Find that place in the Network tab's response and compare.

parse throws on failure, which suits TanStack Query: a thrown error marks the query as failed. safeParse never throws; it returns { success: true, data } or { success: false, error }, which is handy when you want to decide yourself what to do with bad data.

Remember from step 05: when OpenWeather answers with an error (401), the body is {"cod":401,"message":"..."}, so parse complains about lat. The Zod message is then a symptom; the real cause is in the response's status and message. Step 25 checks res.ok first so you see the real cause.

What you should see

  • A new folder src/schemas/ with weatherSchema.ts (about 100 lines).
  • The page still shows the same wall of JSON, with no errors in the browser console.
  • Hovering data in App.tsx shows the full object type instead of any; typing data?. lists current, daily, hourly, lat, lon, timezone, timezone_offset.

Common mistakes

  • The page goes empty after adding parse, and after a few seconds the console shows a ZodError. The schema and the real answer differ. Read the path, look at that field in the Network tab, and fix the schema (often by adding .optional()).
  • z is not defined or red underlines everywhere in the schema file: the import { z } from "zod" line is missing, or Zod is not installed.
  • Returning data instead of weatherSchema.parse(data): no error, but data stays any.
  • Forgetting z.array(...) around hourly or daily: Zod reports "expected object, received array".
  • Trusting a generated schema blindly. It matches one sample answer. Test with several places (try a place with rain, a calm day) and read the API documentation for fields described as optional or "where available".
  • Treating a ZodError about lat as a schema bug. It usually means the request failed (wrong key, missing subscription). Check the status in the Network tab first.
Recap

  • A Zod schema mirrors the JSON: z.object, z.array, z.number, z.string, and .optional() for fields that may be missing.

  • A mismatch throws a ZodError whose path tells you which field to fix.
