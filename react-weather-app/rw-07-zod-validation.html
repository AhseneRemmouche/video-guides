Validating Data with Zod

Schemas, inferred types, optional fields, parse vs safeParse and reading Zod errors.

In step 7 the presenter hovered over the weather data and saw the type any (at 23:17). They described the response with a Zod schema and called .parse(data) (at 27:29), and from then on TypeScript knew every field. Later steps added schemas for geocoding and air pollution. This chapter explains what a schema really is, how the types are generated from it, how to describe fields that may be missing, the difference between parse and safeParse, and, most usefully, how to read a ZodError when something goes wrong.

Why this matters for your project. Two of the bugs found when testing this app surfaced as Zod errors. A city without local_names made the geocode schema fail, and the app silently showed the weather for 0,0. An invalid API key produced expected number, received undefined at path ["lat"], which looks like a data problem but is really an HTTP 401. If you can read a Zod error, you can tell those situations apart in seconds.

All behaviour below was checked against the installed zod 4.1.12. Outputs shown as comments are real outputs from Node; type examples were compiled with tsc in strict mode.

The problem: TypeScript stops at the network

TypeScript checks your code before it runs. Then the types are erased: the JavaScript that runs in the browser has no idea what a number is supposed to be. res.json() returns Promise<any>, because TypeScript cannot know what a server will send. The presenter calls working with any "a big no no" (at 23:41): you can type data.curent.temp with a typo and nothing warns you.

You could write a type by hand and cast: const data = (await res.json()) as Weather. That only tells TypeScript to trust you. If the server sends something else, the code carries on with wrong data and crashes later, far from the cause. Validation means actually checking the data when it arrives. Zod does that, and gives you the TypeScript type for free.

A schema is a description you can run

A schema is a JavaScript object that describes the shape of some data. You build it from small pieces. Here is the project's air pollution schema, src/schemas/airPollutionSchema.ts (shortened):

import z from "zod"

export const AirPollutionSchema = z.object({
  coord: z.object({
    lat: z.number(),
    lon: z.number(),
  }),
  list: z.array(
    z.object({
      dt: z.number(),
      main: z.object({
        aqi: z.number(),
      }),
      components: z.object({
        co: z.number(),
        // ... no, no2, o3, so2, pm2_5, pm10, nh3
      }),
    })
  ),
})

Read it from the outside in: "an object with a coord object and a list array; each list item has a number dt, an object main with a number aqi, and so on". The pieces you will use most:

PieceAcceptsIn this project
z.string(), z.number(), z.boolean()one primitive valuetimezone, temp
z.object({...})an object with these keys (extra keys are dropped)every schema
z.array(item)an array where every element matches itemhourly, daily, the geocode result
z.record(keySchema, valueSchema)an object used as a dictionary, any keyslocal_names (language code to name, e.g. { en: "Tokyo", ... })
z.enum(["a", "b"]), z.literal("a")one of a fixed set of valuesnot used; a good fit for the map types

Two Zod 4 details visible in the project. First, both import styles work: import z from "zod" (geocode and air pollution schemas) and import { z } from "zod" (weather schema). In 4.1.12 the default export is the same object as the named z. Second, z.record needs two arguments in Zod 4, the key schema and the value schema, as the project writes it: z.record(z.string(), z.string()). A one-argument z.record(z.string()), common in older Zod 3 examples, crashed when tested (Cannot read properties of undefined (reading '_zod')).

New to "extra keys are dropped"? What z.object does with unknown fields

OpenWeather sends more fields than the schema lists. By default z.object strips them: z.object({ a: z.number() }).parse({ a: 1, extra: 2 }) returns {"a":1}. That keeps your data small and matching its type. Zod 4 also has z.looseObject, which keeps unknown keys (returns {"a":1,"b":2}), and z.strictObject, which rejects them with Unrecognized key: "b". For third-party APIs the default (strip) is right: the provider may add new fields at any time and that should not break your app.

z.infer: the type comes from the schema

The real trick is that you do not write the TypeScript type separately. Type inference works it out from the schema with z.infer:

const GeocodeSchema = z.array(z.object({
  name: z.string(),
  local_names: z.record(z.string(), z.string()).optional(),
  lat: z.number(), lon: z.number(), country: z.string(), state: z.string().optional(),
}))
type Geocode = z.infer<typeof GeocodeSchema>
// { name: string; local_names?: Record<string, string> | undefined; lat: number; ... }[]

const g: Geocode = [{ name: "Tokyo", lat: 35.68, lon: 139.69, country: "JP" }]   // OK
// @ts-expect-error lat must be a number
const bad: Geocode = [{ name: "X", lat: "1", lon: 2, country: "JP" }]

The project never even writes z.infer in the original code. It does not need to: weatherSchema.parse(data) already returns the inferred type, so getWeather's return type, and therefore data in every card, is typed automatically. The improved api.ts from step 25 uses z.infer inside a generic helper so one function can validate any schema:

async function fetchJson<T extends z.ZodType>(url: string, schema: T): Promise<z.infer<T>> {
  const res = await fetch(url)
  if (!res.ok) {
    const body = await res.json().catch(() => null)
    throw new Error(`OpenWeather request failed (${res.status}): ${body?.message ?? res.statusText}`)
  }
  return schema.parse(await res.json())
}

T extends z.ZodType means "any Zod schema". z.infer<T> means "the data type that schema describes". Pass weatherSchema and you get weather data; pass GeocodeSchema and you get an array of places.

Fields that may be missing: optional, nullable, nullish

Real APIs leave fields out. OpenWeather's geocoding results include state only for some countries, and local_names is missing for many smaller places. Zod has three modifiers, and they mean different things:

ModifierAllows the key to be missing / undefinedAllows nullInferred type
z.string().optional()yesnostring | undefined (key optional)
z.string().nullable()noyesstring | null
z.string().nullish()yesyesstring | null | undefined

Checked with z.object({ a: z.string().optional(), b: z.string().nullable(), c: z.string().nullish() }): { b: null } passes; {} fails (b is nullable but still required); { a: null, b: "x" } fails (optional does not accept null). Pick the modifier from the API's documentation: "may be absent" means optional, "may be null" means nullable.

In the repo, state and current.wind_gust are optional, but local_names is required. That one line caused a real bug, fixed in step 25 by adding .optional():

    local_names: z.record(z.string(), z.string()).optional(),

Note that hourly[].wind_gust is still required in the weather schema while current.wind_gust is optional. The test data included it, so this was not observed failing; if you see a ZodError with a path ending in "wind_gust", you know where to look.

parse or safeParse?

Both run the same check. They differ in how they report failure.

schema.parse(data)schema.safeParse(data)
Valid datareturns the datareturns { success: true, data }
Invalid datathrows a ZodErrorreturns { success: false, error } (a ZodError)
Good forcode where a thrown error is already handled (a query function)code that wants to branch: forms, optional data, logging

The project uses parse inside query functions, and that is the right choice. When a query function throws, TanStack Query marks the query as failed, retries, and finally exposes the error (or throws it to an error boundary for suspense queries; see chapter 6). safeParse is for when you want to decide yourself:

const result = GeocodeSchema.safeParse(json)
if (!result.success) {
  console.warn(z.prettifyError(result.error))
  return []                      // treat as "no match" instead of failing
}
result.data[0]?.lat              // typed as number

(safeParse and prettifyError were run in Node against the real Zod; the surrounding function is a sketch.)

Reading a ZodError

A ZodError contains a list called issues. Each issue has a code (the kind of problem), a path (where in the data), a human message, and extra details such as expected. The error's message is that list printed as JSON. Here are the two real examples from testing this app, reproduced in Node with the project's schemas.

Example 1: a place without local_names

GeocodeSchema.safeParse([{ name: "Smallville", lat: 1, lon: 2, country: "US" }])

[
  {
    "expected": "record",
    "code": "invalid_type",
    "path": [
      0,
      "local_names"
    ],
    "message": "Invalid input: expected record, received undefined"
  }
]

Read the path like an address: item 0 of the array, field local_names. "Expected record, received undefined" means the field was not there at all. The fix is in the schema (make it optional), not in the data.

Example 2: an error response parsed as weather

With an invalid key, OpenWeather answers status 401 with a body like {"cod":401,"message":"Invalid API key. ..."}. The repo's getWeather never checks res.ok, so that body goes straight into weatherSchema.parse:

[
  {
    "expected": "number",
    "code": "invalid_type",
    "path": [
      "lat"
    ],
    "message": "Invalid input: expected number, received undefined"
  },
  {
    "expected": "number",
    "code": "invalid_type",
    "path": [
      "lon"
    ],
    "message": "Invalid input: expected number, received undefined"
  },
  ...

(Shortened: the run against a three-field schema produced three issues; the full weather schema produces one per missing top-level field.) The clue is that every top-level field is missing. That never means "the weather changed shape"; it means "this is not a weather response". Look at the Network tab: the status will be 4xx or 5xx. Step 25's fetchJson checks res.ok first, so the user sees OpenWeather request failed (401): Invalid API key... instead.

Friendlier output in Zod 4

Zod 4 adds helper functions that format an error. Both exist in 4.1.12 and produced these outputs for example 1:

z.prettifyError(error)
✖ Invalid input: expected record, received undefined
  → at [0].local_names

z.treeifyError(error)   // nested object that mirrors the data shape
{"errors":[],"items":[{"errors":[],"properties":{"local_names":{"errors":["Invalid input: expected record, received undefined"]}}}]}

prettifyError is ideal for console.error. treeifyError (and z.flattenError for flat objects) is meant for forms, where you show each message next to its field. Custom messages use the error parameter in Zod 4; a plain string still works as a shortcut. Both were checked:

z.string().min(1, { error: "City name is required" })   // message: "City name is required"
z.string().min(1, "Short form")                          // message: "Short form"

Where validation belongs

Validate once, at the edge of your app, right where untrusted data enters. In this project that edge is api.ts. Everything behind it (the cache, the cards, the side panel) can trust the types completely. Do not sprinkle checks like if (typeof data.current.temp === "number") through components; that is exactly what the schema already guarantees.

Common misconceptions
  • "TypeScript types protect me from bad API data." They are erased before the code runs. Only a run-time check like Zod does.
  • "as Weather is the same as parsing." A cast is a promise you make to the compiler; nothing is checked.
  • "optional and nullable are the same." optional allows missing/undefined, nullable allows null. Use nullish for both.
  • "A ZodError means the API changed." Often it means you validated an error response. Check res.ok first.
  • "Make every field optional to be safe." Then every component must handle undefined. Mark only what the API documents as optional, and let surprises fail loudly.
  • "Old Zod 3 examples work unchanged." Mostly, but not all: Zod 4 needs two arguments for z.record and uses { error: ... } for custom messages.
Recap
  • A schema describes data and can check it at run time; z.infer turns the same schema into a TypeScript type.
  • parse returns data or throws a ZodError; safeParse returns { success, data | error }. Inside a query function, parse is right.
  • optional = may be missing, nullable = may be null, nullish = either. local_names needed .optional().
  • Read an issue's path and expected/received. Many "received undefined" at the top level means you parsed an error response.
  • Zod 4 extras: z.prettifyError, z.treeifyError, z.looseObject/z.strictObject, { error } messages, two-argument z.record.
  • Validate once, at the boundary (api.ts), after checking res.ok.
