JavaScript & TypeScript Essentials for React

Modules, arrow functions, destructuring, promises, async/await, types, generics and type inference.

What you will learn

React code is ordinary JavaScript with a little extra syntax. Most "React problems" beginners hit are really JavaScript problems: a curly brace in the wrong place, a ?. that hides a bug, an await that was forgotten. This chapter covers the language features the weather dashboard uses on almost every line, and shows each one in the project's real files.

  • modules: import and export, default and named, and import type;
  • arrow functions, callbacks and why React passes functions around;
  • destructuring, spread and rest: ({ coords }: Props), const [location, setLocation] = useState(...);
  • template literals for the OpenWeather URLs;
  • optional chaining and nullish coalescing, including the bug they hide in App.tsx;
  • promises and async/await in api.ts;
  • TypeScript: types, unions, optional properties, generics, type inference and narrowing.
Why this matters for your project. The single line that decides which coordinates every card fetches, { lat: geocodeData?.[0].lat ?? 0, ... } in App.tsx, uses three features from this chapter at once. Read it correctly and you can see why the app first requests weather for latitude 0 / longitude 0, and why an empty search result crashes the page (both found while testing the finished app, fixed in step 25).

JavaScript, TypeScript and what the browser runs

The browser only understands JavaScript. TypeScript is JavaScript plus type annotations: notes such as lat: number that say what kind of value a variable holds. Before the browser sees your code, the annotations are simply removed. Vite does that removal while it serves and bundles the files (see chapter 3). Checking whether the types are actually correct is a separate job done by the TypeScript compiler, tsc, which this project runs as the first half of npm run build ("build": "tsc -b && vite build").

That split explains a common surprise: during npm run dev the page can still load while your editor shows red squiggles. The types are a safety net that you (and the build) must look at; they do not protect the running page on their own. Data that arrives from the internet is not checked by TypeScript at all, which is why the project validates API responses with Zod (chapter 7).

Modules: import and export

Every .ts and .tsx file in src/ is a module: its variables are private unless the file exports them, and other files must import what they use. The project uses three flavours.

Paths that start with ./ or ../ are relative to the current file. Paths without a dot, like "react", come from node_modules. Two more forms appear in the project: "@/api" (a path alias for src/, set up in step 12 and explained in chapter 3) and "/src/assets/hamburger.svg?react", where the ?react suffix asks the svgr plugin to turn the SVG file into a component (step 9).

Why import type? The project's tsconfig.app.json turns on "verbatimModuleSyntax": true, which means "keep every normal import in the output exactly as written". A type has nothing to keep, so TypeScript insists you mark it. We tried a plain import of a type in a copy of the project:

when 'verbatimModuleSyntax' is enabled.

Inline marking works too, and the project uses it: import { Suspense, type Dispatch, type SetStateAction } from "react" in SidePanel.tsx.

Functions, arrow functions and callbacks

JavaScript has two common ways to write a function. A function declaration, function App() { ... }, is used for every component and every API helper. An arrow function, (lat, lon) => { ... }, is a shorter form used for small functions that are created inside other code. When the body is a single expression you can drop the braces and the return: () => getGeocode(location) returns whatever getGeocode returns.

  const { data: geocodeData } = useQuery({
    queryKey: ["geocode", location],
    queryFn: () => getGeocode(location),
  })

  const onMapClick = (lat: number, lon: number) => {
    setCoords({ lat, lon })
    setLocation("custom")
  }

Both arrows here are callbacks: functions you hand to someone else to call later. TanStack Query calls queryFn when it needs data; the map calls onMapClick when the user clicks. Notice the difference between queryFn: () => getGeocode(location) and queryFn: getGeocode(location). The first passes a function. The second would call getGeocode immediately, on every render, and pass its promise, which is not what the library expects. The same rule applies to event handlers: onClick={() => setIsSidePanelOpen(true)} in App.tsx waits for the click; onClick={setIsSidePanelOpen(true)} would run during rendering.

A third form appears in SidePanel.tsx: an arrow function that is called the moment it is defined, const qualityColor = (() => { switch (...) { ... } })(). This is an immediately invoked function expression. It lets you use statements like switch or for to compute a single value inside a component. A small named helper function would do the same job and is often easier to read.

Objects, arrays and destructuring

Destructuring unpacks values from an object or array into separate variables. It looks like an object or array literal on the left of the =. The project uses it constantly:

Spread and rest: the three dots

Three dots mean two opposite things depending on where they stand. On the right side or in JSX they spread: <AirPollution {...props} /> passes every property of props as a separate prop. In a destructuring pattern on the left they collect the rest: the shadcn file switch.tsx has function Switch({ className, ...props }), which takes className out and gathers every other prop into props, then forwards them with {...props}. This "take what I need, forward the rest" pattern is how wrapper components work.

New to objects and arrays? A one-minute refresher

An object groups named values: { lat: 35.68, lon: 139.69 }. Read a property with a dot, coords.lat, or with brackets, coords["lat"]. A shorthand: { lat, lon } means { lat: lat, lon: lon } when variables with those names exist — setCoords({ lat, lon }) in App.tsx uses it.

An array is an ordered list: ["Tokyo", "Seoul"]. Read an item by position, starting at 0: geocodeData[0] is the first result. Arrays have helpers that take a callback: map builds a new array (the project maps hourly data to JSX), join glues items into a string (MapLegend.tsx builds a CSS gradient), and Object.entries(obj) turns an object into [key, value] pairs (SidePanel.tsx loops over pollutants).

Template literals: building the API URLs

Strings in backticks are template literals. Anything inside ${...} is evaluated and inserted. Every OpenWeather URL in the project is built this way:

  const res = await fetch(
    `https://api.openweathermap.org/data/3.0/onecall?lat=${lat}&lon=${lon}&units=imperial&exclude=minutely,alerts&appid=${API_KEY}`
  )

Three values are inserted: the coordinates and the API key. Template literals do not encode anything for you. A city name with a space or an & is pasted in as-is, which is why chapter 5 recommends encodeURIComponent or URLSearchParams for user-supplied values. The same feature builds the weather icon address in WeatherIcon.tsx (`https://openweathermap.org/img/wn/${src}.png`) and the gradient string in MapLegend.tsx.

Optional chaining and nullish coalescing

When data comes from the network, it is missing at first. Optional chaining, ?., reads a property only if the thing on its left exists; if the left side is null or undefined, the whole expression stops and becomes undefined instead of throwing an error. Nullish coalescing, ??, supplies a fallback when the left side is null or undefined. Together they appear in the most important line of App.tsx:

  const coords =
    location === "custom"
      ? coordinates
      : { lat: geocodeData?.[0].lat ?? 0, lon: geocodeData?.[0].lon ?? 0 }

The presenter adds the ?. at about 2:22:41 to silence TypeScript's "possibly undefined" error (step 14). Read the expression left to right: if geocodeData is undefined, stop and produce undefined; otherwise take item [0], then its .lat. Then ?? 0 replaces undefined with 0. We ran the same expression in Node with the three situations the app can be in:

let geocodeData // undefined: the query is still loading
console.log(geocodeData?.[0].lat ?? 0)

geocodeData = [{ lat: 35.68, lon: 139.69 }] // Tokyo found
console.log(geocodeData?.[0].lat ?? 0)

geocodeData = [] // the API found nothing
console.log(geocodeData?.[0]?.lat ?? 0) // extra ?. after [0]
console.log(geocodeData?.[0].lat ?? 0)  // the repo's version

0
35.68

TypeError: Cannot read properties of undefined (reading 'lat')

Two lessons follow. First, ?. only guards one step; to survive an empty array you need geocodeData?.[0]?.lat. Second, a fallback value is a decision, not a fix. ?? 0 means "pretend we are at latitude 0, longitude 0" — a real place in the Gulf of Guinea — so the cards happily fetch weather for it while the real coordinates load. That is the "flicker to the middle of the ocean" the presenter notices around 2:28:00 (step 15). A better plan is "no coordinates yet, don't fetch" (TanStack Query's enabled option, used in step 25).

Why ?? and not ||

Older code uses || for fallbacks. It treats every "falsy" value as missing, and 0 is falsy. For coordinates that is wrong, because 0 is a valid latitude:

const lat = 0 // the equator is a real latitude
console.log(lat || 50) // 50 — the real value was thrown away
console.log(lat ?? 50) // 0  — only null/undefined are replaced

Use ?? when 0, "" or false are legitimate values. The project's temperature, wind speed and AQI values can all be 0.

Promises and async/await

Fetching data over the network takes time, and JavaScript never stops the page to wait. Instead, fetch immediately returns a promise: an object that stands for a value that will arrive later (or an error). async and await let you write code that waits for promises while still looking like ordinary top-to-bottom code. All three helpers in api.ts follow the same shape:

export async function getGeocode(location: string) {
  const res = await fetch(
    `http://api.openweathermap.org/geo/1.0/direct?q=${location}&limit=1&appid=${API_KEY}`
  )
  const data = await res.json()
  return GeocodeSchema.parse(data)
}
  1. async function marks the function as asynchronous. It always returns a promise, even though the last line returns a plain array. TypeScript shows the return type as Promise<...>; the presenter points this out at about 2:17:26.
  2. await fetch(...) pauses this function only until the server answers with headers. The rest of the page keeps running.
  3. await res.json() waits again, this time for the body to be downloaded and parsed from JSON text into a JavaScript value.
  4. return GeocodeSchema.parse(data) validates the shape and becomes the promise's final value. If parse throws, the promise is rejected instead.

The order of events surprises many beginners. This script shows it:

async function getNumber() {
  console.log("2. inside, before await")
  const value = await Promise.resolve(42)
  console.log("4. after await:", value)
  return value
}
console.log("1. before the call")
const promise = getNumber()
console.log("3. call returned a Promise:", promise instanceof Promise)
const result = await promise
console.log("5. awaited result:", result)

Errors in async code

Inside an async function, a throw (or a rejected await) rejects the returned promise. You handle it with try { ... } catch (e) { ... } around the await, or let the caller handle it. The project lets TanStack Query catch errors: it retries, then shows the error to the nearest error boundary (step 26). One trap: fetch only rejects when the request could not be made at all (offline, blocked, bad host). A server answer of 401 or 500 is a successful fetch with res.ok === false. The project never checks res.ok, so an "Invalid API key" body is handed to Zod and fails with a confusing validation error. Chapter 5 shows the check.

New to strict mode? What "strict": true turns on

tsconfig.app.json sets "strict": true. The most visible effect is strict null checks: undefined and null are not allowed where a value is expected unless the type says so. That is why TypeScript complained that geocodeData was "possibly undefined" in step 14, and why title?: string must be handled as string | undefined. The project also turns on noUnusedLocals and noUnusedParameters, so an unused variable stops npm run build.

Type inference: types you don't write

You rarely need to annotate everything. TypeScript infers types from values. useState("Tokyo") needs no <string> because the starting value is a string — that is why setLocation(42) failed above without any annotation. You write the generic when the starting value can't tell the whole story, e.g. useState<Theme>("dark") in ThemeProvider.tsx: without it, the state would be the wider type string and any string would be accepted.

Narrowing

When a value can be several types, TypeScript narrows it after a check. The useTheme hook shows the classic case:

export const useTheme = () => {
  const context = useContext(ThemeContext)
  if (!context) throw new Error("useTheme must be used within a ThemeProvider")
  return context
}

useContext returns ThemeContextType | undefined. After if (!context) throw ..., TypeScript knows the undefined case can't reach the next line, so return context has the type ThemeContextType and callers can use theme and toggleTheme without ?.. Comparing with === narrows too: inside if (value === "sunrise" || value === "sunset") in AdditionalInfo.tsx, the code knows which case it is in.

Common misconceptions
  • "TypeScript checks the API response." No. Types are erased; at run time the response can be anything. That is Zod's job.
  • "?. makes the whole chain safe." It protects only the property access right after it. a?.[0].lat still throws when a is an empty array.
  • "|| 0 and ?? 0 are the same." Not when the value can be 0, "" or false.
  • "await blocks the page." It pauses only the async function it is in.
  • "as and ! convert or check values." They only silence the compiler. If you are wrong, you get a run-time error later.
  • "fetch throws on 404 or 401." It resolves; check res.ok yourself.
Recap
  • Every file is a module; use default exports for components, named exports for helpers, and import type for types (required by verbatimModuleSyntax).
  • Pass functions (() => getGeocode(location)), don't call them, when a library or event will call them later.
  • Destructuring unpacks props, hook results and API objects by name or position; three dots spread or collect the rest.
  • ?. guards one step, ?? replaces only null/undefined; a fallback like 0 is a real value and has consequences.
  • async functions return promises at once; await waits inside the function; fetch resolves even for error status codes.
  • TypeScript types (unions, optional properties, generics) catch mistakes before the build, and inference from the Zod schema gives typed data with no extra annotations.
