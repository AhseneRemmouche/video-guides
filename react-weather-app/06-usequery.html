useQuery

Fetch weather data with useQuery: query keys, query functions, loading and data.

▶ Watch this part (20:10)

Goal

Call getWeather from a component with TanStack Query's useQuery hook, print the raw answer on the page, and inspect it in the browser's Network tab. This chapter runs from 20:10 to 23:18. It is the first time the app talks to the internet: "Our React app is now interfacing with an external API, grabbing the appropriate weather data depending on what we pass into the getWeather function" (22:55).

The result is deliberately ugly, "a huge wall of text", but it proves the whole chain works: the key, the URL, the fetch, the provider from step 04 and the query.

New to hooks? What useSomething means

A hook is a function whose name starts with use and which a component calls to get a React feature: useState gives it memory, useEffect lets it run code after drawing, useQuery gives it server data. Hooks follow two rules: call them only at the top level of a component (not inside if, loops or nested functions), and only from components or other hooks. React relies on the order of hook calls to know which value belongs to which call.

When a hook's value changes (the data arrives), React calls your component function again and draws the new result. This is called rendering; a component may render many times.

New to useQuery? The two things you give it and what you get back

useQuery takes one options object with two required parts:

  • queryKey, an array that names the data, for example ["weather"]. It is the label of the drawer in the cache where the answer is stored. Two components with the same key share one request and one answer. When the key changes, TanStack Query fetches again. See query key.
  • queryFn, a function that returns a promise of the data: here, a function that calls getWeather. TanStack Query decides when to call it. See query function.

It returns an object with many fields. The common ones: data (the answer, or undefined until it arrives), isLoading (true while the first request is running), error (the error if the query failed after its retries), isError, isSuccess and refetch. The video only uses data.

The key should contain the coordinates

With queryKey: ["weather"], the cache has one drawer called "weather". When you change lat: 50 to lat: 10 and save, hot reloading redraws App, but the key is still ["weather"], so TanStack Query may simply hand back the answer it already has for 50, 50. A full page reload empties the cache, which is why the presenter's refresh shows the new place.

The rule: everything the query function depends on belongs in the key. Once coordinates come from state (a dropdown or a map click, steps 11–15), a fixed key would show the wrong city's weather. The finished cards do exactly this: queryKey: ["weather", coords] in CurrentWeather.tsx, HourlyForecast.tsx, DailyForecast.tsx and AdditionalInfo.tsx. Because all four use the same key, there is one request for all of them.

Try it: showing loading and errors (not in the video)

The video only reads data. The same hook also tells you when it is loading or failed. This small variation of the 21:50 version (illustrative, not built separately; it only uses fields useQuery always returns) makes the page friendlier and puts the coordinates into the key:

function App() {
  const coords = { lat: 10, lon: 25 }
  const { data, isLoading, error } = useQuery({
    queryKey: ["weather", coords],
    queryFn: () => getWeather(coords),
  })

  if (isLoading) return <p>Loading weather...</p>
  if (error) return <p>Something went wrong: {error.message}</p>

  return <pre>{JSON.stringify(data, null, 2)}</pre>
}

New to JSON.stringify? Turning objects into text

JSON is a text format for data. res.json() in step 05 turned OpenWeather's JSON text into a JavaScript object; JSON.stringify(value) does the reverse. Its optional second argument filters properties (null = keep all) and the third sets the indentation. It is the quickest way to "see" an object while developing; console.log(data) in the browser console is the other.

Finally, hover data in VS Code. The tooltip says its type is any. "This, for one, is completely expected ... TypeScript really has zero way of inferring what the actual data type looks like" (23:17). That is the problem the next step solves.

Common mistakes

  • The page stays empty and the Network tab shows a 401, retried several times. Click the request and read the Response: "Invalid API key" (check .env.local, restart the dev server) or the One Call subscription message (subscribe, see step 05).
  • No QueryClient set, use QueryClientProvider to set one: the provider from step 04 is missing in main.tsx.
  • queryFn: getWeather({ lat: 10, lon: 25 }) without () =>. That calls the function immediately and passes a promise instead of a function; TypeScript underlines it. Keep the arrow.
  • return <>{data}</> without JSON.stringify: React throws "Objects are not valid as a React child". Convert to text first.
  • Writing data.current.temp right away: on the first render data is undefined, so the page crashes with "Cannot read properties of undefined". Use data?.current.temp or check isLoading first.
  • Changing the coordinates and seeing old data. The key does not include them; reload the page, or use ["weather", coords].
  • Calling useQuery inside an if or a click handler. Hooks must be called at the top level of the component, every render.
Recap
  • useQuery({ queryKey, queryFn }) fetches through the shared QueryClient and returns data, isLoading, error and more.
  • queryFn is a function (() => getWeather({ lat, lon })); TanStack Query decides when to call it.
  • data is undefined until the answer arrives; JSON.stringify shows the raw object as text.
  • The browser's Network tab (Fetch/XHR) is the best place to read API answers.
  • Put every input of the query into the key; the final app uses ["weather", coords].
  • data is typed any. Next: Zod gives it a real type.
