Interactive Map: Leaflet Setup

Add a Leaflet map with react-leaflet, shared coordinates and click-to-move.

▶ Watch this part (01:36:23)

Goal

Until now every card fetched the weather for the same hard-coded coordinates (latitude 10, longitude 25). Those numbers mean nothing to a user. In this step you add an interactive map and connect it to the cards: click anywhere on the map, and every card shows the weather for that spot.

You build it in four moves, the same way the presenter does on camera:

  1. Install Leaflet and react-leaflet, paste the library's quick-start example, and trim it.
  2. Listen to clicks with the useMap hook and pan the map to the clicked point.
  3. Lift the coordinates up into App as state, so the map and all four cards share one source of truth.
  4. Put the coordinates in each card's query key, so TanStack Query fetches new data when they change.

What the presenter explains

The presenter starts by saying what is missing (at 1:36:30): the cards look good, but "this 10 and 25 here is just hard-coded", so there is no way to look at the weather anywhere else. They pick Leaflet because it is "one of the most, if not the most widely used library in JavaScript for creating maps", and react-leaflet because it "wraps this entire Leaflet library and gives us super easy to use React components" (1:36:52).

After pasting the quick-start example, the map looks broken until Leaflet's CSS is imported (1:40:11). Then comes the key idea of the step (1:42:49): react-leaflet's useMap hook gives you the Leaflet map object, but only inside MapContainer. The Map component itself renders MapContainer, so it is outside it. The fix is a tiny helper component, MapClick, rendered inside the container, that returns null because it exists only for its behaviour.

To connect map and cards, the presenter lifts the state up (1:47:22): the coordinates live in App, "the most parent component", and are passed down as props. They say that with deeper nesting they would use a context provider instead, but with direct children, props are simpler (1:48:28). Finally (1:57:04) they explain why clicking did nothing at first: all four cards used the query key ["weather"], so TanStack Query kept serving the first cached answer. "If the query key is always static, the cache value … is going to be treated as static as well."

New to web maps? Tiles, zoom levels and latitude/longitude

A web map is not one big picture. The world is cut into small square images called tiles (usually 256 × 256 pixels). At zoom 0 the whole world fits in one tile. Each zoom level doubles the number of tiles in each direction: zoom 1 has 2 × 2 tiles, zoom 2 has 4 × 4, and zoom 5 (the value used in this app) has 32 × 32 = 1,024 tiles. The browser only downloads the tiles you can see, so the map stays fast.

A tile server publishes tiles at a URL pattern like https://{s}.tile.openstreetmap.org/{z}/{x}/{y}.png: {z} is the zoom level, {x} the column, {y} the row, and {s} a server letter. Leaflet fills these in for every visible square. That is what TileLayer does.

Places are given as latitude and longitude. Latitude goes from −90 (South Pole) to 90 (North Pole); longitude goes from −180 to 180, with 0 at Greenwich, London. Leaflet always wants them in that order: [lat, lng].

New to react-leaflet? Leaflet objects vs React components

Leaflet is not a React library. In plain Leaflet you write const map = L.map(div), L.tileLayer(url).addTo(map), L.marker([10, 25]).addTo(map): you create objects and add them to the map yourself.

react-leaflet wraps those calls in components. <MapContainer> creates the L.map once, when it first appears on the page, and shares it with its children through React context. Each child (<TileLayer>, <Marker>) reads that map from context and adds its own Leaflet object to it. When a child disappears, it removes its object.

One consequence matters a lot in step 15: MapContainer reads center and zoom only when it is created. In react-leaflet 5, the code that creates the map calls map.setView(center, zoom) once and never again; later changes to the center prop are ignored. Moving an existing map is your job (map.panTo, map.setView).

Listen to clicks: useMap and MapClick

react-leaflet's useMap() returns the Leaflet map object. With it you can listen to events and move the camera. But it reads the map from the context that MapContainer provides, so it only works in components rendered inside <MapContainer>. "This map component is not wrapped inside of map container. Only the things that are actually inside of it would be" (1:43:11). Calling useMap() directly in Map throws an error from react-leaflet ("No context provided: useLeafletContext() can only be used in a descendant of <MapContainer>").

The presenter first logs the click event (1:45:31): Leaflet's mouse event has a latlng property with lat and lng. Note the spelling: Leaflet says lng, while OpenWeather and this app say lon. Then they destructure it and call map.panTo([lat, lng]), which glides the map so the clicked point becomes the centre.

Lift the coordinates into App

The cards and the map all need the same two numbers. Who should own them? The presenter's rule (1:47:22): put the state in the closest component that is a parent of everyone who needs it. Here that is App. App holds the state; children receive it as props; a child that wants to change it calls a function that App passed down.

New to lifting state up? Props down, events up

In React, data flows down: a parent passes values to children as props. A child cannot change its parent's state directly. To let a child change something, the parent passes down a function (here onMapClick) and the child calls it. Inside, the parent calls its own state setter, React re-renders the parent, and the new value flows down to every child.

Passing a prop through a component that only forwards it (here Map forwards onMapClick to MapClick) is called prop drilling. The presenter accepts two levels: "if it's only two layers … it's really not that big of a deal" (1:54:50). For deeper trees, a context provider avoids it; you will build one for the theme in step 24.

New to query keys? Why the cards did not update

TanStack Query keeps a cache: a table from query key to data. When a component asks for a key that is already in the cache, it gets the cached data straight away. With the key ["weather"], the first fetch stored the weather for 50, 45. Clicking the map changed coords, but the key was still ["weather"], so TanStack Query saw a request it had already answered and kept showing the old data. Your new queryFn never ran.

With ["weather", { lat: 48.8, lon: 2.3 }] the key is new, so TanStack Query runs the query function and stores the result under that key. Keys are compared by their contents, not by object identity, so a new object with the same numbers finds the same entry. Going back to a place you visited is instant.

import { MapContainer, Marker, TileLayer, useMap } from "react-leaflet"
import "leaflet/dist/leaflet.css"

type Props = {
  coords: Coords
  onMapClick: (lat: number, lon: number) => void
}

export default function Map({ coords, onMapClick }: Props) {
  const { lat, lon } = coords
  return (
    <MapContainer
      center={[lat, lon]}
      zoom={5}
      style={{ width: "700px", height: "500px" }}
    >
      <MapClick onMapClick={onMapClick} />
      <TileLayer
        attribution='&copy; <a href="https://www.openstreetmap.org/copyright">OpenStreetMap</a> contributors'

    const { lat, lng } = e.latlng
    map.panTo([lat, lng])
    onMapClick(lat, lng)

  return null

Known issue: map.on in the render body adds a listener on every render

map.on("click", …) sits directly in MapClick's body, with no cleanup. A component body runs on every render, and MapClick re-renders every time App does (every click, and later every dropdown change). Each render registers another click listener on the same Leaflet map, and none is ever removed. After many renders, one click runs the handler many times. It "works" because each extra call sets the same coordinates, but it is wasted work that grows over time. (This is reasoned from the code and Leaflet's API; the number of listeners was not counted in the browser test.)

The React way is to register listeners in an effect with a cleanup, or to use react-leaflet's useMapEvents hook, which does that for you. Step 25 makes that change.

The marker in a production build

In the dev server the blue pin shows up fine. In a production build of the finished app (npm run build, then npm run preview) the pin is a broken image with the alt text "Marker". This was verified in the browser test:

Why: Leaflet finds its default pin images by reading a URL out of its own CSS at runtime (_detectIconPath in Leaflet's source). In production, Vite inlines Leaflet's small marker PNGs into the CSS as data: URLs, and Leaflet then glues a file name onto that data URL, producing an invalid address. The fix is to import the three images yourself and pass an explicit L.icon({…}) to <Marker icon={…}>; step 25 does exactly that. Until then, test with npm run dev and don't be surprised by the preview build.

Common mistakes

  • Map invisible: no height on MapContainer. A Leaflet map has 0 height unless you give it one.
  • Tiles scattered all over the page, zoom buttons unstyled: forgot import "leaflet/dist/leaflet.css".
  • useMap() in Map itself → react-leaflet throws "No context provided: useLeafletContext() can only be used in a descendant of <MapContainer>". Move it into a child like MapClick.
  • Cards don't change after a click: coords missing from one of the query keys. Add it to all four.
  • e.latlng.lon is undefined: Leaflet calls it lng. Only OpenWeather (and this app's Coords) say lon.
  • Coordinates swapped: Leaflet wants [lat, lng]; GeoJSON and some other tools use [lng, lat]. A swapped pair puts Paris in Somalia.
  • Type error "Property 'coords' does not exist on type 'IntrinsicAttributes'": you passed coords to a card whose Props type does not declare it yet.

  • Query keys must include every input: ["weather", coords], otherwise the cache keeps serving the first answer.
  • Two known issues are fixed in step 25: listeners added on every render (map.on in the body) and the broken default marker in production builds.
