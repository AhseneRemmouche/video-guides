Tooling: npm, Vite, TypeScript Config & ESLint

What each config file does, dev vs build, path aliases, and reading lint errors.

What you will learn

A modern React project is surrounded by small configuration files. Beginners often copy them without reading them, then get stuck the first time one of them complains. This chapter goes through every tool and config file in the weather dashboard repo and explains what it does, when it runs and what its errors mean:

  • npm and package.json: scripts, dependencies, version ranges and the lockfile;
  • Vite: the dev server, hot module replacement, the production build, plugins and environment variables;
  • the three tsconfig files and the options that matter;
  • path aliases (@/), which must be configured in two places;
  • ESLint: what the config enables and how to read the 15 errors the repo reports.
Why this matters for your project. The repo builds, but npm run lint fails with 15 errors, the build prints a "chunks larger than 500 kB" warning, and both API keys end up in the JavaScript bundle. All three are tooling facts. Understanding them is what lets you fix them in step 25, step 27 and step 28 instead of ignoring them.

The toolchain at a glance

npm and package.json

Node.js runs JavaScript outside the browser; the build tools are Node programs. npm, which comes with Node, installs packages and runs scripts. package.json is the project's manifest:

{
  "name": "weather-project",
  "private": true,
  "version": "0.0.0",
  "type": "module",
  "scripts": {
    "dev": "vite",
    "build": "tsc -b && vite build",
    "lint": "eslint .",
    "preview": "vite preview"
  },
FieldWhat it does
"private": trueStops an accidental npm publish. Apps are not libraries.
"type": "module"Node treats .js files (like eslint.config.js) as ES modules, so they can use import/export.
"scripts"Named commands. npm run build runs tsc -b && vite build; && means "run the second only if the first succeeded", so a type error stops the build. npm adds node_modules/.bin to the path, which is why vite and eslint work without a global install.
"dependencies"Packages the app's code imports at run time: react, @tanstack/react-query, zod, leaflet...
"devDependencies"Tools used only while developing or building: vite, typescript, eslint, @types/*. (A dev dependency is not shipped to users; but for a Vite app the bundler only includes what your code imports anyway, so the split is mostly about clarity.)

Version ranges and the lockfile

package.json lists ranges, not exact versions. "react": "^19.1.1" means "19.1.1 or any later 19.x". "typescript": "~5.9.3" means "5.9.3 or a later 5.9.x patch". The exact versions actually installed are recorded in package-lock.json. In this repo the lockfile pins React 19.2.0, Vite 7.1.11, TypeScript 5.9.3, ESLint 9.38.0 and Tailwind 4.1.15.

  • npm install installs and may update the lockfile within the ranges.
  • npm ci installs exactly what the lockfile says, and fails if the two files disagree. Use it for a clean, reproducible install (this guide was verified with npm ci).
  • npx runs a package's command, downloading it first if needed — e.g. npx shadcn@latest add select in step 12.
Note on react-leaflet. The lockfile pins react-leaflet 5.0.0-rc.2, a release candidate (a pre-release). The project needs it because it targets React 19. Pre-releases can change before the final version, so check the react-leaflet release notes when you upgrade.

Vite: the dev server and the build

Vite has two very different modes.

Dev (npm run dev). Vite starts a local web server, by default on http://localhost:5173. It does not bundle the app. When the browser asks for /src/main.tsx, Vite transforms just that file (strip types, compile JSX) and sends it back as a native ES module; the browser then requests its imports one by one. Because only requested files are transformed, startup is quick. When you save a file, Vite pushes the change to the browser over a WebSocket and React swaps the component in place, keeping state where possible. That is hot module replacement (React's flavour is called Fast Refresh).

Build (vite build). Vite bundles everything reachable from index.html into a few optimised files in dist/: code is combined, unused exports dropped, everything minified, and filenames get a content hash (index-D0DHRQhv.js) so browsers can cache them safely forever. We built the committed repo:

dist/index.html                 0.48 kB │ gzip:   0.31 kB
dist/assets/index-wTnJkFd2.css   51.22 kB │ gzip:  13.75 kB
dist/assets/index-D0DHRQhv.js  2,005.91 kB │ gzip: 558.90 kB
(!) Some chunks are larger than 500 kB after minification. Consider:
- Use build.rollupOptions.output.manualChunks to improve chunking: https://rollupjs.org/configuration-options/#output-manualchunks
- Adjust chunk size limit for this warning via build.chunkSizeWarningLimit.

The whole app, including Leaflet and the MapTiler SDK, is one 2 MB JavaScript file. It is a warning, not an error, but every visitor downloads all of it before seeing anything. Step 28 lazy-loads the map to split it (index drops to about 623 kB). npm run preview serves dist/ locally so you can test the real build — which is how the broken production map marker was found (step 25).

vite.config.ts: plugins and the alias

import { defineConfig } from "vite"
import react from "@vitejs/plugin-react"
import tailwindcss from "@tailwindcss/vite"
import svgr from "vite-plugin-svgr"
import path from "path"

// https://vite.dev/config/
export default defineConfig({
  plugins: [react(), tailwindcss(), svgr()],
  resolve: {
    alias: {
      "@": path.resolve(__dirname, "./src"),
    },
  },
})
PartWhat it doesAdded in
react()Compiles JSX and enables Fast Refresh.step 2 (from the template)
tailwindcss()Scans your files for class names and generates the CSS for them (chapter 4).step 3
svgr()Makes import Sun from "/src/assets/sun.svg?react" return a React component. src/vite-env.d.ts references vite-plugin-svgr/client so TypeScript knows that import's type.step 9
resolve.aliasRewrites imports that start with @/ to the src folder. path.resolve(__dirname, ...) builds an absolute path; __dirname and the path module need @types/node, which is why it is a dev dependency.step 12

Environment variables and the VITE_ prefix

The OpenWeather key is read in api.ts as import.meta.env.VITE_API_KEY (the presenter sets it up around 17:59, step 5). Vite reads .env files from the project root when it starts, and only variables whose names start with VITE_ are made available to your code. At build time Vite replaces each import.meta.env.VITE_... with the literal value. We built with two variables in a .env file and logged both:

VITE_API_KEY=TESTKEY123
SECRET_KEY=SECRETABC

console.log("env","TESTKEY123",void 0)

The prefixed value was pasted into the bundle as plain text; the unprefixed one became void 0 (undefined). Three practical consequences:

  1. Restart the dev server after editing .env. Vite reads it at startup.
  2. VITE_ means public. Anyone can open the deployed JavaScript and read the key. The prefix exists to stop you exposing other variables by accident; it does not hide anything. See chapter 5 and step 28.
  3. Keep .env out of git anyway. The repo's .gitignore covers *.local (so .env.local is ignored) but not .env. Use .env.local, or add .env to .gitignore.

TypeScript sees import.meta.env.VITE_API_KEY as any, because Vite's ImportMetaEnv type allows any extra key. A typo like VITE_APIKEY type-checks fine and is simply undefined at run time — the API then answers 401.

TypeScript configuration: three files

The Vite template splits TypeScript settings into three files, because two different kinds of code live in the repo: browser code in src/ and Node code in vite.config.ts.

The options worth knowing in tsconfig.app.json:

OptionMeaning for you
"target": "ES2022", "lib": ["ES2022", "DOM", "DOM.Iterable"]Which JavaScript features and built-in APIs (like document, fetch) the type checker knows about.
"moduleResolution": "bundler"Resolve imports the way Vite does (no file extensions needed, package.json "exports" respected).
"noEmit": truetsc only checks; Vite produces the JavaScript.
"jsx": "react-jsx"Use the automatic JSX runtime, so files don't need import React.
"verbatimModuleSyntax": trueType imports must say import type (error TS1484 otherwise — see chapter 1).
"strict": trueThe full set of strict checks, including null checks.
"noUnusedLocals", "noUnusedParameters"An unused variable or parameter is an error, so it fails npm run build.
"erasableSyntaxOnly": trueForbids TypeScript features that generate code (like enum), so stripping types is always enough.
"baseUrl" + "paths": { "@/*": ["./src/*"] }Tells the type checker what @/ means.

Path aliases: one import, two tools

import { getAirPollution } from "@/api" in SidePanel.tsx is read by two separate programs. TypeScript needs paths in the tsconfig to type-check it; Vite needs resolve.alias to find the file. The presenter sets both up while following the shadcn Vite guide (around 2:02:19, step 12). We removed each in turn from a copy of the repo:

src/components/SidePanel.tsx(1,33): error TS2307: Cannot find module '@/api' or its corresponding type declarations.
src/components/SidePanel.tsx(2,29): error TS2307: Cannot find module '@/types' or its corresponding type declarations.

error during build:
[vite]: Rollup failed to resolve import "@/api" from ".../src/components/SidePanel.tsx".
This is most likely unintended because it can break your application at runtime.

The repo also imports SVGs as "/src/assets/hamburger.svg?react". A path starting with / is resolved by Vite from the project root, so it works without the alias; "@/assets/hamburger.svg?react" would work too and is more consistent.

ESLint: catching mistakes the compiler doesn't

A linter reads your code and reports patterns that are legal but probably wrong. The repo uses ESLint 9's "flat config":

export default defineConfig([
  globalIgnores(['dist']),
  {
    files: ['**/*.{ts,tsx}'],
    extends: [
      js.configs.recommended,
      tseslint.configs.recommended,
      reactHooks.configs['recommended-latest'],
      reactRefresh.configs.vite,
    ],
    languageOptions: {
      ecmaVersion: 2020,
      globals: globals.browser,
    },
  },
])
Rule setCatches
js.configs.recommendedGeneral JavaScript mistakes: unused variables, unreachable code, empty destructuring patterns (no-empty-pattern).
tseslint.configs.recommendedTypeScript-specific issues, e.g. {} used as a type (@typescript-eslint/no-empty-object-type), any.
reactHooks.configs['recommended-latest']The rules of hooks and missing effect dependencies (examples in chapter 2).
reactRefresh.configs.viteFiles that would break Fast Refresh (react-refresh/only-export-components).

Running npm run lint on the committed repo reports 15 errors. Here is one file's worth, plus the summary:

src\components\LightDarkToggle.tsx
  6:14  error  The `{}` ("empty object") type allows any non-nullish value, including literals like `0` and `""`.
- If that's what you want, disable this lint rule with an inline comment or configure the 'allowObjectTypes' rule option.
- If you want a type meaning "any object", you probably want `object` instead.
- If you want a type meaning "any value", you probably want `unknown` instead  @typescript-eslint/no-empty-object-type
  8:41  error  Unexpected empty object pattern  no-empty-pattern

src\components\ThemeProvider.tsx
  45:14  error  Fast refresh only works when a file only exports components. Use a new file to share constants or functions between components  react-refresh/only-export-components

✖ 15 problems (15 errors, 0 warnings)

What the 15 errors mean:

  • 14 errors from 7 files (LightDarkToggle and the six skeletons) share one cause: type Props = {} plus function X({}: Props). These components take no props, so the fix is to delete both the type and the empty pattern: export default function CurrentSkeleton() { ... }.
  • 1 error in ThemeProvider.tsx: the file exports the ThemeProvider component and the useTheme hook. Fast Refresh can only hot-swap files that export just components; otherwise it falls back to a full reload. The fix is to move useTheme (and the context) into its own file, src/hooks/useTheme.ts, as step 27 does — after that, lint reports 0 problems.

Lint is not part of npm run build, which is why the repo builds with 15 lint errors. Many teams run lint in CI or as a pre-commit check so problems can't be merged; most editors (with the ESLint extension) also underline them as you type.

New to the terminal? Running these commands

All commands run in a terminal opened in the project folder (the one containing package.json). Running npm run dev from a parent folder fails with "Missing script" or "Could not read package.json". The dev server keeps running until you press Ctrl+C; open a second terminal for other commands. After editing vite.config.ts or .env, stop and restart it.

Pitfalls
  • "It works in dev, so it builds." Dev strips types without checking; tsc -b in the build may still fail. Run npm run build before pushing.
  • "It builds, so it works." The production bundle can behave differently (the Leaflet marker bug). Run npm run preview too.
  • Alias configured in one place only → either TS2307 or "Rollup failed to resolve".
  • .env edits ignored → restart the dev server; check the name starts with VITE_.
  • Treating VITE_ variables as secret → they are inlined into public JavaScript.
  • Deleting package-lock.json to "fix" an install → you lose the exact versions; prefer npm ci.
Recap
  • package.json holds scripts and version ranges; package-lock.json holds exact versions; npm ci reproduces them.
  • npm run dev = fast, unchecked, unbundled with HMR; npm run build = tsc -b type-check, then a bundled, minified dist/; npm run preview serves it.
  • Vite plugins (react, tailwindcss, svgr) extend what imports can do; VITE_ variables are inlined into the bundle and are public.
  • Three tsconfig files separate browser code from Node code; strict, verbatimModuleSyntax and the unused-variable checks shape what you can write.
  • The @/ alias needs both paths (TypeScript) and resolve.alias (Vite).
  • ESLint reports file, position, message and rule; the repo's 15 errors come from empty {} props and a hook exported next to a component.
